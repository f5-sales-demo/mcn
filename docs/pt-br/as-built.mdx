Esta implantação demonstra **alta disponibilidade ativo/ativo de Customer Edge no Azure**
sem nenhum load balancer do Azure na frente dos CEs. Três CEs originam, cada um, a mesma rota
de host por eBGP, e o Azure Route Server instala todos os três como next hops de custo igual na
VNet. A malha de roteamento, e não um load balancer, é portanto onde a distribuição de tráfego
e a remoção de nós com falha devem acontecer.

Tudo o que é mostrado abaixo foi executado contra a implantação ativa, e a saída é a saída que
ela produziu. O que essa frase *não* cobre — failover, como o tráfego se divide entre os
três next hops e por que o VIP apresenta perdas brevemente em uma construção nova — é destacado
explicitamente em vez de deixado como suposição.

## O que está implantado

```text
                  Azure Route Server  ce-ha-lab-rrs  ASN 65515
                          10.0.4.4  and  10.0.4.5
                                      |
              +-----------------------+-----------------------+
              |                       |                       |
        eastus01-bgp            eastus02-bgp            eastus03-bgp     eBGP
              |                       |                       |      CE ASN 64512
        10.0.1.4                10.0.1.5                10.0.1.6     <- CE eth0 / SLO
     f5-xc-ce-vm-01          f5-xc-ce-vm-02          f5-xc-ce-vm-03
    ar-bgp-eastus01         ar-bgp-eastus02         ar-bgp-eastus03
              |                       |                       |
              +----- each advertises 10.250.0.10/32 -----------+
                          three-way ECMP into the VNet
```

| Tenant do F5 Distributed Cloud | `f5-sales-demo` — `https://f5-sales-demo.console.ves.volterra.io` |

| VMs do Azure | `f5-xc-ce-vm-01/02/03`, três NICs cada (management/SLO, external, internal/SLI) |
| Troca de rotas | Azure Route Server `ce-ha-lab-rrs`, ASN `65515`, instâncias `10.0.4.4` e `10.0.4.5` |
| Peerings | um por CE — `eastus01-bgp`, `eastus02-bgp`, `eastus03-bgp` — ASN do CE `64512` |

| Resource group | `rg-mcn-ce-ha-rmordasiewicz` |

<Aside type="caution" title="O VIP precisa ficar fora de todo CIDR de VNet">
`terraform/main.tf` contém um bloco `check` que afirma que o VIP está fora dos CIDRs do hub
e do spoke, e recusa o plano caso contrário. A razão declarada é que um VIP dentro de um
CIDR de VNet perde para a rota de sistema da própria VNet, apesar de a rota BGP ser mais específica.

Trate essa proteção como o contrato: se você reapontar esta demonstração para um endereçamento diferente, o
VIP tem de sair das faixas da VNet junto com ele.
</Aside>

## O tenant é configuração, não o que seu shell está exportando

`var.expected_xc_tenant` nomeia o tenant, tem como padrão `f5-sales-demo` e é o único
lugar em que ele é nomeado. `providers.tf` deriva dele o `api_url` do provider `xcsh`, o que
deliberadamente sobrepõe qualquer `XCSH_API_URL` no ambiente, e uma `postcondition` em
`terraform/main.tf` falha o **plan** quando o ambiente nomeia um tenant diferente.

Leia qualquer uma das duas metades sem executar nada que altere estado:

```bash
cd terraform
terraform output -raw xc_tenant       # what the deployment targets
terraform output -raw xc_env_tenant   # what your shell claims — diagnostic only
```

```text
f5-sales-demo
f5-sales-demo
```

<Aside type="danger" title="Esta proteção existe porque a demonstração silenciosamente se realocou para o tenant errado">
A demonstração MCN foi construída em `f5-sales-demo`. Um arquivo de credenciais passou depois a exportar uma
`XCSH_API_URL` de `f5-amer-ent`; os applies subsequentes emitiram um token para aquele tenant, as VMs de CE
se registraram novamente lá, e seus registros em `f5-sales-demo` foram abandonados. Todo plan
nesse intervalo estava limpo, porque nada na configuração tinha opinião sobre o tenant
([issue 696](https://github.com/f5-sales-demo/mcn/issues/696), corrigido em
[PR 697](https://github.com/f5-sales-demo/mcn/pull/697)). Recuperar isso significou destruir a
stack no tenant errado e reconstruí-la no correto.

O sintoma a reconhecer, porque não é autoexplicativo: um token emitido para outro
tenant falha no endpoint fixado com um `401` puro, o que parece exatamente uma
credencial expirada. Se uma credencial que você acredita ser boa retornar `401`, compare as duas saídas
acima antes de emitir outro token.
</Aside>

## Comprove que está saudável antes de apresentar

Quatro verificações, nesta ordem. Cada uma restringe onde uma falha estaria, de modo que uma falha lhe diz
algo em vez de apenas que algo está errado.

<Steps>

1. **Todos os três sites estão `ONLINE`.** Nada a jusante pode ser verdade se isso não for.

   ```bash
   for s in ar-bgp-eastus01 ar-bgp-eastus02 ar-bgp-eastus03; do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **Cada peering está aprendendo o anúncio de VIP daquele CE.** Consulte cada peering
   separadamente — veja a armadilha abaixo, porque é aqui que a demonstração mais frequentemente parece
   quebrada e não está.

   ```bash
   for p in eastus01-bgp eastus02-bgp eastus03-bgp; do
     echo "--- $p"
     az network routeserver peering list-learned-routes \
       --name "$p" --routeserver ce-ha-lab-rrs -g rg-mcn-ce-ha-rmordasiewicz \
       --query "RouteServiceRole_IN_0[].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp

   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp

   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   Três peerings, três next hops diferentes, um prefixo. Isso é o lado do anúncio
   do ECMP comprovado.

3. **As rotas efetivas do cliente carregam todos os três next hops.** Este é o próprio ECMP,
   conforme a VNet o programou — não o que os CEs afirmam, mas o que o Azure fez com isso.

   ```bash
   az network nic show-effective-route-table \
     --name ar-ecmp-clientVMNic -g rg-mcn-ce-ha-rmordasiewicz \
     --query "value[?addressPrefix[0]=='10.250.0.10/32']" -o json
   ```

   ```json
   [
     {
       "addressPrefix": ["10.250.0.10/32"],
       "nextHopIpAddress": ["10.0.1.5", "10.0.1.4", "10.0.1.6"],
       "nextHopType": "VirtualNetworkGateway",
       "source": "VirtualNetworkGateway",
       "state": "Active"
     }
   ]
   ```

   `state: Active` com três entradas em `nextHopIpAddress` é a verificação. **A ordem
   desses três não é significativa e não é estável** — o Azure os retorna em uma ordem
   diferente entre chamadas, então conte-os em vez de comparar a lista com uma execução anterior. Um
   next hop onde você espera três significa que um CE parou de anunciar, e o passo 2 identifica
   qual.

4. **O VIP atende tráfego.** A partir da VM cliente, e **com o cabeçalho `Host`** — veja
   a segunda armadilha abaixo. Amostre requisições suficientes para ver um problema: algumas dezenas aparecem como
   100 % mesmo durante a janela de convergência descrita mais adiante.

   ```bash
   az vm run-command invoke -g rg-mcn-ce-ha-rmordasiewicz -n ar-ecmp-client \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts 'ok=0; fail=0
                for i in $(seq 1 60); do
                  c=$(curl -s -o /dev/null -m 5 -w "%{http_code}" \
                        -H "Host: ar-bgp-ecmp.bankexample.com" http://10.250.0.10/)
                  [ "$c" = 200 ] && ok=$((ok+1)) || fail=$((fail+1))
                done
                echo "OK=$ok FAIL=$fail"'
   ```

   ```text
   OK=60 FAIL=0
   ```

</Steps>

## Armadilha: um peering mostra uma rota, e isso está correto

`list-learned-routes` tem escopo no peering que você nomeia. Ele reporta o que **aquele** peer
anunciou, não a tabela inteira do Route Server.

Assim, consultar apenas `eastus01-bgp` retorna um único `10.250.0.10/32` via `10.0.1.4`, e é
tentador ler isso como "somente um CE está anunciando — os outros dois estão fora". Nada
está fora. Os outros dois anúncios estão visíveis em seus próprios peerings, que é sobre o que o
passo 2 acima itera.

Confirmar ECMP a partir de uma única consulta de peering não é possível. Itere pelos três
peerings, ou leia a tabela de rotas efetivas do cliente, que mostra o resultado mesclado em uma
única chamada.

## Armadilha: uma requisição por IP puro retorna 404

O load balancer faz correspondência por `Host`. O VIP não é um servidor virtual que serve qualquer coisa
a quem se conectar ao endereço.

```text
curl -H 'Host: ar-bgp-ecmp.bankexample.com' http://10.250.0.10/   ->  200   (10 of 10)
curl                                        http://10.250.0.10/   ->  404
```

Ambas foram produzidas na mesma execução contra a implantação saudável. **Um 404 por
IP puro é a prova de que o caminho funciona** — a requisição alcançou o CE, o proxy do CE respondeu e
recusou porque nenhum domínio configurado correspondeu. Ler isso como uma interrupção o leva
a examinar o BGP, onde você não encontrará nada errado.

O mesmo se aplica durante uma demonstração: se você digitar o endereço em um navegador em vez de
resolver o domínio para ele, você recebe o 404.

## O VIP descarta requisições durante os primeiros três quartos de hora, e então para

Em uma stack recém-construída o VIP perde uma pequena fração das requisições por aproximadamente os primeiros
45 minutos após os CEs atingirem `ONLINE`, e então atende de forma limpa. Medido em 1.470
requisições de `ar-ecmp-client`, todas com o cabeçalho `Host`:

| Janela | Requisições | Falhas | Taxa |
| --- | --- | --- | --- |
| Primeiros ~45 minutos após o ECMP subir | 570 | 12 | **2,11 %** |
| Os 23 minutos seguintes | 900 | **0** | **0,00 %** |

Toda falha foi `curl: (28)` — um timeout com zero bytes recebidos — não um status de erro
HTTP. A última ocorreu cerca de 43 minutos após o ECMP subir. Das 900 requisições limpas,
400 rodaram com timeout de 30 segundos e todas terminaram em menos de 2 segundos, então
nada estava sendo escondido por um timeout curto.

**A origem não foi a causa.** Um lote de controle direto para a origem
(`http://20.98.232.135/`, ignorando o VIP) rodou 120 de 120 limpas *simultaneamente com*
lotes de VIP falhando. A falha está em algum ponto do caminho VIP, ECMP ou CE.

Duas coisas que isto deliberadamente não é chamado de:

- **Não é um defeito de estado estacionário.** Ele se resolve completamente e permanece resolvido. Uma demonstração que está
  ativa há uma hora não tem esse problema — 60 de 60 na verificação acima, e ele
  reproduziu limpo novamente na stack reconstruída.
- **Não é atribuível a um CE específico.** Nada nesta topologia fornece um listener HTTP
  por nó, então não há maneira de vincular uma requisição descartada ao nó que a descartou.
  As interfaces externas do CE (`10.0.2.x`) não têm listener HTTP algum — somente o `/32` do VIP
  responde.

Ele reproduziu em uma reconstrução limpa em um tenant diferente, portanto acompanha a topologia e não
o ambiente.

<Aside type="caution" title="Não amostre 40 requisições e conclua que está tudo bem">
Lotes de 40 a 50 aparecem como 100 % na maior parte do tempo, mesmo dentro da janela de falha. Foi
assim que isso foi inicialmente caracterizado erroneamente como uma falha contínua de baixa taxa e depois como falha alguma.
Amostre 100 ou mais, em lotes separados no tempo.
</Aside>

## A aprovação de registro é automatizada, e o apply ainda é de duas fases

A aprovação de registro não requer mais um humano no console. No provider **v3.81.1** o
recurso `xcsh_registration_approval` a executa, e o módulo do site resolve qual
registro aprovar.

Isso ainda não torna a implantação um único `apply` sem intervenção, e a razão vale
ser compreendida antes de você observar uma primeira execução e concluir que ela falhou:

- O objeto de registro de um CE é nomeado **`r-<uuid>`**. Ele nunca é nomeado a partir do site, então
  nada pode prever o nome no momento do plan.
- O registro só existe depois que a VM inicializou e o `vpm` se registrou.
- Portanto o **primeiro apply não planeja nenhuma aprovação**. Reaplique depois que os CEs tiverem se registrado
  e as aprovações forem criadas.

`terraform/main.tf` documenta essa ordenação no topo do arquivo, que é a versão
autoritativa — a sequência de deploy vive junto com o código que a implementa.

<Aside type="caution" title="Um site recém-criado não é imediatamente alcançável pela API operate">
Por aproximadamente 25 a 30 minutos após um novo site reportar `ONLINE`, os endpoints `vpm/debug`
respondem com uma página `503` do BIG-IP dizendo `The requested URL was rejected`. Parece
um bloqueio de web application firewall ou um token revogado e não é nenhum dos dois. Aguarde e tente novamente.

Isso afeta uma demonstração recém-construída, não uma em execução.
</Aside>

## Alcançando o Site CLI

Diagnósticos rotineiros no equipamento passam pela API de debug, que já está roteirizada aqui.
Confirme que a superfície de comandos ainda corresponde ao que a documentação descreve:

```bash
bash scripts/capture-sitecli.sh --check --site ar-bgp-eastus01 --node f5-xc-ce-vm-01
```

```text
catalog matches the live CE (build crt-20250613-3382, 34 commands)
```

`--check` não escreve nada, portanto é seguro contra a demonstração ativa.

Para os comandos que aquela API não repassa, esta implantação também tem **SSH de operador para a
conta `admin` do appliance**, cujo shell de login é o Site CLI. Está verificado em todos os
três CEs. Conecte-se ao endereço interno (SLI) a partir de um host dentro da VNet, com um
terminal alocado.

<Aside type="danger" title="Nunca fixe no código um endereço interno de CE — eles são reatribuídos em cada reconstrução">
O Azure não preserva qual CE recebe qual endereço na sub-rede interna. Após a reconstrução
mais recente, `f5-xc-ce-vm-01`, `-02` e `-03` detêm `10.0.3.7`, `10.0.3.5` e `10.0.3.4`
respectivamente: não em ordem de nó, não contíguos e diferentes do que detinham antes.
A própria NIC do cliente de teste está na mesma sub-rede e já teve um endereço que um CE detinha
anteriormente.

Leia-os em vez de memorizá-los:

```bash
cd terraform
terraform output -json ce_sli_private_ips
```

```json
{"eastus01":"10.0.3.7","eastus02":"10.0.3.5","eastus03":"10.0.3.4"}
```

Sem o state do Terraform à mão, pergunte ao Azure pelo que você quer usando o nome da NIC, que *é*
estável:

```bash
az network nic show -g rg-mcn-ce-ha-rmordasiewicz \
  -n f5-xc-ce-vm-01-internal-nic \
  --query ipConfigurations[0].privateIPAddress -o tsv
```

</Aside>

```bash
SLI=$(terraform output -json ce_sli_private_ips | jq -r '.eastus01')
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<vm-in-vnet> "admin@$SLI"
```

```text
Registration Status: PROVISIONED
SLO IP: 10.0.1.4/26
WELCOME IN SITE CLI
```

<Aside type="caution" title="Esse acesso existe porque estes CEs foram construídos com ele — não pode ser adicionado depois">
A chave de operador é escrita pelo `write_files` do cloud-init, que roda uma vez na primeira inicialização.
`custom_data` é replace-only, portanto adotar isso em CEs que já estão em execução **substitui
cada VM de CE**. Isso é uma reconstrução da frota, não uma mudança de configuração.

Já foi pior do que isso: um CE substituído nunca conseguia se registrar novamente, porque o registro
do nó destruído ainda mantinha o índice único
`(tenant, cluster_name, hostname)` do control plane — e o `terraform plan` reportava "No changes" durante
todo o tempo em que a frota estava fora. A recuperação exigiu duas reconstruções completas. Isso está corrigido
([issue 674](https://github.com/f5-sales-demo/mcn/issues/674), fechada pela
[PR 693](https://github.com/f5-sales-demo/mcn/pull/693)): o ciclo de vida do objeto de site agora está
acoplado à instância da VM do CE, então substituir a VM substitui o site, e excluir o site
leva seus registros consigo antes de o nó substituto inicializar.

Para esta implantação a mudança já está aplicada e a frota está saudável. Quem for adotá-la
em outro lugar deve ler primeiro a [página de SSH](../customer-edge/access/ssh/).
</Aside>

## Duas outras armadilhas de medição

Ambas produziram respostas erradas com confiança neste ambiente, e nenhuma delas é
óbvia.

- **Sonde de dentro da VNet, não da sua estação de trabalho.** O Netskope completa o handshake TCP
  ele mesmo em portas comuns, então uma sondagem da estação de trabalho reporta uma porta **aberta** que está
  de fato fechada. As portas 80 e 443 aparecem como abertas nos endereços públicos do CE a partir de uma
  estação de trabalho e estão fechadas quando sondadas de dentro da VNet. Use `ar-ecmp-client`.
- **A porta 22 em um CE responde somente no endereço interno (SLI).** Sondado a partir de
  `ar-ecmp-client`, o endereço interno de cada CE retorna `SSH-2.0-OpenSSH_8.7`, enquanto seus
  endereços de management e external expiram — assim como um endereço não utilizado usado como controle.
  A eth0 é renomeada para `a-i-eth0` e não carrega IP de host, porque o datapath é seu proprietário. Portanto,
  sondar o endereço pelo qual você conhece o nó não lhe diz nada sobre o estado de SSH do nó, e
  o endereço SLI é o correto para conectar. Obtenha esse endereço de
  `terraform output -json ce_sli_private_ips`; não presuma que a sub-rede interna seja
  exclusiva de CEs, porque a NIC do cliente de teste também está nela.

<Aside type="note" title="O que esta página não afirma">
Três coisas que um leitor poderia razoavelmente esperar aqui estão ausentes, porque não foram
exercitadas contra a implantação:

- **O failover não foi testado.** Os três next hops de custo igual estão verificados como instalados; o que
  acontece com a tabela de rotas quando um CE é parado não é mostrado, então não ensaie uma
  demonstração de failover a partir desta página sem antes testá-la.
- **A distribuição de tráfego entre os três next hops não foi medida.** 1.470 requisições ao
  VIP estão contabilizadas acima, o que estabelece que o caminho funciona e como ele se comporta
  ao longo do tempo. Nada disso mostra como essas requisições foram distribuídas entre os três next hops,
  e esta topologia não oferece listener HTTP por nó para atribuí-las.
- **A causa do transiente de convergência não está estabelecida.** Ele está caracterizado — quando
  acontece, por quanto tempo, que a origem permanece limpa durante todo o período — e não explicado.

</Aside>
