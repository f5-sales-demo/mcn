Um Customer Edge (CE) é o nó do F5 Distributed Cloud que este repositório provisiona no
Azure — `terraform/modules/ce-node`, construído a partir da imagem de marketplace
`volterraedgeservices/volterra-node`.

Ele executa o data plane (Argo), o control plane (Vega), um proxy Envoy, uma stack
Kubernetes e o `vpm`, o agente que registra o nó e gerencia todo o resto nele.

Quando um CE apresenta comportamento inesperado, o Site CLI é o instrumento. A primeira decisão é qual
caminho de acesso se aplica, e errar isso desperdiça tempo de uma forma que parece um
nó defeituoso.

## Dois caminhos de acesso, e eles não são intercambiáveis

A debug API alcança o nó **através do control plane do F5 Distributed Cloud**.
Essa é justamente a razão pela qual a distinção importa: a API só pode responder depois que o nó
foi registrado e reporta `ONLINE`.

Um nó que falhou no registro — cloud-init inválido, um token expirado, sem rota para
`register.ves.volterra.io` — é exatamente o caso em que você precisa de diagnóstico, e
exatamente o caso que a API não pode atender.

SSH não é uma terceira opção. O `sshd` roda no nó e responde em seu endereço interno (SLI),
mas a conta `admin` não consegue se autenticar: o `vpm` ignora esse usuário, portanto a
`ssh_key` que você configura no objeto de site nunca é aplicada. Nenhuma regra de security group
muda isso. A evidência está na página [SSH](./access/ssh/), que existe porque
cada sintoma ali se parece com uma falha de firewall ou de credencial.

Então: se o site estiver `ONLINE`, use a debug API. Se não estiver, o console serial é a
única forma de entrar.

<Aside type="caution" title="Verifique primeiro o estado do site">
Uma única requisição indica em qual caminho você está:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/config/namespaces/system/sites/<site>" \
  | jq -r '.spec.site_state'
```

`ONLINE` significa que a debug API funcionará. Qualquer outra coisa — ou um site que não
existe — significa console serial.
</Aside>

## Regras de segurança

Elas valem para todos os comandos em todas as páginas abaixo.

- **Somente leitura, a menos que você tenha certeza.** A superfície de comandos é dividida em dois
  níveis de privilégio, e o nível `Exec` ou altera o nó ou lê um marcador de
  estado. Nada nestas páginas executa um comando `Exec`, e o harness de captura
  também não.
- **Nunca presuma que um comando é seguro pelo nome.** `ip-link-set` parece uma
  consulta e derruba uma interface. `systemctl-restart-crio` reinicia o
  container runtime sob um data plane ativo.
- **Prefira o comando mais restrito que responda à pergunta.** `health` e
  `diagnosis` resumem o nó de forma econômica; `flow-l` despeja uma tabela de fluxos com
  629.760 entradas.
- **Um CE atende tráfego ativo.** Estes são ambientes de demonstração compartilhados. Presuma que alguém
  está apresentando a partir do site que você está depurando.

## O que está documentado aqui

Todos os comandos acessíveis pela debug API na build de software que este tenant executa,
cada um com saída capturada de um nó ativo em vez de transcrita de outro lugar.

A [referência de comandos](./commands/) lista todos eles com sua categoria, nível de
privilégio e transporte; os [fluxos de trabalho](./workflows/) os encadeiam nas sequências que você
realmente usa quando algo está errado.

As partes do Site CLI que existem apenas no equipamento — `configure`, `configure-network`,
`factory-reset`, `upgrade` e cerca de sessenta outros comandos `ExecCLI` — não são
abordadas.

Elas são acessíveis apenas a partir de uma sessão de console serial, portanto nada sobre elas pode ser
verificado programaticamente, e sintaxe de comando não verificada é o defeito que esta
documentação existe para evitar repetir.
