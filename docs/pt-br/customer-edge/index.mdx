Um Customer Edge (CE) é o nó do F5 Distributed Cloud que este repositório provisiona no
Azure — `terraform/modules/ce-node`, construído a partir da imagem de marketplace
`volterraedgeservices/volterra-node`.

Ele executa o plano de dados (Argo), o plano de controle (Vega), um proxy Envoy, uma pilha
Kubernetes e o `vpm`, o agente que registra o nó e gerencia todo o restante nele.

Quando um CE apresenta comportamento inadequado, o Site CLI é o instrumento. A primeira
decisão é qual caminho de acesso se aplica, e errar nisso desperdiça tempo de um modo que
se parece com um nó quebrado.

## Dois caminhos de acesso, e eles não são intercambiáveis

    href="./access/debug-api/"
  />
  <LinkCard
    title="Serial console"
    description="For a node that never registered. The only route when the API cannot answer."
    href="./access/serial-console/"
  />
</CardGrid>

A debug API alcança o nó **através do plano de controle do F5 Distributed Cloud**.
Essa é toda a razão pela qual a distinção importa: a API só pode responder depois que o nó
foi registrado e reporta `ONLINE`.

Um nó que falhou ao registrar — cloud-init incorreto, um token expirado, nenhuma rota para
`register.ves.volterra.io` — é exatamente o caso em que você precisa de diagnóstico, e
exatamente o caso que a API não pode atender.

O [SSH](./access/ssh/) é a terceira opção, e a única que alcança toda a superfície de
comandos do appliance — a debug API expõe 34 comandos e o nó em si oferece muitos mais.
Duas coisas o restringem. O `sshd` responde somente no endereço interno (SLI) do nó,
portanto é necessário um host dentro da VNet; e a chave é escrita pelo cloud-init no
primeiro boot, porque o campo `ssh_key` no objeto do site é inerte — o `vpm` ignora o
usuário `admin` e nunca o aplica. Habilitá-lo em nós em execução, portanto, significa
substituí-los.

Então: se o site está `ONLINE` e 34 comandos são suficientes, use a debug API. Se você
precisa do restante da superfície e consegue alcançar a VNet, use SSH. Se o registro é o
que está quebrado, o console serial é a única forma de entrar.

<Aside type="caution" title="Verifique primeiro o estado do site">
Uma única requisição informa em qual caminho você está:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/config/namespaces/system/sites/<site>" \
  | jq -r '.spec.site_state'
```

`ONLINE` significa que a debug API vai funcionar. Qualquer outra coisa — ou um site que não
existe — significa console serial.
</Aside>

## Regras de segurança

Estas valem para todos os comandos em todas as páginas abaixo.

- **Somente leitura, a menos que você tenha certeza.** A superfície de comandos é dividida
  em dois níveis de privilégio, e o nível `Exec` ou modifica o nó ou lê um marcador de
  estado. Nada nestas páginas executa um comando `Exec`, e nem o harness de captura.
- **Nunca presuma que um comando é seguro pelo nome.** `ip-link-set` parece uma
  consulta e derruba uma interface. `systemctl-restart-crio` reinicia o runtime de
  contêineres sob um plano de dados ativo.
- **Prefira o comando mais restrito que responda à pergunta.** `health` e
  `diagnosis` resumem o nó de forma econômica; `flow-l` despeja uma tabela de fluxos com
  629.760 entradas.
- **Um CE serve tráfego ao vivo.** Estes são ambientes de demonstração compartilhados.
  Presuma que alguém está apresentando a partir do site que você está depurando.

## O que está documentado aqui

Todos os comandos alcançáveis pela debug API na build de software que este tenant executa,
cada um com saída capturada de um nó ao vivo, e não transcrita de outro lugar.

A [referência de comandos](./commands/) lista todos eles com sua categoria, nível de
privilégio e transporte; os [workflows](./workflows/) os encadeiam nas sequências que você
realmente usa quando algo está errado.

As partes do Site CLI disponíveis apenas no próprio equipamento — `configure`,
`configure-network`, `factory-reset`, `upgrade` e cerca de sessenta comandos `ExecCLI`
adicionais — não são cobertas, porque sua saída não foi capturada de um nó ao vivo da forma
como todas as páginas abaixo foram.

Elas, no entanto, não estão mais fora de alcance. O `scripts/sitecli_ssh_harvest.py`
percorre o próprio menu de autocompletar do appliance via [SSH](./access/ssh/) e registra a
descrição que o appliance fornece para cada comando, de modo que a superfície possa ser
medida em vez de presumida. Sua execução é negada por padrão — ele enumera tudo e executa
apenas uma lista de permissões — porque sintaxe de comando não verificada, e *efeitos* de
comando não verificados, são o defeito que esta documentação existe para evitar repetir.
