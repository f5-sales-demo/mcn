Capturado em 28/07/2026 de um CE desta implantação. Estes são comandos executados no próprio
equipamento, portanto chegam pela CLI do Site em vez da API de depuração;
`sitecli/exec-catalog.json` registra a superfície e `sitecli/capture-manifest.json` registra
qual nó.

O Envoy termina e faz proxy do tráfego de aplicação no Customer Edge. Estes quatro comandos
consultam sua interface administrativa, e nenhum deles está na
[API de depuração](../../../access/debug-api/).

<Aside type="note" title="Todos eles começam com um medidor de progresso do curl">
São wrappers de `curl` em torno do endpoint administrativo do Envoy, invocados sem `-s`, de
modo que as duas ou três primeiras linhas de cada captura abaixo são o progresso da
transferência do curl escrito em stderr:

```text
  % Total    % Received % Xferd  Average Speed   Time    Time     Time  Current
                                 Dload  Upload   Total   Spent    Left  Speed
  0     0    0     0 …
```

Isso não é saída do Envoy nem um erro. É também útil: a contagem de bytes em `% Received`
indica se o Envoy retornou algo, o que distingue "nenhum listener configurado" de "a
interface administrativa não respondeu".
</Aside>

## `envoy-listeners`

Todos os listeners que o Envoy instalou, no formato `name:address:port`.

```bash
execcli envoy-listeners
```

```text file=../../../../_data/sitecli-envoy-listeners.txt
```

**O que observar.** Nesta implantação, o listener carrega `10.250.0.10:80` — o VIP que o CE
anuncia no BGP. Essa única linha conecta três camadas: se
[`show-ip-bgp-summary`](../../network/bgp/) mostrar o prefixo sendo anunciado mas este
listener estiver ausente, a rota está sendo atraída para um nó que não a atenderá, que é o
pior modo de falha em um conjunto ECMP, porque o tráfego é distribuído para um buraco negro.

O `[fe80:…]:80` ao final é o endereço link-local da interface à qual o listener está
vinculado.

**O que ele não informa.** Nada sobre a saúde dos upstreams — um listener existe
independentemente de haver algo alcançável atrás dele. Use `envoy-clusters` para isso.

## `envoy-clusters`

Todos os clusters, com seus limites de conexões e requisições por prioridade.

```bash
execcli envoy-clusters
```

```text file=../../../../_data/sitecli-envoy-clusters.txt
```

**O que observar.** As linhas seguem o formato `cluster::scope::key::value`. A entrada
`observability_name` identifica cada cluster, e o trio `default_priority::max_connections`,
`max_pending_requests` e `max_requests` é onde os limites de requisições aparecem — um
cluster travado em seu `max_pending_requests` está sendo limitado pela configuração e não
pelo upstream.

## `envoy-config-dump`

A configuração completa do Envoy em JSON. Grande: 126 KB em um nó de demonstração ocioso.

```bash
execcli envoy-config-dump
```

```text file=../../../../_data/sitecli-envoy-config-dump.txt
```

**O que observar.** O array de nível superior `configs` contém um objeto por tipo de
configuração — bootstrap, clusters, listeners, rotas, segredos. Recorra a ele quando um
listener ou cluster existir mas se comportar de forma inesperada, e faça buscas nele em vez
de lê-lo integralmente.

## `envoy-hc-config-dump`

A configuração de verificação de saúde especificamente.

```bash
execcli envoy-hc-config-dump
```

```text file=../../../../_data/sitecli-envoy-hc-config-dump.txt
```

**O que observar.** Nesta implantação, ele retorna um **único byte** — visível como `100 1`
no medidor do curl — o que significa que nenhuma configuração de verificação de saúde está
instalada. Esse é o estado esperado para um CE sem pools de origem com verificação de saúde,
e vale reconhecê-lo: um resultado vazio aqui não é uma consulta com falha.
