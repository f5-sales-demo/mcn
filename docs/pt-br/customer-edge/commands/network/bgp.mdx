O CE executa o FRR para BGP. Nesta topologia, ele estabelece peering com as duas instâncias
do Azure Route Server, anuncia o VIP e aprende o prefixo da VNet.

## `show-ip-bgp-summary`

Comece por aqui. Uma única tela informa se o peering está ativo e por quanto tempo ele tem
se mantido estável.

```bash
{"command":["show-ip-bgp-summary"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp-summary.txt
```

Leia `State/PfxRcd` primeiro. Um número corresponde à quantidade de prefixos recebidos e
significa que a sessão está estabelecida; qualquer outra coisa — `Active`, `Connect`, `Idle` — é
uma sessão que não está ativa. `Up/Down` mostra por quanto tempo o estado atual tem durado,
portanto uma sessão que fica reiniciando exibe um valor suspeitosamente pequeno.

<Aside type="caution" title="O vrf id aqui não é o que o rt espera">
Esta saída informa `vrf-id 3`. Essa é a numeração do FRR. O plano de dados Argo usa um
table id separado, e passar o número do FRR para
[`rt --dump`](../dataplane-forwarding/) retorna `No such file or directory`, o que
parece um nó defeituoso em vez de um argumento incorreto.
</Aside>

## `show-ip-bgp`

A tabela completa, com a seleção de melhor caminho visível.

```bash
{"command":["show-ip-bgp"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp.txt
```

`*` é uma rota válida, `>` o melhor caminho selecionado, `=` um membro de multipath. Na captura
acima, o prefixo aprendido da VNet `10.0.0.0/16` tem dois caminhos — um por cada instância do
Route Server — marcados como `*=` e `*>`: um melhor caminho mais um membro de multipath, de modo
que o nó distribui a carga do tráfego de retorno entre as duas instâncias. O VIP `10.250.0.10/32`
tem um único caminho `*>` porque este nó é o originador dele.

<Aside type="caution" title="O ECMP de três vias da demonstração não é visível nesta saída">
`show-ip-bgp` é a tabela de um único nó. O ECMP que esta implantação demonstra são três CEs
*diferentes* anunciando o mesmo `/32`, e ele é programado no lado do Azure — portanto nenhuma
tabela BGP de um único CE pode mostrá-lo, e a ausência de um marcador de multipath no VIP aqui
não é uma falha. Comprove isso a partir dos peerings do Route Server ou da tabela de rotas
efetiva do cliente; ambos estão na [página as-built](../../../../as-built/).
</Aside>

## `show-ip-bgp-neighbors`

Detalhes por vizinho: capacidades negociadas, temporizadores, contadores de mensagens e o
motivo do último reset.

```bash
{"command":["show-ip-bgp-neighbors"]}
```

Recorra a ele quando o resumo mostrar uma sessão instável e você precisar saber o motivo.
`Last reset` e seu motivo são as linhas úteis.

## `show-ip-bgp-neighbors-advertised-route`

O que este nó está informando aos seus peers, em oposição ao que ele conhece.

```bash
{"command":["show-ip-bgp-neighbors-advertised-route"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp-neighbors-advertised-route.txt
```

Este é o comando para "o VIP não está alcançável a partir da VNet". Se o VIP estiver
ausente aqui, o problema está neste nó e nenhuma análise do peer vai
ajudar.

A saída repete um bloco `bgp neighbor:` **por peer**, portanto nesta topologia você obtém os
mesmos dois prefixos duas vezes — uma para cada instância do Route Server. Isso não é uma
renderização duplicada: é o que confirma que o nó está anunciando para ambas. Um bloco presente para um
peer e ausente ou incompleto para o outro é o caso interessante.
