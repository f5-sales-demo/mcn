Duas variáveis do Terraform definem o software de um Customer Edge: `ce_os_version` para o
sistema operacional e `ce_sw_version` para o build do F5 Distributed Cloud. Ambas se comportam
de maneiras opostas à leitura óbvia, e o custo de errar é uma reconstrução de frota.

## O que os campos de versão fazem, em duas fases

Separar as fases é o ponto central. Quando confundidas, o comportamento parece
contraditório.

**Na primeira inicialização, um nó instala o que `ce_sw_version` especifica.**
`terraform/modules/ce-node` implanta a imagem do marketplace com `version = "latest"`, portanto
o build com que um nó chega é o que essa imagem atualmente distribui — e isso muda ao longo do tempo.
`ce_sw_version` escolhe o **destino**, não se algo acontece, e deixá-lo vazio significa que o
servidor escolhe, e não que o nó permanece onde está. O mesmo vale para `ce_os_version`.

Não assuma que a direção dessa mudança é para cima. `Observado em 2026-07-28`, a imagem
distribuía um build marcado como `20260703-e2c462a` — mais recente que o `crt-20250613-3382`
desta frota e mais recente que o `crt-20260201-0179` que o tenant estava anunciando. **Nomear
um build mais antigo do que o que a imagem carrega solicita que o nó retroceda, e isso pode
falhar** — veja a falha abaixo.

**Depois disso, nada é atualizado automaticamente.** O F5 Distributed Cloud anuncia um build
mais recente e aguarda. Um campo vazio, portanto, não significa "acompanhar o mais recente":
o nó permanece onde chegou inicialmente.

Ambas as fases são visíveis no objeto do site. `Observado em 2026-07-28`, esta frota:

```text
volterra_software_status.available_version   crt-20260201-0179
operating_system_status.available_version    9.2026.14
```

enquanto os nós executam `crt-20250613-3382` e SO `9.2024.6`. Um build mais recente está
disponível e não foi aceito — o estado estável, não uma atualização travada.

## Alterar uma versão exige uma reconstrução, e o Terraform não fará isso por você

`ce_os_version` e `ce_sw_version` são ambos **somente de criação**, e o modo de falha é pior
do que um apply rejeitado. Em ordem:

1. Você altera o valor e aplica. O Terraform propõe uma atualização no local.
2. A API **rejeita** — `[BAD_REQUEST] Invalid request parameters`.
3. Essa requisição rejeitada ainda limpa o campo no servidor, e a leitura do provider
   não o reporta. O estado do Terraform agora diverge do objeto ativo.
4. Cada plan subsequente propõe **a mesma mudança que falha**, indefinidamente.

Portanto, o Terraform não recorre a substituir o site. Ele trava, e permanece travado
até que você substitua o site e sua máquina virtual CE deliberadamente. Mover uma frota para
uma versão diferente é uma **reconstrução que você planeja**, não uma edição que você aplica.

<Aside type="danger" title="Todas as consequências de substituir um CE se aplicam">
Novas chaves de host SSH, endereços internos reatribuídos, um novo registro e a perda de
tudo que existia apenas no nó. O cloud-init é executado novamente na nova VM, portanto o
acesso SSH configurado dessa forma sobrevive — mas ele é executado *apenas* na primeira
inicialização, então qualquer coisa adicionada manualmente ao nó antigo é perdida.

Leia [SSH](./access/ssh/) sobre as consequências para chaves de host e endereços antes de
agendar isso.
</Aside>

A rejeição e a divergência de estado estão registradas nos comentários de
`terraform/modules/xc-site` neste repositório — verificadas lá em ambas as direções,

</Aside>

## Um build fixado pode falhar na instalação, e o site fica travado

Aceitar a fixação não é o mesmo que instalá-la. Em um Customer Edge Azure Secure Mesh v2 de
nó único recém-criado, fixado em `crt-20260201-0179`, o objeto do site reportou a versão
fixada imediatamente — e a instalação falhou:

```text
site_state        PROVISIONING
phase             UPGRADE_FAILED
result            Failed
last_installed    (empty)
message           stage: 10, app: voucher obj: voucher objKind: DaemonSet failed ...
                  required replicas: 1, current replicas: 0
```

`Observado em 2026-07-28.` A fixação do **sistema operacional** foi instalada normalmente na
mesma execução (`9.2024.6` para `9.2026.14`, `UPGRADE_COMPLETED`); apenas a instalação do
software falhou. O site nunca chegou a `ONLINE` e `last_installed_version` permaneceu vazio,
portanto nada reverteu para um build funcional — não havia uma instalação bem-sucedida
anterior para a qual reverter.

**O que tirar disso.** Uma versão que funciona em outro lugar não é evidência de que ela será
instalada no formato do seu site. O mesmo build estava `ONLINE` em um Customer Edge Azure que
não era Secure Mesh v2 e em um site Secure Mesh v2 no VMware; a combinação que falhou foi
Azure *e* Secure Mesh v2. Teste uma mudança de versão em um site descartável antes de aplicá-la
a uma frota, pois uma frota que falha dessa forma fica presa em `PROVISIONING` com a recriação
como única saída.

<Aside type="caution" title="Por que esta página não informa a causa">
O build solicitado era **mais antigo** do que o que a imagem do marketplace distribuía,
portanto o nó foi solicitado a retroceder. Essa é uma explicação plausível para a falha e
**não está estabelecida**: não se sabe se as duas strings de versão (`20260703-e2c462a` e
`crt-20260201-0179`) compartilham um esquema de numeração, e nenhuma captura de um nó da frota
estava disponível para comparação. A falha e a ordenação de versões são observações; o vínculo
entre elas não está comprovado.
</Aside>

## Qual build a documentação descreve

A referência de comandos neste site descreve **`crt-20250613-3382`**, o build que esta frota
executa. Comandos que existem apenas em builds mais recentes estão registrados em
`sitecli/command-classification.json` sob `not_on_this_build` e documentados separadamente, em
[comandos em builds mais recentes](./commands/on-box/newer-builds/), para que nada lá seja
lido como executável aqui. Veja também [comandos no nó](./commands/on-box/).

<Aside type="caution" title="Não planeje uma reconstrução para acessar comandos mais recentes">
Um build mais recente está disponível, e se ele será instalado corretamente nesta topologia
é incerto — há um relato de falha em sites Azure Secure Mesh v2 de nó único e uma
contra-observação de um Customer Edge executando-o. Nenhum dos dois pode ser confirmado a
partir do que permanece no tenant.

Como uma mudança de versão é uma reconstrução de frota, essa incerteza é o fato operativo:
trate o acesso a esses comandos como não comprovado, não como uma atualização programada.
As evidências e o experimento que resolveriam a questão estão registrados em
`sitecli/README.md`.
</Aside>
