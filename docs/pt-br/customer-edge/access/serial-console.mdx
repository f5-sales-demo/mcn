O Azure Serial Console se conecta à porta serial emulada do nó através da plataforma
Azure. Ele não atravessa o control plane do F5 Distributed Cloud, o data plane do nó,
nem qualquer caminho de rede que o nó controle — o que é exatamente o motivo pelo qual
funciona quando nada mais funciona.

Recorra a ele quando um CE **nunca subiu**: o registro falhou, o site está ausente
do tenant, ou o nó está no ar mas não tem rota de saída. Em todos esses casos, a
[API de debug](../debug-api/) não tem túnel pelo qual retransmitir, e o
[SSH não consegue autenticar](../ssh/) nesta build.

## Pré-requisito: diagnóstico de inicialização

O Azure exige diagnóstico de inicialização (boot diagnostics) na VM antes de permitir a
conexão de um console serial. Isso é habilitado por `terraform/modules/ce-node`:

```hcl
boot_diagnostics {}
```

Um bloco vazio seleciona o armazenamento gerenciado pelo Azure, portanto não há conta de
armazenamento de diagnóstico, política de ciclo de vida ou chave de acesso para gerenciar.
Confirme em um nó:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="Habilitá-lo não é retroativo">
O diagnóstico de inicialização captura o log serial **no boot**. Ativá-lo em uma VM que
já está em execução não produz um log para o boot que já ocorreu, então
`az vm boot-diagnostics get-boot-log` responde:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

Isso é esperado, não é uma falha. Um log de boot passa a existir depois que o nó
reinicializar. A conexão ao console ao vivo, no entanto, funciona imediatamente — ela não
depende do log.
</Aside>

## Verificando a disponibilidade sem um terminal

Conectar exige uma sessão interativa, mas saber se a conexão *seria* possível são duas
chamadas de API. Ambas são úteis em uma verificação de saúde.

O serviço precisa estar habilitado para a subscription — um administrador pode desabilitá-lo
para todo o tenant:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

Em seguida, solicite uma conexão à porta serial de um nó específico:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

Uma `connectionString` começando com `wss://` — neste deployment,
`eastus.gateway.serialconsole.azure.com` — significa que o console pode ser conectado
agora. Antes de o diagnóstico de inicialização ser habilitado, essa chamada não tinha nada
a que se conectar.

<Aside type="danger" title="Essa string de conexão é uma credencial">
Trata-se de um bearer token de curta duração embutido em uma URL. Não a registre em logs,
não a cole em um ticket e não faça commit dela. Imprima apenas o host quando estiver
demonstrando que a chamada funcionou.
</Aside>

## Conectando

<Steps>

1. Instale a extensão uma única vez:

   ```bash
   az extension add --name serial-console
   ```

2. Conecte:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. Você chega ao prompt de login do próprio nó, não a um shell. Esse é o Site CLI, e ele
   exige credenciais definidas no nó — a senha de admin do provisionamento, ou uma definida
   através do endpoint de troca de senha. O console serial prova que o *canal*
   funciona; ele não contorna a autenticação.

</Steps>

Capturado de `f5-xc-ce-vm-01`, com omissão no meio onde a saída das units do systemd
não acrescenta nada:

```text file=../../../_data/serial-console-boot.txt
```

Quatro coisas nessa transcrição merecem atenção, porque respondem a perguntas que a
API de debug não pode:

- **cloud-init concluído** — `Datasource DataSourceAzure`, finalizado em 22,37 segundos.
  Um nó que nunca se registra normalmente falhou aqui, e é aqui que você enxerga isso.
- **Ambos os container runtimes iniciaram.** `Container Runtime Interface for OCI (CRI-O)`
  e `Docker Application Container Engine` estão cada um `[ OK ]`, o que é a prova em tempo
  de boot do comportamento de runtime duplo que surpreende as pessoas em
  [crictl](../../commands/system/crictl/) e [docker](../../commands/system/docker/).
- **`VP Manager image load` e `Argo Watch service`** — `vpm` e o Argo subindo.
- **O prompt é do próprio nó**, atrás do seu banner de auditoria. O console serial lhe dá um
  prompt de login, não uma sessão.

<Aside type="caution" title="Conectar interativamente exige um terminal real — mas pode ser automatizado">
`az serial-console connect` coloca o terminal em modo raw, então não pode ser executado a
partir de um pipeline ou de qualquer contexto sem TTY. Ele falha no lado do cliente, antes
de contatar o Azure:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

Esse traceback é tratamento de terminal, não uma indisponibilidade do console serial.

A conexão em si, no entanto, **é** automatizável — opere o websocket diretamente em vez da
CLI. A transcrição acima foi capturada dessa forma, sem TTY. Veja
`scripts/serial_console_capture.py`, que é a maneira como você coletaria evidências de boot
de um nó que falhou em se registrar sem alguém sentado em frente a um terminal.
</Aside>

<Aside type="caution" title="Espere ter que tentar novamente: o gateway recusa aproximadamente uma tentativa a cada duas">
O primeiro frame do gateway é um desafio, não saída, e o cliente o responde com um
bearer token. Mesmo quando isso é feito corretamente, o socket frequentemente fecha
imediatamente:

```
[close] code=1011 reason=Connection not trusted
```

Comportamento observado: funciona de forma intermitente e, sob uso sustentado, todos os nós
do resource group recusam — incluindo nós que funcionavam minutos antes.
`scripts/serial_console_capture.py` tenta novamente por padrão porque repetir frequentemente
funciona.

**A causa não está estabelecida.** O que já foi descartado, porque cada item é um palpite
plausível que desperdiça tempo:

| Não é isso | Como confirmar |
| --- | --- |
| Throttling de ARM/compute | Isso retorna HTTP `429` em chamadas ARM. Aqui é um fechamento de websocket em um canal de dados separado. |
| Interceptação de TLS por um proxy | `openssl s_client -connect <region>.gateway.serialconsole.azure.com:443 \| openssl x509 -noout -issuer`. Um emissor genuíno `O=Microsoft Corporation` descarta isso; um fornecedor de proxy como emissor confirma, e a correção é incluir `*.serialconsole.azure.com` em allow-list. |
| Diagnóstico de inicialização desabilitado | `az vm show -g <rg> -n <vm> --query diagnosticsProfile` reportando `enabled: true`. |
| Incompatibilidade de token entre a concessão e o desafio | Usar um único token para ambos é a prática correta, mas não impede o fechamento. |

O que *é* comportamento documentado do Azure: **uma sessão de console serial por VM, e uma
segunda solicitação bem-sucedida expulsa a primeira.** O usuário expulso é desconectado, mas
não deslogado, então a sessão do shell sobrevive. Duas pessoas depurando um mesmo nó
irão se deslocar mutuamente repetidas vezes.

Para trabalho em volume, prefira a [API de debug](../debug-api/), que não tem nenhuma dessas limitações.
[SSH não é uma alternativa](../ssh/) — não pode ser habilitado nesta build.
</Aside>

<Aside type="caution" title="A colagem é limitada a 2.048 caracteres">
O Azure limita o comprimento da colagem no console serial a 2.048 caracteres, para evitar
sobrecarregar a porta serial. Enviar um comando longo — ou um lote de comandos em uma única
escrita — falha de uma forma que parece um travamento ou throttling, e não um limite de
comprimento.

Envie os comandos individualmente. Essa é uma restrição real para qualquer coleta em volume
por console serial, e outro motivo para preferir a [API de debug](../debug-api/) para esse trabalho.
</Aside>

## O que você pode ver aqui que a API não consegue mostrar

- **cloud-init** executando, falhando ou nunca iniciando — a causa habitual de um nó
  que nunca se registra.
- **Tentativas de registro** contra `register.ves.volterra.io`, incluindo um
  erro de configuração ou um token rejeitado pelo tenant.
- **Mensagens de kernel e de boot** de antes de qualquer agente estar em execução.
- O nó quando ele **não tem nenhum caminho de rede funcional**, o que inviabiliza todas as outras rotas.

Para um nó que *está* `ONLINE`, prefira a API de debug: ela é automatizável, produz
evidências que você pode reproduzir e não ocupa a única porta serial.
