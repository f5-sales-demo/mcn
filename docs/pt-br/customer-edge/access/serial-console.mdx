O Console Serial do Azure conecta-se à porta serial emulada do nó por meio da
plataforma Azure. Ele não atravessa o plano de controle do F5 Distributed Cloud, o
plano de dados do nó, nem qualquer caminho de rede que o nó controle — o que é
exatamente o motivo pelo qual funciona quando nada mais funciona.

Recorra a ele quando um CE **nunca subiu**: o registro falhou, o site está ausente
do tenant, ou o nó está ativo mas não possui rota de saída. Em todos esses casos, a
[API de debug](../debug-api/) não possui túnel para retransmitir, e o SSH está fechado
no nó conforme entregue.

## Pré-requisito: diagnóstico de boot

O Azure exige o diagnóstico de boot na VM antes de conectar um console serial.
Isso é habilitado por `terraform/modules/ce-node`:

```hcl
boot_diagnostics {}
```

Um bloco vazio seleciona o armazenamento gerenciado pelo Azure, portanto não há conta
de armazenamento de diagnóstico, política de ciclo de vida ou chave de acesso para
gerenciar. Confirme em um nó:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="Habilitá-lo não é retroativo">
O diagnóstico de boot captura o log serial **no momento do boot**. Ativá-lo em uma VM
que já está em execução não produz um log para o boot que já ocorreu, portanto
`az vm boot-diagnostics get-boot-log` responde:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

Isso é esperado, não uma falha. Um log de boot existe após a próxima reinicialização
do nó. A conexão ao console ao vivo, no entanto, funciona imediatamente — ela não
depende do log.
</Aside>

## Verificando a disponibilidade sem um terminal

A conexão requer uma sessão interativa, mas se ela *poderia* ser estabelecida são
apenas duas chamadas de API. Ambas são úteis em uma verificação de integridade.

O serviço deve estar habilitado para a assinatura — um administrador pode desativá-lo
em todo o tenant:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

Em seguida, solicite uma conexão à porta serial de um nó específico:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

Um `connectionString` começando com `wss://` — neste deployment
`eastus.gateway.serialconsole.azure.com` — significa que o console pode ser conectado
agora. Antes de o diagnóstico de boot ser habilitado, essa chamada não tinha nada a
que se conectar.

<Aside type="danger" title="Essa string de conexão é uma credencial">
É um token bearer de curta duração incorporado em uma URL. Não a registre em logs,
cole em um chamado ou faça commit dela. Exiba apenas o host ao demonstrar que a
chamada funcionou.
</Aside>

## Conectando

<Steps>

1. Instale a extensão uma vez:

   ```bash
   az extension add --name serial-console
   ```

2. Conecte:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. Você chegará ao próprio prompt de login do nó, não a um shell. Esta é a CLI do
   Site, e ela requer credenciais configuradas no nó — a senha de administrador do
   provisionamento, ou uma definida por meio do endpoint de alteração de senha. O
   console serial prova que o *canal* funciona; ele não ignora a autenticação.

</Steps>

Capturado de `f5-xc-ce-vm-01`, omitido no meio onde a saída das unidades systemd
não acrescenta nada:

```text file=../../../_data/serial-console-boot.txt
```

Quatro coisas nessa transcrição merecem atenção, pois respondem a perguntas que a
API de debug não consegue:

- **cloud-init concluído** — `Datasource DataSourceAzure`, finalizado em 22,37
  segundos. Um nó que nunca se registra geralmente falhou aqui, e é aqui que isso
  fica visível.
- **Ambos os runtimes de container iniciaram.** `Container Runtime Interface for OCI (CRI-O)`
  e `Docker Application Container Engine` estão cada um com `[ OK ]`, o que é a
  prova no momento do boot do comportamento de runtime duplo que surpreende as pessoas
  em [crictl](../../commands/system/crictl/) e [docker](../../commands/system/docker/).
- **`VP Manager image load` e `Argo Watch service`** — `vpm` e Argo inicializando.
- **O prompt é o próprio do nó**, atrás do seu banner de auditoria. O console serial
  fornece um prompt de login, não uma sessão.

<Aside type="caution" title="A conexão interativa requer um terminal real — mas pode ser automatizada">
`az serial-console connect` coloca o terminal em modo raw, portanto não pode ser
executado a partir de um pipeline ou qualquer contexto sem TTY. Ele falha no lado do
cliente, antes de contatar o Azure:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

Esse traceback é de manipulação de terminal, não uma indisponibilidade do console
serial.

A própria conexão, no entanto, **é** automatizável — conduza o websocket diretamente
em vez de usar a CLI. A transcrição acima foi capturada dessa forma, sem TTY. Consulte
`scripts/serial_console_capture.py`, que é a forma de coletar evidências de boot de
um nó que falhou ao se registrar sem um humano no terminal.
</Aside>

<Aside type="caution" title="Espere tentar novamente: o gateway recusa aproximadamente uma tentativa em cada duas">
O primeiro frame do gateway é um desafio, não uma saída, e o cliente o responde com
um token bearer. Mesmo quando isso é feito corretamente, o socket frequentemente fecha
imediatamente:

```
[close] code=1011 reason=Connection not trusted
```

Medido em tentativas repetidas em três nós, isso se alterna: uma recusa é seguida por
um sucesso no mesmo nó. Isso é consistente com uma sessão anterior ainda sendo mantida,
e a tentativa recusada a liberando.

**Não é um problema de credencial**, apesar da mensagem. Tentar novamente normalmente
é suficiente, razão pela qual `scripts/serial_console_capture.py` tenta novamente por
padrão.

Use um único token para a solicitação de sessão e para o desafio de qualquer forma,
correspondendo à extensão `az`. Essa é a prática correta, mas não é o que causa isso.
</Aside>

## O que você pode ver aqui que a API não consegue mostrar

- **cloud-init** em execução, falhando ou nunca iniciando — a causa usual de um nó
  que nunca se registra.
- **Tentativas de registro** contra `register.ves.volterra.io`, incluindo um erro de
  configuração ou um token que o tenant rejeitou.
- **Mensagens do kernel e de boot** de antes de qualquer agente estar em execução.
- O nó quando não possui **nenhum caminho de rede funcionando**, o que invalida todas
  as outras rotas.

Para um nó que *está* `ONLINE`, prefira a API de debug: ela é automatizável, produz
evidências que podem ser re-executadas e não ocupa a única porta serial.
