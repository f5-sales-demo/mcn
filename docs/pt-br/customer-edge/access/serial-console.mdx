O Console Serial do Azure conecta-se à porta serial emulada do nó por meio da plataforma
Azure. Ele não atravessa o plano de controle do F5 Distributed Cloud, o plano de dados
do nó nem qualquer caminho de rede que o nó controle — e é exatamente por isso que
funciona quando nada mais funciona.

Utilize-o quando um CE **nunca subiu**: o registro falhou, o site está ausente do tenant
ou o nó está ativo, mas não tem rota de saída. Em todos esses casos, a
[API de depuração](../debug-api/) não tem túnel para retransmitir. O [SSH](../ssh/)
sobrevive a um registro com falha, mas apenas se sua chave já tiver sido gravada no
primeiro boot e você conseguir alcançar o endereço interno do nó de dentro da VNet —
nenhuma das quais é verdade para um nó com o qual você está tendo contato pela primeira
vez.

## Pré-requisito: diagnóstico de boot

O Azure exige diagnóstico de boot na VM antes de permitir a conexão de um console serial.
Isso é habilitado pelo `terraform/modules/ce-node`:

```hcl
boot_diagnostics {}
```

Um bloco vazio seleciona o armazenamento gerenciado pelo Azure, portanto não há conta
de armazenamento de diagnóstico, política de ciclo de vida ou chave de acesso para
gerenciar. Confirme em um nó:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="Habilitá-lo não é retroativo">
O diagnóstico de boot captura o log serial **no momento do boot**. Ativá-lo para uma VM
que já está em execução não produz um log para o boot que já aconteceu, portanto
`az vm boot-diagnostics get-boot-log` responde:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

Isso é esperado, não é uma falha. Um log de boot existirá após a próxima reinicialização
do nó. A conexão ao console ao vivo, no entanto, funciona imediatamente — ela não depende
do log.
</Aside>

## Verificando a disponibilidade sem um terminal

A conexão requer uma sessão interativa, mas verificar se ela *funcionaria* são apenas
duas chamadas de API. Ambas são úteis em uma verificação de integridade.

O serviço deve estar habilitado para a assinatura — um administrador pode desativá-lo
em todo o tenant:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

Em seguida, solicite uma conexão à porta serial de um nó específico:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

Um `connectionString` começando com `wss://` — neste deployment
`eastus.gateway.serialconsole.azure.com` — significa que o console pode ser conectado
agora. Antes de o diagnóstico de boot ser habilitado, esta chamada não tinha nada a
que conectar.

<Aside type="danger" title="Essa string de conexão é uma credencial">
É um token de portador de curta duração embutido em uma URL. Não a registre em logs,
cole em um ticket ou faça commit dela. Imprima apenas o host quando estiver demonstrando
que a chamada funcionou.
</Aside>

## Conectando

<Steps>

1. Instale a extensão uma vez:

   ```bash
   az extension add --name serial-console
   ```

2. Conecte:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. Você chega ao prompt de login do próprio nó, não a um shell. Esta é a CLI do Site,
   e ela requer credenciais definidas no nó — a senha de administrador do provisionamento
   ou uma definida por meio do endpoint de alteração de senha. O console serial prova que
   o *canal* funciona; ele não ignora a autenticação.

</Steps>

Capturado de `f5-xc-ce-vm-01`, com omissões no meio onde a saída da unidade systemd
não acrescenta nada:

```text file=../../../_data/serial-console-boot.txt
```

Quatro coisas nessa transcrição merecem atenção, pois respondem a perguntas que a
API de depuração não consegue:

- **cloud-init concluído** — `Datasource DataSourceAzure`, finalizado em 22,37 segundos.
  Um nó que nunca se registra geralmente falhou aqui, e é aqui que você vê isso.
- **Ambos os runtimes de container iniciados.** `Container Runtime Interface for OCI (CRI-O)`
  e `Docker Application Container Engine` estão cada um com `[ OK ]`, que é a prova em
  tempo de boot do comportamento de runtime duplo que surpreende as pessoas em
  [crictl](../../commands/system/crictl/) e [docker](../../commands/system/docker/).
- **`VP Manager image load` e `Argo Watch service`** — `vpm` e Argo subindo.
- **O prompt é o do próprio nó**, atrás do seu banner de auditoria. O console serial
  fornece um prompt de login, não uma sessão.

<Aside type="caution" title="A conexão interativa requer um terminal real — mas pode ser automatizada">
`az serial-console connect` coloca o terminal em modo raw, portanto não pode ser
executado a partir de um pipeline ou qualquer contexto sem TTY. Ele falha no lado do
cliente, antes de contatar o Azure:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

Esse traceback é de tratamento de terminal, não uma interrupção do console serial.

A própria conexão, no entanto, **é** automatizável — conduza o websocket diretamente
em vez de usar a CLI. A transcrição acima foi capturada dessa forma, sem TTY. Consulte
`scripts/serial_console_capture.py`, que é a forma de coletar evidências de boot de um
nó que falhou ao se registrar sem que um humano esteja no terminal.
</Aside>

<Aside type="caution" title="Espere tentar novamente: o gateway recusa aproximadamente uma em cada duas tentativas">
O primeiro quadro do gateway é um desafio, não uma saída, e o cliente responde com um
token de portador. Mesmo quando isso é feito corretamente, o socket frequentemente fecha
imediatamente:

```
[close] code=1011 reason=Connection not trusted
```

Comportamento observado: funciona de forma intermitente e, sob uso intenso, todos os nós
no grupo de recursos recusam — incluindo nós que funcionaram minutos antes.
`scripts/serial_console_capture.py` tenta novamente por padrão porque repetir a tentativa
frequentemente funciona.

**A causa não está estabelecida.** O que foi descartado, pois cada um é uma suposição
plausível que desperdiça tempo:

| Não é isso | Como confirmar |
| --- | --- |
| Throttling de ARM/compute | Isso retorna HTTP `429` em chamadas ARM. Este é um fechamento de websocket em um canal de dados separado. |
| Interceptação de TLS por um proxy | `openssl s_client -connect <region>.gateway.serialconsole.azure.com:443 \| openssl x509 -noout -issuer`. Um emissor genuíno `O=Microsoft Corporation` descarta isso; um fornecedor de proxy como emissor confirma, e a correção é colocar `*.serialconsole.azure.com` na lista de permissões. |
| Diagnóstico de boot desabilitado | `az vm show -g <rg> -n <vm> --query diagnosticsProfile` reportando `enabled: true`. |
| Incompatibilidade de token entre concessão e desafio | Usar um token para ambos é a prática correta, mas não impede o fechamento. |

O que *é* comportamento documentado do Azure: **uma sessão de console serial por VM, e
uma segunda solicitação bem-sucedida expulsa a primeira.** O usuário expulso é
desconectado, mas não deslogado, portanto a sessão de shell sobrevive. Duas pessoas
depurando um nó se deslocarão repetidamente.

Para trabalho em volume, prefira a [API de depuração](../debug-api/) ou o
[SSH](../ssh/), nenhum dos quais tem essas limitações. O SSH em particular não tem
limite de colagem nem restrição de sessão única, portanto é a melhor escolha sempre que
o nó for acessível de dentro da VNet.
</Aside>

<Aside type="caution" title="A colagem é limitada a 2.048 caracteres">
O Azure limita o comprimento de colagem do console serial a 2.048 caracteres, para
evitar sobrecarregar a porta serial. Enviar um comando longo — ou um conjunto de
comandos em uma única gravação — falha de uma forma que parece um travamento ou
throttling em vez de um limite de comprimento.

Envie comandos individualmente. Esta é uma restrição real para qualquer coleta em volume
via console serial, e mais um motivo para preferir a [API de depuração](../debug-api/)
para esse trabalho.
</Aside>

## O que você pode ver aqui que a API não consegue mostrar

- **cloud-init** em execução, falhando ou nunca iniciando — a causa usual de um nó
  que nunca se registra.
- **Tentativas de registro** contra `register.ves.volterra.io`, incluindo um erro de
  configuração ou um token rejeitado pelo tenant.
- **Mensagens do kernel e de boot** de antes de qualquer agente estar em execução.
- O nó quando **não tem caminho de rede funcional**, o que derrota todas as outras
  rotas.

Para um nó que *está* `ONLINE`, prefira a API de depuração: ela é automatizável, produz
evidências que você pode reproduzir e não ocupa a única porta serial.
