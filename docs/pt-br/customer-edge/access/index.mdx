Três rotas funcionam, e qual delas se aplica é determinado pelo estado do nó e de onde
você está se conectando, e não por preferência.

| Rota | Exige nó `ONLINE` | Exige alcançabilidade de rede | Limites | Abrange |
| --- | --- | --- | --- | --- |
| [API de depuração](./debug-api/) | **sim** | sim | cerca de 25–30 minutos de aquecimento em um site novo | 34 comandos |
| [SSH](./ssh/) | não | de dentro da VNet, somente para o endereço interno | a chave precisa estar presente desde o primeiro boot | O Site CLI completo no equipamento |
| [Console serial](./serial-console/) | não | não | uma sessão por VM; limite de colagem de 2.048 caracteres | O Site CLI completo no equipamento |

O console serial é o último recurso, e a única rota que sobrevive a um nó sem nenhum
caminho de rede funcional.

SSH é a opção quando a API de depuração não é suficiente, porque o appliance oferece
substancialmente mais comandos do que os 34 que essa API expõe. Ele tem dois custos. A chave é
escrita pelo cloud-init e, portanto, precisa estar presente no **primeiro boot**, o que significa que habilitá-la em
nós em execução os substitui — e isso atualmente trava o registro
([issue 674](https://github.com/f5-sales-demo/mcn/issues/674)). E o `sshd` responde apenas no
endereço interno do nó, então é preciso um host dentro da VNet; sondar o endereço pelo qual
você conhece o nó sempre reportará porta fechada.

## Por que a divisão não é uma preferência

A API de depuração é servida pelo control plane do F5 Distributed Cloud, que faz o relay para
o nó pelo túnel que o `vpm` estabelece durante o registro. Sem registro não há
túnel, o que significa que a API não tem para onde fazer o relay.

Ela falha de um modo pouco útil em vez de óbvio, então um nó que nunca subiu
parece um problema de API.

O console serial vai pelo caminho oposto — através da plataforma Azure até a
porta serial emulada do nó. Não importa se o nó registrou, se tem
alcançabilidade de rede ou se tem um data plane funcional. Essa independência é o objetivo
central, e é por isso que o boot diagnostics precisa permanecer habilitado nas VMs de CE.

<Aside type="note" title="O que usar">
Se você está escrevendo automação, ou coletando evidências que quer reexecutar depois, use
a API de depuração. Se o registro é justamente o que está quebrado, o console serial não é um
plano B — é a única opção.
</Aside>

## Credenciais

Cada rota usa credenciais diferentes, e nenhuma delas deve estar em uma linha de comando.

- **API de depuração** — um token de API do F5 Distributed Cloud, como `XCSH_API_TOKEN`, com a
  URL do tenant como `XCSH_API_URL`. O arquivo de contexto do `xcsh` em
  `~/.config/xcsh/contexts/<tenant>.json` contém ambos, e é o que
  o `scripts/capture-sitecli.sh` lê quando o ambiente não os fornece.
- **SSH** — a metade privada do par de chaves cuja metade pública o deployment escreveu em
  `/var/home/admin/.ssh/authorized_keys` no primeiro boot, mais um host dentro da VNet para
  alcançar o endereço interno. Conecte-se como `admin`, não como `azureuser`.
- **Console serial** — seu login interativo do Azure. Não há service principal
  para isso: o tenant Entra corporativo da F5 não permite provisionar um, o que
  também explica por que nenhuma parte disso roda em CI.

<Aside type="danger" title="Nunca passe um token como argumento">
Um token em uma linha de comando fica no histórico do shell e na lista de processos, onde
qualquer outro usuário da máquina pode lê-lo. O `capture-sitecli.sh` recusa
`--token` categoricamente por esse motivo e fornece o cabeçalho ao `curl` via stdin
em vez disso.
</Aside>
