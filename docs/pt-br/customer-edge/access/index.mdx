Duas rotas funcionam, e qual delas se aplica é decidido pelo estado do nó, e não
por preferência.

| Rota | Requer nó `ONLINE` | Requer alcançabilidade de rede | Limites | Abrange |
| --- | --- | --- | --- | --- |
| [Debug API](./debug-api/) | **sim** | sim | cerca de 25–30 minutos de aquecimento em um novo site | 34 comandos |
| [Console serial](./serial-console/) | não | não | uma sessão por VM; limite de colagem de 2.048 caracteres | O Site CLI completo no próprio equipamento |

O console serial é o último recurso, e a única rota que sobrevive a um nó sem nenhum
caminho de rede funcional.

[**SSH não é uma terceira rota.**](./ssh/) A conta `admin` não consegue se autenticar no
build que este tenant executa, o `vpm` nunca aplica a chave, e não existe configuração de site que
altere isso. A página existe para documentar as evidências, porque todo modo de falha ali
parece um problema de firewall ou de credencial.

## Por que a divisão não é uma preferência

A debug API é servida pelo control plane do F5 Distributed Cloud, que faz o relay para
o nó pelo túnel que o `vpm` estabelece durante o registro. Sem registro não há
túnel, o que significa que a API não tem nada para onde fazer o relay.

Ela falha de forma pouco útil em vez de óbvia, então um nó que nunca subiu
parece um problema de API.

O console serial vai pelo caminho totalmente oposto — através da plataforma Azure até a
porta serial emulada do nó. Ele não se importa se o nó se registrou, se tem
alcançabilidade de rede ou se tem um data plane funcional. Essa independência é todo o
propósito, e é por isso que o diagnóstico de boot precisa permanecer habilitado nas VMs de CE.

<Aside type="note" title="O que usar">
Se você está escrevendo automação, ou coletando evidências que quer reexecutar depois, use
a debug API. Se o registro é justamente o que está quebrado, o console serial não é um
fallback — é a única opção.
</Aside>

## Credenciais

Ambas as rotas usam credenciais diferentes, e nenhuma delas pertence a uma linha de comando.

- **Debug API** — um token de API do F5 Distributed Cloud, como `XCSH_API_TOKEN`, com a
  URL do tenant como `XCSH_API_URL`. O arquivo de contexto do `xcsh` em
  `~/.config/xcsh/contexts/<tenant>.json` contém ambos, e é o que
  `scripts/capture-sitecli.sh` lê quando o ambiente não os fornece.
- **Console serial** — seu login interativo do Azure. Não há service principal
  para isso: o tenant corporativo Entra da F5 não permite provisionar um, o que
  também é o motivo pelo qual nenhuma parte disso é executada em CI.

<Aside type="danger" title="Nunca passe um token como argumento">
Um token na linha de comando acaba no histórico do shell e na lista de processos, onde
qualquer outro usuário da máquina pode lê-lo. Por esse motivo, o `capture-sitecli.sh` recusa
`--token` categoricamente e fornece o header ao `curl` via stdin
em vez disso.
</Aside>
