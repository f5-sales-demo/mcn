Todo Customer Edge serve o Console do Site da F5 em `https://<sli-ip>:65500`. Nesta
implantação, geralmente é a rota a tentar primeiro.

Ele exige o mínimo de você: nenhuma chave SSH para distribuir, nenhum jump host para
manter, nenhum IP público no nó e nenhuma substituição de VM para habilitá-lo. Quem
pode se conectar torna-se uma **decisão do Azure RBAC**. E não requer que o site esteja
registrado — a transcrição abaixo foi capturada enquanto os três sites reportavam
`site_state: FAILED`.

A ressalva é que o Console do Site responde apenas no endereço interno (SLI) do nó,
acessível somente de dentro da VNet. O Azure Bastion fecha essa lacuna sem colocar
mais nada na rede.

<Aside type="note" title="O que é verificado aqui e o que não é">
Cada comando e cada saída nesta página foram executados contra `f5-xc-ce-vm-01` nesta
implantação e são reproduzidos literalmente, incluindo as falhas.

A única coisa não exercitada é **efetuar login**. Os passos param na solicitação de
credencial, portanto nada abaixo descreve como é o console após você estar dentro.
</Aside>

## Antes de começar

<Steps>

1. Faça login no Azure e adicione a extensão Bastion. O tunelamento é um recurso de
   cliente nativo e a extensão não é instalada por padrão.

   ```bash
   az login
   az extension add --name bastion
   ```

2. Tenha a permissão **Reader** na máquina virtual CE, em sua interface de rede e no
   host Bastion.

3. Confirme que o Bastion está implantado e é capaz. O SKU Básico não suporta tunelamento
   nem conexão baseada em IP, portanto `Standard` e `True` aqui são ambos essenciais.

   ```bash
   az network bastion list -g rg-mcn-ce-ha-rmordasiewicz \
     --query "[].{name:name, sku:sku.name, tunneling:enableTunneling}" -o table
   ```

   ```text
   Name               Sku       Tunneling
   -----------------  --------  -----------
   ce-ha-lab-bastion  Standard  True
   ```

</Steps>

## Abrir o túnel

Use os valores do `terraform output` em vez de digitá-los manualmente — o resource id não
é algo para montar à mão.

<Steps>

1. Leia o nome do host Bastion, o grupo de recursos e o resource id da VM do CE alvo.

   ```bash
   cd terraform
   BASTION=$(terraform output -raw bastion_name)
   RG=$(terraform output -raw resource_group_name)
   VM_ID=$(terraform output -json ce_vm_ids | jq -r '.eastus01')
   ```

   ```text
   ce-ha-lab-bastion
   rg-mcn-ce-ha-rmordasiewicz
   /subscriptions/…/providers/Microsoft.Compute/virtualMachines/f5-xc-ce-vm-01
   ```

   <Aside type="caution" title="O mapa é indexado por site, não pelo nome da VM">
   As chaves de `ce_vm_ids` são `eastus01`, `eastus02`, `eastus03` — **não** os nomes das VMs. Um
   filtro como `jq -r '."f5-xc-ce-vm-01"'` retorna `null` e o túnel então falha com um
   resource id vazio. Liste-os se não tiver certeza:

   ```bash
   terraform output -json ce_vm_ids | jq -r 'keys | join(", ")'
   ```

   ```text
   eastus01, eastus02, eastus03
   ```
   </Aside>

2. Inicie o túnel. Ele mantém a porta aberta até ser interrompido, portanto execute-o em
   segundo plano ou use um segundo terminal.

   ```bash
   az network bastion tunnel \
     --name "$BASTION" \
     --resource-group "$RG" \
     --target-resource-id "$VM_ID" \
     --resource-port 65500 \
     --port 65500 &
   ```

   ```text
   WARNING: Opening tunnel on port: 65500
   WARNING: Tunnel is ready, connect on port 65500
   WARNING: Ctrl + C to close
   ```

   As três linhas têm o prefixo `WARNING:`. Isso é o Azure CLI gravando o progresso no
   stderr, não um problema. Aguarde `Tunnel is ready` antes de conectar.

3. Confirme que o listener é local, no loopback:

   ```bash
   lsof -nP -iTCP:65500 -sTCP:LISTEN
   ```

   ```text
   COMMAND   PID  USER  FD  TYPE  DEVICE  SIZE/OFF  NODE  NAME
   Python  41648  you   7u  IPv4  …            0t0   TCP  127.0.0.1:65500 (LISTEN)
   ```

4. Abra o console. O túnel o torna local, portanto o endereço é `localhost` — não o
   endereço do nó.

   ```bash
   open https://localhost:65500/          # macOS
   xdg-open https://localhost:65500/      # Linux
   ```

5. Interrompa o túnel quando terminar — `Ctrl-C` ou `kill %1` se tiver executado em
   segundo plano. Deixá-lo aberto mantém a porta local 65500 e a sessão do Bastion.

</Steps>

## O que você verá

**Uma caixa de diálogo de credencial, não uma página de login.** O console usa
autenticação HTTP Basic, portanto o navegador exibe seu próprio prompt de nome de usuário
e senha. Não há formulário para visualizar:

```bash
curl -skI https://localhost:65500/
```

```text
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Basic realm="Volterra Site Console"
Content-Length: 0
```

Um `401` com esse realm é o console funcionando corretamente. É o que uma requisição não
autenticada deve receber.

**Um aviso de certificado, por três razões ao mesmo tempo.** Verificando o certificado
diretamente:

```bash
openssl s_client -connect localhost:65500 -servername localhost </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
```

```text
subject=C=US, ST=California, L=Santa Clara, O=Volterra, OU=Volterra Edge Services, CN=site-local.volterra.io
issuer=C=US, ST=California, L=Santa Clara, O=Volterra, OU=Volterra Edge Services, CN=site-local.volterra.io
notBefore=Oct 25 04:51:31 2024 GMT
notAfter=Oct 25 04:51:31 2025 GMT
```

O subject é igual ao issuer, portanto é autoassinado. O nome é `site-local.volterra.io`
enquanto você está se conectando a `localhost`, então não haverá correspondência. E na
versão que esta implantação executa, **o certificado expirou em 25 de outubro de 2025** —
o appliance o envia e nada neste repositório o renova.

Espere um aviso categórico do navegador e espere-o a cada vez. A linha de subject acima é
a parte útil: é como você confirma que chegou ao appliance em vez de a outro processo
que esteja escutando na porta local 65500.

## A credencial de administrador

Faça login como `admin`. **Esta documentação não publica a senha e não deve fazê-lo.**

Um Customer Edge recém-saído de fábrica é fornecido com o padrão publicado pela F5, e a
F5 exige que ele seja alterado. Trate a alteração da senha como parte da implantação de um
nó, e não como um hardening posterior. Dois motivos pelos quais isso importa mais aqui do
que pode parecer:

- Esta documentação é pública. Publicar a senha atual do console da frota transformaria
  "ter Reader no Bastion" em acesso total ao appliance para qualquer pessoa que leia a
  página.
- Uma senha publicada na documentação está errada no momento em que alguém a rotaciona, e
  errada da maneira mais enganosa — o leitor conclui que seu acesso está quebrado em vez
  de que a página está desatualizada.

Obtenha a senha de onde sua equipe armazena os segredos operacionais. Se a resposta for
"ainda é o padrão de fábrica", altere-a antes de fazer qualquer outra coisa.

<Aside type="caution" title="Definir a senha pelo Terraform não foi verificado">
`admin_user_credentials.admin_password` no objeto do site parece ser a forma declarativa
de definir isso. **Não foi confirmado** que ele chega ao Console do Site nesta versão,
portanto não assuma que sim.

Não leia a [página SSH](../ssh/) como evidência em nenhum sentido. Sua conclusão de que
`admin_password` "não alterou nada" foi medida em relação à autenticação SSH, que o `vpm`
ignora completamente para o usuário `admin`. Isso não diz nada sobre o console.
</Aside>

## Por que o túnel deve ter como alvo o resource id

`--target-resource-id` é obrigatório. Usar o endereço do nó como alvo é recusado:

```bash
az network bastion tunnel --name "$BASTION" -g "$RG" \
  --target-ip-address 10.0.3.5 --resource-port 65500 --port 65501
```

```text
ERROR: Custom ports are not allowed. Allowed ports for Tunnel with IP connect is 22, 3389.
```

O motivo **não** é que a conexão baseada em IP esteja desabilitada — neste Bastion,
`ip_connect_enabled` é `true`. A Microsoft não suporta portas personalizadas em conexões
de cliente nativo baseadas em IP, independentemente dessa configuração
([documentação do Azure](https://learn.microsoft.com/azure/bastion/connect-ip-address)), e
65500 é uma porta personalizada. Inspecionar a configuração do Bastion aqui não leva a
lugar nenhum; use o resource id.

## Quando não funciona

| Sintoma | Causa | Solução |
| --- | --- | --- |
| `ERROR: Custom ports are not allowed. Allowed ports for Tunnel with IP connect is 22, 3389.` | Usado `--target-ip-address` | Use `--target-resource-id` |
| `ERROR: Defined port is currently unavailable` | Outro túnel já está usando essa porta local | Interrompa o outro túnel ou passe um `--port` diferente; `--resource-port` permanece 65500 |
| O túnel inicia, mas o resource id está vazio | O filtro `jq` usou o nome da VM em vez da chave do site | Use a chave `eastus01`/`02`/`03` |
| `401 Unauthorized`, realm `Volterra Site Console` | Não é uma falha — requisição não autenticada | Forneça a credencial `admin` |
| O navegador recusa o certificado | Autoassinado, incompatibilidade de nome e expirado desde outubro de 2025 | Esperado; confirme que o subject é `CN=site-local.volterra.io` e prossiga |

<Aside type="note" title="Falhas de autorização não foram reproduzidas">
RBAC insuficiente é a outra forma óbvia de isso falhar, mas reproduzi-lo significaria
remover atribuições de função de uma implantação compartilhada, portanto não está
documentado aqui com um erro literal. Se o túnel falhar ao iniciar com um erro de
autorização, verifique a permissão Reader na VM, em sua NIC e no host Bastion.
</Aside>
