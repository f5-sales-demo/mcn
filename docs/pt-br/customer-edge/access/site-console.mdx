Todo Customer Edge serve o Console do Site da F5 em `https://<sli-ip>:65500`. Neste
deployment, normalmente é a rota que se deve tentar primeiro.

É a que exige menos de você: nenhuma chave SSH para distribuir, nenhum host de salto para
manter, nenhum IP público no nó e nenhuma substituição de VM para habilitá-la. Quem pode se
conectar passa a ser uma **decisão de RBAC do Azure**. E não é necessário que o site esteja
registrado: esta página foi capturada inicialmente enquanto todos os três sites reportavam
`site_state: FAILED`, e reverificada sem alterações nos mesmos nós depois que eles ficaram
`ONLINE`.

O problema é que o Console do Site responde apenas no endereço interno (SLI) do nó,
alcançável somente de dentro da VNet. O Azure Bastion resolve essa lacuna sem colocar mais
nada na rede.

<Aside type="note" title="O que está verificado aqui e o que não está">
Todos os comandos e todas as saídas desta página foram executados contra `f5-xc-ce-vm-01` neste
deployment e estão reproduzidos literalmente, incluindo as falhas.

**A autenticação está verificada**: a credencial `admin` do appliance retorna `200` através do
túnel. O que *não* é exercitado é o console em si — nada abaixo descreve o que você pode
ver ou fazer uma vez dentro dele.

**O RBAC do Azure não está verificado.** Todas as execuções foram feitas como proprietário da
assinatura, portanto o requisito de Reader no passo 2 é o requisito documentado pela Microsoft,
e não algo medido aqui.
</Aside>

<Aside type="caution" title="O Bastion é opcional e não é implantado por padrão">
`enable_bastion` tem valor padrão `false`, portanto em um `terraform apply` padrão não existe host
Bastion e `terraform output -raw bastion_name` é `null`. Defina `enable_bastion = true` em
`terraform/terraform.tfvars` — está como `true` neste deployment.

O motivo de ser opcional é custo, não risco: um host de SKU Standard cobra uma tarifa horária
fixa a partir do momento em que é provisionado, independentemente de alguém abrir um túnel — USD
0,29/hora em `eastus` para as duas scale units incluídas (preço de tabela, 2026-07), cerca de USD 212 por
mês. Desligue-o novamente quando a demo não precisar de acesso ao console.
</Aside>

## Antes de começar

<Steps>

1. Faça login no Azure e adicione a extensão do Bastion. O tunelamento é um recurso de cliente
   nativo e a extensão não vem instalada por padrão.

   ```bash
   az login
   az extension add --name bastion
   ```

2. Tenha a função **Reader** na máquina virtual do CE, em sua interface de rede e no host Bastion.
   Este é o requisito documentado pela Microsoft e está **não verificado aqui** — todas as execuções neste
   deployment foram como proprietário da assinatura, portanto nenhuma função menor foi demonstrada como
   suficiente ou insuficiente.

3. Confirme que o Bastion está implantado e é capaz. O SKU Basic não suporta tunelamento nem
   conexão baseada em IP, portanto `Standard` e `True` aqui são ambos essenciais.

   ```bash
   az network bastion list -g rg-mcn-ce-ha-rmordasiewicz \
     --query "[].{name:name, sku:sku.name, tunneling:enableTunneling}" -o table
   ```

   ```text
   Name               Sku       Tunneling
   -----------------  --------  -----------
   ce-ha-lab-bastion  Standard  True
   ```

</Steps>

## Abrir o túnel

Obtenha os valores a partir de `terraform output` em vez de digitá-los — o resource id não é
algo para montar à mão.

<Steps>

1. Leia o nome do host Bastion, o grupo de recursos e o resource id da VM do CE de destino.

   ```bash
   cd terraform
   BASTION=$(terraform output -raw bastion_name)
   RG=$(terraform output -raw resource_group_name)
   VM_ID=$(terraform output -json ce_vm_ids | jq -r '.eastus01')
   ```

   ```text
   ce-ha-lab-bastion
   rg-mcn-ce-ha-rmordasiewicz
   /subscriptions/…/providers/Microsoft.Compute/virtualMachines/f5-xc-ce-vm-01
   ```

   <Aside type="caution" title="O mapa é indexado por site, não por nome de VM">
   As chaves de `ce_vm_ids` são `eastus01`, `eastus02`, `eastus03` — **não** os nomes das VMs. Um
   filtro como `jq -r '."f5-xc-ce-vm-01"'` retorna `null`, e o túnel então falha com um
   resource id vazio. Liste-as se estiver em dúvida:

   ```bash
   terraform output -json ce_vm_ids | jq -r 'keys | join(", ")'
   ```

   ```text
   eastus01, eastus02, eastus03
   ```

   </Aside>

2. Inicie o túnel. Ele mantém a porta aberta até ser interrompido, portanto execute-o em segundo plano ou use um
   segundo terminal.

   ```bash
   az network bastion tunnel \
     --name "$BASTION" \
     --resource-group "$RG" \
     --target-resource-id "$VM_ID" \
     --resource-port 65500 \
     --port 65500 &
   ```

   ```text
   WARNING: Opening tunnel on port: 65500
   WARNING: Tunnel is ready, connect on port 65500
   WARNING: Ctrl + C to close
   ```

   Todas as três linhas têm o prefixo `WARNING:`. Isso é a CLI do Azure escrevendo o progresso no
   stderr, não um problema. Aguarde `Tunnel is ready` antes de conectar.

3. Confirme que o listener é local, em loopback:

   ```bash
   lsof -nP -iTCP:65500 -sTCP:LISTEN
   ```

   ```text
   COMMAND   PID  USER  FD  TYPE  DEVICE  SIZE/OFF  NODE  NAME
   Python  41648  you   7u  IPv4  …            0t0   TCP  127.0.0.1:65500 (LISTEN)
   ```

4. Abra o console. O túnel o torna local, portanto o endereço é `localhost` — não o
   endereço do nó.

   ```bash
   open https://localhost:65500/          # macOS
   xdg-open https://localhost:65500/      # Linux
   ```

5. Encerre o túnel quando terminar — `Ctrl-C`, ou `kill %1` se o colocou em segundo plano.
   Deixá-lo aberto mantém a porta local 65500 e a sessão do Bastion.

</Steps>

## O que você verá

**Uma caixa de diálogo de credenciais, não uma página de login.** O console usa autenticação HTTP Basic, portanto
o navegador exibe seu próprio prompt de nome de usuário e senha. Não há formulário para observar:

```bash
curl -skI https://localhost:65500/
```

```text
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Basic realm="Volterra Site Console"
Content-Type: text/html; charset=utf-8
Content-Length: 0
```

Um `401` com esse realm é o console funcionando corretamente. É o que uma requisição não autenticada
deve receber — e fornecer a credencial `admin` para a mesma URL responde
`200`, que é como você confirma a credencial antes de abrir um navegador:

```bash
curl -sk -u admin -o /dev/null -w '%{http_code}\n' https://localhost:65500/
```

```text
Enter host password for user 'admin':
200
```

`-u admin` sem dois-pontos faz o `curl` solicitar a senha em vez de obtê-la da
linha de comando, onde ela ficaria registrada no histórico do shell e na lista de processos.

**Um aviso de certificado, por três motivos ao mesmo tempo.** Verificando o certificado diretamente:

```bash
openssl s_client -connect localhost:65500 -servername localhost </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
```

```text
subject=C=US, ST=California, L=Santa Clara, O=Volterra, OU=Volterra Edge Services, CN=site-local.volterra.io
issuer=C=US, ST=California, L=Santa Clara, O=Volterra, OU=Volterra Edge Services, CN=site-local.volterra.io
notBefore=Oct 25 04:51:31 2024 GMT
notAfter=Oct 25 04:51:31 2025 GMT
```

O subject é igual ao issuer, portanto é autoassinado. O nome é `site-local.volterra.io` enquanto
você está conectando a `localhost`, portanto não haverá correspondência. E no build que este deployment
executa, **o certificado expirou em 25 de outubro de 2025** — o appliance o entrega, e nada
neste repositório o renova.

Espere um aviso direto do navegador, e espere-o todas as vezes. A linha de subject acima é a
parte útil: é como você confirma que alcançou o appliance e não outra coisa
escutando na porta local 65500.

## A credencial de admin

Faça login como `admin`. **Esta documentação não publica a senha, e não deve.**

<Aside type="danger" title="Neste deployment essa senha ainda é o padrão de fábrica da F5">
Este é um fato medido, não uma suspeita: a credencial padrão de fábrica autentica e
retorna `200` em todos os três CEs hoje. A F5 publica esse padrão e exige que seja
alterado, e isso não foi feito.

A consequência prática é que neste deployment "ter Reader no Bastion" é
equivalente a acesso completo ao console do appliance, para qualquer pessoa que conheça um valor que está na
documentação pública da F5. Altere-a, e trate essa alteração como parte da implantação de um nó em vez
de como um endurecimento posterior.
</Aside>

Dois motivos pelos quais não publicá-la importa mais aqui do que pode parecer:

- Esta documentação é pública. Imprimir a senha atual do console da frota transformaria
  "ter Reader no Bastion" em acesso completo ao appliance para qualquer pessoa que leia a página.
- Uma senha publicada em documentação está errada no momento em que alguém a rotaciona, e
  errada da maneira mais enganosa — o leitor conclui que seu acesso está quebrado em vez
  de que a página está desatualizada.

Depois que ela for rotacionada, obtenha-a de onde sua equipe guarda os segredos operacionais.

<Aside type="caution" title="Definir a senha pelo Terraform não está verificado">
`admin_user_credentials.admin_password` no objeto de site parece ser a maneira declarativa
de definir isso. **Não** foi confirmado que ela chega ao Console do Site neste build, portanto
não presuma que chega.

Também não interprete a [página de SSH](../ssh/) como evidência em nenhum dos sentidos. Sua conclusão de que
`admin_password` "não mudou nada" foi medida contra a autenticação SSH, que o `vpm`
ignora inteiramente para o usuário `admin`. Isso não diz nada sobre o console.
</Aside>

## Por que o túnel deve apontar para o resource id

`--target-resource-id` é obrigatório. Apontar para o endereço do nó é recusado —
qualquer que seja o endereço usado, portanto deliberadamente nenhum endereço real é impresso aqui:

```bash
az network bastion tunnel --name "$BASTION" -g "$RG" \
  --target-ip-address <any-sli-address> --resource-port 65500 --port 65501
```

```text
ERROR: Custom ports are not allowed. Allowed ports for Tunnel with IP connect is 22, 3389.
```

O motivo **não** é que a conexão baseada em IP esteja desabilitada — neste Bastion
`ip_connect_enabled` é `true`. A Microsoft não suporta portas personalizadas em conexões
de cliente nativo baseadas em IP, independentemente dessa configuração
([documentação do Azure](https://learn.microsoft.com/azure/bastion/connect-ip-address)), e 65500 é
uma porta personalizada. Inspecionar a configuração do Bastion aqui não leva a nada; use o resource
id.

## Quando não funciona

| Sintoma | Causa | Correção |
| --- | --- | --- |
| `ERROR: Custom ports are not allowed. Allowed ports for Tunnel with IP connect is 22, 3389.` | Uso de `--target-ip-address` | Use `--target-resource-id` |
| `ERROR: Defined port is currently unavailable` | Outro túnel já ocupa essa porta local | Encerre o outro túnel ou passe um `--port` diferente; `--resource-port` continua 65500 |
| `terraform output -raw bastion_name` é `null` ou vazio | O Bastion não está implantado | Defina `enable_bastion = true` e aplique |
| O túnel inicia, mas o resource id está vazio | O filtro `jq` usou o nome da VM em vez da chave do site | Use as chaves `eastus01`/`02`/`03` |
| `401 Unauthorized`, realm `Volterra Site Console` | Não é uma falha — requisição não autenticada | Forneça a credencial `admin` |
| O navegador recusa o certificado | Autoassinado, nome divergente e expirado desde out. de 2025 | Esperado; confirme que o subject é `CN=site-local.volterra.io` e prossiga |

<Aside type="note" title="Falhas de autorização não foram reproduzidas">
RBAC insuficiente é a outra maneira óbvia de isso falhar, mas reproduzi-la significaria
remover atribuições de função de um deployment compartilhado, portanto não está documentada aqui com um
erro literal. Se o túnel falhar no início com um erro de autorização, verifique a função Reader nos
três recursos: a VM, sua NIC e o host Bastion.
</Aside>
