A API `vpm/debug` executa comandos Site CLI em um nó registrado e retorna sua
saída. Tudo abaixo foi estabelecido em um nó ativo; nada disso é publicado
upstream.

## O catálogo de comandos é autodescritivo

Consulte o nó sobre o que ele suporta enviando um POST para `exec-user` com a chave
`command` **omitida**:

```bash
curl -sS -X POST \
  -H "Authorization: APIToken $XCSH_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"namespace":"system","site":"<site>","node":"<node>"}' \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/<node>/exec-user" \
  | jq -r .output | jq .
```

A resposta é um objeto JSON com chaves pelo nome do comando:

```json
{
  "crictl-inspect": ["System Troubleshooting", "ExecUser", " container-id"],
  "diagnosis":      ["System Troubleshooting", "ExecUser", "no argument needed", "GLOBAL"],
  "ip-link-set":    ["Network Troubleshooting", "Exec", " (<device>||<group>) (up||down)"]
}
```

Cada entrada é `[categoria, nível, exemploDeArgumento?, escopo?]`, e esses campos não
são documentação — eles determinam como o comando deve ser chamado.

<Aside type="caution" title="Omita a chave; não envie um valor incorreto">
A descoberta funciona deixando `command` de fora. Enviar um valor desconhecido retorna
um erro, não o catálogo:

```json
{"code":3,"details":[],"message":"exec command failed: command not supported"}
```

Essa mensagem é também o que você obtém para um comando *real* enviado ao endpoint
errado, portanto é fácil interpretá-la erroneamente como "este comando não existe".
</Aside>

## Três transportes, escolhidos pela entrada do catálogo

| Condição | Método e caminho | Corpo | Retorna |
| --- | --- | --- | --- |
| `scope` é `GLOBAL` | `GET .../vpm/debug/global/<cmd>` | nenhum | JSON |
| `tier` é `ExecUser` | `POST .../vpm/debug/<node>/exec-user` | array `command` | texto |
| `tier` é `Exec` | `POST .../vpm/debug/<node>/exec` | array `command` | texto |

### `ExecUser` — o nível somente leitura <Badge text="31 comandos" variant="note" />

O caso mais comum. Passe o comando e seus argumentos como um array, com o nome do
comando primeiro:

```bash
curl -sS -X POST \
  -H "Authorization: APIToken $XCSH_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"namespace":"system","site":"<site>","node":"<node>","command":["crictl-ps"]}' \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/<node>/exec-user"
```

```json
{ "return_code": 0, "output": "CONTAINER    IMAGE    CREATED    STATE ..." }
```

Os argumentos são elementos separados do array, não uma única string:

```json
{ "command": ["journalctl", "-u", "vpm", "-n", "200"] }
```

### `GLOBAL` — abrangente ao site, e um transporte completamente diferente <Badge text="2 comandos" variant="tip" />

`health` e `diagnosis` são os únicos dois. São requisições `GET` para um caminho
`global`, não recebem argumentos e retornam JSON estruturado em vez de texto de
terminal.

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/global/health" | jq .
```

<Aside type="danger" title="Um comando GLOBAL não é acessível via exec-user">
Esta é a armadilha que mais consome tempo. Enviar `health` ou `diagnosis` para
`exec-user` retorna `command not supported`, o que parece indicar que o comando
não existe no nó — quando na verdade ele existe e você usou o transporte errado.

```bash
# Errado. Retorna: exec command failed: command not supported
-d '{"namespace":"system","site":"…","node":"…","command":["health"]}'   # POST exec-user

# Correto.
GET .../vpm/debug/global/health
```

</Aside>

### `Exec` — o nível privilegiado <Badge text="1 comando nesta build" variant="danger" />

Um endpoint separado, e o nível é imposto em vez de ser indicativo: `exec` rejeita
um comando `ExecUser` com a mesma mensagem `command not supported`. Cada membro
ou modifica o nó ou lê um marcador de estado.

Na build em que este tenant opera, o nível contém apenas `ip-link-set`. Builds mais
recentes adicionam `systemctl-restart-NetworkManager`, `systemctl-restart-crio`,
`systemctl-restart-kubelet`, `systemctl-start-crio-prune` e três comandos
`marker-exists-*`.

<Aside type="danger" title="Nada aqui executa um comando Exec">
O harness de captura recusa este nível e lê o nível a partir do catálogo ativo
em vez de uma lista codificada — portanto, uma build futura que promova um comando
para `Exec` é respeitada sem que ninguém precise editar código. Execute um apenas
deliberadamente, em um nó que você esteja disposto a interromper.
</Aside>

## Encontrando os nomes do site e do nó

O nome do nó é o nome da VM no Azure, e `list-service` é uma forma econômica de
confirmá-lo junto com os serviços em execução:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/global/list-service" \
  | jq -r '[.service[].node] | unique'
```

## Reproduzindo as capturas deste repositório

Cada página de comando incorpora a saída capturada por `scripts/capture-sitecli.sh`,
que implementa todas as três regras acima.

<Steps>

1. Aponte para um tenant. Ele lê `XCSH_API_URL` e `XCSH_API_TOKEN`, ou usa como
   alternativa o contexto `xcsh` ativo.

2. Atualize o catálogo e confirme que o nó não mudou em relação à documentação:

   ```bash
   bash scripts/capture-sitecli.sh --check
   ```

   Isso compara apenas o catálogo registrado e a build do software. Ele relata uma
   mudança de build separadamente de comandos adicionados ou removidos.

3. Recapture quando quiser evidências atualizadas:

   ```bash
   bash scripts/capture-sitecli.sh
   ```

</Steps>

<Aside type="note" title="Capturas são evidências, não artefatos reproduzíveis">
Contadores, tempos de atividade e idades de contêineres variam entre execuções,
portanto recapturar sempre produz um diff. O catálogo é o contrato estável e é
idêntico byte a byte entre execuções quando o nó não mudou; é isso que `--check`
compara. Saídas longas são truncadas e terminam com um marcador explícito, de modo
que uma tabela truncada nunca é exibida como se estivesse completa.
</Aside>

<Aside type="danger" title="Capturando de um nó de cliente: verifique o perfil de redação">
A saída dos comandos carrega identidade de infraestrutura — endereçamento interno,
endereços MAC, números de AS, hostnames — e para um cliente isso é informação
identificadora da organização.

O filtro de limpeza, portanto, usa como padrão um perfil **estrito** que remove
tudo isso. Este repositório declara `lab` em `sitecli/capture-manifest.json`, o
que mantém esses detalhes, e isso só é correto aqui porque essas capturas provêm
de infraestrutura de demonstração de propriedade da F5.

**Não utilize essa configuração em uma captura de cliente.** Tokens, chaves privadas,
o identificador do tenant, UUIDs de objetos, endereços de e-mail e caminhos de
diretório home são removidos em ambos os perfis.

Uma limitação vale ser conhecida: uma tabela de vizinhos BGP imprime o AS como uma
coluna simples sem rótulo para ancorar um padrão, portanto os ASNs são comparados
por valor em relação às faixas privadas. Um ASN **público** ali sobrevive ao perfil
estrito e requer uma revisão manual da saída de `show-ip-bgp*` antes de publicá-la.
</Aside>
