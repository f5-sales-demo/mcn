Capturado em 28/07/2026 de um CE desta implantação. `sitecli/capture-manifest.json`
registra qual nó, e `scripts/capture-sitecli.sh --check` verifica novamente a superfície
de comandos em um CE ativo.

O SSH alcança a conta `admin` do appliance, cujo shell de login é o Site CLI
(`/opt/bin/vpmu`). Esta é a única rota para a **superfície completa de comandos no nó** —
a [API de debug](../debug-api/) expõe 34 comandos, e o próprio appliance oferece muitos
outros que não estão disponíveis nessa API.

```bash
cd terraform
SLI=$(terraform output -json ce_sli_private_ips | jq -r '.eastus01')
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<operator-vm> "admin@$SLI"
```

Cada parte dessa linha de comando é essencial, e as três seções a seguir explicam
qual falha cada uma previne.

Não há prompt de shell para acessar: o shell de login do `admin` **é** o Site CLI, portanto
você chega diretamente ao prompt `>>>`. Execute comandos no nó com `execcli <nome>` — veja
[comandos no nó](../../commands/on-box/).

<Aside type="danger" title="Consulte o endereço interno — nunca reutilize um de uma sessão anterior">
O Azure reatribui a sub-rede interna a cada reconstrução, e não na ordem dos nós. Após a
reconstrução mais recente, `f5-xc-ce-vm-01`, `-02` e `-03` possuem `10.0.3.7`, `10.0.3.5`
e `10.0.3.4`; uma construção anterior os tinha em uma ordem completamente diferente, e a
NIC do cliente de teste está na mesma sub-rede e já teve um endereço que um CE possuía
antes. Conectar-se a um endereço memorizado, portanto, cai no nó errado, em uma VM que não
é um CE, ou em lugar nenhum — e o último desses cenários é idêntico a "SSH não está
habilitado".

`terraform output -json ce_sli_private_ips` é o mapeamento. Sem o estado disponível, o
nome da NIC é estável mesmo que o endereço não seja:

```bash
az network nic show -g "$(terraform output -raw resource_group_name)" \
  -n "$(terraform output -json ce_vm_names | jq -r '.eastus01')-internal-nic" \
  --query ipConfigurations[0].privateIPAddress -o tsv
```

</Aside>

<Aside type="caution" title="Somente na inicialização — um CE existente não pode obter SSH sem ser recriado">
O `write_files` do cloud-init é executado **uma vez, na primeira inicialização**. Após isso,
existe um marcador `/etc/cloud/cloud-init.disabled` no nó e o cloud-init não é executado
novamente.

Portanto, não há caminho in-place para um CE em execução. `custom_data` é somente
substituição no Azure, o que significa que adotar isso em uma implantação existente
**substitui todas as VMs do CE**. Conceder SSH ao operador para nós que já estão ativos
é uma reconstrução, não uma mudança de configuração — e o próximo aviso é o que essa
reconstrução costumava custar, e por que isso não é mais o caso.
</Aside>

<Aside type="caution" title="Substituir uma VM do CE costumava bloquear o registro permanentemente — isso está corrigido, e é por isso que o objeto de site está acoplado à VM">
Vale saber antes de planejar uma reconstrução, pois a forma da falha explica o acoplamento
que você verá no plano.

Antigamente, o registro do nó destruído mantinha o índice único `(tenant, cluster_name,
hostname)` do plano de controle, então o registro do nó substituto era recusado com
`UniqueSecondaryIndexViolationError` e repetido indefinidamente. Excluir o registro não era
suficiente por si só: um `StatusObject` residual então retornava `500` para a requisição
de carga de trabalho e, nesse ponto, cada nó tinha persistido um `registration-obj.yml`
vinculado ao registro que você excluiu, então entrava em loop com `404` sem recuperação
automática. A recuperação exigia duas reconstruções completas. Durante tudo isso,
`terraform plan` reportava **"Nenhuma alteração"**, porque do ponto de vista do Terraform
o estado desejado havia sido atingido.

[Issue 674](https://github.com/f5-sales-demo/mcn/issues/674) está fechado, pelo
[PR 693](https://github.com/f5-sales-demo/mcn/pull/693). `modules/xc-site` agora nomeia a
instância de VM do CE em `replace_triggered_by`, então substituir a VM substitui o objeto
de site, e excluir um site leva seus registros consigo — a chave do índice é liberada antes
da inicialização do nó substituto. A frota foi reconstruída do zero desde então e os três
sites ficaram `ONLINE` sem intervenção.

O acoplamento é observável, não assumido. Cada site está vinculado a um id de *instância*
de VM, e o registro correspondente reporta o mesmo valor como `infra.instance_id`:

```bash
cd terraform && terraform output -json ce_bound_instance_ids
```

Discordância entre os dois significa que um site ainda está vinculado a um nó que não
existe mais, que é o estado do qual um CE reconstruído nunca consegue sair pelo registro.
Ler a metade do registro ainda precisa de uma chamada de API direta — issue
[1376](https://github.com/f5-sales-demo/terraform-provider-xcsh/issues/1376) do provedor é
o que a colocaria na fonte de dados.
</Aside>

## Por que o cloud-init escreve a chave, e não a API

`admin_user_credentials.ssh_key` no objeto de site parece exatamente o campo para isso.
Ele é aceito, sobrevive a uma releitura e não configura nada. `vpm` é o dono dos usuários
locais do nó e se recusa a modificar este — do próprio log do nó, três vezes durante uma
única inicialização:

```text
vpm  users.go:165: Won't do any change for user admin (internal skip)
```

Tudo mais decorre dessa única linha. `/var/home/admin/.ssh` nunca existe, antes ou depois
do site atingir `ONLINE`. A data de última alteração do shadow do `admin` permanece na
data de build da imagem enquanto `vesbkp` e `vesopcon` mostram a data atual, porque `vpm`
definiu os dois e ignorou o `admin`. E `vpm` não registra nada sobre `ssh_key` ou
`authorized_keys` em nenhum momento.

Portanto, o arquivo precisa ser escrito fora do `vpm`. `admin` é uid 2202, gravado na
imagem do nó, então existe antes do cloud-init ser executado e `owner: admin:admin` é
resolvido no momento da escrita — sem `runcmd`, sem correção de propriedade:

```yaml
- path: /var/home/admin/.ssh/authorized_keys
  permissions: "0600"
  owner: admin:admin
  content: |
    ${ssh_public_key}
```

O `sshd` sempre esteve disposto. `sshd -T` reporta `pubkeyauthentication yes`, e `admin`
aparece em `AllowUsers` nos dois arquivos `sshd_config` que são fornecidos com o nó.
Nunca houve nada a habilitar — apenas um arquivo ausente.

<Aside type="danger" title="Não adicione novamente admin_user_credentials e não edite sshd_config">
`admin_user_credentials` foi integrado ao `terraform/modules/xc-site` e revertido depois
que esta evidência foi coletada (#660, PR #663). Não é uma lacuna esperando ser preenchida.

`sshd_config` é substituído durante o registro, então uma edição é descartada no momento
menos conveniente.
</Aside>

## Por que ele responde apenas em um endereço

O `sshd` faz bind em `0.0.0.0:22`, mas apenas o endereço **interno (SLI)** está na pilha
de rede do host de uma forma que o `sshd` responde. eth0 é renomeado para `a-i-eth0` e não
carrega nenhum IP do host — o plano de dados Argo é dono dessa interface, e o endereço de
gerenciamento/SLO que ela teria carregado aparece em `vhost0` em vez disso. As outras duas
NICs permanecem na pilha do host com seus próprios nomes.

Sondado a partir de uma VM dentro da VNet, contra um CE:

```text
endereço de gerenciamento/SLO    tempo esgotado
endereço externo                 tempo esgotado
endereço interno/SLI             ABERTO     SSH-2.0-OpenSSH_8.7
um endereço não utilizado        tempo esgotado    (controle)
```

Uma sondagem contra o endereço pelo qual você conhece o nó, portanto, retorna exatamente
o que um security group fechado retorna. Nada está bloqueando; simplesmente não há
listener nesse endereço.

<Aside type="caution" title="Não leia o nome da interface do guest para determinar em qual sub-rede você está">
Qual de `eth1` e `eth2` carrega o endereço interno **difere entre nós nesta mesma
implantação**. Lido ao vivo dos três CEs:

```text
f5-xc-ce-vm-01    eth1 -> externo      eth2 -> interno/SLI
f5-xc-ce-vm-02    eth2 -> externo      eth1 -> interno/SLI
f5-xc-ce-vm-03    eth1 -> externo      eth2 -> interno/SLI
```

Apenas duas coisas se mantêm em todos os nós: `a-i-eth0` não tem endereço, e `vhost0`
carrega o endereço de gerenciamento/SLO. Para qualquer outra coisa, corresponda pelo
endereço na saída de [`ip addr`](../../commands/network/ip/) em vez do nome da interface.
</Aside>

Os endereços públicos do CE também não têm listener na porta 22, razão pela qual o comando
acima usa `-J`: uma VM de operador dentro da VNet, na mesma sub-rede dos endereços SLI.
Esta implantação constrói uma para esse fim —
`terraform output -raw client_vm_name` a nomeia.

<Aside type="caution" title="-J não passa suas opções para o trecho de salto">
As opções fornecidas na linha de comando se aplicam ao salto final. `-o UserKnownHostsFile=/dev/null`
junto com `-J`, portanto, ainda consulta e escreve no seu `known_hosts` real para o host
de *salto*, o que é uma surpresa se você estiver tentando manter uma frota reconstruída
fora dele. Especifique o primeiro salto explicitamente quando isso importar:

```bash
ssh -tt -o ProxyCommand="ssh -W %h:%p -o UserKnownHostsFile=/dev/null azureuser@<operator-vm>" \
    -o UserKnownHostsFile=/dev/null -i ~/.ssh/id_ed25519 "admin@$SLI"
```

</Aside>

<Aside type="caution" title="Dois erros de medição que produzem respostas erradas com confiança">
Sondar eth0, a interface externa ou o endereço público na porta 22 reporta fechado
independentemente do estado SSH do nó, portanto não informa nada. Apenas o endereço SLI
responde.

E uma sondagem a partir de uma estação de trabalho corporativa pode reportar uma porta
**aberta** que está fechada: o Netskope conclui o handshake TCP por conta própria em
portas comuns. As portas 80 e 443 aparecem como abertas nos endereços públicos do CE a
partir de uma estação de trabalho e estão fechadas quando sondadas de dentro da VNet.
Sonde a partir de uma VM dentro da VNet.
</Aside>

## O Site CLI precisa de um terminal e de um retorno de carro

O shell de login do `admin` não é um shell. É uma aplicação `go-prompt`, que coloca o
terminal em modo raw e lê teclas em vez de linhas. Quatro consequências, cada uma das
quais falha de uma maneira que parece um problema diferente:

| Mecânica | O que acontece sem ela |
| --- | --- |
| Alocar um terminal (`ssh -tt`) | `panic: no such device or address` do `go-prompt.NewStandardInputParser`, que parece um appliance travado |
| Enviar um retorno de carro, não um avanço de linha, para Enter | A linha nunca é enviada e a sessão fecha no fim da entrada sem imprimir nada |
| Manter a entrada padrão aberta | A conexão termina antes do comando ser renderizado, então um comando que funciona parece silencioso |
| Escrever o texto do comando e o byte Enter **separadamente** | A nova linha cai no buffer como um caractere literal e o CLI responde `unknown command`, o que parece que o comando não existe |

`ssh host 'some-command'` portanto não funciona: o argumento é ignorado e o prompt
interativo inicia mesmo assim. Conduza-o como um terminal ou não o use.
`scripts/sitecli_ssh_harvest.py` é a implementação de referência.

<Aside type="caution" title="Um panic com 'no such device or address' significa que a autenticação TEVE SUCESSO">
`vpmu` o emite **após** o login, quando não encontra terminal para se conectar. Lido como
uma falha, parece o pior resultado possível, e na verdade é o último erro antes do sucesso.
Adicione `-tt` e conecte novamente.
</Aside>

<Aside type="caution" title="Substituir um CE altera sua chave de host">
O nó substituto apresenta uma chave de host diferente no mesmo endereço, então a próxima
conexão avisa `REMOTE HOST IDENTIFICATION HAS CHANGED` e recusa. Limpe a entrada antiga
para esse endereço e reconecte. Como habilitar o SSH substitui as VMs de qualquer forma,
espere isso na primeira conexão após adotá-lo.
</Aside>

## O banner é uma verificação de saúde gratuita

Antes de digitar qualquer coisa, o banner de login já respondeu várias das perguntas nas
quais você gastaria comandos. Do `f5-xc-ce-vm-01`, arte ASCII e IP público omitidos:

```text
UNAUTHORIZED ACCESS TO THIS DEVICE IS PROHIBITED
All actions performed on this device are audited

Using https://register.ves.volterra.io
OS: rhel-9.2024.6
Memory: 32768MiB
Storage: sda: 31GiB
CPU: Model: Intel(R) Xeon(R) Platinum 8272CL CPU @ 2.60GHz | CPUs: 8
Software: crt-20250613-3382
DNS: 168.63.129.16: OK
NTP: Synced
Uptime: 0 days, 5 hours, 20 minutes
Registration Status: PROVISIONED
SLO IP: 10.0.1.4/26
WELCOME IN SITE CLI
```

`Registration Status` distingue um nó ainda inicializando (`PROVISIONING`) de um que
concluiu (`PROVISIONED`). `Software` é a string de build que determina quais comandos
existem. `DNS` e `NTP` cobrem as duas dependências que quebram o registro primeiro, então
um nó que nunca ficou online geralmente já informou o motivo aqui — antes de
[`chronyc-sources`](../../commands/network/chronyc-sources/) ou
[`dig`](../../commands/network/dig/) serem necessários.

## Fornecendo o par de chaves

<Steps>

1. Gere um par de chaves, se ainda não tiver um. Ed25519 em vez de RSA: mais curto e
   aceito pelo `sshd` do appliance.

   ```bash
   ssh-keygen -t ed25519 -C "ce-operator" -f ~/.ssh/id_ed25519
   ```

2. Aponte a implantação para a metade **pública**. O módulo raiz lê o arquivo uma vez e
   passa a string para cada nó:

   ```hcl
   # terraform/terraform.tfvars
   ssh_public_key_path = "~/.ssh/id_ed25519.pub"
   ```

   `ssh_public_key` aceita o material inline, que é o que os testes de plano usam.
   A metade privada nunca sai da sua estação de trabalho.

3. Aplique. Leia o aviso no topo desta página primeiro — em uma implantação existente
   isso substitui as VMs do CE.

</Steps>

<Aside type="note" title="O admin_ssh_key da própria VM é algo diferente">
`azurerm_linux_virtual_machine.admin_ssh_key` em `modules/ce-node` autoriza o
administrador da VM do Azure, não a conta `admin` do appliance. Ele não concede acesso ao
Site CLI, e tê-lo configurado não é evidência de que o SSH do CE está configurado.
</Aside>

## O que isso não é

Cada um destes foi testado e descartado enquanto a rota ainda era considerada impossível.
Cada um é plausível o suficiente para custar um dia.

| Não é a causa | Como foi descartado |
| --- | --- |
| A credencial só se aplica no momento da criação | `sshd` inicia cerca de 90 segundos na primeira inicialização, antes do objeto de site existir. `admin_user_credentials` também está presente em `ReplaceSpecType` e se aplica no lugar. |
| `block_all_services` | O fechamento da porta 22 no endereço de gerenciamento é idêntico com ou sem bloqueio de serviços. |
| Uma nova linha à direita na chave | Testado de ambas as formas, sem alteração. O cloud-init ainda a remove, pois um bloco literal caso contrário renderizaria uma segunda linha vazia. |
| Software do CE fixado em versão mais antiga | Reproduzido em três builds, incluindo um rodando OpenSSH 9.9. |
| Um `admin_password` ausente | Definir `admin_password` junto com `ssh_key` em um CE do zero não mudou nada. |

<Aside type="caution" title="Dois campos da API que parecem discriminadores e não são">
`gc_spec.admin_ssh_key` está vazio ou ausente em **todos os 58 sites em `f5-sales-demo`** —
incluindo os dois que definem `admin_user_credentials.ssh_key`. Compará-lo entre um site
que funciona e um que não funciona não informa nada, pois aparece vazio mesmo para os sites
onde a credencial *está* configurada.

`registrations_by_site` omite o campo completamente e retorna `None` para ele, o que
aparece como "não configurado" em vez de "não reportado".
</Aside>

<Aside type="caution" title="Um site recém-criado precisa de cerca de meia hora antes de a API de debug responder">
Por aproximadamente 25 a 30 minutos após um novo site reportar `ONLINE`, os endpoints
`vpm/debug` retornam uma página `503` do BIG-IP com a mensagem `The requested URL was
rejected`. Isso parece um bloqueio de firewall de aplicação web ou um token revogado, e
não é nenhum dos dois: o site não está pronto para retransmitir ainda. Aguarde e tente
novamente em vez de alterar qualquer coisa.

O SSH não tem esse aquecimento. Ele responde assim que o `sshd` está ativo, razão pela
qual é a rota que funciona enquanto um nó ainda está se registrando.
</Aside>
