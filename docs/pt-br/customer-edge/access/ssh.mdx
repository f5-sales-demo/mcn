O SSH acessa a conta `admin` do appliance, cujo shell de login é o Site CLI
(`/opt/bin/vpmu`). Esta é a única rota para a **superfície completa de comandos no box** — a
[API de debug](../debug-api/) expõe 34 comandos, e o próprio appliance oferece muito mais
que não estão nessa API.

```bash
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<operator-vm> admin@10.0.3.5
```

Cada parte dessa linha de comando é essencial, e as três próximas seções explicam
qual falha cada uma previne.

<Aside type="caution" title="Habilitar isso em uma implantação em execução substitui as VMs">
A chave é escrita pelo cloud-init, e o `write_files` do cloud-init é executado **apenas na
primeira inicialização**. Ativar isso para nós existentes significa substituí-los, o que
atualmente trava o registro: o registro obsoleto mantém o índice único
`(tenant, cluster_name, hostname)`, o nó substituto nunca consegue se registrar, e o
`terraform plan` reporta "No changes" o tempo todo. Consulte a
[issue 674](https://github.com/f5-sales-demo/mcn/issues/674) antes de planejar a
alteração, não depois.
</Aside>

## Por que o cloud-init escreve a chave, e não a API

`admin_user_credentials.ssh_key` no objeto do site parece exatamente com o campo para
isso. Ele é aceito, sobrevive a uma releitura e não configura nada. O `vpm` é o dono dos
usuários locais do nó e recusa-se a alterar este — do próprio log do nó, três vezes
em uma única inicialização:

```text
vpm  users.go:165: Won't do any change for user admin (internal skip)
```

Todo o resto decorre dessa única linha. `/var/home/admin/.ssh` nunca existe, antes ou
depois de o site atingir `ONLINE`. A data da última alteração da senha shadow do `admin`
permanece na data de build da imagem, enquanto `vesbkp` e `vesopcon` mostram a data atual,
porque o `vpm` configurou esses dois e pulou o `admin`. E o `vpm` não registra nada sobre
`ssh_key` ou `authorized_keys` em nenhum momento.

Portanto, o arquivo precisa ser escrito fora do `vpm`. O `admin` tem uid 2202, embutido na
imagem do nó, então ele existe antes do cloud-init ser executado e `owner: admin:admin`
é resolvido no momento da escrita — sem `runcmd`, sem correção de propriedade:

```yaml
- path: /var/home/admin/.ssh/authorized_keys
  permissions: "0600"
  owner: admin:admin
  content: |
    ${ssh_public_key}
```

O `sshd` sempre esteve disposto. `sshd -T` reporta `pubkeyauthentication yes`, e `admin`
aparece em `AllowUsers` nos dois arquivos `sshd_config` que acompanham o nó. Nunca
houve nada a habilitar — apenas um arquivo ausente.

<Aside type="danger" title="Não readicione admin_user_credentials e não edite o sshd_config">
`admin_user_credentials` foi integrado ao `terraform/modules/xc-site` e revertido após
essa evidência ser coletada (#660, PR #663). Não é uma lacuna aguardando preenchimento.

O `sshd_config` é substituído durante o registro, portanto uma edição nele é descartada
no momento menos conveniente.
</Aside>

## Por que responde em apenas um endereço

O `sshd` faz bind em `0.0.0.0:22`, mas apenas o endereço **interno (SLI)** está na pilha
de rede do host. A eth0 é renomeada para `a-i-eth0` e não carrega IP do host — o plano de
dados Argo é o dono dessa interface — enquanto eth1 e eth2 permanecem na pilha do host,
onde o `sshd` está escutando.

Sondagem a partir de uma VM dentro da VNet:

```text
10.0.1.4     timed out             CE mgmt/SLO  (eth0)
10.0.2.4     timed out             CE external  (eth1)
10.0.3.5     OPEN                  CE internal/SLI
10.0.3.6     OPEN
10.0.3.7     OPEN
```

Uma sondagem contra o endereço pelo qual você conhece o nó, portanto, retorna exatamente
o que um security group fechado retorna. Nada está bloqueando; não há listener nesse
endereço.

Os endereços públicos do CE também não têm listener na porta 22, por isso o comando acima
usa `-J`: uma VM de operador dentro da VNet, na mesma sub-rede que os endereços SLI.

<Aside type="caution" title="Dois erros de medição que produzem respostas erradas com confiança">
Sondar a eth0, a interface externa ou o endereço público pela porta 22 reporta fechado
independentemente do estado SSH do nó, portanto isso não fornece nenhuma informação. Apenas
o endereço SLI responde.

E uma sondagem de uma estação de trabalho corporativa pode reportar uma porta **aberta**
que está fechada: o Netskope completa o handshake TCP por conta própria em portas comuns.
As portas 80 e 443 aparecem como abertas nos endereços públicos do CE a partir de uma
estação de trabalho e estão fechadas quando sondadas de dentro da VNet. Sonde a partir de
uma VM na VNet.
</Aside>

## O Site CLI precisa de um terminal e de um carriage return

O shell de login do `admin` não é um shell. É uma aplicação `go-prompt`, que coloca o
terminal em modo raw e lê teclas em vez de linhas. Quatro consequências, cada uma das
quais falha de uma forma que parece um problema diferente:

| Mecanismo | O que acontece sem ele |
| --- | --- |
| Alocar um terminal (`ssh -tt`) | `panic: no such device or address` do `go-prompt.NewStandardInputParser`, que parece um appliance com crash |
| Enviar um carriage return, não um line feed, para Enter | A linha nunca é submetida e a sessão é encerrada ao fim da entrada sem ter imprimido nada |
| Manter a entrada padrão aberta | A conexão termina antes do comando ter sido renderizado, então um comando funcional parece silencioso |
| Escrever o texto do comando e o byte Enter **separadamente** | A nova linha cai no buffer como um caractere literal e o CLI responde `unknown command`, o que parece indicar que o comando não existe |

`ssh host 'some-command'` portanto não funciona: o argumento é ignorado e o prompt
interativo inicia de qualquer forma. Utilize-o como terminal ou não utilize.
`scripts/sitecli_ssh_harvest.py` é a implementação de referência.

O banner de login reporta o estado de registro do nó, que é a maneira mais rápida de
distinguir um nó ainda inicializando de um que está quebrado:

```text
Registration Status: PROVISIONING
SLO IP: 10.0.1.4/26
```

## Fornecendo o par de chaves

<Steps>

1. Gere um par de chaves, caso ainda não tenha um. Ed25519 em vez de RSA: mais curto
   e aceito pelo `sshd` do appliance.

   ```bash
   ssh-keygen -t ed25519 -C "ce-operator" -f ~/.ssh/id_ed25519
   ```

2. Aponte a implantação para a metade **pública**. O módulo raiz lê o arquivo uma vez e
   passa a string para cada nó:

   ```hcl
   # terraform/terraform.tfvars
   ssh_public_key_path = "~/.ssh/id_ed25519.pub"
   ```

   `ssh_public_key` aceita o conteúdo diretamente, que é o que os testes do plano usam.
   A metade privada nunca sai da sua estação de trabalho.

3. Aplique. Leia o aviso no topo desta página primeiro — em uma implantação existente isso
   substitui as VMs do CE.

</Steps>

<Aside type="note" title="O admin_ssh_key da própria VM é algo diferente">
`azurerm_linux_virtual_machine.admin_ssh_key` em `modules/ce-node` autoriza o
administrador da VM Azure, não a conta `admin` do appliance. Ele não concede acesso ao
Site CLI, e tê-lo configurado não é evidência de que o SSH do CE está configurado.
</Aside>

## O que isso não é

Cada um desses itens foi testado e descartado enquanto a rota ainda era considerada
impossível. Cada um é plausível o suficiente para custar um dia de trabalho.

| Não é a causa | Como foi descartado |
| --- | --- |
| A credencial só se aplica no momento da criação | O `sshd` inicia cerca de 90 segundos na primeira inicialização, antes de o objeto do site existir. `admin_user_credentials` também está presente em `ReplaceSpecType` e se aplica no lugar. |
| `block_all_services` | O fechamento da porta 22 no endereço de gerenciamento é idêntico independentemente de os serviços estarem bloqueados ou não. |
| Uma nova linha no final da chave | Testado das duas formas, sem alteração. O cloud-init ainda a remove, porque um bloco literal de outra forma renderizaria uma segunda linha vazia. |
| Software CE mais antigo fixado | Reproduzido em três builds, incluindo um executando OpenSSH 9.9. |
| Um `admin_password` ausente | Definir `admin_password` junto com `ssh_key` em um CE do zero não alterou nada. |

<Aside type="caution" title="Dois campos da API que parecem discriminadores e não são">
`gc_spec.admin_ssh_key` está vazio em **todos os 88 sites do tenant**, incluindo os 20 que
definem `admin_password`. Comparar isso entre um site funcionando e um não funcionando não
informa nada, pois está vazio em todo lugar.

`registrations_by_site` omite o campo completamente e retorna `None` para ele, o que
parece "não configurado" em vez de "não reportado".
</Aside>

<Aside type="caution" title="Um site recém-criado precisa de cerca de meia hora antes de a API de operação responder">
Por aproximadamente 25 a 30 minutos após um novo site reportar `ONLINE`, os endpoints
`vpm/debug` retornam uma página BIG-IP `503` com o texto `The requested URL was rejected`.
Isso parece um bloqueio de web application firewall, ou um token revogado, e não é nenhum
dos dois: o site ainda não está pronto para fazer relay. Aguarde e tente novamente em vez
de alterar qualquer coisa.

O SSH não tem esse período de aquecimento. Ele responde assim que o `sshd` está ativo, por
isso é a rota que funciona enquanto um nó ainda está se registrando.
</Aside>
