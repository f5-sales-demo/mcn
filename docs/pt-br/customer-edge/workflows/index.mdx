A [referência de comandos](../commands/) está organizada pelo que cada comando faz. Estes
estão organizados pelo que deu errado.

| Sintoma | Fluxo de trabalho |
| --- | --- |
| O site nunca ficou online ou saiu do tenant | [Registro](./registration/) |
| Rotas não são anunciadas nem aprendidas; o VIP está inacessível | [BGP](./bgp-diagnostics/) |
| O tráfego chega ao nó, mas não é entregue | [Plano de dados](./dataplane-diagnostics/) |

Cada etapa tem link para a página que documenta o comando. Nada é repetido aqui,
de modo que a sintaxe tem exatamente um lugar de origem e não pode divergir do nó.

## Antes de qualquer um deles

Determine em qual caminho de acesso você está, pois isso altera o que é possível fazer:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/config/namespaces/system/sites/<site>" | jq -r '.spec.site_state'
```

`ONLINE` significa que a [API de depuração](../access/debug-api/) responderá. Qualquer outro valor significa que o
fluxo de trabalho de registro é o que você precisa, junto com uma das rotas que não dependem do
registro: [Console do Site](../access/site-console/) enquanto o nó ainda tiver um caminho de rede,
[console serial](../access/serial-console/) quando não tiver.

Um site que está **completamente ausente** tem mais uma explicação a ser descartada antes de "ele nunca
se registrou": a de que você está consultando o tenant errado. `cd terraform && terraform output -raw
xc_tenant` informa o nome daquele ao qual esta implantação pertence.
