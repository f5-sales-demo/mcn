Ejecute estas comprobaciones antes de presentar. Cada una acota dónde estaría un fallo, de modo que un error le
dice algo en lugar de solamente que algo va mal.

Cada comando lee lo que necesita del despliegue. Defina esto una vez y el resto sigue:

```bash
cd terraform
RG=$(terraform output -raw resource_group_name)
RS=$(terraform output -raw route_server_name)
CLIENT=$(terraform output -raw client_vm_name)
DOMAIN=$(terraform output -raw lb_domain)
VIP=$(terraform output -raw vip)
NIC=$(terraform output -raw client_nic_name)
```

## Cuatro comprobaciones, en este orden

<Steps>

1. **Todos los sitios están `ONLINE`.** Nada de lo que sigue puede ser cierto si esto no lo es.

   ```bash
   for s in $(terraform output -json xc_site_names | jq -r '.[]'); do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   Observado el 2026-07-28, tres CE:

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **Cada peering está aprendiendo el anuncio del VIP de ese CE.** Consulte cada peering
   por separado — vea la primera trampa más abajo, porque aquí es donde la demostración parece
   estar rota con más frecuencia y no lo está.

   ```bash
   for k in $(terraform output -json xc_site_names | jq -r 'keys[]'); do
     echo "--- ${k}-bgp"
     az network routeserver peering list-learned-routes \
       --name "${k}-bgp" --routeserver "$RS" -g "$RG" \
       --query "RouteServiceRole_IN_0[?network=='${VIP}/32'].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   Observado el 2026-07-28:

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp
   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp
   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   Tres peerings, tres siguientes saltos distintos, un prefijo. Ese es el lado del anuncio de
   ECMP demostrado.

3. **Las rutas efectivas del cliente incluyen todos los siguientes saltos.** Esto es el ECMP en sí,
   tal como lo ha programado la VNet — no lo que afirman los CE, sino lo que Azure ha hecho con ello.

   ```bash
   az network nic show-effective-route-table -g "$RG" -n "$NIC" \
     --query "value[?addressPrefix[0]=='${VIP}/32'].{prefix:addressPrefix[0],nh:nextHopIpAddress,type:nextHopType,state:state}" \
     -o json
   ```

   Observado el 2026-07-28:

   ```json
   [
     {
       "nh": ["10.0.1.5", "10.0.1.6", "10.0.1.4"],
       "prefix": "10.250.0.10/32",
       "state": "Active",
       "type": "VirtualNetworkGateway"
     }
   ]
   ```

   `state: Active` con una entrada por CE en `nh` es la comprobación. **El orden no es
   significativo y no es estable** — Azure los devuelve de forma distinta entre llamadas, así que
   cuéntelos en lugar de compararlos con una ejecución anterior. Un solo siguiente salto donde espera tres significa
   que un CE ha dejado de anunciar, y el paso 2 identifica cuál.

4. **El VIP sirve tráfico.** Desde la VM cliente, y **con la cabecera `Host`** — vea la
   segunda trampa. Muestree suficientes peticiones para ver un problema: unas pocas docenas se leen como 100 % incluso
   dentro de la ventana de convergencia descrita más abajo.

   ```bash
   az vm run-command invoke -g "$RG" -n "$CLIENT" \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts "ok=0; fail=0
                for i in \$(seq 1 60); do
                  c=\$(curl -s -o /dev/null -m 5 -w '%{http_code}' \
                        -H 'Host: ${DOMAIN}' http://${VIP}/)
                  [ \"\$c\" = 200 ] && ok=\$((ok+1)) || fail=\$((fail+1))
                done
                echo \"OK=\$ok FAIL=\$fail\""
   ```

   Observado el 2026-07-28:

   ```text
   VIP with Host header: OK=60 FAIL=0
   bare IP (no Host): 404
   ```

</Steps>

## Trampa: un peering muestra una sola ruta, y eso es correcto

`list-learned-routes` se limita al peering que usted indica. Informa de lo que **ese** peer
anunció, no de toda la tabla del Route Server.

Así que consultar un solo peering devuelve un único `/32` del VIP a través de un único siguiente salto, y resulta
tentador leerlo como «solo un CE está anunciando — los demás están caídos». Nada está
caído. Los otros anuncios son visibles en sus propios peerings, que es lo que recorre el paso 2.

Confirmar ECMP a partir de la consulta de un único peering no es posible. Bien recorra todos los peerings, bien
lea la tabla de rutas efectivas del cliente, que muestra el resultado combinado en una sola llamada.

## Trampa: una petición con la IP desnuda devuelve 404

El balanceador de carga hace coincidencias sobre `Host`. El VIP no es un servidor virtual que sirva algo a
quienquiera que se conecte a la dirección.

Ambos resultados provienen de la misma ejecución contra el despliegue en buen estado:

```text
curl -H "Host: $DOMAIN" http://$VIP/   ->  200   (60 of 60)
curl                     http://$VIP/   ->  404
```

**Un 404 con la IP desnuda es prueba de que la ruta funciona** — la petición llegó al CE, el proxy del CE
respondió, y la rechazó porque ningún dominio configurado coincidía. Leerlo como una interrupción
le hace mirar el BGP, donde no encontrará nada mal.

Lo mismo se aplica durante una demostración: si escribe la dirección en un navegador en lugar de resolver
el dominio a ella, obtiene el 404.

## El VIP descarta peticiones durante los primeros tres cuartos de hora, y luego deja de hacerlo

En una pila recién construida, el VIP pierde una pequeña fracción de las peticiones durante aproximadamente los
primeros 45 minutos después de que los CE alcanzan `ONLINE`, y después sirve sin problemas. Medido sobre 1.470
peticiones desde la VM cliente, todas con la cabecera `Host`:

| Ventana | Peticiones | Fallos | Tasa |
| --- | --- | --- | --- |
| Primeros ~45 minutos tras el establecimiento de ECMP | 570 | 12 | **2,11 %** |
| Los 23 minutos siguientes | 900 | **0** | **0,00 %** |

Cada fallo fue `curl: (28)` — un tiempo de espera agotado con cero bytes recibidos — no un estado de error
HTTP. El último se produjo unos 43 minutos después de que ECMP se estableciera. De las 900 peticiones correctas,
400 se ejecutaron con un tiempo de espera de 30 segundos y todas ellas terminaron en menos de 2 segundos, así que nada quedó
oculto por un tiempo de espera corto.

**El origen no fue la causa.** Un lote de control directo al origen
(`terraform output -raw origin_ip`, evitando el VIP) ejecutó 120 de 120 correctas *simultáneamente
con* lotes fallidos contra el VIP. El fallo está en algún punto de la ruta VIP, ECMP o CE.

Dos cosas que deliberadamente no se llaman así:

- **No es un defecto de estado estable.** Se resuelve por completo y sigue resuelto. Una demostración que ha
  estado activa durante una hora no tiene este problema — 60 de 60 en la comprobación 4 anterior, en una pila
  que había estado activa durante horas.
- **No es atribuible a un CE concreto.** Nada en esta topología proporciona un listener HTTP por nodo,
  así que no hay forma de asociar una petición descartada al nodo que la descartó.
  Las interfaces externas de los CE no tienen ningún listener HTTP — solo responde el `/32` del VIP.

Se reprodujo en una reconstrucción limpia en un tenant distinto, así que sigue a la topología y no
al entorno.

<Aside type="caution" title="No muestree 40 peticiones y concluya que va bien">
Los lotes de 40 a 50 se leen como 100 % la mayoría de las veces, incluso dentro de la ventana de fallo. Así es
como esto se caracterizó erróneamente primero como un fallo continuo de baja tasa y después como la ausencia total de
fallo. Muestree 100 o más, en lotes separados en el tiempo.
</Aside>

## Dos trampas más de medición

Ambas produjeron respuestas erróneas con total confianza en este entorno, y ninguna es obvia.

- **Sondee desde dentro de la VNet, no desde su estación de trabajo.** Un proxy corporativo puede completar
  él mismo el establecimiento TCP en puertos comunes, de modo que un sondeo desde la estación de trabajo informa de un puerto **abierto**
  que en realidad está cerrado. Los puertos 80 y 443 se leen como abiertos en las direcciones públicas de los CE desde una
  estación de trabajo y están cerrados cuando se sondean desde dentro de la VNet. Use la VM cliente.
- **El puerto 22 de un CE responde únicamente en la dirección interna (SLI).** Sondeado desde la VM cliente,
  la dirección interna de cada CE devuelve un banner de OpenSSH, mientras que sus direcciones de gestión y externa
  expiran — igual que una dirección sin usar utilizada como control. eth0 se renombra
  `a-i-eth0` y no lleva IP de host, porque el datapath es su propietario. Así que sondear la dirección
  por la que conoce el nodo no le dice nada sobre el estado de SSH del nodo.

<Aside type="danger" title="Nunca codifique de forma fija una dirección interna de CE — se reasignan en cada reconstrucción">
Azure no preserva qué CE recibe qué dirección en la subred interna. Observado el
2026-07-28, tras una reconstrucción, los tres CE tenían `10.0.3.7`, `10.0.3.5` y `10.0.3.4`: no
en orden de nodo, no contiguas y distintas de las que tenían antes. La propia NIC del cliente de prueba
está en la misma subred y ha tenido una dirección que antes tenía un CE.

Léalas en lugar de recordarlas:

```bash
terraform output -json ce_sli_private_ips
```

Sin el estado de Terraform a mano, pregunte a Azure por el nombre de la NIC, que *sí* es estable:

```bash
az network nic show -g "$RG" -n "<vm-name>-internal-nic" \
  --query ipConfigurations[0].privateIPAddress -o tsv
```

Conectarse a una dirección recordada le lleva al nodo equivocado, a una VM que no es un CE,
o a ningún sitio — y esto último tiene exactamente el mismo aspecto que «SSH no está habilitado».
</Aside>

## Confirme que la superficie de comandos en el equipo sigue coincidiendo con la documentación

```bash
bash scripts/capture-sitecli.sh --check \
  --site "$(terraform output -json xc_site_names | jq -r '.eastus01')" \
  --node "$(terraform output -json ce_vm_names | jq -r '.eastus01')"
```

`--check` no escribe nada, así que es seguro ejecutarlo contra la demostración en producción.
