Este despliegue demuestra la **alta disponibilidad activo/activo de Customer Edge en Azure**
sin ningún balanceador de carga de Azure delante de los CE. Tres CE originan cada uno la misma
ruta de host mediante eBGP, y el Azure Route Server instala los tres como próximos saltos de
igual coste en la VNet. Por lo tanto, la infraestructura de enrutamiento, en lugar de un
balanceador de carga, es donde deben producirse la distribución del tráfico y la eliminación
de nodos con fallos.

Todo lo que se muestra a continuación se ejecutó contra el despliegue en vivo, y la salida es la
salida que produjo. Dos cosas que esa frase *no* cubre — la conmutación por error y la distribución
del tráfico — se señalan al final en lugar de darse por supuestas.

## Qué se despliega

```text
                  Azure Route Server  ce-ha-lab-rrs  ASN 65515
                          10.0.4.4  and  10.0.4.5
                                      |
              +-----------------------+-----------------------+
              |                       |                       |
        eastus01-bgp            eastus02-bgp            eastus03-bgp     eBGP
              |                       |                       |      CE ASN 64512
        10.0.1.4                10.0.1.5                10.0.1.6     <- CE eth0 / SLO
     f5-xc-ce-vm-01          f5-xc-ce-vm-02          f5-xc-ce-vm-03
    ar-bgp-eastus01         ar-bgp-eastus02         ar-bgp-eastus03
              |                       |                       |
              +----- each advertises 10.250.0.10/32 -----------+
                          three-way ECMP into the VNet
```

| Elemento | Según lo construido |
| --- | --- |
| Customer Edges | 3 sitios Secure Mesh v2 de un solo nodo — `ar-bgp-eastus01`, `ar-bgp-eastus02`, `ar-bgp-eastus03` |
| Software del CE | fijado en `9.2024.6`, build `crt-20250613-3382` |
| VM de Azure | `f5-xc-ce-vm-01/02/03`, tres NIC cada una (gestión/SLO, externa, interna/SLI) |
| Intercambio de rutas | Azure Route Server `ce-ha-lab-rrs`, ASN `65515`, instancias `10.0.4.4` y `10.0.4.5` |
| Peerings | uno por CE — `eastus01-bgp`, `eastus02-bgp`, `eastus03-bgp` — ASN del CE `64512` |
| VIP anunciada | `10.250.0.10/32`, originada de forma idéntica por los tres CE |
| Balanceador de carga | `ar-bgp-ecmp-lb`, que sirve el dominio `ar-bgp-ecmp.bankexample.com` |
| Cliente de prueba | `ar-ecmp-client`, una VM dentro de la misma VNet |
| Grupo de recursos | `rg-mcn-ce-ha-rmordasiewicz` |

<Aside type="caution" title="La VIP debe situarse fuera de todos los CIDR de la VNet">
`terraform/main.tf` incluye un bloque `check` que afirma que la VIP está fuera de los CIDR tanto
del hub como del spoke, y rechaza el plan en caso contrario. La razón declarada es que una VIP
dentro de un CIDR de la VNet pierde frente a la propia ruta del sistema de la VNet, a pesar de que
la ruta BGP sea más específica.

Trate esa salvaguarda como el contrato: si vuelve a apuntar esta demostración a un
direccionamiento distinto, la VIP debe salir de los rangos de la VNet junto con él.
</Aside>

## Compruebe que está en buen estado antes de presentar

Cuatro comprobaciones, en este orden. Cada una acota dónde estaría un fallo, de modo que un
error le indica algo en lugar de únicamente que algo va mal.

<Steps>

1. **Los tres sitios están `ONLINE`.** Nada de lo que sigue puede ser cierto si esto no lo es.

   ```bash
   for s in ar-bgp-eastus01 ar-bgp-eastus02 ar-bgp-eastus03; do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **Cada peering está aprendiendo el anuncio de la VIP de ese CE.** Consulte cada peering
   por separado — vea la trampa más abajo, porque aquí es donde la demostración parece
   estar rota con más frecuencia sin estarlo.

   ```bash
   for p in eastus01-bgp eastus02-bgp eastus03-bgp; do
     echo "--- $p"
     az network routeserver peering list-learned-routes \
       --name "$p" --routeserver ce-ha-lab-rrs -g rg-mcn-ce-ha-rmordasiewicz \
       --query "RouteServiceRole_IN_0[].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp

   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp

   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   Tres peerings, tres próximos saltos distintos, un prefijo. Eso demuestra el lado del
   anuncio de ECMP.

3. **Las rutas efectivas del cliente incluyen los tres próximos saltos.** Esto es el ECMP en
   sí, tal como la VNet lo ha programado — no lo que afirman los CE, sino lo que Azure hizo
   con ello.

   ```bash
   az network nic show-effective-route-table \
     --name ar-ecmp-clientVMNic -g rg-mcn-ce-ha-rmordasiewicz \
     --query "value[?addressPrefix[0]=='10.250.0.10/32']" -o json
   ```

   ```json
   [
     {
       "addressPrefix": ["10.250.0.10/32"],
       "nextHopIpAddress": ["10.0.1.5", "10.0.1.4", "10.0.1.6"],
       "nextHopType": "VirtualNetworkGateway",
       "source": "VirtualNetworkGateway",
       "state": "Active"
     }
   ]
   ```

   `state: Active` con tres entradas en `nextHopIpAddress` es la comprobación. Un único
   próximo salto donde espera tres significa que un CE ha dejado de anunciar, y el paso 2
   identifica cuál.

4. **La VIP sirve tráfico.** Desde la VM cliente y **con la cabecera `Host`** — vea la
   segunda trampa más abajo.

   ```bash
   az vm run-command invoke -g rg-mcn-ce-ha-rmordasiewicz -n ar-ecmp-client \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts 'for i in $(seq 1 10); do
                  curl -s -o /dev/null -w "%{http_code} " \
                    -H "Host: ar-bgp-ecmp.bankexample.com" http://10.250.0.10/
                done'
   ```

   ```text
   200 200 200 200 200 200 200 200 200 200
   ```

</Steps>

## Trampa: un peering muestra una sola ruta, y es correcto

`list-learned-routes` está limitado al peering que indique. Informa de lo que anunció **ese**
peer, no de la tabla completa del Route Server.

Así que consultar `eastus01-bgp` por separado devuelve un único `10.250.0.10/32` vía `10.0.1.4`,
y resulta tentador interpretarlo como «solo un CE está anunciando: los otros dos están caídos».
Nada está caído. Los otros dos anuncios son visibles en sus propios peerings, que es lo que
recorre el paso 2 anterior.

Confirmar ECMP desde una única consulta de peering no es posible. O recorre los tres peerings,
o lee la tabla de rutas efectivas del cliente, que muestra el resultado combinado en una sola
llamada.

## Trampa: una petición a la IP a secas devuelve 404

El balanceador de carga hace coincidencias por `Host`. La VIP no es un servidor virtual que
sirva algo a quien sea que se conecte a la dirección.

```text
curl -H 'Host: ar-bgp-ecmp.bankexample.com' http://10.250.0.10/   ->  200   (10 of 10)
curl                                        http://10.250.0.10/   ->  404
```

Ambos resultados se produjeron en la misma ejecución contra el despliegue en buen estado. **Un
404 con la IP a secas es la prueba de que la ruta funciona**: la petición llegó al CE, el proxy
del CE respondió y la rechazó porque ningún dominio configurado coincidió. Interpretarlo como
una interrupción le lleva a mirar BGP, donde no encontrará nada mal.

Lo mismo se aplica durante una demostración: si escribe la dirección en un navegador en lugar
de resolver el dominio hacia ella, obtiene el 404.

## La aprobación del registro está automatizada, y el apply sigue siendo en dos fases

La aprobación del registro ya no necesita a una persona en la consola. Con el proveedor
**v3.81.1**, el recurso `xcsh_registration_approval` la realiza, y el módulo del sitio resuelve
qué registro aprobar.

Eso sigue sin convertir el despliegue en un único `apply` desatendido, y la razón merece
entenderse antes de observar una primera ejecución y concluir que falló:

- El objeto de registro de un CE se llama **`r-<uuid>`**. Nunca se nombra a partir del sitio,
  de modo que nada puede predecir el nombre en el momento del plan.
- El registro solo existe después de que la VM haya arrancado y `vpm` se haya registrado.
- Por lo tanto, el **primer apply no planifica ninguna aprobación**. Vuelva a aplicar una vez
  que los CE se hayan registrado y se hayan creado las aprobaciones.

`terraform/main.tf` documenta este orden en la parte superior del archivo, que es la versión
autoritativa: la secuencia de despliegue vive junto al código que la implementa.

<Aside type="caution" title="Un sitio recién creado no es inmediatamente accesible mediante la API de operación">
Durante aproximadamente 25 a 30 minutos después de que un sitio nuevo informe `ONLINE`, los
endpoints `vpm/debug` responden con una página `503` de BIG-IP que dice `The requested URL was
rejected`. Parece un bloqueo de un firewall de aplicaciones web o un token revocado, y no es
ninguna de las dos cosas. Espere y vuelva a intentarlo.

Esto afecta a una demostración recién construida, no a una en funcionamiento.
</Aside>

## Dos trampas más de medición

Ambas produjeron respuestas erróneas con total confianza en este entorno, y ninguna es
evidente.

- **Haga las pruebas desde dentro de la VNet, no desde su estación de trabajo.** Netskope
  completa él mismo el handshake TCP en los puertos habituales, de modo que una prueba desde
  la estación de trabajo informa de un puerto **abierto** que en realidad está cerrado. Los
  puertos 80 y 443 se leen como abiertos en las direcciones públicas del CE desde una
  estación de trabajo y están cerrados al probarlos desde dentro de la VNet. Use
  `ar-ecmp-client`.
- **El puerto 22 de un CE responde solo en la dirección interna (SLI).** Probados desde
  `ar-ecmp-client` contra los tres CE, `10.0.3.5`, `10.0.3.6` y `10.0.3.7` devuelven todos
  `SSH-2.0-OpenSSH_8.7`, mientras que las direcciones de gestión y externa expiran, igual que
  una dirección sin usar empleada como control. Por lo tanto, probar la dirección por la que
  conoce el nodo no le dice nada sobre el estado de SSH del nodo.

<Aside type="note" title="Lo que esta página no afirma">
Dos cosas que un lector podría esperar razonablemente aquí están deliberadamente ausentes,
porque no se ejercitaron contra el despliegue:

- **No se probó la conmutación por error.** Se verifica que los tres próximos saltos de igual
  coste están instalados; lo que ocurre con la tabla de rutas cuando se detiene un CE no se
  muestra, así que no ensaye una demostración de conmutación por error a partir de esta página
  sin probarla antes.
- **No se midió la distribución del tráfico.** Diez de diez peticiones a la VIP devolvieron
  `200`, lo que demuestra que la ruta funciona. No muestra cómo se repartieron esas diez entre
  los tres próximos saltos.

</Aside>
