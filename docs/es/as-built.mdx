Este despliegue demuestra **alta disponibilidad activo/activo de Customer Edge en Azure**
sin ningún balanceador de carga de Azure delante de los CE. Tres CE originan cada uno la
misma ruta de host por eBGP, y el Azure Route Server instala los tres como saltos
siguientes de igual coste en la VNet. Por tanto, es el tejido de enrutamiento, y no un
balanceador de carga, donde se supone que ocurren la distribución de tráfico y la
eliminación de nodos caídos.

Todo lo que se muestra a continuación se ejecutó contra el despliegue en vivo, y la salida
es la salida que produjo. Dos cosas que esa frase *no* cubre —la conmutación por error y
la distribución de tráfico— se señalan al final en lugar de darse por supuestas.

## Qué está desplegado

```text
                  Azure Route Server  ce-ha-lab-rrs  ASN 65515
                          10.0.4.4  and  10.0.4.5
                                      |
              +-----------------------+-----------------------+
              |                       |                       |
        eastus01-bgp            eastus02-bgp            eastus03-bgp     eBGP
              |                       |                       |      CE ASN 64512
        10.0.1.4                10.0.1.5                10.0.1.6     <- CE eth0 / SLO
     f5-xc-ce-vm-01          f5-xc-ce-vm-02          f5-xc-ce-vm-03
    ar-bgp-eastus01         ar-bgp-eastus02         ar-bgp-eastus03
              |                       |                       |
              +----- each advertises 10.250.0.10/32 -----------+
                          three-way ECMP into the VNet
```

| Elemento | Según lo construido |
| --- | --- |
| Customer Edges | 3 sitios Secure Mesh v2 de un solo nodo — `ar-bgp-eastus01`, `ar-bgp-eastus02`, `ar-bgp-eastus03` |
| Software del CE | fijado en `9.2024.6`, build `crt-20250613-3382` |
| VM de Azure | `f5-xc-ce-vm-01/02/03`, tres NIC cada una (gestión/SLO, externa, interna/SLI) |
| Intercambio de rutas | Azure Route Server `ce-ha-lab-rrs`, ASN `65515`, instancias `10.0.4.4` y `10.0.4.5` |
| Peerings | uno por CE — `eastus01-bgp`, `eastus02-bgp`, `eastus03-bgp` — ASN del CE `64512` |
| VIP anunciada | `10.250.0.10/32`, originada de forma idéntica por los tres CE |
| Balanceador de carga | `ar-bgp-ecmp-lb`, sirviendo el dominio `ar-bgp-ecmp.bankexample.com` |
| Cliente de prueba | `ar-ecmp-client`, una VM dentro de la misma VNet |
| Grupo de recursos | `rg-mcn-ce-ha-rmordasiewicz` |

<Aside type="caution" title="La VIP debe quedar fuera de todos los CIDR de la VNet">
`terraform/main.tf` incluye un bloque `check` que afirma que la VIP está fuera de los CIDR
del hub y del spoke, y rechaza el plan en caso contrario. Su razón declarada es que una VIP
dentro de un CIDR de VNet pierde frente a la propia ruta de sistema de la VNet, a pesar de
que la ruta BGP sea más específica.

Trate esa protección como el contrato: si reorienta esta demostración a un
direccionamiento distinto, la VIP tiene que salir de los rangos de la VNet con él.
</Aside>

## Compruebe que está en buen estado antes de presentar

Cuatro comprobaciones, en este orden. Cada una acota dónde estaría un fallo, de modo que un
error le dice algo en lugar de solo indicar que algo va mal.

<Steps>

1. **Los tres sitios están `ONLINE`.** Nada de lo que sigue puede ser cierto si esto no lo es.

   ```bash
   for s in ar-bgp-eastus01 ar-bgp-eastus02 ar-bgp-eastus03; do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **Cada peering está aprendiendo el anuncio de la VIP de ese CE.** Consulte cada peering
   por separado — vea la trampa más abajo, porque es aquí donde la demostración parece
   rota con más frecuencia y no lo está.

   ```bash
   for p in eastus01-bgp eastus02-bgp eastus03-bgp; do
     echo "--- $p"
     az network routeserver peering list-learned-routes \
       --name "$p" --routeserver ce-ha-lab-rrs -g rg-mcn-ce-ha-rmordasiewicz \
       --query "RouteServiceRole_IN_0[].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp

   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp

   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   Tres peerings, tres saltos siguientes distintos, un prefijo. Eso demuestra el lado de
   los anuncios de ECMP.

3. **Las rutas efectivas del cliente incluyen los tres saltos siguientes.** Esto es el ECMP
   en sí, tal como lo ha programado la VNet: no lo que afirman los CE, sino lo que Azure
   hizo con ello.

   ```bash
   az network nic show-effective-route-table \
     --name ar-ecmp-clientVMNic -g rg-mcn-ce-ha-rmordasiewicz \
     --query "value[?addressPrefix[0]=='10.250.0.10/32']" -o json
   ```

   ```json
   [
     {
       "addressPrefix": ["10.250.0.10/32"],
       "nextHopIpAddress": ["10.0.1.5", "10.0.1.4", "10.0.1.6"],
       "nextHopType": "VirtualNetworkGateway",
       "source": "VirtualNetworkGateway",
       "state": "Active"
     }
   ]
   ```

   `state: Active` con tres entradas en `nextHopIpAddress` es la comprobación. Un solo
   salto siguiente donde espera tres significa que un CE ha dejado de anunciar, y el paso 2
   identifica cuál.

4. **La VIP sirve tráfico.** Desde la VM cliente, y **con la cabecera `Host`** — vea la
   segunda trampa más abajo.

   ```bash
   az vm run-command invoke -g rg-mcn-ce-ha-rmordasiewicz -n ar-ecmp-client \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts 'for i in $(seq 1 10); do
                  curl -s -o /dev/null -w "%{http_code} " \
                    -H "Host: ar-bgp-ecmp.bankexample.com" http://10.250.0.10/
                done'
   ```

   ```text
   200 200 200 200 200 200 200 200 200 200
   ```

</Steps>

## Trampa: un peering muestra una sola ruta, y eso es correcto

`list-learned-routes` está acotado al peering que usted nombra. Informa de lo que **ese**
par anunció, no de la tabla completa del Route Server.

Así que consultar `eastus01-bgp` por sí solo devuelve un único `10.250.0.10/32` vía
`10.0.1.4`, y resulta tentador leerlo como «solo un CE está anunciando: los otros dos están
caídos». Nada está caído. Los otros dos anuncios se ven en sus propios peerings, que es
justo lo que recorre el bucle del paso 2.

Confirmar ECMP a partir de la consulta de un único peering no es posible. O recorre los
tres peerings, o lee la tabla de rutas efectivas del cliente, que muestra el resultado
combinado en una sola llamada.

## Trampa: una petición a la IP desnuda devuelve 404

El balanceador de carga hace coincidir por `Host`. La VIP no es un servidor virtual que
sirva algo a quienquiera que se conecte a la dirección.

```text
curl -H 'Host: ar-bgp-ecmp.bankexample.com' http://10.250.0.10/   ->  200   (10 of 10)
curl                                        http://10.250.0.10/   ->  404
```

Ambos resultados se produjeron en la misma ejecución contra el despliegue en buen estado.
**Un 404 con la IP desnuda es la prueba de que el camino funciona**: la petición llegó al
CE, el proxy del CE respondió y la rechazó porque ningún dominio configurado coincidía.
Leerlo como una interrupción le hace mirar el BGP, donde no encontrará nada mal.

Lo mismo aplica durante una demostración: si escribe la dirección en un navegador en lugar
de resolver el dominio hacia ella, obtiene el 404.

## La aprobación del registro está automatizada, y el apply sigue siendo en dos fases

La aprobación del registro ya no necesita a una persona en la consola. En la versión
**v3.81.1** del proveedor, el recurso `xcsh_registration_approval` la realiza, y el módulo
del sitio resuelve qué registro aprobar.

Eso sigue sin convertir el despliegue en un único `apply` desatendido, y la razón merece
entenderse antes de que observe una primera ejecución y concluya que falló:

- El objeto de registro de un CE se llama **`r-<uuid>`**. Nunca lleva el nombre del sitio,
  así que nada puede predecir el nombre en tiempo de plan.
- El registro solo existe después de que la VM haya arrancado y `vpm` se haya registrado.
- Por tanto, el **primer apply no planifica ninguna aprobación**. Vuelva a aplicar una vez
  que los CE se hayan registrado y se hayan creado las aprobaciones.

`terraform/main.tf` documenta esta secuencia en la parte superior del archivo, que es la
versión autoritativa: la secuencia de despliegue vive junto al código que la implementa.

<Aside type="caution" title="Un sitio recién creado no es accesible de inmediato por la API de operación">
Durante aproximadamente 25 a 30 minutos después de que un sitio nuevo informe `ONLINE`, los
endpoints `vpm/debug` responden con una página `503` de BIG-IP que dice
`The requested URL was rejected`. Parece un bloqueo de firewall de aplicaciones web o un
token revocado, y no es ninguna de las dos cosas. Espere y reintente.

Esto afecta a una demostración recién construida, no a una en marcha.
</Aside>

## Acceso a la CLI del sitio

Los diagnósticos rutinarios en el equipo pasan por la API de depuración, que ya está
scriptada aquí. Confirme que la superficie de comandos sigue coincidiendo con lo que
describe la documentación:

```bash
bash scripts/capture-sitecli.sh --check --site ar-bgp-eastus01 --node f5-xc-ce-vm-01
```

```text
catalog matches the live CE (build crt-20250613-3382, 34 commands)
```

`--check` no escribe nada, así que es seguro contra la demostración en vivo.

Para los comandos que esa API no retransmite, este despliegue también dispone de **SSH de
operador a la cuenta `admin` del dispositivo**, cuyo shell de inicio de sesión es la CLI del
sitio. Está verificado en los tres CE. Conéctese a la dirección interna (SLI) desde un host
dentro de la VNet, con un terminal asignado:

```bash
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<vm-in-vnet> admin@10.0.3.5
```

```text
WELCOME IN SITE CLI
Registration Status: PROVISIONED
```

<Aside type="caution" title="Ese acceso existe porque estos CE se construyeron con él — no puede añadirse después">
La clave de operador la escribe `write_files` de cloud-init, que se ejecuta una sola vez en
el primer arranque. `custom_data` es solo de reemplazo, así que adoptar esto en CE que ya
están en ejecución reemplaza todas las VM de CE — y reemplazar una actualmente atasca el
registro mientras `terraform plan` informa «No changes»
([incidencia 674](https://github.com/f5-sales-demo/mcn/issues/674)). La recuperación
requirió dos reconstrucciones completas.

Para este despliegue el cambio ya está aplicado y la flota está en buen estado. Quien lo
adopte en otro lugar debería leer antes la
[página de SSH](../customer-edge/access/ssh/).
</Aside>

## Dos trampas más de medición

Ambas produjeron respuestas erróneas con total confianza en este entorno, y ninguna es
evidente.

- **Sondee desde dentro de la VNet, no desde su estación de trabajo.** Netskope completa
  por sí mismo el saludo TCP en puertos comunes, de modo que un sondeo desde la estación de
  trabajo informa de un puerto **abierto** que en realidad está cerrado. Los puertos 80 y
  443 aparecen como abiertos en las direcciones públicas de los CE desde una estación de
  trabajo y están cerrados cuando se sondean desde dentro de la VNet. Use `ar-ecmp-client`.
- **El puerto 22 de un CE responde solo en la dirección interna (SLI).** Sondeados desde
  `ar-ecmp-client` contra los tres CE, `10.0.3.5`, `10.0.3.6` y `10.0.3.7` devuelven todos
  `SSH-2.0-OpenSSH_8.7`, mientras que las direcciones de gestión y externa expiran, igual
  que una dirección sin usar empleada como control. eth0 se renombra como `a-i-eth0` y no
  lleva IP de host, porque la ruta de datos es su propietaria. Así que sondear la dirección
  por la que conoce el nodo no le dice nada sobre el estado de SSH del nodo, y la dirección
  SLI es a la que hay que conectarse.

<Aside type="note" title="Lo que esta página no afirma">
Dos cosas que un lector podría esperar razonablemente aquí están deliberadamente ausentes,
porque no se ejercitaron contra el despliegue:

- **La conmutación por error no se probó.** Se verifica que los tres saltos siguientes de
  igual coste están instalados; lo que le ocurre a la tabla de rutas cuando se detiene un CE
  no se muestra, así que no ensaye una demostración de conmutación por error a partir de
  esta página sin probarlo antes.
- **La distribución de tráfico no se midió.** Diez de diez peticiones a la VIP devolvieron
  `200`, lo que demuestra que el camino funciona. No muestra cómo se repartieron esas diez
  entre los tres saltos siguientes.

</Aside>
