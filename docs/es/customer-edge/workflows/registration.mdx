Capturado el 2026-07-28 desde un CE de esta implementación. `sitecli/capture-manifest.json`
registra qué nodo, y `scripts/capture-sitecli.sh --check` vuelve a verificar la superficie
de comandos contra un CE activo.

<Aside type="danger" title="La API no puede depurar esto">
La API de depuración llega al nodo a través del plano de control de F5 Distributed Cloud, por
el túnel que establece el registro. Si el registro falló no hay túnel,
así que todos los comandos de este sitio no están disponibles para este fallo concreto. Trabaje desde
[Site Console](../../access/site-console/) si el nodo todavía tiene una ruta de red, y desde
la [consola serie](../../access/serial-console/) si no la tiene.
</Aside>

<Steps>

1. **Confirme que está preguntando al inquilino correcto.** Esto cuesta un comando y es lo primero
   porque equivocarse hace que todos los pasos posteriores le mientan: una flota sana en el inquilino
   que no está mirando es indistinguible de una flota que nunca se registró.

   ```bash
   cd terraform
   terraform output -raw xc_tenant       # the tenant this deployment belongs to
   terraform output -raw xc_env_tenant   # the tenant your shell is exporting
   ```

   ```text
   f5-sales-demo
   f5-sales-demo
   ```

   ¿No coinciden, o una credencial que cree correcta devuelve un `401` sin más? Ese es el
   síntoma de un token emitido para otro inquilino, y ya le ha costado a esta implementación una
   reconstrucción completa ([issue 696](https://github.com/f5-sales-demo/mcn/issues/696)).

2. **Confirme qué piensa el inquilino.** Estar ausente de la lista de sitios es un problema
   distinto de estar presente pero no `ONLINE`.

   ```bash
   curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
     "$XCSH_API_URL/api/config/namespaces/system/sites" | jq -r '.items[].name'
   ```

   Si el sitio existe y reporta `ONLINE`, el registro tuvo éxito y usted está en el
   flujo de trabajo equivocado.

3. **Encuentre el registro del sitio y su estado.** Un nodo puede registrarse y luego esperar
   aprobación, lo que desde fuera parece idéntico a un fallo.

   ```bash
   curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
     "$XCSH_API_URL/api/register/namespaces/system/registrations_by_site/<site>" \
     | jq -r '.items[] | "\(.name)  \(.object.status.current_state)  \(.object.spec.gc_spec.infra.hostname)"'
   ```

   ```text
   r-a97e20c8-b7e1-483d-bd76-34a64ff8bc78  ONLINE  f5-xc-ce-vm-01
   ```

   Ningún elemento en absoluto significa que el nodo aún no se ha registrado — vaya a la consola serie. Un elemento
   en un estado distinto de `ONLINE` significa que se registró y algo posterior falló, lo cual
   es una investigación diferente.

   Para barrer todo el espacio de nombres en busca de cualquier cosa pendiente de aprobación, `listregistrationsbystate`
   toma el estado como un **cuerpo `POST`**:

   ```bash
   curl -sS -X POST -H "Authorization: APIToken $XCSH_API_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"namespace":"system","state":"PENDING"}' \
     "$XCSH_API_URL/api/register/namespaces/system/listregistrationsbystate" | jq -r '.items[].name'
   ```

   En una flota sana eso no devuelve nada, porque la aprobación está automatizada.

4. **Confirme que la VM está realmente en ejecución**, antes de asumir un fallo de software.

   ```bash
   az vm list -d -g <resource-group> --query "[].{name:name,power:powerState}" -o table
   ```

   ```text
   Name            Power
   --------------  ----------
   ar-ecmp-client  VM running
   f5-xc-ce-vm-01  VM running
   f5-xc-ce-vm-02  VM running
   f5-xc-ce-vm-03  VM running
   ```

5. **Conéctese a la consola serie.** De forma interactiva esto necesita un terminal real; la conexión
   en sí puede automatizarse por websocket — consulte
   la [consola serie](../../access/serial-console/).

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

   Si se niega, compruebe que el diagnóstico de arranque está habilitado en la VM antes de concluir que el
   nodo es inalcanzable; ese requisito previo y sus modos de fallo se cubren en la página de la
   [consola serie](../../access/serial-console/).

6. **Lea lo que muestra la consola, en este orden.** cloud-init primero — un nodo cuyo
   cloud-init nunca se completó no tiene configuración con la que registrarse. Luego los
   intentos de registro en sí, y después DNS: si el nodo no puede resolver
   `register.ves.volterra.io`, nada de lo posterior puede funcionar.

7. **Una vez que el nodo esté `ONLINE`**, verifique con [`health`](../../commands/system/health/)
   y espere `state: PROVISIONED`.

</Steps>

<Aside type="caution" title="Un registro se nombra por un UUID, nunca por su sitio">
Los registros se nombran `r-<uuid>`, y no existe ningún endpoint que acepte un nombre de sitio donde se
espera un nombre de registro.
`GET .../registrations/<site>` devuelve `404`, lo que se lee como «este sitio no tiene
registro» y en realidad significa «ese no es un nombre de registro». La correspondencia entre sitio y registro
solo proviene de `registrations_by_site/<site>`, como en el paso 3, o de listar
`registrations` y hacer coincidir con `gc_spec.passport.cluster_name`.

La misma trampa hizo parecer que una flota sana tuviera cero registros.
</Aside>

## Las causas habituales

- **Está apuntando al inquilino equivocado**, así que una flota que está bien parece ausente. Paso 1.
- cloud-init no se completó, así que `/etc/vpm/config.yaml` está ausente o es incorrecto.
- El token de registro está caducado, ya consumido, o es de otro inquilino.
- No hay ruta de salida hacia `register.ves.volterra.io`.
- Desfase de reloj lo bastante grande para invalidar certificados — rápido de descartar más adelante con
  [`chronyc-sources`](../../commands/network/chronyc-sources/), pero inalcanzable
  hasta que el nodo esté en línea. El banner de inicio de sesión de [SSH](../../access/ssh/) informa `NTP: Synced`
  y el estado del resolutor antes de que ejecute nada, cuando SSH está disponible.
