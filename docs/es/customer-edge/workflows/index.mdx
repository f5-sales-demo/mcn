La [referencia de comandos](../commands/) está organizada según lo que hace cada comando. Estos
están organizados según lo que ha fallado.

| Síntoma | Flujo de trabajo |
| --- | --- |
| El sitio nunca se puso en línea, o desapareció del tenant | [Registro](./registration/) |
| Las rutas no se anuncian ni se aprenden; el VIP es inalcanzable | [BGP](./bgp-diagnostics/) |
| El tráfico llega al nodo pero no arriba a destino | [Plano de datos](./dataplane-diagnostics/) |

Cada paso enlaza con la página que documenta el comando. Aquí no se repite nada,
de modo que la sintaxis tiene exactamente un único hogar y no puede desviarse de lo que hace el nodo.

## Antes de cualquiera de ellos

Determine en qué ruta de acceso se encuentra, porque cambia lo que es posible:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/config/namespaces/system/sites/<site>" | jq -r '.spec.site_state'
```

`ONLINE` significa que la [API de depuración](../access/debug-api/) responderá. Cualquier otro valor significa que
el flujo de trabajo de registro es el que necesita, junto con una de las rutas que no dependen del
registro: la [Consola del sitio](../access/site-console/) mientras el nodo aún tenga una ruta de red,
y la [consola serie](../access/serial-console/) cuando no la tenga.

Un sitio que **falta por completo** tiene una explicación más que descartar antes de «nunca
se registró»: que esté consultando el tenant equivocado. `cd terraform && terraform output -raw
xc_tenant` indica el nombre de aquel al que pertenece este despliegue.
