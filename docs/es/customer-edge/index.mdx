Un Customer Edge (CE) es el nodo de F5 Distributed Cloud que este repositorio
aprovisiona en Azure — `terraform/modules/ce-node`, construido a partir de la imagen
de marketplace `volterraedgeservices/volterra-node`.

Ejecuta el plano de datos (Argo), el plano de control (Vega), un proxy Envoy, una pila
de Kubernetes y `vpm`, el agente que registra el nodo y gestiona todo lo demás en
él.

Cuando un CE se comporta de forma incorrecta, el Site CLI es el instrumento. La
primera decisión es qué ruta de acceso corresponde, y equivocarse hace perder tiempo
de una manera que parece un nodo averiado.

## Dos rutas de acceso, y no son intercambiables

La API de depuración llega al nodo **a través del plano de control de F5 Distributed
Cloud**. Esa es toda la razón por la que la distinción importa: la API solo puede
responder una vez que el nodo se ha registrado e informa `ONLINE`.

Un nodo que no logró registrarse — un cloud-init defectuoso, un token caducado, sin
ruta hacia `register.ves.volterra.io` — es exactamente el caso en el que necesita
diagnósticos, y exactamente el caso que la API no puede atender.

SSH no es una tercera opción. `sshd` se ejecuta en el nodo y responde en su dirección
interna (SLI), pero la cuenta `admin` no puede autenticarse: `vpm` omite ese usuario,
por lo que la `ssh_key` que configura en el objeto de sitio nunca se aplica. Ninguna
regla del grupo de seguridad lo cambia. La evidencia está en la página
[SSH](./access/ssh/), que existe porque todos los síntomas allí se interpretan como un
fallo de firewall o de credenciales.

Así que: si el sitio está `ONLINE`, use la API de depuración. Si no lo está, la consola
serie es la única forma de entrar.

<Aside type="caution" title="Compruebe primero el estado del sitio">
Una sola solicitud le indica en qué ruta se encuentra:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/config/namespaces/system/sites/<site>" \
  | jq -r '.spec.site_state'
```

`ONLINE` significa que la API de depuración funcionará. Cualquier otra cosa — o un
sitio que no existe — significa consola serie.
</Aside>

## Reglas de seguridad

Estas se aplican a todos los comandos de todas las páginas siguientes.

- **Solo lectura a menos que esté seguro.** La superficie de comandos se divide en dos
  niveles de privilegio, y el nivel `Exec` o modifica el nodo o lee un marcador de
  estado. Nada en estas páginas ejecuta un comando `Exec`, ni tampoco lo hace el
  arnés de captura.
- **Nunca suponga que un comando es seguro por su nombre.** `ip-link-set` se lee como
  una consulta y desactiva una interfaz. `systemctl-restart-crio` reinicia el runtime
  de contenedores bajo un plano de datos en vivo.
- **Prefiera el comando más específico que responda a la pregunta.** `health` y
  `diagnosis` resumen el nodo de forma económica; `flow-l` vuelca una tabla de flujos
  de 629.760 entradas.
- **Un CE sirve tráfico en vivo.** Estos son entornos de demostración compartidos.
  Suponga que alguien está presentando desde el sitio que está depurando.

## Qué se documenta aquí

Todos los comandos accesibles a través de la API de depuración en la compilación de
software que ejecuta este tenant, cada uno con la salida capturada de un nodo en vivo
en lugar de transcrita de otro lugar.

La [referencia de comandos](./commands/) los enumera todos con su categoría, nivel de
privilegio y transporte; los [flujos de trabajo](./workflows/) los encadenan en las
secuencias que realmente utiliza cuando algo va mal.

Las partes del Site CLI disponibles solo en el equipo — `configure`,
`configure-network`, `factory-reset`, `upgrade` y aproximadamente sesenta comandos
`ExecCLI` adicionales — no están cubiertas.

Solo son accesibles desde una sesión de consola serie, por lo que nada sobre ellas
puede verificarse de forma programática, y la sintaxis de comandos no verificada es
precisamente el defecto que esta documentación existe para evitar repetir.
