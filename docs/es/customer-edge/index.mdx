Un Customer Edge (CE) es el nodo de F5 Distributed Cloud que este repositorio aprovisiona en
Azure — `terraform/modules/ce-node`, construido a partir de la
imagen de marketplace `volterraedgeservices/volterra-node`.

Ejecuta el plano de datos (Argo), el plano de control (Vega), un proxy Envoy, una
pila de Kubernetes y `vpm`, el agente que registra el nodo y gestiona todo lo demás
en él.

Cuando un CE presenta problemas, el Site CLI es el instrumento. La primera decisión es cuál
ruta de acceso aplica, y equivocarse en eso desperdicia tiempo de una manera que parece un
nodo roto.

## Dos rutas de acceso, y no son intercambiables

  <LinkCard

La debug API alcanza el nodo **a través del plano de control de F5 Distributed Cloud**.
Esa es la razón completa por la que la división importa: la API solo puede responder una vez que el nodo se ha
registrado y reporta `ONLINE`.

Un nodo que no logró registrarse — cloud-init defectuoso, un token vencido, sin ruta hacia
`register.ves.volterra.io` — es exactamente el caso donde se necesitan diagnósticos, y
exactamente el caso que la API no puede atender.

El nodo también rechaza SSH tal como se entrega. El puerto 22 está cerrado en el CE mismo, no por un
grupo de seguridad de red:

```console
$ ssh -o ConnectTimeout=10 admin@<ce-public-ip>
ssh: connect to host <ce-public-ip> port 22: Connection refused
```

Verificado también desde dentro de la VNet, desde un jump host en la misma subred, por lo que
abrir una regla de grupo de seguridad no lo cambia.

Entonces: si el sitio está `ONLINE`, utilice la debug API. Si no lo está, la consola serial es la
única forma de acceder.

<Aside type="caution" title="Verifique el estado del sitio primero">
Una solicitud le indica en qué ruta se encuentra:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/config/namespaces/system/sites/<site>" \
  | jq -r '.spec.site_state'
```

`ONLINE` significa que la debug API funcionará. Cualquier otra cosa — o un sitio que no
existe — significa consola serial.
</Aside>

## Reglas de seguridad

Estas aplican para cada comando en cada página a continuación.

- **Solo lectura a menos que esté seguro.** La superficie de comandos está dividida en dos
  niveles de privilegio, y el nivel `Exec` ya sea muta el nodo o lee un marcador de estado.
  Ninguna de estas páginas ejecuta un comando `Exec`, y tampoco lo hace el arnés de captura.
- **Nunca asuma que un comando es seguro por su nombre.** `ip-link-set` parece una
  consulta y deja una interfaz inactiva. `systemctl-restart-crio` reinicia el
  runtime de contenedores bajo un plano de datos activo.
- **Prefiera el comando más acotado que responda la pregunta.** `health` y
  `diagnosis` resumen el nodo con bajo costo; `flow-l` vuelca una tabla de flujos de 629,760 entradas.
- **Un CE sirve tráfico en producción.** Estos son entornos de demostración compartidos. Asuma que alguien
  está realizando una presentación desde el sitio que está depurando.

## Qué está documentado aquí

Cada comando alcanzable a través de la debug API en la versión de software que ejecuta este tenant,
cada uno con salida capturada de un nodo activo en lugar de transcrita desde otro lugar.

La [referencia de comandos](./commands/) los lista a todos con su categoría, nivel de privilegio
y transporte; los [flujos de trabajo](./workflows/) los encadenan en las secuencias que
realmente se usan cuando algo falla.

Las partes del Site CLI que solo existen en el nodo — `configure`, `configure-network`,
`factory-reset`, `upgrade` y aproximadamente sesenta comandos `ExecCLI` adicionales — no están
cubiertas.

Son accesibles únicamente desde una sesión de consola serial, por lo que nada sobre ellos puede
verificarse de manera programática, y la sintaxis de comandos no verificada es el defecto que esta
documentación existe para evitar repetir.
