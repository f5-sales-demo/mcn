Azure Serial Console se conecta al puerto serie emulado del nodo a través de la
plataforma de Azure. No atraviesa el plano de control de F5 Distributed Cloud, el plano
de datos del nodo ni ninguna ruta de red que el nodo controle — que es exactamente el
motivo por el que funciona cuando nada más lo hace.

Recurra a ella cuando un CE **nunca llegó a arrancar**: el registro falló, el sitio no
aparece en el tenant, o el nodo está activo pero no tiene ruta de salida. En todos esos
casos, la [API de depuración](../debug-api/) no tiene túnel por el que retransmitir.
[SSH](../ssh/) sobrevive a un registro fallido, pero solo si su clave ya se escribió en
el primer arranque y puede alcanzar la dirección interna del nodo desde dentro de la
VNet — y ninguna de esas dos cosas se cumple en un nodo con el que se encuentra por
primera vez.

Pruebe la [Consola del sitio](../site-console/) antes que esta si el nodo tiene *alguna*
ruta de red funcional: también sobrevive a un registro fallido, no necesita clave y no
expulsa a quien ya esté examinando el nodo. La consola serie es lo que queda cuando la
ruta de red es precisamente lo que está roto.

## Requisito previo: diagnóstico de arranque

Azure exige el diagnóstico de arranque en la VM antes de permitir la conexión de una
consola serie. Esto lo habilita `terraform/modules/ce-node`:

```hcl
boot_diagnostics {}
```

Un bloque vacío selecciona almacenamiento gestionado por Azure, de modo que no hay
cuenta de almacenamiento de diagnóstico, política de ciclo de vida ni clave de acceso
que gestionar. Confírmelo en un nodo:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="Habilitarlo no es retroactivo">
El diagnóstico de arranque captura el registro serie **en el arranque**. Activarlo en una
VM que ya está en ejecución no genera un registro del arranque que ya ocurrió, por lo que
`az vm boot-diagnostics get-boot-log` responde:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

Eso es lo esperado, no un fallo. El registro de arranque existirá después del siguiente
reinicio del nodo. La conexión en vivo a la consola, en cambio, funciona de inmediato —
no depende del registro.
</Aside>

## Comprobar la disponibilidad sin un terminal

Conectarse requiere una sesión interactiva, pero saber si *se podría* conectar son dos
llamadas a la API. Ambas son útiles en una comprobación de estado.

El servicio debe estar habilitado para la suscripción — un administrador puede
deshabilitarlo para todo el tenant:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

Después, solicite una conexión al puerto serie de un nodo concreto:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

Un `connectionString` que empieza por `wss://` — en este despliegue,
`eastus.gateway.serialconsole.azure.com` — significa que la consola es conectable ahora
mismo. Antes de habilitar el diagnóstico de arranque, esta llamada no tenía nada a lo que
conectarse.

<Aside type="danger" title="Esa cadena de conexión es una credencial">
Es un token bearer de vida corta incrustado en una URL. No lo registre, no lo pegue en un
ticket ni lo suba a un repositorio. Muestre únicamente el host cuando esté demostrando que
la llamada funcionó.
</Aside>

## Conexión

<Steps>

1. Instale la extensión una sola vez:

   ```bash
   az extension add --name serial-console
   ```

2. Conéctese:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. Aterriza en el propio indicador de inicio de sesión del nodo, no en un shell, detrás
   del banner de auditoría del dispositivo. La consola serie demuestra que el *canal*
   funciona; no elude la autenticación.

   <Aside type="caution" title="No se ha verificado qué credencial acepta el inicio de sesión serie">
   Nadie ha completado un inicio de sesión por consola serie en este despliegue, así que
   esta página no indica qué escribir. `admin` es la cuenta del dispositivo cuyo shell es
   la CLI del sitio, y esa misma cuenta se autentica mediante
   [Consola del sitio](../site-console/) con una contraseña — pero no se ha demostrado que
   una contraseña funcione en el inicio de sesión de la consola serie, y `sshd` solo acepta
   claves para `admin`, por lo que ambas rutas de credencial son demostrablemente distintas.
   </Aside>

</Steps>

Capturado de `f5-xc-ce-vm-01`, con elisiones en el medio donde la salida de las unidades
de systemd no aporta nada:

```text file=../../../_data/serial-console-boot.txt
```

Hay cuatro cosas en esa transcripción que merece la pena observar, porque responden a
preguntas que la API de depuración no puede responder:

- **cloud-init completado** — `Datasource DataSourceAzure`, finalizado a los 22,37
  segundos. Un nodo que nunca se registra suele haber fallado aquí, y aquí es donde se ve.
- **Ambos runtimes de contenedores arrancaron.** `Container Runtime Interface for OCI (CRI-O)`
  y `Docker Application Container Engine` están cada uno en `[ OK ]`, lo cual es la prueba
  en tiempo de arranque del comportamiento de doble runtime que sorprende a la gente en
  [crictl](../../commands/system/crictl/) y [docker](../../commands/system/docker/).
- **`VP Manager image load` y `Argo Watch service`** — `vpm` y Argo arrancando.
- **El indicador es el propio del nodo**, detrás de su banner de auditoría. La consola
  serie le da un indicador de inicio de sesión, no una sesión.

<Aside type="caution" title="La conexión interactiva necesita un terminal real — pero se puede automatizar">
`az serial-console connect` pone el terminal en modo raw, por lo que no puede ejecutarse
desde una pipeline ni desde ningún contexto sin TTY. Falla en el lado del cliente, antes
de contactar con Azure:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

Ese traceback es manejo del terminal, no una caída de la consola serie.

La conexión en sí, en cambio, **sí** es automatizable — controle el websocket
directamente en lugar de usar la CLI. La transcripción anterior se capturó así, sin TTY.
Consulte `scripts/serial_console_capture.py`, que es la forma en que recopilaría evidencia
de arranque de un nodo que no consiguió registrarse sin que una persona esté sentada ante
un terminal.
</Aside>

<Aside type="caution" title="Prepárese para reintentar: el gateway rechaza aproximadamente uno de cada dos intentos">
El primer frame del gateway es un desafío, no salida, y el cliente lo responde con un
token bearer. Incluso cuando eso se hace correctamente, el socket a menudo se cierra de
inmediato:

```
[close] code=1011 reason=Connection not trusted
```

Comportamiento observado: funciona de forma intermitente y, con un uso sostenido, todos
los nodos del grupo de recursos rechazan la conexión — incluidos nodos que funcionaban
minutos antes. `scripts/serial_console_capture.py` reintenta por defecto porque reintentar
suele funcionar.

**La causa no está establecida.** Lo que se ha descartado, porque cada una es una
suposición plausible que hace perder tiempo:

| No es esto | Cómo confirmarlo |
| --- | --- |
| Throttling de ARM/compute | Eso devuelve HTTP `429` en las llamadas a ARM. Esto es un cierre de websocket en un canal de datos separado. |
| Interceptación TLS por un proxy | `openssl s_client -connect <region>.gateway.serialconsole.azure.com:443 \| openssl x509 -noout -issuer`. Un emisor genuino `O=Microsoft Corporation` lo descarta; un proveedor de proxy como emisor lo confirma, y la solución es permitir `*.serialconsole.azure.com` en la lista blanca. |
| Diagnóstico de arranque deshabilitado | `az vm show -g <rg> -n <vm> --query diagnosticsProfile` informando `enabled: true`. |
| Desajuste de token entre la concesión y el desafío | Usar un mismo token para ambos es la práctica correcta, pero no evita el cierre. |

Lo que *sí* es comportamiento documentado de Azure: **una sesión de consola serie por VM,
y una segunda solicitud satisfactoria expulsa a la primera.** El usuario expulsado se
desconecta pero no cierra sesión, por lo que la sesión del shell sobrevive. Dos personas
depurando un mismo nodo se desplazarán mutuamente de forma repetida.

Para trabajo masivo prefiera la [API de depuración](../debug-api/) o [SSH](../ssh/),
ninguno de los cuales tiene estos límites. SSH en particular no tiene límite de pegado ni
restricción de sesión única, por lo que es la mejor opción siempre que el nodo sea
alcanzable desde dentro de la VNet.
</Aside>

<Aside type="caution" title="El pegado está limitado a 2.048 caracteres">
Azure limita la longitud del pegado en la consola serie a 2.048 caracteres, para evitar
sobrecargar el puerto serie. Enviar un comando largo — o un lote de comandos en una sola
escritura — falla de una forma que se interpreta como un bloqueo o un throttling en lugar
de como un límite de longitud.

Envíe los comandos de uno en uno. Es una restricción real para cualquier recopilación
masiva por consola serie, y otra razón para preferir la
[API de depuración](../debug-api/) para ese trabajo.
</Aside>

## Qué puede ver aquí que la API no le puede mostrar

- **cloud-init** ejecutándose, fallando o sin arrancar nunca — la causa habitual de un
  nodo que nunca se registra.
- **Intentos de registro** contra `register.ves.volterra.io`, incluido un error de
  configuración o un token rechazado por el tenant.
- **Mensajes del kernel y del arranque** de antes de que ningún agente estuviera en
  ejecución.
- El nodo cuando **no tiene ninguna ruta de red funcional**, lo cual inutiliza cualquier
  otra vía.

Para un nodo que *sí* está `ONLINE`, prefiera la API de depuración: es automatizable,
produce evidencia que puede volver a generar y no ocupa el único puerto serie.
