La consola serie de Azure se conecta al puerto serie emulado del nodo a través de la
Plataforma de Azure. No atraviesa el plano de control de F5 Distributed Cloud, el plano de
datos del nodo ni ninguna ruta de red que el nodo controle — que es exactamente la razón por
la que funciona cuando nada más lo hace.

Úsela cuando un CE **nunca se haya iniciado**: el registro falló, el sitio no está presente
en el tenant, o el nodo está activo pero no tiene ruta de salida. En todos esos casos, la
[API de depuración](../debug-api/) no tiene túnel por el que retransmitir, y SSH está cerrado
en el nodo tal como se entrega.

## Requisito previo: diagnósticos de arranque

Azure requiere diagnósticos de arranque en la VM antes de conectar una consola serie.
Esto se habilita mediante `terraform/modules/ce-node`:

```hcl
boot_diagnostics {}
```

Un bloque vacío selecciona el almacenamiento administrado por Azure, por lo que no hay
cuenta de almacenamiento de diagnósticos, política de ciclo de vida ni clave de acceso que
gestionar. Confírmelo en un nodo:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="Habilitarlo no es retroactivo">
Los diagnósticos de arranque capturan el registro serie **en el arranque**. Activarlos para
una VM que ya está en ejecución no produce un registro del arranque que ya ocurrió, por lo
que `az vm boot-diagnostics get-boot-log` responde:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

Esto es esperado, no un fallo. Un registro de arranque existe después del próximo reinicio
del nodo. La conexión a la consola en vivo, sin embargo, funciona de inmediato — no depende
del registro.
</Aside>

## Verificar la disponibilidad sin una terminal

Conectarse requiere una sesión interactiva, pero si *podría* conectarse son dos llamadas a la
API. Ambas son útiles en una verificación de estado.

El servicio debe estar habilitado para la suscripción — un administrador puede deshabilitarlo
a nivel de todo el tenant:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

Luego solicite una conexión al puerto serie de un nodo específico:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

Un `connectionString` que comience con `wss://` — en este despliegue
`eastus.gateway.serialconsole.azure.com` — significa que la consola puede conectarse ahora
mismo. Antes de que se habilitaran los diagnósticos de arranque, esta llamada no tenía nada
a lo que conectarse.

<Aside type="danger" title="Esa cadena de conexión es una credencial">
Es un token portador de corta duración integrado en una URL. No lo registre, no lo pegue en
un ticket ni lo confirme en un repositorio. Imprima solo el host cuando esté demostrando que
la llamada funcionó.
</Aside>

## Conexión

<Steps>

1. Instale la extensión una vez:

   ```bash
   az extension add --name serial-console
   ```

2. Conéctese:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. Llegará al prompt de inicio de sesión propio del nodo, no a un shell. Esta es la CLI del
   sitio y requiere credenciales configuradas en el nodo — la contraseña de administrador del
   aprovisionamiento o una establecida a través del endpoint de cambio de contraseña. La
   consola serie demuestra que el *canal* funciona; no omite la autenticación.

</Steps>

Capturado de `f5-xc-ce-vm-01`, omitido en el medio donde la salida de la unidad systemd
no agrega nada:

```text file=../../../_data/serial-console-boot.txt
```

Cuatro aspectos en esa transcripción merecen atención, porque responden preguntas que la
API de depuración no puede responder:

- **cloud-init completado** — `Datasource DataSourceAzure`, finalizado a los 22,37 segundos.
  Un nodo que nunca se registra generalmente falló aquí, y aquí es donde se puede ver.
- **Ambos runtimes de contenedores iniciados.** `Container Runtime Interface for OCI (CRI-O)`
  y `Docker Application Container Engine` tienen cada uno `[ OK ]`, que es la prueba en
  tiempo de arranque del comportamiento de doble runtime que sorprende a las personas en
  [crictl](../../commands/system/crictl/) y [docker](../../commands/system/docker/).
- **`VP Manager image load` y `Argo Watch service`** — `vpm` y Argo iniciándose.
- **El prompt es el propio del nodo**, detrás de su banner de auditoría. La consola serie
  proporciona un prompt de inicio de sesión, no una sesión.

<Aside type="caution" title="La conexión interactiva requiere una terminal real — pero puede ser automatizada">
`az serial-console connect` pone la terminal en modo raw, por lo que no puede ejecutarse
desde una tubería ni en ningún contexto sin TTY. Falla del lado del cliente, antes de
contactar a Azure:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

Ese traceback es gestión de terminal, no una interrupción de la consola serie.

La conexión en sí, sin embargo, **sí** es automatizable — accione el websocket directamente
en lugar de usar la CLI. La transcripción anterior fue capturada de esa manera, sin TTY.
Consulte `scripts/serial_console_capture.py`, que es cómo recopilaría evidencia de arranque
de un nodo que no se registró sin que haya una persona en la terminal.
</Aside>

<Aside type="caution" title="Espere reintentos: la puerta de enlace rechaza aproximadamente cada dos intentos">
El primer frame de la puerta de enlace es un desafío, no una salida, y el cliente lo responde
con un token portador. Incluso cuando eso se hace correctamente, el socket a menudo se cierra
de inmediato:

```
[close] code=1011 reason=Connection not trusted
```

Medido en intentos repetidos en tres nodos, esto alterna: un rechazo es seguido de un éxito
en el mismo nodo. Eso es consistente con una sesión anterior que todavía se está reteniendo,
y el intento rechazado la libera.

**No es un problema de credenciales**, a pesar del mensaje. Reintentar normalmente es
suficiente, razón por la que `scripts/serial_console_capture.py` reintenta por defecto.

Use un único token tanto para la solicitud de sesión como para el desafío de todos modos,
siguiendo la extensión `az`. Esa es la práctica correcta, pero no es lo que causa esto.
</Aside>

## Lo que puede ver aquí que la API no puede mostrarle

- **cloud-init** ejecutándose, fallando o sin iniciarse nunca — la causa habitual de un
  nodo que nunca se registra.
- **Intentos de registro** contra `register.ves.volterra.io`, incluido un error de
  configuración o un token que el tenant rechazó.
- **Mensajes del kernel y de arranque** de antes de que se ejecutara cualquier agente.
- El nodo cuando **no tiene ninguna ruta de red funcional**, lo que invalida cualquier
  otra ruta.

Para un nodo que *está* `ONLINE`, prefiera la API de depuración: es automatizable, produce
evidencia que puede volver a ejecutar y no ocupa el único puerto serie.
