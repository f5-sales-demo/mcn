La consola serial de Azure se conecta al puerto serial emulado del nodo a través de la
plataforma de Azure. No atraviesa el plano de control de F5 Distributed Cloud, el plano
de datos del nodo, ni ninguna ruta de red que el nodo controle — que es exactamente por
qué funciona cuando nada más lo hace.

Recurra a ella cuando un CE **nunca se levantó**: el registro falló, el sitio está
ausente del tenant, o el nodo está activo pero no tiene ruta de salida. En todos esos
casos, la [API de depuración](../debug-api/) no tiene ningún túnel por el que retransmitir.
[SSH](../ssh/) sobrevive a un registro fallido, pero solo si su clave ya fue escrita en
el primer arranque y puede alcanzar la dirección interna del nodo desde dentro de la
VNet — ninguna de las cuales es verdad para un nodo que está conociendo por primera vez.

## Prerequisito: diagnósticos de arranque

Azure requiere diagnósticos de arranque en la VM antes de poder conectar una consola
serial. Esto se habilita mediante `terraform/modules/ce-node`:

```hcl
boot_diagnostics {}
```

Un bloque vacío selecciona el almacenamiento gestionado por Azure, por lo que no hay
cuenta de almacenamiento de diagnósticos, política de ciclo de vida ni clave de acceso
que administrar. Confírmelo en un nodo:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="Habilitarlo no es retroactivo">
Los diagnósticos de arranque capturan el registro serial **en el arranque**. Activarlos
para una VM que ya está en ejecución no produce un registro para el arranque que ya
ocurrió, por lo que `az vm boot-diagnostics get-boot-log` responde:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

Eso es lo esperado, no una falla. Un registro de arranque existe después de que el nodo
se reinicie. Sin embargo, la conexión de consola en vivo funciona inmediatamente — no
depende del registro.
</Aside>

## Verificar la disponibilidad sin una terminal

La conexión requiere una sesión interactiva, pero si *podría* conectarse son dos
llamadas a la API. Ambas son útiles en una verificación de estado.

El servicio debe estar habilitado para la suscripción — un administrador puede
desactivarlo a nivel de todo el tenant:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

Luego solicite una conexión al puerto serial de un nodo específico:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

Un `connectionString` que comienza con `wss://` — en este despliegue
`eastus.gateway.serialconsole.azure.com` — significa que la consola es conectable en
este momento. Antes de que se habilitaran los diagnósticos de arranque, esta llamada no
tenía nada a lo que conectarse.

<Aside type="danger" title="Esa cadena de conexión es una credencial">
Es un token de portador de corta duración incrustado en una URL. No lo registre, no lo
pegue en un ticket ni lo confirme en un repositorio. Imprima solo el host cuando esté
demostrando que la llamada funcionó.
</Aside>

## Conexión

<Steps>

1. Instale la extensión una vez:

   ```bash
   az extension add --name serial-console
   ```

2. Conéctese:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. Llegará al prompt de inicio de sesión propio del nodo, no a un shell. Esta es la
   CLI del sitio y necesita credenciales configuradas en el nodo — la contraseña de
   administrador del aprovisionamiento, o una establecida a través del endpoint de
   cambio de contraseña. La consola serial demuestra que el *canal* funciona; no
   omite la autenticación.

</Steps>

Capturado de `f5-xc-ce-vm-01`, omitido en el medio donde la salida de la unidad systemd
no aporta nada:

```text file=../../../_data/serial-console-boot.txt
```

Cuatro cosas en esa transcripción merecen atención, porque responden preguntas que la
API de depuración no puede:

- **cloud-init completó** — `Datasource DataSourceAzure`, finalizado a los 22,37
  segundos. Un nodo que nunca se registra generalmente falló aquí, y aquí es donde se
  puede ver.
- **Ambos runtimes de contenedores arrancaron.** `Container Runtime Interface for OCI (CRI-O)`
  y `Docker Application Container Engine` están cada uno en `[ OK ]`, lo que es la
  prueba en el arranque del comportamiento de doble runtime que sorprende a las personas
  en [crictl](../../commands/system/crictl/) y [docker](../../commands/system/docker/).
- **`VP Manager image load` y `Argo Watch service`** — `vpm` y Argo arrancando.
- **El prompt es el propio del nodo**, detrás de su banner de auditoría. La consola
  serial le da un prompt de inicio de sesión, no una sesión.

<Aside type="caution" title="La conexión interactiva necesita una terminal real — pero puede ser automatizada">
`az serial-console connect` pone la terminal en modo raw, por lo que no puede ejecutarse
desde un pipeline ni en ningún contexto sin TTY. Falla en el lado del cliente, antes de
contactar con Azure:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

Ese traceback es manejo de la terminal, no una interrupción de la consola serial.

Sin embargo, la conexión en sí **sí** es automatizable — maneje el websocket
directamente en lugar de la CLI. La transcripción anterior fue capturada de esa forma,
sin TTY. Consulte `scripts/serial_console_capture.py`, que es la manera de recopilar
evidencia de arranque de un nodo que no se registró sin que haya una persona sentada
frente a una terminal.
</Aside>

<Aside type="caution" title="Espere reintentos: la pasarela rechaza aproximadamente uno de cada dos intentos">
El primer frame de la pasarela es un desafío, no una salida, y el cliente lo responde
con un token de portador. Incluso cuando esto se hace correctamente, el socket se cierra
frecuentemente de inmediato:

```
[close] code=1011 reason=Connection not trusted
```

Comportamiento observado: tiene éxito de forma intermitente, y bajo uso sostenido todos
los nodos del grupo de recursos rechazan la conexión — incluidos los nodos que
funcionaron minutos antes. `scripts/serial_console_capture.py` reintenta por defecto
porque reintentar suele funcionar.

**La causa no está establecida.** Lo que se ha descartado, porque cada uno es una
suposición plausible que hace perder tiempo:

| No es esto | Cómo confirmarlo |
| --- | --- |
| Limitación de ARM/compute | Eso devuelve HTTP `429` en las llamadas ARM. Esto es un cierre de websocket en un canal de datos separado. |
| Interceptación TLS por un proxy | `openssl s_client -connect <region>.gateway.serialconsole.azure.com:443 \| openssl x509 -noout -issuer`. Un emisor genuino `O=Microsoft Corporation` lo descarta; un proveedor de proxy como emisor lo confirma, y la solución es incluir en la lista de permitidos `*.serialconsole.azure.com`. |
| Diagnósticos de arranque deshabilitados | `az vm show -g <rg> -n <vm> --query diagnosticsProfile` informando `enabled: true`. |
| Incompatibilidad de token entre la concesión y el desafío | Usar un mismo token para ambos es la práctica correcta, pero no evita el cierre. |

Lo que *sí* es comportamiento documentado de Azure: **una sesión de consola serial por
VM, y una segunda solicitud exitosa desaloja a la primera.** El usuario desalojado es
desconectado pero no cerrado su sesión, por lo que la sesión del shell sobrevive. Dos
personas depurando un nodo se desplazarán mutuamente de forma repetida.

Para trabajo masivo, prefiera la [API de depuración](../debug-api/) o [SSH](../ssh/),
ninguna de las cuales tiene estas limitaciones. SSH en particular no tiene límite de
pegado ni restricción de sesión única, por lo que es la mejor opción siempre que el
nodo sea accesible desde dentro de la VNet.
</Aside>

<Aside type="caution" title="El pegado está limitado a 2.048 caracteres">
Azure limita la longitud del pegado en la consola serial a 2.048 caracteres, para evitar
sobrecargar el puerto serial. Enviar un comando largo — o un lote de comandos en una
sola escritura — falla de una manera que parece un bloqueo o una limitación en lugar de
un límite de longitud.

Envíe los comandos individualmente. Esta es una limitación real en cualquier recopilación
masiva a través de la consola serial, y otra razón para preferir la
[API de depuración](../debug-api/) para ese trabajo.
</Aside>

## Lo que puede ver aquí que la API no puede mostrarle

- **cloud-init** ejecutándose, fallando o nunca iniciando — la causa habitual de un
  nodo que nunca se registra.
- **Intentos de registro** contra `register.ves.volterra.io`, incluido un error de
  configuración o un token que el tenant rechazó.
- **Mensajes del kernel y del arranque** de antes de que cualquier agente estuviera
  en ejecución.
- El nodo cuando **no tiene ninguna ruta de red funcional**, lo que anula todas las
  demás rutas.

Para un nodo que *está* `ONLINE`, prefiera la API de depuración: es automatizable,
produce evidencia que puede volver a ejecutar, y no ocupa el único puerto serial.
