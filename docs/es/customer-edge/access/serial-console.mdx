La consola serie de Azure se conecta al puerto serie emulado del nodo a través de la
Plataforma de Azure. No atraviesa el plano de control de F5 Distributed Cloud, el plano
de datos del nodo, ni ninguna ruta de red que el nodo controle — que es exactamente por
qué funciona cuando nada más lo hace.

Recurra a ella cuando un CE **nunca llegó a iniciarse**: el registro falló, el sitio
está ausente del tenant, o el nodo está activo pero no tiene ruta de salida. En todos
esos casos, la [API de depuración](../debug-api/) no tiene túnel por el que retransmitir,
y SSH está cerrado en el nodo tal como se entrega.

## Requisito previo: diagnósticos de arranque

Azure requiere que los diagnósticos de arranque estén habilitados en la VM antes de
adjuntar una consola serie. Esto lo habilita `terraform/modules/ce-node`:

```hcl
boot_diagnostics {}
```

Un bloque vacío selecciona almacenamiento administrado por Azure, por lo que no hay
cuenta de almacenamiento de diagnósticos, política de ciclo de vida ni clave de acceso
que gestionar. Confírmelo en un nodo:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="Habilitarlo no tiene efecto retroactivo">
Los diagnósticos de arranque capturan el registro serie **en el arranque**. Activarlos
para una VM que ya está en ejecución no produce un registro del arranque que ya ocurrió,
por lo que `az vm boot-diagnostics get-boot-log` responde:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

Esto es esperado, no un fallo. Un registro de arranque existirá después del próximo
reinicio del nodo. Sin embargo, la conexión en vivo a la consola funciona de inmediato
— no depende del registro.
</Aside>

## Verificar la disponibilidad sin una terminal

La conexión requiere una sesión interactiva, pero si *se conectaría* son dos llamadas
a la API. Ambas son útiles en una verificación de salud.

El servicio debe estar habilitado para la suscripción — un administrador puede
deshabilitarlo para todo el tenant:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

Luego solicite una conexión al puerto serie de un nodo específico:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

Un `connectionString` que comience con `wss://` — en este despliegue
`eastus.gateway.serialconsole.azure.com` — significa que la consola es conectable
ahora mismo. Antes de que se habilitaran los diagnósticos de arranque, esta llamada
no tenía nada a lo que conectarse.

<Aside type="danger" title="Esa cadena de conexión es una credencial">
Es un token bearer de corta duración incrustado en una URL. No lo registre, no lo
pegue en un ticket ni lo confirme en un repositorio. Imprima solo el host cuando
esté demostrando que la llamada funcionó.
</Aside>

## Conexión

<Steps>

1. Instale la extensión una vez:

   ```bash
   az extension add --name serial-console
   ```

2. Conéctese:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. Llegará al prompt de inicio de sesión propio del nodo, no a un shell. Esta es la
   CLI del sitio y requiere credenciales configuradas en el nodo — la contraseña de
   administrador del aprovisionamiento, o una establecida a través del endpoint de
   cambio de contraseña. La consola serie demuestra que el *canal* funciona; no
   omite la autenticación.

</Steps>

<Aside type="caution" title="Requiere una terminal real">
`az serial-console connect` pone la terminal en modo raw, por lo que no puede
ejecutarse desde un script, una tubería ni ningún contexto sin TTY. Falla en el
lado del cliente antes de contactar con Azure:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

Ese seguimiento de pila corresponde al manejo de la terminal, no a una interrupción
de la consola serie — las dos llamadas a la API anteriores seguirán informando que
la consola está disponible. Si necesita una señal automatizable, utilícelas en lugar
de intentar escribir un script para la conexión.
</Aside>

## Lo que puede ver aquí que la API no puede mostrarle

- **cloud-init** ejecutándose, fallando o sin iniciarse nunca — la causa habitual de
  un nodo que nunca se registra.
- **Intentos de registro** contra `register.ves.volterra.io`, incluyendo un error de
  configuración o un token que el tenant rechazó.
- **Mensajes del kernel y del arranque** desde antes de que cualquier agente estuviera
  en ejecución.
- El nodo cuando **no tiene ninguna ruta de red operativa**, lo que bloquea todas las
  demás rutas.

Para un nodo que *está* `ONLINE`, prefiera la API de depuración: es ejecutable mediante
scripts, produce evidencia que puede volver a ejecutar y no ocupa el puerto serie único.
