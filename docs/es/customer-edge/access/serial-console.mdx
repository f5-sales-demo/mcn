Azure Serial Console se conecta al puerto serie emulado del nodo a través de la
plataforma de Azure. No atraviesa el plano de control de F5 Distributed Cloud, el
plano de datos del nodo ni ninguna ruta de red que el nodo controle — que es
exactamente por lo que funciona cuando nada más lo hace.

Recurra a ella cuando un CE **nunca llegó a arrancar**: el registro falló, el sitio no
aparece en el tenant, o el nodo está activo pero no tiene ruta de salida. En todos esos
casos, la [API de depuración](../debug-api/) no tiene ningún túnel por el que retransmitir, y
[SSH no puede autenticar](../ssh/) en esta compilación.

## Requisito previo: diagnóstico de arranque

Azure exige el diagnóstico de arranque en la VM antes de conectar una consola serie.
Esto se habilita mediante `terraform/modules/ce-node`:

```hcl
boot_diagnostics {}
```

Un bloque vacío selecciona el almacenamiento gestionado por Azure, por lo que no hay
cuenta de almacenamiento de diagnóstico, política de ciclo de vida ni clave de acceso
que administrar. Confírmelo en un nodo:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="Habilitarlo no es retroactivo">
El diagnóstico de arranque captura el registro serie **en el arranque**. Activarlo en una
VM que ya está en ejecución no genera un registro del arranque que ya ocurrió, por lo que
`az vm boot-diagnostics get-boot-log` responde:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

Eso es lo esperado, no un fallo. Existirá un registro de arranque después del siguiente
reinicio del nodo. La conexión en vivo a la consola, sin embargo, funciona de inmediato —
no depende del registro.
</Aside>

## Comprobar la disponibilidad sin un terminal

Conectarse requiere una sesión interactiva, pero saber si *se conectaría* son dos llamadas
a la API. Ambas son útiles en una comprobación de estado.

El servicio debe estar habilitado para la suscripción — un administrador puede deshabilitarlo
en todo el tenant:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

Después solicite una conexión al puerto serie de un nodo concreto:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

Un `connectionString` que empiece por `wss://` — en este despliegue
`eastus.gateway.serialconsole.azure.com` — significa que la consola es accesible ahora
mismo. Antes de habilitar el diagnóstico de arranque, esta llamada no tenía nada a lo que
conectarse.

<Aside type="danger" title="Esa cadena de conexión es una credencial">
Es un token bearer de corta duración incrustado en una URL. No lo registre en logs, no lo
pegue en un ticket ni lo confirme en un repositorio. Imprima solo el host cuando esté
demostrando que la llamada funcionó.
</Aside>

## Conexión

<Steps>

1. Instale la extensión una vez:

   ```bash
   az extension add --name serial-console
   ```

2. Conéctese:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. Aterriza en el propio prompt de inicio de sesión del nodo, no en un shell. Este es el
   Site CLI, y necesita credenciales establecidas en el nodo — la contraseña de
   administrador del aprovisionamiento, o una establecida a través del endpoint de cambio
   de contraseña. La consola serie demuestra que el *canal* funciona; no omite la
   autenticación.

</Steps>

Capturado desde `f5-xc-ce-vm-01`, con elisiones en la parte media donde la salida de las
unidades de systemd no aporta nada:

```text file=../../../_data/serial-console-boot.txt
```

Cuatro cosas de esa transcripción merecen atención, porque responden preguntas que la
API de depuración no puede:

- **cloud-init se completó** — `Datasource DataSourceAzure`, finalizado en 22,37 segundos.
  Un nodo que nunca se registra suele haber fallado aquí, y aquí es donde se ve.
- **Ambos runtimes de contenedores arrancaron.** `Container Runtime Interface for OCI (CRI-O)`
  y `Docker Application Container Engine` están ambos `[ OK ]`, que es la prueba en tiempo
  de arranque del comportamiento de doble runtime que sorprende a la gente en
  [crictl](../../commands/system/crictl/) y [docker](../../commands/system/docker/).
- **`VP Manager image load` y `Argo Watch service`** — `vpm` y Argo arrancando.
- **El prompt es el del propio nodo**, tras su aviso de auditoría. La consola serie le da un
  prompt de inicio de sesión, no una sesión.

<Aside type="caution" title="Conectarse de forma interactiva requiere un terminal real — pero se puede automatizar">
`az serial-console connect` pone el terminal en modo raw, por lo que no puede ejecutarse desde
un pipeline ni desde cualquier contexto sin TTY. Falla en el lado del cliente, antes de
contactar con Azure:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

Ese traceback es manejo de terminal, no una interrupción de la consola serie.

La conexión en sí, sin embargo, **es** automatizable — controle el websocket directamente en
lugar de la CLI. La transcripción anterior se capturó así, sin TTY. Consulte
`scripts/serial_console_capture.py`, que es la forma de recopilar evidencias de arranque de
un nodo que no logró registrarse sin que una persona esté sentada ante un terminal.
</Aside>

<Aside type="caution" title="Espere tener que reintentar: la puerta de enlace rechaza aproximadamente uno de cada dos intentos">
El primer frame de la puerta de enlace es un desafío, no salida, y el cliente lo responde con
un token bearer. Incluso cuando eso se hace correctamente, el socket a menudo se cierra de
inmediato:

```
[close] code=1011 reason=Connection not trusted
```

Comportamiento observado: tiene éxito de forma intermitente, y con un uso sostenido todos los
nodos del grupo de recursos rechazan la conexión — incluidos nodos que funcionaban minutos
antes. `scripts/serial_console_capture.py` reintenta por defecto porque reintentar suele
funcionar.

**La causa no está establecida.** Lo que se ha descartado, porque cada una es una conjetura
plausible que hace perder tiempo:

| No es esto | Cómo confirmarlo |
| --- | --- |
| Limitación (throttling) de ARM/compute | Eso devuelve HTTP `429` en las llamadas a ARM. Esto es un cierre de websocket en un canal de datos separado. |
| Interceptación TLS por un proxy | `openssl s_client -connect <region>.gateway.serialconsole.azure.com:443 \| openssl x509 -noout -issuer`. Un emisor genuino `O=Microsoft Corporation` lo descarta; un proveedor de proxy como emisor lo confirma, y la solución es incluir `*.serialconsole.azure.com` en la lista de permitidos. |
| Diagnóstico de arranque deshabilitado | `az vm show -g <rg> -n <vm> --query diagnosticsProfile` informando `enabled: true`. |
| Discrepancia de token entre la concesión y el desafío | Usar un mismo token para ambos es la práctica correcta, pero no evita el cierre. |

Lo que *sí* es comportamiento documentado de Azure: **una sesión de consola serie por VM, y una
segunda solicitud exitosa expulsa a la primera.** El usuario expulsado se desconecta pero no
cierra sesión, por lo que la sesión de shell sobrevive. Dos personas depurando un mismo nodo se
desplazarán mutuamente de forma repetida.

Para trabajo masivo prefiera la [API de depuración](../debug-api/), que no tiene ninguno de estos límites.
[SSH no es una alternativa](../ssh/) — no puede habilitarse en esta compilación.
</Aside>

<Aside type="caution" title="El pegado está limitado a 2.048 caracteres">
Azure limita la longitud del pegado en la consola serie a 2.048 caracteres, para evitar
sobrecargar el puerto serie. Enviar un comando largo — o un lote de comandos en una sola
escritura — falla de una manera que se interpreta como un bloqueo o una limitación en lugar de
como un límite de longitud.

Envíe los comandos individualmente. Esta es una restricción real para cualquier recopilación
masiva a través de la consola serie, y otra razón para preferir la
[API de depuración](../debug-api/) para ese trabajo.
</Aside>

## Qué puede ver aquí que la API no puede mostrarle

- **cloud-init** ejecutándose, fallando o sin llegar a arrancar — la causa habitual de un
  nodo que nunca se registra.
- **Intentos de registro** contra `register.ves.volterra.io`, incluido un error de
  configuración o un token que el tenant rechazó.
- **Mensajes del kernel y del arranque** de antes de que cualquier agente estuviera en
  ejecución.
- El nodo cuando **no tiene ninguna ruta de red operativa**, lo que anula cualquier otra vía.

Para un nodo que *sí* está `ONLINE`, prefiera la API de depuración: es automatizable, produce
evidencias que puede volver a generar y no ocupa el único puerto serie.
