Cada Customer Edge sirve la Consola del Sitio de F5 en `https://<sli-ip>:65500`. En este
despliegue suele ser la primera opción a intentar.

Exige lo mínimo: no hay que distribuir claves SSH, no hay host de salto que mantener, no
hay IP pública en el nodo y no es necesario reemplazar la VM para habilitarla. El acceso
se convierte en una **decisión de Azure RBAC**. Además, no requiere que el sitio esté
registrado — la transcripción a continuación se capturó mientras los tres sitios
reportaban `site_state: FAILED`.

El inconveniente es que la Consola del Sitio solo responde en la dirección interna (SLI)
del nodo, accesible únicamente desde dentro de la VNet. Azure Bastion cierra esa brecha
sin añadir nada más a la red.

<Aside type="note" title="Qué se verifica aquí y qué no">
Cada comando y cada salida de esta página se ejecutaron contra `f5-xc-ce-vm-01` en este
despliegue y se reproducen literalmente, incluidos los fallos.

Lo único que no se ejercitó es **iniciar sesión**. Los pasos se detienen en el prompt de
credenciales, por lo que nada de lo que sigue describe el aspecto de la consola una vez
que se ha iniciado sesión.
</Aside>

## Antes de comenzar

<Steps>

1. Inicie sesión en Azure y añada la extensión de Bastion. La tunelización es una
   característica del cliente nativo y la extensión no se instala por defecto.

   ```bash
   az login
   az extension add --name bastion
   ```

2. Tenga el rol **Reader** sobre la máquina virtual CE, su interfaz de red y el host de
   Bastion.

3. Confirme que Bastion está desplegado y es compatible. El SKU Básico no admite ni
   tunelización ni conexión basada en IP, por lo que `Standard` y `True` son aquí ambos
   imprescindibles.

   ```bash
   az network bastion list -g rg-mcn-ce-ha-rmordasiewicz \
     --query "[].{name:name, sku:sku.name, tunneling:enableTunneling}" -o table
   ```

   ```text
   Name               Sku       Tunneling
   -----------------  --------  -----------
   ce-ha-lab-bastion  Standard  True
   ```

</Steps>

## Abrir el túnel

Tome los valores de `terraform output` en lugar de escribirlos manualmente — el id de
recurso no es algo que deba ensamblarse a mano.

<Steps>

1. Lea el nombre del host de Bastion, el grupo de recursos y el id de recurso de la VM CE
   de destino.

   ```bash
   cd terraform
   BASTION=$(terraform output -raw bastion_name)
   RG=$(terraform output -raw resource_group_name)
   VM_ID=$(terraform output -json ce_vm_ids | jq -r '.eastus01')
   ```

   ```text
   ce-ha-lab-bastion
   rg-mcn-ce-ha-rmordasiewicz
   /subscriptions/…/providers/Microsoft.Compute/virtualMachines/f5-xc-ce-vm-01
   ```

   <Aside type="caution" title="El mapa tiene como clave el sitio, no el nombre de la VM">
   Las claves de `ce_vm_ids` son `eastus01`, `eastus02`, `eastus03` — **no** los nombres
   de las VM. Un filtro como `jq -r '."f5-xc-ce-vm-01"'` devuelve `null`, y el túnel falla
   con un id de recurso vacío. Listarlas si no está seguro:

   ```bash
   terraform output -json ce_vm_ids | jq -r 'keys | join(", ")'
   ```

   ```text
   eastus01, eastus02, eastus03
   ```
   </Aside>

2. Inicie el túnel. Mantiene el puerto abierto hasta que se detiene, así que ejecútelo en
   segundo plano o use una segunda terminal.

   ```bash
   az network bastion tunnel \
     --name "$BASTION" \
     --resource-group "$RG" \
     --target-resource-id "$VM_ID" \
     --resource-port 65500 \
     --port 65500 &
   ```

   ```text
   WARNING: Opening tunnel on port: 65500
   WARNING: Tunnel is ready, connect on port 65500
   WARNING: Ctrl + C to close
   ```

   Las tres líneas llevan el prefijo `WARNING:`. Es la CLI de Azure escribiendo el
   progreso en stderr, no un problema. Espere a `Tunnel is ready` antes de conectarse.

3. Confirme que el listener es local, en loopback:

   ```bash
   lsof -nP -iTCP:65500 -sTCP:LISTEN
   ```

   ```text
   COMMAND   PID  USER  FD  TYPE  DEVICE  SIZE/OFF  NODE  NAME
   Python  41648  you   7u  IPv4  …            0t0   TCP  127.0.0.1:65500 (LISTEN)
   ```

4. Abra la consola. El túnel la hace local, por lo que la dirección es `localhost` — no la
   dirección del nodo.

   ```bash
   open https://localhost:65500/          # macOS
   xdg-open https://localhost:65500/      # Linux
   ```

5. Detenga el túnel cuando haya terminado — `Ctrl-C`, o `kill %1` si lo ejecutó en segundo
   plano. Dejarlo abierto mantiene ocupado el puerto local 65500 y la sesión de Bastion.

</Steps>

## Lo que verá

**Un diálogo de credenciales, no una página de inicio de sesión.** La consola usa
autenticación HTTP Basic, por lo que el navegador muestra su propio prompt de usuario y
contraseña. No hay formulario visible:

```bash
curl -skI https://localhost:65500/
```

```text
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Basic realm="Volterra Site Console"
Content-Length: 0
```

Un `401` con ese realm indica que la consola funciona correctamente. Es la respuesta
esperada para una solicitud no autenticada.

**Una advertencia de certificado, por tres motivos a la vez.** Comprobando el certificado
directamente:

```bash
openssl s_client -connect localhost:65500 -servername localhost </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
```

```text
subject=C=US, ST=California, L=Santa Clara, O=Volterra, OU=Volterra Edge Services, CN=site-local.volterra.io
issuer=C=US, ST=California, L=Santa Clara, O=Volterra, OU=Volterra Edge Services, CN=site-local.volterra.io
notBefore=Oct 25 04:51:31 2024 GMT
notAfter=Oct 25 04:51:31 2025 GMT
```

El subject es igual al issuer, por lo que está autofirmado. El nombre es
`site-local.volterra.io` mientras que usted se conecta a `localhost`, de modo que no
coincidirá. Y en la compilación que ejecuta este despliegue, **el certificado expiró el
25 de octubre de 2025** — el appliance lo incluye y nada en este repositorio lo renueva.

Espere una advertencia contundente del navegador, y espérela cada vez. La línea subject
anterior es la parte útil: es como confirma que llegó al appliance y no a algo más que
esté escuchando en el puerto local 65500.

## La credencial de administrador

Inicie sesión como `admin`. **Esta documentación no publica la contraseña, y no debería
hacerlo.**

Un Customer Edge recién instalado viene con el valor predeterminado publicado por F5, y
F5 exige que se cambie. Tratar el cambio como parte del despliegue de un nodo, y no como
un refuerzo posterior. Dos razones por las que esto importa más de lo que podría parecer:

- Esta documentación es pública. Publicar la contraseña actual de la consola de la flota
  convertiría «tener Reader sobre Bastion» en acceso completo al appliance para cualquiera
  que lea la página.
- Una contraseña publicada en la documentación es incorrecta en el momento en que alguien
  la rota, e incorrecta de la manera más engañosa: el lector concluye que su acceso está
  roto en lugar de que la página está desactualizada.

Obtenga la contraseña del lugar donde su equipo guarda los secretos operativos. Si la
respuesta es «sigue siendo el valor predeterminado de fábrica», cámbiela antes de hacer
cualquier otra cosa.

<Aside type="caution" title="No se ha verificado el establecimiento de la contraseña desde Terraform">
`admin_user_credentials.admin_password` en el objeto del sitio parece la forma declarativa
de establecer esto. **No** se ha confirmado que llegue a la Consola del Sitio en esta
compilación, así que no asuma que lo hace.

Tampoco lea la [página de SSH](../ssh/) como evidencia en ningún sentido. Su conclusión de
que `admin_password` «no cambió nada» se midió contra la autenticación SSH, que `vpm`
omite completamente para el usuario `admin`. Eso no dice nada sobre la consola.
</Aside>

## Por qué el túnel debe apuntar al id de recurso

`--target-resource-id` es obligatorio. Apuntar a la dirección del nodo en su lugar es
rechazado:

```bash
az network bastion tunnel --name "$BASTION" -g "$RG" \
  --target-ip-address 10.0.3.5 --resource-port 65500 --port 65501
```

```text
ERROR: Custom ports are not allowed. Allowed ports for Tunnel with IP connect is 22, 3389.
```

La razón **no** es que la conexión basada en IP esté deshabilitada — en este Bastion
`ip_connect_enabled` es `true`. Microsoft no admite puertos personalizados en conexiones
de cliente nativo basadas en IP independientemente de ese ajuste
([documentación de Azure](https://learn.microsoft.com/azure/bastion/connect-ip-address)),
y 65500 es un puerto personalizado. Inspeccionar la configuración de Bastion aquí no lleva
a ningún lado; use el id de recurso.

## Cuando no funciona

| Síntoma | Causa | Solución |
| --- | --- | --- |
| `ERROR: Custom ports are not allowed. Allowed ports for Tunnel with IP connect is 22, 3389.` | Se usó `--target-ip-address` | Use `--target-resource-id` |
| `ERROR: Defined port is currently unavailable` | Otro túnel ya ocupa ese puerto local | Detenga el otro túnel, o pase un `--port` diferente; `--resource-port` se mantiene en 65500 |
| El túnel se inicia pero el id de recurso está vacío | El filtro `jq` usó el nombre de la VM en lugar de la clave del sitio | Use la clave `eastus01`/`02`/`03` |
| `401 Unauthorized`, realm `Volterra Site Console` | No es un fallo — solicitud no autenticada | Proporcione la credencial de `admin` |
| El navegador rechaza el certificado | Autofirmado, nombre no coincide y expirado desde oct. 2025 | Esperado; confirme que el subject es `CN=site-local.volterra.io` y continúe |

<Aside type="note" title="No se reprodujeron fallos de autorización">
Un RBAC insuficiente es la otra forma obvia en que esto falla, pero reproducirlo implicaría
eliminar asignaciones de roles de un despliegue compartido, por lo que no se documenta
aquí con un error literal. Si el túnel falla al iniciarse con un error de autorización,
compruebe el rol Reader sobre los tres: la VM, su NIC y el host de Bastion.
</Aside>
