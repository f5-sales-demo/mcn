Capturado el 2026-07-28 desde un CE de esta implementación. `sitecli/capture-manifest.json`
registra qué nodo, y `scripts/capture-sitecli.sh --check` vuelve a verificar la superficie de
comandos contra un CE en vivo.

Cada Customer Edge sirve la Consola del sitio de F5 en `https://<sli-ip>:65500`. En esta
implementación suele ser la ruta que conviene probar primero.

Es la que menos le exige: ninguna clave SSH que distribuir, ningún host de salto que mantener,
ninguna IP pública en el nodo y ningún reemplazo de VM para habilitarla. Quién puede conectarse
se convierte en una **decisión de Azure RBAC**. Y no necesita que el sitio esté registrado: esta
página se capturó por primera vez mientras los tres sitios informaban `site_state: FAILED`, y se
volvió a verificar sin cambios contra los mismos nodos una vez que estaban `ONLINE`.

La contrapartida es que la Consola del sitio responde únicamente en la dirección interna (SLI)
del nodo, alcanzable solo desde dentro de la VNet. Azure Bastion cierra esa brecha sin colocar
nada más en la red.

<Aside type="note" title="Qué se verifica aquí y qué no">
Cada comando y cada salida de esta página se ejecutó contra `f5-xc-ce-vm-01` en esta
implementación y se reproduce textualmente, incluidos los fallos.

**La autenticación está verificada**: la credencial `admin` del dispositivo devuelve `200` a
través del túnel. Lo que *no* se ejercita es la consola en sí — nada de lo que sigue describe qué
se puede ver o hacer una vez dentro.

**Azure RBAC no está verificado.** Todas las ejecuciones se hicieron como propietario de la
suscripción, por lo que el requisito de Reader del paso 2 es el requisito documentado por
Microsoft y no algo medido aquí.
</Aside>

<Aside type="caution" title="Bastion es opcional y no se implementa por defecto">
`enable_bastion` es `false` por defecto, así que en un `terraform apply` predeterminado no hay
host de Bastion y `terraform output -raw bastion_name` es `null`. Establezca
`enable_bastion = true` en `terraform/terraform.tfvars` — en esta implementación es `true`.

La razón de que sea opcional es el coste, no el riesgo: un host de SKU Standard factura un cargo
fijo por hora desde el momento en que se aprovisiona, tanto si alguien abre un túnel como si no —
USD 0,29/hora en `eastus` para las dos unidades de escalado incluidas (precio de lista, 2026-07),
aproximadamente USD 212 al mes. Vuelva a desactivarlo cuando la demostración no necesite acceso a
la consola.
</Aside>

## Antes de empezar

<Steps>

1. Inicie sesión en Azure y añada la extensión de Bastion. El túnel es una función del cliente
   nativo y la extensión no está instalada por defecto.

   ```bash
   az login
   az extension add --name bastion
   ```

2. Disponga de **Reader** sobre la máquina virtual del CE, su interfaz de red y el host de
   Bastion. Este es el requisito documentado por Microsoft y **no está verificado aquí** — todas
   las ejecuciones en esta implementación se hicieron como propietario de la suscripción, por lo
   que no se ha demostrado que ningún rol inferior sea suficiente o insuficiente.

3. Confirme que Bastion está implementado y es capaz. La SKU Basic no admite ni el túnel ni la
   conexión basada en IP, por lo que `Standard` y `True` aquí son ambos determinantes.

   ```bash
   az network bastion list -g "$(terraform output -raw resource_group_name)" \
     --query "[].{name:name, sku:sku.name, tunneling:enableTunneling}" -o table
   ```

   ```text
   Name               Sku       Tunneling
   -----------------  --------  -----------
   ce-ha-lab-bastion  Standard  True
   ```

</Steps>

## Abrir el túnel

Tome los valores de `terraform output` en lugar de escribirlos — el id de recurso no es algo que
convenga montar a mano.

<Steps>

1. Lea el nombre del host de Bastion, el grupo de recursos y el id de recurso de la VM del CE de destino.

   ```bash
   cd terraform
   BASTION=$(terraform output -raw bastion_name)
   RG=$(terraform output -raw resource_group_name)
   VM_ID=$(terraform output -json ce_vm_ids | jq -r '.eastus01')
   ```

   ```text
   ce-ha-lab-bastion
   rg-mcn-ce-ha-rmordasiewicz
   /subscriptions/…/providers/Microsoft.Compute/virtualMachines/f5-xc-ce-vm-01
   ```

   <Aside type="caution" title="El mapa se indexa por sitio, no por nombre de VM">
   Las claves de `ce_vm_ids` son `eastus01`, `eastus02`, `eastus03` — **no** los nombres de las
   VM. Un filtro como `jq -r '."f5-xc-ce-vm-01"'` devuelve `null`, y entonces el túnel falla con
   un id de recurso vacío. Enumérelas si tiene dudas:

   ```bash
   terraform output -json ce_vm_ids | jq -r 'keys | join(", ")'
   ```

   ```text
   eastus01, eastus02, eastus03
   ```

   </Aside>

2. Inicie el túnel. Mantiene el puerto abierto hasta que se detenga, así que ejecútelo en segundo
   plano o use una segunda terminal.

   ```bash
   az network bastion tunnel \
     --name "$BASTION" \
     --resource-group "$RG" \
     --target-resource-id "$VM_ID" \
     --resource-port 65500 \
     --port 65500 &
   ```

   ```text
   WARNING: Opening tunnel on port: 65500
   WARNING: Tunnel is ready, connect on port 65500
   WARNING: Ctrl + C to close
   ```

   Las tres líneas llevan el prefijo `WARNING:`. Eso es la CLI de Azure escribiendo el progreso
   en stderr, no un problema. Espere a `Tunnel is ready` antes de conectarse.

3. Confirme que el escuchador es local, en loopback:

   ```bash
   lsof -nP -iTCP:65500 -sTCP:LISTEN
   ```

   ```text
   COMMAND   PID  USER  FD  TYPE  DEVICE  SIZE/OFF  NODE  NAME
   Python  41648  you   7u  IPv4  …            0t0   TCP  127.0.0.1:65500 (LISTEN)
   ```

4. Abra la consola. El túnel la hace local, así que la dirección es `localhost` — no la dirección
   del nodo.

   ```bash
   open https://localhost:65500/          # macOS
   xdg-open https://localhost:65500/      # Linux
   ```

5. Detenga el túnel cuando termine — `Ctrl-C`, o `kill %1` si lo dejó en segundo plano. Dejarlo
   abierto retiene el puerto local 65500 y la sesión de Bastion.

</Steps>

## Qué verá

**Un cuadro de diálogo de credenciales, no una página de inicio de sesión.** La consola usa
autenticación HTTP Basic, por lo que el navegador muestra su propia solicitud de nombre de
usuario y contraseña. No hay ningún formulario que mirar:

```bash
curl -skI https://localhost:65500/
```

```text
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Basic realm="Volterra Site Console"
Content-Type: text/html; charset=utf-8
Content-Length: 0
```

Un `401` con ese realm significa que la consola funciona correctamente. Es lo que se supone que
recibe una solicitud no autenticada — y suministrar la credencial `admin` a la misma URL responde
`200`, que es la forma de confirmar la credencial antes de abrir un navegador:

```bash
curl -sk -u admin -o /dev/null -w '%{http_code}\n' https://localhost:65500/
```

```text
Enter host password for user 'admin':
200
```

`-u admin` sin dos puntos hace que `curl` solicite la contraseña en lugar de tomarla de la línea
de comandos, donde acabaría en el historial del shell y en la lista de procesos.

**Una advertencia de certificado, por tres motivos a la vez.** Comprobando el certificado
directamente:

```bash
openssl s_client -connect localhost:65500 -servername localhost </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
```

```text
subject=C=US, ST=California, L=Santa Clara, O=Volterra, OU=Volterra Edge Services, CN=site-local.volterra.io
issuer=C=US, ST=California, L=Santa Clara, O=Volterra, OU=Volterra Edge Services, CN=site-local.volterra.io
notBefore=Oct 25 04:51:31 2024 GMT
notAfter=Oct 25 04:51:31 2025 GMT
```

El sujeto coincide con el emisor, por lo que es autofirmado. El nombre es
`site-local.volterra.io` mientras usted se conecta a `localhost`, así que no coincidirá. Y en la
compilación que ejecuta esta implementación, **el certificado caducó el 25 de octubre de 2025** —
el dispositivo lo incluye, y nada en este repositorio lo renueva.

Espere una advertencia contundente del navegador, y espérela cada vez. La línea del sujeto de
arriba es la parte útil: es cómo confirma que llegó al dispositivo y no a otra cosa escuchando en
el puerto local 65500.

## La credencial de administrador

Inicie sesión como `admin`. **Esta documentación no publica la contraseña, y no debería hacerlo.**

<Aside type="danger" title="En esta implementación esa contraseña sigue siendo el valor de fábrica de F5">
Este es un hecho medido, no una sospecha: la credencial predeterminada de fábrica se autentica y
devuelve `200` en los tres CE a día de hoy. F5 publica ese valor predeterminado y exige que se
cambie, y no se ha hecho.

La consecuencia práctica es que en esta implementación "tener Reader sobre el Bastion" equivale a
acceso completo a la consola del dispositivo, para cualquiera que conozca un valor que está en la
documentación pública de F5. Cámbielo, y trate ese cambio como parte de la implementación de un
nodo y no como un endurecimiento posterior.
</Aside>

Dos razones por las que no publicarla importa más aquí de lo que podría parecer:

- Esta documentación es pública. Imprimir la contraseña actual de la consola de la flota
  convertiría "tener Reader sobre el Bastion" en acceso completo al dispositivo para cualquiera
  que lea la página.
- Una contraseña publicada en la documentación queda incorrecta en el momento en que alguien la
  rota, y de la forma más engañosa — el lector concluye que su acceso está roto en lugar de que
  la página está obsoleta.

Una vez rotada, obténgala de donde su equipo guarde los secretos operativos.

<Aside type="caution" title="Establecer la contraseña desde Terraform no está verificado">
`admin_user_credentials.admin_password` en el objeto de sitio parece la forma declarativa de
establecerla. **No** se ha confirmado que llegue a la Consola del sitio en esta compilación, así
que no dé por supuesto que lo hace.

No interprete la [página de SSH](../ssh/) como evidencia en ningún sentido. Su hallazgo de que
`admin_password` "no cambió nada" se midió contra la autenticación SSH, que `vpm` omite por
completo para el usuario `admin`. Eso no dice nada sobre la consola.
</Aside>

## Por qué el túnel debe apuntar al id de recurso

`--target-resource-id` es obligatorio. Apuntar a la dirección del nodo se rechaza — sea cual sea
la dirección que use, por lo que deliberadamente no se imprime aquí ninguna real:

```bash
az network bastion tunnel --name "$BASTION" -g "$RG" \
  --target-ip-address <any-sli-address> --resource-port 65500 --port 65501
```

```text
ERROR: Custom ports are not allowed. Allowed ports for Tunnel with IP connect is 22, 3389.
```

La razón **no** es que la conexión basada en IP esté deshabilitada — en este Bastion
`ip_connect_enabled` es `true`. Microsoft no admite puertos personalizados en conexiones de
cliente nativo basadas en IP, independientemente de ese ajuste
([documentación de Azure](https://learn.microsoft.com/azure/bastion/connect-ip-address)), y 65500
es un puerto personalizado. Inspeccionar la configuración de Bastion aquí no lleva a ninguna
parte; use el id de recurso.

## Cuando no funciona

| Síntoma | Causa | Solución |
| --- | --- | --- |
| `ERROR: Custom ports are not allowed. Allowed ports for Tunnel with IP connect is 22, 3389.` | Se usó `--target-ip-address` | Use `--target-resource-id` |
| `ERROR: Defined port is currently unavailable` | Otro túnel ya retiene ese puerto local | Detenga el otro túnel, o pase un `--port` distinto; `--resource-port` sigue siendo 65500 |
| `terraform output -raw bastion_name` es `null` o está vacío | Bastion no está implementado | Establezca `enable_bastion = true` y aplique |
| El túnel se inicia pero el id de recurso está vacío | El filtro de `jq` usó el nombre de la VM en lugar de la clave del sitio | Indexe por `eastus01`/`02`/`03` |
| `401 Unauthorized`, realm `Volterra Site Console` | No es un fallo — solicitud no autenticada | Suministre la credencial `admin` |
| El navegador rechaza el certificado | Autofirmado, nombre no coincidente y caducado desde octubre de 2025 | Esperado; confirme que el sujeto es `CN=site-local.volterra.io` y continúe |

<Aside type="note" title="Los fallos de autorización no se reprodujeron">
Un RBAC insuficiente es la otra forma obvia en que esto falla, pero reproducirlo implicaría
eliminar asignaciones de roles de una implementación compartida, por lo que no se documenta aquí
con un error textual. Si el túnel falla al iniciarse con un error de autorización, compruebe
Reader en los tres: la VM, su NIC y el host de Bastion.
</Aside>
