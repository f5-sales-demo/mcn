Capturado el 2026-07-28 desde un CE de este despliegue. Estos son comandos ejecutados en el
propio nodo, por lo que pasan por el Site CLI en lugar de la API de depuración;
`sitecli/exec-catalog.json` registra la superficie y `sitecli/capture-manifest.json` registra
el nodo.

Envoy termina y actúa como proxy del tráfico de aplicaciones en el Customer Edge. Estos cuatro
comandos consultan su interfaz de administración, y ninguno de ellos forma parte de la
[API de depuración](../../../access/debug-api/).

<Aside type="note" title="Cada uno de estos comienza con un medidor de progreso de curl">
Son envoltorios de `curl` alrededor del endpoint de administración de Envoy, invocados sin
`-s`, por lo que las primeras dos o tres líneas de cada captura a continuación son el progreso
de transferencia de curl escrito en stderr:

```text
  % Total    % Received % Xferd  Average Speed   Time    Time     Time  Current
                                 Dload  Upload   Total   Spent    Left  Speed
  0     0    0     0 …
```

Eso no es salida de Envoy ni es un error. También es útil: el conteo de bytes en `% Received`
indica si Envoy devolvió algo, lo que permite distinguir entre "no hay listeners configurados"
y "la interfaz de administración no respondió".
</Aside>

## `envoy-listeners`

Cada listener que Envoy tiene instalado, en formato `nombre:dirección:puerto`.

```bash
execcli envoy-listeners
```

```text file=../../../../_data/sitecli-envoy-listeners.txt
```

**Qué buscar.** En este despliegue el listener contiene `10.250.0.10:80` — el VIP que el CE
anuncia en BGP. Esa única línea une tres capas: si
[`show-ip-bgp-summary`](../../network/bgp/) muestra el prefijo siendo anunciado pero este
listener está ausente, la ruta está siendo atraída hacia un nodo que no la servirá, que es el
peor modo de fallo en un conjunto ECMP porque el tráfico se distribuye en un agujero negro.

El `[fe80:…]:80` al final es la dirección link-local de la interfaz a la que está vinculado
el listener.

**Lo que no indica.** Nada sobre el estado del upstream — un listener existe independientemente
de si algo detrás de él es accesible. Use `envoy-clusters` para eso.

## `envoy-clusters`

Cada cluster, con sus límites de conexiones y solicitudes por prioridad.

```bash
execcli envoy-clusters
```

```text file=../../../../_data/sitecli-envoy-clusters.txt
```

**Qué buscar.** Las líneas tienen el formato `cluster::ámbito::clave::valor`. La entrada
`observability_name` identifica cada cluster, y la combinación
`default_priority::max_connections`, `max_pending_requests` y `max_requests` es donde
aparecen los límites de solicitudes — un cluster fijado en su `max_pending_requests` está
siendo limitado por configuración y no por el upstream.

## `envoy-config-dump`

La configuración completa de Envoy en formato JSON. Es grande: 126 KB en un nodo de
demostración inactivo.

```bash
execcli envoy-config-dump
```

```text file=../../../../_data/sitecli-envoy-config-dump.txt
```

**Qué buscar.** El array `configs` de nivel superior contiene un objeto por tipo de
configuración — bootstrap, clusters, listeners, rutas, secretos. Recurra a este cuando un
listener o cluster existe pero se comporta de forma inesperada, y búsquelo en lugar de leerlo
completo.

## `envoy-hc-config-dump`

La configuración de health-check específicamente.

```bash
execcli envoy-hc-config-dump
```

```text file=../../../../_data/sitecli-envoy-hc-config-dump.txt
```

**Qué buscar.** En este despliegue devuelve **un único byte** — visible como `100 1` en el
medidor de `curl` — lo que significa que no hay configuración de health-check instalada. Ese
es el estado esperado para un CE sin origin pools con health-check, y vale la pena
reconocerlo: un resultado vacío aquí no indica una consulta fallida.
