Envoy termina y actúa como proxy del tráfico de aplicaciones en el Customer Edge. Estos cuatro comandos
consultan su interfaz de administración, y ninguno de ellos está disponible en la
[API de depuración](../../../access/debug-api/).

<Aside type="note" title="Cada uno de estos comienza con un medidor de progreso de curl">
Son envoltorios `curl` alrededor del endpoint de administración de Envoy, invocados sin `-s`, por lo que las primeras
dos o tres líneas de cada captura a continuación corresponden al progreso de transferencia de curl escrito en stderr:

```text
  % Total    % Received % Xferd  Average Speed   Time    Time     Time  Current
                                 Dload  Upload   Total   Spent    Left  Speed
  0     0    0     0 …
```

Eso no es salida de Envoy ni un error. También es útil: el recuento de bytes en `% Received`
le indica si Envoy devolvió algo, lo que permite distinguir entre "no hay listeners
configurados" y "la interfaz de administración no respondió".
</Aside>

## `envoy-listeners`

Cada listener que Envoy tiene instalado, con el formato `nombre:dirección:puerto`.

```bash
execcli envoy-listeners
```

```text file=../../../../_data/sitecli-envoy-listeners.txt
```

**Qué buscar.** En este despliegue, el listener lleva `10.250.0.10:80` — el VIP que el
CE anuncia en BGP. Esa única línea vincula tres capas: si
[`show-ip-bgp-summary`](../../network/bgp/) muestra el prefijo siendo anunciado pero este
listener está ausente, la ruta está siendo atraída hacia un nodo que no la servirá, lo cual es
el peor modo de fallo en un conjunto ECMP porque el tráfico se distribuye mediante balanceo de carga hacia un agujero negro.

El `[fe80:…]:80` al final es la dirección de enlace local de la interfaz a la que está vinculado
el listener.

**Lo que no le indica.** Nada sobre el estado del upstream — un listener existe independientemente
de si algo detrás de él es accesible. Use `envoy-clusters` para eso.

## `envoy-clusters`

Cada cluster, con sus límites de conexión y solicitudes por prioridad.

```bash
execcli envoy-clusters
```

```text file=../../../../_data/sitecli-envoy-clusters.txt
```

**Qué buscar.** Las líneas tienen el formato `cluster::ámbito::clave::valor`. La entrada `observability_name`
identifica cada cluster, y la tripleta `default_priority::max_connections`,
`max_pending_requests` y `max_requests` es donde aparecen los límites de solicitudes — un cluster
fijado en su `max_pending_requests` está siendo limitado por configuración y no por el
upstream.

## `envoy-config-dump`

La configuración completa de Envoy en formato JSON. Es extensa: 126 KB en un nodo de demostración sin actividad.

```bash
execcli envoy-config-dump
```

```text file=../../../../_data/sitecli-envoy-config-dump.txt
```

**Qué buscar.** El arreglo `configs` de nivel superior contiene un objeto por cada tipo de configuración —
bootstrap, clusters, listeners, rutas, secretos. Recurra a esto cuando un listener o cluster
existe pero se comporta de forma inesperada, y búsquelo en lugar de leerlo completo.

## `envoy-hc-config-dump`

La configuración de verificación de estado (health-check) específicamente.

```bash
execcli envoy-hc-config-dump
```

```text file=../../../../_data/sitecli-envoy-hc-config-dump.txt
```

**Qué buscar.** En este despliegue devuelve un **único byte** — visible como `100 1`
en el medidor de curl — lo que significa que no hay configuración de verificación de estado instalada. Ese es el estado
esperado para un CE sin pools de origen con verificación de estado, y vale la pena reconocerlo: un resultado
vacío aquí no es una consulta fallida.
