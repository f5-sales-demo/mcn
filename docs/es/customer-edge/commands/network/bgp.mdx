El CE ejecuta FRR para BGP. En esta topología establece peering con las dos instancias de
Azure Route Server, anuncia la VIP y aprende el prefijo de la VNet.

## `show-ip-bgp-summary`

Empiece aquí. Una sola pantalla le indica si el peering está activo y cuánto tiempo ha
permanecido estable.

```bash
{"command":["show-ip-bgp-summary"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp-summary.txt
```

Lea primero `State/PfxRcd`. Un número es el recuento de prefijos recibidos y significa que la
sesión está establecida; cualquier otra cosa — `Active`, `Connect`, `Idle` — es una sesión
que no está activa. `Up/Down` muestra cuánto tiempo ha durado el estado actual, de modo que una
sesión que se reinicia continuamente muestra un valor sospechosamente pequeño.

<Aside type="caution" title="El vrf id que aparece aquí no es el que rt espera">
Esta salida informa `vrf-id 3`. Esa es la numeración de FRR. El plano de datos de Argo usa un
identificador de tabla distinto, y pasar el número de FRR a
[`rt --dump`](../dataplane-forwarding/) devuelve `No such file or directory`, lo que
parece un nodo averiado en lugar del argumento equivocado.
</Aside>

## `show-ip-bgp`

La tabla completa, con la selección de la mejor ruta visible.

```bash
{"command":["show-ip-bgp"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp.txt
```

`*` es una ruta válida, `>` la mejor ruta seleccionada, `=` un miembro de multipath. En la captura
anterior, el prefijo de la VNet aprendido `10.0.0.0/16` tiene dos rutas — una por cada instancia
de Route Server — marcadas `*=` y `*>`: una mejor ruta más un miembro de multipath, de modo que el nodo
reparte la carga de su tráfico de retorno entre ambas instancias. La VIP `10.250.0.10/32` tiene una única ruta `*>`
porque este nodo la origina.

<Aside type="caution" title="El ECMP de tres vías de la demostración no es visible en esta salida">
`show-ip-bgp` es la tabla de un solo nodo. El ECMP que demuestra esta implementación consiste en tres CE *distintos*
que anuncian el mismo `/32`, y se programa en el lado de Azure — por lo que la tabla BGP de ningún CE individual
puede mostrarlo, y la ausencia de un marcador de multipath en la VIP aquí no es un fallo.
Demuéstrelo en su lugar desde los peerings del Route Server o desde la tabla de rutas efectiva del cliente;
ambas están en la [página de as-built](../../../../as-built/).
</Aside>

## `show-ip-bgp-neighbors`

Detalle por vecino: capacidades negociadas, temporizadores, contadores de mensajes y el
motivo del último reinicio.

```bash
{"command":["show-ip-bgp-neighbors"]}
```

Recurra a él cuando el resumen muestre una sesión inestable y necesite saber por qué.
`Last reset` y su motivo son las líneas útiles.

## `show-ip-bgp-neighbors-advertised-route`

Lo que este nodo está comunicando a sus pares, en contraposición a lo que conoce.

```bash
{"command":["show-ip-bgp-neighbors-advertised-route"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp-neighbors-advertised-route.txt
```

Este es el comando para «la VIP no es alcanzable desde la VNet». Si la VIP está
ausente aquí, el problema está en este nodo y por mucho que observe al par no
conseguirá nada.

La salida repite un bloque `bgp neighbor:` **por par**, de modo que en esta topología obtiene los
mismos dos prefijos dos veces — uno por cada instancia de Route Server. Eso no es una renderización
duplicada: es lo que confirma que el nodo está anunciando a ambos. Un bloque que está presente para un
par y falta o es corto para el otro es el caso interesante.
