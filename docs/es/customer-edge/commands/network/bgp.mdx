El CE ejecuta FRR para BGP. En esta topología establece peering con las dos instancias de
Azure Route Server, anuncia la VIP y aprende el prefijo de la VNet.

## `show-ip-bgp-summary`

Empiece aquí. Una sola pantalla le indica si el peering está activo y cuánto tiempo ha
permanecido estable.

```bash
{"command":["show-ip-bgp-summary"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp-summary.txt
```

Lea primero `State/PfxRcd`. Un número es la cantidad de prefijos recibidos y significa que la
sesión está establecida; cualquier otro valor — `Active`, `Connect`, `Idle` — corresponde a una
sesión que no está activa. `Up/Down` muestra cuánto ha durado el estado actual, de modo que una
sesión que se reinicia constantemente muestra un valor sospechosamente pequeño.

<Aside type="caution" title="El vrf id que aparece aquí no es el que rt necesita">
Esta salida informa `vrf-id 3`. Esa es la numeración de FRR. El plano de datos de Argo utiliza un
identificador de tabla distinto, y pasar el número de FRR a
[`rt --dump`](../dataplane-forwarding/) devuelve `No such file or directory`, lo que
parece un nodo averiado en lugar del argumento incorrecto.
</Aside>

## `show-ip-bgp`

La tabla completa, con la selección de la mejor ruta visible.

```bash
{"command":["show-ip-bgp"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp.txt
```

`*` es una ruta válida, `>` la mejor ruta seleccionada, `=` un miembro de multipath. En la captura
anterior, el prefijo aprendido de la VNet `10.0.0.0/16` tiene dos rutas —una a través de cada instancia
de Route Server— marcadas como `*=` y `*>`: una mejor ruta más un miembro de multipath, por lo que el
nodo reparte la carga de su tráfico de retorno entre ambas instancias. La VIP `10.250.0.10/32` tiene una
única ruta `*>` porque este nodo la origina.

<Aside type="caution" title="El multipath de coste igual de la demostración no es visible en esta salida">
`show-ip-bgp` es la tabla de un solo nodo. El ECMP que demuestra esta implementación consiste en varios
CE *distintos* anunciando el mismo `/32`, y se programa en el lado de Azure — por lo que la tabla BGP de
ningún CE individual puede mostrarlo, y la ausencia de un marcador de multipath en la VIP aquí no
constituye un fallo. Compruébelo en su lugar desde los peerings del Route Server o desde la tabla de rutas
efectiva del cliente; ambas opciones están en la [página de verificación](../../../../demo/verify/).
</Aside>

## `show-ip-bgp-neighbors`

Detalle por vecino: capacidades negociadas, temporizadores, contadores de mensajes y el
motivo del último reinicio.

```bash
{"command":["show-ip-bgp-neighbors"]}
```

Recurra a él cuando el resumen muestre una sesión inestable y necesite saber por qué.
`Last reset` y su motivo son las líneas útiles.

## `show-ip-bgp-neighbors-advertised-route`

Lo que este nodo está comunicando a sus peers, en contraposición a lo que conoce.

```bash
{"command":["show-ip-bgp-neighbors-advertised-route"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp-neighbors-advertised-route.txt
```

Este es el comando para «la VIP no es alcanzable desde la VNet». Si la VIP no aparece
aquí, el problema está en este nodo y no servirá de nada examinar el peer.

La salida repite un bloque `bgp neighbor:` **por cada peer**, de modo que en esta topología obtiene
los mismos dos prefijos dos veces — una vez por cada instancia de Route Server. No se trata de una
representación duplicada: es lo que confirma que el nodo está anunciando a ambos. El caso interesante
es un bloque que está presente para un peer y ausente o incompleto para el otro.
