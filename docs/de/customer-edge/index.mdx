Ein Customer Edge (CE) ist der F5 Distributed Cloud-Knoten, den dieses Repository in
Azure bereitstellt — `terraform/modules/ce-node`, erstellt aus dem
`volterraedgeservices/volterra-node` Marktplatz-Image.

Er führt die Datenebene (Argo), die Steuerungsebene (Vega), einen Envoy-Proxy, einen Kubernetes-Stack
und `vpm` aus — den Agenten, der den Knoten registriert und alles andere darauf
verwaltet.

Wenn ein CE sich nicht korrekt verhält, ist die Site CLI das geeignete Instrument. Die erste Entscheidung besteht darin, welcher Zugriffspfad gilt. Die falsche Wahl kostet Zeit auf eine Weise, die wie ein defekter Knoten aussieht.

## Zwei Zugriffspfade, die nicht austauschbar sind

  <LinkCard

Die Debug-API erreicht den Knoten **über die F5 Distributed Cloud-Steuerungsebene**.
Das ist der eigentliche Grund, warum diese Unterscheidung wichtig ist: Die API kann erst antworten, wenn der Knoten
registriert ist und `ONLINE` meldet.

Ein Knoten, der sich nicht registrieren konnte — fehlerhaftes Cloud-Init, ein abgelaufenes Token, keine Route zu
`register.ves.volterra.io` — ist genau der Fall, in dem Diagnose benötigt wird, und
genau der Fall, den die API nicht bedienen kann.

Der Knoten verweigert außerdem SSH im Auslieferungszustand. Port 22 ist am CE selbst geschlossen, nicht durch eine
Netzwerksicherheitsgruppe:

```console
$ ssh -o ConnectTimeout=10 admin@<ce-public-ip>
ssh: connect to host <ce-public-ip> port 22: Connection refused
```

Auch aus dem VNet heraus verifiziert, von einem Jump-Host im selben Subnetz — das Öffnen einer Sicherheitsgruppenregel ändert daran nichts.

Also: Wenn die Site `ONLINE` ist, verwenden Sie die Debug-API. Wenn nicht, ist die serielle Konsole der einzige Zugang.

<Aside type="caution" title="Überprüfen Sie zuerst den Site-Zustand">
Eine Anfrage zeigt Ihnen, welchen Pfad Sie verwenden:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/config/namespaces/system/sites/<site>" \
  | jq -r '.spec.site_state'
```

`ONLINE` bedeutet, dass die Debug-API funktioniert. Alles andere — oder eine Site, die nicht
existiert — bedeutet serielle Konsole.
</Aside>

## Sicherheitsregeln

Diese gelten für jeden Befehl auf jeder der folgenden Seiten.

- **Nur lesend, sofern Sie nicht sicher sind.** Die Befehlsoberfläche ist in zwei
  Berechtigungsstufen unterteilt, und die `Exec`-Stufe verändert entweder den Knoten oder liest einen Zustandsmarker. Keine der Seiten hier führt einen `Exec`-Befehl aus, und das Erfassungs-Harness ebenfalls nicht.
- **Gehen Sie nie davon aus, dass ein Befehl anhand seines Namens sicher ist.** `ip-link-set` klingt wie eine Abfrage und deaktiviert ein Interface. `systemctl-restart-crio` startet die Container-Runtime unter einer aktiven Datenebene neu.
- **Bevorzugen Sie den kleinstmöglichen Befehl, der die Frage beantwortet.** `health` und
  `diagnosis` fassen den Knotenzustand kostengünstig zusammen; `flow-l` gibt eine Flow-Tabelle mit 629.760 Einträgen aus.
- **Ein CE bedient Live-Datenverkehr.** Dies sind gemeinsam genutzte Demo-Umgebungen. Gehen Sie davon aus, dass jemand gerade von der Site präsentiert, die Sie debuggen.

## Was hier dokumentiert ist

Jeder Befehl, der über die Debug-API des Software-Builds erreichbar ist, den dieser Tenant ausführt,
jeweils mit Ausgabe, die von einem Live-Knoten erfasst wurde und nicht aus anderen Quellen übertragen.

Die [Befehlsreferenz](./commands/) listet alle davon mit ihrer Kategorie, Berechtigungsstufe und Transport auf; die [Workflows](./workflows/) verknüpfen sie zu den Abfolgen, die tatsächlich benötigt werden, wenn etwas nicht stimmt.

Die ausschließlich auf dem Gerät verfügbaren Teile der Site CLI — `configure`, `configure-network`,
`factory-reset`, `upgrade` und etwa sechzig weitere `ExecCLI`-Befehle — sind nicht
abgedeckt.

Sie sind nur über eine serielle Konsolensitzung erreichbar, weshalb nichts daran programmatisch
verifiziert werden kann — und nicht verifizierte Befehlssyntax ist genau der Fehler, dessen Wiederholung diese Dokumentation vermeiden soll.
