Ein Customer Edge (CE) ist der F5 Distributed Cloud Knoten, den dieses Repository in
Azure bereitstellt — `terraform/modules/ce-node`, erstellt aus dem
Marktplatz-Image `volterraedgeservices/volterra-node`.

Er betreibt die Datenebene (Argo), die Steuerungsebene (Vega), einen Envoy-Proxy, einen
Kubernetes-Stack sowie `vpm`, den Agenten, der den Knoten registriert und alles Weitere
darauf verwaltet.

Wenn ein CE sich fehlerhaft verhält, ist die Site CLI das Instrument. Die erste
Entscheidung ist, welcher Zugriffsweg zutrifft, und ein Fehler dabei kostet Zeit auf
eine Weise, die wie ein defekter Knoten aussieht.

## Zwei Zugriffswege, die nicht austauschbar sind

  <LinkCard

  />
  <LinkCard
    title="Serial console"

Die Debug-API erreicht den Knoten **über die F5 Distributed Cloud Steuerungsebene**.
Genau darin liegt die Bedeutung dieser Unterscheidung: Die API kann erst antworten,
wenn der Knoten registriert ist und `ONLINE` meldet.

Ein Knoten, dessen Registrierung fehlgeschlagen ist — fehlerhaftes cloud-init, ein
abgelaufenes Token, keine Route zu `register.ves.volterra.io` — ist genau der Fall, in
dem Sie Diagnose benötigen, und genau der Fall, den die API nicht bedienen kann.

SSH ist keine dritte Option. `sshd` läuft auf dem Knoten und antwortet auf seiner
internen (SLI-)Adresse, aber das `admin`-Konto kann sich nicht authentifizieren: `vpm`
überspringt diesen Benutzer, sodass der `ssh_key`, den Sie am Site-Objekt konfigurieren,
niemals angewendet wird. Keine Sicherheitsgruppenregel ändert das. Die Belege finden
sich auf der [SSH](./access/ssh/)-Seite, die existiert, weil jedes dortige Symptom wie
ein Firewall- oder Anmeldedatenfehler aussieht.

Also: Wenn die Site `ONLINE` ist, verwenden Sie die Debug-API. Wenn nicht, ist die
serielle Konsole der einzige Weg hinein.

<Aside type="caution" title="Prüfen Sie zuerst den Site-Zustand">
Eine Anfrage sagt Ihnen, auf welchem Weg Sie sich befinden:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/config/namespaces/system/sites/<site>" \
  | jq -r '.spec.site_state'
```

`ONLINE` bedeutet, dass die Debug-API funktioniert. Alles andere — oder eine Site, die
nicht existiert — bedeutet serielle Konsole.
</Aside>

## Sicherheitsregeln

Diese gelten für jeden Befehl auf jeder der folgenden Seiten.

- **Nur lesend, sofern Sie nicht ganz sicher sind.** Die Befehlsoberfläche ist in zwei
  Berechtigungsebenen unterteilt, und die `Exec`-Ebene verändert entweder den Knoten oder
  liest einen Zustandsmarker. Nichts auf diesen Seiten führt einen `Exec`-Befehl aus, und
  das Capture-Harness ebenfalls nicht.
- **Gehen Sie niemals davon aus, dass ein Befehl anhand seines Namens sicher ist.**
  `ip-link-set` liest sich wie eine Abfrage und schaltet eine Schnittstelle ab.
  `systemctl-restart-crio` startet die Container-Laufzeitumgebung unter einer laufenden
  Datenebene neu.
- **Bevorzugen Sie den engsten Befehl, der die Frage beantwortet.** `health` und
  `diagnosis` fassen den Knoten kostengünstig zusammen; `flow-l` gibt eine Flow-Tabelle
  mit 629.760 Einträgen aus.
- **Ein CE bedient echten Datenverkehr.** Dies sind gemeinsam genutzte
  Demo-Umgebungen. Gehen Sie davon aus, dass jemand von der Site präsentiert, die Sie
  gerade debuggen.

## Was hier dokumentiert ist

Jeder über die Debug-API erreichbare Befehl auf dem Software-Build, den dieser Tenant
betreibt, jeweils mit Ausgaben, die von einem laufenden Knoten erfasst und nicht von
anderswo übernommen wurden.

Die [Befehlsreferenz](./commands/) listet sie alle mit ihrer Kategorie,
Berechtigungsebene und Transportart auf; die [Workflows](./workflows/) verketten sie zu
den Abläufen, die Sie tatsächlich verwenden, wenn etwas nicht stimmt.

Die ausschließlich auf dem Gerät verfügbaren Teile der Site CLI — `configure`,
`configure-network`, `factory-reset`, `upgrade` und rund sechzig weitere
`ExecCLI`-Befehle — werden nicht behandelt.

Sie sind nur aus einer Sitzung über die serielle Konsole erreichbar, sodass sich nichts
daran programmatisch überprüfen lässt, und nicht verifizierte Befehlssyntax ist genau
der Fehler, dessen Wiederholung diese Dokumentation vermeiden soll.
