Ein Customer Edge (CE) ist der F5 Distributed Cloud Knoten, den dieses Repository in
Azure bereitstellt — `terraform/modules/ce-node`, erstellt aus dem
Marktplatz-Image `volterraedgeservices/volterra-node`.

Er betreibt die Datenebene (Argo), die Steuerebene (Vega), einen Envoy-Proxy, einen
Kubernetes-Stack sowie `vpm`, den Agenten, der den Knoten registriert und alles Weitere
darauf verwaltet.

Wenn sich ein CE fehlerhaft verhält, ist die Site CLI das Instrument. Die erste
Entscheidung ist, welcher Zugriffsweg gilt, und eine falsche Wahl kostet Zeit auf eine
Weise, die wie ein defekter Knoten aussieht.

## Zwei Zugriffswege, und sie sind nicht austauschbar

  <LinkCard

Die Debug-API erreicht den Knoten **über die F5 Distributed Cloud Steuerebene**.
Genau darum ist diese Unterscheidung wichtig: Die API kann erst antworten, sobald sich
der Knoten registriert hat und `ONLINE` meldet.

Ein Knoten, dessen Registrierung fehlgeschlagen ist — fehlerhaftes cloud-init, ein
abgelaufenes Token, keine Route zu `register.ves.volterra.io` — ist genau der Fall, in
dem Sie Diagnose benötigen, und genau der Fall, den die API nicht bedienen kann.

[SSH](./access/ssh/) ist die dritte Option und die einzige, die die vollständige
Befehlsoberfläche der Appliance erreicht — die Debug-API stellt 34 Befehle bereit, der
Knoten selbst bietet weit mehr. Zwei Dinge schränken sie ein. `sshd` antwortet
ausschließlich auf der internen (SLI) Adresse des Knotens, benötigt also einen Host
innerhalb des VNet; und der Schlüssel wird beim ersten Start von cloud-init geschrieben,
denn das Feld `ssh_key` am Site-Objekt ist wirkungslos — `vpm` überspringt den Benutzer
`admin` und wendet es nie an. Die Aktivierung auf laufenden Knoten ersetzt diese daher.

Also: Wenn die Site `ONLINE` ist und 34 Befehle genügen, verwenden Sie die Debug-API.
Wenn Sie den Rest der Oberfläche benötigen und das VNet erreichen können, verwenden Sie
SSH. Wenn die Registrierung das Problem ist, ist die serielle Konsole der einzige Zugang.

<Aside type="caution" title="Prüfen Sie zuerst den Site-Status">
Eine einzige Anfrage sagt Ihnen, auf welchem Weg Sie sind:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/config/namespaces/system/sites/<site>" \
  | jq -r '.spec.site_state'
```

`ONLINE` bedeutet, dass die Debug-API funktioniert. Alles andere — oder eine Site, die
nicht existiert — bedeutet serielle Konsole.
</Aside>

## Sicherheitsregeln

Diese gelten für jeden Befehl auf jeder nachfolgenden Seite.

- **Schreibgeschützt, sofern Sie nicht sicher sind.** Die Befehlsoberfläche ist in zwei
  Berechtigungsstufen unterteilt, und die Stufe `Exec` verändert entweder den Knoten oder
  liest einen Statusmarker. Nichts auf diesen Seiten führt einen `Exec`-Befehl aus, und
  das Capture-Harness ebenso wenig.
- **Gehen Sie nie davon aus, dass ein Befehl aufgrund seines Namens sicher ist.**
  `ip-link-set` liest sich wie eine Abfrage und legt eine Schnittstelle still.
  `systemctl-restart-crio` startet die Container-Laufzeitumgebung unter einer aktiven
  Datenebene neu.
- **Bevorzugen Sie den engsten Befehl, der die Frage beantwortet.** `health` und
  `diagnosis` fassen den Knoten kostengünstig zusammen; `flow-l` gibt eine Flow-Tabelle
  mit 629.760 Einträgen aus.
- **Ein CE bedient produktiven Datenverkehr.** Dies sind gemeinsam genutzte
  Demo-Umgebungen. Gehen Sie davon aus, dass jemand von der Site präsentiert, die Sie
  gerade debuggen.

## Was hier dokumentiert ist

Jeder über die Debug-API erreichbare Befehl des Software-Builds, den dieser Tenant
betreibt, jeweils mit Ausgaben, die von einem Live-Knoten erfasst und nicht von
anderswo übernommen wurden.

Die [Befehlsreferenz](./commands/) listet sie alle mit Kategorie, Berechtigungsstufe und
Transport auf; die [Workflows](./workflows/) verketten sie zu den Abläufen, die Sie
tatsächlich verwenden, wenn etwas nicht stimmt.

Die nur auf dem Gerät verfügbaren Teile der Site CLI — `configure`, `configure-network`,
`factory-reset`, `upgrade` und rund sechzig weitere `ExecCLI`-Befehle — werden nicht
behandelt, weil ihre Ausgabe nicht so von einem Live-Knoten erfasst wurde wie bei jeder
nachfolgenden Seite.

Sie sind jedoch nicht länger unerreichbar. `scripts/sitecli_ssh_harvest.py` steuert das
Vervollständigungsmenü der Appliance über [SSH](./access/ssh/) und zeichnet die
Beschreibung auf, die die Appliance für jeden Befehl liefert, sodass die Oberfläche
gemessen statt erraten werden kann. Die Ausführung ist standardmäßig verweigert — das
Skript zählt alles auf und führt nur eine Allow-List aus —, denn ungeprüfte Befehlssyntax
und ungeprüfte Befehls*wirkungen* sind genau der Fehler, dessen Wiederholung diese
Dokumentation vermeiden soll.
