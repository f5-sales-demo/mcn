Ein Customer Edge (CE) ist der F5 Distributed Cloud-Knoten, den dieses Repository in
Azure bereitstellt – `terraform/modules/ce-node`, erstellt aus dem
`volterraedgeservices/volterra-node` Marktplatz-Image.

Er führt die Datenebene (Argo), die Steuerungsebene (Vega), einen Envoy-Proxy, einen Kubernetes-
Stack sowie `vpm` aus – den Agenten, der den Knoten registriert und alles weitere darauf
verwaltet.

Wenn ein CE Fehlfunktionen aufweist, ist die Site CLI das geeignete Werkzeug. Die erste Entscheidung besteht darin, welcher Zugriffspfad gilt – eine falsche Wahl kostet Zeit auf eine Weise, die wie ein defekter Knoten aussieht.

## Zwei Zugriffspfade, die nicht austauschbar sind

<CardGrid>
  <LinkCard
    title="Debug API"
    description="Für einen Knoten mit dem Status <code>ONLINE</code>. Skriptfähig, schreibgeschützt und umfasst 34 Befehle."
    href="./access/debug-api/"
  />
  <LinkCard
    title="Serielle Konsole"
    description="Für einen Knoten, der sich nie registriert hat. Der einzige Weg, wenn die API nicht antwortet."
    href="./access/serial-console/"
  />
</CardGrid>

Die Debug-API erreicht den Knoten **über die F5 Distributed Cloud-Steuerungsebene**.
Das ist der eigentliche Grund, warum die Unterscheidung wichtig ist: Die API kann erst antworten, wenn sich der Knoten registriert hat und `ONLINE` meldet.

Ein Knoten, der sich nicht registrieren konnte – fehlerhafte Cloud-Init-Konfiguration, ein abgelaufenes Token, keine Route zu
`register.ves.volterra.io` – ist genau der Fall, in dem Sie Diagnosefunktionen benötigen, und gleichzeitig genau der Fall, dem die API nicht bedienen kann.

[SSH](./access/ssh/) ist die dritte Option und die einzige, die die vollständige Befehlsoberfläche des Geräts erreicht – die Debug-API stellt 34 Befehle bereit, während der Knoten selbst viele weitere anbietet. Zwei Einschränkungen bestehen: `sshd` antwortet nur auf der internen Adresse (SLI) des Knotens, sodass ein Host innerhalb des VNet erforderlich ist; und der Schlüssel wird von Cloud-Init beim ersten Start geschrieben, da das Feld `ssh_key` im Site-Objekt wirkungslos ist – `vpm` überspringt den `admin`-Benutzer und wendet ihn nie an. Die nachträgliche Aktivierung auf laufenden Knoten führt daher zu deren Ersatz.

Zusammenfassend gilt: Wenn die Site `ONLINE` ist und 34 Befehle ausreichen, verwenden Sie die Debug-API. Wenn Sie die restliche Oberfläche benötigen und das VNet erreichen können, verwenden Sie SSH. Wenn die Registrierung das Problem ist, ist die serielle Konsole der einzige Zugangsweg.

<Aside type="caution" title="Zuerst den Site-Status prüfen">
Eine Anfrage zeigt Ihnen, auf welchem Pfad Sie sich befinden:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/config/namespaces/system/sites/<site>" \
  | jq -r '.spec.site_state'
```

`ONLINE` bedeutet, dass die Debug-API funktioniert. Jeder andere Status – oder eine Site, die nicht
existiert – bedeutet, dass die serielle Konsole verwendet werden muss.
</Aside>

## Sicherheitsregeln

Diese gelten für jeden Befehl auf jeder der folgenden Seiten.

- **Schreibgeschützt, sofern Sie nicht sicher sind.** Die Befehlsoberfläche ist in zwei
  Berechtigungsstufen unterteilt, und die Stufe `Exec` mutiert entweder den Knoten oder liest einen Zustandsmarker. Keine der Seiten hier führt einen `Exec`-Befehl aus, und das Erfassungs-Harness ebenfalls nicht.
- **Niemals davon ausgehen, dass ein Befehl aufgrund seines Namens sicher ist.** `ip-link-set` klingt wie eine Abfrage und schaltet eine Schnittstelle ab. `systemctl-restart-crio` startet die Container-Runtime unter einer aktiven Datenebene neu.
- **Den engsten Befehl bevorzugen, der die Frage beantwortet.** `health` und
  `diagnosis` fassen den Knoten kostengünstig zusammen; `flow-l` gibt eine Flow-Tabelle mit 629.760 Einträgen aus.
- **Ein CE bedient Live-Datenverkehr.** Dies sind gemeinsam genutzte Demo-Umgebungen. Gehen Sie davon aus, dass jemand von der Site aus präsentiert, die Sie debuggen.

## Was hier dokumentiert ist

Jeder Befehl, der über die Debug-API in dem Software-Build erreichbar ist, auf dem dieser Tenant läuft, jeweils mit einer Ausgabe, die von einem Live-Knoten erfasst wurde und nicht anderswoher übertragen wurde.

Die [Befehlsreferenz](./commands/) listet alle Befehle mit ihrer Kategorie, Berechtigungsstufe und Transportmethode auf; die [Workflows](./workflows/) verketten sie zu den Abläufen, die tatsächlich verwendet werden, wenn etwas nicht stimmt.

Die ausschließlich auf dem Gerät verfügbaren Teile der Site CLI – `configure`, `configure-network`,
`factory-reset`, `upgrade` und rund sechzig weitere `ExecCLI`-Befehle – werden nicht
behandelt.

Sie sind nur über eine serielle Konsolensitzung erreichbar, sodass nichts daran programmatisch überprüft werden kann – und ungeprüfte Befehlssyntax ist genau der Fehler, den diese Dokumentation verhindern soll.
