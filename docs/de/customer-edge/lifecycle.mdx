Zwei Terraform-Variablen legen die Software eines Customer Edge fest: `ce_os_version` für das
Betriebssystem und `ce_sw_version` für den F5 Distributed Cloud-Build. Beide verhalten sich
entgegen der naheliegenden Lesart, und der Preis eines Fehlers ist ein Fleet-Neuaufbau.

## Was die Versionsfelder bewirken – in zwei Phasen

Die Trennung der Phasen ist der eigentliche Kern des Themas. Vermischt man sie, erscheint das
Verhalten widersprüchlich.

**Beim ersten Start installiert ein Knoten das, was `ce_sw_version` benennt.**
`terraform/modules/ce-node` stellt das Marketplace-Image mit `version = "latest"` bereit, der
Build, mit dem ein Knoten ausgeliefert wird, entspricht daher dem, was dieses Image aktuell
enthält – und das ändert sich im Laufe der Zeit. `ce_sw_version` legt das **Ziel** fest, nicht
ob etwas passiert, und ein leeres Feld bedeutet, dass der Server wählt – nicht, dass der Knoten
an Ort und Stelle bleibt. Dasselbe gilt für `ce_os_version`.

Gehen Sie nicht davon aus, dass diese Änderung immer aufwärts gerichtet ist. `Beobachtet
2026-07-28`: Das Image enthielt einen Build mit dem Stempel `20260703-e2c462a` – neuer als der
`crt-20250613-3382` dieses Fleets und neuer als der `crt-20260201-0179`, den der Tenant
anzeigte. **Wird ein älterer Build als der im Image enthaltene angegeben, wird der Knoten
aufgefordert, rückwärts zu wechseln, und das kann fehlschlagen** – siehe den Fehler weiter
unten.

**Danach aktualisiert sich nichts von selbst.** F5 Distributed Cloud bietet einen neueren Build
an und wartet. Ein leeres Feld bedeutet also nicht „neueste Version verfolgen": Der Knoten
verbleibt dort, wo er beim ersten Start gelandet ist.

Beide Phasen sind am Site-Objekt erkennbar. `Beobachtet 2026-07-28` zeigte dieses Fleet:

```text
volterra_software_status.available_version   crt-20260201-0179
operating_system_status.available_version    9.2026.14
```

während die Knoten `crt-20250613-3382` und OS `9.2024.6` ausführten. Ein neuerer Build wird
angeboten und wurde nicht übernommen – das ist der stabile Zustand, kein ins Stocken geratenes
Upgrade.

## Eine Versionsänderung erfordert einen Neuaufbau – Terraform erledigt das nicht für Sie

`ce_os_version` und `ce_sw_version` sind beide **nur bei der Erstellung** wirksam, und der
Fehlermodus ist schlimmer als ein abgelehntes Apply. Im Einzelnen:

1. Sie ändern den Wert und führen Apply aus. Terraform schlägt eine In-place-Aktualisierung vor.
2. Die API **lehnt sie ab** – `[BAD_REQUEST] Invalid request parameters`.
3. Diese abgelehnte Anfrage löscht das Feld trotzdem auf dem Server, und das Read des Providers
   meldet das nicht. Terraforms State stimmt nun nicht mehr mit dem Live-Objekt überein.
4. Jeder folgende Plan schlägt **dieselbe fehlschlagende Änderung** vor, auf unbestimmte Zeit.

Terraform weicht also nicht auf das Ersetzen der Site aus. Es steckt fest und bleibt festgesteckt,
bis Sie die Site und die zugehörige CE-VM bewusst ersetzen. Eine Fleet auf eine andere Version
umzustellen, ist ein **Neuaufbau, den Sie planen**, kein Edit, den Sie einfach anwenden.

<Aside type="danger" title="Alle Konsequenzen des Ersetzens eines CE gelten">
Neue SSH-Host-Keys, neu zugewiesene interne Adressen, eine neue Registrierung und der Verlust
alles dessen, was nur auf dem Knoten existierte. Cloud-init läuft auf der neuen VM erneut, daher
bleibt SSH-Zugang, der auf diesem Weg konfiguriert wurde, erhalten – er läuft jedoch *nur* beim
ersten Start, sodass alles, was manuell zum alten Knoten hinzugefügt wurde, verloren ist.

Lesen Sie [SSH](./access/ssh/) zu den Konsequenzen für Host-Keys und Adressen, bevor Sie diesen
Vorgang einplanen.
</Aside>

<Aside type="note" title="Gemeldet, hier nicht reproduziert">
Die Ablehnung und die State-Divergenz sind in den Kommentaren von `terraform/modules/xc-site`
in diesem Repository dokumentiert – dort in beiden Richtungen verifiziert, sowohl beim Pinnen
als auch beim Entpinnen, auf allen drei Sites – sowie gegen Provider-Issue `xcsh#1387`. Diese

</Aside>

## Ein gepinnter Build kann fehlschlagen, und die Site steckt dann fest

Die Annahme des Pins ist nicht dasselbe wie dessen Installation. Auf einem neu erstellten
Single-Node Azure Secure Mesh v2 Customer Edge, der auf `crt-20260201-0179` gepinnt war,
meldete das Site-Objekt die gepinnte Version sofort – und die Installation schlug dann fehl:

```text
site_state        PROVISIONING
phase             UPGRADE_FAILED
result            Failed
last_installed    (empty)
message           stage: 10, app: voucher obj: voucher objKind: DaemonSet failed ...
                  required replicas: 1, current replicas: 0
```

`Beobachtet 2026-07-28.` Der **Betriebssystem**-Pin wurde im selben Durchlauf normal
installiert (`9.2024.6` auf `9.2026.14`, `UPGRADE_COMPLETED`); nur die Software-Installation
schlug fehl. Die Site erreichte nie `ONLINE`, und `last_installed_version` blieb leer, sodass
kein Rollback auf einen funktionierenden Build stattfand – es gab keine frühere erfolgreiche
Installation, auf die hätte zurückgerollt werden können.

**Was daraus folgt.** Dass eine Version anderswo läuft, ist kein Beweis dafür, dass sie sich auf
der Topologie Ihrer Site installiert. Derselbe Build war `ONLINE` auf einem Azure Customer Edge,
der kein Secure Mesh v2 war, und auf einer Secure Mesh v2 Site auf VMware; die Kombination, die
fehlschlug, war Azure *und* Secure Mesh v2. Testen Sie eine Versionsänderung auf einer
wegwerfbaren Site, bevor Sie sie auf einen Fleet anwenden, denn ein Fleet, der auf diese Weise
fehlschlägt, steckt in `PROVISIONING` fest, und Neuerstellen ist der einzige Ausweg.

<Aside type="caution" title="Warum diese Seite die Ursache nicht nennt">
Der angeforderte Build war **älter** als der, den das Marketplace-Image enthielt, sodass der
Knoten aufgefordert wurde, rückwärts zu wechseln. Das ist eine plausible Erklärung für den
Fehler, aber sie ist **nicht** belegt: Die beiden Versionsstrings (`20260703-e2c462a` und
`crt-20260201-0179`) verwenden nachweislich kein gemeinsames Nummerierungsschema, und es stand
keine Aufzeichnung von einem Fleet-Knoten zum Vergleich zur Verfügung. Der Fehler und die
Versionsreihenfolge sind Beobachtungen; die Verbindung zwischen ihnen ist es nicht.
</Aside>

## Welchen Build die Dokumentation beschreibt

Die Befehlsreferenz auf dieser Site beschreibt **`crt-20250613-3382`**, den Build, den dieser
Fleet ausführt. Befehle, die nur auf neueren Builds existieren, sind in
`sitecli/command-classification.json` unter `not_on_this_build` erfasst und separat
dokumentiert, als [Befehle auf neueren Builds](./commands/on-box/newer-builds/), sodass dort
nichts als hier ausführbar erscheint. Siehe auch [On-Box-Befehle](./commands/on-box/).

<Aside type="caution" title="Planen Sie keinen Neuaufbau, nur um neuere Befehle zu erreichen">
Ein neuerer Build wird angeboten, und ob er sich auf dieser Topologie sauber installiert, ist
ungeklärt – es gibt einen Bericht über einen Fehler auf Single-Node Azure Secure Mesh v2 Sites
und eine Gegenbeobachtung eines laufenden Customer Edge. Beides kann anhand dessen, was im
Tenant verbleibt, nicht bestätigt werden.

Da eine Versionsänderung ein Fleet-Neuaufbau ist, ist diese Ungewissheit der entscheidende
Faktor: Betrachten Sie das Erreichen jener Befehle als unbewiesen, nicht als geplantes Upgrade.
Die Belege und das Experiment, das die Frage klären würde, sind in `sitecli/README.md`
festgehalten.
</Aside>
