Es gibt drei Routen, und welche davon gilt, wird durch den Zustand des Knotens und den
Verbindungsort bestimmt — nicht durch persönliche Präferenz.

| Route | Knoten `ONLINE` erforderlich | Netzwerkerreichbarkeit erforderlich | Einschränkungen | Abdeckung |
| --- | --- | --- | --- | --- |
| [Debug-API](./debug-api/) | **ja** | ja | ca. 25–30 Minuten Anlaufzeit bei einer neuen Site | 34 Befehle |
| [SSH](./ssh/) | nein | von innerhalb des VNet, nur zur internen Adresse | Schlüssel muss ab dem ersten Start vorhanden sein | Die vollständige On-Box-Site-CLI |
| [Serielle Konsole](./serial-console/) | nein | nein | eine Sitzung pro VM; 2.048-Zeichen-Einfügegrenze | Die vollständige On-Box-Site-CLI |

Die serielle Konsole ist das letzte Mittel und die einzige Route, die einen Knoten ohne
funktionierenden Netzwerkpfad überlebt.

SSH ist die erste Wahl, wenn die Debug-API nicht ausreicht, da das Gerät wesentlich mehr
Befehle anbietet als die 34, die die API verfügbar macht. Damit sind zwei Kosten verbunden.
Der Schlüssel wird von cloud-init geschrieben und muss daher beim **ersten Start** vorhanden
sein, was bedeutet, dass dessen Aktivierung auf laufenden Knoten diese ersetzt — und dies
derzeit die Registrierung blockiert
([Issue 674](https://github.com/f5-sales-demo/mcn/issues/674)). Und `sshd` antwortet nur
auf der internen Adresse des Knotens, sodass ein Host innerhalb des VNet benötigt wird;
das Prüfen der Ihnen bekannten Knotenaddresse wird stets als geschlossen gemeldet.

## Warum die Aufteilung keine Frage der Präferenz ist

Die Debug-API wird von der F5 Distributed Cloud Control Plane bereitgestellt, die Anfragen
über den Tunnel weiterleitet, den `vpm` während der Registrierung aufbaut. Keine Registrierung
bedeutet keinen Tunnel, was bedeutet, dass die API nichts weiterleiten kann.

Der Fehler äußert sich auf eine wenig hilfreiche statt auf eine offensichtliche Weise, sodass
ein Knoten, der nie hochgefahren ist, wie ein API-Problem aussieht.

Die serielle Konsole geht den entgegengesetzten Weg — durch die Azure-Plattform zum
emulierten seriellen Port des Knotens. Es spielt keine Rolle, ob der Knoten registriert ist,
Netzwerkerreichbarkeit hat oder eine funktionierende Datenebene besitzt. Diese Unabhängigkeit
ist der eigentliche Zweck, und deshalb müssen die Boot-Diagnosen auf den CE-VMs aktiviert
bleiben.

<Aside type="note" title="Was zu verwenden ist">
Wenn Sie eine Automatisierung schreiben oder Belege sammeln, die Sie später erneut ausführen
möchten, verwenden Sie die Debug-API. Wenn die Registrierung das Problem ist, ist die serielle
Konsole kein Fallback — sie ist die einzige Option.
</Aside>

## Anmeldedaten

Beide Routen verwenden unterschiedliche Anmeldedaten, und keine davon gehört in eine
Befehlszeile.

- **Debug-API** — ein F5 Distributed Cloud API-Token als `XCSH_API_TOKEN`, mit der
  Mandanten-URL als `XCSH_API_URL`. Die `xcsh`-Kontextdatei unter
  `~/.config/xcsh/contexts/<tenant>.json` enthält beide, was
  `scripts/capture-sitecli.sh` liest, wenn die Umgebungsvariablen nicht gesetzt sind.
- **Serielle Konsole** — Ihre interaktive Azure-Anmeldung. Es gibt keinen Dienstprinzipal
  dafür: Der F5-Unternehmens-Entra-Mandant erlaubt keine Bereitstellung eines solchen, was
  auch der Grund ist, warum kein Teil davon in CI ausgeführt wird.

<Aside type="danger" title="Übergeben Sie ein Token niemals als Argument">
Ein Token in einer Befehlszeile landet in der Shell-Historie und in der Prozessliste, wo
jeder andere Benutzer auf dem Rechner es lesen kann. `capture-sitecli.sh` lehnt
`--token` aus diesem Grund grundsätzlich ab und übergibt den Header stattdessen über stdin
an `curl`.
</Aside>
