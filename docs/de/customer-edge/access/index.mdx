Drei Wege funktionieren, und welcher davon zutrifft, entscheidet sich anhand des Zustands des Knotens und des Orts, von dem aus Sie sich verbinden, und nicht anhand einer Vorliebe.

| Weg | Erfordert Knoten `ONLINE` | Erfordert Netzwerkerreichbarkeit | Grenzen | Umfang |
| --- | --- | --- | --- | --- |
| [Debug-API](./debug-api/) | **ja** | ja | etwa 25–30 Minuten Aufwärmzeit bei einer neuen Site | 34 Befehle |
| [SSH](./ssh/) | nein | von innerhalb des VNet, nur zur internen Adresse | Schlüssel muss ab dem ersten Start vorhanden sein | Die vollständige lokale Site-CLI |
| [Serielle Konsole](./serial-console/) | nein | nein | eine Sitzung pro VM; Einfügegrenze von 2.048 Zeichen | Die vollständige lokale Site-CLI |

Die serielle Konsole ist das letzte Mittel und der einzige Weg, der einen Knoten ohne funktionierenden Netzwerkpfad übersteht.

SSH ist die Wahl, wenn die Debug-API nicht ausreicht, denn das Gerät bietet erheblich mehr Befehle als die 34, die diese API bereitstellt. Das hat zwei Kosten. Der Schlüssel wird von cloud-init geschrieben und muss daher beim **ersten Start** vorhanden sein, was bedeutet, dass die Aktivierung auf laufenden Knoten diese ersetzt — und das blockiert derzeit die Registrierung ([Issue 674](https://github.com/f5-sales-demo/mcn/issues/674)). Und `sshd` antwortet ausschließlich auf der internen Adresse des Knotens, es wird also ein Host innerhalb des VNet benötigt; das Prüfen der Adresse, unter der Sie den Knoten kennen, meldet stets „geschlossen".

## Warum die Aufteilung keine Vorliebe ist

Die Debug-API wird von der F5 Distributed Cloud Control Plane bereitgestellt, die über den Tunnel weiterleitet, den `vpm` während der Registrierung aufbaut. Keine Registrierung bedeutet kein Tunnel, was bedeutet, dass die API nichts hat, wohin sie weiterleiten könnte.

Der Fehlschlag erfolgt auf wenig hilfreiche statt auf offensichtliche Weise, sodass ein Knoten, der nie hochgekommen ist, wie ein API-Problem aussieht.

Die serielle Konsole geht den völlig anderen Weg — über die Azure-Plattform zum emulierten seriellen Anschluss des Knotens. Es spielt keine Rolle, ob sich der Knoten registriert hat, Netzwerkerreichbarkeit besitzt oder eine funktionierende Data Plane hat. Genau diese Unabhängigkeit ist der Sinn der Sache, und deshalb muss die Startdiagnose auf den CE-VMs aktiviert bleiben.

<Aside type="note" title="Wozu greifen">
Wenn Sie Automatisierung schreiben oder Belege sammeln, die Sie später erneut ausführen möchten, verwenden Sie die Debug-API. Wenn die Registrierung das ist, was nicht funktioniert, ist die serielle Konsole kein Ausweichweg — sie ist die einzige Option.
</Aside>

## Anmeldedaten

Jeder Weg verwendet andere Anmeldedaten, und keine davon gehört auf eine Befehlszeile.

- **Debug-API** — ein F5 Distributed Cloud API-Token als `XCSH_API_TOKEN`, mit der Mandanten-URL als `XCSH_API_URL`. Die `xcsh`-Kontextdatei unter `~/.config/xcsh/contexts/<tenant>.json` enthält beides, und genau das liest `scripts/capture-sitecli.sh`, wenn die Umgebung sie nicht bereitstellt.
- **SSH** — die private Hälfte des Schlüsselpaars, dessen öffentliche Hälfte die Bereitstellung beim ersten Start in `/var/home/admin/.ssh/authorized_keys` geschrieben hat, sowie ein Host innerhalb des VNet, über den die interne Adresse erreicht wird. Verbinden Sie sich als `admin`, nicht als `azureuser`.
- **Serielle Konsole** — Ihre interaktive Azure-Anmeldung. Es gibt dafür keinen Dienstprinzipal: Der Entra-Mandant des F5-Konzerns erlaubt keine Bereitstellung eines solchen, weshalb auch kein Teil davon in CI läuft.

<Aside type="danger" title="Übergeben Sie ein Token niemals als Argument">
Ein Token auf einer Befehlszeile landet im Shell-Verlauf und in der Prozessliste, wo jeder andere Benutzer auf dem Rechner es lesen kann. `capture-sitecli.sh` verweigert aus diesem Grund `--token` grundsätzlich und übergibt den Header stattdessen über stdin an `curl`.
</Aside>
