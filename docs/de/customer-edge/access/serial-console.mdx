Die serielle Azure-Konsole verbindet sich mit dem emulierten seriellen Port des Knotens über die Azure-Plattform. Sie durchläuft weder die F5 Distributed Cloud-Steuerungsebene, die Datenebene des Knotens noch einen vom Knoten kontrollierten Netzwerkpfad — genau deshalb funktioniert sie, wenn alles andere versagt.

Verwenden Sie sie, wenn ein CE **nie hochgekommen ist**: Die Registrierung ist fehlgeschlagen, die Site fehlt im Tenant, oder der Knoten ist zwar aktiv, hat aber keine Route nach außen. In all diesen Fällen hat die [Debug-API](../debug-api/) keinen Tunnel, über den sie weiterleiten könnte. [SSH](../ssh/) überlebt eine fehlgeschlagene Registrierung, aber nur, wenn der Schlüssel bereits beim ersten Start geschrieben wurde und Sie die interne Adresse des Knotens von innerhalb des VNet erreichen können — beides trifft auf einen Knoten, den Sie zum ersten Mal einrichten, nicht zu.

## Voraussetzung: Boot-Diagnose

Azure erfordert Boot-Diagnosen auf der VM, bevor eine serielle Konsole angehängt werden kann. Dies wird durch `terraform/modules/ce-node` aktiviert:

```hcl
boot_diagnostics {}
```

Ein leerer Block wählt Azure-verwalteten Speicher, sodass kein Diagnosespeicherkonto, keine Lebenszyklusrichtlinie und kein Zugriffsschlüssel verwaltet werden müssen. Auf einem Knoten bestätigen:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="Die Aktivierung wirkt nicht rückwirkend">
Die Boot-Diagnose erfasst das serielle Protokoll **beim Start**. Das Aktivieren für eine bereits laufende VM erzeugt kein Protokoll für den bereits erfolgten Start, sodass `az vm boot-diagnostics get-boot-log` folgendes zurückgibt:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

Das ist zu erwarten und kein Fehler. Ein Startprotokoll ist verfügbar, nachdem der Knoten das nächste Mal neu gestartet wurde. Das direkte Anhängen der Konsole funktioniert jedoch sofort — es hängt nicht vom Protokoll ab.
</Aside>

## Verfügbarkeit ohne Terminal prüfen

Das Anhängen erfordert eine interaktive Sitzung, aber ob es *möglich wäre* anzuhängen, lässt sich mit zwei API-Aufrufen prüfen. Beide sind in einer Zustandsprüfung nützlich.

Der Dienst muss für das Abonnement aktiviert sein — ein Administrator kann ihn mandantenweit deaktivieren:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

Dann eine Verbindung zum seriellen Port eines bestimmten Knotens anfordern:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

Eine `connectionString`, die mit `wss://` beginnt — in dieser Bereitstellung `eastus.gateway.serialconsole.azure.com` — bedeutet, dass die Konsole jetzt angehängt werden kann. Bevor die Boot-Diagnose aktiviert war, hatte dieser Aufruf nichts, woran er sich hätte anhängen können.

<Aside type="danger" title="Diese Verbindungszeichenfolge ist ein Anmeldedatum">
Es handelt sich um ein kurzlebiges Bearer-Token, das in eine URL eingebettet ist. Protokollieren Sie es nicht, fügen Sie es nicht in ein Ticket ein und committen Sie es nicht. Geben Sie beim Demonstrieren nur den Host aus, wenn Sie zeigen möchten, dass der Aufruf funktioniert hat.
</Aside>

## Anhängen

<Steps>

1. Die Erweiterung einmalig installieren:

   ```bash
   az extension add --name serial-console
   ```

2. Anhängen:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. Sie gelangen zur eigenen Anmeldeaufforderung des Knotens, nicht zu einer Shell. Dies ist die Site-CLI, die Anmeldedaten auf dem Knoten erfordert — das Administratorpasswort aus der Bereitstellung oder eines, das über den Endpunkt zur Passwortänderung gesetzt wurde. Die serielle Konsole beweist, dass der *Kanal* funktioniert; sie umgeht die Authentifizierung nicht.

</Steps>

Aufgezeichnet von `f5-xc-ce-vm-01`, in der Mitte gekürzt, wo die systemd-Einheitsausgabe nichts Wesentliches enthält:

```text file=../../../_data/serial-console-boot.txt
```

Vier Dinge in diesem Protokoll sind es wert, beachtet zu werden, weil sie Fragen beantworten, die die Debug-API nicht beantworten kann:

- **cloud-init abgeschlossen** — `Datasource DataSourceAzure`, abgeschlossen nach 22,37 Sekunden. Ein Knoten, der sich nie registriert, ist meist hier fehlgeschlagen, und hier sieht man es.
- **Beide Container-Laufzeiten wurden gestartet.** `Container Runtime Interface for OCI (CRI-O)` und `Docker Application Container Engine` zeigen jeweils `[ OK ]`, was der startzeit-Beweis für das Dual-Runtime-Verhalten ist, das bei [crictl](../../commands/system/crictl/) und [docker](../../commands/system/docker/) für Überraschung sorgt.
- **`VP Manager image load` und `Argo Watch service`** — `vpm` und Argo starten.
- **Die Aufforderung gehört zum Knoten selbst**, hinter seinem Audit-Banner. Die serielle Konsole liefert eine Anmeldeaufforderung, keine Sitzung.

<Aside type="caution" title="Das interaktive Anhängen erfordert ein echtes Terminal — kann aber per Skript automatisiert werden">
`az serial-console connect` versetzt das Terminal in den Raw-Modus, sodass es nicht aus einer Pipeline oder einem Kontext ohne TTY heraus ausgeführt werden kann. Es schlägt auf der Client-Seite fehl, bevor Azure kontaktiert wird:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

Dieser Traceback betrifft die Terminal-Verarbeitung, nicht einen Ausfall der seriellen Konsole.

Das Anhängen selbst ist jedoch **automatisierbar** — treiben Sie den WebSocket direkt an, anstatt die CLI zu verwenden. Das obige Protokoll wurde auf diese Weise aufgezeichnet, ohne TTY. Siehe `scripts/serial_console_capture.py`, mit dem Sie Startnachweise von einem Knoten sammeln können, der sich nicht registriert hat, ohne dass ein Mensch am Terminal sitzt.
</Aside>

<Aside type="caution" title="Wiederholungsversuche einplanen: Das Gateway lehnt etwa jeden zweiten Versuch ab">
Das erste Frame des Gateways ist eine Challenge, keine Ausgabe, und der Client beantwortet sie mit einem Bearer-Token. Selbst wenn das korrekt durchgeführt wird, schließt sich der Socket häufig sofort:

```
[close] code=1011 reason=Connection not trusted
```

Beobachtetes Verhalten: Es gelingt sporadisch, und bei dauerhafter Nutzung verweigert jeder Knoten in der Ressourcengruppe den Zugriff — einschließlich Knoten, die wenige Minuten zuvor noch funktionierten. `scripts/serial_console_capture.py` wiederholt den Versuch standardmäßig, da Wiederholungen häufig zum Erfolg führen.

**Die Ursache ist nicht geklärt.** Was ausgeschlossen wurde, weil es eine plausible Vermutung ist, die Zeit kostet:

| Nicht das | Bestätigung |
| --- | --- |
| ARM/Compute-Drosselung | Dabei wird HTTP `429` bei ARM-Aufrufen zurückgegeben. Hier handelt es sich um ein WebSocket-Schließen auf einem separaten Datenkanal. |
| TLS-Abfangung durch einen Proxy | `openssl s_client -connect <region>.gateway.serialconsole.azure.com:443 \| openssl x509 -noout -issuer`. Ein echter `O=Microsoft Corporation`-Aussteller schließt es aus; ein Proxy-Anbieter als Aussteller bestätigt es, und die Lösung ist, `*.serialconsole.azure.com` auf die Zulassungsliste zu setzen. |
| Boot-Diagnose deaktiviert | `az vm show -g <rg> -n <vm> --query diagnosticsProfile` meldet `enabled: true`. |
| Token-Nichtübereinstimmung zwischen Grant und Challenge | Die Verwendung eines Tokens für beides ist die korrekte Vorgehensweise, verhindert aber das Schließen nicht. |

Was *dokumentiertes* Azure-Verhalten ist: **eine serielle Konsolensitzung pro VM, und eine zweite erfolgreiche Anforderung verdrängt die erste.** Der verdrängte Benutzer wird getrennt, aber nicht abgemeldet, sodass die Shell-Sitzung weiterbesteht. Zwei Personen, die denselben Knoten debuggen, werden sich gegenseitig wiederholt verdrängen.

Für umfangreiche Arbeiten bevorzugen Sie die [Debug-API](../debug-api/) oder [SSH](../ssh/), die keine dieser Einschränkungen aufweisen. SSH hat insbesondere keine Einfügeobergrenze und keine Einzelsitzungsbeschränkung und ist daher die bessere Wahl, wenn der Knoten von innerhalb des VNet erreichbar ist.
</Aside>

<Aside type="caution" title="Die Einfügemenge ist auf 2.048 Zeichen begrenzt">
Azure begrenzt die Einfügelänge der seriellen Konsole auf 2.048 Zeichen, um eine Überlastung des seriellen Ports zu vermeiden. Das Senden eines langen Befehls — oder einer Gruppe von Befehlen in einem einzigen Schreibvorgang — schlägt auf eine Weise fehl, die wie ein Hänger oder eine Drosselung aussieht, nicht wie eine Längenbeschränkung.

Senden Sie Befehle einzeln. Dies ist eine echte Einschränkung bei jeder umfangreichen Sammlung über die serielle Konsole und ein weiterer Grund, für diese Arbeit die [Debug-API](../debug-api/) zu bevorzugen.
</Aside>

## Was hier sichtbar ist, was die API nicht zeigen kann

- **cloud-init** läuft, schlägt fehl oder startet nie — der übliche Grund für einen Knoten, der sich nie registriert.
- **Registrierungsversuche** gegen `register.ves.volterra.io`, einschließlich eines Konfigurationsfehlers oder eines vom Tenant abgelehnten Tokens.
- **Kernel- und Startnachrichten** aus der Zeit, bevor ein Agent lief.
- Der Knoten, wenn er **keinen funktionierenden Netzwerkpfad** hat, was jeden anderen Zugangsweg ausschließt.

Für einen Knoten, der `ONLINE` ist, bevorzugen Sie die Debug-API: Sie ist per Skript automatisierbar, liefert Nachweise, die Sie erneut ausführen können, und belegt nicht den einzigen seriellen Port.
