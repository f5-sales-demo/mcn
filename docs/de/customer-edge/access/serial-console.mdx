Die serielle Azure-Konsole verbindet sich über die Azure-Plattform mit dem emulierten
seriellen Port des Knotens. Sie durchquert weder die Steuerungsebene von F5 Distributed
Cloud noch die Datenebene des Knotens oder irgendeinen Netzwerkpfad, den der Knoten
kontrolliert — genau deshalb funktioniert sie, wenn nichts anderes mehr geht.

Greifen Sie darauf zurück, wenn eine CE **nie hochgekommen ist**: Die Registrierung ist
fehlgeschlagen, die Site fehlt im Tenant, oder der Knoten läuft, hat aber keine Route nach
außen. In all diesen Fällen hat die [Debug-API](../debug-api/) keinen Tunnel zum
Weiterleiten, und [SSH kann sich in diesem Build nicht authentifizieren](../ssh/).

## Voraussetzung: Boot-Diagnose

Azure verlangt Boot-Diagnose auf der VM, bevor eine serielle Konsole angebunden wird.
Dies wird durch `terraform/modules/ce-node` aktiviert:

```hcl
boot_diagnostics {}
```

Ein leerer Block wählt von Azure verwalteten Speicher, sodass es kein
Diagnose-Speicherkonto, keine Lebenszyklusrichtlinie und keinen Zugriffsschlüssel zu
verwalten gibt. Prüfen Sie es auf einem Knoten:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="Die Aktivierung wirkt nicht rückwirkend">
Die Boot-Diagnose erfasst das serielle Protokoll **beim Start**. Sie für eine bereits
laufende VM zu aktivieren, erzeugt kein Protokoll für den bereits erfolgten Start, daher
antwortet `az vm boot-diagnostics get-boot-log`:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

Das ist zu erwarten und kein Fehler. Ein Boot-Protokoll existiert nach dem nächsten
Neustart des Knotens. Das Live-Anbinden der Konsole funktioniert jedoch sofort — es
hängt nicht vom Protokoll ab.
</Aside>

## Verfügbarkeit ohne Terminal prüfen

Das Anbinden erfordert eine interaktive Sitzung, aber ob es *anbinden würde*, sind zwei
API-Aufrufe. Beide sind in einer Zustandsprüfung nützlich.

Der Dienst muss für das Abonnement aktiviert sein — ein Administrator kann ihn
tenantweit deaktivieren:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

Fordern Sie dann eine Verbindung zum seriellen Port eines bestimmten Knotens an:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

Ein `connectionString`, der mit `wss://` beginnt — in dieser Bereitstellung
`eastus.gateway.serialconsole.azure.com` — bedeutet, dass die Konsole gerade jetzt
anbindbar ist. Bevor die Boot-Diagnose aktiviert war, hatte dieser Aufruf nichts, woran
er sich anbinden konnte.

<Aside type="danger" title="Diese Verbindungszeichenfolge ist ein Anmeldedatum">
Es handelt sich um ein kurzlebiges Bearer-Token, das in eine URL eingebettet ist.
Protokollieren Sie es nicht, fügen Sie es nicht in ein Ticket ein und committen Sie es
nicht. Geben Sie nur den Host aus, wenn Sie demonstrieren, dass der Aufruf funktioniert
hat.
</Aside>

## Anbinden

<Steps>

1. Installieren Sie die Erweiterung einmalig:

   ```bash
   az extension add --name serial-console
   ```

2. Anbinden:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. Sie landen bei der Anmeldeaufforderung des Knotens selbst, nicht in einer Shell. Dies
   ist die Site-CLI, und sie benötigt auf dem Knoten hinterlegte Anmeldedaten — das
   Administratorkennwort aus der Bereitstellung oder eines, das über den
   Kennwortänderungs-Endpunkt gesetzt wurde. Die serielle Konsole beweist, dass der
   *Kanal* funktioniert; sie umgeht die Authentifizierung nicht.

</Steps>

Aufgezeichnet von `f5-xc-ce-vm-01`, in der Mitte gekürzt, wo die Ausgabe der
systemd-Units nichts beiträgt:

```text file=../../../_data/serial-console-boot.txt
```

Vier Dinge in diesem Mitschnitt sind bemerkenswert, weil sie Fragen beantworten, die die
Debug-API nicht beantworten kann:

- **cloud-init wurde abgeschlossen** — `Datasource DataSourceAzure`, beendet nach 22,37
  Sekunden. Ein Knoten, der sich nie registriert, ist meist hier gescheitert, und genau
  hier sehen Sie es.
- **Beide Container-Laufzeitumgebungen wurden gestartet.** `Container Runtime Interface for OCI (CRI-O)`
  und `Docker Application Container Engine` sind jeweils `[ OK ]`, was der Startzeit-Beleg
  für das Dual-Runtime-Verhalten ist, das Nutzer bei
  [crictl](../../commands/system/crictl/) und [docker](../../commands/system/docker/)
  überrascht.
- **`VP Manager image load` und `Argo Watch service`** — `vpm` und Argo fahren hoch.
- **Die Eingabeaufforderung ist die des Knotens selbst**, hinter seinem Audit-Banner. Die
  serielle Konsole bringt Ihnen eine Anmeldeaufforderung, keine Sitzung.

<Aside type="caution" title="Interaktives Anbinden benötigt ein echtes Terminal — lässt sich aber skripten">
`az serial-console connect` versetzt das Terminal in den Raw-Modus, sodass es nicht aus
einer Pipeline oder einem Kontext ohne TTY heraus laufen kann. Es schlägt clientseitig
fehl, bevor Azure kontaktiert wird:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

Dieser Traceback betrifft die Terminal-Behandlung, nicht einen Ausfall der seriellen
Konsole.

Das Anbinden selbst **ist** jedoch automatisierbar — steuern Sie das Websocket direkt
statt über die CLI. Der obige Mitschnitt wurde auf diese Weise ohne TTY erfasst. Siehe
`scripts/serial_console_capture.py`, womit Sie Startnachweise von einem Knoten sammeln
würden, dessen Registrierung fehlgeschlagen ist, ohne dass ein Mensch an einem Terminal
sitzt.
</Aside>

<Aside type="caution" title="Rechnen Sie mit Wiederholungen: Das Gateway lehnt etwa jeden zweiten Versuch ab">
Der erste Frame des Gateways ist eine Challenge, keine Ausgabe, und der Client beantwortet
sie mit einem Bearer-Token. Selbst wenn das korrekt geschieht, wird das Socket oft sofort
geschlossen:

```
[close] code=1011 reason=Connection not trusted
```

Beobachtetes Verhalten: Es gelingt zeitweise, und bei anhaltender Nutzung verweigern alle
Knoten in der Ressourcengruppe den Zugriff — einschließlich Knoten, die Minuten zuvor
funktioniert haben. `scripts/serial_console_capture.py` wiederholt standardmäßig, weil
Wiederholen häufig funktioniert.

**Die Ursache ist nicht geklärt.** Was ausgeschlossen wurde, weil jede dieser plausiblen
Vermutungen Zeit kostet:

| Nicht das | Wie zu bestätigen |
| --- | --- |
| ARM-/Compute-Drosselung | Diese liefert HTTP `429` bei ARM-Aufrufen. Hier handelt es sich um ein Websocket-Close auf einem separaten Datenkanal. |
| TLS-Interception durch einen Proxy | `openssl s_client -connect <region>.gateway.serialconsole.azure.com:443 \| openssl x509 -noout -issuer`. Ein echter Aussteller `O=Microsoft Corporation` schließt es aus; ein Proxy-Anbieter als Aussteller bestätigt es, und die Lösung ist, `*.serialconsole.azure.com` freizugeben. |
| Boot-Diagnose deaktiviert | `az vm show -g <rg> -n <vm> --query diagnosticsProfile` meldet `enabled: true`. |
| Token-Nichtübereinstimmung zwischen Grant und Challenge | Ein Token für beides zu verwenden ist korrekte Praxis, verhindert das Schließen aber nicht. |

Was *dokumentiertes* Azure-Verhalten ist: **eine serielle Konsolensitzung pro VM, und eine
zweite erfolgreiche Anfrage verdrängt die erste.** Der verdrängte Benutzer wird getrennt,
aber nicht abgemeldet, sodass die Shell-Sitzung erhalten bleibt. Zwei Personen, die einen
Knoten debuggen, verdrängen sich wiederholt gegenseitig.

Für Massenarbeiten bevorzugen Sie die [Debug-API](../debug-api/), die keine dieser
Beschränkungen hat. [SSH ist keine Alternative](../ssh/) — es kann in diesem Build nicht
aktiviert werden.
</Aside>

<Aside type="caution" title="Einfügen ist auf 2.048 Zeichen begrenzt">
Azure begrenzt die Länge beim Einfügen in die serielle Konsole auf 2.048 Zeichen, um eine
Überlastung des seriellen Ports zu vermeiden. Das Senden eines langen Befehls — oder einer
Reihe von Befehlen in einem einzigen Schreibvorgang — schlägt auf eine Weise fehl, die
sich wie ein Hänger oder eine Drosselung liest, nicht wie eine Längenbegrenzung.

Senden Sie Befehle einzeln. Dies ist eine reale Einschränkung jeder Massenerfassung über
die serielle Konsole und ein weiterer Grund, für solche Arbeiten die
[Debug-API](../debug-api/) zu bevorzugen.
</Aside>

## Was Sie hier sehen können, was die API Ihnen nicht zeigen kann

- **cloud-init**, das läuft, fehlschlägt oder nie startet — die übliche Ursache für einen
  Knoten, der sich nie registriert.
- **Registrierungsversuche** gegen `register.ves.volterra.io`, einschließlich eines
  Konfigurationsfehlers oder eines vom Tenant abgelehnten Tokens.
- **Kernel- und Startmeldungen** aus der Zeit, bevor irgendein Agent lief.
- Den Knoten, wenn er **keinen funktionierenden Netzwerkpfad** hat, was jede andere Route
  zunichtemacht.

Für einen Knoten, der `ONLINE` *ist*, bevorzugen Sie die Debug-API: Sie ist skriptfähig,
sie erzeugt Nachweise, die Sie erneut ausführen können, und sie belegt nicht den einzigen
seriellen Port.
