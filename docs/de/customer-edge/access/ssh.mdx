Erfasst am 28.07.2026 von einer CE dieses Deployments. `sitecli/capture-manifest.json`
hält fest, welcher Knoten es war, und `scripts/capture-sitecli.sh --check` prüft die
Befehlsoberfläche erneut gegen eine laufende CE.

SSH erreicht das `admin`-Konto der Appliance, deren Anmelde-Shell die Site CLI
(`/opt/bin/vpmu`) ist. Dies ist der einzige Weg zur **vollständigen Befehlsoberfläche auf dem
Gerät** — die [Debug-API](../debug-api/) stellt 34 Befehle bereit, und die Appliance selbst
bietet viele weitere, die auf dieser API überhaupt nicht vorhanden sind.

```bash
cd terraform
SLI=$(terraform output -json ce_sli_private_ips | jq -r '.eastus01')
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<operator-vm> "admin@$SLI"
```

Jeder Teil dieser Befehlszeile ist tragend, und die nächsten drei Abschnitte erläutern,
welchen Fehler jeder einzelne verhindert.

<Aside type="danger" title="Interne Adresse nachschlagen — niemals eine aus einer früheren Sitzung übernehmen">
Azure weist das interne Subnetz bei jedem Neuaufbau neu zu, und nicht in Knotenreihenfolge. Nach dem
letzten Neuaufbau halten `f5-xc-ce-vm-01`, `-02` und `-03` die Adressen `10.0.3.7`, `10.0.3.5` und `10.0.3.4`; ein
früherer Build hatte sie in völlig anderer Reihenfolge, und die NIC des Testclients liegt im
gleichen Subnetz und hatte bereits eine Adresse, die zuvor eine CE hielt. Eine Verbindung zu einer
erinnerten Adresse landet daher auf dem falschen Knoten, auf einer VM, die keine CE ist, oder nirgendwo — und Letzteres
sieht genauso aus wie „SSH ist nicht aktiviert“.

`terraform output -json ce_sli_private_ips` liefert die Zuordnung. Ohne verfügbaren State ist der
NIC-Name stabil, auch wenn die Adresse es nicht ist:

```bash
az network nic show -g "$(terraform output -raw resource_group_name)" \
  -n "$(terraform output -json ce_vm_names | jq -r '.eastus01')-internal-nic" \
  --query ipConfigurations[0].privateIPAddress -o tsv
```

</Aside>

<Aside type="caution" title="Nur beim Bootstrap — eine bestehende CE kann SSH nicht ohne Neuerstellung erhalten">
cloud-init `write_files` läuft **einmalig, beim ersten Boot**. Danach existiert auf dem Knoten
eine `/etc/cloud/cloud-init.disabled`-Markierung und cloud-init läuft nicht erneut.

Es gibt also keinen Weg, dies an einer laufenden CE nachzurüsten. `custom_data` ist in Azure
nur durch Ersetzen änderbar, was bedeutet, dass die Übernahme dieser Konfiguration in einem bestehenden Deployment
**jede CE-VM ersetzt**. Operator-SSH auf bereits laufenden Knoten zu gewähren, ist ein Neuaufbau, keine
Konfigurationsänderung — und die nächste Warnung beschreibt, was dieser Neuaufbau früher kostete
und warum er es nicht mehr tut.
</Aside>

<Aside type="caution" title="Das Ersetzen einer CE-VM blockierte die Registrierung früher dauerhaft — das ist behoben, und deshalb ist das Site-Objekt an die VM gekoppelt">
Wissenswert, bevor Sie einen Neuaufbau planen, denn die Form des Fehlers erklärt die
Kopplung, die Sie im Plan sehen werden.

Früher behielt die Registrierung des zerstörten Knotens den eindeutigen Index
`(tenant, cluster_name, hostname)` der Control Plane, sodass die Registrierung des Ersatzknotens mit
`UniqueSecondaryIndexViolationError` abgelehnt und endlos wiederholt wurde. Das Löschen der Registrierung reichte
allein nicht aus: ein übrig gebliebenes `StatusObject` gab dann `500` für die Workload-Anfrage zurück,
und zu diesem Zeitpunkt hatte jeder Knoten eine `registration-obj.yml` persistiert, die ihn an die
von Ihnen gelöschte Registrierung band, sodass er auf `404` ohne Selbstheilung in einer Schleife lief. Die Wiederherstellung erforderte
zwei vollständige Neuaufbauten. Die ganze Zeit über meldete `terraform plan` **„No changes“**, denn
aus Sicht von Terraform war der gewünschte Zustand erreicht.

[Issue 674](https://github.com/f5-sales-demo/mcn/issues/674) ist geschlossen, durch
[PR 693](https://github.com/f5-sales-demo/mcn/pull/693). `modules/xc-site` benennt die CE-VM-Instanz
nun in `replace_triggered_by`, sodass das Ersetzen der VM das Site-Objekt ersetzt, und
das Löschen einer Site nimmt ihre Registrierungen mit — der Indexschlüssel ist frei, bevor der
Ersatzknoten bootet. Die Flotte wurde seither von Grund auf neu aufgebaut, und alle drei Sites
kamen ohne Eingriff `ONLINE`.

Die Kopplung ist beobachtbar und nicht bloß angenommen. Jede Site ist an eine VM-*Instanz*-ID gebunden,
und die passende Registrierung meldet denselben Wert als `infra.instance_id`:

```bash
cd terraform && terraform output -json ce_bound_instance_ids
```

Eine Abweichung zwischen beiden bedeutet, dass eine Site noch an einen Knoten gebunden ist, der nicht mehr existiert,
und das ist der Zustand, aus dem sich eine neu aufgebaute CE niemals herausregistrieren kann. Das Auslesen der
Registrierungsseite erfordert weiterhin einen direkten API-Aufruf — Provider-Issue
[1376](https://github.com/f5-sales-demo/terraform-provider-xcsh/issues/1376) würde dies
in die Datenquelle bringen.
</Aside>

## Warum cloud-init den Schlüssel schreibt und nicht die API

`admin_user_credentials.ssh_key` am Site-Objekt sieht genau wie das Feld dafür aus.
Es wird akzeptiert, es übersteht ein Zurücklesen, und es konfiguriert nichts. `vpm` verwaltet die
lokalen Benutzer des Knotens und weigert sich, diesen anzufassen — aus dem eigenen Log des Knotens, dreimal
innerhalb eines einzigen Boots:

```text
vpm  users.go:165: Won't do any change for user admin (internal skip)
```

Alles andere folgt aus dieser einen Zeile. `/var/home/admin/.ssh` existiert nie, weder vor noch
nachdem die Site `ONLINE` erreicht. Das Datum der letzten Änderung im Shadow-Eintrag von `admin` bleibt auf dem
Build-Datum des Images stehen, während `vesbkp` und `vesopcon` das aktuelle Datum zeigen, weil `vpm` diese
beiden gesetzt und `admin` übersprungen hat. Und `vpm` protokolliert zu keinem Zeitpunkt irgendetwas zu `ssh_key`
oder `authorized_keys`.

Die Datei muss also außerhalb von `vpm` geschrieben werden. `admin` hat die uid 2202, fest im Knoten-Image
eingebacken, existiert also bevor cloud-init läuft, und `owner: admin:admin` löst sich zum Schreibzeitpunkt
auf — kein `runcmd`, keine Nachkorrektur der Eigentümerschaft:

```yaml
- path: /var/home/admin/.ssh/authorized_keys
  permissions: "0600"
  owner: admin:admin
  content: |
    ${ssh_public_key}
```

`sshd` war immer dazu bereit. `sshd -T` meldet `pubkeyauthentication yes`, und `admin`
erscheint in `AllowUsers` in beiden `sshd_config`-Dateien, die mit dem Knoten ausgeliefert werden. Es gab
nie etwas zu aktivieren — nur eine fehlende Datei.

<Aside type="danger" title="admin_user_credentials nicht wieder hinzufügen und sshd_config nicht bearbeiten">
`admin_user_credentials` war in `terraform/modules/xc-site` verdrahtet und wurde zurückgenommen, sobald diese
Belege gesammelt waren (#660, PR #663). Es ist keine Lücke, die darauf wartet, gefüllt zu werden.

`sshd_config` wird während der Registrierung ersetzt, sodass eine Änderung daran zum unpassendsten
Zeitpunkt verworfen wird.
</Aside>

## Warum es nur auf einer Adresse antwortet

`sshd` bindet an `0.0.0.0:22`, aber nur die **interne (SLI)** Adresse liegt so im
Host-Netzwerkstack, dass `sshd` darauf antwortet. eth0 wird in `a-i-eth0` umbenannt und trägt überhaupt
keine Host-IP — die Argo-Datenebene besitzt diese Schnittstelle, und die Management-/SLO-Adresse, die sie
sonst getragen hätte, erscheint stattdessen auf `vhost0`. Die anderen beiden NICs bleiben unter ihren
eigenen Namen im Host-Stack.

Von einer VM innerhalb des VNet gegen eine CE geprüft:

```text
management/SLO address    timed out
external address          timed out
internal/SLI address      OPEN     SSH-2.0-OpenSSH_8.7
an unused address         timed out    (control)
```

Eine Prüfung gegen die Adresse, unter der Sie den Knoten kennen, liefert daher genau das, was eine geschlossene
Sicherheitsgruppe liefert. Nichts blockiert etwas; es gibt auf dieser Adresse keinen Listener.

<Aside type="caution" title="Lesen Sie nicht den Gast-Schnittstellennamen, um zu bestimmen, in welchem Subnetz Sie sind">
Welche von `eth1` und `eth2` die interne Adresse trägt, **unterscheidet sich zwischen Knoten desselben
Deployments**. Live von allen drei CEs gelesen:

```text
f5-xc-ce-vm-01    eth1 -> external      eth2 -> internal/SLI
f5-xc-ce-vm-02    eth2 -> external      eth1 -> internal/SLI
f5-xc-ce-vm-03    eth1 -> external      eth2 -> internal/SLI
```

Nur zwei Dinge gelten auf jedem Knoten: `a-i-eth0` hat keine Adresse, und `vhost0` trägt die
Management-/SLO-Adresse. Für alles Übrige richten Sie sich nach der Adresse in der Ausgabe von
[`ip addr`](../../commands/network/ip/) und nicht nach dem Schnittstellennamen.
</Aside>

Die öffentlichen CE-Adressen haben ebenfalls keinen Listener auf 22, weshalb der obige Befehl
über `-J` läuft: eine Operator-VM innerhalb des VNet, im gleichen Subnetz wie die SLI-Adressen.
Dieses Deployment baut eine zu diesem Zweck —
`terraform output -raw client_vm_name` nennt sie.

<Aside type="caution" title="-J übergibt Ihre Optionen nicht an den Jump-Abschnitt">
Auf der Befehlszeile angegebene Optionen gelten für den letzten Hop. `-o UserKnownHostsFile=/dev/null`
neben `-J` konsultiert und beschreibt daher weiterhin Ihre echte `known_hosts` für den *Jump*-Host,
was überrascht, wenn Sie versuchen, eine neu aufgebaute Flotte daraus fernzuhalten. Schreiben Sie den
ersten Hop aus, wenn das wichtig ist:

```bash
ssh -tt -o ProxyCommand="ssh -W %h:%p -o UserKnownHostsFile=/dev/null azureuser@<operator-vm>" \
    -o UserKnownHostsFile=/dev/null -i ~/.ssh/id_ed25519 "admin@$SLI"
```

</Aside>

<Aside type="caution" title="Zwei Messfehler, die selbstbewusst falsche Antworten erzeugen">
Eine Prüfung von eth0, der externen Schnittstelle oder der öffentlichen Adresse auf Port 22 meldet
unabhängig vom SSH-Zustand des Knotens „geschlossen“ und kann Ihnen daher überhaupt nichts sagen. Nur die
SLI-Adresse antwortet.

Und eine Prüfung von einer Firmen-Workstation kann einen Port als **offen** melden, der geschlossen ist:
Netskope vollzieht den TCP-Handshake auf gängigen Ports selbst. Die Ports 80 und 443 erscheinen von einer
Workstation aus auf den öffentlichen CE-Adressen als offen und sind bei einer Prüfung aus dem VNet
geschlossen. Prüfen Sie von einer VM im VNet.
</Aside>

## Die Site CLI braucht ein Terminal und einen Wagenrücklauf

Die Anmelde-Shell von `admin` ist keine Shell. Es ist eine `go-prompt`-Anwendung, die das
Terminal in den Raw-Modus versetzt und Tastenanschläge statt Zeilen liest. Vier Konsequenzen, von denen jede
auf eine Weise fehlschlägt, die wie ein anderes Problem aussieht:

| Mechanik | Was ohne sie passiert |
| --- | --- |
| Ein Terminal zuweisen (`ssh -tt`) | `panic: no such device or address` aus `go-prompt.NewStandardInputParser`, was wie eine abgestürzte Appliance aussieht |
| Für Enter einen Wagenrücklauf senden, keinen Zeilenvorschub | Die Zeile wird nie abgesendet, und die Sitzung schließt am Eingabeende, ohne etwas ausgegeben zu haben |
| Standardeingabe offen halten | Die Verbindung endet, bevor der Befehl gerendert wurde, sodass ein funktionierender Befehl stumm erscheint |
| Befehlstext und Enter-Byte **getrennt** schreiben | Der Zeilenumbruch landet als literales Zeichen im Puffer und die CLI antwortet `unknown command`, was so aussieht, als existiere der Befehl nicht |

`ssh host 'some-command'` funktioniert daher nicht: das Argument wird ignoriert und die
interaktive Eingabeaufforderung startet trotzdem. Steuern Sie es als Terminal oder gar nicht.
`scripts/sitecli_ssh_harvest.py` ist die Referenzimplementierung.

<Aside type="caution" title="Eine Panic mit „no such device or address“ bedeutet, dass die Authentifizierung ERFOLGREICH war">
`vpmu` gibt sie **nach** der Anmeldung aus, wenn es kein Terminal findet, an das es sich anhängen kann. Als Absturz gelesen
sieht sie wie das schlimmstmögliche Ergebnis aus, und tatsächlich ist sie der letzte Fehler vor dem Erfolg. Fügen Sie
`-tt` hinzu und verbinden Sie sich erneut.
</Aside>

<Aside type="caution" title="Das Ersetzen einer CE ändert ihren Host-Schlüssel">
Der Ersatzknoten präsentiert unter derselben Adresse einen anderen Host-Schlüssel, sodass die nächste
Verbindung mit `REMOTE HOST IDENTIFICATION HAS CHANGED` warnt und verweigert wird. Löschen Sie den alten Eintrag
für diese Adresse und verbinden Sie sich neu. Da das Gewähren von SSH die VMs ohnehin ersetzt, ist damit
bei der allerersten Verbindung nach der Einführung zu rechnen.
</Aside>

## Das Banner ist eine kostenlose Zustandsprüfung

Noch bevor Sie etwas eintippen, hat das Anmeldebanner bereits mehrere der Fragen beantwortet, für die Sie
sonst Befehle aufwenden würden. Von `f5-xc-ce-vm-01`, ASCII-Grafik und öffentliche IP ausgelassen:

```text
UNAUTHORIZED ACCESS TO THIS DEVICE IS PROHIBITED
All actions performed on this device are audited

Using https://register.ves.volterra.io
OS: rhel-9.2024.6
Memory: 32768MiB
Storage: sda: 31GiB
CPU: Model: Intel(R) Xeon(R) Platinum 8272CL CPU @ 2.60GHz | CPUs: 8
Software: crt-20250613-3382
DNS: 168.63.129.16: OK
NTP: Synced
Uptime: 0 days, 5 hours, 20 minutes
Registration Status: PROVISIONED
SLO IP: 10.0.1.4/26
WELCOME IN SITE CLI
```

`Registration Status` unterscheidet einen Knoten, der noch hochkommt (`PROVISIONING`), von einem, der
fertig ist (`PROVISIONED`). `Software` ist die Build-Zeichenkette, die entscheidet, welche Befehle existieren.
`DNS` und `NTP` decken die beiden Abhängigkeiten ab, an denen die Registrierung zuerst scheitert, sodass ein Knoten, der
nie online kam, hier meist schon gesagt hat, warum — noch bevor
[`chronyc-sources`](../../commands/network/chronyc-sources/) oder
[`dig`](../../commands/network/dig/) überhaupt nötig sind.

## Das Schlüsselpaar bereitstellen

<Steps>

1. Erzeugen Sie ein Schlüsselpaar, falls Sie noch keines haben. Ed25519 statt RSA: kürzer,
   und vom `sshd` der Appliance akzeptiert.

   ```bash
   ssh-keygen -t ed25519 -C "ce-operator" -f ~/.ssh/id_ed25519
   ```

2. Richten Sie das Deployment auf die **öffentliche** Hälfte aus. Das Root-Modul liest die Datei einmal und
   gibt die Zeichenkette an jeden Knoten weiter:

   ```hcl
   # terraform/terraform.tfvars
   ssh_public_key_path = "~/.ssh/id_ed25519.pub"
   ```

   `ssh_public_key` nimmt das Material stattdessen inline, was die Plan-Tests verwenden.
   Die private Hälfte verlässt Ihre Workstation nie.

3. Anwenden. Lesen Sie zuerst die Warnung am Anfang dieser Seite — in einem bestehenden Deployment
   ersetzt dies die CE-VMs.

</Steps>

<Aside type="note" title="Der eigene admin_ssh_key der VM ist etwas anderes">
`azurerm_linux_virtual_machine.admin_ssh_key` in `modules/ce-node` autorisiert den Azure-VM-Administrator,
nicht das `admin`-Konto der Appliance. Es gewährt keinen Site-CLI-Zugriff, und
dass es gesetzt ist, belegt nicht, dass CE-SSH konfiguriert ist.
</Aside>

## Was dies nicht ist

Jeder dieser Punkte wurde getestet und ausgeschlossen, als der Weg noch als unmöglich galt.
Jeder ist plausibel genug, um einen Tag zu kosten.

| Nicht die Ursache | Wie es ausgeschlossen wurde |
| --- | --- |
| Die Anmeldedaten gelten nur zur Erstellungszeit | `sshd` startet etwa 90 Sekunden nach dem ersten Boot, bevor das Site-Objekt existiert. `admin_user_credentials` ist außerdem in `ReplaceSpecType` vorhanden und wird im laufenden Betrieb angewandt. |
| `block_all_services` | Der geschlossene Port 22 auf der Management-Adresse ist identisch, ob Dienste blockiert sind oder nicht. |
| Ein abschließender Zeilenumbruch am Schlüssel | Beides getestet, keine Änderung. Cloud-init entfernt ihn ohnehin, weil ein literaler Block sonst eine zweite, leere Zeile erzeugen würde. |
| Fixierte, ältere CE-Software | Auf drei Builds reproduziert, darunter einer mit OpenSSH 9.9. |
| Ein fehlendes `admin_password` | Das Setzen von `admin_password` neben `ssh_key` auf einer neu erstellten CE änderte nichts. |

<Aside type="caution" title="Zwei API-Felder, die wie Unterscheidungsmerkmale aussehen und keine sind">
`gc_spec.admin_ssh_key` ist auf **allen 58 Sites in `f5-sales-demo`** leer oder nicht vorhanden — einschließlich
der beiden, die `admin_user_credentials.ssh_key` tatsächlich setzen. Ein Vergleich zwischen einer funktionierenden und einer
nicht funktionierenden Site sagt Ihnen nichts, weil es selbst für die Sites leer ausgelesen wird, bei denen die
Anmeldedaten *konfiguriert sind*.

`registrations_by_site` lässt das Feld ganz weg und gibt `None` dafür zurück, was sich wie
„nicht konfiguriert“ liest und nicht wie „nicht gemeldet“.
</Aside>

<Aside type="caution" title="Eine neu erstellte Site braucht etwa eine halbe Stunde, bevor die Operate-API antwortet">
Für etwa 25 bis 30 Minuten, nachdem eine neue Site `ONLINE` meldet, geben die `vpm/debug`-Endpunkte
eine BIG-IP-`503`-Seite mit dem Text `The requested URL was rejected` zurück. Das sieht wie eine Blockade durch eine
Web Application Firewall oder ein widerrufenes Token aus und ist beides nicht: die Site ist noch nicht bereit,
weiterzuleiten. Warten und erneut versuchen, statt etwas zu ändern.

SSH hat keine solche Aufwärmphase. Es antwortet, sobald `sshd` läuft, und genau deshalb ist es der Weg,
der funktioniert, während sich ein Knoten noch registriert.
</Aside>
