Erfasst am 2026-07-28 von einer CE dieses Deployments. `sitecli/capture-manifest.json`
zeichnet den jeweiligen Knoten auf, und `scripts/capture-sitecli.sh --check` verifiziert die
Befehlsoberfläche erneut gegenüber einer aktiven CE.

SSH erreicht das `admin`-Konto des Geräts, dessen Login-Shell die Site-CLI
(`/opt/bin/vpmu`) ist. Dies ist der einzige Weg zur **vollständigen On-Box-Befehlsoberfläche** — die
[Debug-API](../debug-api/) stellt 34 Befehle bereit, und das Gerät selbst bietet viele weitere,
die in dieser API überhaupt nicht vorhanden sind.

```bash
cd terraform
SLI=$(terraform output -json ce_sli_private_ips | jq -r '.eastus01')
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<operator-vm> "admin@$SLI"
```

Jeder Teil dieser Befehlszeile ist wesentlich, und die nächsten drei Abschnitte erläutern,
welchen Fehler jeder Teil verhindert.

Es gibt keine Shell-Eingabeaufforderung, auf der man landet: Die Login-Shell von `admin` **ist** die Site-CLI, daher gelangt man direkt zur `>>>`-Eingabeaufforderung. Führen Sie dort On-Box-Befehle als `execcli <name>` aus — siehe
[On-Box-Befehle](../../commands/on-box/).

<Aside type="danger" title="Die interne Adresse nachschlagen — niemals eine aus einer früheren Sitzung übernehmen">
Azure weist das interne Subnetz bei jedem Neuaufbau neu zu, und nicht in Knotenreihenfolge. Nach dem
jüngsten Neuaufbau belegen `f5-xc-ce-vm-01`, `-02` und `-03` die Adressen `10.0.3.7`, `10.0.3.5` und `10.0.3.4`; ein
früherer Build hatte sie in einer völlig anderen Reihenfolge, und die NIC des Testclients befindet sich im
selben Subnetz und hat bereits eine Adresse gehalten, die zuvor eine CE innehatte. Die Verbindung zu einer gespeicherten Adresse
landet daher auf dem falschen Knoten, auf einer VM, die keine CE ist, oder nirgendwo — und letzteres
sieht identisch aus wie „SSH ist nicht aktiviert".

`terraform output -json ce_sli_private_ips` ist die Zuordnung. Ohne verfügbaren State ist der NIC-Name
stabil, auch wenn die Adresse es nicht ist:

```bash
az network nic show -g "$(terraform output -raw resource_group_name)" \
  -n "$(terraform output -json ce_vm_names | jq -r '.eastus01')-internal-nic" \
  --query ipConfigurations[0].privateIPAddress -o tsv
```

</Aside>

<Aside type="caution" title="Nur beim Bootstrap — eine vorhandene CE kann SSH nicht ohne Neuerstellen erlangen">
cloud-init `write_files` wird **einmalig beim ersten Start** ausgeführt. Danach existiert ein
`/etc/cloud/cloud-init.disabled`-Marker auf dem Knoten, und cloud-init wird nicht erneut ausgeführt.

Es gibt daher keinen direkten Weg zu einer laufenden CE. `custom_data` ist in Azure nur durch Ersetzen änderbar,
was bedeutet, dass die Übernahme in ein bestehendes Deployment **jede CE-VM ersetzt**. SSH für Betreiber auf bereits
laufenden Knoten zu gewähren ist ein Neuaufbau, keine Konfigurationsänderung — und die nächste Warnung erklärt,
was dieser Neuaufbau früher gekostet hat und warum das nicht mehr der Fall ist.
</Aside>

<Aside type="caution" title="Das Ersetzen einer CE-VM hat die Registrierung früher dauerhaft blockiert — das ist behoben, und deshalb ist das Site-Objekt an die VM gekoppelt">
Es lohnt sich, dies zu wissen, bevor Sie einen Neuaufbau planen, denn die Form des Fehlers erklärt die
Kopplung, die Sie im Plan sehen werden.

Früher behielt die Registrierung des gelöschten Knotens den einzigartigen `(tenant, cluster_name, hostname)`-Index der Steuerungsebene,
sodass die Registrierung des Ersatzknotens mit `UniqueSecondaryIndexViolationError` abgelehnt und endlos wiederholt wurde. Das Löschen der Registrierung war
allein nicht ausreichend: Ein verbliebenes `StatusObject` gab dann `500` für die Workload-Anfrage zurück, und zu diesem Zeitpunkt
hatte jeder Knoten ein `registration-obj.yml` gespeichert, das ihn an die gelöschte Registrierung band, sodass er
in einer `404`-Schleife ohne Selbstwiederherstellung feststeckte. Die Wiederherstellung erforderte zwei vollständige Neuaufbauten. Währenddessen
meldete `terraform plan` **„No changes"**, weil aus Terraforms Sicht der gewünschte Zustand erreicht war.

[Issue 674](https://github.com/f5-sales-demo/mcn/issues/674) ist geschlossen, durch
[PR 693](https://github.com/f5-sales-demo/mcn/pull/693). `modules/xc-site` benennt nun die CE-VM-Instanz
in `replace_triggered_by`, sodass das Ersetzen der VM das Site-Objekt ersetzt und das Löschen einer Site
deren Registrierungen mitnimmt — der Indexschlüssel ist frei, bevor der Ersatzknoten startet. Die Flotte wurde
seitdem von Grund auf neu aufgebaut, und alle drei Sites kamen ohne Eingriff `ONLINE`.

Die Kopplung ist beobachtbar, nicht angenommen. Jede Site ist an eine VM-*Instanz*-ID gebunden,
und die übereinstimmende Registrierung meldet denselben Wert wie `infra.instance_id`:

```bash
cd terraform && terraform output -json ce_bound_instance_ids
```

Eine Abweichung zwischen den beiden bedeutet, dass eine Site noch an einen Knoten gebunden ist, der nicht mehr existiert,
was der Zustand ist, aus dem sich eine neu aufgebaute CE nie herausregistrieren kann. Das Lesen der Hälfte der Registrierung
erfordert noch immer einen direkten API-Aufruf — Provider-Issue
[1376](https://github.com/f5-sales-demo/terraform-provider-xcsh/issues/1376) wäre das, was es in die Datenquelle bringt.
</Aside>

## Warum cloud-init den Schlüssel schreibt und nicht die API

`admin_user_credentials.ssh_key` am Site-Objekt sieht genau wie das Feld dafür aus.
Es wird akzeptiert, übersteht ein Zurücklesen und konfiguriert nichts. `vpm` verwaltet die
lokalen Benutzer des Knotens und lehnt es ab, diesen anzufassen — aus dem eigenen Log des Knotens, dreimal
über einen einzelnen Start:

```text
vpm  users.go:165: Won't do any change for user admin (internal skip)
```

Alles andere folgt aus dieser einen Zeile. `/var/home/admin/.ssh` existiert nie, weder vor
noch nachdem die Site `ONLINE` erreicht. Das `admin`-Shadow-Datum der letzten Änderung bleibt beim
Image-Build-Datum, während `vesbkp` und `vesopcon` das aktuelle Datum zeigen, weil `vpm` diese
beiden gesetzt und `admin` übersprungen hat. Und `vpm` protokolliert nichts über `ssh_key` oder `authorized_keys`
zu irgendeinem Zeitpunkt.

Die Datei muss also außerhalb von `vpm` geschrieben werden. `admin` hat die UID 2202, fest im Node-Image
verankert, sodass es existiert, bevor cloud-init ausgeführt wird, und `owner: admin:admin` beim Schreiben
aufgelöst wird — kein `runcmd`, kein nachträgliches Korrigieren der Eigentümerschaft:

```yaml
- path: /var/home/admin/.ssh/authorized_keys
  permissions: "0600"
  owner: admin:admin
  content: |
    ${ssh_public_key}
```

`sshd` war stets bereit. `sshd -T` meldet `pubkeyauthentication yes`, und `admin`
erscheint in `AllowUsers` in beiden `sshd_config`-Dateien, die mit dem Knoten ausgeliefert werden. Es gab
nie etwas zu aktivieren — nur eine fehlende Datei.

<Aside type="danger" title="admin_user_credentials nicht erneut hinzufügen und sshd_config nicht bearbeiten">
`admin_user_credentials` war in `terraform/modules/xc-site` eingebaut und wurde zurückgesetzt, sobald diese
Belege gesammelt wurden (#660, PR #663). Es ist keine Lücke, die noch gefüllt werden muss.

`sshd_config` wird während der Registrierung ersetzt, sodass eine Bearbeitung zum ungünstigsten Zeitpunkt
verworfen wird.
</Aside>

## Warum es nur auf einer Adresse antwortet

`sshd` bindet `0.0.0.0:22`, aber nur die **interne (SLI)**-Adresse befindet sich im Host-Netzwerk-Stack
in einer Weise, auf die `sshd` antwortet. eth0 wird in `a-i-eth0` umbenannt und trägt überhaupt keine Host-IP —
die Argo-Datenebene besitzt diese Schnittstelle, und die Management-/SLO-Adresse, die sie sonst
getragen hätte, erscheint stattdessen auf `vhost0`. Die anderen beiden NICs verbleiben im Host-Stack unter
ihren eigenen Namen.

Geprüft von einer VM innerhalb des VNet, gegenüber einer CE:

```text
management/SLO address    timed out
external address          timed out
internal/SLI address      OPEN     SSH-2.0-OpenSSH_8.7
an unused address         timed out    (control)
```

Eine Prüfung gegenüber der Adresse, unter der Sie den Knoten kennen, liefert daher genau das gleiche Ergebnis wie
eine geschlossene Sicherheitsgruppe. Es wird nichts blockiert; es gibt keinen Listener auf dieser Adresse.

<Aside type="caution" title="Den Gastschnittstellennamen nicht lesen, um das Subnetz zu ermitteln">
Welche von `eth1` und `eth2` die interne Adresse trägt, **unterscheidet sich zwischen Knoten in diesem selben
Deployment**. Live von allen drei CEs gelesen:

```text
f5-xc-ce-vm-01    eth1 -> external      eth2 -> internal/SLI
f5-xc-ce-vm-02    eth2 -> external      eth1 -> internal/SLI
f5-xc-ce-vm-03    eth1 -> external      eth2 -> internal/SLI
```

Nur zwei Dinge gelten für jeden Knoten: `a-i-eth0` hat keine Adresse, und `vhost0` trägt die
Management-/SLO-Adresse. Für alles andere sollte man anhand der Adresse in der
[`ip addr`](../../commands/network/ip/)-Ausgabe abgleichen, nicht anhand des Schnittstellennamens.
</Aside>

Die öffentlichen CE-Adressen haben auch keinen Listener auf Port 22, weshalb der obige Befehl
`-J` verwendet: eine Betreiber-VM innerhalb des VNet im selben Subnetz wie die SLI-Adressen. Dieses Deployment
erstellt eine zu diesem Zweck —
`terraform output -raw client_vm_name` benennt sie.

<Aside type="caution" title="-J übergibt Ihre Optionen nicht an den Jump-Abschnitt">
Auf der Befehlszeile angegebene Optionen gelten für den letzten Hop. `-o UserKnownHostsFile=/dev/null`
zusammen mit `-J` konsultiert und schreibt daher für den *Jump-Host* weiterhin Ihre echte `known_hosts`,
was die Überraschung ist, wenn Sie versuchen, einen neu aufgebauten Fleet daraus herauszuhalten. Buchstabieren Sie
den ersten Hop aus, wenn das wichtig ist:

```bash
ssh -tt -o ProxyCommand="ssh -W %h:%p -o UserKnownHostsFile=/dev/null azureuser@<operator-vm>" \
    -o UserKnownHostsFile=/dev/null -i ~/.ssh/id_ed25519 "admin@$SLI"
```

</Aside>

<Aside type="caution" title="Zwei Messfehler, die zuverlässig falsche Antworten liefern">
Das Prüfen von eth0, der externen Schnittstelle oder der öffentlichen Adresse auf Port 22 meldet
geschlossen, unabhängig vom SSH-Zustand des Knotens, und kann daher überhaupt keine Aussage treffen. Nur die SLI-Adresse antwortet.

Und eine Prüfung von einem unternehmenseigenen Arbeitsplatz kann einen Port als **offen** melden, der geschlossen ist:
Netskope vervollständigt den TCP-Handshake selbst auf gängigen Ports. Die Ports 80 und 443 werden auf den öffentlichen CE-Adressen von einem Arbeitsplatz als offen angezeigt und sind geschlossen, wenn sie von innerhalb des VNet geprüft werden. Von einer VM im VNet aus prüfen.
</Aside>

## Die Site-CLI benötigt ein Terminal und einen Wagenrücklauf

Die `admin`-Login-Shell ist keine Shell. Es ist eine `go-prompt`-Anwendung, die das
Terminal in den Raw-Modus versetzt und Tastenanschläge statt Zeilen liest. Vier Konsequenzen,
von denen jede auf eine Weise fehlschlägt, die wie ein anderes Problem aussieht:

| Mechanik | Was ohne sie passiert |
| --- | --- |
| Ein Terminal zuweisen (`ssh -tt`) | `panic: no such device or address` von `go-prompt.NewStandardInputParser`, was sich wie ein abgestürztes Gerät liest |
| Einen Wagenrücklauf senden, kein Zeilenvorschub, für Enter | Die Zeile wird nie abgeschickt, und die Sitzung schließt sich beim Ende der Eingabe, ohne etwas ausgegeben zu haben |
| Standardeingabe offen halten | Die Verbindung endet, bevor der Befehl gerendert wurde, sodass ein funktionierender Befehl stumm erscheint |
| Den Befehlstext und das Enter-Byte **separat** schreiben | Der Zeilenumbruch landet als buchstäbliches Zeichen im Puffer und die CLI antwortet mit `unknown command`, was so wirkt, als würde der Befehl nicht existieren |

`ssh host 'some-command'` funktioniert daher nicht: Das Argument wird ignoriert und die
interaktive Eingabeaufforderung startet trotzdem. Als Terminal bedienen oder gar nicht.
`scripts/sitecli_ssh_harvest.py` ist die Referenzimplementierung.

<Aside type="caution" title="Ein Panic mit dem Text 'no such device or address' bedeutet, dass die Authentifizierung ERFOLGREICH war">
`vpmu` gibt ihn **nach** dem Login aus, wenn kein Terminal gefunden wird, an das es sich anhängen kann. Als Absturz gelesen wirkt es wie das schlimmstmögliche Ergebnis, und es ist tatsächlich der letzte Fehler vor dem Erfolg. `-tt` hinzufügen und erneut verbinden.
</Aside>

<Aside type="caution" title="Das Ersetzen einer CE ändert ihren Host-Schlüssel">
Der Ersatzknoten präsentiert einen anderen Host-Schlüssel unter derselben Adresse, sodass die nächste
Verbindung warnt `REMOTE HOST IDENTIFICATION HAS CHANGED` und die Verbindung verweigert. Den alten Eintrag
für diese Adresse löschen und erneut verbinden. Da die Gewährung von SSH die VMs ohnehin ersetzt, ist dies
bei der allerersten Verbindung nach der Übernahme zu erwarten.
</Aside>

## Das Banner ist eine kostenlose Gesundheitsprüfung

Bevor Sie etwas eingeben, hat das Login-Banner bereits mehrere Fragen beantwortet, auf die Sie
sonst Befehle verwenden würden. Von `f5-xc-ce-vm-01`, ASCII-Kunst und öffentliche IP weggelassen:

```text
UNAUTHORIZED ACCESS TO THIS DEVICE IS PROHIBITED
All actions performed on this device are audited

Using https://register.ves.volterra.io
OS: rhel-9.2024.6
Memory: 32768MiB
Storage: sda: 31GiB
CPU: Model: Intel(R) Xeon(R) Platinum 8272CL CPU @ 2.60GHz | CPUs: 8
Software: crt-20250613-3382
DNS: 168.63.129.16: OK
NTP: Synced
Uptime: 0 days, 5 hours, 20 minutes
Registration Status: PROVISIONED
SLO IP: 10.0.1.4/26
WELCOME IN SITE CLI
```

`Registration Status` unterscheidet einen noch startenden Knoten (`PROVISIONING`) von einem
fertig gestarteten (`PROVISIONED`). `Software` ist der Build-String, der festlegt, welche Befehle existieren.
`DNS` und `NTP` decken die beiden Abhängigkeiten ab, die die Registrierung zuerst unterbrechen, sodass ein Knoten,
der nie online kam, hier meist bereits den Grund genannt hat — bevor
[`chronyc-sources`](../../commands/network/chronyc-sources/) oder
[`dig`](../../commands/network/dig/) überhaupt benötigt werden.

## Das Schlüsselpaar bereitstellen

<Steps>

1. Ein Schlüsselpaar erzeugen, falls noch nicht vorhanden. Ed25519 statt RSA: kürzer
   und vom Geräte-`sshd` akzeptiert.

   ```bash
   ssh-keygen -t ed25519 -C "ce-operator" -f ~/.ssh/id_ed25519
   ```

2. Das Deployment auf die **öffentliche** Hälfte hinweisen. Das Stammmodul liest die Datei einmal und
   übergibt den String an jeden Knoten:

   ```hcl
   # terraform/terraform.tfvars
   ssh_public_key_path = "~/.ssh/id_ed25519.pub"
   ```

   `ssh_public_key` nimmt das Material direkt inline entgegen, was die Plan-Tests verwenden.
   Die private Hälfte verlässt niemals Ihren Arbeitsplatz.

3. Anwenden. Die Warnung am Anfang dieser Seite zuerst lesen — bei einem bestehenden Deployment werden die CE-VMs ersetzt.

</Steps>

<Aside type="note" title="Der admin_ssh_key der VM selbst ist eine andere Sache">
`azurerm_linux_virtual_machine.admin_ssh_key` in `modules/ce-node` autorisiert den Azure-VM-Administrator,
nicht das `admin`-Konto des Geräts. Es gewährt keinen Site-CLI-Zugriff, und das Gesetztsein
ist kein Beweis dafür, dass CE-SSH konfiguriert ist.
</Aside>

## Was dies nicht ist

Jedes der folgenden wurde getestet und ausgeschlossen, solange der Weg noch als unmöglich galt.
Jedes ist plausibel genug, um einen Tag zu kosten.

| Nicht die Ursache | Wie es ausgeschlossen wurde |
| --- | --- |
| Der Credential gilt nur beim Erstellen | `sshd` startet etwa 90 Sekunden nach dem ersten Start, bevor das Site-Objekt existiert. `admin_user_credentials` ist auch in `ReplaceSpecType` vorhanden und gilt direkt. |
| `block_all_services` | Das Schließen von Port 22 auf der Management-Adresse ist identisch, ob Dienste blockiert sind oder nicht. |
| Ein abschließender Zeilenumbruch beim Schlüssel | Beide Varianten getestet, keine Änderung. Cloud-init entfernt ihn trotzdem, weil ein buchstäblicher Block sonst eine zweite, leere Zeile rendern würde. |
| Angeheftete, ältere CE-Software | Auf drei Builds reproduziert, einschließlich eines mit OpenSSH 9.9. |
| Ein fehlendes `admin_password` | Das Setzen von `admin_password` zusammen mit `ssh_key` auf einer neuen CE änderte nichts. |

<Aside type="caution" title="Zwei API-Felder, die wie Unterscheidungsmerkmale aussehen und es nicht sind">
`gc_spec.admin_ssh_key` ist bei **allen 58 Sites in `f5-sales-demo`** leer oder nicht vorhanden — einschließlich
der zwei, die `admin_user_credentials.ssh_key` tatsächlich setzen. Ein Vergleich zwischen einer funktionierenden und einer
nicht funktionierenden Site sagt nichts aus, weil es auch bei den Sites, wo der Credential *ist*
konfiguriert, als leer angezeigt wird.

`registrations_by_site` lässt das Feld vollständig aus und gibt `None` dafür zurück, was als „nicht konfiguriert"
gelesen wird statt als „nicht gemeldet".
</Aside>

<Aside type="caution" title="Eine neu erstellte Site benötigt etwa eine halbe Stunde, bevor die Debug-API antwortet">
Für ungefähr 25 bis 30 Minuten nachdem eine neue Site `ONLINE` meldet, geben die `vpm/debug`-Endpunkte
eine BIG-IP-`503`-Seite zurück mit dem Text `The requested URL was rejected`. Das sieht aus wie eine
Web-App-Firewall (WAF)-Blockierung oder ein widerrufenes Token und ist beides nicht: Die Site ist noch nicht bereit
weiterzuleiten. Warten und erneut versuchen, anstatt etwas zu ändern.

SSH hat keine solche Aufwärmzeit. Es antwortet, sobald `sshd` läuft, weshalb es der Weg ist,
der funktioniert, während ein Knoten noch registriert.
</Aside>
