Jede Customer Edge stellt F5s Site-Konsole unter `https://<sli-ip>:65500` bereit. In dieser
Bereitstellung ist das üblicherweise der Weg, den Sie zuerst ausprobieren sollten.

Er verlangt am wenigsten von Ihnen: kein SSH-Schlüssel zum Verteilen, kein Jump-Host zum
Betreiben, keine öffentliche IP am Knoten und kein Ersetzen der VM, um ihn zu aktivieren. Wer
sich verbinden darf, wird zu einer **Azure-RBAC-Entscheidung**. Und die Site muss nicht
registriert sein: diese Seite wurde erstmals erfasst, während alle drei Sites
`site_state: FAILED` meldeten, und unverändert erneut gegen dieselben Knoten verifiziert,
nachdem sie `ONLINE` waren.

Der Nachteil ist, dass die Site-Konsole nur auf der internen (SLI-)Adresse des Knotens
antwortet, die ausschließlich aus dem Inneren des VNet erreichbar ist. Azure Bastion schließt
diese Lücke, ohne irgendetwas anderes ins Netzwerk zu stellen.

<Aside type="note" title="Was hier verifiziert ist und was nicht">
Jeder Befehl und jede Ausgabe auf dieser Seite wurde gegen `f5-xc-ce-vm-01` in dieser
Bereitstellung ausgeführt und ist wortgetreu wiedergegeben, einschließlich der Fehlschläge.

**Die Authentifizierung ist verifiziert**: die `admin`-Anmeldedaten der Appliance liefern über
den Tunnel `200`. Was *nicht* durchgespielt wird, ist die Konsole selbst — nichts im Folgenden
beschreibt, was Sie sehen oder tun können, sobald Sie drin sind.

**Azure RBAC ist nicht verifiziert.** Jeder Durchlauf erfolgte als Abonnementbesitzer, daher
ist die Reader-Anforderung in Schritt 2 Microsofts dokumentierte Anforderung und nicht etwas,
das hier gemessen wurde.
</Aside>

<Aside type="caution" title="Bastion ist Opt-in und wird nicht standardmäßig bereitgestellt">
`enable_bastion` ist standardmäßig `false`, daher gibt es bei einem Standard-`terraform apply`
keinen Bastion-Host und `terraform output -raw bastion_name` ist `null`. Setzen Sie
`enable_bastion = true` in `terraform/terraform.tfvars` — in dieser Bereitstellung ist es `true`.

Der Grund für das Opt-in sind die Kosten, nicht das Risiko: ein Host mit Standard-SKU
verursacht ab dem Moment der Bereitstellung eine stündliche Grundgebühr, unabhängig davon, ob
jemand einen Tunnel öffnet — USD 0,29/Stunde in `eastus` für die zwei enthaltenen
Skalierungseinheiten (Listenpreis, 2026-07), also etwa USD 212 pro Monat. Schalten Sie es
wieder ab, wenn die Demo keinen Konsolenzugriff benötigt.
</Aside>

## Bevor Sie beginnen

<Steps>

1. Melden Sie sich bei Azure an und fügen Sie die Bastion-Erweiterung hinzu. Tunneling ist eine
   Funktion des nativen Clients und die Erweiterung ist nicht standardmäßig installiert.

   ```bash
   az login
   az extension add --name bastion
   ```

2. Halten Sie **Reader** auf der CE-Virtual Machine, ihrer Netzwerkschnittstelle und dem
   Bastion-Host. Dies ist Microsofts dokumentierte Anforderung und **hier nicht verifiziert** —
   jeder Durchlauf in dieser Bereitstellung erfolgte als Abonnementbesitzer, daher wurde keine
   geringere Rolle als ausreichend oder unzureichend nachgewiesen.

3. Bestätigen Sie, dass Bastion bereitgestellt und leistungsfähig ist. Die Basic-SKU
   unterstützt weder Tunneling noch IP-basierte Verbindungen, daher sind `Standard` und `True`
   hier beide tragend.

   ```bash
   az network bastion list -g rg-mcn-ce-ha-rmordasiewicz \
     --query "[].{name:name, sku:sku.name, tunneling:enableTunneling}" -o table
   ```

   ```text
   Name               Sku       Tunneling
   -----------------  --------  -----------
   ce-ha-lab-bastion  Standard  True
   ```

</Steps>

## Den Tunnel öffnen

Übernehmen Sie die Werte aus `terraform output`, anstatt sie einzutippen — die Ressourcen-ID
ist nichts, was man von Hand zusammensetzen sollte.

<Steps>

1. Lesen Sie den Namen des Bastion-Hosts, die Ressourcengruppe und die VM-Ressourcen-ID der
   Ziel-CE aus.

   ```bash
   cd terraform
   BASTION=$(terraform output -raw bastion_name)
   RG=$(terraform output -raw resource_group_name)
   VM_ID=$(terraform output -json ce_vm_ids | jq -r '.eastus01')
   ```

   ```text
   ce-ha-lab-bastion
   rg-mcn-ce-ha-rmordasiewicz
   /subscriptions/…/providers/Microsoft.Compute/virtualMachines/f5-xc-ce-vm-01
   ```

   <Aside type="caution" title="Die Map ist nach Site indiziert, nicht nach VM-Namen">
   Die Schlüssel von `ce_vm_ids` sind `eastus01`, `eastus02`, `eastus03` — **nicht** die
   VM-Namen. Ein Filter wie `jq -r '."f5-xc-ce-vm-01"'` liefert `null`, und der Tunnel
   scheitert dann an einer leeren Ressourcen-ID. Listen Sie sie auf, wenn Sie unsicher sind:

   ```bash
   terraform output -json ce_vm_ids | jq -r 'keys | join(", ")'
   ```

   ```text
   eastus01, eastus02, eastus03
   ```

   </Aside>

2. Starten Sie den Tunnel. Er hält den Port offen, bis er gestoppt wird, führen Sie ihn also im
   Hintergrund aus oder verwenden Sie ein zweites Terminal.

   ```bash
   az network bastion tunnel \
     --name "$BASTION" \
     --resource-group "$RG" \
     --target-resource-id "$VM_ID" \
     --resource-port 65500 \
     --port 65500 &
   ```

   ```text
   WARNING: Opening tunnel on port: 65500
   WARNING: Tunnel is ready, connect on port 65500
   WARNING: Ctrl + C to close
   ```

   Alle drei Zeilen sind mit `WARNING:` versehen. Das ist die Azure CLI, die den Fortschritt
   nach stderr schreibt, kein Problem. Warten Sie auf `Tunnel is ready`, bevor Sie sich
   verbinden.

3. Bestätigen Sie, dass der Listener lokal auf Loopback läuft:

   ```bash
   lsof -nP -iTCP:65500 -sTCP:LISTEN
   ```

   ```text
   COMMAND   PID  USER  FD  TYPE  DEVICE  SIZE/OFF  NODE  NAME
   Python  41648  you   7u  IPv4  …            0t0   TCP  127.0.0.1:65500 (LISTEN)
   ```

4. Öffnen Sie die Konsole. Der Tunnel macht sie lokal, daher ist die Adresse `localhost` —
   nicht die Adresse des Knotens.

   ```bash
   open https://localhost:65500/          # macOS
   xdg-open https://localhost:65500/      # Linux
   ```

5. Stoppen Sie den Tunnel, wenn Sie fertig sind — `Ctrl-C`, oder `kill %1`, wenn Sie ihn in den
   Hintergrund gelegt haben. Ihn offen zu lassen belegt den lokalen Port 65500 und die
   Bastion-Sitzung.

</Steps>

## Was Sie sehen werden

**Einen Dialog für Anmeldedaten, keine Login-Seite.** Die Konsole verwendet HTTP-Basic-
Authentifizierung, daher zeigt der Browser seine eigene Eingabeaufforderung für Benutzername
und Passwort. Es gibt kein Formular zu betrachten:

```bash
curl -skI https://localhost:65500/
```

```text
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Basic realm="Volterra Site Console"
Content-Type: text/html; charset=utf-8
Content-Length: 0
```

Ein `401` mit diesem Realm bedeutet, dass die Konsole korrekt funktioniert. Es ist das, was
eine nicht authentifizierte Anfrage bekommen soll — und wenn man dieselbe URL mit den
`admin`-Anmeldedaten aufruft, antwortet sie mit `200`, womit Sie die Anmeldedaten bestätigen
können, bevor Sie einen Browser öffnen:

```bash
curl -sk -u admin -o /dev/null -w '%{http_code}\n' https://localhost:65500/
```

```text
Enter host password for user 'admin':
200
```

`-u admin` ohne Doppelpunkt bewirkt, dass `curl` das Passwort abfragt, anstatt es aus der
Kommandozeile zu nehmen, wo es in der Shell-Historie und in der Prozessliste landen würde.

**Eine Zertifikatswarnung, aus drei Gründen gleichzeitig.** Prüfung des Zertifikats direkt:

```bash
openssl s_client -connect localhost:65500 -servername localhost </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
```

```text
subject=C=US, ST=California, L=Santa Clara, O=Volterra, OU=Volterra Edge Services, CN=site-local.volterra.io
issuer=C=US, ST=California, L=Santa Clara, O=Volterra, OU=Volterra Edge Services, CN=site-local.volterra.io
notBefore=Oct 25 04:51:31 2024 GMT
notAfter=Oct 25 04:51:31 2025 GMT
```

Subject entspricht Issuer, es ist also selbstsigniert. Der Name lautet
`site-local.volterra.io`, während Sie sich mit `localhost` verbinden, er wird also nicht
übereinstimmen. Und im Build, auf dem diese Bereitstellung läuft, **ist das Zertifikat am
25. Oktober 2025 abgelaufen** — die Appliance liefert es mit, und nichts in diesem Repository
erneuert es.

Erwarten Sie eine deutliche Browserwarnung, und erwarten Sie sie jedes Mal. Die Subject-Zeile
oben ist der nützliche Teil: damit bestätigen Sie, dass Sie die Appliance erreicht haben und
nicht irgendetwas anderes, das auf dem lokalen Port 65500 lauscht.

## Die Administrator-Anmeldedaten

Melden Sie sich als `admin` an. **Diese Dokumentation veröffentlicht das Passwort nicht und
sollte es auch nicht.**

<Aside type="danger" title="In dieser Bereitstellung ist dieses Passwort noch F5s Werkseinstellung">
Das ist eine gemessene Tatsache, keine Vermutung: die werkseitigen Standard-Anmeldedaten
authentifizieren sich und liefern heute auf allen drei CEs `200`. F5 veröffentlicht diesen
Standard und verlangt, dass er geändert wird, und das ist nicht geschehen.

Die praktische Folge ist, dass in dieser Bereitstellung „hält Reader auf dem Bastion“
gleichbedeutend ist mit vollem Zugriff auf die Appliance-Konsole, für jeden, der einen Wert
kennt, der in F5s öffentlicher Dokumentation steht. Ändern Sie ihn und betrachten Sie die
Änderung als Teil der Bereitstellung eines Knotens und nicht als späteres Hardening.
</Aside>

Zwei Gründe, warum das Nichtveröffentlichen hier mehr zählt, als es aussieht:

- Diese Dokumentation ist öffentlich. Das aktuelle Konsolenpasswort der Flotte abzudrucken
  würde „hält Reader auf dem Bastion“ für jeden, der die Seite liest, in vollen
  Appliance-Zugriff verwandeln.
- Ein in der Dokumentation veröffentlichtes Passwort ist in dem Moment falsch, in dem es jemand
  rotiert — und auf die irreführendste Weise falsch: der Leser schließt daraus, dass sein
  Zugang defekt ist, und nicht, dass die Seite veraltet ist.

Sobald es rotiert wurde, holen Sie es dort, wo Ihr Team betriebliche Geheimnisse verwahrt.

<Aside type="caution" title="Das Setzen des Passworts über Terraform ist nicht verifiziert">
`admin_user_credentials.admin_password` am Site-Objekt sieht nach dem deklarativen Weg aus,
dies zu setzen. Es wurde **nicht** bestätigt, dass es in diesem Build die Site-Konsole
erreicht, gehen Sie also nicht davon aus.

Lesen Sie die [SSH-Seite](../ssh/) auch nicht als Beleg in eine der beiden Richtungen. Ihr
Befund, dass `admin_password` „nichts geändert hat“, wurde gegen die SSH-Authentifizierung
gemessen, die `vpm` für den Benutzer `admin` vollständig überspringt. Das sagt nichts über die
Konsole aus.
</Aside>

## Warum der Tunnel auf die Ressourcen-ID zeigen muss

`--target-resource-id` ist erforderlich. Stattdessen die Adresse des Knotens anzugeben wird
abgelehnt — welche Adresse auch immer Sie verwenden, daher ist hier absichtlich keine echte
abgedruckt:

```bash
az network bastion tunnel --name "$BASTION" -g "$RG" \
  --target-ip-address <any-sli-address> --resource-port 65500 --port 65501
```

```text
ERROR: Custom ports are not allowed. Allowed ports for Tunnel with IP connect is 22, 3389.
```

Der Grund ist **nicht**, dass IP-basierte Verbindungen deaktiviert sind — auf diesem Bastion
ist `ip_connect_enabled` `true`. Microsoft unterstützt benutzerdefinierte Ports über
IP-basierte Verbindungen mit dem nativen Client unabhängig von dieser Einstellung nicht
([Azure-Dokumentation](https://learn.microsoft.com/azure/bastion/connect-ip-address)), und
65500 ist ein benutzerdefinierter Port. Die Bastion-Konfiguration hier zu untersuchen führt
zu nichts; verwenden Sie die Ressourcen-ID.

## Wenn es nicht funktioniert

| Symptom | Ursache | Behebung |
| --- | --- | --- |
| `ERROR: Custom ports are not allowed. Allowed ports for Tunnel with IP connect is 22, 3389.` | `--target-ip-address` verwendet | `--target-resource-id` verwenden |
| `ERROR: Defined port is currently unavailable` | Ein anderer Tunnel belegt diesen lokalen Port bereits | Den anderen Tunnel stoppen oder einen anderen `--port` übergeben; `--resource-port` bleibt 65500 |
| `terraform output -raw bastion_name` ist `null` oder leer | Bastion ist nicht bereitgestellt | `enable_bastion = true` setzen und anwenden |
| Tunnel startet, aber die Ressourcen-ID ist leer | Der `jq`-Filter verwendete den VM-Namen statt des Site-Schlüssels | Auf `eastus01`/`02`/`03` indizieren |
| `401 Unauthorized`, Realm `Volterra Site Console` | Kein Fehler — nicht authentifizierte Anfrage | Die `admin`-Anmeldedaten angeben |
| Browser weist das Zertifikat ab | Selbstsigniert, Namensabweichung und seit Okt. 2025 abgelaufen | Erwartet; bestätigen, dass das Subject `CN=site-local.volterra.io` ist, und fortfahren |

<Aside type="note" title="Autorisierungsfehler wurden nicht reproduziert">
Unzureichendes RBAC ist der andere offensichtliche Weg, auf dem dies scheitert, aber es zu
reproduzieren würde bedeuten, Rollenzuweisungen aus einer gemeinsam genutzten Bereitstellung zu
entfernen, daher ist es hier nicht mit einer wortgetreuen Fehlermeldung dokumentiert. Wenn der
Tunnel beim Start mit einem Autorisierungsfehler fehlschlägt, prüfen Sie Reader auf allen drei:
der VM, ihrer NIC und dem Bastion-Host.
</Aside>
