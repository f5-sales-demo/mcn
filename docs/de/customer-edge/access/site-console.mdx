Jeder Customer Edge stellt F5's Site Console unter `https://<sli-ip>:65500` bereit. In
dieser Bereitstellung ist dies in der Regel der erste zu prüfende Zugangsweg.

Er stellt die geringsten Anforderungen: kein SSH-Schlüssel, der verteilt werden muss, kein
Jump-Host, der gewartet werden muss, keine öffentliche IP auf dem Knoten und kein
VM-Austausch, um ihn zu aktivieren. Wer eine Verbindung herstellen darf, wird zu einer
**Azure-RBAC-Entscheidung**. Und der Site muss nicht registriert sein — das nachfolgende
Protokoll wurde aufgezeichnet, während alle drei Sites den Status `site_state: FAILED`
meldeten.

Der Haken ist, dass die Site Console nur auf der internen (SLI-)Adresse des Knotens
antwortet, die nur aus dem VNet heraus erreichbar ist. Azure Bastion schließt diese Lücke,
ohne etwas anderes ins Netzwerk einzubringen.

<Aside type="note" title="Was hier geprüft wird und was nicht">
Jeder Befehl und jede Ausgabe auf dieser Seite wurde auf `f5-xc-ce-vm-01` in dieser
Bereitstellung ausgeführt und wird wortwörtlich wiedergegeben, einschließlich der Fehler.

Das Einzige, was nicht geprüft wurde, ist die **Anmeldung**. Die Schritte enden bei der
Aufforderung zur Eingabe der Anmeldedaten, daher beschreibt nichts weiter unten, wie die
Konsole nach dem Anmelden aussieht.
</Aside>

## Voraussetzungen

<Steps>

1. Melden Sie sich bei Azure an und fügen Sie die Bastion-Erweiterung hinzu. Tunneling ist
   eine Funktion für native Clients und die Erweiterung ist nicht standardmäßig
   installiert.

   ```bash
   az login
   az extension add --name bastion
   ```

2. Besitzen Sie die Rolle **Reader** auf der CE-VM, ihrer Netzwerkschnittstelle und dem
   Bastion-Host.

3. Bestätigen Sie, dass Bastion bereitgestellt und funktionsfähig ist. Die Basic-SKU
   unterstützt weder Tunneling noch IP-basierte Verbindungen, daher sind `Standard` und
   `True` hier beide entscheidend.

   ```bash
   az network bastion list -g rg-mcn-ce-ha-rmordasiewicz \
     --query "[].{name:name, sku:sku.name, tunneling:enableTunneling}" -o table
   ```

   ```text
   Name               Sku       Tunneling
   -----------------  --------  -----------
   ce-ha-lab-bastion  Standard  True
   ```

</Steps>

## Tunnel öffnen

Verwenden Sie die Werte aus `terraform output`, anstatt sie manuell einzugeben — die
Ressourcen-ID sollte nicht von Hand zusammengestellt werden.

<Steps>

1. Lesen Sie den Bastion-Hostnamen, die Ressourcengruppe und die VM-Ressourcen-ID des
   Ziel-CE aus.

   ```bash
   cd terraform
   BASTION=$(terraform output -raw bastion_name)
   RG=$(terraform output -raw resource_group_name)
   VM_ID=$(terraform output -json ce_vm_ids | jq -r '.eastus01')
   ```

   ```text
   ce-ha-lab-bastion
   rg-mcn-ce-ha-rmordasiewicz
   /subscriptions/…/providers/Microsoft.Compute/virtualMachines/f5-xc-ce-vm-01
   ```

   <Aside type="caution" title="Die Zuordnung ist nach Site, nicht nach VM-Namen verschlüsselt">
   Die Schlüssel von `ce_vm_ids` sind `eastus01`, `eastus02`, `eastus03` — **nicht** die
   VM-Namen. Ein Filter wie `jq -r '."f5-xc-ce-vm-01"'` liefert `null`, und der Tunnel
   schlägt dann mit einer leeren Ressourcen-ID fehl. Listen Sie sie bei Unsicherheit auf:

   ```bash
   terraform output -json ce_vm_ids | jq -r 'keys | join(", ")'
   ```

   ```text
   eastus01, eastus02, eastus03
   ```
   </Aside>

2. Starten Sie den Tunnel. Er hält den Port offen, bis er gestoppt wird. Starten Sie ihn
   daher im Hintergrund oder verwenden Sie ein zweites Terminal.

   ```bash
   az network bastion tunnel \
     --name "$BASTION" \
     --resource-group "$RG" \
     --target-resource-id "$VM_ID" \
     --resource-port 65500 \
     --port 65500 &
   ```

   ```text
   WARNING: Opening tunnel on port: 65500
   WARNING: Tunnel is ready, connect on port 65500
   WARNING: Ctrl + C to close
   ```

   Alle drei Zeilen sind mit `WARNING:` vorangestellt. Das ist die Azure CLI, die
   Fortschrittsinformationen an stderr schreibt — kein Problem. Warten Sie auf
   `Tunnel is ready`, bevor Sie eine Verbindung herstellen.

3. Bestätigen Sie, dass der Listener lokal auf dem Loopback-Interface aktiv ist:

   ```bash
   lsof -nP -iTCP:65500 -sTCP:LISTEN
   ```

   ```text
   COMMAND   PID  USER  FD  TYPE  DEVICE  SIZE/OFF  NODE  NAME
   Python  41648  you   7u  IPv4  …            0t0   TCP  127.0.0.1:65500 (LISTEN)
   ```

4. Öffnen Sie die Konsole. Der Tunnel macht sie lokal, daher lautet die Adresse
   `localhost` — nicht die Adresse des Knotens.

   ```bash
   open https://localhost:65500/          # macOS
   xdg-open https://localhost:65500/      # Linux
   ```

5. Stoppen Sie den Tunnel, wenn Sie fertig sind — `Ctrl-C` oder `kill %1`, wenn Sie ihn
   in den Hintergrund verschoben haben. Ein offener Tunnel belegt den lokalen Port 65500
   sowie die Bastion-Sitzung.

</Steps>

## Was Sie sehen werden

**Ein Anmeldedialog, keine Anmeldeseite.** Die Konsole verwendet HTTP-Basic-Authentifizierung,
daher zeigt der Browser seinen eigenen Benutzernamen- und Passwortdialog an. Es gibt kein
Formular zu sehen:

```bash
curl -skI https://localhost:65500/
```

```text
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Basic realm="Volterra Site Console"
Content-Length: 0
```

Ein `401` mit diesem Realm bedeutet, dass die Konsole korrekt funktioniert. Dies ist die
erwartete Antwort auf eine nicht authentifizierte Anfrage.

**Eine Zertifikatswarnung, aus drei Gründen gleichzeitig.** Direkte Prüfung des
Zertifikats:

```bash
openssl s_client -connect localhost:65500 -servername localhost </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
```

```text
subject=C=US, ST=California, L=Santa Clara, O=Volterra, OU=Volterra Edge Services, CN=site-local.volterra.io
issuer=C=US, ST=California, L=Santa Clara, O=Volterra, OU=Volterra Edge Services, CN=site-local.volterra.io
notBefore=Oct 25 04:51:31 2024 GMT
notAfter=Oct 25 04:51:31 2025 GMT
```

Subject stimmt mit Issuer überein, es handelt sich also um ein selbstsigniertes Zertifikat.
Der Name ist `site-local.volterra.io`, während Sie sich mit `localhost` verbinden, sodass
keine Übereinstimmung vorliegt. Und beim Build dieser Bereitstellung **ist das Zertifikat
am 25. Oktober 2025 abgelaufen** — das Gerät liefert es mit, und nichts in diesem
Repository erneuert es.

Erwarten Sie eine deutliche Browser-Warnung, und zwar jedes Mal. Die oben angezeigte
Subject-Zeile ist der nützliche Teil: Sie bestätigt, dass Sie das Gerät erreicht haben und
nicht etwas anderes, das auf dem lokalen Port 65500 lauscht.

## Die Admin-Anmeldedaten

Melden Sie sich als `admin` an. **Diese Dokumentation veröffentlicht das Passwort nicht
und sollte es auch nicht.**

Ein werksneuer Customer Edge wird mit F5's veröffentlichtem Standardpasswort ausgeliefert,
und F5 verlangt dessen Änderung. Behandeln Sie die Änderung als Teil der
Knotenbereitstellung und nicht als spätere Härtungsmaßnahme. Zwei Gründe, warum das hier
wichtiger ist als es aussehen mag:

- Diese Dokumentation ist öffentlich. Das aktuelle Konsolen-Passwort des Bestands zu
  veröffentlichen würde dazu führen, dass „Reader-Berechtigung auf dem Bastion" für jeden,
  der die Seite liest, zu vollständigem Gerätezugang wird.
- Ein in der Dokumentation veröffentlichtes Passwort ist falsch, sobald jemand es rotiert,
  und falsch auf die irreführendste Art — der Leser schlussfolgert, dass sein Zugang
  defekt ist, anstatt dass die Seite veraltet ist.

Holen Sie das Passwort dort, wo Ihr Team seine Betriebsgeheimnisse aufbewahrt. Lautet die
Antwort „es ist noch das Werkspasswort", ändern Sie es, bevor Sie irgendetwas anderes tun.

<Aside type="caution" title="Das Setzen des Passworts über Terraform wurde nicht geprüft">
`admin_user_credentials.admin_password` am Site-Objekt sieht wie der deklarative Weg aus,
dies zu setzen. Es wurde **nicht** bestätigt, dass es die Site Console in diesem Build
erreicht, daher sollte nicht davon ausgegangen werden.

Lesen Sie auch die [SSH-Seite](../ssh/) nicht als Beweis in die eine oder andere Richtung.
Der dortige Befund, dass `admin_password` „nichts verändert hat", wurde gegen die
SSH-Authentifizierung gemessen, die `vpm` für den `admin`-Benutzer vollständig überspringt.
Das sagt nichts über die Konsole aus.
</Aside>

## Warum der Tunnel auf die Ressourcen-ID zielen muss

`--target-resource-id` ist erforderlich. Das Zielen auf die Adresse des Knotens wird
abgelehnt:

```bash
az network bastion tunnel --name "$BASTION" -g "$RG" \
  --target-ip-address 10.0.3.5 --resource-port 65500 --port 65501
```

```text
ERROR: Custom ports are not allowed. Allowed ports for Tunnel with IP connect is 22, 3389.
```

Der Grund ist **nicht**, dass IP-basierte Verbindungen deaktiviert sind — auf diesem
Bastion ist `ip_connect_enabled` auf `true` gesetzt. Microsoft unterstützt keine
benutzerdefinierten Ports über IP-basierte native Client-Verbindungen, unabhängig von
dieser Einstellung
([Azure-Dokumentation](https://learn.microsoft.com/azure/bastion/connect-ip-address)), und
65500 ist ein benutzerdefinierter Port. Das Untersuchen der Bastion-Konfiguration hier
führt zu nichts; verwenden Sie die Ressourcen-ID.

## Wenn es nicht funktioniert

| Symptom | Ursache | Lösung |
| --- | --- | --- |
| `ERROR: Custom ports are not allowed. Allowed ports for Tunnel with IP connect is 22, 3389.` | `--target-ip-address` wurde verwendet | `--target-resource-id` verwenden |
| `ERROR: Defined port is currently unavailable` | Ein anderer Tunnel belegt bereits diesen lokalen Port | Den anderen Tunnel stoppen oder einen anderen `--port` übergeben; `--resource-port` bleibt 65500 |
| Tunnel startet, aber die Ressourcen-ID ist leer | `jq`-Filter hat den VM-Namen statt des Site-Schlüssels verwendet | Schlüssel `eastus01`/`02`/`03` verwenden |
| `401 Unauthorized`, Realm `Volterra Site Console` | Kein Fehler — nicht authentifizierte Anfrage | `admin`-Anmeldedaten angeben |
| Browser lehnt das Zertifikat ab | Selbstsigniert, Name stimmt nicht überein und seit Oktober 2025 abgelaufen | Erwartet; bestätigen Sie, dass der Subject `CN=site-local.volterra.io` ist, und fahren Sie fort |

<Aside type="note" title="Autorisierungsfehler wurden nicht reproduziert">
Unzureichende RBAC-Berechtigungen sind die andere naheliegende Fehlerursache, aber deren
Reproduktion würde bedeuten, Rollenzuweisungen aus einer gemeinsam genutzten Bereitstellung
zu entfernen. Daher wird sie hier nicht mit einem wortwörtlichen Fehler dokumentiert. Wenn
der Tunnel beim Start mit einem Autorisierungsfehler fehlschlägt, prüfen Sie die
Reader-Berechtigung auf allen drei Objekten: VM, NIC und Bastion-Host.
</Aside>
