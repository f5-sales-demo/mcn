Die `vpm/debug`-API führt Site-CLI-Befehle auf einem registrierten Knoten aus und gibt deren
Ausgabe zurück. Alles Nachfolgende wurde gegen einen aktiven Knoten ermittelt; nichts davon ist
upstream veröffentlicht.

## Der Befehlskatalog beschreibt sich selbst

Fragen Sie den Knoten nach den unterstützten Befehlen, indem Sie an `exec-user` POSTen und dabei den Schlüssel `command`
**weglassen**:

```bash
curl -sS -X POST \
  -H "Authorization: APIToken $XCSH_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"namespace":"system","site":"<site>","node":"<node>"}' \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/<node>/exec-user" \
  | jq -r .output | jq .
```

Die Antwort ist ein JSON-Objekt, dessen Schlüssel die Befehlsnamen sind:

```json
{
  "crictl-inspect": ["System Troubleshooting", "ExecUser", " container-id"],
  "diagnosis":      ["System Troubleshooting", "ExecUser", "no argument needed", "GLOBAL"],
  "ip-link-set":    ["Network Troubleshooting", "Exec", " (<device>||<group>) (up||down)"]
}
```

Jeder Eintrag hat die Form `[category, tier, exampleArgument?, scope?]`, und diese Felder sind
keine Dokumentation – sie legen fest, wie der Befehl aufgerufen werden muss.

<Aside type="caution" title="Lassen Sie den Schlüssel weg; senden Sie keinen falschen Wert">
Discovery funktioniert, indem `command` weggelassen wird. Wird stattdessen ein unbekannter Wert gesendet, erhalten Sie
einen Fehler und nicht den Katalog:

```json
{"code":3,"details":[],"message":"exec command failed: command not supported"}
```

Dieselbe Meldung erhalten Sie auch für einen *echten* Befehl, der an den falschen Endpunkt gesendet wurde,
weshalb sie leicht als „diesen Befehl gibt es nicht“ fehlgedeutet wird.
</Aside>

## Drei Transportwege, ausgewählt durch den Katalogeintrag

| Bedingung | Methode und Pfad | Body | Rückgabe |
| --- | --- | --- | --- |
| `scope` ist `GLOBAL` | `GET .../vpm/debug/global/<cmd>` | keiner | JSON |
| `tier` ist `ExecUser` | `POST .../vpm/debug/<node>/exec-user` | `command`-Array | Text |
| `tier` ist `Exec` | `POST .../vpm/debug/<node>/exec` | `command`-Array | Text |

### `ExecUser` — die schreibgeschützte Stufe <Badge text="31 Befehle" variant="note" />

Der Normalfall. Übergeben Sie den Befehl und seine Argumente als Array, den Befehlsnamen
zuerst:

```bash
curl -sS -X POST \
  -H "Authorization: APIToken $XCSH_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"namespace":"system","site":"<site>","node":"<node>","command":["crictl-ps"]}' \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/<node>/exec-user"
```

```json
{ "return_code": 0, "output": "CONTAINER    IMAGE    CREATED    STATE ..." }
```

Argumente sind separate Array-Elemente, keine einzelne Zeichenkette:

```json
{ "command": ["journalctl", "-u", "vpm", "-n", "200"] }
```

### `GLOBAL` — standortweit und ein völlig anderer Transportweg <Badge text="2 Befehle" variant="tip" />

`health` und `diagnosis` sind die einzigen beiden. Es handelt sich um `GET`-Anfragen an einen `global`-Pfad,
sie nehmen keine Argumente entgegen und geben strukturiertes JSON statt Terminaltext zurück.

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/global/health" | jq .
```

<Aside type="danger" title="Ein GLOBAL-Befehl ist über exec-user nicht erreichbar">
Das ist die Falle, die am meisten Zeit kostet. Werden `health` oder `diagnosis` an
`exec-user` gesendet, erhalten Sie `command not supported`, was so klingt, als existiere der Befehl auf dem Knoten
nicht – obwohl er tatsächlich existiert und Sie lediglich den falschen Transportweg verwendet haben.

```bash
# Wrong. Returns: exec command failed: command not supported
-d '{"namespace":"system","site":"…","node":"…","command":["health"]}'   # POST exec-user

# Right.
GET .../vpm/debug/global/health
```

</Aside>

### `Exec` — die privilegierte Stufe <Badge text="1 Befehl in diesem Build" variant="danger" />

Ein separater Endpunkt, und die Stufe wird erzwungen statt nur empfohlen: `exec` weist
einen `ExecUser`-Befehl mit derselben Meldung `command not supported` zurück. Jedes Mitglied
verändert entweder den Knoten oder liest einen Zustandsmarker.

In dem Build, den dieser Tenant ausführt, enthält die Stufe nur `ip-link-set`. Neuere Builds
ergänzen `systemctl-restart-NetworkManager`, `systemctl-restart-crio`,
`systemctl-restart-kubelet`, `systemctl-start-crio-prune` sowie drei
`marker-exists-*`-Befehle.

<Aside type="danger" title="Hier wird kein Exec-Befehl ausgeführt">
Das Capture-Harness verweigert diese Stufe und liest die Stufe aus dem Live-Katalog
statt aus einer fest codierten Liste – so wird ein zukünftiger Build, der einen Befehl auf `Exec`
hochstuft, respektiert, ohne dass jemand Code ändern muss. Führen Sie einen solchen Befehl nur bewusst aus, auf einem Knoten, dessen
Störung Sie in Kauf nehmen.
</Aside>

## Site- und Knotennamen ermitteln

Der Knotenname ist der Name der Azure-VM, und `list-service` ist ein günstiger Weg, ihn
zusammen mit den darauf laufenden Diensten zu bestätigen:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/global/list-service" \
  | jq -r '[.service[].node] | unique'
```

```json
["", "f5-xc-ce-vm-01"]
```

Manche Dienste melden einen leeren Knotennamen, daher ist eine leere Zeichenkette in dieser Liste ein Artefakt der
Antwort und kein zweiter Knoten. `list-service` ist außerdem nicht im 34-Befehle-Katalog enthalten:
Es handelt sich um einen `global`-Endpunkt, den der Katalog nicht ausweist – deshalb wird er hier dokumentiert
und nicht in der [Befehlsreferenz](../../commands/).

## Die Captures dieses Repositorys reproduzieren

Jede Befehlsseite bettet Ausgaben ein, die von `scripts/capture-sitecli.sh` erfasst wurden, welches
alle drei oben genannten Regeln umsetzt.

<Steps>

1. Richten Sie es auf einen Tenant. Es liest `XCSH_API_URL` und `XCSH_API_TOKEN` oder greift
   auf den aktiven `xcsh`-Kontext zurück.

2. Aktualisieren Sie den Katalog und prüfen Sie, dass sich der Knoten unter der
   Dokumentation nicht verändert hat:

   ```bash
   bash scripts/capture-sitecli.sh --check
   ```

   Dies vergleicht ausschließlich den eingecheckten Katalog und den Software-Build. Eine
   Build-Änderung wird getrennt von hinzugefügten oder entfernten Befehlen gemeldet.

3. Erfassen Sie erneut, wenn Sie frische Belege benötigen:

   ```bash
   bash scripts/capture-sitecli.sh
   ```

</Steps>

<Aside type="note" title="Captures sind Belege, keine reproduzierbaren Artefakte">
Zähler, Laufzeiten und Container-Alter ändern sich zwischen Durchläufen, sodass eine erneute Erfassung immer
ein Diff erzeugt. Der Katalog ist der stabile Vertrag und ist über Durchläufe hinweg byteidentisch,
solange sich der Knoten nicht verändert hat; genau das vergleicht `--check`. Lange Ausgaben werden
gekürzt und enden mit einem expliziten Marker, sodass eine abgeschnittene Tabelle nie so dargestellt wird, als
wäre sie vollständig.
</Aside>

<Aside type="danger" title="Erfassung von einem Kundenknoten: Redaction-Profil prüfen">
Befehlsausgaben enthalten Infrastruktur-Identitäten – interne Adressierung, MAC-Adressen,
AS-Nummern, Hostnamen – und für einen Kunden sind das identifizierende Informationen über die
Organisation.

Der Scrub-Filter verwendet deshalb standardmäßig ein **striktes** Profil, das all dies entfernt.
Dieses Repository deklariert `lab` in `sitecli/capture-manifest.json`, wodurch diese Details
erhalten bleiben, und das ist nur hier korrekt, weil diese Captures aus F5-eigener Demo-Infrastruktur
stammen.

**Übertragen Sie diese Einstellung nicht auf eine Kundenerfassung.** Tokens, private Schlüssel, die Tenant-Kennung,
Objekt-UUIDs, E-Mail-Adressen und Home-Verzeichnispfade werden unter
beiden Profilen entfernt.

Eine Einschränkung sollten Sie kennen: Eine BGP-Nachbartabelle gibt die AS als bloße Spalte
ohne Beschriftung aus, an der sich ein Muster verankern ließe, daher werden ASNs wertbasiert gegen die
privaten Bereiche abgeglichen. Eine **öffentliche** ASN übersteht dort das strikte Profil und erfordert eine manuelle Prüfung der
`show-ip-bgp*`-Ausgabe, bevor Sie sie veröffentlichen.
</Aside>
