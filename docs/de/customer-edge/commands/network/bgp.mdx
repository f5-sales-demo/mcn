hält fest, welcher Knoten es war, und `scripts/capture-sitecli.sh --check` verifiziert die

Die CE betreibt FRR für BGP. In dieser Topologie betreibt sie Peering mit den zwei
Azure-Route-Server-Instanzen, kündigt die VIP an und lernt das VNet-Präfix.

## `show-ip-bgp-summary`

Beginnen Sie hier. Ein Bildschirm zeigt Ihnen, ob das Peering aktiv ist und wie lange es
bereits stabil ist.

```bash
{"command":["show-ip-bgp-summary"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp-summary.txt
```

Lesen Sie zuerst `State/PfxRcd`. Eine Zahl ist die Anzahl der empfangenen Präfixe und
bedeutet, dass die Sitzung etabliert ist; alles andere — `Active`, `Connect`, `Idle` — ist
eine Sitzung, die nicht aktiv ist. `Up/Down` zeigt, wie lange der aktuelle Zustand angehalten
hat, sodass eine Sitzung, die sich ständig zurücksetzt, einen verdächtig kleinen Wert anzeigt.

<Aside type="caution" title="Die vrf id hier ist nicht die, die rt erwartet">
Diese Ausgabe meldet `vrf-id 3`. Das ist die Nummerierung von FRR. Die Argo-Datenebene
verwendet eine separate Tabellen-ID, und wenn man die Nummer von FRR an
[`rt --dump`](../dataplane-forwarding/) übergibt, ergibt das `No such file or directory`, was
wie ein defekter Knoten aussieht statt wie das falsche Argument.
</Aside>

## `show-ip-bgp`

Die vollständige Tabelle mit sichtbarer Best-Path-Auswahl.

```bash
{"command":["show-ip-bgp"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp.txt
```

`*` ist eine gültige Route, `>` der ausgewählte Best Path, `=` ein Multipath-Mitglied. In der
obigen Aufzeichnung hat das gelernte VNet-Präfix `10.0.0.0/16` zwei Pfade — einen über jede
Route-Server-Instanz — markiert mit `*=` und `*>`: ein Best Path plus ein Multipath-Mitglied,
sodass der Knoten seinen Rückverkehr über beide Instanzen verteilt. Die VIP `10.250.0.10/32`
hat einen einzelnen `*>`-Pfad, weil dieser Knoten sie originiert.

<Aside type="caution" title="Das Equal-Cost-Multipath der Demo ist in dieser Ausgabe nicht sichtbar">
`show-ip-bgp` ist die Tabelle eines Knotens. Das ECMP, das dieses Deployment demonstriert,
besteht aus mehreren *verschiedenen* CEs, die dasselbe `/32` ankündigen, und es wird auf der
Azure-Seite programmiert — daher kann die BGP-Tabelle keiner einzelnen CE es zeigen, und das
Fehlen einer Multipath-Markierung an der VIP hier ist kein Fehler. Weisen Sie es stattdessen
über die Route-Server-Peerings oder die effektive Routing-Tabelle des Clients nach; beides
finden Sie auf der [Verifizierungsseite](../../../../demo/verify/).
</Aside>

## `show-ip-bgp-neighbors`

Details pro Nachbar: verhandelte Capabilities, Timer, Nachrichtenzähler und der Grund für den
letzten Reset.

```bash
{"command":["show-ip-bgp-neighbors"]}
```

Greifen Sie darauf zurück, wenn die Zusammenfassung eine flappende Sitzung zeigt und Sie
wissen müssen, warum. `Last reset` und der zugehörige Grund sind die nützlichen Zeilen.

<Aside type="note" title="Noch keine aufgezeichnete Ausgabe auf dieser Seite">
Diese Aufzeichnung kann nicht committet werden, bis `f5-sales-demo/docs-control#795`
eingegangen ist. FRR schreibt ein Wort in seiner Graceful-Restart-Zeile falsch, und
`codespell` weist die Datei ab.

Aufgezeichneten Text zu korrigieren würde bedeuten, dass diese Dokumentation eine Ausgabe
beschreibt, die niemals aufgetreten ist, daher wird es stattdessen upstream behoben. Führen
Sie den Befehl in der Zwischenzeit gegen Ihren eigenen Knoten aus.
</Aside>

## `show-ip-bgp-neighbors-advertised-route`

Was dieser Knoten seinen Peers mitteilt, im Gegensatz zu dem, was er weiß.

```bash
{"command":["show-ip-bgp-neighbors-advertised-route"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp-neighbors-advertised-route.txt
```

Dies ist der Befehl für „die VIP ist aus dem VNet nicht erreichbar“. Wenn die VIP hier fehlt,
liegt das Problem an diesem Knoten und kein Blick auf den Peer wird helfen.

Die Ausgabe wiederholt einen `bgp neighbor:`-Block **pro Peer**, sodass Sie in dieser
Topologie dieselben zwei Präfixe zweimal erhalten — einmal für jede Route-Server-Instanz. Das
ist kein doppeltes Rendering: Es bestätigt, dass der Knoten an beide ankündigt. Der
interessante Fall ist ein Block, der für einen Peer vorhanden und für den anderen fehlend oder
zu kurz ist.
