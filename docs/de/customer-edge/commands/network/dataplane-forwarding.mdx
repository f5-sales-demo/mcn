Argo hält den Weiterleitungszustand von dem Linux-Kernel getrennt. Wenn
[`ip`](../ip/) und diese Befehle nicht übereinstimmen, sind diese Befehle ausschlaggebend für den Datenverkehr.

## `rt`

Die vRouter-Routentabelle, pro VRF.

```bash
{"command":["rt","--dump","2"]}
```

```text file=../../../../_data/sitecli-rt.txt
```

<Aside type="danger" title="Die VRF-ID ist nicht dieselbe, die BGP meldet">
`show-ip-bgp-summary` gibt `vrf-id 3` aus. Das ist die Nummerierung von FRR und gehört einem
anderen Namensraum als die vRouter-Tabellen-ID an. Die Übergabe dieser ID schlägt auf eine Weise fehl, die
wie ein defekter Knoten aussieht:

```
vRouter(Response):  [No such file or directory (2)]
```

Dieselbe Antwort kommt bei `--dump 0` zurück. In dieser Topologie ist **VRF 2** die
befüllte inet4-Tabelle, wobei VRF 1 zwei Routen enthält. Wenn die ID nicht bekannt ist,
sollte man von 1 aufwärts suchen, anstatt der BGP-Ausgabe zu vertrauen.
</Aside>

## `nh`

Die Next-Hop-Tabelle. Jede Route verweist auf eine Next-Hop-ID, und diese löst sie auf.

```bash
{"command":["nh","--list"]}
```

```text file=../../../../_data/sitecli-nh.txt
```

Jeder Eintrag enthält einen `Type` und das zugehörige VRF. Auf diesen Knoten kommen acht Typen vor, in
folgenden Anteilen — identisch über alle drei CEs hinweg:

```text
Tunnel 558   Encap 27   NAT 22   Vrf 16   Receive 14   Composite 4   Drop 2   Resolve 2
```

Eine Route, die zu einem `Drop`-Next-Hop aufgelöst wird, ist ein Blackhole. Diese Kombination sollte immer
dann überprüft werden, wenn ein Präfix in `rt` vorhanden ist, der Datenverkehr aber trotzdem verschwindet.

<Aside type="caution" title="Die obige Aufzeichnung ist gekürzt und enthält daher nicht jeden Typ">
Es handelt sich um die ersten 60 Zeilen von 3.849. `Tunnel`, der mit Abstand häufigste Typ, kommt in
diesen 60 Zeilen gar nicht vor — daher sollte die Aufzeichnung nicht als vollständiges Typinventar gelesen werden, und es sollte nicht
der Schluss gezogen werden, dass ein Typ auf einem Knoten fehlt, weil er in einer gekürzten Aufzeichnung fehlt. Die obigen
Zählungen stammen aus der vollständigen Antwort.
</Aside>

## `vif`

Die virtuelle Schnittstellentabelle: womit die Datenebene verknüpft ist, und Zähler pro Schnittstelle.

```bash
{"command":["vif","--list"]}
```

```text file=../../../../_data/sitecli-vif.txt
```

Die Flags-Legende am Anfang ist es wert, einmal gelesen zu werden — `Vp` markiert die physische
vhost-Schnittstelle, `Dpdk` eine DPDK-verwaltete. Damit lässt sich bestätigen, dass die Datenebene
die erwartete Schnittstelle übernommen hat, und RX- sowie TX-Zähler anzeigen, die Linux nicht anzeigt,
weil der Datenverkehr den Kernel nie erreicht.

## `mpls`

```bash
execcli mpls --help
```

Die Argo-MPLS-Tabelle. Nur **vom Gerät selbst** erreichbar — `mpls` ist nicht in der Debug-API, daher
benötigt es im Gegensatz zu `rt`, `nh` und `vif` oben [SSH](../../../access/ssh/) oder die
[serielle Konsole](../../../access/serial-console/), über
[`execcli`](../../on-box/).

Hier gibt es keine aufgezeichnete Ausgabe. In dieser Bereitstellung leitet der CE IPv4 mit BGP und ECMP weiter und verwendet
keine MPLS-Labels, sodass eine Aufzeichnung eine leere Tabelle zeigen und nichts lehren würde. Ihre Existenz
und die Form ihres `--help`-Arguments sind über das Vervollständigungsmenü des Geräts selbst verifiziert; die
befüllte Ausgabe wird hier nicht wiedergegeben.
