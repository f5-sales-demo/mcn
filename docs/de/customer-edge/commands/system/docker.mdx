Docker führt die Plattformdienste aus. Kubernetes-Workloads befinden sich unter
[CRI-O](../crictl/).

## `docker-ps`

```bash
{"command":["docker-ps"]}
```

```text file=../../../../_data/sitecli-docker-ps.txt
```

<Aside type="tip" title="Drei Container sind die vollständige Liste, kein defekter Knoten">
`vpm`, `argo_watch` und `site-console`. Da der Großteil des Knotens unter CRI-O läuft, wirkt
ein kurzes `docker-ps` wie ein Fehler, wenn man hier Kubernetes-Workloads erwartet.
Das ist es nicht — dies ist die vollständige Menge der Docker-Container auf einem gesunden CE, und
die Anwesenheit von `vpm` mit dem Status `Up` ist die wichtigste Zeile auf dieser Seite.
</Aside>

## `docker-images`

```bash

```

Die Image-Tags geben die Plattformversion an, die der Knoten tatsächlich ausführt. Dies ist
es wert, mit dem von [`health`](../health/) gemeldeten Software-Build verglichen zu werden.

## `docker-inspect`

```bash
{"command":["docker-inspect","<container-id-or-name"]}
```

```text file=../../../../_data/sitecli-docker-inspect.txt
```

Akzeptiert sowohl einen Namen als auch eine ID, sodass `docker-inspect vpm` funktioniert und über
Neustarts hinweg stabil ist. Vollständiges JSON: Einhängepunkte, Umgebung, Neustart-Richtlinie und der Exit-Status.

## `docker-logs`

```bash
{"command":["docker-logs","<container-id-or-name>"]}
```

```text file=../../../../_data/sitecli-docker-logs.txt
```

`docker-logs vpm` ist der schnellste Weg zu Registrierungsfehlern. Für dieselben
Informationen mit Zeitstempeln und über Neustarts hinweg kann stattdessen
[`journalctl`](../journalctl/) verwendet werden.

## `docker-prune`

```bash
execcli docker-prune
```

Entfernt alle ungenutzten Docker-Objekte — gestoppte Container, ungenutzte Netzwerke, verwaiste Images und
den Build-Cache.

**Nur von der Appliance aus.** `docker-prune` ist nicht in der Debug-API verfügbar; es erfordert
[`execcli`](../../on-box/).

<Aside type="danger" title="Destruktiv und hier nicht erfasst">
Dieser Befehl löscht Zustand. Er steht auf der Ablehnungsliste des Harvest-Harness und wurde nie ausgeführt, daher
dokumentiert diese Seite ihn anhand der eigenen Katalog-Metadaten der Appliance, ohne Ausgabe zu zeigen.

Der CE-spezifische Hinweis: Dieser Knoten betreibt **zwei** Container-Laufzeitumgebungen. `docker-prune` betrifft
ausschließlich die Docker-Seite — `vpm`, `argo_watch` und `site-console` — und kann die
Kubernetes-Workloads unter [CRI-O](../crictl/) nicht erreichen. Die Rückgewinnung von Speicherplatz auf der CRI-O-Seite erfordert
einen anderen Befehl, `systemctl-start-crio-prune`, der in diesem Build nicht vorhanden ist.
</Aside>
