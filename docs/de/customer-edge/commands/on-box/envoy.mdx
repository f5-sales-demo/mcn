Aufgezeichnet am 28.07.2026 von einer CE dieses Deployments. Dies sind On-Box-Befehle, sie
laufen daher über die Site-CLI statt über die Debug-API; `sitecli/exec-catalog.json` erfasst die
Oberfläche und `sitecli/capture-manifest.json` erfasst, welcher Knoten verwendet wurde.

Envoy terminiert und proxyt Anwendungsdatenverkehr auf der Customer Edge. Diese vier Befehle
fragen dessen Admin-Schnittstelle ab, und keiner von ihnen ist Teil der
[Debug-API](../../../access/debug-api/).

<Aside type="note" title="Jeder dieser Befehle beginnt mit einer curl-Fortschrittsanzeige">
Es handelt sich um `curl`-Wrapper um den Admin-Endpunkt von Envoy, die ohne `-s` aufgerufen werden. Daher sind die ersten
zwei oder drei Zeilen jeder unten stehenden Aufzeichnung der von curl nach stderr geschriebene Übertragungsfortschritt:

```text
  % Total    % Received % Xferd  Average Speed   Time    Time     Time  Current
                                 Dload  Upload   Total   Spent    Left  Speed
  0     0    0     0 …
```

Das ist keine Envoy-Ausgabe und kein Fehler. Es ist zudem nützlich: Die Byte-Anzahl unter `% Received`
verrät Ihnen, ob Envoy überhaupt etwas zurückgegeben hat, was „keine Listener
konfiguriert" von „die Admin-Schnittstelle hat nicht geantwortet" unterscheidet.
</Aside>

## `envoy-listeners`

Jeder Listener, den Envoy installiert hat, als `name:address:port`.

```bash
execcli envoy-listeners
```

```text file=../../../../_data/sitecli-envoy-listeners.txt
```

**Worauf zu achten ist.** In diesem Deployment führt der Listener `10.250.0.10:80` — die VIP, die
die CE per BGP ankündigt. Diese eine Zeile verbindet drei Schichten miteinander: Wenn
[`show-ip-bgp-summary`](../../network/bgp/) zeigt, dass das Präfix angekündigt wird, dieser
Listener aber fehlt, wird die Route zu einem Knoten gezogen, der sie nicht bedienen wird — das ist
der schlimmste Fehlermodus in einem ECMP-Set, weil der Datenverkehr in ein schwarzes Loch lastverteilt wird.

Die abschließende `[fe80:…]:80` ist die Link-Local-Adresse der Schnittstelle, an die der Listener gebunden
ist.

**Was es Ihnen nicht verrät.** Nichts über die Upstream-Gesundheit — ein Listener existiert unabhängig davon,
ob irgendetwas dahinter erreichbar ist. Verwenden Sie dafür `envoy-clusters`.

## `envoy-clusters`

Jedes Cluster mit seinen Verbindungs- und Anfragelimits pro Priorität.

```bash
execcli envoy-clusters
```

```text file=../../../../_data/sitecli-envoy-clusters.txt
```

**Worauf zu achten ist.** Zeilen haben das Format `cluster::scope::key::value`. Der Eintrag `observability_name`
identifiziert jedes Cluster, und das Tripel aus `default_priority::max_connections`,
`max_pending_requests` und `max_requests` ist der Ort, an dem Anfragelimits sichtbar werden — ein Cluster,
das an seinem `max_pending_requests` festhängt, wird durch die Konfiguration gedrosselt und nicht durch den
Upstream.

## `envoy-config-dump`

Die vollständige Konfiguration von Envoy als JSON. Umfangreich: 126 KB auf einem ansonsten unbeschäftigten Demo-Knoten.

```bash
execcli envoy-config-dump
```

```text file=../../../../_data/sitecli-envoy-config-dump.txt
```

**Worauf zu achten ist.** Das Array `configs` auf oberster Ebene enthält ein Objekt pro Konfigurationstyp —
Bootstrap, Cluster, Listener, Routen, Secrets. Greifen Sie darauf zurück, wenn ein Listener oder Cluster
existiert, sich aber unerwartet verhält, und durchsuchen Sie es, statt es zu lesen.

## `envoy-hc-config-dump`

Speziell die Health-Check-Konfiguration.

```bash
execcli envoy-hc-config-dump
```

```text file=../../../../_data/sitecli-envoy-hc-config-dump.txt
```

**Worauf zu achten ist.** In diesem Deployment gibt der Befehl ein **einziges Byte** zurück — sichtbar als `100 1`
in der curl-Anzeige — was bedeutet, dass keine Health-Check-Konfiguration installiert ist. Das ist der erwartete
Zustand für eine CE ohne Origin-Pools mit Health-Checks, und es lohnt sich, das zu erkennen: Ein leeres
Ergebnis ist hier keine fehlgeschlagene Abfrage.
