Erfasst am 2026-07-28 von einem CE dieses Deployments. Hierbei handelt es sich um On-Box-Befehle, die über die Site CLI und nicht über die Debug-API ausgeführt werden; `sitecli/exec-catalog.json` dokumentiert die Oberfläche und `sitecli/capture-manifest.json` den jeweiligen Knoten.

Envoy beendet und vermittelt Anwendungsdatenverkehr auf dem Customer Edge. Diese vier Befehle
fragen seine Admin-Schnittstelle ab und sind nicht Teil der
[Debug-API](../../../access/debug-api/).

<Aside type="note" title="Jeder dieser Befehle beginnt mit einem curl-Fortschrittsanzeiger">
Es sind `curl`-Wrapper um Envoys Admin-Endpunkt, die ohne `-s` aufgerufen werden, sodass die ersten
zwei oder drei Zeilen jeder folgenden Aufzeichnung den von curl auf stderr geschriebenen Übertragungsfortschritt darstellen:

```text
  % Total    % Received % Xferd  Average Speed   Time    Time     Time  Current
                                 Dload  Upload   Total   Spent    Left  Speed
  0     0    0     0 …
```

Dies ist keine Envoy-Ausgabe und kein Fehler. Es ist zudem nützlich: Der Bytezähler `% Received`
zeigt an, ob Envoy überhaupt etwas zurückgegeben hat, was zwischen „keine Listener konfiguriert"
und „die Admin-Schnittstelle hat nicht geantwortet" unterscheidet.
</Aside>

## `envoy-listeners`

Alle von Envoy installierten Listener, im Format `name:address:port`.

```bash
execcli envoy-listeners
```

```text file=../../../../_data/sitecli-envoy-listeners.txt
```

**Worauf zu achten ist.** In diesem Deployment enthält der Listener `10.250.0.10:80` — die VIP, die der
CE in BGP bewirbt. Diese einzelne Zeile verbindet drei Schichten miteinander: Wenn
[`show-ip-bgp-summary`](../../network/bgp/) zeigt, dass das Präfix beworben wird, dieser
Listener jedoch fehlt, wird die Route zu einem Knoten angezogen, der sie nicht bedienen wird — dies ist
der schlimmste Fehlermodus in einem ECMP-Set, da der Datenverkehr lastverteilt in ein Black Hole geleitet wird.

Die abschließende Adresse `[fe80:…]:80` ist die link-lokale Adresse der Schnittstelle, an die der Listener gebunden ist.

**Was es nicht aussagt.** Nichts über den Upstream-Zustand — ein Listener existiert unabhängig davon,
ob etwas dahinter erreichbar ist. Verwenden Sie `envoy-clusters` dafür.

## `envoy-clusters`

Alle Cluster mit ihren verbindungs- und anfragebezogenen Limits je Priorität.

```bash
execcli envoy-clusters
```

```text file=../../../../_data/sitecli-envoy-clusters.txt
```

**Worauf zu achten ist.** Zeilen haben das Format `cluster::scope::key::value`. Der Eintrag `observability_name`
identifiziert jeden Cluster, und das Tripel `default_priority::max_connections`,
`max_pending_requests` und `max_requests` zeigt, wo Anfragelimits greifen — ein Cluster,
der sein `max_pending_requests`-Limit erreicht hat, wird durch die Konfiguration gedrosselt und nicht durch den Upstream.

## `envoy-config-dump`

Envoys vollständige Konfiguration als JSON. Umfangreich: 126 KB auf einem ansonsten unbeschäftigten Demo-Knoten.

```bash
execcli envoy-config-dump
```

```text file=../../../../_data/sitecli-envoy-config-dump.txt
```

**Worauf zu achten ist.** Das `configs`-Array auf oberster Ebene enthält je ein Objekt pro Konfigurationstyp —
Bootstrap, Cluster, Listener, Routen, Secrets. Greifen Sie darauf zurück, wenn ein Listener oder Cluster
zwar existiert, sich aber unerwartet verhält, und durchsuchen Sie es gezielt, anstatt es vollständig zu lesen.

## `envoy-hc-config-dump`

Die Konfiguration der Zustandsprüfungen (Health Checks) im Einzelnen.

```bash
execcli envoy-hc-config-dump
```

```text file=../../../../_data/sitecli-envoy-hc-config-dump.txt
```

**Worauf zu achten ist.** In diesem Deployment gibt es **ein einzelnes Byte** zurück — im `curl`-Fortschrittsanzeiger als `100 1` sichtbar —, was bedeutet, dass keine Konfiguration für Zustandsprüfungen installiert ist. Dies ist der erwartete
Zustand für einen CE ohne zustandsgeprüfte Origin Pools, und es lohnt sich, dies zu erkennen: Ein leeres
Ergebnis hier ist keine fehlgeschlagene Abfrage.
