Dieses Deployment demonstriert **Active/Active-Hochverfügbarkeit von Customer Edges in Azure**
ohne einen Azure Load Balancer vor den CEs. Drei CEs kündigen jeweils dieselbe Host-Route
per eBGP an, und der Azure Route Server installiert alle drei als gleichwertige Next Hops im
VNet. Damit ist das Routing-Fabric und nicht ein Load Balancer der Ort, an dem
Datenverkehrsverteilung und Entfernung ausgefallener Knoten stattfinden sollen.

Alles unten Gezeigte wurde gegen das laufende Deployment ausgeführt, und die Ausgabe ist die
Ausgabe, die es erzeugt hat. Was dieser Satz *nicht* abdeckt — Failover, wie sich der
Datenverkehr über die drei Next Hops verteilt und warum die VIP auf einem frischen Build
kurzzeitig Pakete verliert — wird ausdrücklich benannt statt stillschweigend vorausgesetzt.

## Was bereitgestellt wird

```text
                  Azure Route Server  ce-ha-lab-rrs  ASN 65515
                          10.0.4.4  and  10.0.4.5
                                      |
              +-----------------------+-----------------------+
              |                       |                       |
        eastus01-bgp            eastus02-bgp            eastus03-bgp     eBGP
              |                       |                       |      CE ASN 64512
        10.0.1.4                10.0.1.5                10.0.1.6     <- CE eth0 / SLO
     f5-xc-ce-vm-01          f5-xc-ce-vm-02          f5-xc-ce-vm-03
    ar-bgp-eastus01         ar-bgp-eastus02         ar-bgp-eastus03
              |                       |                       |
              +----- each advertises 10.250.0.10/32 -----------+
                          three-way ECMP into the VNet
```

| Bestandteil | Wie gebaut |
| --- | --- |
| F5 Distributed Cloud Tenant | `f5-sales-demo` — `https://f5-sales-demo.console.ves.volterra.io` |
| Namespaces | Sites in `system`; der Origin Pool und der Load Balancer in `multi-cloud-networking` |
| Customer Edges | 3 Single-Node-Secure-Mesh-v2-Sites — `ar-bgp-eastus01`, `ar-bgp-eastus02`, `ar-bgp-eastus03` |
| CE-Software | fixiert auf `9.2024.6`, Build `crt-20250613-3382` |
| Azure-VMs | `f5-xc-ce-vm-01/02/03`, je drei NICs (Management/SLO, extern, intern/SLI) |
| Routenaustausch | Azure Route Server `ce-ha-lab-rrs`, ASN `65515`, Instanzen `10.0.4.4` und `10.0.4.5` |
| Peerings | eines pro CE — `eastus01-bgp`, `eastus02-bgp`, `eastus03-bgp` — CE-ASN `64512` |
| Angekündigte VIP | `10.250.0.10/32`, von allen drei CEs identisch angekündigt |
| Load Balancer | `ar-bgp-ecmp-lb`, bedient die Domain `ar-bgp-ecmp.bankexample.com` |
| Testclient | `ar-ecmp-client`, eine VM innerhalb desselben VNet |
| Ressourcengruppe | `rg-mcn-ce-ha-rmordasiewicz` |

<Aside type="caution" title="Die VIP muss außerhalb jedes VNet-CIDR liegen">
`terraform/main.tf` enthält einen `check`-Block, der sicherstellt, dass die VIP außerhalb
sowohl des Hub- als auch des Spoke-CIDR liegt, und andernfalls den Plan verweigert. Die
angegebene Begründung: Eine VIP innerhalb eines VNet-CIDR unterliegt der systemeigenen Route
des VNet, obwohl die BGP-Route spezifischer ist.

Behandeln Sie diese Absicherung als verbindlich: Wenn Sie diese Demo auf eine andere
Adressierung umstellen, muss die VIP mit aus den VNet-Bereichen heraus wandern.
</Aside>

## Der Tenant ist Konfiguration, nicht das, was Ihre Shell gerade exportiert

`var.expected_xc_tenant` benennt den Tenant, hat den Standardwert `f5-sales-demo` und ist die
einzige Stelle, an der er benannt wird. `providers.tf` leitet daraus die `api_url` des
`xcsh`-Providers ab, was bewusst jede `XCSH_API_URL` aus der Umgebung überschreibt, und eine
`postcondition` in `terraform/main.tf` lässt den **Plan** fehlschlagen, wenn die Umgebung
einen anderen Tenant benennt.

Lesen Sie beide Hälften, ohne etwas auszuführen, das den Zustand verändert:

```bash
cd terraform
terraform output -raw xc_tenant       # what the deployment targets
terraform output -raw xc_env_tenant   # what your shell claims — diagnostic only
```

```text
f5-sales-demo
f5-sales-demo
```

<Aside type="danger" title="Diese Absicherung existiert, weil die Demo sich stillschweigend in den falschen Tenant umgesiedelt hat">
Die MCN-Demo wurde in `f5-sales-demo` gebaut. Später begann eine Credential-Datei, eine
`f5-amer-ent`-`XCSH_API_URL` zu exportieren; nachfolgende Applies erzeugten ein Token für
diesen Tenant, die CE-VMs registrierten sich dort neu, und ihre `f5-sales-demo`-Registrierungen
wurden aufgegeben. Jeder Plan dazwischen war sauber, weil nichts in der Konfiguration eine
Meinung zum Tenant hatte
([Issue 696](https://github.com/f5-sales-demo/mcn/issues/696), behoben in
[PR 697](https://github.com/f5-sales-demo/mcn/pull/697)). Die Wiederherstellung bedeutete, den
Stack im falschen Tenant zu zerstören und ihn im richtigen neu aufzubauen.

Das zu erkennende Symptom, weil es sich nicht selbst erklärt: Ein für einen anderen Tenant
erzeugtes Token scheitert am fixierten Endpunkt mit einem nackten `401`, was exakt wie ein
abgelaufenes Credential aussieht. Wenn ein Credential, das Sie für gültig halten, `401`
zurückgibt, vergleichen Sie die beiden obigen Ausgaben, bevor Sie ein weiteres Token erzeugen.
</Aside>

## Weisen Sie vor der Präsentation nach, dass alles gesund ist

Vier Prüfungen, in dieser Reihenfolge. Jede grenzt ein, wo ein Fehler liegen würde, sodass
ein Fehlschlag Ihnen etwas sagt und nicht nur, dass irgendetwas nicht stimmt.

<Steps>

1. **Alle drei Sites sind `ONLINE`.** Nichts weiter unten kann zutreffen, wenn das nicht gilt.

   ```bash
   for s in ar-bgp-eastus01 ar-bgp-eastus02 ar-bgp-eastus03; do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **Jedes Peering lernt die VIP-Ankündigung des jeweiligen CE.** Fragen Sie jedes Peering
   einzeln ab — siehe die Falle weiter unten, denn hier sieht die Demo am häufigsten kaputt
   aus, ohne es zu sein.

   ```bash
   for p in eastus01-bgp eastus02-bgp eastus03-bgp; do
     echo "--- $p"
     az network routeserver peering list-learned-routes \
       --name "$p" --routeserver ce-ha-lab-rrs -g rg-mcn-ce-ha-rmordasiewicz \
       --query "RouteServiceRole_IN_0[].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp

   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp

   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   Drei Peerings, drei verschiedene Next Hops, ein Präfix. Damit ist die Ankündigungsseite
   von ECMP nachgewiesen.

3. **Die effektiven Routen des Clients führen alle drei Next Hops.** Das ist ECMP selbst,
   so wie das VNet es programmiert hat — nicht das, was die CEs behaupten, sondern das, was
   Azure daraus gemacht hat.

   ```bash
   az network nic show-effective-route-table \
     --name ar-ecmp-clientVMNic -g rg-mcn-ce-ha-rmordasiewicz \
     --query "value[?addressPrefix[0]=='10.250.0.10/32']" -o json
   ```

   ```json
   [
     {
       "addressPrefix": ["10.250.0.10/32"],
       "nextHopIpAddress": ["10.0.1.5", "10.0.1.4", "10.0.1.6"],
       "nextHopType": "VirtualNetworkGateway",
       "source": "VirtualNetworkGateway",
       "state": "Active"
     }
   ]
   ```

   `state: Active` mit drei Einträgen in `nextHopIpAddress` ist die Prüfung. **Die Reihenfolge
   dieser drei ist nicht bedeutsam und nicht stabil** — Azure gibt sie zwischen Aufrufen in
   unterschiedlicher Reihenfolge zurück, zählen Sie sie also, statt die Liste mit einem
   früheren Lauf zu vergleichen. Ein Next Hop, wo Sie drei erwarten, bedeutet, dass ein CE
   die Ankündigung eingestellt hat, und Schritt 2 zeigt, welcher.

4. **Die VIP bedient Datenverkehr.** Von der Client-VM aus und **mit dem `Host`-Header** —
   siehe die zweite Falle weiter unten. Nehmen Sie genug Anfragen, um ein Problem zu sehen:
   ein paar Dutzend lesen sich selbst während des weiter unten beschriebenen
   Konvergenzfensters als 100 %.

   ```bash
   az vm run-command invoke -g rg-mcn-ce-ha-rmordasiewicz -n ar-ecmp-client \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts 'ok=0; fail=0
                for i in $(seq 1 60); do
                  c=$(curl -s -o /dev/null -m 5 -w "%{http_code}" \
                        -H "Host: ar-bgp-ecmp.bankexample.com" http://10.250.0.10/)
                  [ "$c" = 200 ] && ok=$((ok+1)) || fail=$((fail+1))
                done
                echo "OK=$ok FAIL=$fail"'
   ```

   ```text
   OK=60 FAIL=0
   ```

</Steps>

## Falle: Ein Peering zeigt eine Route, und das ist korrekt

`list-learned-routes` ist auf das Peering beschränkt, das Sie benennen. Es meldet, was
**dieser** Peer angekündigt hat, nicht die gesamte Tabelle des Route Servers.

Eine alleinige Abfrage von `eastus01-bgp` liefert daher eine einzige `10.250.0.10/32` über
`10.0.1.4`, und es ist verlockend, das als „nur ein CE kündigt an — die anderen beiden sind
ausgefallen“ zu lesen. Nichts ist ausgefallen. Die anderen beiden Ankündigungen sind auf
ihren eigenen Peerings sichtbar, und genau darüber iteriert Schritt 2 oben.

ECMP lässt sich aus einer einzelnen Peering-Abfrage nicht bestätigen. Iterieren Sie entweder
über alle drei Peerings oder lesen Sie die effektive Routentabelle des Clients, die das
zusammengeführte Ergebnis in einem einzigen Aufruf zeigt.

## Falle: Eine Anfrage an die nackte IP liefert 404

Der Load Balancer matcht auf `Host`. Die VIP ist kein virtueller Server, der jedem etwas
ausliefert, der sich mit der Adresse verbindet.

```text
curl -H 'Host: ar-bgp-ecmp.bankexample.com' http://10.250.0.10/   ->  200   (10 of 10)
curl                                        http://10.250.0.10/   ->  404
```

Beides wurde im selben Lauf gegen das gesunde Deployment erzeugt. **Ein 404 auf die nackte IP
ist der Beweis, dass der Pfad funktioniert** — die Anfrage hat den CE erreicht, der Proxy des
CE hat geantwortet und abgelehnt, weil keine konfigurierte Domain passte. Das als Ausfall zu
lesen, schickt Sie zu BGP, wo Sie nichts Fehlerhaftes finden werden.

Dasselbe gilt während einer Demo: Wenn Sie die Adresse in einen Browser eingeben, statt die
Domain darauf aufzulösen, erhalten Sie den 404.

## Die VIP verwirft in den ersten drei Vierteln einer Stunde Anfragen, danach nicht mehr

Auf einem frisch gebauten Stack verliert die VIP für etwa die ersten 45 Minuten, nachdem die
CEs `ONLINE` erreicht haben, einen kleinen Bruchteil der Anfragen und liefert danach sauber
aus. Gemessen über 1.470 Anfragen von `ar-ecmp-client`, alle mit dem `Host`-Header:

| Zeitfenster | Anfragen | Fehlschläge | Rate |
| --- | --- | --- | --- |
| Erste ~45 Minuten, nachdem ECMP stand | 570 | 12 | **2,11 %** |
| Die folgenden 23 Minuten | 900 | **0** | **0,00 %** |

Jeder Fehlschlag war `curl: (28)` — ein Timeout ohne empfangene Bytes — kein HTTP-Fehlerstatus.
Der letzte trat rund 43 Minuten nach dem Hochkommen von ECMP auf. Von den 900 sauberen Anfragen
liefen 400 mit einem 30-Sekunden-Timeout, und jede einzelne war in unter 2 Sekunden fertig, es
wurde also nichts durch ein zu kurzes Timeout verdeckt.

**Der Origin war nicht die Ursache.** Ein Kontrolldurchlauf direkt zum Origin
(`http://20.98.232.135/`, unter Umgehung der VIP) lief *gleichzeitig* mit fehlschlagenden
VIP-Durchläufen 120 von 120 sauber. Der Fehler liegt irgendwo im Pfad aus VIP, ECMP oder CE.

Zwei Dinge, die hier bewusst nicht behauptet werden:

- **Es ist kein Dauerzustandsfehler.** Er verschwindet vollständig und bleibt weg. Eine Demo,
  die seit einer Stunde läuft, hat dieses Problem nicht — 60 von 60 bei der obigen Prüfung, und
  es reproduzierte sich auch auf dem neu gebauten Stack sauber.
- **Er lässt sich keinem bestimmten CE zuordnen.** Nichts in dieser Topologie liefert einen
  HTTP-Listener pro Knoten, es gibt also keine Möglichkeit, eine verworfene Anfrage dem Knoten
  zuzuordnen, der sie verworfen hat. Die externen Schnittstellen der CEs (`10.0.2.x`) haben
  überhaupt keinen HTTP-Listener — nur die VIP `/32` antwortet.

Er reproduzierte sich bei einem sauberen Neuaufbau in einem anderen Tenant, folgt also der
Topologie und nicht der Umgebung.

<Aside type="caution" title="Ziehen Sie keine 40 Anfragen als Stichprobe und schließen Sie daraus, dass alles in Ordnung ist">
Durchläufe von 40 bis 50 Anfragen lesen sich meistens auch innerhalb des fehlerhaften Fensters
als 100 %. So wurde das hier zunächst als anhaltender Fehler mit niedriger Rate und dann als
gar kein Fehler falsch charakterisiert. Nehmen Sie 100 oder mehr Anfragen, in zeitlich
getrennten Durchläufen.
</Aside>

## Die Registrierungsfreigabe ist automatisiert, und das Apply bleibt zweiphasig

Die Registrierungsfreigabe benötigt keinen Menschen mehr in der Konsole. Auf Provider
**v3.81.1** übernimmt das die Ressource `xcsh_registration_approval`, und das Site-Modul
ermittelt, welche Registrierung freizugeben ist.

Damit wird das Deployment trotzdem kein einzelnes, unbeaufsichtigtes `apply`, und der Grund
lohnt sich zu verstehen, bevor Sie einen ersten Lauf beobachten und daraus schließen, er sei
fehlgeschlagen:

- Das Registrierungsobjekt eines CE heißt **`r-<uuid>`**. Es wird nie nach der Site benannt,
  also kann nichts den Namen zur Planzeit vorhersagen.
- Die Registrierung existiert erst, nachdem die VM gebootet ist und `vpm` sich registriert hat.
- Daher plant das **erste Apply überhaupt keine Freigabe**. Führen Sie ein erneutes Apply aus,
  sobald sich die CEs registriert haben und die Freigaben angelegt sind.

`terraform/main.tf` dokumentiert diese Reihenfolge oben in der Datei, und das ist die
maßgebliche Fassung — die Deploy-Sequenz lebt beim Code, der sie umsetzt.

<Aside type="caution" title="Eine brandneue Site ist über die Operate-API nicht sofort erreichbar">
Für etwa 25 bis 30 Minuten, nachdem eine neue Site `ONLINE` meldet, antworten die
`vpm/debug`-Endpunkte mit einer BIG-IP-`503`-Seite mit dem Text `The requested URL was rejected`.
Das sieht aus wie eine Blockade durch eine Web Application Firewall oder ein widerrufenes Token
und ist beides nicht. Warten Sie und versuchen Sie es erneut.

Das betrifft eine frisch gebaute Demo, nicht eine laufende.
</Aside>

## Zugriff auf die Site-CLI

Routinemäßige Diagnosen auf dem Gerät laufen über die Debug-API, die hier bereits skriptgestützt
ist. Bestätigen Sie, dass die Kommandooberfläche noch dem entspricht, was die Dokumentation
beschreibt:

```bash
bash scripts/capture-sitecli.sh --check --site ar-bgp-eastus01 --node f5-xc-ce-vm-01
```

```text
catalog matches the live CE (build crt-20250613-3382, 34 commands)
```

`--check` schreibt nichts und ist daher gegen die laufende Demo unbedenklich.

Für die Befehle, die diese API nicht weiterleitet, verfügt dieses Deployment außerdem über
**Operator-SSH auf das Appliance-Konto `admin`**, dessen Login-Shell die Site-CLI ist. Das ist
auf allen drei CEs verifiziert. Verbinden Sie sich von einem Host innerhalb des VNet aus mit der
internen (SLI-)Adresse und mit zugewiesenem Terminal.

<Aside type="danger" title="Codieren Sie niemals eine interne CE-Adresse fest — sie werden bei jedem Neuaufbau neu vergeben">
Azure bewahrt nicht, welcher CE welche Adresse im internen Subnetz erhält. Nach dem jüngsten
Neuaufbau halten `f5-xc-ce-vm-01`, `-02` und `-03` jeweils `10.0.3.7`, `10.0.3.5` und `10.0.3.4`:
nicht in Knotenreihenfolge, nicht zusammenhängend und anders als zuvor. Die NIC des Testclients
liegt im selben Subnetz und hatte bereits eine Adresse inne, die zuvor ein CE hielt.

Lesen Sie sie aus, statt sie sich zu merken:

```bash
cd terraform
terraform output -json ce_sli_private_ips
```

```json
{"eastus01":"10.0.3.7","eastus02":"10.0.3.5","eastus03":"10.0.3.4"}
```

Ohne Terraform-State zur Hand fragen Sie Azure nach der gewünschten Adresse über den NIC-Namen,
der *stabil* ist:

```bash
az network nic show -g rg-mcn-ce-ha-rmordasiewicz \
  -n f5-xc-ce-vm-01-internal-nic \
  --query ipConfigurations[0].privateIPAddress -o tsv
```

</Aside>

```bash
SLI=$(terraform output -json ce_sli_private_ips | jq -r '.eastus01')
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<vm-in-vnet> "admin@$SLI"
```

```text
Registration Status: PROVISIONED
SLO IP: 10.0.1.4/26
WELCOME IN SITE CLI
```

<Aside type="caution" title="Dieser Zugang existiert, weil diese CEs damit gebaut wurden — er lässt sich nicht nachträglich hinzufügen">
Der Operator-Schlüssel wird von cloud-init `write_files` geschrieben, was einmalig beim ersten
Boot läuft. `custom_data` ist nur ersetzbar, weshalb eine nachträgliche Übernahme auf bereits
laufenden CEs **jede CE-VM ersetzt**. Das ist ein Flotten-Neuaufbau, keine Konfigurationsänderung.

Früher war es noch schlimmer: Ein ersetzter CE konnte sich nie neu registrieren, weil die
Registrierung des zerstörten Knotens weiterhin den eindeutigen Index
`(tenant, cluster_name, hostname)` der Control Plane hielt — und `terraform plan` meldete die
gesamte Zeit, in der die Flotte ausgefallen war, „No changes“. Die Wiederherstellung erforderte
zwei vollständige Neuaufbauten. Das ist behoben
([Issue 674](https://github.com/f5-sales-demo/mcn/issues/674), geschlossen durch
[PR 693](https://github.com/f5-sales-demo/mcn/pull/693)): Der Lebenszyklus des Site-Objekts ist
nun an die CE-VM-Instanz gekoppelt, sodass das Ersetzen der VM die Site ersetzt und das Löschen
der Site ihre Registrierungen mitnimmt, bevor der Ersatzknoten bootet.

Für dieses Deployment ist die Änderung bereits angewendet und die Flotte gesund. Wer sie
anderswo übernimmt, sollte zuerst die [SSH-Seite](../customer-edge/access/ssh/) lesen.
</Aside>

## Zwei weitere Messfallen

Beide haben in dieser Umgebung selbstbewusst falsche Antworten geliefert, und keine davon ist
offensichtlich.

- **Testen Sie von innerhalb des VNet, nicht von Ihrer Workstation.** Netskope schließt den
  TCP-Handshake auf gängigen Ports selbst ab, weshalb eine Workstation-Prüfung einen Port als
  **offen** meldet, der tatsächlich geschlossen ist. Die Ports 80 und 443 erscheinen von einer
  Workstation aus auf den öffentlichen CE-Adressen als offen und sind geschlossen, wenn man von
  innerhalb des VNet prüft. Verwenden Sie `ar-ecmp-client`.
- **Port 22 auf einem CE antwortet nur auf der internen (SLI-)Adresse.** Von `ar-ecmp-client`
  aus geprüft, liefert die interne Adresse jedes CE `SSH-2.0-OpenSSH_8.7`, während seine
  Management- und externen Adressen in ein Timeout laufen — ebenso wie eine ungenutzte Adresse,
  die als Kontrolle verwendet wurde. eth0 ist in `a-i-eth0` umbenannt und trägt keine Host-IP,
  weil der Datenpfad sie besitzt. Eine Prüfung der Adresse, unter der Sie den Knoten kennen,
  sagt Ihnen also nichts über den SSH-Zustand des Knotens, und die SLI-Adresse ist diejenige,
  mit der Sie sich verbinden. Nehmen Sie diese Adresse aus
  `terraform output -json ce_sli_private_ips`; gehen Sie nicht davon aus, dass das interne
  Subnetz nur CEs enthält, denn die NIC des Testclients liegt ebenfalls darin.

<Aside type="note" title="Was diese Seite nicht behauptet">
Drei Dinge, die Leserinnen und Leser hier berechtigterweise erwarten könnten, fehlen, weil sie
gegen das Deployment nicht durchgeführt wurden:

- **Failover wurde nicht getestet.** Die drei gleichwertigen Next Hops sind nachweislich
  installiert; was mit der Routentabelle geschieht, wenn ein CE gestoppt wird, ist nicht
  gezeigt — proben Sie also keine Failover-Demo auf Basis dieser Seite, ohne es vorher
  auszuprobieren.
- **Die Verteilung des Datenverkehrs über die drei Next Hops wurde nicht gemessen.** Oben sind
  1.470 Anfragen an die VIP erfasst, was belegt, dass der Pfad funktioniert und wie er sich über
  die Zeit verhält. Nichts davon zeigt, wie sich diese Anfragen über die drei Next Hops verteilt
  haben, und diese Topologie bietet keinen HTTP-Listener pro Knoten, um sie zuzuordnen.
- **Die Ursache des Konvergenz-Transienten ist nicht geklärt.** Er ist charakterisiert — wann er
  auftritt, wie lange, dass der Origin durchgehend sauber ist — aber nicht erklärt.

</Aside>
