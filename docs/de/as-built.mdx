Diese Bereitstellung demonstriert **Active/Active-Hochverfügbarkeit von Customer Edges in Azure**
ohne einen Azure-Load-Balancer vor den CEs. Drei CEs speisen jeweils dieselbe Host-Route
per eBGP ein, und der Azure Route Server installiert alle drei als gleichwertige Next-Hops im
VNet. Die Routing-Fabric — und nicht ein Load Balancer — ist somit der Ort, an dem
Datenverkehrsverteilung und das Entfernen ausgefallener Knoten stattfinden sollen.

Alles Nachfolgende wurde gegen die laufende Bereitstellung ausgeführt, und die Ausgabe ist die
tatsächlich erzeugte Ausgabe. Zwei Dinge, die dieser Satz *nicht* abdeckt — Failover und
Datenverkehrsverteilung — werden am Ende explizit benannt, statt sie stillschweigend vorauszusetzen.

## Was bereitgestellt wird

```text
                  Azure Route Server  ce-ha-lab-rrs  ASN 65515
                          10.0.4.4  and  10.0.4.5
                                      |
              +-----------------------+-----------------------+
              |                       |                       |
        eastus01-bgp            eastus02-bgp            eastus03-bgp     eBGP
              |                       |                       |      CE ASN 64512
        10.0.1.4                10.0.1.5                10.0.1.6     <- CE eth0 / SLO
     f5-xc-ce-vm-01          f5-xc-ce-vm-02          f5-xc-ce-vm-03
    ar-bgp-eastus01         ar-bgp-eastus02         ar-bgp-eastus03
              |                       |                       |
              +----- each advertises 10.250.0.10/32 -----------+
                          three-way ECMP into the VNet
```

| Bestandteil | Wie gebaut |
| --- | --- |
| Customer Edges | 3 Single-Node-Secure-Mesh-v2-Standorte — `ar-bgp-eastus01`, `ar-bgp-eastus02`, `ar-bgp-eastus03` |
| CE-Software | fixiert auf `9.2024.6`, Build `crt-20250613-3382` |
| Azure-VMs | `f5-xc-ce-vm-01/02/03`, je drei NICs (Management/SLO, extern, intern/SLI) |
| Routenaustausch | Azure Route Server `ce-ha-lab-rrs`, ASN `65515`, Instanzen `10.0.4.4` und `10.0.4.5` |
| Peerings | eines pro CE — `eastus01-bgp`, `eastus02-bgp`, `eastus03-bgp` — CE-ASN `64512` |
| Angekündigter VIP | `10.250.0.10/32`, von allen drei CEs identisch eingespeist |
| Load Balancer | `ar-bgp-ecmp-lb`, bedient die Domain `ar-bgp-ecmp.bankexample.com` |
| Testclient | `ar-ecmp-client`, eine VM innerhalb desselben VNet |
| Ressourcengruppe | `rg-mcn-ce-ha-rmordasiewicz` |

<Aside type="caution" title="Der VIP muss außerhalb jedes VNet-CIDR liegen">
`terraform/main.tf` enthält einen `check`-Block, der sicherstellt, dass der VIP außerhalb sowohl
des Hub- als auch des Spoke-CIDR liegt, und andernfalls den Plan verweigert. Die angegebene Begründung
lautet, dass ein VIP innerhalb eines VNet-CIDR gegen die systemeigene Route des VNet verliert,
obwohl die BGP-Route spezifischer ist.

Behandeln Sie die Absicherung als verbindliche Vorgabe: Wenn Sie diese Demo auf eine andere
Adressierung umstellen, muss der VIP entsprechend aus den VNet-Bereichen herauswandern.
</Aside>

## Vor der Präsentation die Funktionsfähigkeit nachweisen

Vier Prüfungen, in dieser Reihenfolge. Jede grenzt ein, wo ein Fehler liegen würde, sodass ein
Fehlschlag Ihnen etwas verrät und nicht nur, dass irgendetwas nicht stimmt.

<Steps>

1. **Alle drei Standorte sind `ONLINE`.** Nichts Nachgelagertes kann zutreffen, wenn dies nicht gilt.

   ```bash
   for s in ar-bgp-eastus01 ar-bgp-eastus02 ar-bgp-eastus03; do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **Jedes Peering lernt die VIP-Ankündigung des jeweiligen CE.** Fragen Sie jedes Peering
   einzeln ab — siehe die Falle weiter unten, denn genau hier wirkt die Demo am häufigsten
   defekt, ohne es zu sein.

   ```bash
   for p in eastus01-bgp eastus02-bgp eastus03-bgp; do
     echo "--- $p"
     az network routeserver peering list-learned-routes \
       --name "$p" --routeserver ce-ha-lab-rrs -g rg-mcn-ce-ha-rmordasiewicz \
       --query "RouteServiceRole_IN_0[].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp

   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp

   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   Drei Peerings, drei verschiedene Next-Hops, ein Präfix. Damit ist die Ankündigungsseite
   von ECMP nachgewiesen.

3. **Die effektiven Routen des Clients enthalten alle drei Next-Hops.** Das ist ECMP selbst,
   so wie das VNet es programmiert hat — nicht das, was die CEs behaupten, sondern das, was Azure
   daraus gemacht hat.

   ```bash
   az network nic show-effective-route-table \
     --name ar-ecmp-clientVMNic -g rg-mcn-ce-ha-rmordasiewicz \
     --query "value[?addressPrefix[0]=='10.250.0.10/32']" -o json
   ```

   ```json
   [
     {
       "addressPrefix": ["10.250.0.10/32"],
       "nextHopIpAddress": ["10.0.1.5", "10.0.1.4", "10.0.1.6"],
       "nextHopType": "VirtualNetworkGateway",
       "source": "VirtualNetworkGateway",
       "state": "Active"
     }
   ]
   ```

   `state: Active` mit drei Einträgen in `nextHopIpAddress` ist die Prüfung. Ein einzelner
   Next-Hop, wo Sie drei erwarten, bedeutet, dass ein CE die Ankündigung eingestellt hat —
   und Schritt 2 zeigt, welcher.

4. **Der VIP bedient Datenverkehr.** Von der Client-VM aus und **mit dem `Host`-Header** — siehe
   die zweite Falle weiter unten.

   ```bash
   az vm run-command invoke -g rg-mcn-ce-ha-rmordasiewicz -n ar-ecmp-client \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts 'for i in $(seq 1 10); do
                  curl -s -o /dev/null -w "%{http_code} " \
                    -H "Host: ar-bgp-ecmp.bankexample.com" http://10.250.0.10/
                done'
   ```

   ```text
   200 200 200 200 200 200 200 200 200 200
   ```

</Steps>

## Falle: Ein Peering zeigt eine Route — und das ist korrekt

`list-learned-routes` bezieht sich ausschließlich auf das genannte Peering. Es meldet, was
**dieser** Peer angekündigt hat, nicht die gesamte Tabelle des Route Servers.

Eine alleinige Abfrage von `eastus01-bgp` liefert daher ein einzelnes `10.250.0.10/32` über
`10.0.1.4`, und man ist versucht, das als „nur ein CE kündigt an — die anderen beiden sind
ausgefallen" zu lesen. Es ist nichts ausgefallen. Die beiden anderen Ankündigungen sind auf ihren
eigenen Peerings sichtbar, und genau darüber iteriert Schritt 2 oben.

ECMP lässt sich nicht anhand der Abfrage eines einzelnen Peerings bestätigen. Iterieren Sie
entweder über alle drei Peerings oder lesen Sie die effektive Routentabelle des Clients, die das
zusammengeführte Ergebnis in einem einzigen Aufruf zeigt.

## Falle: Eine Anfrage an die nackte IP liefert 404

Der Load Balancer trifft die Zuordnung anhand von `Host`. Der VIP ist kein virtueller Server,
der jedem, der die Adresse ansteuert, irgendetwas ausliefert.

```text
curl -H 'Host: ar-bgp-ecmp.bankexample.com' http://10.250.0.10/   ->  200   (10 of 10)
curl                                        http://10.250.0.10/   ->  404
```

Beide Ergebnisse stammen aus demselben Durchlauf gegen die fehlerfreie Bereitstellung. **Ein
404 auf die nackte IP ist der Beweis, dass der Pfad funktioniert** — die Anfrage hat den CE
erreicht, der Proxy des CE hat geantwortet und abgelehnt, weil keine konfigurierte Domain passte.
Wer das als Ausfall liest, sucht bei BGP nach Fehlern und findet dort nichts.

Dasselbe gilt während einer Demo: Wenn Sie die Adresse in einen Browser eingeben, statt die
Domain darauf aufzulösen, erhalten Sie den 404.

## Die Registrierungsfreigabe ist automatisiert, und das Apply bleibt zweistufig

Die Registrierungsfreigabe erfordert keinen Menschen mehr in der Konsole. Ab Provider-Version
**v3.81.1** übernimmt die Ressource `xcsh_registration_approval` diese Aufgabe, und das
Standortmodul ermittelt, welche Registrierung freizugeben ist.

Damit wird die Bereitstellung trotzdem nicht zu einem einzigen unbeaufsichtigten `apply`, und der
Grund dafür ist es wert, verstanden zu werden, bevor Sie einen ersten Durchlauf beobachten und
daraus schließen, er sei fehlgeschlagen:

- Das Registrierungsobjekt eines CE heißt **`r-<uuid>`**. Es wird nie nach dem Standort benannt,
  sodass sich der Name zur Planungszeit nicht vorhersagen lässt.
- Die Registrierung existiert erst, nachdem die VM gebootet hat und `vpm` sich registriert hat.
- Daher **plant das erste Apply überhaupt keine Freigabe**. Führen Sie erneut ein Apply aus,
  sobald die CEs registriert sind und die Freigaben erstellt wurden.

`terraform/main.tf` dokumentiert diese Reihenfolge am Anfang der Datei — das ist die maßgebliche
Fassung, denn die Bereitstellungsreihenfolge lebt beim Code, der sie umsetzt.

<Aside type="caution" title="Ein brandneuer Standort ist über die Operate-API nicht sofort erreichbar">
Etwa 25 bis 30 Minuten lang, nachdem ein neuer Standort `ONLINE` meldet, antworten die
`vpm/debug`-Endpunkte mit einer BIG-IP-`503`-Seite mit dem Text `The requested URL was rejected`.
Das sieht nach einer Blockade durch eine Web Application Firewall oder einem widerrufenen Token
aus und ist beides nicht. Warten Sie und versuchen Sie es erneut.

Das betrifft eine frisch aufgebaute Demo, nicht eine laufende.
</Aside>

## Zugriff auf die Site CLI

Routinemäßige Diagnosen auf dem Gerät laufen über die Debug-API, die hier bereits skriptgesteuert
ist. Prüfen Sie, ob der Befehlsumfang weiterhin dem entspricht, was die Dokumentation beschreibt:

```bash
bash scripts/capture-sitecli.sh --check --site ar-bgp-eastus01 --node f5-xc-ce-vm-01
```

```text
catalog matches the live CE (build crt-20250613-3382, 34 commands)
```

`--check` schreibt nichts und ist daher gegenüber der laufenden Demo unbedenklich.

Für die Befehle, die diese API nicht weiterleitet, verfügt diese Bereitstellung zusätzlich über
**Operator-SSH zum Appliance-Konto `admin`**, dessen Login-Shell die Site CLI ist. Dies ist auf
allen drei CEs verifiziert. Verbinden Sie sich von einem Host innerhalb des VNet mit der internen
(SLI-)Adresse und einem zugewiesenen Terminal:

```bash
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<vm-in-vnet> admin@10.0.3.5
```

```text
WELCOME IN SITE CLI
Registration Status: PROVISIONED
```

<Aside type="caution" title="Dieser Zugang existiert, weil diese CEs damit gebaut wurden — er lässt sich nicht nachträglich hinzufügen">
Der Operator-Schlüssel wird über cloud-init `write_files` geschrieben, was einmalig beim ersten
Boot ausgeführt wird. `custom_data` ist ausschließlich ersetzbar, sodass die nachträgliche Übernahme
auf bereits laufenden CEs jede CE-VM ersetzt — und das Ersetzen einer einzelnen blockiert derzeit
die Registrierung, während `terraform plan` „No changes" meldet
([Issue 674](https://github.com/f5-sales-demo/mcn/issues/674)). Die Wiederherstellung erforderte
zwei vollständige Neuaufbauten.

Für diese Bereitstellung ist die Änderung bereits angewendet und die Flotte ist fehlerfrei. Wer
sie andernorts übernehmen möchte, sollte zuerst die
[SSH-Seite](../customer-edge/access/ssh/) lesen.
</Aside>

## Zwei weitere Messfallen

Beide haben in dieser Umgebung überzeugend falsche Antworten erzeugt, und keine davon ist
offensichtlich.

- **Prüfen Sie aus dem VNet heraus, nicht von Ihrer Workstation.** Netskope schließt den
  TCP-Handshake auf gängigen Ports selbst ab, sodass eine Prüfung von der Workstation aus einen
  Port als **offen** meldet, der tatsächlich geschlossen ist. Die Ports 80 und 443 erscheinen von
  einer Workstation aus an den öffentlichen CE-Adressen als offen und sind geschlossen, wenn sie
  aus dem VNet heraus geprüft werden. Verwenden Sie `ar-ecmp-client`.
- **Port 22 auf einem CE antwortet ausschließlich auf der internen (SLI-)Adresse.** Von
  `ar-ecmp-client` aus gegen die drei CEs geprüft, liefern `10.0.3.5`, `10.0.3.6` und `10.0.3.7`
  alle `SSH-2.0-OpenSSH_8.7`, während die Management- und externen Adressen in ein Timeout laufen —
  ebenso wie eine ungenutzte Adresse, die als Kontrolle diente. eth0 wird in `a-i-eth0` umbenannt
  und trägt keine Host-IP, weil der Datenpfad sie besitzt. Eine Prüfung der Adresse, unter der Sie
  den Knoten kennen, sagt also nichts über den SSH-Zustand des Knotens aus; die SLI-Adresse ist
  diejenige, zu der Sie sich verbinden.

<Aside type="note" title="Was diese Seite nicht behauptet">
Zwei Dinge, die Leserinnen und Leser hier berechtigterweise erwarten könnten, fehlen bewusst, weil
sie gegen die Bereitstellung nicht durchgeführt wurden:

- **Failover wurde nicht getestet.** Die drei gleichwertigen Next-Hops sind nachweislich installiert;
  was mit der Routentabelle passiert, wenn ein CE gestoppt wird, wird nicht gezeigt. Proben Sie
  daher keine Failover-Demo auf Basis dieser Seite, ohne es zuvor auszuprobieren.
- **Die Datenverkehrsverteilung wurde nicht gemessen.** Zehn von zehn Anfragen an den VIP lieferten
  `200`, was beweist, dass der Pfad funktioniert. Es zeigt nicht, wie sich diese zehn auf die drei
  Next-Hops verteilt haben.

</Aside>
