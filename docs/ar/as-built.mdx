يوضّح هذا النشر **التوافر العالي النشط/النشط لـ Customer Edge في Azure**
دون وجود موازن تحميل Azure أمام الـ CEs. تُنشئ ثلاث CEs المسار المضيف نفسه
عبر eBGP، ويقوم Azure Route Server بتثبيت الثلاثة جميعًا كقفزات تالية متساوية التكلفة داخل
الـ VNet. وبالتالي فإن نسيج التوجيه، وليس موازن التحميل، هو المكان الذي يُفترض أن يحدث فيه توزيع
حركة المرور وإزالة العقد المعطّلة.

كل ما هو معروض أدناه تم تشغيله مقابل النشر الحي، والمخرجات هي المخرجات التي
أنتجها. الأمران اللذان *لا* تشملهما تلك الجملة — تجاوز الفشل وتوزيع حركة المرور —
يُشار إليهما في النهاية بدلًا من تركهما للافتراض.

## ما الذي تم نشره

```text
                  Azure Route Server  ce-ha-lab-rrs  ASN 65515
                          10.0.4.4  and  10.0.4.5
                                      |
              +-----------------------+-----------------------+
              |                       |                       |
        eastus01-bgp            eastus02-bgp            eastus03-bgp     eBGP
              |                       |                       |      CE ASN 64512
        10.0.1.4                10.0.1.5                10.0.1.6     <- CE eth0 / SLO
     f5-xc-ce-vm-01          f5-xc-ce-vm-02          f5-xc-ce-vm-03
    ar-bgp-eastus01         ar-bgp-eastus02         ar-bgp-eastus03
              |                       |                       |
              +----- each advertises 10.250.0.10/32 -----------+
                          three-way ECMP into the VNet
```

| العنصر | كما تم بناؤه |
| --- | --- |
| Customer Edges | 3 مواقع Secure Mesh v2 أحادية العقدة — `ar-bgp-eastus01`، `ar-bgp-eastus02`، `ar-bgp-eastus03` |
| برنامج CE | مثبّت على `9.2024.6`، الإصدار `crt-20250613-3382` |
| أجهزة Azure الافتراضية | `f5-xc-ce-vm-01/02/03`، ثلاث بطاقات NIC لكل منها (الإدارة/SLO، الخارجية، الداخلية/SLI) |
| تبادل المسارات | Azure Route Server `ce-ha-lab-rrs`، ASN `65515`، النسخ `10.0.4.4` و`10.0.4.5` |
| الاقترانات (Peerings) | واحد لكل CE — `eastus01-bgp`، `eastus02-bgp`، `eastus03-bgp` — CE ASN `64512` |
| الـ VIP المُعلن | `10.250.0.10/32`، يُنشأ بشكل متطابق من الـ CEs الثلاثة جميعًا |
| موازن التحميل | `ar-bgp-ecmp-lb`، يخدم النطاق `ar-bgp-ecmp.bankexample.com` |
| عميل الاختبار | `ar-ecmp-client`، جهاز افتراضي داخل الـ VNet نفسه |
| مجموعة الموارد | `rg-mcn-ce-ha-rmordasiewicz` |

<Aside type="caution" title="يجب أن يقع الـ VIP خارج كل نطاق CIDR للـ VNet">
يحتوي `terraform/main.tf` على كتلة `check` تؤكد أن الـ VIP يقع خارج نطاقي CIDR لكل من الـ hub
والـ spoke، وترفض الخطة في غير ذلك. والسبب المذكور هو أن VIP داخل نطاق CIDR الخاص بـ
VNet يخسر أمام مسار النظام الخاص بالـ VNet رغم أن مسار BGP أكثر تحديدًا.

تعامل مع هذا الضمان كعقد: إذا أعدت توجيه هذا العرض التوضيحي إلى عناوين مختلفة، فيجب أن ينتقل
الـ VIP خارج نطاقات الـ VNet معها.
</Aside>

## أثبت سلامته قبل التقديم

أربعة فحوصات، بهذا الترتيب. كل واحد منها يضيّق نطاق موضع العطل، بحيث يخبرك الفشل
بشيء ما بدلًا من مجرد أن هناك خطأ ما.

<Steps>

1. **المواقع الثلاثة جميعها بحالة `ONLINE`.** لا يمكن أن يكون أي شيء لاحق صحيحًا إن لم يكن هذا صحيحًا.

   ```bash
   for s in ar-bgp-eastus01 ar-bgp-eastus02 ar-bgp-eastus03; do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **كل اقتران يتعلم إعلان الـ VIP الخاص بذلك الـ CE.** استعلم عن كل اقتران
   على حدة — راجع الفخ أدناه، لأن هذا هو الموضع الذي يبدو فيه العرض التوضيحي معطلًا في أغلب الأحيان
   وهو ليس كذلك.

   ```bash
   for p in eastus01-bgp eastus02-bgp eastus03-bgp; do
     echo "--- $p"
     az network routeserver peering list-learned-routes \
       --name "$p" --routeserver ce-ha-lab-rrs -g rg-mcn-ce-ha-rmordasiewicz \
       --query "RouteServiceRole_IN_0[].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp

   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp

   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   ثلاثة اقترانات، وثلاث قفزات تالية مختلفة، وبادئة واحدة. هذا هو الجانب الإعلاني
   من ECMP وقد تم إثباته.

3. **المسارات الفعّالة للعميل تحمل القفزات التالية الثلاث جميعها.** هذا هو ECMP نفسه،
   كما برمجه الـ VNet — ليس ما تدّعيه الـ CEs، بل ما فعلته Azure به.

   ```bash
   az network nic show-effective-route-table \
     --name ar-ecmp-clientVMNic -g rg-mcn-ce-ha-rmordasiewicz \
     --query "value[?addressPrefix[0]=='10.250.0.10/32']" -o json
   ```

   ```json
   [
     {
       "addressPrefix": ["10.250.0.10/32"],
       "nextHopIpAddress": ["10.0.1.5", "10.0.1.4", "10.0.1.6"],
       "nextHopType": "VirtualNetworkGateway",
       "source": "VirtualNetworkGateway",
       "state": "Active"
     }
   ]
   ```

   `state: Active` مع ثلاثة مدخلات في `nextHopIpAddress` هو الفحص المطلوب. وجود قفزة تالية واحدة
   حيث تتوقع ثلاثًا يعني أن أحد الـ CEs توقف عن الإعلان، والخطوة 2 تحدد أيها.

4. **الـ VIP يخدم حركة المرور.** من جهاز العميل الافتراضي، و**مع ترويسة `Host`** — راجع
   الفخ الثاني أدناه.

   ```bash
   az vm run-command invoke -g rg-mcn-ce-ha-rmordasiewicz -n ar-ecmp-client \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts 'for i in $(seq 1 10); do
                  curl -s -o /dev/null -w "%{http_code} " \
                    -H "Host: ar-bgp-ecmp.bankexample.com" http://10.250.0.10/
                done'
   ```

   ```text
   200 200 200 200 200 200 200 200 200 200
   ```

</Steps>

## فخ: اقتران واحد يُظهر مسارًا واحدًا، وهذا صحيح

نطاق `list-learned-routes` محصور بالاقتران الذي تسمّيه. فهو يبلّغ عمّا أعلنه **ذلك**
النظير، لا عن جدول Route Server بأكمله.

لذا فإن الاستعلام عن `eastus01-bgp` وحده يُرجع `10.250.0.10/32` واحدًا عبر `10.0.1.4`، ومن
المغري قراءة ذلك على أنه "CE واحد فقط يُعلن — والاثنان الآخران معطّلان". لا شيء
معطّل. الإعلانان الآخران مرئيان على اقترانيهما الخاصين، وهو ما تدور عليه
الخطوة 2 أعلاه.

تأكيد ECMP من استعلام اقتران واحد غير ممكن. إما أن تكرّر العملية على الاقترانات الثلاثة،
أو أن تقرأ جدول المسارات الفعّال للعميل، الذي يُظهر النتيجة المدمجة في استدعاء
واحد.

## فخ: طلب بعنوان IP مجرّد يُرجع 404

يطابق موازن التحميل على أساس `Host`. الـ VIP ليس خادمًا افتراضيًا يقدّم أي شيء
لكل من يتصل بالعنوان.

```text
curl -H 'Host: ar-bgp-ecmp.bankexample.com' http://10.250.0.10/   ->  200   (10 of 10)
curl                                        http://10.250.0.10/   ->  404
```

كلا هذين نتجا في التشغيل نفسه مقابل النشر السليم. **إن الرمز 404 من عنوان IP المجرّد
دليل على أن المسار يعمل** — فقد وصل الطلب إلى الـ CE، وأجاب وكيل الـ CE، ثم
رفضه لأنه لم يطابق أي نطاق مُهيّأ. وقراءته على أنه انقطاع تدفعك إلى
البحث في BGP، حيث لن تجد أي خطأ.

وينطبق الأمر نفسه أثناء العرض التوضيحي: إذا كتبت العنوان في المتصفح بدلًا من
تحليل النطاق إليه، فستحصل على 404.

## الموافقة على التسجيل مؤتمتة، ومع ذلك يظل التطبيق على مرحلتين

لم تعد الموافقة على التسجيل تحتاج إلى شخص في وحدة التحكم. في الموفر **v3.81.1** يقوم
مورد `xcsh_registration_approval` بتنفيذها، وتحدد وحدة الموقع أي تسجيل يجب الموافقة عليه.

ومع ذلك، فإن هذا لا يجعل النشر `apply` واحدًا دون تدخل، والسبب
يستحق الفهم قبل أن تشاهد أول تشغيل وتستنتج أنه فشل:

- كائن تسجيل الـ CE يُسمّى **`r-<uuid>`**. ولا يُسمّى أبدًا باسم الموقع، لذا
  لا يمكن لأي شيء التنبؤ بالاسم في وقت التخطيط.
- التسجيل لا يوجد إلا بعد إقلاع الجهاز الافتراضي وتسجيل `vpm`.
- لذا فإن **أول تطبيق لا يخطط لأي موافقة على الإطلاق**. أعد التطبيق مرة أخرى بعد أن تسجّل الـ CEs
  وتُنشأ الموافقات.

يوثّق `terraform/main.tf` هذا الترتيب في أعلى الملف، وهي النسخة
المرجعية — فتسلسل النشر يقيم مع الكود الذي ينفّذه.

<Aside type="caution" title="الموقع الجديد تمامًا ليس قابلًا للوصول فورًا عبر واجهة operate API">
لمدة تتراوح تقريبًا بين 25 و30 دقيقة بعد أن يبلّغ موقع جديد بحالة `ONLINE`، تجيب نقاط النهاية `vpm/debug`
بصفحة BIG-IP بالرمز `503` تقول `The requested URL was rejected`. يبدو الأمر وكأنه
حجب من جدار حماية تطبيقات ويب أو رمز مميز مُلغى، وهو ليس أيًا منهما. انتظر ثم أعد المحاولة.

يؤثر هذا على عرض توضيحي تم بناؤه حديثًا، وليس على عرض قيد التشغيل.
</Aside>

## الوصول إلى Site CLI

تمرّ التشخيصات الروتينية على الجهاز عبر واجهة debug API، وهي مكتوبة بالسكربتات هنا بالفعل.
تأكّد من أن سطح الأوامر ما زال مطابقًا لما تصفه الوثائق:

```bash
bash scripts/capture-sitecli.sh --check --site ar-bgp-eastus01 --node f5-xc-ce-vm-01
```

```text
catalog matches the live CE (build crt-20250613-3382, 34 commands)
```

لا يكتب `--check` أي شيء، لذا فهو آمن مقابل العرض التوضيحي الحي.

بالنسبة للأوامر التي لا ترحّلها تلك الواجهة، يتوفر في هذا النشر أيضًا **وصول SSH للمشغّل إلى
حساب `admin` على الجهاز**، والذي تكون قوقعة تسجيل الدخول الخاصة به هي Site CLI. وقد جرى التحقق منه على الـ
CEs الثلاثة جميعًا. اتصل بالعنوان الداخلي (SLI) من مضيف داخل الـ VNet، مع تخصيص
طرفية:

```bash
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<vm-in-vnet> admin@10.0.3.5
```

```text
WELCOME IN SITE CLI
Registration Status: PROVISIONED
```

<Aside type="caution" title="هذا الوصول موجود لأن هذه الـ CEs بُنيت به — ولا يمكن إضافته لاحقًا">
يُكتب مفتاح المشغّل بواسطة `write_files` في cloud-init، والذي يعمل مرة واحدة عند الإقلاع الأول.
و`custom_data` قابل للاستبدال فقط، لذا فإن اعتماد هذا على CEs تعمل بالفعل يستبدل
كل جهاز CE افتراضي — واستبدال واحد يعطّل حاليًا التسجيل بينما يبلّغ `terraform plan`
بـ "No changes" ([المشكلة 674](https://github.com/f5-sales-demo/mcn/issues/674)).
استغرقت الاستعادة عمليتي إعادة بناء كاملتين.

بالنسبة لهذا النشر فإن التغيير مطبّق بالفعل والأسطول سليم. وعلى أي شخص
يعتمده في مكان آخر أن يقرأ
[صفحة SSH](../customer-edge/access/ssh/) أولًا.
</Aside>

## فخّان إضافيان في القياس

كلاهما أنتج إجابات خاطئة بثقة في هذه البيئة، وليس أي منهما
بديهيًا.

- **افحص من داخل الـ VNet، لا من محطة عملك.** يكمل Netskope مصافحة TCP
  بنفسه على المنافذ الشائعة، لذا فإن الفحص من محطة العمل يبلّغ عن منفذ **مفتوح** وهو
  في الواقع مغلق. تُقرأ المنافذ 80 و443 على أنها مفتوحة على العناوين العامة للـ CE من
  محطة العمل، بينما تكون مغلقة عند فحصها من داخل الـ VNet. استخدم `ar-ecmp-client`.
- **المنفذ 22 على الـ CE يجيب على العنوان الداخلي (SLI) فقط.** عند الفحص من
  `ar-ecmp-client` مقابل الـ CEs الثلاثة، تُرجع `10.0.3.5` و`10.0.3.6` و`10.0.3.7` جميعها
  `SSH-2.0-OpenSSH_8.7`، بينما تنتهي مهلة عناوين الإدارة والخارجية — كما يحدث مع
  عنوان غير مستخدم اعتُمد كضابط. أُعيدت تسمية eth0 إلى `a-i-eth0` ولا يحمل عنوان IP مضيف،
  لأن مسار البيانات يمتلكه. لذا فإن فحص العنوان الذي تعرف العقدة به لا يخبرك
  بشيء عن حالة SSH للعقدة، وعنوان SLI هو العنوان الذي يجب الاتصال به.

<Aside type="note" title="ما لا تدّعيه هذه الصفحة">
هناك أمران قد يتوقعهما القارئ بشكل معقول هنا وقد غابا عمدًا، لأنهما لم
يُختبرا مقابل النشر:

- **لم يُختبر تجاوز الفشل.** جرى التحقق من تثبيت القفزات التالية الثلاث متساوية التكلفة؛ أما ما
  يحدث لجدول المسارات عند إيقاف أحد الـ CEs فلم يُعرض، لذا لا تتدرب على عرض توضيحي
  لتجاوز الفشل انطلاقًا من هذه الصفحة دون تجربته أولًا.
- **لم يُقس توزيع حركة المرور.** عشرة من عشرة طلبات إلى الـ VIP أرجعت `200`،
  ما يثبت أن المسار يعمل. لكنه لا يُظهر كيف توزّعت تلك الطلبات العشرة على القفزات
  التالية الثلاث.

</Aside>
