يوضح هذا النشر **توفر حافة العميل العالي بنمط active/active في Azure**
دون وجود موازن تحميل Azure أمام حواف العميل. تُصدر ثلاث حواف عميل المسار المضيف نفسه
عبر eBGP، ويقوم Azure Route Server بتثبيت الثلاثة جميعًا كخطوات تالية متساوية التكلفة في
الـ VNet. وبالتالي فإن نسيج التوجيه، بدلًا من موازن التحميل، هو المكان الذي يُفترض أن يحدث فيه
توزيع حركة المرور وإزالة العقد المتعطلة.

كل ما يُعرض أدناه تم تشغيله على النشر الحي، والمخرجات هي المخرجات التي أنتجها فعلًا. أمران
لا تشملهما تلك العبارة — تجاوز الفشل وتوزيع حركة المرور — تم ذكرهما في النهاية
بدلًا من تركهما للافتراض.

## ما تم نشره

```text
                  Azure Route Server  ce-ha-lab-rrs  ASN 65515
                          10.0.4.4  and  10.0.4.5
                                      |
              +-----------------------+-----------------------+
              |                       |                       |
        eastus01-bgp            eastus02-bgp            eastus03-bgp     eBGP
              |                       |                       |      CE ASN 64512
        10.0.1.4                10.0.1.5                10.0.1.6     <- CE eth0 / SLO
     f5-xc-ce-vm-01          f5-xc-ce-vm-02          f5-xc-ce-vm-03
    ar-bgp-eastus01         ar-bgp-eastus02         ar-bgp-eastus03
              |                       |                       |
              +----- each advertises 10.250.0.10/32 -----------+
                          three-way ECMP into the VNet
```

| العنصر | كما هو مبني |
| --- | --- |
| حواف العميل | 3 مواقع Secure Mesh v2 أحادية العقدة — `ar-bgp-eastus01`، `ar-bgp-eastus02`، `ar-bgp-eastus03` |
| برنامج حافة العميل | مثبّت على `9.2024.6`، البنية `crt-20250613-3382` |
| أجهزة Azure الافتراضية | `f5-xc-ce-vm-01/02/03`، ثلاث بطاقات شبكة لكل منها (الإدارة/SLO، خارجية، داخلية/SLI) |
| تبادل المسارات | Azure Route Server `ce-ha-lab-rrs`، ASN `65515`، النسخ `10.0.4.4` و`10.0.4.5` |
| عمليات الاقتران | واحدة لكل حافة عميل — `eastus01-bgp`، `eastus02-bgp`، `eastus03-bgp` — ASN حافة العميل `64512` |
| عنوان VIP المُعلن | `10.250.0.10/32`، يُصدر بشكل متطابق من الحواف الثلاث جميعًا |
| موازن التحميل | `ar-bgp-ecmp-lb`، يخدم النطاق `ar-bgp-ecmp.bankexample.com` |
| عميل الاختبار | `ar-ecmp-client`، جهاز افتراضي داخل الـ VNet نفسه |
| مجموعة الموارد | `rg-mcn-ce-ha-rmordasiewicz` |

<Aside type="caution" title="يجب أن يكون عنوان VIP خارج كل نطاقات CIDR الخاصة بالـ VNet">
يحتوي `terraform/main.tf` على كتلة `check` تتحقق من أن عنوان VIP يقع خارج نطاقي CIDR للـ hub
والـ spoke، وترفض الخطة بخلاف ذلك. والسبب المذكور هو أن عنوان VIP الواقع داخل
نطاق CIDR للـ VNet يُهزم أمام مسار النظام الخاص بالـ VNet نفسه رغم أن مسار BGP أكثر تحديدًا.

تعامل مع هذا الضابط كعقد: إذا أعدت توجيه هذا العرض التوضيحي إلى عنونة مختلفة، فيجب أن ينتقل
عنوان VIP خارج نطاقات الـ VNet معها.
</Aside>

## تحقق من سلامته قبل التقديم

أربع فحوصات، بهذا الترتيب. كل واحدة تضيّق نطاق موضع الخلل، بحيث يخبرك الفشل
بشيء ما بدلًا من مجرد أن هناك خطأ ما.

<Steps>

1. **المواقع الثلاثة جميعها `ONLINE`.** لا شيء لاحق يمكن أن يكون صحيحًا إن لم يكن هذا صحيحًا.

   ```bash
   for s in ar-bgp-eastus01 ar-bgp-eastus02 ar-bgp-eastus03; do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **كل عملية اقتران تتعلم إعلان VIP الخاص بحافة العميل تلك.** استعلم عن كل عملية اقتران
   على حدة — راجع الفخ أدناه، لأن هذا هو الموضع الذي يبدو فيه العرض التوضيحي
   معطّلًا في أغلب الأحيان وهو ليس كذلك.

   ```bash
   for p in eastus01-bgp eastus02-bgp eastus03-bgp; do
     echo "--- $p"
     az network routeserver peering list-learned-routes \
       --name "$p" --routeserver ce-ha-lab-rrs -g rg-mcn-ce-ha-rmordasiewicz \
       --query "RouteServiceRole_IN_0[].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp

   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp

   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   ثلاث عمليات اقتران، ثلاث خطوات تالية مختلفة، بادئة واحدة. هذا هو الجانب الإعلاني
   من ECMP وقد أُثبت.

3. **المسارات الفعالة للعميل تحمل الخطوات التالية الثلاث جميعها.** هذا هو ECMP نفسه،
   كما برمجه الـ VNet — ليس ما تدّعيه حواف العميل، بل ما فعله Azure به.

   ```bash
   az network nic show-effective-route-table \
     --name ar-ecmp-clientVMNic -g rg-mcn-ce-ha-rmordasiewicz \
     --query "value[?addressPrefix[0]=='10.250.0.10/32']" -o json
   ```

   ```json
   [
     {
       "addressPrefix": ["10.250.0.10/32"],
       "nextHopIpAddress": ["10.0.1.5", "10.0.1.4", "10.0.1.6"],
       "nextHopType": "VirtualNetworkGateway",
       "source": "VirtualNetworkGateway",
       "state": "Active"
     }
   ]
   ```

   `state: Active` مع ثلاثة مدخلات في `nextHopIpAddress` هو المطلوب في هذا الفحص. وجود خطوة تالية
   واحدة حيث تتوقع ثلاثًا يعني أن إحدى حواف العميل توقفت عن الإعلان، والخطوة 2 تحدد أيها.

4. **عنوان VIP يخدم حركة المرور.** من الجهاز الافتراضي للعميل، و**مع ترويسة `Host`** — راجع
   الفخ الثاني أدناه.

   ```bash
   az vm run-command invoke -g rg-mcn-ce-ha-rmordasiewicz -n ar-ecmp-client \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts 'for i in $(seq 1 10); do
                  curl -s -o /dev/null -w "%{http_code} " \
                    -H "Host: ar-bgp-ecmp.bankexample.com" http://10.250.0.10/
                done'
   ```

   ```text
   200 200 200 200 200 200 200 200 200 200
   ```

</Steps>

## فخ: عملية اقتران واحدة تُظهر مسارًا واحدًا، وهذا صحيح

`list-learned-routes` محدود النطاق بعملية الاقتران التي تسميها. فهو يُبلّغ عمّا أعلنه
**ذلك** النظير، لا عن جدول Route Server بالكامل.

لذا فإن الاستعلام عن `eastus01-bgp` وحده يُرجع `10.250.0.10/32` واحدًا عبر `10.0.1.4`، ومن
المُغري قراءة ذلك كـ "حافة عميل واحدة فقط تُعلن — والاثنتان الأخريان معطّلتان". لا شيء
معطّل. الإعلانان الآخران مرئيان على عمليات الاقتران الخاصة بهما، وهو ما تقوم به الحلقة في
الخطوة 2 أعلاه.

لا يمكن تأكيد ECMP من استعلام عملية اقتران واحدة. إما أن تمر بحلقة على عمليات الاقتران الثلاث،
أو تقرأ جدول المسارات الفعالة للعميل، الذي يُظهر النتيجة المدمجة في مكالمة واحدة.

## فخ: طلب بعنوان IP مجرد يُرجع 404

يطابق موازن التحميل على أساس `Host`. عنوان VIP ليس خادمًا افتراضيًا يخدم أي شيء
لمن يتصل بالعنوان.

```text
curl -H 'Host: ar-bgp-ecmp.bankexample.com' http://10.250.0.10/   ->  200   (10 of 10)
curl                                        http://10.250.0.10/   ->  404
```

كلتا هاتين النتيجتين أُنتجت في التشغيل نفسه على النشر السليم. **الحصول على 404 من عنوان IP
مجرد هو دليل على أن المسار يعمل** — فقد وصل الطلب إلى حافة العميل، وأجاب وكيل حافة العميل،
ورفض الطلب لأن أي نطاق مُهيأ لم يطابق. وقراءة ذلك كانقطاع تدفعك إلى
البحث في BGP، حيث لن تجد أي خطأ.

الأمر نفسه ينطبق أثناء العرض التوضيحي: إذا كتبت العنوان في المتصفح بدلًا من
تحليل النطاق إليه، فستحصل على 404.

## الموافقة على التسجيل مؤتمتة، ومع ذلك يبقى التطبيق على مرحلتين

لم تعد الموافقة على التسجيل تحتاج إلى شخص في وحدة التحكم. في الموفر **v3.81.1** يقوم
مورد `xcsh_registration_approval` بها، وتحدد وحدة الموقع أي تسجيل يجب الموافقة عليه.

لكن هذا لا يجعل النشر عملية `apply` واحدة دون تدخل، والسبب
يستحق الفهم قبل أن تشاهد أول تشغيل وتستنتج أنه فشل:

- كائن تسجيل حافة العميل يُسمّى **`r-<uuid>`**. لا يُسمّى أبدًا باسم الموقع، لذا
  لا شيء يمكنه التنبؤ بالاسم في وقت التخطيط.
- التسجيل لا يوجد إلا بعد أن يُقلع الجهاز الافتراضي ويسجّل `vpm`.
- لذلك **لا يخطط التطبيق الأول لأي موافقة على الإطلاق**. أعد التطبيق بعد أن تسجّل حواف العميل
  وتُنشأ الموافقات.

يوثّق `terraform/main.tf` هذا الترتيب في أعلى الملف، وهي النسخة
المرجعية — فتسلسل النشر يوجد مع الكود الذي ينفذه.

<Aside type="caution" title="الموقع الجديد تمامًا ليس قابلًا للوصول فورًا عبر واجهة operate API">
لمدة تقارب 25 إلى 30 دقيقة بعد أن يُبلّغ موقع جديد بأنه `ONLINE`، تجيب نقاط النهاية `vpm/debug`
بصفحة BIG-IP بالرمز `503` تقول `The requested URL was rejected`. يبدو الأمر كأنه
حجب من جدار حماية تطبيقات الويب أو رمز مميز مُلغى وهو ليس أيًّا منهما. انتظر، ثم أعد المحاولة.

يؤثر هذا على عرض توضيحي تم بناؤه حديثًا، لا على عرض قائم بالفعل.
</Aside>

تمر التشخيصات على الجهاز عبر واجهة debug API، وهي مكتوبة بالسكربتات هنا مسبقًا. تحقق من أن
مجموعة الأوامر لا تزال مطابقة لما يصفه التوثيق:

```bash
bash scripts/capture-sitecli.sh --check --site ar-bgp-eastus01 --node f5-xc-ce-vm-01
```

```text

```

## فخّان إضافيان في القياس

كلاهما أنتج إجابات خاطئة بثقة في هذه البيئة، وليس أي منهما
بديهيًا.

- **افحص من داخل الـ VNet، لا من محطة عملك.** يُكمل Netskope مصافحة TCP
  بنفسه على المنافذ الشائعة، لذا يُبلّغ الفحص من محطة العمل عن منفذ **مفتوح** وهو
  في الحقيقة مغلق. يظهر المنفذان 80 و443 كمفتوحين على العناوين العامة لحواف العميل من
  محطة العمل ويكونان مغلقين عند فحصهما من داخل الـ VNet. استخدم `ar-ecmp-client`.
- **المنفذ 22 على حافة العميل يجيب على العنوان الداخلي (SLI) فقط.** عند الفحص من
  `ar-ecmp-client` تجاه حواف العميل الثلاث، تُرجع `10.0.3.5` و`10.0.3.6` و`10.0.3.7` جميعها
  `SSH-2.0-OpenSSH_8.7`، بينما تنتهي مهلة عنوانَي الإدارة والخارجي — كما يحدث مع
  عنوان غير مستخدم يُستعمل كعنصر تحكم. لذا فإن فحص العنوان الذي تعرف العقدة به
  لا يخبرك بشيء عن حالة SSH للعقدة.

<Aside type="note" title="ما لا تدّعيه هذه الصفحة">
هناك أمران قد يتوقعهما القارئ هنا بشكل معقول وهما غائبان بشكل متعمد، لأنهما لم
يُختبرا على النشر:

- **لم يُختبر تجاوز الفشل.** تم التحقق من تثبيت الخطوات التالية الثلاث متساوية التكلفة؛ أما ما
  يحدث لجدول المسارات عند إيقاف إحدى حواف العميل فهو غير معروض، لذا لا تتدرب على عرض
  تجاوز الفشل انطلاقًا من هذه الصفحة دون تجربته أولًا.
- **لم يُقس توزيع حركة المرور.** عشرة من عشرة طلبات إلى عنوان VIP أرجعت `200`،
  وهذا يثبت أن المسار يعمل. لكنه لا يُظهر كيف توزعت تلك الطلبات العشرة على الخطوات
  التالية الثلاث.

</Aside>
