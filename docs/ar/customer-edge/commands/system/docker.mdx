يُشغّل Docker خدمات المنصة. أحمال عمل Kubernetes تقع تحت
[CRI-O](../crictl/).

## `docker-ps`

```bash
{"command":["docker-ps"]}
```

```text file=../../../../_data/sitecli-docker-ps.txt
```

<Aside type="tip" title="ثلاثة حاويات هي القائمة الكاملة، وليست عقدة معطلة">
`vpm` و`argo_watch` و`site-console`. نظرًا لأن معظم العقدة تعمل تحت CRI-O، فإن
نتيجة `docker-ps` القصيرة تبدو وكأنها فشل إذا كنت تتوقع أحمال عمل Kubernetes
هنا. لكنها ليست كذلك — فهذه هي المجموعة الكاملة من حاويات Docker على CE سليم،
وإن كان `vpm` موجودًا وفي حالة `Up` فهذا أهم سطر في الصفحة.
</Aside>


## `docker-logs`

```bash
{"command":["docker-logs","<container-id-or-name>"]}
```

```text file=../../../../_data/sitecli-docker-logs.txt
```

يُعدّ `docker-logs vpm` أسرع طريق للوصول إلى أخطاء التسجيل. للحصول على المعلومات
ذاتها مع الطوابع الزمنية وعبر عمليات إعادة التشغيل، استخدم
[`journalctl`](../journalctl/) بدلًا من ذلك.

## `docker-prune`

```bash
execcli docker-prune
```

يُزيل كل كائن Docker غير مُستخدم — الحاويات المتوقفة، والشبكات غير المُستخدمة، والصور المعلقة،
وذاكرة التخزين المؤقت للبناء.

**من الجهاز فقط.** لا يتوفر `docker-prune` في واجهة برمجة التطبيقات للتصحيح؛ فهو يحتاج إلى
[`execcli`](../../on-box/).

<Aside type="danger" title="عملية تدميرية، وغير مُوثَّقة هنا">
هذا الأمر يحذف الحالة. إنه مدرج في قائمة الرفض الخاصة بمجموعة الحصاد ولم يُشغَّل قط، لذا
توثّق هذه الصفحة هذا الأمر من بيانات كتالوج الجهاز الخاص به بدلًا من عرض المخرجات.

التحذير الخاص بـ CE: تعمل هذه العقدة بـ **وقتَي تشغيل** لحاويات. يؤثر `docker-prune`
فقط على الجانب الخاص بـ Docker — `vpm` و`argo_watch` و`site-console` — ولا يصل إلى
أحمال عمل Kubernetes الموجودة تحت [CRI-O](../crictl/). استعادة المساحة على جانب CRI-O
تتطلب أمرًا مختلفًا هو `systemctl-start-crio-prune`، الذي لا يتوفر في هذا الإصدار.
</Aside>
