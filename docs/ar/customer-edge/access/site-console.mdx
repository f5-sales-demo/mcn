كل Customer Edge يقدّم وحدة تحكم الموقع من F5 على `https://<sli-ip>:65500`. في هذا
النشر تكون عادةً المسار الأول الذي يُجرَّب.

وهي الأقل مطالبةً منك: لا مفتاح SSH لتوزيعه، ولا مضيف وسيط لصيانته، ولا عنوان IP عام على
العقدة، ولا استبدال للجهاز الافتراضي لتمكينها. ويصبح تحديد من يُسمح له بالاتصال **قرارًا يتعلق بـ Azure
RBAC**. كما أنها لا تحتاج إلى أن يكون الموقع مسجّلًا: فقد التُقطت هذه الصفحة أولًا
بينما كانت جميع المواقع الثلاثة تُبلّغ عن `site_state: FAILED`، وأُعيد التحقق منها دون تغيير على
العقد نفسها بعد أن أصبحت `ONLINE`.

المشكلة أن وحدة تحكم الموقع لا تستجيب إلا على العنوان الداخلي (SLI) للعقدة،
والذي لا يمكن الوصول إليه إلا من داخل شبكة VNet. ويُغلق Azure Bastion هذه الفجوة دون وضع
أي شيء آخر على الشبكة.

<Aside type="note" title="ما تم التحقق منه هنا، وما لم يتم">
كل أمر وكل مخرَج في هذه الصفحة نُفِّذ على `f5-xc-ce-vm-01` في هذا
النشر ويُستنسخ حرفيًا، بما في ذلك حالات الفشل.

**تم التحقق من المصادقة**: بيانات اعتماد `admin` الخاصة بالجهاز تُعيد `200` عبر
النفق. أما ما *لم* يُجرَّب فهو وحدة التحكم نفسها — لا شيء أدناه يصف ما يمكنك
رؤيته أو فعله بعد أن تدخل.

**لم يُتحقق من Azure RBAC.** كل تنفيذ كان بصفة مالك الاشتراك، لذا فإن شرط Reader
في الخطوة 2 هو شرط موثَّق من Microsoft وليس شيئًا تم قياسه
هنا.
</Aside>

<Aside type="caution" title="Bastion اختياري، ولا يُنشر افتراضيًا">
القيمة الافتراضية لـ `enable_bastion` هي `false`، لذا في `terraform apply` الافتراضي لا يوجد مضيف Bastion
وتكون `terraform output -raw bastion_name` هي `null`. اضبط `enable_bastion = true` في
`terraform/terraform.tfvars` — وهي `true` في هذا النشر.

سبب كونها اختيارية هو التكلفة لا الخطر: مضيف من فئة Standard-SKU يفرض رسمًا ثابتًا بالساعة
من لحظة تزويده، سواء فتح أحد نفقًا أم لا — 0.29 دولار أمريكي
للساعة في `eastus` مقابل وحدتي القياس المضمّنتين (سعر التجزئة، 2026-07)، أي نحو 212 دولارًا أمريكيًا
شهريًا. أوقفها مرة أخرى عندما لا يحتاج العرض التوضيحي إلى الوصول إلى وحدة التحكم.
</Aside>

## قبل أن تبدأ

<Steps>

1. سجّل الدخول إلى Azure وأضف امتداد Bastion. فالتنفيق ميزة خاصة بالعميل الأصلي
   والامتداد غير مُثبَّت افتراضيًا.

   ```bash
   az login
   az extension add --name bastion
   ```

2. احتفظ بدور **Reader** على الجهاز الافتراضي لـ CE، وعلى واجهة الشبكة الخاصة به، وعلى مضيف Bastion.
   هذا شرط موثَّق من Microsoft وهو **غير مُتحقَّق منه هنا** — فكل تنفيذ في هذا
   النشر كان بصفة مالك الاشتراك، لذا لم يُثبت أن أي دور أدنى
   كافٍ أو غير كافٍ.

3. تأكد من أن Bastion مُنشر وقادر. فئة Basic SKU لا تدعم التنفيق ولا
   الاتصال المعتمد على IP، لذا فإن `Standard` و`True` هنا كلاهما أساسيان.

   ```bash
   az network bastion list -g rg-mcn-ce-ha-rmordasiewicz \
     --query "[].{name:name, sku:sku.name, tunneling:enableTunneling}" -o table
   ```

   ```text
   Name               Sku       Tunneling
   -----------------  --------  -----------
   ce-ha-lab-bastion  Standard  True
   ```

</Steps>

## افتح النفق

خُذ القيم من `terraform output` بدلًا من كتابتها — فمعرّف المورد ليس
شيئًا يُجمَّع يدويًا.

<Steps>

1. اقرأ اسم مضيف Bastion، ومجموعة الموارد، ومعرّف مورد الجهاز الافتراضي لـ CE المستهدف.

   ```bash
   cd terraform
   BASTION=$(terraform output -raw bastion_name)
   RG=$(terraform output -raw resource_group_name)
   VM_ID=$(terraform output -json ce_vm_ids | jq -r '.eastus01')
   ```

   ```text
   ce-ha-lab-bastion
   rg-mcn-ce-ha-rmordasiewicz
   /subscriptions/…/providers/Microsoft.Compute/virtualMachines/f5-xc-ce-vm-01
   ```

   <Aside type="caution" title="الخريطة مُفهرسة بحسب الموقع، لا بحسب اسم الجهاز الافتراضي">
   مفاتيح `ce_vm_ids` هي `eastus01` و`eastus02` و`eastus03` — **وليست** أسماء الأجهزة الافتراضية.
   والمُرشِّح مثل `jq -r '."f5-xc-ce-vm-01"'` يُعيد `null`، ثم يفشل النفق بسبب
   معرّف مورد فارغ. اسردها إذا لم تكن متأكدًا:

   ```bash
   terraform output -json ce_vm_ids | jq -r 'keys | join(", ")'
   ```

   ```text
   eastus01, eastus02, eastus03
   ```

   </Aside>

2. ابدأ النفق. فهو يُبقي المنفذ مفتوحًا حتى يُوقَف، لذا شغّله في الخلفية أو استخدم
   طرفية ثانية.

   ```bash
   az network bastion tunnel \
     --name "$BASTION" \
     --resource-group "$RG" \
     --target-resource-id "$VM_ID" \
     --resource-port 65500 \
     --port 65500 &
   ```

   ```text
   WARNING: Opening tunnel on port: 65500
   WARNING: Tunnel is ready, connect on port 65500
   WARNING: Ctrl + C to close
   ```

   جميع الأسطر الثلاثة تبدأ بالبادئة `WARNING:`. هذا هو Azure CLI يكتب التقدّم إلى
   stderr، وليست مشكلة. انتظر ظهور `Tunnel is ready` قبل الاتصال.

3. تأكد من أن المُستمع محلي، على loopback:

   ```bash
   lsof -nP -iTCP:65500 -sTCP:LISTEN
   ```

   ```text
   COMMAND   PID  USER  FD  TYPE  DEVICE  SIZE/OFF  NODE  NAME
   Python  41648  you   7u  IPv4  …            0t0   TCP  127.0.0.1:65500 (LISTEN)
   ```

4. افتح وحدة التحكم. النفق يجعلها محلية، لذا فإن العنوان هو `localhost` — لا
   عنوان العقدة.

   ```bash
   open https://localhost:65500/          # macOS
   xdg-open https://localhost:65500/      # Linux
   ```

5. أوقف النفق عندما تنتهي — بـ `Ctrl-C`، أو `kill %1` إذا شغّلته في الخلفية.
   إن تركته مفتوحًا فسيحتجز المنفذ المحلي 65500 وجلسة Bastion.

</Steps>

## ما سترى

**مربع حوار لبيانات الاعتماد، لا صفحة تسجيل دخول.** تستخدم وحدة التحكم مصادقة HTTP الأساسية، لذا
يُظهر المتصفح مطالبته الخاصة باسم المستخدم وكلمة المرور. لا يوجد نموذج لتنظر إليه:

```bash
curl -skI https://localhost:65500/
```

```text
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Basic realm="Volterra Site Console"
Content-Type: text/html; charset=utf-8
Content-Length: 0
```

الرمز `401` مع تلك النطاق (realm) يعني أن وحدة التحكم تعمل بشكل صحيح. فهذا ما يُفترض أن يتلقاه الطلب
غير المُصادَق — وتقديم بيانات اعتماد `admin` إلى نفس العنوان يُعيد
`200`، وهي الطريقة التي تتأكد بها من بيانات الاعتماد قبل فتح المتصفح:

```bash
curl -sk -u admin -o /dev/null -w '%{http_code}\n' https://localhost:65500/
```

```text
Enter host password for user 'admin':
200
```

استخدام `-u admin` دون نقطتين يجعل `curl` يطالب بكلمة المرور بدلًا من أخذها من
سطر الأوامر، حيث ستنتهي في سجل الأوامر (shell history) وفي قائمة العمليات.

**تحذير بشأن الشهادة، لثلاثة أسباب في وقت واحد.** بالتحقق من الشهادة مباشرة:

```bash
openssl s_client -connect localhost:65500 -servername localhost </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
```

```text
subject=C=US, ST=California, L=Santa Clara, O=Volterra, OU=Volterra Edge Services, CN=site-local.volterra.io
issuer=C=US, ST=California, L=Santa Clara, O=Volterra, OU=Volterra Edge Services, CN=site-local.volterra.io
notBefore=Oct 25 04:51:31 2024 GMT
notAfter=Oct 25 04:51:31 2025 GMT
```

الموضوع (subject) يساوي المُصدِر (issuer)، أي أنها موقّعة ذاتيًا. والاسم هو `site-local.volterra.io` في حين
أنك تتصل بـ `localhost`، لذا لن يتطابق. وفي الإصدار الذي يعمل عليه هذا النشر،
**انتهت صلاحية الشهادة في 25 أكتوبر 2025** — فالجهاز يأتي بها، ولا شيء
في هذا المستودع يُجدّدها.

توقّع تحذيرًا صريحًا من المتصفح، وتوقّعه في كل مرة. سطر الموضوع أعلاه هو
الجزء المفيد: فهو الطريقة التي تتأكد بها من أنك وصلت إلى الجهاز وليس إلى شيء آخر
يستمع على المنفذ المحلي 65500.

## بيانات اعتماد المسؤول

سجّل الدخول باسم `admin`. **هذه الوثائق لا تنشر كلمة المرور، ولا ينبغي أن تفعل ذلك.**

<Aside type="danger" title="في هذا النشر لا تزال كلمة المرور تلك هي الإعداد الافتراضي المصنعي من F5">
هذه حقيقة مقيسة، لا شكّ: فبيانات الاعتماد الافتراضية المصنعية تُصادق
وتُعيد `200` على جميع وحدات CE الثلاث اليوم. تنشر F5 ذلك الإعداد الافتراضي وتشترط تغييره،
وهو ما لم يحدث.

النتيجة العملية أنه في هذا النشر يكون "الحصول على دور Reader على Bastion"
مكافئًا للوصول الكامل إلى وحدة تحكم الجهاز، لأي شخص يعرف قيمة موجودة في
وثائق F5 العامة. غيّرها، وتعامل مع تغييرها كجزء من نشر العقدة بدلًا
من كونها تقويةً لاحقة.
</Aside>

سببان لكون عدم نشرها أهمّ هنا مما قد يبدو:

- هذه الوثائق عامة. فطباعة كلمة مرور وحدة التحكم الحالية للأسطول ستحوّل
  "الحصول على دور Reader على Bastion" إلى وصول كامل للجهاز لكل من يقرأ الصفحة.
- كلمة المرور المنشورة في الوثائق تصبح خاطئة لحظة تدوير أحدهم لها، وخاطئة
  بأكثر الطرق تضليلًا — فيستنتج القارئ أن وصوله معطوب بدلًا
  من أن الصفحة قديمة.

بعد تدويرها، احصل عليها من حيث يحفظ فريقك الأسرار التشغيلية.

<Aside type="caution" title="ضبط كلمة المرور من Terraform غير مُتحقَّق منه">
تبدو `admin_user_credentials.admin_password` في كائن الموقع الطريقة التعريفية
لضبط هذا. لكن **لم** يُتأكد من أنها تصل إلى وحدة تحكم الموقع في هذا الإصدار، لذا
لا تفترض أنها تفعل ذلك.

ولا تقرأ [صفحة SSH](../ssh/) كدليل في أي من الاتجاهين. فما توصلت إليه من أن
`admin_password` "لم تُغيّر شيئًا" قِيس مقابل مصادقة SSH، التي يتجاوزها `vpm`
تمامًا للمستخدم `admin`. وهذا لا يقول شيئًا عن وحدة التحكم.
</Aside>

## لماذا يجب أن يستهدف النفق معرّف المورد

`--target-resource-id` مطلوب. واستهداف عنوان العقدة بدلًا منه مرفوض —
أيًّا كان العنوان الذي تستخدمه، لذا لا يوجد عنوان حقيقي مطبوع هنا بشكل متعمّد:

```bash
az network bastion tunnel --name "$BASTION" -g "$RG" \
  --target-ip-address <any-sli-address> --resource-port 65500 --port 65501
```

```text
ERROR: Custom ports are not allowed. Allowed ports for Tunnel with IP connect is 22, 3389.
```

والسبب **ليس** أن الاتصال المعتمد على IP معطّل — فعلى هذا Bastion تكون
`ip_connect_enabled` هي `true`. فـ Microsoft لا تدعم المنافذ المخصصة عبر اتصالات
العميل الأصلي المعتمدة على IP بغض النظر عن ذلك الإعداد
([وثائق Azure](https://learn.microsoft.com/azure/bastion/connect-ip-address))، والمنفذ 65500
منفذ مخصص. وتفتيش تكوين Bastion هنا لا يؤدي إلى شيء؛ استخدم معرّف
المورد.

## عندما لا يعمل

| العَرَض | السبب | الحل |
| --- | --- | --- |
| `ERROR: Custom ports are not allowed. Allowed ports for Tunnel with IP connect is 22, 3389.` | استُخدمت `--target-ip-address` | استخدم `--target-resource-id` |
| `ERROR: Defined port is currently unavailable` | نفق آخر يحتجز بالفعل ذلك المنفذ المحلي | أوقف النفق الآخر، أو مرّر `--port` مختلفًا؛ وتبقى `--resource-port` على 65500 |
| `terraform output -raw bastion_name` تكون `null` أو فارغة | Bastion غير مُنشر | اضبط `enable_bastion = true` ثم طبّق |
| يبدأ النفق لكن معرّف المورد فارغ | مُرشِّح `jq` استخدم اسم الجهاز الافتراضي بدلًا من مفتاح الموقع | استخدم المفتاح `eastus01`/`02`/`03` |
| `401 Unauthorized`، بالنطاق `Volterra Site Console` | ليس خطأً — طلب غير مُصادَق | قدّم بيانات اعتماد `admin` |
| المتصفح يرفض الشهادة | موقّعة ذاتيًا، وعدم تطابق الاسم، ومنتهية الصلاحية منذ أكتوبر 2025 | متوقّع؛ تأكد من أن الموضوع هو `CN=site-local.volterra.io` ثم تابع |

<Aside type="note" title="لم يُعَد إنتاج حالات فشل التخويل">
عدم كفاية RBAC هو الطريقة الواضحة الأخرى لفشل هذا، لكن إعادة إنتاجها تعني
إزالة تعيينات الأدوار من نشر مشترك، لذا لم تُوثَّق هنا مع
رسالة خطأ حرفية. إذا فشل النفق عند البدء بخطأ تخويل، فتحقق من دور Reader على
الثلاثة جميعًا: الجهاز الافتراضي، وواجهة الشبكة الخاصة به، ومضيف Bastion.
</Aside>
