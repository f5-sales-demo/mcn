تقوم واجهة `vpm/debug` بتشغيل أوامر Site CLI على عقدة مسجَّلة وتُرجع مخرجاتها.
كل ما يلي تم التحقق منه مقابل عقدة حقيقية؛ ولا شيء منه منشور في المصادر الرسمية.

## كتالوج الأوامر يوصف نفسه

اسأل العقدة عما تدعمه بإرسال طلب POST إلى `exec-user` مع **حذف** المفتاح
`command`:

```bash
curl -sS -X POST \
  -H "Authorization: APIToken $XCSH_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"namespace":"system","site":"<site>","node":"<node>"}' \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/<node>/exec-user" \
  | jq -r .output | jq .
```

الاستجابة هي كائن JSON مفاتيحه هي أسماء الأوامر:

```json
{
  "crictl-inspect": ["System Troubleshooting", "ExecUser", " container-id"],
  "diagnosis":      ["System Troubleshooting", "ExecUser", "no argument needed", "GLOBAL"],
  "ip-link-set":    ["Network Troubleshooting", "Exec", " (<device>||<group>) (up||down)"]
}
```

كل مدخل هو `[category, tier, exampleArgument?, scope?]`، وهذه الحقول ليست
توثيقًا — بل هي التي تحدد كيف يجب استدعاء الأمر.

<Aside type="caution" title="احذف المفتاح؛ ولا ترسل قيمة خاطئة">
يعمل الاستكشاف عن طريق ترك `command` خارج الطلب. أما إرسال قيمة غير معروفة بدلًا من ذلك فيُرجع
خطأً، لا الكتالوج:

```json
{"code":3,"details":[],"message":"exec command failed: command not supported"}
```

هذه الرسالة نفسها هي ما تحصل عليه لأمر *حقيقي* أُرسل إلى نقطة النهاية الخاطئة،
لذا يسهل قراءتها خطأً على أنها "هذا الأمر غير موجود".
</Aside>

## ثلاث وسائل نقل، يحددها مدخل الكتالوج

| الشرط | الطريقة والمسار | الجسم | المُرجَع |
| --- | --- | --- | --- |
| `scope` هو `GLOBAL` | `GET .../vpm/debug/global/<cmd>` | لا شيء | JSON |
| `tier` هو `ExecUser` | `POST .../vpm/debug/<node>/exec-user` | مصفوفة `command` | نص |
| `tier` هو `Exec` | `POST .../vpm/debug/<node>/exec` | مصفوفة `command` | نص |

### `ExecUser` — المستوى للقراءة فقط <Badge text="31 أمرًا" variant="note" />

الحالة الشائعة. مرِّر الأمر ووسائطه كمصفوفة، مع اسم الأمر
أولًا:

```bash
curl -sS -X POST \
  -H "Authorization: APIToken $XCSH_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"namespace":"system","site":"<site>","node":"<node>","command":["crictl-ps"]}' \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/<node>/exec-user"
```

```json
{ "return_code": 0, "output": "CONTAINER    IMAGE    CREATED    STATE ..." }
```

الوسائط هي عناصر منفصلة في المصفوفة، وليست سلسلة نصية واحدة:

```json
{ "command": ["journalctl", "-u", "vpm", "-n", "200"] }
```

### `GLOBAL` — على مستوى الموقع، ووسيلة نقل مختلفة تمامًا <Badge text="أمران" variant="tip" />

`health` و`diagnosis` هما الأمران الوحيدان. وهما طلبا `GET` إلى مسار `global`،
لا يأخذان أي وسائط، ويُرجعان JSON منظمًا بدلًا من نص طرفية.

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/global/health" | jq .
```

<Aside type="danger" title="أمر GLOBAL لا يمكن الوصول إليه عبر exec-user">
هذا هو الفخ الذي يستهلك أكبر قدر من الوقت. إرسال `health` أو `diagnosis` إلى
`exec-user` يُرجع `command not supported`، وهو ما يُقرأ كأن الأمر غير
موجود على العقدة — بينما في الحقيقة هو موجود وأنت استخدمت وسيلة النقل الخاطئة.

```bash
# Wrong. Returns: exec command failed: command not supported
-d '{"namespace":"system","site":"…","node":"…","command":["health"]}'   # POST exec-user

# Right.
GET .../vpm/debug/global/health
```

</Aside>

### `Exec` — المستوى المتميز <Badge text="أمر واحد في هذه النسخة" variant="danger" />

نقطة نهاية منفصلة، والمستوى مُلزَم لا استشاري: فـ `exec` يرفض
أمرًا من نوع `ExecUser` بنفس رسالة `command not supported`. وكل عضو فيه
إما يُغيّر العقدة أو يقرأ علامة حالة.

في النسخة التي يشغّلها هذا المستأجر، يحتوي المستوى على `ip-link-set` فقط. أما النسخ الأحدث
فتضيف `systemctl-restart-NetworkManager` و`systemctl-restart-crio`
و`systemctl-restart-kubelet` و`systemctl-start-crio-prune` وثلاثة أوامر
`marker-exists-*`.

<Aside type="danger" title="لا شيء هنا يشغّل أمر Exec">
تَرفض أداة الالتقاط هذا المستوى، وهي تقرأ المستوى من الكتالوج الحيّ
بدلًا من قائمة مثبَّتة في الشيفرة — لذا فإن أي نسخة مستقبلية ترفع أمرًا إلى `Exec`
تُحترم دون أن يعدّل أحد الشيفرة. لا تشغّل أيًّا منها إلا بقصد، وعلى عقدة
أنت مستعد لتعطيلها.
</Aside>

## إيجاد أسماء الموقع والعقدة

اسم العقدة هو اسم آلة Azure الافتراضية، و`list-service` طريقة زهيدة التكلفة لتأكيده
إلى جانب الخدمات العاملة عليها:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/global/list-service" \
  | jq -r '[.service[].node] | unique'
```

```json
["", "f5-xc-ce-vm-01"]
```

بعض الخدمات تُبلّغ عن اسم عقدة فارغ، لذا فإن السلسلة الفارغة في تلك القائمة هي نتيجة عرضية لِـ
الاستجابة وليست عقدة ثانية. كما أن `list-service` غير موجود في كتالوج الأوامر الـ34:
فهو نقطة نهاية `global` لا يعلن عنها الكتالوج، ولذلك يُوثَّق هنا
وليس في [مرجع الأوامر](../../commands/).

## إعادة إنتاج عمليات الالتقاط في هذا المستودع

كل صفحة أمر تضمّن مخرجات مُلتقطة بواسطة `scripts/capture-sitecli.sh`، الذي
ينفّذ القواعد الثلاث المذكورة أعلاه.

<Steps>

1. وجّهه إلى مستأجر. يقرأ `XCSH_API_URL` و`XCSH_API_TOKEN`، أو يرجع
   إلى سياق `xcsh` النشط.

2. حدّث الكتالوج وتأكد من أن العقدة لم تتغير من تحت
   التوثيق:

   ```bash
   bash scripts/capture-sitecli.sh --check
   ```

   هذا يقارن الكتالوج المُودَع ونسخة البرنامج فقط. وهو يُبلّغ عن
   تغيّر النسخة بشكل منفصل عن الأوامر المضافة أو المحذوفة.

3. أعد الالتقاط عندما تريد أدلة حديثة:

   ```bash
   bash scripts/capture-sitecli.sh
   ```

</Steps>

<Aside type="note" title="عمليات الالتقاط أدلة، لا مصنوعات قابلة للتكرار">
تتغير العدادات وأوقات التشغيل وأعمار الحاويات بين التشغيلات، لذا فإن إعادة الالتقاط تُنتج
فرقًا دائمًا. الكتالوج هو العقد المستقر، وهو مطابق على مستوى البايت بين
التشغيلات عندما لا تتغير العقدة؛ وهذا ما يقارنه `--check`. المخرجات الطويلة
تُقتَطع وتنتهي بعلامة صريحة، فلا يُعرض جدول مقتطع أبدًا كأنه
مكتمل.
</Aside>

<Aside type="danger" title="الالتقاط من عقدة عميل: تحقّق من ملف تعريف الحجب">
تحمل مخرجات الأوامر هوية البنية التحتية — العَنْوَنة الداخلية وعناوين MAC
وأرقام AS وأسماء المضيفين — وبالنسبة لعميل فهذه معلومات تُعرّف
المؤسسة.

لذلك فإن مُرشِّح التنقية يستخدم افتراضيًا ملف تعريف **صارمًا** يزيلها كلها.
يعلن هذا المستودع عن `lab` في `sitecli/capture-manifest.json`، وهو ما يُبقي تلك
التفاصيل، وهو صحيح هنا فقط لأن هذه العمليات تأتي من بنية تحتية للعرض التوضيحي مملوكة لِـ F5.

**لا تنقل هذا الإعداد إلى التقاط من عميل.** الرموز والمفاتيح الخاصة ومعرّف
المستأجر ومعرّفات UUID للكائنات وعناوين البريد الإلكتروني ومسارات المجلد الرئيسي تُزال بموجب
كلا الملفين التعريفيين.

يجدر معرفة قيد واحد: جدول جيران BGP يطبع رقم AS كعمود مجرّد
دون تسمية يمكن أن يُثبَّت عليها نمط، لذا تُطابَق أرقام ASN بالقيمة مقابل
النطاقات الخاصة. أي ASN **عام** هناك ينجو من الملف الصارم، ويحتاج إلى مراجعة يدوية لمخرجات
`show-ip-bgp*` قبل نشرها.
</Aside>
