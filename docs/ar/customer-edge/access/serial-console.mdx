مقابل عقدة CE حيّة.

تتصل وحدة التحكم التسلسلية في Azure بالمنفذ التسلسلي المُحاكى للعقدة عبر منصة
Azure. وهي لا تجتاز مستوى التحكم في F5 Distributed Cloud، ولا مستوى البيانات
للعقدة، ولا أي مسار شبكي تتحكم فيه العقدة — ولهذا السبب بالضبط تعمل عندما لا
يعمل أي شيء آخر.

استخدمها عندما **لا تُقلع** عقدة CE أبدًا: فشل التسجيل، أو غياب الموقع عن
المستأجر، أو كانت العقدة تعمل لكن دون مسار للخروج. في كل تلك الحالات لا تمتلك
[واجهة API للتصحيح](../debug-api/) أي نفق لتمرير الاتصال عبره. ويصمد [SSH](../ssh/) أمام
فشل التسجيل، لكن فقط إذا كان مفتاحه قد كُتب بالفعل عند الإقلاع الأول وكان بإمكانك
الوصول إلى العنوان الداخلي للعقدة من داخل VNet — وكلاهما غير متحقق في عقدة
تقابلها للمرة الأولى.

جرّب [وحدة تحكم الموقع](../site-console/) قبل هذه الطريقة إذا كان للعقدة *أي* مسار شبكي
عامل: فهي أيضًا تصمد أمام فشل التسجيل، ولا تحتاج إلى مفتاح، ولا تطرد الشخص الذي
ينظر إلى العقدة بالفعل. أما وحدة التحكم التسلسلية فهي ما يتبقى عندما يكون المسار
الشبكي نفسه هو العنصر المعطوب.

## الشرط المسبق: تشخيصات التشغيل

تتطلب Azure تمكين تشخيصات التشغيل على الجهاز الافتراضي قبل أن تسمح بربط وحدة تحكم تسلسلية.
ويُمكِّن ذلك `terraform/modules/ce-node`:

```hcl
boot_diagnostics {}
```

يؤدي الكتلة الفارغة إلى اختيار تخزين تديره Azure، لذا لا يوجد حساب تخزين
للتشخيصات ولا سياسة دورة حياة ولا مفتاح وصول يجب امتلاكه. تأكد من ذلك على العقدة:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="التمكين ليس بأثر رجعي">
تلتقط تشخيصات التشغيل السجل التسلسلي **عند الإقلاع**. وتشغيلها لجهاز افتراضي
يعمل بالفعل لا يُنتج سجلًا للإقلاع الذي حدث سابقًا، لذا يجيب
`az vm boot-diagnostics get-boot-log`:

```text
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

هذا متوقع وليس خطأً. يوجد سجل إقلاع بعد إعادة تشغيل العقدة في المرة التالية. أما
الربط المباشر بوحدة التحكم فيعمل فورًا — فهو لا يعتمد على السجل.
</Aside>

## التحقق من التوفر دون طرفية

يحتاج الربط إلى جلسة تفاعلية، لكن معرفة ما إذا كان *سيتم* الربط يتم عبر
استدعاءي API. وكلاهما مفيد في فحص السلامة.

يجب أن تكون الخدمة مُمكَّنة للاشتراك — إذ يمكن للمسؤول تعطيلها على مستوى
المستأجر بالكامل:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

ثم اطلب اتصالًا بالمنفذ التسلسلي لعقدة محددة:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

وجود `connectionString` يبدأ بـ `wss://` — في هذا النشر
`eastus.gateway.serialconsole.azure.com` — يعني أن وحدة التحكم قابلة للربط الآن.
وقبل تمكين تشخيصات التشغيل، لم يكن لهذا الاستدعاء ما يرتبط به.

<Aside type="danger" title="سلسلة الاتصال هذه هي بيانات اعتماد">
إنها رمز حامل قصير العمر مُضمَّن في عنوان URL. لا تسجّله، ولا تلصقه في
تذكرة دعم، ولا تودعه في مستودع. اطبع المضيف فقط عندما تعرض أن الاستدعاء
نجح.
</Aside>

## الربط

<Steps>

1. ثبّت الإضافة مرة واحدة:

   ```bash
   az extension add --name serial-console
   ```

2. اربط:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. ستصل إلى محثّ تسجيل الدخول الخاص بالعقدة نفسها، وليس إلى صدفة، وذلك خلف لافتة
   التدقيق الخاصة بالجهاز. تُثبت وحدة التحكم التسلسلية أن *القناة* تعمل؛ لكنها لا
   تتجاوز المصادقة.

   <Aside type="caution" title="بيانات الاعتماد التي يقبلها تسجيل الدخول التسلسلي غير متحققة">
   لم يُكمل أحد تسجيل دخول عبر وحدة التحكم التسلسلية في هذا النشر، لذا لا تحدد هذه
   الصفحة ما يجب كتابته. الحساب `admin` هو حساب الجهاز الذي تكون صدفته هي Site CLI، وهو
   الحساب نفسه الذي يُصادق عبر
   [وحدة تحكم الموقع](../site-console/) بكلمة مرور — لكن لم يُظهَر أن كلمة المرور تعمل عبر
   تسجيل الدخول بوحدة التحكم التسلسلية، و`sshd` مقصور على المفاتيح فقط للحساب `admin`، لذا
   فإن المسارين ليسا — بشكل واضح — مسار بيانات الاعتماد نفسه.
   </Aside>

</Steps>

مُلتقط من `f5-xc-ce-vm-01`، مع حذف الجزء الأوسط حيث لا يضيف مخرج وحدة systemd
أي شيء:

```text file=../../../_data/serial-console-boot.txt
```

هناك أربعة أمور في ذلك النص جديرة بالملاحظة، لأنها تجيب على أسئلة لا تستطيع
واجهة API للتصحيح الإجابة عنها:

- **اكتمال cloud-init** — `Datasource DataSourceAzure`، انتهى عند 22.37 ثانية.
  العقدة التي لا تُسجَّل أبدًا تفشل عادة هنا، وهنا حيث ترى ذلك.
- **بدء تشغيل بيئتَي تشغيل الحاويات.** كل من `Container Runtime Interface for OCI (CRI-O)`
  و`Docker Application Container Engine` بحالة `[ OK ]`، وهو الدليل عند الإقلاع
  على سلوك بيئة التشغيل المزدوجة الذي يفاجئ الناس في
  [crictl](../../commands/system/crictl/) و[docker](../../commands/system/docker/).
- **`VP Manager image load` و`Argo Watch service`** — بدء تشغيل `vpm` وArgo.
- **المحثّ هو محثّ العقدة نفسها**، خلف لافتة التدقيق الخاصة بها. وحدة التحكم
  التسلسلية توصلك إلى محثّ تسجيل دخول، وليس إلى جلسة.

<Aside type="caution" title="الربط التفاعلي يحتاج إلى طرفية حقيقية — لكن يمكن كتابته في سكربت">
يضع `az serial-console connect` الطرفية في الوضع الخام، لذا لا يمكن تشغيله من
خط أنابيب أو من أي سياق بلا TTY. ويفشل من جهة العميل، قبل الاتصال بـ Azure:

```text
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

هذا التتبع يتعلق بمعالجة الطرفية، وليس انقطاعًا في وحدة التحكم التسلسلية.

أما الربط نفسه، فهو **قابل** للأتمتة — قُد الـ websocket مباشرة بدلًا من
استخدام واجهة سطر الأوامر. وقد التُقط النص أعلاه بهذه الطريقة، دون TTY. راجع
`scripts/serial_console_capture.py`، وهي الطريقة التي ستجمع بها أدلة الإقلاع من
عقدة فشلت في التسجيل دون وجود شخص جالس أمام طرفية.
</Aside>

<Aside type="caution" title="توقّع إعادة المحاولة: تعتبر البوابة ترفض ما يقارب محاولة من كل اثنتين">
الإطار الأول من البوابة هو تحدٍّ، وليس مخرجًا، ويجيب عليه العميل برمز حامل. وحتى
عندما يُنجز ذلك بشكل صحيح، غالبًا ما يُغلق المقبس فورًا:

```text
[close] code=1011 reason=Connection not trusted
```

السلوك المرصود: تنجح بشكل متقطع، وتحت الاستخدام المستمر ترفض كل عقدة في
مجموعة الموارد — بما في ذلك العقد التي كانت تعمل قبل دقائق.
يعيد `scripts/serial_console_capture.py` المحاولة افتراضيًا لأن إعادة المحاولة تنجح كثيرًا.

**السبب غير مُثبَت.** وما استُبعد، لأن كل واحد منها تخمين معقول يهدر الوقت:

| ليس هذا | كيفية التأكد |
| --- | --- |
| تقييد ARM/compute | ذلك يُرجع HTTP `429` على استدعاءات ARM. أما هذا فهو إغلاق websocket على قناة بيانات منفصلة. |
| اعتراض TLS بواسطة وكيل | `openssl s_client -connect <region>.gateway.serialconsole.azure.com:443 \| openssl x509 -noout -issuer`. وجود مُصدِر أصلي `O=Microsoft Corporation` يستبعد ذلك؛ ووجود مورّد وكيل كمُصدِر يؤكده، والحل هو إضافة `*.serialconsole.azure.com` إلى قائمة السماح. |
| تعطيل تشخيصات التشغيل | `az vm show -g <rg> -n <vm> --query diagnosticsProfile` يُبلّغ عن `enabled: true`. |
| عدم تطابق الرمز بين المنح والتحدي | استخدام رمز واحد للاثنين هو الممارسة الصحيحة، لكنه لا يمنع الإغلاق. |

أما ما *هو* سلوك موثَّق في Azure: **جلسة وحدة تحكم تسلسلية واحدة لكل جهاز افتراضي،
والطلب الناجح الثاني يطرد الأول.** يُقطع اتصال المستخدم المطرود لكن لا يُخرج من
النظام، لذا تبقى جلسة الصدفة قائمة. وشخصان يصححان عقدة واحدة سيطردان أحدهما
الآخر بشكل متكرر.

للأعمال الجماعية، فضّل [واجهة API للتصحيح](../debug-api/) أو [SSH](../ssh/)، فكلاهما لا
تنطبق عليه هذه القيود. وSSH بشكل خاص لا يفرض حدًّا على اللصق ولا قيدًا على الجلسة
الواحدة، لذا فهو الخيار الأفضل كلما كانت العقدة قابلة للوصول من داخل VNet.
</Aside>

<Aside type="caution" title="اللصق محدود بـ 2,048 حرفًا">
تحدّ Azure طول اللصق في وحدة التحكم التسلسلية بـ 2,048 حرفًا، لتجنّب إرهاق
المنفذ التسلسلي. وإرسال أمر طويل — أو دفعة من الأوامر في عملية كتابة واحدة —
يفشل بطريقة تُقرأ كتعليق أو تقييد بدلًا من كونها حدًّا على الطول.

أرسل الأوامر فرادى. هذا قيد حقيقي على أي جمع جماعي للبيانات عبر وحدة التحكم
التسلسلية، وسبب آخر لتفضيل [واجهة API للتصحيح](../debug-api/) لهذا العمل.
</Aside>

## ما يمكنك رؤيته هنا وما لا تستطيع واجهة API إظهاره

- **cloud-init** أثناء تشغيله، أو فشله، أو عدم بدئه أبدًا — السبب المعتاد لعقدة
  لا تُسجَّل أبدًا.
- **محاولات التسجيل** مقابل `register.ves.volterra.io`، بما في ذلك خطأ في
  التكوين أو رمز رفضه المستأجر.
- **رسائل النواة والإقلاع** من قبل تشغيل أي وكيل.
- العقدة عندما **لا يوجد لها مسار شبكي عامل**، وهو ما يُبطل كل مسار آخر.

أما للعقدة التي *تكون* `ONLINE`، فضّل واجهة API للتصحيح: فهي قابلة للكتابة في
سكربتات، وتنتج أدلة يمكنك إعادة تشغيلها، ولا تشغل المنفذ التسلسلي الوحيد.
