تتصل وحدة التحكم التسلسلية في Azure بالمنفذ التسلسلي المحاكى للعقدة عبر منصة Azure.
لا تعبر المستوى الضابط لـ F5 Distributed Cloud، ولا المستوى الإجرائي للعقدة، ولا أي مسار شبكي تتحكم فيه العقدة — وهذا بالضبط ما يجعلها تعمل حين لا يعمل شيء آخر.

الجأ إليها حين لا يكتمل رفع CE **أبداً**: إذا فشل التسجيل، أو غاب الموقع عن المستأجر، أو كانت العقدة تعمل لكن بلا مسار للخروج. في كل هذه الحالات لا تملك [واجهة برمجة تطبيقات debug](../debug-api/) أي نفق لتمرير الطلبات عبره. يبقى [SSH](../ssh/) صالحاً بعد فشل التسجيل، لكن فقط إذا كان مفتاحه قد كُتب مسبقاً عند الإقلاع الأول وأمكنك الوصول إلى العنوان الداخلي للعقدة من داخل VNet — وهذان الشرطان لا ينطبقان على عقدة تتعرف إليها لأول مرة.

## المتطلب الأساسي: تشخيصات الإقلاع

تشترط Azure تفعيل تشخيصات الإقلاع على الجهاز الافتراضي قبل السماح بتوصيل وحدة التحكم التسلسلية.
يُفعّل ذلك بواسطة `terraform/modules/ce-node`:

```hcl
boot_diagnostics {}
```

يختار الكتلة الفارغة التخزين المُدار من Azure، ممّا يُغني عن حساب تخزين للتشخيصات أو سياسة دورة حياة أو مفتاح وصول. تحقق من ذلك على عقدة:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="التفعيل ليس بأثر رجعي">
تلتقط تشخيصات الإقلاع السجل التسلسلي **عند الإقلاع**. تشغيلها على جهاز افتراضي يعمل بالفعل لا ينتج سجلاً للإقلاع الذي حدث مسبقاً، لذا يُجيب `az vm boot-diagnostics get-boot-log` بـ:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

هذا متوقع وليس خطأً. يُوجد سجل الإقلاع بعد إعادة تشغيل العقدة في المرة التالية. أما توصيل وحدة التحكم المباشر فيعمل فوراً — ولا يعتمد على السجل.
</Aside>

## التحقق من التوفر دون جلسة طرفية

يتطلب التوصيل جلسة تفاعلية، لكن إمكانية التوصيل يمكن استيضاحها بمكالمتَي API. كلتاهما مفيدتان في فحص الصحة.

يجب أن تكون الخدمة مفعّلة للاشتراك — إذ يستطيع المسؤول تعطيلها على مستوى المستأجر بأكمله:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

ثم اطلب اتصالاً بالمنفذ التسلسلي لعقدة محددة:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

`connectionString` يبدأ بـ `wss://` — في هذا النشر
`eastus.gateway.serialconsole.azure.com` — يعني أن وحدة التحكم قابلة للتوصيل الآن. قبل تفعيل تشخيصات الإقلاع، لم يكن لهذه المكالمة ما تتوصل إليه.

<Aside type="danger" title="سلسلة الاتصال هذه بيانات اعتماد">
إنها رمز حامل قصير الأجل مضمّن في رابط URL. لا تُسجّلها، ولا تلصقها في تذكرة دعم، ولا تحفظها في مستودع الكود. اطبع اسم المضيف فقط عند إثبات نجاح المكالمة.
</Aside>

## التوصيل

<Steps>

1. ثبّت الامتداد مرة واحدة:

   ```bash
   az extension add --name serial-console
   ```

2. وصّل:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. ستصل إلى موجه تسجيل الدخول الخاص بالعقدة، لا إلى صدفة مباشرة. هذه هي Site CLI، وتحتاج إلى بيانات اعتماد مُعيَّنة على العقدة — كلمة مرور المسؤول من عملية التوفير، أو كلمة مرور مُحدَّثة عبر نقطة النهاية الخاصة بتغيير كلمة المرور. تثبت وحدة التحكم التسلسلية أن *القناة* تعمل؛ لكنها لا تتجاوز المصادقة.

</Steps>

مُلتقَط من `f5-xc-ce-vm-01`، مع حذف في المنتصف حيث لا تضيف مخرجات وحدة systemd شيئاً:

```text file=../../../_data/serial-console-boot.txt
```

تستحق أربعة أشياء في ذلك النص الانتباه، لأنها تجيب عن أسئلة لا تستطيع واجهة برمجة تطبيقات debug الإجابة عنها:

- **اكتمل cloud-init** — `Datasource DataSourceAzure`، انتهى عند 22.37 ثانية.
  العقدة التي لا تُسجَّل أبداً تفشل عادةً هنا، وهذا هو المكان الذي ترى فيه ذلك.
- **انطلق كلا وقتَي تشغيل الحاويات.** `Container Runtime Interface for OCI (CRI-O)`
  و`Docker Application Container Engine` كلاهما `[ OK ]`، وهو الإثبات عند الإقلاع على السلوك المزدوج وقت التشغيل الذي يُفاجئ المستخدمين في
  [crictl](../../commands/system/crictl/) و[docker](../../commands/system/docker/).
- **`VP Manager image load` و`Argo Watch service`** — `vpm` وArgo يبدآن.
- **موجه الأوامر خاص بالعقدة**، خلف لافتة التدقيق. تمنحك وحدة التحكم التسلسلية موجه تسجيل الدخول لا جلسة مفتوحة.

<Aside type="caution" title="التوصيل التفاعلي يحتاج طرفية حقيقية — لكن يمكن أتمتته">
يضع `az serial-console connect` الطرفية في الوضع الخام، لذا لا يمكن تشغيله من خط أنابيب أو أي سياق بلا TTY. يفشل من جانب العميل قبل الاتصال بـ Azure:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

هذا التتبع خاص بمعالجة الطرفية وليس انقطاعاً في وحدة التحكم التسلسلية.

أما التوصيل نفسه فـ**قابل للأتمتة** — شغّل websocket مباشرةً بدلاً من CLI. النص المُلتقَط أعلاه جُمع بهذه الطريقة دون TTY. انظر
`scripts/serial_console_capture.py`، وهي الطريقة التي تجمع بها أدلة الإقلاع من عقدة فشلت في التسجيل دون حضور بشري أمام الطرفية.
</Aside>

<Aside type="caution" title="توقع إعادة المحاولة: البوابة ترفض تقريباً كل محاولة أخرى">
الإطار الأول من البوابة هو تحدٍّ لا مخرجات، ويردّ العميل عليه برمز حامل. حتى عند القيام بذلك بشكل صحيح يُغلق المقبس في الغالب فوراً:

```
[close] code=1011 reason=Connection not trusted
```

السلوك الملاحظ: ينجح بصورة متقطعة، وعند الاستخدام المستمر ترفض كل عقدة في مجموعة الموارد — بما فيها عقد كانت تعمل قبل دقائق.
يُعيد `scripts/serial_console_capture.py` المحاولة بصورة افتراضية لأن إعادة المحاولة كثيراً ما تنجح.

**السبب غير محدد.** ما تم استبعاده لأن كل احتمال منه تخمين معقول يُضيّع الوقت:

| ليس هذا | كيف تتحقق |
| --- | --- |
| تقنين ARM/compute | ذاك يُعيد HTTP `429` في مكالمات ARM. هذا إغلاق websocket على قناة بيانات منفصلة. |
| اعتراض TLS من وكيل | `openssl s_client -connect <region>.gateway.serialconsole.azure.com:443 \| openssl x509 -noout -issuer`. مُصدِر `O=Microsoft Corporation` الحقيقي يستبعده؛ مُصدِر من بائع وكيل يؤكده، والحل هو إدراج `*.serialconsole.azure.com` في القائمة البيضاء. |
| تعطيل تشخيصات الإقلاع | `az vm show -g <rg> -n <vm> --query diagnosticsProfile` يُظهر `enabled: true`. |
| عدم تطابق الرمز بين المنح والتحدي | استخدام رمز واحد للاثنين ممارسة صحيحة، لكنه لا يمنع الإغلاق. |

ما هو **موثّق** في سلوك Azure: **جلسة وحدة تحكم تسلسلية واحدة لكل جهاز افتراضي، وطلب ناجح ثانٍ يُزيح الأول.** يُقطع اتصال المستخدم المُزاح لكنه لا يُسجَّل خروجه، فتبقى جلسة الصدفة حية. شخصان يعالجان عقدة واحدة سيُزيح كل منهما الآخر بصورة متكررة.

للأعمال الجماعية يُفضّل استخدام [واجهة برمجة تطبيقات debug](../debug-api/) أو [SSH](../ssh/)، ولا يعاني أي منهما من هذه القيود. يتميز SSH بعدم وجود حد للصق ولا قيد على جلسة واحدة، لذا فهو الخيار الأفضل كلما كانت العقدة قابلة للوصول من داخل VNet.
</Aside>

<Aside type="caution" title="اللصق محدود بـ 2048 حرفاً">
تُقيّد Azure طول اللصق في وحدة التحكم التسلسلية بـ 2048 حرفاً لتفادي إثقال المنفذ التسلسلي. إرسال أمر طويل — أو دفعة أوامر في كتابة واحدة — يفشل بطريقة تبدو كتعليق أو تقنين لا كحد للطول.

أرسل الأوامر واحداً تلو الآخر. هذا قيد حقيقي على أي جمع بيانات جماعي عبر وحدة التحكم التسلسلية، وسبب إضافي للتفضيل [واجهة برمجة تطبيقات debug](../debug-api/) لتلك الأعمال.
</Aside>

## ما يمكنك رؤيته هنا ولا تستطيع الـ API إظهاره

- **cloud-init** يعمل أو يفشل أو لا يبدأ أبداً — السبب المعتاد لعقدة لا تُسجَّل قط.
- **محاولات التسجيل** على `register.ves.volterra.io`، بما فيها خطأ في الإعداد أو رمز رفضه المستأجر.
- **رسائل النواة والإقلاع** من قبل تشغيل أي عامل.
- العقدة حين **لا يوجد مسار شبكي يعمل**، مما يُعطّل كل مسار آخر.

لعقدة في حالة `ONLINE`، يُفضّل استخدام واجهة برمجة تطبيقات debug: فهي قابلة للأتمتة، وتنتج أدلة يمكن إعادة تشغيلها، ولا تحتل المنفذ التسلسلي الوحيد.
