ترتبط وحدة التحكم التسلسلية في Azure بالمنفذ التسلسلي المحاكى للعقدة عبر منصة
Azure. وهي لا تعبر مستوى التحكم في F5 Distributed Cloud، ولا مستوى بيانات العقدة،
ولا أي مسار شبكي تتحكم فيه العقدة — وهذا بالضبط سبب عملها عندما يفشل كل شيء آخر.

استخدمها عندما **لا تُقلع** عقدة CE أصلًا: فشل التسجيل، أو غياب الموقع
عن المستأجر، أو أن العقدة تعمل لكن لا يوجد لها مسار للخارج. في جميع هذه الحالات
لا تمتلك [debug API](../debug-api/) نفقًا لتمرير البيانات عبره، و
[لا يستطيع SSH المصادقة](../ssh/) على هذا البناء.

## الشرط المسبق: تشخيصات الإقلاع

تشترط Azure تمكين تشخيصات الإقلاع على الجهاز الافتراضي قبل أن تربط وحدة تحكم تسلسلية.
ويتم تمكين ذلك بواسطة `terraform/modules/ce-node`:

```hcl
boot_diagnostics {}
```

يحدد الحقل الفارغ استخدام تخزين مُدار بواسطة Azure، لذا لا يوجد حساب تخزين للتشخيصات،
ولا سياسة دورة حياة، ولا مفتاح وصول تملكه. تأكد من ذلك على عقدة:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="التمكين ليس بأثر رجعي">
تُسجّل تشخيصات الإقلاع السجل التسلسلي **عند الإقلاع**. تشغيلها على جهاز افتراضي
قيد التشغيل بالفعل لا يُنتج سجلًا للإقلاع الذي حدث سابقًا، ولذلك يُجيب
`az vm boot-diagnostics get-boot-log` بما يلي:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

هذا متوقع وليس خطأً. يوجد سجل إقلاع بعد إعادة تشغيل العقدة في المرة التالية. أما
الربط المباشر بوحدة التحكم فيعمل فورًا — فهو لا يعتمد على السجل.
</Aside>

## التحقق من التوفر بدون طرفية

يتطلب الربط جلسة تفاعلية، لكن معرفة ما إذا كان الربط *سينجح* هي مسألة استدعاءين
لواجهة API. وكلاهما مفيد في فحص السلامة.

يجب أن تكون الخدمة مُمكّنة للاشتراك — إذ يمكن لأي مسؤول تعطيلها على مستوى
المستأجر بالكامل:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

ثم اطلب اتصالًا بالمنفذ التسلسلي لعقدة محددة:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

وجود `connectionString` يبدأ بـ `wss://` — وفي هذا النشر
`eastus.gateway.serialconsole.azure.com` — يعني أن وحدة التحكم قابلة للربط
الآن. قبل تمكين تشخيصات الإقلاع، لم يكن لهذا الاستدعاء ما يرتبط به.

<Aside type="danger" title="سلسلة الاتصال هذه هي بيانات اعتماد">
إنها رمز حامل (bearer token) قصير العمر مُدمج في عنوان URL. لا تُسجّله، ولا تلصقه في
تذكرة دعم، ولا تُودعه في مستودع. اطبع المضيف فقط عندما تُظهر أن الاستدعاء نجح.
</Aside>

## الربط

<Steps>

1. ثبّت الإضافة مرة واحدة:

   ```bash
   az extension add --name serial-console
   ```

2. اربط:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. ستصل إلى مُحث تسجيل الدخول الخاص بالعقدة، وليس إلى صدفة (shell). هذا هو Site CLI،
   ويحتاج إلى بيانات اعتماد مُعيّنة على العقدة — كلمة مرور المسؤول من مرحلة التزويد، أو
   كلمة مرور مُعيّنة عبر نقطة نهاية تغيير كلمة المرور. تُثبت وحدة التحكم التسلسلية أن
   *القناة* تعمل؛ لكنها لا تتجاوز المصادقة.

</Steps>

مُسجّل من `f5-xc-ce-vm-01`، مع حذف الجزء الأوسط حيث لا يُضيف مخرج وحدة systemd أي
شيء:

```text file=../../../_data/serial-console-boot.txt
```

هناك أربعة أمور في هذا النص تستحق الملاحظة، لأنها تجيب عن أسئلة لا تستطيع
واجهة debug API الإجابة عنها:

- **اكتمال cloud-init** — `Datasource DataSourceAzure`، انتهى عند 22.37 ثانية.
  العقدة التي لا تُسجَّل أبدًا تفشل عادة هنا، وهذا هو المكان الذي ترى فيه ذلك.
- **بدء تشغيل بيئتَي تشغيل الحاويات.** كل من `Container Runtime Interface for OCI (CRI-O)`
  و `Docker Application Container Engine` بحالة `[ OK ]`، وهو الإثبات وقت الإقلاع
  لسلوك بيئتَي التشغيل المزدوجتين الذي يفاجئ الناس في
  [crictl](../../commands/system/crictl/) و [docker](../../commands/system/docker/).
- **`VP Manager image load` و `Argo Watch service`** — بدء تشغيل `vpm` و Argo.
- **المُحث هو مُحث العقدة نفسها**، خلف لافتة التدقيق الخاصة بها. توفّر لك وحدة التحكم
  التسلسلية مُحث تسجيل دخول، لا جلسة.

<Aside type="caution" title="يتطلب الربط التفاعلي طرفية حقيقية — لكن يمكن أتمتته بنص برمجي">
يضع `az serial-console connect` الطرفية في الوضع الخام (raw mode)، لذا لا يمكن تشغيله من
خط أنابيب أو من أي سياق بدون TTY. وهو يفشل من جهة العميل، قبل الاتصال بـ Azure:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

هذا التتبع يتعلق بمعالجة الطرفية، وليس انقطاعًا في وحدة التحكم التسلسلية.

أما الربط نفسه، فهو **قابل** للأتمتة — بتشغيل websocket مباشرة بدلًا من
واجهة الأوامر. تم تسجيل النص أعلاه بهذه الطريقة، بدون TTY. راجع
`scripts/serial_console_capture.py`، وهي الطريقة التي تجمع بها أدلة الإقلاع من
عقدة فشلت في التسجيل دون حضور شخص أمام طرفية.
</Aside>

<Aside type="caution" title="توقّع إعادة المحاولة: تَرفض البوابة نحو كل محاولة ثانية">
الإطار الأول من البوابة هو تحدٍّ (challenge)، لا مخرجات، ويردّ العميل عليه برمز
حامل. وحتى عند تنفيذ ذلك بشكل صحيح، غالبًا ما يُغلق المقبس فورًا:

```
[close] code=1011 reason=Connection not trusted
```

السلوك المرصود: تنجح بشكل متقطع، وتحت الاستخدام المتواصل تَرفض كل عقدة في
مجموعة الموارد — بما في ذلك العقد التي عملت قبل دقائق.
يُعيد `scripts/serial_console_capture.py` المحاولة افتراضيًا لأن إعادة المحاولة تنجح غالبًا.

**السبب غير مُثبت.** وفيما يلي ما تم استبعاده، لأن كل احتمال منها تخمين معقول
يُهدر الوقت:

| ليس هذا | كيف تتأكد |
| --- | --- |
| تقييد (throttling) من ARM/compute | ذلك يُعيد HTTP `429` على استدعاءات ARM. أما هذا فإغلاق websocket على قناة بيانات منفصلة. |
| اعتراض TLS بواسطة وكيل (proxy) | `openssl s_client -connect <region>.gateway.serialconsole.azure.com:443 \| openssl x509 -noout -issuer`. وجود مُصدِر أصلي `O=Microsoft Corporation` يستبعد ذلك؛ ووجود مورّد وكيل كمُصدِر يُثبته، والحل هو إضافة `*.serialconsole.azure.com` إلى قائمة السماح. |
| تعطيل تشخيصات الإقلاع | `az vm show -g <rg> -n <vm> --query diagnosticsProfile` يُبلّغ عن `enabled: true`. |
| عدم تطابق الرمز بين المنحة والتحدي | استخدام رمز واحد لكليهما هو الممارسة الصحيحة، لكنه لا يمنع الإغلاق. |

أما ما هو *موثّق* كسلوك في Azure: **جلسة وحدة تحكم تسلسلية واحدة لكل جهاز افتراضي، وأي
طلب ثانٍ ناجح يُطرد الأول.** يُقطع اتصال المستخدم المطرود لكن لا يتم تسجيل خروجه،
لذا تبقى جلسة الصدفة قائمة. وشخصان يُنقّبان عن أخطاء عقدة واحدة سيُزيح كل منهما
الآخر مرارًا.

للأعمال الجماعية، فضّل [debug API](../debug-api/)، التي لا تخضع لأي من هذه الحدود.
[SSH ليس بديلًا](../ssh/) — فلا يمكن تمكينه على هذا البناء.
</Aside>

<Aside type="caution" title="اللصق محدود بـ 2,048 حرفًا">
تحدّ Azure طول اللصق في وحدة التحكم التسلسلية بـ 2,048 حرفًا، لتجنّب إثقال
المنفذ التسلسلي. إرسال أمر طويل — أو دفعة أوامر في عملية كتابة واحدة — يفشل بطريقة
تُقرأ كتعليق أو تقييد، لا كحدّ في الطول.

أرسل الأوامر فرديًا. هذا قيد حقيقي على أي جمع جماعي عبر وحدة التحكم التسلسلية،
وسبب آخر لتفضيل [debug API](../debug-api/) في ذلك العمل.
</Aside>

## ما يمكنك رؤيته هنا ولا تستطيع واجهة API إظهاره

- **cloud-init** أثناء التشغيل، أو الفشل، أو عدم البدء أصلًا — وهو السبب المعتاد لعقدة
  لا تُسجَّل أبدًا.
- **محاولات التسجيل** مقابل `register.ves.volterra.io`، بما في ذلك خطأ في
  التكوين أو رمز رفضه المستأجر.
- **رسائل النواة والإقلاع** من قبل تشغيل أي وكيل.
- العقدة عندما **لا يوجد لها مسار شبكي عامل**، وهو ما يُبطل كل مسار آخر.

للعقدة التي *تكون* `ONLINE`، فضّل debug API: فهي قابلة للأتمتة بالنصوص البرمجية، وتُنتج
أدلة يمكنك إعادة تشغيلها، ولا تشغل المنفذ التسلسلي الوحيد.
