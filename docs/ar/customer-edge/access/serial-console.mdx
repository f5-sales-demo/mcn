تتصل Azure Serial Console بالمنفذ التسلسلي المحاكى للعقدة عبر منصة Azure.
لا تمر عبر مستوى تحكم F5 Distributed Cloud، ولا عبر مستوى البيانات الخاص بالعقدة،
ولا عبر أي مسار شبكي تتحكم فيه العقدة — وهذا بالضبط ما يجعلها تعمل حين لا يعمل شيء آخر.

استخدمها عندما لا تعمل CE **أبداً**: فشل التسجيل، أو أن الموقع غائب عن المستأجر،
أو أن العقدة تعمل لكن ليس لديها مسار للخروج. في كل هذه الحالات، لا يملك
[debug API](../debug-api/) أي نفق لتمرير الاتصال عبره، كما أن SSH مغلق على العقدة
كما جُهِّزت.

## المتطلب الأساسي: تشخيصات الإقلاع

تشترط Azure تفعيل تشخيصات الإقلاع على الجهاز الافتراضي قبل أن تُرفق به وحدة تحكم
تسلسلية. يُمكِّن ذلك `terraform/modules/ce-node`:

```hcl
boot_diagnostics {}
```

الكتلة الفارغة تختار التخزين المُدار من Azure، لذلك لا يوجد حساب تخزين تشخيصات
أو سياسة دورة حياة أو مفتاح وصول للإدارة. تحقق من ذلك على عقدة:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="تفعيلها لا يُطبَّق بأثر رجعي">
تلتقط تشخيصات الإقلاع السجل التسلسلي **عند الإقلاع**. تفعيلها لجهاز افتراضي
يعمل بالفعل لا ينتج سجلاً للإقلاع الذي حدث بالفعل، لذا يُجيب
`az vm boot-diagnostics get-boot-log` بـ:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

هذا متوقع وليس عطلاً. يوجد سجل الإقلاع بعد إعادة تشغيل العقدة التالية. أما الربط
المباشر بوحدة التحكم فيعمل فوراً — ولا يعتمد على السجل.
</Aside>

## التحقق من التوفر دون طرفية

يحتاج الربط إلى جلسة تفاعلية، لكن معرفة ما إذا كان سيربط *فعلاً* أم لا يتطلب
مجرد استدعائَي API. كلاهما مفيد في فحص الصحة.

يجب أن تكون الخدمة مفعّلة للاشتراك — يمكن للمسؤول تعطيلها على مستوى المستأجر:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

ثم اطلب اتصالاً بمنفذ تسلسلي لعقدة محددة:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

`connectionString` يبدأ بـ `wss://` — في هذا النشر
`eastus.gateway.serialconsole.azure.com` — يعني أن وحدة التحكم قابلة للربط الآن.
قبل تفعيل تشخيصات الإقلاع، لم يكن لهذا الاستدعاء ما يربطه.

<Aside type="danger" title="سلسلة الاتصال هذه هي بيانات اعتماد">
إنها رمز تحمل قصير الأجل مضمَّن في رابط URL. لا تسجّله، ولا تلصقه في تذكرة دعم،
ولا تودعه في مستودع. اطبع اسم المضيف فقط عند إثبات نجاح الاستدعاء.
</Aside>

## الربط

<Steps>

1. ثبِّت الامتداد مرة واحدة:

   ```bash
   az extension add --name serial-console
   ```

2. اربط:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. ستصل إلى موجه تسجيل الدخول الخاص بالعقدة، لا إلى Shell. هذه هي Site CLI،
   وتحتاج إلى بيانات اعتماد مُعيَّنة على العقدة — كلمة مرور المسؤول من مرحلة
   التوفير، أو كلمة مرور مُعيَّنة عبر نقطة نهاية تغيير كلمة المرور. تُثبت وحدة
   التحكم التسلسلية أن *القناة* تعمل؛ لكنها لا تتجاوز المصادقة.

</Steps>

مُلتقَطة من `f5-xc-ce-vm-01`، محذوفة في المنتصف حيث لا تضيف مخرجات وحدة systemd
شيئاً:

```text file=../../../_data/serial-console-boot.txt
```

أربعة أشياء في ذلك النص الملتقط تستحق الملاحظة، لأنها تجيب على أسئلة لا يستطيع
debug API الإجابة عليها:

- **اكتمال cloud-init** — `Datasource DataSourceAzure`، انتهى عند 22.37 ثانية.
  العقدة التي لا تُسجَّل قط عادةً ما تكون قد فشلت هنا، وهنا تراها.
- **بدء تشغيل كلا بيئتَي الحاويات.** `Container Runtime Interface for OCI (CRI-O)`
  و`Docker Application Container Engine` كلاهما بحالة `[ OK ]`، وهو الدليل عند
  الإقلاع على سلوك البيئتين المزدوجتين الذي يُفاجئ الناس في
  [crictl](../../commands/system/crictl/) و[docker](../../commands/system/docker/).
- **`VP Manager image load` و`Argo Watch service`** — `vpm` وArgo يبدآن.
- **الموجه هو موجه العقدة نفسه**، خلف بانر التدقيق. تُعطيك وحدة التحكم التسلسلية
  موجه تسجيل دخول، لا جلسة.

<Aside type="caution" title="الربط التفاعلي يحتاج طرفية حقيقية — لكن يمكن أتمتته">
يضع `az serial-console connect` الطرفية في الوضع الخام، لذلك لا يمكن تشغيله من
pipeline أو أي سياق بدون TTY. يفشل من جهة العميل، قبل الاتصال بـ Azure:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

هذا التتبع يتعلق بمعالجة الطرفية، وليس انقطاعاً في وحدة التحكم التسلسلية.

أما الربط نفسه فـ**قابل للأتمتة** — قُد مقبس WebSocket مباشرةً بدلاً من CLI.
النص الملتقط أعلاه كان ملتقَطاً بهذه الطريقة، دون TTY. انظر
`scripts/serial_console_capture.py`، وهي الطريقة التي تجمع بها أدلة الإقلاع من
عقدة فشلت في التسجيل دون الحاجة إلى إنسان يجلس أمام طرفية.
</Aside>

<Aside type="caution" title="توقع إعادة المحاولة: البوابة ترفض تقريباً كل محاولة أخرى">
الإطار الأول من البوابة هو تحدٍّ لا مخرجات، والعميل يُجيب عليه برمز تحمُّل.
حتى حين يتم ذلك بشكل صحيح، كثيراً ما يُغلق المقبس فوراً:

```
[close] code=1011 reason=Connection not trusted
```

قياساً عبر محاولات متكررة على ثلاث عقد، يتناوب هذا: الرفض يعقبه نجاح على
نفس العقدة. هذا يتسق مع وجود جلسة سابقة لا تزال محتجزة، وأن المحاولة المرفوضة
تُحررها.

**هذه ليست مشكلة بيانات اعتماد**، رغم الرسالة. عادةً تكفي إعادة المحاولة،
وهذا لماذا يُعيد `scripts/serial_console_capture.py` المحاولة افتراضياً.

استخدم رمزاً واحداً لكل من طلب الجلسة والتحدي على أي حال، مطابقاً لامتداد `az`.
هذه ممارسة صحيحة، لكنها ليست سبب هذه المشكلة.
</Aside>

## ما يمكنك رؤيته هنا مما لا يستطيع API إظهاره

- **cloud-init** يعمل، أو يفشل، أو لا يبدأ أبداً — السبب المعتاد لعقدة لا تُسجَّل قط.
- **محاولات التسجيل** مقابل `register.ves.volterra.io`، بما فيها خطأ في التهيئة أو
  رمز رفضه المستأجر.
- **رسائل النواة والإقلاع** من قبل أن يعمل أي وكيل.
- العقدة حين **لا يوجد مسار شبكي يعمل**، مما يُعطّل كل مسار آخر.

للعقدة التي تكون `ONLINE`، فضِّل debug API: فهو قابل للأتمتة، وينتج أدلة يمكن
إعادة تشغيلها، ولا يشغل المنفذ التسلسلي الوحيد.
