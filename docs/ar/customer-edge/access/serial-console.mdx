ترتبط وحدة التحكم التسلسلية في Azure بالمنفذ التسلسلي المُحاكى للعقدة عبر منصة
Azure. وهي لا تعبر مستوى التحكم في F5 Distributed Cloud، ولا مستوى البيانات في العقدة،
ولا أي مسار شبكي تتحكم فيه العقدة — وهذا بالضبط سبب عملها
عندما يفشل كل شيء آخر.

استخدمها عندما **لا يعمل** CE من الأساس: فشل التسجيل، أو الموقع غائب
عن المستأجر، أو العقدة تعمل لكن لا يوجد لها مسار للخارج. في جميع هذه الحالات
لا تمتلك [واجهة تصحيح الأخطاء](../debug-api/) نفقًا تُرحّل عبره. [SSH](../ssh/) يصمد بعد
فشل التسجيل، لكن فقط إذا كان مفتاحه قد كُتب بالفعل عند الإقلاع الأول وكان بإمكانك
الوصول إلى العنوان الداخلي للعقدة من داخل VNet — وكلا الشرطين غير متحقق في
عقدة تصادفها للمرة الأولى.

جرّب [وحدة تحكم الموقع](../site-console/) قبل هذه إذا كان للعقدة *أي* مسار شبكي عامل:
فهي أيضًا تصمد بعد فشل التسجيل، ولا تحتاج إلى مفتاح، ولا تطرد الشخص
الذي يفحص العقدة بالفعل. وحدة التحكم التسلسلية هي ما يتبقى عندما يكون المسار الشبكي هو
العنصر المعطوب.

## المتطلب المسبق: تشخيصات الإقلاع

تتطلب Azure تمكين تشخيصات الإقلاع على الجهاز الافتراضي قبل أن تسمح بربط وحدة تحكم تسلسلية.
ويتم تمكين ذلك عبر `terraform/modules/ce-node`:

```hcl
boot_diagnostics {}
```

يختار الحظر الفارغ التخزين المُدار بواسطة Azure، لذا لا يوجد حساب تخزين للتشخيصات،
ولا سياسة دورة حياة، ولا مفتاح وصول تملكه. تأكّد من ذلك على إحدى العقد:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="تمكينها لا يعمل بأثر رجعي">
تُسجّل تشخيصات الإقلاع السجل التسلسلي **عند الإقلاع**. تشغيلها لجهاز افتراضي
يعمل بالفعل لا يُنتج سجلًا للإقلاع الذي حدث سابقًا، لذا فإن
`az vm boot-diagnostics get-boot-log` يجيب بما يلي:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

هذا متوقع، وليس خطأً. يوجد سجل إقلاع بعد أن تُعاد تشغيل العقدة في المرة التالية. أما
الربط المباشر بوحدة التحكم فيعمل فورًا — فهو لا يعتمد على السجل.
</Aside>

## التحقق من التوفر بدون طرفية

يحتاج الربط إلى جلسة تفاعلية، لكن معرفة ما إذا كان *سيُربط* لا تتجاوز نداءي واجهة برمجية.
وكلاهما مفيد في فحص السلامة.

يجب أن تكون الخدمة ممكّنة للاشتراك — فقد يعطّلها المسؤول
على مستوى المستأجر بأكمله:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

ثم اطلب اتصالًا بالمنفذ التسلسلي لعقدة محددة:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

وجود `connectionString` يبدأ بـ `wss://` — وفي هذا النشر
`eastus.gateway.serialconsole.azure.com` — يعني أن وحدة التحكم قابلة للربط
الآن. قبل تمكين تشخيصات الإقلاع، لم يكن لهذا النداء ما يرتبط به.

<Aside type="danger" title="سلسلة الاتصال تلك هي بيانات اعتماد">
إنها رمز حامل قصير الأجل مُدمج في عنوان URL. لا تُسجّله، ولا تلصقه في
تذكرة، ولا تُودعه في المستودع. اطبع المضيف فقط عندما تُبيّن أن النداء
قد نجح.
</Aside>

## الربط

<Steps>

1. ثبّت الإضافة مرة واحدة:

   ```bash
   az extension add --name serial-console
   ```

2. اربط:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. ستصل إلى مُحث تسجيل الدخول الخاص بالعقدة نفسها، وليس إلى واجهة أوامر، خلف لافتة التدقيق
   الخاصة بالجهاز. تُثبت وحدة التحكم التسلسلية أن *القناة* تعمل؛ لكنها لا تتجاوز المصادقة.

   <Aside type="caution" title="بيانات الاعتماد التي يقبلها تسجيل الدخول التسلسلي غير مُتحقق منها">
   لم يُكمل أحد تسجيل دخول عبر وحدة التحكم التسلسلية في هذا النشر، لذا لا تُحدد هذه الصفحة
   ما يجب كتابته. `admin` هو حساب الجهاز الذي تكون واجهة أوامره هي Site CLI، ويُصادق
   الحساب نفسه عبر
   [وحدة تحكم الموقع](../site-console/) بكلمة مرور — لكن لم يُبيَّن أن كلمة المرور تعمل عبر
   تسجيل الدخول بوحدة التحكم التسلسلية، و`sshd` يعتمد على المفتاح فقط لحساب `admin`، لذا فإن الاثنين
   ليسا مسار بيانات اعتماد واحدًا بشكل واضح.
   </Aside>

</Steps>

مُلتقط من `f5-xc-ce-vm-01`، مع حذف الجزء الأوسط حيث لا يُضيف مُخرج وحدة systemd
أي شيء:

```text file=../../../_data/serial-console-boot.txt
```

هناك أربعة أمور في ذلك النص تستحق الانتباه، لأنها تُجيب عن أسئلة لا تستطيع
واجهة تصحيح الأخطاء الإجابة عنها:

- **اكتمال cloud-init** — `Datasource DataSourceAzure`، انتهى عند 22.37 ثانية.
  العقدة التي لا تُسجَّل قط تفشل عادةً هنا، وهذا هو المكان الذي ترى فيه ذلك.
- **بدء كلا وقتَي تشغيل الحاويات.** `Container Runtime Interface for OCI (CRI-O)`
  و`Docker Application Container Engine` كلاهما `[ OK ]`، وهذا هو الدليل عند الإقلاع
  على سلوك وقتَي التشغيل المزدوجين الذي يُفاجئ الناس في
  [crictl](../../commands/system/crictl/) و[docker](../../commands/system/docker/).
- **`VP Manager image load` و`Argo Watch service`** — بدء تشغيل `vpm` وArgo.
- **المُحث هو مُحث العقدة نفسها**، خلف لافتة التدقيق الخاصة بها. توفّر لك وحدة التحكم التسلسلية
  مُحث تسجيل دخول، وليس جلسة.

<Aside type="caution" title="الربط التفاعلي يحتاج إلى طرفية حقيقية — لكن يمكن كتابته برمجيًا">
يضع `az serial-console connect` الطرفية في الوضع الخام، لذا لا يمكن تشغيله من
مسار عمل أو أي سياق بدون TTY. ويفشل من جهة العميل، قبل الاتصال بـ Azure:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

ذلك التتبّع يتعلق بمعالجة الطرفية، وليس بانقطاع في وحدة التحكم التسلسلية.

أما عملية الربط نفسها فهي **قابلة** للأتمتة — قُد websocket مباشرة بدلًا
من واجهة الأوامر. النص أعلاه التُقط بهذه الطريقة، دون TTY. راجع
`scripts/serial_console_capture.py`، وهو ما ستستخدمه لجمع أدلة الإقلاع من
عقدة فشلت في التسجيل دون وجود شخص يجلس أمام طرفية.
</Aside>

<Aside type="caution" title="توقّع إعادة المحاولة: تُرفض البوابة تقريبًا كل محاولة ثانية">
الإطار الأول من البوابة هو تحدٍّ، وليس مُخرجًا، ويجيب العميل عليه برمز
حامل. وحتى عندما يُنفَّذ ذلك بشكل صحيح، غالبًا ما يُغلق المقبس فورًا:

```
[close] code=1011 reason=Connection not trusted
```

السلوك المُلاحظ: ينجح بشكل متقطع، وتحت الاستخدام المتواصل تَرفض كل عقدة في
مجموعة الموارد — بما في ذلك العقد التي عملت قبل دقائق.
يُعيد `scripts/serial_console_capture.py` المحاولة افتراضيًا لأن إعادة المحاولة تنجح كثيرًا.

**السبب غير مُثبت.** وما تم استبعاده، لأن كل منها تخمين معقول
يُهدر الوقت:

| ليس هذا | كيف تتأكد |
| --- | --- |
| تحديد المعدل في ARM/compute | ذلك يُرجع HTTP `429` على نداءات ARM. أما هذا فهو إغلاق websocket على قناة بيانات منفصلة. |
| اعتراض TLS بواسطة وكيل | `openssl s_client -connect <region>.gateway.serialconsole.azure.com:443 \| openssl x509 -noout -issuer`. وجود مُصدر أصلي `O=Microsoft Corporation` يستبعد ذلك؛ ووجود مورد وكيل كمُصدر يُثبته، والحل هو إضافة `*.serialconsole.azure.com` إلى قائمة السماح. |
| تشخيصات الإقلاع معطّلة | `az vm show -g <rg> -n <vm> --query diagnosticsProfile` يُبلّغ عن `enabled: true`. |
| عدم تطابق الرمز بين المنح والتحدي | استخدام رمز واحد لكليهما هو الممارسة الصحيحة، لكنه لا يمنع الإغلاق. |

أما السلوك الموثّق فعلًا في Azure فهو: **جلسة وحدة تحكم تسلسلية واحدة لكل جهاز افتراضي، والطلب الثاني
الناجح يطرد الأول.** يُقطَع اتصال المستخدم المطرود لكن لا يُسجَّل خروجه،
لذا تصمد جلسة واجهة الأوامر. شخصان يُصحّحان عقدة واحدة سيُزيح كل منهما الآخر
مرارًا.

للعمل بالجملة فضّل [واجهة تصحيح الأخطاء](../debug-api/) أو [SSH](../ssh/)، وكلاهما لا
يخضع لهذه القيود. وSSH على وجه الخصوص لا يفرض حدًّا على اللصق ولا قيدًا على جلسة واحدة،
لذا فهو الخيار الأفضل كلما كانت العقدة قابلة للوصول من داخل VNet.
</Aside>

<Aside type="caution" title="اللصق محدود بـ 2,048 حرفًا">
تحد Azure طول اللصق في وحدة التحكم التسلسلية بـ 2,048 حرفًا، لتجنب إثقال
المنفذ التسلسلي. إرسال أمر طويل — أو دفعة من الأوامر في عملية كتابة واحدة — يفشل بطريقة
تبدو كتعليق أو كتحديد للمعدل بدلًا من كونها حدًّا للطول.

أرسل الأوامر بشكل فردي. هذا قيد حقيقي على أي عملية جمع بالجملة عبر وحدة التحكم
التسلسلية، وسبب آخر لتفضيل [واجهة تصحيح الأخطاء](../debug-api/) لذلك العمل.
</Aside>

## ما يمكنك رؤيته هنا ولا تستطيع واجهة برمجة التطبيقات إظهاره

- **cloud-init** أثناء التشغيل أو الفشل أو عدم البدء إطلاقًا — السبب المعتاد لعقدة
  لا تُسجَّل قط.
- **محاولات التسجيل** مقابل `register.ves.volterra.io`، بما في ذلك
  خطأ في الإعداد أو رمز رفضه المستأجر.
- **رسائل النواة والإقلاع** من قبل تشغيل أي وكيل.
- العقدة عندما لا يكون لها **أي مسار شبكي عامل**، وهو ما يُبطل كل مسار آخر.

بالنسبة لعقدة *تكون* `ONLINE`، فضّل واجهة تصحيح الأخطاء: فهي قابلة للكتابة البرمجية، وتُنتج
أدلة يمكنك إعادة تشغيلها، ولا تشغل المنفذ التسلسلي الوحيد.
