Customer Edge (CE) هو عقدة F5 Distributed Cloud التي يوفّرها هذا المستودع داخل
Azure — `terraform/modules/ce-node`، المبنية من صورة السوق
`volterraedgeservices/volterra-node`.

تشغّل هذه العقدة مستوى البيانات (Argo)، ومستوى التحكم (Vega)، ووكيل Envoy، وحزمة
Kubernetes، و`vpm`، وهو الوكيل الذي يسجّل العقدة ويدير كل شيء آخر عليها.

عندما يسيء CE التصرف، يكون Site CLI هو الأداة. القرار الأول هو أي مسار وصول
ينطبق، والخطأ في ذلك يهدر الوقت بطريقة تبدو وكأنها عقدة معطّلة.

يصل debug API إلى العقدة **عبر مستوى تحكم F5 Distributed Cloud**.
وهذا هو السبب الكامل وراء أهمية هذا الفصل: لا يمكن لـ API الإجابة إلا بعد أن تكون العقدة
قد سُجّلت وتُبلّغ عن الحالة `ONLINE`.

العقدة التي فشلت في التسجيل — cloud-init معطوب، أو رمز منتهي الصلاحية، أو عدم وجود مسار إلى
`register.ves.volterra.io` — هي بالضبط الحالة التي تحتاج فيها إلى التشخيصات،
وبالضبط الحالة التي لا يستطيع API خدمتها.

[SSH](./access/ssh/) هو الخيار الثالث، وهو الوحيد الذي يصل إلى سطح الأوامر الكامل للجهاز
— يعرض debug API عدد 34 أمرًا بينما تقدّم العقدة نفسها أوامر أكثر بكثير. يقيّده أمران.
يستجيب `sshd` على العنوان الداخلي (SLI) للعقدة فقط،
لذا يحتاج إلى مضيف داخل الـ VNet؛ والمفتاح يُكتب بواسطة cloud-init عند الإقلاع الأول،
لأن حقل `ssh_key` في كائن الموقع خامل — إذ يتجاوز `vpm` المستخدم `admin`
ولا يطبّقه أبدًا. لذلك فإن تمكينه على العقد قيد التشغيل يستلزم استبدالها.

إذًا: إذا كان الموقع `ONLINE` وكانت الأوامر الـ 34 كافية، استخدم debug API. وإذا كنت بحاجة إلى
بقية السطح وتستطيع الوصول إلى الـ VNet، استخدم SSH. أما إذا كان التسجيل هو المعطّل،
فإن وحدة التحكم التسلسلية هي الطريق الوحيد للدخول.

<Aside type="caution" title="تحقق من حالة الموقع أولاً">
طلب واحد يخبرك بالمسار الذي أنت عليه:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/config/namespaces/system/sites/<site>" \
  | jq -r '.spec.site_state'
```

`ONLINE` تعني أن debug API سيعمل. أي شيء آخر — أو موقع غير موجود —
يعني وحدة التحكم التسلسلية.
</Aside>

## قواعد السلامة

هذه القواعد تنطبق على كل أمر في كل صفحة أدناه.

- **للقراءة فقط ما لم تكن متأكدًا.** ينقسم سطح الأوامر إلى مستويَي
  امتياز، ومستوى `Exec` إما يعدّل العقدة أو يقرأ علامة حالة.
  لا شيء في هذه الصفحات يشغّل أمر `Exec`، وكذلك أداة الالتقاط.
- **لا تفترض أبدًا أن الأمر آمن استنادًا إلى اسمه.** يبدو `ip-link-set` كأنه
  استعلام لكنه يُنزل واجهة شبكة. و`systemctl-restart-crio` يعيد تشغيل
  بيئة تشغيل الحاويات تحت مستوى بيانات نشط.
- **فضّل الأمر الأضيق الذي يجيب على السؤال.** `health` و
  `diagnosis` يلخّصان العقدة بتكلفة زهيدة؛ بينما `flow-l` يفرّغ جدول تدفق يحتوي على 629,760 إدخالًا.
- **يخدم CE حركة مرور حية.** هذه بيئات عرض توضيحي مشتركة. افترض أن هناك من
  يقدّم عرضًا من الموقع الذي تصحّحه.

## ما هو موثّق هنا

كل أمر يمكن الوصول إليه عبر debug API على إصدار البرنامج الذي يشغّله هذا المستأجر،
مع إخراج كل أمر ملتقط من عقدة حية بدلاً من نسخه من مكان آخر.

يسرد [مرجع الأوامر](./commands/) جميع الأوامر مع فئتها ومستوى الامتياز
ووسيلة النقل؛ بينما تربط [سير العمل](./workflows/) بينها في التسلسلات التي
تستخدمها فعليًا عندما يحدث خطأ ما.

أما أجزاء Site CLI المتاحة على الجهاز فقط — `configure`، و`configure-network`،
و`factory-reset`، و`upgrade` وحوالي ستين أمر `ExecCLI` إضافيًا — فهي غير
مشمولة، لأن مخرجاتها لم تُلتقط من عقدة حية بالطريقة التي التُقطت بها كل
صفحة أدناه.

غير أنها لم تعد بعيدة المنال. يقود `scripts/sitecli_ssh_harvest.py` قائمة الإكمال
الخاصة بالجهاز عبر [SSH](./access/ssh/) ويسجّل الوصف الذي يقدّمه الجهاز
لكل أمر، بحيث يمكن قياس السطح بدلاً من تخمينه.
تنفيذه مرفوض افتراضيًا — فهو يعدّد كل شيء ولا يشغّل سوى قائمة سماح —
لأن بنية الأوامر غير المتحقق منها، و*تأثيرات* الأوامر غير المتحقق منها، هي الخلل الذي
وُجد هذا التوثيق لتجنّب تكراره.
