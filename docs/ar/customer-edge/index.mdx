Customer Edge (CE) هو عقدة F5 Distributed Cloud التي يُنشئها هذا المستودع في
Azure — `terraform/modules/ce-node`، المبنية من صورة السوق
`volterraedgeservices/volterra-node`.

تُشغّل هذه العقدة مستوى البيانات (Argo)، ومستوى التحكم (Vega)، ووكيل Envoy، وحزمة
Kubernetes، وأداة `vpm`، وهي العامل الذي يُسجّل العقدة ويُدير كل شيء آخر عليها.

عندما تتصرف CE بشكل غير صحيح، تكون Site CLI هي الأداة المستخدمة. القرار الأول هو
تحديد أيّ مسار وصول ينطبق، إذ إن اختيار المسار الخاطئ يُضيع الوقت بطريقة تبدو كما
لو أن العقدة معطوبة.

يصل debug API إلى العقدة **عبر مستوى التحكم في F5 Distributed Cloud**.
هذا هو السبب الجوهري الذي يجعل التمييز مهمًا: لا يمكن لـ API أن يُجيب إلا بعد أن
تُسجَّل العقدة وتُبلّغ بحالة `ONLINE`.

العقدة التي فشلت في التسجيل — بسبب خطأ في cloud-init، أو رمز منتهي الصلاحية، أو
عدم وجود مسار إلى `register.ves.volterra.io` — هي بالضبط الحالة التي تحتاج فيها إلى
تشخيصات، وهي بالضبط الحالة التي لا يستطيع فيها API خدمتك.

كما أن العقدة ترفض SSH كما يتم شحنها. المنفذ 22 مغلق على CE نفسها، وليس بواسطة
مجموعة أمان الشبكة:

```console
$ ssh -o ConnectTimeout=10 admin@<ce-public-ip>
ssh: connect to host <ce-public-ip> port 22: Connection refused
```

تم التحقق من ذلك من داخل VNet أيضًا، من خادم وسيط على الشبكة الفرعية نفسها، لذلك
فتح قاعدة مجموعة الأمان لا يُغيّر الأمر.

إذن: إذا كان الموقع في حالة `ONLINE`، استخدم debug API. إذا لم يكن كذلك، فإن serial console هو الطريق الوحيد للدخول.

<Aside type="caution" title="تحقق من حالة الموقع أولاً">
طلب واحد يُخبرك بالمسار الذي أنت عليه:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/config/namespaces/system/sites/<site>" \
  | jq -r '.spec.site_state'
```

`ONLINE` يعني أن debug API سيعمل. أي شيء آخر — أو موقع غير موجود — يعني serial console.
</Aside>

## قواعد الأمان

تنطبق هذه القواعد على كل أمر في كل صفحة أدناه.

- **للقراءة فقط ما لم تكن متأكدًا.** سطح الأوامر مقسّم إلى مستويَي صلاحية، ومستوى
  `Exec` إما يُعدّل العقدة أو يقرأ علامة حالة. لا يوجد في هذه الصفحات أي أمر `Exec`، ولا تُشغّل حزمة الالتقاط أيًا منها.
- **لا تفترض أبدًا أن الأمر آمن بناءً على اسمه.** `ip-link-set` يبدو كاستعلام
  ويُعطّل واجهة. `systemctl-restart-crio` يُعيد تشغيل وقت تشغيل الحاويات تحت مستوى
  بيانات حيّ.
- **استخدم أضيق أمر يُجيب على السؤال.** `health` و`diagnosis` يلخّصان العقدة
  بتكلفة منخفضة؛ `flow-l` يُفرغ جدول تدفق مكوّن من 629,760 إدخالاً.
- **تخدم CE حركة مرور حيّة.** هذه بيئات عرض توضيحي مشتركة. افترض أن شخصًا ما يُقدّم
  عرضًا من الموقع الذي تُشخّصه.

## ما هو موثّق هنا

كل أمر يمكن الوصول إليه عبر debug API على إصدار البرنامج الذي يُشغّله هذا المستأجر،
كلٌّ منها مع مخرجات مُلتقَطة من عقدة حيّة وليس منسوخة من مكان آخر.

[مرجع الأوامر](./commands/) يُدرج جميعها مع فئتها، ومستوى صلاحياتها، ووسيلة نقلها؛
أما [سير العمل](./workflows/) فيُرتّبها في التسلسلات التي تستخدمها فعليًا عند حدوث خطأ.

الأجزاء الخاصة بالصندوق فقط في Site CLI — `configure` و`configure-network`
و`factory-reset` و`upgrade` وما يقارب ستين أمرًا إضافيًا من `ExecCLI` — غير مشمولة.

هذه الأوامر لا يمكن الوصول إليها إلا من جلسة serial console، لذلك لا يمكن التحقق من أي شيء يتعلق بها برمجيًا، وصياغة الأوامر غير المُتحقَّق منها هي بالضبط العيب الذي وُجد هذا التوثيق لتفادي تكراره.
