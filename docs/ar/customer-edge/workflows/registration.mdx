<Aside type="danger" title="لا يمكن لواجهة API تشخيص هذه المشكلة">
تصل واجهة API الخاصة بالتشخيص إلى العقدة عبر مستوى التحكم في F5 Distributed Cloud، من خلال
النفق الذي ينشئه التسجيل. إذا فشل التسجيل فلا يوجد نفق،
لذا فإن كل أمر في هذا الموقع غير متاح لهذا الفشل تحديدًا. اعمل من
[وحدة تحكم الموقع](../../access/site-console/) إذا كان لدى العقدة مسار شبكة، ومن
[وحدة التحكم التسلسلية](../../access/serial-console/) إذا لم يكن لديها ذلك.
</Aside>

<Steps>

1. **تأكد من أنك تسأل المستأجر الصحيح.** يكلف هذا أمرًا واحدًا وهو في المقدمة
   لأن الخطأ فيه يجعل كل خطوة لاحقة تكذب عليك: فأسطول سليم في المستأجر
   الذي لا تنظر إليه لا يمكن تمييزه عن أسطول لم يُسجَّل أبدًا.

   ```bash
   cd terraform
   terraform output -raw xc_tenant       # the tenant this deployment belongs to
   terraform output -raw xc_env_tenant   # the tenant your shell is exporting
   ```

   ```text
   f5-sales-demo
   f5-sales-demo
   ```

   هل هما غير متطابقين، أو أن بيانات اعتماد تعتقد أنها صحيحة تُرجع `401` مجردًا؟ هذه هي
   علامة رمز مميز صُدر لمستأجر آخر، وقد كلّف هذا النشر بالفعل عملية
   إعادة بناء كاملة ([المشكلة 696](https://github.com/f5-sales-demo/mcn/issues/696)).

2. **تأكد من رأي المستأجر.** الغياب من قائمة المواقع مشكلة مختلفة
   عن الوجود دون أن تكون الحالة `ONLINE`.

   ```bash
   curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
     "$XCSH_API_URL/api/config/namespaces/system/sites" | jq -r '.items[].name'
   ```

   إذا كان الموقع موجودًا ويُبلّغ عن `ONLINE`، فقد نجح التسجيل وأنت في
   سياق العمل الخطأ.

3. **ابحث عن تسجيل الموقع وحالته.** يمكن لعقدة أن تُسجَّل ثم تنتظر
   الموافقة، وهذا يبدو مماثلًا تمامًا للفشل من الخارج.

   ```bash
   curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
     "$XCSH_API_URL/api/register/namespaces/system/registrations_by_site/<site>" \
     | jq -r '.items[] | "\(.name)  \(.object.status.current_state)  \(.object.spec.gc_spec.infra.hostname)"'
   ```

   ```text
   r-a97e20c8-b7e1-483d-bd76-34a64ff8bc78  ONLINE  f5-xc-ce-vm-01
   ```

   عدم وجود أي عناصر على الإطلاق يعني أن العقدة لم تُسجَّل بعد — انتقل إلى وحدة التحكم التسلسلية. أما وجود عنصر
   في حالة غير `ONLINE` فيعني أنه تم التسجيل وأن شيئًا ما بعد ذلك قد فشل، وهذا
   تحقيق مختلف.

   لمسح مساحة الأسماء بالكامل بحثًا عن أي شيء ينتظر الموافقة، فإن `listregistrationsbystate`
   تأخذ الحالة كـ **جسم `POST`**:

   ```bash
   curl -sS -X POST -H "Authorization: APIToken $XCSH_API_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"namespace":"system","state":"PENDING"}' \
     "$XCSH_API_URL/api/register/namespaces/system/listregistrationsbystate" | jq -r '.items[].name'
   ```

   في أسطول سليم لا يُرجع ذلك شيئًا، لأن الموافقة مؤتمتة.

4. **تأكد من أن الجهاز الافتراضي يعمل فعلًا**، قبل افتراض وجود خلل برمجي.

   ```bash
   az vm list -d -g <resource-group> --query "[].{name:name,power:powerState}" -o table
   ```

   ```text
   Name            Power
   --------------  ----------
   ar-ecmp-client  VM running
   f5-xc-ce-vm-01  VM running
   f5-xc-ce-vm-02  VM running
   f5-xc-ce-vm-03  VM running
   ```

5. **اربط وحدة التحكم التسلسلية.** يتطلب هذا تفاعليًا طرفية حقيقية؛ أما عملية الربط
   نفسها فيمكن كتابتها برمجيًا عبر websocket بدلًا من ذلك — راجع
   [وحدة التحكم التسلسلية](../../access/serial-console/).

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

   إذا رفضت العمل، تحقق من تمكين تشخيصات التمهيد على الجهاز الافتراضي قبل استنتاج أن
   العقدة غير قابلة للوصول؛ هذا المتطلب المسبق وأنماط فشله مشروحة في صفحة
   [وحدة التحكم التسلسلية](../../access/serial-console/).

6. **اقرأ ما تُظهره وحدة التحكم، بهذا الترتيب.** cloud-init أولًا — فالعقدة التي لم
   يكتمل فيها cloud-init ليس لديها تكوين تُسجَّل به. ثم
   محاولات التسجيل نفسها، ثم DNS: إذا لم تستطع العقدة تحليل
   `register.ves.volterra.io`، فلا يمكن لأي شيء لاحق أن يعمل.

7. **بمجرد أن تصبح العقدة `ONLINE`**، تحقق باستخدام [`health`](../../commands/system/health/)
   وتوقّع `state: PROVISIONED`.

</Steps>

<Aside type="caution" title="يُسمّى التسجيل باسم UUID، وليس أبدًا باسم موقعه">
تُسمّى التسجيلات `r-<uuid>`، ولا توجد أي نقطة نهاية تقبل اسم موقع في الموضع الذي يُتوقع فيه
اسم تسجيل.
يُرجع `GET .../registrations/<site>` الرمز `404`، والذي يُقرأ كأنه "هذا الموقع ليس لديه
تسجيل" بينما هو في الحقيقة "هذا ليس اسم تسجيل". لا تأتي مطابقة الموقع بالتسجيل
إلا من `registrations_by_site/<site>`، كما في الخطوة 3، أو بسرد
`registrations` والمطابقة على `gc_spec.passport.cluster_name`.

الفخ نفسه جعل الأمر يبدو كأن أسطولًا سليمًا ليس لديه أي تسجيلات.
</Aside>

## الأسباب المعتادة

- **أنت موجّه إلى المستأجر الخطأ**، فيبدو أسطول سليم كأنه غائب. الخطوة 1.
- لم يكتمل cloud-init، لذا فإن `/etc/vpm/config.yaml` غائب أو خاطئ.
- رمز التسجيل المميز منتهي الصلاحية، أو مُستخدم بالفعل، أو من مستأجر آخر.
- لا يوجد مسار خروج إلى `register.ves.volterra.io`.
- انحراف في الساعة كبير بما يكفي لإبطال الشهادات — يمكن استبعاده سريعًا لاحقًا باستخدام
  [`chronyc-sources`](../../commands/network/chronyc-sources/)، لكنه غير قابل للوصول
  حتى تصبح العقدة متصلة. تُبلّغ لافتة تسجيل الدخول عبر [SSH](../../access/ssh/) عن `NTP: Synced`
  وحالة المحلّل قبل تشغيل أي شيء، عندما يكون SSH متاحًا.
