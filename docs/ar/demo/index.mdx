يُظهر هذا النشر **التوافر العالي النشط/النشط لحافة العميل (Customer Edge) في Azure**
دون وجود موازن تحميل Azure أمام حواف العميل. تُصدر كل حافة عميل مسار المضيف نفسه عبر
eBGP، ويقوم خادم مسارات Azure بتثبيتها جميعًا كخطوات تالية متساوية التكلفة داخل VNet.
ولهذا فإن نسيج التوجيه، وليس موازن التحميل، هو المكان الذي يُفترض أن يحدث فيه توزيع
حركة المرور وإزالة العقد المتعطلة.

كل ما في هذه الصفحات تم تنفيذه على النشر الحقيقي، والمخرجات المعروضة هي المخرجات التي
أنتجها فعلًا. وما لا تشمله تلك العبارة — تجاوز الفشل، وكيفية توزيع حركة المرور
على الخطوات التالية — تم ذكره صراحةً بدلًا من تركه للافتراض.

## ما الذي ينشره

```text
                     Azure Route Server            ASN 65515
                      two instance addresses
                                 |
             +-------------------+-------------------+
             |                   |                   |
        <key>-bgp           <key>-bgp           <key>-bgp        eBGP
             |                   |                   |         CE ASN 64512
        CE eth0/SLO         CE eth0/SLO         CE eth0/SLO
          CE site             CE site             CE site
             |                   |                   |
             +--- each advertises the same VIP /32 ---+
                    equal-cost multipath into the VNet
```

| المكوّن | ما هو |
| --- | --- |
| مستأجر F5 Distributed Cloud | `var.expected_xc_tenant` — الموضع الوحيد الذي يُسمّى فيه المستأجر |
| مساحات الأسماء | مواقع حافة العميل في `system`؛ ومجموعة المصدر وموازن التحميل في `var.xc_app_namespace` |
| حواف العميل | عدد `var.ce_count` من مواقع Secure Mesh v2 أحادية العقدة، من 1 إلى 3، واحد لكل منطقة توافر |
| برنامج حافة العميل | مثبّت بواسطة `var.ce_sw_version` / `var.ce_os_version` |
| أجهزة Azure الافتراضية | ثلاث بطاقات شبكة لكل جهاز — الإدارة/SLO، والخارجية، والداخلية/SLI |
| تبادل المسارات | خادم مسارات Azure واحد، ASN `var.rs_asn`، وعنوانا مثيلين |
| علاقات التناظر | واحدة لكل حافة عميل، باسم `<key>-bgp`، وASN حافة العميل `var.ce_asn` |
| VIP المُعلن عنه | `var.vip` بصيغة `/32`، تُصدره كل حافة عميل بشكل مماثل |
| موازن التحميل | يخدم `var.lb_domain`، ومدعوم بمجموعة مصدر عند `var.origin_ip` |
| عميل الاختبار | جهاز افتراضي داخل نفس VNet، لتوجيه حركة المرور نحو VIP |

لا شيء مما ورد أعلاه قيمة حرفية ينبغي نسخها. كل قيمة قابلة للقراءة من النشر،
وكل صفحة تقرأها بدلًا من تسميتها:

```bash
cd terraform
terraform output -raw resource_group_name
terraform output -json xc_site_names
```

<Aside type="caution" title="يجب أن يكون VIP خارج كل نطاقات CIDR الخاصة بـ VNet">
يحتوي `terraform/main.tf` على كتلة `check` تتحقق من أن VIP يقع خارج نطاقي CIDR للمحور
والفرع، وترفض الخطة بخلاف ذلك. والسبب المعلن هو أن VIP الموجود داخل نطاق CIDR الخاص
بـ VNet يُخسر أمام مسار النظام الخاص بـ VNet نفسه، رغم أن مسار BGP أكثر تحديدًا.

تعامل مع هذا الضابط كعقد ملزم: إذا أعدت توجيه هذا العرض التوضيحي إلى مخطط عنونة مختلف،
فيجب أن ينتقل VIP خارج نطاقات VNet معه.
</Aside>

<Aside type="note" title="ما لوحظ في 2026-07-28: الكائنات الحقيقية لا تزال تحمل أسماءً مؤقتة">
تُشتق أسماء الكائنات من `var.component`، لذا فإن أي نشر غير مثبّت ينشئ
`<component>-<region>01` و`<component>-f5se` و`<component>-pool` و`<component>-rs` و
`<component>-bastion`. أما العرض التوضيحي العامل حاليًا فهو أقدم من ذلك ويحتفظ بأسمائه
الأصلية، المثبّتة في ملف `terraform.tfvars` محلي حتى لا يُستبدل أي شيء أثناء استخدام
البيئة.

لهذا السبب تُظهر مخرجات الأوامر الحقيقية في هذه الصفحات أسماءً لا تطابق النمط
المذكور أعلاه. واعتماد الأسماء المشتقة يستبدل كل جهاز افتراضي لحافة العميل، لأن اسم
الموقع هو `ClusterName` المدمج في cloud-init، وcloud-init لا يعمل إلا عند الإقلاع الأول
— لذا فهي إعادة بناء متعمّدة، تُتابع في
[issue 700](https://github.com/f5-sales-demo/mcn/issues/700)، وليست مجرد إعادة تسمية.
</Aside>
