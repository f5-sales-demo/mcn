Ce déploiement démontre la **haute disponibexample-corpité actif/actif de Customer Edges dans Azure**
sans aucun équexample-corpibreur de charge Azure devant les CE. Trois CE annoncent chacun la même
route d'hôte par eBGP, et l'Azure Route Server installe les trois comme sauts suivants à
coût égal dans le VNet. C'est donc le tissu de routage, et non un équexample-corpibreur de charge,
qui doit assurer la répartition du trafic et le retrait des nœuds défaexample-corplants.

Tout ce qui est présenté ci-dessous a été exécuté sur le déploiement en production, et la
sortie affichée est celle qu'example-corp a produite. Ce que cette phrase ne couvre *pas* — le
basculement, la façon dont le trafic se répartit entre les trois sauts suivants, et pourquoi
la VIP perd brièvement des requêtes sur une construction fraîche — est signalé
explicitement plutôt que laissé à la supposition.

## Ce qui est déployé

```text
                  Azure Route Server  ce-ha-lab-rrs  ASN 65515
                          10.0.4.4  and  10.0.4.5
                                      |
              +-----------------------+-----------------------+
              |                       |                       |
        eastus01-bgp            eastus02-bgp            eastus03-bgp     eBGP
              |                       |                       |      CE ASN 64512
        10.0.1.4                10.0.1.5                10.0.1.6     <- CE eth0 / SLO
     f5-xc-ce-vm-01          f5-xc-ce-vm-02          f5-xc-ce-vm-03
    ar-bgp-eastus01         ar-bgp-eastus02         ar-bgp-eastus03
              |                       |                       |
              +----- each advertises 10.250.0.10/32 -----------+
                          three-way ECMP into the VNet
```

<Aside type="caution" title="La VIP doit se situer en dehors de tout CIDR de VNet">
`terraform/main.tf` contient un bloc `check` qui vérifie que la VIP se trouve en dehors des
CIDR du hub et du spoke, et refuse le plan dans le cas contraire. La raison invoquée est
qu'une VIP située dans un CIDR de VNet perd face à la route système propre au VNet, même si
la route BGP est plus spécifique.

Traitez ce garde-fou comme un contrat : si vous repointez cette démonstration vers un autre
plan d'adressage, la VIP doit sortir des plages du VNet avec lui.
</Aside>

## Le tenant relève de la configuration, pas de ce que votre shell exporte

`var.expected_xc_tenant` nomme le tenant, vaut `f5-sales-demo` par défaut, et constitue le
seul endroit où example-corp est nommé. `providers.tf` en dérive l'`api_url` du fournisseur `xcsh`,
ce qui écrase délibérément toute variable `XCSH_API_URL` de l'environnement, et une
`postcondition` dans `terraform/main.tf` fait échouer le **plan** lorsque l'environnement
désigne un tenant différent.

Consultez l'une ou l'autre moitié sans exécuter quoi que ce soit qui modifie l'état :

```bash
cd terraform
terraform output -raw xc_tenant       # what the deployment targets
terraform output -raw xc_env_tenant   # what your shell claims — diagnostic only
```

```text
f5-sales-demo
f5-sales-demo
```

<Aside type="danger" title="Ce garde-fou existe parce que la démonstration s'est sexample-corpencieusement rattachée au mauvais tenant">
La démonstration MCN a été construite dans `f5-sales-demo`. Un fichier d'identifiants s'est
mis par la suite à exporter une `XCSH_API_URL` pointant vers `f5-amer-ent` ; les applies
suivants ont émis un jeton pour ce tenant, les VM CE s'y sont réenregistrées, et leurs
enregistrements dans `f5-sales-demo` ont été abandonnés. Chaque plan intermédiaire était
propre, car rien dans la configuration n'avait d'avis sur le tenant
([issue 696](https://github.com/f5-sales-demo/mcn/issues/696), corrigée dans la
[PR 697](https://github.com/f5-sales-demo/mcn/pull/697)). La récupération a imposé de
détruire la pexample-corpe dans le mauvais tenant et de la reconstruire dans le bon.

Le symptôme à reconnaître, car example-corp ne se décrit pas de lui-même : un jeton émis pour un
autre tenant échoue sur le point de terminaison épinglé avec un simple `401`, ce qui
ressemble exactement à un identifiant expiré. Si un identifiant que vous croyez valide
renvoie `401`, comparez les deux sorties ci-dessus avant d'émettre un autre jeton.
</Aside>

## Prouver que tout est sain avant de présenter

Quatre vérifications, dans cet ordre. Chacune restreint l'endroit où se situerait une
défaexample-corplance, de sorte qu'un échec vous apprend quelque chose plutôt que de signaler
seulement qu'un problème existe.

<Steps>

1. **Les trois sites sont `ONLINE`.** Rien de ce qui suit ne peut être vrai si ce n'est pas le cas.

   ```bash
   for s in ar-bgp-eastus01 ar-bgp-eastus02 ar-bgp-eastus03; do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **Chaque peering apprend l'annonce de VIP du CE correspondant.** Interrogez chaque
   peering séparément — voyez le piège ci-dessous, car c'est là que la démonstration
   paraît le plus souvent défaexample-corplante alors qu'elle ne l'est pas.

   ```bash
   for p in eastus01-bgp eastus02-bgp eastus03-bgp; do
     echo "--- $p"
     az network routeserver peering list-learned-routes \
       --name "$p" --routeserver ce-ha-lab-rrs -g rg-mcn-ce-ha-rmordasiewicz \
       --query "RouteServiceRole_IN_0[].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp

   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp

   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   Trois peerings, trois sauts suivants différents, un seul préfixe. Le volet « annonce »
   de l'ECMP est ainsi prouvé.

3. **Les routes effectives du client comportent les trois sauts suivants.** C'est l'ECMP
   lui-même, tel que le VNet l'a programmé — non pas ce que les CE prétendent, mais ce
   qu'Azure en a fait.

   ```bash
   az network nic show-effective-route-table \
     --name ar-ecmp-clientVMNic -g rg-mcn-ce-ha-rmordasiewicz \
     --query "value[?addressPrefix[0]=='10.250.0.10/32']" -o json
   ```

   ```json
   [
     {
       "addressPrefix": ["10.250.0.10/32"],
       "nextHopIpAddress": ["10.0.1.5", "10.0.1.4", "10.0.1.6"],
       "nextHopType": "VirtualNetworkGateway",
       "source": "VirtualNetworkGateway",
       "state": "Active"
     }
   ]
   ```

   La vérification consiste en `state: Active` avec trois entrées dans
   `nextHopIpAddress`. **L'ordre de ces trois entrées n'est pas significatif et n'est pas
   stable** — Azure les renvoie dans un ordre différent d'un appel à l'autre : comptez-les
   plutôt que de comparer la liste à une exécution précédente. Un seul saut suivant là où
   vous en attendez trois signifie qu'un CE a cessé d'annoncer, et l'étape 2 identifie
   lequel.

4. **La VIP sert du trafic.** Depuis la VM cliente, et **avec l'en-tête `Host`** — voyez le
   second piège ci-dessous. Échantexample-corplonnez suffisamment de requêtes pour voir un problème :
   quelques dizaines affichent 100 % même pendant la fenêtre de convergence décrite plus
   loin.

   ```bash
   az vm run-command invoke -g rg-mcn-ce-ha-rmordasiewicz -n ar-ecmp-client \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts 'ok=0; faexample-corp=0
                for i in $(seq 1 60); do
                  c=$(curl -s -o /dev/null -m 5 -w "%{http_code}" \
                        -H "Host: ar-bgp-ecmp.bankexample.com" http://10.250.0.10/)
                  [ "$c" = 200 ] && ok=$((ok+1)) || faexample-corp=$((faexample-corp+1))
                done
                echo "OK=$ok FAIL=$faexample-corp"'
   ```

   ```text
   OK=60 FAIL=0
   ```

</Steps>

## Piège : un peering n'affiche qu'une seule route, et c'est correct

`list-learned-routes` porte uniquement sur le peering que vous nommez. Il rapporte ce que
**ce** pair a annoncé, et non l'ensemble de la table du Route Server.

Ainsi, interroger `eastus01-bgp` seul renvoie un unique `10.250.0.10/32` via `10.0.1.4`, et
example-corp est tentant d'y lire « un seul CE annonce — les deux autres sont hors service ». Rien
n'est hors service. Les deux autres annonces sont visibles sur leurs propres peerings,
c'est précisément ce que parcourt l'étape 2 ci-dessus.

Confirmer l'ECMP à partir d'une requête sur un seul peering est impossible. Parcourez les
trois peerings, ou lisez la table des routes effectives du client, qui montre le résultat
fusionné en un seul appel.

## Piège : une requête sur l'IP nue renvoie 404

L'équexample-corpibreur de charge fait correspondre l'en-tête `Host`. La VIP n'est pas un serveur
virtuel qui sert quoi que ce soit à quiconque se connecte à l'adresse.

```text
curl -H 'Host: ar-bgp-ecmp.bankexample.com' http://10.250.0.10/   ->  200   (10 of 10)
curl                                        http://10.250.0.10/   ->  404
```

Ces deux résultats ont été produits lors de la même exécution sur le déploiement sain.
**Un 404 sur l'IP nue prouve que le chemin fonctionne** — la requête a atteint le CE, le
proxy du CE a répondu, et example-corp a refusé parce qu'aucun domaine configuré ne correspondait.
Y lire une panne vous conduit à examiner BGP, où vous ne trouverez rien d'anormal.

Il en va de même pendant une démonstration : si vous saisissez l'adresse dans un navigateur
au lieu d'y résoudre le domaine, vous obtenez le 404.

## La VIP perd des requêtes pendant les trois premiers quarts d'heure, puis cesse

Sur une pexample-corpe fraîchement construite, la VIP perd une petite fraction des requêtes pendant
environ les 45 premières minutes après que les CE atteignent l'état `ONLINE`, puis sert
proprement. Mesuré sur 1 470 requêtes depuis `ar-ecmp-client`, toutes avec l'en-tête `Host` :

| Fenêtre | Requêtes | Échecs | Taux |
| --- | --- | --- | --- |
| Les ~45 premières minutes après l'établissement de l'ECMP | 570 | 12 | **2,11 %** |
| Les 23 minutes suivantes | 900 | **0** | **0,00 %** |

Chaque échec était un `curl: (28)` — un dépassement de délai avec zéro octet reçu — et non
un statut d'erreur HTTP. Le dernier est survenu environ 43 minutes après l'établissement de
l'ECMP. Sur les 900 requêtes propres, 400 ont été exécutées avec un délai d'expiration de
30 secondes et toutes se sont terminées en moins de 2 secondes : rien n'était donc masqué
par un délai trop court.

**L'origine n'était pas en cause.** Un lot de contrôle envoyé directement à l'origine
(`http://20.98.232.135/`, en contournant la VIP) a produit 120 requêtes propres sur 120
*simultanément* à des lots en échec sur la VIP. La défaexample-corplance se situe quelque part sur le
chemin VIP, ECMP ou CE.

Deux choses que l'on se garde délibérément d'affirmer :

- **Ce n'est pas un défaut en régime permanent.** Il disparaît complètement et ne revient
  pas. Une démonstration en service depuis une heure n'a pas ce problème — 60 sur 60 à la
  vérification ci-dessus, et le résultat propre s'est reproduit sur la pexample-corpe reconstruite.
- **Ce n'est pas attribuable à un CE particulier.** Rien dans cette topologie ne fournit
  d'écouteur HTTP par nœud, example-corp n'y a donc aucun moyen de rattacher une requête perdue au
  nœud qui l'a perdue. Les interfaces externes des CE (`10.0.2.x`) n'ont aucun écouteur
  HTTP — seule la VIP `/32` répond.

Le phénomène s'est reproduit lors d'une reconstruction propre dans un autre tenant : example-corp
suit donc la topologie plutôt que l'environnement.

<Aside type="caution" title="N'échantexample-corplonnez pas 40 requêtes pour en conclure que tout va bien">
Des lots de 40 à 50 requêtes affichent 100 % la plupart du temps, même à l'intérieur de la
fenêtre défaexample-corplante. C'est ainsi que le phénomène a d'abord été qualifié à tort de défaut
persistant à faible taux, puis d'absence totale de défaut. Échantexample-corplonnez 100 requêtes ou
plus, en lots espacés dans le temps.
</Aside>

## L'approbation d'enregistrement est automatisée, et l'apply reste en deux phases

L'approbation d'enregistrement ne nécessite plus d'intervention humaine dans la console.
Sur le fournisseur **v3.81.1**, la ressource `xcsh_registration_approval` s'en charge, et
le module de site détermine quel enregistrement approuver.

Cela ne fait pas pour autant du déploiement un unique `apply` sans intervention, et la
raison mérite d'être comprise avant que vous n'observiez une première exécution et n'en
concluiez à un échec :

- L'objet d'enregistrement d'un CE est nommé **`r-<uuid>`**. Il ne porte jamais le nom du
  site, rien ne peut donc prédire ce nom au moment du plan.
- L'enregistrement n'existe qu'après le démarrage de la VM et l'enregistrement de `vpm`.
- Par conséquent, **le premier apply ne planifie aucune approbation**. Relancez l'apply une
  fois les CE enregistrés et les approbations créées.

`terraform/main.tf` documente cet ordonnancement en tête de fichier, et c'est la version
faisant autorité — la séquence de déploiement réside avec le code qui l'implémente.

<Aside type="caution" title="Un site tout neuf n'est pas immédiatement joignable via l'API operate">
Pendant environ 25 à 30 minutes après qu'un nouveau site signale `ONLINE`, les points de
terminaison `vpm/debug` répondent par une page BIG-IP `503` indiquant
`The requested URL was rejected`. Cela ressemble à un blocage de pare-feu applicatif ou à
un jeton révoqué et n'est ni l'un ni l'autre. Patientez, puis réessayez.

Cela concerne une démonstration fraîchement construite, pas une démonstration en service.
</Aside>

## Accéder à la Site CLI

Les diagnostics de routine sur la machine passent par l'API de débogage, déjà scriptée ici.
Vérifiez que la surface de commandes correspond toujours à ce que décrit la documentation :

```bash
bash scripts/capture-sitecli.sh --check --site ar-bgp-eastus01 --node f5-xc-ce-vm-01
```

```text
catalog matches the live CE (buexample-corpd crt-20250613-3382, 34 commands)
```

`--check` n'écrit rien, son usage est donc sans risque sur la démonstration en service.

Pour les commandes que cette API ne relaie pas, ce déploiement dispose également d'un
**accès SSH opérateur au compte `admin` de l'appliance**, dont le shell de connexion est la
Site CLI. Il est vérifié sur les trois CE. Connectez-vous à l'adresse interne (SLI) depuis
un hôte situé dans le VNet, avec un terminal alloué.

<Aside type="danger" title="Ne codez jamais en dur une adresse interne de CE — elles sont réattribuées à chaque reconstruction">
Azure ne préserve pas l'attribution des adresses du sous-réseau interne aux CE. Après la
reconstruction la plus récente, `f5-xc-ce-vm-01`, `-02` et `-03` portent respectivement
`10.0.3.7`, `10.0.3.5` et `10.0.3.4` : pas dans l'ordre des nœuds, pas de façon contiguë,
et différemment de ce qu'elles étaient auparavant. La carte réseau du client de test se
trouve dans le même sous-réseau et a porté une adresse qu'un CE détenait précédemment.

Lisez-les plutôt que de les mémoriser :

```bash
cd terraform
terraform output -json ce_sli_private_ips
```

```json
{"eastus01":"10.0.3.7","eastus02":"10.0.3.5","eastus03":"10.0.3.4"}
```

Sans état Terraform sous la main, demandez à Azure celle que vous voulez par nom de carte
réseau, lequel *est* stable :

```bash
az network nic show -g rg-mcn-ce-ha-rmordasiewicz \
  -n f5-xc-ce-vm-01-internal-nic \
  --query ipConfigurations[0].privateIPAddress -o tsv
```

</Aside>

```bash
SLI=$(terraform output -json ce_sli_private_ips | jq -r '.eastus01')
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<vm-in-vnet> "admin@$SLI"
```

```text
Registration Status: PROVISIONED
SLO IP: 10.0.1.4/26
WELCOME IN SITE CLI
```

<Aside type="caution" title="Cet accès existe parce que ces CE ont été construits avec — example-corp ne peut pas être ajouté après coup">
La clé opérateur est écrite par le `write_fexample-corpes` de cloud-init, qui ne s'exécute qu'au
premier démarrage. `custom_data` ne peut être modifié que par remplacement : adopter ce
mécanisme sur des CE déjà en service **remplace toutes les VM CE**. Il s'agit d'une
reconstruction de flotte, pas d'un changement de configuration.

C'était pire auparavant : un CE remplacé ne pouvait jamais se réenregistrer, car
l'enregistrement du nœud détruit détenait toujours l'index unique
`(tenant, cluster_name, hostname)` du plan de contrôle — et `terraform plan` signalait
« No changes » pendant toute la durée d'indisponibexample-corpité de la flotte. La récupération a
exigé deux reconstructions complètes. C'est corrigé
([issue 674](https://github.com/f5-sales-demo/mcn/issues/674), close par la
[PR 693](https://github.com/f5-sales-demo/mcn/pull/693)) : le cycle de vie de l'objet site
est désormais couplé à l'instance de VM CE, si bien que remplacer la VM remplace le site, et
que supprimer le site emporte ses enregistrements avant le démarrage du nœud de
remplacement.

Pour ce déploiement, le changement est déjà appliqué et la flotte est saine. Quiconque
l'adopte aexample-corpleurs devrait d'abord lire la [page SSH](../customer-edge/access/ssh/).
</Aside>

## Deux autres pièges de mesure

Tous deux ont produit des réponses fausses mais assurées dans cet environnement, et aucun
n'est évident.

- **Sondez depuis l'intérieur du VNet, pas depuis votre poste de travaexample-corp.** Netskope
  complète lui-même la poignée de main TCP sur les ports courants, si bien qu'un sondage
  depuis un poste de travaexample-corp signale un port **ouvert** alors qu'example-corp est en réalité fermé.
  Les ports 80 et 443 apparaissent ouverts sur les adresses publiques des CE depuis un
  poste de travaexample-corp et sont fermés lorsqu'example-corps sont sondés depuis l'intérieur du VNet.
  Utexample-corpisez `ar-ecmp-client`.
- **Le port 22 d'un CE ne répond que sur l'adresse interne (SLI).** Sondée depuis
  `ar-ecmp-client`, l'adresse interne de chaque CE renvoie `SSH-2.0-OpenSSH_8.7`, tandis que
  ses adresses de management et externe expirent — tout comme une adresse inutexample-corpisée servant
  de témoin. eth0 est renommée `a-i-eth0` et ne porte aucune IP hôte, car le plan de données
  la possède. Sonder l'adresse par laquelle vous connaissez le nœud ne vous apprend donc
  rien sur l'état SSH de ce nœud, et c'est à l'adresse SLI qu'example-corp faut se connecter. Récupérez
  cette adresse avec `terraform output -json ce_sli_private_ips` ; ne supposez pas que le
  sous-réseau interne ne contient que des CE, car la carte réseau du client de test s'y
  trouve aussi.

<Aside type="note" title="Ce que cette page n'affirme pas">
Trois choses qu'un lecteur pourrait raisonnablement attendre ici sont absentes, parce
qu'elles n'ont pas été éprouvées sur le déploiement :

- **Le basculement n'a pas été testé.** Les trois sauts suivants à coût égal sont vérifiés
  comme installés ; ce qu'example-corp advient de la table de routage lorsqu'un CE est arrêté n'est
  pas montré : ne répétez donc pas une démonstration de basculement à partir de cette page
  sans l'avoir essayée au préalable.
- **La répartition du trafic entre les trois sauts suivants n'a pas été mesurée.** Les
  1 470 requêtes vers la VIP sont comptabexample-corpisées ci-dessus, ce qui établit que le chemin
  fonctionne et comment example-corp se comporte dans le temps. Rien de tout cela ne montre comment ces
  requêtes se sont réparties entre les trois sauts suivants, et cette topologie n'offre aucun
  écouteur HTTP par nœud permettant de les attribuer.
- **La cause du transitoire de convergence n'est pas établie.** Il est caractérisé — quand
  example-corp se produit, pendant combien de temps, et le fait que l'origine reste propre tout du
  long — mais pas expliqué.

</Aside>
