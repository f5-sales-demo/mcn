L'API `vpm/debug` exécute des commandes Site CLI sur un nœud enregistré et retourne
leur sortie. Tout ce qui suit a été établi sur un nœud actif ; rien de tout cela
n'est publié en amont.

## Le catalogue de commandes est auto-descriptif

Demandez au nœud ce qu'il prend en charge en effectuant un POST vers `exec-user` avec la clé
`command` **omise** :

```bash
curl -sS -X POST \
  -H "Authorization: APIToken $XCSH_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"namespace":"system","site":"<site>","node":"<node>"}' \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/<node>/exec-user" \
  | jq -r .output | jq .
```

La réponse est un objet JSON indexé par nom de commande :

```json
{
  "crictl-inspect": ["System Troubleshooting", "ExecUser", " container-id"],
  "diagnosis":      ["System Troubleshooting", "ExecUser", "no argument needed", "GLOBAL"],
  "ip-link-set":    ["Network Troubleshooting", "Exec", " (<device>||<group>) (up||down)"]
}
```

Chaque entrée est `[category, tier, exampleArgument?, scope?]`, et ces champs ne sont
pas de la documentation — ils déterminent comment la commande doit être appelée.

<Aside type="caution" title="Omettez la clé ; n'envoyez pas une valeur incorrecte">
La découverte fonctionne en laissant `command` de côté. Envoyer une valeur inconnue à la place retourne
une erreur, et non le catalogue :

```json
{"code":3,"details":[],"message":"exec command failed: command not supported"}
```

Ce message est aussi celui que vous obtenez pour une *vraie* commande envoyée au mauvais endpoint,
il est donc facile de le lire à tort comme « cette commande n'existe pas ».
</Aside>

## Trois transports, choisis par l'entrée du catalogue

| Condition | Méthode et chemin | Corps | Retourne |
| --- | --- | --- | --- |
| `scope` vaut `GLOBAL` | `GET .../vpm/debug/global/<cmd>` | aucun | JSON |
| `tier` vaut `ExecUser` | `POST .../vpm/debug/<node>/exec-user` | tableau `command` | texte |
| `tier` vaut `Exec` | `POST .../vpm/debug/<node>/exec` | tableau `command` | texte |

### `ExecUser` — le niveau en lecture seule <Badge text="31 commandes" variant="note" />

Le cas courant. Passez la commande et ses arguments sous forme de tableau, le nom de la commande
en premier :

```bash
curl -sS -X POST \
  -H "Authorization: APIToken $XCSH_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"namespace":"system","site":"<site>","node":"<node>","command":["crictl-ps"]}' \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/<node>/exec-user"
```

```json
{ "return_code": 0, "output": "CONTAINER    IMAGE    CREATED    STATE ..." }
```

Les arguments sont des éléments distincts du tableau, et non une chaîne unique :

```json
{ "command": ["journalctl", "-u", "vpm", "-n", "200"] }
```

### `GLOBAL` — à l'échelle du site, et un transport entièrement différent <Badge text="2 commandes" variant="tip" />

`health` et `diagnosis` sont les deux seules. Ce sont des requêtes `GET` vers un chemin
`global`, elles ne prennent aucun argument et retournent du JSON structuré plutôt que du texte de terminal.

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/global/health" | jq .
```

<Aside type="danger" title="Une commande GLOBAL n'est pas accessible via exec-user">
C'est le piège qui coûte le plus de temps. Envoyer `health` ou `diagnosis` vers
`exec-user` retourne `command not supported`, ce qui se lit comme si la commande
n'existait pas sur le nœud — alors qu'en réalité elle existe et que vous avez utilisé le mauvais transport.

```bash
# Wrong. Returns: exec command failed: command not supported
-d '{"namespace":"system","site":"…","node":"…","command":["health"]}'   # POST exec-user

# Right.
GET .../vpm/debug/global/health
```

</Aside>

### `Exec` — le niveau privilégié <Badge text="1 commande sur cette build" variant="danger" />

Un endpoint distinct, et le niveau est appliqué plutôt qu'indicatif : `exec` rejette
une commande `ExecUser` avec le même message `command not supported`. Chaque membre
soit modifie le nœud, soit lit un marqueur d'état.

Sur la build que ce locataire exécute, le niveau ne contient que `ip-link-set`. Les builds plus récentes
ajoutent `systemctl-restart-NetworkManager`, `systemctl-restart-crio`,
`systemctl-restart-kubelet`, `systemctl-start-crio-prune` et trois
commandes `marker-exists-*`.

<Aside type="danger" title="Rien ici n'exécute une commande Exec">
Le harnais de capture refuse ce niveau, et lit le niveau depuis le catalogue actif
plutôt que depuis une liste codée en dur — ainsi une future build qui promeut une commande vers `Exec`
est respectée sans que quiconque modifie le code. N'en exécutez une que délibérément, sur un nœud que
vous êtes prêt à perturber.
</Aside>

## Trouver les noms de site et de nœud

Le nom du nœud est le nom de la VM Azure, et `list-service` est un moyen économique de le confirmer
en même temps que les services qui s'y exécutent :

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/global/list-service" \
  | jq -r '[.service[].node] | unique'
```

```json
["", "f5-xc-ce-vm-01"]
```

Certains services signalent un nom de nœud vide, donc une chaîne vide dans cette liste est un artefact de
la réponse plutôt qu'un second nœud. `list-service` ne figure pas non plus dans le catalogue de 34 commandes :
c'est un endpoint `global` que le catalogue n'annonce pas, ce qui explique pourquoi il est documenté ici
et non dans la [référence des commandes](../../commands/).

## Reproduire les captures de ce dépôt

Chaque page de commande intègre une sortie capturée par `scripts/capture-sitecli.sh`, qui
met en œuvre les trois règles ci-dessus.

<Steps>

1. Pointez-le vers un locataire. Il lit `XCSH_API_URL` et `XCSH_API_TOKEN`, ou revient
   au contexte `xcsh` actif.

2. Actualisez le catalogue et confirmez que le nœud n'a pas changé sous la
   documentation :

   ```bash
   bash scripts/capture-sitecli.sh --check
   ```

   Cela compare uniquement le catalogue validé et la build logicielle. Il signale un
   changement de build séparément des commandes ajoutées ou supprimées.

3. Effectuez une nouvelle capture lorsque vous souhaitez des preuves fraîches :

   ```bash
   bash scripts/capture-sitecli.sh
   ```

</Steps>

<Aside type="note" title="Les captures sont des preuves, pas des artefacts reproductibles">
Les compteurs, durées de fonctionnement et âges des conteneurs évoluent d'une exécution à l'autre, donc une nouvelle capture produit toujours
un diff. Le catalogue est le contrat stable et est identique octet pour octet d'une exécution à l'autre
lorsque le nœud n'a pas changé ; c'est ce que `--check` compare. Les sorties longues sont
tronquées et se terminent par un marqueur explicite, de sorte qu'un tableau tronqué n'est jamais présenté comme
s'il était complet.
</Aside>

<Aside type="danger" title="Capture depuis un nœud client : vérifiez le profil de censure">
La sortie des commandes véhicule l'identité de l'infrastructure — adressage interne, adresses MAC,
numéros AS, noms d'hôtes — et pour un client, il s'agit d'informations identifiant
l'organisation.

Le filtre de nettoyage utilise donc par défaut un profil **strict** qui supprime tout cela.
Ce dépôt déclare `lab` dans `sitecli/capture-manifest.json`, ce qui conserve ces
détails, et cela n'est correct ici que parce que ces captures proviennent d'une infrastructure
de démonstration détenue par F5.

**Ne transposez pas ce réglage à une capture client.** Les jetons, clés privées, l'identifiant
du locataire, les UUID d'objets, les adresses e-mail et les chemins de répertoires personnels sont supprimés sous
les deux profils.

Une limitation mérite d'être connue : une table de voisins BGP affiche l'AS sous forme de colonne brute
sans étiquette permettant d'ancrer un motif, donc les ASN sont mis en correspondance par valeur avec les
plages privées. Un ASN **public** y survit au profil strict, et nécessite une revue manuelle de
la sortie `show-ip-bgp*` avant publication.
</Aside>
