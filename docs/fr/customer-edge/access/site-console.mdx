Chaque Customer Edge expose la Console du site F5 sur `https://<sli-ip>:65500`. Sur ce
déploiement, c'est généralement la première piste à explorer.

Elle vous demande le moins d'efforts : aucune clé SSH à distribuer, aucun hôte de rebond à
maintenir, aucune IP publique sur le nœud, et aucun remplacement de VM nécessaire pour
l'activer. Qui peut se connecter devient une **décision Azure RBAC**. Elle ne nécessite pas
non plus que le site soit enregistré — la transcription ci-dessous a été capturée alors que
les trois sites signalaient `site_state: FAILED`.

La contrainte est que la Console du site ne répond que sur l'adresse interne (SLI) du nœud,
accessible uniquement depuis l'intérieur du VNet. Azure Bastion comble cet écart sans rien
ajouter d'autre sur le réseau.

<Aside type="note" title="Ce qui est vérifié ici, et ce qui ne l'est pas">
Chaque commande et chaque sortie de cette page ont été exécutées sur `f5-xc-ce-vm-01` dans
ce déploiement et sont reproduites mot pour mot, y compris les échecs.

La seule chose qui n'est pas exercée est **la connexion**. Les étapes s'arrêtent à
l'invite d'identifiants, donc rien ci-dessous ne décrit à quoi ressemble la console une
fois connecté.
</Aside>

## Avant de commencer

<Steps>

1. Connectez-vous à Azure et ajoutez l'extension Bastion. Le tunneling est une
   fonctionnalité de client natif et l'extension n'est pas installée par défaut.

   ```bash
   az login
   az extension add --name bastion
   ```

2. Disposez du rôle **Reader** sur la machine virtuelle CE, son interface réseau, et l'hôte
   Bastion.

3. Confirmez que Bastion est déployé et capable. Le SKU Basic ne prend en charge ni le
   tunneling ni la connexion par IP, donc `Standard` et `True` ici sont tous deux essentiels.

   ```bash
   az network bastion list -g rg-mcn-ce-ha-rmordasiewicz \
     --query "[].{name:name, sku:sku.name, tunneling:enableTunneling}" -o table
   ```

   ```text
   Name               Sku       Tunneling
   -----------------  --------  -----------
   ce-ha-lab-bastion  Standard  True
   ```

</Steps>

## Ouvrir le tunnel

Récupérez les valeurs depuis `terraform output` plutôt que de les saisir manuellement —
l'identifiant de ressource n'est pas quelque chose à assembler à la main.

<Steps>

1. Lisez le nom de l'hôte Bastion, le groupe de ressources, et l'identifiant de ressource
   VM du CE cible.

   ```bash
   cd terraform
   BASTION=$(terraform output -raw bastion_name)
   RG=$(terraform output -raw resource_group_name)
   VM_ID=$(terraform output -json ce_vm_ids | jq -r '.eastus01')
   ```

   ```text
   ce-ha-lab-bastion
   rg-mcn-ce-ha-rmordasiewicz
   /subscriptions/…/providers/Microsoft.Compute/virtualMachines/f5-xc-ce-vm-01
   ```

   <Aside type="caution" title="La carte est indexée par site, pas par nom de VM">
   Les clés de `ce_vm_ids` sont `eastus01`, `eastus02`, `eastus03` — **pas** les noms de
   VM. Un filtre tel que `jq -r '."f5-xc-ce-vm-01"'` retourne `null`, et le tunnel échoue
   alors sur un identifiant de ressource vide. Listez-les en cas de doute :

   ```bash
   terraform output -json ce_vm_ids | jq -r 'keys | join(", ")'
   ```

   ```text
   eastus01, eastus02, eastus03
   ```
   </Aside>

2. Démarrez le tunnel. Il maintient le port ouvert jusqu'à son arrêt, donc mettez-le en
   arrière-plan ou utilisez un second terminal.

   ```bash
   az network bastion tunnel \
     --name "$BASTION" \
     --resource-group "$RG" \
     --target-resource-id "$VM_ID" \
     --resource-port 65500 \
     --port 65500 &
   ```

   ```text
   WARNING: Opening tunnel on port: 65500
   WARNING: Tunnel is ready, connect on port 65500
   WARNING: Ctrl + C to close
   ```

   Les trois lignes sont préfixées par `WARNING:`. C'est l'interface CLI Azure qui écrit
   la progression sur stderr, pas un problème. Attendez `Tunnel is ready` avant de vous
   connecter.

3. Confirmez que l'écouteur est local, sur loopback :

   ```bash
   lsof -nP -iTCP:65500 -sTCP:LISTEN
   ```

   ```text
   COMMAND   PID  USER  FD  TYPE  DEVICE  SIZE/OFF  NODE  NAME
   Python  41648  you   7u  IPv4  …            0t0   TCP  127.0.0.1:65500 (LISTEN)
   ```

4. Ouvrez la console. Le tunnel la rend locale, donc l'adresse est `localhost` — pas
   l'adresse du nœud.

   ```bash
   open https://localhost:65500/          # macOS
   xdg-open https://localhost:65500/      # Linux
   ```

5. Arrêtez le tunnel lorsque vous avez terminé — `Ctrl-C`, ou `kill %1` si vous l'avez
   mis en arrière-plan. Le laisser ouvert maintient le port local 65500 et la session
   Bastion occupés.

</Steps>

## Ce que vous verrez

**Une boîte de dialogue d'identifiants, pas une page de connexion.** La console utilise
l'authentification HTTP Basic, donc le navigateur affiche sa propre invite de nom
d'utilisateur et de mot de passe. Il n'y a pas de formulaire à afficher :

```bash
curl -skI https://localhost:65500/
```

```text
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Basic realm="Volterra Site Console"
Content-Length: 0
```

Un `401` avec ce realm correspond à la console fonctionnant correctement. C'est ce qu'une
requête non authentifiée est censée obtenir.

**Un avertissement de certificat, pour trois raisons simultanées.** En vérifiant le
certificat directement :

```bash
openssl s_client -connect localhost:65500 -servername localhost </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
```

```text
subject=C=US, ST=California, L=Santa Clara, O=Volterra, OU=Volterra Edge Services, CN=site-local.volterra.io
issuer=C=US, ST=California, L=Santa Clara, O=Volterra, OU=Volterra Edge Services, CN=site-local.volterra.io
notBefore=Oct 25 04:51:31 2024 GMT
notAfter=Oct 25 04:51:31 2025 GMT
```

Le sujet est identique à l'émetteur, donc il est auto-signé. Le nom est
`site-local.volterra.io` alors que vous vous connectez à `localhost`, donc il ne
correspondra pas. Et sur la version utilisée par ce déploiement, **le certificat a expiré
le 25 octobre 2025** — l'appliance le fournit, et rien dans ce dépôt ne le renouvelle.

Attendez-vous à un avertissement catégorique du navigateur, et cela à chaque fois. La
ligne de sujet ci-dessus est la partie utile : c'est ainsi que vous confirmez avoir atteint
l'appliance plutôt qu'autre chose écoutant sur le port local 65500.

## Les identifiants administrateur

Connectez-vous en tant que `admin`. **Cette documentation ne publie pas le mot de passe,
et ne devrait pas le faire.**

Un Customer Edge sorti d'usine est livré avec le mot de passe par défaut publié par F5, et
F5 exige qu'il soit modifié. Considérez sa modification comme faisant partie du déploiement
d'un nœud plutôt que comme un renforcement ultérieur. Deux raisons pour lesquelles cela
importe davantage ici qu'il n'y paraît :

- Cette documentation est publique. Publier le mot de passe actuel de la console de la
  flotte transformerait le fait de « détenir le rôle Reader sur Bastion » en accès complet
  à l'appliance pour quiconque lit la page.
- Un mot de passe publié dans la documentation devient erroné dès qu'une rotation est
  effectuée, et erroné de la manière la plus trompeuse qui soit — le lecteur conclut que
  son accès est défaillant plutôt que que la page est obsolète.

Obtenez le mot de passe là où votre équipe conserve les secrets opérationnels. Si la
réponse est « il s'agit toujours du mot de passe par défaut d'usine », changez-le avant
de faire quoi que ce soit d'autre.

<Aside type="caution" title="La définition du mot de passe depuis Terraform n'est pas vérifiée">
`admin_user_credentials.admin_password` sur l'objet site ressemble à la manière
déclarative de définir ceci. Il **n'a pas** été confirmé qu'il atteigne la Console du site
sur cette version, donc ne supposez pas que c'est le cas.

Ne lisez pas non plus la [page SSH](../ssh/) comme preuve dans un sens ou dans l'autre.
Sa conclusion que `admin_password` « n'a rien changé » a été mesurée par rapport à
l'authentification SSH, que `vpm` ignore entièrement pour l'utilisateur `admin`. Cela ne
dit rien sur la console.
</Aside>

## Pourquoi le tunnel doit cibler l'identifiant de ressource

`--target-resource-id` est obligatoire. Cibler l'adresse du nœud à la place est refusé :

```bash
az network bastion tunnel --name "$BASTION" -g "$RG" \
  --target-ip-address 10.0.3.5 --resource-port 65500 --port 65501
```

```text
ERROR: Custom ports are not allowed. Allowed ports for Tunnel with IP connect is 22, 3389.
```

La raison n'est **pas** que la connexion par IP est désactivée — sur ce Bastion,
`ip_connect_enabled` est `true`. Microsoft ne prend pas en charge les ports personnalisés
via les connexions de client natif basées sur IP, quel que soit ce paramètre
([Documentation Azure](https://learn.microsoft.com/azure/bastion/connect-ip-address)), et
65500 est un port personnalisé. L'inspection de la configuration Bastion ici ne mène nulle
part ; utilisez l'identifiant de ressource.

## Quand cela ne fonctionne pas

| Symptôme | Cause | Correction |
| --- | --- | --- |
| `ERROR: Custom ports are not allowed. Allowed ports for Tunnel with IP connect is 22, 3389.` | Utilisation de `--target-ip-address` | Utilisez `--target-resource-id` |
| `ERROR: Defined port is currently unavailable` | Un autre tunnel occupe déjà ce port local | Arrêtez l'autre tunnel, ou passez un `--port` différent ; `--resource-port` reste à 65500 |
| Le tunnel démarre mais l'identifiant de ressource est vide | Le filtre `jq` a utilisé le nom de la VM au lieu de la clé de site | Indexez sur `eastus01`/`02`/`03` |
| `401 Unauthorized`, realm `Volterra Site Console` | Pas une anomalie — requête non authentifiée | Fournissez les identifiants `admin` |
| Le navigateur refuse le certificat | Auto-signé, non-concordance de nom, et expiré depuis octobre 2025 | Attendu ; confirmez que le sujet est `CN=site-local.volterra.io` et continuez |

<Aside type="note" title="Les échecs d'autorisation n'ont pas été reproduits">
Un RBAC insuffisant est l'autre façon évidente dont cela échoue, mais le reproduire
impliquerait de supprimer des attributions de rôles d'un déploiement partagé, donc cela
n'est pas documenté ici avec une erreur verbatim. Si le tunnel échoue au démarrage avec
une erreur d'autorisation, vérifiez le rôle Reader sur les trois éléments : la VM, sa
carte réseau, et l'hôte Bastion.
</Aside>
