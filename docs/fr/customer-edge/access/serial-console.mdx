Azure Serial Console se connecte au port série émulé du nœud via la
Plateforme Azure. Elle ne transite pas par le plan de contrôle F5 Distributed Cloud, le plan de données du nœud, ni par aucun chemin réseau que le nœud contrôle — ce qui est précisément la raison pour laquelle elle fonctionne quand rien d'autre ne fonctionne.

Utilisez-la lorsqu'un CE **n'a jamais démarré** : l'enregistrement a échoué, le site est absent du tenant, ou le nœud est actif mais n'a pas de route vers l'extérieur. Dans tous ces cas, l'[API de débogage](../debug-api/) n'a pas de tunnel par lequel relayer. [SSH](../ssh/) survit à un enregistrement échoué, mais uniquement si sa clé a déjà été écrite au premier démarrage et que vous pouvez atteindre l'adresse interne du nœud depuis l'intérieur du VNet — deux conditions qui ne sont pas réunies pour un nœud que vous rencontrez pour la première fois.

## Prérequis : diagnostics de démarrage

Azure exige que les diagnostics de démarrage soient activés sur la machine virtuelle avant de pouvoir y rattacher une console série.
Cela est activé par `terraform/modules/ce-node` :

```hcl
boot_diagnostics {}
```

Un bloc vide sélectionne le stockage géré par Azure, de sorte qu'il n'y a pas de compte de stockage de diagnostics, de politique de cycle de vie ou de clé d'accès à gérer. Confirmez-le sur un nœud :

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="L'activation n'est pas rétroactive">
Les diagnostics de démarrage capturent le journal série **au démarrage**. Les activer pour une machine virtuelle déjà en cours d'exécution ne produit pas de journal pour le démarrage qui a déjà eu lieu, donc `az vm boot-diagnostics get-boot-log` répond :

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

C'est attendu, ce n'est pas une anomalie. Un journal de démarrage existe après le prochain redémarrage du nœud. En revanche, l'attachement de la console en direct fonctionne immédiatement — il ne dépend pas du journal.
</Aside>

## Vérification de la disponibilité sans terminal

L'attachement nécessite une session interactive, mais savoir s'il *pourrait* s'attacher ne nécessite que deux appels API. Les deux sont utiles dans un contrôle de santé.

Le service doit être activé pour l'abonnement — un administrateur peut le désactiver à l'échelle du tenant :

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

Demandez ensuite une connexion au port série d'un nœud spécifique :

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

Un `connectionString` commençant par `wss://` — dans ce déploiement
`eastus.gateway.serialconsole.azure.com` — signifie que la console est attachable immédiatement. Avant que les diagnostics de démarrage ne soient activés, cet appel n'avait rien à quoi s'attacher.

<Aside type="danger" title="Cette chaîne de connexion est un identifiant">
Il s'agit d'un jeton bearer à durée de vie courte intégré dans une URL. Ne le journalisez pas, ne le collez pas dans un ticket et ne le committez pas. N'affichez que l'hôte lorsque vous démontrez que l'appel a fonctionné.
</Aside>

## Attachement

<Steps>

1. Installez l'extension une seule fois :

   ```bash
   az extension add --name serial-console
   ```

2. Attachez :

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. Vous arrivez sur l'invite de connexion propre au nœud, et non sur un shell. Il s'agit du Site CLI, qui nécessite des identifiants définis sur le nœud — le mot de passe administrateur issu du provisionnement, ou un mot de passe défini via l'endpoint de changement de mot de passe. La console série prouve que le *canal* fonctionne ; elle ne contourne pas l'authentification.

</Steps>

Capturé depuis `f5-xc-ce-vm-01`, avec des parties omises au milieu là où la sortie des unités systemd n'apporte rien :

```text file=../../../_data/serial-console-boot.txt
```

Quatre éléments dans cette transcription méritent attention, car ils répondent à des questions que l'API de débogage ne peut pas résoudre :

- **cloud-init s'est terminé** — `Datasource DataSourceAzure`, terminé à 22,37 secondes.
  Un nœud qui ne s'enregistre jamais a généralement échoué ici, et c'est à cet endroit que vous le verrez.
- **Les deux environnements d'exécution de conteneurs ont démarré.** `Container Runtime Interface for OCI (CRI-O)`
  et `Docker Application Container Engine` sont tous les deux `[ OK ]`, ce qui constitue la preuve au démarrage du comportement à double environnement d'exécution qui surprend les utilisateurs dans [crictl](../../commands/system/crictl/) et [docker](../../commands/system/docker/).
- **`VP Manager image load` et `Argo Watch service`** — `vpm` et Argo démarrent.
- **L'invite est celle du nœud lui-même**, derrière sa bannière d'audit. La console série vous donne une invite de connexion, pas une session.

<Aside type="caution" title="L'attachement interactif nécessite un vrai terminal — mais peut être scripté">
`az serial-console connect` passe le terminal en mode brut, il ne peut donc pas s'exécuter depuis un pipeline ou tout contexte sans TTY. Il échoue côté client, avant de contacter Azure :

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

Cette trace de pile concerne la gestion du terminal, pas une panne de la console série.

L'attachement lui-même, cependant, **est** automatisable — pilotez directement le websocket plutôt que la CLI. La transcription ci-dessus a été capturée de cette façon, sans TTY. Consultez `scripts/serial_console_capture.py`, qui est la méthode permettant de collecter des preuves de démarrage depuis un nœud qui n'a pas réussi à s'enregistrer sans qu'un humain soit assis devant un terminal.
</Aside>

<Aside type="caution" title="Attendez-vous à réessayer : la passerelle refuse environ une tentative sur deux">
La première trame de la passerelle est un défi, pas une sortie, et le client y répond avec un jeton bearer. Même lorsque cela est fait correctement, le socket se ferme souvent immédiatement :

```
[close] code=1011 reason=Connection not trusted
```

Comportement observé : cela réussit de manière intermittente, et sous une utilisation soutenue, chaque nœud du groupe de ressources refuse — y compris des nœuds qui fonctionnaient quelques minutes auparavant.
`scripts/serial_console_capture.py` réessaie par défaut car réessayer fonctionne souvent.

**La cause n'est pas établie.** Ce qui a été exclu, car chacun est une hypothèse plausible qui fait perdre du temps :

| Pas ceci | Comment confirmer |
| --- | --- |
| Limitation ARM/compute | Cela renvoie HTTP `429` sur les appels ARM. Il s'agit ici d'une fermeture de websocket sur un canal de données séparé. |
| Interception TLS par un proxy | `openssl s_client -connect <region>.gateway.serialconsole.azure.com:443 \| openssl x509 -noout -issuer`. Un émetteur authentique `O=Microsoft Corporation` l'exclut ; un fournisseur de proxy comme émetteur le confirme, et la correction consiste à placer `*.serialconsole.azure.com` en liste d'autorisation. |
| Diagnostics de démarrage désactivés | `az vm show -g <rg> -n <vm> --query diagnosticsProfile` indiquant `enabled: true`. |
| Incohérence de jeton entre l'octroi et le défi | Utiliser un seul jeton pour les deux est la pratique correcte, mais n'empêche pas la fermeture. |

Ce qui *est* documenté comme comportement Azure : **une seule session de console série par machine virtuelle, et une deuxième demande réussie évince la première.** L'utilisateur évincé est déconnecté mais pas délogué, donc la session shell persiste. Deux personnes déboguant un même nœud se déplaceront mutuellement de manière répétée.

Pour les travaux en volume, préférez l'[API de débogage](../debug-api/) ou [SSH](../ssh/), qui n'ont pas ces limitations. SSH en particulier n'a pas de limite de collage ni de restriction de session unique, c'est donc le meilleur choix chaque fois que le nœud est accessible depuis l'intérieur du VNet.
</Aside>

<Aside type="caution" title="Le collage est limité à 2 048 caractères">
Azure limite la longueur du collage dans la console série à 2 048 caractères, afin d'éviter de surcharger le port série. L'envoi d'une longue commande — ou d'un lot de commandes en une seule écriture — échoue d'une manière qui ressemble à un blocage ou une limitation plutôt qu'à une limite de longueur.

Envoyez les commandes individuellement. Il s'agit d'une contrainte réelle pour toute collecte en volume via la console série, et une autre raison de préférer l'[API de débogage](../debug-api/) pour ce type de travail.
</Aside>

## Ce que vous pouvez voir ici que l'API ne peut pas vous montrer

- **cloud-init** en cours d'exécution, en échec, ou ne démarrant jamais — cause habituelle d'un nœud qui ne s'enregistre jamais.
- **Les tentatives d'enregistrement** contre `register.ves.volterra.io`, incluant une erreur de configuration ou un jeton rejeté par le tenant.
- **Les messages du noyau et du démarrage** d'avant l'exécution de tout agent.
- Le nœud lorsqu'il **n'a pas de chemin réseau fonctionnel**, ce qui bloque toutes les autres routes.

Pour un nœud qui est `ONLINE`, préférez l'API de débogage : elle est scriptable, elle produit des preuves que vous pouvez rejouer, et elle n'occupe pas le port série unique.
