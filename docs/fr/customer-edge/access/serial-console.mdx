La console série Azure se connecte au port série émulé du nœud via la
Plateforme Azure. Elle ne traverse pas le plan de contrôle F5 Distributed Cloud, le plan de
données du nœud, ni aucun chemin réseau que le nœud contrôle — c'est précisément pour
cette raison qu'elle fonctionne quand rien d'autre ne fonctionne.

Utilisez-la lorsqu'un CE **n'a jamais démarré** : l'enregistrement a échoué, le site est absent
du tenant, ou le nœud est actif mais n'a aucune route de sortie. Dans tous ces cas,
l'[API de débogage](../debug-api/) n'a aucun tunnel par lequel relayer, et SSH est fermé sur le
nœud tel qu'il est livré.

## Prérequis : diagnostics de démarrage

Azure exige que les diagnostics de démarrage soient activés sur la VM avant de pouvoir
attacher une console série. Cela est activé par `terraform/modules/ce-node` :

```hcl
boot_diagnostics {}
```

Un bloc vide sélectionne le stockage géré par Azure, de sorte qu'il n'y a pas de compte
de stockage de diagnostics, de politique de cycle de vie ou de clé d'accès à gérer.
Vérifiez-le sur un nœud :

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="L'activation n'est pas rétroactive">
Les diagnostics de démarrage capturent le journal série **au démarrage**. Les activer pour une
VM déjà en cours d'exécution ne produit pas de journal pour le démarrage qui a déjà eu lieu,
donc `az vm boot-diagnostics get-boot-log` répond :

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

C'est normal, pas une erreur. Un journal de démarrage existe après le prochain redémarrage
du nœud. L'attachement de la console en direct, en revanche, fonctionne immédiatement —
il ne dépend pas du journal.
</Aside>

## Vérification de la disponibilité sans terminal

L'attachement nécessite une session interactive, mais savoir si l'attachement *serait*
possible se résume à deux appels API. Les deux sont utiles dans un contrôle de santé.

Le service doit être activé pour l'abonnement — un administrateur peut le désactiver
à l'échelle du tenant :

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

Ensuite, demandez une connexion au port série d'un nœud spécifique :

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

Un `connectionString` commençant par `wss://` — sur ce déploiement
`eastus.gateway.serialconsole.azure.com` — signifie que la console est attachable
immédiatement. Avant l'activation des diagnostics de démarrage, cet appel n'avait rien
à attacher.

<Aside type="danger" title="Cette chaîne de connexion est un identifiant">
Il s'agit d'un jeton bearer à durée de vie courte intégré dans une URL. Ne le journalisez
pas, ne le collez pas dans un ticket, et ne le commitez pas. Affichez uniquement l'hôte
lorsque vous démontrez que l'appel a fonctionné.
</Aside>

## Attachement

<Steps>

1. Installez l'extension une seule fois :

   ```bash
   az extension add --name serial-console
   ```

2. Attachez :

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. Vous arrivez à l'invite de connexion propre au nœud, et non à un shell. Il s'agit
   de la CLI du site, qui nécessite des identifiants définis sur le nœud — le mot de
   passe administrateur du provisionnement, ou l'un défini via l'endpoint de changement
   de mot de passe. La console série prouve que le *canal* fonctionne ; elle ne contourne
   pas l'authentification.

</Steps>

<Aside type="caution" title="Elle nécessite un vrai terminal">
`az serial-console connect` met le terminal en mode brut, il ne peut donc pas être
exécuté depuis un script, un pipeline, ou tout contexte sans TTY. Il échoue côté client
avant de contacter Azure :

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

Cette trace d'erreur concerne la gestion du terminal, pas une panne de la console série —
les deux appels API ci-dessus signaleront toujours la console comme disponible. Si vous
avez besoin d'un signal automatisable, utilisez-les plutôt que d'essayer de scripter
l'attachement.
</Aside>

## Ce que vous pouvez voir ici que l'API ne peut pas vous montrer

- **cloud-init** en cours d'exécution, en échec, ou ne démarrant jamais — cause habituelle
  d'un nœud qui ne s'enregistre jamais.
- **Les tentatives d'enregistrement** contre `register.ves.volterra.io`, incluant une
  erreur de configuration ou un jeton rejeté par le tenant.
- **Les messages du noyau et du démarrage** d'avant le démarrage de tout agent.
- Le nœud lorsqu'il **n'a aucun chemin réseau fonctionnel**, ce qui neutralise toutes les
  autres routes.

Pour un nœud qui est `ONLINE`, préférez l'API de débogage : elle est scriptable, elle
produit des résultats que vous pouvez relancer, et elle n'occupe pas le port série unique.
