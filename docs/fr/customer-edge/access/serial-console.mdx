La console série Azure se connecte au port série émulé du nœud via la plateforme
Azure. Elle ne traverse ni le plan de contrôle F5 Distributed Cloud, ni le plan de
données du nœud, ni aucun chemin réseau contrôlé par le nœud — c'est précisément
pour cela qu'elle fonctionne quand plus rien d'autre ne fonctionne.

Utilisez-la lorsqu'un CE **n'a jamais démarré** : l'enregistrement a échoué, le site
est absent du tenant, ou le nœud est actif mais n'a aucune route de sortie. Dans tous
ces cas, l'[API de débogage](../debug-api/) n'a aucun tunnel par lequel relayer, et
[SSH ne peut pas s'authentifier](../ssh/) sur cette build.

## Prérequis : diagnostics de démarrage

Azure exige que les diagnostics de démarrage soient activés sur la VM avant
d'attacher une console série. Cela est activé par `terraform/modules/ce-node` :

```hcl
boot_diagnostics {}
```

Un bloc vide sélectionne le stockage géré par Azure, il n'y a donc aucun compte de
stockage de diagnostics, aucune stratégie de cycle de vie ni clé d'accès à gérer.
Confirmez-le sur un nœud :

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="L'activation n'est pas rétroactive">
Les diagnostics de démarrage capturent le journal série **au démarrage**. Les activer
sur une VM déjà en cours d'exécution ne produit pas de journal pour le démarrage déjà
survenu, si bien que `az vm boot-diagnostics get-boot-log` répond :

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

C'est attendu, ce n'est pas une anomalie. Un journal de démarrage existera après le
prochain redémarrage du nœud. L'attachement à la console en direct, en revanche,
fonctionne immédiatement — il ne dépend pas du journal.
</Aside>

## Vérifier la disponibilité sans terminal

L'attachement nécessite une session interactive, mais savoir s'il *pourrait* aboutir
tient en deux appels d'API. Les deux sont utiles dans un contrôle de santé.

Le service doit être activé pour l'abonnement — un administrateur peut le désactiver
à l'échelle du tenant :

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

Demandez ensuite une connexion au port série d'un nœud spécifique :

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

Une `connectionString` commençant par `wss://` — sur ce déploiement
`eastus.gateway.serialconsole.azure.com` — signifie que la console est attachable dès
maintenant. Avant l'activation des diagnostics de démarrage, cet appel n'avait rien
à quoi s'attacher.

<Aside type="danger" title="Cette chaîne de connexion est un identifiant">
Il s'agit d'un jeton porteur à courte durée de vie intégré dans une URL. Ne le
journalisez pas, ne le collez pas dans un ticket et ne le committez pas. N'affichez
que l'hôte lorsque vous démontrez que l'appel a fonctionné.
</Aside>

## Attachement

<Steps>

1. Installez l'extension une seule fois :

   ```bash
   az extension add --name serial-console
   ```

2. Attachez-vous :

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. Vous arrivez sur l'invite de connexion du nœud, pas sur un shell. Il s'agit de la
   Site CLI, et elle nécessite des identifiants définis sur le nœud — le mot de passe
   administrateur issu du provisionnement, ou un mot de passe défini via l'endpoint de
   changement de mot de passe. La console série prouve que le *canal* fonctionne ;
   elle ne contourne pas l'authentification.

</Steps>

Capturé depuis `f5-xc-ce-vm-01`, tronqué au milieu là où la sortie de l'unité systemd
n'apporte rien :

```text file=../../../_data/serial-console-boot.txt
```

Quatre éléments de cette transcription méritent attention, car ils répondent à des
questions auxquelles l'API de débogage ne peut pas répondre :

- **cloud-init a terminé** — `Datasource DataSourceAzure`, terminé à 22,37 secondes.
  Un nœud qui ne s'enregistre jamais a généralement échoué ici, et c'est là que vous
  le constatez.
- **Les deux runtimes de conteneurs ont démarré.** `Container Runtime Interface for OCI (CRI-O)`
  et `Docker Application Container Engine` sont chacun `[ OK ]`, ce qui constitue la
  preuve au démarrage du comportement à double runtime qui surprend dans
  [crictl](../../commands/system/crictl/) et [docker](../../commands/system/docker/).
- **`VP Manager image load` et `Argo Watch service`** — `vpm` et Argo qui démarrent.
- **L'invite est celle du nœud lui-même**, derrière sa bannière d'audit. La console
  série vous donne une invite de connexion, pas une session.

<Aside type="caution" title="L'attachement interactif nécessite un vrai terminal — mais il peut être scripté">
`az serial-console connect` place le terminal en mode brut, il ne peut donc pas
s'exécuter depuis un pipeline ou tout contexte dépourvu de TTY. Il échoue côté client,
avant même de contacter Azure :

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

Cette trace concerne la gestion du terminal, pas une panne de la console série.

L'attachement lui-même, en revanche, **est** automatisable — pilotez directement le
websocket plutôt que la CLI. La transcription ci-dessus a été capturée ainsi, sans TTY.
Voir `scripts/serial_console_capture.py`, qui est la façon dont vous collecteriez des
preuves de démarrage depuis un nœud qui n'a pas réussi à s'enregistrer, sans qu'un
humain soit assis devant un terminal.
</Aside>

<Aside type="caution" title="Attendez-vous à réessayer : la passerelle refuse environ une tentative sur deux">
La première trame de la passerelle est un défi, non une sortie, et le client y répond
avec un jeton porteur. Même lorsque cela est fait correctement, le socket se ferme
souvent immédiatement :

```
[close] code=1011 reason=Connection not trusted
```

Comportement observé : cela réussit par intermittence, et en usage soutenu chaque nœud
du groupe de ressources refuse — y compris des nœuds qui fonctionnaient quelques minutes
plus tôt. `scripts/serial_console_capture.py` réessaie par défaut, car réessayer
fonctionne souvent.

**La cause n'est pas établie.** Voici ce qui a été écarté, car chacune de ces hypothèses
est plausible et fait perdre du temps :

| Pas cela | Comment le confirmer |
| --- | --- |
| Limitation (throttling) ARM/compute | Cela renvoie un HTTP `429` sur les appels ARM. Ici il s'agit d'une fermeture de websocket sur un canal de données distinct. |
| Interception TLS par un proxy | `openssl s_client -connect <region>.gateway.serialconsole.azure.com:443 \| openssl x509 -noout -issuer`. Un émetteur authentique `O=Microsoft Corporation` l'exclut ; un fournisseur de proxy comme émetteur le confirme, et la correction consiste à autoriser `*.serialconsole.azure.com`. |
| Diagnostics de démarrage désactivés | `az vm show -g <rg> -n <vm> --query diagnosticsProfile` indiquant `enabled: true`. |
| Discordance de jeton entre l'octroi et le défi | Utiliser un seul jeton pour les deux est la pratique correcte, mais n'empêche pas la fermeture. |

Ce qui *est* un comportement Azure documenté : **une seule session de console série par
VM, et une seconde requête réussie évince la première.** L'utilisateur évincé est
déconnecté mais pas déloggé, la session shell survit donc. Deux personnes déboguant un
même nœud se délogeront mutuellement de façon répétée.

Pour les travaux en masse, préférez l'[API de débogage](../debug-api/), qui n'a aucune de
ces limites. [SSH n'est pas une alternative](../ssh/) — il ne peut pas être activé sur
cette build.
</Aside>

<Aside type="caution" title="Le collage est plafonné à 2 048 caractères">
Azure limite la longueur des collages en console série à 2 048 caractères, afin d'éviter
de surcharger le port série. L'envoi d'une commande longue — ou d'un lot de commandes en
une seule écriture — échoue d'une manière qui ressemble à un blocage ou à une limitation
plutôt qu'à une limite de longueur.

Envoyez les commandes une par une. C'est une contrainte réelle pour toute collecte en
masse via la console série, et une raison de plus de préférer l'[API de débogage](../debug-api/)
pour ce travail.
</Aside>

## Ce que vous pouvez voir ici et que l'API ne peut pas montrer

- **cloud-init** en cours d'exécution, en échec, ou jamais démarré — la cause
  habituelle d'un nœud qui ne s'enregistre jamais.
- **Les tentatives d'enregistrement** auprès de `register.ves.volterra.io`, y compris
  une erreur de configuration ou un jeton rejeté par le tenant.
- **Les messages du noyau et de démarrage** antérieurs à l'exécution de tout agent.
- Le nœud lorsqu'il n'a **aucun chemin réseau fonctionnel**, ce qui met en échec toutes
  les autres voies.

Pour un nœud qui *est* `ONLINE`, préférez l'API de débogage : elle est scriptable, elle
produit des preuves que vous pouvez rejouer, et elle n'occupe pas l'unique port série.
