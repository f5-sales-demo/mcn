Le CE exécute FRR pour BGP. Sur cette topologie, il établit un peering avec les deux instances
Azure Route Server, annonce la VIP et apprend le préfixe du VNet.

## `show-ip-bgp-summary`

Commencez ici. Un seul écran vous indique si le peering est actif et depuis combien de temps il
est stable.

```bash
{"command":["show-ip-bgp-summary"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp-summary.txt
```

Lisez d'abord `State/PfxRcd`. Un nombre correspond au décompte des préfixes reçus et signifie que
la session est établie ; toute autre valeur — `Active`, `Connect`, `Idle` — indique une session
qui n'est pas active. `Up/Down` indique depuis combien de temps l'état actuel dure, de sorte qu'une
session qui se réinitialise sans cesse affiche une valeur suspicieusement faible.

<Aside type="caution" title="Le vrf id indiqué ici n'est pas celui attendu par rt">
Cette sortie signale `vrf-id 3`. Il s'agit de la numérotation de FRR. Le plan de données Argo utilise
un identifiant de table distinct, et transmettre le numéro de FRR à
[`rt --dump`](../dataplane-forwarding/) renvoie `No such file or directory`, ce qui
ressemble à un nœud défectueux plutôt qu'à un argument incorrect.
</Aside>

## `show-ip-bgp`

La table complète, avec la sélection du meilleur chemin visible.

```bash
{"command":["show-ip-bgp"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp.txt
```

`*` désigne une route valide, `>` le meilleur chemin sélectionné, `=` un membre multipath. Dans la capture
ci-dessus, le préfixe VNet appris `10.0.0.0/16` possède deux chemins — un via chaque instance de Route
Server — marqués `*=` et `*>` : un meilleur chemin plus un membre multipath, de sorte que le nœud répartit
la charge de son trafic de retour sur les deux instances. La VIP `10.250.0.10/32` dispose d'un unique chemin
`*>` car ce nœud en est l'origine.

<Aside type="caution" title="L'ECMP à trois voies de la démonstration n'est pas visible dans cette sortie">
`show-ip-bgp` correspond à la table d'un seul nœud. L'ECMP que ce déploiement illustre repose sur trois CE
*différents* annonçant le même `/32`, et il est programmé côté Azure — aucune table BGP d'un CE isolé ne peut
donc le montrer, et l'absence de marqueur multipath sur la VIP ici n'est pas un défaut.
Vérifiez-le plutôt depuis les peerings du Route Server ou depuis la table de routage effective du client ;
les deux figurent sur la [page as-built](../../../../as-built/).
</Aside>

## `show-ip-bgp-neighbors`

Détail par voisin : capacités négociées, minuteries, compteurs de messages et la
raison de la dernière réinitialisation.

```bash
{"command":["show-ip-bgp-neighbors"]}
```

Utilisez-la lorsque le résumé indique une session instable et que vous devez en connaître la cause.
`Last reset` et son motif sont les lignes utiles.

## `show-ip-bgp-neighbors-advertised-route`

Ce que ce nœud communique à ses pairs, par opposition à ce qu'il connaît.

```bash
{"command":["show-ip-bgp-neighbors-advertised-route"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp-neighbors-advertised-route.txt
```

C'est la commande à utiliser pour « la VIP n'est pas joignable depuis le VNet ». Si la VIP est
absente ici, le problème se situe sur ce nœud et examiner le pair ne servira à
rien.

La sortie répète un bloc `bgp neighbor:` **par pair**, de sorte que sur cette topologie vous obtenez les
deux mêmes préfixes en double — une fois pour chaque instance de Route Server. Il ne s'agit pas d'un rendu
dupliqué : c'est ce qui confirme que le nœud annonce bien aux deux. Le cas intéressant est celui d'un bloc
présent pour un pair et absent ou incomplet pour l'autre.
