## `diagnosis`

<Aside type="caution" title="Portée GLOBAL — un transport différent">
Comme `health`, un `GET` vers le chemin `global` et non accessible via `exec-user`.

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/global/diagnosis"
```

</Aside>

```json file=../../../../_data/sitecli-diagnosis.txt
```

Le nœud sonde sa propre passerelle et rapporte le résultat par nœud ; ainsi, sur un
site multi-nœuds, vous obtenez un bloc pour chacun. `gateway_connectivity` contient
un résumé de ping — `sent`, `received`, `lost` ainsi que les temps d'aller-retour.

<Aside type="note" title="Une perte de 100 % vers la passerelle n'est pas nécessairement une anomalie">
Dans cette topologie, la passerelle ne répond pas aux requêtes ICMP ; par conséquent,
`lost: 100` est l'état stable lorsque le site est `ONLINE` et en cours de
transmission. Traitez ce champ comme un signal uniquement lorsque vous disposez déjà
d'autres indices d'un problème, ou lorsque sa valeur change.
</Aside>

`resolv_conf` est le champ le plus constamment utile : il indique le résolveur que le
nœud utilisera effectivement, ce qui vaut la peine d'être comparé à ce que vous
attendez avant de passer du temps dans [`dig`](../../network/dig/).
