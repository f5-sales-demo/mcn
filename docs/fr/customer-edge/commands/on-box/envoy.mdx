Capturé le 2026-07-28 depuis un CE de ce déploiement. Ce sont des commandes exécutées sur l'appliance, elles passent donc
par la CLI du site plutôt que par l'API de débogage ; `sitecli/exec-catalog.json` enregistre la
surface et `sitecli/capture-manifest.json` enregistre le nœud concerné.

Envoy termine et relaie le trafic applicatif sur le Customer Edge. Ces quatre commandes
interrogent son interface d'administration, et aucune d'elles ne figure sur l'
[API de débogage](../../../access/debug-api/).

<Aside type="note" title="Chacune d'elles commence par un indicateur de progression curl">
Ce sont des wrappers `curl` autour du point de terminaison d'administration d'Envoy, invoqués sans `-s`, de sorte que les deux ou trois
premières lignes de chaque capture ci-dessous correspondent à la progression du transfert écrite par curl sur stderr :

```text
  % Total    % Received % Xferd  Average Speed   Time    Time     Time  Current
                                 Dload  Upload   Total   Spent    Left  Speed
  0     0    0     0 …
```

Il ne s'agit pas d'une sortie d'Envoy ni d'une erreur. C'est même utile : le décompte d'octets `% Received`
vous indique si Envoy a renvoyé quelque chose, ce qui permet de distinguer « aucun listener
configuré » de « l'interface d'administration n'a pas répondu ».
</Aside>

## `envoy-listeners`

Tous les listeners installés par Envoy, sous la forme `name:address:port`.

```bash
execcli envoy-listeners
```

```text file=../../../../_data/sitecli-envoy-listeners.txt
```

**Ce qu'il faut observer.** Sur ce déploiement, le listener porte `10.250.0.10:80` — la VIP que
le CE annonce dans BGP. Cette seule ligne relie trois couches entre elles : si
[`show-ip-bgp-summary`](../../network/bgp/) montre que le préfixe est annoncé mais que ce
listener est absent, la route attire du trafic vers un nœud qui ne le servira pas, ce qui est
le pire mode de défaillance dans un ensemble ECMP car le trafic est réparti dans un trou noir.

L'adresse `[fe80:…]:80` en fin de ligne est l'adresse link-local de l'interface à laquelle le listener est
lié.

**Ce qu'il ne vous dit pas.** Rien sur la santé des upstreams — un listener existe que
quelque chose derrière lui soit joignable ou non. Utilisez `envoy-clusters` pour cela.

## `envoy-clusters`

Tous les clusters, avec leurs limites de connexions et de requêtes par priorité.

```bash
execcli envoy-clusters
```

```text file=../../../../_data/sitecli-envoy-clusters.txt
```

**Ce qu'il faut observer.** Les lignes ont la forme `cluster::scope::key::value`. L'entrée `observability_name`
identifie chaque cluster, et le triplet `default_priority::max_connections`,
`max_pending_requests` et `max_requests` est l'endroit où apparaissent les limites de requêtes — un cluster
bloqué à son `max_pending_requests` est bridé par la configuration plutôt que par
l'upstream.

## `envoy-config-dump`

La configuration complète d'Envoy au format JSON. Volumineuse : 126 Ko sur un nœud de démonstration par ailleurs inactif.

```bash
execcli envoy-config-dump
```

```text file=../../../../_data/sitecli-envoy-config-dump.txt
```

**Ce qu'il faut observer.** Le tableau `configs` de premier niveau contient un objet par type de configuration —
bootstrap, clusters, listeners, routes, secrets. Recourez-y lorsqu'un listener ou un cluster
existe mais se comporte de manière inattendue, et faites une recherche dedans plutôt que de le lire intégralement.

## `envoy-hc-config-dump`

La configuration des contrôles de santé spécifiquement.

```bash
execcli envoy-hc-config-dump
```

```text file=../../../../_data/sitecli-envoy-hc-config-dump.txt
```

**Ce qu'il faut observer.** Sur ce déploiement, elle renvoie **un seul octet** — visible sous la forme `100 1`
dans l'indicateur curl — ce qui signifie qu'aucune configuration de contrôle de santé n'est installée. C'est l'état attendu
pour un CE sans pools d'origine soumis à des contrôles de santé, et il vaut la peine de le reconnaître : un résultat vide
ici n'est pas une requête en échec.
