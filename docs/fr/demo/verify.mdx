Exécutez ces vérifications avant votre présentation. Chacune resserre l'endroit où se situerait
une panne, de sorte qu'un échec vous apprend quelque chose au lieu de signaler seulement que
quelque chose ne va pas.

Chaque commande lit ce dont elle a besoin dans le déploiement. Définissez ces variables une
fois et le reste suit :

```bash
cd terraform
RG=$(terraform output -raw resource_group_name)
RS=$(terraform output -raw route_server_name)
CLIENT=$(terraform output -raw client_vm_name)
DOMAIN=$(terraform output -raw lb_domain)
VIP=$(terraform output -raw vip)
NIC=$(terraform output -raw client_nic_name)
```

## Quatre vérifications, dans cet ordre

<Steps>

1. **Chaque site est `ONLINE`.** Rien de ce qui suit ne peut être vrai si ce n'est pas le cas.

   ```bash
   for s in $(terraform output -json xc_site_names | jq -r '.[]'); do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   Observé le 2026-07-28, trois CE :

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **Chaque peering apprend l'annonce du VIP de ce CE.** Interrogez chaque peering
   séparément — voyez le premier piège ci-dessous, car c'est là que la démonstration semble le
   plus souvent cassée sans l'être.

   ```bash
   for k in $(terraform output -json xc_site_names | jq -r 'keys[]'); do
     echo "--- ${k}-bgp"
     az network routeserver peering list-learned-routes \
       --name "${k}-bgp" --routeserver "$RS" -g "$RG" \
       --query "RouteServiceRole_IN_0[?network=='${VIP}/32'].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   Observé le 2026-07-28 :

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp
   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp
   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   Trois peerings, trois sauts suivants différents, un seul préfixe. C'est le côté annonce de
   l'ECMP qui est prouvé.

3. **Les routes effectives du client portent chaque saut suivant.** C'est l'ECMP lui-même, tel
   que le VNet l'a programmé — non pas ce que les CE prétendent, mais ce qu'Azure en a fait.

   ```bash
   az network nic show-effective-route-table -g "$RG" -n "$NIC" \
     --query "value[?addressPrefix[0]=='${VIP}/32'].{prefix:addressPrefix[0],nh:nextHopIpAddress,type:nextHopType,state:state}" \
     -o json
   ```

   Observé le 2026-07-28 :

   ```json
   [
     {
       "nh": ["10.0.1.5", "10.0.1.6", "10.0.1.4"],
       "prefix": "10.250.0.10/32",
       "state": "Active",
       "type": "VirtualNetworkGateway"
     }
   ]
   ```

   `state: Active` avec une entrée par CE dans `nh` : voilà la vérification. **L'ordre n'est pas
   significatif et n'est pas stable** — Azure les renvoie différemment d'un appel à l'autre,
   donc comptez-les plutôt que de les comparer à une exécution précédente. Un seul saut suivant
   là où vous en attendez trois signifie qu'un CE a cessé d'annoncer, et l'étape 2 identifie
   lequel.

4. **Le VIP sert le trafic.** Depuis la VM cliente, et **avec l'en-tête `Host`** — voyez le
   deuxième piège. Échantillonnez suffisamment de requêtes pour voir un problème : quelques
   dizaines se lisent comme 100 % même à l'intérieur de la fenêtre de convergence décrite
   ci-dessous.

   ```bash
   az vm run-command invoke -g "$RG" -n "$CLIENT" \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts "ok=0; fail=0
                for i in \$(seq 1 60); do
                  c=\$(curl -s -o /dev/null -m 5 -w '%{http_code}' \
                        -H 'Host: ${DOMAIN}' http://${VIP}/)
                  [ \"\$c\" = 200 ] && ok=\$((ok+1)) || fail=\$((fail+1))
                done
                echo \"OK=\$ok FAIL=\$fail\""
   ```

   Observé le 2026-07-28 :

   ```text
   VIP with Host header: OK=60 FAIL=0
   bare IP (no Host): 404
   ```

</Steps>

## Piège : un peering n'affiche qu'une route, et c'est correct

`list-learned-routes` est limité au peering que vous nommez. Il rapporte ce que **ce** pair a
annoncé, pas la table complète du Route Server.

Ainsi, interroger un seul peering renvoie un unique `/32` de VIP via un unique saut suivant, et
il est tentant de lire cela comme « un seul CE annonce — les autres sont hors service ». Rien
n'est hors service. Les autres annonces sont visibles sur leurs propres peerings, ce sur quoi
l'étape 2 boucle.

Confirmer l'ECMP à partir de la requête d'un seul peering est impossible. Soit vous bouclez sur
tous les peerings, soit vous lisez la table de routes effectives du client, qui montre le
résultat fusionné en un seul appel.

## Piège : une requête sur IP nue renvoie 404

L'équilibreur de charge fait correspondre sur `Host`. Le VIP n'est pas un serveur virtuel qui
sert quoi que ce soit à quiconque se connecte à l'adresse.

Ces deux résultats proviennent de la même exécution sur le déploiement sain :

```text
curl -H "Host: $DOMAIN" http://$VIP/   ->  200   (60 of 60)
curl                     http://$VIP/   ->  404
```

**Un 404 sur IP nue est la preuve que le chemin fonctionne** — la requête a atteint le CE, le
proxy du CE a répondu, et il a refusé parce qu'aucun domaine configuré ne correspondait. Le
lire comme une panne vous envoie examiner le BGP, où vous ne trouverez rien d'anormal.

Il en va de même pendant une démonstration : si vous saisissez l'adresse dans un navigateur
plutôt que de résoudre le domaine vers elle, vous obtenez le 404.

## Le VIP perd des requêtes pendant les trois premiers quarts d'heure, puis s'arrête

Sur une pile fraîchement construite, le VIP perd une petite fraction des requêtes pendant
environ les 45 premières minutes après que les CE atteignent l'état `ONLINE`, puis sert
proprement. Mesuré sur 1 470 requêtes depuis la VM cliente, toutes avec l'en-tête `Host` :

| Fenêtre | Requêtes | Échecs | Taux |
| --- | --- | --- | --- |
| ~45 premières minutes après l'établissement de l'ECMP | 570 | 12 | **2,11 %** |
| Les 23 minutes suivantes | 900 | **0** | **0,00 %** |

Chaque échec était un `curl: (28)` — un délai d'attente dépassé avec zéro octet reçu — et non un
statut d'erreur HTTP. Le dernier est survenu environ 43 minutes après l'établissement de l'ECMP.
Sur les 900 requêtes propres, 400 ont été exécutées avec un délai d'attente de 30 secondes et
chacune s'est terminée en moins de 2 secondes, donc rien n'a été masqué par un délai trop court.

**L'origine n'était pas la cause.** Un lot de contrôle directement vers l'origine
(`terraform output -raw origin_ip`, en contournant le VIP) a donné 120 sur 120 propres
*simultanément* à des lots VIP en échec. La panne se situe quelque part dans le chemin VIP, ECMP
ou CE.

Deux choses que l'on se garde délibérément d'affirmer :

- **Ce n'est pas un défaut en régime permanent.** Il disparaît complètement et reste absent.
  Une démonstration en place depuis une heure n'a pas ce problème — 60 sur 60 à la vérification 4
  ci-dessus, sur une pile en place depuis plusieurs heures.
- **Ce n'est pas imputable à un CE particulier.** Rien dans cette topologie ne fournit un
  écouteur HTTP par nœud, donc il n'y a aucun moyen de rattacher une requête perdue au nœud qui
  l'a perdue. Les interfaces externes des CE n'ont aucun écouteur HTTP — seul le `/32` du VIP
  répond.

Le phénomène s'est reproduit lors d'une reconstruction propre dans un autre tenant, il suit donc
la topologie plutôt que l'environnement.

<Aside type="caution" title="N'échantillonnez pas 40 requêtes pour conclure que tout va bien">
Des lots de 40 à 50 requêtes se lisent comme 100 % la plupart du temps, même à l'intérieur de la
fenêtre d'échec. C'est ainsi que ce phénomène a d'abord été mal caractérisé comme un défaut
persistant à faible taux, puis comme une absence totale de défaut. Échantillonnez 100 requêtes ou
plus, en lots espacés dans le temps.
</Aside>

## Deux autres pièges de mesure

Tous deux ont produit des réponses erronées mais assurées dans cet environnement, et aucun n'est
évident.

- **Sondez depuis l'intérieur du VNet, pas depuis votre poste de travail.** Un proxy d'entreprise
  peut compléter lui-même la poignée de main TCP sur les ports courants, de sorte qu'une sonde
  depuis le poste de travail signale un port **ouvert** alors qu'il est en réalité fermé. Les
  ports 80 et 443 apparaissent ouverts sur les adresses publiques des CE depuis un poste de
  travail et sont fermés lorsqu'ils sont sondés depuis l'intérieur du VNet. Utilisez la VM
  cliente.
- **Le port 22 d'un CE ne répond que sur l'adresse interne (SLI).** Sondée depuis la VM cliente,
  l'adresse interne de chaque CE renvoie une bannière OpenSSH, tandis que ses adresses de gestion
  et externe expirent — comme le fait une adresse inutilisée servant de témoin. eth0 est renommée
  `a-i-eth0` et ne porte aucune IP hôte, car le plan de données la possède. Sonder l'adresse par
  laquelle vous connaissez le nœud ne vous apprend donc rien sur l'état SSH de ce nœud.

<Aside type="danger" title="Ne codez jamais en dur une adresse interne de CE — elles sont réattribuées à chaque reconstruction">
Azure ne préserve pas l'attribution des adresses du sous-réseau interne aux CE. Observé le
2026-07-28, après une reconstruction, les trois CE détenaient `10.0.3.7`, `10.0.3.5` et
`10.0.3.4` : pas dans l'ordre des nœuds, pas contiguës, et différentes de ce qu'elles étaient
auparavant. La NIC du client de test se trouve dans le même sous-réseau et a détenu une adresse
qu'un CE détenait précédemment.

Lisez-les au lieu de les mémoriser :

```bash
terraform output -json ce_sli_private_ips
```

Sans état Terraform sous la main, interrogez Azure par nom de NIC, qui *est* stable :

```bash
az network nic show -g "$RG" -n "<vm-name>-internal-nic" \
  --query ipConfigurations[0].privateIPAddress -o tsv
```

Se connecter à une adresse mémorisée vous fait atterrir sur le mauvais nœud, sur une VM qui n'est
pas un CE, ou nulle part — et ce dernier cas est identique à « SSH n'est pas activé ».
</Aside>

## Confirmer que la surface de commandes embarquée correspond toujours à la documentation

```bash
bash scripts/capture-sitecli.sh --check \
  --site "$(terraform output -json xc_site_names | jq -r '.eastus01')" \
  --node "$(terraform output -json ce_vm_names | jq -r '.eastus01')"
```

`--check` n'écrit rien, il est donc sans danger pour la démonstration en production.
