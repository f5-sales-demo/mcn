Acquisito il 2026-07-28 da un CE di questo deployment. `sitecli/capture-manifest.json`
registra quale nodo, e `scripts/capture-sitecli.sh --check` ri-verifica la superficie
dei comandi su un CE attivo.

<Aside type="danger" title="L'API non può eseguire il debug di questo problema">
L'API di debug raggiunge il nodo attraverso il control plane di F5 Distributed Cloud, tramite
il tunnel stabilito dalla registrazione. Se la registrazione è fallita non esiste alcun tunnel,
quindi ogni comando su questo sito non è disponibile per esattamente questo tipo di guasto. Operare da
[Site Console](../../access/site-console/) se il nodo dispone ancora di un percorso di rete, e dalla
[console seriale](../../access/serial-console/) in caso contrario.
</Aside>

<Steps>

1. **Verificare di interrogare il tenant corretto.** Questo costa un solo comando ed è al primo
   posto perché sbagliarlo fa mentire ogni passaggio successivo: una flotta sana nel tenant
   che non si sta osservando è indistinguibile da una flotta che non si è mai registrata.

   ```bash
   cd terraform
   terraform output -raw xc_tenant       # the tenant this deployment belongs to
   terraform output -raw xc_env_tenant   # the tenant your shell is exporting
   ```

   ```text
   f5-sales-demo
   f5-sales-demo
   ```

   Valori non corrispondenti, oppure una credenziale che si ritiene valida che restituisce un semplice `401`? Questo è il
   sintomo di un token emesso per un altro tenant, e a questo deployment è già costato una
   ricostruzione completa ([issue 696](https://github.com/f5-sales-demo/mcn/issues/696)).

2. **Verificare cosa ne pensa il tenant.** Assente dall'elenco dei siti è un problema
   diverso da presente ma non `ONLINE`.

   ```bash
   curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
     "$XCSH_API_URL/api/config/namespaces/system/sites" | jq -r '.items[].name'
   ```

   Se il sito esiste e riporta `ONLINE`, la registrazione è riuscita e ci si trova nel
   workflow sbagliato.

3. **Individuare la registrazione del sito e il suo stato.** Un nodo può registrarsi e poi attendere
   l'approvazione, cosa che dall'esterno appare identica a un guasto.

   ```bash
   curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
     "$XCSH_API_URL/api/register/namespaces/system/registrations_by_site/<site>" \
     | jq -r '.items[] | "\(.name)  \(.object.status.current_state)  \(.object.spec.gc_spec.infra.hostname)"'
   ```

   ```text
   r-a97e20c8-b7e1-483d-bd76-34a64ff8bc78  ONLINE  f5-xc-ce-vm-01
   ```

   L'assenza di elementi significa che il nodo non si è ancora registrato — passare alla console seriale. Un elemento
   in uno stato diverso da `ONLINE` significa che si è registrato e che qualcosa dopo di ciò è fallito, il che
   costituisce un'indagine differente.

   Per esaminare l'intero namespace alla ricerca di qualsiasi elemento in attesa di approvazione, `listregistrationsbystate`
   accetta lo stato come **corpo di una `POST`**:

   ```bash
   curl -sS -X POST -H "Authorization: APIToken $XCSH_API_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"namespace":"system","state":"PENDING"}' \
     "$XCSH_API_URL/api/register/namespaces/system/listregistrationsbystate" | jq -r '.items[].name'
   ```

   Su una flotta sana questo non restituisce nulla, perché l'approvazione è automatizzata.

4. **Verificare che la VM sia effettivamente in esecuzione**, prima di presumere un guasto software.

   ```bash
   az vm list -d -g <resource-group> --query "[].{name:name,power:powerState}" -o table
   ```

   ```text
   Name            Power
   --------------  ----------
   ar-ecmp-client  VM running
   f5-xc-ce-vm-01  VM running
   f5-xc-ce-vm-02  VM running
   f5-xc-ce-vm-03  VM running
   ```

5. **Collegarsi alla console seriale.** In modalità interattiva è necessario un terminale reale; il collegamento
   in sé può invece essere automatizzato tramite websocket — vedere
   [console seriale](../../access/serial-console/).

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

   Se il collegamento viene rifiutato, verificare che la diagnostica di avvio sia abilitata sulla VM prima di concludere che il
   nodo è irraggiungibile; tale prerequisito e le sue modalità di guasto sono trattati nella pagina
   [console seriale](../../access/serial-console/).

6. **Leggere ciò che la console mostra, in questo ordine.** Prima cloud-init — un nodo il cui
   cloud-init non è mai stato completato non ha alcuna configurazione con cui registrarsi. Poi i
   tentativi di registrazione stessi, poi il DNS: se il nodo non riesce a risolvere
   `register.ves.volterra.io`, nulla a valle può funzionare.

7. **Una volta che il nodo è `ONLINE`**, verificare con [`health`](../../commands/system/health/)
   e attendersi `state: PROVISIONED`.

</Steps>

<Aside type="caution" title="Una registrazione prende il nome da un UUID, mai dal suo sito">
Le registrazioni sono denominate `r-<uuid>` e non esiste alcun endpoint che accetti un nome di sito dove è
atteso un nome di registrazione.
`GET .../registrations/<site>` restituisce `404`, che si legge come "questo sito non ha alcuna
registrazione" mentre in realtà significa "quello non è un nome di registrazione". La corrispondenza tra sito e registrazione
si ottiene solo da `registrations_by_site/<site>`, come al passaggio 3, oppure elencando le
`registrations` e confrontando `gc_spec.passport.cluster_name`.

La stessa trappola ha fatto sembrare che una flotta sana avesse zero registrazioni.
</Aside>

## Le cause più comuni

- **Si sta puntando al tenant sbagliato**, quindi una flotta che sta bene appare assente. Passaggio 1.
- cloud-init non è stato completato, quindi `/etc/vpm/config.yaml` è assente o errato.
- Il token di registrazione è scaduto, già consumato o proveniente da un altro tenant.
- Nessuna rotta in uscita verso `register.ves.volterra.io`.
- Scostamento dell'orologio abbastanza grande da invalidare i certificati — facile da escludere successivamente con
  [`chronyc-sources`](../../commands/network/chronyc-sources/), ma non raggiungibile
  finché il nodo non è online. Il banner di accesso [SSH](../../access/ssh/) riporta `NTP: Synced`
  e lo stato del resolver prima di eseguire qualsiasi comando, quando SSH è disponibile.
