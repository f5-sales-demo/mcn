Ogni Customer Edge espone la Console del sito di F5 su `https://<sli-ip>:65500`. In questo
deployment è solitamente la prima soluzione da provare.

Richiede il minimo da parte dell'utente: nessuna chiave SSH da distribuire, nessun jump host da mantenere, nessun IP pubblico sul
nodo e nessuna sostituzione della VM per abilitarla. Chi può connettersi diventa una **decisione Azure RBAC**.
E non richiede che il sito sia registrato — la trascrizione seguente è stata
acquisita mentre tutti e tre i siti riportavano `site_state: FAILED`.

Il limite è che la Console del sito risponde solo sull'indirizzo interno (SLI) del nodo,
raggiungibile solo dall'interno della VNet. Azure Bastion colma questa lacuna senza aggiungere
nient'altro alla rete.

<Aside type="note" title="Cosa viene verificato qui e cosa no">
Ogni comando e ogni output in questa pagina è stato eseguito su `f5-xc-ce-vm-01` in questo
deployment ed è riprodotto fedelmente, compresi i fallimenti.

L'unica cosa non esercitata è **l'accesso**. I passaggi si fermano alla richiesta delle credenziali,
quindi niente di quanto segue descrive come appare la console una volta effettuato l'accesso.
</Aside>

## Prima di iniziare

<Steps>

1. Accedere ad Azure e aggiungere l'estensione Bastion. Il tunneling è una funzionalità del client nativo
   e l'estensione non è installata per impostazione predefinita.

   ```bash
   az login
   az extension add --name bastion
   ```

2. Disporre del ruolo **Reader** sulla macchina virtuale CE, sulla relativa interfaccia di rete e sull'host Bastion.

3. Verificare che Bastion sia distribuito e funzionante. Lo SKU Basic non supporta né il tunneling né la
   connessione basata su IP, quindi `Standard` e `True` sono entrambi valori determinanti.

   ```bash
   az network bastion list -g rg-mcn-ce-ha-rmordasiewicz \
     --query "[].{name:name, sku:sku.name, tunneling:enableTunneling}" -o table
   ```

   ```text
   Name               Sku       Tunneling
   -----------------  --------  -----------
   ce-ha-lab-bastion  Standard  True
   ```

</Steps>

## Aprire il tunnel

Utilizzare i valori ottenuti da `terraform output` anziché digitarli manualmente — l'ID risorsa non è
qualcosa da assemblare a mano.

<Steps>

1. Leggere il nome dell'host Bastion, il gruppo di risorse e l'ID risorsa VM del CE di destinazione.

   ```bash
   cd terraform
   BASTION=$(terraform output -raw bastion_name)
   RG=$(terraform output -raw resource_group_name)
   VM_ID=$(terraform output -json ce_vm_ids | jq -r '.eastus01')
   ```

   ```text
   ce-ha-lab-bastion
   rg-mcn-ce-ha-rmordasiewicz
   /subscriptions/…/providers/Microsoft.Compute/virtualMachines/f5-xc-ce-vm-01
   ```

   <Aside type="caution" title="La mappa è indicizzata per sito, non per nome VM">
   Le chiavi di `ce_vm_ids` sono `eastus01`, `eastus02`, `eastus03` — **non** i nomi delle VM. Un
   filtro come `jq -r '."f5-xc-ce-vm-01"'` restituisce `null`, e il tunnel fallisce quindi con un
   ID risorsa vuoto. Elencarle in caso di dubbio:

   ```bash
   terraform output -json ce_vm_ids | jq -r 'keys | join(", ")'
   ```

   ```text
   eastus01, eastus02, eastus03
   ```
   </Aside>

2. Avviare il tunnel. Mantiene la porta aperta finché non viene interrotto, quindi eseguirlo in background o usare un
   secondo terminale.

   ```bash
   az network bastion tunnel \
     --name "$BASTION" \
     --resource-group "$RG" \
     --target-resource-id "$VM_ID" \
     --resource-port 65500 \
     --port 65500 &
   ```

   ```text
   WARNING: Opening tunnel on port: 65500
   WARNING: Tunnel is ready, connect on port 65500
   WARNING: Ctrl + C to close
   ```

   Tutte e tre le righe sono precedute da `WARNING:`. È l'interfaccia a riga di comando di Azure che scrive i progressi su
   stderr, non un problema. Attendere `Tunnel is ready` prima di connettersi.

3. Verificare che il listener sia locale, sul loopback:

   ```bash
   lsof -nP -iTCP:65500 -sTCP:LISTEN
   ```

   ```text
   COMMAND   PID  USER  FD  TYPE  DEVICE  SIZE/OFF  NODE  NAME
   Python  41648  you   7u  IPv4  …            0t0   TCP  127.0.0.1:65500 (LISTEN)
   ```

4. Aprire la console. Il tunnel la rende locale, quindi l'indirizzo è `localhost` — non
   l'indirizzo del nodo.

   ```bash
   open https://localhost:65500/          # macOS
   xdg-open https://localhost:65500/      # Linux
   ```

5. Interrompere il tunnel al termine — `Ctrl-C`, o `kill %1` se è stato avviato in background.
   Lasciarlo aperto mantiene occupata la porta locale 65500 e la sessione Bastion.

</Steps>

## Cosa si vedrà

**Una finestra di dialogo per le credenziali, non una pagina di login.** La console utilizza l'autenticazione HTTP Basic, quindi
il browser mostra il proprio prompt per nome utente e password. Non c'è alcun modulo da visualizzare:

```bash
curl -skI https://localhost:65500/
```

```text
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Basic realm="Volterra Site Console"
Content-Length: 0
```

Un `401` con quel realm indica che la console funziona correttamente. È la risposta prevista per una
richiesta non autenticata.

**Un avviso relativo al certificato, per tre ragioni contemporaneamente.** Verificando il certificato direttamente:

```bash
openssl s_client -connect localhost:65500 -servername localhost </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
```

```text
subject=C=US, ST=California, L=Santa Clara, O=Volterra, OU=Volterra Edge Services, CN=site-local.volterra.io
issuer=C=US, ST=California, L=Santa Clara, O=Volterra, OU=Volterra Edge Services, CN=site-local.volterra.io
notBefore=Oct 25 04:51:31 2024 GMT
notAfter=Oct 25 04:51:31 2025 GMT
```

Il soggetto coincide con l'emittente, quindi è autofirmato. Il nome è `site-local.volterra.io` mentre
ci si sta connettendo a `localhost`, quindi non corrisponderà. E nella build su cui gira questo deployment,
**il certificato è scaduto il 25 ottobre 2025** — è fornito dall'appliance e niente
in questo repository lo rinnova.

Aspettarsi un avviso esplicito del browser, ogni volta. La riga del soggetto sopra è la
parte utile: è il modo per confermare di aver raggiunto l'appliance anziché qualcos'altro
in ascolto sulla porta locale 65500.

## Le credenziali di amministratore

Accedere come `admin`. **Questa documentazione non pubblica la password, e non dovrebbe farlo.**

Un Customer Edge appena uscito di fabbrica viene fornito con il valore predefinito pubblicato da F5, che F5 richiede di modificare. Trattare la modifica come parte del deploy di un nodo piuttosto che come un'attività di hardening da fare in seguito.
Due motivi per cui questo è più importante di quanto possa sembrare:

- Questa documentazione è pubblica. Pubblicare la password attuale della console dell'intera flotta trasformerebbe
  il ruolo "Reader su Bastion" in accesso completo all'appliance per chiunque legga la pagina.
- Una password pubblicata nella documentazione è sbagliata nel momento in cui qualcuno la ruota, e
  sbagliata nel modo più fuorviante — il lettore conclude che il proprio accesso è interrotto anziché
  che la pagina sia obsoleta.

Ottenere la password da dove il team conserva i segreti operativi. Se la risposta è
"è ancora quella predefinita di fabbrica", cambiarla prima di fare qualsiasi altra cosa.

<Aside type="caution" title="L'impostazione della password tramite Terraform non è verificata">
`admin_user_credentials.admin_password` sull'oggetto sito sembra il modo dichiarativo per
impostare questo valore. **Non è stato confermato** che raggiunga la Console del sito su questa build, quindi non
si assuma che lo faccia.

Non leggere la [pagina SSH](../ssh/) come prova in un senso o nell'altro. La conclusione che
`admin_password` "non ha cambiato nulla" è stata misurata rispetto all'autenticazione SSH, che `vpm`
salta completamente per l'utente `admin`. Questo non dice nulla sulla console.
</Aside>

## Perché il tunnel deve puntare all'ID risorsa

`--target-resource-id` è obbligatorio. Puntare invece all'indirizzo del nodo viene rifiutato:

```bash
az network bastion tunnel --name "$BASTION" -g "$RG" \
  --target-ip-address 10.0.3.5 --resource-port 65500 --port 65501
```

```text
ERROR: Custom ports are not allowed. Allowed ports for Tunnel with IP connect is 22, 3389.
```

Il motivo **non** è che la connessione basata su IP sia disabilitata — su questo Bastion
`ip_connect_enabled` è `true`. Microsoft non supporta porte personalizzate tramite connessioni native
basate su IP, indipendentemente da tale impostazione
([Documentazione di Azure](https://learn.microsoft.com/azure/bastion/connect-ip-address)), e 65500 è
una porta personalizzata. Esaminare la configurazione Bastion qui non porta a nulla; utilizzare l'ID risorsa.

## Quando non funziona

| Sintomo | Causa | Soluzione |
| --- | --- | --- |
| `ERROR: Custom ports are not allowed. Allowed ports for Tunnel with IP connect is 22, 3389.` | Utilizzato `--target-ip-address` | Usare `--target-resource-id` |
| `ERROR: Defined port is currently unavailable` | Un altro tunnel occupa già quella porta locale | Interrompere l'altro tunnel, o passare un `--port` diverso; `--resource-port` rimane 65500 |
| Il tunnel parte ma l'ID risorsa è vuoto | Il filtro `jq` ha usato il nome della VM invece della chiave del sito | Usare la chiave `eastus01`/`02`/`03` |
| `401 Unauthorized`, realm `Volterra Site Console` | Non è un errore — richiesta non autenticata | Fornire le credenziali `admin` |
| Il browser rifiuta il certificato | Autofirmato, nome non corrispondente e scaduto da ottobre 2025 | Previsto; verificare che il soggetto sia `CN=site-local.volterra.io` e procedere |

<Aside type="note" title="Gli errori di autorizzazione non sono stati riprodotti">
Un RBAC insufficiente è l'altro modo ovvio in cui questo fallisce, ma riprodurlo significherebbe
rimuovere assegnazioni di ruolo da un deployment condiviso, quindi non è documentato qui con un
errore verbatim. Se il tunnel fallisce all'avvio con un errore di autorizzazione, verificare il ruolo Reader su
tutti e tre: la VM, la relativa NIC e l'host Bastion.
</Aside>
