Azure Serial Console si collega alla porta seriale emulata del nodo tramite la
Piattaforma Azure. Non attraversa il piano di controllo di F5 Distributed Cloud, il piano
dati del nodo o alcun percorso di rete controllato dal nodo — ed è esattamente per
questo motivo che funziona quando nient'altro funziona.

Ricorrere a essa quando un CE **non si è mai avviato**: la registrazione è fallita, il
sito è assente dal tenant oppure il nodo è attivo ma non dispone di un percorso in uscita.
In tutti questi casi, l'[API di debug](../debug-api/) non dispone di un tunnel attraverso
cui fare il relay, e SSH è disabilitato sul nodo così come viene fornito.

## Prerequisito: diagnostica di avvio

Azure richiede che la diagnostica di avvio sia abilitata sulla VM prima di poter collegare
una console seriale. Questa funzionalità è abilitata da `terraform/modules/ce-node`:

```hcl
boot_diagnostics {}
```

Un blocco vuoto seleziona lo storage gestito da Azure, quindi non vi è alcun account di
storage diagnostico, policy del ciclo di vita o chiave di accesso da gestire. Verificarlo
su un nodo:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="L'abilitazione non è retroattiva">
La diagnostica di avvio acquisisce il log seriale **al momento del boot**. Abilitarla
per una VM già in esecuzione non produce un log per il boot già avvenuto, quindi
`az vm boot-diagnostics get-boot-log` risponde:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

Questo è il comportamento atteso, non un errore. Un log di avvio sarà disponibile dopo
il successivo riavvio del nodo. Il collegamento in tempo reale alla console, tuttavia,
funziona immediatamente — non dipende dal log.
</Aside>

## Verifica della disponibilità senza un terminale

Il collegamento richiede una sessione interattiva, ma è possibile verificare se il
collegamento *avrebbe luogo* con due sole chiamate API. Entrambe sono utili in un
controllo di integrità.

Il servizio deve essere abilitato per la sottoscrizione — un amministratore può
disabilitarlo a livello di tenant:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

Quindi richiedere una connessione alla porta seriale di un nodo specifico:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

Un `connectionString` che inizia con `wss://` — in questo deployment
`eastus.gateway.serialconsole.azure.com` — indica che la console è collegabile in
questo momento. Prima che la diagnostica di avvio fosse abilitata, questa chiamata non
aveva nulla a cui collegarsi.

<Aside type="danger" title="Quella stringa di connessione è una credenziale">
Si tratta di un token bearer di breve durata incorporato in un URL. Non registrarlo,
incollarlo in un ticket o includerlo in un commit. Stampare solo l'host quando si
dimostra che la chiamata ha avuto successo.
</Aside>

## Collegamento

<Steps>

1. Installare l'estensione una volta sola:

   ```bash
   az extension add --name serial-console
   ```

2. Collegarsi:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. Si approda al prompt di login del nodo, non a una shell. Questo è il Site CLI, che
   richiede credenziali configurate sul nodo — la password di amministratore del
   provisioning, oppure una impostata tramite l'endpoint di modifica della password.
   La console seriale dimostra che il *canale* funziona; non bypassa l'autenticazione.

</Steps>

Acquisito da `f5-xc-ce-vm-01`, con omissioni nella parte centrale dove l'output
dell'unità systemd non aggiunge nulla di rilevante:

```text file=../../../_data/serial-console-boot.txt
```

Quattro elementi in quella trascrizione meritano attenzione, poiché rispondono a
domande a cui l'API di debug non può rispondere:

- **cloud-init completato** — `Datasource DataSourceAzure`, terminato a 22,37 secondi.
  Un nodo che non si registra mai di solito ha avuto un errore qui, ed è qui che lo si
  vede.
- **Entrambi i runtime container sono stati avviati.** `Container Runtime Interface for OCI (CRI-O)`
  e `Docker Application Container Engine` sono entrambi `[ OK ]`, il che rappresenta
  la prova al momento del boot del comportamento dual-runtime che sorprende le persone in
  [crictl](../../commands/system/crictl/) e [docker](../../commands/system/docker/).
- **`VP Manager image load` e `Argo Watch service`** — avvio di `vpm` e Argo.
- **Il prompt è quello del nodo**, dietro il suo banner di audit. La console seriale
  fornisce un prompt di login, non una sessione.

<Aside type="caution" title="Il collegamento interattivo richiede un terminale reale — ma può essere automatizzato">
`az serial-console connect` pone il terminale in modalità raw, quindi non può essere
eseguito da una pipeline o in qualsiasi contesto privo di TTY. Il collegamento fallisce
lato client, prima di contattare Azure:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

Quel traceback riguarda la gestione del terminale, non un'interruzione della console
seriale.

Il collegamento in sé, tuttavia, **è** automatizzabile — gestire il websocket
direttamente anziché tramite la CLI. La trascrizione precedente è stata acquisita in
questo modo, senza TTY. Si veda `scripts/serial_console_capture.py`, che rappresenta
il metodo per raccogliere prove di avvio da un nodo che non è riuscito a registrarsi
senza che un operatore umano sia presente al terminale.
</Aside>

<Aside type="caution" title="Prevedere di riprovare: il gateway rifiuta circa ogni altro tentativo">
Il primo frame del gateway è una challenge, non un output, e il client vi risponde con
un token bearer. Anche quando ciò viene eseguito correttamente, il socket spesso si
chiude immediatamente:

```
[close] code=1011 reason=Connection not trusted
```

Misurato su tentativi ripetuti su tre nodi, questo comportamento alterna: un rifiuto è
seguito da un successo sullo stesso nodo. Ciò è coerente con una sessione precedente
ancora attiva, e il tentativo rifiutato la cancella.

**Non si tratta di un problema di credenziali**, nonostante il messaggio. In genere è
sufficiente riprovare, motivo per cui `scripts/serial_console_capture.py` effettua
nuovi tentativi per impostazione predefinita.

Utilizzare comunque un singolo token sia per la richiesta di sessione sia per la
challenge, in modo corrispondente all'estensione `az`. Questa è la prassi corretta, ma
non è la causa di questo comportamento.
</Aside>

## Cosa si può vedere qui che l'API non può mostrare

- **cloud-init** in esecuzione, in errore o mai avviato — la causa abituale di un nodo
  che non si registra mai.
- **Tentativi di registrazione** verso `register.ves.volterra.io`, inclusi eventuali
  errori di configurazione o un token rifiutato dal tenant.
- **Messaggi del kernel e di avvio** prodotti prima che qualsiasi agente fosse in
  esecuzione.
- Il nodo quando **non dispone di un percorso di rete funzionante**, condizione che
  vanifica ogni altro percorso di accesso.

Per un nodo che *è* `ONLINE`, preferire l'API di debug: è automatizzabile, produce
prove che è possibile rieseguire e non occupa la singola porta seriale.
