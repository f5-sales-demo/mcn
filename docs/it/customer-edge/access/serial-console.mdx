La console seriale di Azure si collega alla porta seriale emulata del nodo attraverso la
Piattaforma Azure. Non attraversa il piano di controllo F5 Distributed Cloud, il piano
dati del nodo, né alcun percorso di rete controllato dal nodo — il che è esattamente il
motivo per cui funziona quando tutto il resto non funziona.

Utilizzarla quando un CE **non si è mai avviato**: la registrazione è fallita, il sito è
assente dal tenant, oppure il nodo è attivo ma non ha un percorso di uscita. In tutti
questi casi l'[API di debug](../debug-api/) non dispone di un tunnel attraverso cui
instradare. [SSH](../ssh/) sopravvive a una registrazione fallita, ma solo se la chiave
era già stata scritta al primo avvio e si riesce a raggiungere l'indirizzo interno del
nodo dall'interno della VNet — nessuna delle due condizioni è vera per un nodo che si
incontra per la prima volta.

## Prerequisito: diagnostica di avvio

Azure richiede la diagnostica di avvio sulla VM prima di poter collegare una console
seriale. Questo è abilitato da `terraform/modules/ce-node`:

```hcl
boot_diagnostics {}
```

Un blocco vuoto seleziona l'archiviazione gestita da Azure, quindi non vi è alcun
account di archiviazione per la diagnostica, nessuna policy del ciclo di vita né chiave
di accesso da gestire. Verificarlo su un nodo:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="L'abilitazione non è retroattiva">
La diagnostica di avvio acquisisce il log seriale **all'avvio**. Attivarla per una VM
già in esecuzione non produce un log per l'avvio già avvenuto, quindi
`az vm boot-diagnostics get-boot-log` risponde:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

Questo è previsto, non un'anomalia. Un log di avvio sarà disponibile dopo il prossimo
riavvio del nodo. Il collegamento diretto alla console, tuttavia, funziona
immediatamente — non dipende dal log.
</Aside>

## Verifica della disponibilità senza un terminale

Il collegamento richiede una sessione interattiva, ma verificare se il collegamento
*avverrebbe* richiede solo due chiamate API. Entrambe sono utili in un controllo di
integrità.

Il servizio deve essere abilitato per la sottoscrizione — un amministratore può
disabilitarlo a livello di tenant:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

Quindi richiedere una connessione alla porta seriale di un nodo specifico:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

Una `connectionString` che inizia con `wss://` — in questo deployment
`eastus.gateway.serialconsole.azure.com` — significa che la console è collegabile in
questo momento. Prima che la diagnostica di avvio fosse abilitata, questa chiamata non
aveva nulla a cui connettersi.

<Aside type="danger" title="Quella stringa di connessione è una credenziale">
È un bearer token di breve durata incorporato in un URL. Non registrarla nei log, non
incollarla in un ticket né includerla in un commit. Stampare solo l'host quando si
dimostra che la chiamata ha funzionato.
</Aside>

## Collegamento

<Steps>

1. Installare l'estensione una volta:

   ```bash
   az extension add --name serial-console
   ```

2. Collegarsi:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. Si atterra al prompt di accesso del nodo, non a una shell. Questa è la Site CLI e
   richiede credenziali configurate sul nodo — la password amministratore dal
   provisioning, oppure una impostata tramite l'endpoint di cambio password. La console
   seriale dimostra che il *canale* funziona; non aggira l'autenticazione.

</Steps>

Acquisito da `f5-xc-ce-vm-01`, omesso nella parte centrale dove l'output delle unità
systemd non aggiunge informazioni:

```text file=../../../_data/serial-console-boot.txt
```

Quattro elementi in questa trascrizione meritano attenzione, perché rispondono a domande
a cui l'API di debug non può rispondere:

- **cloud-init completato** — `Datasource DataSourceAzure`, terminato a 22,37 secondi.
  Un nodo che non si registra mai di solito ha avuto un errore qui, ed è qui che lo si
  rileva.
- **Entrambi i runtime dei container avviati.** `Container Runtime Interface for OCI (CRI-O)`
  e `Docker Application Container Engine` sono entrambi `[ OK ]`, il che costituisce la
  prova all'avvio del comportamento a doppio runtime che sorprende le persone in
  [crictl](../../commands/system/crictl/) e [docker](../../commands/system/docker/).
- **`VP Manager image load` e `Argo Watch service`** — `vpm` e Argo che si avviano.
- **Il prompt è quello del nodo**, dietro il suo banner di audit. La console seriale
  fornisce un prompt di accesso, non una sessione.

<Aside type="caution" title="Il collegamento interattivo richiede un terminale reale — ma può essere automatizzato">
`az serial-console connect` mette il terminale in modalità raw, quindi non può essere
eseguito da una pipeline o in qualsiasi contesto senza TTY. Si interrompe lato client,
prima di contattare Azure:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

Questo traceback riguarda la gestione del terminale, non un'interruzione della console
seriale.

Il collegamento stesso, tuttavia, **è** automatizzabile — guidare il websocket
direttamente invece che tramite la CLI. La trascrizione sopra è stata acquisita in quel
modo, senza TTY. Vedere `scripts/serial_console_capture.py`, che è il modo per
raccogliere evidenze di avvio da un nodo che non si è registrato senza che un operatore
sia presente al terminale.
</Aside>

<Aside type="caution" title="Aspettarsi di riprovare: il gateway rifiuta circa un tentativo su due">
Il primo frame del gateway è una sfida, non output, e il client risponde con un bearer
token. Anche quando questo viene eseguito correttamente, il socket spesso si chiude
immediatamente:

```
[close] code=1011 reason=Connection not trusted
```

Comportamento osservato: riesce in modo intermittente, e con un utilizzo prolungato
ogni nodo nel gruppo di risorse rifiuta la connessione — inclusi nodi che funzionavano
minuti prima. `scripts/serial_console_capture.py` ritenta per impostazione predefinita
perché riprovare spesso funziona.

**La causa non è stata stabilita.** Ciò che è stato escluso, poiché ciascuno è
un'ipotesi plausibile che fa perdere tempo:

| Non questo | Come confermarlo |
| --- | --- |
| Throttling ARM/compute | Restituisce HTTP `429` sulle chiamate ARM. Qui si tratta di una chiusura websocket su un canale dati separato. |
| Intercettazione TLS da parte di un proxy | `openssl s_client -connect <region>.gateway.serialconsole.azure.com:443 \| openssl x509 -noout -issuer`. Un issuer `O=Microsoft Corporation` autentico lo esclude; un vendor proxy come issuer lo conferma, e la soluzione è inserire `*.serialconsole.azure.com` nella lista di autorizzazione. |
| Diagnostica di avvio disabilitata | `az vm show -g <rg> -n <vm> --query diagnosticsProfile` che riporta `enabled: true`. |
| Mancata corrispondenza del token tra grant e sfida | Utilizzare un solo token per entrambi è la pratica corretta, ma non impedisce la chiusura. |

Ciò che *è* documentato come comportamento di Azure: **una sola sessione di console
seriale per VM, e una seconda richiesta riuscita espelle la prima.** L'utente espulso
viene disconnesso ma non scollegato, quindi la sessione shell sopravvive. Due persone
che eseguono il debug sullo stesso nodo si displaceranno ripetutamente.

Per il lavoro in blocco preferire l'[API di debug](../debug-api/) o [SSH](../ssh/),
nessuno dei quali ha questi limiti. SSH in particolare non ha limite di incolla né
restrizione a sessione singola, quindi è la scelta migliore ogni volta che il nodo è
raggiungibile dall'interno della VNet.
</Aside>

<Aside type="caution" title="Il limite di incolla è di 2.048 caratteri">
Azure limita la lunghezza del testo incollato nella console seriale a 2.048 caratteri,
per evitare di sovraccaricare la porta seriale. L'invio di un comando lungo — o di un
gruppo di comandi in un'unica scrittura — fallisce in un modo che appare come un blocco
o un throttling piuttosto che come un limite di lunghezza.

Inviare i comandi singolarmente. Questo è un vero vincolo per qualsiasi raccolta in
blocco tramite console seriale, e un altro motivo per preferire l'[API di
debug](../debug-api/) per quel tipo di lavoro.
</Aside>

## Cosa si può vedere qui che l'API non può mostrare

- **cloud-init** in esecuzione, in errore o mai avviato — la causa abituale di un nodo
  che non si registra mai.
- **Tentativi di registrazione** verso `register.ves.volterra.io`, incluso un errore di
  configurazione o un token rifiutato dal tenant.
- **Messaggi del kernel e di avvio** da prima che qualsiasi agente fosse in esecuzione.
- Il nodo quando **non dispone di un percorso di rete funzionante**, il che vanifica
  ogni altro percorso.

Per un nodo che *è* `ONLINE`, preferire l'API di debug: è automatizzabile, produce
evidenze che possono essere rieseguite e non occupa la singola porta seriale.
