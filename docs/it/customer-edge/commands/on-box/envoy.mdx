Acquisito il 28-07-2026 da un CE di questo deployment. Si tratta di comandi eseguiti sul
dispositivo, quindi passano attraverso la Site CLI anziché dall'API di debug;
`sitecli/exec-catalog.json` registra la superficie e `sitecli/capture-manifest.json` registra
quale nodo.

Envoy termina e inoltra il traffico applicativo sul Customer Edge. Questi quattro comandi
interrogano la sua interfaccia di amministrazione e nessuno di essi è disponibile sull'
[API di debug](../../../access/debug-api/).

<Aside type="note" title="Ognuno di questi inizia con un indicatore di avanzamento di curl">
Sono wrapper `curl` attorno all'endpoint di amministrazione di Envoy, invocati senza `-s`, quindi le prime
due o tre righe di ogni acquisizione qui sotto sono l'avanzamento del trasferimento di curl scritto su stderr:

```text
  % Total    % Received % Xferd  Average Speed   Time    Time     Time  Current
                                 Dload  Upload   Total   Spent    Left  Speed
  0     0    0     0 …
```

Non è output di Envoy e non è un errore. È anche utile: il conteggio dei byte `% Received`
indica se Envoy ha restituito qualcosa, il che distingue "nessun listener
configurato" da "l'interfaccia di amministrazione non ha risposto".
</Aside>

## `envoy-listeners`

Ogni listener installato da Envoy, nel formato `name:address:port`.

```bash
execcli envoy-listeners
```

```text file=../../../../_data/sitecli-envoy-listeners.txt
```

**Cosa cercare.** In questo deployment il listener riporta `10.250.0.10:80` — il VIP che il
CE annuncia in BGP. Quella singola riga collega tre livelli: se
[`show-ip-bgp-summary`](../../network/bgp/) mostra il prefisso come annunciato ma questo
listener è assente, la rotta sta attirando traffico verso un nodo che non lo servirà, ovvero
la peggiore modalità di guasto in un set ECMP perché il traffico viene ripartito in un buco nero.

L'indirizzo finale `[fe80:…]:80` è l'indirizzo link-local dell'interfaccia a cui il listener è
associato.

**Cosa non indica.** Nulla sullo stato di salute degli upstream — un listener esiste
indipendentemente dal fatto che qualcosa dietro di esso sia raggiungibile. Per questo si usa `envoy-clusters`.

## `envoy-clusters`

Ogni cluster, con i relativi limiti di connessioni e richieste per priorità.

```bash
execcli envoy-clusters
```

```text file=../../../../_data/sitecli-envoy-clusters.txt
```

**Cosa cercare.** Le righe hanno il formato `cluster::scope::key::value`. La voce `observability_name`
identifica ogni cluster, e la terna `default_priority::max_connections`,
`max_pending_requests` e `max_requests` è dove compaiono i limiti sulle richieste — un cluster
bloccato al suo `max_pending_requests` è limitato dalla configurazione anziché dall'upstream.

## `envoy-config-dump`

La configurazione completa di Envoy in formato JSON. Voluminosa: 126 KB su un nodo demo altrimenti inattivo.

```bash
execcli envoy-config-dump
```

```text file=../../../../_data/sitecli-envoy-config-dump.txt
```

**Cosa cercare.** L'array `configs` di primo livello contiene un oggetto per ogni tipo di configurazione —
bootstrap, cluster, listener, route, secret. Ricorrete a questo comando quando un listener o un cluster
esiste ma si comporta in modo inatteso, ed effettuate una ricerca nel contenuto anziché leggerlo integralmente.

## `envoy-hc-config-dump`

Nello specifico, la configurazione dei controlli di integrità.

```bash
execcli envoy-hc-config-dump
```

```text file=../../../../_data/sitecli-envoy-hc-config-dump.txt
```

**Cosa cercare.** In questo deployment restituisce un **singolo byte** — visibile come `100 1`
nell'indicatore di curl — il che significa che non è installata alcuna configurazione di controllo dell'integrità. Questo è lo
stato previsto per un CE senza pool di origine con controlli di integrità, ed è utile riconoscerlo: un risultato
vuoto in questo caso non è una query fallita.
