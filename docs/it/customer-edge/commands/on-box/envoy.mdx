Envoy termina e fa da proxy per il traffico applicativo sul Customer Edge. Questi quattro comandi
interrogano la sua interfaccia di amministrazione, e nessuno di essi è presente nella
[debug API](../../../access/debug-api/).

<Aside type="note" title="Ognuno di questi inizia con un indicatore di avanzamento curl">
Sono wrapper `curl` attorno all'endpoint di amministrazione di Envoy, invocati senza `-s`, quindi le prime
due o tre righe di ogni acquisizione sottostante sono l'avanzamento del trasferimento di curl scritto su stderr:

```text
  % Total    % Received % Xferd  Average Speed   Time    Time     Time  Current
                                 Dload  Upload   Total   Spent    Left  Speed
  0     0    0     0 …
```

Non si tratta di output di Envoy né di un errore. È anche utile: il conteggio dei byte `% Received`
indica se Envoy ha restituito qualcosa, il che distingue "nessun listener configurato"
da "l'interfaccia di amministrazione non ha risposto".
</Aside>

## `envoy-listeners`

Ogni listener installato da Envoy, nel formato `nome:indirizzo:porta`.

```bash
execcli envoy-listeners
```

```text file=../../../../_data/sitecli-envoy-listeners.txt
```

**Cosa cercare.** In questo deployment il listener riporta `10.250.0.10:80` — il VIP che il
CE annuncia tramite BGP. Quella singola riga collega tre livelli insieme: se
[`show-ip-bgp-summary`](../../network/bgp/) mostra il prefisso annunciato ma questo
listener è assente, la route viene attratta verso un nodo che non la servirà, il che rappresenta
la modalità di guasto peggiore in un set ECMP, poiché il traffico viene distribuito verso un buco nero.

Il `[fe80:…]:80` finale è l'indirizzo link-local dell'interfaccia a cui è associato il listener.

**Cosa non indica.** Nulla sullo stato upstream — un listener esiste indipendentemente dal fatto
che qualcosa dietro di esso sia raggiungibile. Utilizzare `envoy-clusters` per questo scopo.

## `envoy-clusters`

Ogni cluster, con i relativi limiti di connessione e richiesta per priorità.

```bash
execcli envoy-clusters
```

```text file=../../../../_data/sitecli-envoy-clusters.txt
```

**Cosa cercare.** Le righe hanno il formato `cluster::scope::chiave::valore`. La voce `observability_name`
identifica ogni cluster, e la tripletta `default_priority::max_connections`,
`max_pending_requests` e `max_requests` è dove compaiono i limiti delle richieste — un cluster
bloccato al suo `max_pending_requests` viene limitato dalla configurazione piuttosto che dall'upstream.

## `envoy-config-dump`

La configurazione completa di Envoy in formato JSON. Di grandi dimensioni: 126 KB su un nodo demo altrimenti inattivo.

```bash
execcli envoy-config-dump
```

```text file=../../../../_data/sitecli-envoy-config-dump.txt
```

**Cosa cercare.** L'array `configs` di primo livello contiene un oggetto per ogni tipo di configurazione —
bootstrap, cluster, listener, route, secret. Si ricorre a questo quando un listener o un cluster
esiste ma si comporta in modo inatteso; è preferibile effettuare ricerche piuttosto che leggerlo integralmente.

## `envoy-hc-config-dump`

La configurazione degli health check in modo specifico.

```bash
execcli envoy-hc-config-dump
```

```text file=../../../../_data/sitecli-envoy-hc-config-dump.txt
```

**Cosa cercare.** In questo deployment restituisce un **singolo byte** — visibile come `100 1`
nell'indicatore curl — il che significa che non è installata alcuna configurazione di health check. Questo è lo stato
previsto per un CE senza pool di origine sottoposti a health check, ed è importante riconoscerlo:
un risultato vuoto qui non indica una query fallita.
