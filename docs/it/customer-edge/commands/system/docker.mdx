Docker esegue i servizi della piattaforma. I carichi di lavoro Kubernetes si trovano in
[CRI-O](../crictl/).

## `docker-ps`

```bash
{"command":["docker-ps"]}
```

```text file=../../../../_data/sitecli-docker-ps.txt
```

<Aside type="tip" title="Tre container è l'elenco completo, non un nodo difettoso">
`vpm`, `argo_watch` e `site-console`. Poiché la maggior parte del nodo viene eseguita in CRI-O, un
`docker-ps` breve sembra un errore se ci si aspettano carichi di lavoro Kubernetes
qui. Non lo è — questo è il set completo di container Docker su un CE funzionante, e
la presenza di `vpm` con stato `Up` è la riga più importante della pagina.
</Aside>

## `docker-images`

```bash
{"command":["docker-images"]}
```

```text file=../../../../_data/sitecli-docker-images.txt
```

I tag delle immagini identificano la versione della piattaforma effettivamente in esecuzione sul nodo, che vale
la pena confrontare con la build del software riportata da [`health`](../health/).

## `docker-inspect`

```bash
{"command":["docker-inspect","<container-id-or-name"]}
```

```text file=../../../../_data/sitecli-docker-inspect.txt
```

Accetta sia un nome che un id, quindi `docker-inspect vpm` funziona ed è stabile tra
un riavvio e l'altro. JSON completo: mount, variabili d'ambiente, policy di riavvio e lo stato di uscita.

## `docker-logs`

```bash
{"command":["docker-logs","<container-id-or-name>"]}
```

```text file=../../../../_data/sitecli-docker-logs.txt
```

`docker-logs vpm` è il percorso più rapido per gli errori di registrazione. Per le stesse
informazioni con timestamp e attraverso i riavvii, utilizzare invece
[`journalctl`](../journalctl/).

## `docker-prune`

```bash
execcli docker-prune
```

Rimuove ogni oggetto Docker inutilizzato — container fermati, reti inutilizzate, immagini dangling e
cache di build.

**Solo dal box.** `docker-prune` non è disponibile nell'API di debug; richiede
[`execcli`](../../on-box/).

<Aside type="danger" title="Distruttivo e non acquisito qui">
Questo elimina lo stato. Si trova nella lista dei rifiuti dell'harness di raccolta e non è mai stato eseguito, quindi questa
pagina lo documenta dai metadati del catalogo dell'appliance piuttosto che mostrarne l'output.

La cautela specifica per CE: questo nodo esegue **due** runtime di container. `docker-prune` tocca
solo il lato Docker — `vpm`, `argo_watch` e `site-console` — e non può raggiungere i
carichi di lavoro Kubernetes in [CRI-O](../crictl/). Il recupero di spazio sul lato CRI-O è un
comando diverso, `systemctl-start-crio-prune`, che non è presente in questa build.
</Aside>
