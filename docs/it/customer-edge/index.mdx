Un Customer Edge (CE) è il nodo F5 Distributed Cloud che questo repository esegue il provisioning in
Azure — `terraform/modules/ce-node`, creato a partire dall'immagine marketplace
`volterraedgeservices/volterra-node`.

Esegue il piano dati (Argo), il piano di controllo (Vega), un proxy Envoy, uno stack
Kubernetes e `vpm`, l'agente che registra il nodo e gestisce tutto il resto su
di esso.

Quando un CE si comporta in modo anomalo, la Site CLI è lo strumento da utilizzare. La prima decisione è quale
percorso di accesso si applica, e scegliere quello sbagliato fa perdere tempo in un modo che sembra un
nodo difettoso.

## Due percorsi di accesso, e non sono intercambiabili

<CardGrid>
  <LinkCard
    title="Debug API"
    description="For a node that is <code>ONLINE</code>. Scriptable, read-only, and covers 34 commands."
    href="./access/debug-api/"
  />
  <LinkCard
    title="Serial console"
    description="For a node that never registered. The only route when the API cannot answer."
    href="./access/serial-console/"
  />
</CardGrid>

La debug API raggiunge il nodo **attraverso il piano di controllo di F5 Distributed Cloud**.
Questa è la ragione per cui la distinzione è importante: l'API può rispondere solo una volta che il nodo si è
registrato e riporta `ONLINE`.

Un nodo che non è riuscito a registrarsi — cloud-init non valido, token scaduto, nessuna route verso
`register.ves.volterra.io` — è esattamente il caso in cui si ha bisogno della diagnostica, e
esattamente il caso in cui l'API non può rispondere.

[SSH](./access/ssh/) è la terza opzione, e l'unica che raggiunge l'intera superficie di
comandi dell'appliance — la debug API espone 34 comandi e il nodo stesso ne offre molti
di più. Due cose la limitano. `sshd` risponde solo sull'indirizzo interno (SLI) del nodo,
quindi richiede un host all'interno della VNet; e la chiave viene scritta da cloud-init al primo avvio,
poiché il campo `ssh_key` sull'oggetto site è inattivo — `vpm` ignora l'utente `admin` e
non lo applica mai. L'abilitazione su nodi in esecuzione li sostituisce quindi.

Quindi: se il sito è `ONLINE` e 34 comandi sono sufficienti, utilizzare la debug API. Se si ha bisogno della
restante superficie e si può raggiungere la VNet, utilizzare SSH. Se la registrazione è ciò che non funziona,
la console seriale è l'unico modo per accedere.

<Aside type="caution" title="Verificare prima lo stato del sito">
Una sola richiesta indica su quale percorso ci si trova:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/config/namespaces/system/sites/<site>" \
  | jq -r '.spec.site_state'
```

`ONLINE` significa che la debug API funzionerà. Qualsiasi altro valore — o un sito che non
esiste — significa console seriale.
</Aside>

## Regole di sicurezza

Queste si applicano a ogni comando su ogni pagina sottostante.

- **Solo lettura, salvo certezza assoluta.** La superficie dei comandi è suddivisa in due
  livelli di privilegi, e il livello `Exec` o muta il nodo o legge un marcatore di stato.
  Nessuna di queste pagine esegue un comando `Exec`, e nemmeno il harness di acquisizione.
- **Non assumere mai che un comando sia sicuro in base al nome.** `ip-link-set` sembra una
  query e disabilita un'interfaccia. `systemctl-restart-crio` riavvia il
  runtime del container sotto un piano dati attivo.
- **Preferire il comando più specifico che risponda alla domanda.** `health` e
  `diagnosis` riassumono il nodo in modo economico; `flow-l` scarica una tabella di flusso
  da 629.760 voci.
- **Un CE gestisce traffico attivo.** Questi sono ambienti demo condivisi. Si assuma che qualcuno
  stia presentando dal sito che si sta eseguendo il debug.

## Cosa è documentato qui

Ogni comando raggiungibile tramite la debug API sulla build software che questo tenant esegue,
ciascuno con output acquisito da un nodo attivo piuttosto che trascritto da altre fonti.

Il [riferimento ai comandi](./commands/) li elenca tutti con la loro categoria, livello di privilegi
e trasporto; i [flussi di lavoro](./workflows/) li concatenano nelle sequenze che si
utilizzano effettivamente quando qualcosa non funziona.

Le parti della Site CLI accessibili solo sul nodo — `configure`, `configure-network`,
`factory-reset`, `upgrade` e circa sessanta ulteriori comandi `ExecCLI` — non sono
trattate.

Sono raggiungibili solo da una sessione di console seriale, quindi nulla di ciò che le riguarda può essere
verificato programmaticamente, e la sintassi dei comandi non verificata è il difetto che questa
documentazione esiste per evitare di ripetere.
