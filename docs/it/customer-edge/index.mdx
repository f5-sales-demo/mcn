Un Customer Edge (CE) è il nodo F5 Distributed Cloud che questo repository provisiona in
Azure — `terraform/modules/ce-node`, creato a partire dall'immagine marketplace
`volterraedgeservices/volterra-node`.

Esegue il piano dati (Argo), il piano di controllo (Vega), un proxy Envoy, uno stack
Kubernetes e `vpm`, l'agente che registra il nodo e gestisce tutto il resto su di esso.

Quando un CE non funziona correttamente, la Site CLI è lo strumento da utilizzare. La prima decisione riguarda quale percorso di accesso si applica: scegliere quello sbagliato fa perdere tempo in modo che sembra un nodo guasto.

## Due percorsi di accesso, e non sono intercambiabili

La debug API raggiunge il nodo **attraverso il piano di controllo di F5 Distributed Cloud**.
Questo è esattamente il motivo per cui la distinzione è importante: l'API può rispondere solo dopo che il nodo si è registrato e riporta lo stato `ONLINE`.

Un nodo che non è riuscito a registrarsi — cloud-init errato, token scaduto, nessun percorso verso
`register.ves.volterra.io` — è esattamente il caso in cui si ha bisogno della diagnostica, e
precisamente il caso in cui l'API non può rispondere.

Il nodo rifiuta anche SSH nella configurazione predefinita. La porta 22 è chiusa sul CE stesso, non da un gruppo di sicurezza di rete:

```console
$ ssh -o ConnectTimeout=10 admin@<ce-public-ip>
ssh: connect to host <ce-public-ip> port 22: Connection refused
```

Verificato anche dall'interno della VNet, da un jump host sulla stessa subnet, quindi
aprire una regola del gruppo di sicurezza non cambia nulla.

Quindi: se il sito è `ONLINE`, utilizzare la debug API. In caso contrario, la console seriale è l'unico modo per accedere.

<Aside type="caution" title="Verificare prima lo stato del sito">
Una sola richiesta indica quale percorso seguire:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/config/namespaces/system/sites/<site>" \
  | jq -r '.spec.site_state'
```

`ONLINE` significa che la debug API funzionerà. Qualsiasi altro valore — o un sito che non
esiste — significa console seriale.
</Aside>

## Regole di sicurezza

Queste si applicano a ogni comando su ogni pagina seguente.

- **Solo lettura, a meno che non si sia certi.** La superficie dei comandi è suddivisa in due
  livelli di privilegi: il livello `Exec` modifica il nodo oppure legge un marcatore di stato. Nessuna pagina qui esegue un comando `Exec`, e lo stesso vale per il sistema di acquisizione.
- **Non dare mai per scontato che un comando sia sicuro dal suo nome.** `ip-link-set` sembra una
  query ma porta un'interfaccia offline. `systemctl-restart-crio` riavvia il runtime dei
  container sotto un piano dati attivo.
- **Preferire il comando più limitato che risponda alla domanda.** `health` e
  `diagnosis` riassumono il nodo in modo economico; `flow-l` scarica una tabella di flusso con 629.760 voci.
- **Un CE serve traffico in produzione.** Questi sono ambienti demo condivisi. Si assuma che qualcuno
  stia effettuando una presentazione dal sito che si sta eseguendo il debug.

## Cosa è documentato qui

Ogni comando raggiungibile tramite la debug API sulla versione software eseguita da questo tenant,
ciascuno con output acquisito da un nodo in produzione anziché trascritto da altre fonti.

Il [riferimento dei comandi](./commands/) li elenca tutti con la relativa categoria, livello di privilegi e trasporto; i [flussi di lavoro](./workflows/) li concatenano nelle sequenze che si utilizzano effettivamente quando qualcosa non funziona.

Le parti della Site CLI accessibili solo dal nodo — `configure`, `configure-network`,
`factory-reset`, `upgrade` e circa sessanta ulteriori comandi `ExecCLI` — non sono
documentate.

Sono raggiungibili solo da una sessione di console seriale, quindi nulla di ciò che le riguarda può essere
verificato a livello programmatico, e la sintassi di comandi non verificata è il difetto che questa
documentazione si propone di evitare di ripetere.
