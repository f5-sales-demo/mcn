Eseguire questi controlli prima della presentazione. Ogni controllo restringe il punto in cui
si troverebbe un guasto, così un esito negativo dice qualcosa invece di segnalare solo che
qualcosa non funziona.

Ogni comando legge ciò che gli serve dal deployment. Impostare questi valori una volta e il
resto segue:

```bash
cd terraform
RG=$(terraform output -raw resource_group_name)
RS=$(terraform output -raw route_server_name)
CLIENT=$(terraform output -raw client_vm_name)
DOMAIN=$(terraform output -raw lb_domain)
VIP=$(terraform output -raw vip)
NIC=$(terraform output -raw client_nic_name)
```

## Quattro controlli, in questo ordine

<Steps>

1. **Ogni sito è `ONLINE`.** Nulla a valle può essere vero se questo non lo è.

   ```bash
   for s in $(terraform output -json xc_site_names | jq -r '.[]'); do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   Osservato il 2026-07-28, tre CE:

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **Ogni peering apprende l'annuncio del VIP di quel CE.** Interrogare ogni peering
   separatamente — si veda la prima trappola più sotto, perché è qui che la demo sembra
   guasta più spesso senza esserlo.

   ```bash
   for k in $(terraform output -json xc_site_names | jq -r 'keys[]'); do
     echo "--- ${k}-bgp"
     az network routeserver peering list-learned-routes \
       --name "${k}-bgp" --routeserver "$RS" -g "$RG" \
       --query "RouteServiceRole_IN_0[?network=='${VIP}/32'].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   Osservato il 2026-07-28:

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp
   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp
   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   Tre peering, tre next hop diversi, un solo prefisso. Questo dimostra il lato annuncio di
   ECMP.

3. **Le rotte effettive del client contengono ogni next hop.** Questo è ECMP stesso, così
   come la VNet l'ha programmato — non ciò che i CE dichiarano, ma ciò che Azure ne ha fatto.

   ```bash
   az network nic show-effective-route-table -g "$RG" -n "$NIC" \
     --query "value[?addressPrefix[0]=='${VIP}/32'].{prefix:addressPrefix[0],nh:nextHopIpAddress,type:nextHopType,state:state}" \
     -o json
   ```

   Osservato il 2026-07-28:

   ```json
   [
     {
       "nh": ["10.0.1.5", "10.0.1.6", "10.0.1.4"],
       "prefix": "10.250.0.10/32",
       "state": "Active",
       "type": "VirtualNetworkGateway"
     }
   ]
   ```

   `state: Active` con una voce per ogni CE in `nh` è il controllo. **L'ordine non è
   significativo e non è stabile** — Azure li restituisce in modo diverso da una chiamata
   all'altra, quindi conviene contarli anziché confrontarli con un'esecuzione precedente. Un
   solo next hop dove se ne attendono tre significa che un CE ha smesso di annunciare, e il
   passaggio 2 identifica quale.

4. **Il VIP serve traffico.** Dalla VM client, e **con l'header `Host`** — si veda la seconda
   trappola. Campionare un numero di richieste sufficiente per vedere un problema: qualche
   decina risulta al 100 % anche all'interno della finestra di convergenza descritta più
   sotto.

   ```bash
   az vm run-command invoke -g "$RG" -n "$CLIENT" \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts "ok=0; fail=0
                for i in \$(seq 1 60); do
                  c=\$(curl -s -o /dev/null -m 5 -w '%{http_code}' \
                        -H 'Host: ${DOMAIN}' http://${VIP}/)
                  [ \"\$c\" = 200 ] && ok=\$((ok+1)) || fail=\$((fail+1))
                done
                echo \"OK=\$ok FAIL=\$fail\""
   ```

   Osservato il 2026-07-28:

   ```text
   VIP with Host header: OK=60 FAIL=0
   bare IP (no Host): 404
   ```

</Steps>

## Trappola: un peering mostra una sola rotta, ed è corretto

`list-learned-routes` è limitato al peering che si indica. Riporta ciò che **quel** peer ha
annunciato, non l'intera tabella del Route Server.

Quindi interrogare un solo peering restituisce un unico `/32` del VIP tramite un unico next
hop, e viene la tentazione di leggerlo come "solo un CE sta annunciando — gli altri sono
giù". Niente è giù. Gli altri annunci sono visibili sui rispettivi peering, ed è proprio ciò
su cui itera il passaggio 2.

Non è possibile confermare ECMP da una query su un singolo peering. Occorre iterare su tutti
i peering, oppure leggere la tabella delle rotte effettive del client, che mostra il
risultato aggregato in una sola chiamata.

## Trappola: una richiesta a IP nudo restituisce 404

Il load balancer effettua il match sull'header `Host`. Il VIP non è un virtual server che
serve qualcosa a chiunque si connetta all'indirizzo.

Entrambi questi risultati provengono dalla stessa esecuzione sul deployment integro:

```text
curl -H "Host: $DOMAIN" http://$VIP/   ->  200   (60 of 60)
curl                     http://$VIP/   ->  404
```

**Un 404 su IP nudo è la prova che il percorso funziona** — la richiesta ha raggiunto il CE,
il proxy del CE ha risposto e ha rifiutato perché nessun dominio configurato corrispondeva.
Interpretarlo come un'interruzione porta a cercare problemi nel BGP, dove non si troverà
nulla di sbagliato.

Lo stesso vale durante una demo: se si digita l'indirizzo nel browser anziché risolvere il
dominio su di esso, si ottiene il 404.

## Il VIP scarta richieste per i primi tre quarti d'ora, poi smette

Su uno stack appena creato il VIP perde una piccola frazione di richieste per circa i primi
45 minuti dopo che i CE raggiungono lo stato `ONLINE`, e poi serve senza errori. Misurato su
1.470 richieste dalla VM client, tutte con l'header `Host`:

| Finestra | Richieste | Errori | Tasso |
| --- | --- | --- | --- |
| Primi ~45 minuti dopo l'attivazione di ECMP | 570 | 12 | **2,11 %** |
| I 23 minuti successivi | 900 | **0** | **0,00 %** |

Ogni errore era `curl: (28)` — un timeout con zero byte ricevuti — non uno stato di errore
HTTP. L'ultimo si è verificato circa 43 minuti dopo l'attivazione di ECMP. Delle 900
richieste andate a buon fine, 400 sono state eseguite con un timeout di 30 secondi e tutte si
sono concluse in meno di 2 secondi, quindi nulla è stato mascherato da un timeout troppo
breve.

**L'origine non era la causa.** Un batch di controllo diretto all'origine
(`terraform output -raw origin_ip`, bypassando il VIP) ha eseguito 120 richieste su 120 senza
errori *contemporaneamente ai* batch sul VIP che fallivano. Il guasto si colloca da qualche
parte nel percorso VIP, ECMP o CE.

Due cose che deliberatamente non vengono dette:

- **Non è un difetto in regime stazionario.** Si risolve completamente e resta risolto. Una
  demo attiva da un'ora non presenta questo problema — 60 su 60 al controllo 4 di cui sopra,
  su uno stack attivo da ore.
- **Non è attribuibile a un CE specifico.** Nulla in questa topologia fornisce un listener
  HTTP per singolo nodo, quindi non c'è modo di collegare una richiesta scartata al nodo che
  l'ha scartata. Le interfacce esterne dei CE non hanno alcun listener HTTP — risponde solo
  il `/32` del VIP.

Si è riprodotto su una ricostruzione pulita in un tenant differente, quindi segue la
topologia anziché l'ambiente.

<Aside type="caution" title="Non campionare 40 richieste e concludere che va tutto bene">
Batch da 40 a 50 richieste risultano al 100 % nella maggior parte dei casi anche all'interno
della finestra di errore. È così che il fenomeno è stato prima classificato erroneamente come
un guasto continuo a basso tasso e poi come nessun guasto affatto. Campionare 100 richieste o
più, in batch distanziati nel tempo.
</Aside>

## Altre due trappole di misurazione

Entrambe hanno prodotto risposte sbagliate ma convincenti in questo ambiente, e nessuna delle
due è evidente.

- **Sondare dall'interno della VNet, non dalla propria postazione di lavoro.** Un proxy
  aziendale può completare da sé l'handshake TCP sulle porte più comuni, così un test dalla
  postazione di lavoro segnala come **aperta** una porta che in realtà è chiusa. Le porte 80 e
  443 risultano aperte sugli indirizzi pubblici dei CE da una postazione di lavoro e sono
  chiuse quando sondate dall'interno della VNet. Utilizzare la VM client.
- **La porta 22 su un CE risponde solo sull'indirizzo interno (SLI).** Sondato dalla VM
  client, l'indirizzo interno di ciascun CE restituisce un banner OpenSSH, mentre i suoi
  indirizzi di gestione ed esterno vanno in timeout — come accade a un indirizzo non
  utilizzato impiegato come controllo. eth0 è rinominata `a-i-eth0` e non porta alcun IP
  host, perché è il datapath a possederla. Quindi sondare l'indirizzo con cui si conosce il
  nodo non dice nulla sullo stato SSH del nodo.

<Aside type="danger" title="Non inserire mai un indirizzo interno di un CE in modo fisso nel codice — vengono riassegnati a ogni ricostruzione">
Azure non preserva quale CE ottiene quale indirizzo nella subnet interna. Osservato il
2026-07-28, dopo una ricostruzione, i tre CE avevano `10.0.3.7`, `10.0.3.5` e `10.0.3.4`: non
nell'ordine dei nodi, non contigui e diversi da quelli che avevano in precedenza. La NIC del
client di test si trova nella stessa subnet e ha avuto un indirizzo precedentemente
assegnato a un CE.

Conviene leggerli invece di ricordarli:

```bash
terraform output -json ce_sli_private_ips
```

Senza lo stato Terraform a disposizione, si può interrogare Azure per nome della NIC, che *è*
stabile:

```bash
az network nic show -g "$RG" -n "<vm-name>-internal-nic" \
  --query ipConfigurations[0].privateIPAddress -o tsv
```

Connettersi a un indirizzo ricordato porta sul nodo sbagliato, su una VM che non è un CE, o da
nessuna parte — e quest'ultimo caso è indistinguibile da "SSH non è abilitato".
</Aside>

## Verificare che l'insieme dei comandi sul dispositivo corrisponda ancora alla documentazione

```bash
bash scripts/capture-sitecli.sh --check \
  --site "$(terraform output -json xc_site_names | jq -r '.eastus01')" \
  --node "$(terraform output -json ce_vm_names | jq -r '.eastus01')"
```

`--check` non scrive nulla, quindi è sicuro da eseguire sulla demo attiva.
