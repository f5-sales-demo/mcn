Customer Edge (CE) คือโหนด F5 Distributed Cloud ที่ repository นี้จัดเตรียมไว้ใน
Azure — `terraform/modules/ce-node` สร้างจาก
marketplace image `volterraedgeservices/volterra-node`

โหนดนี้รัน data plane (Argo), control plane (Vega), Envoy proxy, Kubernetes
stack และ `vpm` ซึ่งเป็น agent ที่ลงทะเบียนโหนดและจัดการทุกอย่างบนโหนด

เมื่อ CE ทำงานผิดปกติ Site CLI คือเครื่องมือที่ใช้ การตัดสินใจแรกคือต้องเลือกเส้นทางการเข้าถึงที่เหมาะสม เนื่องจากการเลือกผิดจะเสียเวลาในลักษณะที่ดูเหมือนโหนดเสียหาย

## สองเส้นทางการเข้าถึง และไม่สามารถใช้แทนกันได้

debug API เข้าถึงโหนด **ผ่าน F5 Distributed Cloud control plane**
นั่นคือเหตุผลทั้งหมดที่การแยกนี้มีความสำคัญ: API จะตอบสนองได้ก็ต่อเมื่อโหนดลงทะเบียนแล้วและรายงานสถานะ `ONLINE`

โหนดที่ลงทะเบียนไม่สำเร็จ — cloud-init ผิดพลาด, token หมดอายุ, ไม่มีเส้นทางไปยัง
`register.ves.volterra.io` — คือกรณีที่คุณต้องการการวินิจฉัย และ
เป็นกรณีที่ API ไม่สามารถให้บริการได้

[SSH](./access/ssh/) คือตัวเลือกที่สาม และเป็นตัวเลือกเดียวที่เข้าถึงพื้นผิวคำสั่งทั้งหมดของ appliance — debug API เปิดเผยคำสั่ง 34 คำสั่ง ในขณะที่โหนดเองมีคำสั่งเพิ่มเติมอีกมาก มีข้อจำกัดสองประการ `sshd` ตอบสนองบนที่อยู่ภายใน (SLI) ของโหนดเท่านั้น จึงต้องใช้ host ภายใน VNet และ key ถูกเขียนโดย cloud-init ในการบูตครั้งแรก เนื่องจากฟิลด์ `ssh_key` บน site object ไม่ทำงาน — `vpm` ข้ามผู้ใช้ `admin` และ
ไม่นำไปใช้งาน การเปิดใช้งานบนโหนดที่กำลังทำงานอยู่จึงเป็นการแทนที่โหนดเหล่านั้น

ดังนั้น: หาก site อยู่ในสถานะ `ONLINE` และ 34 คำสั่งเพียงพอ ให้ใช้ debug API หากต้องการพื้นผิวคำสั่งที่เหลือและสามารถเข้าถึง VNet ได้ ให้ใช้ SSH หากการลงทะเบียนเป็นปัญหา serial console คือทางเข้าเดียว

<Aside type="caution" title="ตรวจสอบสถานะ site ก่อน">
คำขอเดียวบอกให้คุณรู้ว่าอยู่บนเส้นทางใด:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/config/namespaces/system/sites/<site>" \
  | jq -r '.spec.site_state'
```

`ONLINE` หมายความว่า debug API จะทำงานได้ สถานะอื่นใด — หรือ site ที่ไม่มีอยู่ — หมายความว่าต้องใช้ serial console
</Aside>

## กฎด้านความปลอดภัย

กฎเหล่านี้ใช้กับทุกคำสั่งในทุกหน้าด้านล่าง

- **อ่านอย่างเดียวเว้นแต่คุณมั่นใจ** พื้นผิวคำสั่งแบ่งออกเป็นสองระดับสิทธิ์ และระดับ `Exec` จะเปลี่ยนแปลงโหนดหรืออ่านตัวบ่งชี้สถานะ ไม่มีสิ่งใดในหน้าเหล่านี้ที่รันคำสั่ง `Exec` และ capture harness ก็ไม่รันเช่นกัน
- **อย่าสันนิษฐานว่าคำสั่งปลอดภัยจากชื่อของมัน** `ip-link-set` ดูเหมือนเป็นการสอบถามและทำให้ interface ออฟไลน์ `systemctl-restart-crio` รีสตาร์ท container runtime ภายใต้ data plane ที่กำลังทำงานอยู่
- **เลือกใช้คำสั่งที่แคบที่สุดที่ตอบคำถามได้** `health` และ `diagnosis` สรุปข้อมูลโหนดได้อย่างรวดเร็ว ในขณะที่ `flow-l` dump ตาราง flow ที่มี 629,760 รายการ
- **CE ให้บริการ traffic จริง** สภาพแวดล้อมเหล่านี้เป็น demo environment ที่ใช้ร่วมกัน สันนิษฐานไว้เสมอว่ามีผู้กำลังนำเสนอจาก site ที่คุณกำลัง debug อยู่

## เนื้อหาที่ได้รับการจัดทำเอกสารไว้

ทุกคำสั่งที่เข้าถึงได้ผ่าน debug API บน software build ที่ tenant นี้รันอยู่
แต่ละคำสั่งมี output ที่ capture จากโหนดจริง ไม่ใช่คัดลอกมาจากที่อื่น

[ข้อมูลอ้างอิงคำสั่ง](./commands/) แสดงรายการทั้งหมดพร้อม category, ระดับสิทธิ์ และ transport ส่วน [workflows](./workflows/) เชื่อมโยงคำสั่งเหล่านี้เป็นลำดับขั้นตอนที่ใช้จริงเมื่อมีปัญหาเกิดขึ้น

ส่วนที่ใช้ได้เฉพาะบนโหนด (on-box-only) ของ Site CLI — `configure`, `configure-network`,
`factory-reset`, `upgrade` และคำสั่ง `ExecCLI` เพิ่มเติมอีกประมาณหกสิบคำสั่ง — ไม่ได้รับการจัดทำเอกสารไว้

คำสั่งเหล่านี้เข้าถึงได้เฉพาะจาก serial console session เท่านั้น ดังนั้นจึงไม่สามารถตรวจสอบได้โดยใช้โปรแกรม และ syntax คำสั่งที่ไม่ได้รับการตรวจสอบคือข้อบกพร่องที่เอกสารนี้มีจุดประสงค์เพื่อหลีกเลี่ยงการทำซ้ำ
