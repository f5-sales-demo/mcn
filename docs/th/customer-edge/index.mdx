Customer Edge (CE) คือโหนด F5 Distributed Cloud ที่ที่เก็บโค้ดนี้จัดเตรียมขึ้นใน
Azure — `terraform/modules/ce-node` ซึ่งสร้างจากอิมเมจ
`volterraedgeservices/volterra-node` บนตลาดกลาง

โหนดนี้รัน data plane (Argo), control plane (Vega), พร็อกซี Envoy, สแตก Kubernetes
และ `vpm` ซึ่งเป็นเอเจนต์ที่ลงทะเบียนโหนดและจัดการทุกสิ่งอื่นบนโหนดนั้น

เมื่อ CE ทำงานผิดปกติ Site CLI คือเครื่องมือที่ใช้ การตัดสินใจแรกคือเลือกว่าเส้นทาง
การเข้าถึงแบบใดที่ใช้ได้ และการเลือกผิดจะทำให้เสียเวลาในลักษณะที่ดูเหมือนว่าโหนด
เสียหาย

debug API เข้าถึงโหนด**ผ่าน control plane ของ F5 Distributed Cloud**
นั่นคือเหตุผลทั้งหมดที่การแยกเส้นทางนี้มีความสำคัญ: API จะตอบสนองได้เพียงเมื่อโหนดได้
ลงทะเบียนแล้วและรายงานสถานะ `ONLINE`

โหนดที่ลงทะเบียนไม่สำเร็จ — cloud-init ผิดพลาด โทเคนหมดอายุ ไม่มีเส้นทางไปยัง
`register.ves.volterra.io` — คือกรณีที่คุณต้องการการวินิจฉัยพอดี และเป็น
กรณีที่ API ไม่สามารถให้บริการได้พอดีเช่นกัน

SSH ไม่ใช่ตัวเลือกที่สาม `sshd` ทำงานบนโหนดและตอบสนองบนที่อยู่ภายใน (SLI)
ของมัน แต่บัญชี `admin` ไม่สามารถยืนยันตัวตนได้: `vpm` ข้ามผู้ใช้นั้นไป ดังนั้น
`ssh_key` ที่คุณกำหนดค่าไว้บนอ็อบเจ็กต์ไซต์จะไม่ถูกนำไปใช้เลย ไม่มีกฎของ security group
ใดที่เปลี่ยนแปลงเรื่องนี้ได้ หลักฐานอยู่ในหน้า [SSH](./access/ssh/) ซึ่งมีอยู่เพราะ
อาการทุกอย่างที่นั่นดูเหมือนเป็นความผิดพลาดของไฟร์วอลล์หรือข้อมูลรับรอง

ดังนั้น: หากไซต์อยู่ในสถานะ `ONLINE` ให้ใช้ debug API หากไม่ใช่ serial console คือ
ทางเข้าเพียงทางเดียว

<Aside type="caution" title="ตรวจสอบสถานะของไซต์ก่อน">
คำขอเดียวจะบอกคุณว่าคุณอยู่บนเส้นทางใด:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/config/namespaces/system/sites/<site>" \
  | jq -r '.spec.site_state'
```

`ONLINE` หมายความว่า debug API จะใช้งานได้ อย่างอื่น — หรือไซต์ที่ไม่มีอยู่ —
หมายความว่าต้องใช้ serial console
</Aside>

## กฎด้านความปลอดภัย

กฎเหล่านี้ใช้กับทุกคำสั่งในทุกหน้าด้านล่าง

- **อ่านเท่านั้น เว้นแต่คุณจะมั่นใจ** พื้นผิวคำสั่งถูกแบ่งออกเป็นสองระดับ
  สิทธิ์ และระดับ `Exec` จะเปลี่ยนแปลงสถานะของโหนดหรืออ่านตัวบ่งชี้สถานะ
  ไม่มีสิ่งใดในหน้าเหล่านี้ที่รันคำสั่ง `Exec` และชุดเครื่องมือเก็บข้อมูลก็เช่นกัน
- **อย่าสันนิษฐานว่าคำสั่งปลอดภัยจากชื่อของมัน** `ip-link-set` อ่านดูเหมือน
  การสอบถามข้อมูล แต่จะปิดอินเทอร์เฟซ `systemctl-restart-crio` จะรีสตาร์ต
  container runtime ภายใต้ data plane ที่ทำงานอยู่จริง
- **เลือกใช้คำสั่งที่แคบที่สุดซึ่งตอบคำถามได้** `health` และ
  `diagnosis` สรุปสถานะของโหนดโดยใช้ทรัพยากรน้อย ขณะที่ `flow-l` จะดัมป์ตาราง flow
  ที่มี 629,760 รายการ
- **CE ให้บริการทราฟฟิกจริง** สภาพแวดล้อมเหล่านี้เป็นสภาพแวดล้อมสาธิตที่ใช้ร่วมกัน
  ให้สันนิษฐานว่ามีคนกำลังนำเสนอจากไซต์ที่คุณกำลังแก้ปัญหาอยู่

## สิ่งที่บันทึกไว้ที่นี่

ทุกคำสั่งที่เข้าถึงได้ผ่าน debug API บนซอฟต์แวร์บิลด์ที่เทนแนนต์นี้ใช้งาน
แต่ละคำสั่งมีเอาต์พุตที่เก็บมาจากโหนดจริง ไม่ใช่คัดลอกมาจากที่อื่น

[การอ้างอิงคำสั่ง](./commands/) แสดงรายการทั้งหมดพร้อมหมวดหมู่ ระดับสิทธิ์
และช่องทางการรับส่งข้อมูล ส่วน[เวิร์กโฟลว์](./workflows/) จะร้อยเรียงคำสั่งเหล่านั้นเข้าเป็น
ลำดับที่คุณใช้จริงเมื่อมีสิ่งผิดปกติเกิดขึ้น

ส่วนของ Site CLI ที่ใช้ได้บนตัวเครื่องเท่านั้น — `configure`, `configure-network`,
`factory-reset`, `upgrade` และคำสั่ง `ExecCLI` อีกประมาณหกสิบคำสั่ง — ไม่ได้
ครอบคลุมไว้ที่นี่

คำสั่งเหล่านั้นเข้าถึงได้จากเซสชัน serial console เท่านั้น ดังนั้นจึงไม่มีสิ่งใดเกี่ยวกับ
คำสั่งเหล่านั้นที่สามารถตรวจสอบได้ด้วยโปรแกรม และไวยากรณ์คำสั่งที่ไม่ได้ตรวจสอบคือ
ข้อบกพร่องที่เอกสารชุดนี้มีอยู่เพื่อหลีกเลี่ยงการเกิดซ้ำ
