Customer Edge (CE) คือโหนด F5 Distributed Cloud ที่ repository นี้จัดเตรียมไว้ใน
Azure — `terraform/modules/ce-node` ซึ่งสร้างจากอิมเมจ
`volterraedgeservices/volterra-node` บนตลาดกลาง

โหนดนี้รัน data plane (Argo), control plane (Vega), Envoy proxy, สแตก Kubernetes
และ `vpm` ซึ่งเป็นเอเจนต์ที่ลงทะเบียนโหนดและจัดการทุกอย่างที่เหลือบนโหนดนั้น

เมื่อ CE ทำงานผิดปกติ Site CLI คือเครื่องมือที่ใช้ การตัดสินใจแรกคือเส้นทางการเข้าถึงแบบใดที่ใช้ได้
และการเลือกผิดจะทำให้เสียเวลาไปในลักษณะที่ดูเหมือนว่าโหนดเสีย

## เส้นทางการเข้าถึงสองแบบ ซึ่งใช้แทนกันไม่ได้

debug API เข้าถึงโหนด **ผ่าน control plane ของ F5 Distributed Cloud**
นั่นคือเหตุผลทั้งหมดว่าทำไมการแยกเส้นทางจึงสำคัญ: API จะตอบสนองได้ก็ต่อเมื่อโหนดได้
ลงทะเบียนแล้วและรายงานสถานะ `ONLINE`

โหนดที่ลงทะเบียนไม่สำเร็จ — cloud-init ผิดพลาด, โทเค็นหมดอายุ, ไม่มีเส้นทางไปยัง
`register.ves.volterra.io` — คือกรณีที่คุณต้องการการวินิจฉัยพอดี และเป็นกรณีที่ API
ไม่สามารถให้บริการได้พอดีเช่นกัน

[SSH](./access/ssh/) เป็นตัวเลือกที่สาม และเป็นตัวเลือกเดียวที่เข้าถึงพื้นผิวคำสั่งทั้งหมด
ของอุปกรณ์ได้ — debug API เปิดให้ใช้ 34 คำสั่ง ในขณะที่ตัวโหนดเองมีให้มากกว่านั้นมาก
มีสองสิ่งที่จำกัดการใช้งาน `sshd` ตอบสนองเฉพาะบนที่อยู่ภายใน (SLI) ของโหนดเท่านั้น
จึงต้องมีโฮสต์อยู่ภายใน VNet และคีย์ถูกเขียนโดย cloud-init ในการบูตครั้งแรก
เพราะฟิลด์ `ssh_key` บนอ็อบเจ็กต์ site นั้นไม่มีผล — `vpm` ข้ามผู้ใช้ `admin`
และไม่เคยนำไปใช้ ดังนั้นการเปิดใช้งานบนโหนดที่กำลังทำงานอยู่จึงเท่ากับต้องแทนที่โหนดเหล่านั้น

ดังนั้น: หากไซต์อยู่ในสถานะ `ONLINE` และ 34 คำสั่งเพียงพอ ให้ใช้ debug API หากคุณต้องการ
ส่วนที่เหลือของพื้นผิวคำสั่งและสามารถเข้าถึง VNet ได้ ให้ใช้ SSH หากสิ่งที่เสียคือการลงทะเบียน
serial console คือทางเดียวที่จะเข้าไปได้

<Aside type="caution" title="ตรวจสอบสถานะไซต์ก่อน">
คำขอเพียงหนึ่งรายการจะบอกคุณว่าคุณอยู่บนเส้นทางใด:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/config/namespaces/system/sites/<site>" \
  | jq -r '.spec.site_state'
```

`ONLINE` หมายความว่า debug API จะใช้งานได้ อย่างอื่น — หรือไซต์ที่ไม่มีอยู่จริง —
หมายความว่าต้องใช้ serial console
</Aside>

## กฎความปลอดภัย

กฎเหล่านี้ใช้กับทุกคำสั่งในทุกหน้าด้านล่าง

- **อ่านอย่างเดียวเว้นแต่คุณจะแน่ใจ** พื้นผิวคำสั่งถูกแบ่งออกเป็นสองชั้นสิทธิ์
  และชั้น `Exec` จะเปลี่ยนแปลงสถานะของโหนดหรืออ่านตัวบ่งชี้สถานะ ไม่มีสิ่งใดในหน้าเหล่านี้
  ที่รันคำสั่ง `Exec` และชุดเครื่องมือเก็บข้อมูลก็เช่นกัน
- **อย่าสันนิษฐานว่าคำสั่งปลอดภัยจากชื่อของมัน** `ip-link-set` อ่านดูเหมือนเป็นการ
  สอบถามแต่กลับปิดอินเทอร์เฟซ `systemctl-restart-crio` รีสตาร์ต
  container runtime ภายใต้ data plane ที่กำลังทำงานอยู่
- **เลือกใช้คำสั่งที่แคบที่สุดที่ตอบคำถามได้** `health` และ
  `diagnosis` สรุปสถานะโหนดโดยใช้ทรัพยากรน้อย ส่วน `flow-l` ดัมป์ตาราง flow
  ขนาด 629,760 รายการ
- **CE ให้บริการทราฟฟิกจริง** สภาพแวดล้อมเหล่านี้เป็นสภาพแวดล้อมสาธิตที่ใช้ร่วมกัน
  ให้สันนิษฐานว่ามีคนกำลังนำเสนอจากไซต์ที่คุณกำลังแก้ปัญหาอยู่

## สิ่งที่มีการจัดทำเอกสารไว้ที่นี่

ทุกคำสั่งที่เข้าถึงได้ผ่าน debug API บนซอฟต์แวร์เวอร์ชันที่เทแนนต์นี้ใช้อยู่
โดยแต่ละคำสั่งมีเอาต์พุตที่เก็บมาจากโหนดจริง ไม่ใช่คัดลอกมาจากที่อื่น

[เอกสารอ้างอิงคำสั่ง](./commands/) แสดงรายการทั้งหมดพร้อมหมวดหมู่ ชั้นสิทธิ์
และช่องทางการส่งข้อมูล ส่วน [เวิร์กโฟลว์](./workflows/) นำคำสั่งเหล่านั้นมาร้อยเรียงเป็นลำดับ
ที่คุณใช้จริงเมื่อเกิดปัญหา

ส่วนของ Site CLI ที่ใช้ได้เฉพาะบนตัวเครื่อง — `configure`, `configure-network`,
`factory-reset`, `upgrade` และคำสั่ง `ExecCLI` อีกราวหกสิบคำสั่ง — ไม่ได้ครอบคลุมไว้ที่นี่
เพราะเอาต์พุตของคำสั่งเหล่านั้นยังไม่ได้ถูกเก็บมาจากโหนดจริงในแบบเดียวกับที่ทุกหน้าด้านล่างได้ทำไว้

อย่างไรก็ตาม คำสั่งเหล่านั้นไม่ได้อยู่นอกเหนือการเข้าถึงอีกต่อไป `scripts/sitecli_ssh_harvest.py` เรียกใช้
เมนูเติมคำสั่งอัตโนมัติของตัวอุปกรณ์เองผ่าน [SSH](./access/ssh/) และบันทึกคำอธิบายที่
อุปกรณ์ให้ไว้สำหรับแต่ละคำสั่ง เพื่อให้สามารถวัดพื้นผิวคำสั่งได้แทนที่จะคาดเดา
การประมวลผลของสคริปต์นี้ถูกตั้งค่าให้ปฏิเสธเป็นค่าเริ่มต้น — มันแจกแจงทุกอย่างแต่รันเฉพาะรายการที่อนุญาต —
เพราะไวยากรณ์คำสั่งที่ยังไม่ได้ตรวจสอบ และ *ผลกระทบ* ของคำสั่งที่ยังไม่ได้ตรวจสอบ
คือข้อบกพร่องที่เอกสารชุดนี้มีอยู่เพื่อหลีกเลี่ยงไม่ให้เกิดซ้ำ
