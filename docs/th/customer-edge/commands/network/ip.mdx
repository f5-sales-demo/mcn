รายการเหล่านี้รายงานมุมมองของเคอร์เนล Argo data plane เก็บข้อมูลของตัวเองซึ่งสามารถดูได้ผ่าน
[`vif`](../dataplane-forwarding/) และทั้งสองอาจไม่ตรงกัน

## `ip`

รับ subcommand ของ `ip` โดย `addr` เป็นคำสั่งที่ใช้บ่อย นอกจากนี้ยังรองรับ `route`, `link` และ `neigh`

```bash
{"command":["ip","addr"]}
```

```text file=../../../../_data/sitecli-ip.txt
```

CE มี NIC สามตัวตามการออกแบบ และลำดับมีความสำคัญ: `eth0` คืออินเทอร์เฟซสำหรับการจัดการและ SLO ที่รองรับที่อยู่ BGP local ของไซต์ โดยมีอินเทอร์เฟซภายนอกและภายในตามมา สังเกต `a-i-eth0` ในผลลัพธ์ — data plane ได้เข้าควบคุมอินเทอร์เฟซกายภาพและนำเสนออินเทอร์เฟซของตัวเอง

## `ip-link-show`

แสดงเฉพาะ link-layer: สถานะ, MTU, queueing discipline, MAC

```bash
{"command":["ip-link-show"]}
```

```text file=../../../../_data/sitecli-ip-link-show.txt
```

เร็วกว่า `ip addr` เมื่อต้องการทราบว่า "ลิงก์ขึ้นหรือไม่และ MTU คืออะไร" ความไม่ตรงกันของ MTU เป็นสาเหตุที่เกิดขึ้นซ้ำของอุโมงค์ที่สร้างการเชื่อมต่อได้แต่ไม่มีทราฟฟิกผ่าน

## `ip-link-set` <Badge text="ระดับ Exec — การเปลี่ยนแปลง" variant="danger" />

นำอินเทอร์เฟซหรือกลุ่มขึ้นหรือลง

```
ip-link-set (<device>||<group>) (up||down)
```

<Aside type="danger" title="ไม่ได้รันที่นี่ และไม่สามารถเข้าถึงได้ตามวิธีปกติ">
นี่คือคำสั่งระดับ `Exec` เพียงคำสั่งเดียวใน build นี้ คำสั่งนี้ไปยัง endpoint `exec` แทนที่จะเป็น `exec-user` และมันเปลี่ยนแปลงโหนด: การนำ `eth0` ลงบน CE ระยะไกลจะตัดเส้นทางที่ใช้จัดการ รวมถึง debug API เอง

โดยเจตนาแล้วไม่มีผลลัพธ์ที่บันทึกไว้ในหน้านี้ ระบบ capture harness ปฏิเสธระดับ `Exec` ทั้งหมด และอ่านระดับจาก catalog ที่ใช้งานจริงแทนที่จะเป็นรายการที่กำหนดไว้ตายตัว ดังนั้นสิ่งนี้จะยังคงเป็นจริงหาก build ในอนาคตเลื่อนระดับคำสั่งอื่นเข้ามาในนั้น
</Aside>
