เก็บข้อมูลเมื่อ 2026-07-28 จาก CE หนึ่งเครื่องของการติดตั้งนี้ `sitecli/capture-manifest.json`
บันทึกว่าเป็นโหนดใด และ `scripts/capture-sitecli.sh --check` จะตรวจสอบชุดคำสั่งซ้ำ
กับ CE ที่ทำงานอยู่จริง

CE ใช้ FRR สำหรับ BGP บนโทโพโลยีนี้ CE ทำ peering กับ Azure Route Server สองอินสแตนซ์
ประกาศ VIP และเรียนรู้ prefix ของ VNet

## `show-ip-bgp-summary`

เริ่มที่นี่ หน้าจอเดียวบอกคุณได้ว่าการ peering ทำงานอยู่หรือไม่ และเสถียรมานานเท่าใด

```bash
{"command":["show-ip-bgp-summary"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp-summary.txt
```

อ่าน `State/PfxRcd` ก่อน หากเป็นตัวเลข นั่นคือจำนวน prefix ที่ได้รับ และหมายความว่า
เซสชันถูกสถาปนาแล้ว หากเป็นค่าอื่น — `Active`, `Connect`, `Idle` — คือเซสชันที่ยัง
ไม่ทำงาน `Up/Down` แสดงว่าสถานะปัจจุบันคงอยู่มานานเท่าใด ดังนั้นเซสชันที่รีเซ็ตอยู่
เรื่อย ๆ จะแสดงค่าที่น้อยอย่างน่าสงสัย

<Aside type="caution" title="vrf id ที่นี่ไม่ใช่ตัวที่ rt ต้องการ">
เอาต์พุตนี้รายงาน `vrf-id 3` นั่นคือระบบเลขของ FRR ส่วน Argo data plane ใช้
table id แยกต่างหาก และการส่งเลขของ FRR ไปให้
[`rt --dump`](../dataplane-forwarding/) จะได้ผลลัพธ์ `No such file or directory` ซึ่ง
ดูเหมือนโหนดเสียมากกว่าจะเป็นอาร์กิวเมนต์ที่ผิด
</Aside>

## `show-ip-bgp`

ตารางเต็ม โดยเห็นการเลือก best-path ได้

```bash
{"command":["show-ip-bgp"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp.txt
```

`*` คือเส้นทางที่ใช้งานได้ `>` คือ best path ที่ถูกเลือก `=` คือสมาชิกของ multipath ในข้อมูล
ที่เก็บด้านบน prefix ของ VNet ที่เรียนรู้มา `10.0.0.0/16` มีสองเส้นทาง — หนึ่งเส้นทางผ่าน
Route Server แต่ละอินสแตนซ์ — ถูกทำเครื่องหมาย `*=` และ `*>`: เป็น best path บวกกับสมาชิก multipath
ดังนั้นโหนดจึงกระจายโหลดทราฟฟิกขากลับผ่านทั้งสองอินสแตนซ์ ส่วน VIP `10.250.0.10/32` มีเส้นทาง `*>`
เพียงเส้นทางเดียวเพราะโหนดนี้เป็นผู้ต้นกำเนิด

<Aside type="caution" title="equal-cost multipath ของเดโมไม่ปรากฏในเอาต์พุตนี้">
`show-ip-bgp` คือตารางของโหนดเดียว ส่วน ECMP ที่การติดตั้งนี้สาธิตคือ CE หลายเครื่องที่
*แตกต่างกัน* ประกาศ `/32` เดียวกัน และถูกโปรแกรมไว้ที่ฝั่ง Azure — ดังนั้นตาราง BGP ของ
CE เครื่องใดเครื่องเดียวจึงไม่สามารถแสดงสิ่งนี้ได้ และการไม่มีเครื่องหมาย multipath บน VIP ที่นี่
ไม่ใช่ความผิดพลาด ให้พิสูจน์เรื่องนี้จากการ peering ของ Route Server หรือจากตารางเส้นทางที่มีผลของไคลเอนต์แทน
ทั้งสองอย่างอยู่ใน[หน้าตรวจสอบ](../../../../demo/verify/)
</Aside>

## `show-ip-bgp-neighbors`

รายละเอียดต่อเพื่อนบ้าน: ความสามารถที่เจรจากันได้ ตัวจับเวลา ตัวนับข้อความ และ
เหตุผลของการรีเซ็ตครั้งล่าสุด

```bash
{"command":["show-ip-bgp-neighbors"]}
```

ใช้คำสั่งนี้เมื่อสรุปภาพรวมแสดงว่าเซสชันกระพริบ (flapping) และคุณต้องการทราบสาเหตุ
`Last reset` และเหตุผลของมันคือบรรทัดที่มีประโยชน์

<Aside type="note" title="ยังไม่มีเอาต์พุตที่เก็บไว้ในหน้านี้">
ข้อมูลที่เก็บนี้ยังไม่สามารถ commit ได้จนกว่า `f5-sales-demo/docs-control#795` จะถูกรวมเข้า FRR
สะกดคำผิดในบรรทัด Graceful Restart และ `codespell` ปฏิเสธไฟล์นั้น

การแก้ไขข้อความที่เก็บมาจะทำให้เอกสารนี้อธิบายเอาต์พุตที่ไม่เคยเกิดขึ้นจริง
จึงต้องแก้ที่ต้นทางแทน ในระหว่างนี้ให้รันคำสั่งกับโหนดของคุณเอง
</Aside>

## `show-ip-bgp-neighbors-advertised-route`

สิ่งที่โหนดนี้บอกกับ peer ของมัน ต่างจากสิ่งที่มันรู้

```bash
{"command":["show-ip-bgp-neighbors-advertised-route"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp-neighbors-advertised-route.txt
```

นี่คือคำสั่งสำหรับกรณี "VIP เข้าถึงจาก VNet ไม่ได้" หาก VIP ไม่ปรากฏที่นี่ ปัญหาอยู่ที่
โหนดนี้ และการไปดูที่ peer มากเท่าไรก็ไม่ช่วยอะไร

เอาต์พุตจะแสดงบล็อก `bgp neighbor:` ซ้ำหนึ่งบล็อก**ต่อ peer หนึ่งราย** ดังนั้นบนโทโพโลยีนี้คุณจะได้
prefix สองรายการเดิมซ้ำสองครั้ง — ครั้งละหนึ่งสำหรับ Route Server แต่ละอินสแตนซ์ นั่นไม่ใช่การ
เรนเดอร์ซ้ำซ้อน: มันคือสิ่งที่ยืนยันว่าโหนดกำลังประกาศไปยังทั้งสองราย กรณีที่น่าสนใจคือบล็อกที่มีอยู่
สำหรับ peer หนึ่งราย แต่ขาดหายไปหรือสั้นเกินไปสำหรับอีกราย
