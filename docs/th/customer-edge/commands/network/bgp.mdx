CE ใช้งาน FRR สำหรับ BGP บนโทโพโลยีนี้ CE จะ peer กับ Azure Route Server ทั้งสองอินสแตนซ์
ประกาศ VIP และเรียนรู้ prefix ของ VNet

## `show-ip-bgp-summary`

เริ่มต้นที่นี่ หน้าจอเดียวบอกคุณได้ว่า peering ทำงานอยู่หรือไม่ และเสถียรมานานเท่าใด

```bash
{"command":["show-ip-bgp-summary"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp-summary.txt
```

อ่าน `State/PfxRcd` ก่อน ตัวเลขคือจำนวน prefix ที่ได้รับ และหมายความว่าเซสชันถูกสถาปนาแล้ว
ค่าอื่น ๆ — `Active`, `Connect`, `Idle` — คือเซสชันที่ยังไม่ทำงาน `Up/Down` แสดงว่าสถานะปัจจุบัน
คงอยู่มานานเท่าใด ดังนั้นเซสชันที่รีเซ็ตซ้ำ ๆ จะแสดงค่าที่น้อยอย่างน่าสงสัย

<Aside type="caution" title="ค่า vrf id ที่นี่ไม่ใช่ค่าที่ rt ต้องการ">
เอาต์พุตนี้รายงาน `vrf-id 3` นั่นคือระบบเลขของ FRR ส่วน Argo data plane ใช้
table id แยกต่างหาก และการส่งเลขของ FRR ไปให้
[`rt --dump`](../dataplane-forwarding/) จะคืนค่า `No such file or directory` ซึ่ง
ดูเหมือนโหนดเสียมากกว่าจะเป็นการใส่อาร์กิวเมนต์ผิด
</Aside>

## `show-ip-bgp`

ตารางเต็ม พร้อมมองเห็นการเลือก best-path

```bash
{"command":["show-ip-bgp"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp.txt
```

`*` คือเส้นทางที่ใช้ได้ `>` คือ best path ที่ถูกเลือก `=` คือสมาชิก multipath ในการเก็บข้อมูล
ด้านบน prefix ของ VNet ที่เรียนรู้มา `10.0.0.0/16` มีสองเส้นทาง — เส้นละหนึ่งอินสแตนซ์ของ Route Server —
ทำเครื่องหมายเป็น `*=` และ `*>`: เป็น best path บวกกับสมาชิก multipath ดังนั้นโหนดจึงกระจายโหลด
ทราฟฟิกขากลับผ่านทั้งสองอินสแตนซ์ ส่วน VIP `10.250.0.10/32` มีเส้นทาง `*>` เพียงเส้นเดียว
เพราะโหนดนี้เป็นผู้กำเนิดมันเอง

<Aside type="caution" title="ECMP สามทางของเดโมไม่ปรากฏในเอาต์พุตนี้">
`show-ip-bgp` คือตารางของโหนดเดียว ส่วน ECMP ที่การติดตั้งนี้สาธิตคือ CE *สามตัวที่ต่างกัน*
ประกาศ `/32` เดียวกัน และมันถูกโปรแกรมไว้ที่ฝั่ง Azure — ดังนั้นตาราง BGP ของ CE ตัวใดตัวหนึ่ง
จึงไม่สามารถแสดงมันได้ และการไม่มีเครื่องหมาย multipath บน VIP ที่นี่ไม่ใช่ความผิดปกติ
ให้พิสูจน์จาก peering ของ Route Server หรือจากตารางเส้นทางที่มีผลของไคลเอนต์แทน
ทั้งสองอย่างอยู่ใน [หน้า as-built](../../../../as-built/)
</Aside>

## `show-ip-bgp-neighbors`

รายละเอียดรายเพื่อนบ้าน: ความสามารถที่เจรจากันไว้ ตัวจับเวลา ตัวนับข้อความ และ
เหตุผลของการรีเซ็ตครั้งล่าสุด

```bash
{"command":["show-ip-bgp-neighbors"]}
```

ใช้คำสั่งนี้เมื่อสรุปภาพรวมแสดงว่าเซสชันกำลัง flapping และคุณต้องการทราบสาเหตุ
`Last reset` และเหตุผลของมันคือบรรทัดที่มีประโยชน์

<Aside type="note" title="ยังไม่มีเอาต์พุตที่เก็บไว้ในหน้านี้">
ยังไม่สามารถ commit การเก็บข้อมูลนี้ได้จนกว่า `f5-sales-demo/docs-control#795` จะเสร็จสิ้น FRR
สะกดคำผิดในบรรทัด Graceful Restart และ `codespell` ปฏิเสธไฟล์นี้

การแก้ไขข้อความที่เก็บมาจะทำให้เอกสารนี้อธิบายเอาต์พุตที่ไม่เคยเกิดขึ้นจริง
จึงเลือกแก้ไขที่ต้นทางแทน ในระหว่างนี้ให้รันคำสั่งกับโหนดของคุณเอง
</Aside>

## `show-ip-bgp-neighbors-advertised-route`

สิ่งที่โหนดนี้กำลังบอกกับ peer ของมัน ซึ่งต่างจากสิ่งที่มันรู้

```bash
{"command":["show-ip-bgp-neighbors-advertised-route"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp-neighbors-advertised-route.txt
```

นี่คือคำสั่งสำหรับกรณี "VIP ไม่สามารถเข้าถึงได้จาก VNet" หาก VIP ไม่ปรากฏที่นี่
ปัญหาอยู่ที่โหนดนี้ และการไปดูที่ peer มากแค่ไหนก็ไม่ช่วยอะไร

เอาต์พุตจะแสดงบล็อก `bgp neighbor:` ซ้ำหนึ่งบล็อก**ต่อหนึ่ง peer** ดังนั้นบนโทโพโลยีนี้คุณจะเห็น
prefix สองรายการเดิมซ้ำสองครั้ง — ครั้งละหนึ่งอินสแตนซ์ของ Route Server นั่นไม่ใช่การเรนเดอร์ซ้ำ
แต่เป็นสิ่งที่ยืนยันว่าโหนดกำลังประกาศไปยังทั้งสอง peer กรณีที่น่าสนใจคือบล็อกที่มีอยู่สำหรับ peer หนึ่ง
แต่หายไปหรือสั้นเกินไปสำหรับอีก peer หนึ่ง
