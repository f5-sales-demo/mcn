## `diagnosis`

<Aside type="caution" title="ขอบเขต GLOBAL — การขนส่งข้อมูลที่แตกต่างกัน">
เช่นเดียวกับ `health` การเรียก `GET` ไปยังพาธ `global` และไม่สามารถเข้าถึงได้ผ่าน `exec-user`

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/global/diagnosis"
```

</Aside>

```json file=../../../../_data/sitecli-diagnosis.txt
```

ผลลัพธ์จะถูกรายงานแยกตามโหนด ดังนั้นในไซต์ที่มีหลายโหนดคุณจะได้รับบล็อกละหนึ่งรายการต่อโหนด
`gateway_connectivity` และ `dns_connectivity` แต่ละรายการมีสรุปผลการ ping — `dest_ip`, `sent`,
`received`, `lost` และเวลาไป-กลับ

<Aside type="danger" title="การตรวจสอบด้วย ping ทั้งสองรายการรายงานการสูญหาย 100% บนโหนดที่มีสุขภาพสมบูรณ์">
ในโทโพโลยีนี้ **ทั้ง** `gateway_connectivity` (ไปยัง `10.0.1.1`) และ `dns_connectivity` (ไปยัง
`168.63.129.16`) รายงาน `sent: 5, received: 0, lost: 100` ในขณะที่ไซต์อยู่ในสถานะ `ONLINE`
ส่งต่อทราฟฟิกได้ และ `registration_status: OK` — ได้ตรวจสอบยืนยันอีกครั้งขณะเขียนเอกสารนี้ บล็อก
`lost: 100` สองรายการในการตอบกลับเดียวเป็นสิ่งที่ดูน่าตกใจที่สุดในหน้านี้ แต่
มันคือสถานะปกติ

`dns_connectivity` เป็นรายการที่ทำให้เข้าใจผิดมากกว่าในสองรายการนี้ เพราะ DNS ทำงานได้อย่างชัดเจน:
ในการตอบกลับเดียวกันนั้น `dns_query_result` มีการค้นหาที่สำเร็จสิบรายการ, `NOERROR`, กับ
ตัวแปลชื่อ (resolver) ตัวนั้นเป๊ะ ๆ การตรวจสอบนี้วัดความสามารถในการเข้าถึงผ่าน ICMP ซึ่งที่อยู่ของแพลตฟอร์ม Azure
ไม่ตอบสนอง โดยไม่ได้วัด DNS

ให้พิจารณาฟิลด์ใดฟิลด์หนึ่งเป็นสัญญาณเฉพาะเมื่อคุณมีหลักฐานอื่นของปัญหาอยู่แล้ว หรือ
เมื่อค่าของมันเปลี่ยนแปลง
</Aside>

ฟิลด์ที่ควรอ่านก่อนอยู่ในส่วนอื่นของการตอบกลับ: `registration_status`,
`curl_response` (หนึ่งรายการต่อหนึ่งปลายทาง F5 ที่โหนดต้องใช้ แต่ละรายการเป็น `OK` หรือไม่),
`dns_query_result`, และ `ntp_sync_status`

`resolv_conf` แสดงตัวแปลชื่อที่โหนดจะใช้จริง ซึ่งควรเปรียบเทียบกับ
สิ่งที่คุณคาดหวังก่อนที่จะเสียเวลาไปกับ [`dig`](../../network/dig/)
