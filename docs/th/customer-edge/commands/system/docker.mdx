Docker รันบริการแพลตฟอร์ม ส่วน Kubernetes workloads อยู่ภายใต้
[CRI-O](../crictl/)

## `docker-ps`

```bash
{"command":["docker-ps"]}
```

```text file=../../../../_data/sitecli-docker-ps.txt
```

<Aside type="tip" title="คอนเทนเนอร์สามตัวคือรายการทั้งหมด ไม่ใช่โหนดที่เสียหาย">
`vpm`, `argo_watch` และ `site-console` เนื่องจากโหนดส่วนใหญ่ทำงานภายใต้ CRI-O
การแสดงผล `docker-ps` ที่สั้นอาจดูเหมือนความล้มเหลวหากคุณคาดหวัง Kubernetes workloads
ที่นี่ แต่ไม่ใช่ — นี่คือชุดคอนเทนเนอร์ Docker ทั้งหมดบน CE ที่ทำงานปกติ และ
การที่ `vpm` ปรากฏอยู่และมีสถานะ `Up` คือบรรทัดที่สำคัญที่สุดในหน้านี้
</Aside>

## `docker-prune`

```bash
execcli docker-prune
```

ลบ Docker object ที่ไม่ได้ใช้ทั้งหมด — คอนเทนเนอร์ที่หยุดทำงาน, เครือข่ายที่ไม่ได้ใช้, image ที่ค้างอยู่ และ build cache

**เฉพาะจากเครื่องเท่านั้น** `docker-prune` ไม่อยู่บน debug API จำเป็นต้องใช้
[`execcli`](../../on-box/)

<Aside type="danger" title="ทำลายข้อมูลและไม่ได้บันทึกไว้ที่นี่">
คำสั่งนี้ลบสถานะ มันอยู่ในรายการปฏิเสธของ harvest harness และไม่เคยถูกรัน ดังนั้น
หน้านี้จึงจัดทำเอกสารจาก catalog metadata ของ appliance เอง แทนที่จะแสดงผลลัพธ์

ข้อควรระวังเฉพาะสำหรับ CE: โหนดนี้รัน container runtime **สอง** ตัว `docker-prune` 
ส่งผลกระทบเฉพาะฝั่ง Docker เท่านั้น — `vpm`, `argo_watch` และ `site-console` — 
และไม่สามารถเข้าถึง Kubernetes workloads ภายใต้ [CRI-O](../crictl/) การเรียกคืนพื้นที่
บนฝั่ง CRI-O เป็นคำสั่งที่แตกต่างออกไปคือ `systemctl-start-crio-prune` ซึ่งไม่มีอยู่ใน build นี้
</Aside>
