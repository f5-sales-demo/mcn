ชุดคำสั่งสองชุดแยกกันเข้าถึง Customer Edge ได้ และไม่มีชุดใดบรรจุอีกชุดหนึ่ง

- **บนกล่อง** Site CLI มี **6 คำสั่งระดับบนสุด** และ **82 คำสั่งย่อยของ `execcli`**
- **ผ่านเครือข่าย** [debug API](../../access/debug-api/) มีแคตตาล็อกของตนเองที่มี **34** คำสั่ง

พื้นผิวส่วนใหญ่ที่อยู่บนกล่องไม่มีคำสั่งเทียบเท่าใน API: control plane ของ Vega ทั้งหมด, wrapper ของ Envoy, การจับแพ็กเก็ต, ชุดพารามิเตอร์ของ kubelet, ไฟล์ `edit-*` และคู่การเข้าถึง root เสริม สามารถเข้าถึงได้จากกล่องเท่านั้น

การเข้าถึงต้องใช้ [SSH](../../access/ssh/) หรือ [serial console](../../access/serial-console/) และมีสิ่งหนึ่งที่ไม่มีการบันทึกไว้ที่ใดเลย:

<Aside type="tip" title="execcli เป็นคำสั่งที่ซ่อนอยู่">
`execcli` ไม่ปรากฏในเมนูแบบโต้ตอบของ Site CLI โดยรับชื่อคำสั่งเป็นอาร์กิวเมนต์ และการพิมพ์ `execcli ` ตามด้วย **Tab** จะแสดงรายการทั้ง 82 คำสั่งพร้อมคำอธิบายหนึ่งบรรทัดของอุปกรณ์สำหรับแต่ละคำสั่ง เมนูการเติมข้อความอัตโนมัตินั้นคือแคตตาล็อกที่เชื่อถือได้สำหรับ build และเป็นสิ่งที่ `sitecli/exec-catalog.json` บันทึกไว้
</Aside>

## วิธีการวัดและการทับซ้อนของชุดคำสั่ง

ชุดคำสั่งด้านล่างนี้ไม่ได้คัดลอกมาจากเอกสารของผู้จำหน่าย แต่อ่านมาจากโหนดที่ใช้งานจริงด้วย `scripts/sitecli_ssh_harvest.py` และบันทึกไว้ใน `sitecli/exec-catalog.json` พร้อมที่มา โดยทำการวัดสามครั้งในสามสถานะการลงทะเบียน:

| วัดที่ | ระดับบนสุด | `execcli` |
| --- | --- | --- |
| `site_state: PROVISIONING` | 6 | 82 |
| `site_state: PROVISIONED` | 6 | 82 |
| `site_state: ONLINE` | 6 | 82 |

ทั้งสามครั้งให้ผล **ชุดที่เหมือนกัน** — ชื่อเดียวกัน ไม่ใช่แค่ยอดรวมเดียวกัน และครั้งสุดท้ายเป็น deployment ที่แตกต่างกันโดยมีชื่อ site และทรัพยากรต่างกัน ดังนั้นพื้นผิวคำสั่งจึงไม่เปลี่ยนแปลงตามสถานะการลงทะเบียน และคำสั่งที่ไม่มีอยู่นั้นหายไปจริงๆ ไม่ใช่แค่ยังไม่ถูกเสนอ

เมื่อเทียบกับ 34 คำสั่งของ debug API จะได้ตัวเลขสองค่าที่ควรแยกแยะให้ชัดเจน:

- **51** คำสั่งย่อยของ `execcli` ไม่มีคำสั่งเทียบเท่าใน API
- **55** คือตัวเลขเดียวกันที่นับทั่วทั้งพื้นผิวบนกล่อง เนื่องจากยังรวมคำสั่ง `configure*` สี่คำสั่งที่อยู่ในระดับบนสุดแทนที่จะอยู่ใต้ `execcli`

ทั้งสองค่าถูกต้อง ผู้อ่านที่คำนวณค่าหนึ่งและพบอีกค่าไม่ได้ทำผิดพลาด ตัวเลขทุกตัวที่นี่มาจาก `sitecli/catalog.json` และ `sitecli/exec-catalog.json`

<Aside type="caution" title="คำสั่งห้าคำสั่งที่ไม่มีอยู่จริง">
`factory-reset`, `upgrade`, `reboot`, `show` และ `clear` **ไม่มี** ใน build นี้ สิ่งเหล่านี้เป็นประเภทที่ Site CLI อาจมีอยู่ตามสมเหตุสมผล และถูกพกพาอยู่ในการจำแนกประเภทของ repository นี้ระยะหนึ่งจากสมมติฐานดังกล่าว แต่ไม่มีการนับที่พบว่ามีอยู่ ระดับบนสุดมีหกรายการเท่านั้น: `configure`, `configure-generic-hardware`, `configure-network`, `configure-http-proxy`, `diagnosis` และ `health`
</Aside>

<Aside type="caution" title="คำสั่ง API สามคำสั่งไม่ใช่คำสั่งย่อยของ execcli">
การค้นหาคำสั่งเหล่านี้ภายใต้ `execcli` จะไม่พบสิ่งใด ซึ่งอ่านได้ว่า "คำสั่งหายไป":

- **`health`** และ **`diagnosis`** เป็นคำสั่ง Site CLI **ระดับบนสุด** พิมพ์ที่ prompt `>>>` โดยตรงโดยไม่มีคำนำหน้า `execcli`
- **`dig`** เข้าถึงได้ผ่าน debug API และ **ไม่ปรากฏ** ในเมนูบนกล่องใดเลย ดังนั้นจึงไม่อยู่ในรายการ passthrough ด้านล่าง เป็นคำสั่งที่ใช้ได้ผ่าน API เท่านั้น

</Aside>

## สิ่งที่มีเอกสารและสิ่งที่ระบุไว้เท่านั้น

Customer Edge รัน Linux และ daemon ของบุคคลที่สามจำนวนหนึ่ง การจัดทำเอกสารคำสั่งของพวกเขาจะซ้ำซ้อนกับเอกสารอ้างอิงของตัวเองและบ่งชี้ว่า F5 เป็นเจ้าของ ดังนั้นกฎจึงเป็น: **จัดทำเอกสารซอฟต์แวร์ของ F5 และสำหรับทุกอย่างอื่นให้จัดทำเอกสารเฉพาะสิ่งที่เฉพาะเจาะจงกับ CE เท่านั้น**

สามระดับ เนื่องจาก "ของเรา" และ "ของพวกเขา" ไม่ใช่การแบ่งที่ชัดเจน การแบ่งนี้บันทึกไว้ใน `sitecli/command-classification.json`

| ระดับ | การปฏิบัติ |
| --- | --- |
| **ซอฟต์แวร์ F5** | เอกสารครบถ้วน — วัตถุประสงค์ syntax อาร์กิวเมนต์ output ที่จับไว้ สิ่งที่ต้องมองหา Argo, Vega, `vpm`, `vifdump`, `configure*`, ชุด `edit-*`, พารามิเตอร์ kubelet, การเข้าถึง root |
| **การตีความเฉพาะ CE** | เครื่องมือของบุคคลที่สามที่ output มีความหมายเฉพาะบน CE การอ่านเฉพาะ CE ได้รับการจัดทำเอกสาร และ semantics ของเครื่องมือเองถูกปล่อยให้อยู่ต้นทาง |
| **Passthrough** | Linux หรือบุคคลที่สามทั่วไปที่ไม่มีอะไรเฉพาะ CE ที่จะพูดถึง ระบุว่ามีให้ใช้งาน พร้อมตัวชี้ไปยังต้นทาง ไม่มีข้อความร้อยแก้ว |

ความแตกต่างนี้เป็นตัวตัดสินว่าหน้าใดมีอยู่หรือไม่ และเป็นสิ่งที่ทำให้เอกสารนี้ไม่เสื่อมสลายกลายเป็นสำเนาที่แย่กว่าของ man pages

## Passthrough

มีให้ใช้งานบนกล่องและ **ไม่มีเอกสารที่นี่** — สิ่งเหล่านี้คือระบบปฏิบัติการและ daemon ของบุคคลที่สาม ไม่ใช่ซอฟต์แวร์ของ F5 และเอกสารอ้างอิงของตัวเองดีกว่าสิ่งที่หน้านี้จะพูดซ้ำได้

| คำสั่ง | ต้นทาง |
| --- | --- |
| `ping`, `netstat`, `lsof`, `ip`, `ip-link-show`, `nmcli`, `tracepath` | iproute2, NetworkManager |
| `top`, `check-mem`, `sysctl`, `load-sysctl-conf`, `journalctl`, `files`, `rpm-ostree`, `chronyc-sources` | coreutils, procps, systemd, rpm-ostree, chrony |
| `edit-etc-hosts`, `edit-sysctl-conf` | ไฟล์เหล่านี้เป็นของระบบปฏิบัติการ |
| `systemctl-status-crio`, `systemctl-status-docker`, `systemctl-status-kubelet`, `systemctl-status-iscsid`, `systemctl-status-multipathd` | systemd |
| `systemctl-restart-crio`, `systemctl-restart-docker`, `systemctl-restart-kubelet`, `systemctl-restart-iscsid`, `systemctl-restart-multipathd` | systemd — ทุกคำสั่งเหล่านี้ขัดจังหวะ workload บนโหนด |

สองคำสั่งเหล่านี้ควรรู้จักแม้ว่าจะไม่มีหน้าสำหรับมัน `files` ทำการดำเนินการไฟล์และจะเขียนเฉพาะใต้ `/tmp` เท่านั้น และทุก `systemctl-restart-*` มีความหมายว่าก่อให้เกิดการหยุดชะงักโดยนิยาม — การ restart `crio` หรือ `kubelet` จะขัดจังหวะ workload บนโหนดนั้น

<Aside type="note" title="คำสั่งเจ็ดคำสั่งมีอยู่ใน build ใหม่กว่าแต่ไม่มีใน build นี้">
`collect-database-stats`, `iptables-lv`, คำสั่ง `marker-exists-*` สามคำสั่ง, `systemctl-restart-NetworkManager` และ `systemctl-start-crio-prune` ไม่มีที่นี่และมีอยู่ใน build `20260703-e2c462a` ทำให้มี 89 คำสั่ง `execcli` ที่นั่นเทียบกับ 82 ที่นี่ [คำสั่งใน build ใหม่กว่า](../newer-builds/) จัดทำเอกสารไว้ คำสั่งเหล่านี้ถูกบันทึกไว้ภายใต้ `not_on_this_build.newer_build` ในการจำแนกประเภทเพื่อไม่ให้สิ่งใดที่นี่ถูกเข้าใจผิดว่าเป็นสิ่งที่คุณสามารถรันบน `crt-20250613-3382`

`collect-debug-info` เป็นกรณีแยกต่างหาก: ไม่ปรากฏในเมนูใดและแคตตาล็อกใด ข้อความต้อนรับของ Site CLI บอกว่า CLI "อนุญาตให้ … รวบรวมข้อมูล debug สำหรับฝ่ายสนับสนุน" ดังนั้นชื่อน่าจะถูกดึงมาจากข้อความนั้นมากกว่าที่จะถูกสังเกตจริงๆ คำสั่งนี้ถูกทำเครื่องหมายว่าไม่ได้รับการยืนยันและตั้งใจไม่ตรวจสอบ — การรันคำสั่งที่ไม่รู้จักโดยคาดเดาบนโหนดที่ใช้งานจริงคือวิธีที่การจับแพ็กเก็ต `vifdump` เริ่มทำงานบน CE ที่ยังลงทะเบียนอยู่
</Aside>
