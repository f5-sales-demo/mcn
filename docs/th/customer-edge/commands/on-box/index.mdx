ชุดคำสั่งสองชุดแยกต่างหากสามารถเข้าถึง Customer Edge ได้ และไม่มีชุดใดครอบคลุมอีกชุดหนึ่งอย่างสมบูรณ์

- **บนกล่อง** Site CLI มี **6 คำสั่งระดับบนสุด** และ **82 คำสั่งย่อยของ `execcli`**
- **ผ่านเครือข่าย** [debug API](../../access/debug-api/) มีแคตตาล็อกคำสั่งของตัวเองอีก **34** คำสั่ง

พื้นที่บนกล่องส่วนใหญ่ไม่มี API เทียบเท่า: control plane ของ Vega ทั้งหมด, wrappers ของ Envoy, การดักจับแพ็กเก็ต, ชุดพารามิเตอร์ kubelet, ไฟล์ `edit-*` และคู่การเข้าถึง root เสริม สามารถเข้าถึงได้จากกล่องเท่านั้น

การเข้าถึงต้องใช้ [SSH](../../access/ssh/) หรือ [serial console](../../access/serial-console/) และมีสิ่งหนึ่งที่ไม่มีเอกสารใดบันทึกไว้:

<Aside type="tip" title="execcli เป็นคำสั่งที่ซ่อนอยู่">
`execcli` ไม่ปรากฏในเมนูโต้ตอบของ Site CLI โดยจะรับชื่อคำสั่งเป็นอาร์กิวเมนต์ และการพิมพ์ `execcli ` ตามด้วย **Tab** จะแสดงรายการทั้ง 82 คำสั่งพร้อมคำอธิบายบรรทัดเดียวของอุปกรณ์สำหรับแต่ละคำสั่ง เมนูการเติมคำนั้นคือแคตตาล็อกที่เชื่อถือได้สำหรับ build นั้น และเป็นสิ่งที่ `sitecli/exec-catalog.json` บันทึกไว้
</Aside>

## วิธีการวัดและวิธีที่ชุดคำสั่งทับซ้อนกัน

ชุดคำสั่งด้านล่างนี้ไม่ได้คัดลอกมาจากเอกสารของผู้ผลิต แต่ถูกอ่านจาก node จริงด้วย `scripts/sitecli_ssh_harvest.py` และบันทึกไว้ใน `sitecli/exec-catalog.json` พร้อมแหล่งที่มา โดยมีการรันสามครั้งในสถานะการลงทะเบียนสามแบบ:

| วัดที่ | ระดับบนสุด | `execcli` |
| --- | --- | --- |
| `site_state: PROVISIONING` | 6 | 82 |
| `site_state: PROVISIONED` | 6 | 82 |
| `site_state: ONLINE` | 6 | 82 |

ทั้งสามครั้งให้ **ชุดคำสั่งที่เหมือนกันทุกประการ** — ชื่อเดียวกัน ไม่ใช่แค่ยอดรวมเดียวกัน และครั้งสุดท้ายเป็น deployment ที่แตกต่างกันพร้อมชื่อ site และทรัพยากรที่แตกต่างกัน ดังนั้นพื้นที่คำสั่งจึงไม่เปลี่ยนแปลงตามสถานะการลงทะเบียน และคำสั่งที่ไม่มีอยู่นั้นก็ไม่มีอยู่จริงๆ ไม่ใช่แค่ยังไม่ได้เปิดให้ใช้งาน

เมื่อเทียบกับ 34 คำสั่งของ debug API จะได้ตัวเลขสองตัวที่ควรแยกให้ชัดเจน:

- **51** คำสั่งย่อยของ `execcli` ไม่มี API เทียบเท่า
- **55** คือตัวเลขเดียวกันที่นับทั่วทั้งพื้นที่บนกล่อง เนื่องจากรวมคำสั่ง `configure*` สี่คำสั่งที่อยู่ในระดับบนสุดแทนที่จะอยู่ใต้ `execcli`

ทั้งสองตัวเลขถูกต้อง ผู้อ่านที่คำนวณตัวหนึ่งแล้วได้อีกตัวหนึ่งไม่ได้ทำผิดพลาด ตัวเลขทุกตัวที่นี่มาจาก `sitecli/catalog.json` และ `sitecli/exec-catalog.json`

<Aside type="caution" title="คำสั่งห้าคำสั่งที่ไม่มีอยู่จริง">
`factory-reset`, `upgrade`, `reboot`, `show` และ `clear` **ไม่มี** ใน build นี้ คำสั่งเหล่านี้เป็นประเภทที่ Site CLI น่าจะมี และถูกรวมไว้ในการจำแนกประเภทของ repository นี้ระยะหนึ่งตามสมมติฐานนั้น แต่ไม่มีการระบุพบคำสั่งเหล่านี้เลย ระดับบนสุดมีรายการเพียงหกรายการ: `configure`, `configure-generic-hardware`, `configure-network`, `configure-http-proxy`, `diagnosis` และ `health`
</Aside>

<Aside type="caution" title="คำสั่ง API สามคำสั่งไม่ใช่คำสั่งย่อยของ execcli">
การค้นหาคำสั่งเหล่านี้ใต้ `execcli` จะไม่พบอะไร ซึ่งอ่านได้ว่า "คำสั่งหายไป":

- **`health`** และ **`diagnosis`** เป็นคำสั่ง Site CLI **ระดับบนสุด** พิมพ์ตรงที่พรอมต์ `>>>` โดยไม่มีคำนำหน้า `execcli`
- **`dig`** สามารถเข้าถึงได้ผ่าน debug API และ**ไม่ปรากฏ**ในเมนูบนกล่องทั้งสอง ดังนั้นจึงไม่มีในรายการ passthrough ด้านล่าง มีเฉพาะใน API เท่านั้น

</Aside>

## สิ่งที่มีเอกสารและสิ่งที่แค่แสดงรายการไว้

Customer Edge รัน Linux และ daemon ของบุคคลที่สามหลายตัว การจัดทำเอกสารคำสั่งเหล่านั้นจะซ้ำซ้อนกับเอกสารอ้างอิงของตัวเองและแสดงนัยว่า F5 เป็นเจ้าของ ดังนั้นกฎคือ: **จัดทำเอกสารสำหรับซอฟต์แวร์ของ F5 และสำหรับสิ่งอื่นๆ จัดทำเอกสารเฉพาะสิ่งที่เฉพาะเจาะจงกับ CE เท่านั้น**

สามระดับ เนื่องจาก "ของเรา" และ "ของพวกเขา" ไม่ใช่การแบ่งที่ชัดเจน การแบ่งนี้บันทึกไว้ใน `sitecli/command-classification.json`

| ระดับ | การจัดการ |
| --- | --- |
| **ซอฟต์แวร์ F5** | เอกสารครบถ้วน — วัตถุประสงค์, ไวยากรณ์, อาร์กิวเมนต์, ผลลัพธ์ที่บันทึกไว้, สิ่งที่ควรมองหา Argo, Vega, `vpm`, `vifdump`, `configure*`, ชุด `edit-*`, พารามิเตอร์ kubelet, การเข้าถึง root |
| **การตีความเฉพาะ CE** | เครื่องมือของบุคคลที่สามที่ผลลัพธ์มีความหมายเฉพาะบน CE การอ่านแบบเฉพาะ CE มีเอกสารและความหมายของเครื่องมือเองถูกส่งต่อไปยัง upstream |
| **Passthrough** | Linux ธรรมดาหรือบุคคลที่สามโดยไม่มีสิ่งเฉพาะ CE ที่ต้องกล่าว แสดงรายการว่าพร้อมใช้งาน พร้อมตัวชี้ไปยัง upstream ไม่มีข้อความอธิบาย |

การแบ่งนั้นตัดสินว่าจะมีหน้าเอกสารอยู่หรือไม่ และเป็นสิ่งที่ป้องกันไม่ให้เอกสารนี้กลายเป็นสำเนาที่แย่กว่าของ man pages

## Passthrough

พร้อมใช้งานบนกล่องและ **ไม่มีเอกสารที่นี่** — คำสั่งเหล่านี้คือระบบปฏิบัติการและ daemon ของบุคคลที่สาม ไม่ใช่ซอฟต์แวร์ของ F5 และเอกสารอ้างอิงของตัวเองดีกว่าสิ่งที่หน้านี้จะสรุปซ้ำได้

| คำสั่ง | Upstream |
| --- | --- |
| `ping`, `netstat`, `lsof`, `ip`, `ip-link-show`, `nmcli`, `tracepath` | iproute2, NetworkManager |
| `top`, `check-mem`, `sysctl`, `load-sysctl-conf`, `journalctl`, `files`, `rpm-ostree`, `chronyc-sources` | coreutils, procps, systemd, rpm-ostree, chrony |
| `edit-etc-hosts`, `edit-sysctl-conf` | ไฟล์เหล่านี้เป็นของระบบปฏิบัติการ |
| `systemctl-status-crio`, `systemctl-status-docker`, `systemctl-status-kubelet`, `systemctl-status-iscsid`, `systemctl-status-multipathd` | systemd |
| `systemctl-restart-crio`, `systemctl-restart-docker`, `systemctl-restart-kubelet`, `systemctl-restart-iscsid`, `systemctl-restart-multipathd` | systemd — ทุกคำสั่งเหล่านี้ขัดจังหวะ workload บน node |

สองคำสั่งเหล่านี้ควรทราบแม้ว่าจะไม่มีหน้าเอกสาร `files` ดำเนินการกับไฟล์และจะเขียนได้เฉพาะใต้ `/tmp` เท่านั้น และทุก `systemctl-restart-*` มีผลกระทบโดยนิยาม — การรีสตาร์ท `crio` หรือ `kubelet` จะขัดจังหวะ workload บน node นั้น

<Aside type="note" title="คำสั่งเจ็ดคำสั่งมีอยู่ใน build ใหม่กว่าแต่ไม่มีใน build นี้">
`collect-database-stats`, `iptables-lv`, คำสั่ง `marker-exists-*` สามคำสั่ง, `systemctl-restart-NetworkManager` และ `systemctl-start-crio-prune` ถูกพบผ่าน debug API ใน build `crt-20260201-0179` คำสั่งเหล่านี้ถูกบันทึกไว้ใต้ `not_on_this_build.newer_build_debug_api` ในการจำแนกประเภท เพื่อไม่ให้สิ่งใดที่นี่ถูกเข้าใจผิดว่าเป็นสิ่งที่คุณสามารถรันบน `crt-20250613-3382` ได้

`collect-debug-info` เป็นกรณีแยกต่างหาก: ไม่ปรากฏในเมนูหรือแคตตาล็อกใดเลย ข้อความต้อนรับของ Site CLI ระบุว่า CLI "อนุญาตให้ … รวบรวมข้อมูล debug สำหรับการสนับสนุน" ดังนั้นชื่อนี้น่าจะมาจากข้อความนั้นมากกว่าที่จะถูกพบจริง คำสั่งนี้ถูกทำเครื่องหมายว่าไม่ได้รับการยืนยันและจงใจไม่ทดสอบ — การรันคำสั่งที่ไม่รู้จักแบบเดาสุ่มบน node จริงนั้น เป็นวิธีที่การดักจับแพ็กเก็ต `vifdump` เริ่มต้นบน CE ที่ยังอยู่ในขั้นตอนการลงทะเบียน
</Aside>
