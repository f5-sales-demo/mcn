บันทึกเมื่อ 2026-07-28 จาก CE หนึ่งตัวของการปรับใช้นี้ คำสั่งเหล่านี้เป็นคำสั่งบนกล่อง จึงมาผ่าน Site CLI แทนที่จะเป็น debug API; `sitecli/exec-catalog.json` บันทึกพื้นผิว และ `sitecli/capture-manifest.json` บันทึกโหนดที่ใช้

Envoy ยุติและพร็อกซีทราฟฟิกแอปพลิเคชันบน Customer Edge คำสั่งทั้งสี่นี้สอบถามอินเทอร์เฟซผู้ดูแลระบบ และไม่มีคำสั่งใดอยู่ใน
[debug API](../../../access/debug-api/)

<Aside type="note" title="ทุกคำสั่งเริ่มต้นด้วยมิเตอร์ความคืบหน้าของ curl">
คำสั่งเหล่านี้คือแรปเปอร์ `curl` รอบเอนด์พอยต์ผู้ดูแลระบบของ Envoy ที่เรียกใช้โดยไม่มี `-s` ดังนั้นสองหรือสามบรรทัดแรกของการบันทึกด้านล่างทุกรายการคือความคืบหน้าในการถ่ายโอนของ curl ที่เขียนไปยัง stderr:

```text
  % Total    % Received % Xferd  Average Speed   Time    Time     Time  Current
                                 Dload  Upload   Total   Spent    Left  Speed
  0     0    0     0 …
```

นั่นไม่ใช่เอาต์พุตของ Envoy และไม่ใช่ข้อผิดพลาด นอกจากนี้ยังมีประโยชน์อีกด้วย: จำนวนไบต์ `% Received` บอกคุณว่า Envoy ส่งคืนข้อมูลใด ๆ หรือไม่ ซึ่งแยกความแตกต่างระหว่าง "ไม่มีการกำหนดค่าตัวรับฟัง" กับ "อินเทอร์เฟซผู้ดูแลระบบไม่ตอบสนอง"
</Aside>

## `envoy-listeners`

ตัวรับฟังทุกตัวที่ Envoy ติดตั้งไว้ ในรูปแบบ `name:address:port`

```bash
execcli envoy-listeners
```

```text file=../../../../_data/sitecli-envoy-listeners.txt
```

**สิ่งที่ควรมองหา** ในการปรับใช้นี้ ตัวรับฟังมี `10.250.0.10:80` — VIP ที่ CE ประกาศเข้าสู่ BGP บรรทัดเดียวนั้นเชื่อมสามเลเยอร์เข้าด้วยกัน: หาก [`show-ip-bgp-summary`](../../network/bgp/) แสดงว่าพรีฟิกซ์กำลังถูกประกาศแต่ตัวรับฟังนี้ไม่มีอยู่ เส้นทางกำลังถูกดึงดูดไปยังโหนดที่จะไม่ให้บริการ ซึ่งเป็นโหมดความล้มเหลวที่เลวร้ายที่สุดในชุด ECMP เนื่องจากทราฟฟิกถูกแบ่งปันโหลดเข้าสู่หลุมดำ

`[fe80:…]:80` ที่ท้ายคือที่อยู่ลิงก์โลคัลของอินเทอร์เฟซที่ตัวรับฟังถูกผูกไว้

**สิ่งที่มันไม่บอกคุณ** ไม่มีข้อมูลเกี่ยวกับสถานภาพต้นน้ำ — ตัวรับฟังมีอยู่ไม่ว่าจะมีสิ่งใดอยู่เบื้องหลังหรือเข้าถึงได้หรือไม่ ใช้ `envoy-clusters` สำหรับสิ่งนั้น

## `envoy-clusters`

ทุกคลัสเตอร์ พร้อมขีดจำกัดการเชื่อมต่อและคำขอต่อลำดับความสำคัญ

```bash
execcli envoy-clusters
```

```text file=../../../../_data/sitecli-envoy-clusters.txt
```

**สิ่งที่ควรมองหา** บรรทัดมีรูปแบบ `cluster::scope::key::value` รายการ `observability_name` ระบุแต่ละคลัสเตอร์ และกลุ่มสาม `default_priority::max_connections`, `max_pending_requests` และ `max_requests` คือที่ที่ขีดจำกัดคำขอปรากฏขึ้น — คลัสเตอร์ที่ถูกตรึงที่ `max_pending_requests` กำลังถูกจำกัดโดยการกำหนดค่า ไม่ใช่โดยต้นน้ำ

## `envoy-config-dump`

การกำหนดค่าครบถ้วนของ Envoy ในรูปแบบ JSON ขนาดใหญ่: 126 KB บนโหนดสาธิตที่ไม่มีกิจกรรม

```bash
execcli envoy-config-dump
```

```text file=../../../../_data/sitecli-envoy-config-dump.txt
```

**สิ่งที่ควรมองหา** อาร์เรย์ `configs` ระดับบนสุดมีออบเจกต์หนึ่งต่อประเภทการกำหนดค่า — bootstrap, clusters, listeners, routes, secrets ใช้สิ่งนี้เมื่อตัวรับฟังหรือคลัสเตอร์มีอยู่แต่ทำงานผิดปกติ และค้นหาแทนที่จะอ่านทั้งหมด

## `envoy-hc-config-dump`

การกำหนดค่าการตรวจสอบสุขภาพโดยเฉพาะ

```bash
execcli envoy-hc-config-dump
```

```text file=../../../../_data/sitecli-envoy-hc-config-dump.txt
```

**สิ่งที่ควรมองหา** ในการปรับใช้นี้ คำสั่งคืนค่า **หนึ่งไบต์** — มองเห็นเป็น `100 1` ในมิเตอร์ `curl` — หมายความว่าไม่มีการกำหนดค่าการตรวจสอบสุขภาพที่ติดตั้งอยู่ นั่นคือสถานะที่คาดหวังสำหรับ CE ที่ไม่มีพูลต้นทางที่ถูกตรวจสอบสุขภาพ และควรจำไว้: ผลลัพธ์ว่างเปล่าที่นี่ไม่ใช่การสอบถามที่ล้มเหลว
