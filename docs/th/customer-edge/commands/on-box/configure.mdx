คำสั่งสี่คำสั่งอยู่ใน**ระดับบนสุด**ของ Site CLI แทนที่จะอยู่เบื้องหลัง
[`execcli`](../) — นี่คือสิ่งที่เมนูแบบโต้ตอบแสดงเมื่อคุณเข้าสู่ระบบ ร่วมกับ
[`health`](../../system/health/) และ [`diagnosis`](../../system/diagnosis/)

```text
configure                   Initial configuration of the node
configure-generic-hardware  Configure Hardware that isn't certified by F5XC.
configure-network           Initial configuration of the network
configure-http-proxy        Initial configuration of the HTTP proxy
```

นั่นคือข้อความเมนูของเครื่องเอง และรายการทั้งหกนั้นคือระดับบนสุดทั้งหมด

<Aside type="caution" title="คำสั่งห้าคำสั่งที่คุณอาจคาดหวังไม่มีอยู่ที่นี่">
`factory-reset`, `upgrade`, `reboot`, `show` และ `clear` **ไม่มี**ใน build
`crt-20250613-3382` คำสั่งเหล่านี้ถูกจัดประเภทไว้ใน repository นี้มาสักระยะหนึ่ง
โดยสันนิษฐานว่า Site CLI จะมีคำสั่งเหล่านั้น และการแจงนับสองครั้งอย่างอิสระ —
ครั้งหนึ่งที่ `site_state: PROVISIONING` และอีกครั้งที่ `PROVISIONED` — ไม่พบร่องรอยใดๆ ของคำสั่งเหล่านั้นเลย
ดู[ดัชนีบนกล่อง](../)สำหรับวิธีการวัดผลนั้น
</Aside>

<Aside type="danger" title="แบบโต้ตอบ และกำหนดค่าโหนดที่ทำงานอยู่ใหม่">
แต่ละคำสั่งเหล่านี้เป็นวิซาร์ดที่เขียนทับการกำหนดค่าของโหนด ไม่มีคำสั่งใดถูกรันในระหว่างการจัดทำเอกสารนี้
และไม่มีคำสั่งใดที่มีการบันทึก output — ไม่มีรูปแบบอ่านอย่างเดียวที่จะบันทึกได้
สิ่งที่ยืนยันแล้วคือทั้งสี่คำสั่งมีอยู่จริง และคำอธิบายของคำสั่งเหล่านั้น จากเมนู completion
</Aside>

## `configure`

การกำหนดค่าเริ่มต้นของโหนด: รายละเอียดการลงทะเบียนที่ผูกโหนดกับ tenant และ site

## `configure-network`

การกำหนดค่าเครือข่ายเริ่มต้น — การกำหนดที่อยู่สำหรับอินเทอร์เฟซของโหนด

## `configure-http-proxy`

กำหนดค่า HTTP proxy ขาออก สำหรับ CE ที่ไม่สามารถเข้าถึง control plane ของ F5 ได้โดยตรง

## `configure-generic-hardware`

กำหนดค่าฮาร์ดแวร์ที่ F5 ยังไม่ได้รับรอง เกี่ยวข้องกับการกำหนดค่าฮาร์ดแวร์ที่ได้รับการรับรอง
ซึ่งเข้าถึงได้ผ่าน [`edit-certified-hardware`](../config-files/): หากไม่มี endpoint ฮาร์ดแวร์ที่ได้รับการรับรองที่ถูกต้อง
`vpmd` จะออกพร้อมข้อความ *"fail to match certified hardware"* และโหนดจะไม่ลงทะเบียนเลย

## เหตุผลที่ repository นี้ไม่ใช้คำสั่งเหล่านั้น

คำสั่งเหล่านี้คือเส้นทางด้วยตนเอง และการ deploy นี้ใช้เส้นทางแบบอัตโนมัติแทน การลงทะเบียนถูกเขียนโดย cloud-init
ตั้งแต่การบูตครั้งแรก — `terraform/cloud-init/ce-node.yaml` เขียน
`/etc/vpm/config.yaml` พร้อมชื่อ cluster, token และ endpoint ฮาร์ดแวร์ที่ได้รับการรับรอง — ดังนั้นโหนดจึงขึ้นมาพร้อมกำหนดค่าแล้ว
และ `configure` ไม่มีอะไรต้องทำ

สิ่งนี้มีความสำคัญด้วยเหตุผลสองประการนอกเหนือจากความเป็นระเบียบ:

- **ความสามารถในการทำซ้ำ** โหนดที่กำหนดค่าด้วยวิซาร์ดจะถูกกำหนดค่าแตกต่างกันทุกครั้งที่ใครทำ
  โหนดที่กำหนดค่าด้วย cloud-init จะถูกกำหนดค่าเหมือนกันทุกครั้ง ซึ่งเป็นสิ่งที่ทำให้ demo สามารถ deploy ซ้ำได้
- **คำสั่งเหล่านี้คือเส้นทางการกู้คืน ไม่ใช่เส้นทางการ deploy** ใช้ `configure` เมื่อโหนดต้องการ
  เปลี่ยนทิศทางใหม่และ Terraform ไม่ใช่ตัวเลือก — โหนดที่ไม่เคยลงทะเบียน ผ่าน
  [serial console](../../../access/serial-console/) ที่ไม่มีสิ่งอื่นใดเข้าถึงได้

<Aside type="note" title="การลงทะเบียนคือ state และการแทนที่โหนดเคยทำให้ค้างอยู่">
การลงทะเบียนใหม่ไม่ใช่การดำเนินการเฉพาะฝั่งโหนดเท่านั้น: tenant เก็บ object การลงทะเบียน
ที่มีคีย์บน `(tenant, cluster_name, hostname)` การแทนที่ CE ในขณะที่คงชื่อเดิมไว้
เคยทำให้การ deploy ค้างอยู่อย่างถาวร เนื่องจากการลงทะเบียนของโหนดที่ถูกทำลายยังคงถือครองคีย์นั้นอยู่
ปัญหานั้นได้รับการแก้ไขแล้ว — ดู[ขั้นตอนการลงทะเบียน](../../../workflows/registration/) — แต่นั่นคือเหตุผลที่
`configure` เพียงอย่างเดียวไม่เพียงพอเสมอไปในการนำโหนดที่สร้างใหม่กลับมาใช้งานได้
</Aside>
