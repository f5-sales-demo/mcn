บันทึกเมื่อ 2026-07-28 จาก CE หนึ่งเครื่องของการติดตั้งนี้ `sitecli/capture-manifest.json`
บันทึกว่าเป็นโหนดใด และ `scripts/capture-sitecli.sh --check` จะตรวจสอบชุดคำสั่ง
ซ้ำอีกครั้งกับ CE ที่ทำงานอยู่จริง

<Aside type="danger" title="API ไม่สามารถดีบักปัญหานี้ได้">
debug API เข้าถึงโหนดผ่าน control plane ของ F5 Distributed Cloud ผ่าน
ทันเนลที่การลงทะเบียนสร้างขึ้น หากการลงทะเบียนล้มเหลวก็จะไม่มีทันเนล
ดังนั้นทุกคำสั่งในไซต์นี้จึงใช้งานไม่ได้สำหรับความล้มเหลวรูปแบบนี้ ให้ทำงานจาก
[Site Console](../../access/site-console/) หากโหนดยังมีเส้นทางเครือข่ายอยู่ และจาก
[serial console](../../access/serial-console/) หากไม่มี
</Aside>

<Steps>

1. **ยืนยันว่าคุณกำลังถามเทนแนนต์ที่ถูกต้อง** ขั้นตอนนี้ใช้เพียงคำสั่งเดียวและอยู่เป็นลำดับแรก
   เพราะถ้าผิดพลาดตรงนี้ ทุกขั้นตอนถัดไปจะให้ข้อมูลที่บิดเบือน: ฟลีตที่สมบูรณ์ในเทนแนนต์
   ที่คุณไม่ได้กำลังดูอยู่นั้นแยกไม่ออกจากฟลีตที่ไม่เคยลงทะเบียนสำเร็จ

   ```bash
   cd terraform
   terraform output -raw xc_tenant       # the tenant this deployment belongs to
   terraform output -raw xc_env_tenant   # the tenant your shell is exporting
   ```

   ```text
   f5-sales-demo
   f5-sales-demo
   ```

   ไม่ตรงกัน หรือข้อมูลรับรองที่คุณเชื่อว่าถูกต้องกลับคืนค่า `401` เปล่า ๆ? นั่นคือ
   อาการของโทเคนที่ถูกสร้างขึ้นสำหรับเทนแนนต์อื่น และมันได้ทำให้การติดตั้งนี้ต้อง
   สร้างใหม่ทั้งหมดไปแล้วหนึ่งครั้ง ([issue 696](https://github.com/f5-sales-demo/mcn/issues/696))

2. **ยืนยันว่าเทนแนนต์เข้าใจอย่างไร** การไม่ปรากฏในรายการไซต์เป็นปัญหาที่ต่างจาก
   การปรากฏอยู่แต่ไม่ได้อยู่ในสถานะ `ONLINE`

   ```bash
   curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
     "$XCSH_API_URL/api/config/namespaces/system/sites" | jq -r '.items[].name'
   ```

   หากไซต์มีอยู่และรายงานสถานะ `ONLINE` แสดงว่าการลงทะเบียนสำเร็จ และคุณอยู่ใน
   เวิร์กโฟลว์ที่ผิด

4. **ค้นหาการลงทะเบียนของไซต์และสถานะของมัน** โหนดสามารถลงทะเบียนแล้วรอ
   การอนุมัติ ซึ่งจากภายนอกดูเหมือนกับความล้มเหลวไม่มีผิด

   ```bash
   curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
     "$XCSH_API_URL/api/register/namespaces/system/registrations_by_site/<site>" \
     | jq -r '.items[] | "\(.name)  \(.object.status.current_state)  \(.object.spec.gc_spec.infra.hostname)"'
   ```

   ```text
   r-a97e20c8-b7e1-483d-bd76-34a64ff8bc78  ONLINE  f5-xc-ce-vm-01
   ```

   หากไม่มีรายการใดเลยหมายความว่าโหนดยังไม่ได้ลงทะเบียน — ให้ไปที่ serial console ส่วนรายการ
   ที่อยู่ในสถานะอื่นที่ไม่ใช่ `ONLINE` หมายความว่ามันลงทะเบียนแล้วและมีบางอย่างล้มเหลวหลังจากนั้น
   ซึ่งเป็นการตรวจสอบที่ต่างออกไป

   หากต้องการกวาดทั้ง namespace เพื่อหาสิ่งที่รอการอนุมัติ `listregistrationsbystate`
   รับสถานะเป็น **`POST` body**:

   ```bash
   curl -sS -X POST -H "Authorization: APIToken $XCSH_API_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"namespace":"system","state":"PENDING"}' \
     "$XCSH_API_URL/api/register/namespaces/system/listregistrationsbystate" | jq -r '.items[].name'
   ```

   บนฟลีตที่สมบูรณ์คำสั่งนี้จะไม่คืนค่าอะไรเลย เพราะการอนุมัติเป็นระบบอัตโนมัติ

5. **ยืนยันว่า VM ทำงานอยู่จริง** ก่อนจะสรุปว่าเป็นความผิดพลาดของซอฟต์แวร์

   ```bash
   az vm list -d -g <resource-group> --query "[].{name:name,power:powerState}" -o table
   ```

   ```text
   Name            Power
   --------------  ----------
   ar-ecmp-client  VM running
   f5-xc-ce-vm-01  VM running
   f5-xc-ce-vm-02  VM running
   f5-xc-ce-vm-03  VM running
   ```

6. **เชื่อมต่อ serial console** การใช้งานแบบอินเทอร์แอกทีฟต้องมีเทอร์มินัลจริง ส่วนการเชื่อมต่อ
   นั้นสามารถเขียนสคริปต์ผ่าน websocket ได้แทน — ดู
   [serial console](../../access/serial-console/)

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

   หากถูกปฏิเสธ ให้ตรวจสอบว่าเปิดใช้งาน boot diagnostics บน VM แล้วก่อนจะสรุปว่า
   โหนดเข้าถึงไม่ได้ ข้อกำหนดเบื้องต้นนั้นและรูปแบบความล้มเหลวของมันอธิบายอยู่ในหน้า
   [serial console](../../access/serial-console/)

7. **อ่านสิ่งที่คอนโซลแสดง ตามลำดับนี้** cloud-init ก่อน — โหนดที่ cloud-init
   ไม่เคยทำงานเสร็จจะไม่มีการกำหนดค่าสำหรับการลงทะเบียน จากนั้นดูความพยายาม
   ลงทะเบียนเอง แล้วจึงดู DNS: หากโหนดไม่สามารถแปลงชื่อ
   `register.ves.volterra.io` ได้ ทุกอย่างที่อยู่ถัดจากนั้นก็ทำงานไม่ได้

8. **เมื่อโหนดอยู่ในสถานะ `ONLINE` แล้ว** ให้ตรวจสอบด้วย [`health`](../../commands/system/health/)
   และคาดหวังผลลัพธ์ `state: PROVISIONED`

</Steps>

<Aside type="caution" title="การลงทะเบียนถูกตั้งชื่อตาม UUID ไม่ใช่ตามชื่อไซต์">
การลงทะเบียนมีชื่อรูปแบบ `r-<uuid>` และไม่มีเอนด์พอยต์ใดที่รับชื่อไซต์ในตำแหน่งที่
คาดหวังชื่อการลงทะเบียน
`GET .../registrations/<site>` จะคืนค่า `404` ซึ่งอ่านดูเหมือน "ไซต์นี้ไม่มี
การลงทะเบียน" แต่ความจริงคือ "นั่นไม่ใช่ชื่อการลงทะเบียน" การจับคู่ไซต์กับการลงทะเบียน
มาจาก `registrations_by_site/<site>` เท่านั้น ตามในขั้นตอนที่ 3 หรือโดยการแสดงรายการ
`registrations` แล้วจับคู่กับ `gc_spec.passport.cluster_name`

กับดักเดียวกันนี้ทำให้ดูเหมือนว่าฟลีตที่สมบูรณ์มีการลงทะเบียนเป็นศูนย์
</Aside>

## สาเหตุที่พบบ่อย

- **คุณชี้ไปที่เทนแนนต์ที่ผิด** ทำให้ฟลีตที่ปกติดีดูเหมือนไม่มีอยู่ ขั้นตอนที่ 1
- cloud-init ทำงานไม่เสร็จ ทำให้ `/etc/vpm/config.yaml` ไม่มีอยู่หรือไม่ถูกต้อง
- โทเคนลงทะเบียนหมดอายุ ถูกใช้ไปแล้ว หรือมาจากเทนแนนต์อื่น
- ไม่มีเส้นทางขาออกไปยัง `register.ves.volterra.io`
- ความคลาดเคลื่อนของนาฬิกามากพอที่จะทำให้ใบรับรองไม่ถูกต้อง — ตัดประเด็นนี้ออกได้อย่างรวดเร็วในภายหลังด้วย
  [`chronyc-sources`](../../commands/network/chronyc-sources/) แต่ยังเข้าถึงไม่ได้
  จนกว่าโหนดจะออนไลน์ แบนเนอร์การเข้าสู่ระบบของ [SSH](../../access/ssh/) จะรายงาน `NTP: Synced`
  และสถานะของรีโซลเวอร์ก่อนที่คุณจะรันอะไร เมื่อ SSH พร้อมใช้งาน
