ตัวแปร Terraform สองตัวกำหนดซอฟต์แวร์ของ Customer Edge: `ce_os_version` สำหรับระบบปฏิบัติการ
และ `ce_sw_version` สำหรับบิลด์ F5 Distributed Cloud ทั้งสองมีพฤติกรรมที่ตรงกันข้ามกับการอ่านที่ชัดเจน — ฟิลด์ว่างเปล่าจะให้บิลด์ล่าสุดแทนที่จะไม่มีบิลด์เลย
และเวอร์ชันที่ติดตั้งบนโหนดหนึ่งสามารถล้มเหลวบนโหนดที่เหมือนกันแต่มีดิสก์ขนาดเล็กกว่า

## สิ่งที่ฟิลด์เวอร์ชันทำ ใน 2 ช่วง

การแยกช่วงออกจากกันคือประเด็นหลักทั้งหมด หากรวมเข้าด้วยกัน พฤติกรรมจะดูเหมือนขัดแย้งในตัวเอง

**ในการบูตครั้งแรก โหนดจะติดตั้งสิ่งที่ `ce_sw_version` ระบุชื่อ**
`terraform/modules/ce-node` ปรับใช้ marketplace image ด้วย `version = "latest"` ดังนั้นบิลด์ที่โหนดมาพร้อมกับคือสิ่งที่ image นั้นจัดส่งในขณะนี้ — และสิ่งนั้นเปลี่ยนแปลงตามเวลา
`ce_sw_version` เลือก **ปลายทาง** ไม่ใช่ว่าจะมีอะไรเกิดขึ้นหรือไม่ และการปล่อยว่างไว้หมายความว่าเซิร์ฟเวอร์เป็นผู้เลือก ไม่ใช่ว่าโหนดจะอยู่กับที่ เช่นเดียวกับ
`ce_os_version`

อย่าสันนิษฐานว่าทิศทางของการเปลี่ยนแปลงนั้นเป็นขาขึ้น `สังเกตเมื่อ 2026-07-28` image
จัดส่งบิลด์ที่มีตราประทับ `20260703-e2c462a` — ใหม่กว่า `crt-20250613-3382` ของ fleet นี้ และ
ใหม่กว่า `crt-20260201-0179` ที่ tenant กำลังโฆษณาอยู่ การระบุชื่อบิลด์ที่เก่ากว่าที่ image บรรจุมาจะขอให้โหนดเคลื่อนที่ถอยหลัง และนั่นเป็นเรื่องปกติ: fleet นี้ถูกสร้างขึ้นในลักษณะนั้นและกำลังทำงานอยู่

**การปล่อยฟิลด์เวอร์ชันว่างไว้คือการเลือกที่มีความเสี่ยงมากที่สุด ไม่ใช่ตัวเลือกที่เป็นกลาง** เมื่อสร้าง
เซิร์ฟเวอร์ไม่ได้ปล่อยฟิลด์ว่างทิ้งไว้ตามที่เป็น — มันจะเติมด้วยเวอร์ชัน **ที่โฆษณาล่าสุด**
และติดตั้งเวอร์ชันนั้น ไซต์ที่สร้างโดยไม่ตั้งค่าทั้งสองฟิลด์กลับมาพร้อมกับการปักหมุดไว้ที่
`crt-20260201-0179` และ OS `9.2026.14` ซึ่งเป็นสองเวอร์ชันที่ tenant กำลังโฆษณา และการติดตั้งก็ล้มเหลว `สังเกตเมื่อ 2026-07-29`

มีผลที่ตามมาสองประการ การปล่อยว่างหมายความว่า "ให้เวอร์ชันล่าสุด" ดังนั้นการปรับใช้ที่ไม่ปักหมุดจึงมีโอกาสสูงสุดที่จะพบกับขีดจำกัดดิสก์ที่อธิบายไว้ด้านล่าง และคุณไม่สามารถแยกฟิลด์เดียวโดยปล่อยอีกฟิลด์ว่างไว้ได้ เนื่องจากเซิร์ฟเวอร์จะเติมให้ — ตั้งค่าทั้งสอง อย่างตั้งใจ หรือยอมรับเวอร์ชันล่าสุดของแต่ละอัน

**หลังจากบูตครั้งแรก ไม่มีอะไรอัปเกรดเองโดยอัตโนมัติ** F5 Distributed Cloud โฆษณาบิลด์ที่ใหม่กว่าและรอ นั่นคือจุดที่ "โหนดอยู่ตรงจุดที่มันลงจอด" ถือว่าเป็นจริง — หลังจากการสร้าง ไม่ใช่ระหว่างนั้น

ทั้งสองช่วงสามารถมองเห็นได้บนออบเจกต์ไซต์ `สังเกตเมื่อ 2026-07-28` fleet นี้:

```text
volterra_software_status.available_version   crt-20260201-0179
operating_system_status.available_version    9.2026.14
```

ขณะที่โหนดรัน `crt-20250613-3382` และ OS `9.2024.6` บิลด์ที่ใหม่กว่าอยู่ในข้อเสนอและยังไม่ได้รับ — สถานะคงที่ ไม่ใช่การอัปเกรดที่หยุดชะงัก

## Terraform ไม่สามารถเปลี่ยนเวอร์ชันได้ แต่ API สามารถทำได้

นี่คือสองข้อเท็จจริงที่แยกกัน และการรวมเข้าด้วยกันจะสร้างแผนที่ผิด

**Terraform ไม่สามารถทำได้** `ce_os_version` และ `ce_sw_version` นั้นใช้ได้เฉพาะเวลาสร้างเท่านั้น
เปลี่ยนค่าใดค่าหนึ่งและ apply แล้ว API จะปฏิเสธการอัปเดตด้วย
`[BAD_REQUEST] Invalid request parameters` `สังเกตเมื่อ 2026-07-29` บนไซต์ทิ้งแล้ว ในทั้งสามทิศทาง — การปักหมุด **ไปข้างหน้า** ไปยังบิลด์ที่ใหม่กว่า การปักหมุด **ถอยหลัง** ไปยังบิลด์ที่เก่ากว่า
และ **การยกเลิกการปักหมุด** โดยการล้างทั้งสองฟิลด์ การเคลื่อนไปข้างหน้าไม่ใช่กรณีพิเศษ

**API สามารถทำได้** F5 Distributed Cloud เปิดเผยการดำเนินการอัปเกรดเฉพาะต่อไซต์ ซึ่ง
เริ่มการเปลี่ยนแปลงในสถานที่ — ไม่มีการสร้างใหม่ และไม่มีการเกี่ยวข้องกับ Terraform:

```bash
# software build
curl -X POST -H "Authorization: APIToken $TOKEN" -H 'Content-Type: application/json' \
  --data '{"version": "<software-version>"}' \
  "$API_URL/api/config/namespaces/system/sites/<site-name>/upgrade_sw"

# operating system
curl -X POST -H "Authorization: APIToken $TOKEN" -H 'Content-Type: application/json' \
  --data '{"version": "<os-version>"}' \
  "$API_URL/api/config/namespaces/system/sites/<site-name>/upgrade_os"
```

`สังเกตเมื่อ 2026-07-29`: การเรียก software คืนค่า `200` ไซต์เปลี่ยนไปอยู่ที่ `UPGRADING` พร้อม
`deployment_state.phase` `UPGRADE_IN_PROGRESS` และเวอร์ชันที่ขอในออบเจกต์ไซต์เปลี่ยนเป็นเวอร์ชันที่โพสต์ไป การละเว้นฟิลด์จะคืนค่า `400` พร้อม `version empty in the request` ซึ่งเป็นวิธีที่ยืนยันชื่อฟิลด์

**ควรกันเวลาเป็นชั่วโมง ไม่ใช่นาที และอย่าตื่นตระหนกเมื่อเกิดความล้มเหลว** บนโหนดดิสก์เริ่มต้น
การอัปเกรดเป็น `crt-20260201-0179` ใช้เวลาประมาณหนึ่งชั่วโมง รายงาน `UPGRADE_FAILED` พร้อม
`result` `Failed` ระหว่างทาง และจากนั้น **เสร็จสมบูรณ์** บนบิลด์ใหม่ แพลตฟอร์มลองใหม่

นั่นมีผลโดยตรงสำหรับทุกคนที่กำลังดูการอัปเกรด หรือเขียนสคริปต์สำหรับมัน: ผลลัพธ์ `Failed`
คือสถานะที่ต้องรอผ่าน ไม่ใช่การตัดสิน การถือเอาผลลัพธ์แรกเป็นที่สิ้นสุดจะรายงานความล้มเหลวสำหรับการอัปเกรดที่จะประสบความสำเร็จ

โปรดสังเกตกลุ่มในเส้นทางนั้น: สิ่งเหล่านี้อยู่ภายใต้ **`config`** ไม่ใช่ `operate` เส้นทางเดียวกันภายใต้
`operate` คืนค่า `404 API Group could not be determined` ซึ่งเป็นข้อความเส้นทาง ไม่ใช่การระบุว่าไม่มีการอัปเกรดอยู่ — ความแตกต่างที่ทำให้โปรเจกต์นี้ได้ข้อสรุปที่ผิด

<Aside type="caution" title="การอัปเกรดผ่าน API ทำให้ Terraform ไม่สอดคล้องกัน">
ตัวแปรที่ปักหมุดยังคงบอกสิ่งที่บอกเสมอมา ดังนั้นไซต์ที่ใช้งานอยู่ตอนนี้รันเวอร์ชันที่การกำหนดค่าไม่ได้ระบุชื่อ Terraform จะไม่ปรับให้สอดคล้อง — มันทำไม่ได้ เนื่องจากการอัปเดตถูกปฏิเสธ — ดังนั้นให้ถือว่าการอัปเกรด API เป็นขั้นตอนที่ตั้งใจออกจากการควบคุมของ Terraform และอัปเดตหมุดให้ตรงกันในการสร้างใหม่ครั้งถัดไป
</Aside>

<Aside type="note" title="สองข้ออ้างก่อนหน้าในหน้านี้ ถูกถอนออกแล้ว">
หน้านี้เคยบอกว่าการย้าย CE ไปยังเวอร์ชันที่แตกต่างหมายความว่าต้องสร้างไซต์ใหม่
และการอัปเดตที่ถูกปฏิเสธ "ยังคงล้างฟิลด์บนเซิร์ฟเวอร์" ทำให้ Terraform เสนอการเปลี่ยนแปลงที่ล้มเหลวตลอดไป ไม่มีอันใดรอดการทดสอบ: การอัปเกรด API ด้านบนเริ่มการเปลี่ยนแปลงเวอร์ชันในสถานที่
โดยไม่ต้องสร้างอะไรใหม่ และหลังจากการอัปเดตที่ถูกปฏิเสธสามครั้ง สเปคของไซต์
**ไม่เปลี่ยนแปลง** และไซต์ยังคง `ONLINE` ต่อไป ความแตกต่างที่อธิบายไว้ใน provider issue `xcsh#1387` ถูกสังเกตบน
ไซต์ที่อัปเกรดอัตโนมัติเกินหมุดของมันไปแล้ว ดังนั้นอาจต้องมีสถานะเริ่มต้นที่แตกต่างนั้น
มันไม่ได้ถูกทำซ้ำบนไซต์ที่สเปคตรงกับหมุดของมัน
</Aside>

หากคุณสร้างใหม่แทนที่จะอัปเกรด ผลที่ตามมาทุกประการของการแทนที่ CE จะมีผลบังคับใช้

<Aside type="danger" title="ผลที่ตามมาทุกประการของการแทนที่ CE จะมีผลบังคับใช้">
SSH host keys ใหม่ ที่อยู่ภายในที่ถูกกำหนดใหม่ การลงทะเบียนใหม่ และการสูญเสีย
ทุกอย่างที่อยู่บนโหนดเท่านั้น Cloud-init จะรันอีกครั้งบน VM ใหม่ ดังนั้นการเข้าถึง SSH ที่กำหนดค่าด้วยวิธีนั้นจะรอดชีวิต — แต่มันรัน *เฉพาะ* ในการบูตครั้งแรกเท่านั้น ดังนั้นสิ่งใดก็ตามที่เพิ่มในโหนดเก่าด้วยมือจะหายไป

อ่าน [SSH](./access/ssh/) เกี่ยวกับผลที่ตามมาของ host key และที่อยู่ก่อนกำหนดการนี้
</Aside>

## บิลด์ที่ปักหมุดอาจล้มเหลวในการติดตั้ง และไซต์จะติดค้างอยู่

การยอมรับหมุดไม่เหมือนกับการติดตั้ง บน Customer Edge Azure Secure Mesh v2 แบบโหนดเดียวที่สร้างใหม่
ปักหมุดที่ `crt-20260201-0179` ออบเจกต์ไซต์รายงานเวอร์ชันที่ปักหมุดทันที — และการติดตั้งก็ล้มเหลว:

```text
site_state        PROVISIONING
phase             UPGRADE_FAILED
result            Failed
last_installed    (empty)
message           stage: 10, app: voucher obj: voucher objKind: DaemonSet failed ...
                  required replicas: 1, current replicas: 0
```

`สังเกตเมื่อ 2026-07-28` และทำซ้ำสองครั้งเมื่อ 2026-07-29 หมุด **ระบบปฏิบัติการ**
ติดตั้งตามปกติในการรันเดียวกัน (`9.2024.6` เป็น `9.2026.14`, `UPGRADE_COMPLETED`); เฉพาะการติดตั้งซอฟต์แวร์เท่านั้นที่ล้มเหลว ไซต์ไม่เคยถึง `ONLINE` และ `last_installed_version` ยังคงว่างเปล่า ดังนั้นจึงไม่มีการย้อนกลับไปยังบิลด์ที่ใช้งานได้ — ไม่มีการติดตั้งที่สำเร็จก่อนหน้าที่จะย้อนกลับไปได้

**ความล้มเหลวเมื่อสร้างไม่เหมือนกับความล้มเหลวระหว่างการอัปเกรด** ทั้งสองมีพฤติกรรมที่แตกต่างกันและ
ความแตกต่างมีความสำคัญเมื่อคุณกำลังตัดสินใจว่าจะเข้าแทรกแซงหรือไม่:

| | เมื่อสร้าง | ระหว่างการอัปเกรด API |
| --- | --- | --- |
| มันลองใหม่จนสำเร็จหรือไม่? | ไม่ — ค้างอยู่ที่ `Failed` เป็นเวลากว่า 20 นาที สองครั้ง | ใช่ — กู้คืนและเสร็จสมบูรณ์ |
| โหนดลงเอยที่ไหน? | `PROVISIONING` ไม่มีอะไรติดตั้ง | `ONLINE` บนบิลด์ที่ใช้งานได้ |
| ปลอดภัยหรือไม่ที่จะปล่อยทิ้งไว้? | ไม่ มันติดค้าง | ใช่ มันกู้คืนหรือเก็บบิลด์เก่าไว้ |

ดังนั้นความล้มเหลวเมื่อสร้างต้องการการสร้างใหม่พร้อมดิสก์ขนาดใหญ่ขึ้น ในขณะที่การอัปเกรดที่รายงาน `Failed`
ควรปล่อยทิ้งไว้สักครู่ก่อนที่คุณจะสรุปสิ่งใด

**สาเหตุคือดิสก์ ไม่ใช่เวอร์ชัน** เมทริกซ์ของซอฟต์แวร์ × OS × ขนาดดิสก์ หนึ่งไซต์ Azure Secure Mesh v2 แบบโหนดเดียวทิ้งแล้วต่อการรวมกัน และทั้งหมดมาจาก marketplace image เดียวกัน แยกมันออก `สังเกตเมื่อ 2026-07-29`:

| ซอฟต์แวร์ | OS `9.2024.6` (ที่ image จัดส่ง) | OS `9.2026.14` |
| --- | --- | --- |
| `crt-20250613-3382` | ติดตั้งสำเร็จ | ติดตั้งสำเร็จ |
| `crt-20260201-0179` | ติดตั้งสำเร็จ | **ล้มเหลว** เฉพาะบนดิสก์เริ่มต้นเท่านั้น |

ไม่มีเวอร์ชันใดที่ล้มเหลวเพียงลำพัง เฉพาะคู่เท่านั้นที่ล้มเหลว และเฉพาะบนดิสก์เริ่มต้นของ image — คู่เดียวกันติดตั้งบน **40 GB**, **48 GB** และ **64 GB** ดังนั้นบิลด์ที่ใหม่กว่าไม่ได้ไม่รองรับที่นี่ และระบบปฏิบัติการที่ใหม่กว่าก็ไม่ใช่; เมื่อรวมกันแล้วต้องการดิสก์มากกว่าที่โหนดเริ่มต้นมี

`terraform/modules/ce-node` ไม่ได้ตั้งค่า `disk_size_gb` ดังนั้น Customer Edge ทุกตัวจะได้รับค่าเริ่มต้นของ image **ในการรันคู่ที่ใหม่กว่า ให้ขยายดิสก์** 40 GB คือขนาดเล็กที่สุดที่ทดสอบแล้วใช้งานได้ ขอบเขตที่แน่นอนอยู่ระหว่างค่าเริ่มต้นของ image และ 40 GB และไม่ได้ระบุให้แคบลงกว่านี้

ทดสอบการเปลี่ยนเวอร์ชันบนไซต์ทิ้งแล้วก่อนนำไปใช้กับ fleet โดยไม่คำนึงถึง: fleet ที่ล้มเหลวในลักษณะนี้จะติดค้างใน `PROVISIONING` โดยมีการสร้างใหม่เป็นทางออกเดียว

<Aside type="caution" title="อย่ากำหนดขนาดดิสก์จากตัวเลขก่อนอัปเกรดของ F5">
การตรวจสอบก่อนอัปเกรดที่ F5 บันทึกไว้ต้องการพื้นที่ว่าง 20 GB บวก 15% ของความจุ การตรวจสอบนั้นควบคุมการอัปเกรด **Console UI** และชัดเจนว่าไม่ได้ใช้กับการอัปเกรดที่เริ่มต้นผ่าน API ดังนั้นมันจึงไม่ได้อธิบายความล้มเหลวนี้ เมื่อนำมาใช้ที่นี่มันทำนายว่าดิสก์ 48 GB จะล้มเหลว; 48 GB ติดตั้งได้อย่างสะอาด กำหนดขนาดจากผลลัพธ์ที่วัดได้ด้านบน ไม่ใช่จากสูตรนั้น
</Aside>

<Aside type="note" title="คำอธิบายที่หน้านี้เคยเสนอ ถูกถอนออกแล้ว">
เวอร์ชันก่อนหน้าของหน้านี้แนะนำว่าการติดตั้งล้มเหลวเนื่องจากบิลด์ที่ขอเก่ากว่า image —
ว่าโหนดถูกขอให้เคลื่อนที่ถอยหลัง นั่นผิด Fleet นี้ถูกสร้างจาก image เดียวกันพร้อมหมุดที่เก่ากว่า **สิบสามเดือน** และติดตั้งได้ตามปกติ
และ `crt-20260201-0179` ก็ติดตั้งได้เช่นกันเมื่อหมุด OS ยังอยู่ที่เวอร์ชันของ image เอง ทิศทางการเดินทางไม่ใช่ตัวแปร
</Aside>

## บิลด์ใดที่เอกสารนี้อธิบาย

เอกสารอ้างอิงคำสั่งบนไซต์นี้อธิบาย **`crt-20250613-3382`** บิลด์ที่ fleet นี้รัน คำสั่งที่มีเฉพาะในบิลด์ที่ใหม่กว่าถูกบันทึกไว้ใน
`sitecli/command-classification.json` ภายใต้ `not_on_this_build` และบันทึกแยกกัน ดังที่
[คำสั่งบนบิลด์ที่ใหม่กว่า](./commands/on-box/newer-builds/) ดังนั้นไม่มีอะไรที่นั่นที่อ่านว่าสามารถรันได้ที่นี่ ดูเพิ่มเติมที่ [คำสั่งในกล่อง](./commands/on-box/)

<Aside type="note" title="การเข้าถึงบิลด์ที่ใหม่กว่าได้รับการยุติธรรม และไม่ใช่การสร้างใหม่">
สิ่งนี้เคยถูกบันทึกไว้ที่นี่ว่ายังไม่ได้รับการยุติ พร้อมรายงานของบิลด์ที่ใหม่กว่าที่ล้มเหลวบนไซต์ Azure Secure Mesh v2 แบบโหนดเดียวเทียบกับการสังเกตตรงกันข้ามของหนึ่งที่รันมันอยู่ ทั้งสองได้รับการอธิบายแล้ว: บิลด์ที่ใหม่กว่าติดตั้งได้บนโทโพโลยีนั้น และความล้มเหลวคือขีดจำกัดดิสก์ด้านบน ไม่ใช่บิลด์

ดังนั้นมีสองเส้นทางและไม่มีเส้นทางใดที่ต้องการการสร้างใหม่เพื่อตัวมันเอง — สร้างโหนดที่มีดิสก์ขนาดใหญ่พอ หรืออัปเกรดโหนดที่มีอยู่ผ่าน API `สังเกตเมื่อ 2026-07-29`
</Aside>
