ตัวแปร Terraform สองตัวกำหนดซอฟต์แวร์ของ Customer Edge: `ce_os_version` สำหรับระบบปฏิบัติการ
และ `ce_sw_version` สำหรับบิลด์ F5 Distributed Cloud ทั้งสองทำงานในลักษณะที่ตรงกันข้ามกับการอ่านค่าแบบเข้าใจง่าย
และต้นทุนของความผิดพลาดคือการสร้างฝูงเครื่องใหม่ทั้งหมด

## สิ่งที่ฟิลด์เวอร์ชันทำ แบ่งเป็นสองระยะ

การแยกระยะออกจากกันคือหัวใจสำคัญของเรื่องนี้ หากรวมกัน พฤติกรรมจะดูขัดแย้งกันเอง

**ในการบูตครั้งแรก โหนดจะติดตั้งสิ่งที่ `ce_sw_version` ระบุไว้**
`terraform/modules/ce-node` ใช้งาน marketplace image ด้วย `version = "latest"` ดังนั้น
บิลด์ที่โหนดได้รับมาคือสิ่งที่ image นั้นส่งมาในขณะนั้น — และสิ่งนี้เปลี่ยนแปลงตามเวลา
`ce_sw_version` เลือก **ปลายทาง** ไม่ใช่ว่าจะมีอะไรเกิดขึ้นหรือไม่ และการเว้นว่างหมายความว่าเซิร์ฟเวอร์เป็นผู้เลือก ไม่ใช่ว่าโหนดจะอยู่นิ่ง เช่นเดียวกันกับ `ce_os_version`

อย่าคิดว่าทิศทางของการเปลี่ยนแปลงนั้นจะเป็นการอัปเกรด `ตรวจสอบเมื่อ 2026-07-28` image
ส่งบิลด์ที่ประทับว่า `20260703-e2c462a` — ใหม่กว่า `crt-20250613-3382` ของฝูงเครื่องนี้
และใหม่กว่า `crt-20260201-0179` ที่ tenant ประกาศไว้ **การระบุบิลด์ที่เก่ากว่าที่ image บรรจุมาจะขอให้โหนดถอยหลัง และนั่นอาจล้มเหลวได้** — ดูความล้มเหลวด้านล่าง

**หลังจากนั้น ไม่มีอะไรอัปเกรดเองโดยอัตโนมัติ** F5 Distributed Cloud ประกาศบิลด์ใหม่กว่าและรอ
การเว้นฟิลด์ว่างไว้จึงไม่ใช่ "ติดตามเวอร์ชันล่าสุด": โหนดจะอยู่ที่ที่ลงทะเบียนครั้งแรก

ทั้งสองระยะมองเห็นได้จาก site object `ตรวจสอบเมื่อ 2026-07-28` ฝูงเครื่องนี้:

```text
volterra_software_status.available_version   crt-20260201-0179
operating_system_status.available_version    9.2026.14
```

ในขณะที่โหนดรัน `crt-20250613-3382` และ OS `9.2024.6` บิลด์ใหม่กว่าถูกเสนอไว้และยังไม่ได้ถูกนำมาใช้ — นี่คือสถานะปกติ ไม่ใช่การอัปเกรดที่ค้างอยู่

## การเปลี่ยนเวอร์ชันต้องการการสร้างใหม่ และ Terraform จะไม่ทำให้คุณ

`ce_os_version` และ `ce_sw_version` ต่างเป็น **create-time only** และโหมดความล้มเหลวนั้นแย่กว่าการถูกปฏิเสธ apply ตามลำดับ:

1. คุณเปลี่ยนค่าและ apply Terraform เสนอการอัปเดตแบบ in-place
2. API **ปฏิเสธ** มัน — `[BAD_REQUEST] Invalid request parameters`
3. คำขอที่ถูกปฏิเสธนั้นยังล้างฟิลด์บนเซิร์ฟเวอร์ และการอ่านค่าของ provider ไม่รายงานสิ่งนั้น State ของ Terraform ขณะนี้ขัดแย้งกับ live object
4. ทุก plan ที่ตามมาจะเสนอ **การเปลี่ยนแปลงที่ล้มเหลวแบบเดิม** ซ้ำแล้วซ้ำเล่าอย่างไม่มีกำหนด

ดังนั้น Terraform จึงไม่ fallback ไปแทนที่ site มันติดค้าง และจะติดค้างอยู่อย่างนั้น
จนกว่าคุณจะแทนที่ site และ CE virtual machine นั้นโดยตั้งใจ การย้ายฝูงเครื่องไปยังเวอร์ชันอื่น
คือ **การสร้างใหม่ที่คุณต้องวางแผน** ไม่ใช่การแก้ไขที่คุณ apply

<Aside type="danger" title="ผลกระทบทั้งหมดของการแทนที่ CE นั้นมีผลบังคับ">
SSH host key ใหม่ ที่อยู่ภายในที่ถูกกำหนดใหม่ การลงทะเบียนใหม่ และการสูญเสียทุกอย่างที่อยู่เฉพาะบนโหนด cloud-init รันอีกครั้งบน VM ใหม่ ดังนั้น SSH access ที่กำหนดค่าไว้ในลักษณะนั้นจะยังคงอยู่ — แต่รัน *เฉพาะ* ครั้งแรกที่บูต ดังนั้นทุกสิ่งที่เพิ่มเข้าไปในโหนดเก่าด้วยมือจะหายไป

อ่าน [SSH](./access/ssh/) เกี่ยวกับผลกระทบของ host key และที่อยู่ก่อนกำหนดเวลานี้
</Aside>

<Aside type="note" title="รายงานไว้แล้ว ไม่ได้ทดสอบซ้ำที่นี่">
การปฏิเสธและ state divergence ถูกบันทึกไว้ใน comment ของ `terraform/modules/xc-site` ในที่เก็บนี้ — ยืนยันแล้วทั้งสองทิศทาง ทั้งการ pin และการ unpin บนทั้งสาม site — และกับ provider issue `xcsh#1387` หน้านี้ยังไม่ได้ทดสอบซ้ำ เพราะการทดสอบจะทิ้ง deployment ไว้ในสถานะเสนอการเปลี่ยนแปลงที่ล้มเหลวทุกครั้งที่ plan
</Aside>

## บิลด์ที่ถูก pin ไว้อาจติดตั้งไม่สำเร็จ และ site จะติดค้าง

การยอมรับ pin ไม่เหมือนกับการติดตั้งมันสำเร็จ บน Customer Edge แบบ Azure Secure Mesh v2 single-node ที่เพิ่งสร้างและถูก pin ไปที่ `crt-20260201-0179` site object รายงานเวอร์ชันที่ถูก pin ทันที — แต่การติดตั้งล้มเหลว:

```text
site_state        PROVISIONING
phase             UPGRADE_FAILED
result            Failed
last_installed    (empty)
message           stage: 10, app: voucher obj: voucher objKind: DaemonSet failed ...
                  required replicas: 1, current replicas: 0
```

`ตรวจสอบเมื่อ 2026-07-28` การ pin **ระบบปฏิบัติการ** ติดตั้งสำเร็จในการรันเดียวกัน
(`9.2024.6` เป็น `9.2026.14`, `UPGRADE_COMPLETED`); เฉพาะการติดตั้งซอฟต์แวร์ที่ล้มเหลว site ไม่เคยถึง `ONLINE` และ `last_installed_version` ยังคงว่างเปล่า ดังนั้นจึงไม่มีการ rollback ไปยังบิลด์ที่ทำงานได้ — ไม่มีการติดตั้งก่อนหน้าที่สำเร็จให้ rollback กลับไป

**สิ่งที่ควรเรียนรู้จากนี้** เวอร์ชันที่รันที่อื่นได้ไม่ใช่หลักฐานว่ามันจะติดตั้งได้บน site รูปแบบของคุณ บิลด์เดียวกันนั้น `ONLINE` บน Azure Customer Edge ที่ไม่ใช่ Secure Mesh v2 และบน Secure Mesh v2 site บน VMware; การผสมผสานที่ล้มเหลวคือ Azure *และ* Secure Mesh v2 ทดสอบการเปลี่ยนเวอร์ชันบน site แบบใช้แล้วทิ้งก่อนนำไปใช้กับฝูงเครื่อง เพราะฝูงเครื่องที่ล้มเหลวในลักษณะนี้จะติดค้างอยู่ใน `PROVISIONING` โดยมีการสร้างใหม่เป็นทางออกเดียว

<Aside type="caution" title="เหตุใดหน้านี้จึงไม่บอกสาเหตุ">
บิลด์ที่ร้องขอนั้น **เก่ากว่า** บิลด์ที่ marketplace image ส่งมา ดังนั้นโหนดจึงถูกขอให้ถอยหลัง นั่นเป็นคำอธิบายที่น่าเชื่อสำหรับความล้มเหลวและ **ยังไม่ได้รับการยืนยัน**: string ของเวอร์ชันทั้งสอง (`20260703-e2c462a` และ `crt-20260201-0179`) ไม่ทราบว่าใช้รูปแบบการนับเลขเดียวกัน และไม่มี capture จากโหนดในฝูงเครื่องสำหรับเปรียบเทียบ ความล้มเหลวและลำดับเวอร์ชันเป็นสิ่งที่สังเกตได้; การเชื่อมโยงระหว่างทั้งสองยังไม่ชัดเจน
</Aside>

## บิลด์ที่เอกสารนี้อธิบาย

คู่มือคำสั่งบนไซต์นี้อธิบาย **`crt-20250613-3382`** ซึ่งเป็นบิลด์ที่ฝูงเครื่องนี้รันอยู่ คำสั่งที่มีเฉพาะบนบิลด์ใหม่กว่าถูกบันทึกไว้ใน
`sitecli/command-classification.json` ภายใต้ `not_on_this_build` และจัดทำเอกสารแยกต่างหาก เป็น
[คำสั่งบนบิลด์ใหม่กว่า](./commands/on-box/newer-builds/) ดังนั้นจึงไม่มีสิ่งใดที่นั่นที่อ่านแล้วดูเหมือนรันได้ที่นี่ ดูเพิ่มเติมที่ [on-box commands](./commands/on-box/)

<Aside type="caution" title="อย่าวางแผนการสร้างใหม่เพื่อเข้าถึงคำสั่งใหม่กว่า">
บิลด์ใหม่กว่ากำลังถูกเสนอ และว่ามันจะติดตั้งได้อย่างสะอาดบน topology นี้หรือไม่ยังไม่แน่ชัด — มีรายงานว่าล้มเหลวบน single-node Azure Secure Mesh v2 site และมีการสังเกตย้อนแย้งว่า Customer Edge กำลังรันมันอยู่ ไม่มีสิ่งใดที่สามารถยืนยันได้จากสิ่งที่เหลืออยู่ใน tenant

เนื่องจากการเปลี่ยนเวอร์ชันคือการสร้างฝูงเครื่องใหม่ ความไม่แน่นอนนั้นจึงเป็นข้อเท็จจริงที่สำคัญ: ให้ถือว่าการเข้าถึงคำสั่งเหล่านั้นยังไม่ได้รับการพิสูจน์ ไม่ใช่การอัปเกรดที่กำหนดเวลาไว้ หลักฐานและการทดลองที่จะยุติข้อสงสัยนั้นถูกบันทึกไว้ใน `sitecli/README.md`
</Aside>
