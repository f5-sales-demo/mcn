ตัวแปร Terraform สองตัวกำหนดซอฟต์แวร์ของ Customer Edge ได้แก่ `ce_os_version` สำหรับระบบปฏิบัติการ และ `ce_sw_version` สำหรับบิลด์ F5 Distributed Cloud ทั้งสองมีพฤติกรรมที่ตรงข้ามกับการอ่านที่ชัดเจน และต้นทุนของการทำผิดพลาดคือการสร้างกลุ่มใหม่ทั้งหมด

## สิ่งที่ฟิลด์เวอร์ชันทำ แบ่งเป็นสองระยะ

การแยกระยะออกจากกันคือประเด็นสำคัญทั้งหมด หากรวมกัน พฤติกรรมจะดูเหมือนขัดแย้งในตัวเอง

**ในการบูตครั้งแรก โหนดจะอัปเกรดเสมอ** `terraform/modules/ce-node` ปรับใช้อิมเมจ Marketplace ด้วย `version = "latest"` และอิมเมจนั้นมาพร้อมบิลด์ที่ **เก่ากว่า** สิ่งที่ tenant รัน ดังนั้นการอัปเกรดจะเกิดขึ้นไม่ว่าคุณจะตั้งค่าฟิลด์หรือไม่ก็ตาม `ce_sw_version` เลือกเฉพาะ **ปลายทาง** เท่านั้น — และการปล่อยให้ว่างเปล่าหมายความว่าเซิร์ฟเวอร์เป็นผู้เลือก ไม่ใช่ว่าไม่มีอะไรเกิดขึ้น เช่นเดียวกันกับ `ce_os_version`

**หลังจากนั้น ไม่มีอะไรอัปเกรดเองโดยอัตโนมัติ** F5 Distributed Cloud แจ้งบิลด์ใหม่และรอ การปล่อยฟิลด์ว่างเปล่าจึงไม่ใช่ "ติดตามเวอร์ชันล่าสุด": โหนดจะคงอยู่ที่จุดที่ลงทะเบียนไว้ครั้งแรก

ทั้งสองระยะปรากฏบนออบเจกต์ไซต์ จากการสังเกตเมื่อ `2026-07-28` กลุ่มนี้:

```text
volterra_software_status.available_version   crt-20260201-0179
operating_system_status.available_version    9.2026.14
```

ขณะที่โหนดรัน `crt-20250613-3382` และ OS `9.2024.6` บิลด์ใหม่กว่ามีให้ใช้งานแต่ยังไม่ได้รับการติดตั้ง — นี่คือสถานะปกติ ไม่ใช่การอัปเกรดที่ค้างอยู่

## การเปลี่ยนเวอร์ชันต้องสร้างใหม่ และ Terraform จะไม่ทำให้คุณ

`ce_os_version` และ `ce_sw_version` ทั้งคู่เป็น **create-time only** และรูปแบบความล้มเหลวนั้นแย่กว่าการปฏิเสธ apply ตามลำดับดังนี้:

1. คุณเปลี่ยนค่าและ apply Terraform เสนอการอัปเดตในที่เดิม
2. API **ปฏิเสธ** — `[BAD_REQUEST] Invalid request parameters`
3. คำขอที่ถูกปฏิเสธนั้นยังคงล้างฟิลด์บนเซิร์ฟเวอร์ และการอ่านของ provider ไม่รายงานสิ่งนั้น สถานะของ Terraform ตอนนี้ขัดแย้งกับออบเจกต์จริง
4. ทุก plan ที่ตามมาจะเสนอ **การเปลี่ยนแปลงที่ล้มเหลวเดิม** ซ้ำอย่างไม่มีกำหนด

ดังนั้น Terraform จึงไม่ fallback ไปแทนที่ไซต์ มันติดขัดและจะยังติดขัดต่อไปจนกว่าคุณจะแทนที่ไซต์และเครื่องเสมือน CE อย่างตั้งใจ การย้ายกลุ่มไปยังเวอร์ชันอื่นคือ **การสร้างใหม่ที่คุณวางแผน** ไม่ใช่การแก้ไขที่คุณ apply

<Aside type="danger" title="ผลที่ตามมาทุกประการของการแทนที่ CE ใช้บังคับ">
SSH host keys ใหม่ ที่อยู่ภายในที่ถูกกำหนดใหม่ การลงทะเบียนใหม่ และการสูญเสียทุกสิ่งที่อยู่บนโหนดเท่านั้น Cloud-init รันอีกครั้งบน VM ใหม่ ดังนั้นการเข้าถึง SSH ที่กำหนดค่าด้วยวิธีนั้นจะยังคงอยู่ — แต่รันเฉพาะในการบูตครั้งแรกเท่านั้น ดังนั้นสิ่งที่เพิ่มลงในโหนดเก่าด้วยมือจะหายไป

อ่าน [SSH](./access/ssh/) เกี่ยวกับผลของ host-key และที่อยู่ก่อนกำหนดเวลานี้
</Aside>

<Aside type="note" title="รายงานไว้แล้ว ไม่ได้ทดสอบซ้ำที่นี่">
การปฏิเสธและความแตกต่างของสถานะถูกบันทึกไว้ในความคิดเห็นของ `terraform/modules/xc-site` ในที่เก็บนี้ — ยืนยันแล้วในทั้งสองทิศทาง ทั้งการตรึงและการยกเลิกการตรึง บนทั้งสามไซต์ — และเทียบกับ provider issue `xcsh#1387` หน้านี้ไม่ได้ทดสอบซ้ำ เนื่องจากการทดสอบจะทำให้การปรับใช้เสนอการเปลี่ยนแปลงที่ล้มเหลวในทุก plan
</Aside>

## บิลด์ที่เอกสารอธิบาย

เอกสารอ้างอิงคำสั่งบนไซต์นี้อธิบาย **`crt-20250613-3382`** ซึ่งเป็นบิลด์ที่กลุ่มนี้รัน คำสั่งที่สังเกตพบเฉพาะในบิลด์ใหม่กว่าจะถูกบันทึกตามชื่อใน `sitecli/command-classification.json` ภายใต้ `not_on_this_build` และไม่ได้รับการจัดทำเอกสารว่าสามารถรันได้ ดูที่ [คำสั่ง on-box](./commands/on-box/)

<Aside type="caution" title="อย่าวางแผนการสร้างใหม่เพื่อเข้าถึงคำสั่งใหม่กว่า">
บิลด์ใหม่กว่ามีให้ใช้งาน และไม่ว่าจะติดตั้งได้อย่างราบรื่นบน topology นี้ยังไม่ชัดเจน — มีรายงานว่าล้มเหลวบนไซต์ Azure Secure Mesh v2 แบบโหนดเดียว และมีการสังเกตที่ขัดแย้งกันของ Customer Edge ที่รันอยู่ ไม่สามารถยืนยันทั้งคู่จากสิ่งที่เหลืออยู่ใน tenant

เนื่องจากการเปลี่ยนเวอร์ชันคือการสร้างกลุ่มใหม่ ความไม่แน่นอนนั้นจึงเป็นข้อเท็จจริงที่ต้องคำนึงถึง: ถือว่าการเข้าถึงคำสั่งเหล่านั้นยังไม่ได้รับการพิสูจน์ ไม่ใช่การอัปเกรดที่กำหนดเวลาไว้ หลักฐานและการทดลองที่จะยุติข้อสงสัยนี้ถูกบันทึกไว้ใน `sitecli/README.md`
</Aside>
