มีสี่เส้นทางที่ใช้งานได้ และเส้นทางที่ใช้ได้นั้นถูกกำหนดโดยสถานะของโหนด, ตำแหน่งที่คุณเชื่อมต่อจาก และสิ่งที่คุณต้องการเข้าถึง — ไม่ใช่ตามความต้องการส่วนตัว

| เส้นทาง | ต้องการโหนด `ONLINE` | ต้องการการเข้าถึงเครือข่าย | ข้อจำกัด | ครอบคลุม |
| --- | --- | --- | --- | --- |
| [Debug API](./debug-api/) | **ใช่** | ใช่ | ใช้เวลาประมาณ 25–30 นาทีในการ warm-up บนไซต์ใหม่ | 34 คำสั่ง |
| [Site Console](./site-console/) | ไม่ | ผ่าน Azure Bastion ไม่ต้องใช้ jump host | Bastion ต้องเป็น Standard SKU ที่รองรับ tunneling | UI สำหรับแก้ไขปัญหาโหนดของ F5 |
| [SSH](./ssh/) | ไม่ | จากภายใน VNet ไปยังที่อยู่ภายในเท่านั้น | ต้องมี key ตั้งแต่การบูตครั้งแรก | Site CLI บนเครื่องแบบครบถ้วน |
| [Serial console](./serial-console/) | ไม่ | ไม่ | หนึ่งเซสชันต่อ VM; จำกัดการวางข้อความ 2,048 ตัวอักษร | Site CLI บนเครื่องแบบครบถ้วน |

Serial console คือทางเลือกสุดท้าย และเป็นเส้นทางเดียวที่ยังคงทำงานได้เมื่อโหนดไม่มีเส้นทางเครือข่ายที่ใช้งานได้

[Site Console](./site-console/) มักเป็นตัวเลือกแรกที่ควรลอง เพราะต้องการน้อยที่สุดจากคุณ —
ไม่ต้องแจกจ่าย SSH key, ไม่ต้องใช้ jump host, ไม่ต้องมี public IP บนโหนด และไม่ต้องเปลี่ยน VM —
เพราะการเข้าถึงกลายเป็นการตัดสินใจด้าน Azure RBAC แทนที่จะเป็นปัญหาการแจกจ่ายข้อมูลประจำตัว
มันให้ UI สำหรับแก้ไขปัญหาของ F5 เองแทนที่จะเป็น command surface ดังนั้นให้ข้ามไปใช้เส้นทางอื่น
เมื่อคุณต้องการรันคำสั่งเฉพาะหรือทำ script ใดๆ

SSH คือทางเลือกเมื่อ debug API ไม่เพียงพอ เพราะ appliance มีคำสั่งมากกว่า 34 คำสั่งที่ API เปิดเผยอยู่มาก
มันมีค่าใช้จ่ายสองอย่าง: key ถูกเขียนโดย cloud-init ดังนั้นต้องมีอยู่ตั้งแต่ **การบูตครั้งแรก**
ซึ่งหมายความว่าการเปิดใช้งานบนโหนดที่กำลังทำงานอยู่จะแทนที่โหนดเหล่านั้น — และปัจจุบันทำให้การลงทะเบียนติดขัด
([issue 674](https://github.com/f5-sales-demo/mcn/issues/674)) และ `sshd` ตอบสนองที่ที่อยู่ภายในของโหนดเท่านั้น
ดังนั้นจึงต้องมีเครื่องโฮสต์ภายใน VNet; การตรวจสอบที่อยู่ที่คุณรู้จักโหนดจะรายงานว่าปิดอยู่เสมอ

## เหตุใดการแบ่งแยกนี้จึงไม่ใช่ความต้องการส่วนตัว

Debug API ให้บริการโดย control plane ของ F5 Distributed Cloud ซึ่งส่งต่อไปยังโหนด
ผ่านอุโมงค์ที่ `vpm` สร้างขึ้นระหว่างการลงทะเบียน การไม่มีการลงทะเบียนหมายความว่าไม่มีอุโมงค์
ซึ่งหมายความว่า API ไม่มีอะไรให้ส่งต่อไป

มันล้มเหลวในลักษณะที่ไม่เป็นประโยชน์แทนที่จะเป็นลักษณะที่ชัดเจน ดังนั้นโหนดที่ไม่เคยเริ่มทำงาน
จึงดูเหมือนปัญหาของ API

Serial console ไปในทิศทางตรงกันข้ามอย่างสิ้นเชิง — ผ่านแพลตฟอร์ม Azure ไปยัง
serial port จำลองของโหนด ไม่สนใจว่าโหนดได้ลงทะเบียนแล้วหรือไม่, มีการเข้าถึงเครือข่ายหรือไม่
หรือมี data plane ที่ทำงานอยู่หรือไม่ ความเป็นอิสระนั้นคือจุดประสงค์ทั้งหมด
และนั่นคือเหตุผลที่ boot diagnostics ต้องเปิดใช้งานบน CE VM เสมอ

<Aside type="note" title="สิ่งที่ควรเลือกใช้">
หากคุณกำลังเขียนการทำงานอัตโนมัติ หรือรวบรวมหลักฐานที่คุณต้องการรันซ้ำในภายหลัง ให้ใช้
debug API หากการลงทะเบียนคือสิ่งที่เสียหาย serial console ไม่ใช่ทางเลือกสำรอง — มันคือตัวเลือกเดียว
</Aside>

## ข้อมูลประจำตัว

แต่ละเส้นทางใช้ข้อมูลประจำตัวที่แตกต่างกัน และไม่มีสิ่งใดที่ควรอยู่บน command line

- **Debug API** — F5 Distributed Cloud API token เป็น `XCSH_API_TOKEN` พร้อม
  URL ของ tenant เป็น `XCSH_API_URL` ไฟล์ context ของ `xcsh` ที่
  `~/.config/xcsh/contexts/<tenant>.json` เก็บทั้งสองอย่าง ซึ่งเป็นสิ่งที่
  `scripts/capture-sitecli.sh` อ่านเมื่อ environment ไม่ได้จัดหาให้
- **SSH** — ครึ่งส่วนของ private key ของคู่ keypair ที่ครึ่งส่วน public ถูก deployment เขียนลงใน
  `/var/home/admin/.ssh/authorized_keys` ตั้งแต่การบูตครั้งแรก บวกกับเครื่องโฮสต์ภายใน VNet
  เพื่อเข้าถึงที่อยู่ภายในผ่าน เชื่อมต่อในชื่อ `admin` ไม่ใช่ `azureuser`
- **Serial console** — การล็อกอิน Azure แบบ interactive ของคุณ ไม่มี service principal
  สำหรับเส้นทางนี้: F5 corporate Entra tenant ไม่อนุญาตให้จัดสร้าง ซึ่งเป็นเหตุผลด้วยว่า
  ไม่มีส่วนใดของเส้นทางนี้ที่ทำงานใน CI

<Aside type="danger" title="อย่าส่ง token เป็น argument">
Token บน command line จะถูกบันทึกใน shell history และใน process list ซึ่ง
ผู้ใช้รายอื่นทุกคนบนเครื่องสามารถอ่านได้ `capture-sitecli.sh` ปฏิเสธ
`--token` โดยตรงด้วยเหตุผลนั้น และส่ง header ไปยัง `curl` ผ่าน stdin
แทน
</Aside>
