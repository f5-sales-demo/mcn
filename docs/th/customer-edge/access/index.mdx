มีสองเส้นทาง และเส้นทางที่ใช้นั้นถูกตัดสินโดยสถานะของโหนด ไม่ใช่ตามความต้องการ

| สถานะโหนด | เส้นทาง | รองรับการทำงานอัตโนมัติ | ครอบคลุม |
| --- | --- | --- | --- |
| `ONLINE` | [Debug API](./debug-api/) | ใช่ | 34 คำสั่ง อ่านอย่างเดียวและสิทธิ์พิเศษ |
| ยังไม่ได้ลงทะเบียน หรือเข้าไม่ถึง | [Serial console](./serial-console/) | ไม่ — ต้องใช้เทอร์มินัล | Site CLI แบบเต็มบนอุปกรณ์ |

## เหตุใดการแยกนี้จึงไม่ใช่เรื่องของความต้องการ

Debug API ให้บริการโดย control plane ของ F5 Distributed Cloud ซึ่งส่งต่อไปยังโหนดผ่านอุโมงค์ที่ `vpm` สร้างขึ้นในระหว่างการลงทะเบียน หากไม่มีการลงทะเบียน ก็ไม่มีอุโมงค์ ซึ่งหมายความว่า API ไม่มีอะไรให้ส่งต่อ

มันล้มเหลวในแบบที่ไม่เป็นประโยชน์แทนที่จะเป็นแบบที่ชัดเจน ดังนั้นโหนดที่ไม่เคยออนไลน์จึงดูเหมือนปัญหา API

Serial console ทำงานในทางตรงข้ามอย่างสิ้นเชิง — ผ่านแพลตฟอร์ม Azure ไปยังพอร์ตซีเรียลจำลองของโหนด ไม่ว่าโหนดจะลงทะเบียนแล้ว มีการเข้าถึงเครือข่าย หรือมี data plane ที่ทำงานได้ ล้วนไม่มีผลต่อการทำงานของ Serial console ความเป็นอิสระนี้คือจุดประสงค์หลักทั้งหมด และนั่นคือเหตุผลที่ boot diagnostics ต้องเปิดใช้งานบน CE VMs อยู่เสมอ

<Aside type="note" title="สิ่งที่ควรเลือกใช้">
หากคุณกำลังเขียนการทำงานอัตโนมัติ หรือรวบรวมหลักฐานที่ต้องการรันซ้ำในภายหลัง ให้ใช้
debug API หากการลงทะเบียนคือสิ่งที่เสียหาย Serial console ไม่ใช่ตัวเลือกสำรอง — มันคือตัวเลือกเดียว
</Aside>

## ข้อมูลรับรองตัวตน

ทั้งสองเส้นทางใช้ข้อมูลรับรองตัวตนที่แตกต่างกัน และไม่มีข้อมูลใดที่ควรอยู่ในบรรทัดคำสั่ง

- **Debug API** — โทเค็น API ของ F5 Distributed Cloud ในรูปแบบ `XCSH_API_TOKEN` โดยมี URL ของ tenant เป็น `XCSH_API_URL` ไฟล์ context ของ `xcsh` ที่
  `~/.config/xcsh/contexts/<tenant>.json` จัดเก็บทั้งสองค่า ซึ่งเป็นสิ่งที่
  `scripts/capture-sitecli.sh` อ่านเมื่อ environment ไม่ได้ระบุค่าเหล่านั้นมา
- **Serial console** — การเข้าสู่ระบบ Azure แบบโต้ตอบของคุณ ไม่มี service principal สำหรับกรณีนี้: tenant Entra ขององค์กร F5 ไม่อนุญาตให้จัดเตรียม service principal ดังกล่าว ซึ่งเป็นเหตุผลที่ไม่มีส่วนใดทำงานใน CI

<Aside type="danger" title="อย่าส่งโทเค็นเป็น argument">
โทเค็นในบรรทัดคำสั่งจะถูกบันทึกใน shell history และใน process list ซึ่งผู้ใช้คนอื่นบนเครื่องสามารถอ่านได้ `capture-sitecli.sh` ปฏิเสธ
`--token` โดยตรงด้วยเหตุผลนี้ และส่ง header ไปยัง `curl` ผ่าน stdin
แทน
</Aside>
