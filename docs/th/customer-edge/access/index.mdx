มีสามเส้นทางที่ใช้ได้ และเส้นทางใดจะใช้ได้นั้นถูกกำหนดโดยสถานะของโหนดและตำแหน่งที่คุณเชื่อมต่อมา
มากกว่าจะเป็นเรื่องของความชอบส่วนตัว

| เส้นทาง | ต้องการโหนดสถานะ `ONLINE` | ต้องการการเข้าถึงผ่านเครือข่าย | ข้อจำกัด | ครอบคลุม |
| --- | --- | --- | --- | --- |
| [Debug API](./debug-api/) | **ใช่** | ใช่ | ประมาณ 25–30 นาทีสำหรับการวอร์มอัพในไซต์ใหม่ | 34 คำสั่ง |
| [SSH](./ssh/) | ไม่ | จากภายใน VNet ไปยังที่อยู่ภายในเท่านั้น | ต้องมีคีย์อยู่ตั้งแต่การบูตครั้งแรก | Site CLI บนเครื่องแบบครบถ้วน |
| [Serial console](./serial-console/) | ไม่ | ไม่ | หนึ่งเซสชันต่อหนึ่ง VM; จำกัดการวาง 2,048 อักขระ | Site CLI บนเครื่องแบบครบถ้วน |

Serial console คือทางเลือกสุดท้าย และเป็นเส้นทางเดียวที่ยังใช้งานได้กับโหนดที่ไม่มีเส้นทางเครือข่าย
ที่ใช้งานได้เลย

SSH คือสิ่งที่ควรเลือกใช้เมื่อ debug API ไม่เพียงพอ เพราะอุปกรณ์มีคำสั่งมากกว่า 34 คำสั่งที่ API
เปิดเผยอยู่มาก แต่มีต้นทุนสองอย่าง คีย์ถูกเขียนโดย cloud-init จึงต้องมีอยู่ตั้งแต่**การบูตครั้งแรก**
ซึ่งหมายความว่าการเปิดใช้งานบนโหนดที่กำลังทำงานอยู่จะเป็นการแทนที่โหนดนั้น — และปัจจุบันสิ่งนี้
ทำให้การลงทะเบียนติดขัด ([issue 674](https://github.com/f5-sales-demo/mcn/issues/674)) และ `sshd`
ตอบสนองเฉพาะที่อยู่ภายในของโหนดเท่านั้น จึงจำเป็นต้องมีโฮสต์อยู่ภายใน VNet; การตรวจสอบที่อยู่
ที่คุณรู้จักโหนดนั้นจะรายงานว่าปิดอยู่เสมอ

## เหตุใดการแบ่งแยกนี้จึงไม่ใช่เรื่องความชอบ

Debug API ให้บริการโดยคอนโทรลเพลนของ F5 Distributed Cloud ซึ่งส่งต่อไปยังโหนดผ่านทันเนล
ที่ `vpm` สร้างขึ้นระหว่างการลงทะเบียน หากไม่มีการลงทะเบียนก็ไม่มีทันเนล ซึ่งหมายความว่า
API ไม่มีปลายทางให้ส่งต่อ

มันล้มเหลวในลักษณะที่ไม่ช่วยอะไรมากกว่าจะเป็นแบบที่ชัดเจน ดังนั้นโหนดที่ไม่เคยทำงานขึ้นมาเลย
จึงดูเหมือนเป็นปัญหาของ API

Serial console ทำงานในทางตรงกันข้ามโดยสิ้นเชิง — ผ่านแพลตฟอร์ม Azure ไปยังพอร์ตอนุกรม
จำลองของโหนด มันไม่สนใจว่าโหนดได้ลงทะเบียนแล้วหรือไม่ มีการเข้าถึงผ่านเครือข่ายหรือไม่
หรือมีดาต้าเพลนที่ทำงานได้หรือไม่ ความเป็นอิสระนั้นคือประเด็นสำคัญทั้งหมด และนั่นคือเหตุผลว่า
ทำไม boot diagnostics ต้องเปิดใช้งานไว้บน CE VM

<Aside type="note" title="ควรเลือกใช้อะไร">
หากคุณกำลังเขียนการทำงานอัตโนมัติ หรือรวบรวมหลักฐานที่ต้องการรันซ้ำในภายหลัง ให้ใช้
debug API หากการลงทะเบียนคือสิ่งที่เสียหาย serial console ไม่ใช่ทางเลือกสำรอง —
แต่เป็นทางเลือกเดียวเท่านั้น
</Aside>

## ข้อมูลรับรอง

แต่ละเส้นทางใช้ข้อมูลรับรองที่แตกต่างกัน และไม่มีข้อมูลใดที่ควรอยู่บนบรรทัดคำสั่ง

- **Debug API** — โทเค็น API ของ F5 Distributed Cloud ในรูปแบบ `XCSH_API_TOKEN` พร้อมกับ
  URL ของ tenant ในรูปแบบ `XCSH_API_URL` ไฟล์คอนเท็กซ์ของ `xcsh` ที่
  `~/.config/xcsh/contexts/<tenant>.json` เก็บทั้งสองค่านี้ ซึ่งเป็นสิ่งที่
  `scripts/capture-sitecli.sh` อ่านเมื่อสภาพแวดล้อมไม่ได้ระบุค่าเหล่านั้นไว้
- **SSH** — ส่วนคีย์ส่วนตัวของคู่คีย์ที่ส่วนคีย์สาธารณะถูกเขียนโดยการปรับใช้ลงใน
  `/var/home/admin/.ssh/authorized_keys` ตั้งแต่การบูตครั้งแรก บวกกับโฮสต์ภายใน VNet
  เพื่อใช้เข้าถึงที่อยู่ภายใน เชื่อมต่อในฐานะ `admin` ไม่ใช่ `azureuser`
- **Serial console** — การเข้าสู่ระบบ Azure แบบโต้ตอบของคุณ ไม่มี service principal
  สำหรับสิ่งนี้: Entra tenant ขององค์กร F5 ไม่อนุญาตให้จัดเตรียม service principal
  ซึ่งเป็นเหตุผลเช่นกันว่าทำไมส่วนใดของกระบวนการนี้จึงไม่ทำงานใน CI

<Aside type="danger" title="อย่าส่งโทเค็นเป็นอาร์กิวเมนต์เด็ดขาด">
โทเค็นที่อยู่บนบรรทัดคำสั่งจะไปปรากฏในประวัติเชลล์และในรายการโปรเซส ซึ่งผู้ใช้อื่น
ทุกคนบนเครื่องสามารถอ่านได้ `capture-sitecli.sh` จึงปฏิเสธ `--token` โดยสิ้นเชิง
ด้วยเหตุผลนั้น และส่งเฮดเดอร์ให้ `curl` ทาง stdin แทน
</Aside>
