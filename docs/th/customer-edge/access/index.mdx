มีสามเส้นทางที่ใช้งานได้ และเส้นทางใดที่จะใช้นั้นขึ้นอยู่กับสถานะของโหนดและตำแหน่งที่คุณเชื่อมต่อจาก ไม่ใช่ขึ้นอยู่กับความต้องการส่วนตัว

| เส้นทาง | ต้องการโหนดสถานะ `ONLINE` | ต้องการการเข้าถึงเครือข่าย | ข้อจำกัด | ครอบคลุม |
| --- | --- | --- | --- | --- |
| [Debug API](./debug-api/) | **ใช่** | ใช่ | ประมาณ 25–30 นาทีสำหรับการ warm-up บน site ใหม่ | 34 คำสั่ง |
| [SSH](./ssh/) | ไม่ | จากภายใน VNet ไปยัง internal address เท่านั้น | key ต้องมีอยู่ตั้งแต่การบูตครั้งแรก | Site CLI บนอุปกรณ์แบบเต็มรูปแบบ |
| [Serial console](./serial-console/) | ไม่ | ไม่ | หนึ่ง session ต่อ VM; ขีดจำกัดการวาง 2,048 ตัวอักษร | Site CLI บนอุปกรณ์แบบเต็มรูปแบบ |

Serial console คือทางเลือกสุดท้าย และเป็นเส้นทางเดียวที่ยังคงใช้งานได้แม้โหนดไม่มีเส้นทางเครือข่ายที่ใช้งานได้

SSH คือตัวเลือกที่ควรใช้เมื่อ debug API ไม่เพียงพอ เนื่องจากอุปกรณ์มีคำสั่งเพิ่มเติมมากกว่า 34 คำสั่งที่ API เปิดเผยไว้อย่างมีนัยสำคัญ มีข้อเสียสองประการ ได้แก่ key จะถูกเขียนโดย cloud-init ดังนั้นจะต้องมีอยู่ตั้งแต่**การบูตครั้งแรก** ซึ่งหมายความว่าการเปิดใช้งานบนโหนดที่กำลังทำงานอยู่จะแทนที่โหนดเหล่านั้น — และปัจจุบันนั้นทำให้การลงทะเบียนติดขัด ([issue 674](https://github.com/f5-sales-demo/mcn/issues/674)) และ `sshd` จะตอบสนองบน internal address ของโหนดเท่านั้น ดังนั้นจึงต้องมี host ภายใน VNet; การตรวจสอบ address ที่คุณรู้จักโหนดจะรายงานว่าปิดอยู่เสมอ

## เหตุใดการแบ่งนี้จึงไม่ใช่ความต้องการส่วนตัว

Debug API ให้บริการโดย F5 Distributed Cloud control plane ซึ่งส่งต่อไปยังโหนดผ่านอุโมงค์ที่ `vpm` สร้างขึ้นระหว่างการลงทะเบียน หากไม่มีการลงทะเบียน ก็จะไม่มีอุโมงค์ ซึ่งหมายความว่า API ไม่มีอะไรที่จะส่งต่อไปได้

มันล้มเหลวในลักษณะที่ไม่เป็นประโยชน์มากกว่าที่ชัดเจน ดังนั้นโหนดที่ไม่เคยเปิดใช้งานจะดูเหมือนเป็นปัญหา API

Serial console ทำงานในทิศทางตรงข้ามโดยสิ้นเชิง — ผ่านแพลตฟอร์ม Azure ไปยัง emulated serial port ของโหนด ไม่สนใจว่าโหนดได้ลงทะเบียน มีการเข้าถึงเครือข่าย หรือมี data plane ที่ทำงานได้หรือไม่ ความเป็นอิสระนี้คือจุดประสงค์หลักทั้งหมด และเป็นเหตุผลที่ boot diagnostics จะต้องเปิดใช้งานไว้บน CE VMs

<Aside type="note" title="สิ่งที่ควรเลือกใช้">
หากคุณกำลังเขียนการทำงานอัตโนมัติ หรือรวบรวมหลักฐานที่ต้องการรันซ้ำในภายหลัง ให้ใช้
debug API หากการลงทะเบียนคือสิ่งที่เสียหาย serial console ไม่ใช่ทางเลือกสำรอง — แต่เป็นตัวเลือกเดียวเท่านั้น
</Aside>

## ข้อมูลรับรอง

ทั้งสองเส้นทางใช้ข้อมูลรับรองที่แตกต่างกัน และไม่มีเส้นทางใดที่ควรระบุในบรรทัดคำสั่ง

- **Debug API** — F5 Distributed Cloud API token ในรูปแบบ `XCSH_API_TOKEN` พร้อม tenant URL ในรูปแบบ `XCSH_API_URL` ไฟล์ context ของ `xcsh` ที่
  `~/.config/xcsh/contexts/<tenant>.json` เก็บทั้งสองอย่างนี้ ซึ่งเป็นสิ่งที่
  `scripts/capture-sitecli.sh` อ่านเมื่อ environment ไม่ได้ระบุค่าเหล่านั้น
- **Serial console** — การเข้าสู่ระบบ Azure แบบโต้ตอบของคุณ ไม่มี service principal
  สำหรับเส้นทางนี้: F5 corporate Entra tenant ไม่อนุญาตให้จัดเตรียม service principal ซึ่งเป็นเหตุผลที่ไม่มีส่วนใดของระบบนี้ทำงานใน CI

<Aside type="danger" title="อย่าส่ง token เป็น argument">
Token ที่ระบุในบรรทัดคำสั่งจะถูกบันทึกใน shell history และใน process list ซึ่ง
ผู้ใช้คนอื่นทุกคนบนเครื่องสามารถอ่านได้ `capture-sitecli.sh` ปฏิเสธ
`--token` โดยสิ้นเชิงด้วยเหตุผลนี้ และส่ง header ไปยัง `curl` ผ่าน stdin
แทน
</Aside>
