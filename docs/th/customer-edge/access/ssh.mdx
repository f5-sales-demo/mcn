SSH เข้าถึงบัญชี `admin` ของอุปกรณ์ ซึ่งมี login shell เป็น Site CLI
(`/opt/bin/vpmu`) นี่คือเส้นทางเดียวไปสู่ **พื้นผิวคำสั่งบนเครื่องแบบเต็มรูปแบบ** —
[debug API](../debug-api/) เปิดเผยคำสั่ง 34 คำสั่ง ส่วนตัวอุปกรณ์เองมีคำสั่งอีกมากมาย
ที่ไม่ได้อยู่บน API นั้นเลย

```bash
cd terraform
SLI=$(terraform output -json ce_sli_private_ips | jq -r '.eastus01')
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<operator-vm> "admin@$SLI"
```

ทุกส่วนของบรรทัดคำสั่งนั้นมีความสำคัญ และสามหัวข้อถัดไปจะอธิบายว่า
แต่ละส่วนป้องกันความล้มเหลวแบบใด

<Aside type="danger" title="ค้นหาที่อยู่ภายในเสมอ — อย่านำมาจากเซสชันก่อนหน้า">
Azure กำหนดซับเน็ตภายในใหม่ในทุกครั้งที่สร้างใหม่ และไม่เรียงตามลำดับโหนด หลังจากการสร้างครั้ง
ล่าสุด `f5-xc-ce-vm-01`, `-02` และ `-03` ถือครอง `10.0.3.7`, `10.0.3.5` และ `10.0.3.4`
ส่วนบิลด์ก่อนหน้ามีลำดับที่แตกต่างไปโดยสิ้นเชิง และ NIC ของไคลเอนต์ทดสอบก็อยู่ใน
ซับเน็ตเดียวกันและเคยถือครองที่อยู่ที่ CE เคยถือครองมาก่อน การเชื่อมต่อไปยังที่อยู่ที่จำไว้
จึงไปลงที่โหนดผิด ที่ VM ที่ไม่ใช่ CE หรือไม่ไปที่ใดเลย — และกรณีสุดท้ายนั้นดูเหมือนกันทุกประการกับ
"SSH ไม่ได้เปิดใช้งาน"

`terraform output -json ce_sli_private_ips` คือการแมป หากไม่มี state อยู่ในมือ ชื่อ NIC
จะคงที่แม้ว่าที่อยู่จะไม่คงที่:

```bash
az network nic show -g rg-mcn-ce-ha-rmordasiewicz \
  -n f5-xc-ce-vm-01-internal-nic \
  --query ipConfigurations[0].privateIPAddress -o tsv
```

</Aside>

<Aside type="caution" title="เฉพาะตอน bootstrap เท่านั้น — CE ที่มีอยู่แล้วไม่สามารถได้รับ SSH โดยไม่ถูกสร้างใหม่">
cloud-init `write_files` ทำงาน **หนึ่งครั้ง ในการบูตครั้งแรก** หลังจากนั้นจะมีตัวทำเครื่องหมาย
`/etc/cloud/cloud-init.disabled` อยู่บนโหนด และ cloud-init จะไม่ทำงานอีก

ดังนั้นจึงไม่มีเส้นทางแบบ in-place ไปยัง CE ที่กำลังทำงานอยู่ `custom_data` เป็นแบบแทนที่เท่านั้นใน Azure
ซึ่งหมายความว่าการนำสิ่งนี้มาใช้กับการปรับใช้ที่มีอยู่แล้วจะ **แทนที่ CE VM ทุกตัว**
การให้สิทธิ์ SSH แก่ผู้ปฏิบัติงานบนโหนดที่เปิดใช้งานอยู่แล้วคือการสร้างใหม่ ไม่ใช่การเปลี่ยนแปลงการกำหนดค่า —
และคำเตือนถัดไปคือสิ่งที่การสร้างใหม่นั้นเคยมีต้นทุน และเหตุใดจึงไม่เป็นเช่นนั้นอีกต่อไป
</Aside>

<Aside type="caution" title="การแทนที่ CE VM เคยทำให้การลงทะเบียนติดขัดถาวร — เรื่องนี้แก้ไขแล้ว และนั่นคือเหตุผลที่ออบเจ็กต์ไซต์ถูกผูกกับ VM">
ควรทราบก่อนวางแผนการสร้างใหม่ เพราะรูปแบบของความล้มเหลวจะอธิบายการผูกโยง
ที่คุณจะเห็นในแผน

เดิมทีการลงทะเบียนของโหนดที่ถูกทำลายยังคงถือครองดัชนีเฉพาะ
`(tenant, cluster_name, hostname)` ของ control plane ดังนั้นการลงทะเบียนของโหนดทดแทนจึงถูกปฏิเสธ
ด้วย `UniqueSecondaryIndexViolationError` และลองใหม่ไปเรื่อย ๆ การลบการลงทะเบียนเพียงอย่างเดียว
ไม่เพียงพอ: `StatusObject` ที่ตกค้างอยู่จะคืนค่า `500` สำหรับคำขอ workload
และเมื่อถึงจุดนั้นแต่ละโหนดได้บันทึก `registration-obj.yml` ที่ตรึงมันไว้กับ
การลงทะเบียนที่คุณลบไปแล้ว ดังนั้นมันจึงวนซ้ำที่ `404` โดยไม่สามารถกู้คืนตัวเองได้
การกู้คืนต้องใช้การสร้างใหม่เต็มรูปแบบสองครั้ง ตลอดกระบวนการนั้น `terraform plan` รายงานว่า
**"No changes"** เพราะในมุมมองของ Terraform สถานะที่ต้องการได้บรรลุแล้ว

[Issue 674](https://github.com/f5-sales-demo/mcn/issues/674) ถูกปิดแล้ว โดย
[PR 693](https://github.com/f5-sales-demo/mcn/pull/693) ตอนนี้ `modules/xc-site` ระบุชื่ออินสแตนซ์
CE VM ใน `replace_triggered_by` ดังนั้นการแทนที่ VM จะแทนที่ออบเจ็กต์ไซต์ และ
การลบไซต์จะนำการลงทะเบียนของมันไปด้วย — คีย์ดัชนีจึงว่างก่อนที่โหนดทดแทนจะบูต
ฟลีตถูกสร้างใหม่ตั้งแต่ต้นตั้งแต่นั้นมา และทั้งสามไซต์ขึ้นสถานะ `ONLINE` โดยไม่ต้องเข้าแทรกแซง

การผูกโยงนี้สังเกตได้จริงมากกว่าเป็นการสันนิษฐาน แต่ละไซต์ถูกผูกกับ *อินสแตนซ์* id ของ VM
และการลงทะเบียนที่ตรงกันจะรายงานค่าเดียวกันเป็น `infra.instance_id`:

```bash
cd terraform && terraform output -json ce_bound_instance_ids
```

ความไม่ตรงกันระหว่างสองค่านี้หมายความว่าไซต์ยังคงถูกผูกกับโหนดที่ไม่มีอยู่แล้ว
ซึ่งเป็นสถานะที่ CE ที่สร้างใหม่ไม่มีทางลงทะเบียนออกมาได้ การอ่านฝั่งของการลงทะเบียน
ยังคงต้องเรียก API โดยตรง — provider issue
[1376](https://github.com/f5-sales-demo/terraform-provider-xcsh/issues/1376) คือสิ่งที่จะ
นำมันมาไว้ที่ data source

</Aside>

## เหตุใด cloud-init จึงเขียนคีย์ ไม่ใช่ API

`admin_user_credentials.ssh_key` บนออบเจ็กต์ไซต์ดูเหมือนฟิลด์สำหรับงานนี้ทุกประการ
มันถูกยอมรับ มันคงอยู่เมื่ออ่านกลับ และมันไม่ได้กำหนดค่าอะไรเลย `vpm` เป็นเจ้าของ
ผู้ใช้ในเครื่องของโหนดและปฏิเสธที่จะแตะต้องผู้ใช้รายนี้ — จากล็อกของโหนดเอง สามครั้ง
ในการบูตครั้งเดียว:

```text
vpm  users.go:165: Won't do any change for user admin (internal skip)
```

ทุกอย่างที่เหลือเป็นผลจากบรรทัดเดียวนั้น `/var/home/admin/.ssh` ไม่เคยมีอยู่ ไม่ว่าก่อนหรือ
หลังไซต์จะถึงสถานะ `ONLINE` วันที่เปลี่ยนแปลงล่าสุดของ shadow สำหรับ `admin` ยังคงเป็นวันที่
สร้างอิมเมจ ในขณะที่ `vesbkp` และ `vesopcon` แสดงวันที่ปัจจุบัน เพราะ `vpm` ตั้งค่าสองรายการนั้น
และข้าม `admin` ไป และ `vpm` ไม่ได้บันทึกล็อกอะไรเลยเกี่ยวกับ `ssh_key` หรือ `authorized_keys`
ในทุกจุด

ดังนั้นไฟล์นี้จึงต้องถูกเขียนนอก `vpm` `admin` คือ uid 2202 ซึ่งฝังอยู่ในอิมเมจของโหนด
ดังนั้นมันจึงมีอยู่ก่อนที่ cloud-init จะทำงาน และ `owner: admin:admin` จะถูก resolve
ณ เวลาเขียน — ไม่ต้องใช้ `runcmd` ไม่ต้องแก้ไขความเป็นเจ้าของภายหลัง:

```yaml
- path: /var/home/admin/.ssh/authorized_keys
  permissions: "0600"
  owner: admin:admin
  content: |
    ${ssh_public_key}
```

`sshd` เต็มใจมาโดยตลอด `sshd -T` รายงาน `pubkeyauthentication yes` และ `admin`
ปรากฏใน `AllowUsers` ในไฟล์ `sshd_config` ทั้งสองไฟล์ที่มากับโหนด ไม่เคยมีอะไร
ที่ต้องเปิดใช้งาน — มีเพียงไฟล์ที่ขาดหายไปเท่านั้น

<Aside type="danger" title="อย่าเพิ่ม admin_user_credentials กลับเข้ามา และอย่าแก้ไข sshd_config">
`admin_user_credentials` เคยถูกเชื่อมต่อเข้ากับ `terraform/modules/xc-site` และถูกย้อนกลับ
เมื่อรวบรวมหลักฐานนี้ได้ (#660, PR #663) มันไม่ใช่ช่องว่างที่รอการเติมเต็ม

`sshd_config` ถูกแทนที่ระหว่างการลงทะเบียน ดังนั้นการแก้ไขมันจะถูกทิ้งในช่วงเวลาที่
ไม่สะดวกที่สุด
</Aside>

## เหตุใดจึงตอบเฉพาะบนที่อยู่เดียว

`sshd` bind ที่ `0.0.0.0:22` แต่มีเพียงที่อยู่ **ภายใน (SLI)** เท่านั้นที่อยู่บน host network
stack ในลักษณะที่ `sshd` จะตอบได้ eth0 ถูกเปลี่ยนชื่อเป็น `a-i-eth0` และไม่มี host IP เลย —
Argo data plane เป็นเจ้าของอินเทอร์เฟซนั้น และที่อยู่ management/SLO ที่มันน่าจะถือครอง
ไปปรากฏบน `vhost0` แทน NIC อีกสองตัวยังคงอยู่บน host stack ภายใต้ชื่อของตัวเอง

ทดสอบจาก VM ภายใน VNet เทียบกับ CE หนึ่งตัว:

```text
management/SLO address    timed out
external address          timed out
internal/SLI address      OPEN     SSH-2.0-OpenSSH_8.7
an unused address         timed out    (control)
```

การทดสอบกับที่อยู่ที่คุณรู้จักโหนดนั้นจึงคืนค่าเหมือนกับที่ security group ที่ปิดอยู่จะคืนค่าทุกประการ
ไม่มีอะไรบล็อกมัน; ไม่มี listener บนที่อยู่นั้นเลย

<Aside type="caution" title="อย่าอ่านชื่ออินเทอร์เฟซของ guest เพื่อสรุปว่าคุณอยู่บนซับเน็ตใด">
ระหว่าง `eth1` และ `eth2` ตัวไหนถือครองที่อยู่ภายในนั้น **แตกต่างกันระหว่างโหนดในการปรับใช้
เดียวกันนี้** อ่านสด ๆ จาก CE ทั้งสามตัว:

```text
f5-xc-ce-vm-01    eth1 -> external      eth2 -> internal/SLI
f5-xc-ce-vm-02    eth2 -> external      eth1 -> internal/SLI
f5-xc-ce-vm-03    eth1 -> external      eth2 -> internal/SLI
```

มีเพียงสองสิ่งที่เป็นจริงบนทุกโหนด: `a-i-eth0` ไม่มีที่อยู่ และ `vhost0` ถือครอง
ที่อยู่ management/SLO สำหรับสิ่งอื่นใด ให้จับคู่จากที่อยู่ในผลลัพธ์ของ
[`ip addr`](../../commands/network/ip/) แทนที่จะใช้ชื่ออินเทอร์เฟซ
</Aside>

ที่อยู่สาธารณะของ CE ก็ไม่มี listener บนพอร์ต 22 เช่นกัน ซึ่งเป็นเหตุผลที่คำสั่งด้านบน
ผ่าน `-J`: VM ของผู้ปฏิบัติงานภายใน VNet ในซับเน็ตเดียวกับที่อยู่ SLI
ในการปรับใช้นี้ `ar-ecmp-client` คือ VM ดังกล่าว

<Aside type="caution" title="-J ไม่ได้ส่งตัวเลือกของคุณไปยังขาที่กระโดด">
ตัวเลือกที่ให้ไว้บนบรรทัดคำสั่งจะใช้กับ hop สุดท้าย `-o UserKnownHostsFile=/dev/null`
ที่ใช้ควบคู่กับ `-J` จึงยังคงอ่านและเขียน `known_hosts` จริงของคุณสำหรับโฮสต์ *jump*
ซึ่งเป็นเรื่องน่าประหลาดใจหากคุณพยายามไม่ให้ฟลีตที่สร้างใหม่เข้าไปอยู่ในนั้น ระบุ hop แรก
อย่างชัดเจนเมื่อเรื่องนี้สำคัญ:

```bash
ssh -tt -o ProxyCommand="ssh -W %h:%p -o UserKnownHostsFile=/dev/null azureuser@<operator-vm>" \
    -o UserKnownHostsFile=/dev/null -i ~/.ssh/id_ed25519 "admin@$SLI"
```

</Aside>

<Aside type="caution" title="ความผิดพลาดในการวัดสองอย่างที่ให้คำตอบผิดอย่างมั่นใจ">
การทดสอบพอร์ต 22 บน eth0 อินเทอร์เฟซภายนอก หรือที่อยู่สาธารณะ จะรายงานว่าปิด
ไม่ว่าสถานะ SSH ของโหนดจะเป็นอย่างไร ดังนั้นมันจึงบอกอะไรคุณไม่ได้เลย มีเพียงที่อยู่ SLI
เท่านั้นที่ตอบ

และการทดสอบจากเวิร์กสเตชันขององค์กรอาจรายงานว่าพอร์ต **เปิด** ทั้งที่มันปิด:
Netskope ทำ TCP handshake ให้เองบนพอร์ตทั่วไป พอร์ต 80 และ 443 อ่านว่า
เปิดบนที่อยู่สาธารณะของ CE เมื่อดูจากเวิร์กสเตชัน แต่ปิดเมื่อทดสอบจากภายใน
VNet ให้ทดสอบจาก VM ภายใน VNet
</Aside>

## Site CLI ต้องการเทอร์มินัล และ carriage return

login shell ของ `admin` ไม่ใช่ shell มันคือแอปพลิเคชัน `go-prompt` ซึ่งทำให้
เทอร์มินัลอยู่ในโหมด raw และอ่านการกดแป้นแทนที่จะอ่านเป็นบรรทัด มีผลกระทบสี่ประการ ซึ่งแต่ละอย่าง
ล้มเหลวในลักษณะที่ดูเหมือนปัญหาคนละเรื่อง:

| กลไก | จะเกิดอะไรขึ้นหากไม่มี |
| --- | --- |
| จัดสรรเทอร์มินัล (`ssh -tt`) | `panic: no such device or address` จาก `go-prompt.NewStandardInputParser` ซึ่งอ่านดูเหมือนอุปกรณ์ล่ม |
| ส่ง carriage return ไม่ใช่ line feed สำหรับ Enter | บรรทัดไม่เคยถูกส่ง และเซสชันปิดลงเมื่อสิ้นสุด input โดยไม่ได้พิมพ์อะไรเลย |
| เปิด standard input ไว้ | การเชื่อมต่อจบก่อนที่คำสั่งจะแสดงผล ดังนั้นคำสั่งที่ทำงานได้จึงดูเงียบ |
| เขียนข้อความคำสั่งและไบต์ Enter **แยกกัน** | ตัวอักษรขึ้นบรรทัดใหม่จะไปอยู่ในบัฟเฟอร์เป็นอักขระตามตัวอักษร และ CLI ตอบว่า `unknown command` ซึ่งอ่านดูเหมือนว่าคำสั่งนั้นไม่มีอยู่ |

`ssh host 'some-command'` จึงใช้ไม่ได้: อาร์กิวเมนต์จะถูกละเว้นและ
prompt แบบโต้ตอบจะเริ่มขึ้นอยู่ดี ให้ขับเคลื่อนมันแบบเทอร์มินัล มิฉะนั้นก็อย่าทำเลย
`scripts/sitecli_ssh_harvest.py` คือการนำไปใช้อ้างอิง

<Aside type="caution" title="panic ที่อ่านว่า 'no such device or address' หมายความว่าการยืนยันตัวตนสำเร็จ">
`vpmu` ปล่อยข้อความนี้ **หลัง** การล็อกอิน เมื่อมันไม่พบเทอร์มินัลให้เชื่อมต่อด้วย เมื่ออ่านว่าเป็นการล่ม
มันดูเหมือนผลลัพธ์ที่แย่ที่สุด ทั้งที่จริงแล้วมันคือข้อผิดพลาดสุดท้ายก่อนความสำเร็จ เพิ่ม
`-tt` แล้วเชื่อมต่ออีกครั้ง
</Aside>

<Aside type="caution" title="การแทนที่ CE จะเปลี่ยน host key ของมัน">
โหนดทดแทนจะนำเสนอ host key ที่ต่างออกไปบนที่อยู่เดียวกัน ดังนั้นการเชื่อมต่อครั้งถัดไป
จะเตือนว่า `REMOTE HOST IDENTIFICATION HAS CHANGED` และปฏิเสธ ให้ล้างรายการเก่า
สำหรับที่อยู่นั้นแล้วเชื่อมต่อใหม่ เนื่องจากการให้สิทธิ์ SSH จะแทนที่ VM ทั้งหมดอยู่แล้ว ให้คาดหวังสิ่งนี้
ในการเชื่อมต่อครั้งแรกสุดหลังจากนำมาใช้
</Aside>

## แบนเนอร์คือการตรวจสุขภาพฟรี

ก่อนที่คุณจะพิมพ์อะไร แบนเนอร์ล็อกอินได้ตอบคำถามหลายข้อที่คุณจะต้องเสียคำสั่งไปถาม
เรียบร้อยแล้ว จาก `f5-xc-ce-vm-01` โดยตัด ASCII art และ IP สาธารณะออก:

```text
UNAUTHORIZED ACCESS TO THIS DEVICE IS PROHIBITED
All actions performed on this device are audited

Using https://register.ves.volterra.io
OS: rhel-9.2024.6
Memory: 32768MiB
Storage: sda: 31GiB
CPU: Model: Intel(R) Xeon(R) Platinum 8272CL CPU @ 2.60GHz | CPUs: 8
Software: crt-20250613-3382
DNS: 168.63.129.16: OK
NTP: Synced
Uptime: 0 days, 5 hours, 20 minutes
Registration Status: PROVISIONED
SLO IP: 10.0.1.4/26
WELCOME IN SITE CLI
```

`Registration Status` แยกแยะโหนดที่ยังกำลังเปิดใช้งาน (`PROVISIONING`) ออกจากโหนดที่
เสร็จแล้ว (`PROVISIONED`) `Software` คือสตริงบิลด์ที่กำหนดว่ามีคำสั่งใดอยู่บ้าง
`DNS` และ `NTP` ครอบคลุมสองสิ่งที่ต้องพึ่งพาซึ่งทำให้การลงทะเบียนพังเป็นอันดับแรก ดังนั้นโหนดที่
ไม่เคยออนไลน์มักได้บอกคุณแล้วว่าเพราะอะไรตรงนี้ — ก่อนที่จะจำเป็นต้องใช้
[`chronyc-sources`](../../commands/network/chronyc-sources/) หรือ
[`dig`](../../commands/network/dig/) เลยด้วยซ้ำ

## การจัดหาคู่กุญแจ

<Steps>

1. สร้างคู่กุญแจ หากคุณยังไม่มี ใช้ Ed25519 แทน RSA: สั้นกว่า
   และได้รับการยอมรับจาก `sshd` ของอุปกรณ์

   ```bash
   ssh-keygen -t ed25519 -C "ce-operator" -f ~/.ssh/id_ed25519
   ```

2. ชี้การปรับใช้ไปที่กุญแจฝั่ง **สาธารณะ** โมดูลรากจะอ่านไฟล์หนึ่งครั้งแล้ว
   ส่งสตริงลงไปยังทุกโหนด:

   ```hcl
   # terraform/terraform.tfvars
   ssh_public_key_path = "~/.ssh/id_ed25519.pub"
   ```

   `ssh_public_key` รับเนื้อหาแบบ inline แทน ซึ่งเป็นสิ่งที่การทดสอบแผนใช้
   กุญแจฝั่งส่วนตัวไม่เคยออกจากเวิร์กสเตชันของคุณ

3. Apply อ่านคำเตือนที่ด้านบนของหน้านี้ก่อน — บนการปรับใช้ที่มีอยู่แล้ว สิ่งนี้จะ
   แทนที่ CE VM

</Steps>

<Aside type="note" title="admin_ssh_key ของ VM เองเป็นคนละเรื่องกัน">
`azurerm_linux_virtual_machine.admin_ssh_key` ใน `modules/ce-node` ให้สิทธิ์ผู้ดูแลระบบ
Azure VM ไม่ใช่บัญชี `admin` ของอุปกรณ์ มันไม่ได้ให้สิทธิ์เข้าถึง Site CLI และ
การที่มันถูกตั้งค่าไว้ไม่ใช่หลักฐานว่า CE SSH ถูกกำหนดค่าแล้ว
</Aside>

## สิ่งที่นี่ไม่ใช่

แต่ละข้อต่อไปนี้ถูกทดสอบและตัดออกไปในขณะที่ยังเชื่อว่าเส้นทางนี้เป็นไปไม่ได้
แต่ละข้อดูน่าเชื่อพอที่จะทำให้เสียเวลาไปหนึ่งวัน

| ไม่ใช่สาเหตุ | ตัดออกไปได้อย่างไร |
| --- | --- |
| ข้อมูลรับรองใช้ได้เฉพาะตอนสร้างเท่านั้น | `sshd` เริ่มทำงานประมาณ 90 วินาทีหลังบูตครั้งแรก ก่อนที่ออบเจ็กต์ไซต์จะมีอยู่ `admin_user_credentials` ยังปรากฏใน `ReplaceSpecType` และมีผลแบบ in place ด้วย |
| `block_all_services` | การปิดพอร์ต 22 บนที่อยู่ management เหมือนกันทุกประการไม่ว่าบริการจะถูกบล็อกหรือไม่ |
| ตัวขึ้นบรรทัดใหม่ท้ายคีย์ | ทดสอบทั้งสองแบบแล้ว ไม่มีการเปลี่ยนแปลง Cloud-init ยังคงตัดมันออก เพราะบล็อกตามตัวอักษรจะแสดงบรรทัดที่สองซึ่งว่างเปล่า |
| ซอฟต์แวร์ CE เวอร์ชันเก่าที่ตรึงไว้ | ทำซ้ำได้บนสามบิลด์ รวมถึงบิลด์หนึ่งที่รัน OpenSSH 9.9 |
| `admin_password` ที่ขาดหายไป | การตั้ง `admin_password` ควบคู่กับ `ssh_key` บน CE ที่สร้างใหม่ตั้งแต่ต้นไม่ได้เปลี่ยนอะไรเลย |

<Aside type="caution" title="ฟิลด์ API สองรายการที่ดูเหมือนเป็นตัวชี้วัดแยกแยะแต่ไม่ใช่">
`gc_spec.admin_ssh_key` ว่างเปล่าหรือไม่มีอยู่บน **ทั้ง 58 ไซต์ใน `f5-sales-demo`** — รวมถึง
สองไซต์ที่ตั้งค่า `admin_user_credentials.ssh_key` การเปรียบเทียบค่านี้ระหว่างไซต์ที่ใช้งานได้
กับไซต์ที่ใช้งานไม่ได้จะไม่บอกอะไรคุณเลย เพราะมันอ่านว่าว่างแม้แต่ในไซต์ที่ *มี* การกำหนดค่า
ข้อมูลรับรองไว้

`registrations_by_site` ละเว้นฟิลด์นี้ทั้งหมดและคืนค่า `None` สำหรับมัน ซึ่งอ่านได้ว่า
"ไม่ได้กำหนดค่า" มากกว่า "ไม่ได้รายงาน"
</Aside>
