SSH เข้าถึงบัญชี `admin` ของอุปกรณ์ โดยที่ login shell คือ Site CLI
(`/opt/bin/vpmu`) นี่คือเส้นทางเดียวที่ไปยัง **พื้นที่คำสั่งบนกล่องเต็มรูปแบบ** —
[debug API](../debug-api/) เปิดเผยคำสั่ง 34 รายการ และตัวอุปกรณ์เองมีคำสั่งอีกมากมาย
ที่ไม่ได้อยู่ใน API นั้นเลย

```bash
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<operator-vm> admin@10.0.3.5
```

ทุกส่วนของบรรทัดคำสั่งนั้นมีความสำคัญ และสามส่วนถัดไปจะอธิบาย
ว่าแต่ละส่วนป้องกันความล้มเหลวใด

<Aside type="caution" title="การเปิดใช้งานนี้บนการปรับใช้ที่กำลังทำงานจะแทนที่ VM">
คีย์จะถูกเขียนโดย cloud-init และ cloud-init `write_files` จะทำงาน **เฉพาะในการบูตครั้งแรก**
การเปิดใช้งานสิ่งนี้สำหรับโหนดที่มีอยู่หมายความว่าต้องแทนที่โหนดเหล่านั้น ซึ่งปัจจุบันทำให้การลงทะเบียนค้าง:
การลงทะเบียนที่ล้าสมัยยังคงถือ index `(tenant, cluster_name, hostname)` ที่ไม่ซ้ำกัน
โหนดที่ถูกแทนที่ไม่สามารถลงทะเบียนได้ และ `terraform plan` รายงาน
"No changes" ตลอดเวลา ดู
[issue 674](https://github.com/f5-sales-demo/mcn/issues/674) ก่อนที่คุณจะวางแผนการเปลี่ยนแปลง
ไม่ใช่หลังจากนั้น
</Aside>

## เหตุใด cloud-init จึงเขียนคีย์ ไม่ใช่ API

`admin_user_credentials.ssh_key` บนออบเจกต์ไซต์ดูเหมือนฟิลด์สำหรับสิ่งนี้พอดี
ระบบยอมรับ อ่านกลับได้ และไม่ได้กำหนดค่าอะไรเลย `vpm` เป็นเจ้าของผู้ใช้ภายในเครื่องของโหนด
และปฏิเสธที่จะแตะต้องผู้ใช้รายนี้ — จากล็อกของโหนดเอง สามครั้งในการบูตเดียว:

```text
vpm  users.go:165: Won't do any change for user admin (internal skip)
```

ทุกอย่างที่ตามมาล้วนมาจากบรรทัดเดียวนั้น `/var/home/admin/.ssh` ไม่เคยมีอยู่ ทั้งก่อนและ
หลังจากที่ไซต์ถึงสถานะ `ONLINE` วันที่เปลี่ยนรหัสผ่านล่าสุดของ `admin` shadow ยังคงเป็น
วันที่สร้างอิมเมจ ขณะที่ `vesbkp` และ `vesopcon` แสดงวันที่ปัจจุบัน เนื่องจาก `vpm`
ตั้งค่าทั้งสองและข้าม `admin` และ `vpm` ไม่บันทึกอะไรเกี่ยวกับ `ssh_key` หรือ `authorized_keys`
เลยในทุกจุด

ดังนั้นไฟล์จึงต้องถูกเขียนนอก `vpm` `admin` คือ uid 2202 ที่ฝังอยู่ในอิมเมจโหนด
ดังนั้นจึงมีอยู่ก่อนที่ cloud-init จะทำงาน และ `owner: admin:admin` จะถูกแปลงในเวลาที่เขียน
— ไม่ต้องใช้ `runcmd` ไม่ต้องแก้ไขความเป็นเจ้าของ:

```yaml
- path: /var/home/admin/.ssh/authorized_keys
  permissions: "0600"
  owner: admin:admin
  content: |
    ${ssh_public_key}
```

`sshd` พร้อมอยู่เสมอ `sshd -T` รายงาน `pubkeyauthentication yes` และ `admin`
ปรากฏใน `AllowUsers` ในทั้งสองไฟล์ `sshd_config` ที่มาพร้อมกับโหนด ไม่มีอะไรต้องเปิดใช้งาน
— มีแค่ไฟล์ที่หายไปเท่านั้น

<Aside type="danger" title="อย่าเพิ่ม admin_user_credentials อีกครั้ง และอย่าแก้ไข sshd_config">
`admin_user_credentials` ถูกเชื่อมต่อเข้ากับ `terraform/modules/xc-site` และถูกย้อนกลับเมื่อรวบรวม
หลักฐานนี้แล้ว (#660, PR #663) ไม่ใช่ช่องว่างที่รอการเติมเต็ม

`sshd_config` จะถูกแทนที่ระหว่างการลงทะเบียน ดังนั้นการแก้ไขจะถูกละทิ้งในเวลาที่ไม่สะดวกที่สุด
</Aside>

## เหตุใดจึงตอบสนองบนที่อยู่เดียวเท่านั้น

`sshd` ผูกกับ `0.0.0.0:22` แต่มีเพียงที่อยู่ **ภายใน (SLI)** เท่านั้นที่อยู่บน network stack ของโฮสต์
eth0 ถูกเปลี่ยนชื่อเป็น `a-i-eth0` และไม่มี host IP — Argo data plane เป็นเจ้าของอินเทอร์เฟซนั้น —
ขณะที่ eth1 และ eth2 ยังคงอยู่บน host stack ซึ่ง `sshd` กำลังฟังอยู่

ทดสอบจาก VM ภายใน VNet:

```text
10.0.1.4     timed out             CE mgmt/SLO  (eth0)
10.0.2.4     timed out             CE external  (eth1)
10.0.3.5     OPEN                  CE internal/SLI
10.0.3.6     OPEN
10.0.3.7     OPEN
```

การทดสอบกับที่อยู่ที่คุณรู้จักโหนดจึงให้ผลลัพธ์เหมือนกับ security group ที่ปิดอยู่
ไม่มีอะไรบล็อกมัน เพียงแต่ไม่มีผู้ฟังบนที่อยู่นั้น

ที่อยู่สาธารณะของ CE ก็ไม่มีผู้ฟังบนพอร์ต 22 เช่นกัน นั่นคือเหตุผลที่คำสั่งข้างต้น
ใช้ `-J`: VM ผู้ดำเนินการภายใน VNet ในซับเน็ตเดียวกับที่อยู่ SLI

<Aside type="caution" title="ข้อผิดพลาดในการวัดสองอย่างที่ให้ผลลัพธ์ที่ผิดอย่างมั่นใจ">
การทดสอบ eth0 อินเทอร์เฟซภายนอก หรือที่อยู่สาธารณะสำหรับพอร์ต 22 จะรายงานว่าปิด
ไม่ว่าสถานะ SSH ของโหนดจะเป็นอย่างไร ดังนั้นจึงไม่สามารถบอกอะไรคุณได้เลย มีเพียงที่อยู่ SLI เท่านั้นที่ตอบสนอง

และการทดสอบจากเวิร์กสเตชันของบริษัทอาจรายงานพอร์ต **เปิด** ที่จริงแล้วปิดอยู่:
Netskope ทำการ TCP handshake เองบนพอร์ตทั่วไป พอร์ต 80 และ 443 อ่านว่าเปิดบนที่อยู่สาธารณะของ CE
จากเวิร์กสเตชัน และจริงๆ แล้วปิดเมื่อทดสอบจากภายใน VNet ทดสอบจาก VM ใน VNet
</Aside>

## Site CLI ต้องการเทอร์มินัลและ carriage return

login shell ของ `admin` ไม่ใช่ shell ทั่วไป แต่เป็นแอปพลิเคชัน `go-prompt`
ที่นำเทอร์มินัลเข้าสู่ raw mode และอ่านการกดแป้นพิมพ์แทนที่จะอ่านเป็นบรรทัด
มีผลกระทบสี่ประการ แต่ละอย่างล้มเหลวในลักษณะที่ดูเหมือนปัญหาที่แตกต่างกัน:

| กลไก | สิ่งที่เกิดขึ้นหากไม่มี |
| --- | --- |
| จัดสรรเทอร์มินัล (`ssh -tt`) | `panic: no such device or address` จาก `go-prompt.NewStandardInputParser` ซึ่งดูเหมือนอุปกรณ์ที่ขัดข้อง |
| ส่ง carriage return ไม่ใช่ line feed สำหรับ Enter | บรรทัดไม่ถูกส่ง และเซสชันปิดเมื่อสิ้นสุด input โดยไม่พิมพ์อะไร |
| เปิด standard input ไว้ | การเชื่อมต่อสิ้นสุดก่อนที่คำสั่งจะแสดงผล ทำให้คำสั่งที่ทำงานได้ดูเหมือนไม่มีเสียง |
| เขียนข้อความคำสั่งและไบต์ Enter **แยกกัน** | newline ตกลงในบัฟเฟอร์เป็นอักขระตัวอักษรและ CLI ตอบ `unknown command` ซึ่งดูเหมือนว่าคำสั่งไม่มีอยู่ |

ดังนั้น `ssh host 'some-command'` จึงไม่ทำงาน: อาร์กิวเมนต์จะถูกละเว้นและ interactive prompt
จะเริ่มต้นอยู่ดี ขับเคลื่อนเป็นเทอร์มินัลหรือไม่ก็ไม่ต้องทำเลย
`scripts/sitecli_ssh_harvest.py` คือการอ้างอิงสำหรับการนำไปใช้

แบนเนอร์ล็อกอินรายงานสถานะการลงทะเบียนของโหนด ซึ่งเป็นวิธีที่รวดเร็วที่สุดในการบอกความแตกต่าง
ระหว่างโหนดที่ยังกำลังเริ่มต้นกับโหนดที่เสีย:

```text
Registration Status: PROVISIONING
SLO IP: 10.0.1.4/26
```

## การจัดหา keypair

<Steps>

1. สร้าง keypair หากคุณยังไม่มี ใช้ Ed25519 แทน RSA: สั้นกว่า
   และอุปกรณ์ `sshd` ยอมรับ

   ```bash
   ssh-keygen -t ed25519 -C "ce-operator" -f ~/.ssh/id_ed25519
   ```

2. ชี้การปรับใช้ไปยังครึ่ง **สาธารณะ** โมดูลรูทอ่านไฟล์หนึ่งครั้งและ
   ส่งสตริงไปยังทุกโหนด:

   ```hcl
   # terraform/terraform.tfvars
   ssh_public_key_path = "~/.ssh/id_ed25519.pub"
   ```

   `ssh_public_key` รับวัสดุแบบ inline แทน ซึ่งเป็นสิ่งที่การทดสอบแผนใช้
   ครึ่งส่วนตัวไม่เคยออกจากเวิร์กสเตชันของคุณ

3. Apply อ่านคำเตือนที่ด้านบนของหน้านี้ก่อน — บนการปรับใช้ที่มีอยู่
   จะแทนที่ CE VM

</Steps>

<Aside type="note" title="admin_ssh_key ของ VM เองเป็นคนละสิ่งกัน">
`azurerm_linux_virtual_machine.admin_ssh_key` ใน `modules/ce-node` อนุญาตผู้ดูแล VM Azure
ไม่ใช่บัญชี `admin` ของอุปกรณ์ ไม่ได้ให้สิทธิ์เข้าถึง Site CLI และการตั้งค่านี้
ไม่ใช่หลักฐานว่า CE SSH ได้รับการกำหนดค่าแล้ว
</Aside>

## สิ่งที่นี่ไม่ใช่

แต่ละสิ่งเหล่านี้ถูกทดสอบและตัดออกในขณะที่เส้นทางยังเชื่อว่าเป็นไปไม่ได้
แต่ละอย่างมีความน่าเชื่อถือพอที่จะทำให้เสียเวลาหนึ่งวัน

| ไม่ใช่สาเหตุ | วิธีที่ตัดออก |
| --- | --- |
| ข้อมูลรับรองใช้ได้เฉพาะเวลาสร้าง | `sshd` เริ่มต้นประมาณ 90 วินาทีหลังการบูตครั้งแรก ก่อนที่ออบเจกต์ไซต์จะมีอยู่ `admin_user_credentials` ยังอยู่ใน `ReplaceSpecType` และใช้ได้ทันที |
| `block_all_services` | การปิดพอร์ต 22 บนที่อยู่การจัดการเหมือนกัน ไม่ว่าจะบล็อกบริการหรือไม่ก็ตาม |
| newline ต่อท้ายบนคีย์ | ทดสอบทั้งสองวิธี ไม่มีการเปลี่ยนแปลง cloud-init ยังคง strip มัน เพราะ literal block จะแสดงบรรทัดที่สองที่ว่างเปล่า |
| ซอฟต์แวร์ CE เวอร์ชันเก่าที่ถูกตรึง | ทำซ้ำได้บนสามรุ่น รวมถึงรุ่นหนึ่งที่รัน OpenSSH 9.9 |
| `admin_password` ที่หายไป | การตั้งค่า `admin_password` ควบคู่กับ `ssh_key` บน CE ใหม่ทั้งหมดไม่ได้เปลี่ยนแปลงอะไร |

<Aside type="caution" title="ฟิลด์ API สองรายการที่ดูเหมือนตัวแยกแยะแต่ไม่ใช่">
`gc_spec.admin_ssh_key` ว่างเปล่าบน **ไซต์ทั้งหมด 88 ไซต์ใน tenant** รวมถึง 20 ไซต์ที่
ตั้งค่า `admin_password` การเปรียบเทียบระหว่างไซต์ที่ทำงานได้และไม่ทำงานไม่บอกอะไรคุณ
เพราะมันว่างเปล่าทุกที่

`registrations_by_site` ละเว้นฟิลด์นั้นทั้งหมดและส่งคืน `None` สำหรับมัน ซึ่งอ่านว่า
"ไม่ได้กำหนดค่า" แทนที่จะเป็น "ไม่ได้รายงาน"
</Aside>

เส้นทางที่ใช้งานได้ในขณะที่โหนดยังอยู่ระหว่างการลงทะเบียน
</Aside>
