SSH เข้าถึงบัญชี `admin` ของอุปกรณ์ ซึ่งมี login shell เป็น Site CLI
(`/opt/bin/vpmu`) นี่คือเส้นทางเดียวสู่ **พื้นผิวคำสั่งบนเครื่องแบบเต็มรูปแบบ** —
[debug API](../debug-api/) เปิดเผยคำสั่ง 34 คำสั่ง และตัวอุปกรณ์เองยังมีอีกมากมาย
ที่ไม่ได้อยู่บน API นั้นเลย

```bash
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<operator-vm> admin@10.0.3.5
```

ทุกส่วนของบรรทัดคำสั่งนั้นมีความสำคัญ และสามส่วนถัดไปจะอธิบายว่า
แต่ละส่วนป้องกันความล้มเหลวใด

<Aside type="caution" title="ใช้ได้เฉพาะตอน bootstrap เท่านั้น — CE ที่มีอยู่แล้วไม่สามารถได้รับ SSH โดยไม่สร้างใหม่">
cloud-init `write_files` ทำงาน **ครั้งเดียว ตอนบูตครั้งแรก** หลังจากนั้นจะมีเครื่องหมาย
`/etc/cloud/cloud-init.disabled` อยู่บนโหนด และ cloud-init จะไม่ทำงานอีก

ดังนั้นจึงไม่มีเส้นทางแบบ in-place ไปยัง CE ที่กำลังทำงานอยู่ `custom_data` เป็นแบบแทนที่เท่านั้นใน Azure
ซึ่งหมายความว่าการนำสิ่งนี้มาใช้กับการปรับใช้ที่มีอยู่แล้วจะ **แทนที่ VM ของ CE ทุกตัว**
การให้สิทธิ์ SSH แก่ผู้ปฏิบัติงานสำหรับโหนดที่ทำงานอยู่แล้วคือการสร้างใหม่ ไม่ใช่การเปลี่ยนแปลงการกำหนดค่า —
และคำเตือนถัดไปคือสิ่งที่การสร้างใหม่นั้นมีต้นทุนในปัจจุบัน
</Aside>

<Aside type="danger" title="การแทนที่ VM ของ CE ทำให้การลงทะเบียนติดขัด และ terraform plan รายงานว่า 'No changes' ในขณะที่ทั้งฟลีตล่ม">
นี่คือเรื่องที่หนักที่สุดในหน้านี้ อ่าน
[issue 674](https://github.com/f5-sales-demo/mcn/issues/674) ก่อนที่คุณจะวางแผนการเปลี่ยนแปลง
ไม่ใช่หลังจากนั้น

การลงทะเบียนที่ค้างอยู่ยึดครองดัชนีที่ไม่ซ้ำกัน `(tenant, cluster_name, hostname)` ดังนั้น
การลงทะเบียนของโหนดทดแทนจะถูกปฏิเสธด้วย `UniqueSecondaryIndexViolationError` และมันจะ
ลองใหม่ตลอดไป การลบการลงทะเบียนเพียงอย่างเดียวไม่เพียงพอ: `StatusObject` ที่หลงเหลืออยู่
จะคืนค่า `500` สำหรับคำขอ workload และเมื่อถึงจุดนั้นแต่ละโหนดได้บันทึก
`registration-obj.yml` ที่ผูกมันไว้กับการลงทะเบียนที่คุณลบไปแล้ว ดังนั้นมันจึงวนลูป
ที่ `404` โดยไม่มีการกู้คืนตัวเอง

การกู้คืนจำเป็นต้องลบการลงทะเบียน สร้างวัตถุไซต์ใหม่ **แทนที่
VM เป็นครั้งที่สอง** และจากนั้นใช้การอนุมัติ — สร้างใหม่สองรอบเต็มเพื่อรองรับการเปลี่ยนแปลง
`custom_data` เพียงครั้งเดียว

ตลอดกระบวนการทั้งหมดนั้น `terraform plan` รายงานว่า **"No changes"** เพราะในมุมมองของ Terraform
สถานะที่ต้องการได้บรรลุแล้ว ฟลีตล่มแต่แผนสะอาด
อย่าปฏิบัติต่อการรองรับการเปลี่ยนแปลงนี้เหมือนการ apply ตามปกติ
</Aside>

## ทำไม cloud-init จึงเขียนคีย์ ไม่ใช่ API

`admin_user_credentials.ssh_key` บนวัตถุไซต์ดูเหมือนฟิลด์สำหรับสิ่งนี้ทุกประการ
มันถูกยอมรับ มันคงอยู่เมื่ออ่านกลับ และมันไม่ได้กำหนดค่าอะไรเลย `vpm` เป็นเจ้าของ
ผู้ใช้ในเครื่องของโหนดและปฏิเสธที่จะแตะต้องผู้ใช้รายนี้ — จากล็อกของโหนดเอง สามครั้ง
ในการบูตครั้งเดียว:

```text
vpm  users.go:165: Won't do any change for user admin (internal skip)
```

ทุกอย่างที่เหลือเป็นผลจากบรรทัดเดียวนั้น `/var/home/admin/.ssh` ไม่เคยมีอยู่ ทั้งก่อน
และหลังจากที่ไซต์เข้าสู่สถานะ `ONLINE` วันที่เปลี่ยนแปลงล่าสุดของ shadow ของ `admin` ยังคงอยู่ที่วันที่
สร้างอิมเมจ ในขณะที่ `vesbkp` และ `vesopcon` แสดงวันที่ปัจจุบัน เพราะ `vpm` ตั้งค่าสองรายการนั้น
และข้าม `admin` ไป และ `vpm` ไม่ได้บันทึกล็อกอะไรเกี่ยวกับ `ssh_key` หรือ `authorized_keys` เลย
ณ จุดใดก็ตาม

ดังนั้นไฟล์นี้ต้องถูกเขียนนอก `vpm` `admin` คือ uid 2202 ที่ฝังอยู่ในอิมเมจของโหนด
ดังนั้นมันจึงมีอยู่ก่อนที่ cloud-init จะทำงาน และ `owner: admin:admin` แก้ไขได้ตอนเขียน
— ไม่ต้องใช้ `runcmd` ไม่ต้องแก้ไขความเป็นเจ้าของ:

```yaml
- path: /var/home/admin/.ssh/authorized_keys
  permissions: "0600"
  owner: admin:admin
  content: |
    ${ssh_public_key}
```

`sshd` เต็มใจมาโดยตลอด `sshd -T` รายงาน `pubkeyauthentication yes` และ `admin`
ปรากฏใน `AllowUsers` ในไฟล์ `sshd_config` ทั้งสองไฟล์ที่มาพร้อมกับโหนด ไม่เคยมี
อะไรที่ต้องเปิดใช้งาน — มีเพียงไฟล์ที่ขาดหายไปเท่านั้น

<Aside type="danger" title="อย่าเพิ่ม admin_user_credentials กลับเข้ามา และอย่าแก้ไข sshd_config">
`admin_user_credentials` ถูกเชื่อมต่อเข้ากับ `terraform/modules/xc-site` และถูกย้อนกลับเมื่อรวบรวม
หลักฐานนี้ได้แล้ว (#660, PR #663) มันไม่ใช่ช่องว่างที่รอการเติมเต็ม

`sshd_config` ถูกแทนที่ระหว่างการลงทะเบียน ดังนั้นการแก้ไขมันจะถูกทิ้งในช่วงเวลา
ที่ไม่สะดวกที่สุด
</Aside>

## ทำไมมันจึงตอบสนองบนที่อยู่เดียวเท่านั้น

`sshd` ผูกกับ `0.0.0.0:22` แต่มีเพียงที่อยู่ **ภายใน (SLI)** เท่านั้นที่อยู่บน network
stack ของโฮสต์ eth0 ถูกเปลี่ยนชื่อเป็น `a-i-eth0` และไม่มี IP ของโฮสต์ — Argo data plane เป็นเจ้าของ
อินเทอร์เฟซนั้น — ในขณะที่ eth1 และ eth2 ยังคงอยู่บน stack ของโฮสต์ ซึ่งเป็นที่ที่ `sshd` กำลังฟังอยู่

ตรวจสอบจาก VM ภายใน VNet:

```text
10.0.1.4     timed out             CE mgmt/SLO  (eth0)
10.0.2.4     timed out             CE external  (eth1)
10.0.3.5     OPEN                  CE internal/SLI
10.0.3.6     OPEN
10.0.3.7     OPEN
```

ดังนั้นการตรวจสอบที่อยู่ที่คุณรู้จักโหนดจึงคืนค่าเหมือนกับที่ security group ที่ปิดอยู่
คืนค่าทุกประการ ไม่มีอะไรบล็อกมัน ไม่มีตัวรับฟังบนที่อยู่นั้น

ที่อยู่สาธารณะของ CE ก็ไม่มีตัวรับฟังบนพอร์ต 22 เช่นกัน ซึ่งเป็นเหตุผลว่าทำไมคำสั่งข้างต้น
จึงผ่าน `-J`: VM ของผู้ปฏิบัติงานภายใน VNet ในซับเน็ตเดียวกันกับที่อยู่ SLI

<Aside type="caution" title="ความผิดพลาดในการวัดสองอย่างที่ให้คำตอบผิดอย่างมั่นใจ">
การตรวจสอบ eth0 อินเทอร์เฟซภายนอก หรือที่อยู่สาธารณะสำหรับพอร์ต 22 จะรายงานว่าปิด
ไม่ว่าสถานะ SSH ของโหนดจะเป็นอย่างไร ดังนั้นมันจึงบอกอะไรคุณไม่ได้เลย มีเพียงที่อยู่ SLI
เท่านั้นที่ตอบสนอง

และการตรวจสอบจากเวิร์กสเตชันขององค์กรอาจรายงานว่าพอร์ต **เปิด** ทั้งที่ปิดอยู่:
Netskope ทำ TCP handshake ให้เสร็จสิ้นด้วยตัวเองบนพอร์ตทั่วไป พอร์ต 80 และ 443 อ่านได้ว่า
เปิดอยู่บนที่อยู่สาธารณะของ CE จากเวิร์กสเตชัน และปิดอยู่เมื่อตรวจสอบจากภายใน
VNet ให้ตรวจสอบจาก VM ใน VNet
</Aside>

## Site CLI ต้องการเทอร์มินัล และ carriage return

login shell ของ `admin` ไม่ใช่ shell มันคือแอปพลิเคชัน `go-prompt` ซึ่งทำให้
เทอร์มินัลอยู่ในโหมด raw และอ่านการกดปุ่มแทนที่จะอ่านเป็นบรรทัด มีผลกระทบสี่ประการ ซึ่งแต่ละอย่าง
ล้มเหลวในลักษณะที่ดูเหมือนเป็นปัญหาที่แตกต่างกัน:

| กลไก | สิ่งที่เกิดขึ้นหากไม่มีมัน |
| --- | --- |
| จัดสรรเทอร์มินัล (`ssh -tt`) | `panic: no such device or address` จาก `go-prompt.NewStandardInputParser` ซึ่งอ่านได้ว่าเป็นอุปกรณ์ที่ล่ม |
| ส่ง carriage return ไม่ใช่ line feed สำหรับ Enter | บรรทัดจะไม่ถูกส่งเลย และเซสชันจะปิดลงเมื่อสิ้นสุดอินพุตโดยไม่ได้พิมพ์อะไรออกมา |
| เปิด standard input ไว้ | การเชื่อมต่อสิ้นสุดก่อนที่คำสั่งจะแสดงผล ดังนั้นคำสั่งที่ทำงานได้จึงดูเงียบ |
| เขียนข้อความคำสั่งและไบต์ Enter **แยกกัน** | ตัวขึ้นบรรทัดใหม่จะลงในบัฟเฟอร์เป็นอักขระตามตัวอักษร และ CLI ตอบว่า `unknown command` ซึ่งอ่านได้เหมือนว่าคำสั่งนั้นไม่มีอยู่ |

ดังนั้น `ssh host 'some-command'` จึงไม่ทำงาน: อาร์กิวเมนต์ถูกละเว้นและ
พรอมต์แบบโต้ตอบก็เริ่มต้นขึ้นอยู่ดี ควบคุมมันเหมือนเทอร์มินัลหรือไม่ก็อย่าใช้เลย
`scripts/sitecli_ssh_harvest.py` คือการนำไปใช้อ้างอิง

<Aside type="caution" title="panic ที่อ่านว่า 'no such device or address' หมายความว่าการยืนยันตัวตนสำเร็จแล้ว">
`vpmu` ส่งข้อความนี้ออกมา **หลังจาก** เข้าสู่ระบบ เมื่อมันไม่พบเทอร์มินัลให้เชื่อมต่อ หากอ่านว่าเป็นการล่ม
มันดูเหมือนผลลัพธ์ที่แย่ที่สุดเท่าที่เป็นไปได้ และอันที่จริงมันคือข้อผิดพลาดสุดท้ายก่อนที่จะสำเร็จ เพิ่ม
`-tt` แล้วเชื่อมต่ออีกครั้ง
</Aside>

<Aside type="caution" title="การแทนที่ CE จะเปลี่ยน host key ของมัน">
โหนดทดแทนจะแสดง host key ที่แตกต่างกันที่ที่อยู่เดิม ดังนั้นการเชื่อมต่อครั้งถัดไป
จะเตือนว่า `REMOTE HOST IDENTIFICATION HAS CHANGED` และปฏิเสธ ให้ล้างรายการเก่า
สำหรับที่อยู่นั้นแล้วเชื่อมต่อใหม่ เนื่องจากการให้สิทธิ์ SSH จะแทนที่ VM อยู่แล้ว ให้คาดหวังสิ่งนี้ใน
การเชื่อมต่อครั้งแรกสุดหลังจากนำมาใช้
</Aside>

แบนเนอร์เข้าสู่ระบบรายงานสถานะการลงทะเบียนของโหนด ซึ่งเป็นวิธีที่เร็วที่สุดในการแยกแยะ
โหนดที่ยังกำลังเริ่มทำงานออกจากโหนดที่เสียหาย:

```text
Registration Status: PROVISIONING
SLO IP: 10.0.1.4/26
```

## การจัดหาคู่คีย์

<Steps>

1. สร้างคู่คีย์ หากคุณยังไม่มี ใช้ Ed25519 แทน RSA: สั้นกว่า
   และได้รับการยอมรับโดย `sshd` ของอุปกรณ์

   ```bash
   ssh-keygen -t ed25519 -C "ce-operator" -f ~/.ssh/id_ed25519
   ```

2. ชี้การปรับใช้ไปที่ครึ่ง **สาธารณะ** โมดูลรากอ่านไฟล์เพียงครั้งเดียวและ
   ส่งสตริงลงไปยังทุกโหนด:

   ```hcl
   # terraform/terraform.tfvars
   ssh_public_key_path = "~/.ssh/id_ed25519.pub"
   ```

   `ssh_public_key` รับเนื้อหาแบบ inline แทน ซึ่งเป็นสิ่งที่การทดสอบแผนใช้
   ครึ่งส่วนที่เป็นคีย์ส่วนตัวไม่เคยออกจากเวิร์กสเตชันของคุณ

3. Apply อ่านคำเตือนที่ด้านบนของหน้านี้ก่อน — บนการปรับใช้ที่มีอยู่แล้ว สิ่งนี้
   จะแทนที่ VM ของ CE

</Steps>

<Aside type="note" title="admin_ssh_key ของ VM เองเป็นคนละเรื่องกัน">
`azurerm_linux_virtual_machine.admin_ssh_key` ใน `modules/ce-node` ให้สิทธิ์แก่ผู้ดูแลระบบ
VM ของ Azure ไม่ใช่บัญชี `admin` ของอุปกรณ์ มันไม่ได้ให้การเข้าถึง Site CLI และ
การที่มันถูกตั้งค่าไว้ไม่ใช่หลักฐานว่า CE SSH ได้รับการกำหนดค่าแล้ว
</Aside>

| ข้อมูลรับรองใช้ได้เฉพาะตอนสร้างเท่านั้น | `sshd` เริ่มทำงานประมาณ 90 วินาทีหลังจากการบูตครั้งแรก ก่อนที่วัตถุไซต์จะมีอยู่ `admin_user_credentials` ยังปรากฏใน `ReplaceSpecType` และใช้งานได้แบบ in place |
| `block_all_services` | การปิดพอร์ต 22 บนที่อยู่การจัดการเหมือนกันไม่ว่าบริการจะถูกบล็อกหรือไม่ |
| ตัวขึ้นบรรทัดใหม่ต่อท้ายคีย์ | ทดสอบทั้งสองแบบ ไม่มีการเปลี่ยนแปลง cloud-init ยังคงตัดมันออกอยู่ดี เพราะไม่เช่นนั้นบล็อกแบบตามตัวอักษรจะแสดงบรรทัดที่สองที่ว่างเปล่า |
| ซอฟต์แวร์ CE รุ่นเก่าที่ถูกตรึงไว้ | ทำซ้ำได้บนสามบิลด์ รวมถึงหนึ่งบิลด์ที่รัน OpenSSH 9.9 |
| `admin_password` ที่ขาดหายไป | การตั้งค่า `admin_password` ควบคู่กับ `ssh_key` บน CE ที่สร้างใหม่ทั้งหมดไม่ได้เปลี่ยนแปลงอะไรเลย |

<Aside type="caution" title="ฟิลด์ API สองฟิลด์ที่ดูเหมือนตัวแยกแยะแต่ไม่ใช่">
`gc_spec.admin_ssh_key` ว่างเปล่าใน **ทั้ง 88 ไซต์ในเทแนนต์** รวมถึง 20 ไซต์ที่
ตั้งค่า `admin_password` การเปรียบเทียบมันระหว่างไซต์ที่ทำงานได้กับที่ไม่ทำงานไม่ได้บอกอะไรคุณเลย
เพราะมันว่างเปล่าทุกที่

`registrations_by_site` ละเว้นฟิลด์นี้ทั้งหมดและคืนค่า `None` สำหรับมัน ซึ่งอ่านได้ว่า
"ไม่ได้กำหนดค่า" แทนที่จะเป็น "ไม่ได้รายงาน"
</Aside>
