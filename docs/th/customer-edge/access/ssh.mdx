**ไม่มีเส้นทาง SSH ของ `admin` ที่รองรับบนบิลด์ CE ที่เทแนนต์นี้ใช้งานอยู่** —
`crt-20250613-3382`, OS `9.2024.6` เรื่องนี้ไม่ใช่ประเด็นของการกำหนดค่า บัญชี
`admin` มีอยู่จริง `sshd` ทำงานอยู่ และ `admin_user_credentials.ssh_key`
ได้รับการยอมรับโดยอ็อบเจกต์ไซต์และถูกส่งกลับมาเมื่ออ่านค่าผ่าน API — แต่คีย์นั้น
ไม่เคยถูกนำไปใช้กับโหนด ดังนั้นทุกความพยายามในการยืนยันตัวตนจึงถูกปฏิเสธ

ให้ใช้ [debug API](../debug-api/) แทน ซึ่งเข้าถึงพื้นผิวคำสั่งแบบอ่านอย่างเดียวของโหนด
และมีสคริปต์เตรียมไว้แล้วในรีโพซิทอรีนี้

<Aside type="danger" title="การรองรับเรื่องนี้ใน Terraform ถูกนำออกแล้ว">
`admin_user_credentials` เคยถูกเชื่อมเข้ากับ `terraform/modules/xc-site` แล้วถูกย้อนกลับ
เมื่อรวบรวมหลักฐานด้านล่างได้ครบ (#660, PR #663) มันไม่ใช่ช่องว่างที่รอการเติมเต็ม —
ฟิลด์นี้ไม่ได้กำหนดค่าอะไรบนโหนดเลย อย่านำกลับมาใส่ใหม่
</Aside>

## เหตุใดทุกความพยายามจึงดูเหมือนปัญหาเครือข่าย

`sshd` ผูกกับ `0.0.0.0:22` บน CE แต่มีเพียงแอดเดรส **ภายใน (SLI)** เท่านั้นที่อยู่บน
สแตกเครือข่ายของโฮสต์ เมื่อทดสอบจาก `ar-ecmp-client` ภายใน VNet เดียวกัน กับ CE
สาธิตทั้งสามเครื่อง:

```text
10.0.1.4     TimeoutError: timed out         ← CE mgmt/SLO  (eth0)
10.0.2.4     TimeoutError: timed out         ← CE external  (eth1)
10.0.3.5     CONNECTED  SSH-2.0-OpenSSH_8.7  ← CE internal/SLI
10.0.3.6     CONNECTED  SSH-2.0-OpenSSH_8.7
10.0.3.7     CONNECTED  SSH-2.0-OpenSSH_8.7
10.0.3.99    TimeoutError: timed out         ← unused address, negative control
```

กลไกนี้มองเห็นได้ใน [`health`](../../commands/system/health/): **eth0 ถูกเปลี่ยนชื่อเป็น
`a-i-eth0` และไม่มี IP address ของโฮสต์** — ดาต้าเพลน Argo เป็นเจ้าของอินเทอร์เฟซนั้น —
ขณะที่ eth1 และ eth2 ยังคงอยู่บนสแตกของโฮสต์ที่ `sshd` กำลังรับฟังอยู่

ดังนั้นการทดสอบไปยังแอดเดรสที่คุณรู้จักโหนดนั้น ซึ่งก็คือแอดเดรสสำหรับการจัดการ จะหมดเวลา
เหมือนกับที่ security group ปิดอยู่ทุกประการ ไม่มีอะไรบล็อกมันเลย เพียงแต่ไม่มีตัวรับฟัง
บนแอดเดรสนั้นที่จะตอบกลับ

<Aside type="caution" title="ทดสอบจากภายใน VNet และทดสอบที่แอดเดรสภายใน">
ความผิดพลาดในการวัดสองอย่างตรงนี้ให้คำตอบที่ผิดอย่างมั่นใจ

การทดสอบพอร์ต 22 ที่ eth0 หรืออินเทอร์เฟซภายนอกจะรายงานว่าปิดเสมอ ไม่ว่าสถานะ SSH
ของโหนดจะเป็นอย่างไร ดังนั้นจึงบอกอะไรเกี่ยวกับ SSH ไม่ได้เลย มีเพียงแอดเดรส SLI เท่านั้น
ที่ตอบกลับ

และการทดสอบจากเวิร์กสเตชันขององค์กรอาจรายงานว่าพอร์ต **เปิด** ทั้งที่จริงแล้วปิดอยู่:
Netskope ทำ TCP handshake ให้เองบนพอร์ตทั่วไป พอร์ต 80 และ 443 อ่านค่าได้ว่าเปิดอยู่
บนแอดเดรสสาธารณะของ CE เมื่อทดสอบจากเวิร์กสเตชัน แต่ปิดเมื่อทดสอบจากภายใน VNet
จงทดสอบจาก VM ภายใน VNet
</Aside>

## เหตุใด `admin` จึงยืนยันตัวตนไม่ได้

`vpm` กำหนดค่าผู้ใช้ในเครื่องของโหนดตอนลงทะเบียน และมันปฏิเสธที่จะแตะต้องบัญชีนี้
จากล็อกของโหนดเอง สามครั้งภายในการบูตครั้งเดียว:

```text
vpm  users.go:165: Won't do any change for user admin (internal skip)
```

ทุกอย่างที่เหลือสอดคล้องกับบรรทัดเดียวนั้น:

- บัญชีมีอยู่จริง — `uid=2202(admin) gid=2202(admin) groups=2202(admin),2301(vpm)`,
  โฮมไดเรกทอรี `/var/home/admin`, เชลล์สำหรับล็อกอิน `/opt/bin/vpmu` ซึ่งก็คือ Site CLI
- `/var/home/admin/.ssh` **ไม่เคยมีอยู่** ไม่ว่าจะก่อนหรือหลังไซต์เข้าสู่สถานะ `ONLINE`
  ไม่มีการเขียนไฟล์ `authorized_keys` ณ จุดใดเลย
- `sshd -T` รายงาน `pubkeyauthentication yes`, `passwordauthentication no`,
  `kbdinteractiveauthentication no` ค่า `PasswordAuthentication yes` เพียงแห่งเดียวใน
  `/etc/ssh/sshd_config` อยู่ภายใน `Match User vesbkp,xcuser` ดังนั้น `admin` จึงถูกกันออกจาก
  การยืนยันตัวตนด้วยรหัสผ่าน **ตั้งแต่ระดับอิมเมจ**
- วันที่เปลี่ยนแปลงล่าสุดในไฟล์ shadow ของ `admin` คือวันที่สร้างอิมเมจ 2024-02-16 ขณะที่
  `vesbkp` และ `vesopcon` แสดงวันที่ปัจจุบัน `vpm` ตั้งค่าสองบัญชีนั้นและไม่เคยแตะต้อง
  `admin` เลย
- `vpm` ไม่ได้บันทึกล็อกอะไรเกี่ยวกับ `ssh_key` หรือ `authorized_keys` เลยแม้แต่น้อย

ฝั่งไคลเอนต์ก็สอดคล้องกัน จากความพยายามยืนยันตัวตน 45 ครั้ง ครอบคลุมการดีพลอยใหม่ตั้งแต่ต้น
สามครั้ง การอัปเดตแบบ in-place สองครั้ง และบิลด์ CE ที่ต่างกันสามบิลด์ — รวมถึงบิลด์ล่าสุด
ที่รัน OpenSSH 9.9:

```text
debug1: Authenticating to <sli-ip>:22 as 'admin'
debug1: Offering public key: ... ED25519 SHA256:ENH3M0bFPYMt... explicit
debug1: Authentications that can continue: publickey
admin@<sli-ip>: Permission denied (publickey).
```

เซิร์ฟเวอร์ไม่เคยเสนอการยืนยันตัวตนด้วยรหัสผ่านหรือแบบ keyboard-interactive และ
`journalctl -u sshd` บนโหนดบันทึกว่า
`Connection closed by authenticating user admin ... [preauth]`

## สิ่งที่ไม่ใช่สาเหตุ

แต่ละข้อต่อไปนี้ถูกทดสอบและตัดออกไปแล้ว และแต่ละข้อก็เป็นการคาดเดาที่ดูสมเหตุสมผลพอ
ที่จะทำให้เสียเวลาไปหนึ่งวัน

| ไม่ใช่สาเหตุ | ตัดออกไปได้อย่างไร |
| --- | --- |
| ข้อมูลรับรองใช้ได้เฉพาะตอนสร้างเท่านั้น | `sshd` เริ่มทำงานประมาณ 90 วินาทีหลังบูตครั้งแรก *ก่อนที่อ็อบเจกต์ไซต์จะมีอยู่* — `sshd[1238]: Server listening on 0.0.0.0 port 22` เวลา 13:04:56 ไซต์ถูกสร้างเวลา 13:05:23 นอกจากนี้ `admin_user_credentials` ยังมีอยู่ใน `ReplaceSpecType` และใช้งานได้แบบ in place |
| `block_all_services` | การปิดพอร์ต 22 บน SLO เหมือนกันทุกประการ ไม่ว่าจะบล็อกบริการหรือไม่ก็ตาม |
| อักขระขึ้นบรรทัดใหม่ต่อท้ายคีย์ | ทดสอบทั้งสองแบบแล้ว ไม่มีความเปลี่ยนแปลง |
| ซอฟต์แวร์ CE ที่ถูกตรึงไว้เวอร์ชันเก่า | ทำซ้ำได้บนสามบิลด์ รวมถึงบิลด์หนึ่งที่ใช้ OpenSSH 9.9 |
| การขาด `admin_password` | การตั้งค่า `admin_password` ควบคู่กับ `ssh_key` บน CE ที่สร้างใหม่ตั้งแต่ต้นไม่ได้เปลี่ยนแปลงอะไรเลย |

<Aside type="caution" title="ฟิลด์ API สองตัวที่ดูเหมือนเป็นตัวชี้ขาดแต่ไม่ใช่">
`gc_spec.admin_ssh_key` ว่างเปล่าใน **ทั้ง 88 ไซต์ในเทแนนต์** รวมถึง 20 ไซต์ที่ตั้งค่า
`admin_password` การเปรียบเทียบค่านี้ระหว่างไซต์ที่ใช้งานได้กับไซต์ที่ใช้งานไม่ได้
ไม่ได้บอกอะไรคุณเลย เพราะมันว่างเปล่าทุกที่

`registrations_by_site` ละเว้นฟิลด์นี้ไปทั้งหมดและคืนค่า `None` ให้ ซึ่งอ่านได้ว่า
"ไม่ได้กำหนดค่า" มากกว่า "ไม่ได้รายงาน"
</Aside>

### การควบคุม Site CLI ผ่าน `az vm run-command`

`/opt/bin/vpmu` คือเชลล์สำหรับล็อกอินของ `admin` ดังนั้นการเรียกใช้ผ่าน `az vm run-command`
จึงเข้าถึง Site CLI แบบโต้ตอบตัวเดียวกันกับที่ SSH จะเข้าถึงได้
ตรวจสอบยืนยันแล้วบน CE ชั่วคราวที่ใช้บิลด์เดียวกัน โดย `execcli docker-ps`,
`execcli ip-link-show` และ `health` ล้วนถูกเก็บข้อมูลด้วยวิธีนี้

จำเป็นต้องใช้กลไกสองอย่าง และทั้งสองอย่างไม่ได้ชัดเจนในตัวเอง:

- **`vpmu` จะ panic หากไม่มี PTY** —
  `go-prompt … NewStandardInputParser: no such device or address` ต้องจัดสรร PTY ให้
- **ข้อความคำสั่งกับไบต์ Enter ต้องเป็นการเขียนแยกกัน** หากเขียนในครั้งเดียว
  อักขระขึ้นบรรทัดใหม่จะตกลงในบัฟเฟอร์เป็นอักขระตัวอักษรจริง และ CLI จะตอบว่า
  `unknown command "execcli\n"` ซึ่งอ่านได้เหมือนกับว่าคำสั่งนั้นไม่มีอยู่

เมนูแบบโต้ตอบแสดงรายการ `configure`, `configure-generic-hardware`,
`configure-network`, `configure-http-proxy`, `diagnosis` และ `health` **`execcli` เป็น
คำสั่งที่ซ่อนอยู่** — ไม่ปรากฏในเมนูนั้น และรับชื่อคำสั่งจากแคตตาล็อกเป็นอาร์กิวเมนต์

<Aside type="note" title="เส้นทางนี้ได้รับการตรวจสอบยืนยันบน CE ชั่วคราว ไม่ใช่บนเดโม">
เส้นทาง `run-command` ถูกทดลองใช้บน CE แบบใช้แล้วทิ้งที่รันบิลด์เดียวกันและ
การกำหนดค่าเดียวกัน ยังไม่ได้รันซ้ำกับ `ar-bgp-eastus01/02/03` ดังนั้นให้ถือว่า
พฤติกรรมที่นั่นเป็นสิ่งที่คาดหวังมากกว่าที่พิสูจน์แล้ว ส่วนเส้นทาง debug API นั้น *ได้รับ*
การตรวจสอบยืนยันกับเดโมแล้ว
</Aside>
