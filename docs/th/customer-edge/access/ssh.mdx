บันทึกไว้เมื่อ 2026-07-28 จาก CE หนึ่งเครื่องของการติดตั้งนี้ `sitecli/capture-manifest.json`
บันทึกว่าเป็นโหนดใด และ `scripts/capture-sitecli.sh --check` จะตรวจสอบพื้นผิวคำสั่ง
ซ้ำอีกครั้งกับ CE ที่กำลังทำงานอยู่

SSH เข้าถึงบัญชี `admin` ของแอปพลายแอนซ์ ซึ่งมี login shell เป็น Site CLI
(`/opt/bin/vpmu`) นี่เป็นเส้นทางเดียวไปยัง**พื้นผิวคำสั่งบนเครื่องแบบเต็ม** —
[debug API](../debug-api/) เปิดเผย 34 คำสั่ง และตัวแอปพลายแอนซ์เองมีอีกมากมาย
ที่ไม่ได้อยู่บน API นั้นเลย

```bash
cd terraform
SLI=$(terraform output -json ce_sli_private_ips | jq -r '.eastus01')
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<operator-vm> "admin@$SLI"
```

ทุกส่วนของบรรทัดคำสั่งนั้นมีความสำคัญ และสามหัวข้อถัดไปจะอธิบายว่า
แต่ละส่วนป้องกันความล้มเหลวแบบใด

<Aside type="danger" title="ค้นหาแอดเดรสภายในเสมอ — อย่านำมาจากเซสชันก่อนหน้า">
Azure กำหนดซับเน็ตภายในใหม่ทุกครั้งที่สร้างใหม่ และไม่ได้เรียงตามลำดับโหนด หลังจากการสร้างใหม่
ครั้งล่าสุด `f5-xc-ce-vm-01`, `-02` และ `-03` ถือ `10.0.3.7`, `10.0.3.5` และ `10.0.3.4`;
บิลด์ก่อนหน้ามีลำดับที่ต่างออกไปโดยสิ้นเชิง และ NIC ของไคลเอนต์ทดสอบก็อยู่ในซับเน็ต
เดียวกันและเคยถือแอดเดรสที่ CE เคยถือมาก่อน การเชื่อมต่อไปยังแอดเดรสที่จำไว้
จึงไปลงที่โหนดผิด ที่ VM ที่ไม่ใช่ CE หรือไม่ลงที่ใดเลย — และกรณีสุดท้ายนั้น
ดูเหมือนกันเป๊ะกับ "SSH ไม่ได้เปิดใช้งาน"

`terraform output -json ce_sli_private_ips` คือการแมป หากไม่มี state อยู่ในมือ
ชื่อ NIC จะคงที่แม้ว่าแอดเดรสจะไม่คงที่:

```bash
az network nic show -g "$(terraform output -raw resource_group_name)" \
  -n "$(terraform output -json ce_vm_names | jq -r '.eastus01')-internal-nic" \
  --query ipConfigurations[0].privateIPAddress -o tsv
```

</Aside>

<Aside type="caution" title="เฉพาะช่วง bootstrap เท่านั้น — CE ที่มีอยู่แล้วไม่สามารถได้รับ SSH โดยไม่ถูกสร้างใหม่">
cloud-init `write_files` ทำงาน**หนึ่งครั้ง ตอนบูตครั้งแรก** หลังจากนั้นจะมีมาร์กเกอร์
`/etc/cloud/cloud-init.disabled` อยู่บนโหนด และ cloud-init จะไม่ทำงานอีก

ดังนั้นจึงไม่มีเส้นทางแบบ in-place ไปยัง CE ที่กำลังทำงานอยู่ `custom_data` เป็นแบบ
replace-only ใน Azure ซึ่งหมายความว่าการนำสิ่งนี้มาใช้บนการติดตั้งที่มีอยู่แล้ว
**จะแทนที่ CE VM ทุกเครื่อง** การให้สิทธิ์ SSH ของผู้ปฏิบัติงานแก่โหนดที่ทำงานอยู่แล้ว
คือการสร้างใหม่ ไม่ใช่การเปลี่ยนแปลงการตั้งค่า — และคำเตือนถัดไปคือสิ่งที่การสร้างใหม่นั้น
เคยต้องแลกมา และเหตุผลที่ตอนนี้ไม่ต้องแลกอีกแล้ว
</Aside>

<Aside type="caution" title="การแทนที่ CE VM เคยทำให้การลงทะเบียนติดค้างอย่างถาวร — เรื่องนั้นแก้ไปแล้ว และนั่นคือเหตุผลที่อ็อบเจกต์ไซต์ถูกผูกกับ VM">
ควรทราบก่อนวางแผนการสร้างใหม่ เพราะรูปแบบของความล้มเหลวจะอธิบาย
การผูกโยงที่คุณจะเห็นในแผน

เดิมทีการลงทะเบียนของโหนดที่ถูกทำลายยังคงถือดัชนีเอกลักษณ์
`(tenant, cluster_name, hostname)` ของ control plane ไว้ ดังนั้นการลงทะเบียนของโหนด
ที่มาแทนจึงถูกปฏิเสธด้วย `UniqueSecondaryIndexViolationError` และลองใหม่ไม่สิ้นสุด
การลบการลงทะเบียนออกเพียงอย่างเดียวก็ไม่เพียงพอ: `StatusObject` ที่หลงเหลืออยู่
จะคืนค่า `500` สำหรับคำขอ workload และเมื่อถึงจุดนั้นแต่ละโหนดได้บันทึก
`registration-obj.yml` ที่ตรึงมันไว้กับการลงทะเบียนที่คุณลบไปแล้ว จึงวนลูปที่ `404`
โดยไม่สามารถฟื้นตัวได้เอง การกู้คืนต้องสร้างใหม่ทั้งหมดสองรอบ ตลอดเวลาทั้งหมดนั้น
`terraform plan` รายงานว่า **"No changes"** เพราะจากมุมมองของ Terraform
สถานะที่ต้องการได้บรรลุแล้ว

[Issue 674](https://github.com/f5-sales-demo/mcn/issues/674) ถูกปิดแล้ว โดย
[PR 693](https://github.com/f5-sales-demo/mcn/pull/693) ปัจจุบัน `modules/xc-site` ระบุ
อินสแตนซ์ CE VM ใน `replace_triggered_by` ดังนั้นการแทนที่ VM จะแทนที่อ็อบเจกต์ไซต์
และการลบไซต์จะพาการลงทะเบียนของมันไปด้วย — คีย์ดัชนีจะว่างก่อนที่โหนดที่มาแทนจะบูต
ฟลีตนี้ได้ถูกสร้างใหม่ตั้งแต่ต้นแล้ว และทั้งสามไซต์ขึ้นสถานะ `ONLINE` โดยไม่ต้องเข้าไปแทรกแซง

การผูกโยงนี้สังเกตได้จริง ไม่ใช่เพียงการสันนิษฐาน แต่ละไซต์ถูกผูกกับ *instance* id ของ VM
และการลงทะเบียนที่ตรงกันจะรายงานค่าเดียวกันเป็น `infra.instance_id`:

```bash
cd terraform && terraform output -json ce_bound_instance_ids
```

ความไม่ตรงกันระหว่างสองค่านั้นหมายความว่าไซต์ยังคงถูกผูกกับโหนดที่ไม่มีอยู่อีกแล้ว
ซึ่งเป็นสถานะที่ CE ที่สร้างใหม่จะไม่สามารถลงทะเบียนออกมาได้เลย การอ่านฝั่ง
การลงทะเบียนยังต้องเรียก API โดยตรง — provider issue
[1376](https://github.com/f5-sales-demo/terraform-provider-xcsh/issues/1376) คือสิ่งที่จะ
ทำให้มันอยู่บน data source
</Aside>

## เหตุใด cloud-init จึงเขียนคีย์ แทนที่จะเป็น API

`admin_user_credentials.ssh_key` บนอ็อบเจกต์ไซต์ดูเหมือนเป็นฟิลด์สำหรับเรื่องนี้เป๊ะ
มันถูกยอมรับ มันรอดจากการอ่านย้อนกลับ และมันไม่ได้ตั้งค่าอะไรเลย `vpm` เป็นเจ้าของ
ผู้ใช้ท้องถิ่นของโหนดและปฏิเสธที่จะแตะต้องผู้ใช้รายนี้ — จากล็อกของโหนดเอง สามครั้ง
ในการบูตครั้งเดียว:

```text
vpm  users.go:165: Won't do any change for user admin (internal skip)
```

ทุกอย่างที่เหลือสืบเนื่องมาจากบรรทัดนั้นบรรทัดเดียว `/var/home/admin/.ssh` ไม่เคยมีอยู่
ไม่ว่าก่อนหรือหลังจากที่ไซต์ถึงสถานะ `ONLINE` วันที่เปลี่ยนแปลงล่าสุดของ shadow ของ
`admin` ยังคงเป็นวันที่สร้างอิมเมจ ขณะที่ `vesbkp` และ `vesopcon` แสดงวันที่ปัจจุบัน
เพราะ `vpm` ตั้งค่าสองรายนั้นและข้าม `admin` ไป และ `vpm` ไม่ได้บันทึกล็อกอะไรเกี่ยวกับ
`ssh_key` หรือ `authorized_keys` ณ จุดใดเลย

ดังนั้นไฟล์นั้นจึงต้องถูกเขียนภายนอก `vpm` `admin` คือ uid 2202 ซึ่งฝังมาในอิมเมจของโหนด
ดังนั้นมันมีอยู่ก่อนที่ cloud-init จะทำงาน และ `owner: admin:admin` จะแปลงค่าได้ตอนเขียน
— ไม่ต้องมี `runcmd` ไม่ต้องแก้ไขความเป็นเจ้าของภายหลัง:

```yaml
- path: /var/home/admin/.ssh/authorized_keys
  permissions: "0600"
  owner: admin:admin
  content: |
    ${ssh_public_key}
```

`sshd` เต็มใจอยู่แล้วตลอดมา `sshd -T` รายงาน `pubkeyauthentication yes` และ `admin`
ปรากฏใน `AllowUsers` ในไฟล์ `sshd_config` ทั้งสองไฟล์ที่มาพร้อมกับโหนด ไม่เคยมีอะไร
ที่ต้องเปิดใช้งานเลย — มีเพียงไฟล์ที่ขาดไป

<Aside type="danger" title="อย่าเพิ่ม admin_user_credentials กลับเข้ามา และอย่าแก้ไข sshd_config">
`admin_user_credentials` เคยถูกต่อเข้ากับ `terraform/modules/xc-site` และถูกย้อนกลับ
เมื่อเก็บหลักฐานนี้ได้แล้ว (#660, PR #663) มันไม่ใช่ช่องว่างที่รอการเติมเต็ม

`sshd_config` จะถูกแทนที่ในช่วงการลงทะเบียน ดังนั้นการแก้ไขมันจะถูกทิ้งไป
ในจังหวะที่ไม่สะดวกที่สุด
</Aside>

## เหตุใดจึงตอบสนองบนแอดเดรสเดียวเท่านั้น

`sshd` bind กับ `0.0.0.0:22` แต่มีเพียงแอดเดรส**ภายใน (SLI)** เท่านั้นที่อยู่บน
network stack ของโฮสต์ในลักษณะที่ `sshd` จะตอบสนอง eth0 ถูกเปลี่ยนชื่อเป็น `a-i-eth0`
และไม่มี host IP เลย — Argo data plane เป็นเจ้าของอินเทอร์เฟซนั้น และแอดเดรส
management/SLO ที่มันน่าจะถือไว้จะไปปรากฏบน `vhost0` แทน NIC อีกสองตัวยังคงอยู่บน
host stack ภายใต้ชื่อของตัวเอง

ตรวจสอบจาก VM ภายใน VNet ต่อ CE หนึ่งเครื่อง:

```text
management/SLO address    timed out
external address          timed out
internal/SLI address      OPEN     SSH-2.0-OpenSSH_8.7
an unused address         timed out    (control)
```

การตรวจสอบต่อแอดเดรสที่คุณรู้จักโหนดนั้นจึงคืนผลลัพธ์เหมือนกันเป๊ะกับที่ security group
ที่ปิดอยู่จะคืนมา ไม่มีอะไรบล็อกมัน แต่ไม่มี listener บนแอดเดรสนั้น

<Aside type="caution" title="อย่าอ่านชื่ออินเทอร์เฟซของ guest เพื่อหาว่าคุณอยู่บนซับเน็ตใด">
ระหว่าง `eth1` และ `eth2` ตัวใดถือแอดเดรสภายในนั้น**แตกต่างกันระหว่างโหนดในการติดตั้ง
เดียวกันนี้** อ่านสด ๆ จาก CE ทั้งสามเครื่อง:

```text
f5-xc-ce-vm-01    eth1 -> external      eth2 -> internal/SLI
f5-xc-ce-vm-02    eth2 -> external      eth1 -> internal/SLI
f5-xc-ce-vm-03    eth1 -> external      eth2 -> internal/SLI
```

มีเพียงสองสิ่งที่เป็นจริงบนทุกโหนด: `a-i-eth0` ไม่มีแอดเดรส และ `vhost0` ถือแอดเดรส
management/SLO สำหรับเรื่องอื่น ๆ ให้จับคู่ด้วยแอดเดรสในผลลัพธ์ของ
[`ip addr`](../../commands/network/ip/) แทนที่จะใช้ชื่ออินเทอร์เฟซ
</Aside>

แอดเดรสสาธารณะของ CE ก็ไม่มี listener บนพอร์ต 22 ด้วย ซึ่งเป็นเหตุผลที่คำสั่งด้านบน
ต้องผ่าน `-J`: VM ของผู้ปฏิบัติงานภายใน VNet ในซับเน็ตเดียวกับแอดเดรส SLI
การติดตั้งนี้สร้างขึ้นมาหนึ่งเครื่องเพื่อจุดประสงค์นี้ —
`terraform output -raw client_vm_name` จะบอกชื่อมัน

<Aside type="caution" title="-J ไม่ได้ส่งตัวเลือกของคุณไปยังช่วง jump">
ตัวเลือกที่ให้ไว้บนบรรทัดคำสั่งจะใช้กับ hop สุดท้าย `-o UserKnownHostsFile=/dev/null`
ที่อยู่ควบคู่กับ `-J` จึงยังคงอ่านและเขียน `known_hosts` จริงของคุณสำหรับโฮสต์ *jump*
ซึ่งเป็นเรื่องน่าประหลาดใจหากคุณพยายามกันฟลีตที่สร้างใหม่ออกจากมัน ระบุ hop แรก
ให้ชัดเจนเมื่อเรื่องนี้สำคัญ:

```bash
ssh -tt -o ProxyCommand="ssh -W %h:%p -o UserKnownHostsFile=/dev/null azureuser@<operator-vm>" \
    -o UserKnownHostsFile=/dev/null -i ~/.ssh/id_ed25519 "admin@$SLI"
```

</Aside>

<Aside type="caution" title="ความผิดพลาดในการวัดสองอย่างที่ให้คำตอบผิดอย่างมั่นใจ">
การตรวจสอบ eth0, อินเทอร์เฟซภายนอก หรือแอดเดรสสาธารณะสำหรับพอร์ต 22 จะรายงานว่าปิด
ไม่ว่าสถานะ SSH ของโหนดจะเป็นอย่างไร ดังนั้นมันจึงไม่สามารถบอกอะไรคุณได้เลย
มีเพียงแอดเดรส SLI ที่ตอบสนอง

และการตรวจสอบจากเวิร์กสเตชันขององค์กรอาจรายงานว่าพอร์ต**เปิด** ในขณะที่มันปิดอยู่:
Netskope ทำ TCP handshake ให้เองบนพอร์ตทั่วไป พอร์ต 80 และ 443 อ่านค่าได้ว่าเปิด
บนแอดเดรสสาธารณะของ CE เมื่อดูจากเวิร์กสเตชัน แต่ปิดเมื่อตรวจสอบจากภายใน VNet
ให้ตรวจสอบจาก VM ใน VNet
</Aside>

## Site CLI ต้องการเทอร์มินัล และ carriage return

login shell ของ `admin` ไม่ใช่ shell มันคือแอปพลิเคชัน `go-prompt` ซึ่งทำให้เทอร์มินัล
อยู่ในโหมด raw และอ่านการกดแป้นแทนที่จะอ่านเป็นบรรทัด ผลตามมาสี่ประการ แต่ละอย่าง
ล้มเหลวในลักษณะที่ดูเหมือนเป็นปัญหาที่ต่างกัน:

| กลไก | สิ่งที่เกิดขึ้นหากไม่มีมัน |
| --- | --- |
| จัดสรรเทอร์มินัล (`ssh -tt`) | `panic: no such device or address` จาก `go-prompt.NewStandardInputParser` ซึ่งอ่านได้เหมือนแอปพลายแอนซ์แครช |
| ส่ง carriage return ไม่ใช่ line feed สำหรับ Enter | บรรทัดนั้นไม่เคยถูกส่ง และเซสชันปิดลงเมื่อสิ้นสุดอินพุตโดยไม่พิมพ์อะไรเลย |
| เปิด standard input ไว้ | การเชื่อมต่อสิ้นสุดก่อนที่คำสั่งจะแสดงผล ทำให้คำสั่งที่ทำงานได้ดูเหมือนเงียบ |
| เขียนข้อความคำสั่งและไบต์ Enth **แยกกัน** | newline จะไปอยู่ในบัฟเฟอร์เป็นอักขระตามตัวอักษร และ CLI ตอบว่า `unknown command` ซึ่งอ่านเหมือนว่าคำสั่งนั้นไม่มีอยู่ |

`ssh host 'some-command'` จึงไม่ทำงาน: อาร์กิวเมนต์จะถูกละเลยและพรอมต์แบบโต้ตอบ
จะเริ่มขึ้นอยู่ดี ควบคุมมันแบบเทอร์มินัล ไม่งั้นก็อย่าใช้เลย
`scripts/sitecli_ssh_harvest.py` คือการนำไปใช้อ้างอิง

<Aside type="caution" title="panic ที่อ่านว่า 'no such device or address' หมายความว่าการยืนยันตัวตนสำเร็จแล้ว">
`vpmu` ส่งข้อความนี้ออกมา**หลัง**การเข้าสู่ระบบ เมื่อไม่พบเทอร์มินัลให้แนบกับ หากอ่านว่า
เป็นการแครช มันดูเหมือนผลลัพธ์ที่แย่ที่สุดเท่าที่จะเป็นได้ แต่ที่จริงมันคือข้อผิดพลาด
ตัวสุดท้ายก่อนความสำเร็จ เพิ่ม `-tt` แล้วเชื่อมต่ออีกครั้ง
</Aside>

<Aside type="caution" title="การแทนที่ CE จะเปลี่ยน host key ของมัน">
โหนดที่มาแทนจะแสดง host key ที่แตกต่างกันบนแอดเดรสเดียวกัน ดังนั้นการเชื่อมต่อครั้งถัดไป
จะเตือนว่า `REMOTE HOST IDENTIFICATION HAS CHANGED` และปฏิเสธ ให้ล้างรายการเก่า
ของแอดเดรสนั้นแล้วเชื่อมต่อใหม่ เนื่องจากการให้สิทธิ์ SSH นั้นแทนที่ VM ทั้งหมดอยู่แล้ว
ให้คาดว่าจะพบเรื่องนี้ในการเชื่อมต่อครั้งแรกสุดหลังจากนำมันมาใช้
</Aside>

## แบนเนอร์คือการตรวจสุขภาพฟรี

ก่อนที่คุณจะพิมพ์อะไร แบนเนอร์เข้าสู่ระบบได้ตอบคำถามหลายข้อที่คุณจะต้องเสียคำสั่งไปกับมัน
เรียบร้อยแล้ว จาก `f5-xc-ce-vm-01` โดยตัด ASCII art และ public IP ออก:

```text
UNAUTHORIZED ACCESS TO THIS DEVICE IS PROHIBITED
All actions performed on this device are audited

Using https://register.ves.volterra.io
OS: rhel-9.2024.6
Memory: 32768MiB
Storage: sda: 31GiB
CPU: Model: Intel(R) Xeon(R) Platinum 8272CL CPU @ 2.60GHz | CPUs: 8
Software: crt-20250613-3382
DNS: 168.63.129.16: OK
NTP: Synced
Uptime: 0 days, 5 hours, 20 minutes
Registration Status: PROVISIONED
SLO IP: 10.0.1.4/26
WELCOME IN SITE CLI
```

`Registration Status` แยกแยะโหนดที่ยังกำลังขึ้นมา (`PROVISIONING`) จากโหนดที่
เสร็จแล้ว (`PROVISIONED`) `Software` คือสตริงบิลด์ที่ตัดสินว่าคำสั่งใดมีอยู่
`DNS` และ `NTP` ครอบคลุมสองสิ่งที่ต้องพึ่งพาซึ่งทำให้การลงทะเบียนพังก่อนอย่างอื่น
ดังนั้นโหนดที่ไม่เคยออนไลน์มักได้บอกคุณแล้วว่าเพราะอะไรที่นี่ — ก่อนที่จะต้องใช้
[`chronyc-sources`](../../commands/network/chronyc-sources/) หรือ
[`dig`](../../commands/network/dig/) เลย

## การจัดหาคู่คีย์

<Steps>

1. สร้างคู่คีย์ หากคุณยังไม่มี ใช้ Ed25519 แทน RSA: สั้นกว่า และ `sshd` ของแอปพลายแอนซ์
   ยอมรับ

   ```bash
   ssh-keygen -t ed25519 -C "ce-operator" -f ~/.ssh/id_ed25519
   ```

2. ชี้การติดตั้งไปที่ครึ่ง**สาธารณะ** โมดูลรากอ่านไฟล์หนึ่งครั้งและส่งสตริงลงไป
   ยังทุกโหนด:

   ```hcl
   # terraform/terraform.tfvars
   ssh_public_key_path = "~/.ssh/id_ed25519.pub"
   ```

   `ssh_public_key` รับเนื้อหาแบบ inline แทน ซึ่งเป็นสิ่งที่การทดสอบแผนใช้
   ครึ่งส่วนตัวจะไม่ออกจากเวิร์กสเตชันของคุณเลย

3. Apply อ่านคำเตือนที่ด้านบนของหน้านี้ก่อน — บนการติดตั้งที่มีอยู่แล้ว สิ่งนี้จะแทนที่
   CE VM

</Steps>

<Aside type="note" title="admin_ssh_key ของ VM เองเป็นสิ่งที่แตกต่าง">
`azurerm_linux_virtual_machine.admin_ssh_key` ใน `modules/ce-node` ให้สิทธิ์
ผู้ดูแลระบบ Azure VM ไม่ใช่บัญชี `admin` ของแอปพลายแอนซ์ มันไม่ได้ให้สิทธิ์เข้าถึง
Site CLI และการที่มันถูกตั้งค่าไว้ไม่ใช่หลักฐานว่า CE SSH ถูกตั้งค่าแล้ว
</Aside>

## สิ่งที่นี่ไม่ใช่

แต่ละข้อต่อไปนี้ได้รับการทดสอบและตัดออกไปแล้วในขณะที่ยังเชื่อว่าเส้นทางนี้เป็นไปไม่ได้
แต่ละข้อดูมีเหตุผลมากพอที่จะทำให้เสียเวลาไปหนึ่งวัน

| ไม่ใช่สาเหตุ | ตัดออกไปได้อย่างไร |
| --- | --- |
| ข้อมูลรับรองใช้เฉพาะตอนสร้างเท่านั้น | `sshd` เริ่มทำงานประมาณ 90 วินาทีหลังเข้าสู่การบูตครั้งแรก ก่อนที่อ็อบเจกต์ไซต์จะมีอยู่ `admin_user_credentials` ก็มีอยู่ใน `ReplaceSpecType` ด้วยและใช้งานแบบ in place |
| `block_all_services` | การปิดพอร์ต 22 บนแอดเดรส management เหมือนกันเป๊ะไม่ว่าบริการจะถูกบล็อกหรือไม่ |
| newline ต่อท้ายในคีย์ | ทดสอบทั้งสองแบบ ไม่มีการเปลี่ยนแปลง cloud-init ยังตัดมันออกอยู่ดี เพราะบล็อกแบบตามตัวอักษรจะเรนเดอร์บรรทัดที่สองที่ว่างเปล่าออกมา |
| ซอฟต์แวร์ CE ที่ตรึงเวอร์ชันเก่า | ทำซ้ำได้บนสามบิลด์ รวมถึงหนึ่งบิลด์ที่รัน OpenSSH 9.9 |
| `admin_password` ที่ขาดไป | การตั้ง `admin_password` ควบคู่กับ `ssh_key` บน CE ที่สร้างจากศูนย์ไม่ได้เปลี่ยนแปลงอะไรเลย |

<Aside type="caution" title="ฟิลด์ API สองฟิลด์ที่ดูเหมือนเป็นตัวแยกแยะแต่ไม่ใช่">
`gc_spec.admin_ssh_key` ว่างเปล่าหรือไม่มีอยู่บน**ทั้ง 58 ไซต์ใน `f5-sales-demo`** —
รวมถึงสองไซต์ที่ตั้ง `admin_user_credentials.ssh_key` ไว้ การเปรียบเทียบมันระหว่าง
ไซต์ที่ใช้งานได้และไซต์ที่ใช้งานไม่ได้จึงไม่บอกอะไรคุณเลย เพราะมันอ่านได้ว่าว่างเปล่า
แม้แต่กับไซต์ที่*มี*การตั้งค่าข้อมูลรับรองไว้

`registrations_by_site` ละฟิลด์นี้ออกไปทั้งหมดและคืนค่า `None` สำหรับมัน ซึ่งอ่านได้ว่า
"ไม่ได้ตั้งค่า" มากกว่า "ไม่ได้รายงาน"
</Aside>
