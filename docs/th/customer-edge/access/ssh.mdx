บันทึกเมื่อ 2026-07-28 จาก CE หนึ่งตัวของการใช้งานนี้ `sitecli/capture-manifest.json`
บันทึกโหนดที่ใช้ และ `scripts/capture-sitecli.sh --check` ตรวจสอบ command
surface อีกครั้งกับ CE ที่ใช้งานจริง

SSH เข้าถึงบัญชี `admin` ของอุปกรณ์ ซึ่งมี login shell เป็น Site CLI
(`/opt/bin/vpmu`) นี่เป็นเส้นทางเดียวสู่ **command surface บนกล่องแบบสมบูรณ์** —
[debug API](../debug-api/) เปิดเผย 34 คำสั่ง และตัวอุปกรณ์เองมีอีกหลายคำสั่งที่ไม่อยู่ใน API นั้นเลย

```bash
cd terraform
SLI=$(terraform output -json ce_sli_private_ips | jq -r '.eastus01')
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<operator-vm> "admin@$SLI"
```

ทุกส่วนของ command line นั้นมีความสำคัญ และสามส่วนถัดไปจะอธิบาย
ว่าแต่ละส่วนป้องกันความล้มเหลวใด

ไม่มี shell prompt ให้ใช้งาน: login shell ของ `admin` **คือ** Site CLI ดังนั้นคุณจะมาถึง
prompt `>>>` ของมัน รันคำสั่งบนกล่องด้วย `execcli <name>` ที่นั่น — ดู
[คำสั่งบนกล่อง](../../commands/on-box/)

<Aside type="danger" title="ค้นหาที่อยู่ภายใน — อย่านำที่อยู่จากเซสชันก่อนหน้ามาใช้">
Azure กำหนด internal subnet ใหม่ในทุกการสร้างใหม่ และไม่เรียงตามลำดับโหนด หลังจาก
การสร้างล่าสุด `f5-xc-ce-vm-01`, `-02` และ `-03` ถือ `10.0.3.7`, `10.0.3.5` และ `10.0.3.4`;
การสร้างก่อนหน้ามีลำดับที่แตกต่างกันโดยสิ้นเชิง และ NIC ของ test client อยู่ใน
subnet เดียวกันและเคยถือที่อยู่ที่ CE เคยถือมาก่อน การเชื่อมต่อกับที่อยู่ที่จำไว้
จึงอาจลงเอยที่โหนดผิด ที่ VM ที่ไม่ใช่ CE หรือไม่ได้เชื่อมต่อเลย — และอย่างสุดท้าย
ดูเหมือนกับ "SSH ไม่ได้เปิดใช้งาน" เลย

`terraform output -json ce_sli_private_ips` คือ mapping นั้น หากไม่มี state อยู่ในมือ
ชื่อ NIC คงที่แม้ที่อยู่จะไม่คงที่:

```bash
az network nic show -g "$(terraform output -raw resource_group_name)" \
  -n "$(terraform output -json ce_vm_names | jq -r '.eastus01')-internal-nic" \
  --query ipConfigurations[0].privateIPAddress -o tsv
```

</Aside>

<Aside type="caution" title="Bootstrap เท่านั้น — CE ที่มีอยู่แล้วไม่สามารถเพิ่ม SSH ได้โดยไม่ต้องสร้างใหม่">
cloud-init `write_files` ทำงาน **เพียงครั้งเดียว ในการบูตครั้งแรก** หลังจากนั้น
เครื่องหมาย `/etc/cloud/cloud-init.disabled` จะมีอยู่บนโหนดและ cloud-init จะไม่ทำงานอีก

ดังนั้นจึงไม่มีเส้นทางแบบ in-place ไปยัง CE ที่กำลังทำงาน `custom_data` เป็นแบบ replace-only ใน Azure
ซึ่งหมายความว่าการนำสิ่งนี้มาใช้กับการใช้งานที่มีอยู่แล้ว **จะแทนที่ CE VM ทุกตัว** การให้สิทธิ์
SSH ของผู้ดำเนินการแก่โหนดที่กำลังทำงานอยู่คือการสร้างใหม่ ไม่ใช่การเปลี่ยนแปลงการกำหนดค่า —
และคำเตือนถัดไปคือสิ่งที่การสร้างใหม่นั้นเคยมีต้นทุน และเหตุใดจึงไม่เกิดขึ้นอีกต่อไป
</Aside>

<Aside type="caution" title="การแทนที่ CE VM เคยทำให้การลงทะเบียนค้างอย่างถาวร — สิ่งนั้นได้รับการแก้ไขแล้ว และนั่นคือเหตุที่ site object ถูกผูกไว้กับ VM">
ควรรู้ก่อนที่คุณจะวางแผนการสร้างใหม่ เพราะรูปแบบของความล้มเหลวอธิบายถึง
การผูกมัดที่คุณจะเห็นใน plan

เดิมนั้น การลงทะเบียนของโหนดที่ถูกทำลายจะเก็บดัชนีเฉพาะ `(tenant, cluster_name, hostname)`
ของ control plane ไว้ ดังนั้นการลงทะเบียนของโหนดทดแทนจึงถูกปฏิเสธด้วย
`UniqueSecondaryIndexViolationError` และพยายามใหม่ตลอดเวลา การลบการลงทะเบียนนั้น
ไม่เพียงพอด้วยตัวมันเอง: `StatusObject` ที่เหลืออยู่จะส่งคืน `500` สำหรับคำขอ workload
และถึงจุดนั้นแต่ละโหนดได้บันทึก `registration-obj.yml` ที่ยึดมันกับ
การลงทะเบียนที่คุณลบ ดังนั้นมันจึงวนซ้ำบน `404` โดยไม่มีการกู้คืนตัวเอง การกู้คืน
ต้องใช้การสร้างใหม่สองรอบเต็ม ตลอดเวลาทั้งหมดนั้น `terraform plan` รายงาน **"No changes"**
เพราะจากมุมมองของ Terraform ได้บรรลุสถานะที่ต้องการแล้ว

[Issue 674](https://github.com/f5-sales-demo/mcn/issues/674) ถูกปิดแล้ว โดย
[PR 693](https://github.com/f5-sales-demo/mcn/pull/693) ขณะนี้ `modules/xc-site` ตั้งชื่อ CE
VM instance ใน `replace_triggered_by` ดังนั้นการแทนที่ VM จะแทนที่ site object และ
การลบ site จะลบการลงทะเบียนของมันด้วย — index key จะว่างก่อนที่โหนดทดแทนจะบูต
fleet ได้รับการสร้างใหม่ตั้งแต่ต้นนับแต่นั้น และทั้งสามไซต์ขึ้นมา `ONLINE` โดยไม่ต้องมีการแทรกแซง

การผูกมัดนั้นสังเกตได้มากกว่าจะสันนิษฐาน แต่ละไซต์ถูกผูกไว้กับ VM *instance* id
และการลงทะเบียนที่ตรงกันรายงานค่าเดียวกันกับ `infra.instance_id`:

```bash
cd terraform && terraform output -json ce_bound_instance_ids
```

ความขัดแย้งระหว่างทั้งสองหมายความว่าไซต์ยังคงถูกผูกไว้กับโหนดที่ไม่มีอยู่แล้ว
ซึ่งเป็นสถานะที่ CE ที่สร้างใหม่ไม่สามารถลงทะเบียนออกจากได้ การอ่านข้อมูลครึ่งของการลงทะเบียน
ยังคงต้องการ API call โดยตรง — provider issue
[1376](https://github.com/f5-sales-demo/terraform-provider-xcsh/issues/1376) คือสิ่งที่จะนำ
ข้อมูลนั้นไปไว้ใน data source
</Aside>

## เหตุที่ cloud-init เขียน key ไม่ใช่ API

`admin_user_credentials.ssh_key` บน site object ดูเหมือนกับฟิลด์สำหรับสิ่งนี้พอดี
มันถูกยอมรับ มันอยู่รอดหลังการอ่านกลับ และมันไม่ได้กำหนดค่าอะไรเลย `vpm` เป็น
เจ้าของ local users ของโหนดและปฏิเสธที่จะแตะอันนี้ — จาก log ของโหนดเอง สามครั้ง
ตลอดการบูตครั้งเดียว:

```text
vpm  users.go:165: Won't do any change for user admin (internal skip)
```

ทุกอย่างที่ตามมาเกิดขึ้นจากบรรทัดนั้น `/var/home/admin/.ssh` ไม่เคยมีอยู่ ก่อนหรือ
หลังที่ไซต์ไปถึง `ONLINE` วันที่เปลี่ยนรหัสผ่านล่าสุดใน shadow ของ `admin` ยังคงอยู่ที่
วันที่สร้าง image ในขณะที่ `vesbkp` และ `vesopcon` แสดงวันที่ปัจจุบัน เพราะ `vpm`
ตั้งค่าสองอันนั้นและข้าม `admin` และ `vpm` ไม่มีการบันทึกเกี่ยวกับ `ssh_key` หรือ
`authorized_keys` ณ จุดใดเลย

ดังนั้นไฟล์จึงต้องถูกเขียนนอก `vpm` `admin` คือ uid 2202 ที่ถูก bake ลงใน node
image ดังนั้นมันมีอยู่ก่อนที่ cloud-init จะทำงาน และ `owner: admin:admin` จะแก้ไขได้
ในเวลาเขียน — ไม่มี `runcmd` ไม่มีการแก้ไข ownership:

```yaml
- path: /var/home/admin/.ssh/authorized_keys
  permissions: "0600"
  owner: admin:admin
  content: |
    ${ssh_public_key}
```

`sshd` เต็มใจอยู่เสมอ `sshd -T` รายงาน `pubkeyauthentication yes` และ `admin`
ปรากฏใน `AllowUsers` ในทั้งสอง `sshd_config` ที่มาพร้อมกับโหนด ไม่มีอะไร
ที่ต้องเปิดใช้งาน — มีแค่ไฟล์ที่หายไป

<Aside type="danger" title="อย่าเพิ่ม admin_user_credentials อีก และอย่าแก้ไข sshd_config">
`admin_user_credentials` ถูกเชื่อมต่อไว้ใน `terraform/modules/xc-site` และถูกย้อนกลับเมื่อ
หลักฐานนี้ถูกรวบรวม (#660, PR #663) มันไม่ใช่ช่องว่างที่รอการเติม

`sshd_config` ถูกแทนที่ระหว่างการลงทะเบียน ดังนั้นการแก้ไขมันจะถูกทิ้งในช่วงเวลาที่
ไม่สะดวกที่สุด
</Aside>

## เหตุที่มันตอบสนองบนที่อยู่เดียวเท่านั้น

`sshd` ผูก `0.0.0.0:22` แต่มีเพียงที่อยู่ **internal (SLI)** เท่านั้นที่อยู่บน host network
stack ในลักษณะที่ `sshd` จะตอบสนอง eth0 ถูกเปลี่ยนชื่อเป็น `a-i-eth0` และไม่มี host IP
เลย — Argo data plane เป็นเจ้าของ interface นั้น และที่อยู่ management/SLO ที่มันควรจะมี
ปรากฏบน `vhost0` แทน NIC อีกสองตัวยังคงอยู่บน host stack ภายใต้ชื่อของมันเอง

ตรวจสอบจาก VM ภายใน VNet กับ CE หนึ่งตัว:

```text
management/SLO address    timed out
external address          timed out
internal/SLI address      OPEN     SSH-2.0-OpenSSH_8.7
an unused address         timed out    (control)
```

การตรวจสอบกับที่อยู่ที่คุณรู้จักโหนดนั้นจึงส่งคืนผลเหมือนกับที่ security group ปิดกั้น
ไม่มีอะไรบล็อกมัน ไม่มี listener บนที่อยู่นั้น

<Aside type="caution" title="อย่าอ่านชื่อ interface ของ guest เพื่อคิดออกว่าคุณอยู่บน subnet ใด">
`eth1` และ `eth2` ตัวใดที่รับที่อยู่ภายใน **แตกต่างกันระหว่างโหนดในการใช้งานเดียวกันนี้**
อ่านจากทั้งสาม CE:

```text
f5-xc-ce-vm-01    eth1 -> external      eth2 -> internal/SLI
f5-xc-ce-vm-02    eth2 -> external      eth1 -> internal/SLI
f5-xc-ce-vm-03    eth1 -> external      eth2 -> internal/SLI
```

มีเพียงสองสิ่งที่คงที่บนทุกโหนด: `a-i-eth0` ไม่มีที่อยู่ และ `vhost0` รับที่อยู่
management/SLO สำหรับสิ่งอื่นใด ให้ match บนที่อยู่ใน
[`ip addr`](../../commands/network/ip/) output แทนที่จะ match บนชื่อ interface
</Aside>

ที่อยู่สาธารณะของ CE ไม่มี listener บนพอร์ต 22 เช่นกัน ซึ่งเป็นเหตุที่คำสั่งข้างต้น
ใช้ `-J`: VM ของผู้ดำเนินการภายใน VNet ในซับเน็ตเดียวกับที่อยู่ SLI
การใช้งานนี้สร้างหนึ่งตัวเพื่อจุดประสงค์นั้น —
`terraform output -raw client_vm_name` ตั้งชื่อให้

<Aside type="caution" title="-J ไม่ส่ง options ของคุณไปยัง jump leg">
Options ที่ให้บน command line จะใช้กับ hop สุดท้าย ดังนั้น `-o UserKnownHostsFile=/dev/null`
ที่ใช้พร้อมกับ `-J` จะยังคงอ้างอิงและเขียน `known_hosts` จริงของคุณสำหรับ *jump*
host ซึ่งเป็นสิ่งที่น่าประหลาดใจหากคุณพยายามป้องกันไม่ให้ fleet ที่สร้างใหม่เข้าไปใน
นั้น ระบุ hop แรกออกมาอย่างชัดเจนเมื่อสำคัญ:

```bash
ssh -tt -o ProxyCommand="ssh -W %h:%p -o UserKnownHostsFile=/dev/null azureuser@<operator-vm>" \
    -o UserKnownHostsFile=/dev/null -i ~/.ssh/id_ed25519 "admin@$SLI"
```

</Aside>

<Aside type="caution" title="ข้อผิดพลาดในการวัดสองอย่างที่ให้คำตอบผิดอย่างมั่นใจ">
การตรวจสอบ eth0, external interface หรือ public address สำหรับพอร์ต 22 จะรายงาน
ว่าปิดไม่ว่า SSH state ของโหนดจะเป็นอย่างไร ดังนั้นมันไม่สามารถบอกคุณอะไรได้เลย
มีเพียงที่อยู่ SLI เท่านั้นที่ตอบสนอง

และการตรวจสอบจาก workstation ขององค์กรอาจรายงานพอร์ตว่า **เปิด** ทั้งที่ปิดอยู่:
Netskope ทำการ TCP handshake เองบนพอร์ตทั่วไป พอร์ต 80 และ 443 อ่านว่าเปิดบน
ที่อยู่สาธารณะของ CE จาก workstation และปิดเมื่อตรวจสอบจากภายใน VNet
ตรวจสอบจาก VM ใน VNet
</Aside>

## Site CLI ต้องการเทอร์มินัลและ carriage return

login shell ของ `admin` ไม่ใช่ shell มันเป็นแอปพลิเคชัน `go-prompt` ที่นำ
เทอร์มินัลเข้าสู่ raw mode และอ่าน keystroke แทนที่จะเป็นบรรทัด มีสี่ผลที่ตามมา
แต่ละอย่างล้มเหลวในลักษณะที่ดูเหมือนเป็นปัญหาที่แตกต่างกัน:

| กลไก | สิ่งที่เกิดขึ้นหากไม่มี |
| --- | --- |
| จัดสรรเทอร์มินัล (`ssh -tt`) | `panic: no such device or address` จาก `go-prompt.NewStandardInputParser` ซึ่งดูเหมือนอุปกรณ์ crash |
| ส่ง carriage return ไม่ใช่ line feed สำหรับ Enter | บรรทัดนั้นไม่ถูกส่ง และเซสชันปิดลงที่ end-of-input โดยไม่พิมพ์อะไร |
| เก็บ standard input ไว้เปิด | การเชื่อมต่อสิ้นสุดก่อนที่คำสั่งจะแสดงผล ดังนั้นคำสั่งที่ทำงานได้จะดูเหมือนไม่มีเสียง |
| เขียนข้อความคำสั่งและไบต์ Enter **แยกกัน** | newline จะอยู่ใน buffer เป็นอักขระตามตัวอักษรและ CLI จะตอบกลับ `unknown command` ซึ่งดูเหมือนว่าคำสั่งนั้นไม่มีอยู่ |

ดังนั้น `ssh host 'some-command'` จึงใช้งานไม่ได้: argument ถูกละเว้นและ
interactive prompt เริ่มต้นอยู่ดี ขับเคลื่อนมันในฐานะเทอร์มินัลหรือไม่ก็ไม่ต้องทำ
`scripts/sitecli_ssh_harvest.py` คือ reference implementation

<Aside type="caution" title="panic ที่อ่านว่า 'no such device or address' หมายความว่าการยืนยันตัวตน SUCCEEDED">
`vpmu` ส่งออกมา **หลังจาก** login เมื่อมันไม่พบเทอร์มินัลที่จะแนบ เมื่ออ่านว่าเป็น
crash มันดูเหมือนผลลัพธ์ที่เลวร้ายที่สุดที่เป็นไปได้ และในความเป็นจริงมันคือ
ข้อผิดพลาดสุดท้ายก่อนความสำเร็จ เพิ่ม `-tt` และเชื่อมต่ออีกครั้ง
</Aside>

<Aside type="caution" title="การแทนที่ CE จะเปลี่ยน host key ของมัน">
โหนดทดแทนแสดง host key ที่แตกต่างกันที่ที่อยู่เดียวกัน ดังนั้นการเชื่อมต่อครั้งถัดไป
จะเตือน `REMOTE HOST IDENTIFICATION HAS CHANGED` และปฏิเสธ ล้าง entry เก่า
สำหรับที่อยู่นั้นและเชื่อมต่อใหม่ เนื่องจากการให้สิทธิ์ SSH จะแทนที่ VM ทั้งหมด
คาดว่าสิ่งนี้จะเกิดขึ้นในการเชื่อมต่อครั้งแรกหลังจากนำมันมาใช้
</Aside>

ดังนั้นโหนดที่ไม่เคยออนไลน์มักจะบอกคุณแล้วว่าทำไมที่นี่ — ก่อนที่จะต้องใช้
[`chronyc-sources`](../../commands/network/chronyc-sources/) หรือ
[`dig`](../../commands/network/dig/) เลย

## การจัดหา keypair

<Steps>

1. สร้าง keypair หากคุณยังไม่มี ใช้ Ed25519 แทน RSA: สั้นกว่า
   และอุปกรณ์ `sshd` ยอมรับ

   ```bash
   ssh-keygen -t ed25519 -C "ce-operator" -f ~/.ssh/id_ed25519
   ```

2. ชี้การใช้งานไปที่ครึ่ง **public** root module อ่านไฟล์ครั้งเดียวและ
   ส่ง string ลงไปยังทุกโหนด:

   ```hcl
   # terraform/terraform.tfvars
   ssh_public_key_path = "~/.ssh/id_ed25519.pub"
   ```

   `ssh_public_key` รับ material แบบ inline แทน ซึ่งคือสิ่งที่ plan tests ใช้
   ครึ่ง private ไม่เคยออกจาก workstation ของคุณ

3. Apply อ่านคำเตือนที่ด้านบนของหน้านี้ก่อน — บนการใช้งานที่มีอยู่แล้ว สิ่งนี้
   จะแทนที่ CE VM

</Steps>

<Aside type="note" title="admin_ssh_key ของ VM เองเป็นสิ่งที่แตกต่าง">
`azurerm_linux_virtual_machine.admin_ssh_key` ใน `modules/ce-node` ให้สิทธิ์
Azure VM administrator ไม่ใช่บัญชี `admin` ของอุปกรณ์ มันไม่ให้สิทธิ์เข้าถึง
Site CLI และการที่มันถูกตั้งค่าไว้ไม่ใช่หลักฐานว่า CE SSH ถูกกำหนดค่าแล้ว
</Aside>

## สิ่งที่นี่ไม่ใช่

แต่ละอย่างต่อไปนี้ถูกทดสอบและตัดออกในขณะที่เส้นทางยังถูกเชื่อว่าเป็นไปไม่ได้
แต่ละอย่างมีความน่าเชื่อถือพอที่จะเสียเวลาหนึ่งวัน

| ไม่ใช่สาเหตุ | วิธีที่ตัดออก |
| --- | --- |
| credential ใช้ได้เฉพาะในเวลาสร้างเท่านั้น | `sshd` เริ่มต้นประมาณ 90 วินาทีในการบูตครั้งแรก ก่อนที่ site object จะมีอยู่ `admin_user_credentials` ยังมีอยู่ใน `ReplaceSpecType` และใช้งานได้ in-place |
| `block_all_services` | การปิดพอร์ต 22 บน management address เหมือนกันไม่ว่าจะบล็อก services หรือไม่ |
| trailing newline บน key | ทดสอบทั้งสองทาง ไม่มีการเปลี่ยนแปลง Cloud-init ยังคง strip มัน เพราะ literal block จะ render บรรทัดที่สองว่างเปล่า |
| CE software เวอร์ชันเก่าที่ถูก pin ไว้ | ทดสอบซ้ำบนสาม build รวมถึงหนึ่ง build ที่ใช้ OpenSSH 9.9 |
| `admin_password` ที่หายไป | การตั้งค่า `admin_password` พร้อมกับ `ssh_key` บน CE ที่สร้างใหม่ไม่มีการเปลี่ยนแปลง |

<Aside type="caution" title="สอง API field ที่ดูเหมือน discriminator แต่ไม่ใช่">
`gc_spec.admin_ssh_key` ว่างเปล่าหรือไม่มีอยู่บน **ไซต์ทั้ง 58 ใน `f5-sales-demo`** —
รวมถึงสองไซต์ที่ตั้งค่า `admin_user_credentials.ssh_key` การเปรียบเทียบมัน
ระหว่างไซต์ที่ทำงานได้และไม่ทำงานไม่บอกคุณอะไร เพราะมันอ่านว่าว่างเปล่าแม้กระทั่ง
สำหรับไซต์ที่ credential *ถูก* กำหนดค่าแล้ว

`registrations_by_site` ละเว้น field นั้นโดยสิ้นเชิงและส่งคืน `None` สำหรับมัน ซึ่งอ่านว่า
"ไม่ได้กำหนดค่า" แทนที่จะเป็น "ไม่ได้รายงาน"
</Aside>
