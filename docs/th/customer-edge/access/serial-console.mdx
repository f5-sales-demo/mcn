Azure Serial Console เชื่อมต่อกับพอร์ต serial จำลองของโหนดผ่านแพลตฟอร์ม Azure
ไม่ผ่าน control plane ของ F5 Distributed Cloud, data plane ของโหนด หรือเส้นทางเครือข่ายใดที่โหนดควบคุม — นั่นคือเหตุผลที่มันทำงานได้เมื่อทุกอย่างอื่นล้มเหลว

ใช้งานเมื่อ CE **ไม่เคยเริ่มต้นขึ้น**: การลงทะเบียนล้มเหลว ไซต์ไม่ปรากฏในผู้เช่า หรือโหนดทำงานแต่ไม่มีเส้นทางออก ในกรณีเหล่านั้น [debug API](../debug-api/) ไม่มีอุโมงค์สำหรับส่งผ่าน [SSH](../ssh/) ยังคงทำงานได้เมื่อการลงทะเบียนล้มเหลว แต่ต่อเมื่อคีย์ถูกเขียนไว้ตั้งแต่การบูตครั้งแรกและคุณสามารถเข้าถึงที่อยู่ภายในของโหนดจากภายใน VNet เท่านั้น — ซึ่งทั้งสองอย่างนี้ไม่เป็นความจริงสำหรับโหนดที่คุณพบเป็นครั้งแรก

## ข้อกำหนดเบื้องต้น: boot diagnostics

Azure กำหนดให้มี boot diagnostics บน VM ก่อนที่จะสามารถเชื่อมต่อ serial console ได้
สิ่งนี้เปิดใช้งานโดย `terraform/modules/ce-node`:

```hcl
boot_diagnostics {}
```

บล็อกว่างเปล่าเลือกพื้นที่จัดเก็บที่ Azure จัดการ ดังนั้นจึงไม่มีบัญชีพื้นที่จัดเก็บ diagnostics นโยบาย lifecycle หรือคีย์การเข้าถึงที่ต้องดูแล ยืนยันบนโหนด:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="การเปิดใช้งานไม่ย้อนหลัง">
Boot diagnostics บันทึก serial log **ขณะบูต** การเปิดใช้งานสำหรับ VM ที่กำลังทำงานอยู่แล้วจะไม่สร้าง log สำหรับการบูตที่เกิดขึ้นไปแล้ว ดังนั้น
`az vm boot-diagnostics get-boot-log` จะตอบว่า:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

นั่นเป็นสิ่งที่คาดหวัง ไม่ใช่ข้อผิดพลาด boot log จะมีอยู่หลังจากที่โหนดรีบูตครั้งถัดไป อย่างไรก็ตาม การเชื่อมต่อ console แบบสดทำงานได้ทันที — ไม่ขึ้นอยู่กับ log
</Aside>

## การตรวจสอบความพร้อมใช้งานโดยไม่ต้องใช้เทอร์มินัล

การเชื่อมต่อต้องการเซสชันแบบโต้ตอบ แต่การตรวจสอบว่า *จะ* เชื่อมต่อได้หรือไม่ใช้เพียงสอง API call ทั้งสองมีประโยชน์ในการตรวจสอบสุขภาพ

บริการต้องเปิดใช้งานสำหรับ subscription — ผู้ดูแลระบบสามารถปิดใช้งานได้ทั่วทั้ง tenant:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

จากนั้นขอการเชื่อมต่อไปยัง serial port ของโหนดเฉพาะ:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

`connectionString` ที่ขึ้นต้นด้วย `wss://` — ในการ deploy นี้คือ
`eastus.gateway.serialconsole.azure.com` — หมายความว่า console สามารถเชื่อมต่อได้ตอนนี้ ก่อนที่จะเปิดใช้งาน boot diagnostics การเรียกนี้ไม่มีอะไรให้เชื่อมต่อ

<Aside type="danger" title="สตริงการเชื่อมต่อนั้นคือ credential">
มันคือ bearer token อายุสั้นที่ฝังอยู่ใน URL อย่า log มัน อย่าวางลงในตั๋ว หรือ commit มัน แสดงเฉพาะ host เมื่อคุณต้องการแสดงว่าการเรียกทำงานสำเร็จ
</Aside>

## การเชื่อมต่อ

<Steps>

1. ติดตั้งส่วนขยายครั้งเดียว:

   ```bash
   az extension add --name serial-console
   ```

2. เชื่อมต่อ:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. คุณจะถูกนำไปยัง login prompt ของโหนดเอง ไม่ใช่ shell นี่คือ Site CLI และ
   ต้องการ credential ที่ตั้งไว้บนโหนด — รหัสผ่านผู้ดูแลระบบจากการ provisioning หรือ
   รหัสผ่านที่ตั้งผ่าน endpoint เปลี่ยนรหัสผ่าน Serial console พิสูจน์ว่า *ช่องทาง*
   ทำงาน ไม่ได้ข้ามการยืนยันตัวตน

</Steps>

บันทึกจาก `f5-xc-ce-vm-01` โดยตัดส่วนกลางออกซึ่ง systemd unit output ไม่ได้เพิ่มข้อมูลใด:

```text file=../../../_data/serial-console-boot.txt
```

สี่สิ่งในบันทึกนั้นควรสังเกต เพราะตอบคำถามที่ debug API ไม่สามารถตอบได้:

- **cloud-init เสร็จสมบูรณ์** — `Datasource DataSourceAzure` เสร็จสิ้นที่ 22.37 วินาที
  โหนดที่ไม่เคยลงทะเบียนมักล้มเหลวที่นี่ และนี่คือที่ที่คุณจะเห็น
- **ทั้งสอง container runtime เริ่มต้น** `Container Runtime Interface for OCI (CRI-O)`
  และ `Docker Application Container Engine` ต่างก็เป็น `[ OK ]` ซึ่งเป็นหลักฐานขณะบูตของพฤติกรรม dual-runtime ที่ทำให้ผู้คนแปลกใจใน
  [crictl](../../commands/system/crictl/) และ [docker](../../commands/system/docker/)
- **`VP Manager image load` และ `Argo Watch service`** — `vpm` และ Argo กำลังเริ่มต้น
- **prompt คือของโหนดเอง** ด้านหลัง audit banner ของมัน Serial console ให้ login prompt ไม่ใช่เซสชัน

<Aside type="caution" title="การเชื่อมต่อแบบโต้ตอบต้องการเทอร์มินัลจริง — แต่สามารถเขียนสคริปต์ได้">
`az serial-console connect` เปลี่ยนเทอร์มินัลเป็น raw mode ดังนั้นจึงไม่สามารถรันจาก pipeline หรือบริบทใดที่ไม่มี TTY ได้ มันล้มเหลวฝั่งไคลเอนต์ ก่อนติดต่อ Azure:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

traceback นั้นคือการจัดการเทอร์มินัล ไม่ใช่การหยุดทำงานของ serial console

อย่างไรก็ตาม การเชื่อมต่อเอง **สามารถ** ทำอัตโนมัติได้ — ขับเคลื่อน websocket โดยตรงแทน CLI บันทึกด้านบนถูกบันทึกด้วยวิธีนี้ โดยไม่มี TTY ดู
`scripts/serial_console_capture.py` ซึ่งเป็นวิธีที่คุณจะรวบรวมหลักฐานการบูตจากโหนดที่ล้มเหลวในการลงทะเบียนโดยไม่ต้องมีมนุษย์นั่งอยู่ที่เทอร์มินัล
</Aside>

<Aside type="caution" title="คาดว่าจะต้องลองใหม่: gateway ปฏิเสธประมาณทุกครั้งที่สอง">
เฟรมแรกของ gateway คือ challenge ไม่ใช่ output และไคลเอนต์ตอบสนองด้วย bearer token แม้ว่าจะทำถูกต้อง socket ก็มักจะปิดทันที:

```
[close] code=1011 reason=Connection not trusted
```

พฤติกรรมที่สังเกตได้: มันสำเร็จเป็นครั้งคราว และเมื่อใช้งานต่อเนื่องโหนดทุกตัวในกลุ่มทรัพยากรปฏิเสธ — รวมถึงโหนดที่ทำงานได้เมื่อไม่กี่นาทีก่อน
`scripts/serial_console_capture.py` ลองใหม่โดยค่าเริ่มต้นเพราะการลองใหม่มักได้ผล

**สาเหตุยังไม่ได้รับการยืนยัน** สิ่งที่ถูกตัดออก เพราะแต่ละอย่างเป็นการเดาที่น่าเชื่อซึ่งเสียเวลา:

| ไม่ใช่สิ่งนี้ | วิธียืนยัน |
| --- | --- |
| ARM/compute throttling | สิ่งนั้นส่งคืน HTTP `429` บน ARM call นี่คือ websocket close บน data channel แยกต่างหาก |
| TLS interception โดย proxy | `openssl s_client -connect <region>.gateway.serialconsole.azure.com:443 \| openssl x509 -noout -issuer` ผู้ออกใบรับรองที่เป็น `O=Microsoft Corporation` จริงตัดออก; ผู้ขาย proxy เป็นผู้ออกใบรับรองยืนยัน และการแก้ไขคือ allow-list `*.serialconsole.azure.com` |
| Boot diagnostics ถูกปิดใช้งาน | `az vm show -g <rg> -n <vm> --query diagnosticsProfile` รายงาน `enabled: true` |
| Token ไม่ตรงกันระหว่าง grant และ challenge | การใช้ token เดียวสำหรับทั้งสองคือแนวปฏิบัติที่ถูกต้อง แต่ไม่ป้องกันการปิด |

สิ่งที่ *ได้รับการบันทึก* เป็นพฤติกรรมของ Azure: **หนึ่ง serial console session ต่อ VM และคำขอที่สำเร็จครั้งที่สองจะขับไล่ครั้งแรกออก** ผู้ใช้ที่ถูกขับไล่จะถูกตัดการเชื่อมต่อแต่ไม่ได้ logout ดังนั้น shell session จึงยังคงอยู่ สองคนที่ debug โหนดเดียวจะแทนที่กันซ้ำๆ

สำหรับงานจำนวนมาก ให้ใช้ [debug API](../debug-api/) หรือ [SSH](../ssh/) แทน ซึ่งทั้งคู่ไม่มีข้อจำกัดเหล่านี้ โดยเฉพาะ SSH ไม่มีข้อจำกัดการวางและไม่มีข้อจำกัด single-session ดังนั้นจึงเป็นตัวเลือกที่ดีกว่าเมื่อโหนดสามารถเข้าถึงได้จากภายใน VNet
</Aside>

<Aside type="caution" title="การวางถูกจำกัดที่ 2,048 ตัวอักษร">
Azure จำกัดความยาวการวางของ serial console ที่ 2,048 ตัวอักษร เพื่อหลีกเลี่ยงการโอเวอร์โหลด serial port การส่งคำสั่งที่ยาว — หรือชุดคำสั่งในการเขียนครั้งเดียว — จะล้มเหลวในลักษณะที่อ่านเหมือนการค้างหรือการ throttle แทนที่จะเป็นข้อจำกัดความยาว

ส่งคำสั่งทีละคำสั่ง นี่คือข้อจำกัดจริงสำหรับการรวบรวมข้อมูลจำนวนมากผ่าน serial console และเป็นอีกเหตุผลหนึ่งที่ควรใช้ [debug API](../debug-api/) สำหรับงานนั้น
</Aside>

## สิ่งที่คุณสามารถเห็นที่นี่ซึ่ง API ไม่สามารถแสดงได้

- **cloud-init** กำลังทำงาน ล้มเหลว หรือไม่เคยเริ่มต้น — สาเหตุปกติของโหนดที่ไม่เคยลงทะเบียน
- **การพยายามลงทะเบียน** กับ `register.ves.volterra.io` รวมถึงข้อผิดพลาดการกำหนดค่าหรือ token ที่ tenant ปฏิเสธ
- **ข้อความ Kernel และการบูต** จากก่อนที่ agent ใดจะทำงาน
- โหนดเมื่อมัน **ไม่มีเส้นทางเครือข่ายที่ทำงานได้** ซึ่งทำให้ทุกเส้นทางอื่นล้มเหลว

สำหรับโหนดที่ *อยู่ใน* สถานะ `ONLINE` ให้ใช้ debug API แทน: มันเขียนสคริปต์ได้ ให้หลักฐานที่คุณสามารถรันซ้ำได้ และไม่ครอบครอง serial port เดียว
