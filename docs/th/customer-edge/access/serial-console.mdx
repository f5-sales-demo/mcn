Azure Serial Console เชื่อมต่อกับพอร์ตอนุกรมจำลองของโหนดผ่านแพลตฟอร์ม Azure
ไม่ผ่าน control plane ของ F5 Distributed Cloud, data plane ของโหนด หรือเส้นทางเครือข่ายใด ๆ ที่โหนดควบคุม — ซึ่งนั่นคือเหตุผลว่าทำไมมันจึงทำงานได้เมื่อวิธีอื่นทั้งหมดล้มเหลว

ใช้งานเมื่อ CE **ไม่เคยเริ่มทำงาน**: การลงทะเบียนล้มเหลว, ไซต์ไม่ปรากฏใน tenant, หรือโหนดทำงานอยู่แต่ไม่มีเส้นทางออก ในทุกกรณีเหล่านั้น [debug API](../debug-api/) ไม่มีอุโมงค์ให้ส่งผ่าน และ SSH ถูกปิดไว้บนโหนดตามที่จัดส่งมา

## ข้อกำหนดเบื้องต้น: boot diagnostics

Azure กำหนดให้เปิดใช้งาน boot diagnostics บน VM ก่อนที่จะแนบ serial console ได้
สิ่งนี้เปิดใช้งานโดย `terraform/modules/ce-node`:

```hcl
boot_diagnostics {}
```

บล็อกว่างเปล่าจะเลือกใช้ที่จัดเก็บที่ Azure จัดการ ดังนั้นจึงไม่มีบัญชีที่จัดเก็บ diagnostics, นโยบาย lifecycle หรือคีย์การเข้าถึงที่ต้องดูแล ยืนยันบนโหนด:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="การเปิดใช้งานไม่มีผลย้อนหลัง">
Boot diagnostics จะบันทึก serial log **ขณะบูต** การเปิดใช้งานสำหรับ VM ที่กำลังทำงานอยู่แล้วจะไม่สร้าง log สำหรับการบูตที่เกิดขึ้นไปแล้ว ดังนั้น
`az vm boot-diagnostics get-boot-log` จะตอบกลับว่า:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

นั่นเป็นสิ่งที่คาดไว้ ไม่ใช่ข้อผิดพลาด boot log จะมีอยู่หลังจากโหนดรีบูตครั้งต่อไป อย่างไรก็ตาม การแนบคอนโซลแบบสดจะทำงานได้ทันที — ไม่ขึ้นอยู่กับ log
</Aside>

## การตรวจสอบความพร้อมใช้งานโดยไม่ต้องใช้ terminal

การแนบต้องใช้เซสชันแบบโต้ตอบ แต่การตรวจสอบว่าจะสามารถแนบได้หรือไม่ใช้เพียงสอง API call เท่านั้น ทั้งสองมีประโยชน์ในการตรวจสอบสุขภาพระบบ

บริการต้องเปิดใช้งานสำหรับ subscription — ผู้ดูแลระบบสามารถปิดใช้งานได้ทั่วทั้ง tenant:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

จากนั้นขอการเชื่อมต่อไปยังพอร์ตอนุกรมของโหนดเฉพาะ:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

`connectionString` ที่ขึ้นต้นด้วย `wss://` — บน deployment นี้คือ
`eastus.gateway.serialconsole.azure.com` — หมายความว่าคอนโซลสามารถแนบได้ในขณะนี้ ก่อนที่จะเปิดใช้งาน boot diagnostics การเรียกนี้ไม่มีสิ่งใดให้แนบ

<Aside type="danger" title="connection string นั้นคือข้อมูลรับรองความถูกต้อง">
มันคือ bearer token อายุสั้นที่ฝังอยู่ใน URL อย่าบันทึก, วางในตั๋วสนับสนุน หรือ commit มัน แสดงเฉพาะ host เมื่อคุณกำลังสาธิตว่าการเรียกนั้นทำงาน
</Aside>

## การแนบ

<Steps>

1. ติดตั้ง extension ครั้งเดียว:

   ```bash
   az extension add --name serial-console
   ```

2. แนบ:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. คุณจะเข้าสู่ prompt การเข้าสู่ระบบของโหนด ไม่ใช่ shell นี่คือ Site CLI และต้องใช้ข้อมูลรับรองที่ตั้งค่าบนโหนด — รหัสผ่าน admin จากการจัดเตรียม หรือรหัสที่ตั้งค่าผ่าน endpoint เปลี่ยนรหัสผ่าน Serial console พิสูจน์ว่า *ช่องทาง* ทำงาน ไม่ได้ข้ามผ่านการยืนยันตัวตน

</Steps>

<Aside type="caution" title="ต้องใช้ terminal จริง">
`az serial-console connect` จะเปลี่ยน terminal เป็นโหมด raw ดังนั้นจึงไม่สามารถรันจากสคริปต์, pipeline หรือบริบทใด ๆ ที่ไม่มี TTY ได้ มันล้มเหลวฝั่งไคลเอนต์ก่อนที่จะติดต่อ Azure:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

traceback นั้นเป็นเรื่องของการจัดการ terminal ไม่ใช่การหยุดทำงานของ serial console — สอง API call ข้างต้นจะยังรายงานว่าคอนโซลพร้อมใช้งาน หากคุณต้องการสัญญาณที่ใช้กับระบบอัตโนมัติได้ ให้ใช้วิธีเหล่านั้นแทนการพยายามสร้างสคริปต์สำหรับการแนบ
</Aside>

## สิ่งที่คุณสามารถเห็นได้ที่นี่ซึ่ง API ไม่สามารถแสดงให้คุณเห็น

- **cloud-init** ที่กำลังทำงาน, ล้มเหลว หรือไม่เคยเริ่มต้น — สาเหตุปกติของโหนดที่ไม่เคยลงทะเบียน
- **ความพยายามลงทะเบียน** กับ `register.ves.volterra.io` รวมถึงข้อผิดพลาดในการกำหนดค่าหรือ token ที่ tenant ปฏิเสธ
- **ข้อความ Kernel และการบูต** จากก่อนที่ agent ใด ๆ จะทำงาน
- โหนดเมื่อมัน **ไม่มีเส้นทางเครือข่ายที่ใช้งานได้** ซึ่งทำให้ทุกเส้นทางอื่นล้มเหลว

สำหรับโหนดที่ `ONLINE` อยู่ ควรใช้ debug API: มันใช้กับสคริปต์ได้, สร้างหลักฐานที่คุณสามารถรันซ้ำได้ และไม่ครอบครองพอร์ตอนุกรมเพียงพอร์ตเดียว
