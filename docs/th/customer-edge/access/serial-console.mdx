Azure Serial Console เชื่อมต่อกับพอร์ตอนุกรมจำลองของโหนดผ่านแพลตฟอร์ม Azure
โดยไม่ผ่าน control plane ของ F5 Distributed Cloud, data plane ของโหนด
หรือเส้นทางเครือข่ายใด ๆ ที่โหนดควบคุมอยู่ — ซึ่งนั่นเองคือเหตุผลที่มันทำงานได้
เมื่อวิธีอื่นทั้งหมดใช้ไม่ได้

ใช้วิธีนี้เมื่อ CE **ไม่เคยขึ้นมาเลย**: การลงทะเบียนล้มเหลว, ไซต์ไม่ปรากฏ
ในเทแนนต์, หรือโหนดทำงานอยู่แต่ไม่มีเส้นทางออกไปข้างนอก ในทุกกรณีเหล่านี้
[debug API](../debug-api/) ไม่มีอุโมงค์ให้ส่งต่อผ่าน [SSH](../ssh/) ยังคงใช้ได้แม้
การลงทะเบียนล้มเหลว แต่เฉพาะเมื่อคีย์ของมันถูกเขียนไว้แล้วตั้งแต่การบูตครั้งแรก และคุณสามารถ
เข้าถึงที่อยู่ภายในของโหนดจากภายใน VNet ได้ — ซึ่งทั้งสองข้อนี้ไม่เป็นจริงสำหรับ
โหนดที่คุณเพิ่งพบเป็นครั้งแรก

ลองใช้ [Site Console](../site-console/) ก่อนวิธีนี้ หากโหนดยังมีเส้นทางเครือข่ายที่ใช้งานได้ *บ้าง*:
มันก็ใช้ได้แม้การลงทะเบียนล้มเหลว, ไม่ต้องใช้คีย์, และไม่ไล่ผู้ที่กำลัง
ดูโหนดอยู่ออกไป คอนโซลอนุกรมคือสิ่งที่เหลืออยู่เมื่อเส้นทางเครือข่ายคือสิ่งที่
เสียหาย

## ข้อกำหนดเบื้องต้น: boot diagnostics

Azure กำหนดให้เปิด boot diagnostics บน VM ก่อนจึงจะยอมเชื่อมต่อคอนโซลอนุกรมได้
สิ่งนี้ถูกเปิดใช้งานโดย `terraform/modules/ce-node`:

```hcl
boot_diagnostics {}
```

บล็อกว่างเปล่าจะเลือกใช้ที่เก็บข้อมูลที่จัดการโดย Azure ดังนั้นจึงไม่มีบัญชี
ที่เก็บข้อมูล diagnostics, นโยบายวงจรชีวิต หรือคีย์การเข้าถึงให้ต้องดูแล ยืนยันบนโหนดได้ด้วย:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="การเปิดใช้งานไม่มีผลย้อนหลัง">
Boot diagnostics จะเก็บบันทึกอนุกรม **ขณะบูต** การเปิดใช้งานกับ VM ที่
กำลังทำงานอยู่แล้วจะไม่สร้างบันทึกสำหรับการบูตที่เกิดขึ้นไปแล้ว ดังนั้น
`az vm boot-diagnostics get-boot-log` จะตอบว่า:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

นั่นเป็นสิ่งที่คาดไว้ ไม่ใช่ข้อผิดพลาด บันทึกการบูตจะมีอยู่หลังจากโหนดรีบูตครั้งถัดไป อย่างไรก็ตาม
การเชื่อมต่อคอนโซลแบบสดใช้งานได้ทันที — เพราะไม่ได้ขึ้นอยู่กับบันทึกดังกล่าว
</Aside>

## การตรวจสอบความพร้อมใช้งานโดยไม่ต้องใช้เทอร์มินัล

การเชื่อมต่อจำเป็นต้องมีเซสชันแบบโต้ตอบ แต่การตรวจว่า *จะ* เชื่อมต่อได้หรือไม่นั้นใช้เพียงสอง
การเรียก API ทั้งสองมีประโยชน์ในการตรวจสุขภาพระบบ

บริการต้องถูกเปิดใช้งานสำหรับซับสคริปชัน — ผู้ดูแลระบบสามารถปิดใช้งาน
ทั้งเทแนนต์ได้:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

จากนั้นขอการเชื่อมต่อไปยังพอร์ตอนุกรมของโหนดที่ระบุ:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

`connectionString` ที่ขึ้นต้นด้วย `wss://` — ในการติดตั้งนี้คือ
`eastus.gateway.serialconsole.azure.com` — หมายความว่าคอนโซลสามารถเชื่อมต่อได้
ในขณะนี้ ก่อนที่จะเปิดใช้งาน boot diagnostics การเรียกนี้จะไม่มีอะไรให้เชื่อมต่อ

<Aside type="danger" title="สตริงการเชื่อมต่อนั้นคือข้อมูลรับรอง">
มันคือ bearer token อายุสั้นที่ฝังอยู่ใน URL อย่าบันทึกลงล็อก อย่าวางลงใน
ทิกเก็ต และอย่า commit เก็บไว้ ให้พิมพ์เฉพาะชื่อโฮสต์เมื่อคุณต้องการสาธิตว่าการเรียก
ทำงานได้
</Aside>

## การเชื่อมต่อ

<Steps>

1. ติดตั้งส่วนขยายเพียงครั้งเดียว:

   ```bash
   az extension add --name serial-console
   ```

2. เชื่อมต่อ:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. คุณจะมาถึงหน้าจอ login ของโหนดเอง ไม่ใช่เชลล์ โดยอยู่หลังแบนเนอร์การตรวจสอบ
   ของแอปพลายแอนซ์ คอนโซลอนุกรมพิสูจน์ว่า *ช่องทาง* ใช้งานได้ แต่ไม่ได้ข้ามการยืนยันตัวตน

   <Aside type="caution" title="ยังไม่ได้ตรวจสอบว่าการล็อกอินผ่านอนุกรมรับข้อมูลรับรองแบบใด">
   ยังไม่มีใครล็อกอินผ่านคอนโซลอนุกรมสำเร็จบนการติดตั้งนี้ ดังนั้นหน้านี้
   จึงไม่ระบุว่าต้องพิมพ์อะไร `admin` คือบัญชีของแอปพลายแอนซ์ที่มีเชลล์เป็น Site CLI และ
   บัญชีเดียวกันนี้ยืนยันตัวตนผ่าน
   [Site Console](../site-console/) ด้วยรหัสผ่าน — แต่ยังไม่ได้แสดงให้เห็นว่ารหัสผ่านใช้งานได้
   กับการล็อกอินผ่านคอนโซลอนุกรม และ `sshd` ใช้เฉพาะคีย์สำหรับ `admin` ดังนั้นทั้งสอง
   จึงไม่ใช่เส้นทางข้อมูลรับรองเดียวกันอย่างชัดเจน
   </Aside>

</Steps>

บันทึกจาก `f5-xc-ce-vm-01` โดยตัดส่วนกลางออกเนื่องจากผลลัพธ์ของ systemd unit
ไม่ได้เพิ่มข้อมูลใด:

```text file=../../../_data/serial-console-boot.txt
```

มีสี่สิ่งในบันทึกนั้นที่ควรสังเกต เพราะมันตอบคำถามที่
debug API ตอบไม่ได้:

- **cloud-init ทำงานเสร็จสมบูรณ์** — `Datasource DataSourceAzure` เสร็จที่วินาทีที่ 22.37
  โหนดที่ไม่เคยลงทะเบียนได้มักล้มเหลวตรงนี้ และนี่คือจุดที่คุณจะเห็นมัน
- **รันไทม์คอนเทนเนอร์ทั้งสองตัวเริ่มทำงาน** `Container Runtime Interface for OCI (CRI-O)`
  และ `Docker Application Container Engine` ต่างเป็น `[ OK ]` ซึ่งเป็น
  หลักฐานขณะบูตของพฤติกรรมรันไทม์คู่ที่ทำให้หลายคนแปลกใจใน
  [crictl](../../commands/system/crictl/) และ [docker](../../commands/system/docker/)
- **`VP Manager image load` และ `Argo Watch service`** — `vpm` และ Argo กำลังเริ่มทำงาน
- **พรอมต์นั้นเป็นของโหนดเอง** โดยอยู่หลังแบนเนอร์การตรวจสอบ คอนโซลอนุกรมพาคุณไปถึง
  หน้าจอ login เท่านั้น ไม่ใช่เซสชัน

<Aside type="caution" title="การเชื่อมต่อแบบโต้ตอบต้องใช้เทอร์มินัลจริง — แต่สามารถเขียนสคริปต์ได้">
`az serial-console connect` จะตั้งเทอร์มินัลเป็นโหมด raw จึงไม่สามารถทำงานจาก
ไปป์ไลน์หรือบริบทใด ๆ ที่ไม่มี TTY ได้ มันจะล้มเหลวที่ฝั่งไคลเอนต์ก่อนติดต่อ Azure:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

traceback นั้นเป็นเรื่องการจัดการเทอร์มินัล ไม่ใช่เหตุขัดข้องของคอนโซลอนุกรม

อย่างไรก็ตาม ตัวการเชื่อมต่อเอง **สามารถ** ทำอัตโนมัติได้ — โดยขับเคลื่อน websocket โดยตรงแทน
การใช้ CLI บันทึกด้านบนถูกเก็บมาด้วยวิธีนั้น โดยไม่มี TTY ดู
`scripts/serial_console_capture.py` ซึ่งเป็นวิธีที่คุณจะใช้เก็บหลักฐานการบูตจาก
โหนดที่ลงทะเบียนไม่สำเร็จ โดยไม่ต้องมีคนนั่งอยู่หน้าเทอร์มินัล
</Aside>

<Aside type="caution" title="เตรียมใจลองใหม่: เกตเวย์ปฏิเสธราวหนึ่งในสองครั้งของความพยายาม">
เฟรมแรกของเกตเวย์คือ challenge ไม่ใช่ผลลัพธ์ และไคลเอนต์จะตอบกลับด้วย
bearer token แม้จะทำถูกต้องแล้ว ซ็อกเก็ตก็มักปิดตัวลงทันที:

```
[close] code=1011 reason=Connection not trusted
```

พฤติกรรมที่สังเกตได้: มันสำเร็จเป็นครั้งคราว และเมื่อใช้งานต่อเนื่อง ทุกโหนดใน
รีซอร์สกรุ๊ปจะปฏิเสธ — รวมถึงโหนดที่เพิ่งใช้งานได้เมื่อไม่กี่นาทีก่อน
`scripts/serial_console_capture.py` จะลองใหม่โดยค่าเริ่มต้น เพราะการลองใหม่มักได้ผล

**ยังไม่ทราบสาเหตุที่แน่ชัด** สิ่งที่ตัดออกไปแล้ว เพราะแต่ละข้อเป็นการเดา
ที่ดูสมเหตุสมผลแต่เสียเวลา:

| ไม่ใช่สาเหตุนี้ | วิธียืนยัน |
| --- | --- |
| การจำกัดอัตราของ ARM/compute | กรณีนั้นจะคืนค่า HTTP `429` ในการเรียก ARM แต่นี่เป็นการปิด websocket บนช่องข้อมูลแยกต่างหาก |
| การดักจับ TLS โดยพร็อกซี | `openssl s_client -connect <region>.gateway.serialconsole.azure.com:443 \| openssl x509 -noout -issuer` ผู้ออกใบรับรองที่เป็น `O=Microsoft Corporation` ของแท้จะตัดความเป็นไปได้นี้ออก หากผู้ออกเป็นผู้ให้บริการพร็อกซีก็ยืนยันได้ และวิธีแก้คือ allow-list `*.serialconsole.azure.com` |
| boot diagnostics ถูกปิดใช้งาน | `az vm show -g <rg> -n <vm> --query diagnosticsProfile` รายงาน `enabled: true` |
| โทเค็นไม่ตรงกันระหว่าง grant กับ challenge | การใช้โทเค็นเดียวกันทั้งสองที่เป็นแนวปฏิบัติที่ถูกต้อง แต่ก็ไม่ได้ป้องกันการปิดการเชื่อมต่อ |

สิ่งที่ *เป็น* พฤติกรรมของ Azure ตามที่ระบุในเอกสาร: **หนึ่งเซสชันคอนโซลอนุกรมต่อหนึ่ง VM และคำขอที่สอง
ซึ่งสำเร็จจะไล่คำขอแรกออก** ผู้ที่ถูกไล่ออกจะถูกตัดการเชื่อมต่อแต่ไม่ได้ถูกล็อกเอาต์
ดังนั้นเซสชันเชลล์จึงยังคงอยู่ สองคนที่ดีบักโหนดเดียวกันจะไล่กันไปมาซ้ำ ๆ

สำหรับงานจำนวนมาก ควรใช้ [debug API](../debug-api/) หรือ [SSH](../ssh/) ซึ่งทั้งคู่ไม่มี
ข้อจำกัดเหล่านี้ โดยเฉพาะ SSH ไม่มีข้อจำกัดการวางข้อความและไม่มีข้อจำกัดเซสชันเดียว
จึงเป็นตัวเลือกที่ดีกว่าเมื่อใดก็ตามที่เข้าถึงโหนดได้จากภายใน VNet
</Aside>

<Aside type="caution" title="การวางข้อความถูกจำกัดที่ 2,048 อักขระ">
Azure จำกัดความยาวของการวางข้อความในคอนโซลอนุกรมไว้ที่ 2,048 อักขระ เพื่อไม่ให้
พอร์ตอนุกรมทำงานหนักเกินไป การส่งคำสั่งยาว ๆ — หรือชุดคำสั่งในการเขียนครั้งเดียว — จะล้มเหลวในลักษณะ
ที่ดูเหมือนค้างหรือถูกจำกัดอัตรา มากกว่าจะดูเหมือนข้อจำกัดด้านความยาว

ให้ส่งคำสั่งทีละคำสั่ง นี่เป็นข้อจำกัดจริงสำหรับการเก็บข้อมูลจำนวนมากผ่านคอนโซล
อนุกรม และเป็นอีกเหตุผลที่ควรเลือกใช้ [debug API](../debug-api/) สำหรับงานนั้น
</Aside>

## สิ่งที่คุณเห็นได้ที่นี่แต่ API แสดงให้ไม่ได้

- **cloud-init** ที่กำลังทำงาน ล้มเหลว หรือไม่เคยเริ่มเลย — สาเหตุปกติของโหนด
  ที่ไม่เคยลงทะเบียนได้
- **ความพยายามลงทะเบียน** ไปยัง `register.ves.volterra.io` รวมถึง
  ข้อผิดพลาดการกำหนดค่าหรือโทเค็นที่เทแนนต์ปฏิเสธ
- **ข้อความจากเคอร์เนลและการบูต** ตั้งแต่ก่อนที่เอเจนต์ใด ๆ จะทำงาน
- ตัวโหนดเองเมื่อ **ไม่มีเส้นทางเครือข่ายที่ใช้งานได้เลย** ซึ่งทำให้เส้นทางอื่นทั้งหมดใช้ไม่ได้

สำหรับโหนดที่ *อยู่ในสถานะ* `ONLINE` ควรเลือกใช้ debug API: มันเขียนสคริปต์ได้ ให้
หลักฐานที่คุณสามารถรันซ้ำได้ และไม่ไปยึดครองพอร์ตอนุกรมที่มีเพียงพอร์ตเดียว
