Azure Serial Console เชื่อมต่อกับพอร์ตอนุกรมเสมือนของโน้ดผ่านแพลตฟอร์ม Azure
โดยไม่ผ่าน control plane ของ F5 Distributed Cloud, data plane ของโน้ด
หรือเส้นทางเครือข่ายใด ๆ ที่โน้ดควบคุมอยู่ — ซึ่งนั่นคือเหตุผลที่มันใช้งานได้
เมื่อวิธีอื่นใช้ไม่ได้เลย

ให้ใช้วิธีนี้เมื่อ CE **ไม่เคยขึ้นมาเลย**: การลงทะเบียนล้มเหลว, ไซต์ไม่ปรากฏ
ในเทนแนนต์, หรือโน้ดทำงานอยู่แต่ไม่มีเส้นทางออกไปข้างนอก ในทุกกรณีเหล่านี้
[debug API](../debug-api/) ไม่มีทันเนลให้ส่งต่อ และ
[SSH ไม่สามารถยืนยันตัวตนได้](../ssh/) บนบิลด์นี้

## ข้อกำหนดเบื้องต้น: boot diagnostics

Azure กำหนดให้เปิด boot diagnostics บน VM ก่อนจึงจะเชื่อมต่อคอนโซลอนุกรมได้
ซึ่งถูกเปิดใช้งานโดย `terraform/modules/ce-node`:

```hcl
boot_diagnostics {}
```

บล็อกว่างจะเลือกที่จัดเก็บที่ Azure จัดการให้ ดังนั้นจึงไม่มีบัญชีที่จัดเก็บสำหรับ
diagnostics, นโยบายวงจรชีวิต หรือคีย์การเข้าถึงที่ต้องดูแล ตรวจสอบบนโน้ดได้ด้วย:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="การเปิดใช้งานไม่มีผลย้อนหลัง">
Boot diagnostics จะเก็บบันทึกอนุกรม **ณ ตอนบูต** การเปิดใช้งานสำหรับ VM ที่
กำลังทำงานอยู่แล้วจะไม่สร้างบันทึกของการบูตที่เกิดขึ้นไปแล้ว ดังนั้น
`az vm boot-diagnostics get-boot-log` จะตอบว่า:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

นั่นเป็นสิ่งที่คาดไว้ ไม่ใช่ความผิดพลาด บันทึกการบูตจะมีอยู่หลังจากโน้ดรีบูตครั้งถัดไป
อย่างไรก็ตาม การเชื่อมต่อคอนโซลแบบสดใช้งานได้ทันที — เพราะไม่ได้ขึ้นอยู่กับบันทึกนั้น
</Aside>

## การตรวจสอบความพร้อมใช้งานโดยไม่ต้องมีเทอร์มินัล

การเชื่อมต่อต้องใช้เซสชันแบบอินเทอร์แอกทีฟ แต่การตรวจว่า *จะ* เชื่อมต่อได้หรือไม่นั้น
ใช้เพียงสองการเรียก API ทั้งสองมีประโยชน์ในการตรวจสุขภาพระบบ

บริการนี้ต้องถูกเปิดใช้งานสำหรับซับสคริปชัน — ผู้ดูแลระบบสามารถปิดใช้งานทั้ง
เทนแนนต์ได้:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

จากนั้นขอการเชื่อมต่อไปยังพอร์ตอนุกรมของโน้ดที่ต้องการ:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

`connectionString` ที่เริ่มต้นด้วย `wss://` — ในการติดตั้งนี้คือ
`eastus.gateway.serialconsole.azure.com` — หมายความว่าคอนโซลสามารถเชื่อมต่อได้
ในตอนนี้ ก่อนที่จะเปิดใช้งาน boot diagnostics การเรียกนี้ไม่มีอะไรให้เชื่อมต่อ

<Aside type="danger" title="สตริงการเชื่อมต่อนั้นคือข้อมูลรับรอง">
มันคือ bearer token อายุสั้นที่ฝังอยู่ใน URL อย่าบันทึกเป็นล็อก อย่าวางลงใน
ตั๋วงาน และอย่าคอมมิตลงในโค้ด ให้พิมพ์เฉพาะชื่อโฮสต์เมื่อคุณต้องการสาธิตว่า
การเรียกนั้นทำงานได้
</Aside>

## การเชื่อมต่อ

<Steps>

1. ติดตั้งส่วนขยายหนึ่งครั้ง:

   ```bash
   az extension add --name serial-console
   ```

2. เชื่อมต่อ:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. คุณจะมาถึงพร้อมต์เข้าสู่ระบบของโน้ดเอง ไม่ใช่เชลล์ นี่คือ Site CLI และ
   ต้องมีข้อมูลรับรองที่ตั้งไว้บนโน้ด — รหัสผ่านผู้ดูแลระบบจากการจัดเตรียม หรือ
   รหัสที่ตั้งผ่านเอนด์พอยต์เปลี่ยนรหัสผ่าน คอนโซลอนุกรมพิสูจน์ว่า *ช่องทาง*
   ใช้งานได้ แต่ไม่ได้ข้ามการยืนยันตัวตน

</Steps>

บันทึกจาก `f5-xc-ce-vm-01` ซึ่งตัดส่วนกลางออกในจุดที่เอาต์พุตของ systemd unit
ไม่ได้เพิ่มข้อมูลอะไร:

```text file=../../../_data/serial-console-boot.txt
```

มีสี่สิ่งในบันทึกนั้นที่ควรสังเกต เพราะตอบคำถามที่ debug API ตอบไม่ได้:

- **cloud-init เสร็จสมบูรณ์** — `Datasource DataSourceAzure` เสร็จที่ 22.37 วินาที
  โน้ดที่ไม่เคยลงทะเบียนสำเร็จมักล้มเหลวที่จุดนี้ และนี่คือจุดที่คุณจะเห็นมัน
- **รันไทม์คอนเทนเนอร์ทั้งสองเริ่มทำงาน** `Container Runtime Interface for OCI (CRI-O)`
  และ `Docker Application Container Engine` แต่ละตัวขึ้น `[ OK ]` ซึ่งเป็นหลักฐาน
  ณ เวลาบูตของพฤติกรรมรันไทม์คู่ที่ทำให้หลายคนประหลาดใจใน
  [crictl](../../commands/system/crictl/) และ [docker](../../commands/system/docker/)
- **`VP Manager image load` และ `Argo Watch service`** — `vpm` และ Argo กำลังเริ่มทำงาน
- **พร้อมต์นั้นเป็นของโน้ดเอง** อยู่หลังแบนเนอร์ตรวจสอบของมัน คอนโซลอนุกรมให้คุณ
  ได้เพียงพร้อมต์เข้าสู่ระบบ ไม่ใช่เซสชัน

<Aside type="caution" title="การเชื่อมต่อแบบอินเทอร์แอกทีฟต้องใช้เทอร์มินัลจริง — แต่สามารถเขียนสคริปต์ได้">
`az serial-console connect` จะปรับเทอร์มินัลเข้าสู่โหมด raw จึงไม่สามารถรันจาก
ไปป์ไลน์หรือบริบทใด ๆ ที่ไม่มี TTY ได้ มันจะล้มเหลวที่ฝั่งไคลเอนต์ก่อนจะติดต่อ Azure:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

Traceback นั้นเป็นเรื่องการจัดการเทอร์มินัล ไม่ใช่คอนโซลอนุกรมล่ม

อย่างไรก็ตาม ตัวการเชื่อมต่อเอง **สามารถ** ทำอัตโนมัติได้ — ให้ควบคุมเว็บซ็อกเก็ต
โดยตรงแทนการใช้ CLI บันทึกด้านบนถูกเก็บมาด้วยวิธีนั้น โดยไม่มี TTY ดูที่
`scripts/serial_console_capture.py` ซึ่งเป็นวิธีที่คุณจะใช้เก็บหลักฐานการบูตจาก
โน้ดที่ลงทะเบียนไม่สำเร็จ โดยไม่ต้องมีคนนั่งอยู่หน้าเทอร์มินัล
</Aside>

<Aside type="caution" title="เตรียมใจลองใหม่: เกตเวย์ปฏิเสธประมาณครั้งเว้นครั้ง">
เฟรมแรกของเกตเวย์เป็น challenge ไม่ใช่เอาต์พุต และไคลเอนต์ตอบด้วย bearer token
แม้ทำถูกต้องแล้ว ซ็อกเก็ตก็มักปิดลงทันที:

```
[close] code=1011 reason=Connection not trusted
```

พฤติกรรมที่สังเกตได้: มันสำเร็จเป็นครั้งคราว และเมื่อใช้งานต่อเนื่อง ทุกโน้ดใน
รีซอร์สกรุ๊ปจะปฏิเสธ — รวมถึงโน้ดที่ใช้งานได้เมื่อไม่กี่นาทีก่อน
`scripts/serial_console_capture.py` จะลองใหม่โดยค่าเริ่มต้น เพราะการลองใหม่มักได้ผล

**ยังไม่สามารถระบุสาเหตุได้** สิ่งที่ตัดออกไปแล้ว เพราะแต่ละข้อเป็นการเดาที่
ฟังดูมีเหตุผลแต่เสียเวลา:

| ไม่ใช่สาเหตุนี้ | วิธียืนยัน |
| --- | --- |
| การจำกัดอัตรา (throttling) ของ ARM/compute | กรณีนั้นจะคืน HTTP `429` ในการเรียก ARM แต่นี่เป็นการปิดเว็บซ็อกเก็ตบนช่องข้อมูลแยกต่างหาก |
| การดักจับ TLS โดยพร็อกซี | `openssl s_client -connect <region>.gateway.serialconsole.azure.com:443 \| openssl x509 -noout -issuer` หากผู้ออกใบรับรองเป็น `O=Microsoft Corporation` จริงก็ตัดกรณีนี้ออกได้ หากผู้ออกเป็นผู้ให้บริการพร็อกซีก็ยืนยันได้ และการแก้ไขคือใส่ `*.serialconsole.azure.com` ในรายการอนุญาต |
| boot diagnostics ถูกปิด | `az vm show -g <rg> -n <vm> --query diagnosticsProfile` รายงานว่า `enabled: true` |
| โทเค็นไม่ตรงกันระหว่าง grant และ challenge | การใช้โทเค็นเดียวกันทั้งสองจุดเป็นแนวปฏิบัติที่ถูกต้อง แต่ไม่ได้ป้องกันการปิดการเชื่อมต่อ |

สิ่งที่ *เป็น* พฤติกรรมที่ Azure ระบุไว้ในเอกสาร: **หนึ่งเซสชันคอนโซลอนุกรมต่อหนึ่ง VM
และคำขอที่สำเร็จรายถัดไปจะขับเซสชันแรกออก** ผู้ใช้ที่ถูกขับออกจะถูกตัดการเชื่อมต่อ
แต่ไม่ได้ถูกออกจากระบบ ดังนั้นเซสชันเชลล์ยังคงอยู่ สองคนที่ดีบักโน้ดเดียวกันจะ
เตะกันออกไปมาซ้ำ ๆ

สำหรับงานจำนวนมาก ควรเลือกใช้ [debug API](../debug-api/) ซึ่งไม่มีข้อจำกัดเหล่านี้เลย
[SSH ไม่ใช่ทางเลือก](../ssh/) — เพราะไม่สามารถเปิดใช้งานได้บนบิลด์นี้
</Aside>

<Aside type="caution" title="การวางข้อความจำกัดที่ 2,048 อักขระ">
Azure จำกัดความยาวการวางข้อความในคอนโซลอนุกรมไว้ที่ 2,048 อักขระ เพื่อไม่ให้
พอร์ตอนุกรมทำงานหนักเกินไป การส่งคำสั่งที่ยาว — หรือส่งคำสั่งเป็นชุดในการเขียนครั้งเดียว
— จะล้มเหลวในลักษณะที่ดูเหมือนค้างหรือถูกจำกัดอัตรา มากกว่าจะดูเหมือนข้อจำกัดด้านความยาว

ให้ส่งคำสั่งทีละคำสั่ง นี่เป็นข้อจำกัดจริงของการเก็บข้อมูลจำนวนมากผ่านคอนโซลอนุกรม
และเป็นอีกเหตุผลที่ควรเลือกใช้ [debug API](../debug-api/) สำหรับงานนั้น
</Aside>

## สิ่งที่คุณเห็นได้ที่นี่แต่ API แสดงให้ไม่ได้

- **cloud-init** ที่กำลังทำงาน ล้มเหลว หรือไม่เคยเริ่มเลย — สาเหตุปกติของโน้ด
  ที่ไม่เคยลงทะเบียนสำเร็จ
- **ความพยายามลงทะเบียน** ไปยัง `register.ves.volterra.io` รวมถึงข้อผิดพลาด
  ด้านการกำหนดค่าหรือโทเค็นที่เทนแนนต์ปฏิเสธ
- **ข้อความจากเคอร์เนลและการบูต** จากช่วงก่อนที่เอเจนต์ใด ๆ จะทำงาน
- ตัวโน้ดในตอนที่ **ไม่มีเส้นทางเครือข่ายที่ใช้งานได้** ซึ่งทำให้ทุกเส้นทางอื่นใช้ไม่ได้

สำหรับโน้ดที่ *อยู่ในสถานะ* `ONLINE` ควรเลือกใช้ debug API: มันเขียนสคริปต์ได้
สร้างหลักฐานที่คุณรันซ้ำได้ และไม่ยึดครองพอร์ตอนุกรมเพียงพอร์ตเดียวที่มี
