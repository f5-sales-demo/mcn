API `vpm/debug` เรียกใช้คำสั่ง Site CLI บนโหนดที่ลงทะเบียนไว้และส่งคืนผลลัพธ์ของคำสั่งนั้น
ทุกอย่างด้านล่างนี้ได้รับการยืนยันกับโหนดจริง โดยไม่มีส่วนใดที่ถูกเผยแพร่ไว้ในเอกสารต้นทาง

## แคตตาล็อกคำสั่งอธิบายตัวเองได้

สอบถามโหนดว่ารองรับคำสั่งใดบ้างโดยส่ง POST ไปยัง `exec-user` โดย **ละ** คีย์ `command` ไว้:

```bash
curl -sS -X POST \
  -H "Authorization: APIToken $XCSH_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"namespace":"system","site":"<site>","node":"<node>"}' \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/<node>/exec-user" \
  | jq -r .output | jq .
```

การตอบกลับเป็นออบเจ็กต์ JSON ที่ใช้ชื่อคำสั่งเป็นคีย์:

```json
{
  "crictl-inspect": ["System Troubleshooting", "ExecUser", " container-id"],
  "diagnosis":      ["System Troubleshooting", "ExecUser", "no argument needed", "GLOBAL"],
  "ip-link-set":    ["Network Troubleshooting", "Exec", " (<device>||<group>) (up||down)"]
}
```

แต่ละรายการมีรูปแบบ `[category, tier, exampleArgument?, scope?]` และฟิลด์เหล่านี้ไม่ใช่เพียงคำอธิบาย
แต่เป็นตัวกำหนดว่าคำสั่งนั้นต้องถูกเรียกอย่างไร

<Aside type="caution" title="ละคีย์ไว้ อย่าส่งค่าที่ไม่ถูกต้อง">
การค้นหารายการทำงานได้ด้วยการละ `command` ออกไป หากส่งค่าที่ไม่รู้จักแทน จะได้รับ
ข้อผิดพลาด ไม่ใช่แคตตาล็อก:

```json
{"code":3,"details":[],"message":"exec command failed: command not supported"}
```

ข้อความนั้นยังเป็นสิ่งที่คุณจะได้รับเมื่อส่งคำสั่ง *ที่มีอยู่จริง* ไปยังปลายทางที่ผิด
จึงตีความผิดได้ง่ายว่า "คำสั่งนี้ไม่มีอยู่"
</Aside>

## การรับส่งข้อมูลสามแบบ เลือกตามรายการในแคตตาล็อก

| เงื่อนไข | เมธอดและพาธ | เนื้อหา | ส่งคืน |
| --- | --- | --- | --- |
| `scope` เป็น `GLOBAL` | `GET .../vpm/debug/global/<cmd>` | ไม่มี | JSON |
| `tier` เป็น `ExecUser` | `POST .../vpm/debug/<node>/exec-user` | อาร์เรย์ `command` | ข้อความ |
| `tier` เป็น `Exec` | `POST .../vpm/debug/<node>/exec` | อาร์เรย์ `command` | ข้อความ |

### `ExecUser` — ระดับอ่านอย่างเดียว <Badge text="31 commands" variant="note" />

กรณีที่พบบ่อยที่สุด ส่งคำสั่งและอาร์กิวเมนต์เป็นอาร์เรย์ โดยให้ชื่อคำสั่งอยู่ลำดับแรก:

```bash
curl -sS -X POST \
  -H "Authorization: APIToken $XCSH_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"namespace":"system","site":"<site>","node":"<node>","command":["crictl-ps"]}' \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/<node>/exec-user"
```

```json
{ "return_code": 0, "output": "CONTAINER    IMAGE    CREATED    STATE ..." }
```

อาร์กิวเมนต์ต้องเป็นสมาชิกแยกกันของอาร์เรย์ ไม่ใช่สตริงเดียว:

```json
{ "command": ["journalctl", "-u", "vpm", "-n", "200"] }
```

### `GLOBAL` — ครอบคลุมทั้งไซต์ และใช้การรับส่งข้อมูลที่ต่างออกไปโดยสิ้นเชิง <Badge text="2 commands" variant="tip" />

มีเพียง `health` และ `diagnosis` เท่านั้น ทั้งสองเป็นคำขอ `GET` ไปยังพาธ `global`
ไม่รับอาร์กิวเมนต์ และส่งคืน JSON ที่มีโครงสร้างแทนที่จะเป็นข้อความแบบเทอร์มินัล

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/global/health" | jq .
```

<Aside type="danger" title="คำสั่ง GLOBAL ไม่สามารถเข้าถึงได้ผ่าน exec-user">
นี่คือกับดักที่ทำให้เสียเวลามากที่สุด การส่ง `health` หรือ `diagnosis` ไปยัง
`exec-user` จะได้รับ `command not supported` ซึ่งอ่านแล้วดูเหมือนว่าคำสั่งนั้น
ไม่มีอยู่บนโหนด ทั้งที่ความจริงแล้วมีอยู่ เพียงแต่คุณใช้การรับส่งข้อมูลผิดแบบ

```bash
# Wrong. Returns: exec command failed: command not supported
-d '{"namespace":"system","site":"…","node":"…","command":["health"]}'   # POST exec-user

# Right.
GET .../vpm/debug/global/health
```

</Aside>

### `Exec` — ระดับสิทธิ์พิเศษ <Badge text="1 command on this build" variant="danger" />

เป็นปลายทางแยกต่างหาก และระดับสิทธิ์ถูกบังคับใช้จริงไม่ใช่เพียงคำแนะนำ: `exec` จะปฏิเสธ
คำสั่งระดับ `ExecUser` ด้วยข้อความ `command not supported` เช่นเดียวกัน สมาชิกทุกตัวในระดับนี้
ล้วนเปลี่ยนแปลงสถานะของโหนดหรืออ่านตัวบ่งชี้สถานะ

บนบิลด์ที่เทนแนนต์นี้ใช้งานอยู่ ระดับนี้มีเพียง `ip-link-set` เท่านั้น บิลด์ใหม่กว่านั้น
เพิ่ม `systemctl-restart-NetworkManager`, `systemctl-restart-crio`,
`systemctl-restart-kubelet`, `systemctl-start-crio-prune` และคำสั่ง
`marker-exists-*` อีกสามคำสั่ง

<Aside type="danger" title="ไม่มีสิ่งใดในที่นี้เรียกใช้คำสั่งระดับ Exec">
ชุดเครื่องมือเก็บข้อมูลปฏิเสธระดับนี้ และอ่านระดับสิทธิ์จากแคตตาล็อกจริง
แทนที่จะใช้รายการที่ฝังไว้ตายตัว — ดังนั้นบิลด์ในอนาคตที่เลื่อนคำสั่งขึ้นเป็น `Exec`
จะได้รับการเคารพโดยไม่ต้องมีใครแก้ไขโค้ด ให้เรียกใช้คำสั่งเหล่านี้อย่างตั้งใจเท่านั้น
บนโหนดที่คุณยอมรับได้ว่าจะถูกรบกวน
</Aside>

## การค้นหาชื่อไซต์และชื่อโหนด

ชื่อโหนดคือชื่อ Azure VM และ `list-service` เป็นวิธีง่าย ๆ ในการยืนยันชื่อนั้น
พร้อมกับบริการที่ทำงานอยู่บนโหนด:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/global/list-service" \
  | jq -r '[.service[].node] | unique'
```

```json
["", "f5-xc-ce-vm-01"]
```

บริการบางรายการรายงานชื่อโหนดเป็นค่าว่าง ดังนั้นสตริงว่างในรายการนั้นเป็นผลข้างเคียง
ของการตอบกลับ ไม่ใช่โหนดที่สอง นอกจากนี้ `list-service` ก็ไม่ได้อยู่ในแคตตาล็อก 34 คำสั่ง:
มันเป็นปลายทางแบบ `global` ที่แคตตาล็อกไม่ได้ประกาศไว้ ซึ่งเป็นเหตุผลที่มันถูกบันทึกไว้ที่นี่
แทนที่จะอยู่ใน[เอกสารอ้างอิงคำสั่ง](../../commands/)

## การทำซ้ำการเก็บข้อมูลของที่เก็บโค้ดนี้

ทุกหน้าคำสั่งฝังผลลัพธ์ที่เก็บโดย `scripts/capture-sitecli.sh` ซึ่งนำกฎทั้งสามข้อข้างต้นมาใช้งาน

<Steps>

1. ชี้ไปยังเทนแนนต์ สคริปต์จะอ่าน `XCSH_API_URL` และ `XCSH_API_TOKEN` หรือย้อนกลับไปใช้
   คอนเท็กซ์ `xcsh` ที่ใช้งานอยู่

2. รีเฟรชแคตตาล็อกและยืนยันว่าโหนดไม่ได้เปลี่ยนแปลงไปโดยที่เอกสารไม่รับรู้:

   ```bash
   bash scripts/capture-sitecli.sh --check
   ```

   คำสั่งนี้เปรียบเทียบเฉพาะแคตตาล็อกที่คอมมิตไว้และบิลด์ซอฟต์แวร์เท่านั้น โดยจะรายงาน
   การเปลี่ยนแปลงของบิลด์แยกจากคำสั่งที่ถูกเพิ่มหรือถูกลบออก

3. เก็บข้อมูลใหม่เมื่อคุณต้องการหลักฐานที่เป็นปัจจุบัน:

   ```bash
   bash scripts/capture-sitecli.sh
   ```

</Steps>

<Aside type="note" title="ข้อมูลที่เก็บเป็นหลักฐาน ไม่ใช่สิ่งประดิษฐ์ที่ทำซ้ำได้">
ตัวนับ ระยะเวลาทำงาน และอายุคอนเทนเนอร์เปลี่ยนแปลงไปในแต่ละรอบการรัน ดังนั้นการเก็บข้อมูลใหม่
จะสร้าง diff เสมอ แคตตาล็อกคือข้อตกลงที่เสถียร และเหมือนกันทุกไบต์ในทุกรอบการรัน
เมื่อโหนดไม่ได้เปลี่ยนแปลง นั่นคือสิ่งที่ `--check` เปรียบเทียบ ผลลัพธ์ที่ยาวจะถูกตัดทอน
และลงท้ายด้วยตัวบ่งชี้ที่ชัดเจน เพื่อไม่ให้ตารางที่ถูกตัดทอนถูกแสดงราวกับว่าสมบูรณ์
</Aside>

<Aside type="danger" title="การเก็บข้อมูลจากโหนดของลูกค้า: ตรวจสอบโปรไฟล์การปกปิดข้อมูล">
ผลลัพธ์ของคำสั่งมีข้อมูลระบุตัวตนของโครงสร้างพื้นฐาน — การกำหนดที่อยู่ภายใน, ที่อยู่ MAC,
หมายเลข AS, ชื่อโฮสต์ — และสำหรับลูกค้าแล้ว สิ่งเหล่านี้คือข้อมูลที่ระบุตัวตนขององค์กร

ตัวกรองการล้างข้อมูลจึงใช้โปรไฟล์ **strict** เป็นค่าเริ่มต้น ซึ่งลบข้อมูลเหล่านั้นทั้งหมด
ที่เก็บโค้ดนี้ประกาศ `lab` ไว้ใน `sitecli/capture-manifest.json` ซึ่งคงรายละเอียดเหล่านั้นไว้
และมันถูกต้องเฉพาะในที่นี้เท่านั้น เพราะข้อมูลที่เก็บมาจากโครงสร้างพื้นฐานสาธิตที่ F5 เป็นเจ้าของ

**อย่านำการตั้งค่านั้นไปใช้กับการเก็บข้อมูลของลูกค้า** โทเค็น, คีย์ส่วนตัว, ตัวระบุเทนแนนต์,
UUID ของออบเจ็กต์, ที่อยู่อีเมล และพาธไดเรกทอรีบ้าน จะถูกลบออกภายใต้ทั้งสองโปรไฟล์

มีข้อจำกัดหนึ่งที่ควรทราบ: ตารางเพื่อนบ้าน BGP พิมพ์หมายเลข AS เป็นคอลัมน์เปล่า ๆ
โดยไม่มีป้ายกำกับให้ยึดเป็นรูปแบบการจับคู่ ดังนั้น ASN จึงถูกจับคู่ตามค่ากับช่วงส่วนตัว
ASN แบบ **สาธารณะ** ในนั้นจะรอดพ้นจากโปรไฟล์ strict และจำเป็นต้องตรวจทานผลลัพธ์
`show-ip-bgp*` ด้วยตนเองก่อนที่คุณจะเผยแพร่
</Aside>
