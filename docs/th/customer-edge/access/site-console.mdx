Customer Edge ทุกตัวให้บริการ F5's Site Console บน `https://<sli-ip>:65500` สำหรับการติดตั้งใช้งานนี้ มักเป็นเส้นทางที่ควรลองเป็นอันดับแรก

ต้องการสิ่งจากคุณน้อยที่สุด: ไม่ต้องแจกจ่าย SSH key ไม่ต้องดูแล jump host ไม่ต้องมี public IP บน node และไม่ต้องแทน VM เพื่อเปิดใช้งาน ผู้ที่สามารถเชื่อมต่อได้กลายเป็น**การตัดสินใจด้าน Azure RBAC** และไม่จำเป็นต้องให้ site ลงทะเบียนก่อน — บันทึกด้านล่างนี้ถูกบันทึกขณะที่ทั้งสาม site รายงาน `site_state: FAILED`

ข้อจำกัดคือ Site Console จะตอบรับเฉพาะบนที่อยู่ภายใน (SLI) ของ node เท่านั้น ซึ่งเข้าถึงได้จากภายใน VNet เท่านั้น Azure Bastion ปิดช่องว่างนั้นโดยไม่ต้องวางสิ่งอื่นใดบนเครือข่าย

<Aside type="note" title="สิ่งที่ได้รับการยืนยันที่นี่ และสิ่งที่ไม่ได้รับการยืนยัน">
คำสั่งทุกคำสั่งและผลลัพธ์ทุกรายการในหน้านี้ถูกรันกับ `f5-xc-ce-vm-01` ในการติดตั้งใช้งานนี้ และถูกทำซ้ำตามคำต่อคำ รวมถึงความล้มเหลวด้วย

สิ่งเดียวที่ไม่ได้ทดสอบคือ**การลงชื่อเข้าใช้** ขั้นตอนหยุดที่หน้าต่างป้อนข้อมูลรับรอง ดังนั้นไม่มีสิ่งใดด้านล่างอธิบายว่าคอนโซลมีหน้าตาอย่างไรเมื่อคุณเข้าไปแล้ว
</Aside>

## ก่อนเริ่มต้น

<Steps>

1. ลงชื่อเข้าใช้ Azure และเพิ่ม Bastion extension การทำ Tunneling เป็นฟีเจอร์ native-client และ extension นี้ไม่ได้ติดตั้งมาให้โดยค่าเริ่มต้น

   ```bash
   az login
   az extension add --name bastion
   ```

2. ถือ **Reader** บน CE virtual machine, network interface ของมัน และ Bastion host

3. ยืนยันว่า Bastion ถูก deploy และมีความสามารถเพียงพอ SKU ระดับ Basic ไม่รองรับทั้ง tunneling และการเชื่อมต่อผ่าน IP ดังนั้น `Standard` และ `True` ที่นี่ต่างมีความสำคัญ

   ```bash
   az network bastion list -g rg-mcn-ce-ha-rmordasiewicz \
     --query "[].{name:name, sku:sku.name, tunneling:enableTunneling}" -o table
   ```

   ```text
   Name               Sku       Tunneling
   -----------------  --------  -----------
   ce-ha-lab-bastion  Standard  True
   ```

</Steps>

## เปิด tunnel

รับค่าจาก `terraform output` แทนที่จะพิมพ์เอง — resource id ไม่ใช่สิ่งที่ควรประกอบขึ้นด้วยมือ

<Steps>

1. อ่านชื่อ Bastion host, resource group และ VM resource id ของ CE เป้าหมาย

   ```bash
   cd terraform
   BASTION=$(terraform output -raw bastion_name)
   RG=$(terraform output -raw resource_group_name)
   VM_ID=$(terraform output -json ce_vm_ids | jq -r '.eastus01')
   ```

   ```text
   ce-ha-lab-bastion
   rg-mcn-ce-ha-rmordasiewicz
   /subscriptions/…/providers/Microsoft.Compute/virtualMachines/f5-xc-ce-vm-01
   ```

   <Aside type="caution" title="แผนที่ถูกจัดคีย์ด้วย site ไม่ใช่ชื่อ VM">
   คีย์ของ `ce_vm_ids` คือ `eastus01`, `eastus02`, `eastus03` — **ไม่ใช่** ชื่อ VM ตัวกรองอย่าง `jq -r '."f5-xc-ce-vm-01"'` จะคืนค่า `null` และ tunnel จะล้มเหลวเนื่องจาก resource id ว่างเปล่า แสดงรายการหากไม่แน่ใจ:

   ```bash
   terraform output -json ce_vm_ids | jq -r 'keys | join(", ")'
   ```

   ```text
   eastus01, eastus02, eastus03
   ```
   </Aside>

2. เริ่ม tunnel มันจะคงพอร์ตไว้จนกว่าจะหยุด ดังนั้นให้รันในพื้นหลังหรือใช้ terminal ที่สอง

   ```bash
   az network bastion tunnel \
     --name "$BASTION" \
     --resource-group "$RG" \
     --target-resource-id "$VM_ID" \
     --resource-port 65500 \
     --port 65500 &
   ```

   ```text
   WARNING: Opening tunnel on port: 65500
   WARNING: Tunnel is ready, connect on port 65500
   WARNING: Ctrl + C to close
   ```

   ทั้งสามบรรทัดมีคำนำหน้าว่า `WARNING:` นั่นคือ Azure CLI เขียนความคืบหน้าไปยัง stderr ไม่ใช่ปัญหา รอให้ถึง `Tunnel is ready` ก่อนเชื่อมต่อ

3. ยืนยันว่า listener เป็น local บน loopback:

   ```bash
   lsof -nP -iTCP:65500 -sTCP:LISTEN
   ```

   ```text
   COMMAND   PID  USER  FD  TYPE  DEVICE  SIZE/OFF  NODE  NAME
   Python  41648  you   7u  IPv4  …            0t0   TCP  127.0.0.1:65500 (LISTEN)
   ```

4. เปิดคอนโซล tunnel ทำให้เป็น local ดังนั้นที่อยู่คือ `localhost` — ไม่ใช่ที่อยู่ของ node

   ```bash
   open https://localhost:65500/          # macOS
   xdg-open https://localhost:65500/      # Linux
   ```

5. หยุด tunnel เมื่อเสร็จสิ้น — `Ctrl-C` หรือ `kill %1` หากรันในพื้นหลัง การปล่อยทิ้งไว้จะครอบครอง local port 65500 และ Bastion session

</Steps>

## สิ่งที่คุณจะเห็น

**กล่องโต้ตอบสำหรับข้อมูลรับรอง ไม่ใช่หน้าเข้าสู่ระบบ** คอนโซลใช้การยืนยันตัวตน HTTP Basic ดังนั้นเบราว์เซอร์จะแสดงหน้าต่างป้อนชื่อผู้ใช้และรหัสผ่านของตัวเอง ไม่มีแบบฟอร์มให้ดู:

```bash
curl -skI https://localhost:65500/
```

```text
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Basic realm="Volterra Site Console"
Content-Length: 0
```

`401` พร้อม realm นั้นคือคอนโซลทำงานได้อย่างถูกต้อง นั่นคือสิ่งที่คำขอที่ไม่ได้รับการยืนยันตัวตนควรได้รับ

**คำเตือนเกี่ยวกับใบรับรอง สำหรับสามเหตุผลพร้อมกัน** การตรวจสอบใบรับรองโดยตรง:

```bash
openssl s_client -connect localhost:65500 -servername localhost </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
```

```text
subject=C=US, ST=California, L=Santa Clara, O=Volterra, OU=Volterra Edge Services, CN=site-local.volterra.io
issuer=C=US, ST=California, L=Santa Clara, O=Volterra, OU=Volterra Edge Services, CN=site-local.volterra.io
notBefore=Oct 25 04:51:31 2024 GMT
notAfter=Oct 25 04:51:31 2025 GMT
```

Subject เท่ากับ issuer ดังนั้นมันเป็น self-signed ชื่อคือ `site-local.volterra.io` ขณะที่คุณเชื่อมต่อกับ `localhost` ดังนั้นจะไม่ตรงกัน และในเวอร์ชั่นที่การติดตั้งใช้งานนี้รันอยู่ **ใบรับรองหมดอายุเมื่อวันที่ 25 ตุลาคม 2025** — appliance จัดส่งมาพร้อมกับมัน และไม่มีสิ่งใดใน repository นี้ที่ต่ออายุมัน

คาดว่าจะเห็นคำเตือนของเบราว์เซอร์ที่ชัดเจน และคาดว่าจะเห็นทุกครั้ง บรรทัด subject ด้านบนคือส่วนที่มีประโยชน์: เป็นวิธีที่คุณยืนยันว่าคุณเข้าถึง appliance แทนที่จะเป็นสิ่งอื่นที่รับฟังบน local port 65500

## ข้อมูลรับรองของ admin

ลงชื่อเข้าใช้ในชื่อ `admin` **เอกสารนี้ไม่เผยแพร่รหัสผ่าน และไม่ควรทำเช่นนั้น**

Customer Edge ที่ออกมาใหม่จากโรงงานจะมาพร้อมกับค่าเริ่มต้นที่ F5 เผยแพร่ และ F5 กำหนดให้เปลี่ยนแปลง ให้ถือว่าการเปลี่ยนแปลงนั้นเป็นส่วนหนึ่งของการ deploy node ไม่ใช่การเสริมความปลอดภัยในภายหลัง สองเหตุผลที่สำคัญกว่าที่อาจดูเหมือน:

- เอกสารนี้เป็นสาธารณะ การพิมพ์รหัสผ่านคอนโซลปัจจุบันของ fleet จะเปลี่ยน "ถือ Reader บน Bastion" ให้กลายเป็นการเข้าถึง appliance เต็มรูปแบบสำหรับทุกคนที่อ่านหน้านี้
- รหัสผ่านที่เผยแพร่ในเอกสารจะผิดทันทีที่มีคนหมุนเวียนมัน และผิดในแบบที่ทำให้เข้าใจผิดมากที่สุด — ผู้อ่านสรุปว่าการเข้าถึงของพวกเขามีปัญหา แทนที่จะเป็นว่าหน้านั้นล้าสมัย

รับรหัสผ่านจากที่ที่ทีมของคุณเก็บ operational secrets ไว้ หากคำตอบคือ "ยังคงเป็นค่าเริ่มต้นจากโรงงาน" ให้เปลี่ยนก่อนทำสิ่งอื่นใด

<Aside type="caution" title="การตั้งรหัสผ่านจาก Terraform ยังไม่ได้รับการยืนยัน">
`admin_user_credentials.admin_password` บน site object ดูเหมือนจะเป็นวิธีเชิง declarative ในการตั้งค่านี้ **ยังไม่ได้รับการยืนยัน**ว่าจะเข้าถึง Site Console บน build นี้ ดังนั้นอย่าสันนิษฐานว่าทำได้

อย่าอ่าน[หน้า SSH](../ssh/)เป็นหลักฐานอย่างใดอย่างหนึ่งด้วย การค้นพบว่า `admin_password` "ไม่เปลี่ยนแปลงอะไร" นั้นวัดจากการยืนยันตัวตน SSH ซึ่ง `vpm` ข้ามสำหรับผู้ใช้ `admin` ทั้งหมด นั่นไม่ได้บอกอะไรเกี่ยวกับคอนโซล
</Aside>

## เหตุใด tunnel ต้องกำหนดเป้าหมายที่ resource id

`--target-resource-id` เป็นสิ่งจำเป็น การกำหนดเป้าหมายที่ที่อยู่ของ node แทนจะถูกปฏิเสธ:

```bash
az network bastion tunnel --name "$BASTION" -g "$RG" \
  --target-ip-address 10.0.3.5 --resource-port 65500 --port 65501
```

```text
ERROR: Custom ports are not allowed. Allowed ports for Tunnel with IP connect is 22, 3389.
```

เหตุผล**ไม่ใช่**ว่าการเชื่อมต่อผ่าน IP ถูกปิดใช้งาน — บน Bastion นี้ `ip_connect_enabled` เป็น `true` Microsoft ไม่รองรับ custom ports ผ่านการเชื่อมต่อ native-client แบบ IP โดยไม่คำนึงถึงการตั้งค่านั้น ([Azure docs](https://learn.microsoft.com/azure/bastion/connect-ip-address)) และ 65500 เป็น custom port การตรวจสอบการกำหนดค่า Bastion ที่นี่ไม่มีประโยชน์ ให้ใช้ resource id

## เมื่อไม่ทำงาน

| อาการ | สาเหตุ | วิธีแก้ไข |
| --- | --- | --- |
| `ERROR: Custom ports are not allowed. Allowed ports for Tunnel with IP connect is 22, 3389.` | ใช้ `--target-ip-address` | ใช้ `--target-resource-id` |
| `ERROR: Defined port is currently unavailable` | มี tunnel อื่นครอบครอง local port นั้นอยู่ | หยุด tunnel อื่น หรือส่ง `--port` ที่แตกต่าง โดย `--resource-port` ยังคงเป็น 65500 |
| Tunnel เริ่มต้นแต่ resource id ว่างเปล่า | ตัวกรอง `jq` ใช้ชื่อ VM แทน site key | ใช้คีย์ `eastus01`/`02`/`03` |
| `401 Unauthorized`, realm `Volterra Site Console` | ไม่ใช่ข้อผิดพลาด — คำขอที่ไม่ได้รับการยืนยันตัวตน | ป้อนข้อมูลรับรองของ `admin` |
| เบราว์เซอร์ปฏิเสธใบรับรอง | Self-signed, ชื่อไม่ตรง และหมดอายุตั้งแต่ ต.ค. 2025 | เป็นสิ่งที่คาดไว้ ยืนยันว่า subject คือ `CN=site-local.volterra.io` และดำเนินการต่อ |

<Aside type="note" title="ความล้มเหลวด้านการให้สิทธิ์ไม่ได้รับการทดสอบซ้ำ">
RBAC ที่ไม่เพียงพอเป็นอีกวิธีที่ชัดเจนที่สิ่งนี้จะล้มเหลว แต่การทดสอบซ้ำจะต้องลบ role assignments ออกจาก deployment ที่ใช้ร่วมกัน ดังนั้นจึงไม่ได้บันทึกไว้ที่นี่พร้อม error ตามคำต่อคำ หาก tunnel ล้มเหลวเมื่อเริ่มต้นพร้อม authorization error ให้ตรวจสอบ Reader บนทั้งสามของ VM, NIC ของมัน และ Bastion host
</Aside>
