รันสิ่งเหล่านี้ก่อนที่คุณจะนำเสนอ การตรวจสอบแต่ละขั้นจะจำกัดขอบเขตว่าความผิดพลาดอยู่ที่ใด ดังนั้นเมื่อเกิดความล้มเหลว
คุณจะได้ข้อมูลบางอย่าง ไม่ใช่เพียงรู้ว่ามีอะไรผิดพลาด

ทุกคำสั่งจะอ่านสิ่งที่ต้องการจากการปรับใช้ ตั้งค่าเหล่านี้เพียงครั้งเดียวแล้วส่วนที่เหลือจะตามมา:

```bash
cd terraform
RG=$(terraform output -raw resource_group_name)
RS=$(terraform output -raw route_server_name)
CLIENT=$(terraform output -raw client_vm_name)
DOMAIN=$(terraform output -raw lb_domain)
VIP=$(terraform output -raw vip)
NIC=$(terraform output -raw client_nic_name)
```

## การตรวจสอบสี่ขั้น ตามลำดับนี้

<Steps>

1. **ทุกไซต์อยู่ในสถานะ `ONLINE`** ไม่มีสิ่งใดในขั้นถัดไปที่จะเป็นจริงได้หากข้อนี้ไม่เป็นจริง

   ```bash
   for s in $(terraform output -json xc_site_names | jq -r '.[]'); do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   สังเกตเมื่อ 2026-07-28, CE สามตัว:

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **ทุก peering เรียนรู้การประกาศ VIP ของ CE นั้น** สอบถามแต่ละ peering
   แยกกัน — ดูกับดักข้อแรกด้านล่าง เพราะนี่คือจุดที่การสาธิตมักดูเหมือน
   เสียแต่จริงๆ ไม่ได้เสีย

   ```bash
   for k in $(terraform output -json xc_site_names | jq -r 'keys[]'); do
     echo "--- ${k}-bgp"
     az network routeserver peering list-learned-routes \
       --name "${k}-bgp" --routeserver "$RS" -g "$RG" \
       --query "RouteServiceRole_IN_0[?network=='${VIP}/32'].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   สังเกตเมื่อ 2026-07-28:

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp
   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp
   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   สาม peering, สาม next hop ที่ต่างกัน, หนึ่ง prefix นั่นคือด้านการประกาศของ
   ECMP ที่พิสูจน์แล้ว

3. **เส้นทางที่มีผลของไคลเอนต์บรรจุทุก next hop** นี่คือ ECMP ตัวจริง ตามที่
   VNet ได้โปรแกรมไว้ — ไม่ใช่สิ่งที่ CE อ้าง แต่เป็นสิ่งที่ Azure ทำกับมัน

   ```bash
   az network nic show-effective-route-table -g "$RG" -n "$NIC" \
     --query "value[?addressPrefix[0]=='${VIP}/32'].{prefix:addressPrefix[0],nh:nextHopIpAddress,type:nextHopType,state:state}" \
     -o json
   ```

   สังเกตเมื่อ 2026-07-28:

   ```json
   [
     {
       "nh": ["10.0.1.5", "10.0.1.6", "10.0.1.4"],
       "prefix": "10.250.0.10/32",
       "state": "Active",
       "type": "VirtualNetworkGateway"
     }
   ]
   ```

   `state: Active` พร้อมกับหนึ่งรายการต่อ CE ใน `nh` คือสิ่งที่ต้องตรวจสอบ **ลำดับไม่มี
   ความสำคัญและไม่คงที่** — Azure ส่งคืนลำดับต่างกันในแต่ละครั้งที่เรียก ดังนั้นให้นับ
   จำนวนแทนที่จะเปรียบเทียบกับการรันครั้งก่อน หากมี next hop เพียงหนึ่งรายการในที่ที่คุณคาดว่าจะมีสามรายการ หมายความว่ามี
   CE หยุดประกาศ และขั้นตอนที่ 2 จะระบุว่าเป็นตัวใด

4. **VIP ให้บริการทราฟฟิก** จาก VM ไคลเอนต์ และ **พร้อมส่วนหัว `Host`** — ดู
   กับดักข้อที่สอง สุ่มตัวอย่างคำขอให้มากพอที่จะเห็นปัญหา: เพียงไม่กี่สิบคำขอจะอ่านได้เป็น 100 % แม้
   อยู่ภายในช่วงเวลา convergence ที่อธิบายไว้ด้านล่าง

   ```bash
   az vm run-command invoke -g "$RG" -n "$CLIENT" \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts "ok=0; fail=0
                for i in \$(seq 1 60); do
                  c=\$(curl -s -o /dev/null -m 5 -w '%{http_code}' \
                        -H 'Host: ${DOMAIN}' http://${VIP}/)
                  [ \"\$c\" = 200 ] && ok=\$((ok+1)) || fail=\$((fail+1))
                done
                echo \"OK=\$ok FAIL=\$fail\""
   ```

   สังเกตเมื่อ 2026-07-28:

   ```text
   VIP with Host header: OK=60 FAIL=0
   bare IP (no Host): 404
   ```

</Steps>

## กับดัก: peering หนึ่งรายการแสดงเส้นทางเดียว และนั่นถูกต้อง

`list-learned-routes` มีขอบเขตจำกัดอยู่ที่ peering ที่คุณระบุชื่อ มันรายงานสิ่งที่ peer **นั้น**
ประกาศ ไม่ใช่ตารางทั้งหมดของ Route Server

ดังนั้นการสอบถาม peering เพียงรายการเดียวจะคืนค่า VIP `/32` เพียงรายการเดียวผ่าน next hop เดียว และมัน
ล่อใจให้อ่านว่า "มี CE เพียงตัวเดียวที่ประกาศ — ตัวอื่นล่ม" ไม่มีสิ่งใดล่ม
การประกาศของตัวอื่นมองเห็นได้บน peering ของตนเอง ซึ่งเป็นสิ่งที่ขั้นตอนที่ 2 วนลูป
ผ่าน

การยืนยัน ECMP จากการสอบถาม peering เพียงรายการเดียวเป็นไปไม่ได้ ให้วนลูปทุก peering หรือ
อ่านตารางเส้นทางที่มีผลของไคลเอนต์ ซึ่งแสดงผลลัพธ์ที่รวมกันแล้วในการเรียกครั้งเดียว

## กับดัก: คำขอด้วย IP เปล่าคืนค่า 404

ตัวกระจายโหลดจับคู่ตาม `Host` VIP ไม่ใช่ virtual server ที่ให้บริการอะไรก็ได้แก่
ใครก็ตามที่เชื่อมต่อมายังที่อยู่นั้น

ทั้งสองรายการนี้มาจากการรันเดียวกันบนการปรับใช้ที่สมบูรณ์ดี:

```text
curl -H "Host: $DOMAIN" http://$VIP/   ->  200   (60 of 60)
curl                     http://$VIP/   ->  404
```

**404 จาก IP เปล่าคือหลักฐานว่าเส้นทางทำงานได้** — คำขอไปถึง CE, พร็อกซีของ CE
ตอบกลับ และปฏิเสธเพราะไม่มีโดเมนที่กำหนดค่าไว้ตรงกัน การอ่านว่าเป็นเหตุขัดข้อง
จะทำให้คุณไปมองหาที่ BGP ซึ่งคุณจะไม่พบสิ่งใดผิดปกติ

เช่นเดียวกันในระหว่างการสาธิต: หากคุณพิมพ์ที่อยู่ลงในเบราว์เซอร์แทนที่จะแปลง
โดเมนไปยังที่อยู่นั้น คุณจะได้ 404

## VIP ทิ้งคำขอในช่วงสามในสี่ชั่วโมงแรก แล้วก็หยุด

บนสแต็กที่สร้างใหม่ VIP จะสูญเสียคำขอเพียงเล็กน้อยในช่วงประมาณ
45 นาทีแรกหลังจาก CE เข้าสู่สถานะ `ONLINE` และหลังจากนั้นจะให้บริการได้สะอาด วัดจาก 1,470
คำขอจาก VM ไคลเอนต์ ทั้งหมดพร้อมส่วนหัว `Host`:

| ช่วงเวลา | คำขอ | ความล้มเหลว | อัตรา |
| --- | --- | --- | --- |
| ~45 นาทีแรกหลังจาก ECMP เริ่มทำงาน | 570 | 12 | **2.11 %** |
| 23 นาทีถัดมา | 900 | **0** | **0.00 %** |

ความล้มเหลวทุกครั้งเป็น `curl: (28)` — การหมดเวลาโดยได้รับศูนย์ไบต์ — ไม่ใช่สถานะข้อผิดพลาด
HTTP ครั้งสุดท้ายเกิดขึ้นประมาณ 43 นาทีหลังจาก ECMP เริ่มทำงาน จาก 900 คำขอที่สะอาด
มี 400 คำขอที่รันด้วยการหมดเวลา 30 วินาที และทุกคำขอเสร็จสิ้นภายในเวลาไม่ถึง 2 วินาที ดังนั้นไม่มีสิ่งใด
ถูกซ่อนไว้ด้วยการหมดเวลาที่สั้นเกินไป

**ต้นทางไม่ใช่สาเหตุ** ชุดควบคุมที่ยิงตรงไปยังต้นทาง
(`terraform output -raw origin_ip` โดยข้าม VIP) ทำได้สะอาด 120 จาก 120 *พร้อมกันกับ*
ชุดคำขอ VIP ที่ล้มเหลว ความผิดพลาดอยู่ที่ใดที่หนึ่งในเส้นทาง VIP, ECMP หรือ CE

สองสิ่งที่ตั้งใจไม่เรียกว่าเป็น:

- **ไม่ใช่ข้อบกพร่องในสภาวะคงตัว** มันหายไปอย่างสมบูรณ์และคงอยู่เช่นนั้น การสาธิตที่
  เปิดใช้มาแล้วหนึ่งชั่วโมงจะไม่มีปัญหานี้ — 60 จาก 60 ในการตรวจสอบขั้นที่ 4 ข้างต้น บนสแต็ก
  ที่เปิดใช้มาแล้วหลายชั่วโมง
- **ไม่สามารถระบุว่าเป็นเพราะ CE ตัวใดตัวหนึ่ง** ไม่มีสิ่งใดในโทโพโลยีนี้ที่ให้ตัวรับฟัง
  HTTP แยกต่อโหนด ดังนั้นจึงไม่มีวิธีผูกคำขอที่ถูกทิ้งกับโหนดที่ทิ้งมัน
  อินเทอร์เฟซภายนอกของ CE ไม่มีตัวรับฟัง HTTP เลย — มีเพียง VIP `/32` เท่านั้นที่ตอบสนอง

ปัญหานี้เกิดซ้ำได้บนการสร้างใหม่ที่สะอาดในเทนแนนต์อื่น ดังนั้นมันเป็นไปตามโทโพโลยีมากกว่า
ตามสภาพแวดล้อม

<Aside type="caution" title="อย่าสุ่มตัวอย่าง 40 คำขอแล้วสรุปว่าปกติดี">
ชุดคำขอ 40 ถึง 50 รายการจะอ่านได้เป็น 100 % ในเกือบทุกครั้งแม้อยู่ภายในช่วงที่ล้มเหลว นั่นคือ
สาเหตุที่ปัญหานี้ถูกอธิบายผิดในตอนแรกว่าเป็นความผิดพลาดอัตราต่ำที่เกิดต่อเนื่อง และต่อมาว่าไม่มีความผิดพลาด
เลย ให้สุ่มตัวอย่าง 100 รายการขึ้นไป โดยแบ่งเป็นชุดที่แยกห่างกันตามเวลา
</Aside>

## กับดักในการวัดอีกสองข้อ

ทั้งสองข้อให้คำตอบที่ผิดอย่างมั่นใจในสภาพแวดล้อมนี้ และไม่มีข้อใดที่เห็นได้ชัด

- **ตรวจสอบจากภายใน VNet ไม่ใช่จากเวิร์กสเตชันของคุณ** พร็อกซีขององค์กรสามารถทำ
  TCP handshake ให้สมบูรณ์ด้วยตัวมันเองบนพอร์ตทั่วไป ดังนั้นการตรวจจากเวิร์กสเตชันจะรายงานว่าพอร์ต **เปิด**
  ทั้งที่จริงแล้วปิดอยู่ พอร์ต 80 และ 443 อ่านได้เป็นเปิดบนที่อยู่สาธารณะของ CE จาก
  เวิร์กสเตชัน แต่ปิดเมื่อตรวจจากภายใน VNet ให้ใช้ VM ไคลเอนต์
- **พอร์ต 22 บน CE ตอบสนองเฉพาะบนที่อยู่ภายใน (SLI) เท่านั้น** เมื่อตรวจจาก VM ไคลเอนต์
  ที่อยู่ภายในของแต่ละ CE จะคืนแบนเนอร์ OpenSSH ในขณะที่ที่อยู่สำหรับการจัดการและ
  ที่อยู่ภายนอกจะหมดเวลา — เช่นเดียวกับที่อยู่ที่ไม่ได้ใช้งานซึ่งใช้เป็นตัวควบคุม eth0 ถูกเปลี่ยนชื่อเป็น
  `a-i-eth0` และไม่มี IP ของโฮสต์ เพราะ datapath เป็นเจ้าของมัน ดังนั้นการตรวจที่อยู่
  ที่คุณรู้จักโหนดนั้นจะไม่บอกอะไรคุณเลยเกี่ยวกับสถานะ SSH ของโหนด

<Aside type="danger" title="อย่าฝังที่อยู่ภายในของ CE ไว้ในโค้ดเด็ดขาด — มันจะถูกจัดสรรใหม่ในทุกครั้งที่สร้างใหม่">
Azure ไม่รักษาว่า CE ตัวใดได้ที่อยู่ใดในซับเน็ตภายใน สังเกตเมื่อ
2026-07-28 หลังการสร้างใหม่ CE ทั้งสามตัวถือ `10.0.3.7`, `10.0.3.5` และ `10.0.3.4`: ไม่ได้
เรียงตามลำดับโหนด ไม่ต่อเนื่องกัน และแตกต่างจากที่เคยถือไว้ก่อนหน้านี้ NIC ของ
ไคลเอนต์ทดสอบเองก็อยู่ในซับเน็ตเดียวกันและเคยถือที่อยู่ที่ CE เคยถือไว้ก่อนหน้า

ให้อ่านค่าเหล่านั้นแทนที่จะจดจำ:

```bash
terraform output -json ce_sli_private_ips
```

หากไม่มี Terraform state อยู่ในมือ ให้สอบถาม Azure ด้วยชื่อ NIC ซึ่ง*คงที่*:

```bash
az network nic show -g "$RG" -n "<vm-name>-internal-nic" \
  --query ipConfigurations[0].privateIPAddress -o tsv
```

การเชื่อมต่อไปยังที่อยู่ที่จำไว้จะทำให้คุณไปลงที่โหนดผิดตัว บน VM ที่ไม่ใช่ CE
หรือไม่ไปที่ไหนเลย — และกรณีสุดท้ายนั้นดูเหมือนกับ "SSH ไม่ได้เปิดใช้งาน" อย่างไม่มีผิดเพี้ยน
</Aside>
