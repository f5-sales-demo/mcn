## ข้อกำหนดเบื้องต้น

- **Terraform** ที่เวอร์ชันขั้นต่ำใน `terraform/versions.tf` — `>= 1.8` เพื่อรองรับ
  ฟังก์ชันที่กำหนดโดยผู้ให้บริการ (provider-defined functions) และบล็อก `check` ที่ป้องกัน VIP
- **ผู้ให้บริการ `xcsh`** ไม่มีการตรึงเวอร์ชันใด ๆ: `.terraform.lock.hcl` ถูก gitignore ไว้ และ
  ข้อจำกัดเป็นเพียงค่าขั้นต่ำแบบปลายเปิด ดังนั้นทุกครั้งที่ `init` จะแก้ไขไปเป็นรีลีสล่าสุดที่เผยแพร่แล้ว
  นั่นเป็นความตั้งใจสำหรับโครงการที่ยังอยู่ในช่วงก่อนเผยแพร่ — เดโมควรล้มเหลวเมื่อผู้ให้บริการถดถอย
  แทนที่จะค้างอยู่บนเวอร์ชันเก่าที่ปิดบังปัญหานั้นไว้
- **ข้อมูลรับรอง API ของ F5 XC** สำหรับ tenant ใน `var.expected_xc_tenant` ที่ export เป็น
  `XCSH_API_TOKEN` (หรือคู่ P12/PEM) โดย export เฉพาะข้อมูลรับรองเท่านั้น ไม่ต้อง export URL — ดู
  ด้านล่าง
- **ข้อมูลรับรอง Azure** ที่มีสิทธิ์สร้าง resource group, VNet, Route Server และ VM
- **F5 XC namespace ที่มีอยู่ก่อนแล้ว** สำหรับชั้นแอป การติดตั้งใช้งานจะ *อ่าน* namespace นั้นและไม่เคย
  สร้างหรือทำลายมัน ดังนั้น namespace ที่บรรจุเดโมอื่นที่ไม่เกี่ยวข้องจะไม่มีทางไปอยู่ในรายการ destroy
  ของสแตกนี้

<Aside type="caution" title="dev_overrides แทนที่ผู้ให้บริการที่คุณคิดว่ากำลังทดสอบอยู่อย่างเงียบ ๆ">
หาก `~/.terraformrc` มีบล็อก `dev_overrides` สำหรับ `xcsh` ทุกคำสั่ง Terraform ในเครื่อง
จะใช้ไบนารีในไดเรกทอรีนั้นและ **ละเว้นทั้งข้อจำกัดเวอร์ชันและไฟล์ล็อก** บิลด์ที่เก่าไปเพียงไม่กี่วัน
ก็เพียงพอที่จะทำให้ล้มเหลวด้วยข้อความ `Blocks of type "…" are not expected here` บนการตั้งค่า
ที่ถูกต้องสมบูรณ์เมื่อเทียบกับผู้ให้บริการที่เผยแพร่แล้ว

เก็บมันไว้นอกพาธเริ่มต้น และเลือกใช้เฉพาะเมื่อคุณกำลังพัฒนาผู้ให้บริการ:

```bash
mv ~/.terraformrc ~/.terraformrc.provider-dev
TF_CLI_CONFIG_FILE=~/.terraformrc.provider-dev terraform plan   # when you mean it
```

</Aside>

## ระบุค่าสองค่าที่ไม่มีค่าเริ่มต้น

ตัวแปรอื่น ๆ ทุกตัวมีค่าเริ่มต้นที่ใช้งานได้ และชื่อออบเจ็กต์ทุกชื่อมาจาก
`var.component` มีสองตัวที่ตั้งใจปล่อยไว้โดยไม่มีค่าเริ่มต้น:

```bash
cd terraform
cp terraform.tfvars.example terraform.tfvars
```

| ตัวแปร | เหตุใดจึงไม่มีค่าเริ่มต้น |
| --- | --- |
| `origin_ip` | ค่าเริ่มต้นใด ๆ ก็คือเครื่องเฉพาะเครื่องหนึ่ง ค่าที่เก่าล้าสมัยจะส่งทราฟฟิกของการติดตั้งใช้งานใหม่ไปยังโฮสต์ของคนอื่นแทนที่จะล้มเหลว |
| `lb_domain` | ตัวกระจายโหลดจับคู่ตาม `Host` ดังนั้นนี่คือสิ่งที่ทุกคำขอต้องส่งมา และเป็นของผู้ที่ดำเนินการติดตั้งใช้งาน |

ทั้งสองตัวมีการตรวจสอบรูปแบบ ดังนั้นการพิมพ์ผิดจะทำให้ plan ล้มเหลวแทนที่จะเป็นตัวเดโม

`terraform.tfvars` ถูก gitignore ไว้ และต้องคงอยู่เช่นนั้น: เพราะมันมี subscription id และ
ค่าเฉพาะของวิศวกรแต่ละคน

## Tenant คือการตั้งค่า ไม่ใช่สิ่งใดก็ตามที่ shell ของคุณ export อยู่

`var.expected_xc_tenant` ระบุชื่อ tenant และเป็นที่เดียวที่ระบุชื่อนั้น
`providers.tf` ดึงค่า `api_url` ของผู้ให้บริการ `xcsh` มาจากตัวแปรนี้ ซึ่งตั้งใจให้
เขียนทับ `XCSH_API_URL` ใด ๆ ในสภาพแวดล้อม และ `postcondition` ใน
`terraform/main.tf` จะทำให้ **plan** ล้มเหลวเมื่อสภาพแวดล้อมระบุ tenant ที่ต่างออกไป

อ่านค่าทั้งสองส่วนได้โดยไม่ต้องรันสิ่งใดที่เปลี่ยนสถานะ:

```bash
terraform output -raw xc_tenant       # what the deployment targets
terraform output -raw xc_env_tenant   # what your shell claims — diagnostic only
```

```text
f5-sales-demo
f5-sales-demo
```

<Aside type="danger" title="ราวกันตกนี้มีอยู่เพราะเดโมย้ายตัวเองไปอยู่ใน tenant ที่ผิดอย่างเงียบ ๆ">
เดโมถูกสร้างขึ้นใน tenant หนึ่ง ต่อมาไฟล์ข้อมูลรับรองเริ่ม export `XCSH_API_URL` ของ tenant
*อีกแห่งหนึ่ง* การ apply ครั้งต่อ ๆ มาจึงสร้างโทเคนสำหรับ tenant นั้น CE VM ไป
ลงทะเบียนใหม่ที่นั่น และการลงทะเบียนเดิมของพวกมันก็ถูกทิ้งร้าง ทุก plan ที่เกิดขึ้นระหว่างนั้น
สะอาดหมดจด เพราะไม่มีสิ่งใดในการตั้งค่าที่มีความเห็นเกี่ยวกับ tenant
([issue 696](https://github.com/f5-sales-demo/mcn/issues/696) แก้ไขใน
[PR 697](https://github.com/f5-sales-demo/mcn/pull/697)) การกู้คืนหมายถึงการทำลาย
สแตกใน tenant ที่ผิดและสร้างขึ้นใหม่ใน tenant ที่ถูกต้อง

อาการที่ควรจำได้ เพราะมันไม่ได้อธิบายตัวเอง: โทเคนที่สร้างขึ้นสำหรับ tenant อื่นจะ
ล้มเหลวกับปลายทางที่ตรึงไว้ด้วย `401` เปล่า ๆ ซึ่งอ่านดูเหมือนข้อมูลรับรองหมดอายุเป๊ะ ๆ
หากข้อมูลรับรองที่คุณเชื่อว่ายังใช้ได้คืนค่า `401` ให้เปรียบเทียบเอาต์พุตสองรายการ
ด้านบนก่อนที่คุณจะสร้างโทเคนใหม่
</Aside>

## Apply

<Steps>

1. **เริ่มต้นใช้งาน** การตั้งค่าแบ็กเอนด์ไม่ได้ถูก commit ไว้ ให้ใช้ของคุณเอง

   ```bash
   terraform init -backend-config=backend.hcl
   ```

2. **Apply ครั้งแรก** ขั้นนี้จะสร้าง Azure, ไซต์ CE และโทเคนลงทะเบียน และบูต
   CE ขึ้นมา

   ```bash
   terraform apply
   ```

3. **Apply อีกครั้งหลังจาก CE ลงทะเบียนแล้ว** ขั้นนี้ไม่ใช่ทางเลือก และเหตุผลอยู่
   ด้านล่างนี้ ไม่ใช่สิ่งที่คุณต้องไปค้นพบเอง

   ```bash
   terraform apply
   ```

</Steps>

จากนั้นไปที่ [พิสูจน์ว่าระบบมีสุขภาพดี](../verify/) ก่อนแสดงให้ใครดู

## การอนุมัติการลงทะเบียนเป็นแบบอัตโนมัติ และการ apply ยังเป็นสองเฟส

การอนุมัติการลงทะเบียนไม่จำเป็นต้องมีคนในคอนโซลอีกต่อไป: ทรัพยากร
`xcsh_registration_approval` จะดำเนินการนี้ และโมดูลไซต์จะแก้ไขว่าจะอนุมัติ
การลงทะเบียนใด

สิ่งนั้นยังไม่ทำให้การติดตั้งใช้งานเป็น `apply` ครั้งเดียวแบบไม่ต้องแตะต้อง และเหตุผลนั้นควร
ทำความเข้าใจก่อนที่คุณจะเฝ้าดูการรันครั้งแรกแล้วสรุปว่ามันล้มเหลว:

- ออบเจ็กต์การลงทะเบียนของ CE มีชื่อว่า **`r-<uuid>`** ไม่เคยตั้งชื่อตามไซต์ ดังนั้น
  ไม่มีสิ่งใดที่จะทำนายชื่อได้ในเวลา plan
- การลงทะเบียนจะเกิดขึ้นหลังจาก VM บูตขึ้นและ `vpm` ลงทะเบียนแล้วเท่านั้น
- ดังนั้น **apply ครั้งแรกจะไม่วางแผนการอนุมัติใด ๆ เลย** ให้ apply อีกครั้งหลังจาก CE ลงทะเบียนแล้ว
  แล้วการอนุมัติจะถูกสร้างขึ้น

`terraform/main.tf` บันทึกลำดับนี้ไว้ที่ส่วนบนของไฟล์ ซึ่งเป็นเวอร์ชัน
ที่ถือเป็นแหล่งอ้างอิง — ลำดับการติดตั้งใช้งานอยู่กับโค้ดที่ทำให้มันเกิดขึ้น

<Aside type="caution" title="ไซต์ที่สร้างใหม่ยังเข้าถึงผ่าน operate API ไม่ได้ทันที">
ประมาณ 25 ถึง 30 นาทีหลังจากไซต์ใหม่รายงานสถานะ `ONLINE` ปลายทาง `vpm/debug` จะ
ตอบด้วยหน้า `503` ของ BIG-IP ที่ระบุว่า `The requested URL was rejected` ดูเหมือนกับ
การบล็อกโดยไฟร์วอลล์แอปเว็บ (WAF) หรือโทเคนถูกเพิกถอน แต่ไม่ใช่ทั้งสองอย่าง ให้รอ แล้วลองใหม่

เรื่องนี้ส่งผลกับเดโมที่เพิ่งสร้างใหม่ ไม่ใช่เดโมที่กำลังทำงานอยู่
</Aside>

## SSH ของผู้ปฏิบัติงานเป็นการตัดสินใจในเวลาสร้าง

การติดตั้งใช้งานจะเขียนคีย์ของผู้ปฏิบัติงานไปยังบัญชี `admin` ของแอปพลายแอนซ์ ซึ่งมี login shell
เป็น Site CLI คีย์นี้ถูกเขียนโดย `write_files` ของ cloud-init ซึ่งรันเพียงครั้งเดียวเมื่อบูตครั้งแรก

<Aside type="caution" title="ไม่สามารถเพิ่มเข้าไปใน CE ที่กำลังทำงานอยู่แล้วได้">
`custom_data` เป็นแบบแทนที่เท่านั้น ดังนั้นการนำสิ่งนี้ไปใช้กับ CE ที่กำลังทำงานอยู่จะ **แทนที่ CE VM ทุกตัว**
นั่นคือการสร้างฟลีตใหม่ทั้งหมด ไม่ใช่การเปลี่ยนการตั้งค่า สิ่งเดียวกันนี้ก็เป็นจริงกับสิ่งอื่นใด
ในเทมเพลต cloud-init — รวมถึงคอมเมนต์ เพราะ `custom_data` คือ
`base64encode` ของไฟล์ที่เรนเดอร์แล้ว

เดิมทีเคยแย่กว่านี้: CE ที่ถูกแทนที่จะไม่สามารถลงทะเบียนใหม่ได้เลย เพราะการลงทะเบียนของโหนดที่ถูกทำลาย
ยังคงถือดัชนีที่ไม่ซ้ำกัน `(tenant, cluster_name, hostname)` ของ control plane อยู่ — และ
`terraform plan` รายงานว่า "No changes" ตลอดเวลาที่ฟลีตล่ม
การกู้คืนต้องสร้างใหม่เต็มรูปแบบสองครั้ง ปัญหานั้นได้รับการแก้ไขแล้ว
([issue 674](https://github.com/f5-sales-demo/mcn/issues/674) ปิดโดย
[PR 693](https://github.com/f5-sales-demo/mcn/pull/693)): วงจรชีวิตของออบเจ็กต์ไซต์ตอนนี้
ผูกกับอินสแตนซ์ CE VM ดังนั้นการแทนที่ VM จะแทนที่ไซต์ และการลบไซต์
จะพาการลงทะเบียนของมันไปด้วยก่อนที่โหนดตัวแทนจะบูตขึ้น

ผู้ที่จะนำสิ่งนี้ไปใช้ที่อื่นควรอ่าน
[หน้า SSH](../../customer-edge/access/ssh/) ก่อน
</Aside>

## รื้อถอนออก

```bash
terraform destroy
```

Namespace ของแอปจะยังคงอยู่: มันถูกอ่าน ไม่เคยถูกจัดการ ดังนั้น `destroy` จึงไม่สามารถพา namespace
ที่บรรจุเดโมอื่นที่ไม่เกี่ยวข้องไปด้วยได้ ทุกอย่างที่เหลือใน resource group จะถูกลบไป
