ข้อกล่าวอ้างที่เดโมนี้สนับสนุนมีขอบเขตจำกัดและควรระบุอย่างแม่นยำ เพราะข้อกล่าวอ้างที่กว้างกว่านี้
จะไม่อาจทนต่อคำถามได้:

> Customer Edge หลายตัวต่างประกาศ host route เดียวกันผ่าน eBGP และ Azure ติดตั้งทั้งหมด
> เป็น next hop ที่มีต้นทุนเท่ากัน การกระจายทราฟฟิกและการนำโหนดออกจึงเป็น
> คุณสมบัติของโครงสร้างการกำหนดเส้นทาง — ไม่มีตัวกระจายโหลดของ Azure อยู่หน้า CE เลย

รัน [การตรวจสอบสุขภาพทั้งสี่รายการ](../verify/) ก่อน ทุกอย่างด้านล่างนี้สมมติว่าผ่านแล้ว

## คำสั่งเดียวที่ทำให้มองเห็นได้

Effective route เป็นหลักฐานเดี่ยวที่หนักแน่นที่สุด: เพราะเป็นสิ่งที่ Azure โปรแกรมไว้จริง
ไม่ใช่สิ่งที่ CE กล่าวอ้าง

```bash
cd terraform
az network nic show-effective-route-table \
  -g "$(terraform output -raw resource_group_name)" \
  -n "$(terraform output -raw client_nic_name)" \
  --query "value[?addressPrefix[0]=='$(terraform output -raw vip)/32'].{prefix:addressPrefix[0],nh:nextHopIpAddress,state:state}" \
  -o json
```

สังเกตเมื่อ 2026-07-28:

```json
[
  {
    "nh": ["10.0.1.5", "10.0.1.6", "10.0.1.4"],
    "prefix": "10.250.0.10/32",
    "state": "Active"
  }
]
```

หนึ่ง prefix, สาม next hop, `Active` นั่นคือสาระสำคัญทั้งหมดของเดโมในเอาต์พุตเดียว
และควรหยุดพิจารณาสักครู่: ไม่มีสิ่งใดในภาพนี้ที่เป็นตัวกระจายโหลด

จากนั้นแสดงการให้บริการ จากภายใน VNet และพร้อมกับเฮดเดอร์ `Host`:

```bash
az vm run-command invoke \
  -g "$(terraform output -raw resource_group_name)" \
  -n "$(terraform output -raw client_vm_name)" \
  --command-id RunShellScript --query "value[0].message" -o tsv \
  --scripts "curl -s -o /dev/null -w '%{http_code}\n' \
               -H 'Host: $(terraform output -raw lb_domain)' \
               http://$(terraform output -raw vip)/"
```

<Aside type="caution" title="อย่าสาธิตด้วยการพิมพ์ที่อยู่ลงในเบราว์เซอร์">
ตัวกระจายโหลดจับคู่ด้วย `Host` ดังนั้นคำขอที่ใช้ IP เปล่าจะได้ผลลัพธ์ **404** — บนการดีพลอย
ที่สมบูรณ์ดีทุกอย่าง ให้ส่งเฮดเดอร์ไปด้วย หรือแปลงชื่อโดเมนให้ชี้ไปที่ VIP ก่อน 404 ต่อหน้า
ผู้ฟังนั้นแก้สถานการณ์ได้ยากแม้ว่าจะไม่มีอะไรผิดพลาดเลย
</Aside>

## ลำดับที่แนะนำ

<Steps>

1. **วางกรอบ** หนึ่ง VIP, CE หลายตัว, ไม่มีตัวกระจายโหลด โครงสร้างการกำหนดเส้นทางคือ
   กลไก HA
2. **แสดงด้านการประกาศเส้นทาง** วนดู peering ([การตรวจสอบที่ 2](../verify/)) — CE แต่ละตัว
   ประกาศ prefix เดียวกันด้วย next hop ของตัวเอง ทั้งหมดมี AS path เดียวกัน จึงไม่มีตัวใด
   ถูกเลือกมากกว่า
3. **แสดงสิ่งที่ Azure ทำกับมัน** ตาราง effective route ด้านบน: หนึ่ง prefix, N next hop,
   `Active`
4. **แสดงการให้บริการ** คำสั่ง `curl` ด้านบน พร้อมเฮดเดอร์
5. **แสดงการกำหนดค่า** [Terraform](../terraform/) ถูกเผยแพร่ไว้ที่นี่ อ่านมาจาก
   ไฟล์ที่ใช้ดีพลอยจริง — มีประโยชน์เมื่อมีคนถามว่าสิ่งนี้ทำซ้ำได้หรือไม่

</Steps>

## สิ่งที่เดโมนี้ยังแสดงไม่ได้

ระบุไว้ที่นี่แทนที่จะไปค้นพบสดๆ ทั้งสามข้อเป็นการขาดหลักฐาน ไม่ใช่ความล้มเหลวที่ทราบแล้ว

<Aside type="danger" title="อย่าซ้อมเรื่องราว failover จากหน้าเหล่านี้">
**failover ยังไม่ได้รับการทดสอบ** next hop ที่มีต้นทุนเท่ากันได้รับการยืนยันว่าติดตั้งแล้ว แต่
สิ่งที่เกิดขึ้นกับตารางเส้นทางเมื่อ CE ถูกหยุดหรือหยุดประกาศเส้นทางนั้นยังไม่ได้ถูกทดลอง
กับการดีพลอยนี้ กลไกที่ตั้งใจไว้คือถอนการประกาศของ CE หนึ่งตัวและ
ดูจำนวน next hop ลดลง แต่จนกว่าจะได้รันและวัดผลจริง สิ่งนั้นก็ยังเป็นเพียง
แผน ไม่ใช่ผลลัพธ์ — ดังนั้นอย่าให้คำมั่นสัญญา และอย่าแสดงแบบด้นสดต่อหน้าผู้ฟัง

ติดตามได้ที่ [issue 700](https://github.com/f5-sales-demo/mcn/issues/700) ต้องใช้ช่วงเวลา
ที่ไม่มีใครอื่นใช้สภาพแวดล้อมนี้ เนื่องจากมันเปลี่ยนสถานะการประกาศเส้นทางที่ใช้งานจริง
</Aside>

- **การกระจายทราฟฟิกข้าม next hop ยังไม่ได้ถูกวัด** คำขอ 1,470 รายการไปยัง
  VIP ถูกบันทึกไว้ใน [หน้าการตรวจสอบ](../verify/) ซึ่งยืนยันว่าเส้นทาง
  ใช้งานได้และมีพฤติกรรมอย่างไรตามเวลา แต่ไม่มีสิ่งใดในนั้นแสดงว่าคำขอถูกกระจายข้าม
  next hop อย่างไร และโทโพโลยีนี้ไม่มี HTTP listener ต่อโหนดที่จะใช้ระบุที่มาได้ หาก
  ถูกถามว่า "กระจายเท่ากันไหม?" คำตอบที่ตรงไปตรงมาคือยังไม่ได้วัดในที่นี้
- **สาเหตุของช่วงชั่วคราวในการลู่เข้าของสแตกที่สร้างใหม่ยังไม่ได้ระบุ** มันถูก
  อธิบายลักษณะไว้ — เกิดขึ้นเมื่อใด นานเท่าใด และต้นทางสะอาดตลอดช่วงเวลานั้น —
  แต่ไม่ได้อธิบายสาเหตุ

<Aside type="note" title="หากคุณกำลังนำเสนอบนสแตกที่สร้างใหม่ ให้รอ">
VIP จะสูญเสียคำขอเป็นสัดส่วนเล็กน้อยในช่วงประมาณ 45 นาทีแรกหลังจาก CE
เข้าสู่สถานะ `ONLINE` อาการนี้หายไปโดยสมบูรณ์ ให้สร้างเดโมล่วงหน้านานพอก่อนที่คุณจะต้องใช้
และรันการตรวจสอบที่ 4 อีกครั้งทันทีก่อนนำเสนอ
</Aside>
