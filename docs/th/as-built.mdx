การปรับใช้นี้สาธิต **ความพร้อมใช้งานสูงแบบ active/active ของ Customer Edge ใน Azure**
โดยไม่มี Azure load balancer อยู่ด้านหน้า CE ทั้งสาม CE ต่างประกาศ host route
เดียวกันด้วย eBGP และ Azure Route Server ติดตั้งทั้งสามรายการเป็น next hop แบบ equal-cost ใน
VNet ดังนั้นโครงข่ายการกำหนดเส้นทาง ไม่ใช่ load balancer จึงเป็นจุดที่การกระจายทราฟฟิก
และการถอดโหนดที่ล้มเหลวควรเกิดขึ้น

ทุกอย่างที่แสดงด้านล่างถูกรันกับการปรับใช้จริง และผลลัพธ์คือผลลัพธ์ที่ระบบสร้างขึ้นจริง สองสิ่งที่ประโยคนั้น *ไม่* ครอบคลุม — การสลับการทำงาน (failover) และการกระจายทราฟฟิก —
ถูกระบุไว้ตอนท้ายแทนที่จะปล่อยให้สันนิษฐานเอาเอง

## สิ่งที่ถูกปรับใช้

```text
                  Azure Route Server  ce-ha-lab-rrs  ASN 65515
                          10.0.4.4  and  10.0.4.5
                                      |
              +-----------------------+-----------------------+
              |                       |                       |
        eastus01-bgp            eastus02-bgp            eastus03-bgp     eBGP
              |                       |                       |      CE ASN 64512
        10.0.1.4                10.0.1.5                10.0.1.6     <- CE eth0 / SLO
     f5-xc-ce-vm-01          f5-xc-ce-vm-02          f5-xc-ce-vm-03
    ar-bgp-eastus01         ar-bgp-eastus02         ar-bgp-eastus03
              |                       |                       |
              +----- each advertises 10.250.0.10/32 -----------+
                          three-way ECMP into the VNet
```

| ส่วนประกอบ | ตามที่สร้างจริง |
| --- | --- |
| Customer Edges | ไซต์ Secure Mesh v2 แบบโหนดเดียว 3 ไซต์ — `ar-bgp-eastus01`, `ar-bgp-eastus02`, `ar-bgp-eastus03` |
| ซอฟต์แวร์ CE | ตรึงไว้ที่ `9.2024.6`, build `crt-20250613-3382` |
| Azure VMs | `f5-xc-ce-vm-01/02/03`, มี NIC สามชุดต่อเครื่อง (management/SLO, external, internal/SLI) |
| การแลกเปลี่ยนเส้นทาง | Azure Route Server `ce-ha-lab-rrs`, ASN `65515`, อินสแตนซ์ `10.0.4.4` และ `10.0.4.5` |
| การ Peering | หนึ่งรายการต่อ CE — `eastus01-bgp`, `eastus02-bgp`, `eastus03-bgp` — CE ASN `64512` |
| VIP ที่ประกาศ | `10.250.0.10/32`, ประกาศเหมือนกันโดย CE ทั้งสาม |
| Load balancer | `ar-bgp-ecmp-lb`, ให้บริการโดเมน `ar-bgp-ecmp.bankexample.com` |
| ไคลเอนต์ทดสอบ | `ar-ecmp-client`, VM ภายใน VNet เดียวกัน |
| Resource group | `rg-mcn-ce-ha-rmordasiewicz` |

<Aside type="caution" title="VIP ต้องอยู่นอก CIDR ของทุก VNet">
`terraform/main.tf` มีบล็อก `check` ที่ยืนยันว่า VIP อยู่นอกทั้ง CIDR ของ hub
และ spoke และจะปฏิเสธแผนหากไม่เป็นเช่นนั้น เหตุผลที่ระบุไว้คือ VIP ที่อยู่ภายใน
CIDR ของ VNet จะแพ้ให้กับ system route ของ VNet เอง แม้ว่าเส้นทาง BGP จะเจาะจงมากกว่าก็ตาม

ให้ถือว่าการ์ดนี้คือข้อตกลง: หากคุณเปลี่ยนการสาธิตนี้ไปใช้การกำหนดที่อยู่แบบอื่น
VIP ก็ต้องย้ายออกไปนอกช่วงของ VNet ตามไปด้วย
</Aside>

## พิสูจน์ว่าระบบสมบูรณ์ก่อนนำเสนอ

การตรวจสอบสี่ขั้นตอน ตามลำดับนี้ แต่ละขั้นจะจำกัดขอบเขตว่าความผิดพลาดอยู่ตรงไหน ดังนั้นความล้มเหลวจึงบอก
อะไรบางอย่างกับคุณ ไม่ใช่เพียงบอกว่ามีบางอย่างผิดพลาด

<Steps>

1. **ทั้งสามไซต์อยู่ในสถานะ `ONLINE`** ไม่มีสิ่งใดในขั้นถัดไปที่จะเป็นจริงได้หากข้อนี้ไม่เป็นจริง

   ```bash
   for s in ar-bgp-eastus01 ar-bgp-eastus02 ar-bgp-eastus03; do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **ทุก peering กำลังเรียนรู้การประกาศ VIP ของ CE นั้น** ให้สอบถามแต่ละ peering
   แยกกัน — ดูกับดักด้านล่าง เพราะนี่คือจุดที่การสาธิตมักจะดูเหมือน
   เสียหายทั้งที่ไม่ได้เสีย

   ```bash
   for p in eastus01-bgp eastus02-bgp eastus03-bgp; do
     echo "--- $p"
     az network routeserver peering list-learned-routes \
       --name "$p" --routeserver ce-ha-lab-rrs -g rg-mcn-ce-ha-rmordasiewicz \
       --query "RouteServiceRole_IN_0[].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp

   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp

   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   สาม peering, สาม next hop ที่ต่างกัน, หนึ่ง prefix นั่นคือการพิสูจน์ฝั่งการประกาศ
   ของ ECMP

3. **เส้นทางที่มีผล (effective routes) ของไคลเอนต์มี next hop ครบทั้งสามรายการ** นี่คือตัว ECMP เอง
   ตามที่ VNet ได้โปรแกรมไว้ — ไม่ใช่สิ่งที่ CE อ้าง แต่คือสิ่งที่ Azure ทำกับมันจริง ๆ

   ```bash
   az network nic show-effective-route-table \
     --name ar-ecmp-clientVMNic -g rg-mcn-ce-ha-rmordasiewicz \
     --query "value[?addressPrefix[0]=='10.250.0.10/32']" -o json
   ```

   ```json
   [
     {
       "addressPrefix": ["10.250.0.10/32"],
       "nextHopIpAddress": ["10.0.1.5", "10.0.1.4", "10.0.1.6"],
       "nextHopType": "VirtualNetworkGateway",
       "source": "VirtualNetworkGateway",
       "state": "Active"
     }
   ]
   ```

   `state: Active` พร้อมกับสามรายการใน `nextHopIpAddress` คือสิ่งที่ต้องตรวจสอบ หากมี next hop เพียงหนึ่งรายการ
   ในจุดที่คุณคาดว่าจะมีสาม แสดงว่ามี CE หยุดประกาศเส้นทางแล้ว และขั้นตอนที่ 2 จะระบุว่าเป็นตัวใด

4. **VIP ให้บริการทราฟฟิกได้** จาก VM ไคลเอนต์ และ **พร้อมกับส่วนหัว `Host`** — ดูกับดักที่สองด้านล่าง

   ```bash
   az vm run-command invoke -g rg-mcn-ce-ha-rmordasiewicz -n ar-ecmp-client \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts 'for i in $(seq 1 10); do
                  curl -s -o /dev/null -w "%{http_code} " \
                    -H "Host: ar-bgp-ecmp.bankexample.com" http://10.250.0.10/
                done'
   ```

   ```text
   200 200 200 200 200 200 200 200 200 200
   ```

</Steps>

## กับดัก: peering หนึ่งรายการแสดงเส้นทางเดียว และนั่นถูกต้องแล้ว

`list-learned-routes` มีขอบเขตจำกัดอยู่ที่ peering ที่คุณระบุชื่อ มันรายงานสิ่งที่ peer **นั้น**
ประกาศ ไม่ใช่ตารางทั้งหมดของ Route Server

ดังนั้นการสอบถาม `eastus01-bgp` เพียงอย่างเดียวจะคืนค่า `10.250.0.10/32` รายการเดียวผ่าน `10.0.1.4` และมัน
ชวนให้ตีความว่า "มี CE เพียงตัวเดียวที่ประกาศ — อีกสองตัวล่ม" ซึ่งไม่มีอะไร
ล่มเลย การประกาศอีกสองรายการมองเห็นได้บน peering ของตัวเอง ซึ่งเป็นสิ่งที่
ขั้นตอนที่ 2 ด้านบนวนลูปตรวจสอบ

การยืนยัน ECMP จากการสอบถาม peering เพียงรายการเดียวเป็นไปไม่ได้ ให้วนลูปทั้งสาม
peering หรืออ่านตารางเส้นทางที่มีผลของไคลเอนต์ ซึ่งแสดงผลลัพธ์รวมในการเรียกครั้งเดียว

## กับดัก: คำขอด้วย IP เปล่าคืนค่า 404

Load balancer จับคู่ด้วย `Host` VIP ไม่ใช่ virtual server ที่จะให้บริการอะไรก็ตาม
แก่ใครก็ตามที่เชื่อมต่อมายังที่อยู่นั้น

```text
curl -H 'Host: ar-bgp-ecmp.bankexample.com' http://10.250.0.10/   ->  200   (10 of 10)
curl                                        http://10.250.0.10/   ->  404
```

ทั้งสองรายการนั้นถูกสร้างขึ้นในการรันครั้งเดียวกันกับการปรับใช้ที่สมบูรณ์ดี **404 จาก IP เปล่า
คือหลักฐานว่าเส้นทางทำงานได้** — คำขอไปถึง CE, พร็อกซีของ CE ตอบกลับ และ
ปฏิเสธเพราะไม่มีโดเมนที่กำหนดค่าไว้ตรงกัน การตีความว่าเป็นเหตุขัดข้องจะทำให้คุณไป
ตรวจสอบ BGP ซึ่งคุณจะไม่พบสิ่งผิดปกติใด ๆ

เช่นเดียวกันระหว่างการสาธิต: หากคุณพิมพ์ที่อยู่ลงในเบราว์เซอร์แทนที่จะ
แก้ชื่อโดเมนไปยังที่อยู่นั้น คุณจะได้ 404

## การอนุมัติการลงทะเบียนเป็นแบบอัตโนมัติ และการ apply ยังคงมีสองเฟส

การอนุมัติการลงทะเบียนไม่จำเป็นต้องมีมนุษย์ในคอนโซลอีกต่อไป บนผู้ให้บริการ **v3.81.1** ทรัพยากร
`xcsh_registration_approval` เป็นผู้ดำเนินการ และโมดูลไซต์จะระบุว่าจะอนุมัติการลงทะเบียนใด

นั่นยังไม่ทำให้การปรับใช้เป็น `apply` แบบครั้งเดียวจบโดยไม่ต้องแตะต้อง และเหตุผลนั้น
ควรทำความเข้าใจก่อนที่คุณจะดูการรันครั้งแรกแล้วสรุปว่าล้มเหลว:

- ออบเจ็กต์การลงทะเบียนของ CE มีชื่อว่า **`r-<uuid>`** มันไม่เคยตั้งชื่อตามไซต์ ดังนั้น
  จึงไม่มีอะไรที่จะทำนายชื่อได้ในขั้นตอน plan
- การลงทะเบียนจะมีอยู่ก็ต่อเมื่อ VM บูตขึ้นและ `vpm` ได้ลงทะเบียนแล้วเท่านั้น
- ดังนั้น **การ apply ครั้งแรกจึงไม่วางแผนการอนุมัติใด ๆ เลย** ให้ apply ซ้ำอีกครั้งเมื่อ CE ลงทะเบียนแล้ว
  และการอนุมัติถูกสร้างขึ้น

`terraform/main.tf` บันทึกลำดับนี้ไว้ที่ส่วนบนสุดของไฟล์ ซึ่งเป็นเวอร์ชัน
ที่ถือเป็นแหล่งอ้างอิงหลัก — ลำดับการปรับใช้อยู่คู่กับโค้ดที่นำไปปฏิบัติจริง

<Aside type="caution" title="ไซต์ที่สร้างใหม่จะยังเข้าถึงผ่าน operate API ไม่ได้ทันที">
ประมาณ 25 ถึง 30 นาทีหลังจากไซต์ใหม่รายงานสถานะ `ONLINE` เอ็นด์พอยต์ `vpm/debug`
จะตอบกลับด้วยหน้า `503` ของ BIG-IP ที่ระบุว่า `The requested URL was rejected` ซึ่งดูเหมือน
การบล็อกโดยไฟร์วอลล์แอปเว็บ (WAF) หรือโทเค็นถูกเพิกถอน แต่ไม่ใช่ทั้งสองอย่าง ให้รอแล้วลองใหม่

สิ่งนี้ส่งผลกับการสาธิตที่เพิ่งสร้างใหม่ ไม่ใช่การสาธิตที่กำลังทำงานอยู่แล้ว
</Aside>

## การเข้าถึง Site CLI

การวินิจฉัยบนเครื่องตามปกติจะทำผ่าน debug API ซึ่งมีสคริปต์ไว้ให้แล้วที่นี่
ตรวจสอบว่าชุดคำสั่งยังตรงกับที่เอกสารอธิบายไว้:

```bash
bash scripts/capture-sitecli.sh --check --site ar-bgp-eastus01 --node f5-xc-ce-vm-01
```

```text
catalog matches the live CE (build crt-20250613-3382, 34 commands)
```

`--check` ไม่เขียนข้อมูลใด ๆ จึงปลอดภัยต่อการสาธิตที่ใช้งานจริง

สำหรับคำสั่งที่ API ไม่ได้ส่งต่อให้ การปรับใช้นี้ยังมี **SSH ของผู้ปฏิบัติงานไปยัง
บัญชี `admin` ของอุปกรณ์** ซึ่ง login shell ของบัญชีนี้คือ Site CLI ได้รับการยืนยันแล้วบน CE
ทั้งสามตัว ให้เชื่อมต่อไปยังที่อยู่ภายใน (SLI) จากโฮสต์ที่อยู่ใน VNet โดยจัดสรร
เทอร์มินัลไว้ด้วย:

```bash
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<vm-in-vnet> admin@10.0.3.5
```

```text
WELCOME IN SITE CLI
Registration Status: PROVISIONED
```

<Aside type="caution" title="การเข้าถึงนั้นมีอยู่เพราะ CE เหล่านี้ถูกสร้างมาพร้อมกับมัน — ไม่สามารถเพิ่มภายหลังได้">
คีย์ของผู้ปฏิบัติงานถูกเขียนโดย cloud-init `write_files` ซึ่งทำงานเพียงครั้งเดียวตอนบูตครั้งแรก
`custom_data` เป็นแบบแทนที่เท่านั้น ดังนั้นการนำสิ่งนี้ไปใช้กับ CE ที่ทำงานอยู่แล้วจะแทนที่
CE VM ทุกตัว — และการแทนที่หนึ่งตัวในปัจจุบันทำให้การลงทะเบียนติดขัด ในขณะที่ `terraform plan`
รายงานว่า "No changes" ([issue 674](https://github.com/f5-sales-demo/mcn/issues/674))
การกู้คืนต้องใช้การสร้างใหม่ทั้งหมดถึงสองครั้ง

สำหรับการปรับใช้นี้ การเปลี่ยนแปลงได้ถูกนำไปใช้แล้วและกลุ่มเครื่องอยู่ในสภาพสมบูรณ์ ผู้ที่
จะนำไปใช้ที่อื่นควรอ่าน
[หน้า SSH](../customer-edge/access/ssh/) ก่อน
</Aside>

## กับดักในการวัดผลอีกสองข้อ

ทั้งสองข้อนี้ให้คำตอบที่ผิดอย่างมั่นใจในสภาพแวดล้อมนี้ และไม่มีข้อใดที่
เห็นได้ชัด

- **ตรวจสอบจากภายใน VNet ไม่ใช่จากเวิร์กสเตชันของคุณ** Netskope ทำ TCP handshake
  ให้เสร็จเองบนพอร์ตทั่วไป ดังนั้นการตรวจสอบจากเวิร์กสเตชันจะรายงานว่าพอร์ต **เปิด** ทั้งที่
  จริง ๆ แล้วปิดอยู่ พอร์ต 80 และ 443 แสดงว่าเปิดบนที่อยู่สาธารณะของ CE เมื่อตรวจจาก
  เวิร์กสเตชัน แต่ปิดอยู่เมื่อตรวจจากภายใน VNet ให้ใช้ `ar-ecmp-client`
- **พอร์ต 22 บน CE ตอบสนองเฉพาะบนที่อยู่ภายใน (SLI) เท่านั้น** เมื่อตรวจสอบจาก
  `ar-ecmp-client` ไปยัง CE ทั้งสาม ที่อยู่ `10.0.3.5`, `10.0.3.6` และ `10.0.3.7` ล้วนคืนค่า
  `SSH-2.0-OpenSSH_8.7` ในขณะที่ที่อยู่ management และ external หมดเวลา — เช่นเดียวกับ
  ที่อยู่ที่ไม่ได้ใช้งานซึ่งใช้เป็นตัวควบคุม eth0 ถูกเปลี่ยนชื่อเป็น `a-i-eth0` และไม่มี host IP
  เพราะ datapath เป็นเจ้าของมัน ดังนั้นการตรวจสอบที่อยู่ที่คุณใช้เรียกโหนดจึงไม่บอก
  อะไรเลยเกี่ยวกับสถานะ SSH ของโหนด และที่อยู่ SLI คือที่อยู่ที่ควรเชื่อมต่อไป

<Aside type="note" title="สิ่งที่หน้านี้ไม่ได้กล่าวอ้าง">
สองสิ่งที่ผู้อ่านอาจคาดหวังอย่างสมเหตุสมผลจากหน้านี้ถูกละไว้โดยเจตนา เพราะยังไม่ได้
ทดสอบกับการปรับใช้จริง:

- **ยังไม่ได้ทดสอบการสลับการทำงาน (failover)** มีการยืนยันแล้วว่า next hop แบบ equal-cost ทั้งสามถูกติดตั้งไว้ แต่
  สิ่งที่เกิดขึ้นกับตารางเส้นทางเมื่อ CE หยุดทำงานยังไม่ได้แสดงไว้ ดังนั้นอย่าซ้อมการสาธิต
  failover จากหน้านี้โดยไม่ทดลองก่อน
- **ยังไม่ได้วัดการกระจายทราฟฟิก** คำขอสิบจากสิบรายการไปยัง VIP คืนค่า `200`
  ซึ่งพิสูจน์ว่าเส้นทางทำงานได้ แต่ไม่ได้แสดงว่าคำขอทั้งสิบนั้นกระจายไปยัง next hop
  ทั้งสามอย่างไร

</Aside>
