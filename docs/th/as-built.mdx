การ deploy นี้สาธิต **ความพร้อมใช้งานสูงแบบ active/active ของ Customer Edge ใน Azure**
โดยไม่มี Azure load balancer อยู่ด้านหน้า CE ทั้งสาม CE ต่างประกาศ host route
เดียวกันด้วย eBGP และ Azure Route Server ติดตั้งทั้งสามเป็น next hop ที่มีต้นทุนเท่ากันใน
VNet ดังนั้นโครงข่ายการกำหนดเส้นทาง (routing fabric) แทนที่จะเป็น load balancer จึงเป็นจุดที่การกระจายทราฟฟิก
และการนำโหนดที่ล้มเหลวออกควรเกิดขึ้น

ทุกอย่างที่แสดงด้านล่างถูกรันกับการ deploy จริง และผลลัพธ์คือผลลัพธ์ที่มันสร้างขึ้นจริง
สิ่งที่ประโยคนั้น *ไม่ได้* ครอบคลุม — การ failover, การแบ่งทราฟฟิกไปยัง next hop ทั้งสาม
และเหตุใด VIP จึงสูญเสียแพ็กเก็ตช่วงสั้น ๆ บนบิลด์ใหม่ — จะถูกระบุไว้อย่างชัดเจน
แทนที่จะปล่อยให้เดาเอาเอง

## สิ่งที่ถูก deploy

```text
                  Azure Route Server  ce-ha-lab-rrs  ASN 65515
                          10.0.4.4  and  10.0.4.5
                                      |
              +-----------------------+-----------------------+
              |                       |                       |
        eastus01-bgp            eastus02-bgp            eastus03-bgp     eBGP
              |                       |                       |      CE ASN 64512
        10.0.1.4                10.0.1.5                10.0.1.6     <- CE eth0 / SLO
     f5-xc-ce-vm-01          f5-xc-ce-vm-02          f5-xc-ce-vm-03
    ar-bgp-eastus01         ar-bgp-eastus02         ar-bgp-eastus03
              |                       |                       |
              +----- each advertises 10.250.0.10/32 -----------+
                          three-way ECMP into the VNet
```

## พิสูจน์ว่าระบบสมบูรณ์ก่อนที่คุณจะนำเสนอ

มีสี่การตรวจสอบ ตามลำดับนี้ แต่ละรายการจะจำกัดขอบเขตว่าความผิดพลาดจะอยู่ที่ใด
ดังนั้นความล้มเหลวจะบอกอะไรคุณได้ ไม่ใช่เพียงบอกว่ามีอะไรผิดพลาด

<Steps>

1. **ทั้งสามไซต์อยู่ในสถานะ `ONLINE`** ไม่มีสิ่งใดในขั้นถัดไปเป็นจริงได้หากข้อนี้ไม่เป็นจริง

   ```bash
   for s in ar-bgp-eastus01 ar-bgp-eastus02 ar-bgp-eastus03; do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **ทุก peering เรียนรู้การประกาศ VIP ของ CE นั้น** ให้ query แต่ละ peering
   แยกกัน — ดูกับดักด้านล่าง เพราะนี่คือจุดที่การสาธิตมักดูเหมือน
   เสียบ่อยที่สุดแต่จริง ๆ ไม่เสีย

   ```bash
   for p in eastus01-bgp eastus02-bgp eastus03-bgp; do
     echo "--- $p"
     az network routeserver peering list-learned-routes \
       --name "$p" --routeserver ce-ha-lab-rrs -g rg-mcn-ce-ha-rmordasiewicz \
       --query "RouteServiceRole_IN_0[].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp

   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp

   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   สาม peering, สาม next hop ที่ต่างกัน, หนึ่ง prefix นั่นคือด้านการประกาศ
   ของ ECMP ที่พิสูจน์แล้ว

3. **เส้นทางที่มีผลบังคับใช้ของไคลเอนต์มี next hop ทั้งสามรายการ** นี่คือ ECMP ตัวจริง
   ตามที่ VNet ได้โปรแกรมไว้ — ไม่ใช่สิ่งที่ CE อ้าง แต่เป็นสิ่งที่ Azure ทำกับมัน

   ```bash
   az network nic show-effective-route-table \
     --name ar-ecmp-clientVMNic -g rg-mcn-ce-ha-rmordasiewicz \
     --query "value[?addressPrefix[0]=='10.250.0.10/32']" -o json
   ```

   ```json
   [
     {
       "addressPrefix": ["10.250.0.10/32"],
       "nextHopIpAddress": ["10.0.1.5", "10.0.1.4", "10.0.1.6"],
       "nextHopType": "VirtualNetworkGateway",
       "source": "VirtualNetworkGateway",
       "state": "Active"
     }
   ]
   ```

   `state: Active` พร้อมสามรายการใน `nextHopIpAddress` คือสิ่งที่ต้องตรวจสอบ **ลำดับของ
   ทั้งสามรายการนั้นไม่มีนัยสำคัญและไม่คงที่** — Azure คืนค่าในลำดับที่ต่างกัน
   ระหว่างการเรียกแต่ละครั้ง จึงควรนับจำนวนแทนที่จะเปรียบเทียบรายการกับการรันครั้งก่อน การมี
   next hop เพียงรายการเดียวในจุดที่คุณคาดว่าจะมีสามรายการหมายถึง CE หนึ่งตัวหยุดประกาศแล้ว และขั้นตอนที่ 2 จะระบุ
   ว่าตัวใด

4. **VIP ให้บริการทราฟฟิกได้** จาก VM ไคลเอนต์ และ **พร้อมส่วนหัว `Host`** — ดู
   กับดักที่สองด้านล่าง สุ่มตัวอย่างคำขอให้มากพอที่จะเห็นปัญหา: เพียงไม่กี่สิบคำขอจะอ่านได้เป็น
   100 % แม้ในช่วงเวลา convergence ที่อธิบายไว้ถัดลงไป

   ```bash
   az vm run-command invoke -g rg-mcn-ce-ha-rmordasiewicz -n ar-ecmp-client \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts 'ok=0; fail=0
                for i in $(seq 1 60); do
                  c=$(curl -s -o /dev/null -m 5 -w "%{http_code}" \
                        -H "Host: ar-bgp-ecmp.bankexample.com" http://10.250.0.10/)
                  [ "$c" = 200 ] && ok=$((ok+1)) || fail=$((fail+1))
                done
                echo "OK=$ok FAIL=$fail"'
   ```

   ```text
   OK=60 FAIL=0
   ```

</Steps>

## กับดัก: peering หนึ่งแสดงเส้นทางเดียว และนั่นถูกต้อง

`list-learned-routes` ถูกจำกัดขอบเขตอยู่ที่ peering ที่คุณระบุ มันรายงานสิ่งที่ peer **นั้น**
ประกาศ ไม่ใช่ตารางทั้งหมดของ Route Server

ดังนั้นการ query `eastus01-bgp` เพียงรายการเดียวจะคืนค่า `10.250.0.10/32` เดียวผ่าน `10.0.1.4` และ
เป็นเรื่องน่าหลงเชื่อว่าจะอ่านมันว่า "มี CE เพียงตัวเดียวที่ประกาศ — อีกสองตัวล่ม" ไม่มีอะไร
ล่ม การประกาศของอีกสองตัวมองเห็นได้บน peering ของตัวเอง ซึ่งเป็นสิ่งที่
ขั้นตอนที่ 2 ด้านบนวนลูปครอบคลุม

การยืนยัน ECMP จาก query ของ peering เดียวเป็นไปไม่ได้ ให้วนลูปทั้งสาม
peering หรืออ่านตารางเส้นทางที่มีผลบังคับใช้ของไคลเอนต์ ซึ่งแสดงผลลัพธ์ที่รวมกันแล้วในการเรียก
ครั้งเดียว

## กับดัก: คำขอด้วย IP เปล่าคืนค่า 404

Load balancer จับคู่ตาม `Host` VIP ไม่ใช่ virtual server ที่ให้บริการอะไรก็ได้
กับใครก็ตามที่เชื่อมต่อมาที่ที่อยู่นั้น

```text
curl -H 'Host: ar-bgp-ecmp.bankexample.com' http://10.250.0.10/   ->  200   (10 of 10)
curl                                        http://10.250.0.10/   ->  404
```

ทั้งสองรายการนั้นเกิดขึ้นในการรันเดียวกันกับการ deploy ที่สมบูรณ์ **404 จาก IP เปล่า
คือหลักฐานว่าเส้นทางใช้งานได้** — คำขอไปถึง CE พร็อกซีของ CE ตอบกลับ และ
มันปฏิเสธเพราะไม่มีโดเมนที่คอนฟิกไว้ตรงกัน การอ่านมันว่าเป็นเหตุขัดข้องจะทำให้คุณ
ไปดูที่ BGP ซึ่งคุณจะไม่พบสิ่งใดผิดปกติ

เช่นเดียวกันในระหว่างการสาธิต: หากคุณพิมพ์ที่อยู่ลงในเบราว์เซอร์แทนที่จะ
resolve โดเมนไปที่ที่อยู่นั้น คุณจะได้ 404

## VIP ทิ้งคำขอในช่วงสามในสี่ของชั่วโมงแรก แล้วก็หยุด

บนสแตกที่สร้างใหม่ VIP จะสูญเสียคำขอเป็นสัดส่วนเล็กน้อยในราว 45 นาทีแรก
หลังจาก CE ถึงสถานะ `ONLINE` แล้วหลังจากนั้นจะให้บริการได้อย่างสะอาด วัดจาก 1,470
คำขอจาก `ar-ecmp-client` ทั้งหมดพร้อมส่วนหัว `Host`:

| ช่วงเวลา | คำขอ | ความล้มเหลว | อัตรา |
| --- | --- | --- | --- |
| ~45 นาทีแรกหลัง ECMP ขึ้นทำงาน | 570 | 12 | **2.11 %** |
| 23 นาทีถัดมา | 900 | **0** | **0.00 %** |

ความล้มเหลวทุกครั้งเป็น `curl: (28)` — การหมดเวลาโดยได้รับข้อมูลศูนย์ไบต์ — ไม่ใช่สถานะข้อผิดพลาด HTTP
ครั้งสุดท้ายเกิดขึ้นราว 43 นาทีหลังจาก ECMP ขึ้นทำงาน จาก 900 คำขอที่สะอาดนั้น
400 คำขอรันด้วยการหมดเวลา 30 วินาที และทุกคำขอเสร็จภายในเวลาไม่ถึง 2 วินาที ดังนั้น
ไม่มีอะไรถูกซ่อนไว้ด้วยการหมดเวลาที่สั้นเกินไป

**ต้นทางไม่ใช่สาเหตุ** ชุดคำขอควบคุมที่ยิงตรงไปยังต้นทาง
(`http://20.98.232.135/`, ข้าม VIP) รันสะอาด 120 จาก 120 *พร้อมกับ*
ชุดคำขอ VIP ที่ล้มเหลว ความผิดพลาดอยู่ที่ใดที่หนึ่งในเส้นทาง VIP, ECMP หรือ CE

สองสิ่งที่จงใจไม่เรียกสิ่งนี้ว่า:

- **มันไม่ใช่ข้อบกพร่องในสภาวะคงตัว** มันหายไปโดยสมบูรณ์และคงสะอาดต่อไป การสาธิตที่
  เปิดใช้งานมาแล้วหนึ่งชั่วโมงจะไม่มีปัญหานี้ — 60 จาก 60 ในการตรวจสอบด้านบน และมัน
  สร้างซ้ำได้อย่างสะอาดอีกครั้งบนสแตกที่สร้างใหม่
- **มันไม่สามารถระบุได้ว่าเกิดจาก CE ตัวใดตัวหนึ่ง** ไม่มีอะไรในโทโพโลยีนี้ที่ให้ HTTP listener
  ต่อโหนด ดังนั้นจึงไม่มีวิธีผูกคำขอที่ถูกทิ้งกับโหนดที่ทิ้งมัน
  อินเทอร์เฟซภายนอกของ CE (`10.0.2.x`) ไม่มี HTTP listener เลย — มีเพียง VIP `/32`
  ที่ตอบสนอง

มันสร้างซ้ำได้บนการสร้างใหม่ที่สะอาดในเทนแนนต์อื่น ดังนั้นมันจึงติดตามโทโพโลยีมากกว่า
สภาพแวดล้อม

<Aside type="caution" title="อย่าสุ่มตัวอย่าง 40 คำขอแล้วสรุปว่าไม่มีปัญหา">
ชุด 40 ถึง 50 คำขออ่านได้เป็น 100 % เกือบทุกครั้ง แม้อยู่ในช่วงเวลาที่ล้มเหลว นั่นคือ
สาเหตุที่เรื่องนี้ถูกอธิบายผิดครั้งแรกว่าเป็นความผิดพลาดอัตราต่ำที่เกิดต่อเนื่อง และต่อมาว่าไม่มีความผิดพลาด
เลย จงสุ่มตัวอย่าง 100 คำขอหรือมากกว่า โดยแบ่งเป็นชุดที่เว้นระยะเวลากัน
</Aside>

## การอนุมัติการลงทะเบียนเป็นแบบอัตโนมัติ และการ apply ยังคงเป็นสองเฟส

การอนุมัติการลงทะเบียนไม่จำเป็นต้องมีมนุษย์ในคอนโซลอีกต่อไป บนโปรวายเดอร์ **v3.81.1**
รีซอร์ส `xcsh_registration_approval` ทำหน้าที่นี้ และโมดูลไซต์จะแก้ปัญหาว่าจะอนุมัติ
การลงทะเบียนใด

นั่นยังคงไม่ทำให้การ deploy เป็น `apply` แบบไม่ต้องแตะต้องเพียงครั้งเดียว และเหตุผลนั้น
ควรทำความเข้าใจก่อนที่คุณจะเฝ้าดูการรันครั้งแรกและสรุปว่ามันล้มเหลว:

- ออบเจ็กต์การลงทะเบียนของ CE ตั้งชื่อเป็น **`r-<uuid>`** มันไม่เคยตั้งชื่อตามไซต์ ดังนั้น
  ไม่มีอะไรสามารถทำนายชื่อได้ในเวลา plan
- การลงทะเบียนจะมีอยู่ก็หลังจาก VM บูตแล้วและ `vpm` ได้ลงทะเบียนแล้ว
- ดังนั้น **การ apply ครั้งแรกจะไม่ plan การอนุมัติใด ๆ เลย** ให้ apply ซ้ำอีกครั้งเมื่อ CE ลงทะเบียนแล้ว
  และการอนุมัติถูกสร้างขึ้น

`terraform/main.tf` บันทึกลำดับนี้ไว้ที่ส่วนต้นของไฟล์ ซึ่งเป็นเวอร์ชันที่
เชื่อถือได้ — ลำดับการ deploy อยู่ร่วมกับโค้ดที่นำมันไปปฏิบัติ

<Aside type="caution" title="ไซต์ใหม่ล่าสุดจะยังเข้าถึงไม่ได้ทันทีผ่าน operate API">
ราว 25 ถึง 30 นาทีหลังจากไซต์ใหม่รายงานสถานะ `ONLINE` ปลายทาง `vpm/debug`
จะตอบกลับด้วยหน้า `503` ของ BIG-IP ที่ระบุว่า `The requested URL was rejected` มันดูเหมือน
การบล็อกโดยไฟร์วอลล์แอปพลิเคชันเว็บหรือโทเคนที่ถูกเพิกถอน แต่ไม่ใช่ทั้งสองอย่าง จงรอ แล้วลองใหม่

เรื่องนี้ส่งผลกับการสาธิตที่สร้างใหม่ ไม่ใช่การสาธิตที่กำลังทำงานอยู่
</Aside>

## การเข้าถึง Site CLI

การวินิจฉัยบนเครื่องตามปกติทำผ่าน debug API ซึ่งมีสคริปต์ไว้แล้วที่นี่
ยืนยันว่าชุดคำสั่งยังตรงกับที่เอกสารอธิบายไว้:

```bash
bash scripts/capture-sitecli.sh --check --site ar-bgp-eastus01 --node f5-xc-ce-vm-01
```

```text
catalog matches the live CE (build crt-20250613-3382, 34 commands)
```

`--check` ไม่เขียนสิ่งใด จึงปลอดภัยต่อการสาธิตที่ใช้งานจริง

สำหรับคำสั่งที่ API นั้นไม่ได้ส่งต่อ การ deploy นี้ยังมี **SSH ของผู้ปฏิบัติงานไปยัง
บัญชี `admin` ของแอปพลายแอนซ์** ซึ่งเชลล์สำหรับล็อกอินของมันคือ Site CLI มีการยืนยันบน CE
ทั้งสามตัว เชื่อมต่อไปยังที่อยู่ภายใน (SLI) จากโฮสต์ที่อยู่ใน VNet โดยมีการ
จัดสรรเทอร์มินัล

<Aside type="danger" title="อย่าฮาร์ดโค้ดที่อยู่ภายในของ CE — มันจะถูกกำหนดใหม่ทุกครั้งที่สร้างใหม่">
Azure ไม่คงไว้ว่า CE ตัวใดได้ที่อยู่ใดในซับเน็ตภายใน หลังจากการสร้างใหม่
ครั้งล่าสุด `f5-xc-ce-vm-01`, `-02` และ `-03` ถือ `10.0.3.7`, `10.0.3.5` และ `10.0.3.4`
ตามลำดับ: ไม่ได้เรียงตามลำดับโหนด ไม่ต่อเนื่องกัน และต่างจากที่ถือไว้ก่อนหน้านี้
NIC ของไคลเอนต์ทดสอบเองก็อยู่ในซับเน็ตเดียวกันและเคยถือที่อยู่ที่ CE ถือไว้
ก่อนหน้านี้

ให้อ่านค่าเหล่านั้นแทนที่จะจดจำ:

```bash
cd terraform
terraform output -json ce_sli_private_ips
```

```json
{"eastus01":"10.0.3.7","eastus02":"10.0.3.5","eastus03":"10.0.3.4"}
```

หากไม่มี Terraform state อยู่ในมือ ให้ถาม Azure หาค่าที่คุณต้องการโดยใช้ชื่อ NIC ซึ่ง *มี*
ความคงที่:

```bash
az network nic show -g rg-mcn-ce-ha-rmordasiewicz \
  -n f5-xc-ce-vm-01-internal-nic \
  --query ipConfigurations[0].privateIPAddress -o tsv
```

</Aside>

SLI=$(terraform output -json ce_sli_private_ips | jq -r '.eastus01')

คีย์ของผู้ปฏิบัติงานถูกเขียนโดย `write_files` ของ cloud-init ซึ่งรันเพียงครั้งเดียวในการบูตครั้งแรก
`custom_data` เป็นแบบแทนที่เท่านั้น ดังนั้นการนำสิ่งนี้ไปใช้บน CE ที่กำลังทำงานอยู่แล้วจะ **แทนที่
CE VM ทุกตัว** นั่นคือการสร้างฟลีตใหม่ ไม่ใช่การเปลี่ยนคอนฟิเกอเรชัน

เคยแย่กว่านั้น: CE ที่ถูกแทนที่ไม่สามารถลงทะเบียนใหม่ได้เลย เพราะการลงทะเบียนของโหนด
ที่ถูกทำลายยังคงถือดัชนีเอกลักษณ์ `(tenant, cluster_name, hostname)` ของ control plane
— และ `terraform plan` รายงานว่า "No changes" ตลอดช่วงเวลาที่ฟลีตล่ม การกู้คืนต้องใช้การสร้างใหม่
สองรอบเต็ม เรื่องนี้ได้รับการแก้ไขแล้ว
([issue 674](https://github.com/f5-sales-demo/mcn/issues/674), ปิดโดย
[PR 693](https://github.com/f5-sales-demo/mcn/pull/693)): วงจรชีวิตของออบเจ็กต์ไซต์ตอนนี้
ผูกกับอินสแตนซ์ CE VM ดังนั้นการแทนที่ VM จะแทนที่ไซต์ และการลบไซต์
จะพาการลงทะเบียนของมันไปด้วยก่อนที่โหนดที่มาแทนจะบูต

สำหรับการ deploy นี้ การเปลี่ยนแปลงถูก apply แล้วและฟลีตมีสุขภาพดี ผู้ที่นำไปใช้
ที่อื่นควรอ่าน[หน้า SSH](../customer-edge/access/ssh/)ก่อน
</Aside>

## กับดักการวัดอีกสองข้อ

ทั้งสองข้อนี้ให้คำตอบที่ผิดแบบมั่นใจในสภาพแวดล้อมนี้ และไม่มีข้อใดที่
ชัดเจนในตัวเอง

- **ตรวจสอบจากภายใน VNet ไม่ใช่จากเวิร์กสเตชันของคุณ** Netskope ทำ TCP
  handshake ให้เองบนพอร์ตทั่วไป ดังนั้นการตรวจสอบจากเวิร์กสเตชันจะรายงานว่าพอร์ต **เปิด** ในขณะที่
  จริง ๆ ปิดอยู่ พอร์ต 80 และ 443 อ่านว่าเปิดบนที่อยู่สาธารณะของ CE เมื่อตรวจจาก
  เวิร์กสเตชัน และปิดเมื่อตรวจจากภายใน VNet จงใช้ `ar-ecmp-client`
- **พอร์ต 22 บน CE ตอบสนองเฉพาะบนที่อยู่ภายใน (SLI) เท่านั้น** เมื่อตรวจจาก
  `ar-ecmp-client` ที่อยู่ภายในของ CE แต่ละตัวคืนค่า `SSH-2.0-OpenSSH_8.7` ขณะที่ที่อยู่
  management และ external หมดเวลา — เช่นเดียวกับที่อยู่ที่ไม่ได้ใช้ซึ่งใช้เป็นตัวควบคุม
  eth0 ถูกเปลี่ยนชื่อเป็น `a-i-eth0` และไม่มี host IP เพราะ datapath เป็นเจ้าของมัน ดังนั้นการ
  ตรวจสอบที่อยู่ที่คุณรู้จักโหนดจะไม่บอกอะไรคุณเลยเกี่ยวกับสถานะ SSH ของโหนด และ
  ที่อยู่ SLI คือที่อยู่ที่ต้องเชื่อมต่อ ให้นำที่อยู่นั้นมาจาก
  `terraform output -json ce_sli_private_ips`; อย่าสมมติว่าซับเน็ตภายในมีแต่
  CE เท่านั้น เพราะ NIC ของไคลเอนต์ทดสอบก็อยู่ในนั้นด้วย

<Aside type="note" title="สิ่งที่หน้านี้ไม่ได้อ้าง">
มีสามสิ่งที่ผู้อ่านอาจคาดหวังอย่างสมเหตุสมผลว่าจะพบที่นี่แต่ไม่มี เพราะไม่ได้ถูก
ทดลองกับการ deploy นี้:

- **ยังไม่ได้ทดสอบ failover** next hop ที่มีต้นทุนเท่ากันทั้งสามได้รับการยืนยันว่าติดตั้งแล้ว แต่สิ่งที่
  เกิดขึ้นกับตารางเส้นทางเมื่อ CE ถูกหยุดนั้นไม่ได้แสดงไว้ ดังนั้นอย่าซ้อมการสาธิต
  failover จากหน้านี้โดยไม่ได้ลองก่อน
- **ยังไม่ได้วัดการกระจายทราฟฟิกไปยัง next hop ทั้งสาม** 1,470 คำขอไปยัง
  VIP ถูกบันทึกไว้ด้านบน ซึ่งยืนยันว่าเส้นทางใช้งานได้และมีพฤติกรรมอย่างไร
  ตามเวลาที่ผ่านไป แต่ไม่มีสิ่งใดในนั้นแสดงว่าคำขอเหล่านั้นถูกกระจายไปยัง next hop ทั้งสามอย่างไร
  และโทโพโลยีนี้ไม่มี HTTP listener ต่อโหนดที่จะใช้ระบุที่มาของคำขอได้
- **ยังไม่ได้ระบุสาเหตุของอาการชั่วคราวช่วง convergence** มันถูกอธิบายลักษณะไว้ — เมื่อใด
  ที่เกิดขึ้น นานเท่าใด และว่าต้นทางสะอาดตลอด — แต่ไม่ได้อธิบายสาเหตุ

</Aside>
