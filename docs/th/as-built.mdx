การปรับใช้นี้สาธิต **ความพร้อมใช้งานสูงของ Customer Edge แบบ active/active ใน Azure**
โดยไม่มี Azure load balancer อยู่หน้า CE ทั้งสาม CE แต่ละตัวประกาศ host route
เดียวกันด้วย eBGP และ Azure Route Server ติดตั้งทั้งสามเป็น next hop ที่มีต้นทุนเท่ากันใน
VNet ดังนั้นโครงสร้างการกำหนดเส้นทาง ไม่ใช่ load balancer จึงเป็นจุดที่การกระจายทราฟฟิก
และการถอดโหนดที่ล้มเหลวออกควรเกิดขึ้น

ทุกอย่างที่แสดงด้านล่างถูกรันกับการปรับใช้จริง และผลลัพธ์ที่แสดงคือผลลัพธ์ที่ระบบ
สร้างขึ้นจริง สองสิ่งที่ประโยคนั้น *ไม่* ครอบคลุม — การสลับการทำงาน (failover) และการกระจายทราฟฟิก —
ถูกระบุไว้ตอนท้ายแทนที่จะปล่อยให้สันนิษฐานเอง

## สิ่งที่ถูกปรับใช้

```text
                  Azure Route Server  ce-ha-lab-rrs  ASN 65515
                          10.0.4.4  and  10.0.4.5
                                      |
              +-----------------------+-----------------------+
              |                       |                       |
        eastus01-bgp            eastus02-bgp            eastus03-bgp     eBGP
              |                       |                       |      CE ASN 64512
        10.0.1.4                10.0.1.5                10.0.1.6     <- CE eth0 / SLO
     f5-xc-ce-vm-01          f5-xc-ce-vm-02          f5-xc-ce-vm-03
    ar-bgp-eastus01         ar-bgp-eastus02         ar-bgp-eastus03
              |                       |                       |
              +----- each advertises 10.250.0.10/32 -----------+
                          three-way ECMP into the VNet
```

| ส่วนประกอบ | ตามที่สร้างจริง |
| --- | --- |
| Customer Edge | ไซต์ Secure Mesh v2 แบบโหนดเดียว 3 ไซต์ — `ar-bgp-eastus01`, `ar-bgp-eastus02`, `ar-bgp-eastus03` |
| ซอฟต์แวร์ CE | ตรึงไว้ที่ `9.2024.6`, build `crt-20250613-3382` |
| Azure VM | `f5-xc-ce-vm-01/02/03`, มี NIC สามตัวต่อเครื่อง (management/SLO, external, internal/SLI) |
| การแลกเปลี่ยนเส้นทาง | Azure Route Server `ce-ha-lab-rrs`, ASN `65515`, อินสแตนซ์ `10.0.4.4` และ `10.0.4.5` |
| Peering | หนึ่งรายการต่อ CE — `eastus01-bgp`, `eastus02-bgp`, `eastus03-bgp` — CE ASN `64512` |
| VIP ที่ประกาศ | `10.250.0.10/32` ประกาศเหมือนกันโดย CE ทั้งสามตัว |
| Load balancer | `ar-bgp-ecmp-lb`, ให้บริการโดเมน `ar-bgp-ecmp.bankexample.com` |
| ไคลเอนต์ทดสอบ | `ar-ecmp-client`, VM ที่อยู่ภายใน VNet เดียวกัน |
| Resource group | `rg-mcn-ce-ha-rmordasiewicz` |

<Aside type="caution" title="VIP ต้องอยู่นอก CIDR ของทุก VNet">
`terraform/main.tf` มีบล็อก `check` ที่ยืนยันว่า VIP อยู่นอก CIDR ของทั้ง hub
และ spoke และจะปฏิเสธแผนหากไม่เป็นเช่นนั้น เหตุผลที่ระบุไว้คือ VIP ที่อยู่ภายใน
CIDR ของ VNet จะแพ้ให้กับ system route ของ VNet เอง แม้ว่า BGP route จะเจาะจงกว่าก็ตาม

ให้ถือว่าการป้องกันนี้เป็นข้อสัญญา: ถ้าคุณเปลี่ยนการสาธิตนี้ไปใช้การกำหนดที่อยู่แบบอื่น
VIP ต้องย้ายออกไปนอกช่วง VNet ตามไปด้วย
</Aside>

## พิสูจน์ว่าระบบสมบูรณ์ก่อนที่คุณจะนำเสนอ

การตรวจสอบสี่ข้อ ตามลำดับนี้ แต่ละข้อจะจำกัดขอบเขตว่าความผิดพลาดอยู่ที่ใด ดังนั้นความล้มเหลว
จะบอกอะไรคุณได้ ไม่ใช่เพียงบอกว่ามีอะไรผิดพลาด

<Steps>

1. **ไซต์ทั้งสามอยู่ในสถานะ `ONLINE`** ไม่มีสิ่งใดที่ตามมาจะเป็นจริงได้หากข้อนี้ไม่เป็นจริง

   ```bash
   for s in ar-bgp-eastus01 ar-bgp-eastus02 ar-bgp-eastus03; do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **ทุก peering กำลังเรียนรู้การประกาศ VIP ของ CE นั้น** สอบถามแต่ละ peering
   แยกกัน — ดูกับดักด้านล่าง เพราะนี่คือจุดที่การสาธิตมักดูเหมือน
   เสียหายแต่จริง ๆ ไม่ใช่

   ```bash
   for p in eastus01-bgp eastus02-bgp eastus03-bgp; do
     echo "--- $p"
     az network routeserver peering list-learned-routes \
       --name "$p" --routeserver ce-ha-lab-rrs -g rg-mcn-ce-ha-rmordasiewicz \
       --query "RouteServiceRole_IN_0[].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp

   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp

   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   สาม peering, สาม next hop ที่แตกต่างกัน, หนึ่ง prefix นั่นคือด้านการประกาศ
   ของ ECMP ที่พิสูจน์แล้ว

3. **เส้นทางที่มีผลของไคลเอนต์บรรจุ next hop ทั้งสามรายการ** นี่คือ ECMP ตัวจริง
   ตามที่ VNet ได้โปรแกรมไว้ — ไม่ใช่สิ่งที่ CE อ้าง แต่เป็นสิ่งที่ Azure ทำกับมัน

   ```bash
   az network nic show-effective-route-table \
     --name ar-ecmp-clientVMNic -g rg-mcn-ce-ha-rmordasiewicz \
     --query "value[?addressPrefix[0]=='10.250.0.10/32']" -o json
   ```

   ```json
   [
     {
       "addressPrefix": ["10.250.0.10/32"],
       "nextHopIpAddress": ["10.0.1.5", "10.0.1.4", "10.0.1.6"],
       "nextHopType": "VirtualNetworkGateway",
       "source": "VirtualNetworkGateway",
       "state": "Active"
     }
   ]
   ```

   `state: Active` พร้อมกับสามรายการใน `nextHopIpAddress` คือสิ่งที่ต้องตรวจสอบ หากมี next hop
   เพียงรายการเดียวในจุดที่คุณคาดว่าจะมีสาม หมายความว่า CE ตัวหนึ่งหยุดประกาศแล้ว และขั้นที่ 2 จะระบุว่าตัวใด

4. **VIP ให้บริการทราฟฟิก** จาก VM ไคลเอนต์ และ **พร้อมกับส่วนหัว `Host`** — ดู
   กับดักที่สองด้านล่าง

   ```bash
   az vm run-command invoke -g rg-mcn-ce-ha-rmordasiewicz -n ar-ecmp-client \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts 'for i in $(seq 1 10); do
                  curl -s -o /dev/null -w "%{http_code} " \
                    -H "Host: ar-bgp-ecmp.bankexample.com" http://10.250.0.10/
                done'
   ```

   ```text
   200 200 200 200 200 200 200 200 200 200
   ```

</Steps>

## กับดัก: peering หนึ่งรายการแสดงเส้นทางเพียงหนึ่งเส้น และนั่นถูกต้อง

`list-learned-routes` มีขอบเขตจำกัดอยู่ที่ peering ที่คุณระบุชื่อ มันรายงานสิ่งที่ peer **นั้น**
ประกาศ ไม่ใช่ตารางทั้งหมดของ Route Server

ดังนั้นการสอบถาม `eastus01-bgp` เพียงลำพังจะคืนค่า `10.250.0.10/32` รายการเดียวผ่าน `10.0.1.4` และมัน
ชวนให้อ่านว่า "มี CE เพียงตัวเดียวที่ประกาศ — อีกสองตัวล่มแล้ว" แต่ไม่มีอะไร
ล่มเลย การประกาศของอีกสองตัวมองเห็นได้บน peering ของตัวเอง ซึ่งเป็นสิ่งที่
ขั้นที่ 2 ด้านบนวนตรวจสอบ

การยืนยัน ECMP จากการสอบถาม peering เพียงรายการเดียวนั้นทำไม่ได้ ให้วนตรวจ peering ทั้งสาม
หรืออ่านตารางเส้นทางที่มีผลของไคลเอนต์ ซึ่งแสดงผลลัพธ์ที่รวมกันแล้วในการเรียกเพียงครั้งเดียว

## กับดัก: คำขอด้วย IP เปล่าคืนค่า 404

Load balancer จับคู่ตาม `Host` VIP ไม่ใช่ virtual server ที่ให้บริการอะไรก็ได้
กับใครก็ตามที่เชื่อมต่อมาที่ที่อยู่นั้น

```text
curl -H 'Host: ar-bgp-ecmp.bankexample.com' http://10.250.0.10/   ->  200   (10 of 10)
curl                                        http://10.250.0.10/   ->  404
```

ทั้งสองรายการนั้นเกิดขึ้นในการรันเดียวกันกับการปรับใช้ที่สมบูรณ์ **404 จาก IP เปล่า
คือหลักฐานว่าเส้นทางทำงานได้** — คำขอไปถึง CE, พร็อกซีของ CE ตอบกลับ และ
มันปฏิเสธเพราะไม่มีโดเมนที่กำหนดค่าไว้ตรงกัน การอ่านว่านี่เป็นเหตุขัดข้องจะทำให้คุณ
ไปมองหาที่ BGP ซึ่งคุณจะไม่พบสิ่งใดผิดพลาด

เช่นเดียวกันในระหว่างการสาธิต: หากคุณพิมพ์ที่อยู่ลงในเบราว์เซอร์แทนที่จะ
แปลงชื่อโดเมนไปยังที่อยู่นั้น คุณจะได้ 404

## การอนุมัติการลงทะเบียนเป็นแบบอัตโนมัติ และการ apply ยังคงมีสองระยะ

การอนุมัติการลงทะเบียนไม่จำเป็นต้องมีคนอยู่ในคอนโซลอีกต่อไป บน provider **v3.81.1**
ทรัพยากร `xcsh_registration_approval` ดำเนินการนี้ และโมดูลไซต์จะระบุว่าควรอนุมัติ
การลงทะเบียนรายการใด

สิ่งนั้นยังไม่ทำให้การปรับใช้เป็น `apply` แบบไม่ต้องแตะต้องเพียงครั้งเดียว และเหตุผลนั้น
ควรเข้าใจก่อนที่คุณจะเฝ้าดูการรันครั้งแรกและสรุปว่ามันล้มเหลว:

- ออบเจ็กต์การลงทะเบียนของ CE จะมีชื่อว่า **`r-<uuid>`** มันไม่เคยถูกตั้งชื่อตามไซต์ ดังนั้น
  จึงไม่มีสิ่งใดคาดเดาชื่อได้ในเวลาที่วางแผน
- การลงทะเบียนจะมีอยู่หลังจาก VM บูตแล้วและ `vpm` ได้ลงทะเบียนแล้วเท่านั้น
- ดังนั้น **การ apply ครั้งแรกจะไม่วางแผนการอนุมัติใด ๆ เลย** ให้ apply อีกครั้งเมื่อ CE ลงทะเบียนแล้ว
  และการอนุมัติถูกสร้างขึ้น

`terraform/main.tf` บันทึกลำดับนี้ไว้ที่ส่วนบนของไฟล์ ซึ่งเป็นเวอร์ชัน
ที่ถือเป็นหลักฐานอ้างอิง — ลำดับการปรับใช้อยู่ร่วมกับโค้ดที่นำไปปฏิบัติ

<Aside type="caution" title="ไซต์ที่สร้างใหม่ยังไม่สามารถเข้าถึงได้ทันทีผ่าน operate API">
ประมาณ 25 ถึง 30 นาทีหลังจากไซต์ใหม่รายงานสถานะ `ONLINE` ปลายทาง `vpm/debug`
จะตอบด้วยหน้า `503` ของ BIG-IP ที่ระบุว่า `The requested URL was rejected` ซึ่งดูเหมือน
การบล็อกจากไฟร์วอลล์แอปเว็บ (WAF) หรือโทเค็นที่ถูกเพิกถอน แต่ไม่ใช่ทั้งสองอย่าง ให้รอ แล้วลองใหม่

สิ่งนี้ส่งผลกับการสาธิตที่สร้างขึ้นใหม่ ไม่ใช่การสาธิตที่กำลังทำงานอยู่
</Aside>

```bash
bash scripts/capture-sitecli.sh --check --site ar-bgp-eastus01 --node f5-xc-ce-vm-01
```

```text
catalog matches the live CE (build crt-20250613-3382, 34 commands)
```

## กับดักการวัดอีกสองรายการ

ทั้งสองรายการนี้ให้คำตอบที่ผิดอย่างมั่นใจในสภาพแวดล้อมนี้ และไม่มีรายการใด
ที่เห็นได้ชัดเจน

- **ตรวจสอบจากภายใน VNet ไม่ใช่จากเครื่องทำงานของคุณ** Netskope ทำ TCP handshake
  ให้เสร็จด้วยตัวเองบนพอร์ตทั่วไป ดังนั้นการตรวจสอบจากเครื่องทำงานจะรายงานว่าพอร์ต **เปิด**
  แม้ว่าจริง ๆ จะปิดอยู่ พอร์ต 80 และ 443 อ่านได้ว่าเปิดบนที่อยู่สาธารณะของ CE เมื่อดูจาก
  เครื่องทำงาน แต่ปิดอยู่เมื่อตรวจสอบจากภายใน VNet ให้ใช้ `ar-ecmp-client`
- **พอร์ต 22 บน CE ตอบสนองเฉพาะบนที่อยู่ภายใน (SLI) เท่านั้น** เมื่อตรวจสอบจาก
  `ar-ecmp-client` ไปยัง CE ทั้งสามตัว `10.0.3.5`, `10.0.3.6` และ `10.0.3.7` ทั้งหมดคืนค่า
  `SSH-2.0-OpenSSH_8.7` ขณะที่ที่อยู่ management และ external หมดเวลา — เช่นเดียวกับ
  ที่อยู่ที่ไม่ได้ใช้งานซึ่งใช้เป็นตัวควบคุม ดังนั้นการตรวจสอบที่อยู่ที่คุณรู้จักโหนดนั้น
  จะไม่บอกอะไรคุณเลยเกี่ยวกับสถานะ SSH ของโหนด

สองสิ่งที่ผู้อ่านอาจคาดหวังได้อย่างสมเหตุสมผลจากที่นี่ถูกละไว้อย่างตั้งใจ เพราะยังไม่ได้
ทดลองกับการปรับใช้:

- **ยังไม่ได้ทดสอบการสลับการทำงาน (failover)** next hop ที่มีต้นทุนเท่ากันทั้งสามรายการได้รับการยืนยันว่าติดตั้งแล้ว
  แต่สิ่งที่เกิดขึ้นกับตารางเส้นทางเมื่อ CE ถูกหยุดนั้นไม่ได้แสดงไว้ ดังนั้นอย่าซ้อม
  การสาธิต failover จากหน้านี้โดยไม่ได้ทดลองก่อน
- **ยังไม่ได้วัดการกระจายทราฟฟิก** คำขอสิบในสิบรายการไปยัง VIP คืนค่า `200`
  ซึ่งพิสูจน์ว่าเส้นทางทำงานได้ แต่มันไม่แสดงว่าสิบรายการนั้นถูกกระจายไปยัง next hop
  ทั้งสามรายการอย่างไร

</Aside>
