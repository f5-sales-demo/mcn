Two Terraform variables set a Customer Edge's software: `ce_os_version` for the operating
system and `ce_sw_version` for the F5 Distributed Cloud build. Both behave in ways that are the
opposite of the obvious reading — an empty field gets you the newest build rather than none,
and a version that installs on one node can fail on an identical one with a smaller disk.

## What the version fields do, in two phases

Separating the phases is the whole subject. Conflated, the behaviour reads as
self-contradictory.

**On first boot, a node installs whatever `ce_sw_version` names.**
`terraform/modules/ce-node` deploys the marketplace image with `version = "latest"`, so the
build a node arrives with is whatever that image currently ships — and that moves over time.
`ce_sw_version` chooses the **destination**, not whether anything happens, and leaving it
empty means the server chooses rather than that the node stays put. The same holds for
`ce_os_version`.

Do not assume the direction of that change is upwards. `Observed 2026-07-28`, the image
shipped a build stamped `20260703-e2c462a` — newer than this fleet's `crt-20250613-3382` and
newer than the `crt-20260201-0179` the tenant was advertising. Naming an older build than the
image carries asks the node to move backwards, and that is routine: this fleet was created
that way and is running.

**Leaving a version field empty is the riskiest choice, not the neutral one.** At create the
server does not leave an empty field alone — it fills it with the **newest advertised**
version and installs that. A site created with both fields unset came back pinned to
`crt-20260201-0179` and OS `9.2026.14`, the two versions the tenant was advertising, and the
install then failed. `Observed 2026-07-29`.

There are two consequences. Empty means "give me the newest", so an unpinned deployment is the
one most likely to meet the disk limit described below. And you cannot isolate one field by
leaving the other empty, because the server fills it — set both, deliberately, or accept the
newest of each.

**After first boot, nothing upgrades on its own.** F5 Distributed Cloud advertises a newer
build and waits. That is where "the node stays where it landed" holds — after the create, not
during it.

Both phases are visible on the site object. `Observed 2026-07-28`, this fleet:

```text
volterra_software_status.available_version   crt-20260201-0179
operating_system_status.available_version    9.2026.14
```

while the nodes run `crt-20250613-3382` and OS `9.2024.6`. A newer build is on offer and has
not been taken — the steady state, not a stalled upgrade.

## Terraform cannot change a version. The API can

These are two separate facts, and conflating them produces the wrong plan.

**Terraform cannot.** `ce_os_version` and `ce_sw_version` are effectively create-time only.
Change either and apply, and the API rejects the update with
`[BAD_REQUEST] Invalid request parameters`. `Observed 2026-07-29` on disposable sites, in all
three directions — pinning **forward** to a newer build, pinning **backward** to an older one,
and **un-pinning** by clearing both fields. Forward is not a special case.

**The API can.** F5 Distributed Cloud exposes a dedicated upgrade action per site, which
starts the change in place — no rebuild, and no Terraform involvement:

```bash
# software build
curl -X POST -H "Authorization: APIToken $TOKEN" -H 'Content-Type: application/json' \
  --data '{"version": "<software-version>"}' \
  "$API_URL/api/config/namespaces/system/sites/<site-name>/upgrade_sw"

# operating system
curl -X POST -H "Authorization: APIToken $TOKEN" -H 'Content-Type: application/json' \
  --data '{"version": "<os-version>"}' \
  "$API_URL/api/config/namespaces/system/sites/<site-name>/upgrade_os"
```

`Observed 2026-07-29`: the software call returned `200`, the site moved to `UPGRADING` with
`deployment_state.phase` `UPGRADE_IN_PROGRESS`, and the site object's requested version changed
to the one posted. Omitting the field returns `400` with `version empty in the request`, which
is how the field name was confirmed.

**Budget hours, not minutes, and do not panic at a failure.** On a default-disk node the
upgrade to `crt-20260201-0179` ran for roughly an hour, reported `UPGRADE_FAILED` with
`result` `Failed` part-way through, and then **completed successfully** on the new build. The
platform retries.

That has a direct consequence for anyone watching an upgrade, or scripting one: a `Failed`
result is a state to wait through, not a verdict. Treating the first one as final reports a
failure for an upgrade that is going to succeed.

Note the group in that path: these live under **`config`**, not `operate`. The same paths under
`operate` return `404 API Group could not be determined`, which is a routing message and not a
statement that no upgrade exists — a distinction that cost this project a wrong conclusion.

<Aside type="caution" title="Upgrading through the API puts Terraform out of step">
The pinned variables still say what they always said, so the live site now runs a version the
configuration does not name. Terraform will not reconcile it — it cannot, since the update is
rejected — so treat an API upgrade as a deliberate step out of Terraform's control, and update
the pins to match at the next rebuild.
</Aside>

<Aside type="note" title="Two earlier claims on this page, withdrawn">
This page previously said that moving a CE to a different version means recreating the site,
and that a rejected update "still clears the field on the server" leaving Terraform proposing a
failing change forever. Neither survived testing: the API upgrade above starts a version change in
place, without recreating anything, and after each of the three rejected updates the site's spec
was **unchanged** and the site stayed `ONLINE`. The divergence described in provider issue `xcsh#1387` was observed on a
site that had already auto-upgraded past its pin, so it may need that divergent starting state;
it was not reproduced on a site whose spec matched its pin.
</Aside>

If you do rebuild rather than upgrade, every consequence of replacing a CE applies.

<Aside type="danger" title="Every consequence of replacing a CE applies">
New SSH host keys, reassigned internal addresses, a fresh registration, and the loss of
anything that lived only on the node. Cloud-init runs again on the new VM, so SSH access
configured that way survives — but it runs *only* on first boot, so anything added to the old
node by hand is gone.

Read [SSH](./access/ssh/) on the host-key and address consequences before scheduling this.
</Aside>

## A pinned build can fail to install, and the site is then stuck

Accepting the pin is not the same as installing it. On a freshly created single-node Azure
Secure Mesh v2 Customer Edge pinned to `crt-20260201-0179`, the site object reported the
pinned version immediately — and the install then failed:

```text
site_state        PROVISIONING
phase             UPGRADE_FAILED
result            Failed
last_installed    (empty)
message           stage: 10, app: voucher obj: voucher objKind: DaemonSet failed ...
                  required replicas: 1, current replicas: 0
```

`Observed 2026-07-28`, and reproduced twice on 2026-07-29. The **operating system** pin
installed normally in the same run (`9.2024.6` to `9.2026.14`, `UPGRADE_COMPLETED`); only the
software install failed. The site never reached `ONLINE` and `last_installed_version` stayed
empty, so nothing rolled back to a working build — there was no earlier successful install to
roll back to.

**A failure at create is not like a failure during an upgrade.** The two behave differently and
the difference matters when you are deciding whether to intervene:

| | at create | during an API upgrade |
| --- | --- | --- |
| does it retry into success? | no — held `Failed` for over 20 minutes, twice | yes — recovered and completed |
| where does the node end up? | `PROVISIONING`, nothing installed | `ONLINE` on a working build |
| is it safe to leave? | no, it is stuck | yes, it recovers or keeps the old build |

So a create-time failure needs a rebuild with a bigger disk, while an upgrade reporting `Failed`
should be left alone for a while before you conclude anything.

**The cause is the disk, not the version.** A matrix of software × OS × disk size, one
disposable single-node Azure Secure Mesh v2 site per combination and all from the same
marketplace image, isolates it. `Observed 2026-07-29`:

| software | OS `9.2024.6` (what the image ships) | OS `9.2026.14` |
| --- | --- | --- |
| `crt-20250613-3382` | installs | installs |
| `crt-20260201-0179` | installs | **fails**, on the default disk only |

Neither version fails on its own. Only the pair does, and only on the image's default disk —
the same pair installs on **33 GB** and every larger size tested. So the newer build is not
unsupported here, and neither is the newer operating system; together they need slightly more
disk than a default node has.

`terraform/modules/ce-node` sets no `disk_size_gb`, so every Customer Edge gets the image
default — the one size on which this pair fails. **To run it, enlarge the disk.**

The margin is the surprising part, and it is why this looked like a version problem for so long.
The default is **31 GiB** (the `health` command reports `size_gb: 31`, and `/var` is 29 G with
3.5 G free on a node in the failing state). **33 GB installs cleanly.** So the default is short
by roughly two gigabytes, not by a wide margin.

<Aside type="caution" title="Do not set the measured minimum">
33 GB is the smallest size observed to work — for this version pair, on this image, today. A
build with a slightly larger payload would fail again at 33 GB with no configuration change and
no obvious cause, exactly as the default does now. Choose headroom over the floor: the sizes
verified here are 33, 36, 40, 48 and 64 GB, and the cost of the larger ones is a few gigabytes of
managed disk.
</Aside>

Test a version change on a disposable site before applying it to a fleet regardless: a fleet
that fails this way is stuck in `PROVISIONING` with recreation as the only exit.

<Aside type="caution" title="Do not size the disk from F5's pre-upgrade figure">
F5's documented pre-upgrade check wants 20 GB plus 15% of capacity free. That check gates
**Console UI** upgrades and explicitly does not apply to API-initiated ones, so it does not
describe this failure. Applied here it predicts a 48 GB disk would fail; 48 GB installs
cleanly. Size from the measured outcomes above, not from that formula.
</Aside>

<Aside type="note" title="An explanation this page previously offered, now withdrawn">
An earlier version of this page suggested the install failed because the requested build was
older than the image's — that the node was asked to move backwards. That is wrong. This
fleet was created from the same image with a pin **thirteen months** older and installed
normally, and `crt-20260201-0179` installs too when the OS pin is left at the image's own
version. Direction of travel is not the variable.
</Aside>

## Which build the documentation describes

The command reference on this site describes **`crt-20250613-3382`**, the build this fleet
runs. Commands that exist only on newer builds are recorded in
`sitecli/command-classification.json` under `not_on_this_build` and documented separately, as
[commands on newer builds](./commands/on-box/newer-builds/), so nothing there reads as
runnable here. See also [on-box commands](./commands/on-box/).

<Aside type="note" title="Reaching a newer build is settled, and it is not a rebuild">
This was previously recorded here as unsettled, with a report of the newer build failing on
single-node Azure Secure Mesh v2 sites against a counter-observation of one running it. Both
are now explained: the newer build installs on that topology, and the failure was the disk
limit above, not the build.

So there are two routes and neither requires a rebuild for its own sake — create a node with a
large enough disk, or upgrade an existing one through the API. `Observed 2026-07-29`.
</Aside>
