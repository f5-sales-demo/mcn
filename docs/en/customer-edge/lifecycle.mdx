Two Terraform variables set a Customer Edge's software: `ce_os_version` for the operating
system and `ce_sw_version` for the F5 Distributed Cloud build. Both behave in ways that are
the opposite of the obvious reading, and the cost of getting it wrong is a fleet rebuild.

## What the version fields do, in two phases

Separating the phases is the whole subject. Conflated, the behaviour reads as
self-contradictory.

**On first boot, a node installs whatever `ce_sw_version` names.**
`terraform/modules/ce-node` deploys the marketplace image with `version = "latest"`, so the
build a node arrives with is whatever that image currently ships — and that moves over time.
`ce_sw_version` chooses the **destination**, not whether anything happens, and leaving it
empty means the server chooses rather than that the node stays put. The same holds for
`ce_os_version`.

Do not assume the direction of that change is upwards. `Observed 2026-07-28`, the image
shipped a build stamped `20260703-e2c462a` — newer than this fleet's `crt-20250613-3382` and
newer than the `crt-20260201-0179` the tenant was advertising. **Naming an older build than
the image carries asks the node to go backwards, and that can fail** — see the failure below.

**After that, nothing upgrades on its own.** F5 Distributed Cloud advertises a newer build and
waits. An empty field is therefore not "track latest": the node stays where it first landed.

Both phases are visible on the site object. `Observed 2026-07-28`, this fleet:

```text
volterra_software_status.available_version   crt-20260201-0179
operating_system_status.available_version    9.2026.14
```

while the nodes run `crt-20250613-3382` and OS `9.2024.6`. A newer build is on offer and has
not been taken — the steady state, not a stalled upgrade.

## Changing a version needs a rebuild, and Terraform will not do it for you

`ce_os_version` and `ce_sw_version` are both **create-time only**, and the failure mode is
worse than a rejected apply. In order:

1. You change the value and apply. Terraform proposes an in-place update.
2. The API **rejects** it — `[BAD_REQUEST] Invalid request parameters`.
3. That rejected request still clears the field on the server, and the provider's read does
   not report it. Terraform's state now disagrees with the live object.
4. Every subsequent plan proposes **the same failing change**, indefinitely.

So Terraform does not fall back to replacing the site. It gets stuck, and it stays stuck
until you replace the site and its CE virtual machine deliberately. Moving a fleet to a
different version is a **rebuild you plan**, not an edit you apply.

<Aside type="danger" title="Every consequence of replacing a CE applies">
New SSH host keys, reassigned internal addresses, a fresh registration, and the loss of
anything that lived only on the node. Cloud-init runs again on the new VM, so SSH access
configured that way survives — but it runs *only* on first boot, so anything added to the old
node by hand is gone.

Read [SSH](./access/ssh/) on the host-key and address consequences before scheduling this.
</Aside>

<Aside type="note" title="Reported, not reproduced here">
The rejection and the state divergence are recorded in this repository's own
`terraform/modules/xc-site` comments — verified there in both directions, pinning and
unpinning, on all three sites — and against provider issue `xcsh#1387`. This page has not
re-tested it, because the test leaves the deployment proposing a failing change on every
plan.
</Aside>

## A pinned build can fail to install, and the site is then stuck

Accepting the pin is not the same as installing it. On a freshly created single-node Azure
Secure Mesh v2 Customer Edge pinned to `crt-20260201-0179`, the site object reported the
pinned version immediately — and the install then failed:

```text
site_state        PROVISIONING
phase             UPGRADE_FAILED
result            Failed
last_installed    (empty)
message           stage: 10, app: voucher obj: voucher objKind: DaemonSet failed ...
                  required replicas: 1, current replicas: 0
```

`Observed 2026-07-28.` The **operating system** pin installed normally in the same run
(`9.2024.6` to `9.2026.14`, `UPGRADE_COMPLETED`); only the software install failed. The site
never reached `ONLINE` and `last_installed_version` stayed empty, so nothing rolled back to a
working build — there was no earlier successful install to roll back to.

**What to take from this.** A version that runs elsewhere is not evidence it installs on your
site's shape. The same build was `ONLINE` on an Azure Customer Edge that was not Secure Mesh
v2, and on a Secure Mesh v2 site on VMware; the combination that failed was Azure *and*
Secure Mesh v2. Test a version change on a disposable site before applying it to a fleet,
because a fleet that fails this way is stuck in `PROVISIONING` with recreation as the only
exit.

<Aside type="caution" title="Why this page does not tell you the cause">
The requested build was **older** than the one the marketplace image shipped, so the node was
asked to move backwards. That is a plausible explanation for the failure and it is **not**
established: the two version strings (`20260703-e2c462a` and `crt-20260201-0179`) are not
known to share a numbering scheme, and no capture from a fleet node was available to compare.
The failure and the version ordering are observations; the link between them is not.
</Aside>

## Which build the documentation describes

The command reference on this site describes **`crt-20250613-3382`**, the build this fleet
runs. Commands that exist only on newer builds are recorded in
`sitecli/command-classification.json` under `not_on_this_build` and documented separately, as
[commands on newer builds](./commands/on-box/newer-builds/), so nothing there reads as
runnable here. See also [on-box commands](./commands/on-box/).

<Aside type="caution" title="Do not plan a rebuild in order to reach newer commands">
A newer build is on offer, and whether it installs cleanly on this topology is unsettled —
there is a report of it failing on single-node Azure Secure Mesh v2 sites, and a
counter-observation of a Customer Edge running it. Neither can be confirmed from what remains
in the tenant.

Since a version change is a fleet rebuild, that uncertainty is the operative fact: treat
reaching those commands as unproven, not as a scheduled upgrade. The evidence and the
experiment that would settle it are recorded in `sitecli/README.md`.
</Aside>
