Every Customer Edge serves F5's Site Console on `https://<sli-ip>:65500`. On this
deployment it is usually the route to try first.

It asks least of you: no SSH key to distribute, no jump host to maintain, no public IP on
the node, and no VM replacement to enable it. Who may connect becomes an **Azure RBAC
decision**. And it does not need the site to be registered: this page was first captured
while all three sites were reporting `site_state: FAILED`, and re-verified unchanged against
the same nodes once they were `ONLINE`.

The catch is that the Site Console answers only on the node's internal (SLI) address,
reachable only from inside the VNet. Azure Bastion closes that gap without putting
anything else on the network.

<Aside type="note" title="What is verified here, and what is not">
Every command and every output on this page was run against `f5-xc-ce-vm-01` in this
deployment and is reproduced verbatim, including the failures.

**Authentication is verified**: the appliance's `admin` credential returns `200` through the
tunnel. What is *not* exercised is the console itself — nothing below describes what you can
see or do once you are inside.

**Azure RBAC is not verified.** Every run was as the subscription owner, so the Reader
requirement in step 2 is Microsoft's documented requirement rather than something measured
here.
</Aside>

<Aside type="caution" title="Bastion is opt-in, and is not deployed by default">
`enable_bastion` defaults to `false`, so on a default `terraform apply` there is no Bastion
host and `terraform output -raw bastion_name` is `null`. Set `enable_bastion = true` in
`terraform/terraform.tfvars` — it is `true` on this deployment.

The reason it is opt-in is cost, not risk: a Standard-SKU host bills an hourly standing
charge from the moment it is provisioned, whether or not anyone opens a tunnel — USD
0.29/hour in `eastus` for the two included scale units (retail, 2026-07), roughly USD 212 a
month. Turn it off again when the demo does not need console access.
</Aside>

## Before you start

<Steps>

1. Sign in to Azure and add the Bastion extension. Tunneling is a native-client feature
   and the extension is not installed by default.

   ```bash
   az login
   az extension add --name bastion
   ```

2. Hold **Reader** on the CE virtual machine, its network interface, and the Bastion host.
   This is Microsoft's documented requirement and is **unverified here** — every run in this
   deployment was as the subscription owner, so no lesser role has been shown to be
   sufficient or insufficient.

3. Confirm Bastion is deployed and capable. Basic SKU supports neither tunneling nor
   IP-based connection, so `Standard` and `True` here are both load-bearing.

   ```bash
   az network bastion list -g "$(terraform output -raw resource_group_name)" \
     --query "[].{name:name, sku:sku.name, tunneling:enableTunneling}" -o table
   ```

   ```text
   Name               Sku       Tunneling
   -----------------  --------  -----------
   mcn-ce-ha-bastion  Standard  True
   ```

</Steps>

## Open the tunnel

Take the values from `terraform output` rather than typing them — the resource id is not
something to assemble by hand.

<Steps>

1. Read the name of the Bastion host, the resource group, and the target CE's VM resource id.

   ```bash
   cd terraform
   BASTION=$(terraform output -raw bastion_name)
   RG=$(terraform output -raw resource_group_name)
   VM_ID=$(terraform output -json ce_vm_ids | jq -r '.eastus01')
   ```

   ```text
   mcn-ce-ha-bastion
   rg-mcn-ce-ha-rmordasiewicz
   /subscriptions/…/providers/Microsoft.Compute/virtualMachines/f5-xc-ce-vm-01
   ```

   <Aside type="caution" title="The map is keyed by site, not by VM name">
   `ce_vm_ids` keys are `eastus01`, `eastus02`, `eastus03` — **not** the VM names. A
   filter like `jq -r '."f5-xc-ce-vm-01"'` returns `null`, and the tunnel then fails on an
   empty resource id. List them if unsure:

   ```bash
   terraform output -json ce_vm_ids | jq -r 'keys | join(", ")'
   ```

   ```text
   eastus01, eastus02, eastus03
   ```

   </Aside>

2. Start the tunnel. It holds the port open until stopped, so background it or use a
   second terminal.

   ```bash
   az network bastion tunnel \
     --name "$BASTION" \
     --resource-group "$RG" \
     --target-resource-id "$VM_ID" \
     --resource-port 65500 \
     --port 65500 &
   ```

   ```text
   WARNING: Opening tunnel on port: 65500
   WARNING: Tunnel is ready, connect on port 65500
   WARNING: Ctrl + C to close
   ```

   All three lines are prefixed `WARNING:`. That is the Azure CLI writing progress to
   stderr, not a problem. Wait for `Tunnel is ready` before connecting.

3. Confirm the listener is local, on loopback:

   ```bash
   lsof -nP -iTCP:65500 -sTCP:LISTEN
   ```

   ```text
   COMMAND   PID  USER  FD  TYPE  DEVICE  SIZE/OFF  NODE  NAME
   Python  41648  you   7u  IPv4  …            0t0   TCP  127.0.0.1:65500 (LISTEN)
   ```

4. Open the console. The tunnel makes it local, so the address is `localhost` — not the
   node's address.

   ```bash
   open https://localhost:65500/          # macOS
   xdg-open https://localhost:65500/      # Linux
   ```

5. Stop the tunnel when you are finished — `Ctrl-C`, or `kill %1` if you backgrounded it.
   Leaving it open holds local port 65500 and the Bastion session.

</Steps>

## What you will see

**A credential dialog, not a login page.** The console uses HTTP Basic authentication, so
the browser raises its own username and password prompt. There is no form to look at:

```bash
curl -skI https://localhost:65500/
```

```text
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Basic realm="Volterra Site Console"
Content-Type: text/html; charset=utf-8
Content-Length: 0
```

A `401` with that realm is the console working correctly. It is what an unauthenticated
request is supposed to get — and supplying the `admin` credential to the same URL answers
`200`, which is how you confirm the credential before opening a browser:

```bash
curl -sk -u admin -o /dev/null -w '%{http_code}\n' https://localhost:65500/
```

```text
Enter host password for user 'admin':
200
```

`-u admin` with no colon makes `curl` prompt for the password rather than take it from the
command line, where it would land in shell history and in the process list.

**A certificate warning, for three reasons at once.** Checking the certificate directly:

```bash
openssl s_client -connect localhost:65500 -servername localhost </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
```

```text
subject=C=US, ST=California, L=Santa Clara, O=Volterra, OU=Volterra Edge Services, CN=site-local.volterra.io
issuer=C=US, ST=California, L=Santa Clara, O=Volterra, OU=Volterra Edge Services, CN=site-local.volterra.io
notBefore=Oct 25 04:51:31 2024 GMT
notAfter=Oct 25 04:51:31 2025 GMT
```

Subject equals issuer, so it is self-signed. The name is `site-local.volterra.io` while
you are connecting to `localhost`, so it will not match. And on the build this deployment
runs, **the certificate expired on 25 October 2025** — the appliance ships it, and nothing
in this repository renews it.

Expect a blunt browser warning, and expect it every time. The subject line above is the
useful part: it is how you confirm you reached the appliance rather than something else
listening on local port 65500.

## The admin credential

Sign in as `admin`. **This documentation does not publish the password, and should not.**

<Aside type="danger" title="On this deployment that password is still F5's factory default">
This is a measured fact, not a suspicion: the factory-default credential authenticates and
returns `200` on all three CEs today. F5 publishes that default and requires that it be
changed, and it has not been.

The practical consequence is that on this deployment "holds Reader on the Bastion" is
equivalent to full appliance console access, for anyone who knows a value that is in F5's
public documentation. Change it, and treat changing it as part of deploying a node rather
than as later hardening.
</Aside>

Two reasons not publishing it matters more here than it might look:

- This documentation is public. Printing the fleet's current console password would turn
  "holds Reader on the Bastion" into full appliance access for anyone who reads the page.
- A password published in documentation is wrong the moment somebody rotates it, and
  wrong in the most misleading way — the reader concludes their access is broken rather
  than that the page is stale.

Once it has been rotated, get it from wherever your team keeps operational secrets.

<Aside type="caution" title="Setting the password from Terraform is not verified">
`admin_user_credentials.admin_password` on the site object looks like the declarative way
to set this. It has **not** been confirmed to reach the Site Console on this build, so do
not assume it does.

Do not read the [SSH page](../ssh/) as evidence either way. Its finding that
`admin_password` "changed nothing" was measured against SSH authentication, which `vpm`
skips for the `admin` user entirely. That says nothing about the console.
</Aside>

## Why the tunnel must target the resource id

`--target-resource-id` is required. Targeting the node's address instead is refused —
whatever address you use, so there is deliberately no real one printed here:

```bash
az network bastion tunnel --name "$BASTION" -g "$RG" \
  --target-ip-address <any-sli-address> --resource-port 65500 --port 65501
```

```text
ERROR: Custom ports are not allowed. Allowed ports for Tunnel with IP connect is 22, 3389.
```

The reason is **not** that IP-based connection is disabled — on this Bastion
`ip_connect_enabled` is `true`. Microsoft does not support custom ports over IP-based
native-client connections regardless of that setting
([Azure docs](https://learn.microsoft.com/azure/bastion/connect-ip-address)), and 65500 is
a custom port. Inspecting the Bastion configuration here leads nowhere; use the resource
id.

## When it does not work

| Symptom | Cause | Fix |
| --- | --- | --- |
| `ERROR: Custom ports are not allowed. Allowed ports for Tunnel with IP connect is 22, 3389.` | Used `--target-ip-address` | Use `--target-resource-id` |
| `ERROR: Defined port is currently unavailable` | Another tunnel already holds that local port | Stop the other tunnel, or pass a different `--port`; `--resource-port` stays 65500 |
| `terraform output -raw bastion_name` is `null` or empty | Bastion is not deployed | Set `enable_bastion = true` and apply |
| Tunnel starts but the resource id is empty | `jq` filter used the VM name instead of the site key | Key on `eastus01`/`02`/`03` |
| `401 Unauthorized`, realm `Volterra Site Console` | Not a fault — unauthenticated request | Supply the `admin` credential |
| Browser refuses the certificate | Self-signed, name mismatch, and expired since Oct 2025 | Expected; confirm the subject is `CN=site-local.volterra.io` and proceed |

<Aside type="note" title="Authorization failures were not reproduced">
Insufficient RBAC is the other obvious way this fails, but reproducing it would mean
removing role assignments from a shared deployment, so it is not documented here with a
verbatim error. If the tunnel fails at start with an authorization error, check Reader on
all three of the VM, its NIC, and the Bastion host.
</Aside>
