Use Azure Serial Console when the CE has no working network path. It attaches through the
Azure platform, so it does not depend on F5 registration, the CE data plane, or an inbound
management rule.

Try [Site Console](../site-console/) first when node networking still works. Use the
[debug API](../debug-api/) after the site becomes `ONLINE`.

## Confirm the prerequisite

The CE module enables Azure-managed boot diagnostics:

```hcl
boot_diagnostics {}
```

Confirm it before attaching:

```bash
az vm show \
  --resource-group <resource-group> \
  --name <vm-name> \
  --query diagnosticsProfile.bootDiagnostics.enabled \
  --output tsv
```

The command must return `true`.

<Aside type="note" title="Boot logs start after diagnostics is enabled">
If diagnostics was enabled after a VM booted, the earlier boot has no stored log. Reboot
the node only when that disruption is part of the diagnostic procedure.
</Aside>

## Attach to the node

<Steps>

1. Install the Azure CLI extension.

   ```bash
   az extension add --name serial-console
   ```

2. Read the resource group and available VM names.

   ```bash
   terraform -chdir=terraform output -raw resource_group_name
   terraform -chdir=terraform output -json ce_vm_names | jq -r 'to_entries[] | "\(.key)\t\(.value)"'
   ```

3. Attach from an interactive terminal.

   ```bash
   az serial-console connect \
     --resource-group <resource-group> \
     --name <vm-name>
   ```

4. Sign in at the node prompt with the site-managed `admin` credential.

   Read the matching site name from `xc_site_names`, then read that key from the sensitive
   `site_console_admin_passwords` output. Keep the value out of logs and documentation.

5. Collect only the evidence needed to diagnose boot, cloud-init, registration, or routing.

6. Exit the shell and close the console when you finish.

</Steps>

## Read the boot log without attaching

Use the stored boot log when you only need startup evidence:

```bash
az vm boot-diagnostics get-boot-log \
  --resource-group <resource-group> \
  --name <vm-name>
```

Look for cloud-init completion, container runtime startup, VPM startup, and registration
errors. The log can explain a failure that occurred before the debug API was available.

## Troubleshoot serial access

| Symptom | Cause | Action |
| --- | --- | --- |
| `BlobNotFound` from the boot-log command | No boot occurred after diagnostics was enabled | Use live console or perform an approved reboot |
| Terminal raw-mode error | The command is not running in a real TTY | Run it from an interactive terminal |
| Another operator disconnects | Azure allows one serial session per VM | Coordinate ownership of the session |
| A long paste stalls or fails | Azure limits console paste length | Send short commands individually |
| Login fails | The wrong site's password was selected | Map the VM key through `xc_site_names` before reading the password |

Serial console is a break-glass path, not a bulk collection interface. Return to the debug
API after registration and connectivity recover.
