Azure Serial Console attaches to the node's emulated serial port through the Azure
platform. It does not traverse the F5 Distributed Cloud control plane, the node's
data plane, or any network path the node controls — which is exactly why it works
when nothing else does.

Reach for it when a CE **never came up**: registration failed, the site is absent
from the tenant, or the node is up but has no route out. In all of those cases the
[debug API](../debug-api/) has no tunnel to relay through, and SSH is closed on the
node as shipped.

## Prerequisite: boot diagnostics

Azure requires boot diagnostics on the VM before it will attach a serial console.
This is enabled by `terraform/modules/ce-node`:

```hcl
boot_diagnostics {}
```

An empty block selects Azure-managed storage, so there is no diagnostics storage
account, lifecycle policy or access key to own. Confirm it on a node:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="Enabling it is not retroactive">
Boot diagnostics captures the serial log **at boot**. Turning it on for a VM that
is already running does not produce a log for the boot that already happened, so
`az vm boot-diagnostics get-boot-log` answers:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

That is expected, not a fault. A boot log exists after the node next reboots. Live
console attach, however, works immediately — it does not depend on the log.
</Aside>

## Checking availability without a terminal

Attaching needs an interactive session, but whether it *would* attach is two API
calls. Both are useful in a health check.

The service must be enabled for the subscription — an administrator can disable it
tenant-wide:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

Then ask for a connection to a specific node's serial port:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

A `connectionString` beginning `wss://` — on this deployment
`eastus.gateway.serialconsole.azure.com` — means the console is attachable right
now. Before boot diagnostics was enabled, this call had nothing to attach to.

<Aside type="danger" title="That connection string is a credential">
It is a short-lived bearer token embedded in a URL. Do not log it, paste it into a
ticket, or commit it. Print only the host when you are demonstrating that the call
worked.
</Aside>

## Attaching

<Steps>

1. Install the extension once:

   ```bash
   az extension add --name serial-console
   ```

2. Attach:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. You land at the node's own login prompt, not a shell. This is the Site CLI, and
   it needs credentials set on the node — the admin password from provisioning, or
   one set through the change-password endpoint. Serial console proves the *channel*
   works; it does not bypass authentication.

</Steps>

Captured from `f5-xc-ce-vm-01`, elided in the middle where the systemd unit output
adds nothing:

```text file=../../../_data/serial-console-boot.txt
```

Four things in that transcript are worth noticing, because they answer questions the
debug API cannot:

- **cloud-init completed** — `Datasource DataSourceAzure`, finished at 22.37 seconds.
  A node that never registers usually failed here, and this is where you see it.
- **Both container runtimes started.** `Container Runtime Interface for OCI (CRI-O)`
  and `Docker Application Container Engine` are each `[ OK ]`, which is the boot-time
  proof of the dual-runtime behaviour that surprises people in
  [crictl](../../commands/system/crictl/) and [docker](../../commands/system/docker/).
- **`VP Manager image load` and `Argo Watch service`** — `vpm` and Argo coming up.
- **The prompt is the node's own**, behind its audit banner. Serial console gets you a
  login prompt, not a session.

<Aside type="caution" title="Attaching interactively needs a real terminal — but it can be scripted">
`az serial-console connect` puts the terminal into raw mode, so it cannot run from a
pipeline or any context without a TTY. It fails client-side, before contacting Azure:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

That traceback is terminal handling, not a serial console outage.

The attach itself, however, **is** automatable — drive the websocket directly instead
of the CLI. The transcript above was captured that way, with no TTY. See
`scripts/serial-console-capture.py`, which is how you would collect boot evidence from
a node that failed to register without a human sitting at a terminal.
</Aside>

<Aside type="caution" title="Expect to retry: the gateway refuses roughly every other attempt">
The gateway's first frame is a challenge, not output, and the client answers it with a
bearer token. Even when that is done correctly the socket often closes immediately:

```
[close] code=1011 reason=Connection not trusted
```

Measured across repeated attempts on three nodes, this alternates: a refusal is
followed by a success on the same node, which is consistent with a previous session
still being held and the refused attempt clearing it. **It is not a credential
problem**, and the message is misleading — retrying is normally enough, which is why
`scripts/serial-console-capture.py` retries by default.

Use a single token for both the session request and the challenge anyway, matching the
`az` extension. That is correct practice, but it is not what causes this.
</Aside>

## What you can see here that the API cannot show you

- **cloud-init** running, failing, or never starting — the usual cause of a node
  that never registers.
- **Registration attempts** against `register.ves.volterra.io`, including a
  configuration error or a token the tenant rejected.
- **Kernel and boot messages** from before any agent was running.
- The node when it has **no working network path**, which defeats every other route.

For a node that *is* `ONLINE`, prefer the debug API: it is scriptable, it produces
evidence you can re-run, and it does not occupy the single serial port.
