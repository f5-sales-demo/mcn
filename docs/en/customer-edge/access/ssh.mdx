**There is no supported `admin` SSH path on the CE build this tenant runs** —
`crt-20250613-3382`, OS `9.2024.6`. This is not a matter of configuration. The
`admin` account exists, `sshd` is running, and `admin_user_credentials.ssh_key`
is accepted by the site object and returned by an API read-back — but the key is
never applied to the node, so every authentication attempt is refused.

Use the [debug API](../debug-api/) instead. It reaches the node's read-only command
surface and is already scripted in this repository.

<Aside type="danger" title="Terraform support for this was removed">
`admin_user_credentials` was wired into `terraform/modules/xc-site` and then reverted
once the evidence below was collected (#660, PR #663). It is not a gap waiting to be
filled — the field configures nothing on the node. Do not re-add it.
</Aside>

## Why every attempt looks like a network problem

`sshd` binds `0.0.0.0:22` on the CE, but only the **internal (SLI)** address is on the
host network stack. Probed from `ar-ecmp-client`, inside the same VNet, against all
three demo CEs:

```text
10.0.1.4     TimeoutError: timed out         ← CE mgmt/SLO  (eth0)
10.0.2.4     TimeoutError: timed out         ← CE external  (eth1)
10.0.3.5     CONNECTED  SSH-2.0-OpenSSH_8.7  ← CE internal/SLI
10.0.3.6     CONNECTED  SSH-2.0-OpenSSH_8.7
10.0.3.7     CONNECTED  SSH-2.0-OpenSSH_8.7
10.0.3.99    TimeoutError: timed out         ← unused address, negative control
```

The mechanism is visible in [`health`](../../commands/system/health/): **eth0 is renamed
`a-i-eth0` and carries no host IP address** — the Argo data plane owns that interface —
while eth1 and eth2 stay on the host stack where `sshd` is listening.

So a probe against the address you know the node by, its management address, times out
exactly as a closed security group would. Nothing is blocking it; there is no listener
on that address to answer.

<Aside type="caution" title="Probe from inside the VNet, and probe the internal address">
Two measurement mistakes here produce confident wrong answers.

Probing eth0 or the external interface for port 22 always reports closed, whatever the
node's SSH state, so it cannot tell you anything about SSH. Only the SLI address
answers.

And a probe from a corporate workstation can report a port **open** that is closed:
Netskope completes the TCP handshake itself on common ports. Ports 80 and 443 read as
open on the CE public addresses from a workstation and are closed when probed from
inside the VNet. Probe from a VM in the VNet.
</Aside>

## Why `admin` cannot authenticate

`vpm` configures the node's local users at registration, and it declines to touch this
one. From the node's own log, three times over a single boot:

```text
vpm  users.go:165: Won't do any change for user admin (internal skip)
```

Everything else is consistent with that single line:

- The account exists — `uid=2202(admin) gid=2202(admin) groups=2202(admin),2301(vpm)`,
  home `/var/home/admin`, login shell `/opt/bin/vpmu`, which is the Site CLI.
- `/var/home/admin/.ssh` **never exists**, before or after the site reaches `ONLINE`.
  No `authorized_keys` file is written at any point.
- `sshd -T` reports `pubkeyauthentication yes`, `passwordauthentication no`,
  `kbdinteractiveauthentication no`. The only `PasswordAuthentication yes` in
  `/etc/ssh/sshd_config` sits inside `Match User vesbkp,xcuser`, so `admin` is excluded
  from password authentication **at the image level**.
- `admin`'s shadow last-change date is the image build date, 2024-02-16, while
  `vesbkp` and `vesopcon` show the current date. `vpm` set those two and never touched
  `admin`.
- `vpm` logs nothing about `ssh_key` or `authorized_keys` at all.

The client side agrees. Across 45 authentication attempts spanning three from-scratch
deployments, two in-place updates and three different CE builds — including the latest,
running OpenSSH 9.9:

```text
debug1: Authenticating to <sli-ip>:22 as 'admin'
debug1: Offering public key: ... ED25519 SHA256:ENH3M0bFPYMt... explicit
debug1: Authentications that can continue: publickey
admin@<sli-ip>: Permission denied (publickey).
```

The server never offers password or keyboard-interactive authentication, and
`journalctl -u sshd` on the node records
`Connection closed by authenticating user admin ... [preauth]`.

## What this is not

Each of these was tested and ruled out, and each is a plausible enough guess to cost a
day.

| Not the cause | How it was ruled out |
| --- | --- |
| The credential only applies at create time | `sshd` starts about 90 seconds into first boot, *before the site object exists* — `sshd[1238]: Server listening on 0.0.0.0 port 22` at 13:04:56, site created at 13:05:23. `admin_user_credentials` is also present in `ReplaceSpecType` and applies in place. |
| `block_all_services` | The SLO port-22 closure is identical whether services are blocked or not. |
| A trailing newline on the key | Tested both ways. No change. |
| Pinned, older CE software | Reproduced on three builds, including one with OpenSSH 9.9. |
| A missing `admin_password` | Setting `admin_password` alongside `ssh_key` on a from-scratch CE changed nothing. |

<Aside type="caution" title="Two API fields that look like discriminators and are not">
`gc_spec.admin_ssh_key` is empty on **all 88 sites in the tenant**, including the 20
that set `admin_password`. Comparing it between a working and a non-working site tells
you nothing, because it is empty everywhere.

`registrations_by_site` omits the field entirely and returns `None` for it, which reads
as "not configured" rather than "not reported".
</Aside>

```bash
bash scripts/capture-sitecli.sh --check --site ar-bgp-eastus01 --node f5-xc-ce-vm-01

```

<Aside type="caution" title="A newly created site needs about half an hour before the operate API answers">
For roughly 25 to 30 minutes after a new site reports `ONLINE`, the `vpm/debug`
endpoints return a BIG-IP `503` page reading `The requested URL was rejected`. That
looks like a web application firewall block, or a revoked token, and is neither — the
site is not ready to relay yet. Wait and retry rather than changing anything.
</Aside>

### Driving the Site CLI over `az vm run-command`

`/opt/bin/vpmu` is `admin`'s login shell, so invoking it over `az vm run-command` reaches
the same interactive Site CLI that SSH would have reached.
Verified on a disposable CE of the same build; `execcli docker-ps`,
`execcli ip-link-show` and `health` were all captured that way.

Two mechanics are required and neither is obvious:

- **`vpmu` panics without a PTY** —
  `go-prompt … NewStandardInputParser: no such device or address`. Allocate one.
- **The command text and the Enter byte must be separate writes.** In a single write the
  newline lands in the buffer as a literal character and the CLI answers
  `unknown command "execcli\n"`, which reads as though the command does not exist.

The interactive menu lists `configure`, `configure-generic-hardware`,
`configure-network`, `configure-http-proxy`, `diagnosis` and `health`. **`execcli` is a
hidden command** — it is not in that menu, and it takes a catalog command name as its
argument.

<Aside type="note" title="This path is verified on a disposable CE, not on the demo">
The `run-command` route was exercised on a throwaway CE running the same build and the
same configuration. It has not been re-run against `ar-bgp-eastus01/02/03`, so treat its
behaviour there as expected rather than proven. The debug API route *is* verified
against the demo.
</Aside>
