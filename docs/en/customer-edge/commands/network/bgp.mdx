The CE runs FRR for BGP. On this topology it peers with the two Azure Route Server
instances, advertises the VIP, and learns the VNet prefix.

## `show-ip-bgp-summary`

Start here. One screen tells you whether peering is up and how long it has been
stable.

```bash
{"command":["show-ip-bgp-summary"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp-summary.txt
```

Read `State/PfxRcd` first. A number is the count of prefixes received and means the
session is established; anything else — `Active`, `Connect`, `Idle` — is a session
that is not up. `Up/Down` shows how long the current state has lasted, so a session
that keeps resetting shows a suspiciously small value.

<Aside type="caution" title="The vrf id here is not the one rt wants">
This output reports `vrf-id 3`. That is FRR's numbering. The Argo data plane uses a
separate table id, and passing FRR's number to
[`rt --dump`](../dataplane-forwarding/) returns `No such file or directory`, which
looks like a broken node rather than the wrong argument.
</Aside>

## `show-ip-bgp`

The full table, with best-path selection visible.

```bash
{"command":["show-ip-bgp"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp.txt
```

`*` is a valid route, `>` the selected best path, `=` a multipath member. In the capture
above the learned VNet prefix `10.0.0.0/16` has two paths — one via each Route Server
instance — marked `*=` and `*>`: a best path plus a multipath member, so the node load-shares
its return traffic over both instances. The VIP `10.250.0.10/32` has a single `*>` path
because this node originates it.

<Aside type="caution" title="The demo's equal-cost multipath is not visible in this output">
`show-ip-bgp` is one node's table. The ECMP this deployment demonstrates is several
*different* CEs advertising the same `/32`, and it is programmed on the Azure side — so no
single CE's BGP table can show it, and the absence of a multipath marker on the VIP here is
not a fault. Prove that from the Route Server peerings or the client's effective route table
instead; both are on the [verify page](../../../../demo/verify/).
</Aside>

## `show-ip-bgp-neighbors`

Per-neighbour detail: capabilities negotiated, timers, message counters and the
reason for the last reset.

```bash
{"command":["show-ip-bgp-neighbors"]}
```

Reach for it when the summary shows a session flapping and you need to know why.
`Last reset` and its reason are the useful lines.

## `show-ip-bgp-neighbors-advertised-route`

What this node is telling its peers, as opposed to what it knows.

```bash
{"command":["show-ip-bgp-neighbors-advertised-route"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp-neighbors-advertised-route.txt
```

This is the command for "the VIP is not reachable from the VNet". If the VIP is
absent here, the problem is on this node and no amount of looking at the peer will
help.

The output repeats one `bgp neighbor:` block **per peer**, so on this topology you get the
same two prefixes twice — once for each Route Server instance. That is not a duplicated
render: it is what confirms the node is advertising to both. A block that is present for one
peer and missing or short for the other is the interesting case.
