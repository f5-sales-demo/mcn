Captured 2026-08-03 from one CE of this deployment.

Argo tracks every connection. How you query the table matters more than what it contains,
because the full dump is unbounded in principle and awkward in practice.

<Aside type="caution" title="629,760 is the table's capacity, not the number of flows">
The header line `Flow table(size 161218560, entries 629760)` reports how many slots the data
plane allocated, and it is the same on every node here regardless of load. The live flow
count is not in that line. `Entries: Created … Added … Deleted …` a few lines below are
lifetime counters, and the actual populated flows are the records printed after the legend —
73 of them in a run taken while writing this, in a 542-line response.
</Aside>

## `flow-l-match`

Almost always the one you want. Takes an address, or an address and port.

```bash
{"command":["flow-l-match","100.127.192.10:53"]}
```

```text file=../../../../_data/sitecli-flow-l-match.txt
```

The action on each flow is the point: `F` forward, `D` drop, `N` NAT. A flow present
with action `D` means the data plane made a deliberate decision, which redirects you
to policy rather than to connectivity.

## `flow-l`

The full dump.

```bash
{"command":["flow-l"]}
```

```text file=../../../../_data/sitecli-flow-l.txt
```

<Aside type="caution" title="Trimmed, and the size moves">
The capture above is trimmed to its first 60 lines from a 1,186-line response. A run while
writing this returned 542 lines — the response length tracks how many flows are live, so
neither number is a property of the command. Use `flow-l-match` unless you genuinely need to
survey the whole table.
</Aside>
