Argo keeps forwarding state separate from the Linux kernel. When
[`ip`](../ip/) and these commands disagree, these commands are what moves traffic.

## `rt`

The vRouter route table, per VRF.

```bash
{"command":["rt","--dump","2"]}
```

```text file=../../../../_data/sitecli-rt.txt
```

<Aside type="danger" title="The VRF id is not the one BGP reports">
`show-ip-bgp-summary` prints `vrf-id 3`. That is FRR's numbering and it is a
different namespace from the vRouter table id. Passing it here fails in a way that
reads as a broken node:

```text
vRouter(Response):  [No such file or directory (2)]
```

The same answer comes back for `--dump 0`. On this topology **VRF 2** is the
populated inet4 table, with VRF 1 holding two routes. If you do not know the id,
probe upward from 1 rather than trusting the BGP output.
</Aside>

## `nh`

The next-hop table. Every route points at a next-hop id, and this resolves them.

```bash
{"command":["nh","--list"]}
```

```text file=../../../../_data/sitecli-nh.txt
```

Each entry carries a `Type` and the VRF it belongs to. Eight types occur on these nodes, in
these proportions — identical across all three CEs when counted:

```text
Tunnel 558   Encap 27   NAT 22   Vrf 16   Receive 14   Composite 4   Drop 2   Resolve 2
```

A route resolving to a `Drop` next hop is a blackhole, and that combination is worth checking
whenever a prefix is present in `rt` yet traffic still disappears.

<Aside type="caution" title="The capture above is trimmed, so it does not contain every type">
It is the first 60 lines of 3,849. `Tunnel`, the most common type by a wide margin, does not
appear in those 60 at all — so do not read the capture as the full type inventory, and do not
conclude a type is absent from a node because it is absent from a trimmed capture. The counts
above came from the untrimmed response.
</Aside>

## `vif`

The virtual interface table: what the data plane binds to, and per-interface
counters.

```bash
{"command":["vif","--list"]}
```

```text file=../../../../_data/sitecli-vif.txt
```

The flags legend at the top is worth reading once — `Vp` marks the vhost physical
interface, `Dpdk` a DPDK-managed one. Use this to confirm the data plane has claimed
the interface you expect, and to see RX and TX counters that Linux does not show
because the traffic never reaches the kernel.

## `mpls`

```bash
execcli mpls --help
```

The Argo MPLS table. Reachable **only from the box** — `mpls` is not on the debug API, so
unlike `rt`, `nh` and `vif` above it needs [SSH](../../../access/ssh/) or the
[serial console](../../../access/serial-console/), through
[`execcli`](../../on-box/).

No captured output here. On this deployment the CE forwards IPv4 with BGP and ECMP and does
not use MPLS labels, so a capture would show an empty table and teach nothing. Its existence
and its `--help` argument form are verified from the appliance's own completion menu; its
populated output is not reproduced.
