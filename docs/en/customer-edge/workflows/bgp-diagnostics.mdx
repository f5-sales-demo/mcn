import { Steps, Aside } from "@astrojs/starlight/components";

For a site that is `ONLINE` — if it is not, start with
[registration](../registration/).

<Steps>

1. **Is peering up at all?**
   [`show-ip-bgp-summary`](../../commands/network/bgp/). Read `State/PfxRcd`: a
   number means established, and `Up/Down` shows whether it has been stable. A small
   value on a site that has been up for days means the session is flapping.

2. **If the session is down**, the cause is usually below BGP. Confirm the interface
   carrying the peering is up with
   [`ip-link-show`](../../commands/network/ip/), then confirm reachability to the
   peer address.
   - **On Azure**: Peers are Azure Route Server instances (`az network routeserver peering list-learned-routes`).
   - **On AWS**: Peers are the AWS VPC Router / gateway interface (`10.150.0.1`).
   - **On-Premise KVM**: Peers are the containerized FRR ToR BGP router (`docker exec frr-router vtysh -c "show ip bgp summary"`).

3. **If the session is up but the VIP is unreachable**, check what the node is
   actually advertising with
   [`show-ip-bgp-neighbors-advertised-route`](../../commands/network/bgp/). If the
   VIP is absent there, the problem is on this node and looking at the peer will not
   help.

4. **If the node advertises correctly but traffic still does not arrive**, the
   control plane and the data plane disagree. Check the forwarding table the data
   plane actually uses with [`rt`](../../commands/network/dataplane-forwarding/),
   remembering that its VRF id is not the one BGP reports.

   Then resolve the next hop with `nh`. A prefix present in `rt` whose next hop is
   `Drop` is a blackhole.

5. **If the session flaps**, [`show-ip-bgp-neighbors`](../../commands/network/bgp/)
   carries the last reset reason and the negotiated timers.

</Steps>

<Aside type="caution" title="Two different VRF numbering schemes">
`show-ip-bgp-summary` reports FRR's `vrf-id`. The Argo data plane numbers its tables
separately, and passing FRR's number to `rt --dump` returns `No such file or
directory` — which looks like a broken node rather than a wrong argument. On this
topology VRF 2 is the populated inet4 table.
</Aside>

This workflow diagnoses a CE. It does not prove how many equal-cost paths the upstream
router installed or whether a static path survived a failed CE. For those design and
verification boundaries, see [Routing and failover](../../high-availability/routing-and-failover/).
