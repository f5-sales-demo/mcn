Secure Mesh v2 registration uses one site-scoped node token per node. F5 Distributed Cloud issues
the token inside a complete cloud-init document, and the node consumes it during first boot. A
healthy node progresses automatically from waiting to provisioning to online; there is no separate
approval step in this deployment.

<Aside type="danger" title="The debug API cannot diagnose failed registration">
The debug API reaches a node through the F5 Distributed Cloud control plane. Registration creates
that path. If registration failed, use [Site Console](../../access/site-console/) while the node has
network connectivity or [serial console](../../access/serial-console/) when it doesn't.
</Aside>

<Steps>

1. **Confirm the tenant.**

   ```bash
   cd terraform
   terraform output -raw xc_tenant
   terraform output -raw xc_env_tenant
   ```

   The values must match. A token minted for another tenant commonly returns `401` and makes a
   healthy site appear absent.

2. **Confirm the site exists.**

   ```bash
   curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
     "$XCSH_API_URL/api/config/namespaces/system/sites" \
     | jq -r '.items[] | "\(.name)  \(.object.status.site_state // \"UNKNOWN\")"'
   ```

   If the site is absent, inspect the Terraform apply error. The cloud-init issuance resource
   depends on the site and cannot issue a site-scoped token until the site exists.

3. **Find the node registration.**

   ```bash
   curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
     "$XCSH_API_URL/api/register/namespaces/system/registrations_by_site/<site>" \
     | jq -r '.items[] | "\(.name)  \(.object.status.current_state)  \(.object.spec.gc_spec.infra.hostname)"'
   ```

   No registration means the node did not reach the registration service. A registration that is
   still progressing means first boot reached the control plane; continue by inspecting its state
   and node logs.

4. **Confirm the VM is running.**

   For Azure:

   ```bash
   az vm list -d -g <resource-group> --query "[].{name:name,power:powerState}" -o table
   ```

   Use `aws ec2 describe-instance-status` for AWS and `virsh domstate <domain>` for KVM.

5. **Inspect first-boot logs.**

   Attach to the platform console. For an Azure node:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

   Check cloud-init completion first, then registration attempts, DNS resolution for
   `register.ves.volterra.io`, outbound connectivity, and clock synchronization.

6. **Replace an invalid issuance and its node together.**

   A node token is single use and valid for a limited time. If it expired, was consumed by a failed
   node, or belongs to another tenant, replace the matching `xcsh_site_cloud_init` resource and VM
   in one reviewed plan. A normal refresh retains the original sensitive response and never issues
   another token.

7. **Verify the recovered node.**

   Wait for the site to report `ONLINE`. Then use [`health`](../../commands/system/health/) and
   expect the node registration state to be `PROVISIONED`.

</Steps>

<Aside type="caution" title="Use the site-to-registration endpoint">
Registration objects are named `r-<uuid>`, not after the site. Query
`registrations_by_site/<site>` to resolve the mapping. Passing a site name to
`registrations/<name>` asks for a different object and returns a misleading `404`.
</Aside>

## Common causes

- The API credential and site belong to different tenants.
- Cloud-init did not complete.
- The one-time node token expired or was already consumed.
- The node can't resolve or reach `register.ves.volterra.io`.
- Clock skew invalidates certificates.
