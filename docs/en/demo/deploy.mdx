## Prerequisites

- **Terraform** at the version floor in `terraform/versions.tf` — `>= 1.16.1`, for
  provider-defined functions and the `check` block that guards the VIP.
- **The `xcsh` provider at exactly v8.0.0 for normal deployments.** This deployment uses
  only the clean-break SMSv2 contract. A release-candidate acceptance run may substitute one
  reviewed local binary through the explicit procedure below. The local `.terraform.lock.hcl`
  remains gitignored; the exact source constraint is authoritative.
- **An F5 XC API credential** for the tenant in `var.expected_xc_tenant`, exported as
  `XCSH_API_TOKEN` (or the P12/PEM pair). Export the credential only, never a URL — see
  below.
- **Azure credentials** with rights to create a resource group, VNet, Route Server and VMs.
- **A pre-existing F5 XC namespace** for the app tier. The deployment *reads* it and never
  creates or destroys it, so a namespace holding unrelated demos can never land on this
  stack's destroy list.

<Aside type="caution" title="dev_overrides silently replaces the provider you think you are testing">
If `~/.terraformrc` contains a `dev_overrides` block for `xcsh`, every local Terraform
command uses the binary in that directory and **ignores both the version constraint and the
lock file**. A build a few days old is enough to fail with `Blocks of type "…" are not
expected here` on configuration that is perfectly valid against the published provider.

Keep it out of the default path and opt in only when you are developing the provider:

```bash
mv ~/.terraformrc ~/.terraformrc.provider-dev
TF_CLI_CONFIG_FILE=~/.terraformrc.provider-dev terraform plan   # when you mean it
```

</Aside>

## Supply variable values via `tfvars`

Every variable has a default or derived default. For internet readers and reference deployments, supply your own values via `terraform.tfvars` so deployment-specific names, subscriptions, domains, and addresses are not hardcoded into configuration:

```bash
cd terraform
cp terraform.tfvars.example terraform.tfvars
```

| Variable | Default / Role | Why it should be customized |
| --- | --- | --- |
| `origin_ip` | *(no default)* | Public IP of your origin server (e.g. `203.0.113.10` from RFC 5737 documentation space). |
| `lb_domain` | *(no default)* | FQDN for Rest of World traffic (e.g. `mcn-ce-ha.f5-sales-demo.com` or `mcn.example.com`). |
| `ca_lb_domain` | `mcn-ce-ha.f5-sales-demo.ca` | FQDN for Canada-only traffic (e.g. `mcn.example.ca`). |
| `enable_canada` | `true` | Toggle to deploy parallel Canadian regional infrastructure, virtual sites, and load balancer. |
| `ca_location` | `canadacentral` | Azure region for Canadian CEs and Route Server. |
| `ca_hub_cidr` | `10.200.0.0/16` | VNet CIDR block for Canadian Hub VNet (RFC 1918 space). |
| `ca_vip` | `10.250.1.10` | HA VIP advertised by Canadian CEs via eBGP (must be outside VNet CIDRs). |
| `ca_re_cities` | `["toronto", "montreal"]` | List of Regional Edge cities for Canadian RE Virtual Site selector expression. |

Both `origin_ip` and domains are format-validated so a typo fails the plan rather than runtime routing.

`terraform.tfvars` is gitignored to protect sensitive environment variables, subscription IDs, and custom credentials.

## The tenant is configuration, not whatever your shell is exporting

`var.expected_xc_tenant` names the tenant and is the only place it is named.
`providers.tf` derives the `xcsh` provider's `api_url` from it, which deliberately
overrides any `XCSH_API_URL` in the environment, and a `postcondition` in
`terraform/main.tf` fails the **plan** when the environment names a different tenant.

Read either half without running anything that changes state:

```bash
terraform output -raw xc_tenant       # what the deployment targets
terraform output -raw xc_env_tenant   # what your shell claims — diagnostic only
```

Illustrative output for a correctly matched configuration:

```text
example-corp
example-corp
```

<Aside type="danger" title="This guardrail exists because the demo silently re-homed itself into the wrong tenant">
The demo was built in one tenant. A credential file later began exporting a *different*
tenant's `XCSH_API_URL`; subsequent applies minted a token for that tenant, the CE VMs
re-registered there, and their original registrations were abandoned. Every plan in between
was clean, because nothing in the configuration had an opinion about the tenant
([issue 696](https://github.com/f5-sales-demo/mcn/issues/696), fixed in
[PR 697](https://github.com/f5-sales-demo/mcn/pull/697)). Recovering it meant destroying the
stack in the wrong tenant and rebuilding it in the right one.

The symptom to recognize, because it is not self-describing: a token minted for another
tenant fails the pinned endpoint with a bare `401`, which reads exactly like an expired
credential. If a credential you believe is good returns `401`, compare the two outputs
above before you mint another token.
</Aside>

## AWS SMSv2 preflight is mandatory

The AWS Transit Gateway path is pinned to the immutable
[`xcsh` v8.0.0 release](https://github.com/f5-sales-demo/terraform-provider-xcsh/releases/tag/v8.0.0).
That release publishes contract `f5xc-ce-automation/v3` version `6.1.0` from
`api-specs-enriched` v6.1.2. Its four AWS SMSv2 capabilities, including
`site_upgrade`, must all report `available`; do not bypass a failed gate.

Each AWS site receives its own `xcsh_token.aws` credential with `type = 1` and
`site_name` set to the exact Secure Mesh Site v2 name. The multipart EC2 user data
embeds the provider-issued `xcsh_site_cloud_init` payload, which owns
`/etc/vpm/user_data`. The wrapper may add the early SLI route guard and operator
SSH access, but it must never create or replace `/etc/vpm/config.yaml`; the certified
AWS CE AMI retains that hardware-certification configuration.

For a controlled replacement, `aws_bootstrap_site_keys` is intentionally cumulative:
plan CE01 with `["01"]`, then CE02 with `["01", "02"]`, and CE03 with all three
keys. Each stage limits runtime discovery, Connect peers, external connectors, BGP
configuration, and convergence observation to those admitted sites. It also installs
the admitted site's SLO and SLI subnet associations before creating XC connectors; both
GRE transports otherwise cannot reach the TGW. This prevents a
targeted CE replacement from waiting for absent peer sites or minting their JWT credentials;
the admitted provider-issued cloud-init records remain stable throughout every stage.
The default is all three keys for the complete topology; use the saved-plan preflight for
every partial stage.

Session establishment can be checked during each partial stage. Exact imported workload
and exported listener routes are enforced only after the complete TGW route table,
workload attachment association and propagation, and XC load balancer are applied. The
final status read is ordered behind those resources, so a first complete plan does not
poll for routes that cannot exist yet.

Before any plan is applied with `enable_aws_tgw_connect = true`, save the reviewed
plan and run the non-mutating preflight using the complete command in the Apply
sequence. Put evidence in a new, empty directory outside the repository.

The gate compares the authenticated AWS account and region, XC tenant, and the explicitly
expected one-site or three-site stage. It performs no Azure CLI or Azure resource operation; the
preflight gate itself does not access the backend. It rejects
every Azure resource change, then installs exactly provider v8.0.0 in a disposable
directory and reads its compiled contract. The only durable evidence is
`summary.json`, containing `status`, a fixed reason code, and a UTC timestamp;
account IDs, subscription IDs, tenant names, endpoints, tokens, and resource
values are never written to evidence. The summary also records `provider_mode` and, for a
local candidate, its expected `provider_sha256` so the evidence identifies the exact tested bytes.

Apply only when the summary says `ready` with reason `preflight_passed`. A blocked
result is an expected safe outcome and no infrastructure should be changed.

Before planning AWS sites, supply `aws_smsv2_devices` with `slo` and `sli` guest
device names for site keys `01`, `02`, and `03`. Correlate each guest device with
its AWS ENI MAC using boot-console or supported node-discovery evidence. Names
such as `ens5` and `ens6` are observations for a particular image and instance,
not defaults. Missing site mappings or duplicate devices fail validation.

AWS sites carry the explicit `mcn-topology` label selected by the VIP virtual
site. Verify the virtual site's selectees before claiming VIP placement;
registration does not guarantee a `ves.io/siteName` label exists.

Changing a device can regenerate its XC network-interface object. Review the
site update and dependent connector binding changes serially, and verify actual
forwarding and BGP state after each change. A successful site write alone does
not prove connectivity. Existing configurations must supply this new map; there
are no legacy device-name aliases.

The optional `--execute-uat` phase requires six healthy MAC-bound interfaces and
six Connect peers with twelve established BGP sessions. Both AWS-assigned BGP
endpoints are configured on every tunnel. The status output reports
`connect_peer_count` and `bgp_session_count` separately. During one CE's outage,
eight sessions must remain established; all twelve must return after recovery.
The gate also requires detailed and simplified routes to agree, and runs SSM traffic
every five seconds through failover, and upgrade sites `01`, `02`, and `03` serially
from software `crt-20251002-0027` / OS `9.2026.10` to software
`crt-20260201-0179` / OS `9.2026.17`. Evidence remains a mode-0600 sanitized summary
outside Git.

Traffic evidence separates the VIP result with a bounded 45-second retry window, the
first-attempt VIP transport result, and the direct-origin control result. A retry-backed VIP failure
blocks continuity. Intermittent origin-control failures remain visible in the
receipt without being attributed to the VIP path. Use `--continuity-only` together
with `--execute-uat` to repeat traffic, failover, and reconvergence against sites
that are already at the target versions. That supplemental receipt reports zero
serial upgrades and does not replace the complete upgrade receipt.

## Apply

<Steps>

1. **Initialize.** The backend config is not committed; supply your own with
   `terraform init -upgrade -backend-config=backend.hcl`.

2. **Run the AWS SMSv2 preflight when TGW Connect is enabled.** Continue only on `ready`.
   The first sequence uses the released provider. Add `--execute-uat` only after reviewing the
   AWS-only saved plan; that mode stops and restarts one CE, drives five-second traffic from the
   SSM client, and invokes each site's software and OS actions serially. For prerelease acceptance,
   continue within the same example to select one reviewed local candidate.

   ```bash
   terraform plan -out=/private/path/mcn.tfplan
   AWS_SITE_01=$(terraform output -json aws_site_names | jq -r '.["01"]')
   AWS_SITE_02=$(terraform output -json aws_site_names | jq -r '.["02"]')
   AWS_SITE_03=$(terraform output -json aws_site_names | jq -r '.["03"]')

   scripts/aws-smsv2-uat-preflight.sh \
     --evidence-dir /private/path/mcn-smsv2-evidence \
     --terraform-dir terraform \
     --plan-file /private/path/mcn.tfplan \
     --expected-aws-account '<AWS_ACCOUNT_ID>' \
     --expected-aws-region ap-northeast-1 \
     --expected-xc-tenant '<XC_TENANT>' \
     --expected-site "$AWS_SITE_01" \
     --expected-site "$AWS_SITE_02" \
     --expected-site "$AWS_SITE_03"

   # Prerelease candidate acceptance
   CANDIDATE_BIN=/private/path/provider/terraform-provider-xcsh
   CANDIDATE_DIR=$(dirname "$CANDIDATE_BIN")
   CANDIDATE_SHA256="sha256:$(sha256sum "$CANDIDATE_BIN" | awk '{print $1}')"
   CANDIDATE_TFRC=/private/path/mcn-candidate.tfrc
   REGISTRY_TFRC=/private/path/mcn-registry-only.tfrc

   printf 'provider_installation {\n  direct {}\n}\n' > "$REGISTRY_TFRC"
   chmod 600 "$REGISTRY_TFRC"

   cat > "$CANDIDATE_TFRC" <<EOF
   provider_installation {
     dev_overrides {
       "f5-sales-demo/xcsh" = "$CANDIDATE_DIR"
     }
     direct {}
   }
   EOF
   chmod 600 "$CANDIDATE_TFRC"

   TF_CLI_CONFIG_FILE="$REGISTRY_TFRC" terraform init -upgrade \
     -backend-config=backend.hcl
   TF_CLI_CONFIG_FILE="$CANDIDATE_TFRC" terraform plan \
     -out=/private/path/mcn-candidate.tfplan

   ../scripts/aws-smsv2-uat-preflight.sh \
     --candidate-provider-binary "$CANDIDATE_BIN" \
     --candidate-provider-sha256 "$CANDIDATE_SHA256" \
     --evidence-dir /private/path/mcn-candidate-evidence \
     --terraform-dir . \
     --plan-file /private/path/mcn-candidate.tfplan \
     --expected-aws-account '<AWS_ACCOUNT_ID>' \
     --expected-aws-region ap-northeast-1 \
     --expected-xc-tenant '<XC_TENANT>' \
     --expected-site "$AWS_SITE_01" \
     --expected-site "$AWS_SITE_02" \
     --expected-site "$AWS_SITE_03"

   TF_CLI_CONFIG_FILE="$CANDIDATE_TFRC" terraform apply \
     /private/path/mcn-candidate.tfplan

   ../scripts/aws-smsv2-uat-preflight.sh \
     --execute-uat \
     --candidate-provider-binary "$CANDIDATE_BIN" \
     --candidate-provider-sha256 "$CANDIDATE_SHA256" \
     --evidence-dir /private/path/mcn-candidate-uat-evidence \
     --terraform-dir . \
     --plan-file /private/path/mcn-candidate.tfplan \
     --expected-aws-account '<AWS_ACCOUNT_ID>' \
     --expected-aws-region ap-northeast-1 \
     --expected-xc-tenant '<XC_TENANT>' \
     --expected-site "$AWS_SITE_01" \
     --expected-site "$AWS_SITE_02" \
     --expected-site "$AWS_SITE_03"
   ```

   The preflight ignores ambient Terraform CLI configuration, initializes its contract probe
   through a registry-only configuration, and selects the candidate for contract and live UAT
   operations. It checks the digest before accepting the plan and again around live mutations.
   A missing, ambiguous, changed, or mismatched candidate fails closed. Do not publish a public
   prerelease to replace this procedure.

3. **First apply.** This builds Azure, the CE sites and the registration token, and boots
   the CEs.

   ```bash
   terraform apply
   ```

4. **Apply again once the CEs have registered.** This is not optional, and the reason is
   below rather than being something you discover.

   ```bash
   terraform apply
   ```

</Steps>

Then go to [prove it healthy](../verify/) before showing it to anyone.

## Registration approval is automated, and the apply is still two-phase

Registration approval no longer needs a human in the console: the
`xcsh_registration_approval` resource performs it, and the site module resolves which
registration to approve.

That still does not make the deployment a single hands-off `apply`, and the reason is worth
understanding before you watch a first run and conclude it failed:

- A CE's registration object is named **`r-<uuid>`**. It is never named after the site, so
  nothing can predict the name at plan time.
- The registration only exists after the VM has booted and `vpm` has registered.
- So the **first apply plans no approval at all**. Re-apply once the CEs have registered
  and the approvals are created.

`terraform/main.tf` documents this ordering at the top of the file, which is the
authoritative version — the deploy sequence lives with the code that implements it.

<Aside type="caution" title="A brand-new site is not immediately reachable over the operate API">
For roughly 25 to 30 minutes after a new site reports `ONLINE`, the `vpm/debug` endpoints
answer with a BIG-IP `503` page reading `The requested URL was rejected`. It looks like a
web application firewall block or a revoked token and is neither. Wait, then retry.

This affects a freshly built demo, not a running one.
</Aside>

## Operator SSH is a build-time decision

The deployment writes an operator key to the appliance `admin` account, whose login shell
is the Site CLI. It is written by cloud-init `write_files`, which runs once on first boot.

<Aside type="caution" title="It cannot be added to CEs that are already running">
`custom_data` is replace-only, so adopting this on running CEs **replaces every CE VM**.
That is a fleet rebuild, not a configuration change. The same is true of anything else in
the cloud-init template — including a comment, because `custom_data` is
`base64encode` of the rendered file.

It used to be worse: a replaced CE could never re-register, because the destroyed node's
registration still held the control plane's unique `(tenant, cluster_name, hostname)`
index — and `terraform plan` reported "No changes" for the whole time the fleet was down.
Recovery took two full rebuilds. That is fixed
([issue 674](https://github.com/f5-sales-demo/mcn/issues/674), closed by
[PR 693](https://github.com/f5-sales-demo/mcn/pull/693)): the site object's lifecycle is now
coupled to the CE VM instance, so replacing the VM replaces the site, and deleting the site
takes its registrations with it before the replacement node boots.

Anyone adopting this elsewhere should read the
[SSH page](../../customer-edge/access/ssh/) first.
</Aside>

## Clean up

```bash
terraform destroy
```

The app namespace survives: it is read, never managed, so `destroy` cannot take a namespace
holding unrelated demos with it. Everything else in the resource group goes.
