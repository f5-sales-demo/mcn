Docker, प्लेटफ़ॉर्म सेवाएँ चलाता है। Kubernetes वर्कलोड
[CRI-O](../crictl/) के अंतर्गत हैं।

## `docker-ps`

```bash
{"command":["docker-ps"]}
```

```text file=../../../../_data/sitecli-docker-ps.txt
```

<Aside type="tip" title="तीन कंटेनर पूरी सूची हैं, कोई टूटा हुआ नोड नहीं">
`vpm`, `argo_watch` और `site-console`। चूँकि अधिकांश नोड CRI-O के अंतर्गत चलता है, इसलिए
एक छोटा `docker-ps` विफलता जैसा दिख सकता है यदि आप यहाँ Kubernetes वर्कलोड की अपेक्षा कर रहे हों।
ऐसा नहीं है — यह एक स्वस्थ CE पर Docker कंटेनर का पूरा सेट है, और
`vpm` का उपस्थित होना और `Up` होना इस पृष्ठ की सबसे महत्वपूर्ण पंक्ति है।
</Aside>

यह नाम के साथ-साथ id भी स्वीकार करता है, इसलिए `docker-inspect vpm` काम करता है और
पुनः आरंभ होने पर भी स्थिर रहता है। पूर्ण JSON: माउंट, एनवायरनमेंट, रीस्टार्ट नीति और बाहर निकलने की स्थिति।

`docker-logs vpm` पंजीकरण त्रुटियों तक पहुँचने का सबसे तेज़ रास्ता है। टाइमस्टैम्प के साथ और

## `docker-prune`

```bash
execcli docker-prune
```

हर अनुपयोगी Docker ऑब्जेक्ट को हटाता है — बंद कंटेनर, अनुपयोगी नेटवर्क, डेंगलिंग इमेज और
बिल्ड कैश।

**केवल बॉक्स से।** `docker-prune` डीबग API पर उपलब्ध नहीं है; इसके लिए
[`execcli`](../../on-box/) की आवश्यकता है।

<Aside type="danger" title="विनाशकारी, और यहाँ कैप्चर नहीं किया गया">
यह स्थिति को हटाता है। यह हार्वेस्ट हार्नेस की अस्वीकृति सूची में है और कभी नहीं चलाया गया, इसलिए यह
पृष्ठ आउटपुट दिखाने के बजाय उपकरण के अपने कैटलॉग मेटाडेटा से इसे दस्तावेज़ीकृत करता है।

CE-विशिष्ट सावधानी: यह नोड **दो** कंटेनर रनटाइम चलाता है। `docker-prune` केवल
Docker साइड को प्रभावित करता है — `vpm`, `argo_watch` और `site-console` — और
[CRI-O](../crictl/) के अंतर्गत Kubernetes वर्कलोड तक नहीं पहुँच सकता। CRI-O साइड पर
स्थान पुनः प्राप्त करना एक अलग कमांड है, `systemctl-start-crio-prune`, जो इस बिल्ड पर
उपलब्ध नहीं है।
</Aside>
