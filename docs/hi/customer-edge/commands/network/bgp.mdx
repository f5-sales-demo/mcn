CE, BGP के लिए FRR चलाता है। इस टोपोलॉजी पर यह दो Azure Route Server
इंस्टेंस के साथ पीयर करता है, VIP का विज्ञापन करता है, और VNet प्रीफ़िक्स सीखता है।

## `show-ip-bgp-summary`

यहाँ से शुरू करें। एक स्क्रीन आपको बता देती है कि पीयरिंग चालू है या नहीं और यह कितने समय से
स्थिर है।

```bash
{"command":["show-ip-bgp-summary"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp-summary.txt
```

पहले `State/PfxRcd` पढ़ें। कोई संख्या प्राप्त किए गए प्रीफ़िक्स की गिनती होती है और इसका अर्थ है कि
सेशन स्थापित है; इसके अलावा कुछ भी — `Active`, `Connect`, `Idle` — एक ऐसा सेशन है
जो चालू नहीं है। `Up/Down` दिखाता है कि वर्तमान स्थिति कितने समय तक बनी रही है, इसलिए एक ऐसा सेशन
जो बार-बार रीसेट होता रहता है, संदेहास्पद रूप से छोटा मान दिखाता है।

<Aside type="caution" title="यहाँ दिया गया vrf id वह नहीं है जो rt चाहता है">
यह आउटपुट `vrf-id 3` रिपोर्ट करता है। वह FRR की नंबरिंग है। Argo डेटा प्लेन एक
अलग टेबल id का उपयोग करता है, और FRR की संख्या को
[`rt --dump`](../dataplane-forwarding/) को पास करने पर `No such file or directory` लौटता है, जो
गलत आर्गुमेंट के बजाय एक खराब नोड जैसा दिखता है।
</Aside>

## `show-ip-bgp`

पूर्ण तालिका, जिसमें बेस्ट-पाथ चयन दिखाई देता है।

```bash
{"command":["show-ip-bgp"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp.txt
```

`*` एक वैध रूट है, `>` चयनित बेस्ट पाथ, `=` एक मल्टीपाथ सदस्य। ऊपर के कैप्चर
में सीखे गए VNet प्रीफ़िक्स `10.0.0.0/16` के दो पाथ हैं — प्रत्येक Route Server
इंस्टेंस के माध्यम से एक — जो `*=` और `*>` के रूप में चिह्नित हैं: एक बेस्ट पाथ और साथ में एक मल्टीपाथ सदस्य, इसलिए नोड
अपने रिटर्न ट्रैफ़िक को दोनों इंस्टेंस पर लोड-शेयर करता है। VIP `10.250.0.10/32` का एक ही `*>` पाथ है
क्योंकि यह नोड इसे उत्पन्न करता है।

<Aside type="caution" title="डेमो का तीन-तरफ़ा ECMP इस आउटपुट में दिखाई नहीं देता">
`show-ip-bgp` एक नोड की तालिका है। यह डिप्लॉयमेंट जो ECMP प्रदर्शित करता है, वह तीन *अलग-अलग*
CE द्वारा उसी `/32` का विज्ञापन करना है, और यह Azure की ओर प्रोग्राम किया जाता है — इसलिए किसी एक CE की
BGP तालिका इसे नहीं दिखा सकती, और यहाँ VIP पर मल्टीपाथ मार्कर का न होना कोई खराबी नहीं है।
इसके बजाय इसे Route Server पीयरिंग्स या क्लाइंट की प्रभावी रूट तालिका से प्रमाणित करें;
दोनों [as-built पेज](../../../../as-built/) पर हैं।
</Aside>

## `show-ip-bgp-neighbors`

प्रति-नेबर विवरण: नेगोशिएट की गई क्षमताएँ, टाइमर, संदेश काउंटर और
अंतिम रीसेट का कारण।

```bash
{"command":["show-ip-bgp-neighbors"]}
```

जब सारांश किसी सेशन को फ़्लैप होते दिखाए और आपको कारण जानना हो तो इसका उपयोग करें।
`Last reset` और उसका कारण उपयोगी पंक्तियाँ हैं।

<Aside type="note" title="इस पेज पर अभी कोई कैप्चर किया गया आउटपुट नहीं है">
यह कैप्चर तब तक कमिट नहीं किया जा सकता जब तक `f5-sales-demo/docs-control#795` लैंड नहीं हो जाता। FRR
अपनी Graceful Restart पंक्ति में एक शब्द की स्पेलिंग गलत लिखता है, और `codespell` फ़ाइल को अस्वीकार कर देता है।

कैप्चर किए गए टेक्स्ट को सुधारने से यह दस्तावेज़ीकरण ऐसे आउटपुट का वर्णन करेगा जो कभी
हुआ ही नहीं, इसलिए इसे अपस्ट्रीम में ठीक किया जा रहा है। तब तक कमांड को अपने ही
नोड पर चलाएँ।
</Aside>

## `show-ip-bgp-neighbors-advertised-route`

यह नोड अपने पीयर्स को क्या बता रहा है, इसके विपरीत कि वह क्या जानता है।

```bash
{"command":["show-ip-bgp-neighbors-advertised-route"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp-neighbors-advertised-route.txt
```

यह "VIP, VNet से पहुँच योग्य नहीं है" के लिए उपयुक्त कमांड है। यदि VIP
यहाँ अनुपस्थित है, तो समस्या इसी नोड पर है और पीयर को कितना भी देखने से कोई
मदद नहीं मिलेगी।

आउटपुट **प्रति पीयर** एक `bgp neighbor:` ब्लॉक दोहराता है, इसलिए इस टोपोलॉजी पर आपको
वही दो प्रीफ़िक्स दो बार मिलते हैं — प्रत्येक Route Server इंस्टेंस के लिए एक बार। यह डुप्लिकेट
रेंडर नहीं है: यही पुष्टि करता है कि नोड दोनों को विज्ञापित कर रहा है। ऐसा ब्लॉक जो एक
पीयर के लिए मौजूद है और दूसरे के लिए अनुपस्थित या छोटा है, वह दिलचस्प मामला है।
