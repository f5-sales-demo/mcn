बिल्ड के बीच Site CLI कमांड की सतह बढ़ती है। सात `execcli` कमांड एक ऐसे नए बिल्ड पर मौजूद हैं जो इस फ्लीट द्वारा चलाए जाने वाले बिल्ड से नया है, इसलिए इस अनुभाग का शेष भाग पढ़ने वाला ऑपरेटर उन्हें नहीं पाएगा — और F5 के अपने नए दस्तावेज़ीकरण को पढ़ने वाला कोई व्यक्ति उन्हें खोज सकता है।

यह सतह एक सुपरसेट है, पुनर्व्यवस्था नहीं: नए बिल्ड पर **89** `execcli` कमांड बनाम इस फ्लीट के **82** पर, इन सात के जुड़ने के साथ और कुछ भी हटाया नहीं गया।

<Aside type="caution" title="आप इन्हें इस फ्लीट पर नहीं चला सकते">
ये बिल्ड `20260703-e2c462a` पर मापे गए थे, जो Azure मार्केटप्लेस इमेज के साथ आता है। यह फ्लीट `crt-20250613-3382` चलाता है, जहाँ ये सातों अनुपस्थित हैं — `execcli` एक अज्ञात कमांड की रिपोर्ट करता है। नीचे दी गई सभी जानकारी नए बिल्ड का वर्णन करती है।
</Aside>

## प्रत्येक कमांड क्या करता है

विवरण उपकरण के अपने हैं, कम्पलीशन मेनू से।

| कमांड | उपकरण का विवरण |
| --- | --- |
| `collect-database-stats` | डेटाबेस आँकड़े एकत्र करें |
| `iptables-lv` | iptables -L -v -n दिखाएँ |
| `marker-exists-crio` | जाँचें कि crio रीस्टार्ट मार्कर मौजूद है या नहीं |
| `marker-exists-kubelet` | जाँचें कि kubelet रीस्टार्ट मार्कर मौजूद है या नहीं |
| `marker-exists-NetworkManager` | जाँचें कि NetworkManager रीस्टार्ट मार्कर मौजूद है या नहीं |
| `systemctl-restart-NetworkManager` | NetworkManager सेवा रीस्टार्ट करें |
| `systemctl-start-crio-prune` | crio इमेज प्रून सेवा शुरू करें |

एक समूह के रूप में पढ़ने पर, इनमें से अधिकांश सात असंबंधित उपकरणों के बजाय एक कार्यप्रवाह का वर्णन करते हैं: तीन कमांड पूछते हैं कि किसी सेवा को रीस्टार्ट के लिए फ्लैग किया गया है या नहीं, और दो रीस्टार्ट या प्रून को अंजाम देते हैं। मार्कर जाँच उस जोड़े का सुरक्षित आधा है जिसका दूसरा आधा विघटनकारी है।

**सात में से चार केवल पढ़ते हैं। तीन नोड को बदलते हैं** — और उन तीन में से एक वह नहीं है जिसका आप अनुमान लगाएंगे, जो नीचे अपने अनुभाग का विषय है।

## `marker-exists-crio`

रिपोर्ट करता है कि `crio` के लिए रीस्टार्ट मार्कर फ़ाइल मौजूद है या नहीं।

```bash
execcli marker-exists-crio
```

```text
Capture policy: never execute through the API
```

## `marker-exists-kubelet`

```bash
execcli marker-exists-kubelet
```

```text
Capture policy: never execute through the API
```

## `marker-exists-NetworkManager`

```bash
execcli marker-exists-NetworkManager
```

```text
Capture policy: never execute through the API
```

तीनों ने `missing` का उत्तर दिया, जिसका अर्थ है कि उस सेवा के लिए कोई रीस्टार्ट लंबित नहीं था।

<Aside type="note" title="इस आउटपुट को एक आकार के रूप में पढ़ें, स्वस्थ आधार रेखा के रूप में नहीं">
`2026-07-28 को देखा गया।` जिस नोड से ये कैप्चर किए गए वह कभी `ONLINE` तक नहीं पहुँचा — एक विफल सॉफ़्टवेयर इंस्टॉल के बाद यह `PROVISIONING` में था, यही कारण है कि यह अस्तित्व में था। `missing` वह है जो कमांड तब प्रिंट करता है जब कोई मार्कर मौजूद नहीं होता, और यही उपयोगी हिस्सा है। यह **स्थापित नहीं** है कि एक स्वस्थ नोड उसी तरह उत्तर देता है, और यहाँ कुछ भी नहीं कहता कि लंबित रीस्टार्ट वाला नोड क्या प्रिंट करता है।
</Aside>

## `iptables-lv`

`iptables -L -v -n` चलाता है और इसे अपरिवर्तित लौटाता है, इसलिए यह F5 के अमूर्तन के बजाय नोड की फ़िल्टर तालिकाओं का पैकेट-और-बाइट गिना हुआ दृश्य है।

```bash
execcli iptables-lv
```

```text file=../../../../_data/sitecli-iptables-lv.txt
```

जो अधिकांश यह प्रिंट करता है वह Kubernetes का है: `KUBE-` चेन kube-proxy की सेवा, nodeport और फ़ायरवॉल नियम हैं, और `DOCKER-USER` कंटेनर रनटाइम से संबंधित है। पहली पंक्ति ध्यान देने योग्य है न कि छोड़ने योग्य —

```text
# Warning: iptables-legacy tables present, use iptables-legacy to see them
```

— क्योंकि यह कहती है कि यह दृश्य **अधूरा** है। लेगेसी तालिकाओं में नियम यहाँ नहीं दिखाए गए हैं, और Site CLI कोई ऐसा कमांड नहीं देता जो उन्हें पढ़े।

## `collect-database-stats` अपने नाम के बावजूद नोड पर लिखता है

यह एक जाल है, और जाल नाम है। "डेटाबेस आँकड़े एकत्र करें" और उपकरण का अपना विवरण दोनों अवलोकनीय लगते हैं। कमांड उसी तरह शुरू होता है — खुली फ़ाइल सीमा, `etcd` कितने डिस्क्रिप्टर और कनेक्शन रखता है, एक `lsof` लिस्टिंग, और `etcd` फ़ाइलसिस्टम के लिए `df` — और फिर यह एक **पंद्रह-सेकंड `fio` रैंडम-राइट बेंचमार्क** चलाता है:

```text
Checking if fio disk performance test can run safely...

Running fio disk performance test (15 seconds)...
etcd-test: (g=0): rw=randwrite, bs=(R) 4096B-4096B, (W) 4096B-4096B ...
etcd-test: Laying out IO file (1 file / 250MiB)
```

यह एक **250 MiB** फ़ाइल बिछाता है और नीचे दिए गए रन में 10.6 MiB रैंडम I/O लिखा, एक ऐसे फ़ाइलसिस्टम पर जिसमें 3.5 GiB खाली था। यह पहले जाँच करता है कि क्या यह सुरक्षित रूप से चल सकता है, इसलिए यह लापरवाह नहीं है — लेकिन यह **पढ़ना नहीं** है।

<Aside type="danger" title="इसे लाइव नोड पर एक विघटनकारी कमांड के रूप में मानें">
`etcd` जिस फ़ाइलसिस्टम पर अपना जर्नल लिखता है उसके विरुद्ध एक रैंडम-राइट बेंचमार्क `etcd` के साथ ठीक उसी संसाधन के लिए प्रतिस्पर्धा करता है जिसके प्रति `etcd` सबसे संवेदनशील है। आउटपुट स्वयं इस पर इशारा करता है — "Healthy etcd disks should have p99 < 10ms" — जो ट्रैफ़िक सेवा देने वाले नोड के बारे में नहीं बल्कि परीक्षण के अधीन नोड के बारे में एक बयान है। इसे तभी चलाएँ जब F5 सहायता इसे माँगे, ऐसे नोड पर जिसकी लेटेंसी को आप बाधित करने के लिए तैयार हों।
</Aside>

```bash
execcli collect-database-stats
```

```text file=../../../../_data/sitecli-collect-database-stats.txt
```

इसे पढ़ना: `etcd` के अपनी सीमा समाप्त होने का संदेह होने पर एक सपोर्ट इंजीनियर जो जोड़ा माँगता है वह है खुली फ़ाइल `ulimit` बनाम डिस्क्रिप्टर काउंट, और `clat` पर्सेंटाइल बेंचमार्क का बिंदु हैं। डिस्क-स्टेटस लाइन में `util=94.00%` **परीक्षण के दौरान** डिवाइस कितना व्यस्त था — यह फ़ाइलसिस्टम-भरापन का आँकड़ा नहीं है, और दोनों को भ्रमित करना आसान है।

<Aside type="note" title="इस पृष्ठ पर वह आउटपुट कैसे आया">
इस कमांड को गलती से केवल-पढ़ने योग्य माना गया और एक बार चलाया गया, उस डिस्पोज़ेबल नोड पर जहाँ से ये कैप्चर आए — इसके नाम और विवरण ने बेंचमार्क का कोई संकेत नहीं दिया, और राइट केवल इसके अपने आउटपुट में दिखाई दिए। हार्नेस अब इसे अस्वीकार करता है, और एक परीक्षण कमिट किए गए कैप्चर को राइट मार्कर के लिए स्कैन करता है और विफल होता है यदि ऐसा कमांड केवल-पढ़ने की अनुमति-सूची पर है, क्योंकि एक नाम यह स्थापित नहीं कर सकता कि कमांड केवल पढ़ता है।
</Aside>

## दो जो कभी नहीं चलाए गए

`systemctl-restart-NetworkManager` और `systemctl-start-crio-prune` नाम से प्रलेखित हैं और उनका कोई कैप्चर किया गया आउटपुट नहीं है।

```bash
execcli systemctl-restart-NetworkManager
execcli systemctl-start-crio-prune
```

`NetworkManager` को रीस्टार्ट करने से नोड की नेटवर्किंग बाधित होती है, और प्रून सेवा कंटेनर इमेज हटाती है। दोनों नोड को बदलते हैं, इसलिए न तो चलाया गया — यहाँ तक कि डिस्पोज़ेबल पर भी नहीं।

<Aside type="caution" title="तीन में से कोई भी म्यूटेटिंग कमांड केवल-पढ़ने की अनुमति-सूची पर नहीं है">
`scripts/sitecli_ssh_harvest.py` इन दोनों और `collect-database-stats` को निष्पादित करने से इनकार करता है: केवल इसकी स्पष्ट केवल-पढ़ने की अनुमति-सूची पर नाम चल सकते हैं, और बाकी सब की गणना की जाती है और कभी निष्पादित नहीं किए जाते। परीक्षण यह सुनिश्चित करते हैं कि तीनों उस सूची से बाहर रहें, इसलिए यह इनकार गलती से पूर्ववत नहीं हो सकता।
</Aside>
