इस डिप्लॉयमेंट के एक CE से 2026-07-28 को कैप्चर किया गया। ये ऑन-बॉक्स कमांड हैं, इसलिए ये डीबग API के बजाय
Site CLI के माध्यम से आते हैं; `sitecli/exec-catalog.json` सरफ़ेस को दर्ज करता है और
`sitecli/capture-manifest.json` दर्ज करता है कि कौन सा नोड।

Envoy कस्टमर एज पर एप्लिकेशन ट्रैफ़िक को टर्मिनेट और प्रॉक्सी करता है। ये चार कमांड
इसके एडमिन इंटरफ़ेस से पूछताछ करते हैं, और इनमें से कोई भी
[डीबग API](../../../access/debug-api/) पर नहीं है।

<Aside type="note" title="इनमें से हर एक एक curl प्रोग्रेस मीटर से शुरू होता है">
ये Envoy के एडमिन एंडपॉइंट के चारों ओर `curl` रैपर हैं, जिन्हें `-s` के बिना invoke किया जाता है, इसलिए नीचे के हर कैप्चर की पहली
दो या तीन पंक्तियाँ stderr पर लिखी गई curl की ट्रांसफ़र प्रोग्रेस हैं:

```text
  % Total    % Received % Xferd  Average Speed   Time    Time     Time  Current
                                 Dload  Upload   Total   Spent    Left  Speed
  0     0    0     0 …
```

वह Envoy का आउटपुट नहीं है और कोई त्रुटि भी नहीं है। यह उपयोगी भी है: `% Received` बाइट काउंट
आपको बताता है कि Envoy ने कुछ भी लौटाया या नहीं, जो "कोई listeners
कॉन्फ़िगर नहीं हैं" को "एडमिन इंटरफ़ेस ने उत्तर नहीं दिया" से अलग करता है।
</Aside>

## `envoy-listeners`

हर listener जिसे Envoy ने इंस्टॉल किया है, `name:address:port` के रूप में।

```bash
execcli envoy-listeners
```

```text file=../../../../_data/sitecli-envoy-listeners.txt
```

**क्या देखें।** इस डिप्लॉयमेंट पर listener `10.250.0.10:80` वहन करता है — वह VIP जिसे
CE BGP में विज्ञापित करता है। वह एक पंक्ति तीन लेयर्स को एक साथ जोड़ती है: यदि
[`show-ip-bgp-summary`](../../network/bgp/) दिखाता है कि प्रीफ़िक्स विज्ञापित हो रहा है लेकिन यह
listener अनुपस्थित है, तो रूट एक ऐसे नोड की ओर आकर्षित किया जा रहा है जो उसे सर्व नहीं करेगा, जो
एक ECMP सेट में सबसे बुरा फेल्योर मोड है क्योंकि ट्रैफ़िक एक ब्लैक होल में लोड-शेयर हो जाता है।

अंत में आने वाला `[fe80:…]:80` उस इंटरफ़ेस का लिंक-लोकल पता है जिससे listener बाउंड
है।

**यह आपको क्या नहीं बताता।** अपस्ट्रीम हेल्थ के बारे में कुछ नहीं — एक listener मौजूद रहता है चाहे
उसके पीछे कुछ पहुँच योग्य हो या न हो। उसके लिए `envoy-clusters` का उपयोग करें।

## `envoy-clusters`

हर cluster, उसकी प्रति-प्राथमिकता कनेक्शन और रिक्वेस्ट सीमाओं के साथ।

```bash
execcli envoy-clusters
```

```text file=../../../../_data/sitecli-envoy-clusters.txt
```

**क्या देखें।** पंक्तियाँ `cluster::scope::key::value` के रूप में हैं। `observability_name` एंट्री
हर cluster की पहचान करती है, और `default_priority::max_connections`,
`max_pending_requests` और `max_requests` की तिकड़ी वह जगह है जहाँ रिक्वेस्ट सीमाएँ दिखाई देती हैं — अपने
`max_pending_requests` पर अटका हुआ cluster अपस्ट्रीम के बजाय कॉन्फ़िगरेशन द्वारा थ्रॉटल किया जा रहा है।

## `envoy-config-dump`

Envoy का संपूर्ण कॉन्फ़िगरेशन JSON के रूप में। बड़ा: अन्यथा निष्क्रिय डेमो नोड पर 126 KB।

```bash
execcli envoy-config-dump
```

```text file=../../../../_data/sitecli-envoy-config-dump.txt
```

**क्या देखें।** टॉप-लेवल `configs` ऐरे में प्रत्येक config प्रकार के लिए एक ऑब्जेक्ट होता है —
bootstrap, clusters, listeners, routes, secrets। जब कोई listener या cluster
मौजूद हो लेकिन अप्रत्याशित व्यवहार करे तो इसका सहारा लें, और इसे पढ़ने के बजाय इसमें खोजें।

## `envoy-hc-config-dump`

विशेष रूप से हेल्थ-चेक कॉन्फ़िगरेशन।

```bash
execcli envoy-hc-config-dump
```

```text file=../../../../_data/sitecli-envoy-hc-config-dump.txt
```

**क्या देखें।** इस डिप्लॉयमेंट पर यह एक **सिंगल बाइट** लौटाता है — curl मीटर में `100 1`
के रूप में दिखाई देता है — जिसका अर्थ है कि कोई हेल्थ-चेक कॉन्फ़िगरेशन इंस्टॉल नहीं है। यह बिना हेल्थ-चेक किए गए
ऑरिजिन पूल वाले CE के लिए अपेक्षित स्थिति है, और इसे पहचानना महत्वपूर्ण है: यहाँ एक खाली
परिणाम विफल क्वेरी नहीं है।
