इस डिप्लॉयमेंट के एक CE से 2026-07-28 को कैप्चर किया गया। ये ऑन-बॉक्स कमांड हैं, इसलिए ये
debug API की बजाय Site CLI के माध्यम से आते हैं; `sitecli/exec-catalog.json` सतह को रिकॉर्ड करता है
और `sitecli/capture-manifest.json` नोड को रिकॉर्ड करता है।

Envoy, कस्टमर एज पर एप्लिकेशन ट्रैफ़िक को टर्मिनेट और प्रॉक्सी करता है। ये चार कमांड
इसके एडमिन इंटरफेस को क्वेरी करते हैं, और इनमें से कोई भी
[debug API](../../../access/debug-api/) पर नहीं है।

<Aside type="note" title="इनमें से हर एक curl प्रोग्रेस मीटर से शुरू होता है">
ये Envoy के एडमिन एंडपॉइंट के आसपास `curl` रैपर हैं, जिन्हें `-s` के बिना इनवोक किया जाता है, इसलिए नीचे प्रत्येक कैप्चर की पहली
दो या तीन लाइनें curl का ट्रांसफर प्रोग्रेस हैं जो stderr पर लिखा जाता है:

```text
  % Total    % Received % Xferd  Average Speed   Time    Time     Time  Current
                                 Dload  Upload   Total   Spent    Left  Speed
  0     0    0     0 …
```

यह न तो Envoy आउटपुट है और न ही कोई त्रुटि। यह उपयोगी भी है: `% Received` बाइट काउंट
बताता है कि Envoy ने कुछ लौटाया या नहीं, जो "कोई listeners कॉन्फ़िगर नहीं" को
"एडमिन इंटरफेस ने जवाब नहीं दिया" से अलग करता है।
</Aside>

## `envoy-listeners`

Envoy द्वारा इंस्टॉल किए गए सभी listeners, `name:address:port` के रूप में।

```bash
execcli envoy-listeners
```

```text file=../../../../_data/sitecli-envoy-listeners.txt
```

**क्या देखें।** इस डिप्लॉयमेंट पर listener `10.250.0.10:80` वहन करता है — वह VIP जिसे CE
BGP में advertise करता है। वह एकल लाइन तीन परतों को एक साथ जोड़ती है: यदि
[`show-ip-bgp-summary`](../../network/bgp/) प्रीफ़िक्स advertised दिखाता है लेकिन यह
listener अनुपस्थित है, तो रूट एक ऐसे नोड की ओर आकर्षित हो रहा है जो उसे सर्व नहीं करेगा, जो
एक ECMP सेट में सबसे बुरा failure mode है क्योंकि ट्रैफ़िक load-shared होकर black hole में चला जाता है।

अंत का `[fe80:…]:80` उस इंटरफेस का link-local पता है जिससे listener बाउंड है।

**यह क्या नहीं बताता।** अपस्ट्रीम स्वास्थ्य के बारे में कुछ नहीं — listener तब भी मौजूद रहता है जब
इसके पीछे कुछ भी पहुंचने योग्य न हो। इसके लिए `envoy-clusters` का उपयोग करें।

## `envoy-clusters`

प्रत्येक cluster, उसकी प्रति-प्राथमिकता कनेक्शन और रिक्वेस्ट सीमाओं के साथ।

```bash
execcli envoy-clusters
```

```text file=../../../../_data/sitecli-envoy-clusters.txt
```

**क्या देखें।** लाइनें `cluster::scope::key::value` के रूप में होती हैं। `observability_name` एंट्री
प्रत्येक cluster की पहचान करती है, और `default_priority::max_connections`,
`max_pending_requests` और `max_requests` त्रिक वह स्थान है जहाँ रिक्वेस्ट सीमाएं दिखती हैं — एक cluster
जो अपने `max_pending_requests` पर पिन है, वह अपस्ट्रीम के बजाय कॉन्फ़िगरेशन द्वारा थ्रॉटल हो रहा है।

## `envoy-config-dump`

JSON के रूप में Envoy का पूर्ण कॉन्फ़िगरेशन। बड़ा: अन्यथा idle demo नोड पर 126 KB।

```bash
execcli envoy-config-dump
```

```text file=../../../../_data/sitecli-envoy-config-dump.txt
```

**क्या देखें।** शीर्ष-स्तरीय `configs` एरे में प्रति config प्रकार एक ऑब्जेक्ट होता है —
bootstrap, clusters, listeners, routes, secrets। इसे तब उपयोग करें जब कोई listener या cluster
मौजूद हो लेकिन अप्रत्याशित रूप से व्यवहार करे, और इसे पढ़ने की बजाय खोजें।

## `envoy-hc-config-dump`

विशेष रूप से health-check कॉन्फ़िगरेशन।

```bash
execcli envoy-hc-config-dump
```

```text file=../../../../_data/sitecli-envoy-hc-config-dump.txt
```

**क्या देखें।** इस डिप्लॉयमेंट पर यह **एक बाइट** लौटाता है — `curl` मीटर में `100 1` के रूप में दिखाई देता है — जिसका अर्थ है कि कोई health-check कॉन्फ़िगरेशन इंस्टॉल नहीं है। यह किसी भी health-checked origin pools के बिना CE के लिए अपेक्षित स्थिति है, और यह पहचानने योग्य है: यहाँ एक खाली परिणाम विफल क्वेरी नहीं है।
