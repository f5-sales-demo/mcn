Envoy कस्टमर एज पर एप्लिकेशन ट्रैफ़िक को टर्मिनेट और प्रॉक्सी करता है। ये चार कमांड
इसके एडमिन इंटरफ़ेस को क्वेरी करते हैं, और इनमें से कोई भी
[debug API](../../../access/debug-api/) पर नहीं है।

<Aside type="note" title="इनमें से हर एक curl प्रोग्रेस मीटर से शुरू होता है">
ये Envoy के एडमिन एंडपॉइंट के आसपास `curl` रैपर हैं, जिन्हें `-s` के बिना इनवोक किया जाता है, इसलिए नीचे दिए गए हर कैप्चर की पहली दो या तीन लाइनें stderr पर लिखी गई curl की ट्रांसफर प्रोग्रेस हैं:

```text
  % Total    % Received % Xferd  Average Speed   Time    Time     Time  Current
                                 Dload  Upload   Total   Spent    Left  Speed
  0     0    0     0 …
```

यह Envoy का आउटपुट नहीं है और न ही कोई त्रुटि है। यह उपयोगी भी है: `% Received` बाइट काउंट
आपको बताता है कि Envoy ने कुछ वापस किया या नहीं, जो "कोई लिसनर कॉन्फ़िगर नहीं" और "एडमिन इंटरफ़ेस ने जवाब नहीं दिया" के बीच अंतर स्पष्ट करता है।
</Aside>

## `envoy-listeners`

हर लिसनर जो Envoy ने इंस्टॉल किया है, `name:address:port` के रूप में।

```bash
execcli envoy-listeners
```

```text file=../../../../_data/sitecli-envoy-listeners.txt
```

**क्या देखना चाहिए।** इस डिप्लॉयमेंट में लिसनर `10.250.0.10:80` वहन करता है — वह VIP जिसे
CE, BGP में विज्ञापित करता है। वह एकल लाइन तीन परतों को एक साथ बांधती है: यदि
[`show-ip-bgp-summary`](../../network/bgp/) प्रीफ़िक्स को विज्ञापित दिखाता है लेकिन यह
लिसनर अनुपस्थित है, तो रूट एक ऐसे नोड की ओर आकर्षित हो रहा है जो इसे सर्व नहीं करेगा, जो
ECMP सेट में सबसे खराब विफलता मोड है क्योंकि ट्रैफ़िक ब्लैक होल में लोड-शेयर होता है।

अंत में `[fe80:…]:80` उस इंटरफ़ेस का लिंक-लोकल एड्रेस है जिस पर लिसनर बाउंड है।

**यह क्या नहीं बताता।** अपस्ट्रीम स्वास्थ्य के बारे में कुछ नहीं — एक लिसनर तब भी मौजूद रहता है
जब उसके पीछे कुछ भी पहुंचने योग्य न हो। इसके लिए `envoy-clusters` का उपयोग करें।

## `envoy-clusters`

हर क्लस्टर, इसके प्रति-प्राथमिकता कनेक्शन और अनुरोध सीमाओं के साथ।

```bash
execcli envoy-clusters
```

```text file=../../../../_data/sitecli-envoy-clusters.txt
```

**क्या देखना चाहिए।** लाइनें `cluster::scope::key::value` के रूप में हैं। `observability_name` एंट्री
प्रत्येक क्लस्टर की पहचान करती है, और `default_priority::max_connections`,
`max_pending_requests` और `max_requests` का त्रिक वह स्थान है जहाँ अनुरोध सीमाएँ दिखती हैं — एक क्लस्टर
जो अपनी `max_pending_requests` पर पिन है, वह अपस्ट्रीम के बजाय कॉन्फ़िगरेशन द्वारा थ्रॉटल हो रहा है।

## `envoy-config-dump`

Envoy का पूरा कॉन्फ़िगरेशन JSON के रूप में। बड़ा: एक अन्यथा निष्क्रिय डेमो नोड पर 126 KB।

```bash
execcli envoy-config-dump
```

```text file=../../../../_data/sitecli-envoy-config-dump.txt
```

**क्या देखना चाहिए।** शीर्ष-स्तरीय `configs` ऐरे प्रति कॉन्फ़िग प्रकार एक ऑब्जेक्ट रखता है —
bootstrap, clusters, listeners, routes, secrets। इसे तब उपयोग करें जब कोई लिसनर या क्लस्टर
मौजूद हो लेकिन अप्रत्याशित रूप से व्यवहार करे, और इसे पढ़ने के बजाय खोजें।

## `envoy-hc-config-dump`

विशेष रूप से हेल्थ-चेक कॉन्फ़िगरेशन।

```bash
execcli envoy-hc-config-dump
```

```text file=../../../../_data/sitecli-envoy-hc-config-dump.txt
```

**क्या देखना चाहिए।** इस डिप्लॉयमेंट पर यह **एकल बाइट** लौटाता है — curl मीटर में `100 1` के रूप में दृश्यमान — अर्थात कोई हेल्थ-चेक कॉन्फ़िगरेशन इंस्टॉल नहीं है। यह किसी हेल्थ-चेक किए गए ऑरिजिन पूल के बिना CE के लिए अपेक्षित स्थिति है, और इसे पहचानना उचित है: यहाँ खाली परिणाम विफल क्वेरी नहीं है।
