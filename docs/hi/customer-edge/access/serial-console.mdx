Azure Serial Console, Azure प्लेटफ़ॉर्म के माध्यम से नोड के एमुलेटेड सीरियल पोर्ट से जुड़ता है।
यह F5 Distributed Cloud कंट्रोल प्लेन, नोड के डेटा प्लेन, या नोड द्वारा नियंत्रित किसी भी नेटवर्क पथ से नहीं गुज़रता — और यही कारण है कि यह तब काम करता है जब कुछ और नहीं करता।

इसका उपयोग तब करें जब कोई CE **कभी शुरू ही नहीं हुआ**: पंजीकरण विफल हो गया, साइट टेनेंट से अनुपस्थित है, या नोड चालू है लेकिन उसके पास बाहर जाने का कोई मार्ग नहीं है। इन सभी मामलों में [debug API](../debug-api/) के पास रिले करने के लिए कोई टनल नहीं होती, और SSH नोड पर जैसा भेजा गया था वैसे ही बंद है।

## पूर्वापेक्षा: बूट डायग्नोस्टिक्स

Azure को VM पर सीरियल कंसोल संलग्न करने से पहले बूट डायग्नोस्टिक्स की आवश्यकता होती है।
यह `terraform/modules/ce-node` द्वारा सक्षम किया जाता है:

```hcl
boot_diagnostics {}
```

एक खाली ब्लॉक Azure-प्रबंधित स्टोरेज का चयन करता है, इसलिए कोई डायग्नोस्टिक्स स्टोरेज
अकाउंट, लाइफसाइकल नीति या स्वामित्व वाली एक्सेस कुंजी नहीं है। किसी नोड पर इसकी पुष्टि करें:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="इसे सक्षम करना पूर्वव्यापी नहीं है">
बूट डायग्नोस्टिक्स **बूट के समय** सीरियल लॉग को कैप्चर करता है। किसी ऐसे VM के लिए इसे चालू करना
जो पहले से चल रहा है, उस बूट के लिए लॉग नहीं बनाता जो पहले ही हो चुकी है, इसलिए
`az vm boot-diagnostics get-boot-log` का उत्तर होता है:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

यह अपेक्षित है, कोई खराबी नहीं। नोड के अगली बार रीबूट होने के बाद बूट लॉग उपलब्ध होगा। हालाँकि,
लाइव कंसोल अटैच तुरंत काम करता है — यह लॉग पर निर्भर नहीं करता।
</Aside>

## बिना टर्मिनल के उपलब्धता जाँचना

संलग्न करने के लिए एक इंटरेक्टिव सेशन की आवश्यकता होती है, लेकिन क्या यह *संलग्न होगा* — यह दो API
कॉल में जाना जा सकता है। दोनों हेल्थ चेक में उपयोगी हैं।

सेवा सब्सक्रिप्शन के लिए सक्षम होनी चाहिए — एक प्रशासक इसे टेनेंट-स्तर पर अक्षम कर सकता है:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

फिर किसी विशिष्ट नोड के सीरियल पोर्ट से कनेक्शन के लिए अनुरोध करें:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

`wss://` से शुरू होने वाला `connectionString` — इस डिप्लॉयमेंट पर
`eastus.gateway.serialconsole.azure.com` — का अर्थ है कि कंसोल अभी संलग्न करने योग्य है।
बूट डायग्नोस्टिक्स सक्षम होने से पहले, इस कॉल के पास संलग्न करने के लिए कुछ नहीं था।

<Aside type="danger" title="वह कनेक्शन स्ट्रिंग एक क्रेडेंशियल है">
यह एक URL में एम्बेड किया गया short-lived bearer token है। इसे लॉग न करें, किसी टिकट में
पेस्ट न करें, या कमिट न करें। जब आप प्रदर्शित कर रहे हों कि कॉल काम किया, तो केवल होस्ट प्रिंट करें।
</Aside>

## संलग्न करना

<Steps>

1. एक्सटेंशन एक बार इंस्टॉल करें:

   ```bash
   az extension add --name serial-console
   ```

2. संलग्न करें:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. आप नोड के अपने लॉगिन प्रॉम्प्ट पर पहुँचते हैं, शेल पर नहीं। यह Site CLI है, और
   इसे नोड पर सेट किए गए क्रेडेंशियल की आवश्यकता है — प्रोविज़निंग से admin पासवर्ड, या
   change-password एंडपॉइंट के माध्यम से सेट किया गया। सीरियल कंसोल *चैनल* के काम करने को
   प्रमाणित करता है; यह प्रमाणीकरण को बाईपास नहीं करता।

</Steps>

`f5-xc-ce-vm-01` से कैप्चर किया गया, बीच में संक्षिप्त जहाँ systemd यूनिट आउटपुट
कुछ नया नहीं जोड़ता:

```text file=../../../_data/serial-console-boot.txt
```

उस ट्रांसक्रिप्ट में चार चीजें ध्यान देने योग्य हैं, क्योंकि वे उन प्रश्नों का उत्तर देती हैं जो
debug API नहीं दे सकता:

- **cloud-init पूर्ण हुआ** — `Datasource DataSourceAzure`, 22.37 सेकंड में समाप्त।
  एक नोड जो कभी पंजीकृत नहीं होता वह आमतौर पर यहाँ विफल हुआ होता है, और यहीं आप इसे देखते हैं।
- **दोनों कंटेनर रनटाइम शुरू हुए।** `Container Runtime Interface for OCI (CRI-O)`
  और `Docker Application Container Engine` दोनों `[ OK ]` हैं, जो dual-runtime व्यवहार
  का बूट-टाइम प्रमाण है जो लोगों को [crictl](../../commands/system/crictl/) और
  [docker](../../commands/system/docker/) में आश्चर्यचकित करता है।
- **`VP Manager image load` और `Argo Watch service`** — `vpm` और Argo का शुरू होना।
- **प्रॉम्प्ट नोड का अपना है**, उसके ऑडिट बैनर के पीछे। सीरियल कंसोल आपको एक
  लॉगिन प्रॉम्प्ट देता है, सेशन नहीं।

<Aside type="caution" title="इंटरेक्टिव संलग्नता के लिए एक वास्तविक टर्मिनल की आवश्यकता है — लेकिन इसे स्क्रिप्ट किया जा सकता है">
`az serial-console connect` टर्मिनल को raw mode में डालता है, इसलिए यह किसी
pipeline या TTY रहित किसी संदर्भ से नहीं चल सकता। यह Azure से संपर्क करने से पहले,
client-side विफल होता है:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

वह traceback टर्मिनल हैंडलिंग है, सीरियल कंसोल आउटेज नहीं।

हालाँकि, अटैच स्वयं **स्वचालित** किया जा सकता है — CLI के बजाय सीधे websocket को
चलाएँ। उपरोक्त ट्रांसक्रिप्ट उसी तरह कैप्चर की गई थी, बिना किसी TTY के। देखें
`scripts/serial_console_capture.py`, जो कि वह तरीका है जिससे आप किसी ऐसे नोड से बूट
साक्ष्य एकत्र करेंगे जो बिना किसी मानव के टर्मिनल पर बैठे पंजीकृत होने में विफल रहा।
</Aside>

<Aside type="caution" title="पुनः प्रयास की अपेक्षा करें: गेटवे लगभग हर दूसरे प्रयास को अस्वीकार करता है">
गेटवे का पहला फ्रेम एक challenge है, आउटपुट नहीं, और client इसका उत्तर bearer token से
देता है। यह सही तरीके से करने पर भी socket अक्सर तुरंत बंद हो जाती है:

```
[close] code=1011 reason=Connection not trusted
```

तीन नोड्स पर बार-बार प्रयास के दौरान मापा गया, यह बारी-बारी से होता है: एक ही नोड पर
अस्वीकृति के बाद सफलता आती है। यह एक पिछले सेशन के अभी भी hold में रहने और अस्वीकृत
प्रयास के उसे साफ करने के अनुरूप है।

**यह क्रेडेंशियल की समस्या नहीं है**, संदेश के बावजूद। पुनः प्रयास करना आमतौर पर पर्याप्त
है, यही कारण है कि `scripts/serial_console_capture.py` डिफ़ॉल्ट रूप से पुनः प्रयास करता है।

सेशन अनुरोध और challenge दोनों के लिए एक ही टोकन का उपयोग करें, `az` एक्सटेंशन की तरह।
यह सही अभ्यास है, लेकिन यह इसका कारण नहीं है।
</Aside>

## यहाँ आप क्या देख सकते हैं जो API नहीं दिखा सकता

- **cloud-init** चलना, विफल होना, या कभी शुरू न होना — एक नोड का सामान्य कारण
  जो कभी पंजीकृत नहीं होता।
- **पंजीकरण प्रयास** `register.ves.volterra.io` के विरुद्ध, जिसमें कॉन्फ़िगरेशन त्रुटि
  या टेनेंट द्वारा अस्वीकृत टोकन शामिल है।
- **Kernel और बूट संदेश** किसी भी एजेंट के चलने से पहले।
- नोड जब **कोई कार्यशील नेटवर्क पथ नहीं** होता, जो हर दूसरे मार्ग को विफल करता है।

किसी ऐसे नोड के लिए जो `ONLINE` है, debug API को प्राथमिकता दें: यह स्क्रिप्टयोग्य है,
यह ऐसे साक्ष्य उत्पन्न करता है जिन्हें आप पुनः चला सकते हैं, और यह एकल सीरियल पोर्ट को
अवरुद्ध नहीं करता।
