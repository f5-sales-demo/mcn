Azure Serial Console नोड के एमुलेटेड सीरियल पोर्ट से Azure
प्लेटफ़ॉर्म के माध्यम से जुड़ता है। यह F5 Distributed Cloud कंट्रोल प्लेन, नोड के
डेटा प्लेन, या नोड द्वारा नियंत्रित किसी भी नेटवर्क पथ से नहीं गुज़रता — यही कारण है
कि यह तब काम करता है जब और कुछ नहीं करता।

इसका उपयोग तब करें जब कोई CE **कभी चालू न हुआ हो**: पंजीकरण विफल हो गया, साइट टेनेंट
से अनुपस्थित हो, या नोड चालू तो है लेकिन उसका कोई रूट बाहर नहीं जाता। इन सभी स्थितियों
में [debug API](../debug-api/) के पास रिले करने के लिए कोई टनल नहीं होती, और SSH
नोड पर शिप के समय बंद रहता है।

## पूर्वापेक्षा: बूट डायग्नोस्टिक्स

Azure को VM पर सीरियल कंसोल संलग्न करने से पहले बूट डायग्नोस्टिक्स की आवश्यकता होती है।
यह `terraform/modules/ce-node` द्वारा सक्षम किया जाता है:

```hcl
boot_diagnostics {}
```

एक खाली ब्लॉक Azure-प्रबंधित स्टोरेज का चयन करता है, इसलिए कोई डायग्नोस्टिक्स स्टोरेज
अकाउंट, लाइफसाइकिल पॉलिसी या एक्सेस कुंजी स्वयं प्रबंधित नहीं करनी होती। किसी नोड पर इसे
सत्यापित करें:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="इसे सक्षम करना पूर्वव्यापी नहीं है">
बूट डायग्नोस्टिक्स सीरियल लॉग को **बूट के समय** कैप्चर करता है। किसी पहले से चल रहे VM के
लिए इसे चालू करने से उस बूट का लॉग नहीं बनता जो पहले हो चुका है, इसलिए
`az vm boot-diagnostics get-boot-log` यह उत्तर देता है:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

यह अपेक्षित है, कोई दोष नहीं। नोड के अगली बार रिबूट होने के बाद बूट लॉग उपलब्ध होगा। हालाँकि,
लाइव कंसोल अटैच तुरंत काम करता है — यह लॉग पर निर्भर नहीं करता।
</Aside>

## टर्मिनल के बिना उपलब्धता जाँचना

संलग्न करने के लिए एक इंटरैक्टिव सत्र की आवश्यकता होती है, लेकिन यह *संलग्न होगा या नहीं*
यह दो API कॉल से पता चलता है। दोनों हेल्थ चेक में उपयोगी हैं।

सब्सक्रिप्शन के लिए सेवा सक्षम होनी चाहिए — एक व्यवस्थापक इसे टेनेंट-व्यापी रूप से अक्षम
कर सकता है:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

फिर किसी विशिष्ट नोड के सीरियल पोर्ट से कनेक्शन का अनुरोध करें:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

`wss://` से शुरू होने वाली `connectionString` — इस डिप्लॉयमेंट पर
`eastus.gateway.serialconsole.azure.com` — का अर्थ है कि कंसोल अभी संलग्न करने योग्य है।
बूट डायग्नोस्टिक्स सक्षम होने से पहले, इस कॉल के पास संलग्न करने के लिए कुछ नहीं था।

<Aside type="danger" title="वह कनेक्शन स्ट्रिंग एक क्रेडेंशियल है">
यह एक URL में एम्बेड किया गया अल्पकालिक बेयरर टोकन है। इसे लॉग न करें, किसी टिकट में
पेस्ट न करें, या कमिट न करें। जब आप यह प्रदर्शित कर रहे हों कि कॉल सफल हुई, तो केवल
होस्ट प्रिंट करें।
</Aside>

## संलग्न करना

<Steps>

1. एक्सटेंशन एक बार इंस्टॉल करें:

   ```bash
   az extension add --name serial-console
   ```

2. संलग्न करें:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. आप नोड के अपने लॉगिन प्रॉम्प्ट पर पहुँचते हैं, शेल पर नहीं। यह Site CLI है, और
   इसे नोड पर सेट क्रेडेंशियल की आवश्यकता होती है — प्रोविज़निंग से व्यवस्थापक पासवर्ड,
   या change-password एंडपॉइंट के माध्यम से सेट किया गया पासवर्ड। सीरियल कंसोल *चैनल*
   के काम करने को सिद्ध करता है; यह प्रमाणीकरण को बायपास नहीं करता।

</Steps>

<Aside type="caution" title="इसे एक वास्तविक टर्मिनल की आवश्यकता है">
`az serial-console connect` टर्मिनल को रॉ मोड में डालता है, इसलिए इसे किसी स्क्रिप्ट,
पाइपलाइन, या बिना TTY के किसी संदर्भ से नहीं चलाया जा सकता। यह Azure से संपर्क करने
से पहले क्लाइंट-साइड पर विफल होता है:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

वह ट्रेसबैक टर्मिनल हैंडलिंग है, सीरियल कंसोल आउटेज नहीं — ऊपर दिए गए दो API कॉल
फिर भी कंसोल को उपलब्ध के रूप में रिपोर्ट करेंगे। यदि आपको एक स्वचालन योग्य संकेत
चाहिए, तो अटैच को स्क्रिप्ट करने का प्रयास करने के बजाय उनका उपयोग करें।
</Aside>

## यहाँ आप क्या देख सकते हैं जो API नहीं दिखा सकता

- **cloud-init** चल रहा है, विफल हो रहा है, या कभी शुरू नहीं हुआ — एक नोड का सामान्य
  कारण जो कभी पंजीकृत नहीं होता।
- **पंजीकरण प्रयास** `register.ves.volterra.io` के विरुद्ध, जिसमें कॉन्फ़िगरेशन त्रुटि
  या टेनेंट द्वारा अस्वीकृत टोकन शामिल है।
- **कर्नेल और बूट संदेश** किसी भी एजेंट के चलने से पहले।
- वह नोड जिसका **कोई कार्यशील नेटवर्क पथ नहीं है**, जो हर दूसरे मार्ग को विफल कर देता है।

किसी नोड के लिए जो `ONLINE` *है*, debug API को प्राथमिकता दें: यह स्क्रिप्ट योग्य है,
यह ऐसे साक्ष्य उत्पन्न करता है जिन्हें आप पुनः चला सकते हैं, और यह एकल सीरियल पोर्ट पर
कब्जा नहीं करता।
