इस परिनियोजन के एक CE से 2026-07-28 को कैप्चर किया गया। `sitecli/capture-manifest.json`
यह दर्ज करता है कि कौन सा नोड था, और `scripts/capture-sitecli.sh --check` कमांड सतह को
एक लाइव CE के विरुद्ध पुनः सत्यापित करता है।

Azure Serial Console, Azure प्लेटफ़ॉर्म के माध्यम से नोड के एमुलेटेड सीरियल पोर्ट से जुड़ता है।
यह F5 Distributed Cloud कंट्रोल प्लेन, नोड के डेटा प्लेन, या नोड द्वारा नियंत्रित किसी नेटवर्क
पथ से नहीं गुजरता — और ठीक इसी कारण यह तब भी काम करता है जब कुछ और काम नहीं करता।

इसका सहारा तब लें जब कोई CE **कभी ऊपर ही नहीं आया**: रजिस्ट्रेशन विफल रहा, साइट टेनेंट में
मौजूद नहीं है, या नोड चालू है पर बाहर जाने का कोई रास्ता नहीं है। इन सभी स्थितियों में
[debug API](../debug-api/) के पास रिले करने के लिए कोई टनल नहीं होता। [SSH](../ssh/) विफल
रजिस्ट्रेशन के बाद भी बचा रहता है, लेकिन तभी जब उसकी कुंजी पहले बूट पर ही लिखी जा चुकी हो और
आप VNet के भीतर से नोड के आंतरिक पते तक पहुँच सकें — और किसी ऐसे नोड के लिए, जिससे आप पहली बार
मिल रहे हैं, इनमें से कोई भी सत्य नहीं होता।

यदि नोड के पास *कोई भी* कार्यशील नेटवर्क पथ है तो इससे पहले [Site Console](../site-console/)
आज़माएँ: वह भी विफल रजिस्ट्रेशन के बाद बचा रहता है, उसे कोई कुंजी नहीं चाहिए, और वह उस व्यक्ति को
बाहर नहीं करता जो पहले से नोड देख रहा है। सीरियल कंसोल तब बचता है जब नेटवर्क पथ ही टूटी हुई
चीज़ हो।

## पूर्वापेक्षा: बूट डायग्नोस्टिक्स

सीरियल कंसोल जोड़ने से पहले Azure को VM पर बूट डायग्नोस्टिक्स चाहिए।
यह `terraform/modules/ce-node` द्वारा सक्षम किया जाता है:

```hcl
boot_diagnostics {}
```

एक खाली ब्लॉक Azure-प्रबंधित स्टोरेज चुनता है, इसलिए कोई डायग्नोस्टिक्स स्टोरेज
अकाउंट, लाइफसाइकल पॉलिसी या एक्सेस की अपने पास रखने की ज़रूरत नहीं। किसी नोड पर इसकी पुष्टि करें:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="इसे सक्षम करना पूर्वप्रभावी नहीं है">
बूट डायग्नोस्टिक्स सीरियल लॉग **बूट के समय** कैप्चर करता है। पहले से चल रहे VM पर इसे चालू
करने से उस बूट का लॉग नहीं बनता जो पहले ही हो चुका है, इसलिए
`az vm boot-diagnostics get-boot-log` यह उत्तर देता है:

```text
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

यह अपेक्षित है, कोई खराबी नहीं। नोड के अगली बार रीबूट होने के बाद बूट लॉग मौजूद होता है। लाइव
कंसोल अटैच, हालाँकि, तुरंत काम करता है — यह लॉग पर निर्भर नहीं है।
</Aside>

## टर्मिनल के बिना उपलब्धता की जाँच

अटैच करने के लिए इंटरैक्टिव सत्र चाहिए, लेकिन यह *अटैच होगा या नहीं* — इसका उत्तर दो API
कॉल हैं। दोनों हेल्थ चेक में उपयोगी हैं।

सेवा सब्सक्रिप्शन के लिए सक्षम होनी चाहिए — कोई प्रशासक इसे पूरे टेनेंट में अक्षम कर सकता है:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

फिर किसी विशिष्ट नोड के सीरियल पोर्ट से कनेक्शन के लिए अनुरोध करें:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

`wss://` से शुरू होने वाला `connectionString` — इस परिनियोजन पर
`eastus.gateway.serialconsole.azure.com` — का अर्थ है कि कंसोल अभी अटैच किया जा सकता है।
बूट डायग्नोस्टिक्स सक्षम होने से पहले, इस कॉल के पास अटैच करने के लिए कुछ नहीं था।

<Aside type="danger" title="वह कनेक्शन स्ट्रिंग एक क्रेडेंशियल है">
यह URL में अंतर्निहित एक अल्पकालिक bearer टोकन है। इसे लॉग न करें, किसी टिकट में पेस्ट न करें,
और कमिट न करें। जब आप यह दिखा रहे हों कि कॉल सफल हुई, तो केवल होस्ट प्रिंट करें।
</Aside>

## अटैच करना

<Steps>

1. एक्सटेंशन एक बार इंस्टॉल करें:

   ```bash
   az extension add --name serial-console
   ```

2. अटैच करें:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. आप नोड के अपने लॉगिन प्रॉम्प्ट पर पहुँचते हैं, शेल पर नहीं, अप्लायंस के ऑडिट
   बैनर के पीछे। सीरियल कंसोल सिद्ध करता है कि *चैनल* काम करता है; यह प्रमाणीकरण को बायपास नहीं करता।

   <Aside type="caution" title="सीरियल लॉगिन कौन सा क्रेडेंशियल स्वीकार करता है, यह सत्यापित नहीं है">
   इस परिनियोजन पर किसी ने सीरियल कंसोल के ज़रिए लॉगिन पूरा नहीं किया है, इसलिए यह पृष्ठ यह
   नहीं बताता कि क्या टाइप करना है। `admin` वह अप्लायंस अकाउंट है जिसका शेल Site CLI है, और
   वही अकाउंट पासवर्ड के साथ
   [Site Console](../site-console/) पर प्रमाणित होता है — लेकिन सीरियल कंसोल लॉगिन पर पासवर्ड
   काम करता है, यह दिखाया नहीं गया है, और `admin` के लिए `sshd` केवल-कुंजी है, इसलिए ये दोनों
   प्रत्यक्षतः एक ही क्रेडेंशियल पथ नहीं हैं।
   </Aside>

</Steps>

`f5-xc-ce-vm-01` से कैप्चर किया गया, बीच में वह भाग हटा दिया गया जहाँ systemd यूनिट आउटपुट
कुछ नहीं जोड़ता:

```text file=../../../_data/serial-console-boot.txt
```

उस ट्रांसक्रिप्ट में चार बातें ध्यान देने योग्य हैं, क्योंकि वे उन प्रश्नों का उत्तर देती हैं जो
debug API नहीं दे सकता:

- **cloud-init पूर्ण हुआ** — `Datasource DataSourceAzure`, 22.37 सेकंड पर समाप्त।
  जो नोड कभी रजिस्टर नहीं होता, वह प्रायः यहीं विफल हुआ था, और यही जगह है जहाँ आप इसे देखते हैं।
- **दोनों कंटेनर रनटाइम शुरू हुए।** `Container Runtime Interface for OCI (CRI-O)`
  और `Docker Application Container Engine` दोनों `[ OK ]` हैं, जो उस दोहरे-रनटाइम व्यवहार का
  बूट-समय प्रमाण है जो
  [crictl](../../commands/system/crictl/) और [docker](../../commands/system/docker/) में लोगों को चौंकाता है।
- **`VP Manager image load` और `Argo Watch service`** — `vpm` और Argo का ऊपर आना।
- **प्रॉम्प्ट नोड का अपना है**, उसके ऑडिट बैनर के पीछे। सीरियल कंसोल आपको एक
  लॉगिन प्रॉम्प्ट देता है, सत्र नहीं।

<Aside type="caution" title="इंटरैक्टिव रूप से अटैच करने के लिए वास्तविक टर्मिनल चाहिए — लेकिन इसे स्क्रिप्ट किया जा सकता है">
`az serial-console connect` टर्मिनल को raw मोड में डाल देता है, इसलिए यह किसी पाइपलाइन या
TTY-रहित संदर्भ से नहीं चल सकता। यह Azure से संपर्क करने से पहले, क्लाइंट-साइड पर विफल होता है:

```text
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

वह ट्रेसबैक टर्मिनल हैंडलिंग है, सीरियल कंसोल आउटेज नहीं।

अटैच स्वयं, हालाँकि, **स्वचालित किया जा सकता है** — CLI के बजाय सीधे websocket चलाएँ।
ऊपर का ट्रांसक्रिप्ट इसी तरह, बिना TTY के, कैप्चर किया गया था। देखें
`scripts/serial_console_capture.py`, जिसके ज़रिए आप उस नोड से बूट प्रमाण एकत्र करेंगे जो
रजिस्टर होने में विफल रहा, और वह भी बिना किसी व्यक्ति के टर्मिनल पर बैठे।
</Aside>

<Aside type="caution" title="पुनः प्रयास की अपेक्षा रखें: गेटवे लगभग हर दूसरे प्रयास को अस्वीकार करता है">
गेटवे का पहला फ़्रेम एक चैलेंज होता है, आउटपुट नहीं, और क्लाइंट उसका उत्तर एक bearer टोकन से
देता है। यह सही ढंग से करने पर भी सॉकेट अक्सर तुरंत बंद हो जाता है:

```text
[close] code=1011 reason=Connection not trusted
```

देखा गया व्यवहार: यह रुक-रुक कर सफल होता है, और लगातार उपयोग में रिसोर्स ग्रुप का हर नोड
अस्वीकार कर देता है — उन नोड्स सहित जो कुछ मिनट पहले काम कर रहे थे।
`scripts/serial_console_capture.py` डिफ़ॉल्ट रूप से पुनः प्रयास करता है क्योंकि पुनः प्रयास
अक्सर काम करता है।

**कारण स्थापित नहीं है।** क्या-क्या खारिज किया जा चुका है, क्योंकि इनमें से हर एक एक संभावित
अनुमान है जो समय बर्बाद करता है:

| यह नहीं | पुष्टि कैसे करें |
| --- | --- |
| ARM/compute थ्रॉटलिंग | वह ARM कॉल पर HTTP `429` लौटाता है। यह एक अलग डेटा चैनल पर websocket क्लोज़ है। |
| प्रॉक्सी द्वारा TLS इंटरसेप्शन | `openssl s_client -connect <region>.gateway.serialconsole.azure.com:443 \| openssl x509 -noout -issuer`. एक वास्तविक `O=Microsoft Corporation` जारीकर्ता इसे खारिज करता है; जारीकर्ता के रूप में कोई प्रॉक्सी वेंडर इसकी पुष्टि करता है, और समाधान है `*.serialconsole.azure.com` को allow-list करना। |
| बूट डायग्नोस्टिक्स अक्षम | `az vm show -g <rg> -n <vm> --query diagnosticsProfile` का `enabled: true` बताना। |
| ग्रांट और चैलेंज के बीच टोकन बेमेल | दोनों के लिए एक ही टोकन का उपयोग सही अभ्यास है, पर इससे क्लोज़ नहीं रुकता। |

जो *वास्तव में* प्रलेखित Azure व्यवहार है: **प्रति VM एक सीरियल कंसोल सत्र, और दूसरा
सफल अनुरोध पहले को बाहर कर देता है।** बाहर किया गया उपयोगकर्ता डिस्कनेक्ट होता है पर लॉग आउट
नहीं, इसलिए शेल सत्र बचा रहता है। एक नोड को डिबग करने वाले दो लोग एक-दूसरे को बार-बार
विस्थापित करेंगे।

थोक कार्य के लिए [debug API](../debug-api/) या [SSH](../ssh/) को प्राथमिकता दें, इनमें से
किसी पर ये सीमाएँ नहीं हैं। विशेष रूप से SSH पर कोई पेस्ट सीमा और कोई एकल-सत्र प्रतिबंध नहीं है,
इसलिए जब भी नोड VNet के भीतर से पहुँच योग्य हो, वही बेहतर विकल्प है।
</Aside>

<Aside type="caution" title="पेस्ट की सीमा 2,048 वर्ण है">
Azure सीरियल पोर्ट पर अधिक भार से बचने के लिए सीरियल कंसोल पेस्ट की लंबाई 2,048 वर्णों तक
सीमित करता है। कोई लंबा कमांड — या एक ही राइट में कमांडों का बैच — भेजना इस तरह विफल होता है
जो लंबाई-सीमा की बजाय हैंग या थ्रॉटल जैसा दिखता है।

कमांड एक-एक करके भेजें। सीरियल कंसोल पर किसी भी थोक संग्रह के लिए यह एक वास्तविक अड़चन है,
और उस कार्य के लिए [debug API](../debug-api/) को प्राथमिकता देने का एक और कारण।
</Aside>

## यहाँ आप क्या देख सकते हैं जो API आपको नहीं दिखा सकता

- **cloud-init** का चलना, विफल होना, या कभी शुरू ही न होना — किसी ऐसे नोड का सामान्य कारण
  जो कभी रजिस्टर नहीं होता।
- `register.ves.volterra.io` के विरुद्ध **रजिस्ट्रेशन प्रयास**, जिसमें कोई
  कॉन्फ़िगरेशन त्रुटि या टेनेंट द्वारा अस्वीकृत टोकन शामिल है।
- किसी भी एजेंट के चलने से पहले के **कर्नेल और बूट संदेश**।
- नोड जब उसके पास **कोई कार्यशील नेटवर्क पथ न हो**, जो हर दूसरे मार्ग को नाकाम कर देता है।

जो नोड `ONLINE` *है*, उसके लिए debug API को प्राथमिकता दें: यह स्क्रिप्ट योग्य है, यह ऐसा
प्रमाण उत्पन्न करता है जिसे आप दोबारा चला सकते हैं, और यह एकल सीरियल पोर्ट पर कब्ज़ा नहीं करता।
