Azure Serial Console, Azure प्लेटफ़ॉर्म के माध्यम से नोड के एमुलेटेड सीरियल पोर्ट से जुड़ता है।
यह F5 Distributed Cloud कंट्रोल प्लेन, नोड के डेटा प्लेन, या नोड द्वारा नियंत्रित किसी भी नेटवर्क
पथ से नहीं गुजरता — और ठीक इसी कारण यह तब काम करता है जब बाकी कुछ नहीं करता।

इसका सहारा तब लें जब कोई CE **कभी ऊपर ही नहीं आया**: रजिस्ट्रेशन विफल रहा, साइट टेनेंट में
मौजूद नहीं है, या नोड चल रहा है पर उसके पास बाहर जाने का कोई रूट नहीं है। इन सभी मामलों में
[debug API](../debug-api/) के पास रिले करने के लिए कोई टनल नहीं होता, और इस बिल्ड पर
[SSH प्रमाणीकरण नहीं कर सकता](../ssh/)।

## पूर्वापेक्षा: बूट डायग्नोस्टिक्स

सीरियल कंसोल अटैच करने से पहले Azure को VM पर बूट डायग्नोस्टिक्स की आवश्यकता होती है।
यह `terraform/modules/ce-node` द्वारा सक्षम किया जाता है:

```hcl
boot_diagnostics {}
```

एक खाली ब्लॉक Azure-प्रबंधित स्टोरेज चुनता है, इसलिए किसी डायग्नोस्टिक्स स्टोरेज
अकाउंट, लाइफ़साइकल पॉलिसी या एक्सेस की का स्वामित्व रखने की आवश्यकता नहीं है। किसी नोड पर इसकी पुष्टि करें:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="इसे सक्षम करना पूर्वप्रभावी नहीं है">
बूट डायग्नोस्टिक्स सीरियल लॉग को **बूट के समय** कैप्चर करता है। पहले से चल रही VM पर इसे
चालू करने से उस बूट का लॉग नहीं बनता जो पहले ही हो चुका है, इसलिए
`az vm boot-diagnostics get-boot-log` यह उत्तर देता है:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

यह अपेक्षित है, कोई दोष नहीं। नोड के अगली बार रीबूट होने के बाद बूट लॉग मौजूद होता है। लाइव
कंसोल अटैच, हालाँकि, तुरंत काम करता है — यह लॉग पर निर्भर नहीं है।
</Aside>

## टर्मिनल के बिना उपलब्धता जाँचना

अटैच करने के लिए इंटरैक्टिव सत्र चाहिए, लेकिन यह जानना कि वह अटैच *होगा* या नहीं, दो API
कॉल भर है। दोनों हेल्थ चेक में उपयोगी हैं।

सेवा सब्सक्रिप्शन के लिए सक्षम होनी चाहिए — एक प्रशासक इसे टेनेंट-व्यापी रूप से अक्षम कर सकता है:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

फिर किसी विशिष्ट नोड के सीरियल पोर्ट से कनेक्शन के लिए अनुरोध करें:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

`wss://` से शुरू होने वाला `connectionString` — इस डिप्लॉयमेंट पर
`eastus.gateway.serialconsole.azure.com` — का अर्थ है कि कंसोल अभी अटैच करने योग्य है।
बूट डायग्नोस्टिक्स सक्षम होने से पहले, इस कॉल के पास अटैच करने के लिए कुछ नहीं था।

<Aside type="danger" title="वह कनेक्शन स्ट्रिंग एक क्रेडेंशियल है">
यह एक URL में एम्बेडेड अल्पकालिक bearer टोकन है। इसे लॉग न करें, किसी टिकट में पेस्ट न करें,
और कमिट न करें। जब आप यह दर्शा रहे हों कि कॉल काम कर गई, तो केवल होस्ट प्रिंट करें।
</Aside>

## अटैच करना

<Steps>

1. एक्सटेंशन एक बार इंस्टॉल करें:

   ```bash
   az extension add --name serial-console
   ```

2. अटैच करें:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. आप नोड के अपने लॉगिन प्रॉम्प्ट पर पहुँचते हैं, किसी शेल पर नहीं। यह Site CLI है, और
   इसे नोड पर सेट किए गए क्रेडेंशियल्स की आवश्यकता होती है — प्रोविज़निंग के समय का एडमिन पासवर्ड, या
   change-password एंडपॉइंट के माध्यम से सेट किया गया कोई पासवर्ड। सीरियल कंसोल यह साबित करता है कि *चैनल*
   काम करता है; यह प्रमाणीकरण को बायपास नहीं करता।

</Steps>

`f5-xc-ce-vm-01` से कैप्चर किया गया, बीच में वह हिस्सा हटाया गया है जहाँ systemd यूनिट आउटपुट
कुछ नहीं जोड़ता:

```text file=../../../_data/serial-console-boot.txt
```

उस ट्रांसक्रिप्ट में चार बातें ध्यान देने योग्य हैं, क्योंकि वे उन प्रश्नों का उत्तर देती हैं जिनका
debug API नहीं दे सकता:

- **cloud-init पूरा हुआ** — `Datasource DataSourceAzure`, 22.37 सेकंड पर समाप्त।
  ऐसा नोड जो कभी रजिस्टर नहीं होता, आमतौर पर यहीं विफल होता है, और यहीं आप इसे देख सकते हैं।
- **दोनों कंटेनर रनटाइम शुरू हुए।** `Container Runtime Interface for OCI (CRI-O)`
  और `Docker Application Container Engine` दोनों `[ OK ]` हैं, जो उस दोहरे-रनटाइम व्यवहार का
  बूट-टाइम प्रमाण है जो लोगों को
  [crictl](../../commands/system/crictl/) और [docker](../../commands/system/docker/) में चौंकाता है।
- **`VP Manager image load` और `Argo Watch service`** — `vpm` और Argo का ऊपर आना।
- **प्रॉम्प्ट नोड का स्वयं का है**, उसके ऑडिट बैनर के पीछे। सीरियल कंसोल आपको एक
  लॉगिन प्रॉम्प्ट देता है, कोई सत्र नहीं।

<Aside type="caution" title="इंटरैक्टिव रूप से अटैच करने के लिए वास्तविक टर्मिनल चाहिए — पर इसे स्क्रिप्ट किया जा सकता है">
`az serial-console connect` टर्मिनल को raw मोड में डालता है, इसलिए यह किसी पाइपलाइन या
TTY रहित किसी भी संदर्भ से नहीं चल सकता। यह Azure से संपर्क करने से पहले ही, क्लाइंट-साइड पर विफल होता है:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

वह ट्रेसबैक टर्मिनल हैंडलिंग है, सीरियल कंसोल का आउटेज नहीं।

अटैच स्वयं, हालाँकि, **स्वचालित किया जा सकता** है — CLI के बजाय websocket को सीधे चलाएँ।
ऊपर का ट्रांसक्रिप्ट उसी तरह, बिना किसी TTY के कैप्चर किया गया था। देखें
`scripts/serial_console_capture.py`, जिससे आप बिना किसी व्यक्ति के टर्मिनल पर बैठे उस नोड से
बूट प्रमाण एकत्र कर सकते हैं जो रजिस्टर होने में विफल रहा।
</Aside>

<Aside type="caution" title="पुनःप्रयास की अपेक्षा रखें: गेटवे लगभग हर दूसरे प्रयास को अस्वीकार करता है">
गेटवे का पहला फ़्रेम एक चैलेंज होता है, आउटपुट नहीं, और क्लाइंट उसका उत्तर एक bearer टोकन से देता है।
यह सही ढंग से करने पर भी सॉकेट अक्सर तुरंत बंद हो जाता है:

```
[close] code=1011 reason=Connection not trusted
```

देखा गया व्यवहार: यह रुक-रुक कर सफल होता है, और लगातार उपयोग के दौरान रिसोर्स ग्रुप का हर नोड
अस्वीकार करने लगता है — उन नोड्स सहित जो कुछ मिनट पहले काम कर रहे थे।
`scripts/serial_console_capture.py` डिफ़ॉल्ट रूप से पुनःप्रयास करता है क्योंकि पुनःप्रयास अक्सर काम करता है।

**कारण स्थापित नहीं है।** जो खारिज कर दिया गया है, क्योंकि प्रत्येक एक प्रशंसनीय
अनुमान है जो समय बरबाद करता है:

| यह नहीं है | कैसे पुष्टि करें |
| --- | --- |
| ARM/compute थ्रॉटलिंग | वह ARM कॉल पर HTTP `429` लौटाता है। यह एक अलग डेटा चैनल पर websocket क्लोज़ है। |
| किसी प्रॉक्सी द्वारा TLS इंटरसेप्शन | `openssl s_client -connect <region>.gateway.serialconsole.azure.com:443 \| openssl x509 -noout -issuer`. एक वास्तविक `O=Microsoft Corporation` इशूअर इसे खारिज कर देता है; इशूअर के रूप में कोई प्रॉक्सी वेंडर इसकी पुष्टि करता है, और समाधान है `*.serialconsole.azure.com` को अनुमति-सूची में डालना। |
| बूट डायग्नोस्टिक्स अक्षम | `az vm show -g <rg> -n <vm> --query diagnosticsProfile` द्वारा `enabled: true` रिपोर्ट किया जाना। |
| ग्रांट और चैलेंज के बीच टोकन बेमेल | दोनों के लिए एक ही टोकन का उपयोग सही प्रथा है, पर यह क्लोज़ को नहीं रोकता। |

जो Azure का *प्रलेखित* व्यवहार **है**: **प्रति VM एक सीरियल कंसोल सत्र, और एक दूसरा
सफल अनुरोध पहले वाले को हटा देता है।** हटाया गया उपयोगकर्ता डिस्कनेक्ट हो जाता है पर लॉग आउट नहीं होता,
इसलिए शेल सत्र बचा रहता है। एक ही नोड को डिबग करते दो लोग बार-बार एक-दूसरे को विस्थापित करेंगे।

बड़े पैमाने के कार्य के लिए [debug API](../debug-api/) को प्राथमिकता दें, जिसमें इनमें से कोई सीमा नहीं है।
[SSH कोई विकल्प नहीं है](../ssh/) — इस बिल्ड पर इसे सक्षम नहीं किया जा सकता।
</Aside>

<Aside type="caution" title="पेस्ट की सीमा 2,048 वर्ण है">
सीरियल पोर्ट पर अधिक भार से बचने के लिए Azure सीरियल कंसोल पेस्ट की लंबाई 2,048 वर्णों तक सीमित करता है।
कोई लंबा कमांड — या एक ही राइट में कमांड्स का बैच — भेजने पर यह ऐसे तरीके से विफल होता है
जो लंबाई सीमा के बजाय हैंग या थ्रॉटल जैसा लगता है।

कमांड एक-एक करके भेजें। सीरियल कंसोल पर किसी भी बल्क संग्रहण के लिए यह एक वास्तविक अड़चन है,
और उस काम के लिए [debug API](../debug-api/) को प्राथमिकता देने का एक और कारण है।
</Aside>

## यहाँ आप क्या देख सकते हैं जो API आपको नहीं दिखा सकता

- **cloud-init** का चलना, विफल होना, या कभी शुरू न होना — ऐसे नोड का सामान्य कारण
  जो कभी रजिस्टर नहीं होता।
- `register.ves.volterra.io` के विरुद्ध **रजिस्ट्रेशन प्रयास**, जिसमें कोई
  कॉन्फ़िगरेशन त्रुटि या टेनेंट द्वारा अस्वीकृत टोकन शामिल है।
- किसी एजेंट के चलने से पहले के **कर्नेल और बूट संदेश**।
- वह नोड जब उसके पास **कोई कार्यशील नेटवर्क पथ नहीं** है, जो हर दूसरे रास्ते को नाकाम कर देता है।

ऐसे नोड के लिए जो `ONLINE` *है*, debug API को प्राथमिकता दें: यह स्क्रिप्ट-योग्य है, यह ऐसा प्रमाण
उत्पन्न करता है जिसे आप दोबारा चला सकते हैं, और यह एकल सीरियल पोर्ट पर कब्ज़ा नहीं करता।
