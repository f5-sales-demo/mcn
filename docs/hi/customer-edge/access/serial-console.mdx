Azure Serial Console नोड के एमुलेटेड सीरियल पोर्ट से Azure
प्लेटफ़ॉर्म के माध्यम से जुड़ता है। यह F5 Distributed Cloud कंट्रोल प्लेन, नोड के
डेटा प्लेन, या नोड द्वारा नियंत्रित किसी भी नेटवर्क पथ से नहीं गुज़रता — और यही कारण है कि यह तब काम करता है
जब कुछ और नहीं करता।

इसका उपयोग तब करें जब कोई CE **कभी चालू नहीं हुआ**: पंजीकरण विफल हो गया, साइट
टेनेंट से अनुपस्थित है, या नोड चालू है लेकिन उसके पास बाहर का कोई रूट नहीं है। इन सभी स्थितियों में
[debug API](../debug-api/) के पास रिले करने के लिए कोई टनल नहीं होती। [SSH](../ssh/) एक
विफल पंजीकरण में भी काम करता है, लेकिन केवल तभी जब उसकी key पहले बूट पर लिखी जा चुकी हो और आप
VNet के अंदर से नोड के आंतरिक पते तक पहुँच सकते हों — जो किसी ऐसे नोड के लिए सत्य नहीं है जिससे आप पहली बार मिल रहे हों।

## पूर्व-आवश्यकता: बूट डायग्नोस्टिक्स

Azure को VM पर बूट डायग्नोस्टिक्स की आवश्यकता है इससे पहले कि वह सीरियल कंसोल संलग्न करे।
यह `terraform/modules/ce-node` द्वारा सक्षम किया जाता है:

```hcl
boot_diagnostics {}
```

एक रिक्त ब्लॉक Azure-प्रबंधित स्टोरेज का चयन करता है, इसलिए कोई डायग्नोस्टिक्स स्टोरेज
अकाउंट, lifecycle policy या access key नहीं है जिसे संभालना पड़े। किसी नोड पर इसकी पुष्टि करें:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="इसे सक्षम करना पूर्वव्यापी नहीं है">
बूट डायग्नोस्टिक्स सीरियल लॉग को **बूट के समय** कैप्चर करता है। किसी ऐसे VM के लिए इसे चालू करना जो
पहले से चल रहा है, उस बूट का लॉग नहीं बनाता जो पहले ही हो चुकी है, इसलिए
`az vm boot-diagnostics get-boot-log` यह उत्तर देता है:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

यह अपेक्षित है, कोई दोष नहीं। बूट लॉग नोड के अगली बार रीबूट होने के बाद मौजूद होगा। लाइव
कंसोल अटैच, हालाँकि, तुरंत काम करता है — यह लॉग पर निर्भर नहीं करता।
</Aside>

## टर्मिनल के बिना उपलब्धता की जाँच

अटैच करने के लिए एक इंटरेक्टिव सेशन की आवश्यकता होती है, लेकिन यह *अटैच होगा या नहीं* यह दो API
कॉल से जाना जा सकता है। दोनों हेल्थ चेक में उपयोगी हैं।

सेवा सब्सक्रिप्शन के लिए सक्षम होनी चाहिए — एक एडमिनिस्ट्रेटर इसे
टेनेंट-स्तर पर अक्षम कर सकता है:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

फिर किसी विशिष्ट नोड के सीरियल पोर्ट से कनेक्शन के लिए अनुरोध करें:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

`wss://` से शुरू होने वाला `connectionString` — इस deployment में
`eastus.gateway.serialconsole.azure.com` — का अर्थ है कि कंसोल अभी
संलग्न किया जा सकता है। बूट डायग्नोस्टिक्स सक्षम होने से पहले, इस कॉल के पास संलग्न करने के लिए कुछ नहीं था।

<Aside type="danger" title="वह connection string एक क्रेडेंशियल है">
यह एक URL में एम्बेडेड अल्पकालिक bearer token है। इसे लॉग न करें, किसी टिकट में पेस्ट न करें,
या commit न करें। जब आप यह प्रदर्शित कर रहे हों कि कॉल काम किया, तो केवल host प्रिंट करें।
</Aside>

## संलग्न करना

<Steps>

1. एक्सटेंशन एक बार इंस्टॉल करें:

   ```bash
   az extension add --name serial-console
   ```

2. संलग्न करें:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. आप नोड के स्वयं के लॉगिन प्रॉम्प्ट पर पहुँचते हैं, शेल पर नहीं। यह Site CLI है, और
   इसके लिए नोड पर सेट किए गए क्रेडेंशियल्स की आवश्यकता होती है — प्रोविजनिंग का admin पासवर्ड, या
   change-password endpoint के माध्यम से सेट किया गया कोई पासवर्ड। सीरियल कंसोल *चैनल* के
   काम करने को सिद्ध करता है; यह प्रमाणीकरण को बाईपास नहीं करता।

</Steps>

`f5-xc-ce-vm-01` से कैप्चर किया गया, बीच में संक्षिप्त किया गया जहाँ systemd unit आउटपुट
कुछ नया नहीं जोड़ता:

```text file=../../../_data/serial-console-boot.txt
```

उस ट्रांसक्रिप्ट में चार बातें ध्यान देने योग्य हैं, क्योंकि वे उन प्रश्नों के उत्तर देती हैं जो
debug API नहीं दे सकता:

- **cloud-init पूरा हुआ** — `Datasource DataSourceAzure`, 22.37 सेकंड में समाप्त।
  एक नोड जो कभी पंजीकृत नहीं होता, आमतौर पर यहाँ विफल होता है, और यहीं आप इसे देख सकते हैं।
- **दोनों container runtime शुरू हुए।** `Container Runtime Interface for OCI (CRI-O)`
  और `Docker Application Container Engine` दोनों `[ OK ]` हैं, जो बूट-टाइम
  dual-runtime व्यवहार का प्रमाण है जो लोगों को
  [crictl](../../commands/system/crictl/) और [docker](../../commands/system/docker/) में आश्चर्यचकित करता है।
- **`VP Manager image load` और `Argo Watch service`** — `vpm` और Argo चालू हो रहे हैं।
- **प्रॉम्प्ट नोड का स्वयं का है**, अपने ऑडिट बैनर के पीछे। सीरियल कंसोल आपको
  लॉगिन प्रॉम्प्ट देता है, सेशन नहीं।

<Aside type="caution" title="इंटरेक्टिव तरीके से संलग्न करने के लिए वास्तविक टर्मिनल की आवश्यकता है — लेकिन इसे स्क्रिप्ट किया जा सकता है">
`az serial-console connect` टर्मिनल को raw mode में डालता है, इसलिए यह किसी
pipeline या TTY के बिना किसी भी संदर्भ से नहीं चल सकता। यह Azure से संपर्क करने से पहले,
client-side विफल होता है:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

वह traceback टर्मिनल हैंडलिंग है, सीरियल कंसोल आउटेज नहीं।

अटैच स्वयं, हालाँकि, **स्वचालित** किया जा सकता है — CLI की बजाय सीधे websocket चलाएँ।
ऊपर का ट्रांसक्रिप्ट उसी तरह कैप्चर किया गया था, बिना TTY के। देखें
`scripts/serial_console_capture.py`, जिस तरह से आप किसी ऐसे नोड से बूट साक्ष्य एकत्र करेंगे जो
टर्मिनल पर बैठे किसी व्यक्ति के बिना पंजीकृत होने में विफल रहा।
</Aside>

<Aside type="caution" title="पुनः प्रयास की अपेक्षा करें: gateway लगभग हर दूसरे प्रयास को अस्वीकार करता है">
Gateway का पहला frame एक challenge है, output नहीं, और client इसका उत्तर bearer
token से देता है। यह सही तरीके से करने पर भी socket अक्सर तुरंत बंद हो जाता है:

```
[close] code=1011 reason=Connection not trusted
```

देखा गया व्यवहार: यह रुक-रुक कर सफल होता है, और निरंतर उपयोग के तहत resource group का हर नोड
अस्वीकार करता है — उन नोड्स सहित जो कुछ मिनट पहले काम कर रहे थे।
`scripts/serial_console_capture.py` डिफ़ॉल्ट रूप से पुनः प्रयास करता है क्योंकि पुनः प्रयास अक्सर काम करता है।

**कारण स्थापित नहीं है।** जो बातें खारिज की जा चुकी हैं, क्योंकि प्रत्येक एक प्रशंसनीय
अनुमान है जो समय बर्बाद करता है:

| यह नहीं | कैसे पुष्टि करें |
| --- | --- |
| ARM/compute throttling | वह ARM कॉल पर HTTP `429` लौटाता है। यह एक अलग डेटा चैनल पर websocket close है। |
| proxy द्वारा TLS interception | `openssl s_client -connect <region>.gateway.serialconsole.azure.com:443 \| openssl x509 -noout -issuer`। वास्तविक `O=Microsoft Corporation` issuer इसे खारिज करता है; proxy vendor issuer के रूप में इसकी पुष्टि करता है, और fix है `*.serialconsole.azure.com` को allow-list करना। |
| Boot diagnostics अक्षम | `az vm show -g <rg> -n <vm> --query diagnosticsProfile` जो `enabled: true` रिपोर्ट करे। |
| grant और challenge के बीच Token mismatch | दोनों के लिए एक token का उपयोग करना सही अभ्यास है, लेकिन close को नहीं रोकता। |

जो *वास्तव में* documented Azure व्यवहार है: **प्रति VM एक सीरियल कंसोल सेशन, और दूसरा
सफल अनुरोध पहले को बाहर कर देता है।** बाहर किया गया उपयोगकर्ता disconnect होता है लेकिन logout नहीं,
इसलिए shell सेशन जीवित रहता है। एक नोड को debug करने वाले दो लोग एक-दूसरे को बार-बार बाहर करेंगे।

बल्क कार्य के लिए [debug API](../debug-api/) या [SSH](../ssh/) को प्राथमिकता दें, जिनमें से किसी की
ये सीमाएँ नहीं हैं। SSH विशेष रूप से कोई paste cap नहीं है और कोई single-session प्रतिबंध नहीं है,
इसलिए जब भी नोड VNet के अंदर से पहुँचने योग्य हो, यह बेहतर विकल्प है।
</Aside>

<Aside type="caution" title="Paste 2,048 वर्णों तक सीमित है">
Azure सीरियल पोर्ट को ओवरलोड होने से बचाने के लिए सीरियल कंसोल paste की लंबाई को 2,048 वर्णों तक
सीमित करता है। एक लंबा command — या एक write में commands का batch — भेजना इस तरह से विफल होता है
जो length limit की बजाय hang या throttle जैसा लगता है।

Commands अलग-अलग भेजें। सीरियल कंसोल पर किसी भी bulk collection के लिए यह एक वास्तविक बाधा है,
और उस कार्य के लिए [debug API](../debug-api/) को प्राथमिकता देने का एक और कारण।
</Aside>

## यहाँ जो API नहीं दिखा सकता वह आप यहाँ देख सकते हैं

- **cloud-init** चल रहा है, विफल हो रहा है, या कभी शुरू नहीं हुआ — एक नोड का सामान्य कारण
  जो कभी पंजीकृत नहीं होता।
- **पंजीकरण के प्रयास** `register.ves.volterra.io` के विरुद्ध, जिसमें
  configuration error या ऐसा token शामिल है जिसे tenant ने अस्वीकार कर दिया।
- **Kernel और बूट संदेश** किसी भी agent के चलने से पहले के।
- नोड जब उसके पास **कोई कार्यशील नेटवर्क पथ नहीं है**, जो हर दूसरे मार्ग को निष्फल कर देता है।

किसी ऐसे नोड के लिए जो `ONLINE` *है*, debug API को प्राथमिकता दें: यह स्क्रिप्ट करने योग्य है, यह
ऐसे साक्ष्य उत्पन्न करता है जिन्हें आप पुनः चला सकते हैं, और यह एकल सीरियल पोर्ट को अधिकृत नहीं करता।
