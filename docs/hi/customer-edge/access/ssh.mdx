SSH appliance के `admin` अकाउंट तक पहुँचता है, जिसका लॉगिन शेल Site CLI
(`/opt/bin/vpmu`) है। यह **पूर्ण ऑन-बॉक्स कमांड सतह** तक पहुँचने का एकमात्र मार्ग है —
[debug API](../debug-api/) 34 कमांड उजागर करता है, और appliance स्वयं कई और प्रदान करता है
जो उस API पर बिल्कुल नहीं हैं।

```bash
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<operator-vm> admin@10.0.3.5
```

उस कमांड लाइन का हर हिस्सा महत्वपूर्ण है, और अगले तीन अनुभाग बताते हैं
कि प्रत्येक किस विफलता को रोकता है।

<Aside type="caution" title="इसे चलते हुए deployment पर सक्षम करने से VMs बदल जाते हैं">
की cloud-init द्वारा लिखी जाती है, और cloud-init `write_files` केवल **पहले
बूट** पर चलता है। मौजूदा नोड्स के लिए इसे चालू करने का अर्थ है उन्हें बदलना, जो वर्तमान में
registration को अटका देता है: पुराना registration अनन्य `(tenant, cluster_name, hostname)`
इंडेक्स रखता है, बदला गया नोड कभी register नहीं हो सकता, और `terraform plan`
हर बार "No changes" रिपोर्ट करता है। परिवर्तन की योजना बनाने से **पहले**
[issue 674](https://github.com/f5-sales-demo/mcn/issues/674) देखें, बाद में नहीं।
</Aside>

## API नहीं, cloud-init की लिखी है — क्यों

site ऑब्जेक्ट पर `admin_user_credentials.ssh_key` बिल्कुल इसी के लिए बना फ़ील्ड जैसा दिखता है। यह स्वीकार होता है, read-back में भी बना रहता है, और कुछ भी कॉन्फ़िगर नहीं करता। `vpm` नोड के स्थानीय उपयोगकर्ताओं का स्वामी है और इसे छूने से मना कर देता है — नोड के अपने लॉग से, एक बूट के दौरान तीन बार:

```text
vpm  users.go:165: Won't do any change for user admin (internal skip)
```

उस एक लाइन से सब कुछ स्पष्ट होता है। `/var/home/admin/.ssh` कभी मौजूद नहीं होता, न site के `ONLINE` होने से पहले, न बाद में। `admin` का shadow last-change date इमेज बिल्ड तारीख पर बना रहता है जबकि `vesbkp` और `vesopcon` मौजूदा तारीख दिखाते हैं, क्योंकि `vpm` ने उन दोनों को सेट किया और `admin` को छोड़ दिया। और `vpm` किसी भी समय `ssh_key` या `authorized_keys` के बारे में कुछ लॉग नहीं करता।

इसलिए फ़ाइल को `vpm` के बाहर लिखना होता है। `admin` uid 2202 है, नोड इमेज में बेक किया गया है, इसलिए यह cloud-init चलने से पहले मौजूद होता है और `owner: admin:admin` लिखते समय resolve हो जाता है — कोई `runcmd` नहीं, कोई ownership fix-up नहीं:

```yaml
- path: /var/home/admin/.ssh/authorized_keys
  permissions: "0600"
  owner: admin:admin
  content: |
    ${ssh_public_key}
```

`sshd` हमेशा से तैयार था। `sshd -T` रिपोर्ट करता है `pubkeyauthentication yes`, और `admin`
नोड पर शिप होने वाली दोनों `sshd_config` फ़ाइलों में `AllowUsers` में मौजूद है। कभी कुछ सक्षम नहीं करना था — केवल एक गायब फ़ाइल थी।

<Aside type="danger" title="admin_user_credentials वापस न जोड़ें, और sshd_config संपादित न करें">
`admin_user_credentials` को `terraform/modules/xc-site` में जोड़ा गया था और यह साक्ष्य एकत्र होने के बाद वापस कर दिया गया (#660, PR #663)। यह भरी जाने वाली कोई कमी नहीं है।

`sshd_config` registration के दौरान बदल दिया जाता है, इसलिए इसमें किया गया संपादन सबसे असुविधाजनक समय पर हटा दिया जाता है।
</Aside>

## यह केवल एक पते पर क्यों जवाब देता है

`sshd` `0.0.0.0:22` से bind करता है, लेकिन केवल **आंतरिक (SLI)** पता ही host नेटवर्क स्टैक पर है। eth0 का नाम बदलकर `a-i-eth0` हो जाता है और कोई host IP नहीं रखता — Argo data plane उस interface का स्वामी है — जबकि eth1 और eth2 host स्टैक पर बने रहते हैं, जहाँ `sshd` सुन रहा है।

VNet के अंदर एक VM से probe करने पर:

```text
10.0.1.4     timed out             CE mgmt/SLO  (eth0)
10.0.2.4     timed out             CE external  (eth1)
10.0.3.5     OPEN                  CE internal/SLI
10.0.3.6     OPEN
10.0.3.7     OPEN
```

जिस पते से आप नोड को जानते हैं उसके विरुद्ध probe ठीक वही लौटाती है जो एक बंद security group लौटाता है। कुछ भी block नहीं कर रहा; उस पते पर कोई listener नहीं है।

CE के सार्वजनिक पतों पर भी 22 पर कोई listener नहीं है, यही कारण है कि ऊपर का कमांड `-J` से जाता है: VNet के अंदर एक operator VM, SLI पतों के समान subnet में।

<Aside type="caution" title="दो माप गलतियाँ जो आत्मविश्वास से गलत उत्तर देती हैं">
eth0, external interface, या सार्वजनिक पते पर port 22 के लिए probe करने पर नोड की SSH स्थिति चाहे जो हो, बंद रिपोर्ट होती है, इसलिए यह आपको कुछ भी नहीं बता सकती। केवल SLI पता जवाब देता है।

और एक कॉर्पोरेट वर्कस्टेशन से probe एक ऐसे port को **open** रिपोर्ट कर सकती है जो बंद है:
Netskope सामान्य ports पर TCP handshake स्वयं पूरा करता है। वर्कस्टेशन से CE सार्वजनिक पतों पर Ports 80 और 443 open दिखते हैं और VNet के अंदर से probe करने पर बंद होते हैं। VNet में एक VM से probe करें।
</Aside>

## Site CLI को एक टर्मिनल और एक carriage return चाहिए

`admin` लॉगिन शेल कोई शेल नहीं है। यह एक `go-prompt` एप्लीकेशन है, जो टर्मिनल को raw mode में डालती है और lines की जगह keystrokes पढ़ती है। चार परिणाम, जिनमें से प्रत्येक इस तरह विफल होता है जो अलग समस्या जैसा दिखता है:

| तंत्र | इसके बिना क्या होता है |
| --- | --- |
| एक टर्मिनल आवंटित करें (`ssh -tt`) | `go-prompt.NewStandardInputParser` से `panic: no such device or address`, जो टूटे appliance जैसा दिखता है |
| Enter के लिए line feed नहीं, carriage return भेजें | Line कभी submit नहीं होती, और session end-of-input पर बिना कुछ print किए बंद हो जाता है |
| standard input खुला रखें | command render होने से पहले कनेक्शन समाप्त हो जाता है, इसलिए एक काम करने वाला command चुप दिखता है |
| command text और Enter byte **अलग-अलग** लिखें | newline buffer में literal character के रूप में जाती है और CLI `unknown command` जवाब देती है, जो ऐसा दिखता है जैसे command मौजूद नहीं |

इसलिए `ssh host 'some-command'` काम नहीं करता: argument नजरअंदाज होता है और interactive prompt वैसे भी शुरू होता है। इसे टर्मिनल के रूप में चलाएं या बिल्कुल न चलाएं।
`scripts/sitecli_ssh_harvest.py` संदर्भ implementation है।

लॉगिन banner नोड की registration स्थिति रिपोर्ट करता है, जो अभी आ रहे नोड को टूटे नोड से पहचानने का सबसे तेज़ तरीका है:

```text
Registration Status: PROVISIONING
SLO IP: 10.0.1.4/26
```

## keypair प्रदान करना

<Steps>

1. यदि आपके पास पहले से नहीं है तो एक keypair बनाएं। RSA की बजाय Ed25519: छोटा,
   और appliance `sshd` द्वारा स्वीकृत।

   ```bash
   ssh-keygen -t ed25519 -C "ce-operator" -f ~/.ssh/id_ed25519
   ```

2. deployment को **public** भाग पर इंगित करें। root module एक बार फ़ाइल पढ़ता है और
   string को हर नोड तक पहुँचाता है:

   ```hcl
   # terraform/terraform.tfvars
   ssh_public_key_path = "~/.ssh/id_ed25519.pub"
   ```

   `ssh_public_key` इसके बजाय material inline लेता है, जो plan tests उपयोग करते हैं।
   private भाग कभी आपके workstation से नहीं जाता।

3. Apply करें। पहले इस पृष्ठ के शीर्ष पर चेतावनी पढ़ें — मौजूदा deployment पर यह CE VMs को बदल देता है।

</Steps>

<Aside type="note" title="VM का अपना admin_ssh_key एक अलग चीज़ है">
`modules/ce-node` में `azurerm_linux_virtual_machine.admin_ssh_key` Azure VM administrator को अधिकृत करता है, न कि appliance के `admin` अकाउंट को। यह कोई Site CLI access नहीं देता, और इसका सेट होना यह प्रमाण नहीं है कि CE SSH कॉन्फ़िगर है।
</Aside>

## यह क्या नहीं है

इनमें से प्रत्येक का परीक्षण किया गया और तब खारिज किया गया जब मार्ग को अभी भी असंभव माना जा रहा था।
प्रत्येक इतना प्रशंसनीय है कि एक दिन बर्बाद कर सकता है।

| कारण नहीं | इसे कैसे खारिज किया गया |
| --- | --- |
| credential केवल create के समय लागू होता है | `sshd` पहले बूट के लगभग 90 सेकंड में शुरू होता है, site object के अस्तित्व से पहले। `admin_user_credentials` `ReplaceSpecType` में भी मौजूद है और जगह पर लागू होता है। |
| `block_all_services` | management address पर port-22 बंद होना services block हों या न हों, समान है। |
| key पर trailing newline | दोनों तरीकों से परीक्षण किया, कोई बदलाव नहीं। Cloud-init फिर भी इसे strip करता है, क्योंकि literal block अन्यथा एक दूसरी, खाली line render करता। |
| पुराना, pinned CE software | तीन builds पर reproduced, जिसमें OpenSSH 9.9 चलाने वाला एक भी शामिल है। |
| गायब `admin_password` | scratch से बने CE पर `ssh_key` के साथ `admin_password` सेट करने से कुछ नहीं बदला। |

<Aside type="caution" title="दो API फ़ील्ड जो discriminator जैसे दिखते हैं और नहीं हैं">
`gc_spec.admin_ssh_key` tenant के **सभी 88 sites** पर खाली है, जिनमें वे 20 भी शामिल हैं जो `admin_password` सेट करते हैं। काम करने वाले और न करने वाले site के बीच इसकी तुलना करने से कुछ पता नहीं चलता, क्योंकि यह हर जगह खाली है।

`registrations_by_site` फ़ील्ड को पूरी तरह छोड़ देता है और उसके लिए `None` लौटाता है, जो "not configured" की बजाय "not reported" जैसा दिखता है।
</Aside>

किसी नए site के `ONLINE` रिपोर्ट करने के लगभग 25 से 30 मिनट तक, `vpm/debug` endpoints
एक BIG-IP `503` पृष्ठ लौटाते हैं जिसमें लिखा होता है `The requested URL was rejected`। यह वेब
एप्लीकेशन फ़ायरवॉल block जैसा, या revoked token जैसा दिखता है, और दोनों में से कोई नहीं है: site अभी relay के लिए तैयार नहीं है। कुछ भी बदलने की बजाय प्रतीक्षा करें और पुनः प्रयास करें।

SSH का ऐसा कोई warm-up नहीं है। यह `sshd` के चालू होते ही जवाब देता है, यही कारण है कि यह वह मार्ग है जो नोड के अभी register होने के दौरान काम करता है।
</Aside>
