इस deployment के एक CE से 2026-07-28 को कैप्चर किया गया। `sitecli/capture-manifest.json`
यह रिकॉर्ड करता है कि कौन सा नोड है, और `scripts/capture-sitecli.sh --check` किसी live CE के
विरुद्ध command surface को पुनः सत्यापित करता है।

SSH उपकरण के `admin` अकाउंट तक पहुँचता है, जिसका लॉगिन शेल Site CLI
(`/opt/bin/vpmu`) है। यह **पूर्ण on-box command surface** तक पहुँचने का एकमात्र मार्ग है —
[debug API](../debug-api/) 34 commands को एक्सपोज़ करता है, और उपकरण स्वयं कई और commands
प्रदान करता है जो उस API पर बिल्कुल नहीं हैं।

```bash
cd terraform
SLI=$(terraform output -json ce_sli_private_ips | jq -r '.eastus01')
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<operator-vm> "admin@$SLI"
```

उस command line का हर हिस्सा महत्वपूर्ण है, और अगले तीन अनुभाग बताते हैं
कि प्रत्येक किस विफलता को रोकता है।

लैंड करने के लिए कोई शेल प्रॉम्प्ट नहीं है: `admin` का लॉगिन शेल **ही** Site CLI है, इसलिए आप
उसके `>>>` प्रॉम्प्ट पर पहुँचते हैं। वहाँ on-box commands को `execcli <name>` के रूप में चलाएँ —
[on-box commands](../../commands/on-box/) देखें।

<Aside type="danger" title="internal address को हमेशा देखें — किसी पिछले session की address कभी न लाएँ">
Azure हर rebuild पर internal subnet को फिर से असाइन करता है, और नोड के क्रम में नहीं। सबसे
हालिया build के बाद `f5-xc-ce-vm-01`, `-02` और `-03` क्रमशः `10.0.3.7`, `10.0.3.5` और `10.0.3.4`
रखते हैं; एक पिछले build में वे पूरी तरह अलग क्रम में थे, और test client का NIC उसी subnet में है
और उस address को रख सकता है जो पहले किसी CE के पास थी। इसलिए किसी याद की गई address से
कनेक्ट करना गलत नोड पर, किसी ऐसे VM पर जो CE नहीं है, या कहीं नहीं — पहुँचता है, और अंतिम
स्थिति "SSH सक्षम नहीं है" से बिल्कुल एक जैसी दिखती है।

`terraform output -json ce_sli_private_ips` यह mapping है। State उपलब्ध न होने पर, NIC
का नाम स्थिर रहता है भले ही address नहीं रहती:

```bash
az network nic show -g "$(terraform output -raw resource_group_name)" \
  -n "$(terraform output -json ce_vm_names | jq -r '.eastus01')-internal-nic" \
  --query ipConfigurations[0].privateIPAddress -o tsv
```

</Aside>

<Aside type="caution" title="केवल Bootstrap के समय — किसी मौजूदा CE को बिना recreate किए SSH नहीं मिल सकता">
cloud-init `write_files` **एक बार, पहले boot पर** चलता है। इसके बाद नोड पर
`/etc/cloud/cloud-init.disabled` मार्कर मौजूद रहता है और cloud-init फिर नहीं चलता।

इसलिए किसी चल रहे CE पर in-place path नहीं है। Azure में `custom_data` replace-only है,
जिसका अर्थ है कि इसे किसी मौजूदा deployment पर अपनाने से **हर CE VM बदल जाती है**। उन
नोड्स को ऑपरेटर SSH देना जो पहले से चल रहे हैं, एक rebuild है, configuration परिवर्तन नहीं —
और अगली चेतावनी यह है कि उस rebuild में पहले क्या कीमत थी, और यह अब क्यों नहीं होती।
</Aside>

<Aside type="caution" title="किसी CE VM को बदलना पहले registration को स्थायी रूप से अटका देता था — यह ठीक हो गया है, और इसीलिए site object VM से जुड़ा है">
किसी rebuild की योजना बनाने से पहले यह जानना ज़रूरी है, क्योंकि विफलता का स्वरूप उस
coupling को समझाता है जो आप plan में देखेंगे।

पहले ऐसा होता था कि नष्ट किए गए नोड की registration control plane के unique
`(tenant, cluster_name, hostname)` index को बनाए रखती थी, इसलिए replacement नोड की registration
को `UniqueSecondaryIndexViolationError` के साथ अस्वीकार कर दिया जाता था और वह हमेशा retry
करता रहता था। Registration को delete करना अपने आप में पर्याप्त नहीं था: एक बचे हुए
`StatusObject` ने तब workload request के लिए `500` return किया, और उस समय तक प्रत्येक नोड ने
एक `registration-obj.yml` persist कर दिया था जो उसे आपके delete किए गए registration से pin कर
रहा था, इसलिए वह बिना self-recovery के `404` पर loop करता रहा। Recovery के लिए दो पूरे
rebuilds लगे। इस पूरे समय `terraform plan` ने **"No changes"** रिपोर्ट किया, क्योंकि Terraform
के दृष्टिकोण से desired state प्राप्त हो चुकी थी।

[Issue 674](https://github.com/f5-sales-demo/mcn/issues/674) बंद है,
[PR 693](https://github.com/f5-sales-demo/mcn/pull/693) द्वारा। `modules/xc-site` अब CE
VM instance को `replace_triggered_by` में नामित करता है, इसलिए VM को बदलने से site object
बदलता है, और किसी site को delete करने से उसकी registrations भी जाती हैं — replacement नोड के
boot होने से पहले index key मुक्त हो जाती है। तब से fleet को शुरू से rebuild किया गया है और
तीनों sites बिना हस्तक्षेप के `ONLINE` हो गईं।

यह coupling अनुमानित नहीं, बल्कि observable है। प्रत्येक site एक VM *instance* id से बाँधी
जाती है, और matching registration वही मान `infra.instance_id` के रूप में रिपोर्ट करती है:

```bash
cd terraform && terraform output -json ce_bound_instance_ids
```

दोनों के बीच असहमति का अर्थ है कि एक site अभी भी उस नोड से बंधी है जो अब मौजूद नहीं है,
जो वह अवस्था है जिसमें से एक rebuilt CE कभी register नहीं हो सकता। Registration का आधा हिस्सा
पढ़ने के लिए अभी भी एक direct API call की आवश्यकता है — provider issue
[1376](https://github.com/f5-sales-demo/terraform-provider-xcsh/issues/1376) वही है जो
इसे data source पर रखेगा।
</Aside>

## cloud-init key क्यों लिखता है, API क्यों नहीं

site object पर `admin_user_credentials.ssh_key` बिल्कुल उसी फ़ील्ड जैसा दिखता है। यह accept
होता है, read-back में बना रहता है, और कुछ configure नहीं करता। `vpm` नोड के local users का
मालिक है और इसे touch करने से मना करता है — नोड के अपने log से, एक single boot में तीन बार:

```text
vpm  users.go:165: Won't do any change for user admin (internal skip)
```

बाकी सब कुछ उसी एक लाइन से निकलता है। `/var/home/admin/.ssh` कभी मौजूद नहीं होता, site के
`ONLINE` होने से पहले या बाद में। `admin` shadow last-change date image build date पर बनी रहती
है जबकि `vesbkp` और `vesopcon` current date दिखाते हैं, क्योंकि `vpm` ने उन दोनों को set किया
और `admin` को skip किया। और `vpm` किसी भी बिंदु पर `ssh_key` या `authorized_keys` के बारे में
कुछ log नहीं करता।

इसलिए file को `vpm` के बाहर लिखा जाना चाहिए। `admin` uid 2202 है, node image में baked in है,
इसलिए यह cloud-init के चलने से पहले मौजूद होता है और `owner: admin:admin` write समय पर
resolve होता है — कोई `runcmd` नहीं, कोई ownership fix-up नहीं:

```yaml
- path: /var/home/admin/.ssh/authorized_keys
  permissions: "0600"
  owner: admin:admin
  content: |
    ${ssh_public_key}
```

`sshd` हमेशा से तैयार था। `sshd -T` रिपोर्ट करता है `pubkeyauthentication yes`, और `admin`
नोड पर ship होने वाली दोनों `sshd_config` files में `AllowUsers` में दिखता है। कभी कुछ enable
करने की ज़रूरत नहीं थी — केवल एक missing file थी।

<Aside type="danger" title="admin_user_credentials को फिर से न जोड़ें, और sshd_config को edit न करें">
`admin_user_credentials` को `terraform/modules/xc-site` में wire किया गया था और यह evidence
एकत्र होने के बाद revert किया गया (#660, PR #663)। यह कोई gap नहीं है जिसे भरने की प्रतीक्षा हो।

`sshd_config` registration के दौरान replace होती है, इसलिए उसमें कोई edit सबसे असुविधाजनक
क्षण पर discarded हो जाती है।
</Aside>

## यह केवल एक address पर क्यों जवाब देता है

`sshd` `0.0.0.0:22` से bind करता है, लेकिन केवल **internal (SLI)** address ही host network
stack पर इस तरह है जिस पर `sshd` जवाब देगा। eth0 का नाम बदलकर `a-i-eth0` किया गया है और
इस पर कोई host IP नहीं है — Argo data plane उस interface का मालिक है, और management/SLO
address जो उस पर होती, वह बजाय `vhost0` पर दिखती है। बाकी दो NICs अपने नाम से host stack पर
बने रहते हैं।

VNet के अंदर एक VM से, एक CE के विरुद्ध probe किया गया:

```text
management/SLO address    timed out
external address          timed out
internal/SLI address      OPEN     SSH-2.0-OpenSSH_8.7
an unused address         timed out    (control)
```

इसलिए उस address के विरुद्ध probe जिससे आप नोड को जानते हैं, बंद security group जैसा ही
return करता है। कुछ block नहीं कर रहा; उस address पर कोई listener नहीं है।

<Aside type="caution" title="यह जानने के लिए guest interface name न पढ़ें कि आप किस subnet पर हैं">
`eth1` और `eth2` में से कौन सा internal address रखता है **यह इसी deployment के nodes के
बीच भिन्न होता है**। तीनों CEs से live पढ़ा गया:

```text
f5-xc-ce-vm-01    eth1 -> external      eth2 -> internal/SLI
f5-xc-ce-vm-02    eth2 -> external      eth1 -> internal/SLI
f5-xc-ce-vm-03    eth1 -> external      eth2 -> internal/SLI
```

केवल दो बातें हर नोड पर निश्चित हैं: `a-i-eth0` का कोई address नहीं है, और `vhost0` management/SLO
address रखता है। बाकी किसी भी चीज़ के लिए, interface name के बजाय
[`ip addr`](../../commands/network/ip/) output में address से मिलान करें।
</Aside>

CE public addresses पर भी 22 पर कोई listener नहीं है, इसीलिए ऊपर दिया गया command `-J` से
जाता है: VNet के अंदर एक ऑपरेटर VM, SLI addresses के समान subnet में। यह deployment इस
उद्देश्य के लिए एक बनाता है —
`terraform output -raw client_vm_name` उसका नाम देता है।

<Aside type="caution" title="-J आपके options को jump leg पर नहीं भेजता">
command line पर दिए गए options अंतिम hop पर लागू होते हैं। `-o UserKnownHostsFile=/dev/null`
के साथ `-J` इसलिए *jump* host के लिए आपकी real `known_hosts` को फिर भी देखता और लिखता है,
जो कि surprise है यदि आप एक rebuilt fleet को उससे बाहर रखने की कोशिश कर रहे हैं। जब यह
मायने रखे तो पहले hop को स्पष्ट रूप से लिखें:

```bash
ssh -tt -o ProxyCommand="ssh -W %h:%p -o UserKnownHostsFile=/dev/null azureuser@<operator-vm>" \
    -o UserKnownHostsFile=/dev/null -i ~/.ssh/id_ed25519 "admin@$SLI"
```

</Aside>

<Aside type="caution" title="दो measurement गलतियाँ जो आत्मविश्वास से गलत उत्तर देती हैं">
eth0, external interface, या public address को port 22 के लिए probe करना नोड की SSH state
चाहे जो भी हो closed रिपोर्ट करता है, इसलिए यह आपको कुछ नहीं बता सकता। केवल SLI address
जवाब देती है।

और एक corporate workstation से probe एक ऐसे port को **open** रिपोर्ट कर सकता है जो बंद है:
Netskope सामान्य ports पर TCP handshake स्वयं पूरा करता है। Ports 80 और 443 workstation से
CE public addresses पर open दिखते हैं और VNet के अंदर से probe करने पर बंद हैं। VNet में
किसी VM से probe करें।
</Aside>

## Site CLI को एक terminal और एक carriage return चाहिए

`admin` login shell एक शेल नहीं है। यह एक `go-prompt` application है, जो terminal को raw mode
में डालता है और lines के बजाय keystrokes पढ़ता है। चार परिणाम, जिनमें से प्रत्येक इस तरह
विफल होता है जो एक अलग समस्या जैसा दिखता है:

| Mechanic | इसके बिना क्या होता है |
| --- | --- |
| Terminal allocate करें (`ssh -tt`) | `go-prompt.NewStandardInputParser` से `panic: no such device or address`, जो एक crashed appliance जैसा दिखता है |
| Enter के लिए line feed नहीं, carriage return भेजें | Line कभी submit नहीं होती, और session end-of-input पर कुछ print किए बिना बंद हो जाता है |
| Standard input खुला रखें | Command render होने से पहले connection समाप्त हो जाता है, इसलिए एक काम करने वाला command silent दिखता है |
| Command text और Enter byte **अलग-अलग** लिखें | Newline buffer में literal character के रूप में आता है और CLI `unknown command` जवाब देता है, जो ऐसा पढ़ता है जैसे command मौजूद नहीं है |

इसलिए `ssh host 'some-command'` काम नहीं करता: argument ignore होता है और interactive prompt
वैसे भी शुरू होता है। इसे एक terminal के रूप में चलाएँ या बिल्कुल नहीं।
`scripts/sitecli_ssh_harvest.py` reference implementation है।

<Aside type="caution" title="'no such device or address' पढ़ने वाला panic का अर्थ है authentication सफल हुआ">
`vpmu` इसे login के **बाद** emit करता है, जब उसे attach करने के लिए कोई terminal नहीं मिलती।
एक crash के रूप में पढ़ने पर यह सबसे बुरे संभावित परिणाम जैसा दिखता है, और यह वास्तव में
सफलता से पहले की अंतिम error है। `-tt` जोड़ें और फिर से connect करें।
</Aside>

<Aside type="caution" title="CE की host key दो अलग-अलग कारणों से बदलती है">
अगला connection `REMOTE HOST IDENTIFICATION HAS CHANGED` चेतावनी देता है और मना कर देता है।
उस address की पुरानी entry clear करें और फिर connect करें। दो चीज़ें इसे trigger करती हैं:

- **नोड को बदलना।** Replacement एक अलग key उसी address पर प्रस्तुत करता है। चूँकि SSH देने
  से VMs बदलती हैं, इसे अपनाने के बाद पहले connection पर इसकी अपेक्षा करें।
- **In-place operating-system upgrade**, बिना किसी replacement के। `2026-07-28 को Observed`:
  एक नोड जिसका `ce_os_version` upgrade पूरा हुआ, उसने उसी virtual machine पर, उसी address
  पर एक नई host key प्रस्तुत की।

`StrictHostKeyChecking=accept-new` किसी के साथ भी मदद नहीं करता। यह उन hosts के लिए keys
accept करता है जिन्हें उसने कभी नहीं देखा; एक *बदली हुई* key वही है जिसे वह मना करता है।
केवल stale entry हटाने से यह clear होता है।

Addresses भी move कर सकती हैं। किसी deployment को recreate करने से उन्हें उसी subnet से
फिर से असाइन किया जाता है, इसलिए एक CE और एक jump host addresses बदल सकते हैं — जिसके बाद
एक stale entry केवल पुरानी नहीं बल्कि गलत machine से attached है।
</Aside>

## Keypair उपलब्ध कराना

<Steps>

1. यदि आपके पास पहले से एक नहीं है तो keypair generate करें। RSA के बजाय Ed25519: छोटा,
   और appliance `sshd` द्वारा स्वीकृत।

   ```bash
   ssh-keygen -t ed25519 -C "ce-operator" -f ~/.ssh/id_ed25519
   ```

2. Deployment को **public** half पर point करें। Root module file को एक बार पढ़ता है और
   string को हर नोड पर pass करता है:

   ```hcl
   # terraform/terraform.tfvars
   ssh_public_key_path = "~/.ssh/id_ed25519.pub"
   ```

   `ssh_public_key` material को inline लेता है, जो plan tests उपयोग करते हैं।
   Private half आपके workstation से कभी नहीं जाती।

3. Apply करें। पहले इस page की शुरुआत में दी गई चेतावनी पढ़ें — किसी मौजूदा deployment पर
   यह CE VMs को बदलता है।

</Steps>

<Aside type="note" title="VM का अपना admin_ssh_key अलग चीज़ है">
`modules/ce-node` में `azurerm_linux_virtual_machine.admin_ssh_key` Azure VM administrator
को authorize करता है, appliance `admin` account को नहीं। यह कोई Site CLI access नहीं देता,
और इसे set रखना यह साक्ष्य नहीं है कि CE SSH configure है।
</Aside>

## यह क्या नहीं है

इनमें से प्रत्येक को तब test किया गया और खारिज किया गया जब route को असंभव माना जाता था।
प्रत्येक इतना प्रशंसनीय है कि एक दिन लग सकता है।

| कारण नहीं | कैसे खारिज किया गया |
| --- | --- |
| Credential केवल create time पर लागू होता है | `sshd` पहले boot में लगभग 90 seconds में शुरू होता है, site object के exist करने से पहले। `admin_user_credentials` भी `ReplaceSpecType` में मौजूद है और in-place लागू होता है। |
| `block_all_services` | Management address पर port-22 closure वही है चाहे services blocked हों या नहीं। |
| Key पर trailing newline | दोनों तरह से test किया, कोई बदलाव नहीं। Cloud-init फिर भी इसे strip करता है, क्योंकि literal block अन्यथा एक दूसरी, खाली line render करती। |
| Pinned, पुराना CE software | तीन builds पर reproduce हुआ, जिसमें OpenSSH 9.9 चलाने वाला एक build शामिल है। |
| Missing `admin_password` | शुरू से CE पर `ssh_key` के साथ `admin_password` set करने से कुछ नहीं बदला। |

<Aside type="caution" title="दो API fields जो discriminators जैसी दिखती हैं और नहीं हैं">
`gc_spec.admin_ssh_key` `f5-sales-demo` की **सभी 58 sites पर** empty या absent है — उन दोनों
सहित जो `admin_user_credentials.ssh_key` set करती हैं। एक working और एक non-working site के
बीच इसकी तुलना करने से कुछ पता नहीं चलता, क्योंकि यह उन sites के लिए भी empty read होता है
जहाँ credential *configured* है।

`registrations_by_site` field को पूरी तरह छोड़ देता है और उसके लिए `None` return करता है,
जो "configured नहीं" के बजाय "रिपोर्ट नहीं किया" जैसा पढ़ता है।
</Aside>
