`vpm/debug` API किसी रजिस्टर्ड नोड पर Site CLI कमांड चलाता है और उनका आउटपुट लौटाता है। नीचे दी गई सारी जानकारी एक लाइव नोड के विरुद्ध स्थापित की गई थी; इसमें से कुछ भी अपस्ट्रीम प्रकाशित नहीं है।

## कमांड कैटलॉग स्वयं-वर्णनात्मक है

नोड से पूछें कि वह क्या समर्थन करता है — `exec-user` पर POST करके, `command` कुंजी को **छोड़कर**:

```bash
curl -sS -X POST \
  -H "Authorization: APIToken $XCSH_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"namespace":"system","site":"<site>","node":"<node>"}' \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/<node>/exec-user" \
  | jq -r .output | jq .
```

प्रतिक्रिया एक JSON ऑब्जेक्ट है जिसकी कुंजी कमांड नाम है:

```json
{
  "crictl-inspect": ["System Troubleshooting", "ExecUser", " container-id"],
  "diagnosis":      ["System Troubleshooting", "ExecUser", "no argument needed", "GLOBAL"],
  "ip-link-set":    ["Network Troubleshooting", "Exec", " (<device>||<group>) (up||down)"]
}
```

प्रत्येक प्रविष्टि `[category, tier, exampleArgument?, scope?]` है, और वे फ़ील्ड दस्तावेज़ीकरण नहीं हैं — वे तय करते हैं कि कमांड को कैसे कॉल किया जाना चाहिए।

<Aside type="caution" title="कुंजी छोड़ दें; ग़लत मान न भेजें">
डिस्कवरी `command` को छोड़ देने से काम करती है। इसके बजाय कोई अज्ञात मान भेजने पर कैटलॉग नहीं, एक त्रुटि लौटती है:

```json
{"code":3,"details":[],"message":"exec command failed: command not supported"}
```

यही संदेश तब भी मिलता है जब कोई *वास्तविक* कमांड ग़लत एंडपॉइंट पर भेजी जाती है, इसलिए इसे "यह कमांड मौजूद नहीं है" के रूप में ग़लत समझना आसान है।
</Aside>

## तीन ट्रांसपोर्ट, कैटलॉग प्रविष्टि द्वारा चुने गए

| शर्त | विधि और पथ | बॉडी | लौटाता है |
| --- | --- | --- | --- |
| `scope` `GLOBAL` है | `GET .../vpm/debug/global/<cmd>` | कोई नहीं | JSON |
| `tier` `ExecUser` है | `POST .../vpm/debug/<node>/exec-user` | `command` सरणी | टेक्स्ट |
| `tier` `Exec` है | `POST .../vpm/debug/<node>/exec` | `command` सरणी | टेक्स्ट |

### `ExecUser` — केवल-पठन tier <Badge text="31 commands" variant="note" />

सामान्य स्थिति। कमांड और उसके आर्ग्युमेंट्स को एक सरणी के रूप में पास करें, पहले कमांड नाम:

```bash
curl -sS -X POST \
  -H "Authorization: APIToken $XCSH_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"namespace":"system","site":"<site>","node":"<node>","command":["crictl-ps"]}' \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/<node>/exec-user"
```

```json
{ "return_code": 0, "output": "CONTAINER    IMAGE    CREATED    STATE ..." }
```

आर्ग्युमेंट्स अलग-अलग सरणी तत्व होते हैं, एक ही स्ट्रिंग नहीं:

```json
{ "command": ["journalctl", "-u", "vpm", "-n", "200"] }
```

### `GLOBAL` — साइट-व्यापी, और पूरी तरह एक भिन्न ट्रांसपोर्ट <Badge text="2 commands" variant="tip" />

`health` और `diagnosis` ही केवल दो हैं। ये `global` पथ पर `GET` अनुरोध हैं, कोई आर्ग्युमेंट नहीं लेते, और टर्मिनल टेक्स्ट के बजाय संरचित JSON लौटाते हैं।

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/global/health" | jq .
```

<Aside type="danger" title="कोई GLOBAL कमांड exec-user के माध्यम से पहुँच योग्य नहीं है">
यही वह जाल है जिसमें सबसे अधिक समय बर्बाद होता है। `health` या `diagnosis` को `exec-user` पर भेजने से `command not supported` लौटता है, जो ऐसा प्रतीत होता है मानो वह कमांड नोड पर मौजूद नहीं है — जबकि वास्तव में वह मौजूद है और आपने ग़लत ट्रांसपोर्ट का उपयोग किया।

```bash
# Wrong. Returns: exec command failed: command not supported
-d '{"namespace":"system","site":"…","node":"…","command":["health"]}'   # POST exec-user

# Right.
GET .../vpm/debug/global/health
```

</Aside>

### `Exec` — विशेषाधिकार प्राप्त tier <Badge text="1 command on this build" variant="danger" />

एक अलग एंडपॉइंट, और tier सलाहकारी नहीं बल्कि प्रवर्तित है: `exec` एक `ExecUser` कमांड को उसी `command not supported` संदेश के साथ अस्वीकार कर देता है। इसका प्रत्येक सदस्य या तो नोड को बदलता है या कोई स्टेट मार्कर पढ़ता है।

इस टेनेंट पर चल रहे बिल्ड में, tier में केवल `ip-link-set` है। नए बिल्ड `systemctl-restart-NetworkManager`, `systemctl-restart-crio`, `systemctl-restart-kubelet`, `systemctl-start-crio-prune` और तीन `marker-exists-*` कमांड जोड़ते हैं।

<Aside type="danger" title="यहाँ कुछ भी Exec कमांड नहीं चलाता">
कैप्चर हार्नेस इस tier को अस्वीकार करता है, और tier को हार्डकोडेड सूची के बजाय लाइव कैटलॉग से पढ़ता है — इसलिए भविष्य का कोई बिल्ड जो किसी कमांड को `Exec` में प्रोन्नत करता है, उसका सम्मान किसी के कोड संपादित किए बिना होता है। किसी को केवल जान-बूझकर चलाएँ, ऐसे नोड पर जिसे आप बाधित करने के लिए तैयार हैं।
</Aside>

## साइट और नोड नाम ढूँढना

नोड नाम Azure VM नाम है, और `list-service` इसे उस पर चल रही सेवाओं के साथ पुष्टि करने का एक सस्ता तरीका है:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/global/list-service" \
  | jq -r '[.service[].node] | unique'
```

```json
["", "f5-xc-ce-vm-01"]
```

कुछ सेवाएँ खाली नोड नाम रिपोर्ट करती हैं, इसलिए उस सूची में एक खाली स्ट्रिंग दूसरे नोड के बजाय प्रतिक्रिया की एक कलाकृति है। `list-service` 34-कमांड कैटलॉग में भी नहीं है: यह एक `global` एंडपॉइंट है जिसका कैटलॉग विज्ञापन नहीं करता, इसीलिए इसे यहाँ दस्तावेज़ीकृत किया गया है और [कमांड संदर्भ](../../commands/) में नहीं।

## इस रिपॉज़िटरी के कैप्चर को पुनःउत्पन्न करना

प्रत्येक कमांड पृष्ठ `scripts/capture-sitecli.sh` द्वारा कैप्चर किए गए आउटपुट को एम्बेड करता है, जो ऊपर के तीनों नियमों को लागू करता है।

<Steps>

1. इसे किसी टेनेंट पर लक्षित करें। यह `XCSH_API_URL` और `XCSH_API_TOKEN` पढ़ता है, या सक्रिय `xcsh` संदर्भ पर वापस लौटता है।

2. कैटलॉग रिफ़्रेश करें और पुष्टि करें कि दस्तावेज़ीकरण के नीचे नोड बदला नहीं है:

   ```bash
   bash scripts/capture-sitecli.sh --check
   ```

   यह केवल कमिट किए गए कैटलॉग और सॉफ़्टवेयर बिल्ड की तुलना करता है। यह बिल्ड परिवर्तन को जोड़े गए या हटाए गए कमांड से अलग रिपोर्ट करता है।

3. जब आप ताज़ा साक्ष्य चाहते हों तो पुनः कैप्चर करें:

   ```bash
   bash scripts/capture-sitecli.sh
   ```

</Steps>

<Aside type="note" title="कैप्चर साक्ष्य हैं, पुनःउत्पादनीय आर्टिफ़ैक्ट नहीं">
काउंटर, अपटाइम और कंटेनर की आयु रन-दर-रन बदलते हैं, इसलिए पुनः कैप्चर करने पर हमेशा एक diff बनता है। कैटलॉग स्थिर अनुबंध है और जब नोड नहीं बदला हो तो रनों के बीच बाइट-समान होता है; `--check` उसी की तुलना करता है। लंबा आउटपुट काट दिया जाता है और एक स्पष्ट मार्कर के साथ समाप्त होता है, इसलिए कटी हुई तालिका कभी पूर्ण होने का आभास नहीं देती।
</Aside>

<Aside type="danger" title="किसी ग्राहक नोड से कैप्चर करना: रिडैक्शन प्रोफ़ाइल जाँचें">
कमांड आउटपुट इंफ़्रास्ट्रक्चर पहचान वहन करता है — आंतरिक एड्रेसिंग, MAC पते, AS नंबर, होस्टनाम — और किसी ग्राहक के लिए वह संगठन के बारे में पहचान-योग्य जानकारी होती है।

इसलिए स्क्रब फ़िल्टर डिफ़ॉल्ट रूप से एक **strict** प्रोफ़ाइल पर होता है जो यह सब हटा देता है। यह रिपॉज़िटरी `sitecli/capture-manifest.json` में `lab` घोषित करती है, जो वह विवरण बनाए रखती है, और यह केवल यहाँ ही सही है क्योंकि ये कैप्चर F5 के स्वामित्व वाले डेमो इंफ़्रास्ट्रक्चर से आते हैं।

**उस सेटिंग को ग्राहक कैप्चर तक न ले जाएँ।** टोकन, निजी कुंजियाँ, टेनेंट पहचानकर्ता, ऑब्जेक्ट UUID, ईमेल पते और होम डायरेक्टरी पथ दोनों प्रोफ़ाइलों के अंतर्गत हटा दिए जाते हैं।

एक सीमा जानने योग्य है: एक BGP नेबर तालिका AS को एक नंगे कॉलम के रूप में छापती है जिसमें पैटर्न को टिकाने के लिए कोई लेबल नहीं होता, इसलिए ASN को मान के आधार पर निजी श्रेणियों के विरुद्ध मिलाया जाता है। वहाँ एक **सार्वजनिक** ASN strict से बच जाता है, और प्रकाशित करने से पहले `show-ip-bgp*` आउटपुट की मैनुअल समीक्षा की आवश्यकता होती है।
</Aside>
