चार मार्ग काम करते हैं, और कौन सा लागू होता है यह नोड की स्थिति, आप कहाँ से कनेक्ट कर रहे हैं, और आपको क्या पहुँचना है — इन बातों से तय होता है, न कि वरीयता से।

| मार्ग | नोड `ONLINE` चाहिए | नेटवर्क पहुँच चाहिए | सीमाएँ | कवर करता है |
| --- | --- | --- | --- | --- |
| [Debug API](./debug-api/) | **हाँ** | हाँ | नई साइट पर लगभग 25–30 मिनट का वार्म-अप | 34 कमांड |
| [Site Console](./site-console/) | नहीं | Azure Bastion के माध्यम से, कोई जंप होस्ट नहीं चाहिए | Bastion Standard SKU होना चाहिए जिसमें टनलिंग हो | F5 का नोड ट्रबलशूटिंग UI |
| [SSH](./ssh/) | नहीं | VNet के अंदर से, केवल इंटर्नल एड्रेस पर | कुंजी पहले बूट से उपस्थित होनी चाहिए | पूर्ण ऑन-बॉक्स Site CLI |
| [Serial console](./serial-console/) | नहीं | नहीं | प्रति VM एक सेशन; 2,048-कैरेक्टर पेस्ट सीमा | पूर्ण ऑन-बॉक्स Site CLI |

सीरियल कंसोल अंतिम विकल्प है, और एकमात्र मार्ग जो बिना किसी काम करने वाले नेटवर्क पथ वाले नोड में भी जीवित रहता है।

[Site Console](./site-console/) आमतौर पर पहले आज़माने वाला होता है। यह आपसे सबसे कम माँगता है —
कोई SSH कुंजी वितरित नहीं करनी, कोई जंप होस्ट नहीं, नोड पर कोई सार्वजनिक IP नहीं, और कोई VM प्रतिस्थापन नहीं —
क्योंकि पहुँच एक Azure RBAC निर्णय बन जाती है, न कि क्रेडेंशियल-वितरण की समस्या।
यह कमांड सतह के बजाय F5 का अपना ट्रबलशूटिंग UI देता है, इसलिए जब आपको विशिष्ट कमांड चलानी हों या कुछ स्क्रिप्ट करना हो तो इससे आगे जाएँ।

SSH वह है जिस पर तब पहुँचना चाहिए जब debug API पर्याप्त न हो, क्योंकि अप्लायंस उस API द्वारा एक्सपोज़ की गई 34 कमांड से काफी अधिक कमांड प्रदान करता है। इसकी दो लागतें हैं। कुंजी cloud-init द्वारा लिखी जाती है और इसलिए **पहले बूट** पर उपस्थित होनी चाहिए, जिसका अर्थ है कि इसे चल रहे नोड्स पर सक्षम करने से उन्हें बदला जाता है — और इससे वर्तमान में पंजीकरण अटक जाता है
([issue 674](https://github.com/f5-sales-demo/mcn/issues/674))। और `sshd` केवल नोड के इंटर्नल एड्रेस पर उत्तर देता है, इसलिए VNet के अंदर एक होस्ट की आवश्यकता होती है; जिस एड्रेस से आप नोड को जानते हैं उसे प्रोब करना हमेशा बंद रिपोर्ट करेगा।

## विभाजन वरीयता क्यों नहीं है

Debug API F5 Distributed Cloud कंट्रोल प्लेन द्वारा सेव की जाती है, जो पंजीकरण के दौरान `vpm` द्वारा स्थापित टनल के माध्यम से नोड तक रिले करती है। कोई पंजीकरण नहीं मतलब कोई टनल नहीं, जिसका अर्थ है कि API के पास रिले करने के लिए कुछ नहीं है।

यह एक स्पष्ट तरीके के बजाय अनुपयोगी तरीके से विफल होती है, इसलिए एक नोड जो कभी नहीं आया वह एक API समस्या जैसा दिखता है।

सीरियल कंसोल पूरी तरह से दूसरे तरफ जाता है — Azure प्लेटफ़ॉर्म के माध्यम से नोड के एमुलेटेड सीरियल पोर्ट तक। इसे इस बात की परवाह नहीं है कि नोड ने पंजीकरण किया है, नेटवर्क पहुँच है, या काम करने वाला डेटा प्लेन है। वह स्वतंत्रता ही पूरा बिंदु है, और इसीलिए CE VMs पर बूट डायग्नोस्टिक्स सक्षम रहनी चाहिए।

<Aside type="note" title="किस पर पहुँचना है">
यदि आप स्वचालन लिख रहे हैं, या ऐसे साक्ष्य एकत्र कर रहे हैं जिन्हें आप बाद में फिर से चलाना चाहते हैं, तो
debug API का उपयोग करें। यदि पंजीकरण ही वह चीज़ है जो टूटी है, तो सीरियल कंसोल कोई फ़ॉलबैक नहीं है — यह एकमात्र विकल्प है।
</Aside>

## क्रेडेंशियल

प्रत्येक मार्ग अलग-अलग क्रेडेंशियल का उपयोग करता है, और उनमें से कोई भी कमांड लाइन पर नहीं होना चाहिए।

- **Debug API** — एक F5 Distributed Cloud API टोकन, `XCSH_API_TOKEN` के रूप में, टेनेंट URL के साथ `XCSH_API_URL` के रूप में। `xcsh` कॉन्टेक्स्ट फ़ाइल
  `~/.config/xcsh/contexts/<tenant>.json` पर दोनों को रखती है, जिसे
  `scripts/capture-sitecli.sh` तब पढ़ता है जब एनवायरनमेंट उन्हें प्रदान नहीं करता।
- **SSH** — कीपेयर का प्राइवेट हिस्सा जिसका पब्लिक हिस्सा डिप्लॉयमेंट ने पहले बूट पर
  `/var/home/admin/.ssh/authorized_keys` में लिखा था, साथ ही इंटर्नल एड्रेस तक पहुँचने के लिए VNet के अंदर एक होस्ट। `azureuser` के रूप में नहीं, `admin` के रूप में कनेक्ट करें।
- **Serial console** — आपका इंटरएक्टिव Azure लॉगिन। इसके लिए कोई सर्विस प्रिंसिपल नहीं है: F5 कॉर्पोरेट Entra टेनेंट एक प्रोविज़न करने की अनुमति नहीं देता, यही कारण है कि इसका कोई भाग CI में नहीं चलता।

<Aside type="danger" title="टोकन कभी भी आर्गुमेंट के रूप में न दें">
कमांड लाइन पर एक टोकन शेल हिस्ट्री और प्रोसेस लिस्ट में पहुँच जाता है, जहाँ
मशीन पर हर दूसरा उपयोगकर्ता इसे पढ़ सकता है। इसीलिए `capture-sitecli.sh`
`--token` को पूरी तरह अस्वीकार करता है और इसके बजाय `curl` को stdin पर हेडर प्रदान करता है।
</Aside>
