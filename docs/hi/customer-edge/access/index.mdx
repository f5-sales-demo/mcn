तीन मार्ग काम करते हैं, और इनमें से कौन सा लागू होगा यह नोड की स्थिति और आप कहाँ से
कनेक्ट कर रहे हैं इससे तय होता है, न कि वरीयता से।

| मार्ग | नोड `ONLINE` आवश्यक | नेटवर्क पहुँच आवश्यक | सीमाएँ | दायरा |
| --- | --- | --- | --- | --- |
| [Debug API](./debug-api/) | **हाँ** | हाँ | नई साइट पर लगभग 25–30 मिनट का वार्म-अप | 34 कमांड |
| [SSH](./ssh/) | नहीं | VNet के भीतर से, केवल आंतरिक पते तक | कुंजी पहले बूट से मौजूद होनी चाहिए | पूर्ण ऑन-बॉक्स Site CLI |
| [Serial console](./serial-console/) | नहीं | नहीं | प्रति VM एक सत्र; 2,048-अक्षर पेस्ट सीमा | पूर्ण ऑन-बॉक्स Site CLI |

सीरियल कंसोल अंतिम उपाय है, और एकमात्र ऐसा मार्ग है जो बिना किसी कार्यशील नेटवर्क पथ वाले
नोड पर भी टिका रहता है।

जब डिबग API पर्याप्त न हो तब SSH ही वह विकल्प है जिसकी ओर बढ़ना चाहिए, क्योंकि उपकरण उन 34
कमांडों से काफ़ी अधिक कमांड प्रदान करता है जो वह API उजागर करता है। इसकी दो लागतें हैं। कुंजी
cloud-init द्वारा लिखी जाती है और इसलिए **पहले बूट** पर मौजूद होनी चाहिए, जिसका अर्थ है कि
चल रहे नोड्स पर इसे सक्षम करना उन्हें प्रतिस्थापित कर देता है — और यह वर्तमान में पंजीकरण को
अटका देता है ([issue 674](https://github.com/f5-sales-demo/mcn/issues/674))। और `sshd` केवल
नोड के आंतरिक पते पर उत्तर देता है, इसलिए इसके लिए VNet के भीतर एक होस्ट चाहिए; जिस पते से
आप नोड को जानते हैं उसकी जाँच करने पर वह हमेशा बंद ही दिखेगा।

## यह विभाजन वरीयता क्यों नहीं है

डिबग API F5 Distributed Cloud कंट्रोल प्लेन द्वारा सर्व किया जाता है, जो पंजीकरण के दौरान
`vpm` द्वारा स्थापित की गई टनल के माध्यम से नोड तक रिले करता है। पंजीकरण न होने का अर्थ है
कोई टनल नहीं, जिसका अर्थ है कि API के पास रिले करने के लिए कुछ नहीं है।

यह किसी स्पष्ट तरीके के बजाय एक अनुपयोगी तरीके से विफल होता है, इसलिए जो नोड कभी ऊपर आया
ही नहीं वह एक API समस्या जैसा दिखता है।

सीरियल कंसोल पूरी तरह दूसरे रास्ते से जाता है — Azure प्लेटफ़ॉर्म के माध्यम से नोड के
एमुलेटेड सीरियल पोर्ट तक। इसे इससे कोई फ़र्क नहीं पड़ता कि नोड पंजीकृत हुआ है, उसकी नेटवर्क
पहुँच है, या उसका डेटा प्लेन काम कर रहा है। यही स्वतंत्रता पूरा उद्देश्य है, और इसीलिए CE VMs
पर बूट डायग्नोस्टिक्स सक्षम रहना चाहिए।

<Aside type="note" title="किसे चुनें">
यदि आप स्वचालन लिख रहे हैं, या ऐसे प्रमाण एकत्र कर रहे हैं जिन्हें आप बाद में फिर से चलाना
चाहते हैं, तो डिबग API का उपयोग करें। यदि पंजीकरण ही वह चीज़ है जो टूटी हुई है, तो सीरियल
कंसोल कोई फ़ॉलबैक नहीं है — वही एकमात्र विकल्प है।
</Aside>

## क्रेडेंशियल

प्रत्येक मार्ग अलग-अलग क्रेडेंशियल का उपयोग करता है, और इनमें से कोई भी कमांड लाइन पर नहीं होना चाहिए।

- **Debug API** — एक F5 Distributed Cloud API टोकन, `XCSH_API_TOKEN` के रूप में, और
  टेनेंट URL `XCSH_API_URL` के रूप में। `~/.config/xcsh/contexts/<tenant>.json` पर स्थित
  `xcsh` कॉन्टेक्स्ट फ़ाइल दोनों को रखती है, जिसे `scripts/capture-sitecli.sh` तब पढ़ता है
  जब एनवायरनमेंट उन्हें प्रदान नहीं करता।
- **SSH** — उस कीपेयर का निजी हिस्सा जिसका सार्वजनिक हिस्सा परिनियोजन ने पहले बूट पर
  `/var/home/admin/.ssh/authorized_keys` में लिखा था, साथ ही VNet के भीतर एक होस्ट जिसके
  माध्यम से आंतरिक पते तक पहुँचा जा सके। `azureuser` नहीं, बल्कि `admin` के रूप में कनेक्ट करें।
- **Serial console** — आपका इंटरैक्टिव Azure लॉगिन। इसके लिए कोई सर्विस प्रिंसिपल नहीं है:
  F5 कॉर्पोरेट Entra टेनेंट किसी का प्रावधान करने की अनुमति नहीं देता, यही कारण है कि इसका
  कोई भी हिस्सा CI में नहीं चलता।

<Aside type="danger" title="टोकन को कभी भी आर्गुमेंट के रूप में न भेजें">
कमांड लाइन पर दिया गया टोकन शेल हिस्ट्री और प्रोसेस सूची में पहुँच जाता है, जहाँ मशीन का
हर दूसरा उपयोगकर्ता उसे पढ़ सकता है। इसी कारण `capture-sitecli.sh` `--token` को सीधे
अस्वीकार कर देता है और इसके बजाय हेडर को stdin पर `curl` को प्रदान करता है।
</Aside>
