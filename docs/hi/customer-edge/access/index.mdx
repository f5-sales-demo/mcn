तीन मार्ग काम करते हैं, और कौन सा लागू होता है यह नोड की स्थिति और आप कहाँ से कनेक्ट कर रहे हैं, इससे तय होता है — न कि प्राथमिकता से।

| मार्ग | नोड `ONLINE` चाहिए | नेटवर्क पहुँच चाहिए | सीमाएँ | कवर करता है |
| --- | --- | --- | --- | --- |
| [Debug API](./debug-api/) | **हाँ** | हाँ | नई साइट पर लगभग 25–30 मिनट का वार्म-अप | 34 कमांड |
| [SSH](./ssh/) | नहीं | VNet के अंदर से, केवल आंतरिक पते पर | पहले बूट से कुंजी उपस्थित होनी चाहिए | पूर्ण ऑन-बॉक्स Site CLI |
| [सीरियल कंसोल](./serial-console/) | नहीं | नहीं | प्रति VM एक सेशन; 2,048-कैरेक्टर पेस्ट सीमा | पूर्ण ऑन-बॉक्स Site CLI |

सीरियल कंसोल अंतिम उपाय है, और एकमात्र मार्ग जो बिना किसी कार्यशील नेटवर्क पथ वाले नोड पर भी बना रहता है।

SSH वह विकल्प है जिसे तब अपनाएँ जब debug API पर्याप्त न हो, क्योंकि अप्लायंस उन 34 से काफी अधिक कमांड प्रदान करता है जो API एक्सपोज़ करती है। इसकी दो लागतें हैं। कुंजी cloud-init द्वारा लिखी जाती है और इसलिए **पहले बूट** पर उपस्थित होनी चाहिए, जिसका अर्थ है कि इसे चल रहे नोड्स पर सक्षम करने से वे प्रतिस्थापित हो जाते हैं — और यह वर्तमान में पंजीकरण को अटका देता है ([issue 674](https://github.com/f5-sales-demo/mcn/issues/674))। और `sshd` केवल नोड के आंतरिक पते पर ही उत्तर देता है, इसलिए इसके लिए VNet के अंदर एक होस्ट की आवश्यकता है; जिस पते से आप नोड को जानते हैं उसे प्रोब करने पर हमेशा बंद रिपोर्ट होगी।

## विभाजन प्राथमिकता क्यों नहीं है

Debug API F5 Distributed Cloud कंट्रोल प्लेन द्वारा सर्व की जाती है, जो पंजीकरण के दौरान `vpm` द्वारा स्थापित टनल के माध्यम से नोड तक रिले करती है। कोई पंजीकरण नहीं मतलब कोई टनल नहीं, जिसका अर्थ है API के पास रिले करने के लिए कुछ नहीं।

यह एक स्पष्ट तरीके के बजाय एक अनुपयोगी तरीके से विफल होती है, इसलिए एक नोड जो कभी नहीं आया वह एक API समस्या की तरह दिखता है।

सीरियल कंसोल पूरी तरह दूसरी दिशा में जाता है — Azure प्लेटफ़ॉर्म के माध्यम से नोड के एमुलेटेड सीरियल पोर्ट तक। इसे कोई फर्क नहीं पड़ता कि नोड ने पंजीकरण किया है, नेटवर्क पहुँच है, या कार्यशील डेटा प्लेन है। यह स्वतंत्रता ही इसका पूरा उद्देश्य है, और इसीलिए CE VM पर बूट डायग्नोस्टिक्स सक्षम रहना आवश्यक है।

<Aside type="note" title="क्या उपयोग करें">
यदि आप स्वचालन लिख रहे हैं, या ऐसे साक्ष्य एकत्र कर रहे हैं जिन्हें आप बाद में पुनः चलाना चाहते हैं, तो debug API का उपयोग करें। यदि पंजीकरण वह चीज़ है जो टूटी हुई है, तो सीरियल कंसोल एक फॉलबैक नहीं है — यह एकमात्र विकल्प है।
</Aside>

## क्रेडेंशियल्स

दोनों मार्ग अलग-अलग क्रेडेंशियल्स का उपयोग करते हैं, और न तो कोई कमांड लाइन पर होना चाहिए।

- **Debug API** — एक F5 Distributed Cloud API टोकन, `XCSH_API_TOKEN` के रूप में, टेनेंट URL के साथ `XCSH_API_URL` के रूप में। `~/.config/xcsh/contexts/<tenant>.json` पर `xcsh` कॉन्टेक्स्ट फ़ाइल दोनों को रखती है, जिसे `scripts/capture-sitecli.sh` पढ़ता है जब एनवायरनमेंट उन्हें सप्लाई नहीं करता।
- **सीरियल कंसोल** — आपका इंटरेक्टिव Azure लॉगिन। इसके लिए कोई सर्विस प्रिंसिपल नहीं है: F5 कॉर्पोरेट Entra टेनेंट एक को प्रोविजन करने की अनुमति नहीं देता, यही कारण है कि इसका कोई भी हिस्सा CI में नहीं चलता।

<Aside type="danger" title="टोकन को कभी भी आर्गुमेंट के रूप में न पास करें">
कमांड लाइन पर एक टोकन शेल हिस्ट्री में और प्रोसेस लिस्ट में जाता है, जहाँ मशीन पर हर दूसरा उपयोगकर्ता इसे पढ़ सकता है। `capture-sitecli.sh` इसी कारण से `--token` को पूरी तरह अस्वीकार करता है और इसके बजाय stdin पर `curl` को हेडर सप्लाई करता है।
</Aside>
