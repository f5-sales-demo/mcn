एक Customer Edge (CE) वह F5 Distributed Cloud नोड है जिसे यह रिपॉजिटरी
Azure में प्रोविज़न करती है — `terraform/modules/ce-node`, जो
`volterraedgeservices/volterra-node` मार्केटप्लेस इमेज से बनाई गई है।

यह डेटा प्लेन (Argo), कंट्रोल प्लेन (Vega), एक Envoy प्रॉक्सी, एक Kubernetes
स्टैक, और `vpm` चलाता है — वह एजेंट जो नोड को रजिस्टर करता है और उस पर बाकी सब कुछ प्रबंधित करता है।

जब कोई CE सही तरीके से काम न करे, तो Site CLI ही वह साधन है। पहला निर्णय यह है कि कौन सा
एक्सेस पथ लागू होता है, और गलत पथ चुनना समय बर्बाद करता है — जो एक टूटे हुए नोड जैसा दिखता है।

Debug API नोड तक **F5 Distributed Cloud कंट्रोल प्लेन के माध्यम से** पहुँचता है।
यही कारण है कि यह विभाजन महत्वपूर्ण है: API तभी उत्तर दे सकता है जब नोड ने
रजिस्ट्रेशन कर लिया हो और `ONLINE` रिपोर्ट करे।

एक नोड जो रजिस्टर होने में विफल रहा — गलत cloud-init, एक्सपायर्ड टोकन,
`register.ves.volterra.io` तक कोई रूट नहीं — यह वही मामला है जहाँ आपको डायग्नोस्टिक्स
की ज़रूरत है, और ठीक यही वह मामला है जहाँ API सेवा नहीं दे सकता।

[SSH](./access/ssh/) तीसरा विकल्प है, और एकमात्र ऐसा जो अप्लायंस की
पूरी कमांड सर्फेस तक पहुँचता है — debug API 34 कमांड्स उजागर करता है और नोड स्वयं कई
और प्रदान करता है। दो बातें इसे सीमित करती हैं। `sshd` केवल नोड के आंतरिक (SLI) एड्रेस पर
उत्तर देता है, इसलिए VNet के अंदर एक होस्ट की आवश्यकता होती है; और यह की cloud-init द्वारा पहले
बूट पर लिखी जाती है, क्योंकि site ऑब्जेक्ट पर `ssh_key` फ़ील्ड निष्क्रिय है — `vpm`
`admin` उपयोगकर्ता को छोड़ देता है और इसे कभी लागू नहीं करता। इसलिए चल रहे नोड्स पर इसे
सक्षम करने से वे बदल जाते हैं।

अतः: यदि साइट `ONLINE` है और 34 कमांड्स पर्याप्त हैं, तो debug API का उपयोग करें। यदि आपको
शेष सर्फेस की आवश्यकता है और VNet तक पहुँच सकते हैं, तो SSH का उपयोग करें। यदि रजिस्ट्रेशन
ही टूटा हुआ है, तो serial console ही एकमात्र रास्ता है।

<Aside type="caution" title="पहले साइट की स्थिति जाँचें">
एक अनुरोध आपको बता देता है कि आप किस पथ पर हैं:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/config/namespaces/system/sites/<site>" \
  | jq -r '.spec.site_state'
```

`ONLINE` का मतलब है debug API काम करेगा। कोई भी अन्य स्थिति — या एक साइट जो
मौजूद ही नहीं है — का मतलब है serial console।
</Aside>

## सुरक्षा नियम

ये नीचे दिए गए हर पृष्ठ पर हर कमांड के लिए लागू होते हैं।

- **जब तक निश्चित न हों, केवल पढ़ें।** कमांड सर्फेस दो
  प्रिविलेज टियर में विभाजित है, और `Exec` टियर या तो नोड को बदलता है या एक स्टेट
  मार्कर पढ़ता है। इन पृष्ठों पर कुछ भी `Exec` कमांड नहीं चलाता, और कैप्चर हार्नेस भी नहीं।
- **किसी कमांड को उसके नाम से सुरक्षित न मानें।** `ip-link-set` एक क्वेरी जैसा लगता है
  लेकिन एक इंटरफेस को डाउन कर देता है। `systemctl-restart-crio` एक लाइव डेटा प्लेन के
  अंतर्गत कंटेनर रनटाइम को पुनः आरंभ करता है।
- **वह सबसे संकीर्ण कमांड चुनें जो प्रश्न का उत्तर दे।** `health` और
  `diagnosis` नोड को सस्ते में सारांशित करते हैं; `flow-l` एक 629,760-प्रविष्टि फ़्लो
  टेबल डंप करता है।
- **एक CE लाइव ट्रैफ़िक सेवा दे रहा है।** ये साझा डेमो वातावरण हैं। यह मानकर चलें कि
  कोई उस साइट से प्रेज़ेंट कर रहा है जिसे आप डीबग कर रहे हैं।

## यहाँ क्या प्रलेखित है

इस टेनेंट के सॉफ़्टवेयर बिल्ड पर debug API के माध्यम से पहुँचने योग्य हर कमांड,
प्रत्येक के साथ आउटपुट जो कहीं और से ट्रांसक्राइब करने के बजाय एक लाइव नोड से कैप्चर किया गया है।

[कमांड संदर्भ](./commands/) उन सभी को उनकी श्रेणी, प्रिविलेज
टियर और ट्रांसपोर्ट सहित सूचीबद्ध करता है; [वर्कफ़्लो](./workflows/) उन्हें उन अनुक्रमों में
जोड़ते हैं जो आप वास्तव में तब उपयोग करते हैं जब कुछ गलत हो।

Site CLI के ऑन-बॉक्स-ओनली हिस्से — `configure`, `configure-network`,
`factory-reset`, `upgrade` और लगभग साठ अन्य `ExecCLI` कमांड्स — यहाँ कवर नहीं किए गए हैं।

वे केवल serial console सत्र से ही पहुँचने योग्य हैं, इसलिए उनके बारे में कुछ भी
प्रोग्रामेटिक रूप से सत्यापित नहीं किया जा सकता, और असत्यापित कमांड सिंटैक्स वह दोष है जिसे
दोहराने से बचने के लिए यह दस्तावेज़ीकरण मौजूद है।
