एक Customer Edge (CE) वह F5 Distributed Cloud नोड है जिसे यह रिपॉजिटरी Azure में प्रोविज़न करती है — `terraform/modules/ce-node`, जो `volterraedgeservices/volterra-node` मार्केटप्लेस इमेज से निर्मित है।

यह डेटा प्लेन (Argo), कंट्रोल प्लेन (Vega), एक Envoy प्रॉक्सी, एक Kubernetes स्टैक, और `vpm` चलाता है — वह एजेंट जो नोड को रजिस्टर करता है और उस पर बाकी सब कुछ प्रबंधित करता है।

जब कोई CE गलत व्यवहार करे, तो Site CLI ही उपकरण है। पहला निर्णय यह है कि कौन सा एक्सेस पथ लागू होता है, और इसे गलत समझने से समय बर्बाद होता है जो एक टूटे हुए नोड जैसा दिखता है।

डिबग API नोड तक **F5 Distributed Cloud कंट्रोल प्लेन के माध्यम से** पहुँचती है। यही कारण है कि यह विभाजन महत्वपूर्ण है: API केवल तभी उत्तर दे सकती है जब नोड ने रजिस्ट्रेशन कर लिया हो और `ONLINE` रिपोर्ट करे।

एक नोड जो रजिस्ट्रेशन करने में विफल रहा — खराब cloud-init, एक समाप्त टोकन, `register.ves.volterra.io` तक कोई मार्ग नहीं — यही वह स्थिति है जब आपको डायग्नोस्टिक्स की आवश्यकता होती है, और यही वह स्थिति है जिसमें API सेवा नहीं कर सकती।

नोड शिपमेंट के रूप में SSH भी अस्वीकार करता है। पोर्ट 22 CE पर बंद है, नेटवर्क सुरक्षा ग्रुप द्वारा नहीं:

```console
$ ssh -o ConnectTimeout=10 admin@<ce-public-ip>
ssh: connect to host <ce-public-ip> port 22: Connection refused
```

VNet के अंदर से भी, उसी सबनेट पर एक जंप होस्ट से सत्यापित किया गया, इसलिए सुरक्षा ग्रुप नियम खोलने से यह नहीं बदलता।

अतः: यदि साइट `ONLINE` है, तो डिबग API का उपयोग करें। यदि नहीं है, तो सीरियल कंसोल ही एकमात्र रास्ता है।

<Aside type="caution" title="पहले साइट की स्थिति जाँचें">
एक अनुरोध आपको बताता है कि आप किस पथ पर हैं:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/config/namespaces/system/sites/<site>" \
  | jq -r '.spec.site_state'
```

`ONLINE` का अर्थ है कि डिबग API काम करेगी। कुछ भी और — या कोई साइट जो मौजूद नहीं है — का अर्थ है सीरियल कंसोल।
</Aside>

## सुरक्षा नियम

ये नीचे दिए गए हर पृष्ठ पर हर कमांड के लिए लागू होते हैं।

- **जब तक निश्चित न हों, केवल-पठन।** कमांड सतह दो प्रिविलेज टियर में विभाजित है, और `Exec` टियर या तो नोड को बदलता है या एक स्थिति मार्कर पढ़ता है। इन पृष्ठों पर कोई `Exec` कमांड नहीं चलती, और न ही कैप्चर हार्नेस चलाती है।
- **कभी भी किसी कमांड को उसके नाम से सुरक्षित न मानें।** `ip-link-set` एक क्वेरी जैसा दिखता है और एक इंटरफ़ेस को डाउन कर देता है। `systemctl-restart-crio` एक लाइव डेटा प्लेन के नीचे कंटेनर रनटाइम को रीस्टार्ट करता है।
- **वह सबसे संकीर्ण कमांड पसंद करें जो प्रश्न का उत्तर दे।** `health` और `diagnosis` नोड को सस्ते में सारांशित करते हैं; `flow-l` एक 629,760-प्रविष्टि फ़्लो टेबल डंप करता है।
- **एक CE लाइव ट्रैफ़िक सेवा करता है।** ये साझा डेमो वातावरण हैं। मान लें कि कोई उस साइट से प्रेज़ेंट कर रहा है जिसे आप डीबग कर रहे हैं।

## यहाँ क्या प्रलेखित है

इस टेनेंट द्वारा चलाए जाने वाले सॉफ़्टवेयर बिल्ड पर डिबग API के माध्यम से पहुँचने योग्य हर कमांड, प्रत्येक के साथ कहीं और से प्रतिलिपि किए जाने के बजाय एक लाइव नोड से कैप्चर किया गया आउटपुट।

[कमांड संदर्भ](./commands/) उन सभी को उनकी श्रेणी, प्रिविलेज टियर और ट्रांसपोर्ट के साथ सूचीबद्ध करता है; [वर्कफ़्लो](./workflows/) उन्हें उन अनुक्रमों में जोड़ते हैं जिनका आप वास्तव में उपयोग करते हैं जब कुछ गलत हो।

Site CLI के ऑन-बॉक्स-केवल भाग — `configure`, `configure-network`, `factory-reset`, `upgrade` और लगभग साठ और `ExecCLI` कमांड — को कवर नहीं किया गया है।

वे केवल सीरियल कंसोल सत्र से पहुँचे जा सकते हैं, इसलिए उनके बारे में कुछ भी प्रोग्रामेटिक रूप से सत्यापित नहीं किया जा सकता, और असत्यापित कमांड सिंटैक्स वह दोष है जिसे इस दस्तावेज़ीकरण ने दोहराने से बचने के लिए बनाया गया है।
