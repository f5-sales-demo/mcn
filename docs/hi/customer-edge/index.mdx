एक Customer Edge (CE) वह F5 Distributed Cloud नोड है जिसे यह रिपॉज़िटरी Azure में
प्रोविज़न करती है — `terraform/modules/ce-node`, जो
`volterraedgeservices/volterra-node` मार्केटप्लेस इमेज से बनाया गया है।

यह डेटा प्लेन (Argo), कंट्रोल प्लेन (Vega), एक Envoy प्रॉक्सी, एक Kubernetes
स्टैक, और `vpm` चलाता है — वह एजेंट जो नोड को रजिस्टर करता है और उस पर बाकी सब कुछ
प्रबंधित करता है।

जब कोई CE ठीक से काम न करे, तो Site CLI ही वह उपकरण है। पहला निर्णय यह है कि कौन सा
एक्सेस पथ लागू होता है, और इसे गलत समझना समय को इस तरह बर्बाद करता है जो एक
खराब नोड जैसा प्रतीत होता है।

डिबग API नोड तक **F5 Distributed Cloud कंट्रोल प्लेन के माध्यम से** पहुँचता है।
यही पूरी वजह है कि यह विभाजन महत्वपूर्ण है: API केवल तब उत्तर दे सकता है जब नोड
रजिस्टर हो चुका हो और `ONLINE` रिपोर्ट कर रहा हो।

एक नोड जो रजिस्टर होने में विफल रहा — खराब cloud-init, समाप्त हो चुका टोकन,
`register.ves.volterra.io` तक कोई मार्ग नहीं — ठीक वही स्थिति है जहाँ आपको
डायग्नोस्टिक्स की आवश्यकता होती है, और ठीक वही स्थिति है जिसे API पूरा नहीं कर सकता।

SSH कोई तीसरा विकल्प नहीं है। `sshd` नोड पर चलता है और अपने आंतरिक (SLI) पते पर
उत्तर देता है, लेकिन `admin` खाता प्रमाणित नहीं हो सकता: `vpm` उस उपयोगकर्ता को
छोड़ देता है, इसलिए साइट ऑब्जेक्ट पर आपके द्वारा कॉन्फ़िगर की गई `ssh_key` कभी
लागू नहीं होती। कोई भी सिक्योरिटी ग्रुप नियम इसे नहीं बदलता। साक्ष्य
[SSH](./access/ssh/) पृष्ठ पर है, जो इसलिए मौजूद है क्योंकि वहाँ का हर लक्षण
एक फ़ायरवॉल या क्रेडेंशियल दोष जैसा प्रतीत होता है।

तो: यदि साइट `ONLINE` है, तो डिबग API का उपयोग करें। यदि नहीं, तो सीरियल कंसोल ही
अंदर जाने का एकमात्र रास्ता है।

<Aside type="caution" title="पहले साइट की स्थिति जाँचें">
एक ही अनुरोध आपको बता देता है कि आप किस पथ पर हैं:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/config/namespaces/system/sites/<site>" \
  | jq -r '.spec.site_state'
```

`ONLINE` का अर्थ है कि डिबग API काम करेगा। कुछ भी और — या ऐसी साइट जो मौजूद ही
नहीं है — का अर्थ है सीरियल कंसोल।
</Aside>

## सुरक्षा नियम

ये नीचे दिए गए प्रत्येक पृष्ठ की प्रत्येक कमांड के लिए लागू होते हैं।

- **जब तक आप निश्चित न हों, केवल-पढ़ने योग्य रहें।** कमांड सतह दो
  विशेषाधिकार स्तरों में विभाजित है, और `Exec` स्तर या तो नोड को बदलता है या एक
  स्टेट मार्कर पढ़ता है। इन पृष्ठों पर कुछ भी `Exec` कमांड नहीं चलाता, और न ही
  कैप्चर हार्नेस चलाता है।
- **कभी यह न मानें कि कोई कमांड अपने नाम से सुरक्षित है।** `ip-link-set` एक
  क्वेरी जैसा पढ़ा जाता है और एक इंटरफ़ेस को डाउन कर देता है।
  `systemctl-restart-crio` एक जीवित डेटा प्लेन के अंतर्गत कंटेनर रनटाइम को
  रीस्टार्ट करता है।
- **उस सबसे संकीर्ण कमांड को प्राथमिकता दें जो प्रश्न का उत्तर देती है।** `health` और
  `diagnosis` नोड का सारांश सस्ते में देते हैं; `flow-l` 629,760-प्रविष्टियों वाली
  फ़्लो टेबल डंप करता है।
- **एक CE जीवित ट्रैफ़िक सेवा देता है।** ये साझा डेमो परिवेश हैं। यह मान लें कि कोई
  उसी साइट से प्रस्तुति दे रहा है जिसे आप डिबग कर रहे हैं।

## यहाँ क्या दस्तावेज़ित है

इस टेनेंट पर चल रहे सॉफ़्टवेयर बिल्ड पर डिबग API के माध्यम से पहुँचने योग्य प्रत्येक
कमांड, प्रत्येक के साथ आउटपुट जो किसी जीवित नोड से कैप्चर किया गया है, कहीं और से
प्रतिलिपि नहीं किया गया।

[कमांड संदर्भ](./commands/) उन सभी को उनकी श्रेणी, विशेषाधिकार स्तर और ट्रांसपोर्ट
के साथ सूचीबद्ध करता है; [वर्कफ़्लो](./workflows/) उन्हें उन अनुक्रमों में जोड़ते हैं
जिनका आप वास्तव में कुछ गलत होने पर उपयोग करते हैं।

Site CLI के केवल-ऑन-बॉक्स भाग — `configure`, `configure-network`,
`factory-reset`, `upgrade` और लगभग साठ अन्य `ExecCLI` कमांड — यहाँ शामिल नहीं हैं।

वे केवल सीरियल कंसोल सत्र से पहुँचने योग्य हैं, इसलिए उनके बारे में कुछ भी
प्रोग्रामेटिक रूप से सत्यापित नहीं किया जा सकता, और असत्यापित कमांड सिंटैक्स ही वह
दोष है जिसे दोहराने से बचने के लिए यह दस्तावेज़ीकरण मौजूद है।
