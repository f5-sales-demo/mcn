<Aside type="danger" title="API इसे डीबग नहीं कर सकता">
debug API नोड तक F5 Distributed Cloud कंट्रोल प्लेन के माध्यम से, उस टनल के ऊपर से पहुँचता है
जिसे रजिस्ट्रेशन स्थापित करता है। यदि रजिस्ट्रेशन विफल हुआ तो कोई टनल नहीं है,
इसलिए इस साइट पर मौजूद हर कमांड इस विशेष विफलता के लिए अनुपलब्ध है। यदि नोड के पास अभी भी
कोई नेटवर्क पथ है तो [Site Console](../../access/site-console/) से काम करें, और यदि नहीं है तो
[serial console](../../access/serial-console/) से।
</Aside>

<Steps>

1. **पुष्टि करें कि आप सही टेनेंट से पूछ रहे हैं।** इसमें एक कमांड लगता है और यह पहले है
   क्योंकि इसे गलत करने पर हर बाद का चरण आपसे झूठ बोलेगा: उस टेनेंट में एक स्वस्थ फ़्लीट जिसे
   आप नहीं देख रहे हैं, उस फ़्लीट से अप्रभेद्य है जो कभी रजिस्टर नहीं हुई।

   ```bash
   cd terraform
   terraform output -raw xc_tenant       # the tenant this deployment belongs to
   terraform output -raw xc_env_tenant   # the tenant your shell is exporting
   ```

   ```text
   f5-sales-demo
   f5-sales-demo
   ```

   बेमेल है, या कोई क्रेडेंशियल जिसे आप सही मानते हैं केवल `401` लौटा रहा है? यह
   किसी अन्य टेनेंट के लिए बनाए गए टोकन का लक्षण है, और इसने इस डिप्लॉयमेंट को पहले ही एक
   पूर्ण रीबिल्ड की कीमत चुकाई है ([issue 696](https://github.com/f5-sales-demo/mcn/issues/696))।

2. **पुष्टि करें कि टेनेंट क्या सोचता है।** साइट सूची से अनुपस्थित होना
   मौजूद होने पर `ONLINE` न होने से भिन्न समस्या है।

   ```bash
   curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
     "$XCSH_API_URL/api/config/namespaces/system/sites" | jq -r '.items[].name'
   ```

   यदि साइट मौजूद है और `ONLINE` रिपोर्ट करती है, तो रजिस्ट्रेशन सफल हुआ और आप
   गलत वर्कफ़्लो में हैं।

3. **साइट का रजिस्ट्रेशन और उसकी स्थिति खोजें।** एक नोड रजिस्टर हो सकता है और फिर
   अनुमोदन की प्रतीक्षा कर सकता है, जो बाहर से विफलता जैसा ही दिखता है।

   ```bash
   curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
     "$XCSH_API_URL/api/register/namespaces/system/registrations_by_site/<site>" \
     | jq -r '.items[] | "\(.name)  \(.object.status.current_state)  \(.object.spec.gc_spec.infra.hostname)"'
   ```

   ```text
   r-a97e20c8-b7e1-483d-bd76-34a64ff8bc78  ONLINE  f5-xc-ce-vm-01
   ```

   कोई आइटम न होने का अर्थ है कि नोड ने अभी तक रजिस्टर नहीं किया है — सीरियल कंसोल पर जाएँ।
   `ONLINE` के अलावा किसी स्थिति में कोई आइटम का अर्थ है कि उसने रजिस्टर किया और उसके बाद कुछ
   विफल हुआ, जो एक भिन्न जाँच है।

   अनुमोदन की प्रतीक्षा कर रही किसी भी चीज़ के लिए पूरे नेमस्पेस को खोजने के लिए, `listregistrationsbystate`
   स्थिति को एक **`POST` बॉडी** के रूप में लेता है:

   ```bash
   curl -sS -X POST -H "Authorization: APIToken $XCSH_API_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"namespace":"system","state":"PENDING"}' \
     "$XCSH_API_URL/api/register/namespaces/system/listregistrationsbystate" | jq -r '.items[].name'
   ```

   एक स्वस्थ फ़्लीट पर यह कुछ नहीं लौटाता, क्योंकि अनुमोदन स्वचालित है।

4. **पुष्टि करें कि VM वास्तव में चल रहा है**, सॉफ़्टवेयर दोष मानने से पहले।

   ```bash
   az vm list -d -g <resource-group> --query "[].{name:name,power:powerState}" -o table
   ```

   ```text
   Name            Power
   --------------  ----------
   ar-ecmp-client  VM running
   f5-xc-ce-vm-01  VM running
   f5-xc-ce-vm-02  VM running
   f5-xc-ce-vm-03  VM running
   ```

5. **सीरियल कंसोल संलग्न करें।** इंटरैक्टिव रूप से इसके लिए एक वास्तविक टर्मिनल की आवश्यकता होती है;
   संलग्न करना स्वयं इसके बजाय websocket पर स्क्रिप्ट किया जा सकता है — देखें
   [serial console](../../access/serial-console/)।

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

   यदि यह मना करता है, तो नोड को अगम्य मानने से पहले जाँचें कि VM पर बूट डायग्नोस्टिक्स
   सक्षम है; वह पूर्वापेक्षा और उसके विफलता मोड
   [serial console](../../access/serial-console/) पृष्ठ पर शामिल हैं।

6. **कंसोल जो दिखाता है उसे इस क्रम में पढ़ें।** पहले cloud-init — एक नोड जिसका
   cloud-init कभी पूरा नहीं हुआ, उसके पास रजिस्टर करने के लिए कोई कॉन्फ़िगरेशन नहीं है। फिर
   रजिस्ट्रेशन प्रयास स्वयं, फिर DNS: यदि नोड
   `register.ves.volterra.io` को हल नहीं कर सकता, तो डाउनस्ट्रीम में कुछ भी काम नहीं कर सकता।

7. **एक बार नोड `ONLINE` हो जाए**, तो [`health`](../../commands/system/health/) से सत्यापित करें
   और `state: PROVISIONED` की अपेक्षा करें।

</Steps>

<Aside type="caution" title="एक रजिस्ट्रेशन का नाम UUID पर होता है, कभी उसकी साइट पर नहीं">
रजिस्ट्रेशन का नाम `r-<uuid>` होता है, और ऐसा कोई एंडपॉइंट नहीं है जो वहाँ साइट का नाम लेता हो जहाँ
रजिस्ट्रेशन का नाम अपेक्षित है।
`GET .../registrations/<site>` `404` लौटाता है, जो पढ़ने में लगता है "इस साइट का कोई
रजिस्ट्रेशन नहीं है" और वास्तव में है "वह रजिस्ट्रेशन का नाम नहीं है"। साइट-से-रजिस्ट्रेशन
मैपिंग केवल `registrations_by_site/<site>` से आती है, जैसा कि चरण 3 में है, या
`registrations` को सूचीबद्ध करके और `gc_spec.passport.cluster_name` पर मिलान करके।

इसी जाल ने ऐसा दिखाया जैसे एक स्वस्थ फ़्लीट में शून्य रजिस्ट्रेशन थे।
</Aside>

## सामान्य कारण

- **आप गलत टेनेंट की ओर संकेत कर रहे हैं**, इसलिए एक फ़्लीट जो ठीक है अनुपस्थित दिखती है। चरण 1।
- cloud-init पूरा नहीं हुआ, इसलिए `/etc/vpm/config.yaml` अनुपस्थित है या गलत है।
- रजिस्ट्रेशन टोकन समाप्त हो गया है, पहले ही उपभोग हो चुका है, या किसी अन्य टेनेंट से है।
- `register.ves.volterra.io` तक कोई egress रूट नहीं।
- सर्टिफिकेट को अवैध करने के लिए पर्याप्त बड़ा क्लॉक स्क्यू — बाद में
  [`chronyc-sources`](../../commands/network/chronyc-sources/) से जल्दी खारिज किया जा सकता है, लेकिन
  नोड ऑनलाइन होने तक पहुँच योग्य नहीं। जब SSH उपलब्ध हो, तो [SSH](../../access/ssh/) लॉगिन बैनर
  आपके कुछ भी चलाने से पहले `NTP: Synced` और रिज़ॉल्वर की स्थिति रिपोर्ट करता है।
