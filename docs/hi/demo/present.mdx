यह डेमो जिस दावे का समर्थन करता है वह सीमित है और उसे सटीक रूप से बताना उपयुक्त है, क्योंकि इससे
व्यापक दावा प्रश्नों के सामने टिक नहीं पाएगा:

> कई Customer Edges प्रत्येक eBGP द्वारा उसी होस्ट रूट का विज्ञापन करते हैं, और Azure उन सभी को
> समान-लागत नेक्स्ट हॉप्स के रूप में स्थापित करता है। अतः ट्रैफ़िक वितरण और नोड हटाना
> रूटिंग फ़ैब्रिक के गुण हैं — CEs के सामने कोई Azure लोड बैलेंसर नहीं है।

पहले [चार स्वास्थ्य जाँचें](../verify/) चलाएँ। नीचे दी गई हर बात यह मानकर चलती है कि वे उत्तीर्ण हुईं।

## वह एक कमांड जो इसे दृश्यमान बनाता है

प्रभावी रूट्स सबसे मज़बूत एकल कलाकृति हैं: वे वही हैं जो Azure ने वास्तव में प्रोग्राम किया,
न कि वह जो CEs दावा करते हैं।

```bash
cd terraform
az network nic show-effective-route-table \
  -g "$(terraform output -raw resource_group_name)" \
  -n "$(terraform output -raw client_nic_name)" \
  --query "value[?addressPrefix[0]=='$(terraform output -raw vip)/32'].{prefix:addressPrefix[0],nh:nextHopIpAddress,state:state}" \
  -o json
```

2026-07-28 पर देखा गया:

```json
[
  {
    "nh": ["10.0.1.5", "10.0.1.6", "10.0.1.4"],
    "prefix": "10.250.0.10/32",
    "state": "Active"
  }
]
```

एक प्रीफ़िक्स, तीन नेक्स्ट हॉप्स, `Active`। यही इस डेमो का पूरा सार एक ही आउटपुट में है, और
इस पर रुकना उपयुक्त है: इस चित्र में कुछ भी लोड बैलेंसर नहीं है।

फिर इसे सेवा देते हुए दिखाएँ, VNet के भीतर से और `Host` हेडर के साथ:

```bash
az vm run-command invoke \
  -g "$(terraform output -raw resource_group_name)" \
  -n "$(terraform output -raw client_vm_name)" \
  --command-id RunShellScript --query "value[0].message" -o tsv \
  --scripts "curl -s -o /dev/null -w '%{http_code}\n' \
               -H 'Host: $(terraform output -raw lb_domain)' \
               http://$(terraform output -raw vip)/"
```

<Aside type="caution" title="ब्राउज़र में पता टाइप करके इसका डेमो न करें">
लोड बैलेंसर `Host` पर मैच करता है, इसलिए केवल IP वाला अनुरोध **404** लौटाता है — एक पूरी तरह
स्वस्थ परिनियोजन पर भी। या तो हेडर भेजें, या पहले डोमेन को VIP पर रिज़ॉल्व करें। दर्शकों के
सामने 404 से पीछे हटना कठिन होता है, भले ही कुछ भी गलत न हो।
</Aside>

## सुझाया गया क्रम

<Steps>

1. **इसे प्रस्तुत करें।** एक VIP, कई CEs, कोई लोड बैलेंसर नहीं। रूटिंग फ़ैब्रिक ही
   HA तंत्र है।
2. **विज्ञापन पक्ष दिखाएँ।** पीयरिंग्स को लूप करें ([जाँच 2](../verify/)) — प्रत्येक CE
   अपने स्वयं के नेक्स्ट हॉप के साथ उसी प्रीफ़िक्स का विज्ञापन करता है, सभी का AS पथ एक ही है, इसलिए किसी को
   प्राथमिकता नहीं मिलती।
3. **दिखाएँ कि Azure ने इसके साथ क्या किया।** ऊपर दी गई प्रभावी रूट टेबल: एक प्रीफ़िक्स, N नेक्स्ट
   हॉप्स, `Active`।
4. **इसे सेवा देते हुए दिखाएँ।** ऊपर दिया गया `curl`, हेडर के साथ।
5. **कॉन्फ़िगरेशन दिखाएँ।** [Terraform](../terraform/) यहाँ प्रकाशित है, उन फ़ाइलों से पढ़ा गया
   जो इसे परिनियोजित करती हैं — जब कोई पूछे कि क्या यह पुनरुत्पादनीय है, तब उपयोगी।

</Steps>

## यह डेमो अभी क्या नहीं दिखा सकता

यहाँ बताया गया है, बजाय इसके कि लाइव में पता चले। ये तीनों साक्ष्य की अनुपस्थिति हैं, ज्ञात
विफलताएँ नहीं।

<Aside type="danger" title="इन पृष्ठों से फ़ेलओवर कहानी की रिहर्सल न करें">
**फ़ेलओवर का परीक्षण नहीं किया गया है।** समान-लागत नेक्स्ट हॉप्स स्थापित होने के रूप में सत्यापित हैं; जब कोई
CE रोका जाता है या विज्ञापन बंद कर देता है तो रूट टेबल का क्या होता है, यह इस परिनियोजन पर
आज़माया नहीं गया है। इच्छित तंत्र यह है कि एक CE का विज्ञापन वापस लिया जाए और नेक्स्ट-हॉप गिनती
घटते हुए देखी जाए, लेकिन जब तक वह वास्तव में चलाया और मापा नहीं गया, यह एक
योजना है, परिणाम नहीं — इसलिए इसका वादा न करें, और दर्शकों के सामने इसे तात्कालिक रूप से न करें।

[issue 700](https://github.com/f5-sales-demo/mcn/issues/700) में ट्रैक किया गया। इसके लिए एक ऐसी विंडो
चाहिए जब कोई और इस परिवेश का उपयोग न कर रहा हो, क्योंकि यह लाइव विज्ञापन स्थिति को बदलता है।
</Aside>

- **नेक्स्ट हॉप्स के बीच ट्रैफ़िक वितरण मापा नहीं गया है।** VIP पर 1,470 अनुरोधों का हिसाब
  [सत्यापन पृष्ठ](../verify/) पर दिया गया है, जो स्थापित करता है कि पथ काम करता है और समय के साथ कैसा
  व्यवहार करता है। उसमें से कुछ भी यह नहीं दिखाता कि अनुरोध नेक्स्ट हॉप्स के बीच कैसे फैलाए गए, और
  यह टोपोलॉजी उन्हें आरोपित करने के लिए कोई प्रति-नोड HTTP लिसनर नहीं देती। यदि पूछा जाए
  "क्या यह समान है?", तो ईमानदार उत्तर है कि इसे यहाँ मापा नहीं गया है।
- **नए बिल्ड में कन्वर्जेंस ट्रांज़िएंट का कारण स्थापित नहीं है।** इसे
  चरित्रांकित किया गया है — यह कब होता है, कितनी देर तक, और यह कि पूरे समय ऑरिजिन स्वच्छ रहता है —
  और समझाया नहीं गया है।

<Aside type="note" title="यदि आप नए बनाए गए स्टैक पर प्रस्तुति दे रहे हैं, तो प्रतीक्षा करें">
CEs के `ONLINE` होने के बाद लगभग पहले 45 मिनट तक VIP अनुरोधों का एक छोटा अंश खो देता है। यह
पूरी तरह ठीक हो जाता है। डेमो को आवश्यकता से काफ़ी पहले बनाएँ, और ठीक पहले जाँच 4 को दोबारा चलाएँ।
</Aside>
