यह डिप्लॉयमेंट **Azure में active/active Customer Edge उच्च उपलब्धता** को प्रदर्शित करता है,
जिसमें CEs के सामने कोई Azure लोड बैलेंसर नहीं होता। प्रत्येक CE eBGP द्वारा वही होस्ट रूट
ओरिजिनेट करता है, और Azure Route Server उन सभी को VNet में equal-cost next hops के रूप में इंस्टॉल करता है।
इसलिए ट्रैफ़िक वितरण और विफल नोड को हटाना, लोड बैलेंसर के बजाय रूटिंग फ़ैब्रिक में होना चाहिए।

इन पृष्ठों की प्रत्येक बात लाइव डिप्लॉयमेंट पर चलाई गई थी, और दिखाया गया आउटपुट वही है जो उसने
उत्पन्न किया। वह वाक्य जो *कवर नहीं करता* — failover, और ट्रैफ़िक next hops के बीच कैसे विभाजित
होता है — उसे मान लिए जाने के बजाय स्पष्ट रूप से बताया गया है।

## यह क्या डिप्लॉय करता है

```text
                     Azure Route Server            ASN 65515
                      two instance addresses
                                 |
             +-------------------+-------------------+
             |                   |                   |
        <key>-bgp           <key>-bgp           <key>-bgp        eBGP
             |                   |                   |         CE ASN 64512
        CE eth0/SLO         CE eth0/SLO         CE eth0/SLO
          CE site             CE site             CE site
             |                   |                   |
             +--- each advertises the same VIP /32 ---+
                    equal-cost multipath into the VNet
```

| अंश | यह क्या है |
| --- | --- |
| F5 Distributed Cloud टेनेंट | `var.expected_xc_tenant` — एकमात्र स्थान जहाँ टेनेंट का नाम दिया गया है |
| नेमस्पेस | CE साइटें `system` में; ऑरिजिन पूल और लोड बैलेंसर `var.xc_app_namespace` में |
| Customer Edges | `var.ce_count` सिंगल-नोड Secure Mesh v2 साइटें, 1 से 3, प्रति availability zone एक |
| CE सॉफ़्टवेयर | `var.ce_sw_version` / `var.ce_os_version` द्वारा पिन किया गया |
| Azure VMs | प्रत्येक में तीन NICs — management/SLO, external, internal/SLI |
| रूट एक्सचेंज | एक Azure Route Server, ASN `var.rs_asn`, दो इंस्टेंस एड्रेस |
| Peerings | प्रति CE एक, नाम `<key>-bgp`, CE ASN `var.ce_asn` |
| विज्ञापित VIP | `var.vip` एक `/32` के रूप में, प्रत्येक CE द्वारा समान रूप से ओरिजिनेट किया गया |
| लोड बैलेंसर | `var.lb_domain` को सर्व करता है, `var.origin_ip` पर एक ऑरिजिन पूल द्वारा समर्थित |
| टेस्ट क्लाइंट | उसी VNet के अंदर एक VM, VIP पर ट्रैफ़िक चलाने के लिए |

ऊपर दिया गया कुछ भी ऐसा शाब्दिक मान नहीं है जिसे आपको कॉपी करना चाहिए। प्रत्येक मान डिप्लॉयमेंट से
पढ़ा जा सकता है, और प्रत्येक पृष्ठ उसका नाम देने के बजाय उसे पढ़ता है:

```bash
cd terraform
terraform output -raw resource_group_name
terraform output -json xc_site_names
```

<Aside type="caution" title="VIP को प्रत्येक VNet CIDR के बाहर होना चाहिए">
`terraform/main.tf` में एक `check` ब्लॉक है जो यह प्रमाणित करता है कि VIP hub और spoke दोनों
CIDRs के बाहर है, और अन्यथा प्लान को अस्वीकार कर देता है। इसका बताया गया कारण यह है कि VNet CIDR
के अंदर का VIP, BGP रूट अधिक विशिष्ट होने के बावजूद VNet के अपने सिस्टम रूट से हार जाता है।

इस गार्ड को अनुबंध की तरह लें: यदि आप इस डेमो को भिन्न एड्रेसिंग पर री-पॉइंट करते हैं, तो VIP को भी
उसके साथ VNet रेंज से बाहर जाना होगा।
</Aside>

<Aside type="note" title="2026-07-28 को देखा गया: लाइव ऑब्जेक्ट्स अभी भी अंतरिम नाम रखते हैं">
ऑब्जेक्ट नाम `var.component` से व्युत्पन्न होते हैं, इसलिए एक अनपिन किया गया डिप्लॉयमेंट
`<component>-<region>01`, `<component>-f5se`, `<component>-pool`, `<component>-rs` और
`<component>-bastion` बनाता है। वर्तमान में चल रहा डेमो इससे पुराना है और अपने मूल नाम बनाए रखता है,
जो एक स्थानीय `terraform.tfvars` में पिन किए गए हैं, ताकि पर्यावरण उपयोग में रहते हुए कुछ भी प्रतिस्थापित न हो।

यही कारण है कि इन पृष्ठों पर वास्तविक कमांड आउटपुट में ऐसे नाम दिखते हैं जो ऊपर दिए पैटर्न से मेल
नहीं खाते। व्युत्पन्न नामों को अपनाने से प्रत्येक CE VM प्रतिस्थापित हो जाता है, क्योंकि साइट का नाम वह
`ClusterName` है जो cloud-init में समाहित है और cloud-init केवल पहले बूट पर ही चलता है — इसलिए यह एक
जानबूझकर किया गया पुनर्निर्माण है, जिसे
[issue 700](https://github.com/f5-sales-demo/mcn/issues/700) में ट्रैक किया गया है, न कि नाम बदलना।
</Aside>
