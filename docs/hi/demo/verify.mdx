प्रस्तुति देने से पहले इन्हें चलाएँ। प्रत्येक जाँच यह सीमित करती है कि खराबी कहाँ होगी, इसलिए कोई विफलता
आपको कुछ बताती है, न कि केवल यह कि कुछ गलत है।

प्रत्येक कमांड जो उसे आवश्यक है वह परिनियोजन से पढ़ती है। इन्हें एक बार सेट करें और बाकी अपने आप चलेंगे:

```bash
cd terraform
RG=$(terraform output -raw resource_group_name)
RS=$(terraform output -raw route_server_name)
CLIENT=$(terraform output -raw client_vm_name)
DOMAIN=$(terraform output -raw lb_domain)
VIP=$(terraform output -raw vip)
NIC=$(terraform output -raw client_nic_name)
```

## चार जाँचें, इसी क्रम में

<Steps>

1. **प्रत्येक साइट `ONLINE` है।** यदि यह सत्य नहीं है तो इसके बाद कुछ भी सत्य नहीं हो सकता।

   ```bash
   for s in $(terraform output -json xc_site_names | jq -r '.[]'); do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   2026-07-28 को देखा गया, तीन CE:

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **प्रत्येक पीयरिंग उस CE का VIP विज्ञापन सीख रही है।** प्रत्येक पीयरिंग की क्वेरी
   अलग-अलग करें — नीचे दिया गया पहला जाल देखें, क्योंकि यहीं डेमो सबसे अधिक बार खराब
   दिखता है और होता नहीं है।

   ```bash
   for k in $(terraform output -json xc_site_names | jq -r 'keys[]'); do
     echo "--- ${k}-bgp"
     az network routeserver peering list-learned-routes \
       --name "${k}-bgp" --routeserver "$RS" -g "$RG" \
       --query "RouteServiceRole_IN_0[?network=='${VIP}/32'].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   2026-07-28 को देखा गया:

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp
   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp
   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   तीन पीयरिंग, तीन भिन्न नेक्स्ट हॉप, एक प्रिफ़िक्स। यह ECMP का विज्ञापन पक्ष सिद्ध हो गया।

3. **क्लाइंट के प्रभावी रूट प्रत्येक नेक्स्ट हॉप को धारण करते हैं।** यह स्वयं ECMP है, जैसा
   VNet ने इसे प्रोग्राम किया है — वह नहीं जो CE दावा करते हैं, बल्कि वह जो Azure ने इसके साथ किया।

   ```bash
   az network nic show-effective-route-table -g "$RG" -n "$NIC" \
     --query "value[?addressPrefix[0]=='${VIP}/32'].{prefix:addressPrefix[0],nh:nextHopIpAddress,type:nextHopType,state:state}" \
     -o json
   ```

   2026-07-28 को देखा गया:

   ```json
   [
     {
       "nh": ["10.0.1.5", "10.0.1.6", "10.0.1.4"],
       "prefix": "10.250.0.10/32",
       "state": "Active",
       "type": "VirtualNetworkGateway"
     }
   ]
   ```

   `nh` में प्रति CE एक प्रविष्टि के साथ `state: Active` ही जाँच है। **क्रम महत्वपूर्ण नहीं है और
   स्थिर नहीं है** — Azure इन्हें कॉल-दर-कॉल भिन्न रूप से लौटाता है, इसलिए किसी पिछले रन से तुलना
   करने की बजाय इन्हें गिनें। जहाँ आप तीन की अपेक्षा करते हैं वहाँ एक नेक्स्ट हॉप का अर्थ है कि कोई
   CE विज्ञापन करना बंद कर चुका है, और चरण 2 यह पहचानता है कि कौन सा।

4. **VIP ट्रैफ़िक सर्व करता है।** क्लाइंट VM से, और **`Host` हेडर के साथ** — दूसरा जाल देखें।
   समस्या देखने के लिए पर्याप्त अनुरोधों का नमूना लें: कुछ दर्जन अनुरोध नीचे वर्णित कन्वर्जेंस
   विंडो के भीतर भी 100 % जैसे पढ़े जाते हैं।

   ```bash
   az vm run-command invoke -g "$RG" -n "$CLIENT" \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts "ok=0; fail=0
                for i in \$(seq 1 60); do
                  c=\$(curl -s -o /dev/null -m 5 -w '%{http_code}' \
                        -H 'Host: ${DOMAIN}' http://${VIP}/)
                  [ \"\$c\" = 200 ] && ok=\$((ok+1)) || fail=\$((fail+1))
                done
                echo \"OK=\$ok FAIL=\$fail\""
   ```

   2026-07-28 को देखा गया:

   ```text
   VIP with Host header: OK=60 FAIL=0
   bare IP (no Host): 404
   ```

</Steps>

## जाल: एक पीयरिंग एक रूट दिखाती है, और यह सही है

`list-learned-routes` उस पीयरिंग तक सीमित है जिसका आप नाम देते हैं। यह वही रिपोर्ट करता है जो
**उस** पीयर ने विज्ञापित किया, Route Server की पूरी तालिका नहीं।

इसलिए अकेले एक पीयरिंग की क्वेरी करने पर एक ही नेक्स्ट हॉप के माध्यम से एक ही VIP `/32` लौटता है, और
इसे "केवल एक CE विज्ञापन कर रहा है — अन्य डाउन हैं" के रूप में पढ़ने का प्रलोभन होता है। कुछ भी डाउन
नहीं है। अन्य विज्ञापन अपनी-अपनी पीयरिंग पर दिखाई देते हैं, और चरण 2 इन पर ही लूप करता है।

एकल पीयरिंग क्वेरी से ECMP की पुष्टि करना संभव नहीं है। या तो प्रत्येक पीयरिंग पर लूप करें, या
क्लाइंट की प्रभावी रूट तालिका पढ़ें, जो एक ही कॉल में संयुक्त परिणाम दिखाती है।

## जाल: बेयर-IP अनुरोध 404 लौटाता है

लोड बैलेंसर `Host` पर मिलान करता है। VIP कोई ऐसा वर्चुअल सर्वर नहीं है जो पते से जुड़ने वाले
किसी भी व्यक्ति को कुछ सर्व करे।

ये दोनों स्वस्थ परिनियोजन के विरुद्ध एक ही रन से आए:

```text
curl -H "Host: $DOMAIN" http://$VIP/   ->  200   (60 of 60)
curl                     http://$VIP/   ->  404
```

**बेयर-IP 404 इसका प्रमाण है कि पथ काम करता है** — अनुरोध CE तक पहुँचा, CE के प्रॉक्सी ने उत्तर
दिया, और उसने इनकार किया क्योंकि कोई कॉन्फ़िगर किया गया डोमेन मेल नहीं खाया। इसे आउटेज के रूप में
पढ़ना आपको BGP की ओर देखने भेजता है, जहाँ आपको कुछ गलत नहीं मिलेगा।

यही डेमो के दौरान भी लागू होता है: यदि आप डोमेन को उस पते पर रिज़ॉल्व करने की बजाय ब्राउज़र में पता
टाइप करते हैं, तो आपको 404 मिलेगा।

## VIP पहले पौन घंटे तक अनुरोध गिराता है, फिर रुक जाता है

नए बनाए गए स्टैक पर VIP, CE के `ONLINE` पहुँचने के बाद लगभग पहले 45 मिनट तक अनुरोधों का एक छोटा
अंश खो देता है, और उसके बाद साफ़-सुथरा सर्व करता है। क्लाइंट VM से 1,470 अनुरोधों पर मापा गया, सभी
`Host` हेडर के साथ:

| विंडो | अनुरोध | विफलताएँ | दर |
| --- | --- | --- | --- |
| ECMP आने के बाद पहले ~45 मिनट | 570 | 12 | **2.11 %** |
| उसके बाद के 23 मिनट | 900 | **0** | **0.00 %** |

प्रत्येक विफलता `curl: (28)` थी — शून्य बाइट प्राप्त होने के साथ टाइमआउट — कोई HTTP त्रुटि स्थिति
नहीं। अंतिम विफलता ECMP आने के लगभग 43 मिनट बाद हुई। 900 साफ़ अनुरोधों में से 400 30-सेकंड के
टाइमआउट के साथ चले और प्रत्येक 2 सेकंड से कम में पूरा हुआ, इसलिए किसी छोटे टाइमआउट ने कुछ छिपाया
नहीं।

**ऑरिजिन कारण नहीं था।** सीधे ऑरिजिन पर एक नियंत्रण बैच (`terraform output -raw origin_ip`, VIP को
बायपास करते हुए) विफल हो रहे VIP बैचों *के साथ-साथ* 120 में से 120 साफ़ चला। खराबी VIP, ECMP या
CE पथ में कहीं है।

दो बातें जिन्हें जानबूझकर ऐसा नहीं कहा जा रहा:

- **यह स्थिर-अवस्था का दोष नहीं है।** यह पूरी तरह साफ़ हो जाता है और साफ़ बना रहता है। एक घंटे से
  चल रहे डेमो में यह समस्या नहीं होती — घंटों से चल रहे स्टैक पर, ऊपर की जाँच 4 में 60 में से 60।
- **यह किसी विशेष CE को जिम्मेदार नहीं ठहराया जा सकता।** इस टोपोलॉजी में कुछ भी प्रति-नोड HTTP
  लिसनर नहीं देता, इसलिए गिराए गए अनुरोध को उस नोड से जोड़ने का कोई तरीका नहीं है जिसने उसे गिराया।
  CE के बाहरी इंटरफ़ेस पर कोई HTTP लिसनर बिल्कुल नहीं है — केवल VIP `/32` उत्तर देता है।

यह किसी भिन्न टेनेंट में एक साफ़ पुनर्निर्माण पर पुनः उत्पन्न हुआ, इसलिए यह पर्यावरण की बजाय
टोपोलॉजी का अनुसरण करता है।

<Aside type="caution" title="40 अनुरोधों का नमूना लेकर यह निष्कर्ष न निकालें कि सब ठीक है">
40 से 50 के बैच विफल होने वाली विंडो के भीतर भी अधिकांश समय 100 % जैसे पढ़े जाते हैं। इसी तरह इसे
पहले एक चालू निम्न-दर दोष के रूप में और फिर पूरी तरह से कोई दोष न होने के रूप में गलत ढंग से
चिह्नित किया गया था। समय में अलग-अलग बैचों में 100 या अधिक का नमूना लें।
</Aside>

## दो और मापन जाल

दोनों ने इस परिवेश में आत्मविश्वास से भरे गलत उत्तर उत्पन्न किए, और दोनों में से कोई स्पष्ट नहीं है।

- **VNet के भीतर से प्रोब करें, अपने वर्कस्टेशन से नहीं।** एक कॉर्पोरेट प्रॉक्सी सामान्य पोर्ट पर
  स्वयं TCP हैंडशेक पूरा कर सकता है, इसलिए वर्कस्टेशन प्रोब उस पोर्ट को **खुला** बताता है जो वास्तव
  में बंद है। वर्कस्टेशन से CE के सार्वजनिक पतों पर पोर्ट 80 और 443 खुले पढ़े जाते हैं और VNet के
  भीतर से प्रोब करने पर बंद होते हैं। क्लाइंट VM का उपयोग करें।
- **CE पर पोर्ट 22 केवल आंतरिक (SLI) पते पर उत्तर देता है।** क्लाइंट VM से प्रोब करने पर, प्रत्येक
  CE का आंतरिक पता एक OpenSSH बैनर लौटाता है, जबकि उसके प्रबंधन और बाहरी पते टाइमआउट हो जाते हैं —
  जैसा कि नियंत्रण के रूप में उपयोग किए गए किसी अप्रयुक्त पते के साथ भी होता है। eth0 का नाम बदलकर
  `a-i-eth0` कर दिया जाता है और वह कोई होस्ट IP नहीं रखता, क्योंकि डेटापथ उसका स्वामी है। इसलिए जिस
  पते से आप नोड को जानते हैं, उसे प्रोब करना नोड की SSH स्थिति के बारे में कुछ नहीं बताता।

<Aside type="danger" title="किसी CE के आंतरिक पते को कभी हार्डकोड न करें — प्रत्येक पुनर्निर्माण पर वे पुनः आवंटित होते हैं">
Azure यह संरक्षित नहीं करता कि आंतरिक सबनेट में किस CE को कौन सा पता मिलता है। 2026-07-28 को देखा
गया, पुनर्निर्माण के बाद, तीन CE के पास `10.0.3.7`, `10.0.3.5` और `10.0.3.4` थे: नोड क्रम में नहीं,
सन्निहित नहीं, और पहले जो उनके पास था उससे भिन्न। परीक्षण क्लाइंट का अपना NIC उसी सबनेट में बैठता है
और उसके पास वह पता रहा है जो पहले किसी CE के पास था।

उन्हें याद रखने की बजाय पढ़ें:

```bash
terraform output -json ce_sli_private_ips
```

Terraform स्टेट उपलब्ध न होने पर, NIC नाम से Azure से पूछें, जो *स्थिर* है:

```bash
az network nic show -g "$RG" -n "<vm-name>-internal-nic" \
  --query ipConfigurations[0].privateIPAddress -o tsv
```

किसी याद किए हुए पते से जुड़ना आपको गलत नोड पर पहुँचाता है, ऐसे VM पर जो CE नहीं है, या कहीं नहीं —
और इनमें से अंतिम स्थिति "SSH सक्षम नहीं है" के समान ही दिखती है।
</Aside>

## पुष्टि करें कि ऑन-बॉक्स कमांड सतह अभी भी दस्तावेज़ों से मेल खाती है

```bash
bash scripts/capture-sitecli.sh --check \
  --site "$(terraform output -json xc_site_names | jq -r '.eastus01')" \
  --node "$(terraform output -json ce_vm_names | jq -r '.eastus01')"
```

`--check` कुछ नहीं लिखता, इसलिए यह लाइव डेमो के विरुद्ध सुरक्षित है।
