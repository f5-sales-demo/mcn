यह डिप्लॉयमेंट **Azure में सक्रिय/सक्रिय Customer Edge उच्च उपलब्धता** को प्रदर्शित करता है,
CEs के आगे किसी Azure लोड बैलेंसर के बिना। तीनों CE eBGP द्वारा एक ही होस्ट रूट
ओरिजिनेट करते हैं, और Azure Route Server तीनों को VNet में समान-लागत नेक्स्ट हॉप के रूप में
इंस्टॉल करता है। इसलिए ट्रैफ़िक वितरण और विफल-नोड हटाना लोड बैलेंसर के बजाय
रूटिंग फ़ैब्रिक में होना अपेक्षित है।

नीचे दिखाया गया सब कुछ लाइव डिप्लॉयमेंट पर चलाया गया था, और आउटपुट वही है जो इसने
उत्पन्न किया। दो चीज़ें जो यह वाक्य *कवर नहीं करता* — फ़ेलओवर और ट्रैफ़िक वितरण —
उन्हें मान लेने के लिए छोड़ने के बजाय अंत में स्पष्ट रूप से बताया गया है।

## क्या डिप्लॉय किया गया है

```text
                  Azure Route Server  ce-ha-lab-rrs  ASN 65515
                          10.0.4.4  and  10.0.4.5
                                      |
              +-----------------------+-----------------------+
              |                       |                       |
        eastus01-bgp            eastus02-bgp            eastus03-bgp     eBGP
              |                       |                       |      CE ASN 64512
        10.0.1.4                10.0.1.5                10.0.1.6     <- CE eth0 / SLO
     f5-xc-ce-vm-01          f5-xc-ce-vm-02          f5-xc-ce-vm-03
    ar-bgp-eastus01         ar-bgp-eastus02         ar-bgp-eastus03
              |                       |                       |
              +----- each advertises 10.250.0.10/32 -----------+
                          three-way ECMP into the VNet
```

| घटक | यथा-निर्मित |
| --- | --- |
| Customer Edges | 3 सिंगल-नोड Secure Mesh v2 साइटें — `ar-bgp-eastus01`, `ar-bgp-eastus02`, `ar-bgp-eastus03` |
| CE सॉफ़्टवेयर | पिन किया गया `9.2024.6`, बिल्ड `crt-20250613-3382` |
| Azure VMs | `f5-xc-ce-vm-01/02/03`, प्रत्येक में तीन NIC (management/SLO, external, internal/SLI) |
| रूट एक्सचेंज | Azure Route Server `ce-ha-lab-rrs`, ASN `65515`, इंस्टेंस `10.0.4.4` और `10.0.4.5` |
| पीयरिंग | प्रति CE एक — `eastus01-bgp`, `eastus02-bgp`, `eastus03-bgp` — CE ASN `64512` |
| विज्ञापित VIP | `10.250.0.10/32`, तीनों CEs द्वारा समान रूप से ओरिजिनेट किया गया |
| लोड बैलेंसर | `ar-bgp-ecmp-lb`, डोमेन `ar-bgp-ecmp.bankexample.com` की सेवा करता है |
| टेस्ट क्लाइंट | `ar-ecmp-client`, उसी VNet के अंदर एक VM |
| रिसोर्स ग्रुप | `rg-mcn-ce-ha-rmordasiewicz` |

<Aside type="caution" title="VIP प्रत्येक VNet CIDR के बाहर होना चाहिए">
`terraform/main.tf` में एक `check` ब्लॉक है जो यह प्रमाणित करता है कि VIP हब और स्पोक
दोनों CIDRs के बाहर है, और अन्यथा प्लान को अस्वीकार कर देता है। इसका बताया गया कारण यह है कि
VNet CIDR के अंदर का VIP, BGP रूट अधिक विशिष्ट होने के बावजूद, VNet के अपने सिस्टम रूट से हार जाता है।

इस गार्ड को अनुबंध की तरह मानें: यदि आप इस डेमो को भिन्न एड्रेसिंग पर पुनः निर्देशित करते हैं, तो
VIP को भी उसके साथ VNet रेंज से बाहर जाना होगा।
</Aside>

## प्रस्तुति से पहले इसे स्वस्थ सिद्ध करें

चार जाँचें, इसी क्रम में। प्रत्येक यह सीमित करती है कि दोष कहाँ होगा, इसलिए एक विफलता आपको
कुछ बताती है, न कि केवल यह कि कुछ गलत है।

<Steps>

1. **तीनों साइटें `ONLINE` हैं।** यदि यह सत्य नहीं है तो डाउनस्ट्रीम कुछ भी सत्य नहीं हो सकता।

   ```bash
   for s in ar-bgp-eastus01 ar-bgp-eastus02 ar-bgp-eastus03; do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **प्रत्येक पीयरिंग उस CE का VIP विज्ञापन सीख रही है।** प्रत्येक पीयरिंग को
   अलग-अलग क्वेरी करें — नीचे दिया गया जाल देखें, क्योंकि यहीं डेमो सबसे अधिक बार
   टूटा हुआ दिखता है जबकि वह नहीं है।

   ```bash
   for p in eastus01-bgp eastus02-bgp eastus03-bgp; do
     echo "--- $p"
     az network routeserver peering list-learned-routes \
       --name "$p" --routeserver ce-ha-lab-rrs -g rg-mcn-ce-ha-rmordasiewicz \
       --query "RouteServiceRole_IN_0[].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp

   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp

   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   तीन पीयरिंग, तीन भिन्न नेक्स्ट हॉप, एक प्रीफ़िक्स। यह ECMP का विज्ञापन पक्ष
   सिद्ध हो गया।

3. **क्लाइंट के प्रभावी रूट तीनों नेक्स्ट हॉप रखते हैं।** यह स्वयं ECMP है,
   जैसा VNet ने इसे प्रोग्राम किया है — CEs जो दावा करते हैं वह नहीं, बल्कि Azure ने उसके साथ जो किया।

   ```bash
   az network nic show-effective-route-table \
     --name ar-ecmp-clientVMNic -g rg-mcn-ce-ha-rmordasiewicz \
     --query "value[?addressPrefix[0]=='10.250.0.10/32']" -o json
   ```

   ```json
   [
     {
       "addressPrefix": ["10.250.0.10/32"],
       "nextHopIpAddress": ["10.0.1.5", "10.0.1.4", "10.0.1.6"],
       "nextHopType": "VirtualNetworkGateway",
       "source": "VirtualNetworkGateway",
       "state": "Active"
     }
   ]
   ```

   `nextHopIpAddress` में तीन एंट्री के साथ `state: Active` ही जाँच है। जहाँ आप तीन की अपेक्षा
   करते हैं वहाँ एक नेक्स्ट हॉप का अर्थ है कि एक CE ने विज्ञापन बंद कर दिया है, और चरण 2 बताता है कौन सा।

4. **VIP ट्रैफ़िक सर्व करता है।** क्लाइंट VM से, और **`Host` हेडर के साथ** — नीचे
   दूसरा जाल देखें।

   ```bash
   az vm run-command invoke -g rg-mcn-ce-ha-rmordasiewicz -n ar-ecmp-client \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts 'for i in $(seq 1 10); do
                  curl -s -o /dev/null -w "%{http_code} " \
                    -H "Host: ar-bgp-ecmp.bankexample.com" http://10.250.0.10/
                done'
   ```

   ```text
   200 200 200 200 200 200 200 200 200 200
   ```

</Steps>

## जाल: एक पीयरिंग एक रूट दिखाती है, और यह सही है

`list-learned-routes` उस पीयरिंग तक सीमित है जिसका नाम आप देते हैं। यह रिपोर्ट करता है कि **उस**
पीयर ने क्या विज्ञापित किया, न कि Route Server की पूरी तालिका।

तो केवल `eastus01-bgp` की क्वेरी करने पर `10.0.1.4` के माध्यम से एक ही `10.250.0.10/32` लौटता है, और
इसे "केवल एक CE विज्ञापन कर रहा है — अन्य दो डाउन हैं" पढ़ने का प्रलोभन होता है। कुछ भी
डाउन नहीं है। अन्य दो विज्ञापन उनकी अपनी पीयरिंग पर दिखते हैं, जिन पर ऊपर का
चरण 2 लूप करता है।

एक ही पीयरिंग क्वेरी से ECMP की पुष्टि करना संभव नहीं है। या तो तीनों
पीयरिंग पर लूप करें, या क्लाइंट की प्रभावी रूट तालिका पढ़ें, जो एक ही कॉल में मर्ज किया गया परिणाम
दिखाती है।

## जाल: केवल-IP अनुरोध 404 लौटाता है

लोड बैलेंसर `Host` पर मैच करता है। VIP कोई वर्चुअल सर्वर नहीं है जो एड्रेस से कनेक्ट करने वाले
किसी को भी कुछ सर्व करे।

```text
curl -H 'Host: ar-bgp-ecmp.bankexample.com' http://10.250.0.10/   ->  200   (10 of 10)
curl                                        http://10.250.0.10/   ->  404
```

इन दोनों को स्वस्थ डिप्लॉयमेंट पर एक ही रन में उत्पन्न किया गया था। **केवल-IP
404 यह प्रमाण है कि पथ काम करता है** — अनुरोध CE तक पहुँचा, CE के प्रॉक्सी ने उत्तर दिया, और
उसने अस्वीकार किया क्योंकि कोई कॉन्फ़िगर किया गया डोमेन मैच नहीं हुआ। इसे आउटेज पढ़ना आपको
BGP देखने भेजता है, जहाँ आपको कुछ भी गलत नहीं मिलेगा।

डेमो के दौरान भी यही लागू होता है: यदि आप डोमेन को उस पर रिज़ॉल्व करने के बजाय ब्राउज़र में
एड्रेस टाइप करते हैं, तो आपको 404 मिलेगा।

## रजिस्ट्रेशन अनुमोदन स्वचालित है, और अप्लाई अभी भी दो-चरणीय है

रजिस्ट्रेशन अनुमोदन के लिए अब कंसोल में किसी व्यक्ति की आवश्यकता नहीं है। प्रोवाइडर **v3.81.1** पर
`xcsh_registration_approval` संसाधन इसे करता है, और साइट मॉड्यूल यह हल करता है कि कौन सा
रजिस्ट्रेशन अनुमोदित करना है।

इससे भी डिप्लॉयमेंट एक ही हैंड्स-ऑफ़ `apply` नहीं बन जाता, और यह कारण
पहला रन देखने और उसे विफल मान लेने से पहले समझने योग्य है:

- एक CE का रजिस्ट्रेशन ऑब्जेक्ट **`r-<uuid>`** नाम का होता है। इसका नाम कभी साइट के नाम पर नहीं होता, इसलिए
  प्लान समय पर कोई भी नाम की भविष्यवाणी नहीं कर सकता।
- रजिस्ट्रेशन केवल VM बूट होने और `vpm` द्वारा रजिस्टर करने के बाद अस्तित्व में आता है।
- इसलिए **पहला अप्लाई किसी भी अनुमोदन की योजना नहीं बनाता**। CEs रजिस्टर हो जाने और
  अनुमोदन बन जाने के बाद एक बार पुनः अप्लाई करें।

`terraform/main.tf` इस क्रम को फ़ाइल के शीर्ष पर दस्तावेज़ित करता है, जो
आधिकारिक संस्करण है — डिप्लॉय अनुक्रम उसी कोड के साथ रहता है जो उसे लागू करता है।

<Aside type="caution" title="एक बिल्कुल नई साइट ऑपरेट API पर तुरंत पहुँच योग्य नहीं होती">
एक नई साइट के `ONLINE` रिपोर्ट करने के बाद लगभग 25 से 30 मिनट तक, `vpm/debug` एंडपॉइंट
`The requested URL was rejected` पढ़ने वाले BIG-IP `503` पेज के साथ उत्तर देते हैं। यह वेब एप्लिकेशन
फ़ायरवॉल ब्लॉक या रद्द किए गए टोकन जैसा लगता है और दोनों में से कुछ नहीं है। प्रतीक्षा करें, फिर पुनः प्रयास करें।

यह नए बनाए गए डेमो को प्रभावित करता है, चल रहे डेमो को नहीं।
</Aside>

## दो और मापन जाल

इन दोनों ने इस परिवेश में आत्मविश्वास से गलत उत्तर उत्पन्न किए, और दोनों में से कोई भी
स्पष्ट नहीं है।

- **VNet के अंदर से जाँच करें, अपने वर्कस्टेशन से नहीं।** Netskope सामान्य पोर्ट पर स्वयं TCP
  हैंडशेक पूरा करता है, इसलिए वर्कस्टेशन जाँच एक ऐसे पोर्ट को **खुला** बताती है जो
  वास्तव में बंद है। वर्कस्टेशन से CE सार्वजनिक एड्रेस पर पोर्ट 80 और 443 खुले पढ़े जाते हैं
  और VNet के अंदर से जाँचने पर बंद होते हैं। `ar-ecmp-client` का उपयोग करें।
- **CE पर पोर्ट 22 केवल आंतरिक (SLI) एड्रेस पर उत्तर देता है।**
  `ar-ecmp-client` से तीनों CEs के विरुद्ध जाँच करने पर, `10.0.3.5`, `10.0.3.6` और `10.0.3.7` सभी
  `SSH-2.0-OpenSSH_8.7` लौटाते हैं, जबकि management और external एड्रेस टाइम आउट हो जाते हैं — जैसा कि
  नियंत्रण के रूप में प्रयुक्त एक अप्रयुक्त एड्रेस भी। इसलिए जिस एड्रेस से आप नोड को जानते हैं, उसकी जाँच करना
  नोड की SSH स्थिति के बारे में आपको कुछ नहीं बताता।

<Aside type="note" title="यह पृष्ठ क्या दावा नहीं करता">
दो चीज़ें जिनकी पाठक यहाँ उचित रूप से अपेक्षा कर सकता है, जानबूझकर अनुपस्थित हैं, क्योंकि उन्हें
डिप्लॉयमेंट के विरुद्ध परखा नहीं गया था:

- **फ़ेलओवर का परीक्षण नहीं किया गया।** तीन समान-लागत नेक्स्ट हॉप इंस्टॉल होने के रूप में सत्यापित हैं; एक CE
  रोके जाने पर रूट तालिका का क्या होता है वह नहीं दिखाया गया है, इसलिए इस पृष्ठ से फ़ेलओवर डेमो का
  पहले प्रयास किए बिना अभ्यास न करें।
- **ट्रैफ़िक वितरण मापा नहीं गया।** VIP पर दस में से दस अनुरोधों ने `200` लौटाया,
  जो सिद्ध करता है कि पथ काम करता है। यह नहीं दिखाता कि वे दस तीनों नेक्स्ट हॉप में कैसे फैले थे।

</Aside>
