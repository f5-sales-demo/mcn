यह परिनियोजन **Azure में सक्रिय/सक्रिय Customer Edge उच्च उपलब्धता** को प्रदर्शित करता है
जिसमें CEs के आगे कोई Azure लोड बैलेंसर नहीं है। तीन CE प्रत्येक eBGP द्वारा एक ही होस्ट
रूट को मूल रूप से प्रचारित करते हैं, और Azure Route Server तीनों को VNet में समान-लागत वाले नेक्स्ट हॉप के रूप में स्थापित करता है।
इसलिए ट्रैफ़िक वितरण और विफल नोड को हटाने का कार्य लोड बैलेंसर के बजाय राउटिंग फ़ैब्रिक में होना अपेक्षित है।

नीचे दिखाया गया सब कुछ लाइव परिनियोजन के विरुद्ध चलाया गया था, और आउटपुट वही आउटपुट है जो उसने
उत्पन्न किया। दो चीज़ें जिन्हें वह वाक्य *कवर नहीं करता* — फ़ेलओवर और ट्रैफ़िक वितरण —
उन्हें मान लेने के बजाय अंत में स्पष्ट रूप से बताया गया है।

## क्या तैनात किया गया है

```text
                  Azure Route Server  ce-ha-lab-rrs  ASN 65515
                          10.0.4.4  and  10.0.4.5
                                      |
              +-----------------------+-----------------------+
              |                       |                       |
        eastus01-bgp            eastus02-bgp            eastus03-bgp     eBGP
              |                       |                       |      CE ASN 64512
        10.0.1.4                10.0.1.5                10.0.1.6     <- CE eth0 / SLO
     f5-xc-ce-vm-01          f5-xc-ce-vm-02          f5-xc-ce-vm-03
    ar-bgp-eastus01         ar-bgp-eastus02         ar-bgp-eastus03
              |                       |                       |
              +----- each advertises 10.250.0.10/32 -----------+
                          three-way ECMP into the VNet
```

| घटक | यथानिर्मित |
| --- | --- |
| Customer Edges | 3 सिंगल-नोड Secure Mesh v2 साइटें — `ar-bgp-eastus01`, `ar-bgp-eastus02`, `ar-bgp-eastus03` |
| CE सॉफ़्टवेयर | पिन किया गया `9.2024.6`, बिल्ड `crt-20250613-3382` |
| Azure VMs | `f5-xc-ce-vm-01/02/03`, प्रत्येक में तीन NIC (management/SLO, external, internal/SLI) |
| रूट एक्सचेंज | Azure Route Server `ce-ha-lab-rrs`, ASN `65515`, इंस्टेंस `10.0.4.4` और `10.0.4.5` |
| पीयरिंग | प्रति CE एक — `eastus01-bgp`, `eastus02-bgp`, `eastus03-bgp` — CE ASN `64512` |
| प्रचारित VIP | `10.250.0.10/32`, तीनों CEs द्वारा समान रूप से मूल रूप से प्रचारित |
| लोड बैलेंसर | `ar-bgp-ecmp-lb`, डोमेन `ar-bgp-ecmp.bankexample.com` की सेवा करते हुए |
| परीक्षण क्लाइंट | `ar-ecmp-client`, उसी VNet के भीतर एक VM |
| रिसोर्स ग्रुप | `rg-mcn-ce-ha-rmordasiewicz` |

<Aside type="caution" title="VIP को हर VNet CIDR के बाहर होना चाहिए">
`terraform/main.tf` में एक `check` ब्लॉक है जो यह प्रमाणित करता है कि VIP हब और स्पोक दोनों
CIDRs के बाहर है, अन्यथा प्लान को अस्वीकार कर देता है। इसका बताया गया कारण यह है कि VNet CIDR के भीतर का VIP
BGP रूट अधिक विशिष्ट होने के बावजूद VNet के अपने सिस्टम रूट से हार जाता है।

इस गार्ड को अनुबंध की तरह मानें: यदि आप इस डेमो को भिन्न एड्रेसिंग पर पुनः निर्देशित करते हैं, तो
VIP को भी उसके साथ VNet रेंज से बाहर जाना होगा।
</Aside>

## प्रस्तुत करने से पहले सिद्ध करें कि यह स्वस्थ है

चार जाँचें, इसी क्रम में। प्रत्येक यह सीमित करती है कि दोष कहाँ हो सकता है, इसलिए एक विफलता आपको
कुछ बताती है, न कि केवल यह कि कुछ गलत है।

<Steps>

1. **तीनों साइटें `ONLINE` हैं।** यदि यह सत्य नहीं है तो आगे कुछ भी सत्य नहीं हो सकता।

   ```bash
   for s in ar-bgp-eastus01 ar-bgp-eastus02 ar-bgp-eastus03; do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **प्रत्येक पीयरिंग उस CE का VIP विज्ञापन सीख रही है।** प्रत्येक पीयरिंग को
   अलग-अलग क्वेरी करें — नीचे दिया गया जाल देखें, क्योंकि यहीं पर डेमो सबसे अधिक बार
   टूटा हुआ दिखता है जबकि होता नहीं है।

   ```bash
   for p in eastus01-bgp eastus02-bgp eastus03-bgp; do
     echo "--- $p"
     az network routeserver peering list-learned-routes \
       --name "$p" --routeserver ce-ha-lab-rrs -g rg-mcn-ce-ha-rmordasiewicz \
       --query "RouteServiceRole_IN_0[].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp

   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp

   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   तीन पीयरिंग, तीन भिन्न नेक्स्ट हॉप, एक प्रीफ़िक्स। यह ECMP का विज्ञापन पक्ष
   सिद्ध हो गया।

3. **क्लाइंट के प्रभावी रूट तीनों नेक्स्ट हॉप ले जाते हैं।** यह स्वयं ECMP है,
   जैसा VNet ने इसे प्रोग्राम किया है — CEs जो दावा करते हैं वह नहीं, बल्कि Azure ने उसके साथ जो किया।

   ```bash
   az network nic show-effective-route-table \
     --name ar-ecmp-clientVMNic -g rg-mcn-ce-ha-rmordasiewicz \
     --query "value[?addressPrefix[0]=='10.250.0.10/32']" -o json
   ```

   ```json
   [
     {
       "addressPrefix": ["10.250.0.10/32"],
       "nextHopIpAddress": ["10.0.1.5", "10.0.1.4", "10.0.1.6"],
       "nextHopType": "VirtualNetworkGateway",
       "source": "VirtualNetworkGateway",
       "state": "Active"
     }
   ]
   ```

   `nextHopIpAddress` में तीन प्रविष्टियों के साथ `state: Active` ही जाँच है। जहाँ आप तीन की अपेक्षा करते हैं
   वहाँ एक नेक्स्ट हॉप का अर्थ है कि किसी CE ने विज्ञापन करना बंद कर दिया है, और चरण 2 यह पहचानता है कि कौन सा।

4. **VIP ट्रैफ़िक की सेवा करता है।** क्लाइंट VM से, और **`Host` हेडर के साथ** — नीचे
   दूसरा जाल देखें।

   ```bash
   az vm run-command invoke -g rg-mcn-ce-ha-rmordasiewicz -n ar-ecmp-client \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts 'for i in $(seq 1 10); do
                  curl -s -o /dev/null -w "%{http_code} " \
                    -H "Host: ar-bgp-ecmp.bankexample.com" http://10.250.0.10/
                done'
   ```

   ```text
   200 200 200 200 200 200 200 200 200 200
   ```

</Steps>

## जाल: एक पीयरिंग एक रूट दिखाती है, और यह सही है

`list-learned-routes` उस पीयरिंग तक सीमित है जिसका नाम आप देते हैं। यह रिपोर्ट करता है कि **उस** पीयर ने
क्या प्रचारित किया, न कि Route Server की पूरी तालिका।

इसलिए अकेले `eastus01-bgp` की क्वेरी करने पर `10.0.1.4` के माध्यम से एकल `10.250.0.10/32` लौटता है, और
इसे "केवल एक CE विज्ञापन कर रहा है — अन्य दो डाउन हैं" के रूप में पढ़ने का प्रलोभन होता है। कुछ भी
डाउन नहीं है। अन्य दो विज्ञापन उनकी अपनी पीयरिंग पर दिखाई देते हैं, और ऊपर का चरण 2 यही लूप करता है।

एकल पीयरिंग क्वेरी से ECMP की पुष्टि करना संभव नहीं है। या तो तीनों पीयरिंग को लूप करें, या
क्लाइंट की प्रभावी रूट तालिका पढ़ें, जो एक ही कॉल में विलय किया गया परिणाम दिखाती है।

## जाल: केवल-IP अनुरोध 404 लौटाता है

लोड बैलेंसर `Host` पर मैच करता है। VIP कोई ऐसा वर्चुअल सर्वर नहीं है जो पते से जुड़ने वाले
किसी भी व्यक्ति को कुछ भी परोसे।

```text
curl -H 'Host: ar-bgp-ecmp.bankexample.com' http://10.250.0.10/   ->  200   (10 of 10)
curl                                        http://10.250.0.10/   ->  404
```

ये दोनों स्वस्थ परिनियोजन के विरुद्ध एक ही रन में उत्पन्न हुए थे। **केवल-IP
404 इस बात का प्रमाण है कि पथ काम कर रहा है** — अनुरोध CE तक पहुँचा, CE के प्रॉक्सी ने उत्तर दिया, और
उसने अस्वीकार कर दिया क्योंकि कोई कॉन्फ़िगर किया गया डोमेन मेल नहीं खाया। इसे आउटेज के रूप में पढ़ना आपको
BGP की ओर देखने भेजता है, जहाँ आपको कुछ गलत नहीं मिलेगा।

यही बात डेमो के दौरान लागू होती है: यदि आप डोमेन को हल करने के बजाय ब्राउज़र में पता टाइप करते हैं,
तो आपको 404 मिलेगा।

## पंजीकरण अनुमोदन स्वचालित है, और apply अब भी दो-चरणीय है

पंजीकरण अनुमोदन के लिए अब कंसोल में किसी मनुष्य की आवश्यकता नहीं है। प्रोवाइडर **v3.81.1** पर
`xcsh_registration_approval` संसाधन इसे निष्पादित करता है, और साइट मॉड्यूल यह हल करता है कि किस
पंजीकरण को अनुमोदित करना है।

फिर भी यह परिनियोजन को एकल हस्तक्षेप-रहित `apply` नहीं बनाता, और पहली रन देखकर यह निष्कर्ष निकालने से पहले कि
यह विफल हो गई, कारण समझना उपयोगी है:

- किसी CE का पंजीकरण ऑब्जेक्ट **`r-<uuid>`** नाम का होता है। इसका नाम कभी साइट के अनुसार नहीं होता, इसलिए
  प्लान समय पर कोई भी नाम की भविष्यवाणी नहीं कर सकता।
- पंजीकरण तभी अस्तित्व में आता है जब VM बूट हो चुका हो और `vpm` ने पंजीकरण कर लिया हो।
- इसलिए **पहला apply किसी भी अनुमोदन की योजना नहीं बनाता**। एक बार CEs पंजीकृत हो जाएँ और
  अनुमोदन बन जाएँ, तो पुनः apply करें।

`terraform/main.tf` इस क्रम को फ़ाइल के शीर्ष पर प्रलेखित करता है, जो आधिकारिक संस्करण है —
परिनियोजन अनुक्रम उसी कोड के साथ रहता है जो इसे लागू करता है।

<Aside type="caution" title="एक बिल्कुल नई साइट ऑपरेट API पर तुरंत पहुँच योग्य नहीं होती">
किसी नई साइट के `ONLINE` रिपोर्ट करने के बाद लगभग 25 से 30 मिनट तक, `vpm/debug` एंडपॉइंट
`The requested URL was rejected` पढ़ने वाले BIG-IP `503` पेज के साथ उत्तर देते हैं। यह किसी
वेब एप्लिकेशन फ़ायरवॉल ब्लॉक या रद्द किए गए टोकन जैसा दिखता है और दोनों में से कुछ भी नहीं है। प्रतीक्षा करें, फिर पुनः प्रयास करें।

यह नए बनाए गए डेमो को प्रभावित करता है, चल रहे डेमो को नहीं।
</Aside>

## Site CLI तक पहुँचना

नियमित ऑन-बॉक्स डायग्नोस्टिक्स डिबग API के माध्यम से जाते हैं, जो यहाँ पहले से स्क्रिप्ट किया गया है।
पुष्टि करें कि कमांड सरफ़ेस अब भी वही है जो दस्तावेज़ीकरण बताता है:

```bash
bash scripts/capture-sitecli.sh --check --site ar-bgp-eastus01 --node f5-xc-ce-vm-01
```

```text
catalog matches the live CE (build crt-20250613-3382, 34 commands)
```

`--check` कुछ नहीं लिखता, इसलिए यह लाइव डेमो के विरुद्ध सुरक्षित है।

जिन कमांड को वह API रिले नहीं करता, उनके लिए इस परिनियोजन में **अप्लायंस `admin` अकाउंट तक
ऑपरेटर SSH** भी है, जिसका लॉगिन शेल Site CLI है। यह तीनों CEs पर सत्यापित है।
VNet के भीतर के किसी होस्ट से आंतरिक (SLI) पते से कनेक्ट करें, टर्मिनल आवंटित करते हुए:

```bash
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<vm-in-vnet> admin@10.0.3.5
```

```text
WELCOME IN SITE CLI
Registration Status: PROVISIONED
```

<Aside type="caution" title="वह पहुँच इसलिए मौजूद है क्योंकि ये CEs उसी के साथ बनाए गए थे — इसे बाद में नहीं जोड़ा जा सकता">
ऑपरेटर कुंजी cloud-init `write_files` द्वारा लिखी जाती है, जो पहले बूट पर एक बार चलती है।
`custom_data` केवल-प्रतिस्थापन है, इसलिए पहले से चल रहे CEs पर इसे अपनाने से हर CE VM बदल जाती है —
और एक को बदलने से वर्तमान में पंजीकरण अटक जाता है जबकि `terraform plan`
"No changes" रिपोर्ट करता है ([issue 674](https://github.com/f5-sales-demo/mcn/issues/674))।
रिकवरी में दो पूर्ण पुनर्निर्माण लगे।

इस परिनियोजन के लिए परिवर्तन पहले ही लागू है और फ़्लीट स्वस्थ है। जो कोई इसे कहीं और
अपनाए, उसे पहले
[SSH पेज](../customer-edge/access/ssh/) पढ़ना चाहिए।
</Aside>

## दो और मापन जाल

इन दोनों ने इस परिवेश में आत्मविश्वास से गलत उत्तर दिए, और इनमें से कोई भी
स्पष्ट नहीं है।

- **अपने वर्कस्टेशन से नहीं, VNet के भीतर से जाँच करें।** Netskope सामान्य पोर्ट पर स्वयं TCP
  हैंडशेक पूरा कर देता है, इसलिए वर्कस्टेशन प्रोब एक पोर्ट को **खुला** रिपोर्ट करता है जो
  वास्तव में बंद है। वर्कस्टेशन से CE सार्वजनिक पतों पर पोर्ट 80 और 443 खुले दिखते हैं और
  VNet के भीतर से जाँचने पर बंद होते हैं। `ar-ecmp-client` का उपयोग करें।
- **किसी CE पर पोर्ट 22 केवल आंतरिक (SLI) पते पर उत्तर देता है।**
  `ar-ecmp-client` से तीनों CEs के विरुद्ध जाँच करने पर, `10.0.3.5`, `10.0.3.6` और `10.0.3.7` सभी
  `SSH-2.0-OpenSSH_8.7` लौटाते हैं, जबकि management और external पते टाइम आउट हो जाते हैं — जैसा कि
  नियंत्रण के रूप में उपयोग किया गया एक अप्रयुक्त पता भी करता है। eth0 का नाम बदलकर `a-i-eth0` कर दिया गया है और उसमें कोई होस्ट IP नहीं है,
  क्योंकि डेटापाथ उसका स्वामी है। इसलिए जिस पते से आप नोड को जानते हैं उसे जाँचना आपको
  नोड की SSH स्थिति के बारे में कुछ नहीं बताता, और SLI पता ही वह है जिससे कनेक्ट करना है।

<Aside type="note" title="यह पेज क्या दावा नहीं करता">
दो चीज़ें जिनकी कोई पाठक यहाँ उचित रूप से अपेक्षा कर सकता है, जानबूझकर अनुपस्थित हैं, क्योंकि उन्हें
परिनियोजन के विरुद्ध परखा नहीं गया था:

- **फ़ेलओवर का परीक्षण नहीं किया गया।** तीन समान-लागत नेक्स्ट हॉप स्थापित होने के रूप में सत्यापित हैं; जब कोई CE
  रोका जाता है तो रूट तालिका का क्या होता है, यह नहीं दिखाया गया है, इसलिए बिना पहले आज़माए इस पेज से
  फ़ेलओवर डेमो का पूर्वाभ्यास न करें।
- **ट्रैफ़िक वितरण को मापा नहीं गया।** VIP को भेजे गए दस में से दस अनुरोधों ने `200` लौटाया,
  जो सिद्ध करता है कि पथ काम करता है। यह नहीं दिखाता कि वे दस तीनों नेक्स्ट हॉप में कैसे वितरित हुए।

</Aside>
