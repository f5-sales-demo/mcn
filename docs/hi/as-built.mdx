यह तैनाती **Azure में सक्रिय/सक्रिय Customer Edge उच्च उपलब्धता** को प्रदर्शित करती है,
जिसमें CEs के आगे कोई Azure लोड बैलेंसर नहीं है। तीनों CE eBGP द्वारा वही होस्ट
रूट ओरिजिनेट करते हैं, और Azure Route Server तीनों को VNet में समान-लागत अगले हॉप के रूप में
स्थापित करता है। इसलिए ट्रैफ़िक वितरण और विफल नोड को हटाना, लोड बैलेंसर के बजाय, रूटिंग
फ़ैब्रिक में होना अपेक्षित है।

नीचे दिखाया गया सब कुछ लाइव तैनाती के विरुद्ध चलाया गया था, और आउटपुट वही आउटपुट है जो उसने
उत्पन्न किया। वह वाक्य जिसे *नहीं* समेटता — फ़ेलओवर, ट्रैफ़िक तीनों अगले हॉप में कैसे बँटता है,
और नए बिल्ड पर VIP क्यों संक्षिप्त रूप से हानिपूर्ण रहता है — उसे मान लिए जाने के बजाय स्पष्ट रूप से
इंगित किया गया है।

## क्या तैनात किया गया है

```text
                  Azure Route Server  ce-ha-lab-rrs  ASN 65515
                          10.0.4.4  and  10.0.4.5
                                      |
              +-----------------------+-----------------------+
              |                       |                       |
        eastus01-bgp            eastus02-bgp            eastus03-bgp     eBGP
              |                       |                       |      CE ASN 64512
        10.0.1.4                10.0.1.5                10.0.1.6     <- CE eth0 / SLO
     f5-xc-ce-vm-01          f5-xc-ce-vm-02          f5-xc-ce-vm-03
    ar-bgp-eastus01         ar-bgp-eastus02         ar-bgp-eastus03
              |                       |                       |
              +----- each advertises 10.250.0.10/32 -----------+
                          three-way ECMP into the VNet
```

<Aside type="caution" title="VIP को हर VNet CIDR के बाहर होना चाहिए">
`terraform/main.tf` में एक `check` ब्लॉक है जो यह प्रमाणित करता है कि VIP हब और स्पोक दोनों
CIDR के बाहर है, और अन्यथा प्लान को अस्वीकार कर देता है। इसका बताया गया कारण यह है कि VNet CIDR
के भीतर स्थित VIP, BGP रूट अधिक विशिष्ट होने के बावजूद, VNet के अपने सिस्टम रूट से हार जाता है।

इस गार्ड को अनुबंध की तरह मानें: यदि आप इस डेमो को भिन्न एड्रेसिंग पर पुनः निर्देशित करते हैं, तो
VIP को भी उसके साथ VNet रेंज से बाहर जाना होगा।
</Aside>

## टेनेंट कॉन्फ़िगरेशन है, वह नहीं जो आपका शेल एक्सपोर्ट कर रहा है

`var.expected_xc_tenant` टेनेंट का नाम देता है, डिफ़ॉल्ट रूप से `f5-sales-demo` है, और यही एकमात्र
स्थान है जहाँ इसका नाम दिया गया है। `providers.tf` इससे `xcsh` प्रोवाइडर का `api_url` व्युत्पन्न
करता है, जो जानबूझकर परिवेश में मौजूद किसी भी `XCSH_API_URL` को अधिरोहित करता है, और
`terraform/main.tf` में एक `postcondition` **प्लान** को विफल कर देता है जब परिवेश किसी भिन्न टेनेंट
का नाम देता है।

स्थिति बदलने वाला कुछ भी चलाए बिना दोनों भाग पढ़ें:

```bash
cd terraform
terraform output -raw xc_tenant       # what the deployment targets
terraform output -raw xc_env_tenant   # what your shell claims — diagnostic only
```

```text
f5-sales-demo
f5-sales-demo
```

CE VMs वहाँ पुनः पंजीकृत हो गए, और उनके `f5-sales-demo` पंजीकरण त्याग दिए गए। इस बीच का प्रत्येक
प्लान स्वच्छ था, क्योंकि कॉन्फ़िगरेशन में किसी भी चीज़ की टेनेंट के बारे में कोई राय नहीं थी
([issue 696](https://github.com/f5-sales-demo/mcn/issues/696), जिसे
[PR 697](https://github.com/f5-sales-demo/mcn/pull/697) में ठीक किया गया)। इसे पुनर्प्राप्त करने का
अर्थ था गलत टेनेंट में स्टैक को नष्ट करना और सही टेनेंट में उसे पुनर्निर्मित करना।

पहचानने योग्य लक्षण, क्योंकि यह स्वयं-वर्णनात्मक नहीं है: किसी अन्य टेनेंट के लिए बनाया गया टोकन
पिन किए गए एंडपॉइंट पर एक सादे `401` के साथ विफल होता है, जो ठीक एक समाप्त क्रेडेंशियल जैसा
पढ़ा जाता है। यदि कोई क्रेडेंशियल जिसे आप सही मानते हैं `401` लौटाता है, तो दूसरा टोकन बनाने से पहले
ऊपर दिए गए दोनों आउटपुट की तुलना करें।
</Aside>

## प्रस्तुति से पहले सिद्ध करें कि यह स्वस्थ है

चार जाँचें, इसी क्रम में। प्रत्येक यह सीमित करती है कि दोष कहाँ हो सकता है, ताकि विफलता आपको
कुछ बताए, केवल यह नहीं कि कुछ गलत है।

<Steps>

1. **तीनों साइटें `ONLINE` हैं।** यदि यह सत्य नहीं है तो डाउनस्ट्रीम कुछ भी सत्य नहीं हो सकता।

   ```bash
   for s in ar-bgp-eastus01 ar-bgp-eastus02 ar-bgp-eastus03; do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **प्रत्येक पीयरिंग उस CE का VIP विज्ञापन सीख रही है।** प्रत्येक पीयरिंग को अलग-अलग
   क्वेरी करें — नीचे दिया गया जाल देखें, क्योंकि यही वह स्थान है जहाँ डेमो सबसे अधिक बार
   टूटा हुआ प्रतीत होता है परन्तु नहीं है।

   ```bash
   for p in eastus01-bgp eastus02-bgp eastus03-bgp; do
     echo "--- $p"
     az network routeserver peering list-learned-routes \
       --name "$p" --routeserver ce-ha-lab-rrs -g rg-mcn-ce-ha-rmordasiewicz \
       --query "RouteServiceRole_IN_0[].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp

   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp

   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   तीन पीयरिंग, तीन भिन्न अगले हॉप, एक प्रीफ़िक्स। यह ECMP का विज्ञापन पक्ष सिद्ध हो गया।

3. **क्लाइंट के प्रभावी रूट तीनों अगले हॉप वहन करते हैं।** यह स्वयं ECMP है,
   जैसा VNet ने इसे प्रोग्राम किया है — वह नहीं जो CEs दावा करते हैं, बल्कि वह जो Azure ने उसके साथ किया।

   ```bash
   az network nic show-effective-route-table \
     --name ar-ecmp-clientVMNic -g rg-mcn-ce-ha-rmordasiewicz \
     --query "value[?addressPrefix[0]=='10.250.0.10/32']" -o json
   ```

   ```json
   [
     {
       "addressPrefix": ["10.250.0.10/32"],
       "nextHopIpAddress": ["10.0.1.5", "10.0.1.4", "10.0.1.6"],
       "nextHopType": "VirtualNetworkGateway",
       "source": "VirtualNetworkGateway",
       "state": "Active"
     }
   ]
   ```

   `nextHopIpAddress` में तीन प्रविष्टियों के साथ `state: Active` ही जाँच है। **उन तीनों का क्रम
   महत्वपूर्ण नहीं है और स्थिर नहीं है** — Azure उन्हें कॉलों के बीच भिन्न क्रम में लौटाता है,
   इसलिए सूची की पिछले रन से तुलना करने के बजाय उन्हें गिनें। जहाँ आप तीन की अपेक्षा करते हैं वहाँ
   एक अगला हॉप का अर्थ है कि किसी CE ने विज्ञापन बंद कर दिया है, और चरण 2 यह पहचानता है
   कि कौन सा।

4. **VIP ट्रैफ़िक की सेवा करता है।** क्लाइंट VM से, और **`Host` हेडर के साथ** — नीचे दूसरा
   जाल देखें। समस्या देखने के लिए पर्याप्त अनुरोध सैंपल करें: कुछ दर्जन अनुरोध, आगे वर्णित
   कन्वर्जेंस विंडो के दौरान भी, 100 % के रूप में पढ़े जाते हैं।

   ```bash
   az vm run-command invoke -g rg-mcn-ce-ha-rmordasiewicz -n ar-ecmp-client \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts 'ok=0; fail=0
                for i in $(seq 1 60); do
                  c=$(curl -s -o /dev/null -m 5 -w "%{http_code}" \
                        -H "Host: ar-bgp-ecmp.bankexample.com" http://10.250.0.10/)
                  [ "$c" = 200 ] && ok=$((ok+1)) || fail=$((fail+1))
                done
                echo "OK=$ok FAIL=$fail"'
   ```

   ```text
   OK=60 FAIL=0
   ```

</Steps>

## जाल: एक पीयरिंग एक रूट दिखाती है, और यह सही है

`list-learned-routes` उस पीयरिंग तक सीमित है जिसका नाम आप देते हैं। यह रिपोर्ट करता है कि **उस**
पीयर ने क्या विज्ञापित किया, Route Server की पूरी तालिका नहीं।

तो अकेले `eastus01-bgp` की क्वेरी `10.0.1.4` के माध्यम से एकल `10.250.0.10/32` लौटाती है, और
इसे "केवल एक CE विज्ञापन कर रहा है — अन्य दो डाउन हैं" के रूप में पढ़ने का प्रलोभन होता है। कुछ भी
डाउन नहीं है। अन्य दो विज्ञापन उनकी अपनी पीयरिंग पर दिखाई देते हैं, जिन पर ऊपर का चरण 2 लूप करता है।

एकल पीयरिंग क्वेरी से ECMP की पुष्टि करना संभव नहीं है। या तो तीनों पीयरिंग पर लूप करें, या
क्लाइंट की प्रभावी रूट तालिका पढ़ें, जो एक ही कॉल में मिला हुआ परिणाम दिखाती है।

## जाल: सादा-IP अनुरोध 404 लौटाता है

लोड बैलेंसर `Host` पर मैच करता है। VIP कोई ऐसा वर्चुअल सर्वर नहीं है जो पते से जुड़ने वाले
किसी को भी कुछ भी परोसे।

```text
curl -H 'Host: ar-bgp-ecmp.bankexample.com' http://10.250.0.10/   ->  200   (10 of 10)
curl                                        http://10.250.0.10/   ->  404
```

इन दोनों को स्वस्थ तैनाती के विरुद्ध एक ही रन में उत्पन्न किया गया था। **सादा-IP 404 इस बात का
प्रमाण है कि पथ काम करता है** — अनुरोध CE तक पहुँचा, CE के प्रॉक्सी ने उत्तर दिया, और उसने अस्वीकार
किया क्योंकि कोई कॉन्फ़िगर किया गया डोमेन मैच नहीं हुआ। इसे आउटेज के रूप में पढ़ने पर आप BGP की
जाँच करने लगेंगे, जहाँ आपको कुछ गलत नहीं मिलेगा।

यही डेमो के दौरान भी लागू होता है: यदि आप डोमेन को इस पते पर रिज़ॉल्व करने के बजाय ब्राउज़र में
पता टाइप करते हैं, तो आपको 404 मिलेगा।

## VIP पहले पौन घंटे तक अनुरोध छोड़ता है, फिर रुक जाता है

नए बनाए गए स्टैक पर, CEs `ONLINE` होने के बाद लगभग पहले 45 मिनट तक VIP अनुरोधों का एक छोटा
अंश खोता है, और उसके बाद स्वच्छ रूप से सेवा देता है। `ar-ecmp-client` से 1,470 अनुरोधों पर मापा गया,
सभी `Host` हेडर के साथ:

| विंडो | अनुरोध | विफलताएँ | दर |
| --- | --- | --- | --- |
| ECMP उठने के बाद पहले ~45 मिनट | 570 | 12 | **2.11 %** |
| उसके बाद के 23 मिनट | 900 | **0** | **0.00 %** |

प्रत्येक विफलता `curl: (28)` थी — शून्य बाइट प्राप्त होने के साथ एक टाइमआउट — कोई HTTP त्रुटि
स्थिति नहीं। अंतिम विफलता ECMP उठने के लगभग 43 मिनट बाद घटी। 900 स्वच्छ अनुरोधों में से,
400 30-सेकंड टाइमआउट के साथ चले और उनमें से प्रत्येक 2 सेकंड से कम में पूरा हुआ, इसलिए किसी छोटे
टाइमआउट द्वारा कुछ भी छिपाया नहीं जा रहा था।

**ऑरिजिन इसका कारण नहीं था।** सीधे ऑरिजिन के लिए एक कंट्रोल बैच
(`http://20.98.232.135/`, VIP को बायपास करते हुए) विफल होते VIP बैचों के *साथ-साथ* 120 में से
120 स्वच्छ चला। दोष VIP, ECMP या CE पथ में कहीं है।

दो बातें जिन्हें जानबूझकर यह नहीं कहा जा रहा है:

- **यह स्थिर-अवस्था दोष नहीं है।** यह पूर्णतः समाप्त हो जाता है और समाप्त ही रहता है। एक घंटे से
  चल रहे डेमो में यह समस्या नहीं है — ऊपर की जाँच पर 60 में से 60, और पुनर्निर्मित स्टैक पर
  यह पुनः स्वच्छ रूप से पुनरुत्पादित हुआ।
- **यह किसी विशेष CE को आरोपित नहीं किया जा सकता।** इस टोपोलॉजी में कुछ भी प्रति-नोड HTTP
  लिसनर नहीं देता, इसलिए किसी छोड़े गए अनुरोध को उस नोड से बाँधने का कोई तरीका नहीं है जिसने
  उसे छोड़ा। CE के बाहरी इंटरफ़ेस (`10.0.2.x`) पर कोई HTTP लिसनर ही नहीं है — केवल VIP `/32`
  उत्तर देता है।

यह एक भिन्न टेनेंट में स्वच्छ पुनर्निर्माण पर पुनरुत्पादित हुआ, इसलिए यह परिवेश के बजाय टोपोलॉजी
का अनुसरण करता है।

<Aside type="caution" title="40 अनुरोध सैंपल कर यह निष्कर्ष न निकालें कि सब ठीक है">
40 से 50 के बैच अधिकांश समय, विफल होने वाली विंडो के भीतर भी, 100 % के रूप में पढ़े जाते हैं। इसी
कारण इसे पहले एक चालू निम्न-दर दोष के रूप में और फिर बिल्कुल भी दोष न होने के रूप में गलत
वर्णित किया गया था। समय में अलग-अलग बैचों में 100 या अधिक सैंपल करें।
</Aside>

## पंजीकरण अनुमोदन स्वचालित है, और apply अब भी दो-चरणीय है

पंजीकरण अनुमोदन के लिए अब कंसोल में किसी व्यक्ति की आवश्यकता नहीं है। प्रोवाइडर **v3.81.1** पर
`xcsh_registration_approval` रिसोर्स इसे करता है, और साइट मॉड्यूल यह हल करता है कि किस
पंजीकरण को अनुमोदित करना है।

इससे भी तैनाती एक ही हैंड्स-ऑफ़ `apply` नहीं बन जाती, और पहला रन देखकर यह निष्कर्ष निकालने से पहले
कि वह विफल हो गया, कारण समझना उपयोगी है:

- किसी CE के पंजीकरण ऑब्जेक्ट का नाम **`r-<uuid>`** होता है। इसका नाम कभी साइट के अनुसार नहीं
  होता, इसलिए कोई भी चीज़ प्लान समय पर नाम की भविष्यवाणी नहीं कर सकती।
- पंजीकरण केवल तब अस्तित्व में आता है जब VM बूट हो गया हो और `vpm` ने पंजीकरण किया हो।
- अतः **पहला apply कोई अनुमोदन प्लान ही नहीं करता**। CEs के पंजीकृत हो जाने और अनुमोदन बन जाने
  के बाद पुनः apply करें।

`terraform/main.tf` फ़ाइल के शीर्ष पर इस क्रम का दस्तावेज़ीकरण करती है, जो प्रामाणिक संस्करण है —
डिप्लॉय क्रम उस कोड के साथ रहता है जो उसे कार्यान्वित करता है।

<Aside type="caution" title="एक बिल्कुल नई साइट operate API के माध्यम से तुरंत पहुँच योग्य नहीं होती">
किसी नई साइट के `ONLINE` रिपोर्ट करने के बाद लगभग 25 से 30 मिनट तक, `vpm/debug` एंडपॉइंट
`The requested URL was rejected` पढ़ने वाले BIG-IP `503` पृष्ठ के साथ उत्तर देते हैं। यह किसी
वेब एप्लिकेशन फ़ायरवॉल ब्लॉक या रद्द किए गए टोकन जैसा दिखता है और इनमें से कुछ भी नहीं है।
प्रतीक्षा करें, फिर पुनः प्रयास करें।

यह नए बनाए गए डेमो को प्रभावित करता है, चल रहे डेमो को नहीं।
</Aside>

## Site CLI तक पहुँचना

नियमित ऑन-बॉक्स डायग्नोस्टिक्स डीबग API के माध्यम से जाते हैं, जो यहाँ पहले से स्क्रिप्टेड है।
पुष्टि करें कि कमांड सरफ़ेस अब भी दस्तावेज़ीकरण द्वारा वर्णित के अनुरूप है:

```bash
bash scripts/capture-sitecli.sh --check --site ar-bgp-eastus01 --node f5-xc-ce-vm-01
```

```text
catalog matches the live CE (build crt-20250613-3382, 34 commands)
```

`--check` कुछ नहीं लिखता, इसलिए यह लाइव डेमो के विरुद्ध सुरक्षित है।

जिन कमांड को वह API रिले नहीं करता, उनके लिए इस तैनाती में **अप्लायंस `admin` खाते तक
ऑपरेटर SSH** भी है, जिसका लॉगिन शेल Site CLI है। इसे तीनों CEs पर सत्यापित किया गया है।
VNet के भीतर के किसी होस्ट से आंतरिक (SLI) पते से जुड़ें, टर्मिनल आवंटित करके।

<Aside type="danger" title="किसी CE आंतरिक पते को कभी हार्डकोड न करें — वे प्रत्येक पुनर्निर्माण पर पुनः असाइन होते हैं">
Azure यह सुरक्षित नहीं रखता कि आंतरिक सबनेट में किस CE को कौन सा पता मिलता है। सबसे हाल के
पुनर्निर्माण के बाद `f5-xc-ce-vm-01`, `-02` और `-03` क्रमशः `10.0.3.7`, `10.0.3.5` और `10.0.3.4`
रखते हैं: न नोड क्रम में, न सतत, और पहले जो उनके पास था उससे भिन्न। टेस्ट क्लाइंट का अपना NIC
उसी सबनेट में है और उसने एक ऐसा पता रखा है जो पहले किसी CE के पास था।

उन्हें याद रखने के बजाय पढ़ें:

```bash
cd terraform
terraform output -json ce_sli_private_ips
```

```json
{"eastus01":"10.0.3.7","eastus02":"10.0.3.5","eastus03":"10.0.3.4"}
```

Terraform स्टेट हाथ में न होने पर, जो चाहिए उसे NIC नाम से Azure से पूछें, जो *स्थिर* है:

```bash
az network nic show -g rg-mcn-ce-ha-rmordasiewicz \
  -n f5-xc-ce-vm-01-internal-nic \
  --query ipConfigurations[0].privateIPAddress -o tsv
```

</Aside>

```bash
SLI=$(terraform output -json ce_sli_private_ips | jq -r '.eastus01')
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<vm-in-vnet> "admin@$SLI"
```

```text
Registration Status: PROVISIONED
SLO IP: 10.0.1.4/26
WELCOME IN SITE CLI
```

<Aside type="caution" title="वह एक्सेस इसलिए मौजूद है क्योंकि ये CEs उसके साथ बनाए गए थे — इसे बाद में जोड़ा नहीं जा सकता">
ऑपरेटर कुंजी cloud-init `write_files` द्वारा लिखी जाती है, जो पहले बूट पर एक बार चलता है।
`custom_data` केवल-प्रतिस्थापन है, इसलिए पहले से चल रहे CEs पर इसे अपनाना **प्रत्येक CE VM को
प्रतिस्थापित करता है**। यह एक फ़्लीट पुनर्निर्माण है, कॉन्फ़िगरेशन परिवर्तन नहीं।

पहले यह उससे भी बुरा था: प्रतिस्थापित CE कभी पुनः पंजीकृत नहीं हो सकता था, क्योंकि नष्ट किए गए
नोड का पंजीकरण अब भी कंट्रोल प्लेन के अनूठे `(tenant, cluster_name, hostname)` इंडेक्स को धारण
करता था — और `terraform plan` पूरे उस समय के लिए "No changes" रिपोर्ट करता था जब फ़्लीट डाउन
थी। पुनर्प्राप्ति में दो पूर्ण पुनर्निर्माण लगे। यह ठीक कर दिया गया है
([issue 674](https://github.com/f5-sales-demo/mcn/issues/674), जिसे
[PR 693](https://github.com/f5-sales-demo/mcn/pull/693) द्वारा बंद किया गया): साइट ऑब्जेक्ट का
लाइफ़साइकिल अब CE VM इंस्टेंस से युग्मित है, इसलिए VM को प्रतिस्थापित करने पर साइट प्रतिस्थापित
होती है, और साइट को हटाने पर प्रतिस्थापन नोड के बूट होने से पहले उसके पंजीकरण भी साथ चले जाते हैं।

इस तैनाती के लिए यह परिवर्तन पहले से लागू है और फ़्लीट स्वस्थ है। इसे अन्यत्र अपनाने वाले किसी भी
व्यक्ति को पहले [SSH पृष्ठ](../customer-edge/access/ssh/) पढ़ना चाहिए।
</Aside>

## दो और मापन जाल

इन दोनों ने इस परिवेश में आत्मविश्वासपूर्ण गलत उत्तर उत्पन्न किए, और इनमें से कोई भी स्पष्ट
नहीं है।

- **VNet के भीतर से जाँचें, अपने वर्कस्टेशन से नहीं।** Netskope सामान्य पोर्ट पर TCP हैंडशेक
  स्वयं पूरा कर देता है, इसलिए वर्कस्टेशन जाँच एक ऐसे पोर्ट को **खुला** रिपोर्ट करती है जो
  वास्तव में बंद है। वर्कस्टेशन से CE सार्वजनिक पतों पर पोर्ट 80 और 443 खुले पढ़े जाते हैं और
  VNet के भीतर से जाँचने पर बंद हैं। `ar-ecmp-client` का उपयोग करें।
- **किसी CE पर पोर्ट 22 केवल आंतरिक (SLI) पते पर उत्तर देता है।** `ar-ecmp-client` से जाँचने पर,
  प्रत्येक CE का आंतरिक पता `SSH-2.0-OpenSSH_8.7` लौटाता है, जबकि उसके प्रबंधन और बाहरी पते
  टाइमआउट हो जाते हैं — जैसा कि कंट्रोल के रूप में प्रयुक्त एक अप्रयुक्त पता भी। eth0 का नाम
  `a-i-eth0` कर दिया गया है और वह कोई होस्ट IP नहीं वहन करता, क्योंकि डेटापाथ उसका स्वामी है।
  अतः जिस पते से आप नोड को जानते हैं, उसे जाँचने से नोड की SSH स्थिति के बारे में कुछ पता
  नहीं चलता, और SLI पता ही वह है जिससे जुड़ना है। वह पता
  `terraform output -json ce_sli_private_ips` से लें; यह न मान लें कि आंतरिक सबनेट
  केवल-CEs है, क्योंकि टेस्ट क्लाइंट का NIC भी उसमें है।

<Aside type="note" title="यह पृष्ठ क्या दावा नहीं करता">
तीन बातें जिनकी पाठक यहाँ उचित रूप से अपेक्षा कर सकता है, अनुपस्थित हैं, क्योंकि उन्हें तैनाती के
विरुद्ध अभ्यास में नहीं लाया गया:

- **फ़ेलओवर का परीक्षण नहीं किया गया।** तीन समान-लागत अगले हॉप स्थापित होने के रूप में सत्यापित
  हैं; किसी CE को रोकने पर रूट तालिका का क्या होता है यह नहीं दिखाया गया है, इसलिए इस पृष्ठ से
  फ़ेलओवर डेमो का अभ्यास पहले उसे आज़माए बिना न करें।
- **तीनों अगले हॉप में ट्रैफ़िक वितरण मापा नहीं गया।** VIP के लिए 1,470 अनुरोधों का हिसाब ऊपर
  दिया गया है, जो यह स्थापित करता है कि पथ काम करता है और समय के साथ यह कैसा व्यवहार करता है।
  उसमें से कुछ भी यह नहीं दिखाता कि वे अनुरोध तीनों अगले हॉप में कैसे बँटे, और यह टोपोलॉजी उन्हें
  आरोपित करने के लिए कोई प्रति-नोड HTTP लिसनर नहीं देती।
- **कन्वर्जेंस ट्रांज़िएंट का कारण स्थापित नहीं है।** इसे लक्षणित किया गया है — यह कब होता है,
  कितनी देर तक, कि ऑरिजिन आरंभ से अंत तक स्वच्छ है — और समझाया नहीं गया है।

</Aside>
