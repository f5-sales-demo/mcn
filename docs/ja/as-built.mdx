このデプロイメントは、CE の前段に Azure ロードバランサーを置かない **Azure における
アクティブ/アクティブ Customer Edge 高可用性** を示すものです。3 台の CE がそれぞれ同一の
ホストルートを eBGP でオリジネートし、Azure Route Server がその 3 つすべてを VNet 内の
等コストネクストホップとしてインストールします。したがって、トラフィック分散と障害ノードの
除外が行われる場所は、ロードバランサーではなくルーティングファブリックです。

以下に示す内容はすべて稼働中のデプロイメントに対して実行したものであり、出力はそこで実際に
生成されたものです。この一文が *カバーしていない* もの — フェイルオーバー、3 つのネクストホップ
間でトラフィックがどう分割されるか、新規構築時に VIP が一時的にパケットロスを起こす理由 — に
ついては、暗黙の前提とせず明示的に取り上げます。

## デプロイされるもの

```text
                  Azure Route Server  ce-ha-lab-rrs  ASN 65515
                          10.0.4.4  and  10.0.4.5
                                      |
              +-----------------------+-----------------------+
              |                       |                       |
        eastus01-bgp            eastus02-bgp            eastus03-bgp     eBGP
              |                       |                       |      CE ASN 64512
        10.0.1.4                10.0.1.5                10.0.1.6     <- CE eth0 / SLO
     f5-xc-ce-vm-01          f5-xc-ce-vm-02          f5-xc-ce-vm-03
    ar-bgp-eastus01         ar-bgp-eastus02         ar-bgp-eastus03
              |                       |                       |
              +----- each advertises 10.250.0.10/32 -----------+
                          three-way ECMP into the VNet
```

| 要素 | 構築内容 |
| --- | --- |
| F5 Distributed Cloud テナント | `f5-sales-demo` — `https://f5-sales-demo.console.ves.volterra.io` |
| ネームスペース | サイトは `system`、オリジンプールとロードバランサーは `multi-cloud-networking` |
| Customer Edge | 3 つのシングルノード Secure Mesh v2 サイト — `ar-bgp-eastus01`、`ar-bgp-eastus02`、`ar-bgp-eastus03` |
| CE ソフトウェア | `9.2024.6` にピン留め、ビルド `crt-20250613-3382` |
| Azure VM | `f5-xc-ce-vm-01/02/03`、それぞれ 3 つの NIC（management/SLO、external、internal/SLI） |
| ルート交換 | Azure Route Server `ce-ha-lab-rrs`、ASN `65515`、インスタンス `10.0.4.4` と `10.0.4.5` |
| ピアリング | CE ごとに 1 つ — `eastus01-bgp`、`eastus02-bgp`、`eastus03-bgp` — CE ASN `64512` |
| アドバタイズされる VIP | `10.250.0.10/32`、3 台の CE すべてが同一にオリジネート |
| ロードバランサー | `ar-bgp-ecmp-lb`、ドメイン `ar-bgp-ecmp.bankexample.com` を提供 |
| テストクライアント | `ar-ecmp-client`、同一 VNet 内の VM |
| リソースグループ | `rg-mcn-ce-ha-rmordasiewicz` |

<Aside type="caution" title="VIP はすべての VNet CIDR の外側に配置する必要があります">
`terraform/main.tf` には、VIP がハブとスポークの両方の CIDR の外側にあることを表明する
`check` ブロックがあり、そうでない場合はプランを拒否します。その理由として挙げられているのは、
VNet CIDR 内にある VIP は、BGP ルートのほうがより詳細であっても VNet 自身のシステムルートに
負けてしまうという点です。

このガードを契約として扱ってください。このデモを異なるアドレッシングに向け直す場合、VIP も
それに合わせて VNet 範囲の外に移動させる必要があります。
</Aside>

## テナントは設定であり、シェルがエクスポートしている値ではありません

`var.expected_xc_tenant` がテナントを指定し、デフォルトは `f5-sales-demo` で、テナントが
指定される唯一の場所です。`providers.tf` はここから `xcsh` プロバイダーの `api_url` を導出し、
これは環境変数の `XCSH_API_URL` を意図的に上書きします。また `terraform/main.tf` の
`postcondition` は、環境が異なるテナントを指している場合に **プラン** を失敗させます。

状態を変更する処理を実行せずに、どちらの側も読み取れます。

```bash
cd terraform
terraform output -raw xc_tenant       # what the deployment targets
terraform output -raw xc_env_tenant   # what your shell claims — diagnostic only
```

```text
f5-sales-demo
f5-sales-demo
```

<Aside type="danger" title="このガードレールは、デモが誤ったテナントへ黙って移動してしまったために存在します">
MCN デモは `f5-sales-demo` で構築されました。その後、ある資格情報ファイルが `f5-amer-ent` の
`XCSH_API_URL` をエクスポートするようになり、以降の apply はそのテナント向けのトークンを発行し、
CE VM はそちらに再登録され、`f5-sales-demo` 側の登録は放棄されました。その間のプランはすべて
クリーンでした。設定内にテナントについての意見を持つものが何もなかったためです
（[issue 696](https://github.com/f5-sales-demo/mcn/issues/696)、
[PR 697](https://github.com/f5-sales-demo/mcn/pull/697) で修正）。復旧には、誤ったテナント側の
スタックを破棄し、正しいテナントで再構築する必要がありました。

認識すべき症状は、それ自体が状況を説明してくれないため注意が必要です。別テナント向けに発行された
トークンは、ピン留めされたエンドポイントに対して素の `401` で失敗し、期限切れの資格情報とまったく
同じように見えます。有効なはずの資格情報が `401` を返す場合は、別のトークンを発行する前に上記 2 つの
出力を比較してください。
</Aside>

## プレゼンテーション前に正常性を証明する

4 つのチェックを、この順序で行います。それぞれが障害箇所を絞り込むため、失敗したときに単に
「何かがおかしい」ではなく、意味のある情報が得られます。

<Steps>

1. **3 つのサイトすべてが `ONLINE` であること。** これが成り立たなければ、下流のいかなる項目も
   成立しません。

   ```bash
   for s in ar-bgp-eastus01 ar-bgp-eastus02 ar-bgp-eastus03; do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **すべてのピアリングがその CE の VIP アドバタイズメントを学習していること。** 各ピアリングを
   個別にクエリしてください。下記のトラップを参照 — ここはデモが壊れているように見えて実際は
   そうではないケースが最も多い箇所です。

   ```bash
   for p in eastus01-bgp eastus02-bgp eastus03-bgp; do
     echo "--- $p"
     az network routeserver peering list-learned-routes \
       --name "$p" --routeserver ce-ha-lab-rrs -g rg-mcn-ce-ha-rmordasiewicz \
       --query "RouteServiceRole_IN_0[].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp

   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp

   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   3 つのピアリング、3 つの異なるネクストホップ、1 つのプレフィックス。これで ECMP の
   アドバタイズ側が証明されました。

3. **クライアントの有効ルートが 3 つのネクストホップすべてを保持していること。** これは
   VNet が実際にプログラムした ECMP そのものです — CE が主張する内容ではなく、Azure が
   それをどう処理したかです。

   ```bash
   az network nic show-effective-route-table \
     --name ar-ecmp-clientVMNic -g rg-mcn-ce-ha-rmordasiewicz \
     --query "value[?addressPrefix[0]=='10.250.0.10/32']" -o json
   ```

   ```json
   [
     {
       "addressPrefix": ["10.250.0.10/32"],
       "nextHopIpAddress": ["10.0.1.5", "10.0.1.4", "10.0.1.6"],
       "nextHopType": "VirtualNetworkGateway",
       "source": "VirtualNetworkGateway",
       "state": "Active"
     }
   ]
   ```

   `nextHopIpAddress` に 3 つのエントリがあり `state: Active` であることがチェック項目です。
   **この 3 つの順序に意味はなく、安定もしていません** — Azure は呼び出しごとに異なる順序で
   返すため、以前の実行結果とリストを比較するのではなく、個数を数えてください。3 つあるはずの
   ところにネクストホップが 1 つしかない場合は、ある CE がアドバタイズを停止しており、
   ステップ 2 でどれかが特定できます。

4. **VIP がトラフィックを処理していること。** クライアント VM から、かつ **`Host` ヘッダー付きで**
   実行します — 下記の 2 つ目のトラップを参照。問題を検出できるだけの十分なリクエスト数を
   サンプリングしてください。数十回程度では、後述の収束ウィンドウ中でも 100 % に見えてしまいます。

   ```bash
   az vm run-command invoke -g rg-mcn-ce-ha-rmordasiewicz -n ar-ecmp-client \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts 'ok=0; fail=0
                for i in $(seq 1 60); do
                  c=$(curl -s -o /dev/null -m 5 -w "%{http_code}" \
                        -H "Host: ar-bgp-ecmp.bankexample.com" http://10.250.0.10/)
                  [ "$c" = 200 ] && ok=$((ok+1)) || fail=$((fail+1))
                done
                echo "OK=$ok FAIL=$fail"'
   ```

   ```text
   OK=60 FAIL=0
   ```

</Steps>

## トラップ: 1 つのピアリングに 1 つのルートしか表示されないのは正しい動作です

`list-learned-routes` は指定したピアリングにスコープされます。報告されるのは **その** ピアが
アドバタイズした内容であり、Route Server のテーブル全体ではありません。

したがって `eastus01-bgp` だけをクエリすると `10.0.1.4` 経由の `10.250.0.10/32` が 1 件だけ
返り、「1 台の CE しかアドバタイズしていない — 他の 2 台はダウンしている」と読みたくなります。
何もダウンしていません。他の 2 つのアドバタイズメントはそれぞれのピアリング上で確認でき、
それが上記ステップ 2 でループしている内容です。

単一のピアリングクエリから ECMP を確認することはできません。3 つのピアリングすべてをループするか、
1 回の呼び出しでマージ結果を表示するクライアントの有効ルートテーブルを読んでください。

## トラップ: IP アドレス直打ちのリクエストは 404 を返します

ロードバランサーは `Host` でマッチします。VIP は、そのアドレスに接続してきた相手に何でも
提供する仮想サーバーではありません。

```text
curl -H 'Host: ar-bgp-ecmp.bankexample.com' http://10.250.0.10/   ->  200   (10 of 10)
curl                                        http://10.250.0.10/   ->  404
```

この両方は、正常なデプロイメントに対する同一の実行で生成されたものです。**IP 直打ちの 404 は
パスが機能している証拠です** — リクエストは CE に到達し、CE のプロキシが応答し、設定された
ドメインに一致しなかったため拒否したのです。これを障害と解釈すると BGP を調べに行くことになり、
そこには何も問題は見つかりません。

デモ中も同様です。ドメインを解決せずにブラウザにアドレスを直接入力すると 404 が返ります。

## VIP は最初の 45 分間ほどリクエストをドロップし、その後停止します

新規構築したスタックでは、CE が `ONLINE` に達してからおよそ最初の 45 分間、VIP はごく一部の
リクエストを失い、その後はクリーンに処理します。`ar-ecmp-client` から 1,470 リクエストを
すべて `Host` ヘッダー付きで測定した結果:

| ウィンドウ | リクエスト数 | 失敗数 | 割合 |
| --- | --- | --- | --- |
| ECMP 確立後の最初の約 45 分間 | 570 | 12 | **2.11 %** |
| 続く 23 分間 | 900 | **0** | **0.00 %** |

すべての失敗は `curl: (28)` — 受信バイト数ゼロのタイムアウト — であり、HTTP エラーステータス
ではありませんでした。最後の失敗は ECMP 確立からおよそ 43 分後に発生しました。900 件のクリーンな
リクエストのうち 400 件はタイムアウト 30 秒で実行され、そのすべてが 2 秒未満で完了したため、
短いタイムアウトによって何かが隠されていたということはありません。

**オリジンは原因ではありませんでした。** オリジンへ直接（`http://20.98.232.135/`、VIP を
バイパス）実行した対照バッチは、VIP のバッチが失敗している *のと同時に* 120 件中 120 件が
クリーンでした。障害は VIP、ECMP、または CE のパスのどこかにあります。

これについて意図的に述べていないことが 2 つあります。

- **定常状態の欠陥ではありません。** 完全に解消し、その状態が続きます。1 時間稼働しているデモに
  この問題はありません — 上記チェックで 60 件中 60 件成功し、再構築したスタックでも再びクリーンに
  再現されました。
- **特定の CE に起因するものではありません。** このトポロジにはノードごとの HTTP リスナーが
  存在しないため、ドロップされたリクエストをドロップしたノードに紐付ける手段がありません。
  CE の外部インターフェイス（`10.0.2.x`）には HTTP リスナーが一切なく、応答するのは VIP の
  `/32` だけです。

異なるテナントでのクリーンな再構築でも再現したため、これは環境ではなくトポロジに起因します。

<Aside type="caution" title="40 リクエストだけサンプリングして問題なしと結論しないでください">
40〜50 件のバッチは、失敗ウィンドウの内側であってもほとんどの場合 100 % に見えます。これが原因で、
この現象は最初に「継続的な低頻度の障害」と誤って特徴づけられ、次に「まったく障害なし」と誤解
されました。時間を空けたバッチで 100 件以上をサンプリングしてください。
</Aside>

## 登録承認は自動化されていますが、apply は依然として 2 フェーズです

登録承認にコンソール上の人手はもう必要ありません。プロバイダー **v3.81.1** では
`xcsh_registration_approval` リソースがこれを実行し、サイトモジュールがどの登録を承認するかを
解決します。

とはいえ、これでデプロイメントが単一の手放し `apply` になるわけではなく、その理由は初回実行を
見て失敗したと結論づける前に理解しておく価値があります。

- CE の登録オブジェクトは **`r-<uuid>`** という名前です。サイト名にちなんだ名前になることは
  決してないため、プラン時に名前を予測することはできません。
- 登録は、VM が起動して `vpm` が登録した後にのみ存在します。
- したがって **初回の apply では承認は一切プランされません**。CE が登録され承認が作成された後に
  再度 apply してください。

`terraform/main.tf` はこの順序をファイル冒頭で説明しており、そちらが正典です — デプロイ手順は
それを実装するコードとともに存在します。

<Aside type="caution" title="新規作成されたサイトは operate API 経由ですぐには到達できません">
新しいサイトが `ONLINE` を報告してからおよそ 25〜30 分間、`vpm/debug` エンドポイントは
`The requested URL was rejected` と表示される BIG-IP の `503` ページを返します。Web アプリケーション
ファイアウォールによるブロックやトークンの失効のように見えますが、そのどちらでもありません。
待ってから再試行してください。

これは新規構築したデモに影響するもので、稼働中のデモには影響しません。
</Aside>

## Site CLI への接続

日常的なオンボックス診断はデバッグ API 経由で行われ、これはすでにここでスクリプト化されています。
コマンド一覧がドキュメントの記述と一致していることを確認します。

```bash
bash scripts/capture-sitecli.sh --check --site ar-bgp-eastus01 --node f5-xc-ce-vm-01
```

```text
catalog matches the live CE (build crt-20250613-3382, 34 commands)
```

`--check` は何も書き込まないため、稼働中のデモに対して安全に実行できます。

その API が中継しないコマンドのために、このデプロイメントには **アプライアンスの `admin`
アカウントへのオペレーター SSH** も用意されており、そのログインシェルは Site CLI です。3 台の
CE すべてで検証済みです。VNet 内のホストから内部（SLI）アドレスに、端末を割り当てて接続します。

<Aside type="danger" title="CE の内部アドレスをハードコードしないでください — 再構築のたびに再割り当てされます">
Azure は、内部サブネットでどの CE がどのアドレスを取得するかを保持しません。直近の再構築後、
`f5-xc-ce-vm-01`、`-02`、`-03` はそれぞれ `10.0.3.7`、`10.0.3.5`、`10.0.3.4` を保持しています。
ノード順でもなく、連続でもなく、以前保持していたものとも異なります。テストクライアント自身の
NIC も同じサブネットにあり、以前に CE が保持していたアドレスを取得したことがあります。

記憶するのではなく、読み取ってください。

```bash
cd terraform
terraform output -json ce_sli_private_ips
```

```json
{"eastus01":"10.0.3.7","eastus02":"10.0.3.5","eastus03":"10.0.3.4"}
```

Terraform の state が手元にない場合は、*安定している* NIC 名で Azure に問い合わせてください。

```bash
az network nic show -g rg-mcn-ce-ha-rmordasiewicz \
  -n f5-xc-ce-vm-01-internal-nic \
  --query ipConfigurations[0].privateIPAddress -o tsv
```

</Aside>

```bash
SLI=$(terraform output -json ce_sli_private_ips | jq -r '.eastus01')
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<vm-in-vnet> "admin@$SLI"
```

```text
Registration Status: PROVISIONED
SLO IP: 10.0.1.4/26
WELCOME IN SITE CLI
```

<Aside type="caution" title="このアクセスは、これらの CE がそれを前提に構築されたから存在します — 後から追加することはできません">
オペレーターキーは cloud-init の `write_files` によって書き込まれ、これは初回ブート時に一度だけ
実行されます。`custom_data` は置換のみ可能なため、すでに稼働中の CE でこれを採用すると
**すべての CE VM が置き換えられます**。これは設定変更ではなく、フリート全体の再構築です。

かつてはさらに悪い状況でした。置き換えられた CE は再登録できませんでした。破棄されたノードの
登録が依然としてコントロールプレーンの一意インデックス
`(tenant, cluster_name, hostname)` を保持していたためです。しかも `terraform plan` は、フリートが
ダウンしている間ずっと「No changes」と報告していました。復旧には 2 回のフル再構築を要しました。
これは修正済みです（[issue 674](https://github.com/f5-sales-demo/mcn/issues/674)、
[PR 693](https://github.com/f5-sales-demo/mcn/pull/693) でクローズ）。サイトオブジェクトの
ライフサイクルは CE VM インスタンスに結び付けられたため、VM を置き換えるとサイトも置き換えられ、
サイトを削除すると置き換え後のノードが起動する前にその登録も削除されます。

このデプロイメントではこの変更はすでに適用済みで、フリートは正常です。他の環境でこれを採用する
場合は、まず [SSH ページ](../customer-edge/access/ssh/) を読んでください。
</Aside>

## さらに 2 つの測定上のトラップ

どちらもこの環境で自信を持った誤答を生み出したもので、いずれも自明ではありません。

- **ワークステーションからではなく、VNet 内部からプローブしてください。** Netskope は一般的な
  ポートで TCP ハンドシェイクを自ら完了するため、ワークステーションからのプローブは実際には
  閉じているポートを **オープン** と報告します。ポート 80 と 443 は、ワークステーションからは
  CE のパブリックアドレス上でオープンに見えますが、VNet 内部からプローブすると閉じています。
  `ar-ecmp-client` を使用してください。
- **CE のポート 22 は内部（SLI）アドレスでのみ応答します。** `ar-ecmp-client` からプローブすると、
  各 CE の内部アドレスは `SSH-2.0-OpenSSH_8.7` を返しますが、管理アドレスと外部アドレスは
  タイムアウトします — 対照として使用した未使用アドレスと同様です。eth0 は `a-i-eth0` に
  リネームされ、ホスト IP を持ちません。データパスがそれを所有しているためです。したがって、
  そのノードを識別しているアドレスをプローブしても、ノードの SSH の状態については何もわかりません。
  接続すべきは SLI アドレスです。そのアドレスは
  `terraform output -json ce_sli_private_ips` から取得してください。内部サブネットが CE 専用だと
  仮定しないでください。テストクライアントの NIC もそこに含まれています。

<Aside type="note" title="このページが主張していないこと">
読者がここで当然期待しうる 3 つの事項が欠けています。デプロイメントに対して実行していないためです。

- **フェイルオーバーはテストしていません。** 3 つの等コストネクストホップがインストールされて
  いることは検証済みですが、CE を停止したときにルートテーブルがどうなるかは示していません。
  そのため、事前に試すことなくこのページからフェイルオーバーのデモをリハーサルしないでください。
- **3 つのネクストホップ間のトラフィック分散は測定していません。** 上記では VIP への 1,470 件の
  リクエストを集計しており、これによってパスが機能することと時間経過に伴う挙動が確認できます。
  しかし、それらのリクエストが 3 つのネクストホップにどう分散されたかは示しておらず、
  このトポロジにはそれを帰属させるためのノードごとの HTTP リスナーが存在しません。
- **収束時の一過性事象の原因は特定されていません。** それがいつ発生し、どれだけ続き、その間
  オリジンはクリーンであったかという特徴づけは行っていますが、説明はしていません。

</Aside>
