このデプロイメントは、CE の前段に Azure ロードバランサーを置かない
**Azure における アクティブ/アクティブ Customer Edge 高可用性** を実証します。3 台の CE が
それぞれ同一のホストルートを eBGP で広告し、Azure Route Server がその 3 つすべてを
VNet 内の等コストネクストホップとしてインストールします。したがって、トラフィックの分散と
障害ノードの除外が行われるのは、ロードバランサーではなくルーティングファブリックです。

以下に示す内容はすべて稼働中のデプロイメントに対して実行したものであり、出力はそこで
実際に生成されたものです。この文が *カバーしていない* 2 つの事項 — フェイルオーバーと
トラフィック分散 — については、暗黙の前提とせず末尾で明示しています。

## デプロイされる構成

```text
                  Azure Route Server  ce-ha-lab-rrs  ASN 65515
                          10.0.4.4  and  10.0.4.5
                                      |
              +-----------------------+-----------------------+
              |                       |                       |
        eastus01-bgp            eastus02-bgp            eastus03-bgp     eBGP
              |                       |                       |      CE ASN 64512
        10.0.1.4                10.0.1.5                10.0.1.6     <- CE eth0 / SLO
     f5-xc-ce-vm-01          f5-xc-ce-vm-02          f5-xc-ce-vm-03
    ar-bgp-eastus01         ar-bgp-eastus02         ar-bgp-eastus03
              |                       |                       |
              +----- each advertises 10.250.0.10/32 -----------+
                          three-way ECMP into the VNet
```

| 構成要素 | 構築内容 |
| --- | --- |
| Customer Edge | 3 つのシングルノード Secure Mesh v2 サイト — `ar-bgp-eastus01`、`ar-bgp-eastus02`、`ar-bgp-eastus03` |
| CE ソフトウェア | `9.2024.6` に固定、ビルド `crt-20250613-3382` |
| Azure VM | `f5-xc-ce-vm-01/02/03`、各 3 NIC（管理/SLO、外部、内部/SLI） |
| ルート交換 | Azure Route Server `ce-ha-lab-rrs`、ASN `65515`、インスタンス `10.0.4.4` と `10.0.4.5` |
| ピアリング | CE ごとに 1 つ — `eastus01-bgp`、`eastus02-bgp`、`eastus03-bgp` — CE ASN `64512` |
| 広告される VIP | `10.250.0.10/32`、3 台の CE すべてから同一に広告 |
| ロードバランサー | `ar-bgp-ecmp-lb`、ドメイン `ar-bgp-ecmp.bankexample.com` を提供 |
| テストクライアント | `ar-ecmp-client`、同一 VNet 内の VM |
| リソースグループ | `rg-mcn-ce-ha-rmordasiewicz` |

<Aside type="caution" title="VIP はすべての VNet CIDR の外側に配置する必要があります">
`terraform/main.tf` には、VIP がハブとスポーク両方の CIDR の外側にあることをアサートし、
そうでなければプランを拒否する `check` ブロックが含まれています。その理由として挙げられているのは、
VNet CIDR 内の VIP は、BGP ルートの方がより具体的であるにもかかわらず VNet 自身のシステムルートに負けるためです。

このガードを契約として扱ってください。このデモを別のアドレッシングに向け直す場合、
VIP もそれに合わせて VNet 範囲の外へ移動させる必要があります。
</Aside>

## プレゼン前に健全性を証明する

次の順序で 4 つのチェックを行います。それぞれが障害箇所を絞り込むため、失敗は
「何かがおかしい」だけでなく、具体的な情報を教えてくれます。

<Steps>

1. **3 つのサイトすべてが `ONLINE` であること。** これが成立しなければ、以降のいずれも成立しません。

   ```bash
   for s in ar-bgp-eastus01 ar-bgp-eastus02 ar-bgp-eastus03; do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **各ピアリングがその CE の VIP 広告を学習していること。** 各ピアリングを
   個別にクエリしてください — 下記の落とし穴を参照。ここが、デモが壊れているように
   見えて実際はそうではない、最も頻度の高い箇所です。

   ```bash
   for p in eastus01-bgp eastus02-bgp eastus03-bgp; do
     echo "--- $p"
     az network routeserver peering list-learned-routes \
       --name "$p" --routeserver ce-ha-lab-rrs -g rg-mcn-ce-ha-rmordasiewicz \
       --query "RouteServiceRole_IN_0[].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp

   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp

   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   3 つのピアリング、3 つの異なるネクストホップ、1 つのプレフィックス。これで ECMP の
   広告側が証明されました。

3. **クライアントの有効ルートが 3 つすべてのネクストホップを保持していること。** これは
   VNet がプログラムした ECMP そのものです — CE の主張ではなく、Azure が実際に行った結果です。

   ```bash
   az network nic show-effective-route-table \
     --name ar-ecmp-clientVMNic -g rg-mcn-ce-ha-rmordasiewicz \
     --query "value[?addressPrefix[0]=='10.250.0.10/32']" -o json
   ```

   ```json
   [
     {
       "addressPrefix": ["10.250.0.10/32"],
       "nextHopIpAddress": ["10.0.1.5", "10.0.1.4", "10.0.1.6"],
       "nextHopType": "VirtualNetworkGateway",
       "source": "VirtualNetworkGateway",
       "state": "Active"
     }
   ]
   ```

   `nextHopIpAddress` に 3 エントリがあり `state: Active` であることがチェックポイントです。
   3 つ期待されるところにネクストホップが 1 つしかない場合は CE が広告を停止しており、
   ステップ 2 でどれかを特定できます。

4. **VIP がトラフィックを処理すること。** クライアント VM から、かつ **`Host` ヘッダー付き** で実行します — 下記 2 番目の落とし穴を参照。

   ```bash
   az vm run-command invoke -g rg-mcn-ce-ha-rmordasiewicz -n ar-ecmp-client \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts 'for i in $(seq 1 10); do
                  curl -s -o /dev/null -w "%{http_code} " \
                    -H "Host: ar-bgp-ecmp.bankexample.com" http://10.250.0.10/
                done'
   ```

   ```text
   200 200 200 200 200 200 200 200 200 200
   ```

</Steps>

## 落とし穴: 1 つのピアリングにルートが 1 つしか表示されないが、それが正しい

`list-learned-routes` は指定したピアリングにスコープされます。Route Server のテーブル全体ではなく、
**そのピア** が広告した内容を報告します。

そのため `eastus01-bgp` 単独でクエリすると `10.0.1.4` 経由の `10.250.0.10/32` が 1 件だけ返り、
「1 台の CE しか広告していない — 他の 2 台はダウンしている」と読みたくなります。何もダウンしていません。
他の 2 つの広告はそれぞれのピアリング上で確認でき、上記ステップ 2 はそれをループしているのです。

単一のピアリングクエリから ECMP を確認することはできません。3 つのピアリングすべてをループするか、
1 回の呼び出しでマージ結果を示すクライアントの有効ルートテーブルを参照してください。

## 落とし穴: IP 直打ちのリクエストは 404 を返す

ロードバランサーは `Host` でマッチします。VIP は、そのアドレスに接続した相手に何かを提供する
仮想サーバーではありません。

```text
curl -H 'Host: ar-bgp-ecmp.bankexample.com' http://10.250.0.10/   ->  200   (10 of 10)
curl                                        http://10.250.0.10/   ->  404
```

これらはいずれも、健全なデプロイメントに対する同一の実行で得られたものです。**IP 直打ちの
404 は経路が機能している証拠です** — リクエストは CE に到達し、CE のプロキシが応答し、
設定されたドメインに一致しなかったため拒否したのです。これを障害と読むと BGP を調べに行くことになり、
そこには何の問題も見つかりません。

同じことがデモ中にも当てはまります。ドメインを解決させるのではなくアドレスをブラウザに直接
入力すれば、404 が返ります。

## 登録承認は自動化されているが、apply は依然として 2 フェーズ

登録承認にコンソールでの人手はもう必要ありません。プロバイダー **v3.81.1** では
`xcsh_registration_approval` リソースがこれを実行し、サイトモジュールがどの登録を承認するかを解決します。

それでもデプロイメントが単一の手離れした `apply` になるわけではありません。その理由は、
初回実行を見て失敗だと結論づける前に理解しておく価値があります。

- CE の登録オブジェクトは **`r-<uuid>`** という名前です。サイト名に基づく命名は決してされないため、
  プラン時に名前を予測することはできません。
- 登録は VM が起動し `vpm` が登録を行った後にのみ存在します。
- したがって **初回の apply では承認は一切プランされません**。CE が登録され承認が作成された後に、
  再度 apply してください。

`terraform/main.tf` はこの順序をファイル冒頭に記載しており、そちらが正式版です —
デプロイ手順はそれを実装するコードとともに存在します。

<Aside type="caution" title="新規作成したサイトは operate API ですぐには到達できません">
新しいサイトが `ONLINE` を報告してからおよそ 25〜30 分間、`vpm/debug` エンドポイントは
`The requested URL was rejected` と表示される BIG-IP の `503` ページを返します。Web アプリケーション
ファイアウォールによるブロックやトークンの失効のように見えますが、どちらでもありません。待ってから再試行してください。

これは新規構築したデモに影響するものであり、稼働中のデモには影響しません。
</Aside>

## さらに 2 つの計測上の落とし穴

いずれもこの環境で自信を持った誤答を生み出したものであり、どちらも自明ではありません。

- **ワークステーションからではなく、VNet 内部からプローブしてください。** Netskope は一般的なポートで
  TCP ハンドシェイクを自ら完了させるため、ワークステーションからのプローブは実際には閉じているポートを
  **オープン** と報告します。ポート 80 と 443 は、ワークステーションから見ると CE のパブリックアドレス上で
  オープンと読み取れますが、VNet 内部からプローブすると閉じています。`ar-ecmp-client` を使用してください。
- **CE のポート 22 は内部 (SLI) アドレスでのみ応答します。** `ar-ecmp-client` から 3 台の CE に対して
  プローブすると、`10.0.3.5`、`10.0.3.6`、`10.0.3.7` はいずれも `SSH-2.0-OpenSSH_8.7` を返す一方、
  管理アドレスと外部アドレスはタイムアウトします — 対照として使用した未使用アドレスと同様です。
  したがって、そのノードを識別しているアドレスに対してプローブしても、ノードの SSH 状態については何もわかりません。

<Aside type="note" title="このページが主張していないこと">
読者が当然期待しうる 2 つの事項は、デプロイメントに対して実際に検証していないため、
意図的に記載していません。

- **フェイルオーバーは未検証です。** 3 つの等コストネクストホップがインストールされていることは検証済みですが、
  CE を停止したときにルートテーブルがどうなるかは示していません。したがって、まず自分で試すことなく
  このページからフェイルオーバーのデモをリハーサルしないでください。
- **トラフィック分散は未計測です。** VIP への 10 件中 10 件のリクエストが `200` を返し、
  経路が機能していることは証明されました。しかし、その 10 件が 3 つのネクストホップにどう分散されたかは示していません。

</Aside>
