このデプロイメントは、CE の前段に Azure ロードバランサーを置かずに **Azure における
アクティブ/アクティブ Customer Edge 高可用性** を実証します。3 台の CE がそれぞれ同一のホスト
ルートを eBGP でオリジネートし、Azure Route Server がその 3 つすべてを VNet 内の等コスト
ネクストホップとしてインストールします。したがって、トラフィック分散と障害ノードの除外が
行われるのはロードバランサーではなく、ルーティングファブリックです。

以下に示す内容はすべて稼働中のデプロイメントに対して実行したものであり、出力はそれが実際に
生成した出力です。この文が *カバーしていない* 2 つの点 — フェイルオーバーとトラフィック分散 —
については、暗黙の前提として残さず、末尾で明示的に取り上げます。

## デプロイされているもの

```text
                  Azure Route Server  ce-ha-lab-rrs  ASN 65515
                          10.0.4.4  and  10.0.4.5
                                      |
              +-----------------------+-----------------------+
              |                       |                       |
        eastus01-bgp            eastus02-bgp            eastus03-bgp     eBGP
              |                       |                       |      CE ASN 64512
        10.0.1.4                10.0.1.5                10.0.1.6     <- CE eth0 / SLO
     f5-xc-ce-vm-01          f5-xc-ce-vm-02          f5-xc-ce-vm-03
    ar-bgp-eastus01         ar-bgp-eastus02         ar-bgp-eastus03
              |                       |                       |
              +----- each advertises 10.250.0.10/32 -----------+
                          three-way ECMP into the VNet
```

| 構成要素 | 構築内容 |
| --- | --- |
| Customer Edge | 3 つのシングルノード Secure Mesh v2 サイト — `ar-bgp-eastus01`、`ar-bgp-eastus02`、`ar-bgp-eastus03` |
| CE ソフトウェア | `9.2024.6` に固定、ビルド `crt-20250613-3382` |
| Azure VM | `f5-xc-ce-vm-01/02/03`、各 3 NIC（管理/SLO、外部、内部/SLI） |
| ルート交換 | Azure Route Server `ce-ha-lab-rrs`、ASN `65515`、インスタンス `10.0.4.4` および `10.0.4.5` |
| ピアリング | CE ごとに 1 つ — `eastus01-bgp`、`eastus02-bgp`、`eastus03-bgp` — CE ASN `64512` |
| アドバタイズされる VIP | `10.250.0.10/32`、3 台すべての CE が同一に オリジネート |
| ロードバランサー | `ar-bgp-ecmp-lb`、ドメイン `ar-bgp-ecmp.bankexample.com` を提供 |
| テストクライアント | `ar-ecmp-client`、同じ VNet 内の VM |
| リソースグループ | `rg-mcn-ce-ha-rmordasiewicz` |

<Aside type="caution" title="VIP はすべての VNet CIDR の外側に配置しなければなりません">
`terraform/main.tf` には、VIP がハブとスポークの両 CIDR の外側にあることをアサートし、そうで
なければプランを拒否する `check` ブロックが含まれています。その理由として述べられているのは、
VNet CIDR 内の VIP は BGP ルートのほうがより具体的であるにもかかわらず、VNet 自身のシステム
ルートに負けてしまうという点です。

このガードは契約として扱ってください。このデモを別のアドレス体系に向け直す場合、VIP もそれに
合わせて VNet 範囲の外へ移動させる必要があります。
</Aside>

## プレゼンテーション前に正常性を証明する

4 つのチェックを、この順序で実施します。それぞれが障害箇所を絞り込むため、失敗した場合には
「何かがおかしい」というだけでなく、具体的な情報が得られます。

<Steps>

1. **3 つのサイトすべてが `ONLINE` である。** これが成り立たなければ、下流のどれも成り立ちません。

   ```bash
   for s in ar-bgp-eastus01 ar-bgp-eastus02 ar-bgp-eastus03; do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **すべてのピアリングがその CE の VIP アドバタイズメントを学習している。** 各ピアリングを
   個別にクエリしてください — 下記の罠を参照。ここがデモが壊れているように見えて、実際は
   壊れていない最も多いポイントです。

   ```bash
   for p in eastus01-bgp eastus02-bgp eastus03-bgp; do
     echo "--- $p"
     az network routeserver peering list-learned-routes \
       --name "$p" --routeserver ce-ha-lab-rrs -g rg-mcn-ce-ha-rmordasiewicz \
       --query "RouteServiceRole_IN_0[].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp

   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp

   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   3 つのピアリング、3 つの異なるネクストホップ、1 つのプレフィックス。これで ECMP の
   アドバタイズ側が証明されました。

3. **クライアントの有効ルートに 3 つのネクストホップすべてが含まれている。** これが ECMP
   そのもの、つまり VNet がプログラムした状態です — CE が主張している内容ではなく、Azure が
   それをどう扱ったかです。

   ```bash
   az network nic show-effective-route-table \
     --name ar-ecmp-clientVMNic -g rg-mcn-ce-ha-rmordasiewicz \
     --query "value[?addressPrefix[0]=='10.250.0.10/32']" -o json
   ```

   ```json
   [
     {
       "addressPrefix": ["10.250.0.10/32"],
       "nextHopIpAddress": ["10.0.1.5", "10.0.1.4", "10.0.1.6"],
       "nextHopType": "VirtualNetworkGateway",
       "source": "VirtualNetworkGateway",
       "state": "Active"
     }
   ]
   ```

   `nextHopIpAddress` に 3 つのエントリがあり `state: Active` であることがチェック項目です。
   3 つあるべきところにネクストホップが 1 つしかない場合は、ある CE がアドバタイズを停止した
   ことを意味し、ステップ 2 でどの CE かが特定できます。

4. **VIP がトラフィックを処理する。** クライアント VM から、**`Host` ヘッダーを付けて** 実行
   します — 下記の 2 つ目の罠を参照してください。

   ```bash
   az vm run-command invoke -g rg-mcn-ce-ha-rmordasiewicz -n ar-ecmp-client \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts 'for i in $(seq 1 10); do
                  curl -s -o /dev/null -w "%{http_code} " \
                    -H "Host: ar-bgp-ecmp.bankexample.com" http://10.250.0.10/
                done'
   ```

   ```text
   200 200 200 200 200 200 200 200 200 200
   ```

</Steps>

## 罠: あるピアリングにルートが 1 つしか表示されるが、それは正しい

`list-learned-routes` は指定したピアリングにスコープされます。**そのピア** がアドバタイズした
内容を報告するもので、Route Server のテーブル全体ではありません。

そのため `eastus01-bgp` だけをクエリすると `10.0.1.4` 経由の `10.250.0.10/32` が 1 件だけ返り、
「1 台の CE だけがアドバタイズしている — 他の 2 台はダウンしている」と読み取りたくなります。
何もダウンしていません。他の 2 つのアドバタイズメントはそれぞれのピアリング上で確認でき、
上記のステップ 2 がまさにそれをループしています。

単一のピアリングクエリから ECMP を確認することはできません。3 つのピアリングすべてを
ループするか、マージされた結果を 1 回の呼び出しで示すクライアントの有効ルートテーブルを
参照してください。

## 罠: IP アドレスのみのリクエストは 404 を返す

ロードバランサーは `Host` でマッチします。VIP は、そのアドレスに接続してきた誰にでも何かを
提供する仮想サーバーではありません。

```text
curl -H 'Host: ar-bgp-ecmp.bankexample.com' http://10.250.0.10/   ->  200   (10 of 10)
curl                                        http://10.250.0.10/   ->  404
```

これら両方は、正常なデプロイメントに対する同一の実行で生成されました。**IP アドレスのみでの
404 は経路が機能していることの証明です** — リクエストは CE に到達し、CE のプロキシが応答し、
設定済みドメインに一致しなかったため拒否したのです。これを障害と読み取ると BGP を調べに行く
ことになり、そこには何も問題は見つかりません。

デモ中も同じことが当てはまります。ドメインを解決させるのではなくアドレスをブラウザに直接
入力すれば、404 が返ります。

## 登録承認は自動化されているが、apply は依然として 2 フェーズ

登録承認にコンソールでの人手は不要になりました。プロバイダー **v3.81.1** では
`xcsh_registration_approval` リソースがこれを実行し、サイトモジュールがどの登録を承認するかを
解決します。

それでもデプロイメントが単一の手離れした `apply` になるわけではなく、その理由は初回実行を
見て「失敗した」と結論づける前に理解しておく価値があります。

- CE の登録オブジェクトは **`r-<uuid>`** という名前になります。サイト名に由来する名前が付く
  ことはないため、プラン時に名前を予測することはできません。
- 登録は VM が起動し `vpm` が登録を行った後にのみ存在します。
- したがって **初回の apply では承認は一切プランされません**。CE が登録され承認が作成された
  後に、もう一度 apply してください。

`terraform/main.tf` はこの順序をファイル冒頭に記載しており、それが正式版です — デプロイ
シーケンスは、それを実装するコードとともに存在します。

<Aside type="caution" title="新規サイトは operate API 経由で即座に到達可能になるわけではありません">
新しいサイトが `ONLINE` を報告してから概ね 25〜30 分間、`vpm/debug` エンドポイントは
`The requested URL was rejected` と表示される BIG-IP の `503` ページを返します。Web
アプリケーションファイアウォールによるブロックやトークンの失効のように見えますが、どちらでも
ありません。待ってから再試行してください。

これは新しく構築したデモに影響するもので、稼働中のものには影響しません。
</Aside>

## Site CLI へのアクセス

日常的なオンボックス診断はデバッグ API 経由で行い、ここではすでにスクリプト化されています。
コマンド一覧がドキュメントの記述と一致しているか確認してください。

```bash
bash scripts/capture-sitecli.sh --check --site ar-bgp-eastus01 --node f5-xc-ce-vm-01
```

```text
catalog matches the live CE (build crt-20250613-3382, 34 commands)
```

`--check` は何も書き込まないため、稼働中のデモに対しても安全です。

その API が中継しないコマンドについては、このデプロイメントには **アプライアンスの `admin`
アカウントへのオペレーター SSH** も用意されており、そのログインシェルは Site CLI です。3 台の
CE すべてで検証済みです。VNet 内のホストから内部（SLI）アドレスへ、ターミナルを割り当てて
接続します。

```bash
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<vm-in-vnet> admin@10.0.3.5
```

```text
WELCOME IN SITE CLI
Registration Status: PROVISIONED
```

<Aside type="caution" title="このアクセスはこれらの CE がそれを前提に構築されたために存在します — 後から追加することはできません">
オペレーターキーは cloud-init の `write_files` によって書き込まれ、これは初回起動時に一度だけ
実行されます。`custom_data` は置換専用であるため、すでに稼働中の CE でこれを採用すると
すべての CE VM が置換されます — そして 1 台を置換すると現時点では登録が詰まり、
`terraform plan` は「No changes」と報告します（[issue 674](https://github.com/f5-sales-demo/mcn/issues/674)）。
復旧には 2 回のフル再構築を要しました。

このデプロイメントでは変更はすでに適用済みで、フリートは正常です。他の環境でこれを採用する
場合は、まず
[SSH ページ](../customer-edge/access/ssh/) をお読みください。
</Aside>

## さらに 2 つの測定上の罠

いずれもこの環境で自信に満ちた誤った答えを生み出したもので、どちらも自明ではありません。

- **ワークステーションからではなく、VNet 内部からプローブしてください。** Netskope は一般的な
  ポートで TCP ハンドシェイクを自ら完了させるため、ワークステーションからのプローブは実際には
  閉じているポートを **オープン** として報告します。ポート 80 と 443 はワークステーションから
  見ると CE のパブリックアドレスでオープンと読み取れますが、VNet 内部からプローブすると
  閉じています。`ar-ecmp-client` を使用してください。
- **CE のポート 22 は内部（SLI）アドレスでのみ応答します。** `ar-ecmp-client` から 3 台の CE に
  対してプローブすると、`10.0.3.5`、`10.0.3.6`、`10.0.3.7` はいずれも
  `SSH-2.0-OpenSSH_8.7` を返し、管理アドレスと外部アドレスはタイムアウトします — 対照として
  使った未使用アドレスも同様です。eth0 は `a-i-eth0` にリネームされ、データパスが所有している
  ためホスト IP を持ちません。したがって、ノードを識別しているアドレスをプローブしても
  そのノードの SSH 状態については何もわかりません。接続すべきは SLI アドレスです。

<Aside type="note" title="このページが主張していないこと">
読者がここで当然期待しうる 2 つの点は、デプロイメントに対して実際に検証されていないため、
意図的に含めていません。

- **フェイルオーバーはテストしていません。** 3 つの等コストネクストホップがインストールされて
  いることは検証済みですが、CE を停止したときにルートテーブルがどうなるかは示していません。
  したがって、事前に試すことなくこのページからフェイルオーバーのデモをリハーサルしないで
  ください。
- **トラフィック分散は測定していません。** VIP への 10 件のリクエストのうち 10 件が `200` を
  返し、経路が機能していることは証明されます。しかし、その 10 件が 3 つのネクストホップに
  どのように分散されたかは示していません。

</Aside>
