このデモが裏付ける主張は限定的であり、正確に述べる価値があります。より広範な主張は質問に耐えられないからです。

> 複数の Customer Edge がそれぞれ eBGP によって同じホストルートをアドバタイズし、Azure はそのすべてを等コストのネクストホップとしてインストールします。したがってトラフィックの分散とノードの除外は、ルーティングファブリックの特性です — CE の前段に Azure のロードバランサーは存在しません。

まず[4 つのヘルスチェック](../verify/)を実行してください。以下の内容はすべて、それらが合格していることを前提としています。

## 可視化するための 1 つのコマンド

有効ルートは最も強力な単一の証拠です。それは CE が主張している内容ではなく、Azure が実際にプログラムした内容だからです。

```bash
cd terraform
az network nic show-effective-route-table \
  -g "$(terraform output -raw resource_group_name)" \
  -n "$(terraform output -raw client_nic_name)" \
  --query "value[?addressPrefix[0]=='$(terraform output -raw vip)/32'].{prefix:addressPrefix[0],nh:nextHopIpAddress,state:state}" \
  -o json
```

2026-07-28 に観測:

```json
[
  {
    "nh": ["10.0.1.5", "10.0.1.6", "10.0.1.4"],
    "prefix": "10.250.0.10/32",
    "state": "Active"
  }
]
```

1 つのプレフィックス、3 つのネクストホップ、`Active`。これが 1 つの出力に凝縮されたこのデモの要点であり、ここで一呼吸置く価値があります。この構図の中にロードバランサーは一切存在しません。

次に、VNet 内部から `Host` ヘッダーを付けてサービス提供している様子を示します。

```bash
az vm run-command invoke \
  -g "$(terraform output -raw resource_group_name)" \
  -n "$(terraform output -raw client_vm_name)" \
  --command-id RunShellScript --query "value[0].message" -o tsv \
  --scripts "curl -s -o /dev/null -w '%{http_code}\n' \
               -H 'Host: $(terraform output -raw lb_domain)' \
               http://$(terraform output -raw vip)/"
```

<Aside type="caution" title="ブラウザにアドレスを入力してデモしないでください">
ロードバランサーは `Host` でマッチングするため、IP のみのリクエストは完全に正常なデプロイメントであっても **404** を返します。ヘッダーを送信するか、先にドメインを VIP に解決してください。何も問題がなくても、聴衆の前での 404 は取り返しがつきにくいものです。
</Aside>

## 推奨する順序

<Steps>

1. **枠組みを示す。** 1 つの VIP、複数の CE、ロードバランサーなし。ルーティングファブリックが HA のメカニズムです。
2. **アドバタイズ側を示す。** ピアリングをループする（[チェック 2](../verify/)）— 各 CE が自身のネクストホップで同じプレフィックスをアドバタイズし、すべて同じ AS パスであるため、どれも優先されません。
3. **Azure がそれをどう扱ったかを示す。** 上記の有効ルートテーブル: 1 つのプレフィックス、N 個のネクストホップ、`Active`。
4. **サービス提供している様子を示す。** 上記の `curl` を、ヘッダー付きで実行します。
5. **構成を示す。** [Terraform](../terraform/) はここで公開されており、デプロイに使用するファイルから読み込まれています — これが再現可能かどうか尋ねられたときに役立ちます。

</Steps>

## このデモがまだ示せないこと

ライブで発見するのではなく、ここに明記します。3 つすべては証拠の不在であり、既知の障害ではありません。

<Aside type="danger" title="これらのページからフェイルオーバーのストーリーをリハーサルしないでください">
**フェイルオーバーはテストされていません。** 等コストのネクストホップがインストールされていることは検証済みですが、CE が停止されたりアドバタイズを停止したときにルートテーブルがどうなるかは、このデプロイメントに対して実際に検証されていません。意図されているメカニズムは、1 つの CE のアドバタイズを取り下げてネクストホップ数が減少するのを観察することですが、それが実際に実行され測定されるまでは結果ではなく計画にすぎません — したがって約束せず、聴衆の前で即興で行わないでください。

[issue 700](https://github.com/f5-sales-demo/mcn/issues/700) で追跡しています。ライブのアドバタイズ状態を変更するため、他の誰も環境を使用していない時間帯が必要です。
</Aside>

- **ネクストホップ間のトラフィック分散は測定されていません。** VIP への 1,470 件のリクエストは[検証ページ](../verify/)で説明されており、パスが機能することと時間経過に伴う挙動を裏付けています。しかしそのいずれも、リクエストがネクストホップ間でどのように分散されたかを示すものではなく、このトポロジーにはそれらを帰属させるためのノードごとの HTTP リスナーがありません。「均等ですか?」と尋ねられた場合、正直な答えは、ここでは測定されていない、というものです。
- **新規ビルド時の収束の一時的な現象の原因は特定されていません。** それは特徴づけられている（いつ発生し、どのくらい続き、その間オリジンはクリーンであること）だけで、説明はされていません。

<Aside type="note" title="新しくビルドしたスタックでプレゼンする場合は待ってください">
CE が `ONLINE` に達してから最初の約 45 分間、VIP はごくわずかな割合のリクエストを失います。これは完全に解消します。必要になる十分前にデモを構築し、直前にチェック 4 を再実行してください。
</Aside>
