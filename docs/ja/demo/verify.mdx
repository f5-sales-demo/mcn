プレゼンテーションの前にこれらを実行してください。各チェックは障害箇所を絞り込むため、失敗した場合は「何かがおかしい」というだけでなく、具体的な情報が得られます。

すべてのコマンドは必要な値をデプロイメントから読み取ります。以下を一度設定すれば、残りはそれに従います:

```bash
cd terraform
RG=$(terraform output -raw resource_group_name)
RS=$(terraform output -raw route_server_name)
CLIENT=$(terraform output -raw client_vm_name)
DOMAIN=$(terraform output -raw lb_domain)
VIP=$(terraform output -raw vip)
NIC=$(terraform output -raw client_nic_name)
```

## 4つのチェック、この順序で

<Steps>

1. **すべてのサイトが `ONLINE` であること。** これが成り立たなければ、下流のどれも成り立ちません。

   ```bash
   for s in $(terraform output -json xc_site_names | jq -r '.[]'); do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   2026-07-28 の観測、CE 3台:

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **すべてのピアリングがその CE の VIP アドバタイズを学習していること。** 各ピアリングを個別にクエリしてください — 以下の最初の罠を参照してください。ここがこのデモで最も頻繁に「壊れているように見えて実際は壊れていない」箇所です。

   ```bash
   for k in $(terraform output -json xc_site_names | jq -r 'keys[]'); do
     echo "--- ${k}-bgp"
     az network routeserver peering list-learned-routes \
       --name "${k}-bgp" --routeserver "$RS" -g "$RG" \
       --query "RouteServiceRole_IN_0[?network=='${VIP}/32'].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   2026-07-28 の観測:

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp
   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp
   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   3つのピアリング、3つの異なるネクストホップ、1つのプレフィックス。これで ECMP のアドバタイズ側が証明されました。

3. **クライアントの有効ルートがすべてのネクストホップを保持していること。** これが ECMP そのもの、つまり VNet がプログラムした形です — CE が主張している内容ではなく、Azure が実際にそれをどう扱ったかです。

   ```bash
   az network nic show-effective-route-table -g "$RG" -n "$NIC" \
     --query "value[?addressPrefix[0]=='${VIP}/32'].{prefix:addressPrefix[0],nh:nextHopIpAddress,type:nextHopType,state:state}" \
     -o json
   ```

   2026-07-28 の観測:

   ```json
   [
     {
       "nh": ["10.0.1.5", "10.0.1.6", "10.0.1.4"],
       "prefix": "10.250.0.10/32",
       "state": "Active",
       "type": "VirtualNetworkGateway"
     }
   ]
   ```

   `state: Active` であり、`nh` に CE ごとに1つのエントリがあることがチェック内容です。**順序は意味を持たず、安定しません** — Azure は呼び出しごとに異なる順序で返すため、以前の実行結果と比較するのではなく、数を数えてください。3つ期待している場所にネクストホップが1つしかない場合は、ある CE がアドバタイズを停止していることを意味し、ステップ2でどれかが特定できます。

4. **VIP がトラフィックを処理していること。** クライアント VM から、そして **`Host` ヘッダー付きで** 実行します — 2つ目の罠を参照してください。問題を検出できる十分な数のリクエストをサンプリングしてください: 数十件では、以下で説明する収束ウィンドウの中にあっても 100 % と読めてしまいます。

   ```bash
   az vm run-command invoke -g "$RG" -n "$CLIENT" \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts "ok=0; fail=0
                for i in \$(seq 1 60); do
                  c=\$(curl -s -o /dev/null -m 5 -w '%{http_code}' \
                        -H 'Host: ${DOMAIN}' http://${VIP}/)
                  [ \"\$c\" = 200 ] && ok=\$((ok+1)) || fail=\$((fail+1))
                done
                echo \"OK=\$ok FAIL=\$fail\""
   ```

   2026-07-28 の観測:

   ```text
   VIP with Host header: OK=60 FAIL=0
   bare IP (no Host): 404
   ```

</Steps>

## 罠: 1つのピアリングが1つのルートしか表示しないのは正しい動作

`list-learned-routes` は指定したピアリングにスコープされます。**そのピア**がアドバタイズした内容を報告するもので、Route Server のテーブル全体ではありません。

そのため、1つのピアリングだけをクエリすると、単一のネクストホップ経由の単一の VIP `/32` が返ってきます。これを「1つの CE だけがアドバタイズしている — 他はダウンしている」と読みたくなります。何もダウンしていません。他のアドバタイズはそれぞれのピアリング上で確認でき、それがステップ2でループしている内容です。

単一のピアリングクエリから ECMP を確認することはできません。すべてのピアリングをループするか、マージ済みの結果を1回の呼び出しで表示するクライアントの有効ルートテーブルを読んでください。

## 罠: ベアIPリクエストは404を返す

ロードバランサーは `Host` でマッチします。VIP は、そのアドレスに接続してきた相手に何かを提供する仮想サーバーではありません。

以下の両方は、正常なデプロイメントに対する同一の実行から得られたものです:

```text
curl -H "Host: $DOMAIN" http://$VIP/   ->  200   (60 of 60)
curl                     http://$VIP/   ->  404
```

**ベアIPの404はパスが機能している証拠です** — リクエストは CE に到達し、CE のプロキシが応答し、設定されたドメインに一致しなかったため拒否したのです。これを障害と読み取ると BGP を調べに行くことになりますが、そこには何の問題も見つかりません。

これはデモ中にも当てはまります: ドメインを解決するのではなくアドレスをブラウザに直接入力すると、404 が返ってきます。

## VIP は最初の45分ほどリクエストをドロップし、その後止まる

新規に構築したスタックでは、CE が `ONLINE` になってからおよそ最初の45分間、VIP はわずかな割合のリクエストを失い、その後はクリーンに処理します。クライアント VM から 1,470 リクエストを、すべて `Host` ヘッダー付きで測定した結果:

| ウィンドウ | リクエスト | 失敗 | 率 |
| --- | --- | --- | --- |
| ECMP 確立後 最初の約45分 | 570 | 12 | **2.11 %** |
| その後の23分間 | 900 | **0** | **0.00 %** |

すべての失敗は `curl: (28)` — 受信バイト数ゼロのタイムアウト — であり、HTTP エラーステータスではありませんでした。最後の失敗は ECMP 確立から約43分後に発生しました。クリーンだった 900 リクエストのうち 400 は 30 秒のタイムアウトで実行され、すべてが2秒未満で完了したため、短いタイムアウトによって何かが隠されていたわけではありません。

**原因はオリジンではありませんでした。** オリジンへ直接送信した対照バッチ（`terraform output -raw origin_ip`、VIP をバイパス）は、VIP バッチが失敗している *のと同時に* 120 中 120 がクリーンでした。障害は VIP、ECMP、または CE のパスのどこかにあります。

これを意図的にそう呼んでいない2点:

- **定常状態の欠陥ではありません。** 完全に解消し、その後も解消したままです。1時間稼働しているデモではこの問題は発生しません — 数時間稼働していたスタックでは上記のチェック4で 60 中 60 でした。
- **特定の CE に帰属させられません。** このトポロジーにはノードごとの HTTP リスナーが存在しないため、ドロップされたリクエストをドロップしたノードに紐づける方法がありません。CE の外部インターフェイスには HTTP リスナーが一切なく — VIP `/32` のみが応答します。

異なるテナントでのクリーンな再構築でも再現したため、環境ではなくトポロジーに起因するものです。

<Aside type="caution" title="40リクエストをサンプリングして問題なしと結論しないこと">
40〜50件のバッチは、失敗ウィンドウの内側であってもほとんどの場合 100 % と読めてしまいます。これが原因で、当初は継続的な低率の障害と誤って特徴づけられ、その後は障害なしと誤認されました。100件以上を、時間を隔てたバッチでサンプリングしてください。
</Aside>

## さらに2つの測定上の罠

どちらもこの環境で自信を持った誤った答えを生み出し、どちらも自明ではありません。

- **ワークステーションからではなく、VNet の内側からプローブしてください。** 企業プロキシは一般的なポートに対して自ら TCP ハンドシェイクを完了できるため、ワークステーションからのプローブは実際には閉じているポートを **open** と報告します。CE のパブリックアドレスに対するポート 80 と 443 は、ワークステーションからは open と読めますが、VNet 内側からプローブすると閉じています。クライアント VM を使用してください。
- **CE のポート 22 は内部 (SLI) アドレスでのみ応答します。** クライアント VM からプローブすると、各 CE の内部アドレスは OpenSSH バナーを返しますが、管理アドレスおよび外部アドレスはタイムアウトします — 対照として使用した未使用アドレスと同様です。eth0 は `a-i-eth0` にリネームされ、ホスト IP を持ちません。データパスがそれを所有しているためです。したがって、ノードを識別するために知っているアドレスをプローブしても、そのノードの SSH 状態については何も分かりません。

<Aside type="danger" title="CE の内部アドレスを決してハードコードしないこと — 再構築ごとに再割り当てされます">
Azure は内部サブネット内でどの CE がどのアドレスを取得するかを保持しません。2026-07-28 の観測では、再構築後、3台の CE は `10.0.3.7`、`10.0.3.5`、`10.0.3.4` を保持していました: ノードの順序でもなく、連続でもなく、以前保持していたものとも異なります。テストクライアント自身の NIC も同じサブネットにあり、以前 CE が保持していたアドレスを保持したことがあります。

覚えておくのではなく、読み取ってください:

```bash
terraform output -json ce_sli_private_ips
```

Terraform の state が手元にない場合は、NIC 名で Azure に問い合わせてください。NIC 名は安定しています:

```bash
az network nic show -g "$RG" -n "<vm-name>-internal-nic" \
  --query ipConfigurations[0].privateIPAddress -o tsv
```

記憶したアドレスに接続すると、誤ったノードに到達したり、CE ではない VM に到達したり、あるいはどこにも到達しなかったりします — そして最後のケースは「SSH が有効になっていない」と見分けがつきません。
</Aside>

## オンボックスのコマンド面がまだドキュメントと一致していることを確認する

```bash
bash scripts/capture-sitecli.sh --check \
  --site "$(terraform output -json xc_site_names | jq -r '.eastus01')" \
  --node "$(terraform output -json ce_vm_names | jq -r '.eastus01')"
```

`--check` は何も書き込まないため、稼働中のデモに対して安全です。
