SSH はアプライアンスの `admin` アカウントに到達します。そのログインシェルは Site CLI
(`/opt/bin/vpmu`) です。これは**オンボックスの全コマンド面**への唯一の経路です。
[デバッグ API](../debug-api/) は 34 個のコマンドを公開していますが、アプライアンス自体は
その API にまったく存在しないコマンドをさらに多く提供しています。

```bash
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<operator-vm> admin@10.0.3.5
```

このコマンドラインのすべての部分が重要な役割を担っており、続く 3 つのセクションで
それぞれがどの障害を防いでいるのかを説明します。

<Aside type="caution" title="ブートストラップ時のみ — 既存の CE は再作成しなければ SSH を得られない">
cloud-init の `write_files` は**初回起動時に一度だけ**実行されます。その後はノード上に
`/etc/cloud/cloud-init.disabled` マーカーが存在し、cloud-init は再度実行されません。

したがって、稼働中の CE にインプレースで適用する経路はありません。Azure では
`custom_data` は置き換え専用であるため、既存のデプロイでこれを採用すると**すべての CE VM が
置き換えられます**。すでに稼働しているノードにオペレーター SSH を付与することは設定変更では
なく再構築です。そして次の警告が、その再構築に現在かかるコストです。
</Aside>

<Aside type="danger" title="CE VM の置き換えは登録を詰まらせ、フリートがダウンしていても terraform plan は 'No changes' と報告する">
これはこのページで最も重い内容です。変更を計画した**後**ではなく、その前に
[issue 674](https://github.com/f5-sales-demo/mcn/issues/674) を読んでください。

古い登録が一意な `(tenant, cluster_name, hostname)` インデックスを保持しているため、
置き換えノードの登録は `UniqueSecondaryIndexViolationError` で拒否され、無限にリトライします。
登録を削除するだけでは不十分です。残存する `StatusObject` がワークロード要求に対して `500` を
返し、その時点で各ノードは削除した登録に固定された `registration-obj.yml` を永続化しているため、
自己回復のないまま `404` でループします。

復旧には、登録の削除、サイトオブジェクトの再作成、**VM の 2 回目の置き換え**、そして承認の適用が
必要でした。1 回の `custom_data` 変更を吸収するために 2 回の完全な再構築です。

その間ずっと `terraform plan` は **"No changes"** と報告していました。Terraform の観点からは
望ましい状態に到達していたからです。フリートはダウンしており、プランはクリーンでした。この変更の
吸収を通常の apply として扱わないでください。
</Aside>

## cloud-init が鍵を書き込み、API が書き込まない理由

サイトオブジェクトの `admin_user_credentials.ssh_key` は、まさにこの用途のフィールドに見えます。
受け付けられ、読み戻しでも残りますが、何も設定しません。`vpm` はノードのローカルユーザーを
所有していますが、このユーザーには手を触れません。ノード自身のログから、1 回の起動で 3 回:

```text
vpm  users.go:165: Won't do any change for user admin (internal skip)
```

他のすべてはこの 1 行から導かれます。`/var/home/admin/.ssh` は、サイトが `ONLINE` に到達する
前も後も、決して存在しません。`admin` の shadow の最終変更日はイメージのビルド日のままで、
`vesbkp` と `vesopcon` は現在の日付を示します。`vpm` がその 2 つを設定し、`admin` をスキップした
からです。そして `vpm` は `ssh_key` や `authorized_keys` について一切ログを出しません。

したがって、このファイルは `vpm` の外側で書き込む必要があります。`admin` は uid 2202 で
ノードイメージに焼き込まれているため、cloud-init の実行前から存在し、`owner: admin:admin` は
書き込み時に解決されます。`runcmd` も所有権の修正も不要です:

```yaml
- path: /var/home/admin/.ssh/authorized_keys
  permissions: "0600"
  owner: admin:admin
  content: |
    ${ssh_public_key}
```

`sshd` は常に受け入れる用意ができていました。`sshd -T` は `pubkeyauthentication yes` を報告し、
ノードに同梱される両方の `sshd_config` ファイルの `AllowUsers` に `admin` が含まれています。
有効化すべきものは何もなく、ただファイルが欠けていただけでした。

<Aside type="danger" title="admin_user_credentials を再追加しないこと、sshd_config を編集しないこと">
`admin_user_credentials` は `terraform/modules/xc-site` に組み込まれましたが、この証拠を
収集した時点で差し戻されました (#660、PR #663)。これは埋めるべき欠落ではありません。

`sshd_config` は登録中に置き換えられるため、そこへの編集は最も都合の悪いタイミングで破棄されます。
</Aside>

## 1 つのアドレスでのみ応答する理由

`sshd` は `0.0.0.0:22` にバインドしますが、ホストのネットワークスタック上にあるのは
**内部 (SLI)** アドレスだけです。eth0 は `a-i-eth0` にリネームされ、ホスト IP を持ちません
(Argo データプレーンがそのインターフェースを所有しています)。一方、eth1 と eth2 はホスト
スタック上に残り、そこで `sshd` がリッスンしています。

VNet 内の VM からプローブした結果:

```text
10.0.1.4     timed out             CE mgmt/SLO  (eth0)
10.0.2.4     timed out             CE external  (eth1)
10.0.3.5     OPEN                  CE internal/SLI
10.0.3.6     OPEN
10.0.3.7     OPEN
```

したがって、あなたがノードを識別しているアドレスに対するプローブは、閉じられたセキュリティ
グループが返すのとまったく同じ結果を返します。何もブロックしていません。そのアドレスに
リスナーが存在しないだけです。

CE のパブリックアドレスにも 22 番のリスナーはありません。そのため上記のコマンドは `-J` を
経由します。VNet 内の、SLI アドレスと同じサブネットにあるオペレーター VM です。

<Aside type="caution" title="自信を持って誤った答えを導く 2 つの測定ミス">
eth0、外部インターフェース、またはパブリックアドレスに対してポート 22 をプローブすると、
ノードの SSH 状態にかかわらず閉じていると報告されるため、何も分かりません。応答するのは
SLI アドレスだけです。

また、企業のワークステーションからのプローブは、閉じているポートを**オープン**と報告する
ことがあります。Netskope が一般的なポートで TCP ハンドシェイクを自ら完了させるためです。
ワークステーションからは CE のパブリックアドレスのポート 80 と 443 がオープンと読み取られますが、
VNet 内からプローブすると閉じています。VNet 内の VM からプローブしてください。
</Aside>

## Site CLI にはターミナルとキャリッジリターンが必要

`admin` のログインシェルはシェルではありません。`go-prompt` アプリケーションであり、ターミナルを
raw モードにして行単位ではなくキーストロークを読み取ります。4 つの帰結があり、それぞれが
まったく別の問題に見える形で失敗します:

| 仕組み | それがない場合に起こること |
| --- | --- |
| ターミナルを割り当てる (`ssh -tt`) | `go-prompt.NewStandardInputParser` から `panic: no such device or address` が出て、アプライアンスがクラッシュしたように見える |
| Enter にはラインフィードではなくキャリッジリターンを送る | 行が送信されず、何も出力しないまま入力終端でセッションが閉じる |
| 標準入力を開いたままにする | コマンドが描画される前に接続が終了するため、動作しているコマンドが無反応に見える |
| コマンド文字列と Enter バイトを**別々に**書き込む | 改行がリテラル文字としてバッファに入り、CLI が `unknown command` と応答するため、コマンドが存在しないように読める |

したがって `ssh host 'some-command'` は動作しません。引数は無視され、対話プロンプトが
そのまま開始されます。ターミナルとして駆動するか、まったく使わないかのどちらかです。
`scripts/sitecli_ssh_harvest.py` がリファレンス実装です。

<Aside type="caution" title="'no such device or address' というパニックは認証が成功したことを意味する">
`vpmu` はログイン**後**、アタッチすべきターミナルが見つからないときにこれを出力します。
クラッシュとして読むと最悪の結果に見えますが、実際には成功する直前の最後のエラーです。
`-tt` を追加して再接続してください。
</Aside>

<Aside type="caution" title="CE を置き換えるとホスト鍵が変わる">
置き換えノードは同じアドレスで異なるホスト鍵を提示するため、次回の接続で
`REMOTE HOST IDENTIFICATION HAS CHANGED` と警告され、接続が拒否されます。そのアドレスの
古いエントリを削除して再接続してください。SSH を付与すること自体が VM の置き換えを伴うため、
採用後の最初の接続でこれが発生すると想定してください。
</Aside>

ログインバナーはノードの登録状態を報告します。これは、まだ起動中のノードと壊れたノードを
区別する最も手早い方法です:

```text
Registration Status: PROVISIONING
SLO IP: 10.0.1.4/26
```

## キーペアの指定

<Steps>

1. まだ持っていない場合はキーペアを生成します。RSA ではなく Ed25519 を使用します。より短く、
   アプライアンスの `sshd` に受け入れられます。

   ```bash
   ssh-keygen -t ed25519 -C "ce-operator" -f ~/.ssh/id_ed25519
   ```

2. デプロイに**公開**鍵側を指定します。ルートモジュールがファイルを一度読み取り、その文字列を
   すべてのノードに渡します:

   ```hcl
   # terraform/terraform.tfvars
   ssh_public_key_path = "~/.ssh/id_ed25519.pub"
   ```

   `ssh_public_key` は代わりに内容をインラインで受け取ります。plan のテストではこちらを使用します。
   秘密鍵側はワークステーションから外に出ることはありません。

3. 適用します。まずこのページ冒頭の警告を読んでください。既存のデプロイでは、これにより
   CE VM が置き換えられます。

</Steps>

<Aside type="note" title="VM 自身の admin_ssh_key は別物">
`modules/ce-node` の `azurerm_linux_virtual_machine.admin_ssh_key` は Azure VM の管理者を
認可するものであり、アプライアンスの `admin` アカウントではありません。Site CLI へのアクセスは
一切付与されず、これが設定されていることは CE SSH が構成されている証拠にはなりません。
</Aside>

## これは何ではないか

以下のそれぞれは、この経路がまだ不可能だと信じられていた間にテストされ、除外されました。
いずれももっともらしく、1 日を費やすに足るものです。

| 原因ではないもの | どのように除外されたか |
| --- | --- |
| 資格情報は作成時にのみ適用される | `sshd` は初回起動から約 90 秒で起動し、それはサイトオブジェクトが存在する前です。`admin_user_credentials` は `ReplaceSpecType` にも存在し、インプレースで適用されます。 |
| `block_all_services` | 管理アドレスのポート 22 の閉塞は、サービスがブロックされているかどうかにかかわらず同一です。 |
| 鍵の末尾の改行 | 両方の方法でテストし、変化なし。リテラルブロックでは 2 行目の空行が描画されてしまうため、cloud-init は依然としてそれを取り除きます。 |
| 固定された古い CE ソフトウェア | OpenSSH 9.9 が動作しているものを含め、3 つのビルドで再現しました。 |
| `admin_password` の欠落 | ゼロから作成した CE で `ssh_key` と併せて `admin_password` を設定しても何も変わりませんでした。 |

<Aside type="caution" title="判別材料に見えて、そうではない 2 つの API フィールド">
`gc_spec.admin_ssh_key` は、`admin_password` を設定している 20 サイトを含め、**テナント内の
88 サイトすべて**で空です。動作するサイトと動作しないサイトの間でこれを比較しても何も分かりません。
どこでも空だからです。

`registrations_by_site` はこのフィールドを完全に省略し、`None` を返します。これは「報告されて
いない」ではなく「未設定」として読めてしまいます。
</Aside>

<Aside type="caution" title="新規作成したサイトは operate API が応答するまで約 30 分かかる">
新しいサイトが `ONLINE` を報告してからおよそ 25〜30 分間、`vpm/debug` エンドポイントは
`The requested URL was rejected` と表示される BIG-IP の `503` ページを返します。これは Web
アプリファイアウォールによるブロックやトークンの失効のように見えますが、どちらでもありません。
サイトがまだ中継の準備ができていないだけです。何かを変更するのではなく、待ってから再試行してください。

SSH にはそのようなウォームアップはありません。`sshd` が起動した時点で応答するため、ノードが
まだ登録中でも機能する経路となっています。
</Aside>
