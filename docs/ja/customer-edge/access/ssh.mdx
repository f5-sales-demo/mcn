**このテナントで稼働している CE ビルドには、サポートされた `admin` SSH 経路は存在しません** —
`crt-20250613-3382`、OS `9.2024.6`。これは設定の問題ではありません。`admin` アカウントは存在し、
`sshd` は動作しており、`admin_user_credentials.ssh_key` はサイトオブジェクトに受け付けられ、
API の読み戻しでも返されます。しかし、そのキーがノードに適用されることは決してないため、
すべての認証試行は拒否されます。

代わりに [debug API](../debug-api/) を使用してください。ノードの読み取り専用コマンド
サーフェスに到達でき、このリポジトリで既にスクリプト化されています。

<Aside type="danger" title="これに対する Terraform サポートは削除されました">
`admin_user_credentials` は一度 `terraform/modules/xc-site` に組み込まれましたが、以下の証跡が
収集された時点で差し戻されました (#660、PR #663)。これは埋められるのを待っているギャップでは
ありません — このフィールドはノード上で何も設定しません。再追加しないでください。
</Aside>

## なぜどの試行もネットワークの問題に見えるのか

`sshd` は CE 上で `0.0.0.0:22` にバインドしますが、ホストのネットワークスタックに存在するのは
**内部 (SLI)** アドレスのみです。同一 VNet 内の `ar-ecmp-client` から、3 台のデモ CE すべてに
対してプローブした結果:

```text
10.0.1.4     TimeoutError: timed out         ← CE mgmt/SLO  (eth0)
10.0.2.4     TimeoutError: timed out         ← CE external  (eth1)
10.0.3.5     CONNECTED  SSH-2.0-OpenSSH_8.7  ← CE internal/SLI
10.0.3.6     CONNECTED  SSH-2.0-OpenSSH_8.7
10.0.3.7     CONNECTED  SSH-2.0-OpenSSH_8.7
10.0.3.99    TimeoutError: timed out         ← unused address, negative control
```

その仕組みは [`health`](../../commands/system/health/) で確認できます。**eth0 は
`a-i-eth0` にリネームされ、ホスト IP アドレスを一切持ちません** — このインターフェースは
Argo データプレーンが所有しています — 一方、eth1 と eth2 は `sshd` がリッスンしている
ホストスタック側に残ります。

したがって、あなたがノードを識別しているアドレス、すなわち管理アドレスに対するプローブは、
セキュリティグループが閉じている場合とまったく同じようにタイムアウトします。何かが
ブロックしているわけではなく、そのアドレスに応答するリスナーが存在しないのです。

<Aside type="caution" title="VNet 内部からプローブし、内部アドレスをプローブすること">
ここでの 2 つの計測ミスは、自信に満ちた誤答を生み出します。

eth0 や外部インターフェースのポート 22 をプローブすると、ノードの SSH 状態にかかわらず常に
クローズと報告されるため、SSH について何も分かりません。応答するのは SLI アドレスだけです。

さらに、企業のワークステーションからのプローブは、実際には閉じているポートを **オープン** と
報告することがあります。Netskope が一般的なポートで TCP ハンドシェイクを自ら完了させるためです。
ポート 80 と 443 はワークステーションからは CE のパブリックアドレス上でオープンと読み取られますが、
VNet 内部からプローブするとクローズです。VNet 内の VM からプローブしてください。
</Aside>

## なぜ `admin` は認証できないのか

`vpm` は登録時にノードのローカルユーザーを設定しますが、このユーザーには手を触れないことを
明示しています。ノード自身のログから、1 回の起動中に 3 回:

```text
vpm  users.go:165: Won't do any change for user admin (internal skip)
```

その他すべてが、この 1 行と整合しています:

- アカウントは存在します — `uid=2202(admin) gid=2202(admin) groups=2202(admin),2301(vpm)`、
  ホーム `/var/home/admin`、ログインシェル `/opt/bin/vpmu`(Site CLI)。
- `/var/home/admin/.ssh` は、サイトが `ONLINE` になる前も後も **決して存在しません**。
  `authorized_keys` ファイルはいかなる時点でも書き込まれません。
- `sshd -T` は `pubkeyauthentication yes`、`passwordauthentication no`、
  `kbdinteractiveauthentication no` を報告します。`/etc/ssh/sshd_config` 内の唯一の
  `PasswordAuthentication yes` は `Match User vesbkp,xcuser` の内側にあるため、`admin` は
  **イメージレベルで** パスワード認証から除外されています。
- `admin` の shadow の最終変更日はイメージのビルド日である 2024-02-16 であるのに対し、
  `vesbkp` と `vesopcon` は現在の日付を示しています。`vpm` はこの 2 つを設定し、`admin` には
  一切触れていません。
- `vpm` は `ssh_key` や `authorized_keys` について何もログを出しません。

クライアント側も同様です。3 回のゼロからのデプロイ、2 回のインプレース更新、3 種類の異なる
CE ビルド(OpenSSH 9.9 で動作する最新版を含む)にまたがる 45 回の認証試行を通じて:

```text
debug1: Authenticating to <sli-ip>:22 as 'admin'
debug1: Offering public key: ... ED25519 SHA256:ENH3M0bFPYMt... explicit
debug1: Authentications that can continue: publickey
admin@<sli-ip>: Permission denied (publickey).
```

サーバーはパスワード認証もキーボードインタラクティブ認証も一切提示せず、ノード上の
`journalctl -u sshd` には
`Connection closed by authenticating user admin ... [preauth]` が記録されます。

## これは何ではないのか

以下はいずれも検証のうえ除外されたものであり、いずれも 1 日を費やすに足るもっともらしい推測です。

| 原因ではないもの | どのように除外されたか |
| --- | --- |
| 資格情報は作成時のみ適用される | `sshd` は初回起動から約 90 秒後、*サイトオブジェクトが存在するより前* に起動します — 13:04:56 に `sshd[1238]: Server listening on 0.0.0.0 port 22`、サイト作成は 13:05:23。`admin_user_credentials` は `ReplaceSpecType` にも存在し、インプレースで適用されます。 |
| `block_all_services` | SLO のポート 22 のクローズ状態は、サービスがブロックされているかどうかに関係なく同一です。 |
| キー末尾の改行 | 両方の方法でテスト済み。変化なし。 |
| 固定された古い CE ソフトウェア | OpenSSH 9.9 を含む 3 つのビルドで再現しました。 |
| `admin_password` の欠如 | ゼロから構築した CE で `ssh_key` と併せて `admin_password` を設定しても、何も変わりませんでした。 |

<Aside type="caution" title="判別材料に見えて実はそうではない 2 つの API フィールド">
`gc_spec.admin_ssh_key` は、`admin_password` を設定している 20 サイトを含め、**テナント内の
88 サイトすべて** で空です。動作しているサイトと動作していないサイトの間でこれを比較しても
何も分かりません。どこでも空だからです。

`registrations_by_site` はこのフィールドを完全に省略し、`None` を返すため、「報告されていない」
ではなく「設定されていない」と読み取られてしまいます。
</Aside>

Web アプリケーションファイアウォールによるブロックや、失効したトークンのように見えますが、
そのいずれでもありません — サイトがまだ中継の準備を整えていないだけです。何かを変更するのではなく、
待ってから再試行してください。
</Aside>

### `az vm run-command` 経由での Site CLI の操作

`/opt/bin/vpmu` は `admin` のログインシェルであるため、`az vm run-command` 経由でこれを呼び出せば、
SSH で到達したはずの対話型 Site CLI と同じものに到達できます。
同じビルドの使い捨て CE で検証済みです。`execcli docker-ps`、`execcli ip-link-show`、`health` は
いずれもこの方法で取得できました。

2 つの仕組みが必要であり、どちらも自明ではありません:

- **`vpmu` は PTY がないとパニックします** —
  `go-prompt … NewStandardInputParser: no such device or address`。PTY を割り当ててください。
- **コマンドテキストと Enter バイトは別々の書き込みでなければなりません。** 1 回の書き込みにすると、
  改行がリテラル文字としてバッファに入り、CLI は `unknown command "execcli\n"` と応答します。
  これはコマンドが存在しないかのように読めます。

対話型メニューには `configure`、`configure-generic-hardware`、`configure-network`、
`configure-http-proxy`、`diagnosis`、`health` が表示されます。**`execcli` は隠しコマンドです** —
このメニューには載っておらず、引数としてカタログのコマンド名を取ります。

<Aside type="note" title="この経路は使い捨て CE で検証済みであり、デモ環境では未検証です">
`run-command` 経路は、同じビルドと同じ構成で動作する使い捨ての CE で実施されました。
`ar-bgp-eastus01/02/03` に対しては再実行していないため、そこでの動作は実証済みではなく想定として
扱ってください。debug API 経路は *確かに* デモに対して検証済みです。
</Aside>
