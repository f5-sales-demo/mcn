SSH はアプライアンスの `admin` アカウントに到達します。このアカウントのログインシェルは Site CLI
（`/opt/bin/vpmu`）です。これは **オンボックスのコマンドサーフェス全体** への唯一のルートです —
[デバッグ API](../debug-api/) は 34 のコマンドを公開していますが、アプライアンス自体はその API には含まれていない多くのコマンドを提供しています。

```bash
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<operator-vm> admin@10.0.3.5
```

このコマンドラインの各部分はすべて重要な意味を持っており、次の 3 つのセクションでそれぞれが防ぐ障害を説明します。

<Aside type="caution" title="実行中のデプロイメントでこれを有効化すると VM が置き換えられます">
キーは cloud-init によって書き込まれ、cloud-init の `write_files` は **初回起動時のみ** 実行されます。
既存のノードでこれを有効化することは、それらを置き換えることを意味します。これにより現在、登録が行き詰まります：
古い登録が一意の `(tenant, cluster_name, hostname)` インデックスを保持し、置き換えられたノードは登録できず、`terraform plan` は終始「No changes」と報告します。
変更を計画する**前に**
[issue 674](https://github.com/f5-sales-demo/mcn/issues/674) を確認してください。後では手遅れです。
</Aside>

## API ではなく cloud-init がキーを書き込む理由

サイトオブジェクトの `admin_user_credentials.ssh_key` は、まさにこのためのフィールドのように見えます。
受け入れられ、読み返しにも残り、しかし何も設定しません。`vpm` はノードのローカルユーザーを管理しており、
このユーザーへの操作を拒否します — ノード自体のログに、単一起動中に 3 回記録されています：

```text
vpm  users.go:165: Won't do any change for user admin (internal skip)
```

その 1 行からすべてが導かれます。`/var/home/admin/.ssh` はサイトが `ONLINE` になる前後を問わず、決して存在しません。
`admin` のシャドウ最終変更日はイメージビルド日のままですが、`vesbkp` と `vesopcon` は現在の日付を示します。
これは `vpm` がその 2 つを設定し、`admin` をスキップしたためです。また `vpm` は `ssh_key` や `authorized_keys` についていかなる時点でもログを残しません。

そのため、ファイルは `vpm` の外部で書き込む必要があります。`admin` は uid 2202 であり、ノードイメージに焼き込まれているため、
cloud-init が実行される前から存在し、書き込み時に `owner: admin:admin` が解決されます —
`runcmd` も所有権の修正も不要です：

```yaml
- path: /var/home/admin/.ssh/authorized_keys
  permissions: "0600"
  owner: admin:admin
  content: |
    ${ssh_public_key}
```

`sshd` は常に受け入れる状態にありました。`sshd -T` は `pubkeyauthentication yes` を報告し、`admin` は
ノードに同梱されている両方の `sshd_config` ファイルの `AllowUsers` に記載されています。
有効化すべきものは何もありませんでした — ただファイルが存在していなかっただけです。

<Aside type="danger" title="admin_user_credentials を再追加せず、sshd_config も編集しないこと">
`admin_user_credentials` は `terraform/modules/xc-site` に組み込まれ、この証拠が収集された後に元に戻されました（#660、PR #663）。
これは埋めるべきギャップではありません。

`sshd_config` は登録時に置き換えられるため、編集内容は最も不都合なタイミングで破棄されます。
</Aside>

## 1 つのアドレスのみで応答する理由

`sshd` は `0.0.0.0:22` にバインドしていますが、ホストのネットワークスタックには **内部 (SLI)** アドレスのみが存在します。
eth0 は `a-i-eth0` にリネームされ、ホスト IP を持ちません — Argo データプレーンがそのインターフェースを所有します —
一方、eth1 と eth2 はホストスタック上に残り、そこで `sshd` がリッスンしています。

VNet 内の VM からプローブした場合：

```text
10.0.1.4     timed out             CE mgmt/SLO  (eth0)
10.0.2.4     timed out             CE external  (eth1)
10.0.3.5     OPEN                  CE internal/SLI
10.0.3.6     OPEN
10.0.3.7     OPEN
```

したがって、既知のノードアドレスへのプローブは、閉じたセキュリティグループが返すものとまったく同じ結果を返します。
何もブロックしていません；そのアドレスにはリスナーが存在しないのです。

CE のパブリックアドレスにもポート 22 のリスナーはありません。これが上記のコマンドが `-J` を使用する理由です：
SLI アドレスと同じサブネット内の VNet 内のオペレーター VM を経由します。

<Aside type="caution" title="自信を持って誤った答えを生み出す 2 つの測定ミス">
eth0、外部インターフェース、またはパブリックアドレスのポート 22 をプローブすると、ノードの SSH 状態に関わらずクローズと報告されるため、
まったく何も確認できません。SLI アドレスだけが応答します。

また、企業のワークステーションからのプローブでは、実際にはクローズなポートが **オープン** と報告されることがあります：
Netskope は一般的なポートで TCP ハンドシェイクを自ら完了させます。CE パブリックアドレスのポート 80 および 443 は
ワークステーションからはオープンと読み取れますが、VNet 内からプローブするとクローズです。VNet 内の VM からプローブしてください。
</Aside>

## Site CLI にはターミナルとキャリッジリターンが必要

`admin` のログインシェルはシェルではありません。これは `go-prompt` アプリケーションであり、
ターミナルをロウモードにして行ではなくキーストロークを読み取ります。4 つの結果があり、それぞれが異なる問題のように見える形で失敗します：

| 仕組み | それなしに起こること |
| --- | --- |
| ターミナルを割り当てる（`ssh -tt`） | `go-prompt.NewStandardInputParser` から `panic: no such device or address` が発生し、アプライアンスがクラッシュしたように見える |
| Enter にラインフィードではなくキャリッジリターンを送信する | 行が送信されず、何も表示されないまま入力終端でセッションが閉じる |
| 標準入力を開いたままにする | コマンドがレンダリングされる前に接続が終了するため、正常なコマンドがサイレントに見える |
| コマンドテキストと Enter バイトを**個別に**書き込む | 改行がリテラル文字としてバッファに入り、CLI が `unknown command` と応答するため、コマンドが存在しないように見える |

そのため、`ssh host 'some-command'` は機能しません：引数は無視され、インタラクティブプロンプトが起動します。
ターミナルとして操作するか、使用しないかのどちらかです。
`scripts/sitecli_ssh_harvest.py` がリファレンス実装です。

ログインバナーにはノードの登録状態が表示されます。これは起動中のノードと壊れたノードを最も素早く判別する方法です：

```text
Registration Status: PROVISIONING
SLO IP: 10.0.1.4/26
```

## キーペアの提供

<Steps>

1. キーペアがない場合は生成します。RSA ではなく Ed25519 を使用します：短く、アプライアンスの `sshd` でも受け入れられます。

   ```bash
   ssh-keygen -t ed25519 -C "ce-operator" -f ~/.ssh/id_ed25519
   ```

2. デプロイメントが **公開** 鍵を参照するように設定します。ルートモジュールはファイルを一度読み込み、
   文字列をすべてのノードに渡します：

   ```hcl
   # terraform/terraform.tfvars
   ssh_public_key_path = "~/.ssh/id_ed25519.pub"
   ```

   `ssh_public_key` は代わりに素材をインラインで受け取ります。これはプランテストが使用する方法です。
   秘密鍵はワークステーションから外に出ることはありません。

3. 適用します。既存のデプロイメントでは CE VM が置き換えられるため、このページの冒頭の警告を先に読んでください。

</Steps>

<Aside type="note" title="VM 自身の admin_ssh_key は別のものです">
`modules/ce-node` の `azurerm_linux_virtual_machine.admin_ssh_key` は、アプライアンスの `admin` アカウントではなく、
Azure VM の管理者を認可します。Site CLI へのアクセスは付与されず、これが設定されていても CE SSH が設定されている証拠にはなりません。
</Aside>

## これが原因でないもの

これらはそれぞれ、ルートがまだ不可能と考えられていた間にテストされ、除外されました。
いずれも 1 日を費やすに十分な説得力があります。

| 原因ではないもの | 除外された方法 |
| --- | --- |
| 資格情報は作成時にのみ適用される | `sshd` は初回起動から約 90 秒後に起動し、サイトオブジェクトが存在する前です。`admin_user_credentials` は `ReplaceSpecType` にも存在し、その場で適用されます。 |
| `block_all_services` | 管理アドレスのポート 22 クローズは、サービスがブロックされているかどうかに関わらず同一です。 |
| キーの末尾の改行 | 両方でテスト済み、変化なし。cloud-init はそれでもこれを除去します。リテラルブロックは他の場合、2 番目の空行をレンダリングするためです。 |
| ピン留めされた旧バージョンの CE ソフトウェア | OpenSSH 9.9 を実行しているものを含む 3 つのビルドで再現しました。 |
| `admin_password` の欠如 | ゼロから作成した CE で `ssh_key` と共に `admin_password` を設定しても何も変わりませんでした。 |

<Aside type="caution" title="識別子のように見えるが実際はそうでない 2 つの API フィールド">
`gc_spec.admin_ssh_key` は、`admin_password` を設定している 20 サイトを含む **テナント内の全 88 サイト** で空です。
動作しているサイトと動作していないサイトを比較しても何もわかりません。どこでも空だからです。

`registrations_by_site` はそのフィールドを完全に省略し、`None` を返します。これは「設定されていない」ではなく
「報告されていない」と読めます。
</Aside>

<Aside type="caution" title="新規作成されたサイトは、operate API が応答するまでに約半時間かかります">
新しいサイトが `ONLINE` を報告してから約 25〜30 分間、`vpm/debug` エンドポイントは
`The requested URL was rejected` と書かれた BIG-IP の `503` ページを返します。
これは Web アプリファイアウォール (WAF) のブロック、またはトークンの失効のように見えますが、どちらでもありません：
サイトはまだリレーする準備ができていないのです。何かを変更するのではなく、待機して再試行してください。

SSH にはそのようなウォームアップはありません。`sshd` が起動するとすぐに応答します。
これが、ノードがまだ登録中でも機能するルートである理由です。
</Aside>
