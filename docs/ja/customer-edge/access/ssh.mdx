このデプロイの 1 つの CE から 2026-07-28 にキャプチャされました。`sitecli/capture-manifest.json`
はどのノードかを記録しており、`scripts/capture-sitecli.sh --check` はライブ CE に対してコマンド
サーフェスを再検証します。

SSH はアプライアンスの `admin` アカウントに到達します。このアカウントのログインシェルは Site CLI
(`/opt/bin/vpmu`) です。これは**ボックス上のフルコマンドサーフェス**への唯一のルートです —
[デバッグ API](../debug-api/) は 34 のコマンドを公開しており、アプライアンス自体にはその API に
まったく含まれていない多くのコマンドがあります。

```bash
cd terraform
SLI=$(terraform output -json ce_sli_private_ips | jq -r '.eastus01')
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<operator-vm> "admin@$SLI"
```

そのコマンドラインのすべての部分は重要であり、次の 3 つのセクションでそれぞれが防ぐ
障害を説明します。

ランディングするシェルプロンプトはありません: `admin` のログインシェル**は** Site CLI
そのものであり、`>>>` プロンプトに直接到達します。そこで `execcli <name>` としてオンボックスコマンドを
実行してください — [オンボックスコマンド](../../commands/on-box/) を参照してください。

<Aside type="danger" title="内部アドレスを必ず参照してください — 前のセッションから引き継がないでください">
Azure は再構築のたびに内部サブネットを再割り当てし、ノード順通りとは限りません。直近の
再構築後、`f5-xc-ce-vm-01`、`-02`、`-03` はそれぞれ `10.0.3.7`、`10.0.3.5`、`10.0.3.4` を
保持しています。以前のビルドでは異なる順序でした。また、テストクライアントの NIC は同じサブネットに
あり、以前 CE が保持していたアドレスを保持している場合があります。したがって、記憶しているアドレスに
接続すると、誤ったノード、CE ではない VM、またはどこにも到達できない可能性があります — そして
最後のケースは「SSH が有効になっていない」と同一に見えます。

`terraform output -json ce_sli_private_ips` がマッピングです。手元に状態がない場合、アドレスは
変わりますが NIC 名は安定しています:

```bash
az network nic show -g "$(terraform output -raw resource_group_name)" \
  -n "$(terraform output -json ce_vm_names | jq -r '.eastus01')-internal-nic" \
  --query ipConfigurations[0].privateIPAddress -o tsv
```

</Aside>

<Aside type="caution" title="ブートストラップのみ — 既存の CE は再作成なしに SSH を有効にできません">
cloud-init の `write_files` は**初回起動時に一度だけ**実行されます。その後、ノードに
`/etc/cloud/cloud-init.disabled` マーカーが存在し、cloud-init は再度実行されません。

したがって、実行中の CE へのインプレースパスはありません。`custom_data` は Azure では
置き換え専用であり、既存のデプロイにこれを採用すると**すべての CE VM が置き換えられます**。
すでに稼働しているノードへのオペレーター SSH の付与は、設定変更ではなく再構築です —
そして次の警告はその再構築にかつてかかっていたコスト、およびそれがもはやかからない理由です。
</Aside>

<Aside type="caution" title="CE VM の置き換えはかつて登録を永続的に詰まらせていました — これは修正済みであり、サイトオブジェクトが VM に結合されている理由です">
再構築を計画する前に知っておく価値があります。障害の形状がプランに見られる結合を説明するためです。

かつては、破棄されたノードの登録がコントロールプレーンの一意な `(tenant, cluster_name, hostname)`
インデックスを保持していたため、置き換えノードの登録が `UniqueSecondaryIndexViolationError` で
拒否され、永遠に再試行されていました。登録を削除するだけでは不十分でした: 残った
`StatusObject` がワークロードリクエストに対して `500` を返し、その時点では各ノードが削除した
登録にピン留めされた `registration-obj.yml` を永続化していたため、自己回復なしに `404` でループ
しました。回復には 2 回の完全な再構築が必要でした。その間ずっと `terraform plan` は
**「変更なし」** と報告していました。Terraform の観点からは望ましい状態が達成されていたためです。

[Issue 674](https://github.com/f5-sales-demo/mcn/issues/674) は
[PR 693](https://github.com/f5-sales-demo/mcn/pull/693) によってクローズされました。
`modules/xc-site` は CE VM インスタンスを `replace_triggered_by` に指定するようになりました。
これにより VM を置き換えるとサイトオブジェクトも置き換えられ、サイトを削除するとその登録も一緒に
削除されます — インデックスキーは置き換えノードが起動する前に解放されます。それ以来、フリートは
ゼロから再構築され、3 つのサイトすべてが介入なしに `ONLINE` になりました。

結合は仮定ではなく観察可能です。各サイトは VM の*インスタンス* ID にバインドされており、
一致する登録は `infra.instance_id` と同じ値を報告します:

```bash
cd terraform && terraform output -json ce_bound_instance_ids
```

2 つの間の不一致は、サイトがもはや存在しないノードにまだバインドされていることを意味します。
これは再構築された CE が登録から抜け出せない状態です。登録の半分を読み取るには直接 API 呼び出しが
必要です — プロバイダーの Issue
[1376](https://github.com/f5-sales-demo/terraform-provider-xcsh/issues/1376) がそれを
データソースに追加するものです。
</Aside>

## cloud-init がキーを書き込む理由、API ではない理由

サイトオブジェクトの `admin_user_credentials.ssh_key` はまさにこのためのフィールドのように見えます。
受け入れられ、読み返しても残り、しかし何も設定しません。`vpm` はノードのローカルユーザーを所有
しており、このユーザーには手を加えません — ノード自身のログから、1 回のブートで 3 回:

```text
vpm  users.go:165: Won't do any change for user admin (internal skip)
```

それ以外はすべてその 1 行から続きます。`/var/home/admin/.ssh` は、サイトが `ONLINE` になる前も
後も存在しません。`admin` のシャドウ最終変更日はイメージのビルド日のままですが、`vesbkp` と
`vesopcon` は現在の日付を示しています。`vpm` がその 2 つを設定し、`admin` をスキップしたためです。
そして `vpm` は `ssh_key` や `authorized_keys` については一切ログに記録しません。

そのため、ファイルは `vpm` の外部で書き込む必要があります。`admin` は uid 2202 で、ノードイメージに
組み込まれているため、cloud-init が実行される前から存在しており、`owner: admin:admin` は書き込み時に
解決されます — `runcmd` も所有権の修正も不要です:

```yaml
- path: /var/home/admin/.ssh/authorized_keys
  permissions: "0600"
  owner: admin:admin
  content: |
    ${ssh_public_key}
```

`sshd` は常に受け入れる態勢にありました。`sshd -T` は `pubkeyauthentication yes` を報告し、
`admin` はノードに付属している両方の `sshd_config` ファイルの `AllowUsers` に含まれています。
有効にするものは何もありませんでした — ファイルが欠けていただけです。

<Aside type="danger" title="admin_user_credentials を再追加しないでください。また sshd_config を編集しないでください">
`admin_user_credentials` は `terraform/modules/xc-site` に組み込まれ、この証拠が収集された後に
元に戻されました (#660、PR #663)。これは埋められるべきギャップではありません。

`sshd_config` は登録中に置き換えられるため、編集は最も都合の悪いタイミングで破棄されます。
</Aside>

## 1 つのアドレスのみで応答する理由

`sshd` は `0.0.0.0:22` にバインドしていますが、`sshd` が応答するのは**内部 (SLI)**
アドレスだけです。eth0 は `a-i-eth0` に名前変更されており、ホスト IP を持ちません —
Argo データプレーンがそのインターフェースを所有しており、それが持つはずだった
management/SLO アドレスは代わりに `vhost0` に表示されます。他の 2 つの NIC は
それぞれの名前でホストスタックに残ります。

VNet 内の VM から 1 つの CE に対してプローブした結果:

```text
management/SLO address    タイムアウト
external address          タイムアウト
internal/SLI address      OPEN     SSH-2.0-OpenSSH_8.7
an unused address         タイムアウト    (control)
```

したがって、ノードを認識しているアドレスに対するプローブは、閉じたセキュリティグループが
返すものとまったく同じ結果を返します。何もブロックしているわけではなく、そのアドレスに
リスナーがないだけです。

<Aside type="caution" title="ゲストインターフェース名を読んでどのサブネットにいるかを判断しないでください">
`eth1` と `eth2` のどちらが内部アドレスを持つかは、**同じデプロイのノード間で異なります**。
3 つの CE すべてからライブで読み取った結果:

```text
f5-xc-ce-vm-01    eth1 -> external      eth2 -> internal/SLI
f5-xc-ce-vm-02    eth2 -> external      eth1 -> internal/SLI
f5-xc-ce-vm-03    eth1 -> external      eth2 -> internal/SLI
```

すべてのノードで成立するのは 2 点のみです: `a-i-eth0` はアドレスを持たず、`vhost0` が
management/SLO アドレスを持ちます。それ以外については、インターフェース名ではなく
[`ip addr`](../../commands/network/ip/) の出力のアドレスで照合してください。
</Aside>

CE のパブリックアドレスにも 22 番のリスナーはありません。そのため上記のコマンドが `-J` を
使用しています: SLI アドレスと同じサブネット内の VNet 内のオペレーター VM です。このデプロイは
その目的のために 1 つをビルドしています —
`terraform output -raw client_vm_name` でその名前を確認できます。

<Aside type="caution" title="-J はジャンプレッグにオプションを渡しません">
コマンドラインに指定されたオプションは最終ホップに適用されます。`-J` と一緒に
`-o UserKnownHostsFile=/dev/null` を指定しても、*ジャンプ*ホストの実際の `known_hosts` を
参照して書き込みます。これは、再構築したフリートをそこから除外しようとしている場合に
驚きとなります。それが重要な場合は最初のホップを明示的に指定してください:

```bash
ssh -tt -o ProxyCommand="ssh -W %h:%p -o UserKnownHostsFile=/dev/null azureuser@<operator-vm>" \
    -o UserKnownHostsFile=/dev/null -i ~/.ssh/id_ed25519 "admin@$SLI"
```

</Aside>

<Aside type="caution" title="自信を持って誤った答えを生む 2 つの測定ミス">
eth0、外部インターフェース、またはパブリックアドレスをポート 22 でプローブすると、
ノードの SSH 状態に関わらずクローズと報告されるため、何も判断できません。応答するのは
SLI アドレスのみです。

また、企業ワークステーションからのプローブは、実際にはクローズしているポートを**オープン**と
報告することがあります: Netskope が一般的なポートで TCP ハンドシェイクを自ら完了します。
ポート 80 と 443 は、ワークステーションから CE のパブリックアドレスにオープンとして表示されますが、
VNet 内からプローブするとクローズです。VNet 内の VM からプローブしてください。
</Aside>

## Site CLI はターミナルとキャリッジリターンを必要とします

`admin` のログインシェルはシェルではありません。`go-prompt` アプリケーションであり、
ターミナルをローモードにして行ではなくキーストロークを読み取ります。それぞれが異なる問題のように
見える失敗をする 4 つの結果があります:

| 仕組み | それなしで起こること |
| --- | --- |
| ターミナルを割り当てる (`ssh -tt`) | `go-prompt.NewStandardInputParser` から `panic: no such device or address` が発生し、アプライアンスがクラッシュしたように見える |
| Enter にラインフィードではなくキャリッジリターンを送信する | 行が送信されず、何も出力されないまま入力終了でセッションが閉じる |
| 標準入力を開いたままにする | コマンドがレンダリングされる前に接続が終了するため、正常に動作するコマンドがサイレントに見える |
| コマンドテキストと Enter バイトを**別々に**書き込む | 改行がバッファにリテラル文字として入り、CLI が `unknown command` と答えるため、コマンドが存在しないように見える |

したがって `ssh host 'some-command'` は機能しません: 引数は無視され、インタラクティブプロンプトが
とにかく開始されます。ターミナルとして駆動するか、まったく使用しないかのどちらかです。
`scripts/sitecli_ssh_harvest.py` がリファレンス実装です。

<Aside type="caution" title="'no such device or address' と読めるパニックは認証が成功したことを意味します">
`vpmu` はログイン**後に**、接続するターミナルが見つからないときにこれを発行します。クラッシュとして
読むと最悪の結果のように見えますが、実際には成功直前の最後のエラーです。`-tt` を追加して
再接続してください。
</Aside>

<Aside type="caution" title="CE を置き換えるとホストキーが変わります">
置き換えノードは同じアドレスで異なるホストキーを提示するため、次の接続で `REMOTE HOST IDENTIFICATION HAS CHANGED` と警告され拒否されます。そのアドレスの古いエントリをクリアして再接続してください。SSH の付与自体が VM を置き換えるため、採用後の最初の接続でこれが発生することを想定してください。
</Aside>

## バナーは無料のヘルスチェックです

何も入力する前に、ログインバナーはすでにコマンドで確認するはずだったいくつかの質問に答えています。
`f5-xc-ce-vm-01` から、ASCII アートとパブリック IP は省略:

```text
UNAUTHORIZED ACCESS TO THIS DEVICE IS PROHIBITED
All actions performed on this device are audited

Using https://register.ves.volterra.io
OS: rhel-9.2024.6
Memory: 32768MiB
Storage: sda: 31GiB
CPU: Model: Intel(R) Xeon(R) Platinum 8272CL CPU @ 2.60GHz | CPUs: 8
Software: crt-20250613-3382
DNS: 168.63.129.16: OK
NTP: Synced
Uptime: 0 days, 5 hours, 20 minutes
Registration Status: PROVISIONED
SLO IP: 10.0.1.4/26
WELCOME IN SITE CLI
```

`Registration Status` は、まだ起動中のノード (`PROVISIONING`) と完了したノード (`PROVISIONED`) を
区別します。`Software` はどのコマンドが存在するかを決定するビルド文字列です。`DNS` と `NTP` は
登録を最初に破壊する 2 つの依存関係をカバーしているため、オンラインにならなかったノードは通常
すでにここで理由を伝えています —
[`chronyc-sources`](../../commands/network/chronyc-sources/) や
[`dig`](../../commands/network/dig/) が必要になる前に。

## キーペアの提供

<Steps>

1. まだキーペアがない場合は生成します。RSA ではなく Ed25519 を使用してください: より短く、
   アプライアンスの `sshd` でも受け入れられます。

   ```bash
   ssh-keygen -t ed25519 -C "ce-operator" -f ~/.ssh/id_ed25519
   ```

2. デプロイメントに**公開**側を指定します。ルートモジュールはファイルを一度読み込み、
   文字列をすべてのノードに渡します:

   ```hcl
   # terraform/terraform.tfvars
   ssh_public_key_path = "~/.ssh/id_ed25519.pub"
   ```

   `ssh_public_key` は代わりにマテリアルをインラインで受け取ります。これがプランテストで
   使用されるものです。秘密鍵はワークステーションから出ません。

3. 適用します。このページの上部にある警告を先に読んでください — 既存のデプロイでは
   CE VM が置き換えられます。

</Steps>

<Aside type="note" title="VM 自身の admin_ssh_key は別のものです">
`modules/ce-node` の `azurerm_linux_virtual_machine.admin_ssh_key` は、アプライアンスの
`admin` アカウントではなく Azure VM 管理者を認可します。これは Site CLI アクセスを付与せず、
設定されていることは CE SSH が設定されている証拠にはなりません。
</Aside>

## これは何ではないか

以下のそれぞれは、ルートがまだ不可能と信じられていた間にテストされ、除外されました。
それぞれは 1 日を費やすのに十分なほど妥当に見えます。

| 原因ではない | 除外された方法 |
| --- | --- |
| 資格情報は作成時のみ適用される | `sshd` はサイトオブジェクトが存在する前の最初のブートから約 90 秒後に起動します。`admin_user_credentials` は `ReplaceSpecType` にも存在し、インプレースで適用されます。 |
| `block_all_services` | management アドレスのポート 22 クローズは、サービスがブロックされているかどうかに関わらず同一です。 |
| キーの末尾の改行 | 両方でテストされ、変化なし。リテラルブロックは別の空行をレンダリングするため、cloud-init はそれでも削除します。 |
| ピン留めされた古い CE ソフトウェア | OpenSSH 9.9 を実行しているものを含む 3 つのビルドで再現されました。 |
| `admin_password` の欠如 | ゼロから始める CE で `ssh_key` と並べて `admin_password` を設定しても変化なし。 |

<Aside type="caution" title="判別子のように見えるが実際はそうでない 2 つの API フィールド">
`gc_spec.admin_ssh_key` は `f5-sales-demo` の**58 サイトすべて**で空または不在です —
`admin_user_credentials.ssh_key` を設定している 2 つのサイトを含みます。動作しているサイトと
動作していないサイトの間で比較しても何もわかりません。資格情報が設定されているサイトでも空と
読み取れるためです。

`registrations_by_site` はフィールドを完全に省略し、`None` を返します。これは「設定されていない」
ではなく「報告されていない」と読めます。
</Aside>

<Aside type="caution" title="新しく作成されたサイトはデバッグ API が応答するまで約 30 分かかります">
新しいサイトが `ONLINE` と報告してから約 25 〜 30 分間、`vpm/debug` エンドポイントは
`The requested URL was rejected` と読める BIG-IP の `503` ページを返します。これは Web
アプリファイアウォール (WAF) のブロック、またはトークンの失効のように見えますが、どちらでもありません:
サイトはまだリレーの準備ができていません。何かを変更するのではなく、待機して再試行してください。

SSH にはそのようなウォームアップはありません。`sshd` が起動するとすぐに応答します。
これがノードがまだ登録中の間も機能するルートである理由です。
</Aside>
