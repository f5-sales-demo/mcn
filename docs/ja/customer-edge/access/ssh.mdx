SSH はアプライアンスの `admin` アカウントに接続します。そのログインシェルは Site CLI
(`/opt/bin/vpmu`) です。これは **オンボックスのコマンド機能全体** に到達できる唯一の経路です —
[debug API](../debug-api/) が公開するのは 34 コマンドですが、アプライアンス自体はその API には
まったく存在しない多数のコマンドを提供しています。

```bash
cd terraform
SLI=$(terraform output -json ce_sli_private_ips | jq -r '.eastus01')
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<operator-vm> "admin@$SLI"
```

このコマンドラインのすべての部分に意味があり、続く 3 つのセクションでそれぞれが
どの障害を防いでいるのかを説明します。

<Aside type="danger" title="内部アドレスは必ず調べること — 以前のセッションの値を流用してはならない">
Azure は再構築のたびに内部サブネットを再割り当てし、しかもノード順ではありません。直近の
再構築後、`f5-xc-ce-vm-01`、`-02`、`-03` はそれぞれ `10.0.3.7`、`10.0.3.5`、`10.0.3.4` を
保持しています。以前のビルドではまったく別の順序でしたし、テストクライアントの NIC も同じ
サブネットにあり、かつて CE が保持していたアドレスを持っていたことがあります。したがって記憶した
アドレスに接続すると、誤ったノードに着地するか、CE ではない VM に着地するか、どこにも到達しません —
そして最後のケースは「SSH が有効化されていない」場合とまったく同じに見えます。

`terraform output -json ce_sli_private_ips` がそのマッピングです。state が手元にない場合、
アドレスは安定しませんが NIC 名は安定しています:

```bash
az network nic show -g rg-mcn-ce-ha-rmordasiewicz \
  -n f5-xc-ce-vm-01-internal-nic \
  --query ipConfigurations[0].privateIPAddress -o tsv
```

</Aside>

<Aside type="caution" title="ブートストラップ時のみ — 既存の CE は再作成なしに SSH を得られない">
cloud-init の `write_files` は **初回ブート時に一度だけ** 実行されます。その後はノード上に
`/etc/cloud/cloud-init.disabled` マーカーが存在し、cloud-init は再実行されません。

したがって稼働中の CE に対するインプレースの経路は存在しません。`custom_data` は Azure では
置き換え専用であり、既存デプロイメントでこれを採用すると **すべての CE VM が置き換えられます**。
すでに稼働中のノードにオペレーター SSH を付与することは、構成変更ではなく再構築です —
そして次の警告は、その再構築がかつてどれだけのコストを要したか、そしてなぜもう要さないのかについてです。
</Aside>

<Aside type="caution" title="CE VM の置き換えはかつて登録を恒久的に詰まらせた — これは修正済みであり、サイトオブジェクトが VM に結合されている理由でもある">
再構築を計画する前に知っておく価値があります。障害の形状が、プラン上で目にする結合関係を説明するからです。

かつては、破棄されたノードの登録がコントロールプレーンの一意な
`(tenant, cluster_name, hostname)` インデックスを保持し続けたため、置き換えノードの登録が
`UniqueSecondaryIndexViolationError` で拒否され、永久にリトライされていました。登録を削除するだけでは
不十分でした。残存する `StatusObject` がワークロードリクエストに対して `500` を返し、その時点で
各ノードは削除した登録に固定する `registration-obj.yml` を永続化していたため、自己回復なしに `404` を
ループしていました。復旧には 2 回のフル再構築を要しました。その間ずっと `terraform plan` は
**"No changes"** を報告していました。Terraform の観点からは望ましい状態に到達していたからです。

[Issue 674](https://github.com/f5-sales-demo/mcn/issues/674) は
[PR 693](https://github.com/f5-sales-demo/mcn/pull/693) によりクローズされています。`modules/xc-site` は
現在、`replace_triggered_by` で CE VM インスタンスを指定しており、VM を置き換えるとサイトオブジェクトも
置き換えられ、サイトの削除はその登録も一緒に削除します — 置き換えノードがブートする前にインデックスキーが
解放されます。以降、フリートはゼロから再構築され、3 つのサイトすべてが介入なしに `ONLINE` になりました。

この結合関係は仮定ではなく観測可能です。各サイトは VM *インスタンス* id にバインドされており、
対応する登録は同じ値を `infra.instance_id` として報告します:

```bash
cd terraform && terraform output -json ce_bound_instance_ids
```

両者の不一致は、サイトがもはや存在しないノードにまだバインドされていることを意味し、これは
再構築された CE が決して登録し直せない状態です。登録側の値を読むには依然として直接的な API 呼び出しが
必要です — プロバイダーの issue
[1376](https://github.com/f5-sales-demo/terraform-provider-xcsh/issues/1376) がこれをデータソースに
載せるものです。
</Aside>

## cloud-init が鍵を書き込み、API が書き込まない理由

サイトオブジェクトの `admin_user_credentials.ssh_key` はまさにこの用途のフィールドに見えます。
受け入れられ、読み戻しても残りますが、何も構成しません。`vpm` はノードのローカルユーザーを所有しており、
このユーザーには手を触れることを拒否します — ノード自身のログから、1 回のブート中に 3 回:

```text
vpm  users.go:165: Won't do any change for user admin (internal skip)
```

その他すべてはこの 1 行から導かれます。`/var/home/admin/.ssh` は、サイトが `ONLINE` になる前も
後も、決して存在しません。`admin` の shadow の最終変更日はイメージのビルド日のままである一方、
`vesbkp` と `vesopcon` は現在の日付を示します。`vpm` がその 2 つを設定し、`admin` をスキップしたためです。
そして `vpm` は `ssh_key` や `authorized_keys` について、いかなる時点でも何もログに残しません。

したがってファイルは `vpm` の外側で書き込む必要があります。`admin` は uid 2202 でノードイメージに
焼き込まれているため、cloud-init 実行前から存在し、`owner: admin:admin` は書き込み時に解決されます —
`runcmd` も所有権の後処理も不要です:

```yaml
- path: /var/home/admin/.ssh/authorized_keys
  permissions: "0600"
  owner: admin:admin
  content: |
    ${ssh_public_key}
```

`sshd` は常に受け入れる用意がありました。`sshd -T` は `pubkeyauthentication yes` を報告し、
`admin` はノードに同梱される両方の `sshd_config` ファイルの `AllowUsers` に含まれています。
有効化すべきものは元から何もなく — 欠けていたのはファイルだけでした。

<Aside type="danger" title="admin_user_credentials を再追加しないこと、sshd_config を編集しないこと">
`admin_user_credentials` は `terraform/modules/xc-site` に組み込まれましたが、この証拠が
収集された時点で差し戻されました (#660、PR #663)。埋めるべきギャップではありません。

`sshd_config` は登録中に置き換えられるため、それへの編集は最も都合の悪いタイミングで破棄されます。
</Aside>

## 1 つのアドレスでのみ応答する理由

`sshd` は `0.0.0.0:22` にバインドしますが、`sshd` が応答する形でホストのネットワークスタック上に
あるのは **内部 (SLI)** アドレスだけです。eth0 は `a-i-eth0` にリネームされ、ホスト IP をまったく
持ちません — そのインターフェイスは Argo データプレーンが所有しており、本来そこに載るはずの
管理/SLO アドレスは代わりに `vhost0` に現れます。残る 2 つの NIC は、それぞれの名前でホストスタック上に
留まります。

VNet 内の VM から 1 台の CE に対してプローブした結果:

```text
management/SLO address    timed out
external address          timed out
internal/SLI address      OPEN     SSH-2.0-OpenSSH_8.7
an unused address         timed out    (control)
```

したがって、あなたがノードを識別しているアドレスに対するプローブは、閉じられたセキュリティグループが
返すものとまったく同じ結果を返します。何もブロックしていません。そのアドレスにリスナーが存在しないのです。

<Aside type="caution" title="どのサブネット上にいるかを判断するためにゲストのインターフェイス名を読まないこと">
`eth1` と `eth2` のどちらが内部アドレスを持つかは、**この同一デプロイメント内のノード間でも異なります**。
3 台の CE すべてからライブで読み取った結果:

```text
f5-xc-ce-vm-01    eth1 -> external      eth2 -> internal/SLI
f5-xc-ce-vm-02    eth2 -> external      eth1 -> internal/SLI
f5-xc-ce-vm-03    eth1 -> external      eth2 -> internal/SLI
```

すべてのノードで成り立つのは 2 点だけです: `a-i-eth0` はアドレスを持たず、`vhost0` が
管理/SLO アドレスを持つこと。それ以外については、インターフェイス名ではなく
[`ip addr`](../../commands/network/ip/) の出力にあるアドレスで照合してください。
</Aside>

CE のパブリックアドレスにも 22 番のリスナーはありません。だからこそ上記のコマンドは `-J` を
経由しています。VNet 内、SLI アドレスと同じサブネットにあるオペレーター VM です。このデプロイメントでは
`ar-ecmp-client` がその VM です。

<Aside type="caution" title="-J はあなたのオプションを踏み台側に渡さない">
コマンドラインで指定したオプションは最終ホップに適用されます。したがって `-J` と併せて
`-o UserKnownHostsFile=/dev/null` を指定しても、*踏み台* ホストについては実際の `known_hosts` を
参照し、書き込みます。再構築されたフリートをそこから排除しようとしている場合、これは意外な点です。
それが重要な場合は、最初のホップを明示的に記述してください:

```bash
ssh -tt -o ProxyCommand="ssh -W %h:%p -o UserKnownHostsFile=/dev/null azureuser@<operator-vm>" \
    -o UserKnownHostsFile=/dev/null -i ~/.ssh/id_ed25519 "admin@$SLI"
```

</Aside>

<Aside type="caution" title="自信を持って誤った答えを出す 2 つの計測ミス">
eth0、外部インターフェイス、またはパブリックアドレスの 22 番ポートをプローブすると、ノードの
SSH 状態にかかわらず closed と報告されるため、何も判断できません。応答するのは SLI アドレスだけです。

また、企業のワークステーションからのプローブは、閉じているポートを **open** と報告することがあります:
Netskope が一般的なポートについて TCP ハンドシェイクを自ら完了させるためです。ワークステーションからは
CE のパブリックアドレスの 80 番と 443 番が open と読めますが、VNet 内からプローブすると閉じています。
VNet 内の VM からプローブしてください。
</Aside>

## Site CLI にはターミナルとキャリッジリターンが必要

`admin` のログインシェルはシェルではありません。`go-prompt` アプリケーションであり、ターミナルを
raw モードにして、行ではなくキーストロークを読み取ります。4 つの帰結があり、それぞれが別の問題に
見える形で失敗します:

| 仕組み | それがない場合に起こること |
| --- | --- |
| ターミナルを割り当てる (`ssh -tt`) | `go-prompt.NewStandardInputParser` からの `panic: no such device or address`。アプライアンスがクラッシュしたように読める |
| Enter にラインフィードではなくキャリッジリターンを送る | 行が送信されず、何も出力しないまま入力終端でセッションが閉じる |
| 標準入力を開いたままにする | コマンドが描画される前に接続が終了するため、動作しているコマンドが無反応に見える |
| コマンドテキストと Enter バイトを **別々に** 書き込む | 改行がリテラル文字としてバッファに入り、CLI は `unknown command` と応答する。コマンドが存在しないかのように読める |

したがって `ssh host 'some-command'` は機能しません。引数は無視され、いずれにせよ対話型プロンプトが
起動します。ターミナルとして駆動するか、まったく使わないかのどちらかです。
`scripts/sitecli_ssh_harvest.py` がリファレンス実装です。

<Aside type="caution" title="'no such device or address' と読める panic は認証が成功したことを意味する">
`vpmu` はログイン **後** に、アタッチするターミナルが見つからないときにこれを出力します。クラッシュとして
読むと最悪の結果に見えますが、実際には成功の直前の最後のエラーです。`-tt` を追加して再接続してください。
</Aside>

<Aside type="caution" title="CE を置き換えるとホスト鍵が変わる">
置き換えノードは同じアドレスで異なるホスト鍵を提示するため、次回の接続で
`REMOTE HOST IDENTIFICATION HAS CHANGED` と警告され、拒否されます。そのアドレスの古いエントリを
削除して再接続してください。SSH を付与すること自体が VM を置き換えるため、採用後の最初の接続で
これが起きることを想定してください。
</Aside>

## バナーは無料のヘルスチェック

何かを入力する前に、ログインバナーがすでに、そうでなければコマンドを費やして調べるであろう
いくつかの疑問に答えています。`f5-xc-ce-vm-01` からの出力（アスキーアートとパブリック IP は省略）:

```text
UNAUTHORIZED ACCESS TO THIS DEVICE IS PROHIBITED
All actions performed on this device are audited

Using https://register.ves.volterra.io
OS: rhel-9.2024.6
Memory: 32768MiB
Storage: sda: 31GiB
CPU: Model: Intel(R) Xeon(R) Platinum 8272CL CPU @ 2.60GHz | CPUs: 8
Software: crt-20250613-3382
DNS: 168.63.129.16: OK
NTP: Synced
Uptime: 0 days, 5 hours, 20 minutes
Registration Status: PROVISIONED
SLO IP: 10.0.1.4/26
WELCOME IN SITE CLI
```

`Registration Status` は、まだ起動中のノード (`PROVISIONING`) と完了したノード (`PROVISIONED`) を
区別します。`Software` はどのコマンドが存在するかを決めるビルド文字列です。`DNS` と `NTP` は
登録を最初に壊す 2 つの依存関係をカバーしているため、オンラインにならなかったノードは通常すでに
ここで理由を伝えています — [`chronyc-sources`](../../commands/network/chronyc-sources/) や
[`dig`](../../commands/network/dig/) が必要になる前に。

## キーペアの提供

<Steps>

1. まだ持っていない場合は、キーペアを生成します。RSA ではなく Ed25519 を使用します: 短く、
   アプライアンスの `sshd` に受け入れられます。

   ```bash
   ssh-keygen -t ed25519 -C "ce-operator" -f ~/.ssh/id_ed25519
   ```

2. デプロイメントに **公開** 鍵側を指定します。ルートモジュールがファイルを一度読み取り、
   その文字列をすべてのノードに渡します:

   ```hcl
   # terraform/terraform.tfvars
   ssh_public_key_path = "~/.ssh/id_ed25519.pub"
   ```

   `ssh_public_key` は代わりに鍵素材をインラインで受け取ります。プランのテストではこちらを使用します。
   秘密鍵側はワークステーションから決して外に出ません。

3. 適用します。まずこのページ冒頭の警告を読んでください — 既存のデプロイメントではこれにより
   CE VM が置き換えられます。

</Steps>

<Aside type="note" title="VM 自身の admin_ssh_key は別物">
`modules/ce-node` の `azurerm_linux_virtual_machine.admin_ssh_key` は Azure VM の管理者を
認可するものであり、アプライアンスの `admin` アカウントではありません。Site CLI へのアクセスは
付与されず、これが設定されていることは CE SSH が構成されている証拠にはなりません。
</Aside>

## これではないもの

以下はいずれも、この経路がまだ不可能だと考えられていた間にテストされ、除外されたものです。
いずれも 1 日を費やすには十分にもっともらしいものです。

| 原因ではないもの | どのように除外されたか |
| --- | --- |
| クレデンシャルは作成時のみ適用される | `sshd` は初回ブートの約 90 秒後、サイトオブジェクトが存在する前に起動します。`admin_user_credentials` は `ReplaceSpecType` にも存在し、インプレースで適用されます。 |
| `block_all_services` | 管理アドレスの 22 番ポートの閉鎖は、サービスがブロックされているかどうかにかかわらず同一です。 |
| 鍵末尾の改行 | 両方の方法でテストしましたが変化はありません。cloud-init は依然としてこれを取り除きます。そうでなければリテラルブロックが 2 行目の空行を描画してしまうためです。 |
| 固定された古い CE ソフトウェア | OpenSSH 9.9 を実行しているものを含む 3 つのビルドで再現しました。 |
| `admin_password` の欠如 | ゼロから作成した CE で `ssh_key` と併せて `admin_password` を設定しても何も変わりませんでした。 |

<Aside type="caution" title="判別材料に見えるが実はそうではない 2 つの API フィールド">
`gc_spec.admin_ssh_key` は **`f5-sales-demo` の 58 サイトすべて** で空か存在しません —
`admin_user_credentials.ssh_key` を実際に設定している 2 サイトも含めてです。動作しているサイトと
していないサイトの間でこれを比較しても何も分かりません。クレデンシャルが *実際に* 構成されている
サイトでも空と読めるからです。

`registrations_by_site` はこのフィールドを完全に省略し、`None` を返します。これは
「報告されていない」ではなく「構成されていない」と読めてしまいます。
</Aside>

<Aside type="caution" title="新規作成されたサイトは operate API が応答するまで約 30 分を要する">
新しいサイトが `ONLINE` を報告してからおよそ 25〜30 分の間、`vpm/debug` エンドポイントは
`The requested URL was rejected` と表示される BIG-IP の `503` ページを返します。これは Web
アプリケーションファイアウォールによるブロックや、失効したトークンのように見えますが、そのどちらでも
ありません。サイトがまだ中継の準備を終えていないだけです。何かを変更するのではなく、待って再試行してください。

SSH にはそのようなウォームアップはありません。`sshd` が起動次第応答します。だからこそ、ノードがまだ
登録中の間でも機能する経路なのです。
</Aside>
