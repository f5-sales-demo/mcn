このデプロイメントの1つのCEから2026-07-28にキャプチャされました。`sitecli/capture-manifest.json`
にはどのノードかが記録されており、`scripts/capture-sitecli.sh --check` でライブCEに対してコマンド
サーフェスを再検証できます。

SSHはアプライアンスの `admin` アカウントに到達します。ログインシェルはSite CLI
（`/opt/bin/vpmu`）です。これは**オンボックスコマンドサーフェス全体**への唯一のルートです — 
[デバッグAPI](../debug-api/)は34コマンドを公開していますが、アプライアンス自体にはそのAPIには存在しない
より多くのコマンドがあります。

```bash
cd terraform
SLI=$(terraform output -json ce_sli_private_ips | jq -r '.eastus01')
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<operator-vm> "admin@$SLI"
```

このコマンドラインのすべての部分が重要な役割を担っており、次の3つのセクションでそれぞれが防ぐ障害を説明します。

着地するシェルプロンプトはありません: `admin` のログインシェル**そのもの**がSite CLIであるため、
`>>>` プロンプトに到達します。そこで `execcli <name>` としてオンボックスコマンドを実行します —
[オンボックスコマンド](../../commands/on-box/)を参照してください。

<Aside type="danger" title="内部アドレスは必ず検索してください — 前のセッションから持ち越さないでください">
Azureは再ビルドのたびに内部サブネットを再割り当てします。ノード順では行われません。最新のビルドでは
`f5-xc-ce-vm-01`、`-02`、`-03` がそれぞれ `10.0.3.7`、`10.0.3.5`、`10.0.3.4` を保持しています。
以前のビルドでは完全に異なる順序でした。テストクライアントのNICは同じサブネットにあり、以前CEが
保持していたアドレスを保持しています。記憶されたアドレスに接続すると、誤ったノード、CEでないVM、
またはどこにもつながらない可能性があります — 最後のケースは「SSHが有効ではない」と同一に見えます。

`terraform output -json ce_sli_private_ips` がマッピングです。状態が手元にない場合、NIC
名はアドレスが変わっても安定しています:

```bash
az network nic show -g "$(terraform output -raw resource_group_name)" \
  -n "$(terraform output -json ce_vm_names | jq -r '.eastus01')-internal-nic" \
  --query ipConfigurations[0].privateIPAddress -o tsv
```

</Aside>

<Aside type="caution" title="ブートストラップ時のみ — 既存のCEはSSHを再作成なしに取得できません">
cloud-init の `write_files` は**初回ブート時に一度だけ**実行されます。その後、ノード上に
`/etc/cloud/cloud-init.disabled` マーカーが存在し、cloud-initは再実行されません。

そのため、実行中のCEへのインプレースパスはありません。`custom_data` はAzureでは置換専用であり、
既存のデプロイメントにこれを採用することは**すべてのCE VMを置換**することを意味します。すでに
稼働しているノードへのオペレーターSSHの付与は再ビルドであり、設定変更ではありません — 次の警告は
その再ビルドがかつてどれほどのコストを伴っていたか、そしてなぜそれがもはや問題でないかについてです。
</Aside>

<Aside type="caution" title="CE VMの置換はかつて登録を永久にブロックしていました — それは修正済みです。サイトオブジェクトがVMに結合されている理由もここにあります">
再ビルドを計画する前に知っておく価値があります。障害の形状がプランで見られる結合を説明しているからです。

かつては、破棄されたノードの登録がコントロールプレーンの一意な `(tenant, cluster_name, hostname)`
インデックスを保持し続けていたため、代替ノードの登録が `UniqueSecondaryIndexViolationError` で
拒否されて永遠にリトライしていました。登録を削除するだけでは不十分でした: 残った `StatusObject` が
ワークロードリクエストに `500` を返し、その時点で各ノードが削除した登録にピン留めする
`registration-obj.yml` を永続化していたため、自己回復なしに `404` でループしていました。
回復には2回の完全な再ビルドが必要でした。その間ずっと `terraform plan` は**「変更なし」**を報告していました。
Terraformの観点からは望ましい状態に達していたためです。

[Issue 674](https://github.com/f5-sales-demo/mcn/issues/674) は
[PR 693](https://github.com/f5-sales-demo/mcn/pull/693) によってクローズされました。
`modules/xc-site` はCE VMインスタンスを `replace_triggered_by` に指定するようになり、
VMを置換するとサイトオブジェクトも置換されます。サイトを削除するとその登録も削除されます —
インデックスキーは代替ノードがブートする前に解放されます。フリートはその後スクラッチから再ビルドされ、
3つのサイトすべてが介入なしに `ONLINE` になりました。

結合は推測ではなく観察可能です。各サイトはVMの*インスタンス*IDにバインドされており、
対応する登録は `infra.instance_id` と同じ値を報告します:

```bash
cd terraform && terraform output -json ce_bound_instance_ids
```

両者の不一致は、サイトがまだ存在しないノードにバインドされていることを意味します。
これは再ビルドされたCEが登録から抜け出せない状態です。登録側の値の読み取りには
まだ直接のAPIコールが必要です — プロバイダーのissue
[1376](https://github.com/f5-sales-demo/terraform-provider-xcsh/issues/1376) がデータソースに
追加する予定です。
</Aside>

## cloud-initがキーを書き込む理由、APIでないのはなぜか

サイトオブジェクトの `admin_user_credentials.ssh_key` はこれのためのフィールドのように見えます。
受け入れられ、読み返しても残り、そして何も設定しません。`vpm` がノードのローカルユーザーを所有しており、
このユーザーへのタッチを拒否します — ノード自身のログから、1回のブートで3回記録されています:

```text
vpm  users.go:165: Won't do any change for user admin (internal skip)
```

その後のすべてはこの1行から来ています。`/var/home/admin/.ssh` はサイトが `ONLINE` になる前後を
問わず存在しません。`admin` のシャドウ最終変更日はイメージのビルド日のままです。一方、`vesbkp` と
`vesopcon` は現在の日付を示します。`vpm` がこの2つを設定して `admin` をスキップしたためです。
そして `vpm` は `ssh_key` や `authorized_keys` についていかなる時点でも何もログに記録しません。

つまり、ファイルは `vpm` の外部で書き込む必要があります。`admin` はuid 2202で、ノードイメージに
ベイクされているため、cloud-initが実行される前から存在しており、書き込み時に `owner: admin:admin`
が解決されます — `runcmd` も所有権の修正も不要です:

```yaml
- path: /var/home/admin/.ssh/authorized_keys
  permissions: "0600"
  owner: admin:admin
  content: |
    ${ssh_public_key}
```

`sshd` は常に対応していました。`sshd -T` は `pubkeyauthentication yes` を報告し、`admin` は
ノードに同梱されている両方の `sshd_config` ファイルの `AllowUsers` に記載されています。
有効化すべきものは何もなかった — 欠けていたのはファイルだけでした。

<Aside type="danger" title="admin_user_credentialsを再追加しないでください。sshd_configを編集しないでください">
`admin_user_credentials` は `terraform/modules/xc-site` に組み込まれ、この証拠が収集された後に
差し戻されました（#660、PR #663）。これは埋めるべきギャップではありません。

`sshd_config` は登録時に置換されるため、編集は最も不都合なタイミングで破棄されます。
</Aside>

## 1つのアドレスのみで応答する理由

`sshd` は `0.0.0.0:22` にバインドしていますが、**内部（SLI）**アドレスのみが `sshd` が
応答できる形でホストネットワークスタックに存在します。eth0は `a-i-eth0` にリネームされ、
ホストIPを持ちません — Argoデータプレーンがそのインターフェースを所有しており、本来そこに
あるべき管理/SLOアドレスは代わりに `vhost0` に表示されます。他の2つのNICはそれぞれの名前で
ホストスタックに残ります。

VNet内のVMから1つのCEに対してプローブした結果:

```text
management/SLO address    timed out
external address          timed out
internal/SLI address      OPEN     SSH-2.0-OpenSSH_8.7
an unused address         timed out    (control)
```

ノードのアドレスとして知っているアドレスへのプローブは、閉じたセキュリティグループが返すのと
まったく同じ結果を返します。何もブロックしていません。そのアドレスにリスナーが存在しないのです。

<Aside type="caution" title="ゲストインターフェース名からどのサブネットにいるかを判断しないでください">
`eth1` と `eth2` のどちらが内部アドレスを持つかは、**同じデプロイメントのノード間でも異なります**。
3つのCEすべてからライブで読み取った結果:

```text
f5-xc-ce-vm-01    eth1 -> external      eth2 -> internal/SLI
f5-xc-ce-vm-02    eth2 -> external      eth1 -> internal/SLI
f5-xc-ce-vm-03    eth1 -> external      eth2 -> internal/SLI
```

すべてのノードで成立する事実は2つだけです: `a-i-eth0` にはアドレスがなく、`vhost0` が
管理/SLOアドレスを持ちます。それ以外については、インターフェース名ではなく
[`ip addr`](../../commands/network/ip/) 出力のアドレスで照合してください。
</Aside>

CEのパブリックアドレスにもポート22のリスナーがないため、上記のコマンドが `-J` を使用する理由です:
SLIアドレスと同じサブネット内のVNet内のオペレーターVM。このデプロイメントはその目的のために
1つを構築しています —
`terraform output -raw client_vm_name` で名前を確認できます。

<Aside type="caution" title="-Jはジャンプレッグにオプションを渡しません">
コマンドラインで指定されたオプションは最終ホップに適用されます。`-J` と共に
`-o UserKnownHostsFile=/dev/null` を指定しても、*ジャンプ*ホストの実際の `known_hosts` を
参照して書き込みます。再ビルドされたフリートをそこから除外しようとしている場合に驚かされます。
それが重要な場合は最初のホップを明示的に指定してください:

```bash
ssh -tt -o ProxyCommand="ssh -W %h:%p -o UserKnownHostsFile=/dev/null azureuser@<operator-vm>" \
    -o UserKnownHostsFile=/dev/null -i ~/.ssh/id_ed25519 "admin@$SLI"
```

</Aside>

<Aside type="caution" title="自信を持って誤った答えを生む2つの測定ミス">
eth0、外部インターフェース、またはパブリックアドレスのポート22をプローブすると、ノードのSSH状態に
関わらず閉じていると報告されるため、何も判断できません。SLIアドレスのみが応答します。

そして、企業のワークステーションからのプローブは、実際には閉じているポートを**オープン**と報告する
ことがあります: Netskope が一般的なポートでTCPハンドシェイクを自ら完了させます。ワークステーションから
CEのパブリックアドレスのポート80と443はオープンと読み取られますが、VNet内からプローブすると閉じています。
VNet内のVMからプローブしてください。
</Aside>

## Site CLIにはターミナルとキャリッジリターンが必要です

`admin` のログインシェルはシェルではありません。それは `go-prompt` アプリケーションであり、
ターミナルをrawモードにしてラインではなくキーストロークを読み取ります。4つの結果があり、
それぞれが異なる問題のように見える失敗をします:

| 仕組み | それなしで何が起きるか |
| --- | --- |
| ターミナルを割り当てる（`ssh -tt`） | `go-prompt.NewStandardInputParser` から `panic: no such device or address` が発生し、アプライアンスがクラッシュしたように見える |
| Enterに改行（LF）ではなくキャリッジリターン（CR）を送る | ラインが送信されず、何も出力せずに入力終了でセッションが閉じる |
| 標準入力を開いたままにする | コマンドがレンダリングされる前に接続が終了するため、動作するコマンドが無音に見える |
| コマンドテキストとEnterバイトを**別々に**書き込む | 改行がバッファにリテラル文字として入り、CLIが `unknown command` と答える。コマンドが存在しないように見える |

したがって `ssh host 'some-command'` は機能しません: 引数は無視されてインタラクティブプロンプトが
とにかく起動します。ターミナルとして操作するか、まったく操作しないかのどちらかです。
`scripts/sitecli_ssh_harvest.py` がリファレンス実装です。

<Aside type="caution" title="'no such device or address' というパニックは認証が成功したことを意味します">
`vpmu` はログイン**後**、アタッチするターミナルが見つからないときにこれを出力します。クラッシュと
読み取ると最悪の結果のように見えますが、実際には成功の直前の最後のエラーです。`-tt` を追加して
再接続してください。
</Aside>

<Aside type="caution" title="CEのホストキーが2つの異なる理由で変わることがあります">
次の接続では `REMOTE HOST IDENTIFICATION HAS CHANGED` の警告が出て拒否されます。そのアドレスの
古いエントリを削除して再接続してください。2つのことがこれをトリガーします:

- **ノードの置換。** 置換ノードが同じアドレスで異なるキーを提示します。SSHの付与はVMを置換するため、
  採用後の最初の接続でこれが発生します。
- **VMの置換なしの、インプレースのオペレーティングシステムアップグレード。** `2026-07-28に観察`:
  `ce_os_version` のアップグレードが完了したノードが、同じ仮想マシン上の同じアドレスで新しいホストキーを提示しました。

`StrictHostKeyChecking=accept-new` はどちらにも役立ちません。これは一度も見たことがないホストの
キーを受け入れます。*変更された*キーはまさにそれが拒否するものです。古いエントリを削除するだけで解消されます。

アドレスが移動することもあります。デプロイメントを再作成すると同じサブネットから再割り当てされるため、
CEとジャンプホストがアドレスを入れ替えることがあります — その後、古いエントリは単に時代遅れなだけでなく、
間違ったマシンに付いています。
</Aside>

## バナーは無料のヘルスチェックです

何かを入力する前に、ログインバナーはすでにコマンドに費やすであろういくつかの質問に答えています。
`f5-xc-ce-vm-01` から、ASCIIアートとパブリックIPを省略した内容:

```text
UNAUTHORIZED ACCESS TO THIS DEVICE IS PROHIBITED
All actions performed on this device are audited

Using https://register.ves.volterra.io
OS: rhel-9.2024.6
Memory: 32768MiB
Storage: sda: 31GiB
CPU: Model: Intel(R) Xeon(R) Platinum 8272CL CPU @ 2.60GHz | CPUs: 8
Software: crt-20250613-3382
DNS: 168.63.129.16: OK
NTP: Synced
Uptime: 0 days, 5 hours, 20 minutes
Registration Status: PROVISIONED
SLO IP: 10.0.1.4/26
WELCOME IN SITE CLI
```

`Registration Status` は、まだ起動中のノード（`PROVISIONING`）と完了したノード（`PROVISIONED`）を
区別します。`Software` は存在するコマンドを決定するビルド文字列です。`DNS` と `NTP` は最初に
登録を破壊する2つの依存関係をカバーしているため、オンラインになれなかったノードは通常ここですでに
原因を示しています —
[`chronyc-sources`](../../commands/network/chronyc-sources/) や
[`dig`](../../commands/network/dig/) が必要になる前に。

## キーペアの提供

<Steps>

1. キーペアをまだ持っていない場合は生成してください。RSAではなくEd25519を使用してください:
   短く、アプライアンスの `sshd` に受け入れられます。

   ```bash
   ssh-keygen -t ed25519 -C "ce-operator" -f ~/.ssh/id_ed25519
   ```

2. デプロイメントが**公開**鍵を参照するように設定します。ルートモジュールはファイルを一度読み取り、
   文字列をすべてのノードに渡します:

   ```hcl
   # terraform/terraform.tfvars
   ssh_public_key_path = "~/.ssh/id_ed25519.pub"
   ```

   `ssh_public_key` はマテリアルをインラインで受け取ります。これはプランテストが使用する方法です。
   秘密鍵はワークステーションから外に出ません。

3. 適用します。このページの先頭の警告を先に読んでください — 既存のデプロイメントではCE VMが置換されます。

</Steps>

<Aside type="note" title="VMのadmin_ssh_keyは別のものです">
`modules/ce-node` の `azurerm_linux_virtual_machine.admin_ssh_key` はAzure VMの管理者を
認可するものであり、アプライアンスの `admin` アカウントではありません。Site CLIアクセスを
付与するものではなく、それが設定されていることはCE SSHが設定されている証拠ではありません。
</Aside>

## これが何でないか

以下の各項目は、そのルートがまだ不可能と信じられていた間にテストされ、除外されました。
それぞれ1日を費やすほど妥当に見えます。

| 原因でないもの | 除外の根拠 |
| --- | --- |
| 資格情報は作成時のみ適用される | `sshd` は最初のブートから約90秒後に開始されます。サイトオブジェクトが存在する前です。`admin_user_credentials` は `ReplaceSpecType` にも存在し、インプレースで適用されます。 |
| `block_all_services` | 管理アドレスのポート22のクローズは、サービスがブロックされているかどうかに関わらず同一です。 |
| キーの末尾の改行 | 両方でテスト済み、変化なし。リテラルブロックがそうでなければ2行目の空行をレンダリングするため、cloud-initはそれを取り除きます。 |
| ピン留めされた古いCEソフトウェア | OpenSSH 9.9を実行しているものを含む3つのビルドで再現されました。 |
| 欠けている `admin_password` | スクラッチからのCEで `ssh_key` とともに `admin_password` を設定しても何も変わりませんでした。 |

<Aside type="caution" title="識別子のように見えて識別子ではない2つのAPIフィールド">
`gc_spec.admin_ssh_key` は、`admin_user_credentials.ssh_key` を設定している2つのサイトを含む、
**`f5-sales-demo` の58のサイトすべて**で空または欠如しています。動作しているサイトと動作していない
サイトを比較しても何もわかりません。資格情報が設定されているサイトでも空として読み取られるためです。

`registrations_by_site` はフィールドを完全に省略し、`None` を返します。これは「設定されていない」
ではなく「報告されていない」と読み取られます。
</Aside>

<Aside type="caution" title="新しく作成されたサイトはデバッグAPIが応答するまで約30分かかります">
新しいサイトが `ONLINE` を報告してから約25〜30分間、`vpm/debug` エンドポイントは
`The requested URL was rejected` と表示するBIG-IPの `503` ページを返します。これは
Webアプリファイアウォール (WAF)のブロックや失効したトークンのように見えますが、どちらでもありません:
サイトはまだリレーの準備ができていません。何かを変更するのではなく、待ってから再試行してください。

SSHにはそのようなウォームアップはありません。`sshd` が起動するとすぐに応答します。これが、
ノードがまだ登録中のときにも機能するルートである理由です。
</Aside>
