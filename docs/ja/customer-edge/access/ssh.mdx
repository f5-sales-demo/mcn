2026-07-28 に、このデプロイメントの CE 1 台から取得したものです。`sitecli/capture-manifest.json`
にどのノードかが記録されており、`scripts/capture-sitecli.sh --check` で稼働中の CE に対して
コマンド面を再検証できます。

SSH はアプライアンスの `admin` アカウントに到達し、そのログインシェルは Site CLI
(`/opt/bin/vpmu`) です。これは**オンボックスの完全なコマンド面**への唯一の経路です。
[デバッグ API](../debug-api/) は 34 個のコマンドを公開しますが、アプライアンス自体はその API に
まったく載っていないコマンドを他にも多数提供しています。

```bash
cd terraform
SLI=$(terraform output -json ce_sli_private_ips | jq -r '.eastus01')
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<operator-vm> "admin@$SLI"
```

このコマンドラインのどの部分も欠かせないものであり、次の 3 つのセクションでそれぞれが
どの失敗を防いでいるのかを説明します。

<Aside type="danger" title="内部アドレスは必ず調べること — 以前のセッションのものを流用しない">
Azure は再構築ごとに内部サブネットを再割り当てし、しかもノード順にはなりません。直近の
再構築後は `f5-xc-ce-vm-01`、`-02`、`-03` がそれぞれ `10.0.3.7`、`10.0.3.5`、`10.0.3.4` を
保持していますが、以前のビルドではまったく異なる順序でした。さらにテストクライアントの NIC も
同じサブネットにあり、以前 CE が保持していたアドレスを持っていたことがあります。
したがって記憶していたアドレスに接続すると、誤ったノードに着地したり、CE ではない VM に
着地したり、どこにも着地しないことになります。そして最後のケースは「SSH が有効になっていない」と
まったく同じに見えます。

`terraform output -json ce_sli_private_ips` がそのマッピングです。state が手元にない場合、
アドレスは安定していなくても NIC 名は安定しています。

```bash
az network nic show -g "$(terraform output -raw resource_group_name)" \
  -n "$(terraform output -json ce_vm_names | jq -r '.eastus01')-internal-nic" \
  --query ipConfigurations[0].privateIPAddress -o tsv
```

</Aside>

<Aside type="caution" title="ブートストラップ時のみ — 既存の CE は再作成なしに SSH を得られない">
cloud-init の `write_files` は**初回ブート時に一度だけ**実行されます。その後はノード上に
`/etc/cloud/cloud-init.disabled` マーカーが存在し、cloud-init は再実行されません。

したがって稼働中の CE にインプレースで適用する経路はありません。Azure では `custom_data` は
置き換え専用であり、既存デプロイメントでこれを採用すると**すべての CE VM が置き換えられます**。
すでに稼働しているノードにオペレーター SSH を付与することは、設定変更ではなく再構築です。
そして次の警告は、その再構築がかつてどれほどのコストを伴ったか、そしてなぜもう伴わないのかを
説明します。
</Aside>

<Aside type="caution" title="CE VM の置き換えはかつて登録を恒久的に詰まらせた — これは修正済みであり、サイトオブジェクトが VM と結合している理由でもある">
再構築を計画する前に知っておく価値があります。というのも、この失敗の形が、プランで目にする
結合関係を説明するからです。

かつては、破棄されたノードの登録がコントロールプレーンの一意な
`(tenant, cluster_name, hostname)` インデックスを保持し続けたため、置き換えノードの登録が
`UniqueSecondaryIndexViolationError` で拒否され、永遠にリトライされました。登録を削除するだけでは
不十分でした。残存した `StatusObject` がワークロードリクエストに対して `500` を返し、その時点で
各ノードは削除した登録に紐づく `registration-obj.yml` を永続化していたため、自己復旧なしに
`404` でループしました。復旧には 2 回のフル再構築が必要でした。その間ずっと `terraform plan` は
**「No changes」**と報告していました。Terraform の視点からは望ましい状態に到達していたからです。

[Issue 674](https://github.com/f5-sales-demo/mcn/issues/674) は
[PR 693](https://github.com/f5-sales-demo/mcn/pull/693) によってクローズされています。
`modules/xc-site` は現在 `replace_triggered_by` で CE VM インスタンスを指定しており、VM を
置き換えるとサイトオブジェクトも置き換えられ、サイトを削除するとその登録も一緒に削除されます。
つまり置き換えノードがブートする前にインデックスキーが解放されます。以降、フリートはゼロから
再構築され、3 サイトすべてが介入なしに `ONLINE` になりました。

この結合は仮定ではなく観測可能です。各サイトは VM *インスタンス* ID にバインドされており、
対応する登録は `infra.instance_id` として同じ値を報告します。

```bash
cd terraform && terraform output -json ce_bound_instance_ids
```

両者が一致しない場合、サイトがもはや存在しないノードにバインドされたままであることを意味し、
これは再構築された CE が決して登録から抜け出せない状態です。登録側の値を読むには依然として
直接の API 呼び出しが必要です。プロバイダー issue
[1376](https://github.com/f5-sales-demo/terraform-provider-xcsh/issues/1376) がこれをデータソースに
載せるためのものです。
</Aside>

## cloud-init が鍵を書き込む理由、そして API が書き込まない理由

サイトオブジェクトの `admin_user_credentials.ssh_key` は、まさにこの用途のフィールドのように
見えます。受け付けられ、読み戻しても残りますが、何も設定しません。`vpm` はノードのローカル
ユーザーを所有しており、このユーザーには手を触れないことを選びます。ノード自身のログから、
1 回のブート中に 3 回:

```text
vpm  users.go:165: Won't do any change for user admin (internal skip)
```

その他すべてはこの 1 行から導かれます。`/var/home/admin/.ssh` はサイトが `ONLINE` に到達する
前も後も、決して存在しません。`admin` の shadow の最終変更日はイメージのビルド日のままである一方、
`vesbkp` と `vesopcon` は現在の日付を示します。これは `vpm` がその 2 つを設定し、`admin` を
スキップしたからです。そして `vpm` は `ssh_key` や `authorized_keys` について一切ログを出しません。

したがってファイルは `vpm` の外側で書き込む必要があります。`admin` は uid 2202 で、ノード
イメージに焼き込まれているため cloud-init の実行前に存在し、`owner: admin:admin` は書き込み時に
解決されます。`runcmd` も所有権の修正も不要です。

```yaml
- path: /var/home/admin/.ssh/authorized_keys
  permissions: "0600"
  owner: admin:admin
  content: |
    ${ssh_public_key}
```

`sshd` は常に受け入れる用意がありました。`sshd -T` は `pubkeyauthentication yes` を報告し、
ノードに同梱される両方の `sshd_config` ファイルの `AllowUsers` に `admin` が現れます。
有効化すべきものは何もありませんでした。欠けていたのはファイルだけです。

<Aside type="danger" title="admin_user_credentials を再追加せず、sshd_config も編集しない">
`admin_user_credentials` は `terraform/modules/xc-site` に組み込まれていましたが、この証拠が
収集された時点で差し戻されました (#660、PR #663)。これは埋めるべき欠落ではありません。

`sshd_config` は登録処理中に置き換えられるため、それに対する編集は最も都合の悪いタイミングで
破棄されます。
</Aside>

## 1 つのアドレスでのみ応答する理由

`sshd` は `0.0.0.0:22` にバインドしますが、`sshd` が応答する形でホストのネットワークスタックに
載っているのは**内部 (SLI)** アドレスだけです。eth0 は `a-i-eth0` にリネームされ、ホスト IP を
まったく持ちません。そのインターフェイスは Argo データプレーンが所有し、本来そこに載るはずの
管理/SLO アドレスは代わりに `vhost0` に現れます。残る 2 つの NIC はそれぞれの名前でホスト
スタック上に留まります。

VNet 内部の VM から 1 台の CE に対してプローブした結果:

```text
management/SLO address    timed out
external address          timed out
internal/SLI address      OPEN     SSH-2.0-OpenSSH_8.7
an unused address         timed out    (control)
```

したがって、あなたがそのノードを識別しているアドレスに対するプローブは、閉じられた
セキュリティグループが返すのとまったく同じ結果を返します。何もブロックしていません。
そのアドレスにリスナーが存在しないのです。

<Aside type="caution" title="どのサブネット上にいるかを判断するためにゲストのインターフェイス名を読まないこと">
`eth1` と `eth2` のどちらが内部アドレスを持つかは、**この同一デプロイメント内のノード間でも
異なります**。3 台の CE すべてからライブで読み取った結果:

```text
f5-xc-ce-vm-01    eth1 -> external      eth2 -> internal/SLI
f5-xc-ce-vm-02    eth2 -> external      eth1 -> internal/SLI
f5-xc-ce-vm-03    eth1 -> external      eth2 -> internal/SLI
```

すべてのノードで成り立つのは 2 点だけです。`a-i-eth0` はアドレスを持たない、そして `vhost0` は
管理/SLO アドレスを持つ。それ以外については、インターフェイス名ではなく
[`ip addr`](../../commands/network/ip/) の出力に含まれるアドレスで照合してください。
</Aside>

CE のパブリックアドレスにも 22 番のリスナーはありません。だからこそ上記のコマンドは `-J` を
経由します。VNet 内部にあり、SLI アドレスと同じサブネットにあるオペレーター VM です。
このデプロイメントはその目的のために 1 台を構築します。
`terraform output -raw client_vm_name` がその名前を示します。

<Aside type="caution" title="-J はジャンプ側にオプションを渡さない">
コマンドラインで与えたオプションは最終ホップに適用されます。したがって `-J` と併せて
`-o UserKnownHostsFile=/dev/null` を指定しても、*ジャンプ*ホストについては実際の `known_hosts` を
依然として参照し、書き込みます。再構築したフリートをそこから除外しようとしている場合、
これが意外な点です。それが問題になるときは、最初のホップを明示的に書いてください。

```bash
ssh -tt -o ProxyCommand="ssh -W %h:%p -o UserKnownHostsFile=/dev/null azureuser@<operator-vm>" \
    -o UserKnownHostsFile=/dev/null -i ~/.ssh/id_ed25519 "admin@$SLI"
```

</Aside>

<Aside type="caution" title="自信を持って誤った答えを出す 2 つの測定ミス">
eth0、外部インターフェイス、またはパブリックアドレスに対してポート 22 をプローブすると、
ノードの SSH 状態にかかわらず closed と報告されるため、何も分かりません。応答するのは SLI
アドレスだけです。

そして企業のワークステーションからのプローブは、閉じているポートを**開いている**と報告し得ます。
Netskope が一般的なポートに対して自ら TCP ハンドシェイクを完了するためです。ワークステーションから
見ると CE のパブリックアドレスでポート 80 と 443 は開いているように読めますが、VNet 内部から
プローブすると閉じています。VNet 内の VM からプローブしてください。
</Aside>

## Site CLI にはターミナルとキャリッジリターンが必要

`admin` のログインシェルはシェルではありません。`go-prompt` アプリケーションであり、
ターミナルを raw モードにして行ではなくキーストロークを読み取ります。結果は 4 つあり、
それぞれ別の問題のように見える形で失敗します。

| 仕組み | それがない場合に起きること |
| --- | --- |
| ターミナルを割り当てる (`ssh -tt`) | `go-prompt.NewStandardInputParser` からの `panic: no such device or address`。アプライアンスがクラッシュしたように読める |
| Enter としてラインフィードではなくキャリッジリターンを送る | 行が送信されず、何も表示しないまま入力終了でセッションが閉じる |
| 標準入力を開いたままにする | コマンドが描画される前に接続が終わるため、動作しているコマンドが無反応に見える |
| コマンド文字列と Enter バイトを**別々に**書き込む | 改行がリテラル文字としてバッファに入り、CLI が `unknown command` と応答するため、そのコマンドが存在しないかのように読める |

したがって `ssh host 'some-command'` は機能しません。引数は無視され、どのみち対話プロンプトが
起動します。ターミナルとして駆動するか、まったく使わないかのいずれかです。
`scripts/sitecli_ssh_harvest.py` がリファレンス実装です。

<Aside type="caution" title="'no such device or address' と読めるパニックは、認証が成功したことを意味する">
`vpmu` はログイン**後**、アタッチするターミナルが見つからないときにこれを出力します。クラッシュと
読むと最悪の結果のように見えますが、実際には成功の直前の最後のエラーです。`-tt` を追加して
再接続してください。
</Aside>

<Aside type="caution" title="CE を置き換えるとホスト鍵が変わる">
置き換えノードは同じアドレスで異なるホスト鍵を提示するため、次の接続は
`REMOTE HOST IDENTIFICATION HAS CHANGED` と警告して拒否します。そのアドレスの古いエントリを
消して再接続してください。SSH を付与すること自体が VM を置き換えるため、採用後の最初の接続で
これが起きると想定してください。
</Aside>

## バナーは無料のヘルスチェック

何かを入力する前に、ログインバナーはコマンドを費やして調べるはずだった質問のいくつかに
すでに答えています。`f5-xc-ce-vm-01` から、アスキーアートとパブリック IP を省略:

```text
UNAUTHORIZED ACCESS TO THIS DEVICE IS PROHIBITED
All actions performed on this device are audited

Using https://register.ves.volterra.io
OS: rhel-9.2024.6
Memory: 32768MiB
Storage: sda: 31GiB
CPU: Model: Intel(R) Xeon(R) Platinum 8272CL CPU @ 2.60GHz | CPUs: 8
Software: crt-20250613-3382
DNS: 168.63.129.16: OK
NTP: Synced
Uptime: 0 days, 5 hours, 20 minutes
Registration Status: PROVISIONED
SLO IP: 10.0.1.4/26
WELCOME IN SITE CLI
```

`Registration Status` は、まだ起動中のノード (`PROVISIONING`) と完了したノード
(`PROVISIONED`) を区別します。`Software` はどのコマンドが存在するかを決めるビルド文字列です。
`DNS` と `NTP` は登録を最初に壊す 2 つの依存関係をカバーするため、オンラインにならなかった
ノードは通常ここで既に理由を教えてくれています。
[`chronyc-sources`](../../commands/network/chronyc-sources/) や
[`dig`](../../commands/network/dig/) がまったく必要になる前に。

## キーペアの提供

<Steps>

1. まだ持っていない場合はキーペアを生成します。RSA ではなく Ed25519 を使います。より短く、
   アプライアンスの `sshd` に受け付けられます。

   ```bash
   ssh-keygen -t ed25519 -C "ce-operator" -f ~/.ssh/id_ed25519
   ```

2. デプロイメントを**公開**鍵側に向けます。ルートモジュールがファイルを一度読み取り、
   文字列を各ノードに渡します。

   ```hcl
   # terraform/terraform.tfvars
   ssh_public_key_path = "~/.ssh/id_ed25519.pub"
   ```

   `ssh_public_key` は代わりに鍵素材をインラインで受け取り、プランのテストではこちらを使います。
   秘密鍵側はワークステーションから出ることはありません。

3. 適用します。まずこのページ冒頭の警告を読んでください。既存のデプロイメントではこれにより
   CE VM が置き換えられます。

</Steps>

<Aside type="note" title="VM 自身の admin_ssh_key は別物">
`modules/ce-node` の `azurerm_linux_virtual_machine.admin_ssh_key` は Azure VM の管理者を
認可するものであり、アプライアンスの `admin` アカウントではありません。Site CLI へのアクセスは
一切付与せず、設定されていることが CE SSH が構成されている証拠にはなりません。
</Aside>

## これが原因ではないもの

以下はいずれも、この経路がまだ不可能だと考えられていた間にテストされ、除外されたものです。
いずれも 1 日を費やすに足るほどもっともらしいものです。

| 原因ではないもの | どのように除外したか |
| --- | --- |
| 資格情報は作成時にしか適用されない | `sshd` は初回ブートの約 90 秒後、サイトオブジェクトが存在する前に起動します。`admin_user_credentials` は `ReplaceSpecType` にも存在し、インプレースで適用されます。 |
| `block_all_services` | 管理アドレスにおけるポート 22 の閉塞は、サービスがブロックされているかどうかにかかわらず同一です。 |
| 鍵末尾の改行 | 両方でテストし、変化なし。cloud-init は依然としてこれを除去します。リテラルブロックでなければ 2 行目の空行が描画されてしまうためです。 |
| 固定された古い CE ソフトウェア | OpenSSH 9.9 を実行しているものを含む 3 つのビルドで再現しました。 |
| `admin_password` の欠落 | ゼロから構築した CE で `ssh_key` と併せて `admin_password` を設定しても何も変わりませんでした。 |

<Aside type="caution" title="判別要素のように見えて、そうではない 2 つの API フィールド">
`gc_spec.admin_ssh_key` は **`f5-sales-demo` の全 58 サイト**で空または不在です。
`admin_user_credentials.ssh_key` を実際に設定している 2 サイトも含めてです。動作するサイトと
動作しないサイトの間でこれを比較しても何も分かりません。資格情報が*実際に*構成されている
サイトでも空として読めてしまうからです。

`registrations_by_site` はこのフィールドを完全に省略し、`None` を返します。これは
「報告されていない」ではなく「構成されていない」と読めてしまいます。
</Aside>

<Aside type="caution" title="新規作成されたサイトは operate API が応答するまで約 30 分かかる">
新しいサイトが `ONLINE` を報告してからおよそ 25〜30 分間、`vpm/debug` エンドポイントは
`The requested URL was rejected` と表示される BIG-IP の `503` ページを返します。これは Web
アプリケーションファイアウォールのブロックや、失効したトークンのように見えますが、どちらでも
ありません。サイトがまだ中継の準備ができていないのです。何かを変更するのではなく、待って
再試行してください。

SSH にはこのようなウォームアップはありません。`sshd` が起動した時点で応答します。だからこそ
ノードがまだ登録中でも機能する経路なのです。
</Aside>
