すべての Customer Edge は、F5 のサイトコンソールを `https://<sli-ip>:65500` で提供します。この
デプロイでは、通常まず試すべき手順です。

必要なものが最も少ない方法です。配布すべき SSH キーなし、維持すべきジャンプホストなし、ノードへのパブリック IP なし、
そして有効化のための VM 交換もなし。接続を許可するかどうかは **Azure RBAC の決定** になります。
また、サイトが登録済みである必要もありません — 以下のトランスクリプトは、3 つのサイトすべてが
`site_state: FAILED` を報告している間に取得されたものです。

注意点として、サイトコンソールはノードの内部 (SLI) アドレスでのみ応答し、VNet 内部からのみ到達可能です。
Azure Bastion は、ネットワークに他のものを追加することなくこのギャップを埋めます。

<Aside type="note" title="ここで検証されていること、されていないこと">
このページのすべてのコマンドとすべての出力は、このデプロイの `f5-xc-ce-vm-01` に対して実行されたものであり、
失敗を含め、そのまま再現されています。

実施されていない唯一のことは **サインイン** です。手順は認証情報プロンプトで停止するため、
以下にはコンソールにサインイン後の表示については説明していません。
</Aside>

## 始める前に

<Steps>

1. Azure にサインインし、Bastion 拡張機能を追加します。トンネリングはネイティブクライアントの機能であり、
   拡張機能はデフォルトではインストールされません。

   ```bash
   az login
   az extension add --name bastion
   ```

2. CE 仮想マシン、そのネットワークインターフェイス、および Bastion ホストに対して **Reader** 権限を保持します。

3. Bastion がデプロイされており、対応可能であることを確認します。Basic SKU はトンネリングも
   IP ベースの接続もサポートしていないため、ここでの `Standard` と `True` はどちらも重要です。

   ```bash
   az network bastion list -g rg-mcn-ce-ha-rmordasiewicz \
     --query "[].{name:name, sku:sku.name, tunneling:enableTunneling}" -o table
   ```

   ```text
   Name               Sku       Tunneling
   -----------------  --------  -----------
   ce-ha-lab-bastion  Standard  True
   ```

</Steps>

## トンネルを開く

値は手入力せず、`terraform output` から取得してください — リソース ID は手動で組み立てるべきものではありません。

<Steps>

1. Bastion ホスト名、リソースグループ、および対象 CE の VM リソース ID を読み取ります。

   ```bash
   cd terraform
   BASTION=$(terraform output -raw bastion_name)
   RG=$(terraform output -raw resource_group_name)
   VM_ID=$(terraform output -json ce_vm_ids | jq -r '.eastus01')
   ```

   ```text
   ce-ha-lab-bastion
   rg-mcn-ce-ha-rmordasiewicz
   /subscriptions/…/providers/Microsoft.Compute/virtualMachines/f5-xc-ce-vm-01
   ```

   <Aside type="caution" title="マップのキーはサイト名であり、VM 名ではありません">
   `ce_vm_ids` のキーは `eastus01`、`eastus02`、`eastus03` であり、**VM 名ではありません**。
   `jq -r '."f5-xc-ce-vm-01"'` のようなフィルターは `null` を返し、その後トンネルは
   空のリソース ID で失敗します。不明な場合は一覧を確認してください:

   ```bash
   terraform output -json ce_vm_ids | jq -r 'keys | join(", ")'
   ```

   ```text
   eastus01, eastus02, eastus03
   ```
   </Aside>

2. トンネルを開始します。停止するまでポートを開いたままにするため、バックグラウンドで実行するか、
   別のターミナルを使用してください。

   ```bash
   az network bastion tunnel \
     --name "$BASTION" \
     --resource-group "$RG" \
     --target-resource-id "$VM_ID" \
     --resource-port 65500 \
     --port 65500 &
   ```

   ```text
   WARNING: Opening tunnel on port: 65500
   WARNING: Tunnel is ready, connect on port 65500
   WARNING: Ctrl + C to close
   ```

   3 行すべての先頭に `WARNING:` が付いています。これは Azure CLI が進行状況を
   stderr に書き込んでいるもので、問題ではありません。接続する前に `Tunnel is ready` が
   表示されるまで待ってください。

3. リスナーがローカル、ループバック上にあることを確認します:

   ```bash
   lsof -nP -iTCP:65500 -sTCP:LISTEN
   ```

   ```text
   COMMAND   PID  USER  FD  TYPE  DEVICE  SIZE/OFF  NODE  NAME
   Python  41648  you   7u  IPv4  …            0t0   TCP  127.0.0.1:65500 (LISTEN)
   ```

4. コンソールを開きます。トンネルによってローカルになるため、アドレスはノードのアドレスではなく
   `localhost` です。

   ```bash
   open https://localhost:65500/          # macOS
   xdg-open https://localhost:65500/      # Linux
   ```

5. 完了したらトンネルを停止します — `Ctrl-C`、またはバックグラウンドで実行している場合は `kill %1`。
   開いたままにすると、ローカルポート 65500 と Bastion セッションが占有されます。

</Steps>

## 表示される内容

**ログインページではなく、認証情報ダイアログ。** コンソールは HTTP Basic 認証を使用するため、
ブラウザーが独自のユーザー名とパスワードのプロンプトを表示します。フォームは表示されません:

```bash
curl -skI https://localhost:65500/
```

```text
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Basic realm="Volterra Site Console"
Content-Length: 0
```

そのレルムを持つ `401` は、コンソールが正常に動作していることを示しています。
未認証のリクエストに対して返すべき応答がこれです。

**証明書の警告が、3 つの理由で同時に表示されます。** 証明書を直接確認すると:

```bash
openssl s_client -connect localhost:65500 -servername localhost </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
```

```text
subject=C=US, ST=California, L=Santa Clara, O=Volterra, OU=Volterra Edge Services, CN=site-local.volterra.io
issuer=C=US, ST=California, L=Santa Clara, O=Volterra, OU=Volterra Edge Services, CN=site-local.volterra.io
notBefore=Oct 25 04:51:31 2024 GMT
notAfter=Oct 25 04:51:31 2025 GMT
```

Subject と issuer が同じため、自己署名証明書です。名前は `site-local.volterra.io` ですが、
`localhost` に接続しているため一致しません。このデプロイが実行しているビルドでは、
**証明書は 2025 年 10 月 25 日に期限切れになりました** — アプライアンスがそれを搭載して出荷されており、
このリポジトリ内でそれを更新するものは何もありません。

率直なブラウザーの警告が表示されることを想定し、毎回それが表示されることを想定してください。
上記の subject 行が有用な部分です: ローカルポート 65500 でリッスンしている他の何かではなく、
アプライアンスに到達したことを確認する方法がこれです。

## 管理者認証情報

`admin` としてサインインします。**このドキュメントはパスワードを公開しておらず、公開すべきではありません。**

出荷直後の Customer Edge には F5 が公開しているデフォルトが搭載されており、F5 はそれを変更するよう求めています。
変更することは、後からの強化としてではなく、ノードのデプロイの一部として扱ってください。
ここでそれが見かけ以上に重要な理由が 2 つあります:

- このドキュメントは公開されています。フリートの現在のコンソールパスワードを記載すると、
  「Bastion で Reader を保持している」が、そのページを読んだすべての人にとって完全なアプライアンスアクセスになります。
- ドキュメントに公開されたパスワードは、誰かがローテーションした瞬間に無効になり、
  最も誤解を招く形で無効になります — 読者はページが古いのではなく、自分のアクセスが壊れていると結論づけます。

パスワードはチームが運用上のシークレットを保管している場所から取得してください。
答えが「まだ工場出荷時のデフォルトです」であれば、他のことをする前に変更してください。

<Aside type="caution" title="Terraform からパスワードを設定することは確認されていません">
サイトオブジェクトの `admin_user_credentials.admin_password` は、これを宣言的に設定する方法のように見えます。
ただし、このビルドのサイトコンソールへの到達は **確認されていない** ため、そうであると仮定しないでください。

[SSH ページ](../ssh/) もどちらの根拠としても読まないでください。`admin_password` が「何も変えなかった」
という発見は SSH 認証に対して測定されたものであり、`vpm` は `admin` ユーザーの SSH 認証を
完全にスキップします。それはコンソールについては何も示しません。
</Aside>

## トンネルがリソース ID を対象としなければならない理由

`--target-resource-id` は必須です。代わりにノードのアドレスを対象とすると拒否されます:

```bash
az network bastion tunnel --name "$BASTION" -g "$RG" \
  --target-ip-address 10.0.3.5 --resource-port 65500 --port 65501
```

```text
ERROR: Custom ports are not allowed. Allowed ports for Tunnel with IP connect is 22, 3389.
```

理由は IP ベースの接続が無効になっているからでは**ありません** — この Bastion では
`ip_connect_enabled` が `true` です。Microsoft は、その設定に関わらず、IP ベースの
ネイティブクライアント接続でのカスタムポートをサポートしていません
([Azure ドキュメント](https://learn.microsoft.com/azure/bastion/connect-ip-address))、
そして 65500 はカスタムポートです。ここで Bastion の設定を調査しても解決策はありません。リソース ID を使用してください。

## 動作しない場合

| 症状 | 原因 | 修正 |
| --- | --- | --- |
| `ERROR: Custom ports are not allowed. Allowed ports for Tunnel with IP connect is 22, 3389.` | `--target-ip-address` を使用した | `--target-resource-id` を使用する |
| `ERROR: Defined port is currently unavailable` | 別のトンネルがすでにそのローカルポートを保持している | 他のトンネルを停止するか、別の `--port` を渡す。`--resource-port` は 65500 のまま |
| トンネルが開始するがリソース ID が空 | `jq` フィルターがサイトキーではなく VM 名を使用した | `eastus01`/`02`/`03` をキーにする |
| `401 Unauthorized`、レルム `Volterra Site Console` | 障害ではない — 未認証リクエスト | `admin` 認証情報を提供する |
| ブラウザーが証明書を拒否する | 自己署名、名前不一致、2025 年 10 月以降に期限切れ | 想定内。Subject が `CN=site-local.volterra.io` であることを確認して続行する |

<Aside type="note" title="認可の失敗は再現されませんでした">
RBAC 権限の不足がこの失敗のもう一つの明らかな原因ですが、それを再現するには
共有デプロイからロールの割り当てを削除する必要があるため、ここでは逐語的なエラーとして
ドキュメント化されていません。トンネルが認可エラーで開始に失敗した場合は、
VM、そのネットワークインターフェイス (NIC)、および Bastion ホストの 3 つすべてに対する
Reader 権限を確認してください。
</Aside>
