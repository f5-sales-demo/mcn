2026-07-28 に本デプロイメントの CE 1 台から取得しました。どのノードかは
`sitecli/capture-manifest.json` に記録されており、`scripts/capture-sitecli.sh --check` が
稼働中の CE に対してコマンド群を再検証します。

すべての Customer Edge は `https://<sli-ip>:65500` で F5 のサイトコンソールを提供します。
本デプロイメントでは通常、これが最初に試すべき経路です。

要求されるものが最も少ない方法です。配布すべき SSH キーも、維持すべき踏み台ホストも、
ノード上のパブリック IP も、有効化のための VM 置き換えも不要です。誰が接続できるかは
**Azure RBAC の判断**になります。さらに、サイトが登録済みである必要もありません。本ページは
3 サイトすべてが `site_state: FAILED` を報告している状態で初めて取得され、同じノードが
`ONLINE` になった後にも変更なしで再検証されています。

難点は、サイトコンソールがノードの内部 (SLI) アドレスでのみ応答し、そのアドレスは VNet 内部からのみ
到達可能である点です。Azure Bastion は、ネットワーク上に他のものを配置することなくこのギャップを
埋めます。

<Aside type="note" title="ここで検証済みのこと、検証されていないこと">
本ページのすべてのコマンドとすべての出力は、本デプロイメントの `f5-xc-ce-vm-01` に対して
実行され、失敗も含めてそのまま再現されています。

**認証は検証済みです**: アプライアンスの `admin` 資格情報はトンネル経由で `200` を返します。
*検証されていない*のはコンソール自体です。以下には、内部に入った後に何が見えるか、何ができるかは
一切記述されていません。

**Azure RBAC は検証されていません。** すべての実行はサブスクリプション所有者として行われたため、
手順 2 の Reader 要件は、ここで測定されたものではなく Microsoft の文書化された要件です。
</Aside>

<Aside type="caution" title="Bastion はオプトインで、デフォルトではデプロイされません">
`enable_bastion` のデフォルトは `false` であるため、デフォルトの `terraform apply` では Bastion
ホストは存在せず、`terraform output -raw bastion_name` は `null` になります。
`terraform/terraform.tfvars` で `enable_bastion = true` を設定してください — 本デプロイメントでは
`true` になっています。

オプトインである理由はリスクではなくコストです。Standard SKU のホストは、誰かがトンネルを開いて
いるかどうかにかかわらず、プロビジョニングされた時点から時間単位の固定料金が課金されます。
`eastus` では標準で含まれる 2 つのスケールユニットに対して 0.29 USD/時 (小売価格、2026-07)、
月あたり約 212 USD です。デモでコンソールアクセスが不要になったら、再び無効にしてください。
</Aside>

## 開始する前に

<Steps>

1. Azure にサインインし、Bastion 拡張機能を追加します。トンネリングはネイティブクライアントの機能で、
   拡張機能はデフォルトではインストールされていません。

   ```bash
   az login
   az extension add --name bastion
   ```

2. CE 仮想マシン、そのネットワークインターフェイス、および Bastion ホストに対して **Reader** を
   保有してください。これは Microsoft の文書化された要件であり、**ここでは未検証**です。本デプロイ
   メントでのすべての実行はサブスクリプション所有者として行われたため、これより低い権限が十分か
   不十分かは示されていません。

3. Bastion がデプロイされ、必要な機能を備えていることを確認します。Basic SKU はトンネリングも
   IP ベース接続もサポートしないため、ここでの `Standard` と `True` はいずれも重要な意味を持ちます。

   ```bash
   az network bastion list -g "$(terraform output -raw resource_group_name)" \
     --query "[].{name:name, sku:sku.name, tunneling:enableTunneling}" -o table
   ```

   ```text
   Name               Sku       Tunneling
   -----------------  --------  -----------
   ce-ha-lab-bastion  Standard  True
   ```

</Steps>

## トンネルを開く

値は手入力せず `terraform output` から取得してください — リソース ID は手作業で組み立てるような
ものではありません。

<Steps>

1. Bastion ホストの名前、リソースグループ、対象 CE の VM リソース ID を読み取ります。

   ```bash
   cd terraform
   BASTION=$(terraform output -raw bastion_name)
   RG=$(terraform output -raw resource_group_name)
   VM_ID=$(terraform output -json ce_vm_ids | jq -r '.eastus01')
   ```

   ```text
   ce-ha-lab-bastion
   rg-mcn-ce-ha-rmordasiewicz
   /subscriptions/…/providers/Microsoft.Compute/virtualMachines/f5-xc-ce-vm-01
   ```

   <Aside type="caution" title="マップのキーはサイト名であり、VM 名ではありません">
   `ce_vm_ids` のキーは `eastus01`、`eastus02`、`eastus03` であり、**VM 名ではありません**。
   `jq -r '."f5-xc-ce-vm-01"'` のようなフィルターは `null` を返し、その結果トンネルは空の
   リソース ID で失敗します。不明な場合は一覧表示してください。

   ```bash
   terraform output -json ce_vm_ids | jq -r 'keys | join(", ")'
   ```

   ```text
   eastus01, eastus02, eastus03
   ```

   </Aside>

2. トンネルを開始します。停止するまでポートを開いたまま保持するため、バックグラウンドで実行するか、
   2 つ目のターミナルを使用してください。

   ```bash
   az network bastion tunnel \
     --name "$BASTION" \
     --resource-group "$RG" \
     --target-resource-id "$VM_ID" \
     --resource-port 65500 \
     --port 65500 &
   ```

   ```text
   WARNING: Opening tunnel on port: 65500
   WARNING: Tunnel is ready, connect on port 65500
   WARNING: Ctrl + C to close
   ```

   3 行すべてに `WARNING:` が付いています。これは Azure CLI が進行状況を stderr に書き出している
   だけで、問題ではありません。接続する前に `Tunnel is ready` を待ってください。

3. リスナーがローカルのループバック上にあることを確認します。

   ```bash
   lsof -nP -iTCP:65500 -sTCP:LISTEN
   ```

   ```text
   COMMAND   PID  USER  FD  TYPE  DEVICE  SIZE/OFF  NODE  NAME
   Python  41648  you   7u  IPv4  …            0t0   TCP  127.0.0.1:65500 (LISTEN)
   ```

4. コンソールを開きます。トンネルによりローカルになるため、アドレスはノードのアドレスではなく
   `localhost` です。

   ```bash
   open https://localhost:65500/          # macOS
   xdg-open https://localhost:65500/      # Linux
   ```

5. 終了したらトンネルを停止します — `Ctrl-C`、またはバックグラウンド実行した場合は `kill %1`。
   開いたままにしておくと、ローカルポート 65500 と Bastion セッションを保持し続けます。

</Steps>

## 表示される内容

**ログインページではなく、資格情報ダイアログです。** コンソールは HTTP Basic 認証を使用するため、
ブラウザが独自のユーザー名とパスワードのプロンプトを表示します。表示されるフォームはありません。

```bash
curl -skI https://localhost:65500/
```

```text
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Basic realm="Volterra Site Console"
Content-Type: text/html; charset=utf-8
Content-Length: 0
```

そのレルムを伴う `401` は、コンソールが正しく動作している証拠です。これは認証されていないリクエスト
が受け取るべき応答であり、同じ URL に `admin` 資格情報を渡すと `200` が返ります。これがブラウザを
開く前に資格情報を確認する方法です。

```bash
curl -sk -u admin -o /dev/null -w '%{http_code}\n' https://localhost:65500/
```

```text
Enter host password for user 'admin':
200
```

コロンなしの `-u admin` は、コマンドラインからパスワードを取得する代わりに `curl` にプロンプトを
表示させます。コマンドラインに書くと、シェル履歴やプロセス一覧に残ってしまいます。

**証明書の警告が、同時に 3 つの理由で表示されます。** 証明書を直接確認すると次のようになります。

```bash
openssl s_client -connect localhost:65500 -servername localhost </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
```

```text
subject=C=US, ST=California, L=Santa Clara, O=Volterra, OU=Volterra Edge Services, CN=site-local.volterra.io
issuer=C=US, ST=California, L=Santa Clara, O=Volterra, OU=Volterra Edge Services, CN=site-local.volterra.io
notBefore=Oct 25 04:51:31 2024 GMT
notAfter=Oct 25 04:51:31 2025 GMT
```

subject と issuer が同一なので自己署名です。名前は `site-local.volterra.io` ですが接続先は
`localhost` なので一致しません。そして本デプロイメントが動作しているビルドでは、
**証明書は 2025 年 10 月 25 日に期限切れになっています** — アプライアンスがそれを同梱しており、
このリポジトリ内には更新する仕組みはありません。

ブラウザからの明確な警告を、毎回想定してください。上記の subject 行が有用な部分です。これにより、
ローカルポート 65500 で待ち受ける別の何かではなく、アプライアンスに到達したことを確認できます。

## admin 資格情報

`admin` としてサインインします。**本ドキュメントはパスワードを公開しませんし、公開すべきではありません。**

<Aside type="danger" title="本デプロイメントでは、そのパスワードは今も F5 の工場出荷時デフォルトです">
これは推測ではなく測定された事実です。工場出荷時のデフォルト資格情報は、現時点で 3 台すべての CE で
認証され `200` を返します。F5 はそのデフォルトを公開し、変更することを要求していますが、変更されて
いません。

実際上の帰結として、本デプロイメントでは「Bastion に対する Reader を保有している」ことが、F5 の
公開ドキュメントに載っている値を知っている者にとっては、アプライアンスコンソールへの完全な
アクセスと同等になります。これを変更し、後からのハードニングではなくノードのデプロイの一部として
変更を扱ってください。
</Aside>

ここで公開しないことが見た目以上に重要である理由は 2 つあります。

- 本ドキュメントは公開されています。フリート全体の現在のコンソールパスワードを記載すれば、
  「Bastion に対する Reader を保有している」ことが、このページを読む誰にとってもアプライアンスへの
  完全なアクセスになってしまいます。
- ドキュメントに公開されたパスワードは、誰かがローテーションした瞬間に誤りになります。しかも最も
  誤解を招く形で誤りになります。読者は、ページが古いのではなく自分のアクセスが壊れていると
  結論づけてしまいます。

ローテーション後は、チームが運用上のシークレットを保管している場所から取得してください。

<Aside type="caution" title="Terraform からのパスワード設定は検証されていません">
サイトオブジェクトの `admin_user_credentials.admin_password` は、これを設定する宣言的な方法のように
見えます。しかし、本ビルドでサイトコンソールに反映されることは**確認されていない**ため、反映されると
想定しないでください。

[SSH のページ](../ssh/) をどちらの証拠としても読まないでください。そこでの `admin_password` が
「何も変えなかった」という所見は SSH 認証に対して測定されたものであり、`vpm` は `admin` ユーザーに
ついては SSH 認証を完全にスキップします。これはコンソールについては何も語っていません。
</Aside>

## トンネルがリソース ID を対象としなければならない理由

`--target-resource-id` は必須です。代わりにノードのアドレスを対象にすると拒否されます — 使用する
アドレスが何であれ拒否されるため、ここでは意図的に実際のアドレスを記載していません。

```bash
az network bastion tunnel --name "$BASTION" -g "$RG" \
  --target-ip-address <any-sli-address> --resource-port 65500 --port 65501
```

```text
ERROR: Custom ports are not allowed. Allowed ports for Tunnel with IP connect is 22, 3389.
```

理由は IP ベース接続が無効になっているからでは**ありません** — この Bastion では
`ip_connect_enabled` は `true` です。Microsoft はその設定にかかわらず、IP ベースのネイティブ
クライアント接続でのカスタムポートをサポートしていません
([Azure ドキュメント](https://learn.microsoft.com/azure/bastion/connect-ip-address))。そして
65500 はカスタムポートです。ここで Bastion の構成を調べても何も得られません。リソース ID を
使用してください。

## うまくいかない場合

| 症状 | 原因 | 対処 |
| --- | --- | --- |
| `ERROR: Custom ports are not allowed. Allowed ports for Tunnel with IP connect is 22, 3389.` | `--target-ip-address` を使用した | `--target-resource-id` を使用する |
| `ERROR: Defined port is currently unavailable` | 別のトンネルがそのローカルポートを既に保持している | 他のトンネルを停止する、または別の `--port` を指定する。`--resource-port` は 65500 のまま |
| `terraform output -raw bastion_name` が `null` または空 | Bastion がデプロイされていない | `enable_bastion = true` を設定して apply する |
| トンネルは開始するがリソース ID が空 | `jq` フィルターがサイトキーではなく VM 名を使用した | `eastus01`/`02`/`03` をキーにする |
| `401 Unauthorized`、レルム `Volterra Site Console` | 障害ではない — 認証されていないリクエスト | `admin` 資格情報を渡す |
| ブラウザが証明書を拒否する | 自己署名、名前の不一致、2025 年 10 月以降の期限切れ | 想定内。subject が `CN=site-local.volterra.io` であることを確認して続行する |

<Aside type="note" title="認可の失敗は再現されていません">
不十分な RBAC はこれが失敗するもう 1 つの明白な要因ですが、再現するには共有デプロイメントから
ロール割り当てを削除する必要があるため、ここでは実際のエラー文をそのまま記載していません。
トンネルが開始時に認可エラーで失敗した場合は、VM、その NIC、Bastion ホストの 3 つすべてについて
Reader を確認してください。
</Aside>
