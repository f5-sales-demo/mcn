Azure Serial Console は、Azure プラットフォームを通じてノードのエミュレートされたシリアルポートに接続します。F5 Distributed Cloud のコントロールプレーン、ノードのデータプレーン、あるいはノードが制御するネットワーク経路を一切経由しません。だからこそ、他のあらゆる手段が使えないときに機能します。

CE が**まったく起動しなかった**場合にこれを使用します。すなわち、登録に失敗した、サイトがテナントに存在しない、あるいはノードは起動しているが外部への経路がない、といったケースです。これらすべてのケースにおいて、[デバッグ API](../debug-api/) は中継するトンネルを持たず、[SSH はこのビルドでは認証できません](../ssh/)。

## 前提条件: ブート診断

Azure がシリアルコンソールを接続するには、VM 側でブート診断が有効になっている必要があります。これは `terraform/modules/ce-node` によって有効化されます:

```hcl
boot_diagnostics {}
```

空のブロックは Azure マネージドストレージを選択するため、管理すべき診断用ストレージアカウント、ライフサイクルポリシー、アクセスキーは存在しません。ノード上で確認します:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="有効化は遡及的に適用されません">
ブート診断は**ブート時**にシリアルログを取得します。すでに実行中の VM に対して有効化しても、すでに発生したブートのログは生成されないため、`az vm boot-diagnostics get-boot-log` は次のように応答します:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

これは想定された動作であり、障害ではありません。ブートログはノードが次に再起動した後に存在します。ただし、ライブコンソールへの接続は即座に機能します。ログには依存しません。
</Aside>

## ターミナルなしで可用性を確認する

接続にはインタラクティブなセッションが必要ですが、接続*できるかどうか*は 2 回の API 呼び出しで確認できます。どちらもヘルスチェックに有用です。

サービスはサブスクリプションに対して有効化されている必要があります。管理者はテナント全体で無効化できます:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

次に、特定のノードのシリアルポートへの接続を要求します:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

`wss://` で始まる `connectionString` — このデプロイメントでは `eastus.gateway.serialconsole.azure.com` — が返れば、コンソールは現時点で接続可能です。ブート診断が有効化される前は、この呼び出しには接続先が存在しませんでした。

<Aside type="danger" title="その接続文字列は資格情報です">
これは URL に埋め込まれた短命のベアラートークンです。ログに記録したり、チケットに貼り付けたり、コミットしたりしないでください。呼び出しが成功したことを示す際は、ホスト名のみを出力してください。
</Aside>

## 接続する

<Steps>

1. 拡張機能を一度インストールします:

   ```bash
   az extension add --name serial-console
   ```

2. 接続します:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. 接続先はシェルではなく、ノード自身のログインプロンプトです。これは Site CLI であり、ノード上に設定された資格情報が必要です。プロビジョニング時の管理者パスワード、またはパスワード変更エンドポイント経由で設定したものです。シリアルコンソールは*チャネル*が機能することを証明するだけで、認証を回避するものではありません。

</Steps>

`f5-xc-ce-vm-01` から取得したもので、systemd ユニットの出力が何も付け加えない中間部分は省略しています:

```text file=../../../_data/serial-console-boot.txt
```

このトランスクリプトの中で注目すべき点が 4 つあります。これらはデバッグ API では答えられない問いに答えてくれます:

- **cloud-init が完了した** — `Datasource DataSourceAzure`、22.37 秒で完了。登録されないノードは通常ここで失敗しており、それを確認できるのがここです。
- **両方のコンテナランタイムが起動した。** `Container Runtime Interface for OCI (CRI-O)` と `Docker Application Container Engine` はいずれも `[ OK ]` であり、これは [crictl](../../commands/system/crictl/) と [docker](../../commands/system/docker/) で人々を驚かせるデュアルランタイム挙動のブート時の証拠です。
- **`VP Manager image load` と `Argo Watch service`** — `vpm` と Argo が起動しています。
- **プロンプトはノード自身のもの**であり、監査バナーの背後にあります。シリアルコンソールで得られるのはログインプロンプトであり、セッションではありません。

<Aside type="caution" title="インタラクティブな接続には実際のターミナルが必要ですが、スクリプト化は可能です">
`az serial-console connect` はターミナルを raw モードにするため、パイプラインや TTY のないコンテキストからは実行できません。Azure に接続する前に、クライアント側で失敗します:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

このトレースバックはターミナル処理に関するものであり、シリアルコンソールの障害ではありません。

ただし、接続そのものは**自動化可能**です。CLI ではなく websocket を直接操作します。上記のトランスクリプトは TTY なしでその方法で取得されました。`scripts/serial_console_capture.py` を参照してください。これは、登録に失敗したノードから、人がターミナルの前に座ることなくブートの証拠を収集する方法です。
</Aside>

<Aside type="caution" title="再試行を想定してください: ゲートウェイはおよそ 2 回に 1 回拒否します">
ゲートウェイの最初のフレームは出力ではなくチャレンジであり、クライアントはベアラートークンで応答します。それを正しく行っても、ソケットはしばしば即座にクローズします:

```
[close] code=1011 reason=Connection not trusted
```

観測された挙動: 断続的に成功し、継続的に使用するとリソースグループ内のすべてのノードが拒否するようになります。数分前に機能していたノードも含めてです。`scripts/serial_console_capture.py` はデフォルトで再試行します。再試行がしばしば有効だからです。

**原因は特定されていません。** 除外された可能性は次のとおりです。それぞれもっともらしい推測であり、時間を浪費するためです:

| これではない | 確認方法 |
| --- | --- |
| ARM/コンピュートのスロットリング | それは ARM 呼び出しに対して HTTP `429` を返します。これは別のデータチャネル上での websocket クローズです。 |
| プロキシによる TLS インターセプト | `openssl s_client -connect <region>.gateway.serialconsole.azure.com:443 \| openssl x509 -noout -issuer`。正規の `O=Microsoft Corporation` 発行者であればこれは除外されます。プロキシベンダーが発行者であれば確定であり、対処は `*.serialconsole.azure.com` を許可リストに追加することです。 |
| ブート診断が無効 | `az vm show -g <rg> -n <vm> --query diagnosticsProfile` が `enabled: true` を報告していること。 |
| グラントとチャレンジの間のトークン不一致 | 両方に同一トークンを使うのは正しい手法ですが、クローズを防ぎません。 |

Azure の*文書化された*挙動として: **VM ごとに 1 つのシリアルコンソールセッションのみで、2 回目の成功したリクエストが最初のものを追い出します。** 追い出されたユーザーは切断されますがログアウトはされないため、シェルセッションは残ります。1 つのノードを 2 人でデバッグすると、互いを繰り返し追い出すことになります。

大量の作業には、これらの制限が一切ない[デバッグ API](../debug-api/) を優先してください。[SSH は代替手段になりません](../ssh/) — このビルドでは有効化できません。
</Aside>

<Aside type="caution" title="貼り付けは 2,048 文字に制限されています">
Azure はシリアルポートへの過負荷を避けるため、シリアルコンソールの貼り付け長を 2,048 文字に制限しています。長いコマンド、または複数のコマンドを 1 回の書き込みでまとめて送信すると、長さ制限としてではなく、ハングやスロットリングのように見える形で失敗します。

コマンドは個別に送信してください。これはシリアルコンソール経由の大量収集における実際の制約であり、その作業には[デバッグ API](../debug-api/) を優先すべきもう一つの理由です。
</Aside>

## API では見られないものがここでは見える

- **cloud-init** の実行、失敗、あるいはまったく起動しないこと — 登録されないノードの典型的な原因です。
- `register.ves.volterra.io` に対する**登録試行**。設定エラーやテナントに拒否されたトークンを含みます。
- あらゆるエージェントが起動する以前の**カーネルおよびブートメッセージ**。
- **有効なネットワーク経路がない**状態のノード。これは他のあらゆる経路を無効にします。

`ONLINE` である*ノード*については、デバッグ API を優先してください。スクリプト化可能で、再実行できる証拠を生成し、唯一のシリアルポートを占有しません。
