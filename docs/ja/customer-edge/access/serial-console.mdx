Azure シリアルコンソールは、Azure プラットフォームを通じてノードのエミュレートされたシリアルポートに接続します。F5 Distributed Cloud コントロールプレーン、ノードのデータプレーン、またはノードが制御するネットワークパスを経由しません。これが、他の手段がすべて機能しない場合でも使用できる理由です。

CE が**起動しなかった**場合に使用してください。登録に失敗した、サイトがテナントに存在しない、またはノードは起動しているが外部への経路がない場合などが該当します。これらのケースでは、[デバッグ API](../debug-api/) がリレーするトンネルを持ちません。[SSH](../ssh/) は登録失敗後も機能しますが、最初のブート時にキーがすでに書き込まれており、VNet 内部からノードの内部アドレスに到達できる場合に限られます。初めて接続するノードでは、これらの条件は通常満たされていません。

## 前提条件: ブート診断

Azure は、シリアルコンソールを接続する前に VM のブート診断を有効にする必要があります。これは `terraform/modules/ce-node` によって有効化されます。

```hcl
boot_diagnostics {}
```

空のブロックは Azure 管理ストレージを選択するため、診断ストレージアカウント、ライフサイクルポリシー、またはアクセスキーを管理する必要はありません。ノードで確認するには次のコマンドを実行します。

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="有効化は遡及的ではありません">
ブート診断は**ブート時**にシリアルログをキャプチャします。すでに実行中の VM でこれを有効にしても、すでに発生したブートのログは生成されないため、`az vm boot-diagnostics get-boot-log` は次のように応答します。

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

これは想定される動作であり、障害ではありません。ブートログは次回のノード再起動後に存在します。一方、ライブコンソールの接続はすぐに機能します。ログには依存していません。
</Aside>

## ターミナルなしでの可用性確認

接続にはインタラクティブなセッションが必要ですが、接続*可能かどうか*は2回の API 呼び出しで確認できます。どちらもヘルスチェックに有用です。

サービスはサブスクリプションに対して有効である必要があります。管理者はテナント全体で無効にすることができます。

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

次に、特定のノードのシリアルポートへの接続を要求します。

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

`wss://` で始まる `connectionString`（このデプロイでは `eastus.gateway.serialconsole.azure.com`）が返された場合、コンソールは現在接続可能であることを意味します。ブート診断が有効化される前は、この呼び出しには接続先がありませんでした。

<Aside type="danger" title="この接続文字列はクレデンシャルです">
これは URL に埋め込まれた短命のベアラートークンです。ログに記録したり、チケットに貼り付けたり、コミットしたりしないでください。呼び出しが成功したことを示す際は、ホスト名のみを出力してください。
</Aside>

## 接続手順

<Steps>

1. 拡張機能を一度インストールします。

   ```bash
   az extension add --name serial-console
   ```

2. 接続します。

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. ノード自体のログインプロンプトが表示されます。シェルではありません。これは Site CLI であり、ノードに設定されたクレデンシャル（プロビジョニング時の管理者パスワード、またはパスワード変更エンドポイントで設定したもの）が必要です。シリアルコンソールは*チャネル*が機能することを証明しますが、認証をバイパスするものではありません。

</Steps>

`f5-xc-ce-vm-01` からキャプチャされたもので、systemd ユニットの出力が情報を追加しない中間部分は省略されています。

```text file=../../../_data/serial-console-boot.txt
```

このトランスクリプトで注目すべき点が4つあります。これらはデバッグ API では答えられない問いに答えるものです。

- **cloud-init が完了** — `Datasource DataSourceAzure`、22.37秒で完了。登録されないノードは通常ここで失敗しており、ここで確認できます。
- **両方のコンテナランタイムが起動。** `Container Runtime Interface for OCI (CRI-O)` と `Docker Application Container Engine` がそれぞれ `[ OK ]` であり、[crictl](../../commands/system/crictl/) や [docker](../../commands/system/docker/) で驚かれるデュアルランタイム動作のブート時の証拠です。
- **`VP Manager image load` と `Argo Watch service`** — `vpm` と Argo が起動中。
- **プロンプトはノード自体のもの**で、監査バナーの背後にあります。シリアルコンソールはセッションではなく、ログインプロンプトを提供します。

<Aside type="caution" title="インタラクティブな接続には実際のターミナルが必要ですが、スクリプト化は可能です">
`az serial-console connect` はターミナルをローモードにするため、パイプラインや TTY のないコンテキストでは実行できません。Azure に接続する前にクライアント側で失敗します。

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

このトレースバックはターミナル処理の問題であり、シリアルコンソールの障害ではありません。

ただし、接続自体は**自動化可能**です。CLI の代わりに WebSocket を直接操作します。上記のトランスクリプトはその方法でキャプチャされており、TTY は不要です。登録に失敗したノードから人間がターミナルに座ることなくブート証拠を収集する方法については、`scripts/serial_console_capture.py` を参照してください。
</Aside>

<Aside type="caution" title="リトライが必要な場合があります: ゲートウェイはほぼ1回おきに接続を拒否します">
ゲートウェイの最初のフレームは出力ではなくチャレンジであり、クライアントはベアラートークンで応答します。これが正しく行われた場合でも、ソケットはすぐに閉じられることがよくあります。

```
[close] code=1011 reason=Connection not trusted
```

観察された動作: 断続的に成功し、継続的に使用するとリソースグループ内のすべてのノードが拒否されます。数分前に機能していたノードも含まれます。`scripts/serial_console_capture.py` はデフォルトでリトライします。リトライが機能することが多いためです。

**原因は特定されていません。** 次のものは、もっともらしい推測として時間を無駄にする可能性があるため、除外されています。

| 原因ではないもの | 確認方法 |
| --- | --- |
| ARM/コンピューティングスロットリング | ARM 呼び出しで HTTP `429` が返されます。これは別のデータチャネルでの WebSocket クローズです。 |
| プロキシによる TLS インターセプション | `openssl s_client -connect <region>.gateway.serialconsole.azure.com:443 \| openssl x509 -noout -issuer`。本物の `O=Microsoft Corporation` 発行者であれば除外できます。プロキシベンダーが発行者として表示される場合は確認でき、修正方法は `*.serialconsole.azure.com` を許可リストに追加することです。 |
| ブート診断が無効 | `az vm show -g <rg> -n <vm> --query diagnosticsProfile` で `enabled: true` が報告される場合。 |
| 付与とチャレンジ間のトークン不一致 | 両方に1つのトークンを使用することが正しい方法ですが、クローズを防げません。 |

**ドキュメント化された Azure の動作**: **VM ごとに1つのシリアルコンソールセッション**であり、2番目の成功した要求は最初のセッションを排除します。排除されたユーザーは切断されますが、ログアウトされないため、シェルセッションは維持されます。1つのノードをデバッグする2人のユーザーは繰り返し互いを切断し合います。

大量の作業には [デバッグ API](../debug-api/) または [SSH](../ssh/) を優先してください。どちらもこれらの制限がありません。特に SSH は貼り付け制限もシングルセッション制限もないため、VNet 内部からノードに到達できる場合は SSH が適しています。
</Aside>

<Aside type="caution" title="貼り付けは2,048文字に制限されています">
Azure はシリアルポートへの過負荷を防ぐために、シリアルコンソールの貼り付け長を2,048文字に制限しています。長いコマンドや複数のコマンドを一度に送信すると、長さ制限としてではなく、ハングやスロットルのように見える形で失敗します。

コマンドは個別に送信してください。これはシリアルコンソールでの大量収集に対する実際の制約であり、この作業には [デバッグ API](../debug-api/) を優先するもう一つの理由です。
</Aside>

## API では確認できないが、ここで確認できること

- **cloud-init** の実行、失敗、または未開始 — 登録されないノードの通常の原因。
- `register.ves.volterra.io` に対する**登録試行**（設定エラーやテナントが拒否したトークンを含む）。
- エージェントが実行される前の**カーネルおよびブートメッセージ**。
- **機能するネットワークパスがない**ノード（他のすべての経路を無効にします）。

ノードが `ONLINE` 状態の場合は、デバッグ API を優先してください。スクリプト化可能で、再実行可能な証拠を生成し、単一のシリアルポートを占有しません。
