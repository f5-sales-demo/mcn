Azure シリアルコンソールは、Azure プラットフォームを通じてノードのエミュレートされたシリアルポートに接続します。F5 Distributed Cloud コントロールプレーン、ノードのデータプレーン、またはノードが制御するネットワークパスを経由しないため、他の手段がすべて機能しない場合でも利用できます。

CE が**一度も起動しなかった**場合に使用してください。具体的には、登録に失敗した場合、テナントにサイトが存在しない場合、またはノードは起動しているが外部への経路がない場合です。これらのケースでは [debug API](../debug-api/) がリレーするトンネルを持たず、SSH はノードの出荷時に閉じられています。

## 前提条件: ブート診断

Azure では、シリアルコンソールを接続する前に VM のブート診断が有効になっている必要があります。これは `terraform/modules/ce-node` によって有効化されます:

```hcl
boot_diagnostics {}
```

空のブロックは Azure 管理ストレージを選択するため、診断用ストレージアカウント、ライフサイクルポリシー、またはアクセスキーを管理する必要はありません。ノードで確認するには次のコマンドを実行します:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="有効化は遡及されません">
ブート診断はシリアルログを**ブート時**にキャプチャします。すでに実行中の VM に対して有効にしても、既に完了したブートのログは生成されないため、`az vm boot-diagnostics get-boot-log` は次のように応答します:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

これは想定された動作であり、障害ではありません。ブートログはノードが次回再起動した後に生成されます。一方、ライブコンソールへの接続はログに依存しないため、すぐに機能します。
</Aside>

## ターミナルなしでの利用可否確認

接続にはインタラクティブなセッションが必要ですが、接続が*可能かどうか*は2つの API 呼び出しで確認できます。どちらもヘルスチェックとして有用です。

サービスがサブスクリプションで有効になっている必要があります。管理者はテナント全体で無効化できます:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

次に、特定のノードのシリアルポートへの接続を要求します:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

`wss://` で始まる `connectionString` — このデプロイメントでは `eastus.gateway.serialconsole.azure.com` — が返された場合、コンソールは現時点で接続可能です。ブート診断が有効化される前は、この呼び出しには接続先がありませんでした。

<Aside type="danger" title="この接続文字列はクレデンシャルです">
これは URL に埋め込まれた短命のベアラートークンです。ログに記録したり、チケットに貼り付けたり、コミットしたりしないでください。呼び出しが成功したことを示す場合は、ホスト名のみを表示してください。
</Aside>

## 接続手順

<Steps>

1. 拡張機能を一度インストールします:

   ```bash
   az extension add --name serial-console
   ```

2. 接続します:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. シェルではなく、ノード自身のログインプロンプトが表示されます。これは Site CLI であり、ノードに設定されたクレデンシャル（プロビジョニング時の管理者パスワード、またはパスワード変更エンドポイントで設定したもの）が必要です。シリアルコンソールは*チャネル*が機能していることを確認しますが、認証をバイパスするものではありません。

</Steps>

`f5-xc-ce-vm-01` からキャプチャしたトランスクリプトです（systemd ユニットの出力が不要な中間部分は省略しています）:

```text file=../../../_data/serial-console-boot.txt
```

このトランスクリプトには、デバッグ API では確認できない4つの注目すべき点があります:

- **cloud-init が完了した** — `Datasource DataSourceAzure`、22.37秒で完了。登録されないノードは通常ここで失敗しており、その様子をここで確認できます。
- **両方のコンテナランタイムが起動した。** `Container Runtime Interface for OCI (CRI-O)` と `Docker Application Container Engine` がそれぞれ `[ OK ]` となっており、[crictl](../../commands/system/crictl/) および [docker](../../commands/system/docker/) で驚かれるデュアルランタイムの動作をブート時に確認できます。
- **`VP Manager image load` および `Argo Watch service`** — `vpm` と Argo が起動している。
- **プロンプトはノード自身のもの**であり、監査バナーの後に表示されます。シリアルコンソールではセッションではなくログインプロンプトが表示されます。

<Aside type="caution" title="インタラクティブな接続には実際のターミナルが必要ですが、スクリプト化は可能です">
`az serial-console connect` はターミナルを raw モードにするため、パイプラインや TTY のないコンテキストでは実行できません。Azure に接続する前にクライアント側で失敗します:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

このトレースバックはターミナルの処理に関するものであり、シリアルコンソールの障害ではありません。

ただし、接続自体は**自動化可能**です。CLI の代わりに WebSocket を直接操作することで実現できます。上記のトランスクリプトはその方法でキャプチャされており、TTY を必要としません。登録に失敗したノードから、人間がターミナルに張り付くことなくブートの証跡を収集する方法については、`scripts/serial_console_capture.py` を参照してください。
</Aside>

<Aside type="caution" title="リトライを前提としてください: ゲートウェイはおよそ1回おきに接続を拒否します">
ゲートウェイの最初のフレームは出力ではなくチャレンジであり、クライアントはベアラートークンで応答します。正しく処理された場合でも、ソケットがすぐに閉じられることがよくあります:

```
[close] code=1011 reason=Connection not trusted
```

3つのノードで繰り返し計測したところ、この動作は交互に発生します。つまり、拒否された後、同じノードへの次の試行は成功します。これは以前のセッションがまだ保持されており、拒否された試行がそれをクリアしているためと考えられます。

メッセージの内容に反して、**これはクレデンシャルの問題ではありません**。通常はリトライで解決するため、`scripts/serial_console_capture.py` はデフォルトでリトライを行います。

セッションリクエストとチャレンジの両方に同一のトークンを使用してください。これは `az` 拡張機能に合わせた正しいやり方ですが、この問題の原因ではありません。
</Aside>

## API では確認できない情報

- **cloud-init** の実行、失敗、または未起動 — 登録されないノードの通常の原因。
- `register.ves.volterra.io` への**登録の試み** — 設定エラーやテナントが拒否したトークンを含む。
- エージェントが起動する前の**カーネルおよびブートメッセージ**。
- **機能するネットワークパスがない**状態のノード — これは他のすべての手段を無効にします。

ノードが `ONLINE` 状態にある場合は、デバッグ API を優先してください。スクリプト化が可能で、再実行可能な証跡を生成でき、単一のシリアルポートを占有しません。
