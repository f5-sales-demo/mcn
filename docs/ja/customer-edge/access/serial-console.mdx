2026-07-28 に、このデプロイメントの 1 台の CE から取得しました。`sitecli/capture-manifest.json`
にどのノードかが記録されており、`scripts/capture-sitecli.sh --check` が稼働中の CE に対して
コマンド面を再検証します。

Azure シリアルコンソールは、Azure プラットフォームを通じてノードのエミュレートされた
シリアルポートに接続します。F5 Distributed Cloud のコントロールプレーン、ノードのデータ
プレーン、ノードが制御するネットワーク経路のいずれも経由しません。だからこそ、他のすべてが
機能しないときに動作するのです。

CE が **一度も起動しなかった** 場合にこれを使ってください。登録に失敗した、サイトがテナントに
存在しない、あるいはノードは起動しているが外部への経路がない、といったケースです。これらの
いずれの場合も、[デバッグ API](../debug-api/) には中継するトンネルがありません。[SSH](../ssh/)
は登録失敗後も利用できますが、それは初回ブート時に鍵が書き込まれており、かつ VNet 内部から
ノードの内部アドレスに到達できる場合に限られます。初めて向き合うノードでは、そのどちらも
成り立ちません。

ノードに **何らかの** 動作するネットワーク経路があるなら、これより先に
[サイトコンソール](../site-console/) を試してください。こちらも登録失敗後に利用でき、鍵も不要で、
すでにノードを見ている人を追い出すこともありません。シリアルコンソールは、壊れているのが
ネットワーク経路そのものである場合に残された手段です。

## 前提条件: ブート診断

Azure はシリアルコンソールを接続する前に、VM でブート診断が有効になっていることを要求します。
これは `terraform/modules/ce-node` で有効化されています。

```hcl
boot_diagnostics {}
```

空のブロックは Azure マネージドストレージを選択するため、所有・管理すべき診断ストレージ
アカウント、ライフサイクルポリシー、アクセスキーは存在しません。ノード上で確認します。

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="有効化は遡及적ではありません">
ブート診断は **ブート時** のシリアルログを取得します。すでに実行中の VM に対して有効化しても、
すでに発生済みのブートに対するログは生成されないため、
`az vm boot-diagnostics get-boot-log` はこう応答します。

```text
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

これは想定どおりの動作であり、障害ではありません。ノードが次に再起動した後にブートログが
存在するようになります。ただしライブのコンソール接続は即座に機能します。ログには依存しません。
</Aside>

## ターミナルなしで可用性を確認する

接続にはインタラクティブなセッションが必要ですが、接続 *できるかどうか* は 2 回の API 呼び出しで
分かります。どちらもヘルスチェックに有用です。

サービスはサブスクリプションに対して有効化されている必要があります。管理者はテナント全体で
無効化できます。

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

次に、特定のノードのシリアルポートへの接続を要求します。

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

`wss://` で始まる `connectionString`（このデプロイメントでは
`eastus.gateway.serialconsole.azure.com`）が返れば、コンソールは今すぐ接続可能ということです。
ブート診断を有効化する前は、この呼び出しには接続先が存在しませんでした。

<Aside type="danger" title="この接続文字列は資格情報です">
これは URL に埋め込まれた短命のベアラートークンです。ログに出力したり、チケットに貼り付けたり、
コミットしたりしないでください。呼び出しが成功したことを示す際は、ホストのみを表示してください。
</Aside>

## 接続する

<Steps>

1. 拡張機能を一度インストールします。

   ```bash
   az extension add --name serial-console
   ```

2. 接続します。

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. 到達するのはシェルではなく、アプライアンスの監査バナーの背後にあるノード自身のログイン
   プロンプトです。シリアルコンソールは *チャネル* が機能することを証明しますが、認証を
   バイパスするものではありません。

   <Aside type="caution" title="シリアルログインがどの資格情報を受け付けるかは未検証です">
   このデプロイメントではシリアルコンソール経由でのログインを完了した人がいないため、この
   ページでは何を入力するかを記載しません。`admin` はシェルが Site CLI であるアプライアンス
   アカウントであり、同じアカウントが
   [サイトコンソール](../site-console/) 経由でパスワードによって認証されます。しかし、
   シリアルコンソールのログインでパスワードが機能することは示されておらず、`admin` に対する
   `sshd` は鍵のみのため、この 2 つは明らかに同一の資格情報経路ではありません。
   </Aside>

</Steps>

`f5-xc-ce-vm-01` から取得したもので、systemd ユニットの出力が何も付け加えない中間部分は
省略しています。

```text file=../../../_data/serial-console-boot.txt
```

このトランスクリプトの中で注目に値するものが 4 つあります。デバッグ API では答えられない
問いに答えてくれるからです。

- **cloud-init が完了した** — `Datasource DataSourceAzure`、22.37 秒で終了。
  登録に至らないノードは通常ここで失敗しており、それが見えるのはこの場所です。
- **両方のコンテナランタイムが起動した。** `Container Runtime Interface for OCI (CRI-O)`
  と `Docker Application Container Engine` がそれぞれ `[ OK ]` になっており、これは
  [crictl](../../commands/system/crictl/) や [docker](../../commands/system/docker/) で
  人を驚かせるデュアルランタイム動作のブート時の証拠です。
- **`VP Manager image load` と `Argo Watch service`** — `vpm` と Argo の起動。
- **プロンプトはノード自身のもの** であり、その監査バナーの背後にあります。シリアルコンソールが
  得られるのはログインプロンプトであって、セッションではありません。

<Aside type="caution" title="インタラクティブな接続には実際のターミナルが必要ですが、スクリプト化は可能です">
`az serial-console connect` はターミナルを raw モードにするため、パイプラインや TTY のない
コンテキストからは実行できません。Azure に接続する前に、クライアント側で失敗します。

```text
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

このトレースバックはターミナル処理に関するものであり、シリアルコンソールの障害ではありません。

ただし接続自体は **自動化可能です** — CLI の代わりに websocket を直接操作します。上記の
トランスクリプトは TTY なしでその方法で取得しました。`scripts/serial_console_capture.py` を
参照してください。これは、ターミナルの前に人が座らずに、登録に失敗したノードからブートの
証拠を収集する方法です。
</Aside>

<Aside type="caution" title="リトライを想定してください: ゲートウェイはおおよそ 2 回に 1 回拒否します">
ゲートウェイの最初のフレームは出力ではなくチャレンジであり、クライアントはベアラートークンで
応答します。それを正しく行っても、ソケットはしばしば即座にクローズします。

```text
[close] code=1011 reason=Connection not trusted
```

観測された挙動: 断続的に成功し、継続的に使用するとリソースグループ内のすべてのノードが
拒否するようになります。数分前に成功していたノードも含めてです。
`scripts/serial_console_capture.py` はデフォルトでリトライします。リトライすればしばしば
成功するからです。

**原因は特定されていません。** 除外できたものは以下のとおりです。いずれも時間を無駄にする
もっともらしい推測だからです。

| これではない | 確認方法 |
| --- | --- |
| ARM/コンピュートのスロットリング | それは ARM 呼び出しに対して HTTP `429` を返します。これは別のデータチャネル上での websocket クローズです。 |
| プロキシによる TLS インターセプト | `openssl s_client -connect <region>.gateway.serialconsole.azure.com:443 \| openssl x509 -noout -issuer`。正規の `O=Microsoft Corporation` 発行者ならこれは除外されます。プロキシベンダーが発行者ならこれが確定し、対処は `*.serialconsole.azure.com` の許可リスト登録です。 |
| ブート診断が無効 | `az vm show -g <rg> -n <vm> --query diagnosticsProfile` が `enabled: true` を報告していること。 |
| 付与時とチャレンジ時でのトークン不一致 | 両方に同じトークンを使うのが正しい方法ですが、クローズを防ぐことはできません。 |

一方で、**ドキュメント化された Azure の挙動** は次のとおりです。**VM ごとにシリアルコンソール
セッションは 1 つのみで、2 番目のリクエストが成功すると 1 番目を追い出します。** 追い出された
ユーザーは切断されますがログアウトはされないため、シェルセッションは維持されます。1 つのノードを
2 人でデバッグすると、互いを繰り返し追い出し合うことになります。

大量の作業には [デバッグ API](../debug-api/) または [SSH](../ssh/) を選んでください。どちらにも
これらの制限はありません。特に SSH には貼り付けの上限もシングルセッション制約もないため、
VNet 内部からノードに到達できる場合は常に SSH のほうが良い選択です。
</Aside>

<Aside type="caution" title="貼り付けは 2,048 文字が上限です">
Azure はシリアルポートへの過負荷を避けるため、シリアルコンソールの貼り付け長を 2,048 文字に
制限しています。長いコマンド、あるいは複数コマンドを 1 回の書き込みでまとめて送信すると、
長さ制限ではなくハングやスロットリングのように見える形で失敗します。

コマンドは個別に送信してください。これはシリアルコンソール上での大量収集における実際の制約
であり、その作業には [デバッグ API](../debug-api/) を選ぶべきもう一つの理由です。
</Aside>

## API では見せられないが、ここで見えるもの

- **cloud-init** の実行、失敗、あるいはまったく開始されていない状態 — 登録に至らない
  ノードの通常の原因です。
- `register.ves.volterra.io` に対する **登録試行**。設定エラーや、テナントが拒否した
  トークンも含みます。
- どのエージェントも稼働する前の **カーネルおよびブートメッセージ**。
- **動作するネットワーク経路がない** 状態のノード。これは他のあらゆる経路を無効にします。

`ONLINE` である ノードには、デバッグ API を選んでください。スクリプト化可能であり、再実行できる
証拠を生成し、唯一のシリアルポートを占有しません。
