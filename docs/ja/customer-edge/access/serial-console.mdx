Azure シリアルコンソールは、Azure プラットフォームを通じてノードのエミュレートされた
シリアルポートに接続します。F5 Distributed Cloud のコントロールプレーン、ノードの
データプレーン、あるいはノードが制御するネットワーク経路のいずれも経由しません。だからこそ、
他のすべてが機能しないときに機能します。

CE が **一度も起動しなかった** 場合にこれを使用してください。登録に失敗した、サイトが
テナントに存在しない、ノードは起動しているが外部への経路がない、といった場合です。これらの
いずれのケースでも、[デバッグ API](../debug-api/) には中継するトンネルがありません。
[SSH](../ssh/) は登録失敗後も生き残りますが、それは初回ブート時に鍵が既に書き込まれており、
VNet 内部からノードの内部アドレスに到達できる場合に限られます。初めて対面するノードでは、
そのどちらも成立しません。

ノードに **何らかの** 機能するネットワーク経路がある場合は、これより先に
[サイトコンソール](../site-console/) を試してください。こちらも登録失敗後も生き残り、鍵を
必要とせず、既にノードを見ている人を追い出すこともありません。シリアルコンソールは、壊れて
いるものがネットワーク経路そのものである場合に残された手段です。

## 前提条件: ブート診断

Azure は、シリアルコンソールを接続する前に VM でブート診断が有効になっていることを要求します。
これは `terraform/modules/ce-node` によって有効化されます:

```hcl
boot_diagnostics {}
```

空のブロックは Azure マネージドストレージを選択するため、診断用ストレージアカウント、
ライフサイクルポリシー、アクセスキーを保有する必要はありません。ノード上で確認します:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="有効化は遡って適用されません">
ブート診断は **ブート時に** シリアルログを取得します。既に稼働している VM に対して有効化しても、
既に発生したブートのログは生成されないため、`az vm boot-diagnostics get-boot-log` はこう答えます:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

これは想定された動作であり、障害ではありません。ブートログはノードが次に再起動した後に存在します。
ただしライブコンソールへの接続は即座に機能します。ログには依存しません。
</Aside>

## ターミナルなしで可用性を確認する

接続にはインタラクティブなセッションが必要ですが、接続 *できるかどうか* は 2 つの API 呼び出しで
分かります。どちらもヘルスチェックに有用です。

サブスクリプションでサービスが有効になっている必要があります。管理者はテナント全体で無効化できます:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

次に、特定のノードのシリアルポートへの接続を要求します:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

`wss://` で始まる `connectionString`（このデプロイでは
`eastus.gateway.serialconsole.azure.com`）は、コンソールが今まさに接続可能であることを
意味します。ブート診断を有効化する前は、この呼び出しには接続先が存在しませんでした。

<Aside type="danger" title="その接続文字列は認証情報です">
これは URL に埋め込まれた短命のベアラートークンです。ログに記録したり、チケットに貼り付けたり、
コミットしたりしないでください。呼び出しが成功したことを示す際には、ホスト名のみを出力してください。
</Aside>

## 接続する

<Steps>

1. 拡張機能を一度インストールします:

   ```bash
   az extension add --name serial-console
   ```

2. 接続します:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. 到達するのはシェルではなく、アプライアンスの監査バナーの背後にあるノード自身のログイン
   プロンプトです。シリアルコンソールは *チャネル* が機能することを証明するものであり、認証を
   バイパスするものではありません。

   <Aside type="caution" title="シリアルログインがどの認証情報を受け付けるかは検証されていません">
   このデプロイでシリアルコンソール経由のログインを完了した人はいないため、このページでは何を
   入力すべきかを示しません。`admin` はシェルが Site CLI であるアプライアンスアカウントであり、
   同じアカウントは
   [サイトコンソール](../site-console/) 経由でパスワードによる認証を行います。しかし、シリアル
   コンソールのログインでパスワードが機能することは示されておらず、`sshd` は `admin` に対して
   鍵のみを受け付けるため、この 2 つは明確に同じ認証情報の経路ではありません。
   </Aside>

</Steps>

`f5-xc-ce-vm-01` から取得したもので、systemd ユニットの出力が何も付け加えない中間部分は
省略しています:

```text file=../../../_data/serial-console-boot.txt
```

このトランスクリプトの中で注目すべき点が 4 つあります。デバッグ API では答えられない疑問に
答えてくれるからです:

- **cloud-init が完了している** — `Datasource DataSourceAzure`、22.37 秒で完了。
  登録できないノードは通常ここで失敗しており、それが見えるのはここです。
- **両方のコンテナランタイムが起動している。** `Container Runtime Interface for OCI (CRI-O)`
  と `Docker Application Container Engine` はいずれも `[ OK ]` であり、これは
  [crictl](../../commands/system/crictl/) や [docker](../../commands/system/docker/) で
  人々を驚かせるデュアルランタイム動作のブート時における証拠です。
- **`VP Manager image load` と `Argo Watch service`** — `vpm` と Argo の起動。
- **プロンプトはノード自身のもの** で、その監査バナーの背後にあります。シリアルコンソールが
  提供するのはログインプロンプトであり、セッションではありません。

<Aside type="caution" title="インタラクティブな接続には実際のターミナルが必要ですが、スクリプト化は可能です">
`az serial-console connect` はターミナルを raw モードにするため、パイプラインや TTY のない
コンテキストからは実行できません。Azure に接続する前に、クライアント側で失敗します:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

このトレースバックはターミナル処理に関するものであり、シリアルコンソールの障害ではありません。

ただし接続自体は **自動化可能** です。CLI ではなく websocket を直接駆動します。上記の
トランスクリプトは TTY なしでその方法により取得されました。
`scripts/serial_console_capture.py` を参照してください。これは、登録に失敗したノードから
人がターミナルに座ることなくブートの証拠を収集する方法です。
</Aside>

<Aside type="caution" title="再試行を想定してください: ゲートウェイはおよそ 2 回に 1 回拒否します">
ゲートウェイの最初のフレームは出力ではなくチャレンジであり、クライアントはベアラートークンで
応答します。それを正しく行ってもソケットはしばしば即座にクローズされます:

```
[close] code=1011 reason=Connection not trusted
```

観測された挙動: 断続的に成功し、継続的に使用するとリソースグループ内のすべてのノードが拒否
するようになります。数分前には機能していたノードも含まれます。
`scripts/serial_console_capture.py` はデフォルトで再試行します。再試行がしばしば機能するからです。

**原因は特定されていません。** 除外されたものは以下のとおりです。いずれももっともらしい推測で
あり、時間を無駄にするためです:

| これではない | 確認方法 |
| --- | --- |
| ARM/コンピュートのスロットリング | それは ARM 呼び出しに対して HTTP `429` を返します。これは別のデータチャネル上での websocket クローズです。 |
| プロキシによる TLS インターセプト | `openssl s_client -connect <region>.gateway.serialconsole.azure.com:443 \| openssl x509 -noout -issuer`。正真正銘の `O=Microsoft Corporation` 発行者であればこれを除外できます。プロキシベンダーが発行者であればこれが該当し、対処は `*.serialconsole.azure.com` を許可リストに追加することです。 |
| ブート診断が無効 | `az vm show -g <rg> -n <vm> --query diagnosticsProfile` が `enabled: true` を報告していること。 |
| 付与とチャレンジ間のトークン不一致 | 両方に同一のトークンを使用するのは正しい手法ですが、クローズを防ぐことはできません。 |

*文書化されている* Azure の挙動は次のとおりです: **VM ごとにシリアルコンソールセッションは 1 つで、
2 回目のリクエストが成功すると最初のセッションは追い出されます。** 追い出されたユーザーは切断
されますがログアウトはされないため、シェルセッションは残ります。1 つのノードを 2 人でデバッグ
すると、互いを繰り返し追い出し合うことになります。

大量の作業には [デバッグ API](../debug-api/) または [SSH](../ssh/) を推奨します。どちらにも
これらの制限はありません。特に SSH はペーストの上限も単一セッションの制限もないため、ノードが
VNet 内部から到達可能な場合は常により良い選択です。
</Aside>

<Aside type="caution" title="ペーストは 2,048 文字に制限されています">
Azure はシリアルポートの過負荷を避けるため、シリアルコンソールのペースト長を 2,048 文字に
制限しています。長いコマンド、あるいは 1 回の書き込みでのコマンドのバッチ送信は、長さ制限
ではなくハングやスロットリングのように見える形で失敗します。

コマンドは個別に送信してください。これはシリアルコンソール経由での一括収集に対する実際の制約で
あり、その作業には [デバッグ API](../debug-api/) を推奨するもう一つの理由です。
</Aside>

## API では見られないものがここでは見える

- **cloud-init** の実行、失敗、あるいは起動しないこと。登録できないノードの典型的な原因です。
- `register.ves.volterra.io` に対する **登録試行**。設定エラーやテナントが拒否したトークンも含みます。
- エージェントが動作する前の **カーネルおよびブートメッセージ**。
- **機能するネットワーク経路がない** 状態のノード。これは他のあらゆる経路を無力化します。

`ONLINE` である ノードにはデバッグ API を推奨します。スクリプト化可能で、再実行できる証拠を
生成し、単一のシリアルポートを占有しません。
