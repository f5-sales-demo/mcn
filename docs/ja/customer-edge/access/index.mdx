3つの経路が利用できますが、どれが該当するかは好みではなく、ノードの状態と接続元の場所によって決まります。

| 経路 | ノードが `ONLINE` である必要 | ネットワーク到達性が必要 | 制限 | 対象範囲 |
| --- | --- | --- | --- | --- |
| [デバッグ API](./debug-api/) | **はい** | はい | 新規サイトでは約25〜30分のウォームアップが必要 | 34 コマンド |
| [SSH](./ssh/) | いいえ | VNet 内部から、内部アドレスに対してのみ | 初回ブート時点で鍵が存在している必要がある | オンボックス Site CLI の全機能 |
| [シリアルコンソール](./serial-console/) | いいえ | いいえ | VM ごとに1セッション、貼り付けは2,048文字まで | オンボックス Site CLI の全機能 |

シリアルコンソールは最後の手段であり、ネットワーク経路が一切機能していないノードでも使える唯一の経路です。

デバッグ API では不十分な場合に手を伸ばすべきなのが SSH です。アプライアンスは、その API が公開している34コマンドよりもはるかに多くのコマンドを提供しているためです。ただし2つの代償があります。鍵は cloud-init によって書き込まれるため、**初回ブート**時点で存在している必要があり、稼働中のノードで有効化するにはノードを置き換えることになります。そして現時点では、それによって登録処理が停止してしまいます（[issue 674](https://github.com/f5-sales-demo/mcn/issues/674)）。また、`sshd` はノードの内部アドレスでのみ応答するため、VNet 内部のホストが必要です。あなたがノードを識別しているアドレスに対してプローブしても、常に closed と報告されます。

## この使い分けが好みの問題ではない理由

デバッグ API は F5 Distributed Cloud のコントロールプレーンによって提供され、登録時に `vpm` が確立したトンネル経由でノードへ中継されます。登録がなければトンネルもなく、トンネルがなければ API には中継先が存在しません。

その失敗の仕方は明白ではなく分かりにくいため、一度も立ち上がらなかったノードが API の問題のように見えてしまいます。

シリアルコンソールはまったく逆の経路をたどり、Azure プラットフォームを介してノードのエミュレートされたシリアルポートに接続します。ノードが登録済みかどうか、ネットワーク到達性があるかどうか、データプレーンが機能しているかどうかを問いません。その独立性こそが要点であり、CE VM でブート診断を有効のままにしておかなければならない理由でもあります。

<Aside type="note" title="どちらを選ぶべきか">
自動化を記述する場合や、後で再実行したい証跡を収集する場合は、デバッグ API を使用してください。壊れているのが登録処理そのものである場合、シリアルコンソールはフォールバックではなく、唯一の選択肢です。
</Aside>

## 認証情報

各経路は異なる認証情報を使用し、そのいずれもコマンドラインに置くべきものではありません。

- **デバッグ API** — F5 Distributed Cloud の API トークンを `XCSH_API_TOKEN` として、テナント URL を `XCSH_API_URL` として指定します。`~/.config/xcsh/contexts/<tenant>.json` にある `xcsh` のコンテキストファイルが両方を保持しており、環境変数が指定されていない場合に `scripts/capture-sitecli.sh` が読み込むのはこのファイルです。
- **SSH** — デプロイ時に初回ブートで `/var/home/admin/.ssh/authorized_keys` に公開鍵が書き込まれた鍵ペアの秘密鍵と、内部アドレスに到達するための VNet 内部のホストが必要です。接続ユーザーは `azureuser` ではなく `admin` です。
- **シリアルコンソール** — 対話型の Azure ログインを使用します。これ用のサービスプリンシパルは存在しません。F5 の社内 Entra テナントではサービスプリンシパルのプロビジョニングが許可されておらず、これがこの手順のいずれも CI で実行できない理由でもあります。

<Aside type="danger" title="トークンを引数として渡さないこと">
コマンドラインに置かれたトークンはシェル履歴とプロセスリストに残り、そのマシン上の他のすべてのユーザーが読み取れる状態になります。`capture-sitecli.sh` がこの理由で `--token` を全面的に拒否し、代わりに標準入力経由で `curl` にヘッダーを渡しているのはそのためです。
</Aside>
