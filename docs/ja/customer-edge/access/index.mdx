3つのルートが利用可能であり、どのルートを使用するかは、設定の好みではなく、ノードの状態と接続元によって決まります。

| ルート | ノードの `ONLINE` が必要 | ネットワーク到達性が必要 | 制限事項 | 対象範囲 |
| --- | --- | --- | --- | --- |
| [デバッグ API](./debug-api/) | **はい** | はい | 新しいサイトでは約25〜30分のウォームアップが必要 | 34コマンド |
| [SSH](./ssh/) | いいえ | VNet 内から内部アドレスのみ | キーは初回起動時に存在している必要がある | オンボックス Site CLI の全機能 |
| [シリアルコンソール](./serial-console/) | いいえ | いいえ | VM ごとに1セッション、2,048文字のペースト上限 | オンボックス Site CLI の全機能 |

シリアルコンソールは最後の手段であり、ネットワークパスが機能していないノードでも使用できる唯一のルートです。

SSH は、デバッグ API では不十分な場合に使用します。アプライアンスは API が公開する34コマンドよりも実質的に多くのコマンドを提供しているためです。ただし、2つのコストがあります。キーは cloud-init によって書き込まれるため、**初回起動**時に存在している必要があります。つまり、稼働中のノードで有効にするとノードが置き換えられ、現在は登録がブロックされます（[issue 674](https://github.com/f5-sales-demo/mcn/issues/674)）。また、`sshd` はノードの内部アドレスにのみ応答するため、VNet 内にホストが必要です。ノードの既知のアドレスをプローブすると、常にクローズドと報告されます。

## この分割が設定の好みではない理由

デバッグ API は F5 Distributed Cloud コントロールプレーンによって提供され、登録時に `vpm` が確立するトンネルを経由してノードにリレーします。登録がない場合はトンネルがなく、API がリレーする先もありません。

明確なエラーではなく、わかりにくい方法で失敗するため、起動しなかったノードは API の問題のように見えます。

シリアルコンソールはまったく逆の方向から — Azure プラットフォームを通じてノードのエミュレートされたシリアルポートに — アクセスします。ノードが登録されているか、ネットワーク到達性があるか、またはデータプレーンが動作しているかを問いません。この独立性こそが重要であり、CE VM でブート診断を有効のままにしておく必要がある理由です。

<Aside type="note" title="使用するルートの選択">
自動化を作成している場合、または後で再実行したいエビデンスを収集する場合は、デバッグ API を使用してください。登録が壊れている場合、シリアルコンソールはフォールバックではなく — 唯一の選択肢です。
</Aside>

## 認証情報

両方のルートで異なる認証情報を使用し、どちらもコマンドラインに含めるべきではありません。

- **デバッグ API** — F5 Distributed Cloud API トークン（`XCSH_API_TOKEN` として）と、テナント URL（`XCSH_API_URL` として）。`~/.config/xcsh/contexts/<tenant>.json` の `xcsh` コンテキストファイルに両方が格納されており、環境変数が提供されていない場合に `scripts/capture-sitecli.sh` が読み取ります。
- **シリアルコンソール** — インタラクティブな Azure ログイン。このためのサービスプリンシパルはありません。F5 コーポレートの Entra テナントではプロビジョニングが許可されていないため、このプロセスのどの部分も CI では実行されません。

<Aside type="danger" title="トークンを引数として渡さないこと">
コマンドラインにトークンを含めると、シェル履歴およびプロセスリストに記録され、マシン上の他のすべてのユーザーが読み取れるようになります。`capture-sitecli.sh` はその理由から `--token` を完全に拒否し、代わりに `curl` にヘッダーを stdin 経由で提供します。
</Aside>
