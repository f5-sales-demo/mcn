2 つの経路が利用可能であり、どちらが適用されるかは好みではなくノードの状態によって決まります。

| 経路 | ノードが `ONLINE` である必要 | ネットワーク到達性の必要 | 制限 | 対象範囲 |
| --- | --- | --- | --- | --- |
| [Debug API](./debug-api/) | **あり** | あり | 新しいサイトではウォームアップに約 25〜30 分 | 34 コマンド |
| [シリアルコンソール](./serial-console/) | なし | なし | VM ごとに 1 セッション。貼り付けは 2,048 文字までという上限 | オンボックスの Site CLI 全機能 |

シリアルコンソールは最後の手段であり、ネットワーク経路が一切機能しないノードでも唯一使える経路です。

[**SSH は 3 番目の経路ではありません。**](./ssh/) このテナントが稼働しているビルドでは `admin` アカウントで認証できず、`vpm` が鍵を適用することもなく、それを変更するサイト設定も存在しません。このページはその根拠を記録するために存在します。そこでの失敗モードはどれもファイアウォールや認証情報の問題のように見えるためです。

## この分岐が好みの問題ではない理由

Debug API は F5 Distributed Cloud のコントロールプレーンによって提供され、登録時に `vpm` が確立するトンネルを経由してノードに中継されます。登録されていなければトンネルもなく、つまり API には中継先が存在しません。

明白な形ではなく分かりにくい形で失敗するため、そもそも起動しなかったノードが API の問題のように見えてしまいます。

シリアルコンソールはまったく別の道筋をたどります。Azure プラットフォームを経由してノードのエミュレートされたシリアルポートに接続します。ノードが登録済みかどうか、ネットワーク到達性があるかどうか、データプレーンが機能しているかどうかは一切問いません。この独立性こそが本質であり、CE VM でブート診断を有効のままにしておかなければならない理由です。

<Aside type="note" title="どちらを選ぶべきか">
自動化を書いている場合、または後で再実行したい証跡を収集している場合は Debug API を使用してください。登録そのものが壊れている場合、シリアルコンソールはフォールバックではなく唯一の選択肢です。
</Aside>

## 認証情報

2 つの経路はそれぞれ異なる認証情報を使用し、どちらもコマンドラインに置くべきものではありません。

- **Debug API** — F5 Distributed Cloud の API トークンを `XCSH_API_TOKEN` として、テナント URL を `XCSH_API_URL` として指定します。`~/.config/xcsh/contexts/<tenant>.json` にある `xcsh` のコンテキストファイルが両方を保持しており、環境変数が与えられていない場合に `scripts/capture-sitecli.sh` が読み取るのはこれです。
- **シリアルコンソール** — 対話的な Azure ログインを使用します。これ用のサービスプリンシパルは存在しません。F5 の社内 Entra テナントではサービスプリンシパルのプロビジョニングが許可されておらず、これがこの作業のどの部分も CI で実行されない理由でもあります。

<Aside type="danger" title="トークンを引数として渡してはいけません">
コマンドライン上のトークンはシェル履歴とプロセスリストに残り、そのマシンの他のすべてのユーザーが読み取れる状態になります。`capture-sitecli.sh` がその理由で `--token` を完全に拒否し、代わりにヘッダーを標準入力経由で `curl` に渡しているのはこのためです。
</Aside>
