`vpm/debug` API は、登録済みのノード上で Site CLI コマンドを実行し、その出力を返します。以下の内容はすべて稼働中のノードに対して確認したものであり、いずれもアップストリームでは公開されていません。

## コマンドカタログは自己記述的である

`command` キーを**省略**して `exec-user` に POST することで、ノードがサポートする内容を問い合わせられます:

```bash
curl -sS -X POST \
  -H "Authorization: APIToken $XCSH_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"namespace":"system","site":"<site>","node":"<node>"}' \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/<node>/exec-user" \
  | jq -r .output | jq .
```

レスポンスはコマンド名をキーとする JSON オブジェクトです:

```json
{
  "crictl-inspect": ["System Troubleshooting", "ExecUser", " container-id"],
  "diagnosis":      ["System Troubleshooting", "ExecUser", "no argument needed", "GLOBAL"],
  "ip-link-set":    ["Network Troubleshooting", "Exec", " (<device>||<group>) (up||down)"]
}
```

各エントリは `[category, tier, exampleArgument?, scope?]` であり、これらのフィールドは単なるドキュメントではありません。コマンドをどのように呼び出さなければならないかを決定します。

<Aside type="caution" title="キーは省略すること。誤った値を送信しないこと">
ディスカバリは `command` を省略することで動作します。代わりに未知の値を送信した場合、カタログではなくエラーが返ります:

```json
{"code":3,"details":[],"message":"exec command failed: command not supported"}
```

このメッセージは、*実在する* コマンドを誤ったエンドポイントに送信した場合にも返るため、「このコマンドは存在しない」と誤読しやすいものです。
</Aside>

## カタログエントリによって選択される 3 つのトランスポート

| 条件 | メソッドとパス | ボディ | 戻り値 |
| --- | --- | --- | --- |
| `scope` が `GLOBAL` | `GET .../vpm/debug/global/<cmd>` | なし | JSON |
| `tier` が `ExecUser` | `POST .../vpm/debug/<node>/exec-user` | `command` 配列 | テキスト |
| `tier` が `Exec` | `POST .../vpm/debug/<node>/exec` | `command` 配列 | テキスト |

### `ExecUser` — 読み取り専用の tier <Badge text="31 commands" variant="note" />

一般的なケースです。コマンドとその引数を、コマンド名を先頭にした配列として渡します:

```bash
curl -sS -X POST \
  -H "Authorization: APIToken $XCSH_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"namespace":"system","site":"<site>","node":"<node>","command":["crictl-ps"]}' \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/<node>/exec-user"
```

```json
{ "return_code": 0, "output": "CONTAINER    IMAGE    CREATED    STATE ..." }
```

引数は単一の文字列ではなく、個別の配列要素として指定します:

```json
{ "command": ["journalctl", "-u", "vpm", "-n", "200"] }
```

### `GLOBAL` — サイト全体を対象とし、まったく異なるトランスポートを使用する <Badge text="2 commands" variant="tip" />

`health` と `diagnosis` の 2 つのみです。これらは `global` パスへの `GET` リクエストであり、引数を取らず、ターミナルのテキストではなく構造化された JSON を返します。

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/global/health" | jq .
```

<Aside type="danger" title="GLOBAL コマンドは exec-user 経由では到達できない">
これは最も時間を無駄にしがちな罠です。`health` や `diagnosis` を `exec-user` に送信すると `command not supported` が返り、あたかもそのコマンドがノード上に存在しないかのように読めますが、実際には存在しており、誤ったトランスポートを使用しただけです。

```bash
# 誤り。返り値: exec command failed: command not supported
-d '{"namespace":"system","site":"…","node":"…","command":["health"]}'   # POST exec-user

# 正しい。
GET .../vpm/debug/global/health
```

</Aside>

### `Exec` — 特権 tier <Badge text="1 command on this build" variant="danger" />

別のエンドポイントであり、この tier は助言的なものではなく強制されます。`exec` は `ExecUser` のコマンドを同じ `command not supported` メッセージで拒否します。このメンバーはいずれもノードを変更するか、状態マーカーを読み取ります。

このテナントが稼働しているビルドでは、この tier には `ip-link-set` のみが含まれます。より新しいビルドでは `systemctl-restart-NetworkManager`、`systemctl-restart-crio`、`systemctl-restart-kubelet`、`systemctl-start-crio-prune`、および 3 つの `marker-exists-*` コマンドが追加されています。

<Aside type="danger" title="ここでは Exec コマンドを一切実行しない">
キャプチャハーネスはこの tier を拒否し、ハードコードされたリストではなく稼働中のカタログから tier を読み取ります。そのため、将来のビルドでコマンドが `Exec` に昇格されても、コードを編集することなく尊重されます。実行する場合は意図的に、かつ中断を許容できるノード上でのみ行ってください。
</Aside>

## サイト名とノード名を確認する

ノード名は Azure VM 名であり、`list-service` はそのノード上で稼働しているサービスと併せて確認できる手軽な方法です:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/global/list-service" \
  | jq -r '[.service[].node] | unique'
```

```json
["", "f5-xc-ce-vm-01"]
```

一部のサービスは空のノード名を報告するため、このリスト内の空文字列は 2 番目のノードではなくレスポンスの副産物です。また `list-service` は 34 コマンドのカタログには含まれていません。これはカタログが公表していない `global` エンドポイントであり、そのためここに記載しており、[コマンドリファレンス](../../commands/)には記載していません。

## このリポジトリのキャプチャを再現する

各コマンドページには `scripts/capture-sitecli.sh` によってキャプチャされた出力が埋め込まれており、このスクリプトは上記の 3 つのルールすべてを実装しています。

<Steps>

1. テナントを指定します。`XCSH_API_URL` と `XCSH_API_TOKEN` を読み取るか、アクティブな `xcsh` コンテキストにフォールバックします。

2. カタログを更新し、ドキュメントの前提となるノードが変更されていないことを確認します:

   ```bash
   bash scripts/capture-sitecli.sh --check
   ```

   これはコミット済みのカタログとソフトウェアビルドのみを比較します。ビルドの変更は、コマンドの追加・削除とは分けて報告されます。

3. 新しい証跡が必要な場合は再キャプチャします:

   ```bash
   bash scripts/capture-sitecli.sh
   ```

</Steps>

<Aside type="note" title="キャプチャは証跡であり、再現可能な成果物ではない">
カウンタ、稼働時間、コンテナの経過時間は実行ごとに変化するため、再キャプチャすると必ず差分が生じます。カタログは安定した契約であり、ノードが変更されていない限り実行間でバイト単位で同一です。`--check` が比較するのはこの部分です。長い出力は切り詰められ、明示的なマーカーで終わるため、切り詰められた表が完全なものとして表示されることはありません。
</Aside>

<Aside type="danger" title="顧客ノードからのキャプチャ: 秘匿化プロファイルを確認すること">
コマンド出力にはインフラストラクチャの識別情報 — 内部アドレッシング、MAC アドレス、AS 番号、ホスト名 — が含まれ、顧客にとってはこれが組織を特定できる情報となります。

そのためスクラブフィルタは、それらすべてを削除する **strict** プロファイルをデフォルトとしています。このリポジトリは `sitecli/capture-manifest.json` で `lab` を宣言しており、これらの詳細を保持しますが、これが正しいのはこれらのキャプチャが F5 所有のデモインフラストラクチャから取得されているためです。

**この設定を顧客のキャプチャに持ち込まないでください。** トークン、秘密鍵、テナント識別子、オブジェクト UUID、メールアドレス、ホームディレクトリパスは、いずれのプロファイルでも削除されます。

知っておくべき制限が 1 つあります。BGP ネイバーテーブルは AS をパターンの起点となるラベルのない単なる列として出力するため、ASN は private レンジに対する値の一致で判定されます。そこにある **public** な ASN は strict でも残るため、公開前に `show-ip-bgp*` の出力を手動でレビューする必要があります。
</Aside>
