[デバッグAPI](../../access/debug-api/)が公開するのは**34コマンド**です。アプライアンス自体は
**82コマンド**を提供しており、**そのうち55コマンドにはAPIの対応物がありません** — Vegaコントロールプレーン全体、
Envoyラッパー、パケットキャプチャ、kubeletパラメーターセット、`edit-*`ファイル、および
補助ルートアクセスペアは、ボックスからのみ到達可能です。

これらにアクセスするには[SSH](../../access/ssh/)または
[シリアルコンソール](../../access/serial-console/)が必要であり、どこにもドキュメント化されていない点が1つあります：

<Aside type="tip" title="execcliは隠しコマンドです">
`execcli`はSite CLIのインタラクティブメニューには表示されません。コマンド名を引数として受け取り、
`execcli ` に続けて**Tab**を入力すると、アプライアンス自身の各コマンドの1行説明とともに82コマンドすべてが一覧表示されます。
この補完メニューがビルドに対する正式なカタログであり、`sitecli/exec-catalog.json`に記録されているものです。
</Aside>

## 計測方法

以下のセットはベンダードキュメントから転記したものではありません。2台の稼働中ノードから読み取り、
その出所とともに`sitecli/exec-catalog.json`にコミットされました：

| | トップレベル | `execcli` |
| --- | --- | --- |
| `site_state: PROVISIONING`で計測 | 6 | 82 |
| `site_state: PROVISIONED`で計測 | 6 | 82 |

2回の実行は**同一のセット**を返しました。これは件数よりも重要です：つまり、コマンドサーフェスは
登録状態によって変化しないため、存在しないコマンドは本当に存在しないのであり、
まだ提供されていないわけではありません。

<Aside type="caution" title="存在しない5つのコマンド">
`factory-reset`、`upgrade`、`reboot`、`show`、`clear`は**このビルドには存在しません**。
これらはSite CLIが持っていそうなコマンドであり、その前提でしばらくこのリポジトリの分類に含まれていましたが、
どちらの列挙でも見つかりませんでした。トップレベルには正確に6つのエントリがあります：
`configure`、`configure-generic-hardware`、`configure-network`、`configure-http-proxy`、
`diagnosis`、`health`です。
</Aside>

## ドキュメント化されているものと一覧のみのもの

Customer EdgeはLinuxおよびいくつかのサードパーティデーモンで動作しています。それらのコマンドをドキュメント化すると
独自のリファレンスと重複し、F5がそれらを所有しているかのような印象を与えてしまいます。そのためルールは次のとおりです：
**F5のソフトウェアはドキュメント化し、それ以外については、CEに固有の内容のみをドキュメント化する。**

「自社のもの」と「他社のもの」は明確に分けられないため、3段階に分けています。この分類は
`sitecli/command-classification.json`に記録されています。

| 段階 | 扱い |
| --- | --- |
| **F5ソフトウェア** | 完全ドキュメント化 — 目的、構文、引数、キャプチャした出力、確認すべき内容。Argo、Vega、`vpm`、`vifdump`、`configure*`、`edit-*`セット、kubeletパラメーター、ルートアクセス。 |
| **CE固有の解釈** | CE上で特定の意味を持つサードパーティツール。CE固有の読み方をドキュメント化し、ツール自体のセマンティクスは上流に委ねます。 |
| **パススルー** | CE固有の説明がない、純粋なLinuxまたはサードパーティ。利用可能なものとして一覧表示し、上流へのポインターを示します。解説文はなし。 |

この区別がページが存在するかどうかを決定し、このドキュメントがmanページの劣化コピーに成り下がらないようにするための仕組みです。

## パススルー

ボックス上で利用可能ですが、**ここではドキュメント化しません** — これらはF5のソフトウェアではなく、
オペレーティングシステムおよびサードパーティデーモンであり、それら自身のリファレンスのほうが
このページで記述できる内容より優れています。

| コマンド | 上流 |
| --- | --- |
| `ping`, `netstat`, `lsof`, `ip`, `ip-link-show`, `nmcli`, `tracepath`, `dig` | iproute2, NetworkManager, BINDユーティリティ |
| `top`, `check-mem`, `sysctl`, `load-sysctl-conf`, `journalctl`, `files`, `rpm-ostree`, `chronyc-sources` | coreutils, procps, systemd, rpm-ostree, chrony |
| `edit-etc-hosts`, `edit-sysctl-conf` | これらのファイルはオペレーティングシステムのものです |
| `systemctl-status-crio`, `systemctl-status-docker`, `systemctl-status-kubelet`, `systemctl-status-iscsid`, `systemctl-status-multipathd` | systemd |
| `systemctl-restart-crio`, `systemctl-restart-docker`, `systemctl-restart-kubelet`, `systemctl-restart-iscsid`, `systemctl-restart-multipathd` | systemd — これらのコマンドはすべてノード上のワークロードを中断します |

これらのうち2つは、専用ページがなくても知っておく価値があります。`files`はファイル操作を実行し、
`/tmp`以下にのみ書き込みます。また、`systemctl-restart-*`はすべて定義上破壊的です —
`crio`や`kubelet`を再起動すると、そのノード上のワークロードが中断されます。

<Aside type="note" title="新しいビルドには存在するがこのビルドには存在しない7つのコマンド">
`collect-database-stats`、`iptables-lv`、3つの`marker-exists-*`コマンド、
`systemctl-restart-NetworkManager`、`systemctl-start-crio-prune`は、
ビルド`crt-20260201-0179`のデバッグAPIを通じて確認されました。これらは分類内の
`not_on_this_build.newer_build_debug_api`に記録されており、
`crt-20250613-3382`で実行できるものと誤解されないようにしています。

`collect-debug-info`は別のケースです：どのメニューにもカタログにも表示されません。
Site CLIのウェルカムテキストには、CLIが「サポートのためのデバッグ情報収集を…可能にする」と書かれているため、
この名前はおそらく実際の観測ではなくその文章から派生したものです。未検証とマークされており、
意図的にプローブしていません — 稼働中のノードに対して未知のコマンドを試験的に実行することは、
まだ登録中のCEで`vifdump`パケットキャプチャが開始されてしまった原因でもあります。
</Aside>
