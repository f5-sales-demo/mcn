Customer Edge に到達するコマンドセットは2つあり、どちらかがもう一方を含むことはありません。

- **ボックス上**では、Site CLI に **6つのトップレベルコマンド**と **82の `execcli` サブコマンド**があります。
- **ネットワーク越し**では、[デバッグ API](../../access/debug-api/) が独自の **34コマンド**のカタログを持ちます。

ボックス上の大部分には API に相当するものがありません。Vega コントロールプレーン全体、Envoy ラッパー、パケットキャプチャ、kubelet パラメーターセット、`edit-*` ファイル、補助ルートアクセスペアはボックスからのみ到達可能です。

これらにアクセスするには [SSH](../../access/ssh/) または[シリアルコンソール](../../access/serial-console/)が必要であり、どこにも記載されていないことが1点あります。

<Aside type="tip" title="execcli は非表示コマンドです">
`execcli` は Site CLI のインタラクティブメニューには表示されません。コマンド名を引数として受け取り、`execcli ` に続けて **Tab** キーを押すと、アプライアンス独自の各コマンドの1行説明とともに82個すべてが表示されます。この補完メニューがビルドの公式カタログであり、`sitecli/exec-catalog.json` に記録されています。
</Aside>

## 測定方法とセットの重複について

以下のセットはベンダードキュメントから転記したものではありません。`scripts/sitecli_ssh_harvest.py` を使ってライブノードから読み取り、その出所とともに `sitecli/exec-catalog.json` にコミットされています。3つの登録状態で3回実行しました。

| 測定時点 | トップレベル | `execcli` |
| --- | --- | --- |
| `site_state: PROVISIONING` | 6 | 82 |
| `site_state: PROVISIONED` | 6 | 82 |
| `site_state: ONLINE` | 6 | 82 |

3回すべてで**同一のセット**が返されました。同じ合計数だけでなく、同じ名前であり、最後の実行は異なるサイト名とリソース名を持つ別のデプロイメントでした。つまり、コマンドサーフェスは登録状態によって変化せず、存在しないコマンドは「まだ提供されていない」のではなく、本当に存在しないことを意味します。

デバッグ API の34コマンドと比較すると、2つの数字を明確に区別する必要があります。

- **51**の `execcli` サブコマンドには API に相当するものがありません。
- **55**は、ボックス上のサーフェス全体でカウントした場合の同じ数字です。`execcli` の下ではなくトップレベルに存在する4つの `configure*` コマンドも含まれるためです。

どちらも正しい数字です。一方を再計算してもう一方が出ても、間違いではありません。ここに記載されるすべての数字は `sitecli/catalog.json` および `sitecli/exec-catalog.json` から導出されています。

<Aside type="caution" title="存在しない5つのコマンド">
`factory-reset`、`upgrade`、`reboot`、`show`、`clear` はこのビルドには**存在しません**。これらは Site CLI が持っていそうなコマンドであり、そのような想定のもとでしばらくこのリポジトリの分類に含まれていましたが、列挙では一度も見つかりませんでした。トップレベルには正確に6つのエントリがあります。`configure`、`configure-generic-hardware`、`configure-network`、`configure-http-proxy`、`diagnosis`、`health` です。
</Aside>

<Aside type="caution" title="3つの API コマンドは execcli サブコマンドではありません">
`execcli` の下でこれらを検索しても何も見つからず、「コマンドが存在しない」と読み取れます。

- **`health`** と **`diagnosis`** は Site CLI の**トップレベル**コマンドです。`execcli` プレフィックスなしで `>>>` プロンプトから直接入力します。
- **`dig`** はデバッグ API 経由で到達可能であり、ボックス上のどちらのメニューにも**表示されません**。そのため、以下のパススルー一覧には含まれていません。API 専用です。

</Aside>

## ドキュメント化されているものと一覧のみのもの

Customer Edge は Linux と複数のサードパーティデーモンを実行しています。それらのコマンドをドキュメント化すると、それぞれのリファレンスと重複し、F5 がそれらを所有しているかのような印象を与えてしまいます。そのため、ルールは次のとおりです。**F5 のソフトウェアをドキュメント化し、それ以外については CE 固有のものだけをドキュメント化する。**

「自社のもの」と「他社のもの」は明確に分けられないため、3つの階層があります。この分類は `sitecli/command-classification.json` に記録されています。

| 階層 | 扱い |
| --- | --- |
| **F5 ソフトウェア** | 完全なドキュメント — 目的、構文、引数、キャプチャされた出力、確認すべき点。Argo、Vega、`vpm`、`vifdump`、`configure*`、`edit-*` セット、kubelet パラメーター、ルートアクセス。 |
| **CE 固有の解釈** | CE 上で特定の意味を持つサードパーティツール。CE 固有の読み方をドキュメント化し、ツール自体のセマンティクスはアップストリームに委ねます。 |
| **パススルー** | CE 固有の補足事項がない、純粋な Linux またはサードパーティ。利用可能として一覧表示し、アップストリームへのポインターを記載。説明文なし。 |

この区別がページを作成するかどうかを決定するものであり、このドキュメントがマンページの劣化コピーに成り下がらないようにするための仕組みです。

## パススルー

ボックス上で利用可能であり、**ここではドキュメント化されていません** — これらはオペレーティングシステムおよびサードパーティデーモンであり、F5 のソフトウェアではないため、それぞれのリファレンスのほうがこのページで再述するより優れています。

| コマンド | アップストリーム |
| --- | --- |
| `ping`, `netstat`, `lsof`, `ip`, `ip-link-show`, `nmcli`, `tracepath` | iproute2, NetworkManager |
| `top`, `check-mem`, `sysctl`, `load-sysctl-conf`, `journalctl`, `files`, `rpm-ostree`, `chronyc-sources` | coreutils, procps, systemd, rpm-ostree, chrony |
| `edit-etc-hosts`, `edit-sysctl-conf` | これらのファイルはオペレーティングシステムのものです |
| `systemctl-status-crio`, `systemctl-status-docker`, `systemctl-status-kubelet`, `systemctl-status-iscsid`, `systemctl-status-multipathd` | systemd |
| `systemctl-restart-crio`, `systemctl-restart-docker`, `systemctl-restart-kubelet`, `systemctl-restart-iscsid`, `systemctl-restart-multipathd` | systemd — これらはすべてノード上のワークロードを中断します |

これらのうち2つは、ページが存在しなくても知っておく価値があります。`files` はファイル操作を実行し、`/tmp` 配下にのみ書き込みます。そして `systemctl-restart-*` はすべて定義上破壊的です — `crio` または `kubelet` を再起動すると、そのノード上のワークロードが中断されます。

<Aside type="note" title="新しいビルドには存在するがこのビルドには存在しない7つのコマンド">
`collect-database-stats`、`iptables-lv`、3つの `marker-exists-*` コマンド、`systemctl-restart-NetworkManager`、`systemctl-start-crio-prune` は、ビルド `crt-20260201-0179` のデバッグ API を通じて確認されました。これらは分類内の `not_on_this_build.newer_build_debug_api` に記録されており、`crt-20250613-3382` で実行できるものと混同されないようにしています。

`collect-debug-info` は別のケースです。どのメニューにもカタログにも表示されません。Site CLI のウェルカムテキストには CLI が「サポート向けのデバッグ情報を収集できる」と記載されており、この名前はそのテキストから派生したものと考えられます。未確認としてマークされており、意図的にプローブは行いません — ライブノード上で未知のコマンドを試験的に実行することが、まだ登録中の CE で `vifdump` パケットキャプチャが起動してしまったきっかけでした。
</Aside>
