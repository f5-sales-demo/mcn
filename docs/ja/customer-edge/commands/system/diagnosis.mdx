## `diagnosis`

<Aside type="caution" title="GLOBAL スコープ — 異なるトランスポート">
`health` と同様に、`global` パスへの `GET` であり、`exec-user` 経由では到達できません。

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/global/diagnosis"
```

</Aside>

```json file=../../../../_data/sitecli-diagnosis.txt
```

結果はノードごとに報告されるため、マルチノードサイトではノードごとに 1 ブロックが返されます。
`gateway_connectivity` と `dns_connectivity` はそれぞれ ping のサマリー — `dest_ip`、`sent`、
`received`、`lost`、およびラウンドトリップ時間 — を含みます。

<Aside type="danger" title="完全に正常なノードでも両方の ping プローブが 100% ロスを報告する">
このトポロジーでは、サイトが `ONLINE` でトラフィックを転送しており `registration_status: OK` であるにもかかわらず、
**両方**の `gateway_connectivity`（`10.0.1.1` 宛）と `dns_connectivity`（`168.63.129.16` 宛）が
`sent: 5, received: 0, lost: 100` を報告します — 本稿の執筆中に改めて確認済みです。1 つのレスポンスに
`lost: 100` のブロックが 2 つ並ぶのは、このページで最も驚かせる見た目のものですが、
これが正常な状態です。

2 つのうち `dns_connectivity` の方がより誤解を招きます。DNS は明らかに機能しているからです。同じ
レスポンスの `dns_query_result` には、まさにそのリゾルバーに対する 10 件の成功したルックアップ
（`NOERROR`）が含まれています。このプローブは ICMP 到達性を測定しており、Azure のプラットフォーム
アドレスはそれに応答しません。つまり DNS を測定しているわけではありません。

いずれのフィールドも、すでに問題を示す別の証拠がある場合、または値が変化した場合にのみシグナルとして
扱ってください。
</Aside>

最初に読むべきフィールドはレスポンスの別の箇所にあります。`registration_status`、
`curl_response`（ノードが必要とする F5 エンドポイントごとに 1 エントリで、それぞれ `OK` かどうか）、
`dns_query_result`、および `ntp_sync_status` です。

`resolv_conf` は、ノードが実際に使用するリゾルバーを示します。[`dig`](../../network/dig/) に時間を
費やす前に、期待している内容と比較する価値があります。
