これらはカーネルの視点を報告します。Argo データプレーンは
[`vif`](../dataplane-forwarding/) を通じて確認できる独自の視点を保持しており、両者は一致しないことがあります。

## `ip`

`ip` サブコマンドを受け取ります。一般的なのは `addr` ですが、`route`、`link`、`neigh` も
使用できます。

```bash
{"command":["ip","addr"]}
```

```text file=../../../../_data/sitecli-ip.txt
```

CE は設計上 3 つの Azure NIC を持ちます — 管理/SLO、外部、内部/SLI — しかし
ゲストはその順序が示すような形でそれらを提示しません。そして出力を読み誤ると
時間を無駄にすることになるのはまさにこの点です。

| ゲスト内 | 担うもの |
| --- | --- |
| `a-i-eth0` | **アドレスをまったく持たない** — これは名称変更された物理 eth0 であり、Argo データプレーンが所有しています |
| `vhost0` | 管理/SLO アドレス。BGP のピア元となり、サイトオブジェクトが報告するアドレスです |
| `eth1` と `eth2` | 外部および内部/SLI アドレス — ただし**順序は固定されていません** |

<Aside type="danger" title="eth1 と eth2 のどちらが内部インターフェースかはノードごとに異なります">
この 1 つのデプロイメント内にある 3 台の CE から実際に読み取った結果: `f5-xc-ce-vm-01` と
`f5-xc-ce-vm-03` では内部/SLI アドレスは `eth2` にあり、`f5-xc-ce-vm-02` では
`eth1` にあります。設定上、これを選択しているものは何もありません。

したがって、インターフェース名からサブネットを推測してはならず、あるノードのマッピングを別のノードに
持ち込んでもいけません。代わりにアドレスで照合してください — CE アドレスが属するサブネットは、
それを保持するインターフェースが一定でなくても安定しています。
</Aside>

`a-i-eth0` がアドレスを持たないことは、管理アドレスで `sshd` に到達できない理由そのものでもあります。
ポートがブロックされているのではなく、そこにリスナーが存在しないのです。
[SSH](../../../access/ssh/) を参照してください。

## `ip-link-show`

リンク層のみ: 状態、MTU、キューイング規則、MAC。

```bash
{"command":["ip-link-show"]}
```

```text file=../../../../_data/sitecli-ip-link-show.txt
```

「リンクはアップしているか、その MTU は何か」を知りたい場合は `ip addr` より高速です。
MTU の不一致は、トンネルは確立するがトラフィックが通らないという事象の再発しやすい原因です。

## `ip-link-set` <Badge text="Exec ティア — 変更を伴う" variant="danger" />

インターフェースまたはグループをアップまたはダウンさせます。

```
ip-link-set (<device>||<group>) (up||down)
```

<Aside type="danger" title="ここでは実行しておらず、通常の方法では到達できません">
これはこのビルドにおける唯一の `Exec` ティアのコマンドです。`exec-user` ではなく `exec`
エンドポイントに送られ、ノードを変更します。リモート CE で `eth0` をダウンさせると、
デバッグ API 自体を含め、それを管理している経路が失われます。

このページには意図的にキャプチャされた出力がありません。キャプチャハーネスは
`Exec` ティア全体を拒否し、ハードコードされたリストではなくライブカタログから
ティアを読み取るため、将来のビルドで他のコマンドがこのティアに昇格しても
この記述は有効なままです。
</Aside>
