2026-07-28 に、このデプロイメントの 1 台の CE から取得しました。`sitecli/capture-manifest.json`
にどのノードかが記録されており、`scripts/capture-sitecli.sh --check` は稼働中の CE に対して
コマンド群を再検証します。

これらはカーネルの視点を報告します。Argo データプレーンは独自の視点を保持しており、
[`vif`](../dataplane-forwarding/) を通じて確認できます。両者は一致しないことがあります。

## `ip`

`ip` のサブコマンドを取ります。`addr` が一般的ですが、`route`、`link`、`neigh` も
動作します。

```bash
{"command":["ip","addr"]}
```

```text file=../../../../_data/sitecli-ip.txt
```

CE は設計上 3 つの Azure NIC を持ちます — 管理/SLO、外部、内部/SLI — しかしゲストは
その順序が示すような形でそれらを提示しません。そして、ここで出力を読み誤ると時間を
無駄にします。

| ゲスト内 | 担うもの |
| --- | --- |
| `a-i-eth0` | **アドレスをまったく持たない** — これはリネームされた物理 eth0 で、Argo データプレーンが所有します |
| `vhost0` | 管理/SLO アドレス。BGP のピアリング元であり、サイトオブジェクトが報告するアドレスです |
| `eth1` と `eth2` | 外部および内部/SLI アドレス — ただし **順序は固定されていません** |

<Aside type="danger" title="eth1 と eth2 のどちらが内部インターフェイスかはノードごとに異なります">
この 1 つのデプロイメントの 3 台の CE から実際に読み取った結果: `f5-xc-ce-vm-01` と
`f5-xc-ce-vm-03` では内部/SLI アドレスは `eth2` にあり、`f5-xc-ce-vm-02` では `eth1` に
あります。これを決定づける設定は何もありません。

したがって、インターフェイス名からサブネットを推測してはならず、あるノードのマッピングを
別のノードに持ち込んではなりません。代わりにアドレスで照合してください — CE のアドレスが
属するサブネットは、それを保持するインターフェイスが安定しなくても安定しています。
</Aside>

`a-i-eth0` がアドレスを持たないことは、管理アドレスで `sshd` に到達できない理由そのもの
でもあります。そこにはリスナーが存在しないのであって、ポートがブロックされている
わけではありません。[SSH](../../../access/ssh/) を参照してください。

## `ip-link-show`

リンク層のみ: 状態、MTU、キューイング規則、MAC。

```bash
{"command":["ip-link-show"]}
```

```text file=../../../../_data/sitecli-ip-link-show.txt
```

「リンクは up か、MTU は何か」という問いに対しては `ip addr` より高速です。
MTU の不一致は、確立はするがトラフィックが通らないトンネルの繰り返し発生する原因です。

## `ip-link-set` <Badge text="Exec ティア — 変更を伴う" variant="danger" />

インターフェイスまたはグループを up / down にします。

```
ip-link-set (<device>||<group>) (up||down)
```

<Aside type="danger" title="ここでは実行しておらず、通常の方法では到達できません">
これはこのビルドにおける唯一の `Exec` ティアのコマンドです。`exec-user` ではなく `exec`
エンドポイントに送られ、ノードを変更します。リモート CE で `eth0` を down にすると、
デバッグ API 自体を含め、それを管理している経路が失われます。

このページには意図的にキャプチャした出力がありません。キャプチャハーネスは `Exec`
ティア全体を拒否し、ハードコードされたリストではなく稼働中のカタログからティアを
読み取るため、将来のビルドが他のコマンドをこのティアに昇格させてもこの記述は有効なままです。
</Aside>
