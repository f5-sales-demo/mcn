Argo は転送状態を Linux カーネルとは別に保持します。
[`ip`](../ip/) とこれらのコマンドの内容が食い違う場合、実際にトラフィックを動かしているのはこれらのコマンドが示す情報です。

## `rt`

VRF ごとの vRouter ルートテーブルです。

```bash
{"command":["rt","--dump","2"]}
```

```text file=../../../../_data/sitecli-rt.txt
```

<Aside type="danger" title="VRF id は BGP が報告するものとは異なります">
`show-ip-bgp-summary` は `vrf-id 3` と出力します。これは FRR の採番であり、vRouter のテーブル id とは別の名前空間です。これをここに渡すと、ノードが壊れているように見える形で失敗します:

```
vRouter(Response):  [No such file or directory (2)]
```

`--dump 0` でも同じ応答が返ります。このトポロジでは **VRF 2** が値の入った inet4 テーブルであり、VRF 1 は 2 つのルートを保持しています。id が分からない場合は、BGP の出力を信頼するのではなく、1 から順に上へ探ってください。
</Aside>

## `nh`

ネクストホップテーブルです。すべてのルートはネクストホップ id を指しており、このコマンドがそれを解決します。

```bash
{"command":["nh","--list"]}
```

```text file=../../../../_data/sitecli-nh.txt
```

各エントリには `Type` と、それが属する VRF が含まれます。これらのノードでは 8 種類のタイプが出現し、その割合は次のとおりです。カウントすると 3 台の CE すべてで同一です:

```text
Tunnel 558   Encap 27   NAT 22   Vrf 16   Receive 14   Composite 4   Drop 2   Resolve 2
```

`Drop` ネクストホップに解決されるルートはブラックホールであり、プレフィックスが `rt` に存在するにもかかわらずトラフィックが消失する場合には、この組み合わせを確認する価値があります。

<Aside type="caution" title="上記のキャプチャは切り詰められているため、すべてのタイプは含まれていません">
これは 3,849 行のうち最初の 60 行です。圧倒的に最も多いタイプである `Tunnel` は、その 60 行にはまったく現れません。したがって、このキャプチャをタイプの完全な一覧として読まないでください。また、切り詰められたキャプチャに現れないからといって、そのタイプがノードに存在しないと結論づけないでください。上記のカウントは切り詰めていない応答から得たものです。
</Aside>

## `vif`

仮想インターフェイステーブルです。データプレーンが何にバインドしているか、およびインターフェイスごとのカウンターを示します。

```bash
{"command":["vif","--list"]}
```

```text file=../../../../_data/sitecli-vif.txt
```

先頭のフラグの凡例は一度目を通しておく価値があります。`Vp` は vhost 物理インターフェイスを、`Dpdk` は DPDK 管理下のインターフェイスを示します。これを使って、期待するインターフェイスがデータプレーンによって取得されていることを確認できます。また、トラフィックがカーネルに到達しないために Linux では表示されない RX および TX カウンターを確認できます。
