このデプロイメントの 1 台の CE から 2026-07-28 に取得しました。`sitecli/capture-manifest.json`
にどのノードかが記録されており、`scripts/capture-sitecli.sh --check` が稼働中の CE に対して
コマンド面を再検証します。

CE は BGP に FRR を使用します。このトポロジーでは 2 つの Azure Route Server
インスタンスとピアリングし、VIP をアドバタイズし、VNet プレフィックスを学習します。

## `show-ip-bgp-summary`

ここから始めてください。1 画面で、ピアリングが確立しているか、どれだけの期間
安定しているかが分かります。

```bash
{"command":["show-ip-bgp-summary"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp-summary.txt
```

まず `State/PfxRcd` を確認します。数値は受信したプレフィックス数であり、セッションが
確立していることを意味します。それ以外 — `Active`、`Connect`、`Idle` — はセッションが
確立していない状態です。`Up/Down` は現在の状態が続いている期間を示すため、
リセットを繰り返しているセッションは不自然に小さい値を示します。

<Aside type="caution" title="ここに表示される vrf id は rt が求めるものではありません">
この出力は `vrf-id 3` を報告しています。これは FRR の採番です。Argo データプレーンは
別のテーブル id を使用しており、FRR の番号を
[`rt --dump`](../dataplane-forwarding/) に渡すと `No such file or directory` が返ります。
これは引数が間違っているというより、ノードが壊れているように見えてしまいます。
</Aside>

## `show-ip-bgp`

ベストパス選択が可視化されたフルテーブルです。

```bash
{"command":["show-ip-bgp"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp.txt
```

`*` は有効なルート、`>` は選択されたベストパス、`=` はマルチパスのメンバーです。上記の
キャプチャでは、学習した VNet プレフィックス `10.0.0.0/16` に 2 つのパス — 各 Route Server
インスタンス経由で 1 つずつ — があり、`*=` と `*>` でマークされています。つまりベストパスに
加えてマルチパスメンバーがあるため、ノードは戻りトラフィックを両インスタンスで
ロードシェアします。VIP `10.250.0.10/32` はこのノードが起点となっているため、単一の `*>`
パスになります。

<Aside type="caution" title="このデモの等コストマルチパスはこの出力には現れません">
`show-ip-bgp` は 1 ノードのテーブルです。このデプロイメントが示す ECMP は複数の
*異なる* CE が同じ `/32` をアドバタイズするものであり、Azure 側でプログラムされます。
したがって単一の CE の BGP テーブルではそれを示すことはできず、ここで VIP に
マルチパスマーカーが無いことは障害ではありません。代わりに Route Server のピアリング、
またはクライアントの有効ルートテーブルから証明してください。どちらも
[検証ページ](../../../../demo/verify/) にあります。
</Aside>

## `show-ip-bgp-neighbors`

ネイバーごとの詳細: ネゴシエートされた機能、タイマー、メッセージカウンター、
および直近のリセット理由です。

```bash
{"command":["show-ip-bgp-neighbors"]}
```

サマリーでセッションのフラッピングが見られ、その理由を知る必要があるときに使用します。
`Last reset` とその理由が有用な行です。

<Aside type="note" title="このページにはまだキャプチャ出力がありません">
このキャプチャは `f5-sales-demo/docs-control#795` がマージされるまでコミットできません。
FRR が Graceful Restart の行で単語を誤記しており、`codespell` がファイルを拒否します。

キャプチャしたテキストを修正すると、このドキュメントが実際には発生していない出力を
説明することになるため、代わりに上流で修正されています。それまでの間は、ご自身の
ノードに対してコマンドを実行してください。
</Aside>

## `show-ip-bgp-neighbors-advertised-route`

このノードが知っている内容ではなく、ピアに伝えている内容です。

```bash
{"command":["show-ip-bgp-neighbors-advertised-route"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp-neighbors-advertised-route.txt
```

これは「VIP が VNet から到達できない」ときのためのコマンドです。ここに VIP が
存在しない場合、問題はこのノードにあり、ピアをいくら調べても解決には至りません。

出力は **ピアごとに** `bgp neighbor:` ブロックを繰り返すため、このトポロジーでは
同じ 2 つのプレフィックスが 2 回表示されます — 各 Route Server インスタンスに対して
1 回ずつです。これはレンダリングの重複ではなく、ノードが両方にアドバタイズしていることを
確認できるものです。一方のピアには存在するがもう一方には無い、あるいは内容が短い
ブロックがある場合が注目すべきケースです。
