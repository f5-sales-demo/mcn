CE は BGP のために FRR を実行しています。このトポロジーでは、2 つの Azure Route Server
インスタンスとピアリングし、VIP をアドバタイズし、VNet プレフィックスを学習します。

## `show-ip-bgp-summary`

ここから始めてください。1 画面で、ピアリングが確立しているか、そしてどれだけの期間
安定しているかがわかります。

```bash
{"command":["show-ip-bgp-summary"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp-summary.txt
```

まず `State/PfxRcd` を読んでください。数値は受信したプレフィックス数であり、セッションが
確立していることを意味します。それ以外 — `Active`、`Connect`、`Idle` — はセッションが
確立していないことを示します。`Up/Down` は現在の状態が継続している時間を示すため、
リセットを繰り返しているセッションは不自然に小さな値を示します。

<Aside type="caution" title="ここに表示される vrf id は rt が求めるものではありません">
この出力は `vrf-id 3` を報告しています。これは FRR の採番です。Argo データプレーンは
別のテーブル ID を使用しており、FRR の番号を
[`rt --dump`](../dataplane-forwarding/) に渡すと `No such file or directory` が返されます。
これは引数の誤りではなく、ノードが壊れているように見えてしまいます。
</Aside>

## `show-ip-bgp`

ベストパス選択が可視化された、フルテーブルです。

```bash
{"command":["show-ip-bgp"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp.txt
```

`*` は有効なルート、`>` は選択されたベストパス、`=` はマルチパスメンバーです。上のキャプチャでは、
学習された VNet プレフィックス `10.0.0.0/16` に 2 つのパス — 各 Route Server インスタンス経由に
1 つずつ — があり、`*=` と `*>` でマークされています。ベストパスに加えてマルチパスメンバーが
存在するため、ノードは戻りトラフィックを両インスタンスで負荷分散します。VIP `10.250.0.10/32` は
このノードが起点であるため、単一の `*>` パスを持ちます。

<Aside type="caution" title="このデモの 3 方向 ECMP はこの出力には表示されません">
`show-ip-bgp` は 1 つのノードのテーブルです。このデプロイメントが示す ECMP は、3 つの*異なる*
CE が同じ `/32` をアドバタイズしているものであり、Azure 側でプログラムされています。したがって、
単一の CE の BGP テーブルではそれを示すことはできず、ここで VIP にマルチパスマーカーがないことは
障害ではありません。代わりに Route Server のピアリング、またはクライアントの有効ルートテーブルから
確認してください。どちらも[as-built ページ](../../../../as-built/)にあります。
</Aside>

## `show-ip-bgp-neighbors`

ネイバーごとの詳細：ネゴシエートされた機能、タイマー、メッセージカウンター、そして
直近のリセット理由。

```bash
{"command":["show-ip-bgp-neighbors"]}
```

サマリーでセッションのフラッピングが見られ、その理由を知る必要があるときに使用してください。
`Last reset` とその理由が有用な行です。

<Aside type="note" title="このページにはまだキャプチャした出力がありません">
このキャプチャは `f5-sales-demo/docs-control#795` がマージされるまでコミットできません。FRR が
Graceful Restart の行で単語のスペルを誤っており、`codespell` がそのファイルを拒否します。

キャプチャしたテキストを修正すると、このドキュメントが実際には発生しなかった出力を記述することに
なるため、代わりにアップストリームで修正が進められています。それまでの間は、ご自身のノードに対して
コマンドを実行してください。
</Aside>

## `show-ip-bgp-neighbors-advertised-route`

このノードが知っている内容ではなく、ピアに対して伝えている内容です。

```bash
{"command":["show-ip-bgp-neighbors-advertised-route"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp-neighbors-advertised-route.txt
```

これは「VIP が VNet から到達できない」場合のためのコマンドです。ここに VIP が存在しない場合、
問題はこのノードにあり、ピア側をいくら調べても解決しません。

出力は**ピアごとに** `bgp neighbor:` ブロックを繰り返すため、このトポロジーでは同じ 2 つの
プレフィックスが 2 回表示されます — 各 Route Server インスタンスにつき 1 回です。これは重複した
レンダリングではなく、ノードが両方にアドバタイズしていることを裏付けるものです。片方のピアには
ブロックが存在するのに、もう片方が欠落している、または短い場合こそが注目すべきケースです。
