カスタマーエッジ (CE) は、このリポジトリが Azure にプロビジョニングする F5 Distributed Cloud ノードです。`terraform/modules/ce-node` モジュールを使用し、`volterraedgeservices/volterra-node` マーケットプレイスイメージからビルドされます。

データプレーン (Argo)、コントロールプレーン (Vega)、Envoy プロキシ、Kubernetes スタック、およびノードを登録してその他すべてを管理するエージェント `vpm` が稼働しています。

CE が正常に動作しない場合は、Site CLI が調査のための主要ツールとなります。最初の判断はどちらのアクセスパスが適用されるかを確認することです。誤った選択をすると、ノードが壊れているように見えて時間を無駄にしてしまいます。

## 2つのアクセスパス（互換性なし）

デバッグ API は **F5 Distributed Cloud コントロールプレーンを経由して**ノードに到達します。これが分岐の理由です。API は、ノードが登録され `ONLINE` と報告された後にのみ応答できます。

登録に失敗したノード — cloud-init の不具合、期限切れトークン、`register.ves.volterra.io` へのルートなし — は診断が最も必要なケースですが、まさにその場合に API は応答できません。

ノードは出荷時の設定で SSH を拒否します。ポート 22 は CE 自体で閉じられており、ネットワークセキュリティグループによるものではありません。

```console
$ ssh -o ConnectTimeout=10 admin@<ce-public-ip>
ssh: connect to host <ce-public-ip> port 22: Connection refused
```

VNet 内からも、同じサブネット上のジャンプホストからも確認済みです。そのため、セキュリティグループルールを開いても変わりません。

つまり、サイトが `ONLINE` であればデバッグ API を使用してください。そうでない場合は、シリアルコンソールが唯一のアクセス手段です。

<Aside type="caution" title="まずサイトの状態を確認してください">
次のリクエスト 1 回で、どちらのパスが該当するかを確認できます。

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/config/namespaces/system/sites/<site>" \
  | jq -r '.spec.site_state'
```

`ONLINE` であればデバッグ API が使用可能です。それ以外の値が返る場合、またはサイトが存在しない場合はシリアルコンソールを使用してください。
</Aside>

## 安全に関するルール

以下のルールは、以降のすべてのページにおけるすべてのコマンドに適用されます。

- **確信がない限り、読み取り専用の操作のみ行うこと。** コマンドは 2 つの権限レベルに分かれており、`Exec` レベルのコマンドはノードを変更するか、状態マーカーを読み取ります。これらのページおよびキャプチャハーネスでは `Exec` コマンドを実行しません。
- **コマンドの名前から安全性を判断しないこと。** `ip-link-set` はクエリのように見えますが、インターフェースをダウンさせます。`systemctl-restart-crio` はライブデータプレーン上のコンテナランタイムを再起動します。
- **質問に答えられる最も範囲の狭いコマンドを優先すること。** `health` と `diagnosis` はノードを低コストで要約できますが、`flow-l` は 629,760 エントリのフローテーブルをダンプします。
- **CE はライブトラフィックを処理しています。** これらは共有デモ環境です。デバッグ対象のサイトから誰かがプレゼンテーションを行っていることを前提としてください。

## このドキュメントの対象範囲

このテナントが実行しているソフトウェアビルドにおいて、デバッグ API からアクセス可能なすべてのコマンドを網羅しており、それぞれのコマンドの出力はライブノードから実際にキャプチャされたものであり、他の資料からの転記ではありません。

[コマンドリファレンス](./commands/)には、すべてのコマンドのカテゴリー、権限レベル、トランスポートが一覧表示されています。[ワークフロー](./workflows/)では、問題が発生した際に実際に使用する手順としてコマンドを連結しています。

Site CLI のノード上限定の部分 — `configure`、`configure-network`、`factory-reset`、`upgrade`、およびその他約 60 の `ExecCLI` コマンド — は対象外です。

これらはシリアルコンソールセッションからのみアクセス可能であり、プログラム的に検証することができません。未検証のコマンド構文はこのドキュメントが繰り返しを避けるために存在する欠陥そのものです。
