Customer Edge (CE) は、このリポジトリが Azure へプロビジョニングする F5 Distributed Cloud ノードです。`terraform/modules/ce-node` で定義され、`volterraedgeservices/volterra-node` マーケットプレイスイメージから構築されます。

CE 上では、データプレーン (Argo)、コントロールプレーン (Vega)、Envoy プロキシ、Kubernetes スタック、そしてノードを登録しその他すべてを管理するエージェントである `vpm` が動作します。

CE に問題が発生した場合、Site CLI が診断の手段となります。最初に判断すべきは、どのアクセス経路が該当するかです。これを誤ると、あたかもノードが故障しているかのように見える形で時間を浪費することになります。

## 2 つのアクセス経路 — 互いに置き換えることはできません

デバッグ API は **F5 Distributed Cloud コントロールプレーンを経由して** ノードに到達します。この区別が重要である理由はまさにそこにあります。API が応答できるのは、ノードが登録を完了し `ONLINE` を報告している場合に限られます。

登録に失敗したノード — 不正な cloud-init、期限切れのトークン、`register.ves.volterra.io` への経路がない、といったケース — こそが診断を必要とする状況であり、同時に API が対応できない状況でもあります。

SSH は第 3 の選択肢にはなりません。`sshd` はノード上で動作しており内部 (SLI) アドレスで応答しますが、`admin` アカウントでは認証できません。`vpm` がそのユーザーをスキップするため、サイトオブジェクトに設定した `ssh_key` は決して適用されません。セキュリティグループのルールを変更しても解決しません。その根拠は [SSH](./access/ssh/) のページに記載されています。このページが存在するのは、そこに挙げられたあらゆる症状がファイアウォールや認証情報の不具合のように見えるためです。

したがって、サイトが `ONLINE` であればデバッグ API を使用します。そうでなければ、シリアルコンソールが唯一の手段です。

<Aside type="caution" title="まずサイトの状態を確認してください">
どちらの経路をたどるべきかは、1 回のリクエストで判明します。

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/config/namespaces/system/sites/<site>" \
  | jq -r '.spec.site_state'
```

`ONLINE` であればデバッグ API が使用できます。それ以外の場合 — またはサイトが存在しない場合 — はシリアルコンソールを使用します。
</Aside>

## 安全のためのルール

以下は、これ以降のすべてのページのすべてのコマンドに当てはまります。

- **確信がない限り読み取り専用にとどめてください。** コマンド群は 2 つの権限階層に分かれており、`Exec` 階層はノードを変更するか、状態マーカーを読み取ります。これらのページで `Exec` コマンドを実行するものはなく、キャプチャハーネスも同様です。
- **コマンド名から安全だと判断しないでください。** `ip-link-set` はクエリのように読めますが、インターフェイスをダウンさせます。`systemctl-restart-crio` は稼働中のデータプレーンの下でコンテナランタイムを再起動します。
- **疑問に答えられる最も限定的なコマンドを選んでください。** `health` と `diagnosis` は低コストでノードの概要を示しますが、`flow-l` は 629,760 エントリのフローテーブルをダンプします。
- **CE は実トラフィックを処理しています。** これらは共有のデモ環境です。デバッグ対象のサイトから誰かがプレゼンテーションを行っていると想定してください。

## ここで文書化されている内容

このテナントが実行しているソフトウェアビルドにおいて、デバッグ API 経由で到達可能なすべてのコマンドを扱っており、いずれも他所から転記したものではなく、稼働中のノードから取得した出力を掲載しています。

[コマンドリファレンス](./commands/) はそれらすべてをカテゴリ、権限階層、トランスポートとともに一覧化しています。[ワークフロー](./workflows/) は、問題が発生した際に実際に使用する一連の手順としてそれらを連結します。

Site CLI のうちオンボックス専用の部分 — `configure`、`configure-network`、`factory-reset`、`upgrade`、およびおよそ 60 の追加 `ExecCLI` コマンド — は対象外です。

これらはシリアルコンソールセッションからのみ到達可能であるため、プログラムによる検証ができません。未検証のコマンド構文こそ、このドキュメントが繰り返しを避けようとしている欠陥です。
