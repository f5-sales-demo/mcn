Customer Edge (CE) とは、本リポジトリが Azure にプロビジョニングする F5 Distributed Cloud
ノードのことです — `terraform/modules/ce-node` で定義され、
`volterraedgeservices/volterra-node` マーケットプレイスイメージから構築されます。

CE では、データプレーン (Argo)、コントロールプレーン (Vega)、Envoy プロキシ、Kubernetes
スタック、そしてノードを登録しノード上のその他すべてを管理するエージェントである `vpm`
が動作します。

CE に問題が発生した際の診断手段は Site CLI です。最初に判断すべきは、どちらのアクセス経路が
該当するかであり、これを誤ると、あたかもノードが壊れているように見える形で時間を無駄に
することになります。

## 2つのアクセス経路 — これらは互換ではありません

    href="./access/debug-api/"
  />
  <LinkCard
    title="Serial console"
    description="For a node that never registered. The only route when the API cannot answer."
    href="./access/serial-console/"

</CardGrid>

デバッグ API は **F5 Distributed Cloud のコントロールプレーン経由で**ノードに到達します。
この違いが重要である理由はまさにここにあります。API が応答できるのは、ノードが登録を完了し
`ONLINE` を報告した後だけなのです。

登録に失敗したノード — cloud-init の不備、期限切れのトークン、
`register.ves.volterra.io` への経路がない状態 — は、まさに診断が必要なケースであり、
同時にまさに API が対応できないケースでもあります。

[SSH](./access/ssh/) は第3の選択肢であり、アプライアンスのコマンド面全体に到達できる唯一の
手段です — デバッグ API が公開するのは 34 コマンドですが、ノード自身はそれよりはるかに多くを
提供します。ただし2つの制約があります。`sshd` が応答するのはノードの内部 (SLI) アドレスのみで
あるため、VNet 内部のホストが必要です。またキーは初回起動時に cloud-init によって書き込まれます。
これはサイトオブジェクトの `ssh_key` フィールドが機能しないためです — `vpm` は `admin` ユーザーを
スキップし、このフィールドを適用しません。したがって、稼働中のノードで SSH を有効にするには
ノードを置き換えることになります。

つまり、サイトが `ONLINE` であり 34 コマンドで十分であればデバッグ API を使用します。それ以外の
コマンド面が必要で VNet に到達できる場合は SSH を使用します。壊れているのが登録処理そのもので
ある場合は、シリアルコンソールが唯一の入口です。

<Aside type="caution" title="まずサイトの状態を確認してください">
1回のリクエストで、どちらの経路にいるかが分かります。

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/config/namespaces/system/sites/<site>" \
  | jq -r '.spec.site_state'
```

`ONLINE` であればデバッグ API が使えます。それ以外の場合 — あるいはサイトが存在しない場合 —
はシリアルコンソールになります。
</Aside>

## 安全に関するルール

以下は、後述するすべてのページのすべてのコマンドに当てはまります。

- **確信がない限り読み取り専用に留めること。** コマンド面は2つの権限階層に分かれており、
  `Exec` 階層はノードを変更するか、状態マーカーを読み取ります。これらのページにある
  ものはいずれも `Exec` コマンドを実行しませんし、キャプチャハーネスも同様です。
- **コマンド名から安全性を推測しないこと。** `ip-link-set` はクエリのように読めますが、
  インターフェイスをダウンさせます。`systemctl-restart-crio` は稼働中のデータプレーンの
  下でコンテナランタイムを再起動します。
- **疑問に答える最も範囲の狭いコマンドを選ぶこと。** `health` と `diagnosis` は低コストで
  ノードの概要を示しますが、`flow-l` は 629,760 エントリのフローテーブルをダンプします。
- **CE は実トラフィックを処理しています。** これらは共有のデモ環境です。デバッグ対象の
  サイトから誰かがプレゼンテーションを行っていると想定してください。

## ここで文書化されている内容

本テナントが稼働しているソフトウェアビルドにおいて、デバッグ API から到達可能なすべての
コマンドを扱います。それぞれの出力は、他所から転記したものではなく、稼働中のノードから
キャプチャしたものです。

[コマンドリファレンス](./commands/) はそれらすべてを、カテゴリ、権限階層、トランスポートと
ともに一覧化します。[ワークフロー](./workflows/) は、問題が発生した際に実際に使用する
一連の手順としてそれらを連鎖させます。

Site CLI のうちオンボックス専用の部分 — `configure`、`configure-network`、
`factory-reset`、`upgrade`、およびおよそ60個のさらなる `ExecCLI` コマンド — は
扱っていません。以下のすべてのページのようには、稼働中のノードから出力をキャプチャして
いないためです。

ただし、これらはもはや手の届かないものではありません。`scripts/sitecli_ssh_harvest.py` は
[SSH](./access/ssh/) 経由でアプライアンス自身の補完メニューを操作し、各コマンドについて
アプライアンスが提示する説明を記録します。これにより、コマンド面は推測ではなく実測できます。
このスクリプトの実行はデフォルト拒否です — すべてを列挙する一方、実行するのは許可リストに
あるものだけです — なぜなら、未検証のコマンド構文、そして未検証のコマンドの*作用*こそが、
本ドキュメントが繰り返すことを避けようとしている欠陥だからです。
