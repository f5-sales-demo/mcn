カスタマーエッジ (CE) は、このリポジトリが Azure にプロビジョニングする F5 Distributed Cloud ノードです — `terraform/modules/ce-node` は、`volterraedgeservices/volterra-node` マーケットプレイスイメージから構築されます。

データプレーン (Argo)、コントロールプレーン (Vega)、Envoy プロキシ、Kubernetes スタック、および `vpm` (ノードを登録し、その他すべてを管理するエージェント) を実行します。

CE が正常に動作しない場合、Site CLI が診断ツールとなります。最初の判断は、どちらのアクセスパスが適用されるかを確認することです。誤ったパスを選択すると、ノードが壊れているように見えて時間を無駄にします。

## 2つのアクセスパス（互換性なし）

デバッグ API は、**F5 Distributed Cloud コントロールプレーンを経由して**ノードに到達します。これが分岐の重要な理由です: API は、ノードが登録されて `ONLINE` を報告した後にのみ応答できます。

登録に失敗したノード — 不正な cloud-init、期限切れのトークン、`register.ves.volterra.io` へのルートなし — は、まさに診断が必要なケースであり、同時に API が応答できないケースでもあります。

[SSH](./access/ssh/) は 3 番目のオプションであり、アプライアンスのすべてのコマンドサーフェスに到達できる唯一の手段です — デバッグ API は 34 のコマンドを公開しており、ノード自体にはさらに多くのコマンドがあります。ただし、2 つの制約があります。`sshd` はノードの内部 (SLI) アドレスでのみ応答するため、VNet 内のホストが必要です。また、鍵は最初の起動時に cloud-init によって書き込まれます。これは、サイトオブジェクトの `ssh_key` フィールドが無効であるためです — `vpm` は `admin` ユーザーをスキップし、適用しません。したがって、実行中のノードでこれを有効にすると、ノードが置き換えられます。

つまり: サイトが `ONLINE` であり、34 のコマンドで十分な場合は、デバッグ API を使用してください。残りのサーフェスが必要で VNet に到達できる場合は、SSH を使用してください。登録に問題がある場合は、シリアルコンソールが唯一のアクセス手段です。

<Aside type="caution" title="まずサイトの状態を確認する">
1 つのリクエストで、現在どのパスにいるかを確認できます:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/config/namespaces/system/sites/<site>" \
  | jq -r '.spec.site_state'
```

`ONLINE` はデバッグ API が機能することを意味します。それ以外の場合 — またはサイトが存在しない場合 — はシリアルコンソールを使用してください。
</Aside>

## 安全規則

これらは、以下のすべてのページのすべてのコマンドに適用されます。

- **確信がない限り、読み取り専用にとどめる。** コマンドサーフェスは 2 つの権限レベルに分かれており、`Exec` レベルはノードを変更するか、状態マーカーを読み取ります。このページのいずれも `Exec` コマンドを実行せず、キャプチャハーネスも同様です。
- **コマンドが名前から安全だと思い込まない。** `ip-link-set` はクエリのように見えますが、インターフェースをダウンさせます。`systemctl-restart-crio` は、ライブデータプレーン下でコンテナランタイムを再起動します。
- **質問に答えられる最も限定的なコマンドを優先する。** `health` と `diagnosis` はノードを安価に要約します。`flow-l` は 629,760 エントリのフローテーブルをダンプします。
- **CE はライブトラフィックを処理している。** これらは共有デモ環境です。デバッグ中のサイトから誰かがプレゼンテーションを行っていると想定してください。

## ここに記載されている内容

このテナントが実行するソフトウェアビルドのデバッグ API から到達可能なすべてのコマンドが、他の場所から転記するのではなく、ライブノードからキャプチャされた出力とともに記載されています。

[コマンドリファレンス](./commands/) にはすべてのコマンドがカテゴリ、権限レベル、トランスポートとともに一覧表示されており、[ワークフロー](./workflows/) では問題が発生した際に実際に使用するシーケンスに組み合わせられています。

ノード上のみのサイト CLI の部分 — `configure`、`configure-network`、`factory-reset`、`upgrade`、およびさらに約 60 の `ExecCLI` コマンド — はカバーされていません。

これらはシリアルコンソールセッションからのみ到達可能であるため、プログラム的に検証することができません。未検証のコマンド構文こそ、このドキュメントが繰り返さないために存在する欠陥です。
