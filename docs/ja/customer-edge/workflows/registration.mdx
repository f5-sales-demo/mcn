<Aside type="danger" title="API ではこの問題をデバッグできません">
デバッグ API は、登録によって確立されるトンネル経由で、F5 Distributed Cloud
コントロールプレーンを通じてノードに到達します。登録が失敗している場合はトンネルが存在しないため、
まさにこの障害においてはこのサイトのすべてのコマンドが利用できません。ノードにネットワーク経路が残っている場合は
[サイトコンソール](../../access/site-console/)から、残っていない場合は
[シリアルコンソール](../../access/serial-console/)から作業してください。
</Aside>

<Steps>

1. **正しいテナントを参照しているか確認します。** これはコマンド 1 回で済み、最初に実施する理由は、
   ここを誤ると以降のすべてのステップが誤った情報を返すからです。参照していないテナント内の正常なフリートは、
   一度も登録されなかったフリートと区別がつきません。

   ```bash
   cd terraform
   terraform output -raw xc_tenant       # the tenant this deployment belongs to
   terraform output -raw xc_env_tenant   # the tenant your shell is exporting
   ```

   ```text
   f5-sales-demo
   f5-sales-demo
   ```

   一致していない、あるいは正しいと思っていた認証情報が素の `401` を返す場合、それは別のテナント向けに
   発行されたトークンの症状であり、すでにこのデプロイメントで完全な再構築 1 回分のコストが発生しています
   ([issue 696](https://github.com/f5-sales-demo/mcn/issues/696))。

2. **テナント側の認識を確認します。** サイト一覧に存在しないことと、存在するが `ONLINE` でないことは
   別の問題です。

   ```bash
   curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
     "$XCSH_API_URL/api/config/namespaces/system/sites" | jq -r '.items[].name'
   ```

   サイトが存在し `ONLINE` と報告されている場合、登録は成功しており、あなたは誤ったワークフローを
   たどっています。

3. **サイトの登録とその状態を確認します。** ノードは登録後に承認待ちとなることがあり、
   外部から見ると障害と全く同じように見えます。

   ```bash
   curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
     "$XCSH_API_URL/api/register/namespaces/system/registrations_by_site/<site>" \
     | jq -r '.items[] | "\(.name)  \(.object.status.current_state)  \(.object.spec.gc_spec.infra.hostname)"'
   ```

   ```text
   r-a97e20c8-b7e1-483d-bd76-34a64ff8bc78  ONLINE  f5-xc-ce-vm-01
   ```

   項目がまったく無い場合は、ノードがまだ登録されていないことを意味します — シリアルコンソールへ進んでください。
   `ONLINE` 以外の状態の項目がある場合は、登録は完了しその後で何かが失敗しており、別の調査となります。

   承認待ちのものを名前空間全体で洗い出すには、`listregistrationsbystate` が状態を
   **`POST` ボディ**として受け取ります。

   ```bash
   curl -sS -X POST -H "Authorization: APIToken $XCSH_API_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"namespace":"system","state":"PENDING"}' \
     "$XCSH_API_URL/api/register/namespaces/system/listregistrationsbystate" | jq -r '.items[].name'
   ```

   正常なフリートでは承認が自動化されているため、これは何も返しません。

4. **ソフトウェア障害を疑う前に、VM が実際に稼働していることを確認します。**

   ```bash
   az vm list -d -g <resource-group> --query "[].{name:name,power:powerState}" -o table
   ```

   ```text
   Name            Power
   --------------  ----------
   ar-ecmp-client  VM running
   f5-xc-ce-vm-01  VM running
   f5-xc-ce-vm-02  VM running
   f5-xc-ce-vm-03  VM running
   ```

5. **シリアルコンソールに接続します。** 対話的に行うには実際のターミナルが必要です。接続自体は
   websocket 経由でスクリプト化することもできます —
   [シリアルコンソール](../../access/serial-console/)を参照してください。

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

   拒否される場合は、ノードが到達不能だと結論づける前に、VM でブート診断が有効になっているか確認してください。
   その前提条件と障害パターンについては
   [シリアルコンソール](../../access/serial-console/)のページで説明しています。

6. **コンソールの表示を、この順序で読み取ります。** まず cloud-init です — cloud-init が完了していない
   ノードには、登録に使う構成が存在しません。次に登録の試行そのもの、続いて DNS です。ノードが
   `register.ves.volterra.io` を解決できなければ、その下流のいずれも機能しません。

7. **ノードが `ONLINE` になったら**、[`health`](../../commands/system/health/) で検証し、
   `state: PROVISIONED` を期待します。

</Steps>

<Aside type="caution" title="登録は UUID で命名され、サイト名では命名されません">
登録は `r-<uuid>` という名前を持ち、登録名が期待される箇所でサイト名を受け取るエンドポイントは存在しません。
`GET .../registrations/<site>` は `404` を返し、これは「このサイトには登録がない」と読めますが、
実際には「それは登録名ではない」という意味です。サイトと登録の対応付けは、ステップ 3 のように
`registrations_by_site/<site>` から得るか、`registrations` を一覧して
`gc_spec.passport.cluster_name` で照合するしかありません。

同じ罠によって、正常なフリートに登録が 1 件も存在しないように見えたことがあります。
</Aside>

## よくある原因

- **誤ったテナントを参照している**ため、正常なフリートが存在しないように見える。ステップ 1。
- cloud-init が完了せず、`/etc/vpm/config.yaml` が存在しないか内容が誤っている。
- 登録トークンが期限切れ、すでに使用済み、または別テナントのもの。
- `register.ves.volterra.io` への外向き経路がない。
- 証明書を無効化するほど大きなクロックスキュー — 後で
  [`chronyc-sources`](../../commands/network/chronyc-sources/) で素早く切り分けられますが、
  ノードがオンラインになるまでは到達できません。[SSH](../../access/ssh/) のログインバナーは、
  SSH が利用できる場合、何かを実行する前に `NTP: Synced` とリゾルバーの状態を報告します。
