ルーティングレベルの高可用性設計では、各Customer Edge (CE) サイトはBorder Gateway Protocol (BGP)を介して同じサービスプレフィックスを生成します。ノースバウンドルーターは、使用可能な広報をEqual-Cost Multi-Path (ECMP)ネクストホップとしてインストールし、トラフィックを分散して障害パスを削除するポイントになります。

```text
サービス VIP /32
       |
アップストリームルーター: イコールコストネクストホップ
       |              |              |
    CEサイト 1     CEサイト 2     CEサイト 3
```

## サービスアドレスをルートとして広報する

サービスがIPv4の場合、個々の仮想IPアドレス（VIP）を`/32`ホストルートとして広報します。これらのサービスアドレス用にルーティング専用のプレフィックスを予約し、そのプレフィックスをVirtual Private Cloud（VPC）、Virtual Network（VNet）、VLAN、またはローカルサブネットに接続しないでください。ネットワークは、接続されたセグメント上のAddress Resolution Protocol（ARP）からではなく、ルーティング広報からサービスアドレスを学習する必要があります。

サービスプレフィックスを分離しておくことで、接続されたルートとBGPルートの間の曖昧さを回避できます。また、ルートポリシー、フィルタリング、および容量計画が明確になります。プレフィックスは組織のアドレス管理プロセスに従って割り当ててください。ラボのプレフィックスを別のネットワークにコピーしないでください。

## ルーティングに障害パスを撤回させる

確立されたBGPセッションは、アップストリームルーターにライブネス信号を提供します。セッションがクローズされるか、そのホールドタイマーが満了すると、ピアはそのセッションを介して学習したルートを撤回します。Bidirectional Forwarding Detection（BFD）は、両方のピアがサポートして有効にしている場合、より高速な障害検出を提供できます。したがって、収束時間は設定されたプロトコルとタイマーに依存し、瞬時ではありません。

スタティックルートには、同等のセッション状態はありません。カスタマールーターまたはSoftware-Defined Wide Area Network（SD-WAN）コントローラーがサポートされているヘルスチェックメカニズムでネクストホップを追跡してルートを削除しない限り、CEに障害が発生した後もスタティックなECMPパスは選択対象のまま残ります。そのメカニズムがない場合、ルーターは障害が発生したCEを選択し続け、一部のフローをブラックホール化する可能性があります。

<Aside type="danger" title="到達可能なネクストホップはアプリケーションの正常性を示しません">
BGPはルーティングピアが利用可能であることを証明します。これは、必ずしもそのピアの背後にあるすべてのアプリケーションが正常であることを証明するものではありません。ルーティングセッションの状態で十分であるか、サービスヘルスに別のサポートされた信号が必要かを判断してください。
</Aside>

## CEフリートの前にルーターのサイズを決定する

ルーターは、インストールするイコールコストパスの数を決定します。ルーターの最大ECMPパス数と、各VIPに対して予想されるCE広報の数を比較してください。広報数がインストールされたパスの制限より大きい場合、追加の正常なCEサイトがそのプレフィックスに対して使用されないままになる可能性があります。

BGPの受信ルートビューだけに頼るのではなく、インストールされたフォワーディングテーブルを確認してください。コントロールプレーンはデータプレーンがインストールするよりも多くの候補を保持できます。

## 優先度とECMPを異なるポリシーとして扱う

パスは、ルート選択属性とメトリックがそれらを等しくする場合にのみイコールコストになります。ローカルプレファレンス、Multi-Exit Discriminator（MED）、アドミニストレーティブディスタンス、またはスタティックルートメトリックを変更すると、特定のCEを特定のVIPに対して優先させることができます。これは有効なステアリングポリシーですが、均等分散ではなくアクティブ/優先（active/preferred）の動作です。

そのような非対称性が意図的である場合にのみ、プレフィックスごとに優先度を適用してください。優先パスが撤回されたときに優先度の低いパスが使用可能になることを確認し、CEが停止した後も存続する追跡されていないスタティックな優先パスを残さないでください。

## コントロールプレーンのラベルとトラフィックのエビデンスを分離する

複数のトンネルまたはパスを持つ設計では、`ACTIVE`ラベルはコントロールプレーン同期用に選択されたパスを識別できますが、他のECMPパスがデータを転送していないことを証明するものではありません。そのラベルのみからフォワーディング状態を推測しないでください。ルートまたはトンネルテーブルを検証し、予想されるすべてのパスのトラフィックカウンタを観察してください。

## パス全体を検証する

各サービスプレフィックスについて、以下をすべて検証します。

- 意図したすべてのCEがプレフィックスを広報していること。
- アップストリームのBGPテーブルが予想されるパスを受け入れていること。
- フォワーディングテーブルが、プラットフォームがサポートする数と過不足なく同じ数のパスをインストールしていること。
- 1つの広報を撤回すると、設定された検出および収束インターバル後にそのネクストホップが削除されること。
- 残りのパスを通じてアプリケーションチェックが成功すること。

CEの広報の問題とアップストリームのフォワーディングの問題を区別するために、リポジトリの[BGP診断ワークフロー](../../workflows/bgp-diagnostics/)を使用してください。
