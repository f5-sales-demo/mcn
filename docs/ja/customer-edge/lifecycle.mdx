Terraform の 2 つの変数が Customer Edge のソフトウェアを設定します。オペレーティングシステム用の `ce_os_version` と、F5 Distributed Cloud ビルド用の `ce_sw_version` です。どちらも直感的な読み方とは逆の動作をします。空のフィールドは何もしないのではなく最新ビルドを取得し、あるノードにインストールできるバージョンが、ディスクが小さい同一構成のノードでは失敗する場合があります。

## バージョンフィールドの動作（2 つのフェーズ）

フェーズを分けて理解することが重要です。混同すると、動作が矛盾しているように見えます。

**初回起動時、ノードは `ce_sw_version` で指定されたものをインストールします。**
`terraform/modules/ce-node` は `version = "latest"` でマーケットプレイスイメージをデプロイするため、ノードが最初に持つビルドはそのイメージが現在提供しているものであり、それは時間とともに変化します。`ce_sw_version` は**インストール先**を指定するものであり、何かが起こるかどうかを制御するものではありません。空欄にするとノードがそのままになるのではなく、サーバーが判断します。`ce_os_version` についても同様です。

その変化の方向が必ずしも上位バージョンへの移行だとは思わないでください。`2026-07-28 確認`: イメージは `20260703-e2c462a` というスタンプのビルドを提供していました。これはこのフリートの `crt-20250613-3382` より新しく、テナントが告知していた `crt-20260201-0179` より新しいものでした。イメージが持つものより古いビルドを指定することは、ノードに後退を求めることになります。しかしそれは通常の操作です。このフリートはそのようにして作成され、稼働しています。

**バージョンフィールドを空欄にすることは、中立的な選択ではなく最もリスクが高い選択です。** 作成時、サーバーは空のフィールドをそのままにしません。**最新の告知バージョン**で埋めてインストールします。両フィールドを未設定で作成したサイトは `crt-20260201-0179` と OS `9.2026.14`（テナントが告知していた 2 つのバージョン）に固定されて戻ってきましたが、インストールに失敗しました。`2026-07-29 確認`。

これには 2 つの影響があります。空欄は「最新を提供せよ」を意味するため、ピンを指定しないデプロイは後述のディスク制限に遭遇する可能性が最も高くなります。また、一方のフィールドを空欄にして他方だけを設定することはできません。サーバーが空欄を埋めるためです。両方を意図的に設定するか、それぞれの最新バージョンを受け入れるかのどちらかです。

**初回起動後、自動的にアップグレードされることはありません。** F5 Distributed Cloud は新しいビルドを告知して待ちます。「ノードは起動時に定着した状態にとどまる」という動作は、作成中ではなく作成後に当てはまります。

両フェーズはサイトオブジェクトで確認できます。`2026-07-28 確認`: このフリートでは:

```text
volterra_software_status.available_version   crt-20260201-0179
operating_system_status.available_version    9.2026.14
```

ノードは `crt-20250613-3382` および OS `9.2024.6` で稼働しています。新しいビルドが提供されていますが、適用されていません。これは停滞したアップグレードではなく、安定した状態です。

## Terraform はバージョンを変更できない。API は変更できる

これらは 2 つの別個の事実であり、混同すると誤った計画につながります。

**Terraform はできません。** `ce_os_version` と `ce_sw_version` は実質的に作成時のみ有効です。どちらかを変更して apply すると、API は `[BAD_REQUEST] Invalid request parameters` でアップデートを拒否します。`2026-07-29 確認`（使い捨てサイトで 3 方向すべてを確認）— 新しいビルドへの**前進**ピン、古いビルドへの**後退**ピン、および両フィールドをクリアする**ピン解除**。前進は特別なケースではありません。

**API はできます。** F5 Distributed Cloud はサイトごとに専用のアップグレードアクションを公開しており、再構築なしで、Terraform を介さずにその場でバージョン変更を開始します:

```bash
# ソフトウェアビルド
curl -X POST -H "Authorization: APIToken $TOKEN" -H 'Content-Type: application/json' \
  --data '{"version": "<software-version>"}' \
  "$API_URL/api/config/namespaces/system/sites/<site-name>/upgrade_sw"

# オペレーティングシステム
curl -X POST -H "Authorization: APIToken $TOKEN" -H 'Content-Type: application/json' \
  --data '{"version": "<os-version>"}' \
  "$API_URL/api/config/namespaces/system/sites/<site-name>/upgrade_os"
```

`2026-07-29 確認`: ソフトウェアコールは `200` を返し、サイトは `deployment_state.phase` が `UPGRADE_IN_PROGRESS` の `UPGRADING` 状態に移行し、サイトオブジェクトのリクエストバージョンが POST したバージョンに変更されました。フィールドを省略すると `version empty in the request` の `400` が返されます。これによりフィールド名が確認されました。

**時間の見積もりは分単位ではなく時間単位で、失敗が発生してもパニックにならないでください。** デフォルトディスクのノードで `crt-20260201-0179` へのアップグレードは約 1 時間かかり、途中で `UPGRADE_FAILED`（`result`: `Failed`）を報告しましたが、その後**新しいビルドで正常に完了しました**。プラットフォームはリトライします。

これはアップグレードを監視したり、スクリプト化したりする場合に直接的な影響があります。`Failed` 結果は待機すべき状態であり、最終判定ではありません。最初の失敗を最終結果として扱うと、成功するアップグレードを失敗と報告することになります。

そのパスのグループに注意してください。これらは `operate` ではなく **`config`** 配下にあります。`operate` 配下の同じパスは `404 API Group could not be determined` を返しますが、これはルーティングメッセージであり、アップグレードが存在しないという意味ではありません。この違いがこのプロジェクトで誤った結論をもたらしました。

<Aside type="caution" title="API 経由のアップグレードは Terraform との不整合を引き起こします">
ピン変数は変更前の値のままであるため、稼働中のサイトは設定に記載されていないバージョンで動作します。Terraform はこれを調整しません。更新が拒否されるためです。API アップグレードは Terraform の管理外への意図的な変更として扱い、次の再構築時にピンを実際の状態に合わせて更新してください。
</Aside>

<Aside type="note" title="このページで以前に述べた 2 つの主張を撤回します">
このページでは以前、CE を異なるバージョンに移行するにはサイトの再作成が必要であること、および拒否されたアップデートが「サーバー上のフィールドをクリアする」ため Terraform が失敗する変更を永続的に提案し続けるということを述べていました。いずれもテストでは確認されませんでした。上記の API アップグレードは再作成なしでその場でバージョン変更を開始し、3 回の拒否されたアップデートそれぞれの後もサイトの spec は**変更されず**、サイトは `ONLINE` のままでした。プロバイダー issue `xcsh#1387` で説明されている不整合は、すでにピンを超えて自動アップグレードされたサイトで観察されたものであり、その不整合した開始状態が必要である可能性があります。spec がピンと一致するサイトでは再現されませんでした。
</Aside>

アップグレードではなく再構築する場合は、CE を置き換えるすべての影響が適用されます。

<Aside type="danger" title="CE を置き換えるすべての影響が適用されます">
新しい SSH ホストキー、再割り当てされた内部アドレス、新しい登録、およびノード上にのみ存在していたものの消失。Cloud-init は新しい VM で再度実行されるため、そのように設定された SSH アクセスは引き継がれます。ただし、Cloud-init は初回起動時**のみ**実行されるため、古いノードに手動で追加されたものはすべて失われます。

このスケジュールを組む前に、ホストキーとアドレスへの影響について [SSH](./access/ssh/) を参照してください。
</Aside>

## ピン指定したビルドがインストールに失敗し、サイトがスタックする

ピンを受け入れることとインストールすることは同じではありません。`crt-20260201-0179` にピン指定した新規作成の単一ノード Azure Secure Mesh v2 Customer Edge では、サイトオブジェクトはすぐにピン指定バージョンを報告しましたが、インストールに失敗しました:

```text
site_state        PROVISIONING
phase             UPGRADE_FAILED
result            Failed
last_installed    (empty)
message           stage: 10, app: voucher obj: voucher objKind: DaemonSet failed ...
                  required replicas: 1, current replicas: 0
```

`2026-07-28 確認`、2026-07-29 に 2 回再現。同じ実行で**オペレーティングシステム**のピンは正常にインストールされました（`9.2024.6` から `9.2026.14`、`UPGRADE_COMPLETED`）。失敗したのはソフトウェアのインストールのみです。サイトは `ONLINE` に到達せず、`last_installed_version` は空のままでした。そのため、動作するビルドへのロールバックは行われませんでした。以前の正常なインストールが存在しないためです。

**作成時の失敗はアップグレード中の失敗とは異なります。** 両者は動作が異なり、介入するかどうかを判断する際にその違いが重要です:

| | 作成時 | API アップグレード中 |
| --- | --- | --- |
| リトライして成功するか？ | いいえ — 20 分以上 `Failed` のまま、2 回とも | はい — 回復して完了した |
| ノードはどこで終わるか？ | `PROVISIONING`、何もインストールされない | 動作するビルドで `ONLINE` |
| 放置しても安全か？ | いいえ、スタックしている | はい、回復するか古いビルドを維持する |

したがって、作成時の失敗は大きなディスクでの再構築が必要ですが、`Failed` を報告するアップグレードは、何か結論を出す前にしばらく放置すべきです。

**原因はバージョンではなくディスクです。** ソフトウェア × OS × ディスクサイズのマトリックスで、組み合わせごとに使い捨ての単一ノード Azure Secure Mesh v2 サイトを 1 つずつ、すべて同じマーケットプレイスイメージから作成することで特定できます。`2026-07-29 確認`:

| ソフトウェア | OS `9.2024.6`（イメージが提供するもの） | OS `9.2026.14` |
| --- | --- | --- |
| `crt-20250613-3382` | インストール成功 | インストール成功 |
| `crt-20260201-0179` | インストール成功 | **失敗**、デフォルトディスクのみ |

どちらのバージョンも単独では失敗しません。組み合わせた場合のみ、イメージのデフォルトディスク上でのみ失敗します。同じ組み合わせは **40 GB**、**48 GB**、**64 GB** ではインストールに成功します。つまり、新しいビルドはここでサポートされていないわけではなく、新しいオペレーティングシステムも同様です。両方を組み合わせると、デフォルトノードが持つよりも多くのディスクが必要になります。

`terraform/modules/ce-node` は `disk_size_gb` を設定しないため、すべての Customer Edge はイメージのデフォルトになります。**新しいペアを実行するには、ディスクを拡張してください。** テストした中で機能する最小サイズは 40 GB です。正確な境界はイメージのデフォルトと 40 GB の間にありますが、それ以上は詰めていません。

フリートに適用する前に、使い捨てサイトでバージョン変更をテストしてください。この方法で失敗するフリートは `PROVISIONING` でスタックし、再作成のみが唯一の解決策です。

<Aside type="caution" title="F5 のアップグレード前の数値からディスクサイズを決定しないでください">
F5 の文書化されたアップグレード前チェックは、20 GB プラス容量の 15% の空き領域を要求します。このチェックは**コンソール UI** アップグレードのゲートであり、API 起動のアップグレードには明示的に適用されないため、この失敗を説明するものではありません。ここに適用すると 48 GB ディスクが失敗すると予測しますが、48 GB は正常にインストールされます。その数式ではなく、上記の実測結果からサイズを決定してください。
</Aside>

<Aside type="note" title="このページで以前に提示した説明を撤回します">
以前のバージョンのこのページでは、インストールが失敗したのはリクエストされたビルドがイメージのビルドより古かったため、つまりノードが後退を求められたためだと示唆していました。これは誤りです。このフリートは同じイメージから**13 ヶ月**古いピンで作成されて正常にインストールされており、OS ピンをイメージ自身のバージョンのままにすると `crt-20260201-0179` もインストールに成功します。移行の方向が変数ではありません。
</Aside>

## ドキュメントが説明するビルド

このサイトのコマンドリファレンスは、このフリートが稼働している **`crt-20250613-3382`** を説明しています。新しいビルドにのみ存在するコマンドは `sitecli/command-classification.json` の `not_on_this_build` に記録されており、[新しいビルドのコマンド](./commands/on-box/newer-builds/)として別途文書化されています。そのため、ここで実行可能と読める内容に誤りはありません。[オンボックスコマンド](./commands/on-box/)も参照してください。

<Aside type="note" title="新しいビルドへの到達は解決済みであり、再構築は不要です">
これは以前、単一ノード Azure Secure Mesh v2 サイトで新しいビルドが失敗したという報告と、それが動作しているという反対観察とともに未解決として記録されていました。両方とも現在は説明されています。新しいビルドはそのトポロジーにインストールでき、失敗はビルドではなく上記のディスク制限によるものでした。

したがって、2 つのルートがあり、どちらも独自の理由での再構築を必要としません。十分なディスクサイズのノードを新規作成するか、API 経由で既存のものをアップグレードするかです。`2026-07-29 確認`。
</Aside>
