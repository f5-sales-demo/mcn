Terraform の変数が 2 つ、Customer Edge のソフトウェアを設定します。オペレーティングシステム用の `ce_os_version` と F5 Distributed Cloud ビルド用の `ce_sw_version` です。どちらも直感的な読み方とは逆の動作をするため、誤ると代償はフリートの再構築となります。

## バージョンフィールドの役割 — 2 つのフェーズ

このフェーズを分けて考えることが本質です。混同すると、挙動が自己矛盾しているように見えます。

**初回起動時、ノードは `ce_sw_version` で指定されたものをインストールします。**
`terraform/modules/ce-node` は `version = "latest"` でマーケットプレイスイメージをデプロイするため、ノードが最初に持ってくるビルドは、そのイメージが現時点で提供しているものです — これは時間とともに変化します。
`ce_sw_version` は何かが起こるかどうかではなく、**到達先**を指定します。空欄にすると、ノードがそのまま留まるのではなく、サーバーが判断します。`ce_os_version` についても同様です。

その変化の方向が上位バージョンへの移行だと決め込まないでください。`2026-07-28 に観測した時点では`、イメージは `20260703-e2c462a` というビルドを提供していました — このフリートの `crt-20250613-3382` より新しく、テナントが告知していた `crt-20260201-0179` よりも新しいものです。**イメージが持っているビルドより古いビルドを指定すると、ノードに後退を求めることになり、失敗する可能性があります** — 後述する失敗例を参照してください。

**その後は、自動でアップグレードされることはありません。** F5 Distributed Cloud は新しいビルドを告知して待機します。フィールドを空欄にしても「最新を追う」設定にはなりません。ノードは最初に到達したバージョンに留まります。

両フェーズはサイトオブジェクトで確認できます。`2026-07-28 に観測した時点では`、このフリートは：

```text
volterra_software_status.available_version   crt-20260201-0179
operating_system_status.available_version    9.2026.14
```

ノードは `crt-20250613-3382` と OS `9.2024.6` で稼働しています。新しいビルドが提供されているにもかかわらず適用されていない — これは停滞したアップグレードではなく、定常状態です。

## バージョン変更には再構築が必要であり、Terraform は自動的に行いません

`ce_os_version` と `ce_sw_version` はどちらも**作成時のみ**有効であり、失敗のパターンは単なる apply の拒否よりも深刻です。順を追って説明します：

1. 値を変更して apply します。Terraform はインプレース更新を提案します。
2. API がそれを**拒否**します — `[BAD_REQUEST] Invalid request parameters`。
3. この拒否されたリクエストによってサーバー上のフィールドがクリアされ、プロバイダーの read はそれを報告しません。Terraform の状態は実際のオブジェクトと乖離します。
4. その後のすべての plan で**同じ失敗する変更**が永続的に提案され続けます。

つまり Terraform はサイトの置き換えにフォールバックしません。スタックしたまま、意図的にサイトとその CE 仮想マシンを置き換えるまでスタックし続けます。フリートを別のバージョンに移行するには、適用するだけの編集ではなく、**計画して実施する再構築**が必要です。

<Aside type="danger" title="CE 置き換えに伴うすべての影響が発生します">
新しい SSH ホストキー、再割り当てされた内部アドレス、新規登録、およびノード上にのみ存在していたものの喪失。新しい VM で cloud-init が再実行されるため、その方法で設定された SSH アクセスは引き継がれます — ただし cloud-init は**初回起動時のみ**実行されるため、手動で旧ノードに追加したものはすべて失われます。

このスケジュールを立てる前に、ホストキーとアドレスの影響について [SSH](./access/ssh/) を参照してください。
</Aside>

<Aside type="note" title="報告済み、本環境では再現なし">
拒否と状態の乖離は、このリポジトリの `terraform/modules/xc-site` コメントに記録されています — すべて 3 つのサイトで、ピン留めとピン解除の両方向について検証済み — またプロバイダーの issue `xcsh#1387` に対しても記録されています。このページでは再テストしていません。テストを行うと、デプロイメントがすべての plan で失敗する変更を提案し続ける状態になるためです。
</Aside>

## ピン留めされたビルドはインストールに失敗することがあり、サイトはスタックします

ピン留めを受け入れることとインストールが成功することは同じではありません。`crt-20260201-0179` にピン留めされた新規作成の Azure Secure Mesh v2 Customer Edge（シングルノード）では、サイトオブジェクトにピン留めバージョンがすぐに反映されました — しかしその後インストールが失敗しました：

```text
site_state        PROVISIONING
phase             UPGRADE_FAILED
result            Failed
last_installed    (empty)
message           stage: 10, app: voucher obj: voucher objKind: DaemonSet failed ...
                  required replicas: 1, current replicas: 0
```

`2026-07-28 に観測。` **オペレーティングシステム**のピン留めは同じ実行で正常にインストールされました（`9.2024.6` から `9.2026.14`、`UPGRADE_COMPLETED`）。失敗したのはソフトウェアのインストールのみです。サイトは `ONLINE` に到達せず、`last_installed_version` は空のままでした。このため、動作しているビルドへのロールバックは行われませんでした — ロールバック先となる以前の正常なインストールが存在しなかったためです。

**この件から得られる教訓。** 他の場所で動作しているバージョンが、自分のサイトの構成でもインストールできるという保証はありません。同じビルドが、Secure Mesh v2 ではない Azure Customer Edge と、VMware 上の Secure Mesh v2 サイトでは `ONLINE` になっていました。失敗した組み合わせは Azure *かつ* Secure Mesh v2 でした。バージョン変更をフリートに適用する前に、使い捨てのサイトでテストしてください。この方法で失敗したフリートは `PROVISIONING` でスタックし、再作成以外に出口はありません。

<Aside type="caution" title="このページが原因を断定しない理由">
要求されたビルドはマーケットプレイスイメージが提供していたものより**古かった**ため、ノードは後退を求められていました。これは失敗の説明として妥当ですが、**確定していません**。2 つのバージョン文字列（`20260703-e2c462a` と `crt-20260201-0179`）が同じ番号体系を共有しているかどうかは不明であり、比較対象となるフリートノードのキャプチャも入手できませんでした。失敗とバージョンの順序は観測事実ですが、両者の関係は確立されていません。
</Aside>

## このドキュメントが説明するビルド

本サイトのコマンドリファレンスは、このフリートが稼働している **`crt-20250613-3382`** を説明しています。新しいビルドにのみ存在するコマンドは、`sitecli/command-classification.json` の `not_on_this_build` に記録され、[新しいビルドのコマンド](./commands/on-box/newer-builds/)として個別にドキュメント化されています。そのため、ここに記載されているものは本環境で実行可能なものとして読めます。[オンボックスコマンド](./commands/on-box/)も参照してください。

<Aside type="caution" title="新しいコマンドに到達するために再構築を計画しないでください">
新しいビルドが提供されていますが、このトポロジーでクリーンにインストールできるかどうかは未確定です — シングルノード Azure Secure Mesh v2 サイトで失敗したという報告と、それを実行している Customer Edge の反対の観測があります。テナントに残っているものからは、どちらも確認できません。

バージョン変更はフリートの再構築を意味するため、この不確実性が決定的な事実です。該当するコマンドへの到達は、予定されたアップグレードとしてではなく、未証明のものとして扱ってください。その根拠と解決に必要な実験は `sitecli/README.md` に記録されています。
</Aside>
