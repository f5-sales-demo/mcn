本部署示範 **Azure 中的 active/active Customer Edge 高可用性**，
且 CE 前方不放置任何 Azure 負載平衡器。三個 CE 各自透過 eBGP 發佈相同的主機
路由，而 Azure Route Server 會將三者全部安裝為 VNet 中的等價成本下一跳。
因此，流量分配與失效節點移除應當發生在路由架構中，而非負載平衡器上。

以下所示內容全部是針對實際部署執行的結果，輸出即為其所產生的輸出。這句話*未*
涵蓋的兩件事 —— 容錯移轉與流量分配 —— 會在最後明確指出，而非留待讀者自行假設。

## 部署了什麼

```text
                  Azure Route Server  ce-ha-lab-rrs  ASN 65515
                          10.0.4.4  and  10.0.4.5
                                      |
              +-----------------------+-----------------------+
              |                       |                       |
        eastus01-bgp            eastus02-bgp            eastus03-bgp     eBGP
              |                       |                       |      CE ASN 64512
        10.0.1.4                10.0.1.5                10.0.1.6     <- CE eth0 / SLO
     f5-xc-ce-vm-01          f5-xc-ce-vm-02          f5-xc-ce-vm-03
    ar-bgp-eastus01         ar-bgp-eastus02         ar-bgp-eastus03
              |                       |                       |
              +----- each advertises 10.250.0.10/32 -----------+
                          three-way ECMP into the VNet
```

| 元件 | 實作內容 |
| --- | --- |
| Customer Edge | 3 個單節點 Secure Mesh v2 站點 —— `ar-bgp-eastus01`、`ar-bgp-eastus02`、`ar-bgp-eastus03` |
| CE 軟體 | 固定版本 `9.2024.6`，組建 `crt-20250613-3382` |
| Azure VM | `f5-xc-ce-vm-01/02/03`，每台三張 NIC（管理/SLO、外部、內部/SLI） |
| 路由交換 | Azure Route Server `ce-ha-lab-rrs`，ASN `65515`，執行個體 `10.0.4.4` 與 `10.0.4.5` |
| 對等連線 | 每個 CE 一個 —— `eastus01-bgp`、`eastus02-bgp`、`eastus03-bgp` —— CE ASN `64512` |
| 發佈的 VIP | `10.250.0.10/32`，由三個 CE 以相同方式發佈 |
| 負載平衡器 | `ar-bgp-ecmp-lb`，服務網域 `ar-bgp-ecmp.bankexample.com` |
| 測試用戶端 | `ar-ecmp-client`，位於同一 VNet 內的 VM |
| 資源群組 | `rg-mcn-ce-ha-rmordasiewicz` |

<Aside type="caution" title="VIP 必須位於所有 VNet CIDR 之外">
`terraform/main.tf` 內含一個 `check` 區塊，用以斷言 VIP 位於 hub 與 spoke CIDR
之外，否則拒絕該 plan。其列出的理由是：即使 BGP 路由更為明確，位於 VNet CIDR
內的 VIP 仍會敗給 VNet 自身的系統路由。

請將此防護視為契約：如果你將本示範改指向不同的定址方案，VIP 也必須隨之移出
VNet 範圍。
</Aside>

## 在展示前證明其運作正常

四項檢查，依此順序進行。每一項都會縮小故障可能的範圍，因此失敗能告訴你
具體資訊，而不只是「有東西壞了」。

<Steps>

1. **三個站點皆為 `ONLINE`。** 若此項不成立，下游的任何結果都不可能為真。

   ```bash
   for s in ar-bgp-eastus01 ar-bgp-eastus02 ar-bgp-eastus03; do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **每個對等連線都學到該 CE 的 VIP 發佈。** 分別查詢每個對等連線 ——
   請參閱下方的陷阱說明，因為這正是本示範最常看起來壞掉、但其實沒壞的地方。

   ```bash
   for p in eastus01-bgp eastus02-bgp eastus03-bgp; do
     echo "--- $p"
     az network routeserver peering list-learned-routes \
       --name "$p" --routeserver ce-ha-lab-rrs -g rg-mcn-ce-ha-rmordasiewicz \
       --query "RouteServiceRole_IN_0[].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp

   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp

   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   三個對等連線、三個不同的下一跳、一個前綴。這就證明了 ECMP 的發佈端。

3. **用戶端的有效路由包含全部三個下一跳。** 這才是 ECMP 本身，
   也就是 VNet 實際編程的結果 —— 不是 CE 所聲稱的內容，而是 Azure 對它做了什麼。

   ```bash
   az network nic show-effective-route-table \
     --name ar-ecmp-clientVMNic -g rg-mcn-ce-ha-rmordasiewicz \
     --query "value[?addressPrefix[0]=='10.250.0.10/32']" -o json
   ```

   ```json
   [
     {
       "addressPrefix": ["10.250.0.10/32"],
       "nextHopIpAddress": ["10.0.1.5", "10.0.1.4", "10.0.1.6"],
       "nextHopType": "VirtualNetworkGateway",
       "source": "VirtualNetworkGateway",
       "state": "Active"
     }
   ]
   ```

   `state: Active` 且 `nextHopIpAddress` 中有三筆項目，就是這項檢查的重點。
   若你預期三個下一跳卻只看到一個，表示某個 CE 已停止發佈，而步驟 2 可指出是哪一個。

4. **VIP 能提供流量服務。** 從用戶端 VM 執行，且**要帶上 `Host` 標頭** ——
   請參閱下方第二個陷阱。

   ```bash
   az vm run-command invoke -g rg-mcn-ce-ha-rmordasiewicz -n ar-ecmp-client \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts 'for i in $(seq 1 10); do
                  curl -s -o /dev/null -w "%{http_code} " \
                    -H "Host: ar-bgp-ecmp.bankexample.com" http://10.250.0.10/
                done'
   ```

   ```text
   200 200 200 200 200 200 200 200 200 200
   ```

</Steps>

## 陷阱：某個對等連線只顯示一條路由，而這是正確的

`list-learned-routes` 的範圍限於你指定的那個對等連線。它報告的是**該**對等體
所發佈的內容，而非 Route Server 的整張表。

因此單獨查詢 `eastus01-bgp` 只會回傳一筆經由 `10.0.1.4` 的 `10.250.0.10/32`，
很容易被解讀為「只有一個 CE 在發佈 —— 另外兩個掛了」。其實什麼都沒掛。
另外兩筆發佈可在各自的對等連線上看到，這正是上方步驟 2 所迴圈查詢的內容。

無法從單一對等連線查詢來確認 ECMP。你必須迴圈查詢全部三個對等連線，
或讀取用戶端的有效路由表 —— 後者只需一次呼叫即可顯示合併後的結果。

## 陷阱：以裸 IP 發出的請求會回傳 404

負載平衡器是依 `Host` 進行比對。VIP 並不是一台會對任何連上該位址的人
提供服務的虛擬伺服器。

```text
curl -H 'Host: ar-bgp-ecmp.bankexample.com' http://10.250.0.10/   ->  200   (10 of 10)
curl                                        http://10.250.0.10/   ->  404
```

以上兩者都是在同一次針對健康部署的執行中產生的。**裸 IP 的 404 正是路徑
可用的證明** —— 請求抵達了 CE、CE 的代理做出了回應，並因為沒有相符的已設定
網域而拒絕。將它解讀為服務中斷，只會讓你去查 BGP，而你在那裡什麼問題都找不到。

示範過程中亦適用同樣道理：如果你在瀏覽器中輸入位址而非解析網域到該位址，
你就會得到 404。

## 註冊核准已自動化，而 apply 仍為兩階段

註冊核准已不再需要人員登入 console。在 provider **v3.81.1** 上，
`xcsh_registration_approval` 資源會執行核准，站點模組則負責解析要核准哪一筆註冊。

這仍然無法讓部署變成單次免人工的 `apply`，而其原因值得在你觀看首次執行
並認定它失敗之前先行了解：

- CE 的註冊物件名稱為 **`r-<uuid>`**。它絕不會以站點命名，因此在 plan 階段
  無法預測其名稱。
- 註冊只有在 VM 開機且 `vpm` 完成註冊之後才會存在。
- 因此**第一次 apply 完全不會規劃任何核准動作**。待 CE 註冊完成且核准物件
  建立後，再重新 apply 一次。

`terraform/main.tf` 在檔案開頭記錄了這個順序，該處為權威版本 ——
部署順序與實作它的程式碼放在一起。

<Aside type="caution" title="全新站點無法立即透過 operate API 存取">
在新站點回報 `ONLINE` 之後大約 25 到 30 分鐘內，`vpm/debug` 端點會回應
一個 BIG-IP `503` 頁面，內容為 `The requested URL was rejected`。它看起來像是
Web 應用程式防火牆封鎖或憑證被撤銷，但兩者都不是。請等待後重試。

這只會影響剛建好的示範環境，不會影響已在運行的環境。
</Aside>

## 存取 Site CLI

機上診斷是透過 debug API 進行，此處已寫成腳本。請確認指令介面仍與
文件所述相符：

```bash
bash scripts/capture-sitecli.sh --check --site ar-bgp-eastus01 --node f5-xc-ce-vm-01
```

```text
catalog matches the live CE (build crt-20250613-3382, 34 commands)
```

`--check` 不會寫入任何內容，因此對運行中的示範環境是安全的。

## 另外兩個測量陷阱

這兩者在本環境中都產生了令人深信不疑的錯誤答案，且兩者皆不明顯。

- **請從 VNet 內部探測，而非從你的工作站。** Netskope 會在常見通訊埠上自行
  完成 TCP 交握，因此工作站的探測會把實際上關閉的通訊埠報告為**開放**。
  從工作站探測 CE 的公用位址時，通訊埠 80 與 443 顯示為開放，而從 VNet
  內部探測則為關閉。請使用 `ar-ecmp-client`。
- **CE 上的通訊埠 22 只在內部（SLI）位址上回應。** 從 `ar-ecmp-client` 針對
  三個 CE 探測時，`10.0.3.5`、`10.0.3.6` 與 `10.0.3.7` 全部回傳
  `SSH-2.0-OpenSSH_8.7`，而管理位址與外部位址則逾時 —— 作為對照組的
  未使用位址亦然。因此，探測你所熟知的節點位址，完全無法告訴你該節點的
  SSH 狀態。
