此部署示範**在 Azure 中的 active/active Customer Edge 高可用性**，
且 CE 前方不放置任何 Azure 負載平衡器。三個 CE 各自透過 eBGP 起源相同的主機
路由，而 Azure Route Server 會將三者全部安裝為 VNet 中的等價成本下一躍點。因此，
流量分配與失效節點移除應當發生在路由網狀架構中，而非負載平衡器上。

以下所有內容都是針對實際部署執行的，輸出即為其產生的實際輸出。這句話*未*涵蓋的
兩件事 —— 容錯移轉與流量分配 —— 會在最後明確指出，而非留給讀者臆測。

## 部署了什麼

```text
                  Azure Route Server  ce-ha-lab-rrs  ASN 65515
                          10.0.4.4  and  10.0.4.5
                                      |
              +-----------------------+-----------------------+
              |                       |                       |
        eastus01-bgp            eastus02-bgp            eastus03-bgp     eBGP
              |                       |                       |      CE ASN 64512
        10.0.1.4                10.0.1.5                10.0.1.6     <- CE eth0 / SLO
     f5-xc-ce-vm-01          f5-xc-ce-vm-02          f5-xc-ce-vm-03
    ar-bgp-eastus01         ar-bgp-eastus02         ar-bgp-eastus03
              |                       |                       |
              +----- each advertises 10.250.0.10/32 -----------+
                          three-way ECMP into the VNet
```

| 元件 | 竣工內容 |
| --- | --- |
| Customer Edge | 3 個單節點 Secure Mesh v2 站台 —— `ar-bgp-eastus01`、`ar-bgp-eastus02`、`ar-bgp-eastus03` |
| CE 軟體 | 鎖定 `9.2024.6`，組建 `crt-20250613-3382` |
| Azure VM | `f5-xc-ce-vm-01/02/03`，每台三張 NIC（管理/SLO、外部、內部/SLI） |
| 路由交換 | Azure Route Server `ce-ha-lab-rrs`，ASN `65515`，執行個體 `10.0.4.4` 與 `10.0.4.5` |
| 對等連線 | 每個 CE 一組 —— `eastus01-bgp`、`eastus02-bgp`、`eastus03-bgp` —— CE ASN `64512` |
| 通告的 VIP | `10.250.0.10/32`，由三個 CE 以相同方式起源 |
| 負載平衡器 | `ar-bgp-ecmp-lb`，服務網域 `ar-bgp-ecmp.bankexample.com` |
| 測試用戶端 | `ar-ecmp-client`，位於同一 VNet 內的 VM |
| 資源群組 | `rg-mcn-ce-ha-rmordasiewicz` |

<Aside type="caution" title="VIP 必須位於每個 VNet CIDR 之外">
`terraform/main.tf` 帶有一個 `check` 區塊，會斷言 VIP 位於 hub 與 spoke 兩個 CIDR
之外，否則拒絕該 plan。其說明的理由是：位於 VNet CIDR 內的 VIP，即使 BGP 路由更為
具體，仍會輸給 VNet 自身的系統路由。

請將此防護視為契約：若你將此示範改指向不同的定址方案，VIP 也必須隨之移出 VNet 範圍。
</Aside>

## 在簡報前證明其健康狀態

四項檢查，依此順序進行。每一項都會縮小故障的範圍，因此失敗會告訴你某些訊息，
而不只是「有東西壞了」。

<Steps>

1. **三個站台皆為 `ONLINE`。** 若此項不成立，其後的一切都不可能為真。

   ```bash
   for s in ar-bgp-eastus01 ar-bgp-eastus02 ar-bgp-eastus03; do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **每個對等連線都學習到該 CE 的 VIP 通告。** 分別查詢每個對等連線 ——
   請見下方的陷阱說明，因為這正是此示範最常看起來壞掉、實則正常之處。

   ```bash
   for p in eastus01-bgp eastus02-bgp eastus03-bgp; do
     echo "--- $p"
     az network routeserver peering list-learned-routes \
       --name "$p" --routeserver ce-ha-lab-rrs -g rg-mcn-ce-ha-rmordasiewicz \
       --query "RouteServiceRole_IN_0[].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp

   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp

   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   三個對等連線、三個不同的下一躍點、一條前綴。這就證明了 ECMP 的通告面。

3. **用戶端的有效路由帶有全部三個下一躍點。** 這才是 ECMP 本身，
   也就是 VNet 實際編程的結果 —— 不是 CE 宣稱的內容，而是 Azure 據此所做的處理。

   ```bash
   az network nic show-effective-route-table \
     --name ar-ecmp-clientVMNic -g rg-mcn-ce-ha-rmordasiewicz \
     --query "value[?addressPrefix[0]=='10.250.0.10/32']" -o json
   ```

   ```json
   [
     {
       "addressPrefix": ["10.250.0.10/32"],
       "nextHopIpAddress": ["10.0.1.5", "10.0.1.4", "10.0.1.6"],
       "nextHopType": "VirtualNetworkGateway",
       "source": "VirtualNetworkGateway",
       "state": "Active"
     }
   ]
   ```

   `state: Active` 且 `nextHopIpAddress` 中有三筆項目，就是這項檢查的重點。若你預期三個
   下一躍點卻只看到一個，表示有 CE 已停止通告，而步驟 2 可辨識出是哪一個。

4. **VIP 能提供服務。** 從用戶端 VM 執行，並**帶上 `Host` 標頭** —— 請見下方第二個陷阱。

   ```bash
   az vm run-command invoke -g rg-mcn-ce-ha-rmordasiewicz -n ar-ecmp-client \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts 'for i in $(seq 1 10); do
                  curl -s -o /dev/null -w "%{http_code} " \
                    -H "Host: ar-bgp-ecmp.bankexample.com" http://10.250.0.10/
                done'
   ```

   ```text
   200 200 200 200 200 200 200 200 200 200
   ```

</Steps>

## 陷阱：單一對等連線只顯示一條路由，而這是正確的

`list-learned-routes` 的範圍僅限於你所指定的對等連線。它回報的是**該**對等體
所通告的內容，而非 Route Server 的整張路由表。

因此單獨查詢 `eastus01-bgp` 只會回傳一條經由 `10.0.1.4` 的 `10.250.0.10/32`，很容易被
解讀為「只有一個 CE 在通告 —— 另外兩個掛了」。其實沒有任何東西掛掉。另外兩筆通告
可在各自的對等連線上看到，這正是上述步驟 2 所迴圈處理的內容。

無法從單一對等連線查詢來確認 ECMP。要嘛迴圈查詢全部三個對等連線，要嘛讀取用戶端的
有效路由表，後者可在一次呼叫中顯示合併後的結果。

## 陷阱：純 IP 請求回傳 404

負載平衡器是依 `Host` 進行比對。VIP 並不是一台會對任何連到該位址的人提供內容的
虛擬伺服器。

```text
curl -H 'Host: ar-bgp-ecmp.bankexample.com' http://10.250.0.10/   ->  200   (10 of 10)
curl                                        http://10.250.0.10/   ->  404
```

以上兩者都是在同一次針對健康部署的執行中產生的。**純 IP 的 404 正是路徑可用的證明** ——
請求抵達了 CE，CE 的 proxy 做出了回應，並因為沒有比對到已設定的網域而拒絕。將其
解讀為服務中斷，會讓你去查 BGP，而在那裡你什麼問題也找不到。

示範過程中亦然：若你在瀏覽器輸入的是位址而非解析到該位址的網域，你就會得到 404。

## 註冊核准已自動化，但套用仍是兩階段

註冊核准不再需要有人到主控台操作。在 provider **v3.81.1** 上，
`xcsh_registration_approval` 資源會執行此動作，而站台模組會解析出要核准哪一筆註冊。

但這仍不代表部署是單次、全自動的 `apply`，其原因值得在你觀看首次執行並斷定它失敗之前
先行理解：

- CE 的註冊物件命名為 **`r-<uuid>`**。它絕不會以站台命名，因此在 plan 階段無法預測名稱。
- 註冊只有在 VM 開機且 `vpm` 完成註冊之後才會存在。
- 因此**第一次 apply 完全不會規劃任何核准**。待 CE 完成註冊、核准項目建立後，再重新 apply 一次。

`terraform/main.tf` 在檔案開頭記載了這個順序，該版本才是權威來源 ——
部署順序與實作它的程式碼放在一起。

<Aside type="caution" title="全新建立的站台無法立即透過 operate API 存取">
在新站台回報 `ONLINE` 之後大約 25 到 30 分鐘內，`vpm/debug` 端點會回應 BIG-IP 的 `503`
頁面，內容為 `The requested URL was rejected`。它看起來像是 Web 應用程式防火牆封鎖或
權杖遭撤銷，但兩者都不是。請稍候再重試。

這只影響剛建置好的示範，不影響已在運行的示範。
</Aside>

## 存取 Site CLI

例行的機上診斷透過 debug API 進行，此處已寫成腳本。
請確認指令介面仍與文件所述相符：

```bash
bash scripts/capture-sitecli.sh --check --site ar-bgp-eastus01 --node f5-xc-ce-vm-01
```

```text
catalog matches the live CE (build crt-20250613-3382, 34 commands)
```

`--check` 不會寫入任何內容，因此對實際運行的示範是安全的。

對於該 API 無法轉送的指令，此部署另有**以操作者身分 SSH 連入設備的 `admin` 帳號**，
其登入 shell 即為 Site CLI。三個 CE 上都已驗證可用。請從 VNet 內的主機連線到內部
（SLI）位址，並配置終端機：

```bash
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<vm-in-vnet> admin@10.0.3.5
```

```text
WELCOME IN SITE CLI
Registration Status: PROVISIONED
```

<Aside type="caution" title="該存取權存在，是因為這些 CE 在建置時就帶有它 —— 事後無法加入">
操作者金鑰是由 cloud-init 的 `write_files` 寫入，而該機制只在首次開機時執行一次。
`custom_data` 屬於僅能取代的欄位，因此在已經運行的 CE 上採用此做法會取代
每一台 CE VM —— 而取代其中一台目前會卡住註冊，同時 `terraform plan`
卻回報「No changes」（[issue 674](https://github.com/f5-sales-demo/mcn/issues/674)）。
復原花了兩次完整重建。

就本部署而言，該變更已經套用，且整個機群健康。任何要在他處採用的人，
應先閱讀 [SSH 頁面](../customer-edge/access/ssh/)。
</Aside>

## 另外兩個量測陷阱

這兩者都在此環境中產生了「看似篤定卻錯誤」的答案，而且都不明顯。

- **請從 VNet 內部而非你的工作站進行探測。** Netskope 會自行在常見連接埠上完成 TCP
  三向交握，因此工作站的探測會回報某個連接埠**開放**，實際上卻是關閉的。從工作站探測
  CE 公開位址時，連接埠 80 與 443 顯示為開放，但從 VNet 內部探測時則為關閉。請使用
  `ar-ecmp-client`。
- **CE 上的連接埠 22 僅在內部（SLI）位址上回應。** 從 `ar-ecmp-client` 對三個 CE 探測，
  `10.0.3.5`、`10.0.3.6` 與 `10.0.3.7` 都會回傳 `SSH-2.0-OpenSSH_8.7`，而管理位址與外部
  位址則逾時 —— 作為對照組的未使用位址亦然。eth0 已被更名為 `a-i-eth0` 且不帶主機 IP，
  因為它由資料路徑所擁有。因此，探測你用來認識該節點的位址，並不能告訴你該節點的 SSH
  狀態，而 SLI 位址才是應該連線的對象。

<Aside type="note" title="本頁未主張的內容">
讀者可能合理期待出現在此的兩件事被刻意省略，因為它們並未在此部署上實際演練：

- **未測試容錯移轉。** 三個等價成本下一躍點已驗證安裝完成；但當某個 CE 被停止時路由表
  會發生什麼，並未展示，因此請勿僅憑本頁就排練容錯移轉示範，務必先實際嘗試。
- **未量測流量分配。** 對 VIP 發出的十次請求中有十次回傳 `200`，這證明路徑可用，
  但並未顯示這十次是如何分散到三個下一躍點上的。

</Aside>
