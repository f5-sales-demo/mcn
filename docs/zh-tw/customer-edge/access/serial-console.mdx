Azure 序列主控台透過 Azure 平台連接至節點的模擬序列埠。它不經過 F5 Distributed Cloud 控制平面、節點的資料平面，或任何由節點控制的網路路徑 — 這正是它在其他方式都失效時仍能運作的原因。

當 CE **從未啟動**時，請使用此方式：註冊失敗、網站不存在於租戶中，或節點已啟動但沒有對外路由。在上述所有情況下，[偵錯 API](../debug-api/) 沒有可供轉送的通道。[SSH](../ssh/) 在註冊失敗後仍可使用，但前提是其金鑰已在第一次開機時寫入，且您能從 VNet 內部存取節點的內部位址 — 對於初次接觸的節點，這兩個條件均不成立。

## 前置條件：開機診斷

Azure 要求在連接序列主控台之前，必須先在 VM 上啟用開機診斷。這由 `terraform/modules/ce-node` 負責啟用：

```hcl
boot_diagnostics {}
```

空白區塊會選用 Azure 管理的儲存體，因此不需要自行管理診斷儲存體帳戶、生命週期原則或存取金鑰。在節點上確認設定：

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="啟用並不具有追溯效力">
開機診斷會在**開機時**擷取序列記錄。對已在執行中的 VM 啟用此功能，不會為已發生的開機程序產生記錄，因此 `az vm boot-diagnostics get-boot-log` 會回應：

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

這是預期行為，並非故障。在節點下次重新開機後，才會產生開機記錄。然而，即時主控台連接可立即使用 — 不依賴記錄檔。
</Aside>

## 在不使用終端機的情況下檢查可用性

連接需要互動式工作階段，但是否*能夠*連接只需兩個 API 呼叫即可確認。兩者在健康檢查中均有其用途。

該服務必須已針對訂閱啟用 — 管理員可在租戶層級將其停用：

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

接著請求連接至特定節點的序列埠：

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

以 `wss://` 開頭的 `connectionString` — 在此部署中為
`eastus.gateway.serialconsole.azure.com` — 表示主控台目前可連接。在啟用開機診斷之前，此呼叫沒有任何可連接的目標。

<Aside type="danger" title="該連接字串是一組憑證">
它是嵌入於 URL 中的短效 Bearer Token。請勿記錄、貼入工單或提交至版本控制。在示範呼叫成功時，僅輸出主機名稱即可。
</Aside>

## 連接步驟

<Steps>

1. 安裝一次擴充功能：

   ```bash
   az extension add --name serial-console
   ```

2. 進行連接：

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. 您將進入節點本身的登入提示，而非 Shell。這是 Site CLI，需要節點上設定的憑證 — 即佈建時的管理員密碼，或透過變更密碼端點所設定的密碼。序列主控台證明了*通道*可用；它並不繞過驗證。

</Steps>

以下內容擷取自 `f5-xc-ce-vm-01`，中間 systemd 單元輸出無關緊要的部分已省略：

```text file=../../../_data/serial-console-boot.txt
```

該記錄中有四點值得注意，因為它們回答了偵錯 API 無法回答的問題：

- **cloud-init 已完成** — `Datasource DataSourceAzure`，於 22.37 秒時完成。從未完成註冊的節點通常在此步驟失敗，您可在此處看到相關訊息。
- **兩個容器執行階段均已啟動。** `Container Runtime Interface for OCI (CRI-O)` 與 `Docker Application Container Engine` 均顯示 `[ OK ]`，這是開機時雙執行階段行為的佐證，此行為常讓人在 [crictl](../../commands/system/crictl/) 與 [docker](../../commands/system/docker/) 中感到困惑。
- **`VP Manager image load` 與 `Argo Watch service`** — `vpm` 與 Argo 正在啟動。
- **提示符號為節點本身的**，位於其稽核橫幅之後。序列主控台提供的是登入提示，而非工作階段。

<Aside type="caution" title="互動式連接需要真實終端機 — 但可透過腳本執行">
`az serial-console connect` 會將終端機設為原始模式，因此無法從管道或任何沒有 TTY 的情境中執行。它會在聯繫 Azure 之前於客戶端失敗：

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

此堆疊追蹤是終端機處理問題，而非序列主控台中斷。

然而，連接本身**可以**自動化 — 直接驅動 WebSocket，而非使用 CLI。上方的記錄即以此方式擷取，無需 TTY。請參閱 `scripts/serial_console_capture.py`，這是在無人守候終端機的情況下，從未能完成註冊的節點收集開機證據的方式。
</Aside>

<Aside type="caution" title="請預期需要重試：閘道大約每隔一次請求就會拒絕連接">
閘道的第一個訊框是挑戰，而非輸出，客戶端需以 Bearer Token 回應。即使正確完成，Socket 也常常會立即關閉：

```
[close] code=1011 reason=Connection not trusted
```

觀察到的行為：連接間歇性成功，在持續使用下，資源群組中的每個節點都會拒絕連接 — 包括幾分鐘前還能正常使用的節點。`scripts/serial_console_capture.py` 預設會進行重試，因為重試通常有效。

**原因尚未確定。** 以下是已排除的原因，因為每項都是合理的猜測，但都只是在浪費時間：

| 不是這個原因 | 如何確認 |
| --- | --- |
| ARM/compute 節流 | 節流會在 ARM 呼叫上回傳 HTTP `429`。這是在獨立資料通道上的 WebSocket 關閉。 |
| 代理伺服器的 TLS 攔截 | `openssl s_client -connect <region>.gateway.serialconsole.azure.com:443 \| openssl x509 -noout -issuer`。真正的 `O=Microsoft Corporation` 發行者可排除此原因；代理供應商作為發行者則確認此問題，修復方式為將 `*.serialconsole.azure.com` 加入允許清單。 |
| 開機診斷已停用 | `az vm show -g <rg> -n <vm> --query diagnosticsProfile` 回報 `enabled: true`。 |
| 授予與挑戰之間的 Token 不符 | 對兩者使用同一個 Token 是正確做法，但無法防止連接關閉。 |

已有文件記載的 Azure 行為：**每個 VM 僅允許一個序列主控台工作階段，第二個成功的請求會驅逐第一個。** 被驅逐的使用者會斷開連接，但不會被登出，因此 Shell 工作階段得以保留。兩人同時偵錯同一節點時，將會不斷互相取代對方的連接。

進行批次作業時，建議優先使用[偵錯 API](../debug-api/) 或 [SSH](../ssh/)，兩者均無上述限制。尤其是 SSH，沒有貼上上限也沒有單一工作階段限制，因此只要能從 VNet 內部存取節點，SSH 是更好的選擇。
</Aside>

<Aside type="caution" title="貼上長度上限為 2,048 個字元">
Azure 將序列主控台的貼上長度限制為 2,048 個字元，以避免序列埠超載。傳送長指令 — 或在單次寫入中傳送一批指令 — 失敗時的表現會像是卡住或被節流，而非長度限制錯誤。

請逐一傳送指令。這是透過序列主控台進行批次收集的實際限制，也是進行此類工作時應優先選用[偵錯 API](../debug-api/) 的另一個原因。
</Aside>

## 此處可看到而 API 無法顯示的資訊

- **cloud-init** 的執行、失敗或從未啟動 — 這是節點從未完成註冊的常見原因。
- 針對 `register.ves.volterra.io` 的**註冊嘗試**，包括設定錯誤或租戶拒絕的 Token。
- 在任何代理程式執行之前的**核心與開機訊息**。
- 節點在**沒有可用網路路徑**時的狀態，此情況會讓所有其他存取路由失效。

對於已處於 `ONLINE` 狀態的節點，請優先使用偵錯 API：它可編寫腳本、產生可重複執行的證據，且不會佔用唯一的序列埠。
