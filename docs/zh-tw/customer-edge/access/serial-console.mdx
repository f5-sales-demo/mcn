擷取自本部署環境中某一台 CE，時間為 2026-07-28。`sitecli/capture-manifest.json`
記錄了是哪一個節點，而 `scripts/capture-sitecli.sh --check` 會針對執行中的 CE
重新驗證指令介面。

Azure 序列主控台透過 Azure 平台掛接到節點的模擬序列埠。它不會經過 F5 Distributed Cloud
控制平面、節點的資料平面，或任何由節點掌控的網路路徑——這正是為什麼在其他方式都失效時，
它依然能運作。

當某台 CE **從未成功啟動**時就該動用它：註冊失敗、租戶中找不到該站點，
或節點雖已啟動卻沒有對外路由。在上述所有情況下，
[除錯 API](../debug-api/) 都沒有可轉送的通道。[SSH](../ssh/) 在註冊失敗後仍可使用，
但前提是其金鑰已在首次開機時寫入，且你能從 VNet 內部連到節點的內部位址——
對於一台你初次接觸的節點，這兩點都不成立。

如果節點還有**任何**可用的網路路徑，請先嘗試 [Site Console](../site-console/)：
它同樣能在註冊失敗後使用、不需要金鑰，也不會把已在查看該節點的人踢下線。
序列主控台是在網路路徑本身就是故障點時所剩的最後手段。

## 前置條件：開機診斷

Azure 要求 VM 必須啟用開機診斷，才會掛接序列主控台。
這已由 `terraform/modules/ce-node` 啟用：

```hcl
boot_diagnostics {}
```

空白區塊表示選用 Azure 代管的儲存體，因此不需要自行管理診斷儲存體帳戶、
生命週期政策或存取金鑰。在節點上確認：

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="啟用不具追溯效力">
開機診斷是在**開機時**擷取序列記錄。對一台已在執行中的 VM 啟用它，
並不會為已經發生的那次開機產生記錄，因此
`az vm boot-diagnostics get-boot-log` 會回應：

```text
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

這是預期行為，不是故障。節點下次重新開機後才會有開機記錄。
不過即時主控台掛接可以立刻使用——它不依賴該記錄。
</Aside>

## 不用終端機也能檢查可用性

掛接需要互動式工作階段，但要判斷它*是否能*掛接只需兩個 API 呼叫。
兩者在健康檢查中都很有用。

該服務必須在訂閱層級為啟用狀態——管理員可以在整個租戶範圍停用它：

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

接著請求連線到特定節點的序列埠：

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

回傳以 `wss://` 開頭的 `connectionString`——在本部署環境中是
`eastus.gateway.serialconsole.azure.com`——表示主控台現在就可以掛接。
在啟用開機診斷之前，此呼叫沒有任何可掛接的對象。

<Aside type="danger" title="該連線字串是一項憑證">
它是嵌在 URL 中的短期 bearer token。不要記錄它、貼進工單，或提交進版本庫。
當你要示範呼叫成功時，只印出主機名稱即可。
</Aside>

## 掛接

<Steps>

1. 安裝擴充功能（僅需一次）：

   ```bash
   az extension add --name serial-console
   ```

2. 掛接：

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. 你會抵達節點自己的登入提示字元，而不是 shell，且位於設備的稽核橫幅之後。
   序列主控台證明的是*通道*可用；它不會繞過身分驗證。

   <Aside type="caution" title="序列登入接受哪一種憑證尚未驗證">
   本部署環境中還沒有人透過序列主控台完成登入，因此本頁不會說明該輸入什麼。
   `admin` 是設備帳戶，其 shell 為 Site CLI，同一個帳戶也能以密碼透過
   [Site Console](../site-console/) 進行驗證——但密碼是否適用於序列主控台登入
   尚未得到證實，而 `sshd` 對 `admin` 僅接受金鑰，所以這兩者顯然不是同一條憑證路徑。
   </Aside>

</Steps>

擷取自 `f5-xc-ce-vm-01`，中段 systemd unit 輸出因無額外資訊而省略：

```text file=../../../_data/serial-console-boot.txt
```

該記錄中有四點值得注意，因為它們回答了除錯 API 無法回答的問題：

- **cloud-init 已完成**——`Datasource DataSourceAzure`，於 22.37 秒完成。
  從未註冊成功的節點通常就是在這裡失敗，而這裡正是你能看到的地方。
- **兩套容器執行環境都已啟動。**`Container Runtime Interface for OCI (CRI-O)`
  與 `Docker Application Container Engine` 都是 `[ OK ]`，這是雙執行環境行為在開機時的
  證據，而該行為常讓人在
  [crictl](../../commands/system/crictl/) 與 [docker](../../commands/system/docker/) 中感到意外。
- **`VP Manager image load` 與 `Argo Watch service`**——`vpm` 與 Argo 正在啟動。
- **提示字元是節點自己的**，位於其稽核橫幅之後。序列主控台給你的是登入提示字元，
  不是一個工作階段。

<Aside type="caution" title="互動式掛接需要真正的終端機——但可以指令碼化">
`az serial-console connect` 會把終端機切換為 raw 模式，因此無法在管線
或任何沒有 TTY 的環境中執行。它會在聯絡 Azure 之前於用戶端就失敗：

```text
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

那段追溯訊息是終端機處理問題，不是序列主控台故障。

不過掛接本身**確實**可以自動化——直接驅動 websocket，而不使用 CLI。
上方的記錄就是以這種方式擷取的，沒有 TTY。請參閱
`scripts/serial_console_capture.py`，這就是你要在無人守著終端機的情況下，
從註冊失敗的節點收集開機證據的做法。
</Aside>

<Aside type="caution" title="預期需要重試：閘道大約每兩次就拒絕一次">
閘道的第一個訊框是一個挑戰，而不是輸出，用戶端會以 bearer token 回應。
即使正確完成這一步，socket 仍經常立即關閉：

```text
[close] code=1011 reason=Connection not trusted
```

觀察到的行為：它會間歇性成功，而在持續使用下，資源群組中的每個節點都會拒絕連線——
包括幾分鐘前還能正常運作的節點。
`scripts/serial_console_capture.py` 預設會重試，因為重試通常有效。

**成因尚未確立。**以下是已排除的可能性，因為每一項都是會浪費時間的合理猜測：

| 不是這個 | 如何確認 |
| --- | --- |
| ARM／compute 節流 | 節流會在 ARM 呼叫上回傳 HTTP `429`。這裡是另一條資料通道上的 websocket 關閉。 |
| 代理伺服器進行 TLS 攔截 | `openssl s_client -connect <region>.gateway.serialconsole.azure.com:443 \| openssl x509 -noout -issuer`。若發行者確實是 `O=Microsoft Corporation` 即可排除；若發行者是代理廠商則可確認，修正方式是將 `*.serialconsole.azure.com` 加入允許清單。 |
| 開機診斷未啟用 | `az vm show -g <rg> -n <vm> --query diagnosticsProfile` 回報 `enabled: true`。 |
| 授權與挑戰之間的 token 不一致 | 兩者使用同一個 token 是正確做法，但無法避免連線關閉。 |

而*確實*有文件記載的 Azure 行為是：**每台 VM 只能有一個序列主控台工作階段，
第二個成功的請求會踢掉第一個。**被踢掉的使用者會斷線但不會登出，
因此 shell 工作階段仍會存在。兩個人同時除錯同一個節點會反覆把對方擠掉。

批量作業請優先採用[除錯 API](../debug-api/) 或 [SSH](../ssh/)，兩者都沒有這些限制。
SSH 尤其沒有貼上字數上限，也沒有單一工作階段限制，
因此只要能從 VNet 內部連到節點，它就是更好的選擇。
</Aside>

<Aside type="caution" title="貼上內容上限為 2,048 個字元">
Azure 將序列主控台的貼上長度限制為 2,048 個字元，以避免序列埠過載。
送出過長的指令——或在一次寫入中送出一批指令——失敗的樣子會像是卡住或被節流，
而不像是長度限制。

請逐一送出指令。這是透過序列主控台進行任何批量收集時的實際限制，
也是該類工作應優先使用[除錯 API](../debug-api/) 的另一個理由。
</Aside>

## 在這裡能看到、但 API 無法呈現的內容

- **cloud-init** 正在執行、失敗，或從未啟動——這是節點從未註冊成功的常見原因。
- 針對 `register.ves.volterra.io` 的**註冊嘗試**，包括設定錯誤
  或租戶拒絕的 token。
- 任何代理程式尚未執行之前的**核心與開機訊息**。
- 節點**完全沒有可用網路路徑**時的狀態，而這種情況會讓其他所有途徑失效。

對於*處於* `ONLINE` 狀態的節點，請優先使用除錯 API：它可指令碼化、
能產生可重複執行的證據，且不會佔用唯一的序列埠。
