Azure 序列主控台透過 Azure 平台連接至節點的模擬序列埠。它不經過 F5 Distributed Cloud 控制平面、節點的資料平面，或任何由節點控制的網路路徑——這正是它在其他方式都失效時仍能運作的原因。

當 CE **從未啟動**時請使用此途徑：註冊失敗、站台不存在於租戶中，或節點已啟動但無對外路由。在上述所有情況下，[debug API](../debug-api/) 沒有可供中繼的通道，而且節點出廠時 SSH 也處於關閉狀態。

## 前置條件：開機診斷

Azure 在允許連接序列主控台之前，要求 VM 必須啟用開機診斷。此設定由 `terraform/modules/ce-node` 啟用：

```hcl
boot_diagnostics {}
```

空白區塊會選用 Azure 管理的儲存體，因此不需要自行管理診斷儲存體帳戶、生命週期原則或存取金鑰。在節點上確認設定：

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="啟用並不具有追溯效力">
開機診斷會在**開機時**擷取序列日誌。對已在執行中的 VM 啟用此功能，不會為已完成的開機程序產生日誌，因此 `az vm boot-diagnostics get-boot-log` 會回應：

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

這是預期行為，並非故障。節點下次重新開機後才會產生開機日誌。然而，即時主控台連接可立即運作——它不依賴日誌。
</Aside>

## 不使用終端機檢查可用性

連接需要互動式工作階段，但判斷是否*能夠*連接只需兩個 API 呼叫。兩者都適用於健康狀態檢查。

必須為訂閱啟用此服務——管理員可以在整個租戶範圍內停用它：

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

接著向特定節點的序列埠要求連線：

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

以 `wss://` 開頭的 `connectionString`——在本部署環境中為 `eastus.gateway.serialconsole.azure.com`——表示主控台目前可以連接。在啟用開機診斷之前，此呼叫沒有任何可連接的目標。

<Aside type="danger" title="該連線字串是一種憑證">
它是嵌入於 URL 中的短期持有人權杖。請勿將其記錄於日誌、貼入工單或提交至版本控制。在展示呼叫成功時，僅顯示主機名稱即可。
</Aside>

## 連接方式

<Steps>

1. 安裝延伸模組（僅需一次）：

   ```bash
   az extension add --name serial-console
   ```

2. 連接：

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. 您會進入節點本身的登入提示，而非 Shell。這是 Site CLI，需要節點上設定的憑證——來自佈建時的管理員密碼，或透過 change-password 端點設定的密碼。序列主控台驗證的是*通道*是否正常運作；它並不繞過身份驗證。

</Steps>

以下為從 `f5-xc-ce-vm-01` 擷取的記錄，中間省略了 systemd 單元輸出中無關緊要的部分：

```text file=../../../_data/serial-console-boot.txt
```

該記錄中有四項值得注意的內容，因為它們回答了 debug API 無法回答的問題：

- **cloud-init 已完成** — `Datasource DataSourceAzure`，在 22.37 秒時完成。從未完成註冊的節點通常在此處失敗，在這裡可以看到失敗原因。
- **兩個容器執行環境均已啟動。** `Container Runtime Interface for OCI (CRI-O)` 與 `Docker Application Container Engine` 均顯示 `[ OK ]`，這是雙執行環境行為在開機時的確認，該行為在 [crictl](../../commands/system/crictl/) 和 [docker](../../commands/system/docker/) 中常令人感到意外。
- **`VP Manager image load` 與 `Argo Watch service`** — `vpm` 和 Argo 正在啟動。
- **提示符號是節點本身的**，位於其稽核橫幅之後。序列主控台提供的是登入提示，而非工作階段。

<Aside type="caution" title="互動式連接需要真實終端機——但可以透過腳本自動化">
`az serial-console connect` 會將終端機設為原始模式，因此無法在管線或任何沒有 TTY 的情境中執行。它在客戶端就會失敗，甚至在聯繫 Azure 之前：

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

該堆疊追蹤是終端機處理問題，並非序列主控台中斷。

然而，連接本身**可以**自動化——直接驅動 WebSocket，而非使用 CLI。上方記錄即是以這種方式擷取的，不需要 TTY。請參閱 `scripts/serial_console_capture.py`，這是在節點未能完成註冊時、無需人員守候終端機即可收集開機記錄的方法。
</Aside>

<Aside type="caution" title="預期需要重試：閘道大約每隔一次嘗試就會拒絕連線">
閘道的第一個訊框是挑戰，而非輸出，客戶端需以持有人權杖回應。即便操作正確，Socket 也常會立即關閉：

```
[close] code=1011 reason=Connection not trusted
```

經過在三個節點上反覆測試，此現象呈現交替出現的規律：拒絕之後，同一節點上的下一次嘗試便會成功。這與先前的工作階段仍被佔用一致，而被拒絕的嘗試會將其清除。

**這不是憑證問題**，儘管訊息如此顯示。通常重試即可解決，這也是 `scripts/serial_console_capture.py` 預設會重試的原因。

無論如何，請對工作階段請求和挑戰使用同一個權杖，與 `az` 延伸模組的做法保持一致。這是正確的做法，但並非導致此問題的原因。
</Aside>

## 此處可見而 API 無法顯示的資訊

- **cloud-init** 執行中、失敗或從未啟動——這是節點從未完成註冊的常見原因。
- **向 `register.ves.volterra.io` 發起的註冊嘗試**，包括設定錯誤或租戶拒絕的權杖。
- **核心與開機訊息**，來自任何代理程式執行之前的階段。
- 節點在**沒有可用網路路徑**時的狀態，這會讓所有其他途徑失效。

對於狀態為 `ONLINE` 的節點，建議優先使用 debug API：它可以透過腳本自動化、產生可重現的記錄，且不會佔用唯一的序列埠。
