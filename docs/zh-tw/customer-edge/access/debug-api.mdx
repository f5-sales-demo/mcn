`vpm/debug` API 會在已註冊的節點上執行 Site CLI 命令並回傳其輸出。以下所有內容都是針對實際運作的節點驗證所得；這些內容皆未由上游發布。

## 命令目錄具備自我描述能力

在 POST 至 `exec-user` 時**省略** `command` 鍵，即可詢問節點支援哪些命令：

```bash
curl -sS -X POST \
  -H "Authorization: APIToken $XCSH_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"namespace":"system","site":"<site>","node":"<node>"}' \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/<node>/exec-user" \
  | jq -r .output | jq .
```

回應是以命令名稱為鍵的 JSON 物件：

```json
{
  "crictl-inspect": ["System Troubleshooting", "ExecUser", " container-id"],
  "diagnosis":      ["System Troubleshooting", "ExecUser", "no argument needed", "GLOBAL"],
  "ip-link-set":    ["Network Troubleshooting", "Exec", " (<device>||<group>) (up||down)"]
}
```

每一筆項目的格式為 `[category, tier, exampleArgument?, scope?]`，而這些欄位並非文件說明——它們決定了命令必須以何種方式呼叫。

<Aside type="caution" title="請省略該鍵；不要傳送錯誤的值">
探索功能的運作方式是將 `command` 完全省略。若改為傳送未知的值，回傳的會是錯誤，而不是目錄：

```json
{"code":3,"details":[],"message":"exec command failed: command not supported"}
```

當一個*真實存在*的命令被送到錯誤的端點時，也會得到相同的訊息，因此很容易被誤讀為「此命令不存在」。
</Aside>

## 三種傳輸方式，由目錄項目決定

| 條件 | 方法與路徑 | 主體 | 回傳 |
| --- | --- | --- | --- |
| `scope` 為 `GLOBAL` | `GET .../vpm/debug/global/<cmd>` | 無 | JSON |
| `tier` 為 `ExecUser` | `POST .../vpm/debug/<node>/exec-user` | `command` 陣列 | 文字 |
| `tier` 為 `Exec` | `POST .../vpm/debug/<node>/exec` | `command` 陣列 | 文字 |

### `ExecUser` — 唯讀層級 <Badge text="31 個命令" variant="note" />

最常見的情況。將命令及其引數以陣列形式傳遞，命令名稱放在第一個位置：

```bash
curl -sS -X POST \
  -H "Authorization: APIToken $XCSH_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"namespace":"system","site":"<site>","node":"<node>","command":["crictl-ps"]}' \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/<node>/exec-user"
```

```json
{ "return_code": 0, "output": "CONTAINER    IMAGE    CREATED    STATE ..." }
```

引數必須是獨立的陣列元素，而不是單一字串：

```json
{ "command": ["journalctl", "-u", "vpm", "-n", "200"] }
```

### `GLOBAL` — 站點範圍，且傳輸方式完全不同 <Badge text="2 個命令" variant="tip" />

只有 `health` 與 `diagnosis` 這兩個。它們是對 `global` 路徑發出的 `GET` 請求，不接受任何引數，並回傳結構化 JSON 而非終端機文字。

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/global/health" | jq .
```

<Aside type="danger" title="GLOBAL 命令無法透過 exec-user 存取">
這是最耗費時間的陷阱。將 `health` 或 `diagnosis` 送至 `exec-user` 會回傳 `command not supported`，看起來就像該命令在節點上不存在——但事實上它確實存在，只是你用錯了傳輸方式。

```bash
# 錯誤。回傳：exec command failed: command not supported
-d '{"namespace":"system","site":"…","node":"…","command":["health"]}'   # POST exec-user

# 正確。
GET .../vpm/debug/global/health
```

</Aside>

### `Exec` — 特權層級 <Badge text="此組建上有 1 個命令" variant="danger" />

這是獨立的端點，而且層級屬於強制執行而非建議性質：`exec` 會以相同的 `command not supported` 訊息拒絕 `ExecUser` 命令。此層級的每個成員都會變更節點狀態或讀取狀態標記。

在此租戶所執行的組建上，該層級僅包含 `ip-link-set`。較新的組建則加入了 `systemctl-restart-NetworkManager`、`systemctl-restart-crio`、`systemctl-restart-kubelet`、`systemctl-start-crio-prune` 以及三個 `marker-exists-*` 命令。

<Aside type="danger" title="本文件不會執行任何 Exec 命令">
擷取工具會拒絕此層級，並且是從即時目錄而非硬編碼清單讀取層級資訊——因此若未來的組建將某個命令提升至 `Exec`，也會被自動遵守，無須任何人修改程式碼。只有在你刻意為之、且願意讓該節點受到干擾時，才執行這類命令。
</Aside>

## 尋找站點與節點名稱

節點名稱即 Azure VM 名稱，而 `list-service` 是一種成本低廉的方式，可同時確認節點名稱與其上執行的服務：

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/global/list-service" \
  | jq -r '[.service[].node] | unique'
```

```json
["", "f5-xc-ce-vm-01"]
```

某些服務回報的節點名稱為空，因此該清單中的空字串是回應本身的產物，而不是第二個節點。`list-service` 也不在 34 個命令的目錄之中：它是目錄未公告的 `global` 端點，這也是為什麼它記錄在此處，而不在[命令參考](../../commands/)中。

## 重現本儲存庫的擷取結果

每個命令頁面都嵌入了由 `scripts/capture-sitecli.sh` 擷取的輸出，該腳本實作了上述全部三項規則。

<Steps>

1. 將其指向某個租戶。它會讀取 `XCSH_API_URL` 與 `XCSH_API_TOKEN`，否則退回使用目前啟用的 `xcsh` 環境。

2. 重新整理目錄，並確認節點未在文件之下發生變更：

   ```bash
   bash scripts/capture-sitecli.sh --check
   ```

   這只會比對已提交的目錄與軟體組建。它會將組建變更與新增或移除的命令分別回報。

3. 當你需要最新證據時重新擷取：

   ```bash
   bash scripts/capture-sitecli.sh
   ```

</Steps>

<Aside type="note" title="擷取結果是證據，而非可重現的產物">
計數器、運行時間與容器存續時間會在每次執行之間變動，因此重新擷取必然會產生差異。目錄才是穩定的契約，在節點未變更時，各次執行之間會逐位元組相同；這正是 `--check` 所比對的內容。過長的輸出會被裁剪並以明確的標記結尾，因此被截斷的表格絕不會被呈現為完整內容。
</Aside>

<Aside type="danger" title="從客戶節點擷取時：請檢查遮蔽設定檔">
命令輸出會攜帶基礎架構身分資訊——內部尋址、MAC 位址、AS 編號、主機名稱——而對客戶而言，這些都是可識別該組織的資訊。

因此清理過濾器預設採用**嚴格（strict）**設定檔，將這些資訊全部移除。本儲存庫在 `sitecli/capture-manifest.json` 中宣告為 `lab`，會保留這些細節，而這僅在此處成立，因為這些擷取結果來自 F5 自有的示範基礎架構。

**請勿將該設定套用至客戶的擷取作業。** 在兩種設定檔之下，權杖、私密金鑰、租戶識別碼、物件 UUID、電子郵件位址與家目錄路徑都會被移除。

有一項限制值得注意：BGP 鄰居表會將 AS 以未加標籤的裸欄位形式輸出，沒有可供比對模式定位的標籤，因此 ASN 是依數值比對私有範圍。位於該處的**公有** ASN 在嚴格模式下仍會保留，發布前需要人工檢閱 `show-ip-bgp*` 的輸出。
</Aside>
