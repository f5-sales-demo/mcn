SSH 可連線至設備的 `admin` 帳號，其登入 Shell 為 Site CLI
（`/opt/bin/vpmu`）。這是通往**完整機上指令介面**的唯一路徑——
[debug API](../debug-api/) 僅提供 34 個指令，而設備本身提供了更多未列於該 API 的指令。

```bash
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<operator-vm> admin@10.0.3.5
```

該指令列的每個部分都不可或缺，接下來三個章節將說明各部分分別防止哪種失敗情況。

<Aside type="caution" title="在執行中的部署上啟用此功能將替換 VM">
金鑰由 cloud-init 寫入，而 cloud-init 的 `write_files` 僅在**首次開機**時執行。
對現有節點啟用此功能意味著必須替換它們，而目前這樣做會導致註冊卡住：
舊的註冊記錄佔用了唯一的 `(tenant, cluster_name, hostname)` 索引，
替換後的節點永遠無法完成註冊，且 `terraform plan` 全程顯示「No changes」。
請在規劃變更**之前**參閱 [issue 674](https://github.com/f5-sales-demo/mcn/issues/674)，而非之後。
</Aside>

## 為何 cloud-init 負責寫入金鑰，而非 API

site 物件上的 `admin_user_credentials.ssh_key` 看起來正是用於此用途的欄位。
它可以被接受、可以在讀回時保留，但實際上不設定任何東西。`vpm` 負責管理節點的本機使用者，
並拒絕操作此帳號——從節點自身的日誌中，在單次開機期間出現了三次：

```text
vpm  users.go:165: Won't do any change for user admin (internal skip)
```

所有後續問題都源自這一行。`/var/home/admin/.ssh` 從未存在過，無論是在 site 到達 `ONLINE`
狀態之前或之後。`admin` 的 shadow 最後修改日期停留在映像檔建置日期，
而 `vesbkp` 和 `vesopcon` 顯示的是當前日期，因為 `vpm` 設定了這兩者並跳過了 `admin`。
且 `vpm` 在任何時間點都沒有記錄任何關於 `ssh_key` 或 `authorized_keys` 的日誌。

因此，該檔案必須在 `vpm` 之外寫入。`admin` 的 uid 為 2202，已烘焙至節點映像檔中，
所以它在 cloud-init 執行前就已存在，`owner: admin:admin` 在寫入時即可解析——
無需 `runcmd`，無需事後修正擁有權：

```yaml
- path: /var/home/admin/.ssh/authorized_keys
  permissions: "0600"
  owner: admin:admin
  content: |
    ${ssh_public_key}
```

`sshd` 一直是允許連線的。`sshd -T` 回報 `pubkeyauthentication yes`，
且 `admin` 出現在節點上兩個 `sshd_config` 檔案的 `AllowUsers` 中。
從來不需要啟用任何東西——只是缺少一個檔案。

<Aside type="danger" title="請勿重新加入 admin_user_credentials，也請勿編輯 sshd_config">
`admin_user_credentials` 曾被接入 `terraform/modules/xc-site`，
在收集到此證據後已恢復（#660，PR #663）。這不是一個等待填補的缺口。

`sshd_config` 在註冊期間會被替換，因此對其所做的編輯將在最不方便的時機被丟棄。
</Aside>

## 為何它只在一個位址上回應

`sshd` 綁定 `0.0.0.0:22`，但只有**內部（SLI）**位址存在於主機網路堆疊中。
eth0 被重新命名為 `a-i-eth0` 且不攜帶主機 IP——Argo 資料平面擁有該介面——
而 eth1 和 eth2 保留在主機堆疊上，`sshd` 正在那裡監聽。

從 VNet 內部的 VM 探測結果：

```text
10.0.1.4     timed out             CE mgmt/SLO  (eth0)
10.0.2.4     timed out             CE external  (eth1)
10.0.3.5     OPEN                  CE internal/SLI
10.0.3.6     OPEN
10.0.3.7     OPEN
```

因此，對您所知道的節點位址進行探測，會得到與關閉的安全群組完全相同的結果。
沒有任何東西在封鎖它；只是該位址上沒有監聽器。

CE 的公用位址在連接埠 22 上也沒有監聽器，這就是為什麼上述指令需要透過 `-J` 跳轉：
一個位於 VNet 內部、與 SLI 位址同一子網路中的操作員 VM。

<Aside type="caution" title="兩種會產生自信但錯誤答案的測量錯誤">
探測 eth0、外部介面或公用位址的連接埠 22，無論節點的 SSH 狀態如何都會回報關閉，
因此無法提供任何資訊。只有 SLI 位址才會回應。

此外，從公司工作站探測可能會將實際關閉的連接埠回報為**開放**：
Netskope 會在常見連接埠上自行完成 TCP 握手。
從工作站探測時，CE 公用位址的 80 和 443 連接埠顯示為開放，
但從 VNet 內部探測時則是關閉的。請從 VNet 內的 VM 進行探測。
</Aside>

## Site CLI 需要終端機，以及歸位字元

`admin` 的登入 Shell 不是一般的 Shell。它是一個 `go-prompt` 應用程式，
會將終端機設為原始模式並逐鍵讀取輸入，而非按行讀取。
這帶來四個後果，每一個失敗的表現看起來都像不同的問題：

| 機制 | 缺少時會發生什麼 |
| --- | --- |
| 配置終端機（`ssh -tt`） | `go-prompt.NewStandardInputParser` 發生 `panic: no such device or address`，看起來像設備當機 |
| 按 Enter 時傳送歸位字元而非換行字元 | 該行永遠不會被提交，工作階段在輸入結束時關閉且未印出任何內容 |
| 保持標準輸入開啟 | 指令尚未渲染完畢連線就已結束，導致正常運作的指令看起來沒有任何輸出 |
| **分別**寫入指令文字和 Enter 位元組 | 換行字元作為字面字元落入緩衝區，CLI 回答 `unknown command`，看起來像是該指令不存在 |

因此 `ssh host 'some-command'` 無法運作：參數會被忽略，互動式提示符照常啟動。
必須以終端機方式驅動，否則就完全無法使用。
`scripts/sitecli_ssh_harvest.py` 是參考實作。

登入橫幅會回報節點的註冊狀態，這是區分仍在啟動中的節點與故障節點的最快方式：

```text
Registration Status: PROVISIONING
SLO IP: 10.0.1.4/26
```

## 提供金鑰對

<Steps>

1. 若您尚未擁有金鑰對，請先產生一個。使用 Ed25519 而非 RSA：更短，
   且被設備的 `sshd` 接受。

   ```bash
   ssh-keygen -t ed25519 -C "ce-operator" -f ~/.ssh/id_ed25519
   ```

2. 將部署指向**公鑰**的那一半。根模組讀取一次該檔案，
   並將字串傳遞給每個節點：

   ```hcl
   # terraform/terraform.tfvars
   ssh_public_key_path = "~/.ssh/id_ed25519.pub"
   ```

   `ssh_public_key` 則接受內嵌的金鑰材料，這是計畫測試所使用的方式。
   私鑰永遠不會離開您的工作站。

3. 套用。請先閱讀本頁頂端的警告——在現有部署上執行此操作將替換 CE VM。

</Steps>

<Aside type="note" title="VM 自身的 admin_ssh_key 是不同的東西">
`modules/ce-node` 中的 `azurerm_linux_virtual_machine.admin_ssh_key`
授權的是 Azure VM 管理員，而非設備的 `admin` 帳號。
它不授予任何 Site CLI 存取權，且設定了此項目並不代表 CE SSH 已完成設定。
</Aside>

## 這不是什麼

以下每一項在該路由仍被認為不可能時都經過了測試並被排除。
每一項都有足夠的可信度讓人花費一天時間。

| 不是原因 | 如何被排除 |
| --- | --- |
| 憑證僅在建立時套用 | `sshd` 在首次開機約 90 秒後啟動，早於 site 物件存在。`admin_user_credentials` 也存在於 `ReplaceSpecType` 中並就地套用。 |
| `block_all_services` | 無論服務是否被封鎖，管理位址上連接埠 22 的關閉狀態完全相同。 |
| 金鑰末尾的換行字元 | 兩種方式都測試過，沒有差異。cloud-init 仍會去除它，因為字面區塊否則會渲染出第二個空行。 |
| 已固定的舊版 CE 軟體 | 在三個版本上重現，包括一個執行 OpenSSH 9.9 的版本。 |
| 缺少 `admin_password` | 在全新 CE 上同時設定 `admin_password` 和 `ssh_key` 沒有任何改變。 |

<Aside type="caution" title="兩個看起來像判別依據但實際上不是的 API 欄位">
`gc_spec.admin_ssh_key` 在**租戶中所有 88 個 site** 上都是空的，
包括設定了 `admin_password` 的 20 個。
在正常運作與異常的 site 之間比較此欄位沒有任何意義，因為它在所有地方都是空的。

`registrations_by_site` 完全省略了該欄位，並為其回傳 `None`，
這讀起來像「未設定」而非「未回報」。
</Aside>

<Aside type="caution" title="新建立的 site 在 operate API 回應前需要約半小時">
在新 site 回報 `ONLINE` 後約 25 至 30 分鐘內，`vpm/debug` 端點會回傳
BIG-IP 的 `503` 頁面，顯示「The requested URL was rejected」。
這看起來像是 Web 應用程式防火牆封鎖或令牌被撤銷，但都不是：
site 尚未準備好進行轉傳。請等待並重試，而非修改任何設定。

SSH 沒有此類預熱階段。它在 `sshd` 啟動後即可回應，
這就是為何在節點仍在註冊期間，SSH 是能夠正常運作的路由。
</Aside>
