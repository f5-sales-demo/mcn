SSH 會連上設備的 `admin` 帳號，其登入 shell 為 Site CLI
（`/opt/bin/vpmu`）。這是取得**完整機上命令介面**的唯一途徑——
[debug API](../debug-api/) 只公開 34 個命令，而設備本身提供的命令遠多於此，
其中許多完全不在該 API 上。

```bash
cd terraform
SLI=$(terraform output -json ce_sli_private_ips | jq -r '.eastus01')
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<operator-vm> "admin@$SLI"
```

該命令列的每一個部分都不可或缺，接下來的三個小節會說明每一個部分各自預防了哪一種失敗。

<Aside type="danger" title="請查詢內部位址——絕對不要沿用先前工作階段的位址">
Azure 在每次重建時都會重新指派內部子網路位址，而且不會依節點順序。在最近一次重建之後，
`f5-xc-ce-vm-01`、`-02` 與 `-03` 分別持有 `10.0.3.7`、`10.0.3.5` 與 `10.0.3.4`；
先前的建置順序則完全不同，而且測試用戶端的 NIC 位於同一個子網路，並曾持有某個 CE 先前使用過的位址。
因此，連線到記憶中的位址會落到錯誤的節點、落到根本不是 CE 的 VM，或者根本連不上——
而最後這種情況看起來與「SSH 未啟用」完全一樣。

`terraform output -json ce_sli_private_ips` 就是對應關係。若手邊沒有 state，NIC
名稱是穩定的，即使位址並非如此：

```bash
az network nic show -g rg-mcn-ce-ha-rmordasiewicz \
  -n f5-xc-ce-vm-01-internal-nic \
  --query ipConfigurations[0].privateIPAddress -o tsv
```

</Aside>

<Aside type="caution" title="僅限開機引導階段——既有的 CE 若不重新建立就無法取得 SSH">
cloud-init `write_files` **只會在首次開機時執行一次**。之後節點上會存在
`/etc/cloud/cloud-init.disabled` 標記檔，cloud-init 不會再次執行。

因此，對執行中的 CE 沒有原地套用的途徑。`custom_data` 在 Azure 中屬於僅可替換
（replace-only）的屬性，這意味著在既有部署上採用此做法會**替換每一台 CE VM**。
為已經運行中的節點授予操作人員 SSH 存取權是一次重建，而非組態變更——
下一則警告說明了該重建過去會付出什麼代價，以及為何現在不再如此。
</Aside>

<Aside type="caution" title="替換 CE VM 過去會永久卡住註冊——此問題已修正，這也是站台物件與 VM 耦合的原因">
在規劃重建之前值得先了解，因為該失敗的形態解釋了你將在 plan 中看到的耦合關係。

過去的情況是：被銷毀節點的註冊仍持有控制平面唯一的
`(tenant, cluster_name, hostname)` 索引，因此替換節點的註冊會被以
`UniqueSecondaryIndexViolationError` 拒絕，並無止盡地重試。單獨刪除註冊並不足夠：
殘留的 `StatusObject` 會對工作負載請求回傳 `500`，而到那時每個節點都已經持久化了一份
`registration-obj.yml`，將自己釘在你已刪除的那份註冊上，於是它會在 `404` 上不斷迴圈且無法自我復原。
復原需要兩次完整重建。在整個過程中，`terraform plan` 都回報**「No changes」**，
因為從 Terraform 的角度來看，期望狀態已經達成。

[Issue 674](https://github.com/f5-sales-demo/mcn/issues/674) 已藉由
[PR 693](https://github.com/f5-sales-demo/mcn/pull/693) 關閉。`modules/xc-site` 現在會在
`replace_triggered_by` 中指名 CE VM 實例，因此替換 VM 就會替換站台物件，而刪除站台會連帶刪除其註冊——
在替換節點開機之前索引鍵就已釋出。此後整個機群已從零重建，三個站台皆在無需人工介入的情況下進入 `ONLINE`。

這種耦合是可觀察的，而非假設。每個站台都綁定到一個 VM *instance* id，
而對應的註冊會以 `infra.instance_id` 回報相同的值：

```bash
cd terraform && terraform output -json ce_bound_instance_ids
```

兩者不一致意味著某個站台仍綁定到一個已不存在的節點，而這正是重建後的 CE 永遠無法完成註冊的狀態。
要讀取註冊那一側的值仍需直接呼叫 API——provider issue
[1376](https://github.com/f5-sales-demo/terraform-provider-xcsh/issues/1376) 就是能讓它出現在
data source 上的那件事。
</Aside>

## 為何是由 cloud-init 寫入金鑰，而不是 API

站台物件上的 `admin_user_credentials.ssh_key` 看起來正是為此而設的欄位。它會被接受、
會在回讀時保留，但什麼也不會設定。`vpm` 擁有節點的本機使用者，並拒絕變更這一個——
以下取自節點自身的日誌，在單次開機中出現三次：

```text
vpm  users.go:165: Won't do any change for user admin (internal skip)
```

其他一切都源自這一行。`/var/home/admin/.ssh` 從不存在，無論站台是否已達到 `ONLINE`。
`admin` 的 shadow 最後變更日期仍停留在映像建置日期，而 `vesbkp` 與 `vesopcon` 顯示的是當前日期，
因為 `vpm` 設定了那兩個帳號而略過了 `admin`。而且 `vpm` 在任何時候都不會記錄任何關於
`ssh_key` 或 `authorized_keys` 的內容。

因此這個檔案必須在 `vpm` 之外寫入。`admin` 的 uid 是 2202，已烘焙進節點映像，
所以它在 cloud-init 執行之前就已存在，`owner: admin:admin` 在寫入時即可解析——
不需要 `runcmd`，也不需要事後修正擁有者：

```yaml
- path: /var/home/admin/.ssh/authorized_keys
  permissions: "0600"
  owner: admin:admin
  content: |
    ${ssh_public_key}
```

`sshd` 一直都是願意配合的。`sshd -T` 回報 `pubkeyauthentication yes`，而 `admin`
出現在節點隨附的兩份 `sshd_config` 檔案的 `AllowUsers` 中。從來就沒有什麼需要啟用——
只是缺少一個檔案。

<Aside type="danger" title="不要重新加回 admin_user_credentials，也不要編輯 sshd_config">
`admin_user_credentials` 曾被接進 `terraform/modules/xc-site`，並在蒐集到這些證據後回退
（#660、PR #663）。它並不是一個等待填補的缺口。

`sshd_config` 會在註冊期間被替換，因此對它的編輯會在最不方便的時刻被丟棄。
</Aside>

## 為何只在一個位址上回應

`sshd` 綁定 `0.0.0.0:22`，但只有**內部（SLI）**位址以 `sshd` 會回應的方式存在於主機網路堆疊上。
eth0 被重新命名為 `a-i-eth0`，且完全不帶主機 IP——Argo 資料平面擁有該介面，
而它本應承載的管理／SLO 位址則出現在 `vhost0` 上。另外兩張 NIC 則以各自的名稱留在主機堆疊上。

從 VNet 內的一台 VM 針對某一台 CE 探測：

```text
management/SLO address    timed out
external address          timed out
internal/SLI address      OPEN     SSH-2.0-OpenSSH_8.7
an unused address         timed out    (control)
```

因此，針對你所熟知的節點位址進行探測，得到的結果與被安全群組封鎖時完全相同。
並沒有任何東西在阻擋；只是該位址上沒有監聽器。

<Aside type="caution" title="不要以客體介面名稱來推斷你位於哪個子網路">
`eth1` 與 `eth2` 之中哪一個承載內部位址，**在這同一個部署中的各節點之間並不相同**。
從三台 CE 即時讀取的結果：

```text
f5-xc-ce-vm-01    eth1 -> external      eth2 -> internal/SLI
f5-xc-ce-vm-02    eth2 -> external      eth1 -> internal/SLI
f5-xc-ce-vm-03    eth1 -> external      eth2 -> internal/SLI
```

只有兩件事在每個節點上都成立：`a-i-eth0` 沒有位址，以及 `vhost0` 承載管理／SLO 位址。
至於其他一切，請依據
[`ip addr`](../../commands/network/ip/) 輸出中的位址來比對，而不是依據介面名稱。
</Aside>

CE 的公用位址在 22 埠上同樣沒有監聽器，這也是上述命令要透過 `-J` 的原因：
一台位於 VNet 內、與 SLI 位址同一子網路的操作人員 VM。在此部署中，
`ar-ecmp-client` 就是那台 VM。

<Aside type="caution" title="-J 不會將你的選項傳遞給跳板那一段連線">
在命令列上給定的選項只套用於最後一段連線。因此，`-o UserKnownHostsFile=/dev/null`
與 `-J` 並用時，仍會為*跳板*主機查詢並寫入你真正的 `known_hosts`，
如果你想避免讓重建後的機群進入其中，這就會是意外之處。當這件事重要時，請把第一段連線明確寫出來：

```bash
ssh -tt -o ProxyCommand="ssh -W %h:%p -o UserKnownHostsFile=/dev/null azureuser@<operator-vm>" \
    -o UserKnownHostsFile=/dev/null -i ~/.ssh/id_ed25519 "admin@$SLI"
```

</Aside>

<Aside type="caution" title="兩種會產生自信卻錯誤答案的量測錯誤">
針對 eth0、外部介面或公用位址探測 22 埠，無論節點的 SSH 狀態如何都會回報關閉，
因此它完全無法告訴你任何事情。只有 SLI 位址會回應。

而從公司工作站進行探測可能會將一個實際上關閉的埠回報為**開啟**：
Netskope 會自行在常見埠上完成 TCP 交握。從工作站探測時，CE 公用位址的 80 與 443 埠讀取為開啟，
而從 VNet 內部探測時則是關閉。請從 VNet 內的 VM 進行探測。
</Aside>

## Site CLI 需要一個終端機，以及一個歸位字元

`admin` 的登入 shell 並不是 shell。它是一個 `go-prompt` 應用程式，會將終端機置於原始（raw）模式，
並讀取按鍵而非整行輸入。由此產生四項後果，每一項的失敗方式看起來都像是不同的問題：

| 機制 | 缺少它會發生什麼 |
| --- | --- |
| 配置終端機（`ssh -tt`） | 來自 `go-prompt.NewStandardInputParser` 的 `panic: no such device or address`，看起來像設備崩潰 |
| Enter 要送出歸位字元（carriage return），而非換行字元（line feed） | 該行永遠不會被送出，工作階段會在輸入結束時關閉，且什麼都沒印出 |
| 保持標準輸入開啟 | 連線在命令完成渲染之前就結束，因此一個正常運作的命令看起來毫無輸出 |
| **分別**寫入命令文字與 Enter 位元組 | 換行字元會以字面字元落入緩衝區，CLI 會回應 `unknown command`，看起來就像該命令不存在 |

因此 `ssh host 'some-command'` 無法運作：該引數會被忽略，互動式提示仍舊會啟動。
要嘛以終端機方式驅動它，要嘛就別用。`scripts/sitecli_ssh_harvest.py` 是參考實作。

<Aside type="caution" title="讀到 'no such device or address' 的 panic 表示驗證已經成功">
`vpmu` 是在登入**之後**才發出它，也就是當它找不到可附加的終端機時。若把它讀成崩潰，
看起來像是最糟的結果，但事實上它是成功之前的最後一個錯誤。加上
`-tt` 再重新連線即可。
</Aside>

<Aside type="caution" title="替換 CE 會改變它的主機金鑰">
替換節點會在相同位址上出示不同的主機金鑰，因此下一次連線會警告
`REMOTE HOST IDENTIFICATION HAS CHANGED` 並拒絕連線。請清除該位址的舊項目後重新連線。
既然授予 SSH 一定會替換 VM，就要預期在採用之後的第一次連線就會遇到這個情況。
</Aside>

## 橫幅本身就是一份免費的健康檢查

在你輸入任何內容之前，登入橫幅已經回答了若干原本得花費多道命令才能得知的問題。
以下取自 `f5-xc-ce-vm-01`，ASCII 圖案與公用 IP 已省略：

```text
UNAUTHORIZED ACCESS TO THIS DEVICE IS PROHIBITED
All actions performed on this device are audited

Using https://register.ves.volterra.io
OS: rhel-9.2024.6
Memory: 32768MiB
Storage: sda: 31GiB
CPU: Model: Intel(R) Xeon(R) Platinum 8272CL CPU @ 2.60GHz | CPUs: 8
Software: crt-20250613-3382
DNS: 168.63.129.16: OK
NTP: Synced
Uptime: 0 days, 5 hours, 20 minutes
Registration Status: PROVISIONED
SLO IP: 10.0.1.4/26
WELCOME IN SITE CLI
```

`Registration Status` 可區分仍在啟動中的節點（`PROVISIONING`）與已完成的節點（`PROVISIONED`）。
`Software` 是決定哪些命令存在的建置字串。
`DNS` 與 `NTP` 涵蓋最先導致註冊失敗的兩個依賴項，所以一個始終無法上線的節點通常已經在這裡告訴你原因了——
甚至完全不需要用到
[`chronyc-sources`](../../commands/network/chronyc-sources/) 或
[`dig`](../../commands/network/dig/)。

## 提供金鑰對

<Steps>

1. 若你還沒有金鑰對，請先產生一組。使用 Ed25519 而非 RSA：較短，
   且為設備的 `sshd` 所接受。

   ```bash
   ssh-keygen -t ed25519 -C "ce-operator" -f ~/.ssh/id_ed25519
   ```

2. 將部署指向**公開**的那一半。根模組會讀取該檔案一次，
   並將字串向下傳遞給每個節點：

   ```hcl
   # terraform/terraform.tfvars
   ssh_public_key_path = "~/.ssh/id_ed25519.pub"
   ```

   `ssh_public_key` 則是直接內嵌金鑰內容，plan 測試就是使用這種方式。
   私鑰那一半永遠不會離開你的工作站。

3. 套用。請先閱讀本頁最上方的警告——在既有部署上，這會替換 CE VM。

</Steps>

<Aside type="note" title="VM 自身的 admin_ssh_key 是另一回事">
`modules/ce-node` 中的 `azurerm_linux_virtual_machine.admin_ssh_key` 授權的是 Azure
VM 管理員，而不是設備的 `admin` 帳號。它不會授予任何 Site CLI 存取權，
而且它有設定並不能作為 CE SSH 已組態的證據。
</Aside>

## 這些都不是原因

以下每一項都曾在該途徑仍被認為不可能時經過測試並排除。
每一項都足夠合理，足以耗掉一整天。

| 並非原因 | 如何被排除 |
| --- | --- |
| 該憑證只在建立時套用 | `sshd` 在首次開機約 90 秒時啟動，早於站台物件存在之前。`admin_user_credentials` 也存在於 `ReplaceSpecType` 中，並會原地套用。 |
| `block_all_services` | 無論服務是否被封鎖，管理位址上 22 埠的關閉狀態完全相同。 |
| 金鑰結尾的換行字元 | 兩種方式都測試過，沒有差別。cloud-init 仍會將其去除，因為字面區塊否則會渲染出第二行空行。 |
| 釘住的舊版 CE 軟體 | 在三個建置上重現，包括一個執行 OpenSSH 9.9 的建置。 |
| 缺少 `admin_password` | 在從零建立的 CE 上，於 `ssh_key` 之外同時設定 `admin_password`，結果毫無變化。 |

<Aside type="caution" title="兩個看似判別依據但實則不是的 API 欄位">
`gc_spec.admin_ssh_key` 在 **`f5-sales-demo` 的全部 58 個站台上**都是空的或不存在——包括
那兩個確實設定了 `admin_user_credentials.ssh_key` 的站台。在可用與不可用的站台之間比較這個欄位，
不會告訴你任何事情，因為即使是那些*確實*已組態該憑證的站台，它讀取出來也是空的。

`registrations_by_site` 完全省略該欄位並回傳 `None`，這讀起來像是「未組態」，
而其實是「未回報」。
</Aside>

<Aside type="caution" title="新建立的站台需要約半小時後 operate API 才會回應">
在新站台回報 `ONLINE` 之後大約 25 到 30 分鐘內，`vpm/debug` 端點會回傳一個 BIG-IP `503`
頁面，內容為 `The requested URL was rejected`。那看起來像是 Web 應用防火牆封鎖，
或是憑證被撤銷，但兩者皆非：站台還沒準備好轉送。請等待並重試，而不要去改動任何東西。
