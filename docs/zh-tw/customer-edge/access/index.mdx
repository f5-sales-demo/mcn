有兩種路徑可行，而適用哪一種取決於節點的狀態，而非個人偏好。

| 路徑 | 需要節點處於 `ONLINE` | 需要網路可達性 | 限制 | 涵蓋範圍 |
| --- | --- | --- | --- | --- |
| [Debug API](./debug-api/) | **是** | 是 | 新站台約需 25–30 分鐘的暖機時間 | 34 個命令 |
| [序列主控台](./serial-console/) | 否 | 否 | 每個 VM 僅限一個工作階段；貼上內容上限 2,048 個字元 | 完整的機上 Site CLI |

序列主控台是最後手段，也是唯一能在節點完全沒有可用網路路徑時仍可運作的路徑。

[**SSH 並非第三種路徑。**](./ssh/) `admin` 帳號無法在此租戶執行的組建版本上完成驗證，`vpm` 從不套用該金鑰，也沒有任何站台設定能改變這一點。該頁面的存在是為了記錄佐證，因為其中每一種失敗模式看起來都像是防火牆或憑證問題。

## 為何這種區分不是偏好問題

Debug API 由 F5 Distributed Cloud 控制平面提供服務，並透過 `vpm` 在註冊期間建立的通道中繼至節點。沒有註冊就沒有通道，也就表示 API 沒有任何可中繼的對象。

它會以一種毫無幫助而非顯而易見的方式失敗，因此一個從未成功啟動的節點看起來就像是 API 問題。

序列主控台則完全走另一條路——透過 Azure 平台連到節點的模擬序列埠。它不在乎節點是否已註冊、是否具備網路可達性，或是否有可運作的資料平面。這種獨立性正是重點所在，也是為什麼開機診斷必須在 CE VM 上保持啟用的原因。

<Aside type="note" title="該選用哪一種">
如果您正在撰寫自動化腳本，或是在蒐集日後想重新執行的佐證資料，請使用 Debug API。如果壞掉的正是註冊本身，序列主控台就不是備援方案——它是唯一的選擇。
</Aside>

## 憑證

兩種路徑使用不同的憑證，且兩者都不該出現在命令列上。

- **Debug API** — 一組 F5 Distributed Cloud API 權杖，設為 `XCSH_API_TOKEN`，並將租戶 URL 設為 `XCSH_API_URL`。位於 `~/.config/xcsh/contexts/<tenant>.json` 的 `xcsh` 內容檔同時存放這兩項資訊，當環境未提供時，`scripts/capture-sitecli.sh` 便會讀取此檔案。
- **序列主控台** — 您的互動式 Azure 登入。此處沒有服務主體可用：F5 企業 Entra 租戶不允許佈建服務主體，這也是為什麼這部分作業完全不在 CI 中執行。

<Aside type="danger" title="切勿將權杖作為引數傳遞">
命令列上的權杖會留存在 shell 歷程記錄與處理程序清單中，機器上的其他所有使用者都能讀取。基於此原因，`capture-sitecli.sh` 直接拒絕 `--token`，改為透過 stdin 將標頭提供給 `curl`。
</Aside>
