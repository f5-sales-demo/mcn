共有四種可用路徑，適用哪一種取決於節點狀態、您的連線來源，以及您需要連接的目標——而非個人偏好。

| 路徑 | 需要節點 `ONLINE` | 需要網路可達性 | 限制 | 涵蓋範圍 |
| --- | --- | --- | --- | --- |
| [除錯 API](./debug-api/) | **是** | 是 | 新站台約需 25–30 分鐘暖機 | 34 個命令 |
| [Site Console](./site-console/) | 否 | 透過 Azure Bastion，無需跳板主機 | Bastion 必須為支援通道的 Standard SKU | F5 的節點疑難排解介面 |
| [SSH](./ssh/) | 否 | 從 VNet 內部，僅限連接至內部位址 | 金鑰必須於首次開機時已存在 | 完整的節點上 Site CLI |
| [序列主控台](./serial-console/) | 否 | 否 | 每部 VM 一個工作階段；貼上上限 2,048 字元 | 完整的節點上 Site CLI |

序列主控台是最後手段，也是唯一在節點無任何可用網路路徑時仍能運作的路徑。

[Site Console](./site-console/) 通常是優先嘗試的選項。它對您的要求最少——無需散佈 SSH 金鑰、無需跳板主機、節點無需公開 IP，也無需替換 VM——因為存取控制改由 Azure RBAC 決定，而非憑證散佈問題。它提供的是 F5 自有的疑難排解介面，而非命令操作介面，因此當您需要執行特定命令或進行腳本化操作時，請改用其他路徑。

當除錯 API 不足以滿足需求時，請選擇 SSH，因為設備提供的命令遠多於 API 所公開的 34 個。但它有兩項成本。金鑰由 cloud-init 寫入，因此必須在**首次開機**時已存在，這意味著在運行中的節點上啟用 SSH 會導致節點被替換——而這目前會卡住註冊流程（[問題 674](https://github.com/f5-sales-demo/mcn/issues/674)）。此外，`sshd` 僅在節點的內部位址上回應，因此需要 VNet 內部的主機；探測您所知道的節點位址將始終回報連接埠關閉。

## 為何此區分並非出於偏好

除錯 API 由 F5 Distributed Cloud 控制平面提供服務，透過 `vpm` 在註冊期間建立的通道轉送至節點。未完成註冊即表示沒有通道，也就表示 API 沒有任何目標可供轉送。

它的失敗方式並不直觀，而是以令人困惑的方式呈現，因此從未成功啟動的節點看起來像是 API 問題。

序列主控台則完全不同——透過 Azure 平台連接至節點的模擬序列埠。它不在乎節點是否已完成註冊、是否具有網路可達性，或是否擁有可運作的資料平面。這種獨立性正是其核心價值，也是為何開機診斷必須在 CE 虛擬機器上保持啟用狀態。

<Aside type="note" title="應選用的路徑">
若您正在撰寫自動化腳本，或收集日後需要重新執行的證據，請使用除錯 API。若註冊本身是問題所在，序列主控台並非備援方案——而是唯一的選項。
</Aside>

## 憑證

每條路徑使用不同的憑證，且任何憑證都不應出現在命令列中。

- **除錯 API** — F5 Distributed Cloud API 權杖，以 `XCSH_API_TOKEN` 設定，並以 `XCSH_API_URL` 設定租戶 URL。位於 `~/.config/xcsh/contexts/<tenant>.json` 的 `xcsh` 上下文檔案同時儲存這兩項設定，這也是當環境未提供時 `scripts/capture-sitecli.sh` 所讀取的位置。
- **SSH** — 部署時寫入 `/var/home/admin/.ssh/authorized_keys` 的金鑰對中的私鑰（於首次開機時寫入），以及 VNet 內部可連接至內部位址的主機。請以 `admin` 身份連線，而非 `azureuser`。
- **序列主控台** — 您的互動式 Azure 登入。此處不存在服務主體：F5 企業 Entra 租戶不允許佈建服務主體，這也是為何本流程的任何部分均不在 CI 中執行。

<Aside type="danger" title="切勿以引數傳遞權杖">
命令列上的權杖會留存於 Shell 歷史記錄及行程清單中，機器上的所有其他使用者均可讀取。`capture-sitecli.sh` 基於此原因明確拒絕 `--token` 參數，改為透過 stdin 將標頭提供給 `curl`。
</Aside>
