三種途徑都可行，而適用哪一種取決於節點的狀態以及您從何處連線，而非取決於個人偏好。

| 途徑 | 需要節點處於 `ONLINE` | 需要網路可達性 | 限制 | 涵蓋範圍 |
| --- | --- | --- | --- | --- |
| [除錯 API](./debug-api/) | **是** | 是 | 新站台約需 25–30 分鐘暖機 | 34 個指令 |
| [SSH](./ssh/) | 否 | 需從 VNet 內部連線，且僅限內部位址 | 金鑰必須自首次開機起即存在 | 完整的機上 Site CLI |
| [序列主控台](./serial-console/) | 否 | 否 | 每部 VM 僅限一個工作階段；貼上內容上限 2,048 個字元 | 完整的機上 Site CLI |

序列主控台是最後手段，也是唯一能在節點毫無可用網路路徑時仍然可行的途徑。

當除錯 API 不敷使用時，SSH 就是該採用的途徑，因為設備提供的指令遠多於該 API 所公開的 34 個。它有兩項代價。金鑰是由 cloud-init 寫入的，因此必須在**首次開機**時就存在，這表示要在執行中的節點上啟用它就得將其汰換 —— 而目前這麼做會使註冊卡住（[issue 674](https://github.com/f5-sales-demo/mcn/issues/674)）。此外，`sshd` 僅在節點的內部位址上回應，因此需要一台位於 VNet 內部的主機；探測您所熟知的節點位址永遠會回報為關閉。

## 為何這樣的區分並非偏好問題

除錯 API 是由 F5 Distributed Cloud 控制平面提供服務，並透過 `vpm` 在註冊期間建立的通道中繼至節點。沒有註冊就沒有通道，也就表示該 API 沒有任何可中繼的對象。

它的失敗方式並不明顯，反而相當令人費解，因此一個從未成功啟動的節點看起來會像是 API 的問題。

序列主控台則走的是完全不同的路徑 —— 透過 Azure 平台連到節點的模擬序列埠。它不在意節點是否已註冊、是否具備網路可達性，或資料平面是否正常運作。這種獨立性正是重點所在，也是為什麼開機診斷必須在 CE VM 上保持啟用的原因。

<Aside type="note" title="該採用哪一種">
如果您正在撰寫自動化流程，或是收集日後想要重新執行的佐證資料，請使用除錯 API。如果出問題的正是註冊本身，那麼序列主控台就不是備援方案 —— 它是唯一的選擇。
</Aside>

## 認證憑證

每一種途徑使用不同的認證憑證，且沒有任何一種應該出現在命令列上。

- **除錯 API** —— 一組 F5 Distributed Cloud API 權杖，設為 `XCSH_API_TOKEN`，並將租戶 URL 設為 `XCSH_API_URL`。位於 `~/.config/xcsh/contexts/<tenant>.json` 的 `xcsh` 內容檔同時保存兩者，這也是 `scripts/capture-sitecli.sh` 在環境未提供它們時所讀取的來源。
- **SSH** —— 金鑰對的私鑰部分，其公鑰部分由部署程序在首次開機時寫入 `/var/home/admin/.ssh/authorized_keys`，此外還需要一台位於 VNet 內部的主機，以便透過它連到內部位址。請以 `admin` 身分連線，而非 `azureuser`。
- **序列主控台** —— 您的互動式 Azure 登入。此處沒有服務主體可用：F5 企業 Entra 租戶不允許佈建服務主體，這也是為什麼這部分完全不在 CI 中執行的原因。

<Aside type="danger" title="切勿將權杖作為引數傳遞">
命令列上的權杖會留在 shell 歷史紀錄與行程清單中，機器上的其他每一位使用者都能讀取。`capture-sitecli.sh` 正是基於這個原因完全拒絕 `--token`，改為透過 stdin 將標頭提供給 `curl`。
</Aside>
