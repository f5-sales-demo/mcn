共有三種途徑可用，適用哪一種取決於節點的狀態以及您的連線來源，而非個人偏好。

| 途徑 | 需要節點 `ONLINE` | 需要網路可達性 | 限制 | 涵蓋範圍 |
| --- | --- | --- | --- | --- |
| [除錯 API](./debug-api/) | **是** | 是 | 新站台約 25–30 分鐘的暖機時間 | 34 個命令 |
| [SSH](./ssh/) | 否 | 僅限從 VNet 內部連至內部位址 | 金鑰必須於首次開機時即存在 | 完整的機器內站台 CLI |
| [序列主控台](./serial-console/) | 否 | 否 | 每台 VM 一個工作階段；貼上字元上限 2,048 個 | 完整的機器內站台 CLI |

序列主控台是最後手段，也是唯一能在節點沒有任何可用網路路徑時仍可使用的途徑。

當除錯 API 不敷使用時，應優先選擇 SSH，因為設備提供的命令數量遠多於 API 所公開的 34 個命令。此途徑有兩項代價：金鑰由 cloud-init 寫入，因此必須在**首次開機**時即存在，這意味著在執行中的節點上啟用此功能將會取代這些節點——而這目前會卡住註冊流程（[問題 674](https://github.com/f5-sales-demo/mcn/issues/674)）。此外，`sshd` 僅回應節點的內部位址，因此需要 VNet 內部的主機；透過您已知的節點位址進行探測將始終回報連線關閉。

## 為何此劃分並非取決於偏好

除錯 API 由 F5 Distributed Cloud 控制平面提供服務，並透過 `vpm` 在註冊期間建立的隧道中繼至節點。未完成註冊即表示沒有隧道，也就意味著 API 沒有可中繼的目標。

其失敗的方式令人費解，而非顯而易見，因此從未正常啟動的節點看起來就像是 API 問題。

序列主控台則採取完全不同的途徑——透過 Azure 平台連接至節點的模擬序列埠。它不在乎節點是否已完成註冊、是否具備網路可達性，或資料平面是否正常運作。這種獨立性正是其核心價值所在，也是為何 CE VM 必須持續啟用開機診斷的原因。

<Aside type="note" title="選擇途徑的建議">
若您正在撰寫自動化腳本，或蒐集日後需要重新執行的驗證資料，請使用除錯 API。若問題出在註冊流程本身，序列主控台並非退而求其次的選項——它是唯一可用的選擇。
</Aside>

## 憑證

兩種途徑使用不同的憑證，且均不應出現在命令列上。

- **除錯 API** — F5 Distributed Cloud API 權杖，以 `XCSH_API_TOKEN` 表示，並以 `XCSH_API_URL` 表示租戶 URL。`xcsh` 設定檔位於 `~/.config/xcsh/contexts/<tenant>.json`，其中儲存了這兩項資訊，當環境未提供時，`scripts/capture-sitecli.sh` 即從此處讀取。
- **序列主控台** — 您的互動式 Azure 登入。此途徑不使用服務主體：F5 企業 Entra 租戶不允許佈建服務主體，這也是為何此流程的任何部分都不在 CI 中執行的原因。

<Aside type="danger" title="切勿以引數形式傳遞權杖">
出現在命令列上的權杖會留存於 Shell 歷史記錄及行程清單中，機器上的所有其他使用者均可讀取。基於此原因，`capture-sitecli.sh` 明確拒絕 `--token` 參數，並改以標準輸入方式將標頭傳遞給 `curl`。
</Aside>
