Customer Edge (CE) 是本儲存庫佈建至 Azure 的 F5 Distributed Cloud 節點 —
`terraform/modules/ce-node`，以
`volterraedgeservices/volterra-node` marketplace 映像檔建置而成。

它執行資料平面 (Argo)、控制平面 (Vega)、一個 Envoy Proxy、一套 Kubernetes
堆疊，以及 `vpm` — 負責註冊節點並管理節點上其餘一切的代理程式。

當 CE 運作異常時，Site CLI 就是診斷工具。第一個決定是判斷適用哪一條存取路徑，
選錯會浪費時間，而且看起來就像節點壞掉了一樣。

## 兩條存取路徑，兩者不可互換

    href="./access/debug-api/"
  />
  <LinkCard
    title="Serial console"
    description="For a node that never registered. The only route when the API cannot answer."
    href="./access/serial-console/"
  />
</CardGrid>

Debug API **透過 F5 Distributed Cloud 控制平面**連上節點。
這正是這項區分之所以重要的原因：只有在節點已完成註冊且回報 `ONLINE` 之後，
API 才能回應。

註冊失敗的節點 — cloud-init 有誤、權杖過期、無法路由至
`register.ves.volterra.io` — 正是你最需要診斷的情況，
也正是 API 無法服務的情況。

[SSH](./access/ssh/) 是第三個選項，也是唯一能觸及設備完整命令介面的方式 —
debug API 只公開 34 個命令，而節點本身提供的遠不止於此。有兩件事限制了它。
`sshd` 只在節點的內部 (SLI) 位址上回應，因此需要一台位於 VNet 內的主機；
而金鑰是由 cloud-init 在首次開機時寫入的，因為 site 物件上的 `ssh_key` 欄位無作用 —
`vpm` 會跳過 `admin` 使用者且從不套用它。因此，要在執行中的節點上啟用它就等於替換節點。

所以：如果站台為 `ONLINE` 且 34 個命令已足夠，請使用 debug API。如果你需要其餘的
命令介面且能連上 VNet，請使用 SSH。如果壞掉的是註冊本身，序列主控台是唯一的入口。

<Aside type="caution" title="先檢查站台狀態">
一個請求就能告訴你該走哪條路徑：

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/config/namespaces/system/sites/<site>" \
  | jq -r '.spec.site_state'
```

`ONLINE` 表示 debug API 可以運作。其他任何狀態 — 或站台根本不存在 —
都表示要用序列主控台。
</Aside>

## 安全規則

以下規則適用於下列各頁的每一個命令。

- **除非你有十足把握，否則只做唯讀操作。** 命令介面分為兩個權限層級，
  而 `Exec` 層級不是會變更節點狀態，就是會讀取某個狀態標記。這些頁面上沒有任何
  內容會執行 `Exec` 命令，擷取工具 (capture harness) 也不會。
- **絕不要從命令名稱推斷它是安全的。** `ip-link-set` 讀起來像查詢，
  實際上會讓介面斷線。`systemctl-restart-crio` 會在資料平面運作中重新啟動
  容器執行環境。
- **優先使用能回答問題的最小範圍命令。** `health` 與 `diagnosis`
  能以低成本摘要節點狀態；`flow-l` 則會傾印一份 629,760 筆的流量表。
- **CE 承載即時流量。** 這些是共用的展示環境。請假設有人正在用你要除錯的
  站台進行簡報。

## 這裡記錄了哪些內容

本租戶所執行的軟體版本上，透過 debug API 可觸及的每一個命令，
每一個都附有從實際運作節點擷取的輸出，而非從別處轉錄而來。

[命令參考](./commands/) 列出所有命令及其類別、權限層級與傳輸方式；
[工作流程](./workflows/) 則將它們串連成出問題時實際會使用的操作順序。

Site CLI 中僅限於機上執行的部分 — `configure`、`configure-network`、
`factory-reset`、`upgrade` 以及大約六十個其他 `ExecCLI` 命令 — 不在涵蓋範圍內，
因為它們的輸出並未像下列每一頁那樣，從實際運作的節點擷取而來。

不過，它們已不再遙不可及。`scripts/sitecli_ssh_harvest.py` 會透過
[SSH](./access/ssh/) 驅動設備本身的補全選單，並記錄設備對每個命令所給出的描述，
如此一來這片命令介面就能被量測，而非僅憑猜測。
它的執行採預設拒絕 — 它會列舉一切，但只執行允許清單中的項目 —
因為未經驗證的命令語法，以及未經驗證的命令*效果*，正是這份文件存在要避免重蹈覆轍的缺陷。
