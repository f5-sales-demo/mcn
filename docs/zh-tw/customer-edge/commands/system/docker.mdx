Docker 負責執行平台服務。Kubernetes 工作負載則在
[CRI-O](../crictl/) 下運行。

## `docker-ps`

```bash
{"command":["docker-ps"]}
```

```text file=../../../../_data/sitecli-docker-ps.txt
```

<Aside type="tip" title="三個容器是完整清單，而非節點異常">
`vpm`、`argo_watch` 和 `site-console`。由於節點大部分的服務在 CRI-O 下運行，若您預期此處會有 Kubernetes 工作負載，簡短的 `docker-ps` 輸出看起來可能像是故障。但實際並非如此——這是健康 CE 上 Docker 容器的完整清單，`vpm` 存在且狀態為 `Up` 是此頁面最重要的一行資訊。
</Aside>

## `docker-inspect`

```bash
{"command":["docker-inspect","<container-id-or-name"]}
```

```text file=../../../../_data/sitecli-docker-inspect.txt
```

接受名稱或 ID 作為參數，因此 `docker-inspect vpm` 可正常運作，且在重新啟動後仍保持穩定。完整 JSON 內容涵蓋：掛載點、環境變數、重啟策略及退出狀態。

```

```

`docker-logs vpm` 是查詢註冊錯誤最快速的方式。若需要包含時間戳記且跨重啟的相同資訊，請改用 [`journalctl`](../journalctl/)。

## `docker-prune`

```bash
execcli docker-prune
```

移除所有未使用的 Docker 物件——包括已停止的容器、未使用的網路、懸空映像及建置快取。

**僅限從設備本機執行。** `docker-prune` 不在除錯 API 中；需透過 [`execcli`](../../on-box/) 執行。

<Aside type="danger" title="具破壞性，且不在本頁記錄範圍內">
此指令會刪除狀態資料。它列於收集框架的拒絕清單中，從未被執行，因此本頁依據設備自身的目錄元資料進行說明，而非顯示實際輸出。

CE 特定注意事項：此節點運行**兩個**容器執行環境。`docker-prune` 僅影響 Docker 側——即 `vpm`、`argo_watch` 和 `site-console`——無法觸及 [CRI-O](../crictl/) 下的 Kubernetes 工作負載。若要回收 CRI-O 側的空間，需使用不同的指令 `systemctl-start-crio-prune`，但該指令在此版本中並不存在。
</Aside>
