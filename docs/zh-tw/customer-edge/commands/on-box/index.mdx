[debug API](../../access/debug-api/) 公開 **34 個指令**。設備本身提供 **82 個**，**其中 55 個沒有對應的 API** — 整個 Vega 控制平面、Envoy 封裝器、封包擷取、kubelet 參數集、`edit-*` 檔案以及輔助 root 存取組合，只能從機箱本身存取。

要存取這些指令，需要 [SSH](../../access/ssh/) 或[序列主控台](../../access/serial-console/)，以及一項未記錄於任何文件的資訊：

<Aside type="tip" title="execcli 是一個隱藏指令">
`execcli` 不會出現在 Site CLI 的互動式選單中。它以指令名稱作為引數，輸入 `execcli ` 後按下 **Tab** 鍵，即可列出所有 82 個指令，以及設備本身為每個指令提供的單行說明。該補全選單是特定組建版本的權威目錄，也是 `sitecli/exec-catalog.json` 所記錄的內容。
</Aside>

## 測量方式

下列指令集並非從廠商文件謄錄而來，而是從兩個實際執行中的節點讀取，並連同其來源紀錄提交至 `sitecli/exec-catalog.json`：

| | 頂層 | `execcli` |
| --- | --- | --- |
| 於 `site_state: PROVISIONING` 時測量 | 6 | 82 |
| 於 `site_state: PROVISIONED` 時測量 | 6 | 82 |

兩次執行回傳**完全相同的指令集**。這比數量本身更重要：這意味著指令介面不會隨註冊狀態改變，因此若某個指令不存在，代表它確實不存在，而非尚未提供。

<Aside type="caution" title="五個不存在的指令">
`factory-reset`、`upgrade`、`reboot`、`show` 和 `clear` **不在此組建版本中**。這些是 Site CLI 可能具備的指令類型，在此儲存庫的分類中曾依此假設保留了一段時間，但兩次列舉均未發現它們。頂層確切只有六個項目：`configure`、`configure-generic-hardware`、`configure-network`、`configure-http-proxy`、`diagnosis` 和 `health`。
</Aside>

## 已完整記錄與僅列出的指令

Customer Edge 執行 Linux 及多個第三方常駐程序。記錄其指令會重複其自身的參考文件，並暗示 F5 擁有這些軟體，因此規則是：**記錄 F5 的軟體，對於其他所有項目，僅記錄 CE 特有的內容。**

分為三個層級，因為「我們的」與「他們的」並非截然分明。此分類記錄於 `sitecli/command-classification.json`。

| 層級 | 處理方式 |
| --- | --- |
| **F5 軟體** | 完整文件記錄 — 用途、語法、引數、擷取的輸出內容、應注意事項。Argo、Vega、`vpm`、`vifdump`、`configure*`、`edit-*` 指令集、kubelet 參數、root 存取。 |
| **CE 特定解讀** | 第三方工具，其輸出在 CE 上具有特定意義。記錄 CE 特定的解讀方式，工具本身的語義留待上游文件說明。 |
| **直通** | 純 Linux 或第三方工具，沒有 CE 特定內容需說明。列為可用，並指向上游文件。無說明文字。 |

此區別決定是否需要建立專屬頁面，也是避免本文件淪為比 man 頁面更差的複製品的關鍵。

## 直通

可在機箱上使用，但**未在此記錄** — 這些屬於作業系統和第三方常駐程序，而非 F5 的軟體，其自身的參考文件比本頁所能重述的內容更為完善。

| 指令 | 上游 |
| --- | --- |
| `ping`、`netstat`、`lsof`、`ip`、`ip-link-show`、`nmcli`、`tracepath`、`dig` | iproute2、NetworkManager、BIND 工具程式 |
| `top`、`check-mem`、`sysctl`、`load-sysctl-conf`、`journalctl`、`files`、`rpm-ostree`、`chronyc-sources` | coreutils、procps、systemd、rpm-ostree、chrony |
| `edit-etc-hosts`、`edit-sysctl-conf` | 這些檔案屬於作業系統 |
| `systemctl-status-crio`、`systemctl-status-docker`、`systemctl-status-kubelet`、`systemctl-status-iscsid`、`systemctl-status-multipathd` | systemd |
| `systemctl-restart-crio`、`systemctl-restart-docker`、`systemctl-restart-kubelet`、`systemctl-restart-iscsid`、`systemctl-restart-multipathd` | systemd — 這些指令中的每一個都會中斷節點上的工作負載 |

其中兩個值得特別注意，即使它們沒有專屬頁面。`files` 執行檔案操作，且只會在 `/tmp` 目錄下寫入。每個 `systemctl-restart-*` 本質上都會造成服務中斷 — 重新啟動 `crio` 或 `kubelet` 會中斷該節點上的工作負載。

<Aside type="note" title="七個指令存在於較新組建版本中，但不在此版本">
`collect-database-stats`、`iptables-lv`、三個 `marker-exists-*` 指令、`systemctl-restart-NetworkManager` 和 `systemctl-start-crio-prune` 是透過 debug API 在組建版本 `crt-20260201-0179` 上觀察到的。它們記錄於分類中的 `not_on_this_build.newer_build_debug_api` 下，以避免此處任何內容被誤認為可在 `crt-20250613-3382` 上執行的指令。

`collect-debug-info` 是另一種情況：它不出現在任何選單或目錄中。Site CLI 的歡迎文字表示該 CLI「允許…收集支援所需的除錯資訊」，因此該名稱很可能源自該說明文字，而非實際觀察所得。此指令已標記為未驗證，且刻意不予探測 — 在實際執行的節點上隨意執行未知指令，正是導致一個仍在註冊中的 CE 上意外啟動 `vifdump` 封包擷取的原因。
</Aside>
