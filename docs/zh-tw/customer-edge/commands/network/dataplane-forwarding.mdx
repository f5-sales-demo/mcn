Argo 將轉送狀態與 Linux 核心分開保存。當
[`ip`](../ip/) 與這些指令的結果不一致時，實際搬動流量的是這些指令。

## `rt`

vRouter 路由表，依 VRF 區分。

```bash
{"command":["rt","--dump","2"]}
```

```text file=../../../../_data/sitecli-rt.txt
```

<Aside type="danger" title="這裡的 VRF id 不是 BGP 回報的那個">
`show-ip-bgp-summary` 會印出 `vrf-id 3`。那是 FRR 的編號方式，與 vRouter 表的 id 屬於
不同的命名空間。在此處傳入該值會失敗，而失敗的樣子看起來像節點壞掉：

```
vRouter(Response):  [No such file or directory (2)]
```

`--dump 0` 也會得到相同的回覆。在此拓樸中，**VRF 2** 才是有資料的 inet4 表，而 VRF 1 中
有兩條路由。如果你不知道 id，請從 1 開始往上探測，而不要信任 BGP 的輸出。
</Aside>

## `nh`

下一跳表。每條路由都指向一個下一跳 id，而此指令可解析這些 id。

```bash
{"command":["nh","--list"]}
```

```text file=../../../../_data/sitecli-nh.txt
```

每一筆項目都帶有一個 `Type` 以及其所屬的 VRF。這些節點上會出現八種類型，比例如下
——經統計後，三個 CE 上完全相同：

```text
Tunnel 558   Encap 27   NAT 22   Vrf 16   Receive 14   Composite 4   Drop 2   Resolve 2
```

若某條路由解析到 `Drop` 下一跳，即為黑洞；每當某個前綴存在於 `rt` 中但流量仍然消失時，
這個組合就值得檢查。

<Aside type="caution" title="上方的擷取內容已經裁剪過，因此並未包含所有類型">
那是 3,849 行中的前 60 行。`Tunnel` 是數量遠遠領先的最常見類型，卻完全沒有出現在那 60 行中
——因此請勿將該擷取內容視為完整的類型清單，也不要因為某個類型未出現在裁剪過的擷取內容中，
就斷定該節點上不存在此類型。上方的計數來自未裁剪的完整回覆。
</Aside>

## `vif`

虛擬介面表：資料平面所綁定的對象，以及各介面的計數器。

```bash
{"command":["vif","--list"]}
```

```text file=../../../../_data/sitecli-vif.txt
```

頂端的旗標圖例值得看過一次 —— `Vp` 標示 vhost 實體介面，`Dpdk` 則表示由 DPDK 管理的
介面。可利用此表確認資料平面確實接管了你所預期的介面，並查看 Linux 不會顯示的 RX 與 TX
計數器，因為那些流量從未進入核心。
