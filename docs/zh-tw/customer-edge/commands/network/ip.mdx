## `ip`

接受一個 `ip` 子指令。`addr` 是最常用的；`route`、`link` 與 `neigh` 也可以使用。

```bash
{"command":["ip","addr"]}
```

```text file=../../../../_data/sitecli-ip.txt
```

CE 依設計具有三張 Azure 網卡——管理/SLO、外部、內部/SLI——但客體作業系統呈現它們的方式
並非那個排序所暗示的樣子，而這正是誤讀輸出會耗費時間的地方。

| 在客體中 | 承載 |
| --- | --- |
| `a-i-eth0` | **完全沒有位址**——這是被重新命名的物理 eth0，由 Argo 資料平面所擁有 |
| `vhost0` | 管理/SLO 位址，也就是 BGP 對等連線所使用、且站點物件所回報的那一個 |
| `eth1` 與 `eth2` | 外部與內部/SLI 位址——但**順序並不固定** |

<Aside type="danger" title="eth1 與 eth2 之中哪一個是內部介面，各節點並不相同">
從這一個部署中的三台 CE 即時讀取：在 `f5-xc-ce-vm-01` 與
`f5-xc-ce-vm-03` 上，內部/SLI 位址位於 `eth2`；而在 `f5-xc-ce-vm-02` 上則位於
`eth1`。設定中沒有任何項目決定這件事。

因此，切勿從介面名稱推斷子網路，也切勿把某個節點的對應關係套用到另一個節點。
請改為以位址進行比對——CE 位址所屬的子網路是穩定的，即使承載它的介面並不穩定。

</Aside>

`a-i-eth0` 沒有承載任何位址，也正是為什麼無法透過管理位址連上 `sshd` 的全部原因：
那裡根本沒有監聽者，而不是連接埠被封鎖。請參閱
[SSH](../../../access/ssh/)。

## `ip-link-show`

僅顯示連結層資訊：狀態、MTU、排隊規則、MAC。

```bash
{"command":["ip-link-show"]}
```

```text file=../../../../_data/sitecli-ip-link-show.txt
```

當問題是「連結是否已啟用、它的 MTU 是多少」時，這比 `ip addr` 更快。
MTU 不一致是隧道能建立卻無法傳遞流量的常見原因。

## `ip-link-set` <Badge text="Exec 層級 — 具變更性" variant="danger" />

將某個介面或群組設為啟用或停用。

```
ip-link-set (<device>||<group>) (up||down)
```

<Aside type="danger" title="此處未執行，且無法以慣常方式存取">
這是此組建中唯一的 `Exec` 層級指令。它送往 `exec` 端點
而非 `exec-user`，且它會變更節點：在遠端 CE 上將 `eth0` 停用，
會移除你用來管理它的路徑，包括除錯 API 本身。

本頁刻意沒有擷取任何輸出。擷取工具會拒絕整個 `Exec` 層級，
且它是從即時目錄讀取層級資訊，而非依據硬編碼清單，
因此即使未來的組建將其他指令提升至該層級，這項說明仍然成立。
</Aside>
