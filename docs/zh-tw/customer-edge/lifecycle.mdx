兩個 Terraform 變數用於設定 Customer Edge 的軟體：`ce_os_version` 負責作業系統，`ce_sw_version` 負責 F5 Distributed Cloud 的建置版本。兩者的行為與直觀理解恰好相反，一旦設定有誤，代價就是整個機群的重建。

## 版本欄位的作用——分兩個階段說明

釐清這兩個階段是本文的核心。若將它們混為一談，行為看起來會自相矛盾。

**在首次開機時，節點必定會升級。** `terraform/modules/ce-node` 以 `version = "latest"` 部署市集映像，而該映像所附帶的建置版本**舊於** Tenant 目前運行的版本。因此，無論是否設定欄位，升級都會發生。`ce_sw_version` 僅決定升級的**目標版本**——留空表示由伺服器自行決定，而非什麼都不做。`ce_os_version` 亦同理。

**之後，不會有任何自動升級。** F5 Distributed Cloud 會公告新建置版本並等待。空白欄位並非「跟蹤最新版本」：節點會停留在首次啟動後落地的版本。

這兩個階段都可在 Site 物件上觀察到。`觀察於 2026-07-28`，此機群：

```text
volterra_software_status.available_version   crt-20260201-0179
operating_system_status.available_version    9.2026.14
```

而節點目前運行 `crt-20250613-3382`，OS 版本為 `9.2024.6`。較新的建置已提供但尚未套用——這是穩定狀態，而非升級卡住。

## 變更版本需要重建，且 Terraform 不會代勞

`ce_os_version` 與 `ce_sw_version` 均為**僅限建立時設定**，且失敗的方式比被拒絕的套用更為嚴重。流程如下：

1. 你變更值並執行 apply。Terraform 提議進行就地更新。
2. API **拒絕**此請求——`[BAD_REQUEST] Invalid request parameters`。
3. 這個被拒絕的請求仍會清除伺服器上的欄位，而 Provider 的 read 操作不會回報此情況。Terraform 的狀態此時與實際物件不一致。
4. 此後每次 plan 都會**重複提議同一個失敗的變更**，無限循環。

因此 Terraform 不會退而求其次改為替換 Site，而是卡住，並持續卡住，直到你主動替換 Site 及其 CE 虛擬機器。將機群遷移至不同版本是一項**需要規劃的重建**，而非可以直接套用的編輯。

<Aside type="danger" title="替換 CE 的所有後果均適用">
新的 SSH 主機金鑰、重新指派的內部位址、重新進行註冊，以及所有僅存在於節點上的資料將會遺失。新虛擬機器上會再次執行 cloud-init，因此以此方式設定的 SSH 存取可保留——但 cloud-init **僅在首次開機時執行**，所以任何手動新增至舊節點的設定都將消失。

在排程此操作前，請先閱讀 [SSH](./access/ssh/) 以了解主機金鑰與位址變更的影響。
</Aside>

<Aside type="note" title="已記錄，未在此重現">
拒絕事件與狀態不一致的問題已記錄於本儲存庫的 `terraform/modules/xc-site` 註解中——在三個 Site 上均已驗證，涵蓋固定版本與取消固定兩個方向——並對應 Provider issue `xcsh#1387`。本頁未重新測試，因為測試會導致部署在每次 plan 時都提議一個失敗的變更。

## 本文件所描述的建置版本

本站的指令參考說明的是 **`crt-20250613-3382`**，即此機群目前運行的版本。僅在較新建置版本上觀察到的指令，會以名稱記錄於 `sitecli/command-classification.json` 的 `not_on_this_build` 欄位下，且不作為可執行指令加以說明。詳見[節點上的指令](./commands/on-box/)。

<Aside type="caution" title="請勿為了取用新指令而規劃重建">
目前已有較新的建置版本可供使用，但它能否在此拓撲上順利安裝仍未確定——有報告指出它在單節點 Azure Secure Mesh v2 Site 上安裝失敗，但也有觀察記錄顯示某 Customer Edge 正在運行該版本，兩者均無法從 Tenant 現有的資訊加以確認。

由於版本變更即代表機群重建，這個不確定性便是關鍵事實：應將取用這些指令視為未經驗證的事項，而非已排定的升級。相關證據與可釐清此問題的實驗已記錄於 `sitecli/README.md`。
</Aside>
