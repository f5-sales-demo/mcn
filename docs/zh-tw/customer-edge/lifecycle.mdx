兩個 Terraform 變數設定 Customer Edge 的軟體：`ce_os_version` 用於作業系統，`ce_sw_version` 用於 F5 Distributed Cloud 建置。兩者的行為與直觀理解恰好相反——空白欄位會取得最新版本而非不安裝任何版本，而在某個節點上可成功安裝的版本，可能因磁碟較小而在完全相同的另一個節點上失敗。

## 版本欄位的作用，分為兩個階段

區分這兩個階段才是重點。混為一談後，行為看起來會自相矛盾。

**在第一次開機時，節點會安裝 `ce_sw_version` 所指定的版本。**
`terraform/modules/ce-node` 使用 `version = "latest"` 部署市集映像，因此節點啟動時的建置版本取決於該映像當前所包含的版本——這會隨時間變動。`ce_sw_version` 選擇的是**目標**版本，而非是否執行任何操作，留空表示由伺服器決定，而非讓節點保持原狀。`ce_os_version` 亦同。

請勿假設該變更方向必然是向上升級。`觀察於 2026-07-28`，映像所包含的建置版本為 `20260703-e2c462a`——比此機群的 `crt-20250613-3382` 更新，也比租戶所通告的 `crt-20260201-0179` 更新。若指定的版本比映像所帶的版本舊，即要求節點向下回退，這是正常情況：此機群即是如此建立並運行的。

**留空版本欄位是風險最高的選擇，而非中性選擇。** 建立時，伺服器不會保留空白欄位——它會以**最新通告**的版本填入並進行安裝。某次以兩個欄位均未設定的方式建立的站台，結果被鎖定到 `crt-20260201-0179` 和 OS `9.2026.14`（即租戶當時通告的兩個版本），隨後安裝失敗。`觀察於 2026-07-29`。

這帶來兩個後果。空白代表「給我最新版本」，因此未鎖定版本的部署最可能遭遇下方所述的磁碟限制。同時，你無法透過留空其中一個欄位來單獨隔離另一個，因為伺服器會自動填入——請明確設定兩個欄位，否則就接受各自的最新版本。

**第一次開機後，不會自動升級。** F5 Distributed Cloud 通告較新的建置並等待。「節點停留在初始版本」這個說法指的是建立之後的階段，而非建立過程中。

兩個階段均可在站台物件上觀察到。`觀察於 2026-07-28`，此機群：

```text
volterra_software_status.available_version   crt-20260201-0179
operating_system_status.available_version    9.2026.14
```

而節點運行的是 `crt-20250613-3382` 和 OS `9.2024.6`。較新的建置已提供但尚未被採用——這是穩定狀態，而非升級卡住。

## Terraform 無法變更版本，但 API 可以

這是兩個獨立的事實，混淆後會導致錯誤的計劃。

**Terraform 無法變更。** `ce_os_version` 和 `ce_sw_version` 實際上僅為建立時有效的參數。若變更其中任一項並執行 apply，API 會以 `[BAD_REQUEST] Invalid request parameters` 拒絕更新。`觀察於 2026-07-29`，在可棄用的站台上，三個方向均測試過——**向前**鎖定到較新版本、**向後**鎖定到較舊版本，以及清除兩個欄位**取消鎖定**。向前並非特殊情況。

**API 可以變更。** F5 Distributed Cloud 為每個站台提供專屬的升級操作，可就地啟動版本變更——無需重建，也無需 Terraform 介入：

```bash
# 軟體建置
curl -X POST -H "Authorization: APIToken $TOKEN" -H 'Content-Type: application/json' \
  --data '{"version": "<software-version>"}' \
  "$API_URL/api/config/namespaces/system/sites/<site-name>/upgrade_sw"

# 作業系統
curl -X POST -H "Authorization: APIToken $TOKEN" -H 'Content-Type: application/json' \
  --data '{"version": "<os-version>"}' \
  "$API_URL/api/config/namespaces/system/sites/<site-name>/upgrade_os"
```

`觀察於 2026-07-29`：軟體升級呼叫回傳 `200`，站台進入 `UPGRADING` 狀態，`deployment_state.phase` 為 `UPGRADE_IN_PROGRESS`，站台物件的請求版本也變更為所傳送的版本。省略欄位會回傳 `400` 及 `version empty in the request`，這也是確認欄位名稱的方式。

**請預留數小時而非數分鐘，且遇到失敗時不要驚慌。** 在預設磁碟的節點上，升級至 `crt-20260201-0179` 約需一小時，中途曾回報 `UPGRADE_FAILED`，`result` 為 `Failed`，但最終**成功完成**並運行在新版本上。平台會自動重試。

這對監控升級或編寫自動化腳本的人有直接影響：`Failed` 結果是需要等待的狀態，而非最終判決。將第一次失敗視為最終結果，會將一個即將成功的升級誤報為失敗。

請注意路徑中的群組：這些端點位於 **`config`** 下，而非 `operate`。`operate` 下的相同路徑會回傳 `404 API Group could not be determined`，這是路由訊息，而非表示不存在升級端點——這個區別曾讓本專案得出錯誤結論。

<Aside type="caution" title="透過 API 升級會使 Terraform 狀態不同步">
鎖定的變數仍維持原本的值，因此線上站台現在運行的版本並非設定所指定的版本。Terraform 不會進行協調——因為更新會被拒絕——所以請將 API 升級視為刻意脫離 Terraform 控制的操作，並在下次重建時將鎖定的版本更新為一致。
</Aside>

<Aside type="note" title="本頁兩項先前的說法，現已撤回">
本頁先前表示將 CE 移至不同版本需要重建站台，以及被拒絕的更新「仍會清除伺服器上的欄位」，導致 Terraform 持續提出失敗的變更。兩者均未通過測試：上述 API 升級可就地啟動版本變更，無需重建任何內容；且在三次被拒絕的更新後，站台規格**均未變更**，站台維持 `ONLINE` 狀態。provider issue `xcsh#1387` 中描述的偏差是在站台已自動升級超過其鎖定版本的情況下觀察到的，因此可能需要該偏差的初始狀態；在規格與鎖定版本一致的站台上未能重現。
</Aside>

若選擇重建而非升級，則替換 CE 的所有後果均適用。

<Aside type="danger" title="替換 CE 的所有後果均適用">
新的 SSH 主機金鑰、重新分配的內部位址、全新的註冊，以及僅存在於節點上的所有內容遺失。Cloud-init 會在新 VM 上重新執行，因此以該方式設定的 SSH 存取會保留——但它*僅*在第一次開機時執行，因此任何手動新增至舊節點的內容將全部消失。

在排定此操作前，請閱讀 [SSH](./access/ssh/) 以了解主機金鑰與位址的影響。
</Aside>

## 鎖定的建置版本可能安裝失敗，且站台將卡住

接受鎖定並不等同於成功安裝。在鎖定到 `crt-20260201-0179` 的全新單節點 Azure Secure Mesh v2 Customer Edge 上，站台物件立即回報了鎖定的版本——但安裝隨後失敗：

```text
site_state        PROVISIONING
phase             UPGRADE_FAILED
result            Failed
last_installed    (empty)
message           stage: 10, app: voucher obj: voucher objKind: DaemonSet failed ...
                  required replicas: 1, current replicas: 0
```

`觀察於 2026-07-28`，並於 2026-07-29 重現兩次。**作業系統**鎖定在同一次執行中正常安裝（`9.2024.6` 至 `9.2026.14`，`UPGRADE_COMPLETED`）；僅軟體安裝失敗。站台從未達到 `ONLINE` 狀態，`last_installed_version` 維持空白，因此沒有回退到可運行的版本——沒有先前成功安裝的版本可供回退。

**建立時的失敗與升級過程中的失敗不同。** 兩者行為有所差異，當你決定是否介入時，這一差異至關重要：

| | 建立時 | API 升級過程中 |
| --- | --- | --- |
| 是否會重試並成功？ | 否——維持 `Failed` 超過 20 分鐘，發生兩次 | 是——恢復並完成 |
| 節點最終狀態為何？ | `PROVISIONING`，未安裝任何版本 | `ONLINE`，運行可用的建置版本 |
| 是否可以放置不管？ | 否，已卡住 | 是，它會自行恢復或保留舊版本 |

因此，建立時的失敗需要使用更大磁碟重建，而升級過程中回報 `Failed` 應等待一段時間再下結論。

**原因是磁碟，而非版本。** 以軟體 × OS × 磁碟大小的矩陣，每個組合使用一個可棄用的單節點 Azure Secure Mesh v2 站台，全部使用相同的市集映像，可以隔離出原因。`觀察於 2026-07-29`：

| 軟體 | OS `9.2024.6`（映像預設版本） | OS `9.2026.14` |
| --- | --- | --- |
| `crt-20250613-3382` | 安裝成功 | 安裝成功 |
| `crt-20260201-0179` | 安裝成功 | **失敗**，僅在預設磁碟上 |

兩個版本單獨均不會失敗。只有組合在一起，且僅在映像的預設磁碟上才會失敗——相同的組合在 **40 GB**、**48 GB** 和 **64 GB** 磁碟上均可成功安裝。因此較新的建置版本在此並非不受支援，較新的作業系統亦然；兩者組合所需的磁碟空間超過預設節點所具備的容量。

`terraform/modules/ce-node` 未設定 `disk_size_gb`，因此每個 Customer Edge 均使用映像預設值。**若要運行較新的版本組合，請擴大磁碟。** 40 GB 是測試中可成功安裝的最小容量；確切的邊界介於映像預設值與 40 GB 之間，未進一步縮小範圍。

無論如何，在將版本變更套用至機群之前，請先在可棄用的站台上進行測試：若機群以此方式失敗，將卡在 `PROVISIONING` 狀態，重建是唯一的出路。

<Aside type="caution" title="請勿依據 F5 的升級前數據來估算磁碟大小">
F5 文件中的升級前檢查要求剩餘 20 GB 加上容量的 15%。該檢查適用於**主控台 UI** 升級，且明確說明不適用於 API 發起的升級，因此它並不描述此失敗情況。若套用此公式，會預測 48 GB 磁碟將失敗；但 48 GB 實際上可成功安裝。請依據上述實測結果來估算磁碟大小，而非套用該公式。
</Aside>

<Aside type="note" title="本頁先前提供的一個解釋，現已撤回">
本頁早期版本曾指出安裝失敗是因為請求的建置版本比映像的版本舊——即節點被要求向下回退。這是錯誤的。此機群使用相同映像建立時，鎖定的版本比映像舊了**十三個月**，安裝正常；且當 OS 鎖定保留在映像自身版本時，`crt-20260201-0179` 也能正常安裝。版本變更的方向並非關鍵變數。
</Aside>

## 文件所描述的建置版本

本站的命令參考資料描述的是 **`crt-20250613-3382`**，即此機群所運行的建置版本。僅存在於較新建置的命令記錄於 `sitecli/command-classification.json` 的 `not_on_this_build` 下，並另行記載於[較新建置上的命令](./commands/on-box/newer-builds/)，因此其中不會有在此處標示為可執行的內容。另請參閱[節點上的命令](./commands/on-box/)。

<Aside type="note" title="升級至較新建置的方式已確定，且無需重建">
此問題先前記錄為未解決，並有一份報告指出較新建置在單節點 Azure Secure Mesh v2 站台上失敗，另有一份反例觀察到有站台正在運行該版本。兩者現均已得到解釋：較新的建置可在該拓撲上安裝，失敗是上述磁碟限制所致，而非建置本身的問題。

因此有兩條路徑，且均無需為此目的重建——使用足夠大磁碟建立新節點，或透過 API 升級現有節點。`觀察於 2026-07-29`。
</Aside>
