在展示之前先執行這些檢查。每一項檢查都會縮小故障可能所在的範圍，因此失敗會告訴你某些具體資訊，而不只是「某處出了問題」。

每一道指令都會從部署中讀取所需資訊。設定一次後，其餘都會沿用：

```bash
cd terraform
RG=$(terraform output -raw resource_group_name)
RS=$(terraform output -raw route_server_name)
CLIENT=$(terraform output -raw client_vm_name)
DOMAIN=$(terraform output -raw lb_domain)
VIP=$(terraform output -raw vip)
NIC=$(terraform output -raw client_nic_name)
```

## 四項檢查，依此順序

<Steps>

1. **每個站台都是 `ONLINE`。** 若這一點不成立，其後的一切都不可能為真。

   ```bash
   for s in $(terraform output -json xc_site_names | jq -r '.[]'); do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   2026-07-28 觀察結果，三個 CE：

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **每個 peering 都學到該 CE 的 VIP 通告。** 分別查詢每一個 peering——請參閱下方第一個陷阱，因為這正是本示範最常看起來壞掉、實際上卻沒壞的地方。

   ```bash
   for k in $(terraform output -json xc_site_names | jq -r 'keys[]'); do
     echo "--- ${k}-bgp"
     az network routeserver peering list-learned-routes \
       --name "${k}-bgp" --routeserver "$RS" -g "$RG" \
       --query "RouteServiceRole_IN_0[?network=='${VIP}/32'].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   2026-07-28 觀察結果：

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp
   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp
   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   三個 peering、三個不同的 next hop、一個前綴。這就證明了 ECMP 的通告端。

3. **用戶端的有效路由包含每一個 next hop。** 這才是 ECMP 本身，也就是 VNet 實際編程的結果——不是 CE 宣稱了什麼，而是 Azure 對它做了什麼。

   ```bash
   az network nic show-effective-route-table -g "$RG" -n "$NIC" \
     --query "value[?addressPrefix[0]=='${VIP}/32'].{prefix:addressPrefix[0],nh:nextHopIpAddress,type:nextHopType,state:state}" \
     -o json
   ```

   2026-07-28 觀察結果：

   ```json
   [
     {
       "nh": ["10.0.1.5", "10.0.1.6", "10.0.1.4"],
       "prefix": "10.250.0.10/32",
       "state": "Active",
       "type": "VirtualNetworkGateway"
     }
   ]
   ```

   檢查重點是 `state: Active`，且 `nh` 中每個 CE 各有一筆。**順序並不具意義，也不穩定**——Azure 每次呼叫回傳的順序都不同，所以請計算數量，而不是與先前執行結果比對。若預期三個卻只看到一個 next hop，代表某個 CE 已停止通告，而步驟 2 可以指出是哪一個。

4. **VIP 能夠服務流量。** 從用戶端 VM 發出，並且**帶上 `Host` 標頭**——請參閱第二個陷阱。取樣要夠多才看得出問題：即使在下述收斂視窗內，幾十次請求也會顯示為 100 %。

   ```bash
   az vm run-command invoke -g "$RG" -n "$CLIENT" \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts "ok=0; fail=0
                for i in \$(seq 1 60); do
                  c=\$(curl -s -o /dev/null -m 5 -w '%{http_code}' \
                        -H 'Host: ${DOMAIN}' http://${VIP}/)
                  [ \"\$c\" = 200 ] && ok=\$((ok+1)) || fail=\$((fail+1))
                done
                echo \"OK=\$ok FAIL=\$fail\""
   ```

   2026-07-28 觀察結果：

   ```text
   VIP with Host header: OK=60 FAIL=0
   bare IP (no Host): 404
   ```

</Steps>

## 陷阱：某個 peering 只顯示一條路由，而這是正確的

`list-learned-routes` 的範圍僅限於你指定的那個 peering。它回報的是**那一個**對等體所通告的內容，而非 Route Server 的完整表格。

因此單獨查詢一個 peering 只會回傳一條經由單一 next hop 的 VIP `/32`，很容易被解讀為「只有一個 CE 在通告——其他的掛了」。其實什麼都沒掛。其他通告會出現在它們各自的 peering 上，而步驟 2 正是在逐一迴圈查詢。

無法從單一 peering 查詢確認 ECMP。要嘛迴圈查詢每個 peering，要嘛讀取用戶端的有效路由表，後者只需一次呼叫就能顯示合併後的結果。

## 陷阱：裸 IP 請求回傳 404

負載平衡器是依 `Host` 比對的。VIP 並不是一個對任何連上該位址的人都提供服務的虛擬伺服器。

以下兩者來自對同一套健康部署的同一次執行：

```text
curl -H "Host: $DOMAIN" http://$VIP/   ->  200   (60 of 60)
curl                     http://$VIP/   ->  404
```

**裸 IP 的 404 正是路徑可用的證明**——請求抵達了 CE、CE 的 proxy 做出了回應，並因為沒有相符的已設定網域而拒絕。把它讀成故障，只會讓你跑去看 BGP，而在那裡什麼問題都找不到。

示範過程中也一樣：如果你在瀏覽器直接輸入位址、而不是將網域解析到它，就會得到 404。

## VIP 在前四十五分鐘左右會丟棄請求，之後就停止

在剛建置好的堆疊上，CE 進入 `ONLINE` 後的大約前 45 分鐘內，VIP 會遺失一小部分請求，之後便乾淨地提供服務。從用戶端 VM 量測 1,470 次請求，全部帶有 `Host` 標頭：

| 時段 | 請求數 | 失敗數 | 比率 |
| --- | --- | --- | --- |
| ECMP 啟用後的前約 45 分鐘 | 570 | 12 | **2.11 %** |
| 接下來的 23 分鐘 | 900 | **0** | **0.00 %** |

每一次失敗都是 `curl: (28)`——逾時且未收到任何位元組——而不是 HTTP 錯誤狀態。最後一次發生在 ECMP 啟用後約 43 分鐘。在 900 次乾淨請求中，有 400 次以 30 秒逾時執行，且每一次都在 2 秒內完成，因此並沒有因為逾時設得太短而被掩蓋的情況。

**原點伺服器並非成因。** 一組直接打向原點（`terraform output -raw origin_ip`，繞過 VIP）的對照批次，在 VIP 批次正在失敗的**同時**，120 次全數乾淨通過。故障出在 VIP、ECMP 或 CE 路徑的某處。

有兩件事刻意不這麼稱呼：

- **這不是穩態缺陷。** 它會完全消失並持續保持乾淨。已經運行一小時的示範不會有這個問題——在已運行數小時的堆疊上，上述檢查 4 是 60 中 60。
- **無法歸咎於特定 CE。** 此拓撲中沒有任何機制提供每節點的 HTTP 監聽器，因此無法把被丟棄的請求綁定到丟棄它的節點。CE 的外部介面根本沒有 HTTP 監聽器——只有 VIP `/32` 會回應。

在不同租用戶中重新乾淨建置也重現了此現象，因此它跟隨的是拓撲，而非環境。

<Aside type="caution" title="不要只取樣 40 次請求就斷定沒問題">
即使在失敗視窗內，40 到 50 次的批次大多數時候仍會顯示 100 %。這正是此現象一開始被誤判為持續性低比率故障、接著又被誤判為完全沒問題的原因。請取樣 100 次以上，並分成在時間上彼此分隔的批次。
</Aside>

## 另外兩個量測陷阱

兩者都在此環境中產生了看似有信心的錯誤答案，而且都不明顯。

- **請從 VNet 內部探測，而不是從你的工作站。** 企業 proxy 可能會自行完成常見連接埠的 TCP 交握，因此工作站的探測會回報一個實際上是關閉的連接埠為**開啟**。從工作站探測 CE 公用位址時，連接埠 80 與 443 顯示為開啟；從 VNet 內部探測時則是關閉。請使用用戶端 VM。
- **CE 上的連接埠 22 僅在內部（SLI）位址上回應。** 從用戶端 VM 探測時，每個 CE 的內部位址都會回傳 OpenSSH 橫幅，而其管理與外部位址則逾時——作為對照的未使用位址亦然。eth0 已更名為 `a-i-eth0` 且不帶主機 IP，因為資料路徑擁有它。因此，探測你所熟知的節點位址，並不能告訴你該節點的 SSH 狀態。

<Aside type="danger" title="切勿硬編碼 CE 內部位址——每次重建都會重新指派">
Azure 不會保留哪個 CE 在內部子網路中取得哪個位址。2026-07-28 觀察，重建之後，三個 CE 分別持有 `10.0.3.7`、`10.0.3.5` 與 `10.0.3.4`：既非節點順序、也不連續，且與先前持有的不同。測試用戶端自己的 NIC 也位於同一子網路，並曾持有先前某個 CE 使用過的位址。

請讀取它們，而不要記住它們：

```bash
terraform output -json ce_sli_private_ips
```

若手邊沒有 Terraform 狀態，可依 NIC 名稱向 Azure 查詢，NIC 名稱**確實**是穩定的：

```bash
az network nic show -g "$RG" -n "<vm-name>-internal-nic" \
  --query ipConfigurations[0].privateIPAddress -o tsv
```

連到記憶中的位址，會讓你落在錯誤的節點上、落在不是 CE 的 VM 上，或哪裡都到不了——而最後這種情況看起來與「SSH 未啟用」一模一樣。
</Aside>

## 確認機上指令介面仍與文件相符

```bash
bash scripts/capture-sitecli.sh --check \
  --site "$(terraform output -json xc_site_names | jq -r '.eastus01')" \
  --node "$(terraform output -json ce_vm_names | jq -r '.eastus01')"
```

`--check` 不會寫入任何內容，因此對正在運行的示範是安全的。
