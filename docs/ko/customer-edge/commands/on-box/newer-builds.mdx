Site CLI 명령어 목록은 빌드 간에 증가합니다. 7개의 `execcli` 명령어가 이 플리트가 실행하는
버전보다 최신 빌드에 존재하므로, 이 섹션의 나머지 부분을 읽는 운영자는 해당 명령어를 찾지 못할
것이며, F5의 최신 공식 문서를 읽는 사람은 해당 명령어가 있을 것으로 기대할 수 있습니다.

이 목록은 재배열이 아닌 상위 집합입니다. 최신 빌드에는 **89**개의 `execcli` 명령어가 있으며,
이 플리트에는 **82**개가 있고, 7개가 추가되고 삭제된 것은 없습니다.

<Aside type="caution" title="이 플리트에서는 실행할 수 없습니다">
이 명령어들은 Azure 마켓플레이스 이미지에 포함된 빌드 `20260703-e2c462a`에서 측정되었습니다.
이 플리트는 `crt-20250613-3382`를 실행하며, 해당 버전에서는 7개 모두 존재하지 않습니다 —
`execcli`는 알 수 없는 명령어라고 보고합니다. 아래의 모든 내용은 최신 빌드를 설명합니다.
</Aside>

## 각 명령어의 기능

설명은 완성 메뉴에 나타나는 어플라이언스 자체의 것입니다.

| 명령어 | 어플라이언스의 설명 |
| --- | --- |
| `collect-database-stats` | 데이터베이스 통계 수집 |
| `iptables-lv` | iptables -L -v -n 표시 |
| `marker-exists-crio` | crio 재시작 마커 존재 여부 확인 |
| `marker-exists-kubelet` | kubelet 재시작 마커 존재 여부 확인 |
| `marker-exists-NetworkManager` | NetworkManager 재시작 마커 존재 여부 확인 |
| `systemctl-restart-NetworkManager` | NetworkManager 서비스 재시작 |
| `systemctl-start-crio-prune` | crio 이미지 정리 서비스 시작 |

이것들을 하나의 집합으로 읽으면, 대부분은 7개의 관련 없는 도구가 아니라 하나의 워크플로를
설명합니다. 3개의 명령어는 서비스가 재시작 대기 상태로 표시되었는지 묻고, 2개는 재시작 또는
정리를 수행합니다. 마커 확인은 다른 한쪽이 파괴적인 쌍의 안전한 절반입니다.

**7개 중 4개는 읽기만 합니다. 3개는 노드를 변경합니다** — 그리고 그 3개 중 하나는 예상하는
것이 아니며, 이것이 아래 별도 섹션의 주제입니다.

## `marker-exists-crio`

`crio`에 대한 재시작 마커 파일이 존재하는지 보고합니다.

```bash
execcli marker-exists-crio
```

```text
Capture policy: never execute through the API
```

## `marker-exists-kubelet`

```bash
execcli marker-exists-kubelet
```

```text
Capture policy: never execute through the API
```

## `marker-exists-NetworkManager`

```bash
execcli marker-exists-NetworkManager
```

```text
Capture policy: never execute through the API
```

세 가지 모두 `missing`으로 응답했으며, 해당 서비스에 대한 재시작이 대기 중이지 않음을 의미합니다.

<Aside type="note" title="이 출력을 정상적인 기준선이 아닌 형태로 읽으십시오">
`2026-07-28 관측됨.` 이 데이터를 캡처한 노드는 `ONLINE` 상태에 도달하지 못했습니다 — 소프트웨어
설치 실패 후 `PROVISIONING` 상태였으며, 그것이 노드가 존재했던 이유입니다. `missing`은 마커가
없을 때 명령어가 출력하는 것이며, 그것이 유용한 부분입니다. 정상적인 노드가 동일한 방식으로
응답한다는 것은 **확인되지 않았으며**, 재시작 대기 중인 노드가 무엇을 출력하는지에 대해서도
여기에서 설명하지 않습니다.
</Aside>

## `iptables-lv`

`iptables -L -v -n`을 실행하고 변경 없이 반환하므로, F5 추상화가 아닌 노드의 필터 테이블에 대한
패킷 및 바이트 수 뷰입니다.

```bash
execcli iptables-lv
```

```text file=../../../../_data/sitecli-iptables-lv.txt
```

출력의 대부분은 Kubernetes의 것입니다. `KUBE-` 체인은 kube-proxy의 서비스, nodeport 및
방화벽 규칙이며, `DOCKER-USER`는 컨테이너 런타임에 속합니다. 첫 번째 줄은 건너뛰지 않고 주목할
가치가 있습니다 —

```text
# Warning: iptables-legacy tables present, use iptables-legacy to see them
```

— 왜냐하면 이 뷰가 **불완전함**을 나타내기 때문입니다. 레거시 테이블의 규칙은 여기에 표시되지
않으며, Site CLI는 해당 규칙을 읽는 명령어를 제공하지 않습니다.

## `collect-database-stats`는 이름과 달리 노드에 씁니다

이 명령어는 함정이며, 함정은 이름에 있습니다. "데이터베이스 통계 수집"과 어플라이언스 자체의
설명 모두 관찰 목적으로 읽힙니다. 명령어는 그런 방식으로 시작합니다 — 열린 파일 제한, `etcd`가
보유한 디스크립터 및 연결 수, `lsof` 목록, `etcd` 파일시스템에 대한 `df` — 그리고 나서
**15초짜리 `fio` 랜덤 쓰기 벤치마크**를 실행합니다.

```text
Checking if fio disk performance test can run safely...

Running fio disk performance test (15 seconds)...
etcd-test: (g=0): rw=randwrite, bs=(R) 4096B-4096B, (W) 4096B-4096B ...
etcd-test: Laying out IO file (1 file / 250MiB)
```

**250 MiB** 파일을 배치하고, 3.5 GiB의 여유 공간이 있는 파일시스템에서 아래 실행 시 10.6 MiB의
랜덤 I/O를 기록했습니다. 안전하게 실행할 수 있는지 사전에 확인하므로 무모하지는 않습니다 —
하지만 **읽기가 아닙니다**.

<Aside type="danger" title="라이브 노드에서는 파괴적인 명령어로 취급하십시오">
`etcd`가 자체 저널을 기록하는 파일시스템에 대한 랜덤 쓰기 벤치마크는 정확히 `etcd`가 가장
민감한 리소스를 두고 `etcd`와 경쟁합니다. 출력 자체가 이를 가리킵니다 — "Healthy etcd disks
should have p99 < 10ms" — 이는 트래픽을 처리하는 노드가 아닌 테스트 중인 노드에 대한 설명입니다.
F5 지원팀이 요청할 때, 레이턴시를 방해할 의향이 있는 노드에서 실행하십시오.
</Aside>

```bash
execcli collect-database-stats
```

```text file=../../../../_data/sitecli-collect-database-stats.txt
```

읽는 방법: 열린 파일 `ulimit`과 디스크립터 수의 쌍은 `etcd`가 한계를 초과하는 것으로 의심될 때
지원 엔지니어가 요청하는 항목이며, `clat` 백분위수는 벤치마크의 핵심입니다. 디스크 통계 줄의
`util=94.00%`는 **테스트 중** 장치가 얼마나 사용되었는지를 나타냅니다 — 파일시스템 사용량
수치가 아니며, 두 가지는 혼동하기 쉽습니다.

<Aside type="note" title="이 페이지에 해당 출력이 포함된 경위">
이 명령어는 읽기 전용으로 잘못 처리되어, 이 캡처가 수집된 일회용 노드에서 한 번 실행되었습니다
— 이름과 설명에서 벤치마크의 힌트를 전혀 찾을 수 없었으며, 쓰기는 자체 출력에서야 비로소
확인되었습니다. 하네스는 이제 이를 거부하며, 테스트는 커밋된 캡처에서 쓰기 마커를 스캔하고
그러한 명령어가 읽기 전용 허용 목록에 있는 경우 실패합니다. 이름만으로는 명령어가 읽기만
수행한다는 것을 보장할 수 없기 때문입니다.
</Aside>

## 실행되지 않은 두 가지 명령어

`systemctl-restart-NetworkManager`와 `systemctl-start-crio-prune`은 이름으로만 문서화되어
있으며 캡처된 출력이 없습니다.

```bash
execcli systemctl-restart-NetworkManager
execcli systemctl-start-crio-prune
```

`NetworkManager`를 재시작하면 노드의 네트워킹이 중단되고, 정리 서비스는 컨테이너 이미지를
삭제합니다. 두 명령어 모두 노드를 변경하므로, 일회용 노드에서도 실행하지 않았습니다.

<Aside type="caution" title="변경을 수행하는 세 가지 명령어 중 어느 것도 읽기 전용 허용 목록에 없습니다">
`scripts/sitecli_ssh_harvest.py`는 이 두 명령어와 `collect-database-stats` 실행을 거부합니다.
명시적인 읽기 전용 허용 목록에 있는 이름만 실행할 수 있으며, 나머지는 모두 열거되고 절대
실행되지 않습니다. 테스트는 세 가지 모두 해당 목록에서 제외되어 있는지 확인하므로, 실수로 거부가
취소될 수 없습니다.
</Aside>

이 사이트 형태에 설치되지 않습니다 — [소프트웨어 버전 및 재빌드](../../../lifecycle/)를

**확인되지 않았습니다**.
</Aside>
