두 가지 명령이 `xuser`라는 루트 계정을 생성하고 제거합니다. 이 명령들은 F5 소유이며,
[debug API](../../../access/debug-api/)에는 없고, `admin` 계정으로 수행할 수 없는 작업을 위한 탈출구입니다.

<Aside type="danger" title="이 명령들은 노드의 계정 상태를 변경하며, 여기서는 실행하지 않습니다">
`get-auxilary-root-access-to-node`는 **루트 사용자**를 생성합니다. 이는 세션이 종료된 후에도
유지되는 노드 변경 사항으로, 탐색적으로 실행할 사항이 아닙니다. 두 명령 모두 어플라이언스 자체
완성 메뉴에서 문서화되어 있으며, 실행된 적이 없고, 수집 하네스는 두 명령 모두 거부합니다.

"auxiliary"의 오탈자는 어플라이언스의 것이며, 이 페이지의 오탈자가 아닙니다. 표시된 대로
입력하지 않으면 명령을 찾을 수 없습니다.
</Aside>

## `get-auxilary-root-access-to-node`

`xuser` 루트 계정을 생성합니다.

```bash
execcli get-auxilary-root-access-to-node
```

**이 명령이 진정한 해답인 경우.** 일부 진단 작업은 `admin`으로는 단순히 접근할 수 없습니다.
이 빌드에서 확인된 가장 명확한 예시는 [`kubelet-get-params`](../kubelet/)로, `open /etc/vpm/kubelet-custom-params.txt: permission denied` 오류와 함께 실패합니다 — 파일은 존재하지만
`admin` 계정으로는 읽을 수 없습니다. 루트 액세스는 이러한 유형의 문제에 대한 문서화된 경로입니다.

**이 명령을 사용하기 전에**, [debug API](../../../access/debug-api/)가 이미 해당 질문에
답하는지 고려하십시오. debug API의 `exec` 티어는 영구 계정을 생성하지 않고 권한 있는 명령을
실행하므로, 노드에 더 작은 변경을 가합니다.

## `remove-auxilary-root-access-to-node`

`xuser` 계정을 삭제합니다.

```bash
execcli remove-auxilary-root-access-to-node
```

**작업이 완료되면 이 명령을 실행하십시오.** 하나의 진단 세션을 위해 생성되었다가 그대로 남겨진
루트 계정은 어플라이언스에 남아 있는 자격 증명으로, 누구도 이를 상기시켜 주지 않습니다. 생성과
제거를 [`vifdump`](../packet-capture/)와 `vifdump-file-rm`이 쌍을 이루는 것처럼,
동일한 세션 내에서 쌍으로 취급하십시오.

<Aside type="note" title="확인되지 않은 사항">
두 명령의 출력이 기록되지 않았으므로, 이 페이지는 성공 시 어떤 결과가 나타나는지, `xuser`가
어떤 비밀번호나 키로 생성되는지, 또는 세션이 열려 있는 동안 제거가 거부되는지 여부를 알 수
없습니다. 이를 확인하려면 수정해도 괜찮은 노드가 필요합니다.
</Aside>
