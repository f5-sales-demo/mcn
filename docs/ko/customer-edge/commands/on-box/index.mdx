두 개의 별도 명령어 세트가 Customer Edge에 도달하며, 어느 쪽도 다른 쪽을 포함하지 않습니다.

- **박스 내부**에서 Site CLI는 **최상위 명령어 6개**와 **`execcli` 하위 명령어 82개**를 갖습니다.
- **네트워크를 통해**, [debug API](../../access/debug-api/)는 자체 **34개** 카탈로그를 보유합니다.

온박스 인터페이스의 대부분은 API에 해당하는 항목이 없습니다. 전체 Vega 컨트롤 플레인, Envoy 래퍼, 패킷 캡처, kubelet 매개변수 세트, `edit-*` 파일 및 보조 루트 액세스 쌍은 박스에서만 접근할 수 있습니다.

이에 접근하려면 [SSH](../../access/ssh/) 또는 [시리얼 콘솔](../../access/serial-console/)이 필요하며, 어디에도 문서화되지 않은 한 가지 사항이 있습니다:

<Aside type="tip" title="execcli는 숨겨진 명령어입니다">
`execcli`는 Site CLI의 대화형 메뉴에 표시되지 않습니다. 명령어 이름을 인수로 받으며, `execcli ` 뒤에 **Tab**을 누르면 어플라이언스의 자체 한 줄 설명과 함께 82개 전체가 나열됩니다. 해당 완성 메뉴가 빌드에 대한 권위 있는 카탈로그이며, `sitecli/exec-catalog.json`에 기록된 내용입니다.
</Aside>

## 측정 방법 및 세트 겹침

아래 세트는 벤더 문서에서 옮겨 적은 것이 아닙니다. `scripts/sitecli_ssh_harvest.py`를 사용하여 라이브 노드에서 직접 읽어 그 출처와 함께 `sitecli/exec-catalog.json`에 커밋되었습니다. 세 가지 등록 상태에서 세 번 실행한 결과:

| 측정 시점 | 최상위 | `execcli` |
| --- | --- | --- |
| `site_state: PROVISIONING` | 6 | 82 |
| `site_state: PROVISIONED` | 6 | 82 |
| `site_state: ONLINE` | 6 | 82 |

세 번 모두 **동일한 세트**를 반환했습니다 — 단순히 총계가 같은 것이 아니라 이름이 동일했으며, 마지막은 다른 사이트 및 리소스 이름을 가진 다른 배포였습니다. 따라서 명령어 인터페이스는 등록 상태에 따라 변하지 않으며, 없는 명령어는 아직 제공되지 않는 것이 아니라 진정으로 없는 것입니다.

debug API의 34개와 비교하면 두 가지 수치를 명확히 구분해야 합니다:

- **51개**의 `execcli` 하위 명령어는 API에 해당하는 항목이 없습니다.
- **55개**는 전체 온박스 인터페이스에서 계산된 동일한 수치로, `execcli` 하위가 아닌 최상위에 있는 4개의 `configure*` 명령어도 포함됩니다.

둘 다 올바른 수치입니다. 독자가 하나를 재계산하여 다른 값을 찾았다면 실수한 것이 아닙니다. 여기의 모든 수치는 `sitecli/catalog.json` 및 `sitecli/exec-catalog.json`에서 도출되었습니다.

<Aside type="caution" title="존재하지 않는 다섯 개의 명령어">
`factory-reset`, `upgrade`, `reboot`, `show`, `clear`는 이 빌드에 **없습니다**. Site CLI에 있을 법한 명령어들로, 한동안 그 가정 하에 이 저장소의 분류에 포함되어 있었지만, 어떤 열거에서도 발견되지 않았습니다. 최상위에는 정확히 여섯 개의 항목이 있습니다: `configure`, `configure-generic-hardware`, `configure-network`, `configure-http-proxy`, `diagnosis`, `health`.
</Aside>

<Aside type="caution" title="세 개의 API 명령어는 execcli 하위 명령어가 아닙니다">
`execcli`에서 이것들을 찾으면 아무것도 나오지 않아 "명령어가 없다"고 읽힐 수 있습니다:

- **`health`**와 **`diagnosis`**는 **최상위** Site CLI 명령어입니다. `execcli` 접두사 없이 `>>>` 프롬프트에서 직접 입력하세요.
- **`dig`**는 debug API를 통해 접근 가능하며 온박스 메뉴 **어디에도** 나타나지 않으므로, 아래 패스스루 목록에 없습니다. API 전용입니다.

</Aside>

## 문서화된 항목과 목록만 제공된 항목

Customer Edge는 Linux와 여러 서드파티 데몬을 실행합니다. 해당 명령어를 문서화하면 자체 참조를 중복하고 F5가 소유한 것처럼 암시하므로, 규칙은 다음과 같습니다: **F5 소프트웨어는 문서화하고, 나머지는 CE에 특화된 내용만 문서화합니다.**

"우리 것"과 "그들 것"이 명확히 구분되지 않으므로 세 계층이 있습니다. 분류는 `sitecli/command-classification.json`에 기록되어 있습니다.

| 계층 | 처리 방식 |
| --- | --- |
| **F5 소프트웨어** | 전체 문서화 — 목적, 구문, 인수, 캡처된 출력, 확인할 사항. Argo, Vega, `vpm`, `vifdump`, `configure*`, `edit-*` 세트, kubelet 매개변수, 루트 액세스. |
| **CE 특화 해석** | CE에서 특별한 의미를 갖는 서드파티 도구. CE 특화 해석이 문서화되고 도구 자체의 의미론은 업스트림에 맡깁니다. |
| **패스스루** | CE에 특화된 내용이 없는 일반 Linux 또는 서드파티. 사용 가능 항목으로 나열하고 업스트림으로 포인터 제공. 본문 없음. |

이 구분이 페이지 존재 여부를 결정하며, 이 문서가 man 페이지의 더 나쁜 사본으로 변질되는 것을 방지합니다.

## 패스스루

박스에서 사용 가능하지만 **여기서는 문서화하지 않습니다** — 이것들은 F5 소프트웨어가 아닌 운영 체제와 서드파티 데몬이며, 자체 참조가 이 페이지에서 재서술하는 것보다 낫습니다.

| 명령어 | 업스트림 |
| --- | --- |
| `ping`, `netstat`, `lsof`, `ip`, `ip-link-show`, `nmcli`, `tracepath` | iproute2, NetworkManager |
| `top`, `check-mem`, `sysctl`, `load-sysctl-conf`, `journalctl`, `files`, `rpm-ostree`, `chronyc-sources` | coreutils, procps, systemd, rpm-ostree, chrony |
| `edit-etc-hosts`, `edit-sysctl-conf` | 해당 파일들은 운영 체제의 것입니다 |
| `systemctl-status-crio`, `systemctl-status-docker`, `systemctl-status-kubelet`, `systemctl-status-iscsid`, `systemctl-status-multipathd` | systemd |
| `systemctl-restart-crio`, `systemctl-restart-docker`, `systemctl-restart-kubelet`, `systemctl-restart-iscsid`, `systemctl-restart-multipathd` | systemd — 이 명령어들은 모두 노드의 워크로드를 중단시킵니다 |

이 중 두 가지는 별도 페이지가 없더라도 알아둘 가치가 있습니다. `files`는 파일 작업을 수행하며 `/tmp` 하위에만 쓸 수 있습니다. 그리고 모든 `systemctl-restart-*`는 정의상 중단을 유발합니다 — `crio` 또는 `kubelet`을 재시작하면 해당 노드의 워크로드가 중단됩니다.

<Aside type="note" title="일부 명령어는 최신 빌드에만 존재하며 이 빌드에는 없습니다">
`collect-database-stats`, `iptables-lv`, 세 개의 `marker-exists-*` 명령어, `systemctl-restart-NetworkManager`, `systemctl-start-crio-prune`은 여기서는 없고 빌드 `20260703-e2c462a`에는 있으며, 이 빌드의 82개 대비 89개의 `execcli` 명령어를 제공합니다. [최신 빌드의 명령어](../newer-builds/)에서 이를 문서화합니다. 분류에서 `not_on_this_build.newer_build`로 기록되어 있어 여기 있는 어떤 것도 `crt-20250613-3382`에서 실행 가능한 것으로 오해되지 않습니다.

`collect-debug-info`는 별도의 경우입니다. 어떤 메뉴나 카탈로그에도 나타나지 않습니다. Site CLI 환영 텍스트에 "지원을 위한 디버그 정보 수집"이 가능하다고 나와 있어, 이름은 관찰된 것이 아니라 해당 문장에서 파생된 것으로 보입니다. 검증되지 않은 것으로 표시되어 있으며 의도적으로 탐색하지 않습니다 — 라이브 노드에서 알 수 없는 명령어를 추측으로 실행하는 것은 아직 등록 중인 CE에서 `vifdump` 패킷 캡처를 시작하게 되는 방식입니다.
</Aside>
