세 가지 명령어가 커스텀 kubelet 파라미터 파일인
`/etc/vpm/kubelet-custom-params.txt`를 관리합니다. 세 명령어 모두 F5의 것이며,
[debug API](../../../access/debug-api/)에는 없고, 모두 지원 주도형입니다 — kubelet
파라미터는 노드가 Kubernetes 워크로드를 실행하는 방식을 변경합니다.

<Aside type="danger" title="F5 지원팀이 요청하는 경우에만 사용하십시오">
커스텀 kubelet 파라미터는 재부팅 후에도 유지되며 노드가 실행하는 모든 워크로드에 적용됩니다.
여기서는 유효성 검사가 없습니다. 잘못된 파라미터도 허용되며 다음 kubelet 시작 시 적용됩니다.
</Aside>

## `kubelet-get-params`

현재 커스텀 파라미터를 읽습니다.

```bash
execcli kubelet-get-params
```

```text file=../../../../_data/sitecli-kubelet-get-params.txt
```

**이 명령어는 이 빌드에서 사이트 CLI의 Site CLI에서 작동하지 않습니다.** `admin` 계정은
파라미터 파일을 읽을 수 없으므로, 파라미터 설정 여부와 관계없이 명령어가 실패합니다:

```text
Error: failed to read all params: failed to read custom param file:
open /etc/vpm/kubelet-custom-params.txt: permission denied
```

**이것이 보이는 것보다 더 중요한 이유.** 실패는 빈 결과가 아닌 *권한* 오류이며, 두 가지를
혼동하기 쉽습니다 — "failed to read all params"는 "파라미터가 없다"는 것처럼 읽힙니다.
이것은 파라미터가 구성되지 않았다는 증거가 아닙니다. 이 빌드에서 사이트 CLI로 파라미터를
확인할 수 있는 유일한 방법은 [보조 루트 접근](../root-access/)을 사용하는 것이며,
이 역시 지원 주도형입니다.

<Aside type="note" title="검증된 내용">
명령어가 존재하고 실행되며, 빌드 `crt-20250613-3382`에서 `admin`으로 위의 오류를
반환합니다. `xuser` 루트 계정에서 성공하는지 여부는 **테스트되지 않았습니다** —
해당 계정을 획득하면 노드가 수정됩니다.
</Aside>

## `kubelet-add-param`

커스텀 파라미터를 추가합니다.

```bash
execcli kubelet-add-param <parameter>
```

인수 없이 실행하면 자체 항수(arity)를 보고하며, 이것이 아무것도 설정하지 않고 요건을
확인한 방법입니다:

```text
Error: at least one parameter is required
```

**캡처된 출력 없음.** 이 명령어는 노드에 씁니다. 존재하며 인수를 필요로 한다는 것이
검증되었습니다; 인수와 함께 실행되지는 않았습니다.

## `kubelet-remove-param`

커스텀 파라미터를 제거합니다.

```bash
execcli kubelet-remove-param <parameter>
```

**캡처된 출력 없음**, 같은 이유입니다.

<Aside type="caution" title="두 쓰기 명령어 모두 읽기 전용 허용 목록에 없습니다">
`scripts/sitecli_ssh_harvest.py`는 `kubelet-add-param`과
`kubelet-remove-param`의 실행을 거부합니다. 명시적인 읽기 전용 허용 목록에 있는
이름만 실행할 수 있으며, 그 외의 것은 열거만 되고 절대 실행되지 않습니다. 이는
의도적인 것입니다 — 차단 목록은 누군가가 나열하는 것만 막을 수 있습니다.
</Aside>
