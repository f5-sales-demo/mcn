이 명령들은 커널의 관점을 보고합니다. Argo 데이터 플레인은
[`vif`](../dataplane-forwarding/)를 통해 볼 수 있는 자체 관점을 유지하며, 두 관점은 서로 일치하지 않을 수 있습니다.

## `ip`

`ip` 하위 명령을 받습니다. `addr`가 일반적으로 사용되며, `route`, `link`, `neigh`도
동작합니다.

```bash
{"command":["ip","addr"]}
```

```text file=../../../../_data/sitecli-ip.txt
```

CE는 설계상 세 개의 Azure NIC(관리/SLO, 외부, 내부/SLI)를 갖지만,
게스트는 그 순서가 암시하는 방식으로 이를 표시하지 않으며, 바로 이 지점에서 출력을
잘못 읽으면 시간을 낭비하게 됩니다.

| 게스트에서 | 담당 |
| --- | --- |
| `a-i-eth0` | **주소가 전혀 없음** — 이름이 변경된 물리 eth0이며, Argo 데이터 플레인이 소유합니다 |
| `vhost0` | 관리/SLO 주소로, BGP 피어링에 사용되고 사이트 객체가 보고하는 주소입니다 |
| `eth1` 및 `eth2` | 외부 및 내부/SLI 주소 — 단, **고정된 순서가 아닙니다** |

<Aside type="danger" title="eth1과 eth2 중 어느 것이 내부 인터페이스인지는 노드마다 다릅니다">
이 배포의 세 CE에서 실시간으로 확인한 결과: `f5-xc-ce-vm-01`과
`f5-xc-ce-vm-03`에서는 내부/SLI 주소가 `eth2`에 있고, `f5-xc-ce-vm-02`에서는
`eth1`에 있습니다. 구성에서 이를 선택하는 요소는 아무것도 없습니다.

따라서 인터페이스 이름으로 서브넷을 추론하지 말고, 한 노드의 매핑을 다른 노드에
적용하지 마십시오. 대신 주소를 기준으로 판단하십시오 — 인터페이스는 고정적이지 않지만
CE 주소가 속한 서브넷은 안정적입니다.
</Aside>

`a-i-eth0`에 주소가 없다는 점은 관리 주소에서 `sshd`에 접근할 수 없는 이유
그 자체이기도 합니다. 포트가 차단된 것이 아니라, 거기에 리스너가 없는 것입니다.
[SSH](../../../access/ssh/)를 참조하십시오.

## `ip-link-show`

링크 계층만 표시합니다: 상태, MTU, 큐잉 규칙, MAC.

```bash
{"command":["ip-link-show"]}
```

```text file=../../../../_data/sitecli-ip-link-show.txt
```

"링크가 활성 상태인지, MTU는 얼마인지"가 질문일 때 `ip addr`보다 빠릅니다.
MTU 불일치는 터널이 설정되기는 하지만 트래픽이 전달되지 않는 문제의 반복적인 원인입니다.

## `ip-link-set` <Badge text="Exec tier — mutating" variant="danger" />

인터페이스 또는 그룹을 활성화하거나 비활성화합니다.

```
ip-link-set (<device>||<group>) (up||down)
```

<Aside type="danger" title="여기서는 실행하지 않으며, 일반적인 방식으로 접근할 수도 없습니다">
이 빌드에서 유일한 `Exec` 계층 명령입니다. `exec-user`가 아닌 `exec` 엔드포인트로
전달되며, 노드를 변경합니다. 원격 CE에서 `eth0`을 비활성화하면 디버그 API 자체를 포함하여
해당 노드를 관리하는 경로가 제거됩니다.

이 페이지에는 의도적으로 캡처된 출력이 없습니다. 캡처 하네스는 `Exec` 계층 전체를
거부하며, 하드코딩된 목록이 아니라 라이브 카탈로그에서 계층 정보를 읽으므로,
향후 빌드에서 다른 명령이 이 계층으로 승격되더라도 이 내용은 유효하게 유지됩니다.
</Aside>
