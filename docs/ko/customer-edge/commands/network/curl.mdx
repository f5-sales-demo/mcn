두 개의 명령이 있으며, 이 둘의 차이가 곧 전체 가치입니다.

## `curl-host`

호스트 네트워크 네임스페이스에서 실행됩니다 — 데이터 플레인이 개입하기 전, 노드 자체의 연결성입니다.

```bash
{"command":["curl-host","-v","cloud.f5.com"]}
```

```text file=../../../../_data/sitecli-curl-host.txt
```

## `curl-vega`

호스트가 아닌 Vega(컨트롤 플레인) 컨텍스트에서 실행됩니다. 관찰 가능한 차이이자 여기서 확인된
유일한 차이는 상속되는 환경입니다. `curl-vega`는 사설 범위, `int.ves.io`, `int.volterra.us`
및 사이트 자체의 `.tenant.local` 도메인을 포함하는 `NO_PROXY` 목록을 보고하지만, `curl-host`는
아무것도 보고하지 않습니다. 이것이 DNS 경로에 대해 무엇을 의미하는지는 측정되지 않았습니다.

```bash
{"command":["curl-vega","-v","cloud.f5.com"]}
```

```text file=../../../../_data/sitecli-curl-vega.txt
```

<Aside type="tip" title="이 쌍은 이분 탐색입니다">
둘 다 실행하십시오. `curl-host`는 성공하고 `curl-vega`는 실패한다면, 노드에는 연결성이 있으나
컨트롤 플레인 컨텍스트의 무언가 — 프록시 설정 또는 리졸버 — 가 그렇지 않은 것입니다. 둘 다
실패한다면 문제는 노드보다 상류에 있습니다: 라우팅, 방화벽, 또는 이그레스 경로입니다.
`curl-host`만 실패한다면 특이한 상황을 발견한 것이므로 호스트 라우팅 테이블을 먼저 확인해야 합니다.

정상적인 노드에서는 둘 다 성공하고 동일한 주소에 도달하므로, 깨끗한 결과 쌍은 어떤 컨텍스트가
사용되고 있는지에 대해 아무것도 증명하지 않습니다 — 정보를 담고 있는 것은 *차이*입니다.
</Aside>

두 명령 모두 일반적인 `curl` 인자를 별도의 배열 요소로 받습니다. 연결 및 TLS 핸드셰이크 줄이
보통 실패가 드러나는 지점이므로 `-v`는 유지할 만합니다.
