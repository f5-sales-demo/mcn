Argo는 포워딩 상태를 Linux 커널과 별도로 유지합니다. [`ip`](../ip/)와 이 명령들이 일치하지 않는 경우, 실제로 트래픽을 이동시키는 것은 이 명령들입니다.

## `rt`

VRF별 vRouter 라우트 테이블입니다.

```bash
{"command":["rt","--dump","2"]}
```

```text file=../../../../_data/sitecli-rt.txt
```

<Aside type="danger" title="VRF id는 BGP가 보고하는 것과 다릅니다">
`show-ip-bgp-summary`는 `vrf-id 3`을 출력합니다. 이는 FRR의 넘버링이며 vRouter 테이블 id와는 다른 네임스페이스입니다. 이 값을 여기에 전달하면 노드가 손상된 것처럼 읽히는 방식으로 실패합니다:

```
vRouter(Response):  [No such file or directory (2)]
```

`--dump 0`에 대해서도 동일한 응답이 반환됩니다. 이 토폴로지에서 **VRF 2**는 채워진 inet4 테이블이며, VRF 1은 두 개의 라우트를 보유합니다. id를 모르는 경우, BGP 출력을 신뢰하지 말고 1부터 위로 탐색하십시오.
</Aside>

## `nh`

넥스트 홉 테이블입니다. 모든 라우트는 넥스트 홉 id를 가리키며, 이를 통해 해석됩니다.

```bash
{"command":["nh","--list"]}
```

```text file=../../../../_data/sitecli-nh.txt
```

각 항목은 `Type` — `Drop`, `Encap`, `Tunnel`, `Composite` — 과 해당 VRF를 포함합니다. `Drop` 넥스트 홉으로 해석되는 라우트는 블랙홀이며, 접두사가 `rt`에 존재함에도 트래픽이 사라지는 경우 해당 조합을 확인할 필요가 있습니다.

## `vif`

가상 인터페이스 테이블: 데이터 플레인이 바인딩하는 대상과 인터페이스별 카운터입니다.

```bash
{"command":["vif","--list"]}
```

```text file=../../../../_data/sitecli-vif.txt
```

상단의 플래그 범례는 한 번 읽어볼 가치가 있습니다 — `Vp`는 vhost 물리 인터페이스를 표시하고, `Dpdk`는 DPDK 관리 인터페이스를 표시합니다. 이를 사용하여 데이터 플레인이 예상한 인터페이스를 차지했는지 확인하고, 트래픽이 커널에 도달하지 않기 때문에 Linux가 표시하지 않는 RX 및 TX 카운터를 확인하십시오.
