서른네 개의 명령어 중 열세 개입니다.

| 원하는 항목 | 사용 명령어 |
| --- | --- |
| 노드 정상 여부에 대한 단일 답변 | [health](./health/) |
| 노드 자체에서 실행하는 연결 및 DNS 프로브 | [diagnosis](./diagnosis/) |
| Kubernetes 워크로드 컨테이너 | [crictl](./crictl/) |
| 플랫폼 컨테이너: vpm, argo, site-console | [docker](./docker/) |
| 등록을 포함한 서비스 로그 | [journalctl](./journalctl/) |

## 노드는 두 개의 컨테이너 런타임을 실행합니다

이 사실은 사람들을 종종 놀라게 하며, 어떤 명령어가 질문에 답하는지 달라집니다.

- **Docker**는 플랫폼 컨테이너인 `vpm`, `argo_watch`, `site-console`을 실행합니다.
- **CRI-O**는 Kubernetes 워크로드를 실행하며, `crictl`을 통해 접근합니다.

두 런타임은 동시에 실행되고, 둘 다 실제 출력을 반환하며, 어느 쪽도 다른 쪽을 대체하지 않습니다. `docker-ps`에서 세 개의 컨테이너가 표시되는 것은 손상된 노드의 부분적인 뷰가 아니라, Docker가 실행하는 전체 목록입니다. `vpm`을 찾고 있다면 Docker 컨테이너입니다. 파드를 찾고 있다면 CRI-O에서 확인하십시오.

## 두 개의 명령어는 서로 다른 전송 방식을 사용합니다

`health`와 `diagnosis`는 `GLOBAL` 범위입니다. 즉, `global` 경로에 대한 `GET` 요청으로, 터미널 텍스트가 아닌 JSON을 반환하며, **`exec-user`를 통해 접근할 수 없습니다**. 해당 경로로 전송하면 `command not supported`라는 응답이 반환되는데, 이는 마치 명령어가 존재하지 않는 것처럼 보입니다. [디버그 API](../../access/debug-api/)를 참조하십시오.
