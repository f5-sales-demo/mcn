Docker는 플랫폼 서비스를 실행합니다. Kubernetes 워크로드는
[CRI-O](../crictl/) 하에서 실행됩니다.

## `docker-ps`

```bash
{"command":["docker-ps"]}
```

```text file=../../../../_data/sitecli-docker-ps.txt
```

<Aside type="tip" title="컨테이너 세 개가 전체 목록이며, 손상된 노드가 아닙니다">
`vpm`, `argo_watch`, `site-console`. 노드의 대부분이 CRI-O 하에서 실행되기 때문에,
Kubernetes 워크로드를 기대하는 경우 짧은 `docker-ps` 출력이 실패처럼 보일 수 있습니다.
그렇지 않습니다 — 이것이 정상적인 CE에서 실행되는 Docker 컨테이너의 전체 목록이며,
`vpm`이 존재하고 `Up` 상태인 것이 이 페이지에서 가장 중요한 항목입니다.
</Aside>

## `docker-images`

```bash
{"command":["docker-images"]}
```

```text file=../../../../_data/sitecli-docker-images.txt
```

이미지 태그는 노드가 실제로 실행 중인 플랫폼 버전을 식별하며,
[`health`](../health/)에서 보고된 소프트웨어 빌드와 비교해 볼 만합니다.

## `docker-inspect`

```bash
{"command":["docker-inspect","<container-id-or-name"]}
```

```text file=../../../../_data/sitecli-docker-inspect.txt
```

id뿐만 아니라 이름도 허용하므로 `docker-inspect vpm`이 작동하며 재시작 후에도 안정적입니다.
전체 JSON: 마운트, 환경 변수, 재시작 정책, 종료 상태를 포함합니다.

## `docker-logs`

```bash
{"command":["docker-logs","<container-id-or-name>"]}
```

```text file=../../../../_data/sitecli-docker-logs.txt
```

`docker-logs vpm`은 등록 오류를 확인하는 가장 빠른 방법입니다. 타임스탬프와 함께
재시작 전후의 동일한 정보를 확인하려면 [`journalctl`](../journalctl/)을 사용하세요.

## `docker-prune`

```bash
execcli docker-prune
```

사용하지 않는 모든 Docker 객체를 제거합니다 — 중지된 컨테이너, 사용하지 않는 네트워크,
댕글링 이미지 및 빌드 캐시.

**박스에서만 실행 가능합니다.** `docker-prune`은 디버그 API에 없으며,
[`execcli`](../../on-box/)가 필요합니다.

<Aside type="danger" title="파괴적인 명령이며 여기서는 캡처되지 않습니다">
이 명령은 상태를 삭제합니다. 수집 하네스의 거부 목록에 포함되어 있으며 실행된 적이 없으므로,
이 페이지는 출력을 보여주는 대신 어플라이언스 자체의 카탈로그 메타데이터를 기반으로 문서화합니다.

CE 관련 주의 사항: 이 노드는 **두 개**의 컨테이너 런타임을 실행합니다. `docker-prune`은
Docker 측 — `vpm`, `argo_watch`, `site-console` — 만 영향을 미치며,
[CRI-O](../crictl/) 하의 Kubernetes 워크로드에는 접근할 수 없습니다. CRI-O 측의
공간 회수는 별도의 명령인 `systemctl-start-crio-prune`을 사용하며, 이 빌드에는 없습니다.
</Aside>
