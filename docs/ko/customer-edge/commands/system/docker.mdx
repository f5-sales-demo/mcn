Docker는 플랫폼 서비스를 실행합니다. Kubernetes 워크로드는
[CRI-O](../crictl/) 하위에 있습니다.

## `docker-ps`

```bash
{"command":["docker-ps"]}
```

```text file=../../../../_data/sitecli-docker-ps.txt
```

<Aside type="tip" title="컨테이너 세 개가 전체 목록이며, 노드가 손상된 것이 아닙니다">
`vpm`, `argo_watch`, `site-console`. 노드의 대부분은 CRI-O 하위에서 실행되기 때문에,
Kubernetes 워크로드를 기대하는 경우 짧은 `docker-ps` 결과가 오류처럼 보일 수 있습니다.
그렇지 않습니다 — 이것이 정상적인 CE에서 실행되는 Docker 컨테이너의 완전한 목록이며,
`vpm`이 존재하고 `Up` 상태인 것이 이 페이지에서 가장 중요한 항목입니다.
</Aside>

## `docker-ps-a`

```bash
{"command":["docker-ps-a"]}
```

```text file=../../../../_data/sitecli-docker-ps-a.txt
```

종료된 컨테이너도 포함하므로, 계속 종료되는 `vpm`의 흔적을 여기서 확인할 수 있습니다.

## `docker-images`

```bash
{"command":["docker-images"]}
```

```text file=../../../../_data/sitecli-docker-images.txt
```

이미지 태그는 노드가 실제로 실행 중인 플랫폼 버전을 나타내며,
[`health`](../health/)에서 보고되는 소프트웨어 빌드와 비교해 볼 가치가 있습니다.

## `docker-inspect`

```bash
{"command":["docker-inspect","<container-id-or-name"]}
```

```text file=../../../../_data/sitecli-docker-inspect.txt
```

이름과 ID 모두 허용하므로 `docker-inspect vpm`은 재시작 후에도 안정적으로 동작합니다.
전체 JSON: 마운트, 환경 변수, 재시작 정책 및 종료 상태를 포함합니다.

## `docker-logs`

```bash
{"command":["docker-logs","<container-id-or-name>"]}
```

```text file=../../../../_data/sitecli-docker-logs.txt
```

`docker-logs vpm`은 등록 오류를 확인하는 가장 빠른 방법입니다. 타임스탬프와 함께
재시작 전후의 동일한 정보를 확인하려면 [`journalctl`](../journalctl/)을 사용하십시오.
