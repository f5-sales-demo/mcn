CRI-O는 Kubernetes 워크로드를 실행합니다. 플랫폼 서비스인 `vpm`, `argo_watch`,
`site-console`은 [Docker](../docker/) 컨테이너이므로 여기에는 표시되지 않습니다.

## `crictl-ps`

```bash
{"command":["crictl-ps"]}
```

```text file=../../../../_data/sitecli-crictl-ps.txt
```

실행 중인 컨테이너와 해당 파드, 이미지, 재시작 횟수를 표시합니다. `ATTEMPT` 값이 중요합니다.
재시작 횟수가 증가하고 있다면 크래시 루프 상태이며, 이 출력의 컨테이너 ID는 아래 두 명령어에서 사용됩니다.

## `crictl-ps-a`

```bash
{"command":["crictl-ps-a"]}
```

```text file=../../../../_data/sitecli-crictl-ps-a.txt
```

종료된 컨테이너도 포함하여 표시합니다. 이전에 실행 중이었지만 현재는 실행되지 않는 경우에 사용하십시오 —
종료된 항목과 해당 컨테이너 ID를 통해 실패한 실행의 로그를 확인할 수 있습니다.

## `crictl-images`

```bash
{"command":["crictl-images"]}
```

```text file=../../../../_data/sitecli-crictl-images.txt
```

이미지가 노드에 실제로 존재하는지 확인하여, 풀 실패와 스케줄링 실패를 구별할 수 있습니다.

## `crictl-inspect`

```bash
{"command":["crictl-inspect","<container-id>"]}
```

```text file=../../../../_data/sitecli-crictl-inspect.txt
```

전체 JSON 형식으로 마운트, 환경 변수, 리소스 제한, 명령줄, 종료 상태를 표시합니다.
내용이 길기 때문에 직접 읽는 것보다 쿼리를 사용하는 것을 권장합니다.

## `crictl-logs`

```bash
{"command":["crictl-logs","<container-id>"]}
```

```text file=../../../../_data/sitecli-crictl-logs.txt
```

<Aside type="note" title="컨테이너 ID는 실행마다 다릅니다">
이 캡처에 사용된 ID는 특정 샘플 실행에서 가져온 것으로, 귀하의 노드에는 존재하지 않습니다.
먼저 `crictl-ps`에서 현재 ID를 확인하십시오. 캡처 하네스는 정확히 그런 방식으로 동작합니다 —
매니페스트가 ID를 하드코딩하지 않고 캡처 시점에 첫 번째 컨테이너 ID를 동적으로 확인합니다.
</Aside>
