## `diagnosis`

<Aside type="caution" title="GLOBAL 범위 — 다른 전송 방식">
`health`와 마찬가지로 `global` 경로에 대한 `GET` 요청이며 `exec-user`를 통해서는 접근할 수 없습니다.

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/global/diagnosis"
```

</Aside>

```json file=../../../../_data/sitecli-diagnosis.txt
```

결과는 노드별로 보고되므로, 다중 노드 사이트에서는 각 노드마다 하나의 블록을 받게 됩니다.
`gateway_connectivity`와 `dns_connectivity`는 각각 핑 요약 — `dest_ip`, `sent`,
`received`, `lost` 및 왕복 시간 — 을 포함합니다.

<Aside type="danger" title="완벽하게 정상인 노드에서도 두 핑 프로브 모두 100% 손실을 보고합니다">
이 토폴로지에서는 사이트가 `ONLINE`이고 트래픽을 전달하고 있으며 `registration_status: OK`인 상태에서도
`gateway_connectivity`(대상 `10.0.1.1`)와 `dns_connectivity`(대상 `168.63.129.16`) **모두**
`sent: 5, received: 0, lost: 100`을 보고합니다 — 이 문서를 작성하는 동안 다시 확인했습니다. 하나의 응답에
두 개의 `lost: 100` 블록이 나타나는 것은 이 페이지에서 가장 놀라워 보이는 부분이지만, 이것이 정상 상태입니다.

`dns_connectivity`가 둘 중 더 오해를 불러일으키는 쪽입니다. DNS가 실제로 작동한다는 것이 명백히 입증되기
때문입니다. 동일한 응답의 `dns_query_result`에는 바로 그 리졸버에 대한 열 건의 성공적인 조회 결과인
`NOERROR`가 담겨 있습니다. 이 프로브는 ICMP 도달 가능성을 측정하는데, Azure 플랫폼 주소는 이에 응답하지
않습니다. 즉 DNS를 측정하는 것이 아닙니다.

이 두 필드는 이미 다른 문제의 증거가 있을 때, 또는 값이 변화할 때에만 신호로 취급하십시오.
</Aside>

먼저 읽어볼 만한 필드는 응답의 다른 곳에 있습니다: `registration_status`,
`curl_response`(노드가 필요로 하는 F5 엔드포인트마다 하나의 항목이며, 각각 `OK` 또는 그 외),
`dns_query_result`, `ntp_sync_status`입니다.

`resolv_conf`는 노드가 실제로 사용할 리졸버를 보여주며, [`dig`](../../network/dig/)에 시간을 쏟기 전에
예상한 값과 비교해 볼 가치가 있습니다.
