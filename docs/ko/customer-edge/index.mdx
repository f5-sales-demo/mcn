Customer Edge(CE)는 이 저장소가 Azure에 프로비저닝하는 F5 Distributed Cloud 노드입니다 —
`terraform/modules/ce-node`이며, `volterraedgeservices/volterra-node` 마켓플레이스 이미지를 기반으로 빌드됩니다.

CE는 데이터 플레인(Argo), 컨트롤 플레인(Vega), Envoy 프록시, Kubernetes 스택, 그리고 노드를 등록하고 나머지 모든 것을 관리하는 에이전트인 `vpm`을 실행합니다.

CE가 오작동할 때는 Site CLI가 핵심 도구입니다. 첫 번째 결정은 어느 접근 경로가 적용되는지 확인하는 것이며, 잘못 선택하면 노드가 고장난 것처럼 보이면서 시간을 낭비하게 됩니다.

디버그 API는 **F5 Distributed Cloud 컨트롤 플레인을 통해** 노드에 접근합니다.
이것이 두 경로를 구분해야 하는 핵심 이유입니다. API는 노드가 등록을 완료하고 `ONLINE` 상태를 보고해야만 응답할 수 있습니다.

등록에 실패한 노드 — 잘못된 cloud-init, 만료된 토큰, `register.ves.volterra.io`로의 경로 없음 — 는 정확히 진단이 필요한 상황이면서, 동시에 API가 서비스를 제공할 수 없는 상황입니다.

또한 노드는 기본적으로 SSH를 거부합니다. 포트 22는 네트워크 보안 그룹이 아닌 CE 자체에서 닫혀 있습니다:

```console
$ ssh -o ConnectTimeout=10 admin@<ce-public-ip>
ssh: connect to host <ce-public-ip> port 22: Connection refused
```

동일한 서브넷의 점프 호스트에서 VNet 내부에서도 확인되었으므로, 보안 그룹 규칙을 열어도 변경되지 않습니다.

따라서: 사이트가 `ONLINE` 상태이면 디버그 API를 사용하고, 그렇지 않으면 시리얼 콘솔이 유일한 접근 방법입니다.

<Aside type="caution" title="먼저 사이트 상태를 확인하세요">
요청 하나로 어느 경로를 사용할지 확인할 수 있습니다:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/config/namespaces/system/sites/<site>" \
  | jq -r '.spec.site_state'
```

`ONLINE`이면 디버그 API가 작동합니다. 그 외의 값이나 존재하지 않는 사이트는 시리얼 콘솔을 사용해야 합니다.
</Aside>

## 안전 규칙

아래의 모든 페이지에서 모든 명령에 적용됩니다.

- **확신이 없으면 읽기 전용으로만 사용하세요.** 명령 범위는 두 가지 권한 계층으로 나뉘며, `Exec` 계층은 노드를 변경하거나 상태 마커를 읽습니다. 이 페이지의 어떤 명령도 `Exec` 명령을 실행하지 않으며, 캡처 하네스도 마찬가지입니다.
- **명령 이름만 보고 안전하다고 가정하지 마세요.** `ip-link-set`은 조회처럼 보이지만 인터페이스를 다운시킵니다. `systemctl-restart-crio`는 라이브 데이터 플레인 아래의 컨테이너 런타임을 재시작합니다.
- **질문에 답할 수 있는 가장 좁은 범위의 명령을 사용하세요.** `health`와 `diagnosis`는 노드를 저렴하게 요약하지만, `flow-l`은 629,760개 항목의 플로우 테이블을 덤프합니다.
- **CE는 라이브 트래픽을 처리합니다.** 이것은 공유 데모 환경입니다. 디버깅 중인 사이트에서 누군가 발표하고 있다고 가정하세요.

## 여기서 문서화된 내용

이 테넌트가 실행하는 소프트웨어 빌드의 디버그 API를 통해 접근 가능한 모든 명령이 포함되어 있으며, 각 명령의 출력은 다른 곳에서 옮겨 쓴 것이 아닌 라이브 노드에서 캡처한 것입니다.

[명령 참조](./commands/)에는 모든 명령의 카테고리, 권한 계층 및 전송 방식이 나열되어 있으며, [워크플로우](./workflows/)는 실제로 문제가 발생했을 때 사용하는 순서대로 명령들을 연결합니다.

노드 내부에서만 접근 가능한 Site CLI의 구성 요소들 — `configure`, `configure-network`, `factory-reset`, `upgrade` 및 약 60개의 추가 `ExecCLI` 명령 — 은 다루지 않습니다.

이 명령들은 시리얼 콘솔 세션에서만 접근할 수 있으므로 프로그래밍 방식으로 검증할 수 없으며, 검증되지 않은 명령 구문이 바로 이 문서가 반복하지 않으려는 결함입니다.
