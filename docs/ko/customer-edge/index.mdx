Customer Edge(CE)는 이 저장소가 Azure에 프로비저닝하는 F5 Distributed Cloud 노드입니다.
`terraform/modules/ce-node`로 구성되며,
`volterraedgeservices/volterra-node` 마켓플레이스 이미지로 빌드됩니다.

데이터 플레인(Argo), 컨트롤 플레인(Vega), Envoy 프록시, Kubernetes
스택, 그리고 노드를 등록하고 모든 것을 관리하는 에이전트인 `vpm`을 실행합니다.

CE가 오작동할 때는 Site CLI가 핵심 도구입니다. 첫 번째 결정은 어떤
접근 경로가 적용되는지 파악하는 것이며, 잘못된 경로를 선택하면 노드가 고장난 것처럼 보이면서 시간을 낭비하게 됩니다.

디버그 API는 **F5 Distributed Cloud 컨트롤 플레인을 통해** 노드에 접근합니다.
이것이 구분이 중요한 이유입니다. API는 노드가 등록되어 `ONLINE` 상태를 보고한 후에만 응답할 수 있습니다.

등록에 실패한 노드 — 잘못된 cloud-init, 만료된 토큰, `register.ves.volterra.io`로의 경로 없음 — 는
바로 진단이 필요한 경우이자, API가 응답할 수 없는 경우입니다.

[SSH](./access/ssh/)는 세 번째 옵션이며, 어플라이언스의 전체 명령 표면에 접근할 수 있는 유일한 방법입니다.
디버그 API는 34개의 명령을 노출하지만 노드 자체는 훨씬 더 많은 명령을 제공합니다. 두 가지 제약이 있습니다.
`sshd`는 노드의 내부(SLI) 주소에서만 응답하므로 VNet 내부의 호스트가 필요합니다. 또한 키는
cloud-init이 첫 부팅 시 기록하는데, 사이트 객체의 `ssh_key` 필드는 작동하지 않습니다.
`vpm`이 `admin` 사용자를 건너뛰어 적용하지 않기 때문입니다. 따라서 실행 중인 노드에서 이를 활성화하면 해당 노드가 교체됩니다.

정리하면: 사이트가 `ONLINE` 상태이고 34개의 명령으로 충분하다면 디버그 API를 사용하십시오. 나머지 명령 표면이 필요하고 VNet에 접근할 수 있다면 SSH를 사용하십시오. 등록이 문제라면 시리얼 콘솔이 유일한 접근 방법입니다.

<Aside type="caution" title="사이트 상태를 먼저 확인하십시오">
요청 한 번으로 어떤 경로를 사용해야 하는지 알 수 있습니다.

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/config/namespaces/system/sites/<site>" \
  | jq -r '.spec.site_state'
```

`ONLINE`이면 디버그 API가 작동합니다. 그 외의 상태이거나 사이트가
존재하지 않는 경우에는 시리얼 콘솔을 사용하십시오.
</Aside>

## 안전 규칙

아래의 모든 페이지에 있는 모든 명령에 적용됩니다.

- **확실하지 않으면 읽기 전용으로 사용하십시오.** 명령 표면은 두 가지
  권한 계층으로 나뉘며, `Exec` 계층은 노드를 변경하거나 상태 마커를 읽습니다.
  이 페이지들에서는 `Exec` 명령을 실행하지 않으며, 캡처 하네스도 마찬가지입니다.
- **이름만 보고 명령이 안전하다고 가정하지 마십시오.** `ip-link-set`은
  조회처럼 보이지만 인터페이스를 다운시킵니다. `systemctl-restart-crio`는
  실행 중인 데이터 플레인 아래의 컨테이너 런타임을 재시작합니다.
- **질문에 답할 수 있는 가장 좁은 명령을 선택하십시오.** `health`와
  `diagnosis`는 노드를 저렴하게 요약합니다. `flow-l`은 629,760개 항목의 플로우
  테이블을 덤프합니다.
- **CE는 실시간 트래픽을 처리합니다.** 이는 공유 데모 환경입니다. 디버깅 중인 사이트에서 누군가
  발표하고 있다고 가정하십시오.

## 이 문서에서 다루는 내용

이 테넌트가 실행하는 소프트웨어 빌드에서 디버그 API를 통해 접근 가능한 모든 명령을,
다른 곳에서 필사한 것이 아닌 실제 노드에서 캡처한 출력과 함께 설명합니다.

[명령 참조](./commands/)는 모든 명령을 카테고리, 권한 계층, 전송 방식과 함께 나열하며,
[워크플로](./workflows/)는 실제로 문제가 발생했을 때 사용하는 순서로 이들을 연결합니다.

노드 내부에서만 접근 가능한 Site CLI 부분 — `configure`, `configure-network`,
`factory-reset`, `upgrade` 및 약 60개의 추가 `ExecCLI` 명령 — 은 다루지 않습니다.

이 명령들은 시리얼 콘솔 세션에서만 접근할 수 있으므로, 프로그래밍 방식으로 검증할 수 없습니다.
검증되지 않은 명령 구문은 바로 이 문서가 반복을 피하고자 하는 결함입니다.
