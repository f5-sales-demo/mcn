Customer Edge(CE)는 이 리포지터리가 Azure에 프로비저닝하는 F5 Distributed Cloud 노드입니다 —
`terraform/modules/ce-node`, `volterraedgeservices/volterra-node` 마켓플레이스 이미지로
빌드됩니다.

여기에서 데이터 플레인(Argo), 컨트롤 플레인(Vega), Envoy 프록시, Kubernetes
스택, 그리고 노드를 등록하고 노드의 나머지 모든 것을 관리하는 에이전트인 `vpm`이 실행됩니다.

CE에 문제가 발생하면 Site CLI가 진단 도구입니다. 첫 번째 결정은 어떤
접근 경로가 해당되는지이며, 이를 잘못 판단하면 노드가 고장난 것처럼 보이는
방식으로 시간을 낭비하게 됩니다.

## 두 가지 접근 경로, 그리고 이들은 서로 대체할 수 없습니다

디버그 API는 **F5 Distributed Cloud 컨트롤 플레인을 통해** 노드에 도달합니다.
그것이 바로 이 구분이 중요한 이유입니다. API는 노드가 등록을 완료하고
`ONLINE`을 보고한 이후에만 응답할 수 있습니다.

등록에 실패한 노드 — 잘못된 cloud-init, 만료된 토큰,
`register.ves.volterra.io`로의 경로 부재 — 는 바로 진단이 필요한 경우이면서,
동시에 API가 지원할 수 없는 경우입니다.

SSH는 세 번째 선택지가 아닙니다. 노드에서 `sshd`가 실행되며 내부(SLI)
주소로 응답하지만, `admin` 계정은 인증할 수 없습니다. `vpm`이 해당 사용자를 건너뛰기 때문에
사이트 객체에 구성한 `ssh_key`가 결코 적용되지 않습니다. 어떤 보안 그룹 규칙으로도
이를 바꿀 수 없습니다. 그 증거는 [SSH](./access/ssh/) 페이지에 있으며, 그곳의
모든 증상이 방화벽 또는 자격 증명 오류처럼 읽히기 때문에 이 페이지가 존재합니다.

따라서: 사이트가 `ONLINE`이면 디버그 API를 사용하십시오. 그렇지 않다면 시리얼 콘솔이
유일한 진입 방법입니다.

<Aside type="caution" title="먼저 사이트 상태를 확인하십시오">
하나의 요청으로 어느 경로에 있는지 알 수 있습니다:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/config/namespaces/system/sites/<site>" \
  | jq -r '.spec.site_state'
```

`ONLINE`은 디버그 API가 작동한다는 의미입니다. 그 외의 값 — 또는 존재하지
않는 사이트 — 는 시리얼 콘솔을 의미합니다.
</Aside>

## 안전 규칙

아래 모든 페이지의 모든 명령에 적용됩니다.

- **확신이 없다면 읽기 전용으로.** 명령 표면은 두 가지
  권한 계층으로 나뉘며, `Exec` 계층은 노드를 변경하거나 상태
  마커를 읽습니다. 이 페이지들에서는 어떤 `Exec` 명령도 실행하지 않으며,
  캡처 하네스도 그렇습니다.
- **명령 이름만으로 안전하다고 절대 가정하지 마십시오.** `ip-link-set`은 조회처럼
  읽히지만 인터페이스를 다운시킵니다. `systemctl-restart-crio`는 라이브 데이터 플레인 아래에서
  컨테이너 런타임을 재시작합니다.
- **질문에 답하는 가장 좁은 범위의 명령을 우선하십시오.** `health`와
  `diagnosis`는 저렴하게 노드를 요약합니다. `flow-l`은 629,760개 항목의 플로우
  테이블을 덤프합니다.
- **CE는 실제 트래픽을 처리합니다.** 이들은 공유된 데모 환경입니다. 디버깅 중인
  사이트에서 누군가 발표하고 있다고 가정하십시오.

## 여기에 문서화된 내용

이 테넌트가 실행하는 소프트웨어 빌드에서 디버그 API를 통해 접근할 수 있는 모든 명령이며,
각각의 출력은 다른 곳에서 전사한 것이 아니라 라이브 노드에서 캡처한 것입니다.

[명령 참조](./commands/)는 모든 명령을 카테고리, 권한
계층 및 전송 방식과 함께 나열합니다. [워크플로](./workflows/)는 문제가 발생했을 때
실제로 사용하는 순서로 명령을 연결합니다.

Site CLI의 온박스 전용 부분 — `configure`, `configure-network`,
`factory-reset`, `upgrade` 및 약 60개의 추가 `ExecCLI` 명령 — 은 다루지
않습니다.

이들은 시리얼 콘솔 세션에서만 접근할 수 있으므로 그에 관한 어떤 것도
프로그래밍 방식으로 검증할 수 없으며, 검증되지 않은 명령 구문은 이
문서가 반복을 피하고자 존재하는 바로 그 결함입니다.
