Customer Edge(CE)는 이 리포지토리가 Azure에 프로비저닝하는 F5 Distributed Cloud 노드입니다 —
`terraform/modules/ce-node`이며, `volterraedgeservices/volterra-node` 마켓플레이스
이미지로부터 빌드됩니다.

이 노드는 데이터 플레인(Argo), 컨트롤 플레인(Vega), Envoy 프록시, Kubernetes
스택, 그리고 노드를 등록하고 노드상의 나머지 모든 것을 관리하는 에이전트인 `vpm`을 실행합니다.

CE에 문제가 발생했을 때 사용하는 도구는 Site CLI입니다. 첫 번째 결정 사항은 어떤
액세스 경로가 적용되는지이며, 이를 잘못 선택하면 노드가 고장난 것처럼 보이는 방식으로
시간을 낭비하게 됩니다.

## 두 가지 액세스 경로, 서로 대체할 수 없습니다

디버그 API는 **F5 Distributed Cloud 컨트롤 플레인을 통해** 노드에 접근합니다.
이것이 바로 이 구분이 중요한 이유입니다. API는 노드가 등록을 완료하고 `ONLINE`으로
보고된 후에만 응답할 수 있습니다.

등록에 실패한 노드 — 잘못된 cloud-init, 만료된 토큰,
`register.ves.volterra.io`로의 경로 부재 — 는 정확히 진단이 필요한 경우이면서,
정확히 API가 처리할 수 없는 경우입니다.

[SSH](./access/ssh/)는 세 번째 옵션이며, 어플라이언스의 전체 명령 표면에 도달할 수 있는
유일한 방법입니다 — 디버그 API는 34개의 명령을 노출하지만 노드 자체는 훨씬 더 많은 명령을
제공합니다. 두 가지 제약이 있습니다. `sshd`는 노드의 내부(SLI) 주소에서만 응답하므로
VNet 내부의 호스트가 필요합니다. 그리고 키는 첫 부팅 시 cloud-init에 의해 작성되는데,
사이트 객체의 `ssh_key` 필드는 작동하지 않기 때문입니다 — `vpm`은 `admin` 사용자를 건너뛰고
이를 절대 적용하지 않습니다. 따라서 실행 중인 노드에서 이를 활성화하려면 노드를 교체해야 합니다.

따라서: 사이트가 `ONLINE`이고 34개의 명령으로 충분하다면 디버그 API를 사용하십시오. 나머지
명령 표면이 필요하고 VNet에 접근할 수 있다면 SSH를 사용하십시오. 등록 자체가 문제라면
시리얼 콘솔이 유일한 진입 방법입니다.

<Aside type="caution" title="먼저 사이트 상태를 확인하십시오">
한 번의 요청으로 어떤 경로에 있는지 알 수 있습니다:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/config/namespaces/system/sites/<site>" \
  | jq -r '.spec.site_state'
```

`ONLINE`이면 디버그 API가 작동합니다. 그 외의 값 — 또는 존재하지 않는 사이트 — 는
시리얼 콘솔을 의미합니다.
</Aside>

## 안전 규칙

아래 모든 페이지의 모든 명령에 적용됩니다.

- **확신이 없다면 읽기 전용으로.** 명령 표면은 두 가지 권한 계층으로 나뉘며,
  `Exec` 계층은 노드를 변경하거나 상태 마커를 읽습니다. 이 페이지들에서는 어떤
  `Exec` 명령도 실행하지 않으며, 캡처 하네스 역시 실행하지 않습니다.
- **명령 이름만으로 안전하다고 가정하지 마십시오.** `ip-link-set`은 조회처럼
  읽히지만 인터페이스를 다운시킵니다. `systemctl-restart-crio`는 라이브 데이터
  플레인 아래에서 컨테이너 런타임을 재시작합니다.
- **질문에 답하는 가장 좁은 범위의 명령을 선택하십시오.** `health`와
  `diagnosis`는 노드를 저렴하게 요약합니다. `flow-l`은 629,760개 항목의 플로우
  테이블을 덤프합니다.
- **CE는 라이브 트래픽을 처리합니다.** 이들은 공유 데모 환경입니다. 디버깅 중인
  사이트에서 누군가 발표하고 있다고 가정하십시오.

## 여기에 문서화된 내용

이 테넌트가 실행하는 소프트웨어 빌드에서 디버그 API를 통해 도달할 수 있는 모든 명령이며,
각 명령의 출력은 다른 곳에서 옮겨온 것이 아니라 라이브 노드에서 캡처한 것입니다.

[명령 참조](./commands/)는 모든 명령을 카테고리, 권한 계층, 전송 방식과 함께
나열합니다. [워크플로](./workflows/)는 문제가 발생했을 때 실제로 사용하는 순서대로
이들을 연결합니다.

Site CLI의 온박스 전용 부분 — `configure`, `configure-network`,
`factory-reset`, `upgrade` 및 대략 60개의 추가 `ExecCLI` 명령 — 은 다루지 않습니다.
아래 모든 페이지처럼 라이브 노드에서 그 출력을 캡처하지 않았기 때문입니다.

그러나 이제 더 이상 접근 불가능한 것은 아닙니다. `scripts/sitecli_ssh_harvest.py`는
[SSH](./access/ssh/)를 통해 어플라이언스 자체의 자동 완성 메뉴를 구동하고 각 명령에 대해
어플라이언스가 제공하는 설명을 기록하므로, 명령 표면을 추측하는 대신 측정할 수 있습니다.
이 스크립트의 실행은 기본적으로 거부됩니다 — 모든 것을 열거하되 허용 목록에 있는 것만
실행합니다 — 검증되지 않은 명령 구문, 그리고 검증되지 않은 명령 *효과*가 바로 이 문서가
반복을 피하고자 존재하는 결함이기 때문입니다.
