2026-07-28에 이 배포의 CE 한 대에서 캡처했습니다. `sitecli/capture-manifest.json`은
어느 노드였는지를 기록하며, `scripts/capture-sitecli.sh --check`는 실제 CE를 대상으로
명령 표면을 다시 검증합니다.

`vpm/debug` API는 등록된 노드에서 Site CLI 명령을 실행하고 그 출력을 반환합니다.
아래 내용은 모두 실제 노드를 대상으로 확인한 것이며, 어느 것도 업스트림에 공개되어
있지 않습니다.

## 명령 카탈로그는 자기 기술적입니다

`command` 키를 **생략한** 채 `exec-user`에 POST하여 노드가 무엇을 지원하는지
문의하십시오:

```bash
curl -sS -X POST \
  -H "Authorization: APIToken $XCSH_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"namespace":"system","site":"<site>","node":"<node>"}' \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/<node>/exec-user" \
  | jq -r .output | jq .
```

응답은 명령 이름을 키로 하는 JSON 객체입니다:

```json
{
  "crictl-inspect": ["System Troubleshooting", "ExecUser", " container-id"],
  "diagnosis":      ["System Troubleshooting", "ExecUser", "no argument needed", "GLOBAL"],
  "ip-link-set":    ["Network Troubleshooting", "Exec", " (<device>||<group>) (up||down)"]
}
```

각 항목은 `[category, tier, exampleArgument?, scope?]`이며, 이 필드들은 문서가 아니라
해당 명령을 어떻게 호출해야 하는지를 결정합니다.

<Aside type="caution" title="키를 생략하십시오. 잘못된 값을 보내지 마십시오">
디스커버리는 `command`를 빼는 방식으로 동작합니다. 대신 알 수 없는 값을 보내면
카탈로그가 아니라 오류가 반환됩니다:

```json
{"code":3,"details":[],"message":"exec command failed: command not supported"}
```

이 메시지는 *실제* 명령을 잘못된 엔드포인트로 보냈을 때에도 나타나므로,
"이 명령은 존재하지 않는다"로 잘못 읽기 쉽습니다.
</Aside>

## 카탈로그 항목에 따라 선택되는 세 가지 전송 방식

| 조건 | 메서드와 경로 | 본문 | 반환값 |
| --- | --- | --- | --- |
| `scope`가 `GLOBAL` | `GET .../vpm/debug/global/<cmd>` | 없음 | JSON |
| `tier`가 `ExecUser` | `POST .../vpm/debug/<node>/exec-user` | `command` 배열 | 텍스트 |
| `tier`가 `Exec` | `POST .../vpm/debug/<node>/exec` | `command` 배열 | 텍스트 |

### `ExecUser` — 읽기 전용 계층 <Badge text="31 commands" variant="note" />

일반적인 경우입니다. 명령과 그 인수를 배열로, 명령 이름을 먼저 두어 전달하십시오:

```bash
curl -sS -X POST \
  -H "Authorization: APIToken $XCSH_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"namespace":"system","site":"<site>","node":"<node>","command":["crictl-ps"]}' \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/<node>/exec-user"
```

```json
{ "return_code": 0, "output": "CONTAINER    IMAGE    CREATED    STATE ..." }
```

인수는 하나의 문자열이 아니라 개별 배열 요소입니다:

```json
{ "command": ["journalctl", "-u", "vpm", "-n", "200"] }
```

### `GLOBAL` — 사이트 전체 범위이며, 전송 방식이 완전히 다릅니다 <Badge text="2 commands" variant="tip" />

`health`와 `diagnosis`가 유일한 두 가지입니다. 이들은 `global` 경로에 대한 `GET`
요청이며, 인수를 받지 않고, 터미널 텍스트가 아닌 구조화된 JSON을 반환합니다.

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/global/health" | jq .
```

<Aside type="danger" title="GLOBAL 명령은 exec-user를 통해 접근할 수 없습니다">
이것이 가장 많은 시간을 낭비하게 만드는 함정입니다. `health` 또는 `diagnosis`를
`exec-user`로 보내면 `command not supported`가 반환되는데, 이는 해당 명령이 노드에
존재하지 않는 것처럼 읽힙니다 — 실제로는 존재하며 전송 방식을 잘못 사용한 것입니다.

```bash
# Wrong. Returns: exec command failed: command not supported
-d '{"namespace":"system","site":"…","node":"…","command":["health"]}'   # POST exec-user

# Right.
GET .../vpm/debug/global/health
```

</Aside>

### `Exec` — 권한이 필요한 계층 <Badge text="1 command on this build" variant="danger" />

별도의 엔드포인트이며, 계층은 권고가 아니라 강제됩니다: `exec`는 `ExecUser` 명령을
동일한 `command not supported` 메시지로 거부합니다. 모든 구성원은 노드를 변경하거나
상태 마커를 읽습니다.

이 테넌트가 실행하는 빌드에서 이 계층에는 `ip-link-set`만 포함되어 있습니다. 더 최신
빌드에서는 `systemctl-restart-NetworkManager`, `systemctl-restart-crio`,
`systemctl-restart-kubelet`, `systemctl-start-crio-prune` 및 세 개의
`marker-exists-*` 명령이 추가됩니다.

<Aside type="danger" title="여기서는 Exec 명령을 실행하지 않습니다">
캡처 하니스는 이 계층을 거부하며, 하드코딩된 목록이 아니라 실제 카탈로그에서 계층을
읽습니다 — 따라서 향후 빌드에서 어떤 명령이 `Exec`로 승격되어도 코드를 수정하지 않고
그대로 반영됩니다. 실행은 반드시 의도적으로, 중단을 감수할 수 있는 노드에서만
수행하십시오.
</Aside>

## 사이트와 노드 이름 찾기

노드 이름은 Azure VM 이름이며, `list-service`는 해당 노드에서 실행 중인 서비스와 함께
이를 확인하는 간단한 방법입니다:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/global/list-service" \
  | jq -r '[.service[].node] | unique'
```

```json
["", "f5-xc-ce-vm-01"]
```

일부 서비스는 빈 노드 이름을 보고하므로, 이 목록의 빈 문자열은 두 번째 노드가 아니라
응답의 부산물입니다. `list-service`는 34개 명령 카탈로그에도 포함되어 있지 않습니다:
이는 카탈로그가 광고하지 않는 `global` 엔드포인트이며, 그래서
[명령 참조](../../commands/)가 아니라 여기에 문서화되어 있습니다.

## 이 리포지토리의 캡처 재현하기

모든 명령 페이지에는 위의 세 가지 규칙을 모두 구현한 `scripts/capture-sitecli.sh`가
캡처한 출력이 포함되어 있습니다.

<Steps>

1. 테넌트를 지정하십시오. 이 스크립트는 `XCSH_API_URL`과 `XCSH_API_TOKEN`을 읽거나,
   활성 `xcsh` 컨텍스트로 대체합니다.

2. 카탈로그를 새로 고치고 문서 아래의 노드가 변경되지 않았는지 확인하십시오:

   ```bash
   bash scripts/capture-sitecli.sh --check
   ```

   이는 커밋된 카탈로그와 소프트웨어 빌드만 비교합니다. 빌드 변경은 추가되거나 제거된
   명령과 별도로 보고합니다.

3. 새로운 증거가 필요할 때 다시 캡처하십시오:

   ```bash
   bash scripts/capture-sitecli.sh
   ```

</Steps>

<Aside type="note" title="캡처는 증거이지, 재현 가능한 산출물이 아닙니다">
카운터, 업타임, 컨테이너 수명은 실행마다 변하므로, 다시 캡처하면 항상 diff가
발생합니다. 카탈로그는 안정적인 계약이며 노드가 변경되지 않았다면 실행 간에 바이트
단위로 동일합니다. 이것이 `--check`가 비교하는 대상입니다. 긴 출력은 잘리고 명시적인
마커로 끝나므로, 절단된 표가 완전한 것처럼 표시되는 일은 없습니다.
</Aside>

<Aside type="danger" title="고객 노드에서 캡처하기: 편집(redaction) 프로필을 확인하십시오">
명령 출력은 인프라 정체성 — 내부 주소 지정, MAC 주소, AS 번호, 호스트 이름 — 을 담고
있으며, 고객에게는 이것이 조직을 식별하는 정보입니다.

따라서 스크럽 필터는 기본적으로 이 모든 것을 제거하는 **strict** 프로필을 사용합니다.
이 리포지토리는 `sitecli/capture-manifest.json`에서 `lab`을 선언하여 그러한 세부 정보를
유지하는데, 이는 이 캡처들이 F5 소유의 데모 인프라에서 나온 것이기 때문에 여기서만
올바릅니다.

**그 설정을 고객 캡처에 그대로 가져가지 마십시오.** 토큰, 개인 키, 테넌트 식별자,
객체 UUID, 이메일 주소, 홈 디렉터리 경로는 두 프로필 모두에서 제거됩니다.

한 가지 알아둘 만한 제약이 있습니다: BGP 이웃 테이블은 AS를 패턴을 고정할 레이블 없이
단순한 열로 출력하므로, ASN은 사설 범위와의 값 비교로 매칭됩니다. 거기에 있는
**공개** ASN은 strict에서도 살아남으므로, 게시하기 전에 `show-ip-bgp*` 출력을 수동으로
검토해야 합니다.
</Aside>
