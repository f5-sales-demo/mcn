`vpm/debug` API는 등록된 노드에서 Site CLI 명령을 실행하고 그 출력을 반환합니다.
아래 내용은 모두 실제 운영 중인 노드를 대상으로 확인한 것이며, 어느 것도 상위
문서에 공개되어 있지 않습니다.

## 명령 카탈로그는 자기 서술적입니다

노드가 무엇을 지원하는지 확인하려면 `command` 키를 **생략한** 상태로
`exec-user`에 POST 요청을 보냅니다:

```bash
curl -sS -X POST \
  -H "Authorization: APIToken $XCSH_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"namespace":"system","site":"<site>","node":"<node>"}' \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/<node>/exec-user" \
  | jq -r .output | jq .
```

응답은 명령 이름을 키로 하는 JSON 객체입니다:

```json
{
  "crictl-inspect": ["System Troubleshooting", "ExecUser", " container-id"],
  "diagnosis":      ["System Troubleshooting", "ExecUser", "no argument needed", "GLOBAL"],
  "ip-link-set":    ["Network Troubleshooting", "Exec", " (<device>||<group>) (up||down)"]
}
```

각 항목은 `[category, tier, exampleArgument?, scope?]` 형식이며, 이 필드들은
단순한 문서가 아니라 명령을 어떻게 호출해야 하는지를 결정합니다.

<Aside type="caution" title="키를 생략하십시오. 잘못된 값을 보내지 마십시오">
디스커버리는 `command`를 생략함으로써 동작합니다. 대신 알 수 없는 값을 보내면
카탈로그가 아니라 오류가 반환됩니다:

```json
{"code":3,"details":[],"message":"exec command failed: command not supported"}
```

이 메시지는 *실제로 존재하는* 명령을 잘못된 엔드포인트로 보냈을 때에도 반환되므로,
"이 명령은 존재하지 않는다"로 잘못 해석하기 쉽습니다.
</Aside>

## 카탈로그 항목이 결정하는 세 가지 전송 방식

| 조건 | 메서드 및 경로 | 본문 | 반환값 |
| --- | --- | --- | --- |
| `scope`가 `GLOBAL` | `GET .../vpm/debug/global/<cmd>` | 없음 | JSON |
| `tier`가 `ExecUser` | `POST .../vpm/debug/<node>/exec-user` | `command` 배열 | 텍스트 |
| `tier`가 `Exec` | `POST .../vpm/debug/<node>/exec` | `command` 배열 | 텍스트 |

### `ExecUser` — 읽기 전용 계층 <Badge text="31 commands" variant="note" />

가장 일반적인 경우입니다. 명령과 그 인수를 배열로 전달하며, 명령 이름을 먼저
넣습니다:

```bash
curl -sS -X POST \
  -H "Authorization: APIToken $XCSH_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"namespace":"system","site":"<site>","node":"<node>","command":["crictl-ps"]}' \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/<node>/exec-user"
```

```json
{ "return_code": 0, "output": "CONTAINER    IMAGE    CREATED    STATE ..." }
```

인수는 하나의 문자열이 아니라 별개의 배열 요소로 전달합니다:

```json
{ "command": ["journalctl", "-u", "vpm", "-n", "200"] }
```

### `GLOBAL` — 사이트 전체를 대상으로 하며, 전송 방식이 완전히 다릅니다 <Badge text="2 commands" variant="tip" />

`health`와 `diagnosis`가 유일한 두 가지입니다. 이들은 `global` 경로에 대한 `GET`
요청이며, 인수를 받지 않고 터미널 텍스트가 아닌 구조화된 JSON을 반환합니다.

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/global/health" | jq .
```

<Aside type="danger" title="GLOBAL 명령은 exec-user로 접근할 수 없습니다">
가장 많은 시간을 낭비하게 되는 함정입니다. `health` 또는 `diagnosis`를
`exec-user`로 보내면 `command not supported`가 반환되는데, 이는 해당 명령이
노드에 존재하지 않는 것처럼 읽힙니다 — 실제로는 명령이 존재하지만 잘못된 전송
방식을 사용한 것입니다.

```bash
# Wrong. Returns: exec command failed: command not supported
-d '{"namespace":"system","site":"…","node":"…","command":["health"]}'   # POST exec-user

# Right.
GET .../vpm/debug/global/health
```

</Aside>

### `Exec` — 권한이 필요한 계층 <Badge text="1 command on this build" variant="danger" />

별도의 엔드포인트를 사용하며, 계층 구분은 권고가 아니라 강제됩니다: `exec`는
`ExecUser` 명령을 동일한 `command not supported` 메시지로 거부합니다. 이 계층의
모든 명령은 노드를 변경하거나 상태 마커를 읽습니다.

이 테넌트가 실행 중인 빌드에서 해당 계층에는 `ip-link-set`만 포함되어 있습니다.
더 새로운 빌드에서는 `systemctl-restart-NetworkManager`, `systemctl-restart-crio`,
`systemctl-restart-kubelet`, `systemctl-start-crio-prune` 및 세 개의
`marker-exists-*` 명령이 추가됩니다.

<Aside type="danger" title="여기서는 Exec 명령을 실행하지 않습니다">
캡처 하니스는 이 계층을 거부하며, 하드코딩된 목록이 아니라 실제 카탈로그에서
계층 정보를 읽습니다 — 따라서 향후 빌드에서 어떤 명령이 `Exec`로 승격되어도
코드를 수정하지 않고 그대로 반영됩니다. 이 계층의 명령은 중단을 감수할 수 있는
노드에서 의도적으로만 실행하십시오.
</Aside>

## 사이트 및 노드 이름 찾기

노드 이름은 Azure VM 이름이며, `list-service`는 해당 노드에서 실행 중인 서비스와
함께 이를 확인하는 간편한 방법입니다:

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/global/list-service" \
  | jq -r '[.service[].node] | unique'
```

```json
["", "f5-xc-ce-vm-01"]
```

일부 서비스는 빈 노드 이름을 보고하므로, 이 목록의 빈 문자열은 두 번째 노드가
아니라 응답 자체의 부산물입니다. `list-service`는 34개 명령 카탈로그에도
포함되지 않습니다: 카탈로그가 공개하지 않는 `global` 엔드포인트이며, 그래서
[명령 참조](../../commands/)가 아니라 여기에 문서화되어 있습니다.

## 이 리포지토리의 캡처 재현하기

모든 명령 페이지에는 `scripts/capture-sitecli.sh`로 캡처한 출력이 포함되어
있으며, 이 스크립트는 위의 세 가지 규칙을 모두 구현합니다.

<Steps>

1. 테넌트를 지정합니다. `XCSH_API_URL`과 `XCSH_API_TOKEN`을 읽거나, 활성
   `xcsh` 컨텍스트로 대체합니다.

2. 카탈로그를 갱신하고 문서 아래에서 노드가 변경되지 않았는지 확인합니다:

   ```bash
   bash scripts/capture-sitecli.sh --check
   ```

   이는 커밋된 카탈로그와 소프트웨어 빌드만을 비교합니다. 빌드 변경은 명령 추가
   또는 제거와는 별도로 보고됩니다.

3. 새로운 근거 자료가 필요할 때 다시 캡처합니다:

   ```bash
   bash scripts/capture-sitecli.sh
   ```

</Steps>

<Aside type="note" title="캡처는 근거 자료이며, 재현 가능한 산출물이 아닙니다">
카운터, 가동 시간, 컨테이너 생성 경과 시간은 실행마다 변하므로 재캡처하면 항상
차이가 발생합니다. 카탈로그는 안정적인 계약이며 노드가 변경되지 않았다면 실행
간에 바이트 단위로 동일합니다. `--check`가 비교하는 대상이 바로 이것입니다. 긴
출력은 잘리며 명시적인 마커로 끝나므로, 잘린 표가 완전한 것처럼 표시되는 일은
없습니다.
</Aside>

<Aside type="danger" title="고객 노드에서 캡처할 때: 삭제 프로필을 확인하십시오">
명령 출력에는 인프라 식별 정보 — 내부 주소 지정, MAC 주소, AS 번호, 호스트 이름
— 가 포함되며, 고객의 경우 이는 해당 조직을 식별할 수 있는 정보입니다.

따라서 스크럽 필터는 이 모든 정보를 제거하는 **strict** 프로필을 기본값으로
사용합니다. 이 리포지토리는 `sitecli/capture-manifest.json`에서 `lab`을
선언하여 그러한 세부 정보를 유지하는데, 이는 이 캡처들이 F5 소유의 데모
인프라에서 나왔기 때문에만 올바른 설정입니다.

**이 설정을 고객 캡처에 그대로 적용하지 마십시오.** 토큰, 개인 키, 테넌트
식별자, 객체 UUID, 이메일 주소, 홈 디렉터리 경로는 두 프로필 모두에서
제거됩니다.

알아둘 만한 제한이 하나 있습니다: BGP 네이버 테이블은 패턴을 고정할 라벨 없이
AS를 단순한 열로 출력하므로, ASN은 사설 범위와 값으로 대조하여 일치시킵니다.
그곳에 있는 **공개** ASN은 strict 프로필에서도 살아남으므로, 공개 전에
`show-ip-bgp*` 출력을 수동으로 검토해야 합니다.
</Aside>
