SSH는 어플라이언스의 `admin` 계정에 접속하며, 이 계정의 로그인 셸은 Site CLI
(`/opt/bin/vpmu`)입니다. 이것이 **온박스 명령 전체 영역**에 도달하는 유일한 경로입니다 —
[debug API](../debug-api/)는 34개의 명령을 노출하지만, 어플라이언스 자체는 그 API에 전혀
없는 훨씬 더 많은 명령을 제공합니다.

```bash
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<operator-vm> admin@10.0.3.5
```

이 명령줄의 모든 부분이 필수적이며, 다음 세 개의 섹션에서 각 부분이 어떤 실패를
방지하는지 설명합니다.

<Aside type="caution" title="부트스트랩 전용 — 기존 CE는 재생성 없이는 SSH를 얻을 수 없습니다">
cloud-init `write_files`는 **첫 부팅 시 한 번만** 실행됩니다. 그 이후에는 노드에
`/etc/cloud/cloud-init.disabled` 마커가 존재하여 cloud-init이 다시 실행되지 않습니다.

따라서 실행 중인 CE에 대해 인플레이스 경로는 없습니다. Azure에서 `custom_data`는 교체
전용이므로, 기존 배포에 이를 적용하면 **모든 CE VM이 교체됩니다**. 이미 가동 중인 노드에
운영자 SSH를 부여하는 것은 구성 변경이 아니라 재구축이며 — 다음 경고가 그 재구축에
현재 드는 비용입니다.
</Aside>

<Aside type="danger" title="CE VM 교체는 등록을 막아버리고, 플릿이 다운된 상태에서도 terraform plan은 'No changes'를 보고합니다">
이 페이지에서 가장 무거운 내용입니다. 변경을 계획한 후가 아니라 그 전에
[issue 674](https://github.com/f5-sales-demo/mcn/issues/674)를 읽으십시오.

오래된 등록이 고유한 `(tenant, cluster_name, hostname)` 인덱스를 점유하므로, 교체된
노드의 등록은 `UniqueSecondaryIndexViolationError`로 거부되고 무한히 재시도합니다. 등록을
삭제하는 것만으로는 충분하지 않습니다. 남아 있는 `StatusObject`가 워크로드 요청에 대해
`500`을 반환하며, 그 시점에는 각 노드가 삭제한 등록에 고정된 `registration-obj.yml`을
이미 유지하고 있으므로 자체 복구 없이 `404`를 반복합니다.

복구를 위해서는 등록을 삭제하고, 사이트 객체를 다시 생성하고, **VM을 두 번째로 교체한**
다음 승인을 적용해야 했습니다 — `custom_data` 변경 하나를 흡수하기 위해 두 번의 전체
재구축이 필요했습니다.

이 모든 과정 내내 `terraform plan`은 **"No changes"**를 보고했습니다. Terraform 관점에서는
원하는 상태에 도달했기 때문입니다. 플릿은 다운되었고 plan은 깔끔했습니다. 이 변경의
흡수를 일상적인 apply로 취급하지 마십시오.
</Aside>

## 왜 API가 아니라 cloud-init이 키를 기록하는가

사이트 객체의 `admin_user_credentials.ssh_key`는 정확히 이 용도의 필드처럼 보입니다.
수락되고, 읽기 재확인에도 남아 있지만, 아무것도 구성하지 않습니다. `vpm`이 노드의 로컬
사용자를 소유하며 이 사용자만은 건드리지 않겠다고 거부합니다 — 노드 자체 로그에서, 한 번의
부팅 동안 세 차례:

```text
vpm  users.go:165: Won't do any change for user admin (internal skip)
```

나머지 모든 것이 그 한 줄에서 따라옵니다. `/var/home/admin/.ssh`는 사이트가 `ONLINE`에
도달하기 전이나 후에나 결코 존재하지 않습니다. `admin`의 shadow 마지막 변경 날짜는 이미지
빌드 날짜에 머물러 있는 반면 `vesbkp`와 `vesopcon`은 현재 날짜를 표시하는데, `vpm`이 그
두 계정만 설정하고 `admin`은 건너뛰었기 때문입니다. 그리고 `vpm`은 어느 시점에도 `ssh_key`나
`authorized_keys`에 관해 아무것도 기록하지 않습니다.

따라서 이 파일은 `vpm` 외부에서 기록되어야 합니다. `admin`은 노드 이미지에 내장된 uid
2202이므로 cloud-init이 실행되기 전에 이미 존재하며, `owner: admin:admin`은 기록 시점에
확인됩니다 — `runcmd`도, 소유권 보정도 필요 없습니다:

```yaml
- path: /var/home/admin/.ssh/authorized_keys
  permissions: "0600"
  owner: admin:admin
  content: |
    ${ssh_public_key}
```

`sshd`는 언제나 준비되어 있었습니다. `sshd -T`는 `pubkeyauthentication yes`를 보고하며,
노드에 함께 제공되는 두 `sshd_config` 파일 모두에서 `admin`이 `AllowUsers`에 나타납니다.
활성화할 것은 애초에 없었고 — 빠진 파일 하나만 있었습니다.

<Aside type="danger" title="admin_user_credentials를 다시 추가하지 말고, sshd_config를 편집하지 마십시오">
`admin_user_credentials`는 `terraform/modules/xc-site`에 연결되었다가 이 증거가 수집된 후
되돌려졌습니다 (#660, PR #663). 채워지기를 기다리는 공백이 아닙니다.

`sshd_config`는 등록 과정에서 교체되므로, 이에 대한 편집은 가장 곤란한 시점에 폐기됩니다.
</Aside>

## 왜 하나의 주소에서만 응답하는가

`sshd`는 `0.0.0.0:22`에 바인딩하지만, 호스트 네트워크 스택에 올라와 있는 것은 **내부(SLI)**
주소뿐입니다. eth0은 `a-i-eth0`으로 이름이 변경되고 호스트 IP를 갖지 않습니다 — Argo 데이터
플레인이 그 인터페이스를 소유합니다 — 반면 eth1과 eth2는 호스트 스택에 남아 있으며, 거기서
`sshd`가 수신 대기합니다.

VNet 내부의 VM에서 프로브한 결과:

```text
10.0.1.4     timed out             CE mgmt/SLO  (eth0)
10.0.2.4     timed out             CE external  (eth1)
10.0.3.5     OPEN                  CE internal/SLI
10.0.3.6     OPEN
10.0.3.7     OPEN
```

따라서 여러분이 노드를 식별하는 데 사용하는 주소에 대한 프로브는 차단된 보안 그룹이
반환하는 것과 정확히 동일한 결과를 반환합니다. 아무것도 차단하고 있지 않으며, 그 주소에는
리스너가 없습니다.

CE 공용 주소에도 22번 포트의 리스너가 없으며, 그래서 위 명령이 `-J`를 거칩니다. SLI 주소와
같은 서브넷에 있는 VNet 내부의 운영자 VM입니다.

<Aside type="caution" title="확신에 찬 오답을 만들어내는 두 가지 측정 실수">
eth0, 외부 인터페이스, 또는 공용 주소에 대해 22번 포트를 프로브하면 노드의 SSH 상태와
무관하게 닫힘으로 보고되므로, 아무것도 알려주지 못합니다. SLI 주소만 응답합니다.

그리고 회사 워크스테이션에서의 프로브는 닫힌 포트를 **열림**으로 보고할 수 있습니다.
Netskope가 일반적인 포트에서 TCP 핸드셰이크를 자체적으로 완료하기 때문입니다. 워크스테이션에서
보면 CE 공용 주소의 80번과 443번 포트가 열림으로 읽히지만, VNet 내부에서 프로브하면 닫혀
있습니다. VNet 내의 VM에서 프로브하십시오.
</Aside>

## Site CLI는 터미널과 캐리지 리턴을 필요로 합니다

`admin`의 로그인 셸은 셸이 아닙니다. 이는 `go-prompt` 애플리케이션으로, 터미널을 raw 모드로
전환하고 줄 단위가 아니라 키 입력을 읽습니다. 네 가지 결과가 있으며, 각각은 서로 다른 문제처럼
보이는 방식으로 실패합니다:

| 동작 | 없을 때 일어나는 일 |
| --- | --- |
| 터미널 할당 (`ssh -tt`) | `go-prompt.NewStandardInputParser`에서 `panic: no such device or address` 발생 — 어플라이언스가 크래시한 것처럼 읽힙니다 |
| Enter로 라인 피드가 아니라 캐리지 리턴 전송 | 라인이 결코 제출되지 않고, 아무것도 출력하지 않은 채 입력 종료 시점에 세션이 닫힙니다 |
| 표준 입력을 열어 둠 | 명령이 렌더링되기 전에 연결이 종료되어, 정상 동작하는 명령이 아무 응답 없는 것처럼 보입니다 |
| 명령 텍스트와 Enter 바이트를 **따로** 기록 | 개행이 버퍼에 리터럴 문자로 들어가 CLI가 `unknown command`로 응답하며, 이는 그 명령이 존재하지 않는 것처럼 읽힙니다 |

따라서 `ssh host 'some-command'`는 동작하지 않습니다. 인자는 무시되고 대화형 프롬프트가
그대로 시작됩니다. 터미널로 구동하거나 아예 하지 마십시오.
`scripts/sitecli_ssh_harvest.py`가 참조 구현입니다.

<Aside type="caution" title="'no such device or address'라는 패닉은 인증이 성공했음을 의미합니다">
`vpmu`는 로그인 **이후**, 연결할 터미널을 찾지 못했을 때 이를 발생시킵니다. 크래시로 읽으면
최악의 결과처럼 보이지만, 실제로는 성공 직전의 마지막 오류입니다. `-tt`를 추가하고 다시
연결하십시오.
</Aside>

<Aside type="caution" title="CE를 교체하면 호스트 키가 변경됩니다">
교체된 노드는 동일한 주소에서 다른 호스트 키를 제시하므로, 다음 연결에서
`REMOTE HOST IDENTIFICATION HAS CHANGED` 경고가 발생하고 연결이 거부됩니다. 해당 주소의
이전 항목을 지우고 다시 연결하십시오. SSH를 부여하는 것 자체가 VM을 교체하므로, 이를 도입한
후 첫 연결에서 이 상황을 예상하십시오.
</Aside>

로그인 배너는 노드의 등록 상태를 보고하며, 이는 여전히 기동 중인 노드와 고장난 노드를
구분하는 가장 빠른 방법입니다:

```text
Registration Status: PROVISIONING
SLO IP: 10.0.1.4/26
```

## 키페어 제공

<Steps>

1. 아직 없다면 키페어를 생성하십시오. RSA가 아니라 Ed25519입니다. 더 짧고, 어플라이언스
   `sshd`가 수락합니다.

   ```bash
   ssh-keygen -t ed25519 -C "ce-operator" -f ~/.ssh/id_ed25519
   ```

2. 배포가 **공개** 키를 가리키도록 하십시오. 루트 모듈이 파일을 한 번 읽고 그 문자열을
   모든 노드에 전달합니다:

   ```hcl
   # terraform/terraform.tfvars
   ssh_public_key_path = "~/.ssh/id_ed25519.pub"
   ```

   `ssh_public_key`는 대신 자료를 인라인으로 받으며, plan 테스트에서 사용하는 방식입니다.
   비공개 키는 여러분의 워크스테이션을 결코 벗어나지 않습니다.

3. 적용하십시오. 이 페이지 상단의 경고를 먼저 읽으십시오 — 기존 배포에서는 이 작업이
   CE VM을 교체합니다.

</Steps>

<Aside type="note" title="VM 자체의 admin_ssh_key는 별개의 것입니다">
`modules/ce-node`의 `azurerm_linux_virtual_machine.admin_ssh_key`는 Azure VM 관리자를
인가하며, 어플라이언스 `admin` 계정이 아닙니다. Site CLI 접근 권한을 부여하지 않으며, 이것이
설정되어 있다는 사실은 CE SSH가 구성되었다는 증거가 아닙니다.
</Aside>

## 이것이 아닌 것들

아래 각 항목은 이 경로가 아직 불가능하다고 믿어지던 동안 테스트되고 배제되었습니다.
각각은 하루를 소모할 만큼 그럴듯합니다.

| 원인이 아닌 것 | 어떻게 배제되었는가 |
| --- | --- |
| 자격 증명이 생성 시점에만 적용됨 | `sshd`는 첫 부팅 약 90초 시점에, 사이트 객체가 존재하기 전에 시작됩니다. `admin_user_credentials`는 `ReplaceSpecType`에도 존재하며 인플레이스로 적용됩니다. |
| `block_all_services` | 관리 주소의 22번 포트 차단은 서비스가 차단되었는지 여부와 무관하게 동일합니다. |
| 키 끝의 개행 | 양쪽 모두 테스트했으며 변화 없음. cloud-init은 여전히 이를 제거하는데, 그렇지 않으면 리터럴 블록이 두 번째 빈 줄을 렌더링하게 됩니다. |
| 고정된 구버전 CE 소프트웨어 | OpenSSH 9.9를 실행하는 빌드를 포함해 세 개의 빌드에서 재현되었습니다. |
| `admin_password` 누락 | 처음부터 새로 만든 CE에서 `ssh_key`와 함께 `admin_password`를 설정해도 아무 변화가 없었습니다. |

<Aside type="caution" title="구분자처럼 보이지만 그렇지 않은 두 개의 API 필드">
`gc_spec.admin_ssh_key`는 `admin_password`를 설정한 20개를 포함해 **테넌트의 88개 사이트
전부**에서 비어 있습니다. 동작하는 사이트와 동작하지 않는 사이트 사이에서 이를 비교하는
것은 아무것도 알려주지 못합니다. 어디서나 비어 있기 때문입니다.

`registrations_by_site`는 이 필드를 완전히 생략하고 `None`을 반환하는데, 이는 "보고되지
않음"이 아니라 "구성되지 않음"처럼 읽힙니다.
</Aside>
