이 배포의 CE 노드 하나에서 2026-07-28에 캡처되었습니다. `sitecli/capture-manifest.json`에
어느 노드인지 기록되어 있으며, `scripts/capture-sitecli.sh --check`로 실제 CE를 대상으로
명령 표면을 재검증할 수 있습니다.

SSH는 어플라이언스의 `admin` 계정에 도달하며, 해당 계정의 로그인 셸은 Site CLI
(`/opt/bin/vpmu`)입니다. 이것이 **박스 내 전체 명령 표면**에 접근하는 유일한 경로입니다 —
[debug API](../debug-api/)는 34개의 명령을 노출하지만, 어플라이언스 자체에는 해당 API에
없는 명령이 훨씬 더 많습니다.

```bash
cd terraform
SLI=$(terraform output -json ce_sli_private_ips | jq -r '.eastus01')
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<operator-vm> "admin@$SLI"
```

해당 명령줄의 모든 부분은 필수적이며, 다음 세 섹션에서 각 부분이 방지하는 오류를
설명합니다.

도착하는 셸 프롬프트가 없습니다: `admin`의 로그인 셸 **자체가** Site CLI이므로,
`>>>` 프롬프트에 바로 접속됩니다. 거기서 `execcli <name>`으로 박스 내 명령을 실행하세요 —
[박스 내 명령](../../commands/on-box/)을 참조하십시오.

<Aside type="danger" title="내부 주소는 반드시 조회하여 확인하십시오 — 이전 세션의 주소를 그대로 사용하지 마십시오">
Azure는 재빌드할 때마다 내부 서브넷을 재할당하며, 노드 순서대로 할당되지 않습니다. 가장
최근 빌드에서 `f5-xc-ce-vm-01`, `-02`, `-03`은 각각 `10.0.3.7`, `10.0.3.5`, `10.0.3.4`를
보유하고 있었으며, 이전 빌드에서는 완전히 다른 순서였습니다. 또한 테스트 클라이언트의 NIC가
동일한 서브넷에 있으며, 이전에 CE가 보유했던 주소를 현재 갖고 있습니다. 따라서 기억해둔
주소로 접속하면 잘못된 노드에 연결되거나, CE가 아닌 VM에 연결되거나, 아무 데도 연결되지
않을 수 있으며 — 마지막 경우는 "SSH가 활성화되지 않음"과 동일하게 보입니다.

`terraform output -json ce_sli_private_ips`가 매핑 정보입니다. 상태를 바로 확인하기
어려운 경우, 주소는 변경되더라도 NIC 이름은 안정적으로 유지됩니다:

```bash
az network nic show -g "$(terraform output -raw resource_group_name)" \
  -n "$(terraform output -json ce_vm_names | jq -r '.eastus01')-internal-nic" \
  --query ipConfigurations[0].privateIPAddress -o tsv
```

</Aside>

<Aside type="caution" title="부트스트랩 전용 — 기존 CE는 재생성 없이 SSH를 활성화할 수 없습니다">
cloud-init의 `write_files`는 **최초 부팅 시 한 번만** 실행됩니다. 이후에는 노드에
`/etc/cloud/cloud-init.disabled` 마커가 생성되며 cloud-init은 다시 실행되지 않습니다.

따라서 실행 중인 CE에 대한 인플레이스 경로는 없습니다. `custom_data`는 Azure에서
교체 전용이므로, 기존 배포에 이를 적용하면 **모든 CE VM이 교체됩니다**. 이미 실행 중인
노드에 운영자 SSH를 부여하는 것은 재빌드이며 구성 변경이 아닙니다 — 다음 경고는 해당
재빌드가 예전에 어떤 비용을 초래했는지, 그리고 왜 더 이상 그렇지 않은지를 설명합니다.
</Aside>

<Aside type="caution" title="CE VM 교체가 예전에는 등록을 영구적으로 막았습니다 — 이는 수정되었으며, 사이트 오브젝트가 VM과 결합된 이유입니다">
재빌드를 계획하기 전에 알아두십시오. 이 장애의 형태가 계획에서 볼 결합 구조를 설명하기
때문입니다.

예전에는 삭제된 노드의 등록이 컨트롤 플레인의 고유한 `(tenant, cluster_name, hostname)`
인덱스를 유지했기 때문에, 교체 노드의 등록이 `UniqueSecondaryIndexViolationError`로
거부되어 무한 재시도 상태가 되었습니다. 등록을 삭제하는 것만으로는 충분하지 않았습니다:
남아 있는 `StatusObject`가 워크로드 요청에 대해 `500`을 반환했고, 그 시점에서 각 노드는
삭제한 등록에 고정된 `registration-obj.yml`을 영속화했기 때문에 자기 복구 없이 `404`로
루프했습니다. 복구에는 두 번의 전체 재빌드가 필요했습니다. 그 모든 과정에서
`terraform plan`은 **"변경 사항 없음"** 을 보고했는데, Terraform의 관점에서는 원하는 상태에
도달했기 때문입니다.

[Issue 674](https://github.com/f5-sales-demo/mcn/issues/674)는
[PR 693](https://github.com/f5-sales-demo/mcn/pull/693)으로 해결되어 종료되었습니다.
`modules/xc-site`는 이제 CE VM 인스턴스를 `replace_triggered_by`에 명시하므로, VM을
교체하면 사이트 오브젝트도 교체되며, 사이트를 삭제하면 해당 등록도 함께 삭제됩니다 —
교체 노드가 부팅되기 전에 인덱스 키가 해제됩니다. 이후 플리트를 처음부터 재빌드했으며,
세 사이트 모두 개입 없이 `ONLINE` 상태로 올라왔습니다.

결합은 가정이 아닌 관측 가능한 것입니다. 각 사이트는 VM *인스턴스* ID에 바인딩되며,
해당 등록은 `infra.instance_id`와 동일한 값을 보고합니다:

```bash
cd terraform && terraform output -json ce_bound_instance_ids
```

두 값이 일치하지 않으면 사이트가 더 이상 존재하지 않는 노드에 여전히 바인딩된 것으로,
재빌드된 CE가 등록에서 빠져나올 수 없는 상태입니다. 등록의 절반을 읽는 것은 여전히 직접
API 호출이 필요합니다 — 프로바이더 이슈
[1376](https://github.com/f5-sales-demo/terraform-provider-xcsh/issues/1376)이 이를
데이터 소스에 추가할 사항입니다.
</Aside>

## cloud-init이 키를 기록하는 이유, API가 아닌 이유

사이트 오브젝트의 `admin_user_credentials.ssh_key`는 이 기능을 위한 필드처럼 정확히
보입니다. 수락되고, 읽기 검증에서도 유지되며, 아무것도 구성하지 않습니다. `vpm`이 노드의
로컬 사용자를 소유하며 이 계정에 대한 변경을 거부합니다 — 단일 부팅 동안 세 번에 걸쳐
노드 자체 로그에서:

```text
vpm  users.go:165: Won't do any change for user admin (internal skip)
```

그 한 줄에서 모든 것이 이어집니다. `/var/home/admin/.ssh`는 사이트가 `ONLINE`에 도달하기
전이나 후에도 절대 존재하지 않습니다. `vpm`이 `vesbkp`와 `vesopcon` 두 계정을 설정하고
`admin`을 건너뛰었기 때문에, `admin` 섀도의 최종 변경 날짜는 이미지 빌드 날짜로 유지되는
반면 `vesbkp`와 `vesopcon`은 현재 날짜를 표시합니다. 그리고 `vpm`은 어느 시점에서도
`ssh_key`나 `authorized_keys`에 대해 아무것도 기록하지 않습니다.

따라서 파일은 `vpm` 외부에서 작성되어야 합니다. `admin`은 노드 이미지에 베이킹된 uid
2202이므로 cloud-init 실행 전에 존재하며, `owner: admin:admin`은 작성 시점에 해석됩니다
— `runcmd`도, 소유권 수정도 필요 없습니다:

```yaml
- path: /var/home/admin/.ssh/authorized_keys
  permissions: "0600"
  owner: admin:admin
  content: |
    ${ssh_public_key}
```

`sshd`는 항상 수락할 준비가 되어 있었습니다. `sshd -T`는 `pubkeyauthentication yes`를
보고하며, `admin`은 노드에 탑재된 두 `sshd_config` 파일 모두에서 `AllowUsers`에 포함되어
있습니다. 활성화할 것은 없었습니다 — 단지 파일이 없었을 뿐입니다.

<Aside type="danger" title="admin_user_credentials를 다시 추가하지 마십시오, sshd_config도 편집하지 마십시오">
`admin_user_credentials`는 `terraform/modules/xc-site`에 연결되었다가 이 증거가 수집된 후
되돌려졌습니다 (#660, PR #663). 이는 채워지기를 기다리는 공백이 아닙니다.

`sshd_config`는 등록 중에 교체되므로, 편집 내용은 가장 불편한 순간에 폐기됩니다.
</Aside>

## 하나의 주소에서만 응답하는 이유

`sshd`는 `0.0.0.0:22`에 바인딩되지만, `sshd`가 응답하는 방식으로 호스트 네트워크 스택에
있는 것은 **내부(SLI)** 주소뿐입니다. eth0은 `a-i-eth0`으로 이름이 변경되고 호스트 IP를
전혀 갖지 않습니다 — Argo 데이터 플레인이 해당 인터페이스를 소유하며, 원래 그 인터페이스가
가졌을 관리/SLO 주소는 `vhost0`에 나타납니다. 나머지 두 NIC는 자체 이름으로 호스트
스택에 유지됩니다.

VNet 내부의 VM에서 하나의 CE를 대상으로 프로빙한 결과:

```text
management/SLO address    timed out
external address          timed out
internal/SLI address      OPEN     SSH-2.0-OpenSSH_8.7
an unused address         timed out    (control)
```

따라서 알고 있는 노드 주소를 대상으로 프로빙하면 닫힌 보안 그룹과 정확히 동일한 결과가
반환됩니다. 차단되는 것이 없으며, 해당 주소에는 리스너가 없습니다.

<Aside type="caution" title="게스트 인터페이스 이름으로 어느 서브넷에 있는지 파악하지 마십시오">
`eth1`과 `eth2` 중 어느 것이 내부 주소를 갖는지는 **동일한 이 배포의 노드 간에도
다릅니다**. 세 CE 모두에서 라이브로 읽은 결과:

```text
f5-xc-ce-vm-01    eth1 -> external      eth2 -> internal/SLI
f5-xc-ce-vm-02    eth2 -> external      eth1 -> internal/SLI
f5-xc-ce-vm-03    eth1 -> external      eth2 -> internal/SLI
```

모든 노드에서 공통으로 유지되는 것은 두 가지뿐입니다: `a-i-eth0`에는 주소가 없고,
`vhost0`이 관리/SLO 주소를 갖습니다. 그 외의 모든 것은 인터페이스 이름이 아닌
[`ip addr`](../../commands/network/ip/) 출력의 주소를 기준으로 매핑하십시오.
</Aside>

CE 공용 주소에도 포트 22에 리스너가 없으며, 이것이 위의 명령이 `-J`를 사용하는 이유입니다:
SLI 주소와 동일한 서브넷에 있는 VNet 내부의 운영자 VM을 통하는 것입니다. 이 배포는
해당 목적으로 하나를 빌드합니다 —
`terraform output -raw client_vm_name`이 이름을 나타냅니다.

<Aside type="caution" title="-J는 점프 구간에 옵션을 전달하지 않습니다">
명령줄에 지정된 옵션은 최종 홉에 적용됩니다. 따라서 `-J`와 함께 사용된
`-o UserKnownHostsFile=/dev/null`은 *점프* 호스트에 대해 여전히 실제 `known_hosts`를
참조하고 기록합니다. 재빌드된 플리트를 `known_hosts`에 포함시키지 않으려는 경우 이것이
예상치 못한 동작이 됩니다. 그럴 때는 첫 번째 홉을 명시적으로 지정하십시오:

```bash
ssh -tt -o ProxyCommand="ssh -W %h:%p -o UserKnownHostsFile=/dev/null azureuser@<operator-vm>" \
    -o UserKnownHostsFile=/dev/null -i ~/.ssh/id_ed25519 "admin@$SLI"
```

</Aside>

<Aside type="caution" title="확신 있는 오답을 만드는 두 가지 측정 실수">
eth0, 외부 인터페이스, 또는 공용 주소를 대상으로 포트 22를 프로빙하면 노드의 SSH 상태에
관계없이 닫힘으로 보고되므로, 아무런 정보도 얻을 수 없습니다. SLI 주소만 응답합니다.

그리고 기업 워크스테이션에서의 프로빙은 닫혀 있는 포트를 **열려** 있다고 보고할 수
있습니다: Netskope가 일반적인 포트에서 TCP 핸드셰이크를 직접 완료하기 때문입니다. 포트
80과 443은 워크스테이션에서 CE 공용 주소에 대해 열린 것으로 읽히지만 VNet 내부에서
프로빙하면 닫혀 있습니다. VNet 내부의 VM에서 프로빙하십시오.
</Aside>

## Site CLI에는 터미널과 캐리지 리턴이 필요합니다

`admin` 로그인 셸은 셸이 아닙니다. 터미널을 로우 모드로 전환하고 줄 단위가 아닌 키 입력을
읽는 `go-prompt` 애플리케이션입니다. 각각이 서로 다른 문제처럼 보이는 방식으로 실패하는
네 가지 결과가 있습니다:

| 메커니즘 | 없을 때 발생하는 현상 |
| --- | --- |
| 터미널 할당 (`ssh -tt`) | `go-prompt.NewStandardInputParser`에서 `panic: no such device or address`가 발생하며, 이는 어플라이언스가 충돌한 것처럼 보임 |
| Enter에 라인 피드가 아닌 캐리지 리턴 전송 | 줄이 제출되지 않고, 입력 종료 시 아무것도 출력하지 않은 채 세션이 닫힘 |
| 표준 입력 열어두기 | 명령이 렌더링되기 전에 연결이 종료되어, 정상 작동하는 명령이 침묵처럼 보임 |
| 명령 텍스트와 Enter 바이트를 **별도로** 전송 | 개행 문자가 버퍼에 리터럴 문자로 들어가고 CLI가 `unknown command`로 응답하여, 명령이 존재하지 않는 것처럼 보임 |

따라서 `ssh host 'some-command'`는 작동하지 않습니다: 인수가 무시되고 대화형 프롬프트가
시작됩니다. 터미널로 구동하거나 아예 사용하지 마십시오.
`scripts/sitecli_ssh_harvest.py`가 참조 구현입니다.

<Aside type="caution" title="'no such device or address'를 읽는 패닉은 인증이 성공했음을 의미합니다">
`vpmu`는 연결할 터미널을 찾지 못하면 로그인 **후에** 이를 출력합니다. 충돌로 읽히면
최악의 결과처럼 보이지만, 실제로는 성공 직전의 마지막 오류입니다. `-tt`를 추가하고
다시 연결하십시오.
</Aside>

<Aside type="caution" title="CE를 교체하면 호스트 키가 변경됩니다">
교체 노드는 동일한 주소에서 다른 호스트 키를 제시하므로, 다음 연결 시
`REMOTE HOST IDENTIFICATION HAS CHANGED` 경고가 나타나고 거부됩니다. 해당 주소의 이전
항목을 지우고 다시 연결하십시오. SSH 부여가 VM을 교체하므로, 이를 적용한 후 첫 번째
연결 시 이 상황을 예상하십시오.
</Aside>

## 배너는 무료 상태 확인입니다

아무것도 입력하기 전에 로그인 배너가 이미 여러 질문에 답변해 두었습니다. `f5-xc-ce-vm-01`
에서 ASCII 아트와 공인 IP를 생략한 내용:

```text
UNAUTHORIZED ACCESS TO THIS DEVICE IS PROHIBITED
All actions performed on this device are audited

Using https://register.ves.volterra.io
OS: rhel-9.2024.6
Memory: 32768MiB
Storage: sda: 31GiB
CPU: Model: Intel(R) Xeon(R) Platinum 8272CL CPU @ 2.60GHz | CPUs: 8
Software: crt-20250613-3382
DNS: 168.63.129.16: OK
NTP: Synced
Uptime: 0 days, 5 hours, 20 minutes
Registration Status: PROVISIONED
SLO IP: 10.0.1.4/26
WELCOME IN SITE CLI
```

`Registration Status`는 아직 올라오는 중인 노드(`PROVISIONING`)와 완료된 노드
(`PROVISIONED`)를 구분합니다. `Software`는 어떤 명령이 존재하는지를 결정하는 빌드 문자열
입니다. `DNS`와 `NTP`는 등록을 가장 먼저 중단시키는 두 가지 의존성을 다루므로, 온라인
상태가 되지 않은 노드는 보통 여기서 이미 그 이유를 알려주었을 것입니다 —
[`chronyc-sources`](../../commands/network/chronyc-sources/)나
[`dig`](../../commands/network/dig/)가 전혀 필요하지 않은 경우도 있습니다.

## 키페어 제공

<Steps>

1. 아직 없다면 키페어를 생성하십시오. RSA가 아닌 Ed25519를 사용하십시오: 더 짧고,
   어플라이언스 `sshd`에서 허용됩니다.

   ```bash
   ssh-keygen -t ed25519 -C "ce-operator" -f ~/.ssh/id_ed25519
   ```

2. 배포가 **공개** 절반을 가리키도록 설정하십시오. 루트 모듈이 파일을 한 번 읽고
   문자열을 모든 노드에 전달합니다:

   ```hcl
   # terraform/terraform.tfvars
   ssh_public_key_path = "~/.ssh/id_ed25519.pub"
   ```

   `ssh_public_key`는 대신 인라인으로 자료를 받으며, 이것이 플랜 테스트에서 사용하는
   방식입니다. 개인 절반은 절대 워크스테이션을 벗어나지 않습니다.

3. 적용하십시오. 먼저 이 페이지 상단의 경고를 읽으십시오 — 기존 배포에서는 CE VM이
   교체됩니다.

</Steps>

<Aside type="note" title="VM 자체의 admin_ssh_key는 별개입니다">
`modules/ce-node`의 `azurerm_linux_virtual_machine.admin_ssh_key`는 어플라이언스 `admin`
계정이 아닌 Azure VM 관리자를 인증합니다. Site CLI 접근 권한을 부여하지 않으며, 이것이
설정되어 있다고 해서 CE SSH가 구성된 것은 아닙니다.
</Aside>

## 이것이 아닌 것

다음 각각은 경로가 여전히 불가능하다고 여겨지던 동안 테스트되어 배제되었습니다.
각각은 하루를 소비할 만큼 그럴듯합니다.

| 원인이 아닌 것 | 배제 방법 |
| --- | --- |
| 자격 증명은 생성 시에만 적용됨 | `sshd`는 최초 부팅 약 90초 후에 시작되며, 사이트 오브젝트가 존재하기 전입니다. `admin_user_credentials`는 `ReplaceSpecType`에도 있으며 인플레이스로 적용됩니다. |
| `block_all_services` | 관리 주소의 포트 22 닫힘은 서비스 차단 여부와 관계없이 동일합니다. |
| 키 끝의 개행 문자 | 양쪽 모두 테스트했으며 변화 없음. cloud-init은 여전히 이를 제거하는데, 리터럴 블록이 그렇지 않으면 두 번째 빈 줄을 렌더링하기 때문입니다. |
| 고정된 구버전 CE 소프트웨어 | OpenSSH 9.9를 실행하는 버전을 포함하여 세 번의 빌드에서 재현됨. |
| `admin_password` 누락 | 처음부터 새로 만든 CE에서 `ssh_key`와 함께 `admin_password`를 설정해도 아무 변화 없음. |

<Aside type="caution" title="판별자처럼 보이지만 그렇지 않은 두 API 필드">
`gc_spec.admin_ssh_key`는 `f5-sales-demo`의 **모든 58개 사이트에서** 비어 있거나
없습니다 — `admin_user_credentials.ssh_key`를 설정한 두 사이트를 포함하여. 작동하는
사이트와 작동하지 않는 사이트 간에 이를 비교해도 아무런 정보를 얻을 수 없으며, 자격
증명이 *구성된* 사이트에서도 빈 값으로 읽히기 때문입니다.

`registrations_by_site`는 해당 필드를 완전히 생략하고 `None`을 반환하며, 이는 "구성되지
않음"이 아닌 "보고되지 않음"으로 읽힙니다.
</Aside>
