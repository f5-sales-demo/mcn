SSH는 어플라이언스 `admin` 계정에 접근하며, 이 계정의 로그인 셸은 Site CLI
(`/opt/bin/vpmu`)입니다. 이것이 **온-박스 전체 명령 인터페이스**에 접근하는 유일한 경로입니다 —
[디버그 API](../debug-api/)는 34개의 명령을 제공하지만, 어플라이언스 자체는 해당 API에 포함되지 않은
훨씬 더 많은 명령을 제공합니다.

```bash
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<operator-vm> admin@10.0.3.5
```

이 명령줄의 모든 부분은 필수적이며, 다음 세 섹션에서 각 부분이 방지하는 오류를 설명합니다.

<Aside type="caution" title="실행 중인 배포에서 이를 활성화하면 VM이 교체됩니다">
키는 cloud-init에 의해 작성되며, cloud-init의 `write_files`는 **최초 부팅 시에만** 실행됩니다.
기존 노드에 대해 이를 활성화하면 노드를 교체해야 하는데, 현재 이로 인해 등록이 중단됩니다:
기존 등록이 고유한 `(tenant, cluster_name, hostname)` 인덱스를 보유하고 있어 교체 노드는 등록할 수 없으며,
`terraform plan`은 그동안 "변경 없음"을 보고합니다. 변경을 계획하기 **전에**
[이슈 674](https://github.com/f5-sales-demo/mcn/issues/674)를 확인하십시오.
</Aside>

## API가 아닌 cloud-init이 키를 작성하는 이유

사이트 객체의 `admin_user_credentials.ssh_key`는 정확히 이를 위한 필드처럼 보입니다.
허용되고, 읽기 시 유지되며, 아무것도 구성하지 않습니다. `vpm`이 노드의 로컬 사용자를 소유하며
이 사용자는 건드리지 않습니다 — 노드 자체의 로그에서, 단일 부팅 동안 세 번:

```text
vpm  users.go:165: Won't do any change for user admin (internal skip)
```

이 한 줄에서 모든 것이 따라옵니다. `/var/home/admin/.ssh`는 사이트가 `ONLINE` 상태에 도달하기
전후 어느 시점에도 존재하지 않습니다. `admin`의 shadow 최종 변경 날짜는 이미지 빌드 날짜에
그대로 유지되는 반면, `vesbkp`와 `vesopcon`은 현재 날짜를 표시합니다. `vpm`이 이 두 사용자는
설정했지만 `admin`은 건너뛰었기 때문입니다. 그리고 `vpm`은 `ssh_key`나 `authorized_keys`에
대해 어느 시점에도 아무것도 기록하지 않습니다.

따라서 파일은 `vpm` 외부에서 작성되어야 합니다. `admin`은 uid 2202로 노드 이미지에 내장되어
있어 cloud-init 실행 전에 존재하므로, `owner: admin:admin`은 쓰기 시점에 확인됩니다 —
`runcmd`도, 소유권 수정도 필요 없습니다:

```yaml
- path: /var/home/admin/.ssh/authorized_keys
  permissions: "0600"
  owner: admin:admin
  content: |
    ${ssh_public_key}
```

`sshd`는 항상 허용 상태였습니다. `sshd -T`는 `pubkeyauthentication yes`를 보고하며,
`admin`은 노드에 포함된 두 `sshd_config` 파일 모두의 `AllowUsers`에 나타납니다.
활성화해야 할 것은 없었습니다 — 파일이 없었을 뿐입니다.

<Aside type="danger" title="admin_user_credentials를 다시 추가하지 마십시오. sshd_config도 편집하지 마십시오">
`admin_user_credentials`는 `terraform/modules/xc-site`에 연결되었다가 이 증거가 수집된 후
되돌렸습니다 (#660, PR #663). 채워야 할 빈자리가 아닙니다.

`sshd_config`는 등록 중에 교체되므로, 편집 내용은 가장 불편한 순간에 폐기됩니다.
</Aside>

## 하나의 주소에서만 응답하는 이유

`sshd`는 `0.0.0.0:22`에 바인딩되지만, **내부 (SLI)** 주소만 호스트 네트워크 스택에 있습니다.
eth0은 `a-i-eth0`으로 이름이 변경되어 호스트 IP를 가지지 않습니다 — Argo 데이터 플레인이
해당 인터페이스를 소유합니다 — 반면 eth1과 eth2는 `sshd`가 수신 대기 중인 호스트 스택에 남아 있습니다.

VNet 내부 VM에서 프로브한 결과:

```text
10.0.1.4     timed out             CE mgmt/SLO  (eth0)
10.0.2.4     timed out             CE external  (eth1)
10.0.3.5     OPEN                  CE internal/SLI
10.0.3.6     OPEN
10.0.3.7     OPEN
```

따라서 노드를 알고 있는 주소로 프로브하면 닫힌 보안 그룹이 반환하는 것과 정확히 같은 결과가
반환됩니다. 차단하는 것이 없고, 해당 주소에 리스너가 없는 것입니다.

CE 공인 주소에도 포트 22에 리스너가 없습니다. 그것이 위 명령이 `-J`를 사용하는 이유입니다:
SLI 주소와 동일한 서브넷에 있는 VNet 내부의 운영자 VM입니다.

<Aside type="caution" title="확신을 갖고 잘못된 답을 도출하는 두 가지 측정 실수">
eth0, 외부 인터페이스 또는 포트 22에 대한 공인 주소를 프로브하면 노드의 SSH 상태에 관계없이
닫힘으로 보고되므로, 아무것도 알려줄 수 없습니다. SLI 주소만 응답합니다.

그리고 회사 워크스테이션에서의 프로브는 닫혀 있는 포트를 **열려 있음**으로 보고할 수 있습니다:
Netskope가 일반적인 포트에서 TCP 핸드셰이크를 직접 완료하기 때문입니다. 포트 80과 443은
워크스테이션에서 CE 공인 주소에 대해 열려 있는 것으로 표시되지만, VNet 내부에서 프로브하면
닫혀 있습니다. VNet의 VM에서 프로브하십시오.
</Aside>

## Site CLI에는 터미널과 캐리지 리턴이 필요합니다

`admin` 로그인 셸은 셸이 아닙니다. 이것은 `go-prompt` 애플리케이션으로, 터미널을 raw 모드로
전환하고 라인이 아닌 키 입력을 읽습니다. 각각이 다른 문제처럼 보이는 방식으로 실패하는 네 가지 결과:

| 동작 방식 | 없을 때 발생하는 현상 |
| --- | --- |
| 터미널 할당 (`ssh -tt`) | `go-prompt.NewStandardInputParser`에서 `panic: no such device or address` 발생, 어플라이언스가 충돌한 것처럼 보임 |
| Enter에 라인 피드가 아닌 캐리지 리턴 전송 | 라인이 제출되지 않으며, 세션은 아무것도 출력하지 않고 입력 종료 시 닫힘 |
| 표준 입력을 열린 상태로 유지 | 명령이 렌더링되기 전에 연결이 종료되어 작동하는 명령이 침묵처럼 보임 |
| 명령 텍스트와 Enter 바이트를 **별도로** 작성 | 줄바꿈이 리터럴 문자로 버퍼에 들어가고 CLI가 `unknown command`로 응답, 마치 명령이 존재하지 않는 것처럼 보임 |

따라서 `ssh host 'some-command'`는 작동하지 않습니다: 인수는 무시되고 대화형 프롬프트가
어쨌든 시작됩니다. 터미널로 구동하거나 아예 구동하지 마십시오.
`scripts/sitecli_ssh_harvest.py`가 참조 구현입니다.

로그인 배너는 노드의 등록 상태를 보고하며, 이는 아직 시작 중인 노드와 손상된 노드를 구별하는
가장 빠른 방법입니다:

```text
Registration Status: PROVISIONING
SLO IP: 10.0.1.4/26
```

## 키페어 제공

<Steps>

1. 아직 키페어가 없다면 생성하십시오. RSA가 아닌 Ed25519: 더 짧고,
   어플라이언스 `sshd`에서 허용됩니다.

   ```bash
   ssh-keygen -t ed25519 -C "ce-operator" -f ~/.ssh/id_ed25519
   ```

2. 배포가 **공개** 키를 가리키도록 하십시오. 루트 모듈은 파일을 한 번 읽어
   모든 노드에 문자열을 전달합니다:

   ```hcl
   # terraform/terraform.tfvars
   ssh_public_key_path = "~/.ssh/id_ed25519.pub"
   ```

   `ssh_public_key`는 대신 인라인으로 재료를 가져가며, 이것이 플랜 테스트가 사용하는 방식입니다.
   개인 키는 절대 워크스테이션을 떠나지 않습니다.

3. 적용하십시오. 먼저 이 페이지 상단의 경고를 읽으십시오 — 기존 배포에서는 CE VM이 교체됩니다.

</Steps>

<Aside type="note" title="VM 자체의 admin_ssh_key는 다른 것입니다">
`modules/ce-node`의 `azurerm_linux_virtual_machine.admin_ssh_key`는 어플라이언스 `admin`
계정이 아닌 Azure VM 관리자에게 권한을 부여합니다. Site CLI 접근 권한을 부여하지 않으며,
설정되어 있다는 것이 CE SSH가 구성되어 있다는 증거가 아닙니다.
</Aside>

## 이것이 아닌 것들

이것들은 경로가 여전히 불가능하다고 여겨지는 동안 테스트되고 제외된 것들입니다.
각각은 하루를 낭비할 만큼 그럴듯합니다.

| 원인이 아닌 것 | 제외된 방법 |
| --- | --- |
| 자격 증명은 생성 시에만 적용됨 | `sshd`는 최초 부팅 약 90초 후에 시작되며, 사이트 객체가 존재하기 전입니다. `admin_user_credentials`는 `ReplaceSpecType`에도 존재하며 현재 위치에서 적용됩니다. |
| `block_all_services` | 관리 주소의 포트 22 폐쇄는 서비스가 차단되었는지 여부와 관계없이 동일합니다. |
| 키에 후행 줄바꿈 | 두 가지 방법으로 테스트했으며 변경 없음. cloud-init은 리터럴 블록이 두 번째 빈 줄을 렌더링할 수 있어 어쨌든 제거합니다. |
| 고정된 이전 CE 소프트웨어 | OpenSSH 9.9를 실행하는 빌드를 포함하여 세 가지 빌드에서 재현됨. |
| 누락된 `admin_password` | 처음부터 CE에서 `ssh_key`와 함께 `admin_password`를 설정해도 변경 없음. |

<Aside type="caution" title="판별자처럼 보이지만 그렇지 않은 두 API 필드">
`gc_spec.admin_ssh_key`는 `admin_password`를 설정한 20개를 포함하여 **테넌트의 모든 88개
사이트**에서 비어 있습니다. 작동하는 사이트와 작동하지 않는 사이트를 비교해도 아무것도 알 수 없습니다.
모든 곳에서 비어 있기 때문입니다.

`registrations_by_site`는 필드를 완전히 생략하고 이에 대해 `None`을 반환하는데, 이는
"보고되지 않음"이 아닌 "구성되지 않음"으로 읽힙니다.
</Aside>

<Aside type="caution" title="새로 생성된 사이트는 운영 API가 응답하기까지 약 30분이 필요합니다">
새 사이트가 `ONLINE`을 보고한 후 약 25~30분 동안, `vpm/debug` 엔드포인트는 `The requested
URL was rejected`라고 읽히는 BIG-IP `503` 페이지를 반환합니다. 이것은 웹 애플리케이션
방화벽 차단이나 취소된 토큰처럼 보이지만 둘 다 아닙니다: 사이트가 아직 릴레이할 준비가 되지
않은 것입니다. 아무것도 변경하지 말고 기다렸다가 다시 시도하십시오.

SSH는 그러한 워밍업이 없습니다. `sshd`가 시작되는 즉시 응답하는데, 이것이 노드가 아직
등록 중일 때 작동하는 경로인 이유입니다.
</Aside>
