세 가지 경로가 모두 동작하며, 어떤 경로가 적용되는지는 선호도가 아니라 노드의 상태와 접속하는 위치에 따라 결정됩니다.

| 경로 | 노드 `ONLINE` 필요 | 네트워크 도달성 필요 | 제한 | 다루는 범위 |
| --- | --- | --- | --- | --- |
| [디버그 API](./debug-api/) | **예** | 예 | 신규 사이트에서 약 25~30분의 준비 시간 | 34개 명령 |
| [SSH](./ssh/) | 아니요 | VNet 내부에서, 내부 주소로만 | 최초 부팅부터 키가 존재해야 함 | 온박스 Site CLI 전체 |
| [시리얼 콘솔](./serial-console/) | 아니요 | 아니요 | VM당 세션 1개; 2,048자 붙여넣기 제한 | 온박스 Site CLI 전체 |

시리얼 콘솔은 최후의 수단이며, 동작하는 네트워크 경로가 없는 노드에서도 살아남는 유일한 경로입니다.

디버그 API로 부족할 때 손을 뻗어야 하는 것이 SSH입니다. 어플라이언스는 해당 API가 노출하는 34개보다 훨씬 많은 명령을 제공하기 때문입니다. 다만 두 가지 대가가 있습니다. 키는 cloud-init이 기록하므로 **최초 부팅** 시점에 존재해야 하며, 이는 실행 중인 노드에서 이를 활성화하려면 노드를 교체해야 함을 의미합니다 — 그리고 현재 이는 등록 과정을 멈추게 만듭니다 ([issue 674](https://github.com/f5-sales-demo/mcn/issues/674)). 또한 `sshd`는 노드의 내부 주소에서만 응답하므로, VNet 내부의 호스트가 필요합니다. 여러분이 알고 있는 주소로 탐지를 시도하면 항상 닫혀 있다고 보고됩니다.

## 이 구분이 선호도의 문제가 아닌 이유

디버그 API는 F5 Distributed Cloud 컨트롤 플레인이 제공하며, 등록 과정에서 `vpm`이 수립한 터널을 통해 노드로 중계합니다. 등록이 없으면 터널이 없고, 터널이 없으면 API가 중계할 대상이 없습니다.

이는 명확한 방식이 아니라 도움이 되지 않는 방식으로 실패하므로, 애초에 올라오지 못한 노드가 API 문제처럼 보이게 됩니다.

시리얼 콘솔은 완전히 다른 경로를 택합니다 — Azure 플랫폼을 거쳐 노드의 에뮬레이트된 시리얼 포트로 연결됩니다. 노드가 등록되었는지, 네트워크 도달성이 있는지, 데이터 플레인이 동작하는지 전혀 상관하지 않습니다. 그 독립성이 바로 핵심이며, CE VM에서 부팅 진단을 계속 활성화해 두어야 하는 이유입니다.

<Aside type="note" title="무엇을 선택할 것인가">
자동화를 작성하거나 나중에 다시 실행할 증거를 수집하는 경우에는 디버그 API를 사용하십시오. 등록 자체가 고장 난 상황이라면, 시리얼 콘솔은 대체 수단이 아니라 — 유일한 선택지입니다.
</Aside>

## 자격 증명

각 경로는 서로 다른 자격 증명을 사용하며, 그중 어느 것도 명령줄에 두어서는 안 됩니다.

- **디버그 API** — F5 Distributed Cloud API 토큰을 `XCSH_API_TOKEN`으로, 테넌트 URL을 `XCSH_API_URL`로 지정합니다. `~/.config/xcsh/contexts/<tenant>.json`의 `xcsh` 컨텍스트 파일이 둘 다 보관하며, 환경 변수가 제공되지 않을 때 `scripts/capture-sitecli.sh`가 이 파일을 읽습니다.
- **SSH** — 배포 과정에서 공개 키가 최초 부팅 시 `/var/home/admin/.ssh/authorized_keys`에 기록된 키페어의 비공개 키, 그리고 내부 주소로 접속하기 위한 VNet 내부의 호스트가 필요합니다. `azureuser`가 아니라 `admin`으로 접속하십시오.
- **시리얼 콘솔** — 대화형 Azure 로그인. 이를 위한 서비스 주체는 없습니다: F5 사내 Entra 테넌트가 서비스 주체 프로비저닝을 허용하지 않으며, 이는 이 작업의 어떤 부분도 CI에서 실행되지 않는 이유이기도 합니다.

<Aside type="danger" title="토큰을 인수로 전달하지 마십시오">
명령줄의 토큰은 셸 히스토리와 프로세스 목록에 남아, 해당 머신의 다른 모든 사용자가 읽을 수 있습니다. 그런 이유로 `capture-sitecli.sh`는 `--token`을 아예 거부하고, 대신 stdin으로 `curl`에 헤더를 전달합니다.
</Aside>
