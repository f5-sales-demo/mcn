두 가지 경로가 모두 동작하며, 어느 것이 적용되는지는 선호도가 아니라 노드의 상태에 따라 결정됩니다.

| 경로 | 노드 `ONLINE` 필요 | 네트워크 도달성 필요 | 제한 | 범위 |
| --- | --- | --- | --- | --- |
| [Debug API](./debug-api/) | **예** | 예 | 신규 사이트에서 약 25~30분의 워밍업 | 34개 명령 |
| [Serial console](./serial-console/) | 아니요 | 아니요 | VM당 세션 1개; 2,048자 붙여넣기 제한 | 온박스 Site CLI 전체 |

Serial console은 최후의 수단이며, 동작하는 네트워크 경로가 전혀 없는 노드에서도 살아남는 유일한 경로입니다.

[**SSH는 세 번째 경로가 아닙니다.**](./ssh/) 이 테넌트가 실행 중인 빌드에서는 `admin` 계정이 인증할 수 없고, `vpm`은 키를 적용하지 않으며, 이를 변경하는 사이트 설정도 없습니다. 해당 페이지는 증거를 문서화하기 위해 존재합니다. 거기서 발생하는 모든 실패 양상이 방화벽 문제나 자격 증명 문제처럼 보이기 때문입니다.

## 이 구분이 선호도의 문제가 아닌 이유

Debug API는 F5 Distributed Cloud 컨트롤 플레인이 제공하며, 등록 과정에서 `vpm`이 설정한 터널을 통해 노드로 중계합니다. 등록이 없다는 것은 터널이 없다는 뜻이고, 이는 API가 중계할 대상이 없다는 뜻입니다.

이 경우 명확하게 실패하지 않고 도움이 되지 않는 방식으로 실패하기 때문에, 애초에 올라오지 못한 노드가 API 문제처럼 보입니다.

Serial console은 완전히 다른 방향으로 진행됩니다 — Azure 플랫폼을 거쳐 노드의 에뮬레이트된 직렬 포트로 연결됩니다. 노드가 등록되었는지, 네트워크 도달성이 있는지, 데이터 플레인이 동작하는지는 전혀 상관하지 않습니다. 그 독립성이 바로 핵심이며, CE VM에서 부팅 진단(boot diagnostics)을 계속 활성화해 두어야 하는 이유입니다.

<Aside type="note" title="What to reach for">
자동화를 작성하는 경우나 이후에 다시 실행하고자 하는 증거를 수집하는 경우에는 Debug API를 사용하십시오. 등록 자체가 고장 난 상황이라면 serial console은 대체 수단이 아니라 — 유일한 선택지입니다.
</Aside>

## 자격 증명

두 경로는 서로 다른 자격 증명을 사용하며, 어느 것도 명령줄에 두어서는 안 됩니다.

- **Debug API** — F5 Distributed Cloud API 토큰을 `XCSH_API_TOKEN`으로, 테넌트 URL을 `XCSH_API_URL`로 지정합니다. `~/.config/xcsh/contexts/<tenant>.json`에 있는 `xcsh` 컨텍스트 파일이 두 값을 모두 보관하며, 환경 변수가 제공되지 않을 때 `scripts/capture-sitecli.sh`가 이 파일을 읽습니다.
- **Serial console** — 대화형 Azure 로그인을 사용합니다. 이를 위한 서비스 주체는 없습니다: F5 사내 Entra 테넌트가 서비스 주체 프로비저닝을 허용하지 않으며, 이것이 이 작업의 어떤 부분도 CI에서 실행되지 않는 이유이기도 합니다.

<Aside type="danger" title="Never pass a token as an argument">
명령줄의 토큰은 셸 히스토리와 프로세스 목록에 남게 되며, 해당 머신의 다른 모든 사용자가 이를 읽을 수 있습니다. 그런 이유로 `capture-sitecli.sh`는 `--token`을 아예 거부하고, 대신 stdin으로 `curl`에 헤더를 전달합니다.
</Aside>
