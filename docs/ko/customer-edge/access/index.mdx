두 가지 경로가 존재하며, 어느 경로가 적용되는지는 선호도가 아니라 노드의 상태에 따라 결정됩니다.

| 노드 상태 | 경로 | 스크립트 가능 여부 | 대상 범위 |
| --- | --- | --- | --- |
| `ONLINE` | [Debug API](./debug-api/) | 가능 | 34개 명령, 읽기 전용 및 권한 있는 명령 |
| 등록되지 않았거나 연결 불가 | [시리얼 콘솔](./serial-console/) | 불가 — 터미널 필요 | 전체 온박스 Site CLI |

## 분리가 선호도의 문제가 아닌 이유

Debug API는 F5 Distributed Cloud 컨트롤 플레인에 의해 제공되며, 등록 중에 `vpm`이 설정한 터널을 통해 노드로 릴레이됩니다. 등록이 없으면 터널이 없고, 터널이 없으면 API가 릴레이할 대상도 없습니다.

명확한 방식이 아닌 도움이 되지 않는 방식으로 실패하기 때문에, 정상적으로 올라오지 못한 노드가 API 문제처럼 보입니다.

시리얼 콘솔은 완전히 반대 방향으로 작동합니다 — Azure 플랫폼을 통해 노드의 에뮬레이트된 시리얼 포트로 연결됩니다. 노드가 등록되었는지, 네트워크 연결성이 있는지, 또는 데이터 플레인이 정상 작동하는지 여부를 신경 쓰지 않습니다. 이 독립성이 바로 핵심이며, CE VM에서 부트 진단을 활성화된 상태로 유지해야 하는 이유입니다.

<Aside type="note" title="어느 것을 선택할지">
자동화를 작성하거나 나중에 재실행하려는 증거를 수집하는 경우 Debug API를 사용하세요. 등록 자체가 문제라면, 시리얼 콘솔은 대안이 아닙니다 — 유일한 선택지입니다.
</Aside>

## 자격 증명

두 경로 모두 서로 다른 자격 증명을 사용하며, 어느 것도 명령줄에 노출되어서는 안 됩니다.

- **Debug API** — `XCSH_API_TOKEN`으로 설정된 F5 Distributed Cloud API 토큰과 `XCSH_API_URL`로 설정된 테넌트 URL. `~/.config/xcsh/contexts/<tenant>.json`에 위치한 `xcsh` 컨텍스트 파일에 두 가지 모두 저장되어 있으며, 환경 변수가 제공되지 않을 때 `scripts/capture-sitecli.sh`가 이를 읽습니다.
- **시리얼 콘솔** — 대화형 Azure 로그인. 이를 위한 서비스 주체는 없습니다. F5 기업 Entra 테넌트에서 서비스 주체 프로비저닝을 허용하지 않으며, 이것이 이 작업의 어떤 부분도 CI에서 실행되지 않는 이유이기도 합니다.

<Aside type="danger" title="토큰을 인수로 전달하지 마세요">
명령줄에 입력된 토큰은 셸 히스토리와 프로세스 목록에 남아, 해당 머신의 다른 모든 사용자가 읽을 수 있습니다. `capture-sitecli.sh`는 바로 이런 이유로 `--token` 옵션을 거부하며, 대신 `curl`에 stdin을 통해 헤더를 제공합니다.
</Aside>
