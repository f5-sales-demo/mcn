세 가지 경로가 작동하며, 어떤 경로가 적용되는지는 선호도가 아닌 노드의 상태와 연결 위치에 따라 결정됩니다.

| 경로 | 노드 `ONLINE` 필요 | 네트워크 도달 가능성 필요 | 제한 사항 | 적용 범위 |
| --- | --- | --- | --- | --- |
| [디버그 API](./debug-api/) | **예** | 예 | 새 사이트에서 약 25~30분의 워밍업 | 34개 명령 |
| [SSH](./ssh/) | 아니요 | VNet 내부에서, 내부 주소로만 | 첫 번째 부팅 시 키가 있어야 함 | 온박스 전체 Site CLI |
| [시리얼 콘솔](./serial-console/) | 아니요 | 아니요 | VM당 1개 세션; 2,048자 붙여넣기 제한 | 온박스 전체 Site CLI |

시리얼 콘솔은 최후의 수단이며, 작동 중인 네트워크 경로가 없는 노드에서도 유일하게 사용할 수 있는 경로입니다.

SSH는 디버그 API로 충분하지 않을 때 사용해야 하는 경로입니다. 어플라이언스가 API가 노출하는 34개 명령보다 훨씬 더 많은 명령을 제공하기 때문입니다. 단, 두 가지 비용이 따릅니다. 키는 cloud-init에 의해 기록되므로 **첫 번째 부팅** 시에 반드시 있어야 합니다. 즉, 실행 중인 노드에서 키를 활성화하면 해당 노드가 교체되며, 현재 이 과정에서 등록이 중단될 수 있습니다([이슈 674](https://github.com/f5-sales-demo/mcn/issues/674)). 그리고 `sshd`는 노드의 내부 주소에서만 응답하므로 VNet 내부의 호스트가 필요합니다. 노드를 식별하는 주소를 탐색하면 항상 닫힌 것으로 표시됩니다.

## 이 구분이 선호도가 아닌 이유

디버그 API는 F5 Distributed Cloud 컨트롤 플레인이 제공하며, 등록 중에 `vpm`이 구성한 터널을 통해 노드로 릴레이합니다. 등록이 없으면 터널이 없고, 터널이 없으면 API가 릴레이할 대상이 없습니다.

명확한 오류가 아닌 도움이 되지 않는 방식으로 실패하므로, 처음부터 올라오지 않은 노드는 API 문제처럼 보일 수 있습니다.

시리얼 콘솔은 완전히 다른 방식으로 작동합니다. Azure 플랫폼을 통해 노드의 에뮬레이션된 시리얼 포트에 연결됩니다. 노드의 등록 여부, 네트워크 도달 가능성, 데이터 플레인 작동 여부와 무관합니다. 이러한 독립성이 핵심이며, CE VM에서 부팅 진단을 계속 활성화해야 하는 이유입니다.

<Aside type="note" title="사용할 경로">
자동화를 작성하거나 나중에 재실행할 증거를 수집하는 경우, 디버그 API를 사용하십시오. 등록이 문제인 경우 시리얼 콘솔은 대안이 아니라 유일한 옵션입니다.
</Aside>

## 자격 증명

두 경로 모두 서로 다른 자격 증명을 사용하며, 어느 것도 명령줄에 입력해서는 안 됩니다.

- **디버그 API** — `XCSH_API_TOKEN`으로 설정된 F5 Distributed Cloud API 토큰과, `XCSH_API_URL`로 설정된 테넌트 URL. `~/.config/xcsh/contexts/<tenant>.json`의 `xcsh` 컨텍스트 파일에 두 값이 모두 저장되어 있으며, 환경에서 제공하지 않을 때 `scripts/capture-sitecli.sh`가 이 파일을 읽습니다.
- **시리얼 콘솔** — 대화형 Azure 로그인. 이를 위한 서비스 주체가 없습니다. F5 기업 Entra 테넌트에서 서비스 주체 프로비저닝을 허용하지 않으며, CI에서 이 부분이 실행되지 않는 이유도 여기에 있습니다.

<Aside type="danger" title="토큰을 인수로 전달하지 마십시오">
명령줄의 토큰은 셸 히스토리와 프로세스 목록에 남아, 해당 머신의 다른 모든 사용자가 읽을 수 있습니다. `capture-sitecli.sh`는 바로 이 이유로 `--token`을 완전히 거부하며, 대신 `curl`에 stdin으로 헤더를 전달합니다.
</Aside>
