모든 Customer Edge는 `https://<sli-ip>:65500`에서 F5의 사이트 콘솔을 제공합니다. 이
배포 환경에서는 보통 가장 먼저 시도해볼 수 있는 방법입니다.

이 방법은 요구 사항이 가장 적습니다. 배포할 SSH 키도 없고, 유지 관리할 점프 호스트도 없으며, 노드에 공개 IP가 없어도 되고, 활성화를 위해 VM을 교체할 필요도 없습니다. 연결 권한은 **Azure RBAC 결정** 사항입니다. 그리고 사이트가 등록되어 있을 필요도 없습니다 — 아래의 실행 기록은 세 사이트 모두 `site_state: FAILED`를 보고하는 동안 캡처된 것입니다.

한 가지 제약은 사이트 콘솔이 노드의 내부(SLI) 주소에서만 응답하므로, VNet 내부에서만 접근할 수 있다는 점입니다. Azure Bastion은 네트워크에 다른 것을 추가하지 않고도 이 간극을 해소합니다.

<Aside type="note" title="여기서 검증된 것과 검증되지 않은 것">
이 페이지의 모든 명령어와 출력은 이 배포 환경의 `f5-xc-ce-vm-01`에 대해 실행된 것으로, 실패 사례를 포함하여 그대로 재현되었습니다.

검증되지 않은 한 가지는 **로그인**입니다. 단계는 자격 증명 프롬프트에서 멈추므로, 아래 내용에는 콘솔에 접속한 이후의 모습이 설명되어 있지 않습니다.
</Aside>

## 시작하기 전에

<Steps>

1. Azure에 로그인하고 Bastion 확장을 추가합니다. 터널링은 네이티브 클라이언트 기능으로 확장이 기본적으로 설치되어 있지 않습니다.

   ```bash
   az login
   az extension add --name bastion
   ```

2. CE 가상 머신, 해당 네트워크 인터페이스, Bastion 호스트에 대해 **Reader** 권한을 보유합니다.

3. Bastion이 배포되어 있고 사용 가능한지 확인합니다. Basic SKU는 터널링과 IP 기반 연결을 모두 지원하지 않으므로, 여기서 `Standard`와 `True`는 모두 필수 요건입니다.

   ```bash
   az network bastion list -g rg-mcn-ce-ha-rmordasiewicz \
     --query "[].{name:name, sku:sku.name, tunneling:enableTunneling}" -o table
   ```

   ```text
   Name               Sku       Tunneling
   -----------------  --------  -----------
   ce-ha-lab-bastion  Standard  True
   ```

</Steps>

## 터널 열기

직접 입력하지 말고 `terraform output`에서 값을 가져오세요 — 리소스 ID는 수동으로 조합할 성질의 것이 아닙니다.

<Steps>

1. Bastion 호스트 이름, 리소스 그룹, 그리고 대상 CE의 VM 리소스 ID를 읽습니다.

   ```bash
   cd terraform
   BASTION=$(terraform output -raw bastion_name)
   RG=$(terraform output -raw resource_group_name)
   VM_ID=$(terraform output -json ce_vm_ids | jq -r '.eastus01')
   ```

   ```text
   ce-ha-lab-bastion
   rg-mcn-ce-ha-rmordasiewicz
   /subscriptions/…/providers/Microsoft.Compute/virtualMachines/f5-xc-ce-vm-01
   ```

   <Aside type="caution" title="맵의 키는 VM 이름이 아닌 사이트로 지정됩니다">
   `ce_vm_ids`의 키는 `eastus01`, `eastus02`, `eastus03`이며 — VM 이름이 **아닙니다**. `jq -r '."f5-xc-ce-vm-01"'`과 같은 필터는 `null`을 반환하고, 이 경우 터널은 빈 리소스 ID로 인해 실패합니다. 확실하지 않은 경우 목록을 확인하세요:

   ```bash
   terraform output -json ce_vm_ids | jq -r 'keys | join(", ")'
   ```

   ```text
   eastus01, eastus02, eastus03
   ```
   </Aside>

2. 터널을 시작합니다. 중지할 때까지 포트를 열어 두므로, 백그라운드로 실행하거나 두 번째 터미널을 사용하세요.

   ```bash
   az network bastion tunnel \
     --name "$BASTION" \
     --resource-group "$RG" \
     --target-resource-id "$VM_ID" \
     --resource-port 65500 \
     --port 65500 &
   ```

   ```text
   WARNING: Opening tunnel on port: 65500
   WARNING: Tunnel is ready, connect on port 65500
   WARNING: Ctrl + C to close
   ```

   세 줄 모두 앞에 `WARNING:`이 붙어 있습니다. 이는 Azure CLI가 진행 상황을 stderr에 출력하는 것으로, 문제가 아닙니다. 연결하기 전에 `Tunnel is ready`가 나타날 때까지 기다리세요.

3. 리스너가 루프백에서 로컬로 동작하는지 확인합니다:

   ```bash
   lsof -nP -iTCP:65500 -sTCP:LISTEN
   ```

   ```text
   COMMAND   PID  USER  FD  TYPE  DEVICE  SIZE/OFF  NODE  NAME
   Python  41648  you   7u  IPv4  …            0t0   TCP  127.0.0.1:65500 (LISTEN)
   ```

4. 콘솔을 엽니다. 터널이 로컬로 만들어 주므로 주소는 노드의 주소가 아닌 `localhost`입니다.

   ```bash
   open https://localhost:65500/          # macOS
   xdg-open https://localhost:65500/      # Linux
   ```

5. 완료되면 터널을 중지합니다 — `Ctrl-C`를 누르거나 백그라운드로 실행했다면 `kill %1`을 사용합니다. 터널을 열어 두면 로컬 포트 65500과 Bastion 세션이 계속 점유됩니다.

</Steps>

## 표시되는 내용

**로그인 페이지가 아닌 자격 증명 대화 상자.** 콘솔은 HTTP Basic 인증을 사용하므로, 브라우저가 자체적으로 사용자 이름 및 비밀번호 프롬프트를 표시합니다. 별도의 폼은 없습니다:

```bash
curl -skI https://localhost:65500/
```

```text
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Basic realm="Volterra Site Console"
Content-Length: 0
```

해당 realm으로의 `401` 응답은 콘솔이 정상적으로 작동하고 있는 것입니다. 인증되지 않은 요청은 이러한 응답을 받아야 합니다.

**세 가지 이유가 동시에 작용하는 인증서 경고.** 인증서를 직접 확인하면:

```bash
openssl s_client -connect localhost:65500 -servername localhost </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates
```

```text
subject=C=US, ST=California, L=Santa Clara, O=Volterra, OU=Volterra Edge Services, CN=site-local.volterra.io
issuer=C=US, ST=California, L=Santa Clara, O=Volterra, OU=Volterra Edge Services, CN=site-local.volterra.io
notBefore=Oct 25 04:51:31 2024 GMT
notAfter=Oct 25 04:51:31 2025 GMT
```

Subject와 issuer가 동일하므로 자체 서명된 인증서입니다. 이름은 `site-local.volterra.io`인데 `localhost`로 연결하고 있으므로 일치하지 않습니다. 그리고 이 배포 환경에서 실행 중인 빌드에서는 **인증서가 2025년 10월 25일에 만료되었으며** — 어플라이언스에 포함되어 제공되고, 이 저장소에서 갱신하는 것은 없습니다.

브라우저 경고가 바로 표시될 것이며, 매번 반복됩니다. 위의 subject 줄이 유용한 부분입니다. 이를 통해 로컬 포트 65500에서 수신 대기 중인 다른 무언가가 아닌 어플라이언스에 도달했음을 확인할 수 있습니다.

## 관리자 자격 증명

`admin`으로 로그인합니다. **이 문서에서는 비밀번호를 공개하지 않으며, 공개해서도 안 됩니다.**

공장 초기 상태의 Customer Edge는 F5에서 공개한 기본값으로 출하되며, F5는 이를 변경하도록 요구합니다. 나중에 보안을 강화하는 것이 아니라 노드 배포의 일부로 변경하는 것으로 취급하세요. 이것이 겉보기보다 더 중요한 두 가지 이유가 있습니다:

- 이 문서는 공개되어 있습니다. 플릿의 현재 콘솔 비밀번호를 게시하면 "Bastion에 대한 Reader 권한 보유"가 이 페이지를 읽는 누구에게나 어플라이언스 전체 접근으로 이어집니다.
- 문서에 게시된 비밀번호는 누군가 교체하는 순간 틀린 정보가 되며, 그것도 가장 오해하기 쉬운 방식으로 — 독자는 페이지가 오래된 것이 아니라 자신의 접근이 차단된 것이라고 결론짓게 됩니다.

비밀번호는 팀에서 운영 비밀 정보를 보관하는 곳에서 가져오세요. 답이 "여전히 공장 기본값"이라면, 다른 작업을 하기 전에 먼저 변경하세요.

<Aside type="caution" title="Terraform에서 비밀번호 설정은 검증되지 않았습니다">
사이트 객체의 `admin_user_credentials.admin_password`는 이를 선언적으로 설정하는 방법처럼 보입니다. 이 빌드에서 사이트 콘솔에 적용된다는 것이 **확인되지 않았으므로**, 그렇게 가정하지 마세요.

[SSH 페이지](../ssh/)를 어느 쪽의 증거로도 읽지 마세요. `admin_password`가 "아무것도 변경하지 않았다"는 결과는 SSH 인증을 대상으로 측정된 것으로, `vpm`은 `admin` 사용자에 대해 SSH 인증을 완전히 건너뜁니다. 이는 콘솔에 대해서는 아무것도 말해주지 않습니다.
</Aside>

## 터널이 리소스 ID를 대상으로 해야 하는 이유

`--target-resource-id`는 필수입니다. 노드의 주소를 대상으로 하면 거부됩니다:

```bash
az network bastion tunnel --name "$BASTION" -g "$RG" \
  --target-ip-address 10.0.3.5 --resource-port 65500 --port 65501
```

```text
ERROR: Custom ports are not allowed. Allowed ports for Tunnel with IP connect is 22, 3389.
```

이 Bastion에서 `ip_connect_enabled`가 `true`이므로 IP 기반 연결이 비활성화되어서가 **아닙니다** — Microsoft는 해당 설정에 관계없이 IP 기반 네이티브 클라이언트 연결에서 사용자 지정 포트를 지원하지 않으며([Azure 문서](https://learn.microsoft.com/azure/bastion/connect-ip-address)), 65500은 사용자 지정 포트입니다. 여기서 Bastion 구성을 검사해도 해결 방법이 없습니다. 리소스 ID를 사용하세요.

## 작동하지 않을 때

| 증상 | 원인 | 해결 방법 |
| --- | --- | --- |
| `ERROR: Custom ports are not allowed. Allowed ports for Tunnel with IP connect is 22, 3389.` | `--target-ip-address` 사용 | `--target-resource-id` 사용 |
| `ERROR: Defined port is currently unavailable` | 다른 터널이 이미 해당 로컬 포트를 점유 중 | 다른 터널을 중지하거나 다른 `--port` 전달; `--resource-port`는 65500 유지 |
| 터널이 시작되지만 리소스 ID가 비어 있음 | `jq` 필터가 사이트 키 대신 VM 이름을 사용 | `eastus01`/`02`/`03`을 키로 사용 |
| `401 Unauthorized`, realm `Volterra Site Console` | 오류가 아님 — 인증되지 않은 요청 | `admin` 자격 증명 제공 |
| 브라우저가 인증서를 거부 | 자체 서명, 이름 불일치, 2025년 10월 이후 만료 | 예상된 동작; subject가 `CN=site-local.volterra.io`인지 확인 후 진행 |

<Aside type="note" title="권한 부여 실패는 재현되지 않았습니다">
RBAC 권한 부족도 이 방법이 실패하는 또 다른 명백한 원인이지만, 이를 재현하면 공유 배포 환경에서 역할 할당을 제거해야 하므로 여기서는 그대로의 오류와 함께 문서화되지 않았습니다. 터널이 시작 시 권한 부여 오류와 함께 실패하면, VM, 해당 NIC, Bastion 호스트 세 가지 모두에 대한 Reader 권한을 확인하세요.
</Aside>
