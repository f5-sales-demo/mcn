Azure 시리얼 콘솔은 Azure 플랫폼을 통해 노드의 에뮬레이트된 시리얼 포트에 연결됩니다.
F5 Distributed Cloud 컨트롤 플레인, 노드의 데이터 플레인, 또는 노드가 제어하는 어떠한
네트워크 경로도 통과하지 않으므로 — 다른 모든 수단이 실패했을 때도 작동하는 것이 바로
이 이유입니다.

CE가 **전혀 기동되지 않은** 경우에 이 방법을 사용하십시오: 등록 실패, 테넌트에서
사이트 부재, 또는 노드가 기동되었지만 외부 경로가 없는 경우. 이러한 모든 경우에
[디버그 API](../debug-api/)는 중계할 터널이 없습니다. [SSH](../ssh/)는 등록 실패
시에도 유효하지만, 최초 부트 시 키가 이미 기록되어 있고 VNet 내부에서 노드의 내부
주소에 접근 가능한 경우에만 해당됩니다 — 처음 접하는 노드에서는 두 조건 모두
충족되지 않습니다.

## 사전 요구사항: 부트 진단

Azure는 VM에 부트 진단이 활성화되어 있어야 시리얼 콘솔을 연결할 수 있습니다.
이는 `terraform/modules/ce-node`에서 활성화됩니다:

```hcl
boot_diagnostics {}
```

빈 블록은 Azure 관리 스토리지를 선택하므로, 소유할 진단 스토리지 계정, 수명 주기
정책 또는 액세스 키가 없습니다. 노드에서 확인하는 방법:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="활성화는 소급 적용되지 않습니다">
부트 진단은 **부트 시** 시리얼 로그를 캡처합니다. 이미 실행 중인 VM에서 이를
활성화해도 이미 완료된 부트에 대한 로그는 생성되지 않으므로, `az vm boot-diagnostics get-boot-log`는 다음과 같이 응답합니다:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

이는 예상된 동작이며 결함이 아닙니다. 부트 로그는 노드가 다음에 재부팅된 후 생성됩니다.
그러나 라이브 콘솔 연결은 즉시 작동하며 — 로그에 의존하지 않습니다.
</Aside>

## 터미널 없이 가용성 확인하기

연결에는 대화형 세션이 필요하지만, 연결 *가능 여부*는 두 번의 API 호출로 확인할 수
있습니다. 두 호출 모두 상태 확인 시 유용합니다.

서비스는 구독에 대해 활성화되어 있어야 합니다 — 관리자가 테넌트 전체에서 비활성화할 수 있습니다:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

그런 다음 특정 노드의 시리얼 포트에 대한 연결을 요청합니다:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

`wss://`로 시작하는 `connectionString` — 이 배포에서는
`eastus.gateway.serialconsole.azure.com` — 은 지금 바로 콘솔에 연결 가능함을
의미합니다. 부트 진단이 활성화되기 전에는 이 호출에 연결할 대상이 없었습니다.

<Aside type="danger" title="해당 연결 문자열은 자격 증명입니다">
이것은 URL에 포함된 단기 베어러 토큰입니다. 로그에 기록하거나, 티켓에 붙여넣거나,
커밋하지 마십시오. 호출이 성공했음을 증명할 때는 호스트만 출력하십시오.
</Aside>

## 연결하기

<Steps>

1. 확장을 한 번 설치합니다:

   ```bash
   az extension add --name serial-console
   ```

2. 연결합니다:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. 쉘이 아닌 노드 자체의 로그인 프롬프트에 접속됩니다. 이것은 Site CLI이며,
   노드에 설정된 자격 증명이 필요합니다 — 프로비저닝 시의 관리자 비밀번호, 또는
   change-password 엔드포인트를 통해 설정된 비밀번호. 시리얼 콘솔은 *채널*이
   작동함을 증명하지만, 인증을 우회하지는 않습니다.

</Steps>

`f5-xc-ce-vm-01`에서 캡처한 내용으로, systemd 유닛 출력이 추가적인 정보를 제공하지
않는 중간 부분은 생략되었습니다:

```text file=../../../_data/serial-console-boot.txt
```

해당 트랜스크립트에서 주목할 만한 네 가지 사항은 디버그 API가 답할 수 없는 질문들에
대한 답을 제공합니다:

- **cloud-init 완료** — `Datasource DataSourceAzure`, 22.37초에 완료.
  등록에 실패하는 노드는 보통 여기서 실패하며, 이를 확인할 수 있는 곳이 바로 여기입니다.
- **두 컨테이너 런타임이 모두 시작됨.** `Container Runtime Interface for OCI (CRI-O)`와
  `Docker Application Container Engine`이 각각 `[ OK ]` 상태이며, 이는
  [crictl](../../commands/system/crictl/) 및 [docker](../../commands/system/docker/)에서
  사람들을 놀라게 하는 이중 런타임 동작에 대한 부트 시점의 증거입니다.
- **`VP Manager image load`와 `Argo Watch service`** — `vpm`과 Argo가 기동됩니다.
- **프롬프트는 노드 자체의 것으로**, 감사 배너 뒤에 있습니다. 시리얼 콘솔은 세션이
  아닌 로그인 프롬프트를 제공합니다.

<Aside type="caution" title="대화형 연결에는 실제 터미널이 필요하지만 — 스크립트로 자동화할 수 있습니다">
`az serial-console connect`는 터미널을 raw 모드로 전환하므로, 파이프라인이나 TTY가
없는 컨텍스트에서는 실행할 수 없습니다. Azure에 연결하기 전에 클라이언트 측에서
실패합니다:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

해당 트레이스백은 터미널 처리 문제이며, 시리얼 콘솔 장애가 아닙니다.

그러나 연결 자체는 **자동화 가능합니다** — CLI 대신 웹소켓을 직접 구동하십시오.
위의 트랜스크립트는 TTY 없이 그 방법으로 캡처되었습니다. 인간이 터미널 앞에 앉지
않고도 등록에 실패한 노드에서 부트 증거를 수집하는 방법인 `scripts/serial_console_capture.py`를
참조하십시오.
</Aside>

<Aside type="caution" title="재시도를 예상하십시오: 게이트웨이는 대략 두 번 중 한 번꼴로 요청을 거부합니다">
게이트웨이의 첫 번째 프레임은 출력이 아닌 챌린지이며, 클라이언트는 베어러 토큰으로
응답합니다. 이것이 올바르게 수행되더라도 소켓이 즉시 닫히는 경우가 많습니다:

```
[close] code=1011 reason=Connection not trusted
```

관찰된 동작: 간헐적으로 성공하며, 지속적으로 사용하면 리소스 그룹의 모든 노드가
거부합니다 — 몇 분 전에 작동했던 노드 포함.
`scripts/serial_console_capture.py`는 재시도가 종종 효과적이므로 기본적으로 재시도합니다.

**원인은 확인되지 않았습니다.** 그럴듯한 추측처럼 보여 시간을 낭비할 수 있어 배제된 항목들:

| 해당 없음 | 확인 방법 |
| --- | --- |
| ARM/compute 스로틀링 | 이는 ARM 호출에서 HTTP `429`를 반환합니다. 이것은 별도의 데이터 채널에서의 웹소켓 종료입니다. |
| 프록시에 의한 TLS 인터셉션 | `openssl s_client -connect <region>.gateway.serialconsole.azure.com:443 \| openssl x509 -noout -issuer`. 정상적인 `O=Microsoft Corporation` 발급자는 이를 배제하며, 프록시 벤더가 발급자로 나타나면 확인된 것이고 수정 방법은 `*.serialconsole.azure.com`을 허용 목록에 추가하는 것입니다. |
| 부트 진단 비활성화 | `az vm show -g <rg> -n <vm> --query diagnosticsProfile`에서 `enabled: true`가 보고됨. |
| 부여와 챌린지 간 토큰 불일치 | 두 가지 모두에 하나의 토큰을 사용하는 것이 올바른 방법이지만, 종료를 방지하지는 않습니다. |

Azure의 **공식 문서화된 동작**: **VM당 하나의 시리얼 콘솔 세션만 허용되며, 두 번째로
성공한 요청이 첫 번째를 퇴출시킵니다.** 퇴출된 사용자는 연결이 끊기지만 로그아웃되지는
않으므로 쉘 세션은 유지됩니다. 한 노드를 디버깅하는 두 명의 사용자는 서로를 반복적으로
퇴출시킬 것입니다.

대량 작업에는 [디버그 API](../debug-api/) 또는 [SSH](../ssh/)를 권장하며, 두 방법
모두 이러한 제한이 없습니다. 특히 SSH는 붙여넣기 제한도 없고 단일 세션 제한도 없으므로,
VNet 내부에서 노드에 접근 가능한 경우 더 나은 선택입니다.
</Aside>

<Aside type="caution" title="붙여넣기는 2,048자로 제한됩니다">
Azure는 시리얼 포트 과부하를 방지하기 위해 시리얼 콘솔 붙여넣기 길이를 2,048자로
제한합니다. 긴 명령 — 또는 한 번의 쓰기로 여러 명령을 묶어 전송하는 경우 — 은
길이 제한이 아닌 중단이나 스로틀링처럼 보이는 방식으로 실패합니다.

명령을 개별적으로 전송하십시오. 이것은 시리얼 콘솔을 통한 대량 수집에 있어 실질적인
제약이며, 해당 작업에는 [디버그 API](../debug-api/)를 권장하는 또 다른 이유입니다.
</Aside>

## API가 보여줄 수 없는 것들

- **cloud-init**의 실행, 실패, 또는 시작되지 않음 — 등록에 실패하는 노드의 일반적인 원인.
- `register.ves.volterra.io`에 대한 **등록 시도**, 구성 오류 또는 테넌트가 거부한 토큰 포함.
- 에이전트가 실행되기 전의 **커널 및 부트 메시지**.
- **작동하는 네트워크 경로가 없는** 노드, 이는 다른 모든 경로를 무력화합니다.

`ONLINE` 상태인 노드에는 디버그 API를 권장합니다: 스크립트로 자동화 가능하고,
재실행 가능한 증거를 생성하며, 단일 시리얼 포트를 점유하지 않습니다.
