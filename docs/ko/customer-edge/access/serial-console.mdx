Azure 직렬 콘솔은 Azure 플랫폼을 통해 노드의 에뮬레이션된 직렬 포트에 연결됩니다.
F5 Distributed Cloud 제어 플레인, 노드의 데이터 플레인, 또는 노드가 제어하는 어떠한 네트워크 경로도 통과하지 않습니다 — 바로 그렇기 때문에 다른 모든 방법이 실패할 때에도 작동합니다.

CE가 **전혀 기동되지 않은** 경우에 사용하십시오: 등록 실패, 테넌트에서 사이트가 표시되지 않음, 또는 노드는 작동 중이지만 외부로 나가는 경로가 없는 경우가 이에 해당합니다. 이러한 모든 경우, [디버그 API](../debug-api/)는 릴레이할 터널이 없으며, SSH는 출하 시 노드에서 비활성화되어 있습니다.

## 사전 요건: 부팅 진단

Azure는 직렬 콘솔을 연결하기 전에 VM에 부팅 진단이 활성화되어 있어야 합니다.
이는 `terraform/modules/ce-node`에서 다음과 같이 활성화됩니다:

```hcl
boot_diagnostics {}
```

빈 블록은 Azure 관리 스토리지를 선택하므로, 별도의 진단 스토리지 계정, 수명 주기 정책 또는 액세스 키를 관리할 필요가 없습니다. 노드에서 다음과 같이 확인하십시오:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="활성화는 소급 적용되지 않습니다">
부팅 진단은 **부팅 시** 직렬 로그를 캡처합니다. 이미 실행 중인 VM에 이를 활성화해도 이미 완료된 부팅에 대한 로그는 생성되지 않으므로, `az vm boot-diagnostics get-boot-log` 명령은 다음과 같이 응답합니다:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

이는 예상된 동작이며 오류가 아닙니다. 부팅 로그는 노드가 다음에 재부팅된 이후에 생성됩니다. 그러나 라이브 콘솔 연결은 즉시 작동합니다 — 로그에 의존하지 않습니다.
</Aside>

## 터미널 없이 가용성 확인하기

연결에는 대화형 세션이 필요하지만, 연결 *가능 여부*는 두 번의 API 호출로 확인할 수 있습니다. 두 호출 모두 상태 확인에 유용합니다.

해당 서비스는 구독에 대해 활성화되어 있어야 합니다 — 관리자가 테넌트 전체에서 비활성화할 수 있습니다:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

그런 다음 특정 노드의 직렬 포트에 대한 연결을 요청하십시오:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

`wss://`로 시작하는 `connectionString` — 이 배포에서는
`eastus.gateway.serialconsole.azure.com` — 이 반환되면 현재 콘솔에 연결할 수 있다는 의미입니다. 부팅 진단이 활성화되기 전에는 이 호출이 연결할 대상이 없었습니다.

<Aside type="danger" title="해당 연결 문자열은 자격 증명입니다">
URL에 포함된 단기 베어러 토큰입니다. 로그에 기록하거나, 티켓에 붙여넣거나, 커밋하지 마십시오. 호출이 성공했음을 보여줄 때는 호스트 부분만 출력하십시오.
</Aside>

## 연결하기

<Steps>

1. 확장을 한 번 설치합니다:

   ```bash
   az extension add --name serial-console
   ```

2. 연결합니다:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. 셸이 아닌 노드 자체의 로그인 프롬프트로 이동합니다. 이것은 Site CLI이며,
   노드에 설정된 자격 증명이 필요합니다 — 프로비저닝 시 설정된 관리자 암호, 또는 비밀번호 변경 엔드포인트를 통해 설정된 암호입니다. 직렬 콘솔은 *채널*이 작동함을 증명할 뿐, 인증을 우회하지는 않습니다.

</Steps>

<Aside type="caution" title="실제 터미널이 필요합니다">
`az serial-console connect`는 터미널을 raw 모드로 전환하므로, 스크립트, 파이프라인, 또는 TTY가 없는 컨텍스트에서는 실행할 수 없습니다. Azure에 접속하기 전에 클라이언트 측에서 실패합니다:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

해당 트레이스백은 터미널 처리 문제이며, 직렬 콘솔 장애가 아닙니다 — 위의 두 API 호출은 여전히 콘솔을 사용 가능 상태로 보고합니다. 자동화 가능한 신호가 필요한 경우, 연결을 스크립팅하려 하지 말고 해당 API 호출을 사용하십시오.
</Aside>

## API로는 확인할 수 없지만 여기서 볼 수 있는 것들

- **cloud-init** 실행 중, 실패, 또는 시작조차 하지 않음 — 노드가 등록되지 않는 일반적인 원인.
- **등록 시도** (`register.ves.volterra.io`에 대한) — 구성 오류 또는 테넌트가 거부한 토큰 포함.
- **커널 및 부팅 메시지** — 에이전트가 실행되기 전의 메시지.
- **작동하는 네트워크 경로가 없는** 상태의 노드 — 다른 모든 접근 경로를 차단하는 상태.

노드가 `ONLINE` 상태인 경우에는 디버그 API를 사용하는 것이 좋습니다: 스크립팅이 가능하고, 재실행할 수 있는 증거를 생성하며, 단일 직렬 포트를 점유하지 않습니다.
