Azure 시리얼 콘솔은 Azure 플랫폼을 통해 노드의 에뮬레이션된 시리얼 포트에 연결됩니다.
F5 Distributed Cloud 컨트롤 플레인, 노드의 데이터 플레인, 또는 노드가 제어하는 어떠한 네트워크 경로도 경유하지 않습니다 — 바로 이것이 다른 모든 방법이 실패할 때도 작동하는 이유입니다.

CE가 **전혀 시작되지 않은 경우** — 등록에 실패했거나, 사이트가 테넌트에 나타나지 않거나, 노드가 실행 중이지만 외부 경로가 없는 경우 — 에 사용하십시오. 이러한 모든 경우에 [debug API](../debug-api/)는 중계할 터널이 없으며, SSH는 노드 출하 시 기본적으로 닫혀 있습니다.

## 사전 요구 사항: 부트 진단

Azure는 시리얼 콘솔을 연결하기 전에 VM에서 부트 진단이 활성화되어 있어야 합니다.
이는 `terraform/modules/ce-node`에서 활성화됩니다:

```hcl
boot_diagnostics {}
```

빈 블록은 Azure 관리 스토리지를 선택하므로, 진단 스토리지 계정, 수명 주기 정책 또는 액세스 키를 별도로 관리할 필요가 없습니다. 노드에서 확인하려면:

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="활성화는 소급 적용되지 않습니다">
부트 진단은 **부팅 시** 시리얼 로그를 캡처합니다. 이미 실행 중인 VM에서 활성화해도
이미 완료된 부팅에 대한 로그는 생성되지 않으므로, `az vm boot-diagnostics get-boot-log`는 다음과 같이 응답합니다:

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

이는 예상된 동작이며 오류가 아닙니다. 부트 로그는 노드가 다음에 재부팅된 후 생성됩니다. 반면 라이브 콘솔 연결은 즉시 작동하며 — 로그에 의존하지 않습니다.
</Aside>

## 터미널 없이 가용성 확인하기

연결에는 대화형 세션이 필요하지만, 연결 *가능 여부*는 두 번의 API 호출로 확인할 수 있습니다. 두 호출 모두 상태 확인에 유용합니다.

구독에 대해 서비스가 활성화되어 있어야 합니다 — 관리자가 테넌트 전체에서 비활성화할 수 있습니다:

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

그런 다음 특정 노드의 시리얼 포트에 대한 연결을 요청합니다:

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

`wss://`로 시작하는 `connectionString` — 이 배포에서는
`eastus.gateway.serialconsole.azure.com` — 이 반환되면 현재 콘솔에 연결 가능한 상태임을 의미합니다. 부트 진단이 활성화되기 전에는 이 호출이 연결할 대상이 없었습니다.

<Aside type="danger" title="해당 연결 문자열은 자격 증명입니다">
URL에 포함된 단기 베어러 토큰입니다. 로그에 기록하거나, 티켓에 붙여넣거나, 커밋하지 마십시오. 호출이 성공했음을 시연할 때는 호스트 이름만 출력하십시오.
</Aside>

## 연결하기

<Steps>

1. 확장을 한 번 설치합니다:

   ```bash
   az extension add --name serial-console
   ```

2. 연결합니다:

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. 셸이 아닌 노드 자체의 로그인 프롬프트로 진입합니다. 이것은 Site CLI이며,
   노드에 설정된 자격 증명 — 프로비저닝 시의 관리자 비밀번호 또는 비밀번호 변경 엔드포인트를 통해 설정된 비밀번호 — 이 필요합니다. 시리얼 콘솔은 *채널*이 작동함을 증명할 뿐이며, 인증을 우회하지는 않습니다.

</Steps>

`f5-xc-ce-vm-01`에서 캡처한 출력으로, systemd 유닛 출력이 추가 정보를 제공하지 않는 중간 부분은 생략되었습니다:

```text file=../../../_data/serial-console-boot.txt
```

해당 기록에서 주목할 만한 네 가지 사항이 있습니다. 이는 디버그 API가 답할 수 없는 질문들에 대한 답변입니다:

- **cloud-init 완료** — `Datasource DataSourceAzure`, 22.37초에 완료됨.
  등록에 실패한 노드는 대체로 여기서 문제가 발생하며, 이 로그에서 확인할 수 있습니다.
- **두 컨테이너 런타임이 모두 시작됨.** `Container Runtime Interface for OCI (CRI-O)`
  와 `Docker Application Container Engine`이 각각 `[ OK ]` 상태로, 이는
  [crictl](../../commands/system/crictl/) 및 [docker](../../commands/system/docker/)에서 사람들을 놀라게 하는 이중 런타임 동작의 부팅 시 증거입니다.
- **`VP Manager image load` 및 `Argo Watch service`** — `vpm`과 Argo가 시작됨.
- **프롬프트는 노드 자체의 것**으로, 감사 배너 뒤에 위치합니다. 시리얼 콘솔은 세션이 아닌 로그인 프롬프트를 제공합니다.

<Aside type="caution" title="대화형 연결에는 실제 터미널이 필요하지만 — 스크립트로 자동화할 수 있습니다">
`az serial-console connect`는 터미널을 raw 모드로 전환하므로, 파이프라인이나 TTY가 없는 컨텍스트에서는 실행할 수 없습니다. Azure에 접속하기 전에 클라이언트 측에서 실패합니다:

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

이 스택 추적은 터미널 처리 문제이며, 시리얼 콘솔 장애가 아닙니다.

그러나 연결 자체는 **자동화 가능합니다** — CLI 대신 웹소켓을 직접 구동하면 됩니다. 위의 기록은 TTY 없이 그 방식으로 캡처된 것입니다. 등록에 실패한 노드에서 사람이 터미널 앞에 앉지 않고도 부팅 증거를 수집하는 방법인 `scripts/serial_console_capture.py`를 참조하십시오.
</Aside>

<Aside type="caution" title="재시도를 예상하십시오: 게이트웨이는 대략 두 번 중 한 번 연결을 거부합니다">
게이트웨이의 첫 번째 프레임은 출력이 아닌 챌린지이며, 클라이언트는 베어러 토큰으로 응답합니다. 올바르게 수행하더라도 소켓이 즉시 닫히는 경우가 있습니다:

```
[close] code=1011 reason=Connection not trusted
```

세 개의 노드에서 반복 시도를 측정한 결과, 이는 교대로 발생합니다: 거부 후 동일한 노드에서 다음 시도가 성공합니다. 이는 이전 세션이 아직 유지되고 있으며, 거부된 시도가 이를 해제하는 것과 일치합니다.

메시지에도 불구하고 **자격 증명 문제가 아닙니다**. 재시도만으로 충분한 경우가 대부분이며, 이것이 `scripts/serial_console_capture.py`가 기본적으로 재시도하는 이유입니다.

세션 요청과 챌린지 모두에 단일 토큰을 사용하십시오. `az` 확장과 동일한 방식입니다. 이것이 올바른 방법이지만, 이 문제의 원인은 아닙니다.
</Aside>

## API가 보여줄 수 없는 것들

- **cloud-init** 실행, 실패, 또는 시작되지 않음 — 노드가 등록되지 않는 일반적인 원인.
- `register.ves.volterra.io`에 대한 **등록 시도**, 구성 오류 또는 테넌트가 거부한 토큰 포함.
- 에이전트가 실행되기 전의 **커널 및 부팅 메시지**.
- **작동하는 네트워크 경로가 없는** 노드 — 이는 다른 모든 접근 방법을 무력화합니다.

노드가 `ONLINE` 상태인 경우에는 디버그 API를 사용하십시오: 스크립트로 자동화할 수 있고, 재실행 가능한 증거를 생성하며, 단일 시리얼 포트를 점유하지 않습니다.
