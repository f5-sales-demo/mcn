두 Terraform 변수가 Customer Edge의 소프트웨어를 설정합니다. 운영체제에는 `ce_os_version`,
F5 Distributed Cloud 빌드에는 `ce_sw_version`을 사용합니다. 두 변수 모두 직관적인 해석과
반대로 동작하며, 잘못 사용할 경우 플릿 재구축이라는 비용이 발생합니다.

## 버전 필드의 역할, 두 단계로 나누어

단계를 분리하는 것이 핵심입니다. 혼동하면 동작이 자기 모순적으로 읽힙니다.

**첫 번째 부팅 시, 노드는 `ce_sw_version`에 지정된 빌드를 설치합니다.**
`terraform/modules/ce-node`는 `version = "latest"`로 마켓플레이스 이미지를 배포하므로,
노드가 처음 도착할 때의 빌드는 해당 이미지가 현재 포함하고 있는 것이며, 이는 시간에 따라
변동됩니다. `ce_sw_version`은 노드가 유지될지 여부가 아닌 **목적지**를 선택합니다. 비워
두면 서버가 선택하며, 노드가 현재 위치에 머무는 것이 아닙니다. `ce_os_version`도 마찬가지입니다.

변경 방향이 항상 상위 버전이라고 가정하지 마십시오. `2026-07-28 관찰 기준`, 이미지는
`20260703-e2c462a` 스탬프가 찍힌 빌드를 포함하고 있었는데, 이 플릿의 `crt-20250613-3382`보다
새롭고, 테넌트가 광고하던 `crt-20260201-0179`보다도 새로운 것이었습니다. **이미지가 포함한
것보다 오래된 빌드를 지정하면 노드에게 하위 버전으로 이동하도록 요청하는 것이며, 이는 실패할 수
있습니다** — 아래의 실패 사례를 참조하십시오.

**그 이후에는 자동으로 업그레이드되지 않습니다.** F5 Distributed Cloud는 더 새로운 빌드를
광고하고 기다립니다. 따라서 빈 필드는 "최신 버전 추적"이 아닙니다. 노드는 처음 배치된 위치에
그대로 머뭅니다.

두 단계 모두 사이트 오브젝트에서 확인할 수 있습니다. `2026-07-28 관찰 기준`, 이 플릿:

```text
volterra_software_status.available_version   crt-20260201-0179
operating_system_status.available_version    9.2026.14
```

노드는 `crt-20250613-3382` 및 OS `9.2024.6`을 실행하고 있었습니다. 더 새로운 빌드가 제공되고
있지만 적용되지 않은 상태 — 이것이 중단된 업그레이드가 아닌 정상 상태입니다.

## 버전 변경에는 재구축이 필요하며, Terraform은 이를 대신해 주지 않습니다

`ce_os_version`과 `ce_sw_version`은 모두 **생성 시 한 번만 설정 가능**하며, 실패 방식은
단순히 적용 거부보다 더 심각합니다. 순서대로:

1. 값을 변경하고 apply를 실행합니다. Terraform은 인플레이스 업데이트를 제안합니다.
2. API가 이를 **거부**합니다 — `[BAD_REQUEST] Invalid request parameters`.
3. 거부된 요청이 서버의 해당 필드를 지우며, 프로바이더의 read는 이를 보고하지 않습니다. 이제
   Terraform의 상태가 실제 오브젝트와 불일치합니다.
4. 이후의 모든 plan이 **동일한 실패하는 변경**을 무한히 제안합니다.

따라서 Terraform은 사이트를 교체하는 방향으로 폴백하지 않습니다. 고착되며, 사이트와 CE 가상
머신을 의도적으로 교체할 때까지 그 상태가 유지됩니다. 플릿을 다른 버전으로 이전하는 것은
**계획된 재구축**이며, 적용할 수 있는 편집이 아닙니다.

<Aside type="danger" title="CE 교체의 모든 결과가 적용됩니다">
새로운 SSH 호스트 키, 재할당된 내부 주소, 새로운 등록, 그리고 노드에만 존재하던 모든 항목의
손실. Cloud-init이 새 VM에서 다시 실행되므로 그 방식으로 구성된 SSH 접근은 유지되지만,
cloud-init은 *첫 번째 부팅 시에만* 실행되므로 이전 노드에 수동으로 추가된 모든 것은 사라집니다.

일정을 잡기 전에 호스트 키 및 주소 관련 결과에 대해 [SSH](./access/ssh/)를 읽으십시오.
</Aside>

<Aside type="note" title="보고된 사항, 여기서 재현되지 않음">
거부 및 상태 불일치는 이 저장소의 `terraform/modules/xc-site` 주석에 기록되어 있으며 —
핀 설정 및 해제 양방향으로, 세 사이트 모두에서 검증됨 — 프로바이더 이슈 `xcsh#1387`에도
기록되어 있습니다. 이 페이지는 재테스트하지 않았습니다. 테스트를 수행하면 배포가 모든 plan마다
실패하는 변경을 제안하는 상태로 남기 때문입니다.
</Aside>

## 핀된 빌드는 설치에 실패할 수 있으며, 그 경우 사이트는 고착됩니다

핀을 수락하는 것과 설치하는 것은 다릅니다. `crt-20260201-0179`로 핀된 새로 생성된 단일 노드
Azure Secure Mesh v2 Customer Edge에서, 사이트 오브젝트는 즉시 핀된 버전을 보고했지만 —
그 후 설치에 실패했습니다:

```text
site_state        PROVISIONING
phase             UPGRADE_FAILED
result            Failed
last_installed    (empty)
message           stage: 10, app: voucher obj: voucher objKind: DaemonSet failed ...
                  required replicas: 1, current replicas: 0
```

`2026-07-28 관찰 기준.` **운영체제** 핀은 동일한 실행에서 정상적으로 설치되었으며
(`9.2024.6`에서 `9.2026.14`로, `UPGRADE_COMPLETED`), 소프트웨어 설치만 실패했습니다.
사이트는 `ONLINE`에 도달하지 못했고 `last_installed_version`은 빈 상태로 유지되어,
이전의 성공적인 설치 기록이 없었기 때문에 동작하는 빌드로 롤백되지 않았습니다.

**여기서 얻을 교훈.** 다른 곳에서 실행 중인 버전이라도 해당 사이트의 구성에서 설치된다는 보장은
없습니다. 동일한 빌드가 Secure Mesh v2가 아닌 Azure Customer Edge에서는 `ONLINE` 상태였고,
VMware의 Secure Mesh v2 사이트에서도 `ONLINE` 상태였습니다. 실패한 조합은 Azure *와*
Secure Mesh v2였습니다. 플릿에 적용하기 전에 일회용 사이트에서 버전 변경을 테스트하십시오.
이 방식으로 실패한 플릿은 `PROVISIONING`에 고착되며 재생성만이 유일한 탈출구입니다.

<Aside type="caution" title="이 페이지가 원인을 알려주지 않는 이유">
요청된 빌드가 마켓플레이스 이미지가 포함한 것보다 **오래된** 것이었으므로, 노드는 하위 버전으로
이동하도록 요청받은 것입니다. 이것이 실패에 대한 그럴듯한 설명이지만, **확립된 것은 아닙니다**.
두 버전 문자열(`20260703-e2c462a`와 `crt-20260201-0179`)이 동일한 번호 체계를 공유하는지
알 수 없으며, 비교를 위한 플릿 노드의 캡처도 없었습니다. 실패와 버전 순서는 관찰 결과이며,
그 사이의 연결 고리는 확인되지 않았습니다.
</Aside>

## 문서가 설명하는 빌드

이 사이트의 명령어 레퍼런스는 이 플릿이 실행하는 빌드인 **`crt-20250613-3382`**를 설명합니다.
더 새로운 빌드에만 존재하는 명령어는
`sitecli/command-classification.json`의 `not_on_this_build`에 기록되어 있으며
[더 새로운 빌드의 명령어](./commands/on-box/newer-builds/)로 별도로 문서화되어 있습니다.
따라서 해당 항목에서 여기서 실행 가능한 것으로 읽히는 내용은 없습니다. [온박스 명령어](./commands/on-box/)도 참조하십시오.

<Aside type="caution" title="더 새로운 명령어에 도달하기 위해 재구축을 계획하지 마십시오">
더 새로운 빌드가 제공되고 있으나, 이 토폴로지에서 깔끔하게 설치될지는 불확실합니다 —
단일 노드 Azure Secure Mesh v2 사이트에서 실패했다는 보고와, Customer Edge가 해당 빌드를
실행하고 있다는 반대 관찰이 모두 있습니다. 테넌트에 남아 있는 것으로는 어느 쪽도 확인할 수 없습니다.

버전 변경은 플릿 재구축이므로, 그 불확실성이 핵심 사실입니다. 해당 명령어에 도달하는 것을
예정된 업그레이드가 아닌 미확인 사항으로 취급하십시오. 이를 검증할 증거와 실험은
`sitecli/README.md`에 기록되어 있습니다.
</Aside>
