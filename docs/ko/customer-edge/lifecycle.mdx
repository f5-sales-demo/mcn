두 가지 Terraform 변수가 Customer Edge의 소프트웨어를 설정합니다: 운영 체제를 위한 `ce_os_version`과
F5 Distributed Cloud 빌드를 위한 `ce_sw_version`. 두 변수 모두 직관적인 해석과 반대되는 방식으로 동작합니다 —
빈 필드는 아무것도 없는 것이 아니라 최신 빌드를 가져오며,
한 노드에 설치되는 버전이 디스크가 더 작은 동일한 노드에서는 실패할 수 있습니다.

## 버전 필드의 역할, 두 단계로

단계를 구분하는 것이 핵심입니다. 혼동하면 동작이 자기 모순적으로 읽힙니다.

**첫 번째 부팅 시, 노드는 `ce_sw_version`에 지정된 것을 설치합니다.**
`terraform/modules/ce-node`는 `version = "latest"`로 마켓플레이스 이미지를 배포하므로,
노드가 도착할 때 가지고 있는 빌드는 해당 이미지가 현재 제공하는 것이며 — 이것은 시간이 지남에 따라 변경됩니다.
`ce_sw_version`은 노드가 머물지 여부가 아니라 **목적지**를 선택하며, 비워두면 노드가 그대로 유지되는 것이 아니라 서버가 선택합니다. `ce_os_version`도 마찬가지입니다.

변경 방향이 상향이라고 가정하지 마십시오. `2026-07-28 관측`, 이미지는 `20260703-e2c462a`로 표시된 빌드를 제공했는데 — 이 플리트의 `crt-20250613-3382`보다 새롭고 테넌트가 광고하던 `crt-20260201-0179`보다도 새로운 버전입니다. 이미지가 가진 것보다 오래된 빌드를 지정하면 노드가 이전 버전으로 이동하도록 요청하는 것이며, 이는 일상적인 일입니다: 이 플리트는 그렇게 생성되었으며 실행 중입니다.

**버전 필드를 비워두는 것은 중립적인 선택이 아니라 가장 위험한 선택입니다.** 생성 시 서버는 빈 필드를 그대로 두지 않습니다 — **광고된 최신** 버전으로 채우고 설치합니다. 두 필드를 모두 설정하지 않고 생성된 사이트는 테넌트가 광고하던 두 버전인 `crt-20260201-0179`와 OS `9.2026.14`로 고정되어 돌아왔으며, 설치는 이후 실패했습니다. `2026-07-29 관측`.

두 가지 결과가 있습니다. 비워두면 "최신 버전을 주세요"를 의미하므로, 고정되지 않은 배포는 아래에 설명된 디스크 한도에 가장 많이 직면할 가능성이 있습니다. 그리고 다른 필드를 비워두어 한 필드를 독립적으로 설정할 수 없습니다. 서버가 채우기 때문입니다 — 두 필드를 모두 의도적으로 설정하거나, 각각의 최신 버전을 수용하십시오.

**첫 번째 부팅 이후에는 자동으로 업그레이드되지 않습니다.** F5 Distributed Cloud는 더 새로운 빌드를 광고하고 기다립니다. "노드가 도착한 곳에 그대로 유지된다"는 것은 생성 중이 아니라 생성 후에 해당합니다.

두 단계 모두 사이트 객체에서 확인할 수 있습니다. `2026-07-28 관측`, 이 플리트:

```text
volterra_software_status.available_version   crt-20260201-0179
operating_system_status.available_version    9.2026.14
```

노드는 `crt-20250613-3382`와 OS `9.2024.6`으로 실행 중입니다. 더 새로운 빌드가 제공되고 있지만 적용되지 않은 상태 — 중단된 업그레이드가 아닌 정상 상태입니다.

## Terraform은 버전을 변경할 수 없습니다. API는 가능합니다

이것은 두 가지 별개의 사실이며, 혼동하면 잘못된 계획을 세우게 됩니다.

**Terraform은 불가능합니다.** `ce_os_version`과 `ce_sw_version`은 사실상 생성 시에만 적용됩니다.
둘 중 하나를 변경하고 적용하면 API는 `[BAD_REQUEST] Invalid request parameters`로 업데이트를 거부합니다. `2026-07-29 관측` 일회용 사이트에서, 세 가지 방향 모두 — 더 새로운 빌드로 **고정 전진**, 이전 빌드로 **고정 후진**, 그리고 두 필드를 모두 지워서 **고정 해제**. 전진은 특별한 경우가 아닙니다.

**API는 가능합니다.** F5 Distributed Cloud는 사이트별 전용 업그레이드 작업을 제공하며, 이는 재구성 없이, Terraform 없이 변경을 현재 위치에서 시작합니다:

```bash
# 소프트웨어 빌드
curl -X POST -H "Authorization: APIToken $TOKEN" -H 'Content-Type: application/json' \
  --data '{"version": "<software-version>"}' \
  "$API_URL/api/config/namespaces/system/sites/<site-name>/upgrade_sw"

# 운영 체제
curl -X POST -H "Authorization: APIToken $TOKEN" -H 'Content-Type: application/json' \
  --data '{"version": "<os-version>"}' \
  "$API_URL/api/config/namespaces/system/sites/<site-name>/upgrade_os"
```

`2026-07-29 관측`: 소프트웨어 호출은 `200`을 반환했고, 사이트는 `deployment_state.phase`가 `UPGRADE_IN_PROGRESS`인 `UPGRADING` 상태로 전환되었으며, 사이트 객체의 요청된 버전은 게시된 버전으로 변경되었습니다. 필드를 생략하면 `version empty in the request`와 함께 `400`을 반환하며, 이를 통해 필드 이름이 확인되었습니다.

**몇 분이 아닌 몇 시간을 예상하고, 실패에 당황하지 마십시오.** 기본 디스크 노드에서 `crt-20260201-0179`로의 업그레이드는 약 한 시간 동안 실행되었고, 중간에 `result`가 `Failed`인 `UPGRADE_FAILED`를 보고했지만 **새 빌드에서 성공적으로 완료되었습니다**. 플랫폼이 재시도합니다.

이것은 업그레이드를 모니터링하거나 스크립팅하는 사람에게 직접적인 결과를 가져옵니다: `Failed` 결과는 통과해야 할 상태이지 최종 판단이 아닙니다. 첫 번째 결과를 최종으로 처리하면 성공할 업그레이드를 실패로 보고하게 됩니다.

해당 경로의 그룹에 주의하십시오: 이것들은 `operate`가 아닌 **`config`** 아래에 있습니다. `operate` 아래의 동일한 경로는 `404 API Group could not be determined`를 반환하는데, 이것은 라우팅 메시지이지 업그레이드가 존재하지 않는다는 의미가 아닙니다 — 이 프로젝트가 잘못된 결론을 내리게 한 구분입니다.

<Aside type="caution" title="API를 통한 업그레이드는 Terraform과 불일치 상태를 만듭니다">
고정된 변수는 여전히 이전에 설정된 값을 말하므로, 현재 사이트는 구성에 명시되지 않은 버전으로 실행됩니다. Terraform은 이를 조정하지 않습니다 — 업데이트가 거부되므로 불가능합니다 — 따라서 API 업그레이드를 Terraform 제어 밖의 의도적인 단계로 처리하고, 다음 재구성 시 일치하도록 핀을 업데이트하십시오.
</Aside>

<Aside type="note" title="이 페이지의 이전 두 가지 주장, 철회됨">
이 페이지는 이전에 CE를 다른 버전으로 이동하려면 사이트를 재생성해야 한다고 했으며, 거부된 업데이트가 "서버에서 필드를 지워" Terraform이 영원히 실패하는 변경을 제안하게 된다고 했습니다. 두 가지 모두 테스트를 통해 살아남지 못했습니다: 위의 API 업그레이드는 아무것도 재생성하지 않고 현재 위치에서 버전 변경을 시작하며, 세 가지 거부된 업데이트 각각 후에 사이트 스펙은 **변경되지 않았고** 사이트는 `ONLINE` 상태를 유지했습니다. 프로바이더 이슈 `xcsh#1387`에서 설명된 불일치는 이미 핀보다 자동 업그레이드된 사이트에서 관측되었으므로, 그 불일치 시작 상태가 필요할 수 있습니다; 스펙이 핀과 일치하는 사이트에서는 재현되지 않았습니다.
</Aside>

업그레이드 대신 재구성을 선택한다면, CE 교체의 모든 결과가 적용됩니다.

<Aside type="danger" title="CE 교체의 모든 결과가 적용됩니다">
새 SSH 호스트 키, 재할당된 내부 주소, 새 등록, 그리고 노드에만 존재했던 모든 것의 손실. Cloud-init이 새 VM에서 다시 실행되므로 그 방식으로 구성된 SSH 액세스는 유지됩니다 — 하지만 첫 번째 부팅 시에만 실행되므로, 이전 노드에 수동으로 추가된 모든 것은 사라집니다.

이를 예약하기 전에 호스트 키 및 주소 관련 결과에 대해 [SSH](./access/ssh/)를 읽으십시오.
</Aside>

## 고정된 빌드는 설치에 실패할 수 있으며, 사이트는 이후 멈춥니다

핀을 수락하는 것은 설치하는 것과 동일하지 않습니다. `crt-20260201-0179`로 고정된 새로 생성된 단일 노드 Azure Secure Mesh v2 Customer Edge에서, 사이트 객체는 즉시 고정된 버전을 보고했지만 — 설치가 이후 실패했습니다:

```text
site_state        PROVISIONING
phase             UPGRADE_FAILED
result            Failed
last_installed    (empty)
message           stage: 10, app: voucher obj: voucher objKind: DaemonSet failed ...
                  required replicas: 1, current replicas: 0
```

`2026-07-28 관측`, 2026-07-29에 두 번 재현. **운영 체제** 핀은 동일한 실행에서 정상적으로 설치되었습니다(`9.2024.6`에서 `9.2026.14`로, `UPGRADE_COMPLETED`); 소프트웨어 설치만 실패했습니다. 사이트는 `ONLINE`에 도달하지 못했고 `last_installed_version`은 비어 있었으므로, 작동 중인 빌드로 롤백되지 않았습니다 — 롤백할 이전의 성공적인 설치가 없었습니다.

**생성 시 실패는 업그레이드 중 실패와 다릅니다.** 두 가지는 다르게 동작하며, 개입 여부를 결정할 때 이 차이가 중요합니다:

| | 생성 시 | API 업그레이드 중 |
| --- | --- | --- |
| 재시도로 성공하는가? | 아니요 — 두 번 모두 20분 이상 `Failed` 유지 | 예 — 복구되어 완료됨 |
| 노드는 어디에 있는가? | `PROVISIONING`, 아무것도 설치되지 않음 | 작동 중인 빌드에서 `ONLINE` |
| 그대로 두어도 안전한가? | 아니요, 멈춰 있습니다 | 예, 복구되거나 이전 빌드를 유지합니다 |

따라서 생성 시 실패는 더 큰 디스크로 재구성이 필요하고, 업그레이드가 `Failed`를 보고하면 결론을 내리기 전에 잠시 기다려야 합니다.

**원인은 버전이 아니라 디스크입니다.** 소프트웨어 × OS × 디스크 크기의 매트릭스로, 동일한 마켓플레이스 이미지에서 조합당 일회용 단일 노드 Azure Secure Mesh v2 사이트 하나씩, 이를 분리합니다. `2026-07-29 관측`:

| 소프트웨어 | OS `9.2024.6` (이미지가 제공하는 버전) | OS `9.2026.14` |
| --- | --- | --- |
| `crt-20250613-3382` | 설치됨 | 설치됨 |
| `crt-20260201-0179` | 설치됨 | **실패**, 기본 디스크에서만 |

어느 버전도 단독으로는 실패하지 않습니다. 쌍만이 실패하며, 이미지의 기본 디스크에서만 그렇습니다 — 동일한 쌍은 **40 GB**, **48 GB**, **64 GB**에서 설치됩니다. 따라서 더 새로운 빌드가 여기서 지원되지 않는 것도 아니고, 더 새로운 운영 체제도 마찬가지입니다; 함께 사용하면 기본 노드가 가진 것보다 더 많은 디스크가 필요합니다.

`terraform/modules/ce-node`는 `disk_size_gb`를 설정하지 않으므로, 모든 Customer Edge는 이미지 기본값을 사용합니다. **더 새로운 쌍을 실행하려면 디스크를 확대하십시오.** 40 GB는 테스트된 가장 작은 크기로 작동합니다; 정확한 경계는 이미지 기본값과 40 GB 사이에 있으며 더 이상 좁히지 않았습니다.

플리트에 적용하기 전에 일회용 사이트에서 버전 변경을 테스트하십시오: 이 방식으로 실패하는 플리트는 재생성만이 유일한 출구인 `PROVISIONING`에 멈추게 됩니다.

<Aside type="caution" title="F5의 업그레이드 전 수치로 디스크 크기를 정하지 마십시오">
F5의 문서화된 업그레이드 전 점검은 20 GB에 용량의 15%를 더한 여유 공간을 요구합니다. 해당 점검은 **콘솔 UI** 업그레이드를 제어하며 API로 시작된 업그레이드에는 명시적으로 적용되지 않으므로, 이 실패를 설명하지 않습니다. 여기에 적용하면 48 GB 디스크가 실패할 것이라고 예측합니다; 48 GB는 정상적으로 설치됩니다. 해당 공식이 아닌 위의 측정된 결과를 기반으로 크기를 정하십시오.
</Aside>

<Aside type="note" title="이 페이지가 이전에 제시한 설명, 이제 철회됨">
이 페이지의 이전 버전은 요청된 빌드가 이미지의 빌드보다 오래되었기 때문에 설치가 실패했다고 제안했습니다 — 노드가 이전 버전으로 이동하도록 요청받았다는 것입니다. 이것은 잘못되었습니다. 이 플리트는 **13개월** 이상 오래된 핀으로 동일한 이미지에서 생성되어 정상적으로 설치되었으며, `crt-20260201-0179`도 OS 핀이 이미지 자체 버전으로 유지될 때는 설치됩니다. 이동 방향은 변수가 아닙니다.
</Aside>

## 문서가 설명하는 빌드
