이 배포는 CE 앞단에 Azure 로드 밸런서를 두지 않고 **Azure에서의 액티브/액티브 Customer Edge 고가용성**을
보여줍니다. 세 개의 CE가 각각 동일한 호스트 경로를 eBGP로 광고하고, Azure Route Server는 세 경로 모두를
VNet 내 동일 비용 넥스트 홉으로 설치합니다. 따라서 트래픽 분산과 장애 노드 제거는 로드 밸런서가 아니라
라우팅 패브릭에서 일어나도록 설계되어 있습니다.

아래에 표시된 모든 내용은 실제 배포 환경에서 실행되었으며, 출력은 실제로 생성된 출력입니다. 그 문장이
*포함하지 않는* 것 — 페일오버, 트래픽이 세 넥스트 홉에 어떻게 나뉘는지, 그리고 새로 빌드한 환경에서 VIP가
잠시 패킷을 잃는 이유 — 은 가정에 맡기지 않고 명시적으로 언급합니다.

## 배포되는 것

```text
                  Azure Route Server  ce-ha-lab-rrs  ASN 65515
                          10.0.4.4  and  10.0.4.5
                                      |
              +-----------------------+-----------------------+
              |                       |                       |
        eastus01-bgp            eastus02-bgp            eastus03-bgp     eBGP
              |                       |                       |      CE ASN 64512
        10.0.1.4                10.0.1.5                10.0.1.6     <- CE eth0 / SLO
     f5-xc-ce-vm-01          f5-xc-ce-vm-02          f5-xc-ce-vm-03
    ar-bgp-eastus01         ar-bgp-eastus02         ar-bgp-eastus03
              |                       |                       |
              +----- each advertises 10.250.0.10/32 -----------+
                          three-way ECMP into the VNet
```

| 구성 항목 | 구축 상태 |
| --- | --- |
| F5 Distributed Cloud 테넌트 | `f5-sales-demo` — `https://f5-sales-demo.console.ves.volterra.io` |
| 네임스페이스 | 사이트는 `system`에, 오리진 풀과 로드 밸런서는 `multi-cloud-networking`에 |
| Customer Edge | 3개의 단일 노드 Secure Mesh v2 사이트 — `ar-bgp-eastus01`, `ar-bgp-eastus02`, `ar-bgp-eastus03` |
| CE 소프트웨어 | 고정된 `9.2024.6`, 빌드 `crt-20250613-3382` |
| Azure VM | `f5-xc-ce-vm-01/02/03`, 각각 3개의 NIC (관리/SLO, 외부, 내부/SLI) |
| 경로 교환 | Azure Route Server `ce-ha-lab-rrs`, ASN `65515`, 인스턴스 `10.0.4.4` 및 `10.0.4.5` |
| 피어링 | CE당 하나 — `eastus01-bgp`, `eastus02-bgp`, `eastus03-bgp` — CE ASN `64512` |
| 광고되는 VIP | `10.250.0.10/32`, 세 CE 모두가 동일하게 광고 |
| 로드 밸런서 | `ar-bgp-ecmp-lb`, 도메인 `ar-bgp-ecmp.bankexample.com` 서비스 |
| 테스트 클라이언트 | `ar-ecmp-client`, 동일 VNet 내부의 VM |
| 리소스 그룹 | `rg-mcn-ce-ha-rmordasiewicz` |

<Aside type="caution" title="VIP는 모든 VNet CIDR 밖에 위치해야 합니다">
`terraform/main.tf`에는 VIP가 허브와 스포크 CIDR 양쪽 모두의 밖에 있음을 검증하고, 그렇지 않으면 플랜을
거부하는 `check` 블록이 있습니다. 그 이유는 VNet CIDR 내부에 있는 VIP는 BGP 경로가 더 구체적이더라도
VNet 자체의 시스템 경로에 밀리기 때문입니다.

이 가드를 계약으로 취급하십시오. 이 데모를 다른 주소 체계로 재지정한다면, VIP도 함께 VNet 범위 밖으로
이동해야 합니다.
</Aside>

## 테넌트는 셸이 무엇을 export하든 무관하게 구성으로 결정됩니다

`var.expected_xc_tenant`가 테넌트를 지정하며, 기본값은 `f5-sales-demo`이고, 테넌트가 지정되는 유일한
위치입니다. `providers.tf`는 여기서 `xcsh` 프로바이더의 `api_url`을 파생시키며, 이는 환경의
`XCSH_API_URL`을 의도적으로 무시합니다. 그리고 `terraform/main.tf`의 `postcondition`은 환경이 다른
테넌트를 지정할 때 **플랜**을 실패시킵니다.

상태를 변경하는 작업 없이 양쪽 값을 모두 확인할 수 있습니다.

```bash
cd terraform
terraform output -raw xc_tenant       # what the deployment targets
terraform output -raw xc_env_tenant   # what your shell claims — diagnostic only
```

```text
f5-sales-demo
f5-sales-demo
```

<Aside type="danger" title="이 가드레일은 데모가 조용히 잘못된 테넌트로 재등록된 사건 때문에 존재합니다">
MCN 데모는 `f5-sales-demo`에 구축되었습니다. 이후 자격 증명 파일이 `f5-amer-ent`의 `XCSH_API_URL`을
export하기 시작했고, 이후의 apply가 해당 테넌트용 토큰을 발급했으며, CE VM들이 거기에 재등록되면서
`f5-sales-demo`의 등록은 버려졌습니다. 그 사이의 모든 플랜은 깨끗했습니다. 구성에 테넌트에 대한 판단이
전혀 없었기 때문입니다
([issue 696](https://github.com/f5-sales-demo/mcn/issues/696), [PR 697](https://github.com/f5-sales-demo/mcn/pull/697)에서 수정).
복구를 위해서는 잘못된 테넌트의 스택을 파괴하고 올바른 테넌트에 다시 구축해야 했습니다.

인지해야 할 증상은 스스로를 설명해주지 않기 때문에 언급합니다. 다른 테넌트용으로 발급된 토큰은 고정된
엔드포인트에서 아무 설명 없는 `401`로 실패하며, 이는 만료된 자격 증명과 똑같이 보입니다. 정상이라고
믿는 자격 증명이 `401`을 반환한다면, 다른 토큰을 발급하기 전에 위의 두 출력을 비교하십시오.
</Aside>

## 발표 전에 정상 상태임을 입증하십시오

네 가지 점검을 이 순서로 수행합니다. 각 점검은 결함의 위치를 좁혀주므로, 실패는 단순히 "무언가 잘못되었다"
이상의 정보를 알려줍니다.

<Steps>

1. **세 사이트가 모두 `ONLINE`입니다.** 이것이 아니라면 그 이후의 어떤 것도 참일 수 없습니다.

   ```bash
   for s in ar-bgp-eastus01 ar-bgp-eastus02 ar-bgp-eastus03; do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **모든 피어링이 해당 CE의 VIP 광고를 학습하고 있습니다.** 각 피어링을 개별적으로 조회하십시오 —
   아래 함정 항목을 참고하십시오. 데모가 고장난 것처럼 보이지만 실제로는 아닌 경우가 여기서 가장 자주
   발생합니다.

   ```bash
   for p in eastus01-bgp eastus02-bgp eastus03-bgp; do
     echo "--- $p"
     az network routeserver peering list-learned-routes \
       --name "$p" --routeserver ce-ha-lab-rrs -g rg-mcn-ce-ha-rmordasiewicz \
       --query "RouteServiceRole_IN_0[].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp

   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp

   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   세 개의 피어링, 세 개의 서로 다른 넥스트 홉, 하나의 프리픽스. 이것으로 ECMP의 광고 측면이 입증됩니다.

3. **클라이언트의 유효 경로가 세 넥스트 홉을 모두 포함합니다.** 이것이 VNet이 프로그래밍한 ECMP 자체입니다.
   CE가 주장하는 내용이 아니라 Azure가 그것으로 실제 수행한 결과입니다.

   ```bash
   az network nic show-effective-route-table \
     --name ar-ecmp-clientVMNic -g rg-mcn-ce-ha-rmordasiewicz \
     --query "value[?addressPrefix[0]=='10.250.0.10/32']" -o json
   ```

   ```json
   [
     {
       "addressPrefix": ["10.250.0.10/32"],
       "nextHopIpAddress": ["10.0.1.5", "10.0.1.4", "10.0.1.6"],
       "nextHopType": "VirtualNetworkGateway",
       "source": "VirtualNetworkGateway",
       "state": "Active"
     }
   ]
   ```

   `nextHopIpAddress`에 세 항목이 있고 `state: Active`인 것이 점검 기준입니다. **그 세 항목의 순서는
   의미가 없으며 안정적이지도 않습니다** — Azure는 호출마다 다른 순서로 반환하므로, 목록을 이전 실행과
   비교하지 말고 개수를 세십시오. 세 개를 기대하는 자리에 하나의 넥스트 홉만 있다면 어떤 CE가 광고를
   중단한 것이며, 2단계가 어느 CE인지 알려줍니다.

4. **VIP가 트래픽을 서비스합니다.** 클라이언트 VM에서, 그리고 **`Host` 헤더와 함께** 수행하십시오 —
   아래 두 번째 함정을 참고하십시오. 문제를 발견할 만큼 충분히 많은 요청을 샘플링하십시오. 수십 건
   정도는 아래에서 설명하는 수렴 구간 동안에도 100 %로 보입니다.

   ```bash
   az vm run-command invoke -g rg-mcn-ce-ha-rmordasiewicz -n ar-ecmp-client \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts 'ok=0; fail=0
                for i in $(seq 1 60); do
                  c=$(curl -s -o /dev/null -m 5 -w "%{http_code}" \
                        -H "Host: ar-bgp-ecmp.bankexample.com" http://10.250.0.10/)
                  [ "$c" = 200 ] && ok=$((ok+1)) || fail=$((fail+1))
                done
                echo "OK=$ok FAIL=$fail"'
   ```

   ```text
   OK=60 FAIL=0
   ```

</Steps>

## 함정: 하나의 피어링이 하나의 경로만 보여주며, 그것이 정상입니다

`list-learned-routes`는 지정한 피어링으로 범위가 한정됩니다. Route Server의 전체 테이블이 아니라
**해당** 피어가 광고한 내용을 보고합니다.

따라서 `eastus01-bgp`만 조회하면 `10.0.1.4`를 통한 단일 `10.250.0.10/32`가 반환되며, 이를 "CE 하나만
광고 중 — 나머지 둘은 다운"으로 읽고 싶어집니다. 다운된 것은 없습니다. 나머지 두 광고는 각자의 피어링에서
확인되며, 위 2단계가 바로 그것을 순회합니다.

단일 피어링 조회로 ECMP를 확인하는 것은 불가능합니다. 세 피어링 모두를 순회하거나, 병합된 결과를 한 번의
호출로 보여주는 클라이언트의 유효 경로 테이블을 읽으십시오.

## 함정: IP만으로 요청하면 404가 반환됩니다

로드 밸런서는 `Host`로 매칭합니다. VIP는 주소로 접속하는 누구에게나 무언가를 서비스하는 가상 서버가
아닙니다.

```text
curl -H 'Host: ar-bgp-ecmp.bankexample.com' http://10.250.0.10/   ->  200   (10 of 10)
curl                                        http://10.250.0.10/   ->  404
```

두 결과 모두 정상 배포 환경에서 동일한 실행으로 생성되었습니다. **IP만으로 요청했을 때의 404는 경로가
동작한다는 증거입니다** — 요청이 CE에 도달했고, CE의 프록시가 응답했으며, 매칭되는 구성 도메인이 없어
거부한 것입니다. 이를 장애로 해석하면 BGP를 들여다보게 되지만, 거기서는 잘못된 점을 찾을 수 없습니다.

데모 중에도 동일합니다. 도메인을 해석하는 대신 브라우저에 주소를 직접 입력하면 404를 받게 됩니다.

## VIP는 처음 45분 동안 요청을 일부 버리고, 그 후 멈춥니다

새로 구축한 스택에서 VIP는 CE가 `ONLINE`에 도달한 후 대략 처음 45분 동안 소수의 요청을 잃고, 그 이후에는
깨끗하게 서비스합니다. `ar-ecmp-client`에서 모두 `Host` 헤더와 함께 1,470건의 요청으로 측정한 결과는
다음과 같습니다.

| 구간 | 요청 수 | 실패 수 | 비율 |
| --- | --- | --- | --- |
| ECMP가 올라온 후 처음 약 45분 | 570 | 12 | **2.11 %** |
| 그 다음 23분 | 900 | **0** | **0.00 %** |

모든 실패는 `curl: (28)` — 수신 바이트 0의 타임아웃 — 이었으며 HTTP 오류 상태가 아니었습니다. 마지막
실패는 ECMP가 올라온 후 약 43분에 발생했습니다. 정상 처리된 900건 중 400건은 30초 타임아웃으로 실행되었고
모두 2초 이내에 완료되었으므로, 짧은 타임아웃 때문에 무언가가 숨겨진 것은 아닙니다.

**오리진이 원인은 아니었습니다.** 오리진으로 직접 향하는 대조 배치(`http://20.98.232.135/`, VIP 우회)는
실패하는 VIP 배치와 *동시에* 120건 중 120건이 정상이었습니다. 결함은 VIP, ECMP 또는 CE 경로 어딘가에
있습니다.

이것을 의도적으로 이렇게 부르지 않는 두 가지가 있습니다.

- **정상 상태의 결함이 아닙니다.** 완전히 해소되고 그 상태를 유지합니다. 한 시간 동안 가동된 데모에는 이
  문제가 없습니다 — 위 점검에서 60건 중 60건 성공했고, 재구축한 스택에서도 다시 깨끗하게 재현되었습니다.
- **특정 CE에 귀속시킬 수 없습니다.** 이 토폴로지에는 노드별 HTTP 리스너가 없으므로, 버려진 요청을 그것을
  버린 노드에 결부시킬 방법이 없습니다. CE 외부 인터페이스(`10.0.2.x`)에는 HTTP 리스너가 전혀 없으며,
  VIP `/32`만 응답합니다.

다른 테넌트에서 새로 재구축했을 때에도 재현되었으므로, 환경보다는 토폴로지에 따르는 현상입니다.

<Aside type="caution" title="40건을 샘플링하고 정상이라고 결론 내리지 마십시오">
40~50건 배치는 실패 구간 안에서도 대부분 100 %로 보입니다. 그래서 이 현상이 처음에는 지속적인 저비율
결함으로, 그다음에는 결함이 전혀 없는 것으로 잘못 규정되었습니다. 시간 간격을 둔 배치로 100건 이상을
샘플링하십시오.
</Aside>

## 등록 승인은 자동화되어 있으나, apply는 여전히 2단계입니다

등록 승인에는 더 이상 콘솔에서 사람이 개입할 필요가 없습니다. 프로바이더 **v3.81.1**에서
`xcsh_registration_approval` 리소스가 이를 수행하며, 사이트 모듈이 어떤 등록을 승인할지 해석합니다.

그렇다고 해서 배포가 단일 무인 `apply`가 되는 것은 아니며, 첫 실행을 지켜보고 실패했다고 결론 내리기 전에
그 이유를 이해할 필요가 있습니다.

- CE의 등록 객체 이름은 **`r-<uuid>`**입니다. 사이트 이름을 따르지 않으므로, 플랜 시점에 이름을 예측할
  수 있는 방법이 없습니다.
- 등록은 VM이 부팅되고 `vpm`이 등록한 후에만 존재합니다.
- 따라서 **첫 apply는 승인을 전혀 계획하지 않습니다.** CE가 등록되고 승인이 생성된 후 다시 apply하십시오.

`terraform/main.tf`는 파일 상단에 이 순서를 문서화하고 있으며, 그것이 권위 있는 버전입니다 — 배포 순서는
그것을 구현하는 코드와 함께 존재합니다.

<Aside type="caution" title="새로 만든 사이트는 operate API로 즉시 접근할 수 없습니다">
새 사이트가 `ONLINE`을 보고한 후 대략 25~30분 동안 `vpm/debug` 엔드포인트는 `The requested URL was rejected`가
표시된 BIG-IP `503` 페이지로 응답합니다. 웹 애플리케이션 방화벽 차단이나 폐기된 토큰처럼 보이지만 둘 다
아닙니다. 기다린 후 재시도하십시오.

이는 새로 구축한 데모에 영향을 주며, 이미 실행 중인 데모에는 해당하지 않습니다.
</Aside>

## Site CLI 접근

일상적인 온박스 진단은 디버그 API를 통해 이루어지며, 여기에 이미 스크립트로 작성되어 있습니다.
명령 인터페이스가 문서에서 설명하는 것과 여전히 일치하는지 확인하십시오.

```bash
bash scripts/capture-sitecli.sh --check --site ar-bgp-eastus01 --node f5-xc-ce-vm-01
```

```text
catalog matches the live CE (build crt-20250613-3382, 34 commands)
```

`--check`는 아무것도 기록하지 않으므로 실제 데모 환경에서도 안전합니다.

해당 API가 중계하지 않는 명령을 위해, 이 배포에는 로그인 셸이 Site CLI인 **어플라이언스 `admin` 계정에 대한
운영자 SSH**도 있습니다. 세 CE 모두에서 검증되었습니다. VNet 내부의 호스트에서 내부(SLI) 주소로 접속하며,
터미널을 할당하십시오.

<Aside type="danger" title="CE 내부 주소를 하드코딩하지 마십시오 — 재구축마다 재할당됩니다">
Azure는 내부 서브넷에서 어떤 CE가 어떤 주소를 갖는지 보존하지 않습니다. 가장 최근 재구축 후
`f5-xc-ce-vm-01`, `-02`, `-03`은 각각 `10.0.3.7`, `10.0.3.5`, `10.0.3.4`를 보유합니다. 노드 순서도 아니고,
연속적이지도 않으며, 이전에 보유했던 것과도 다릅니다. 테스트 클라이언트의 NIC도 같은 서브넷에 있으며,
이전에 어떤 CE가 보유했던 주소를 가진 적이 있습니다.

기억하지 말고 읽어오십시오.

```bash
cd terraform
terraform output -json ce_sli_private_ips
```

```json
{"eastus01":"10.0.3.7","eastus02":"10.0.3.5","eastus03":"10.0.3.4"}
```

Terraform 상태를 사용할 수 없다면, *실제로* 안정적인 NIC 이름으로 원하는 주소를 Azure에 문의하십시오.

```bash
az network nic show -g rg-mcn-ce-ha-rmordasiewicz \
  -n f5-xc-ce-vm-01-internal-nic \
  --query ipConfigurations[0].privateIPAddress -o tsv
```

</Aside>

```bash
SLI=$(terraform output -json ce_sli_private_ips | jq -r '.eastus01')
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<vm-in-vnet> "admin@$SLI"
```

```text
Registration Status: PROVISIONED
SLO IP: 10.0.1.4/26
WELCOME IN SITE CLI
```

<Aside type="caution" title="이 접근 권한은 해당 CE들이 그렇게 구축되었기 때문에 존재합니다 — 나중에 추가할 수 없습니다">
운영자 키는 첫 부팅 시 한 번만 실행되는 cloud-init `write_files`에 의해 기록됩니다. `custom_data`는
교체만 가능하므로, 이미 실행 중인 CE에 이를 도입하면 **모든 CE VM이 교체됩니다**. 그것은 구성 변경이 아니라
플릿 재구축입니다.

과거에는 그보다 더 나빴습니다. 교체된 CE는 결코 재등록할 수 없었는데, 파괴된 노드의 등록이 여전히
컨트롤 플레인의 고유 `(tenant, cluster_name, hostname)` 인덱스를 점유하고 있었기 때문입니다. 그리고
플릿이 다운된 내내 `terraform plan`은 "No changes"를 보고했습니다. 복구에는 두 번의 완전한 재구축이
필요했습니다. 이는 수정되었습니다
([issue 674](https://github.com/f5-sales-demo/mcn/issues/674), [PR 693](https://github.com/f5-sales-demo/mcn/pull/693)으로 종료):
사이트 객체의 라이프사이클이 이제 CE VM 인스턴스와 결합되어 있어, VM을 교체하면 사이트도 교체되고,
사이트를 삭제하면 교체 노드가 부팅되기 전에 그 등록들도 함께 제거됩니다.

이 배포에는 해당 변경이 이미 적용되어 있고 플릿은 정상입니다. 다른 환경에서 이를 도입하려는 사람은 먼저
[SSH 페이지](../customer-edge/access/ssh/)를 읽어야 합니다.
</Aside>

## 두 가지 추가 측정 함정

두 가지 모두 이 환경에서 확신에 찬 잘못된 답을 만들어냈으며, 어느 쪽도 명확하지 않습니다.

- **워크스테이션이 아니라 VNet 내부에서 프로브하십시오.** Netskope는 일반적인 포트에서 TCP 핸드셰이크를
  스스로 완료하므로, 워크스테이션에서의 프로브는 실제로 닫혀 있는 포트를 **열림**으로 보고합니다. 워크스테이션
  에서는 CE 공용 주소의 80, 443 포트가 열림으로 보이지만, VNet 내부에서 프로브하면 닫혀 있습니다.
  `ar-ecmp-client`를 사용하십시오.
- **CE의 22번 포트는 내부(SLI) 주소에서만 응답합니다.** `ar-ecmp-client`에서 프로브했을 때 각 CE의 내부
  주소는 `SSH-2.0-OpenSSH_8.7`을 반환하지만, 관리 및 외부 주소는 타임아웃됩니다 — 대조군으로 사용한 미사용
  주소와 동일합니다. eth0은 `a-i-eth0`으로 이름이 변경되었고 데이터패스가 소유하기 때문에 호스트 IP를 갖지
  않습니다. 따라서 노드를 식별하는 데 사용하는 주소를 프로브하는 것은 그 노드의 SSH 상태에 대해 아무것도
  알려주지 않으며, 접속해야 하는 것은 SLI 주소입니다. 그 주소는
  `terraform output -json ce_sli_private_ips`에서 얻으십시오. 테스트 클라이언트의 NIC도 내부 서브넷에
  있으므로, 내부 서브넷이 CE만의 것이라고 가정하지 마십시오.

<Aside type="note" title="이 페이지가 주장하지 않는 것">
독자가 여기서 합리적으로 기대할 수 있는 세 가지가 없습니다. 배포 환경에서 실제로 수행되지 않았기 때문입니다.

- **페일오버는 테스트되지 않았습니다.** 세 개의 동일 비용 넥스트 홉이 설치되었음은 검증되었지만, CE 하나를
  중지했을 때 경로 테이블에 무슨 일이 일어나는지는 제시되지 않았습니다. 따라서 먼저 직접 시도해보지 않은
  채 이 페이지만으로 페일오버 데모를 준비하지 마십시오.
- **세 넥스트 홉에 걸친 트래픽 분산은 측정되지 않았습니다.** 위에서 VIP로 향한 1,470건의 요청이 집계되어
  있으며, 이는 경로가 동작한다는 것과 시간에 따른 동작 방식을 확인해 줍니다. 그러나 그중 어느 것도 그
  요청들이 세 넥스트 홉에 어떻게 분산되었는지 보여주지 않으며, 이 토폴로지에는 그것을 귀속시킬 노드별
  HTTP 리스너가 없습니다.
- **수렴 과도 현상의 원인은 규명되지 않았습니다.** 언제 발생하는지, 얼마나 지속되는지, 그 기간 내내 오리진이
  깨끗하다는 것까지 특성화되었을 뿐이며, 설명되지는 않았습니다.

</Aside>
