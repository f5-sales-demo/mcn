이 배포는 CE 앞단에 Azure 로드 밸런서를 두지 않은 상태에서 **Azure의 액티브/액티브 Customer Edge 고가용성**을 시연합니다. 3개의 CE가 각각 동일한 호스트 경로를 eBGP로 오리진하고, Azure Route Server는 이 3개를 모두 VNet 내의 동일 비용 넥스트 홉으로 설치합니다. 따라서 트래픽 분산과 실패한 노드의 제거가 이루어지는 지점은 로드 밸런서가 아니라 라우팅 패브릭입니다.

아래에 표시된 모든 것은 실제 배포 환경에서 실행되었으며, 출력은 그 실행이 생성한 출력 그대로입니다. 그 문장이 다루지 *않는* 두 가지 — 페일오버와 트래픽 분산 — 은 추측에 맡기지 않고 문서 끝에서 명시적으로 언급합니다.

## 배포 구성

```text
                  Azure Route Server  ce-ha-lab-rrs  ASN 65515
                          10.0.4.4  and  10.0.4.5
                                      |
              +-----------------------+-----------------------+
              |                       |                       |
        eastus01-bgp            eastus02-bgp            eastus03-bgp     eBGP
              |                       |                       |      CE ASN 64512
        10.0.1.4                10.0.1.5                10.0.1.6     <- CE eth0 / SLO
     f5-xc-ce-vm-01          f5-xc-ce-vm-02          f5-xc-ce-vm-03
    ar-bgp-eastus01         ar-bgp-eastus02         ar-bgp-eastus03
              |                       |                       |
              +----- each advertises 10.250.0.10/32 -----------+
                          three-way ECMP into the VNet
```

| 구성 항목 | 실제 구축 내용 |
| --- | --- |
| Customer Edge | 3개의 단일 노드 Secure Mesh v2 사이트 — `ar-bgp-eastus01`, `ar-bgp-eastus02`, `ar-bgp-eastus03` |
| CE 소프트웨어 | `9.2024.6` 고정, 빌드 `crt-20250613-3382` |
| Azure VM | `f5-xc-ce-vm-01/02/03`, 각 3개의 NIC(관리/SLO, 외부, 내부/SLI) |
| 경로 교환 | Azure Route Server `ce-ha-lab-rrs`, ASN `65515`, 인스턴스 `10.0.4.4` 및 `10.0.4.5` |
| 피어링 | CE당 1개 — `eastus01-bgp`, `eastus02-bgp`, `eastus03-bgp` — CE ASN `64512` |
| 광고되는 VIP | `10.250.0.10/32`, 3개의 CE가 모두 동일하게 오리진 |
| 로드 밸런서 | `ar-bgp-ecmp-lb`, 도메인 `ar-bgp-ecmp.bankexample.com` 서비스 |
| 테스트 클라이언트 | `ar-ecmp-client`, 동일 VNet 내부의 VM |
| 리소스 그룹 | `rg-mcn-ce-ha-rmordasiewicz` |

<Aside type="caution" title="VIP는 모든 VNet CIDR 외부에 있어야 합니다">
`terraform/main.tf`에는 VIP가 허브 및 스포크 CIDR 모두의 외부에 있음을 단정하는 `check` 블록이 있으며, 그렇지 않으면 플랜을 거부합니다. 명시된 이유는 VNet CIDR 내부의 VIP는 BGP 경로가 더 구체적이더라도 VNet 자체의 시스템 경로에 밀린다는 점입니다.

이 가드를 계약으로 취급하십시오. 이 데모를 다른 주소 체계로 재지정한다면, VIP도 함께 VNet 범위 밖으로 이동해야 합니다.
</Aside>

## 발표 전에 정상 상태임을 증명하기

다음 순서로 네 가지를 점검합니다. 각 단계는 결함의 위치를 좁혀 주므로, 실패 시 단순히 "무언가 잘못되었다"가 아니라 구체적인 정보를 알려 줍니다.

<Steps>

1. **3개의 사이트가 모두 `ONLINE`인지.** 이것이 아니라면 그 아래의 어떤 것도 참일 수 없습니다.

   ```bash
   for s in ar-bgp-eastus01 ar-bgp-eastus02 ar-bgp-eastus03; do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **모든 피어링이 해당 CE의 VIP 광고를 학습하고 있는지.** 각 피어링을 개별적으로 조회하십시오 — 아래의 함정을 참고하십시오. 데모가 고장난 것처럼 보이지만 실제로는 정상인 경우가 여기서 가장 자주 발생합니다.

   ```bash
   for p in eastus01-bgp eastus02-bgp eastus03-bgp; do
     echo "--- $p"
     az network routeserver peering list-learned-routes \
       --name "$p" --routeserver ce-ha-lab-rrs -g rg-mcn-ce-ha-rmordasiewicz \
       --query "RouteServiceRole_IN_0[].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp

   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp

   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   3개의 피어링, 3개의 서로 다른 넥스트 홉, 하나의 프리픽스. 이것이 ECMP의 광고 측면이 증명된 것입니다.

3. **클라이언트의 유효 경로가 3개의 넥스트 홉을 모두 포함하는지.** 이것이 VNet이 프로그래밍한 대로의 ECMP 자체입니다 — CE가 주장하는 내용이 아니라 Azure가 그것으로 실제 수행한 결과입니다.

   ```bash
   az network nic show-effective-route-table \
     --name ar-ecmp-clientVMNic -g rg-mcn-ce-ha-rmordasiewicz \
     --query "value[?addressPrefix[0]=='10.250.0.10/32']" -o json
   ```

   ```json
   [
     {
       "addressPrefix": ["10.250.0.10/32"],
       "nextHopIpAddress": ["10.0.1.5", "10.0.1.4", "10.0.1.6"],
       "nextHopType": "VirtualNetworkGateway",
       "source": "VirtualNetworkGateway",
       "state": "Active"
     }
   ]
   ```

   `nextHopIpAddress`에 3개의 항목이 있고 `state: Active`인지가 점검 사항입니다. 3개를 기대하는 곳에 넥스트 홉이 1개라면 어떤 CE가 광고를 중단한 것이며, 2단계가 어느 것인지 식별해 줍니다.

4. **VIP가 트래픽을 서비스하는지.** 클라이언트 VM에서, 그리고 **`Host` 헤더와 함께** — 아래 두 번째 함정을 참고하십시오.

   ```bash
   az vm run-command invoke -g rg-mcn-ce-ha-rmordasiewicz -n ar-ecmp-client \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts 'for i in $(seq 1 10); do
                  curl -s -o /dev/null -w "%{http_code} " \
                    -H "Host: ar-bgp-ecmp.bankexample.com" http://10.250.0.10/
                done'
   ```

   ```text
   200 200 200 200 200 200 200 200 200 200
   ```

</Steps>

## 함정: 하나의 피어링이 하나의 경로만 표시하는 것은 정상입니다

`list-learned-routes`는 지정한 피어링으로 범위가 한정됩니다. Route Server의 전체 테이블이 아니라 **해당** 피어가 광고한 내용을 보고합니다.

따라서 `eastus01-bgp`만 조회하면 `10.0.1.4`를 경유하는 단일 `10.250.0.10/32`가 반환되며, 이를 "CE 하나만 광고 중 — 나머지 두 개는 다운"으로 읽고 싶어집니다. 아무것도 다운되지 않았습니다. 나머지 두 광고는 각자의 피어링에서 확인할 수 있으며, 위 2단계가 바로 그것을 루프로 순회합니다.

단일 피어링 조회로 ECMP를 확인하는 것은 불가능합니다. 3개의 피어링을 모두 루프로 순회하거나, 병합된 결과를 한 번의 호출로 보여 주는 클라이언트의 유효 경로 테이블을 확인하십시오.

## 함정: IP만으로 요청하면 404가 반환됩니다

로드 밸런서는 `Host`로 매칭합니다. VIP는 해당 주소로 접속하는 누구에게나 무엇이든 서비스하는 가상 서버가 아닙니다.

```text
curl -H 'Host: ar-bgp-ecmp.bankexample.com' http://10.250.0.10/   ->  200   (10 of 10)
curl                                        http://10.250.0.10/   ->  404
```

두 결과는 모두 정상 배포 환경에서 동일한 실행으로 생성되었습니다. **IP만으로 요청했을 때의 404는 경로가 작동한다는 증거입니다** — 요청이 CE에 도달했고, CE의 프록시가 응답했으며, 구성된 도메인이 일치하지 않아 거부한 것입니다. 이를 장애로 읽으면 BGP를 들여다보게 되지만 거기에는 잘못된 것이 없습니다.

데모 중에도 동일하게 적용됩니다. 도메인을 해당 주소로 해석하는 대신 브라우저에 주소를 직접 입력하면 404를 받게 됩니다.

## 등록 승인은 자동화되어 있지만, apply는 여전히 2단계입니다

등록 승인은 더 이상 콘솔에서 사람의 개입을 필요로 하지 않습니다. 프로바이더 **v3.81.1**에서는 `xcsh_registration_approval` 리소스가 이를 수행하며, 사이트 모듈이 어떤 등록을 승인할지 결정합니다.

그렇더라도 배포가 손을 대지 않는 단일 `apply`가 되지는 않으며, 그 이유는 첫 실행을 보고 실패했다고 결론짓기 전에 이해해 둘 가치가 있습니다.

- CE의 등록 객체 이름은 **`r-<uuid>`** 입니다. 사이트 이름을 따르지 않으므로 플랜 시점에 이름을 예측할 수 없습니다.
- 등록은 VM이 부팅되고 `vpm`이 등록을 수행한 이후에만 존재합니다.
- 따라서 **첫 apply는 승인을 전혀 계획하지 않습니다.** CE가 등록되고 승인이 생성된 후 다시 apply하십시오.

`terraform/main.tf`는 파일 상단에 이 순서를 문서화하고 있으며, 그것이 권위 있는 버전입니다 — 배포 순서는 이를 구현하는 코드와 함께 존재합니다.

<Aside type="caution" title="새로 만든 사이트는 operate API로 즉시 도달할 수 없습니다">
새 사이트가 `ONLINE`을 보고한 후 약 25~30분 동안 `vpm/debug` 엔드포인트는 `The requested URL was rejected`라고 표시된 BIG-IP `503` 페이지로 응답합니다. 웹 애플리케이션 방화벽 차단이나 취소된 토큰처럼 보이지만 둘 다 아닙니다. 기다린 후 재시도하십시오.

이는 새로 구축한 데모에 영향을 주며, 이미 운영 중인 데모에는 해당되지 않습니다.
</Aside>

## 측정과 관련된 두 가지 추가 함정

두 가지 모두 이 환경에서 확신에 찬 잘못된 답을 만들어 냈으며, 어느 것도 자명하지 않습니다.

- **워크스테이션이 아니라 VNet 내부에서 프로브하십시오.** Netskope는 일반적인 포트에서 TCP 핸드셰이크를 자체적으로 완료하므로, 워크스테이션에서의 프로브는 실제로 닫혀 있는 포트를 **열림**으로 보고합니다. 워크스테이션에서 보면 CE 공용 주소의 80번과 443번 포트가 열린 것으로 읽히지만, VNet 내부에서 프로브하면 닫혀 있습니다. `ar-ecmp-client`를 사용하십시오.
- **CE의 22번 포트는 내부(SLI) 주소에서만 응답합니다.** `ar-ecmp-client`에서 3개의 CE를 프로브하면 `10.0.3.5`, `10.0.3.6`, `10.0.3.7`이 모두 `SSH-2.0-OpenSSH_8.7`을 반환하지만, 관리 주소와 외부 주소는 타임아웃됩니다 — 대조군으로 사용한 미사용 주소도 마찬가지입니다. 따라서 노드를 식별하는 데 사용하는 주소를 프로브하는 것은 그 노드의 SSH 상태에 대해 아무것도 알려 주지 않습니다.

<Aside type="note" title="이 페이지가 주장하지 않는 것">
독자가 여기서 합리적으로 기대할 수 있는 두 가지는 의도적으로 빠져 있습니다. 이 배포 환경에서 실제로 수행되지 않았기 때문입니다.

- **페일오버는 테스트되지 않았습니다.** 3개의 동일 비용 넥스트 홉이 설치되었음은 검증되었지만, CE를 중단했을 때 경로 테이블에 무슨 일이 일어나는지는 제시되지 않았습니다. 따라서 먼저 직접 시도해 보지 않은 상태로 이 페이지를 근거로 페일오버 데모를 연습하지 마십시오.
- **트래픽 분산은 측정되지 않았습니다.** VIP에 대한 10개의 요청 중 10개가 `200`을 반환했고, 이는 경로가 작동함을 증명합니다. 그러나 그 10개가 3개의 넥스트 홉에 어떻게 분산되었는지는 보여 주지 않습니다.

</Aside>
