이 배포는 CE 앞단에 Azure 로드 밸런서를 두지 않은 **Azure에서의 액티브/액티브 Customer Edge 고가용성**을 시연합니다. 세 개의 CE가 각각 동일한 호스트 경로를 eBGP로 오리진하고, Azure Route Server는 세 경로 모두를 VNet 내에서 동일 비용 넥스트 홉으로 설치합니다. 따라서 트래픽 분산과 실패한 노드 제거가 일어나야 하는 지점은 로드 밸런서가 아니라 라우팅 패브릭입니다.

아래에 표시된 모든 내용은 실제 배포 환경에서 실행되었으며, 출력은 그 실행이 생성한 출력 그대로입니다. 그 문장이 포괄하지 *않는* 두 가지 — 페일오버와 트래픽 분산 — 는 가정에 맡기지 않고 마지막에 별도로 언급합니다.

## 배포되는 것

```text
                  Azure Route Server  ce-ha-lab-rrs  ASN 65515
                          10.0.4.4  and  10.0.4.5
                                      |
              +-----------------------+-----------------------+
              |                       |                       |
        eastus01-bgp            eastus02-bgp            eastus03-bgp     eBGP
              |                       |                       |      CE ASN 64512
        10.0.1.4                10.0.1.5                10.0.1.6     <- CE eth0 / SLO
     f5-xc-ce-vm-01          f5-xc-ce-vm-02          f5-xc-ce-vm-03
    ar-bgp-eastus01         ar-bgp-eastus02         ar-bgp-eastus03
              |                       |                       |
              +----- each advertises 10.250.0.10/32 -----------+
                          three-way ECMP into the VNet
```

| 구성 요소 | 구축 내용 |
| --- | --- |
| Customer Edge | 3개의 단일 노드 Secure Mesh v2 사이트 — `ar-bgp-eastus01`, `ar-bgp-eastus02`, `ar-bgp-eastus03` |
| CE 소프트웨어 | `9.2024.6`으로 고정, 빌드 `crt-20250613-3382` |
| Azure VM | `f5-xc-ce-vm-01/02/03`, 각각 3개의 NIC (관리/SLO, 외부, 내부/SLI) |
| 경로 교환 | Azure Route Server `ce-ha-lab-rrs`, ASN `65515`, 인스턴스 `10.0.4.4` 및 `10.0.4.5` |
| 피어링 | CE당 하나 — `eastus01-bgp`, `eastus02-bgp`, `eastus03-bgp` — CE ASN `64512` |
| 광고되는 VIP | `10.250.0.10/32`, 세 개의 CE 모두가 동일하게 오리진 |
| 로드 밸런서 | `ar-bgp-ecmp-lb`, 도메인 `ar-bgp-ecmp.bankexample.com` 서비스 |
| 테스트 클라이언트 | `ar-ecmp-client`, 동일 VNet 내부의 VM |
| 리소스 그룹 | `rg-mcn-ce-ha-rmordasiewicz` |

<Aside type="caution" title="VIP는 모든 VNet CIDR 외부에 있어야 합니다">
`terraform/main.tf`에는 VIP가 허브와 스포크 CIDR 양쪽 모두의 외부에 있음을 단언하고, 그렇지 않으면 플랜을 거부하는 `check` 블록이 있습니다. 그 이유로 명시된 것은, VNet CIDR 내부의 VIP는 BGP 경로가 더 구체적임에도 VNet 자체의 시스템 경로에 밀린다는 점입니다.

이 가드를 계약으로 취급하십시오. 이 데모를 다른 주소 체계로 재지정한다면 VIP도 함께 VNet 범위 밖으로 이동해야 합니다.
</Aside>

## 발표 전에 정상 상태임을 입증하기

네 가지 확인을 이 순서대로 수행합니다. 각 단계가 결함의 위치를 좁혀주므로, 실패는 단지 무언가 잘못되었다는 사실만이 아니라 무언가를 알려줍니다.

<Steps>

1. **세 사이트 모두 `ONLINE`입니다.** 이것이 아니라면 그 아래의 어떤 것도 성립할 수 없습니다.

   ```bash
   for s in ar-bgp-eastus01 ar-bgp-eastus02 ar-bgp-eastus03; do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **모든 피어링이 해당 CE의 VIP 광고를 학습하고 있습니다.** 각 피어링을 개별적으로 조회하십시오 — 아래의 함정을 참고하십시오. 이 지점이 데모가 고장난 것처럼 보이지만 실제로는 아닌 경우가 가장 흔합니다.

   ```bash
   for p in eastus01-bgp eastus02-bgp eastus03-bgp; do
     echo "--- $p"
     az network routeserver peering list-learned-routes \
       --name "$p" --routeserver ce-ha-lab-rrs -g rg-mcn-ce-ha-rmordasiewicz \
       --query "RouteServiceRole_IN_0[].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp

   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp

   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   세 개의 피어링, 세 개의 서로 다른 넥스트 홉, 하나의 프리픽스. 이것으로 ECMP의 광고 측면이 입증됩니다.

3. **클라이언트의 유효 경로가 세 개의 넥스트 홉을 모두 포함합니다.** 이것이 VNet이 프로그래밍한 대로의 ECMP 자체입니다 — CE가 주장하는 내용이 아니라, Azure가 그것으로 무엇을 했는지입니다.

   ```bash
   az network nic show-effective-route-table \
     --name ar-ecmp-clientVMNic -g rg-mcn-ce-ha-rmordasiewicz \
     --query "value[?addressPrefix[0]=='10.250.0.10/32']" -o json
   ```

   ```json
   [
     {
       "addressPrefix": ["10.250.0.10/32"],
       "nextHopIpAddress": ["10.0.1.5", "10.0.1.4", "10.0.1.6"],
       "nextHopType": "VirtualNetworkGateway",
       "source": "VirtualNetworkGateway",
       "state": "Active"
     }
   ]
   ```

   `nextHopIpAddress`에 세 개의 항목이 있고 `state: Active`인 것이 확인 지점입니다. 세 개를 예상했는데 넥스트 홉이 하나라면 어떤 CE가 광고를 중단했다는 뜻이며, 2단계에서 어느 CE인지 식별합니다.

4. **VIP가 트래픽을 서비스합니다.** 클라이언트 VM에서, 그리고 **`Host` 헤더와 함께** 실행합니다 — 아래 두 번째 함정을 참고하십시오.

   ```bash
   az vm run-command invoke -g rg-mcn-ce-ha-rmordasiewicz -n ar-ecmp-client \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts 'for i in $(seq 1 10); do
                  curl -s -o /dev/null -w "%{http_code} " \
                    -H "Host: ar-bgp-ecmp.bankexample.com" http://10.250.0.10/
                done'
   ```

   ```text
   200 200 200 200 200 200 200 200 200 200
   ```

</Steps>

## 함정: 하나의 피어링이 하나의 경로만 보여주는데, 그것이 정상입니다

`list-learned-routes`는 지정한 피어링으로 범위가 한정됩니다. **그** 피어가 광고한 내용을 보고하며, Route Server의 전체 테이블을 보고하지 않습니다.

그래서 `eastus01-bgp`만 조회하면 `10.0.1.4`를 경유하는 단일 `10.250.0.10/32`가 반환되고, 이를 "CE 하나만 광고 중 — 나머지 둘은 다운"으로 읽고 싶어집니다. 다운된 것은 없습니다. 나머지 두 개의 광고는 각자의 피어링에서 보이며, 이것이 위의 2단계가 순회하는 이유입니다.

단일 피어링 조회로 ECMP를 확인하는 것은 불가능합니다. 세 피어링을 모두 순회하거나, 병합된 결과를 한 번의 호출로 보여주는 클라이언트의 유효 경로 테이블을 읽으십시오.

## 함정: IP만으로 요청하면 404가 반환됩니다

로드 밸런서는 `Host`로 매칭합니다. VIP는 해당 주소로 접속하는 누구에게나 무언가를 제공하는 가상 서버가 아닙니다.

```text
curl -H 'Host: ar-bgp-ecmp.bankexample.com' http://10.250.0.10/   ->  200   (10 of 10)
curl                                        http://10.250.0.10/   ->  404
```

두 결과 모두 정상 상태의 배포에 대해 동일한 실행에서 생성되었습니다. **IP만으로 요청했을 때의 404는 경로가 동작한다는 증거입니다** — 요청이 CE에 도달했고, CE의 프록시가 응답했으며, 구성된 도메인이 일치하지 않아 거부한 것입니다. 이를 장애로 해석하면 BGP를 들여다보게 되고, 거기서는 아무 문제도 찾을 수 없습니다.

데모 중에도 마찬가지입니다. 도메인을 해당 주소로 해석하는 대신 주소를 브라우저에 직접 입력하면 404가 나옵니다.

## 등록 승인은 자동화되어 있으며, 적용은 여전히 두 단계입니다

등록 승인에는 더 이상 콘솔에서의 사람 개입이 필요하지 않습니다. 프로바이더 **v3.81.1**에서는 `xcsh_registration_approval` 리소스가 이를 수행하고, 사이트 모듈이 어떤 등록을 승인할지 해석합니다.

그렇더라도 배포가 단일한 무인 `apply`가 되는 것은 아니며, 첫 실행을 지켜보며 실패했다고 결론짓기 전에 그 이유를 이해할 가치가 있습니다.

- CE의 등록 객체 이름은 **`r-<uuid>`**입니다. 사이트 이름을 따르지 않으므로, 플랜 시점에 이름을 예측할 수 있는 것은 없습니다.
- 등록은 VM이 부팅되고 `vpm`이 등록을 완료한 후에만 존재합니다.
- 따라서 **첫 apply는 어떤 승인도 플랜하지 않습니다.** CE가 등록되고 승인이 생성된 후 한 번 더 apply하십시오.

`terraform/main.tf`는 파일 상단에 이 순서를 문서화하고 있으며, 그것이 권위 있는 버전입니다 — 배포 순서는 그것을 구현하는 코드와 함께 있습니다.

<Aside type="caution" title="갓 생성된 사이트는 operate API로 즉시 접근할 수 없습니다">
새 사이트가 `ONLINE`을 보고한 후 약 25~30분 동안 `vpm/debug` 엔드포인트는 `The requested URL was rejected`라고 표시된 BIG-IP `503` 페이지로 응답합니다. 웹 애플리케이션 방화벽 차단이나 폐기된 토큰처럼 보이지만 둘 다 아닙니다. 기다린 후 재시도하십시오.

이는 새로 구축한 데모에 해당하며, 이미 운영 중인 데모에는 해당하지 않습니다.
</Aside>

## Site CLI에 접근하기

일상적인 온박스 진단은 디버그 API를 통하며, 여기에 이미 스크립트로 작성되어 있습니다. 명령 표면이 문서에 설명된 내용과 여전히 일치하는지 확인하십시오.

```bash
bash scripts/capture-sitecli.sh --check --site ar-bgp-eastus01 --node f5-xc-ce-vm-01
```

```text
catalog matches the live CE (build crt-20250613-3382, 34 commands)
```

`--check`는 아무것도 쓰지 않으므로, 운영 중인 데모에 대해 안전합니다.

해당 API가 중계하지 않는 명령을 위해, 이 배포에는 로그인 셸이 Site CLI인 **어플라이언스 `admin` 계정에 대한 운영자 SSH**도 있습니다. 세 CE 모두에서 검증되었습니다. VNet 내부의 호스트에서 내부(SLI) 주소로, 터미널을 할당하여 접속하십시오.

```bash
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<vm-in-vnet> admin@10.0.3.5
```

```text
WELCOME IN SITE CLI
Registration Status: PROVISIONED
```

<Aside type="caution" title="이 접근 권한은 이 CE들이 그렇게 구축되었기 때문에 존재합니다 — 나중에 추가할 수 없습니다">
운영자 키는 cloud-init `write_files`에 의해 기록되며, 이는 최초 부팅 시 한 번만 실행됩니다. `custom_data`는 교체 전용이므로, 이미 실행 중인 CE에 이를 도입하면 모든 CE VM이 교체됩니다 — 그리고 하나를 교체하면 현재로서는 `terraform plan`이 "No changes"를 보고하는 동안 등록이 막혀버립니다([이슈 674](https://github.com/f5-sales-demo/mcn/issues/674)). 복구에는 전체 재구축 두 번이 필요했습니다.

이 배포에서는 해당 변경이 이미 적용되어 있고 플릿은 정상입니다. 다른 곳에서 이를 도입하려는 사람은 먼저 [SSH 페이지](../customer-edge/access/ssh/)를 읽어야 합니다.
</Aside>

## 두 가지 추가 측정 함정

두 경우 모두 이 환경에서 확신에 찬 잘못된 답을 만들어냈고, 어느 쪽도 명백하지 않습니다.

- **워크스테이션이 아니라 VNet 내부에서 프로브하십시오.** Netskope가 일반적인 포트에서 TCP 핸드셰이크를 스스로 완료하므로, 워크스테이션 프로브는 실제로는 닫힌 포트를 **열림**으로 보고합니다. 포트 80과 443은 워크스테이션에서 CE 공용 주소에 대해 열림으로 읽히지만, VNet 내부에서 프로브하면 닫혀 있습니다. `ar-ecmp-client`를 사용하십시오.
- **CE의 22번 포트는 내부(SLI) 주소에서만 응답합니다.** `ar-ecmp-client`에서 세 CE에 대해 프로브했을 때 `10.0.3.5`, `10.0.3.6`, `10.0.3.7`은 모두 `SSH-2.0-OpenSSH_8.7`을 반환하지만, 관리 주소와 외부 주소는 타임아웃됩니다 — 대조군으로 사용한 미사용 주소도 마찬가지입니다. eth0은 `a-i-eth0`으로 이름이 변경되며 호스트 IP를 갖지 않는데, 데이터패스가 이를 소유하기 때문입니다. 따라서 노드를 식별하는 데 사용하는 주소를 프로브해도 노드의 SSH 상태에 대해서는 아무것도 알 수 없으며, 접속해야 하는 것은 SLI 주소입니다.

<Aside type="note" title="이 페이지가 주장하지 않는 것">
독자가 여기서 합리적으로 기대할 수 있는 두 가지가 의도적으로 빠져 있는데, 배포에 대해 실제로 수행되지 않았기 때문입니다.

- **페일오버는 테스트되지 않았습니다.** 세 개의 동일 비용 넥스트 홉이 설치되었음은 검증되었지만, CE를 정지했을 때 경로 테이블에 어떤 일이 일어나는지는 제시되지 않았습니다. 따라서 먼저 직접 시도해 보지 않고 이 페이지를 근거로 페일오버 데모를 준비하지 마십시오.
