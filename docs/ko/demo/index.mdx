이 배포는 CE 앞단에 Azure 로드 밸런서를 두지 않고 **Azure에서 액티브/액티브 Customer Edge 고가용성**을 구현하는 방법을 보여줍니다. 각 CE는 eBGP로 동일한 호스트 경로를 광고하며, Azure Route Server는 이들 전부를 VNet 내에서 동일 비용 넥스트 홉으로 설치합니다.
따라서 트래픽 분산과 장애 노드 제거가 일어나야 하는 지점은 로드 밸런서가 아니라 라우팅 패브릭입니다.

이 페이지들의 모든 내용은 실제 배포 환경에서 실행된 것이며, 표시된 출력은 그 실행이 만들어낸 출력입니다. 그 문장이 *포함하지 않는* 것 — 페일오버, 그리고 트래픽이 넥스트 홉들 사이에서 어떻게 나뉘는지 — 는 추측에 맡기지 않고 명시적으로 언급합니다.

## 배포되는 구성

```text
                     Azure Route Server            ASN 65515
                      two instance addresses
                                 |
             +-------------------+-------------------+
             |                   |                   |
        <key>-bgp           <key>-bgp           <key>-bgp        eBGP
             |                   |                   |         CE ASN 64512
        CE eth0/SLO         CE eth0/SLO         CE eth0/SLO
          CE site             CE site             CE site
             |                   |                   |
             +--- each advertises the same VIP /32 ---+
                    equal-cost multipath into the VNet
```

| 구성 요소 | 설명 |
| --- | --- |
| F5 Distributed Cloud 테넌트 | `var.expected_xc_tenant` — 테넌트 이름이 지정되는 유일한 위치 |
| 네임스페이스 | CE 사이트는 `system`에, 오리진 풀과 로드 밸런서는 `var.xc_app_namespace`에 |
| Customer Edge | `var.ce_count`개의 단일 노드 Secure Mesh v2 사이트, 1~3개, 가용 영역당 하나 |
| CE 소프트웨어 | `var.ce_sw_version` / `var.ce_os_version`으로 고정됨 |
| Azure VM | 각각 NIC 3개 — 관리/SLO, 외부, 내부/SLI |
| 경로 교환 | Azure Route Server 1개, ASN `var.rs_asn`, 인스턴스 주소 2개 |
| 피어링 | CE당 1개, `<key>-bgp`로 명명, CE ASN `var.ce_asn` |
| 광고되는 VIP | `/32`로서의 `var.vip`, 모든 CE가 동일하게 광고 |
| 로드 밸런서 | `var.lb_domain`을 서비스하며, `var.origin_ip`의 오리진 풀이 백엔드 |
| 테스트 클라이언트 | 동일 VNet 내부의 VM으로, VIP를 향해 트래픽을 발생시키는 데 사용 |

위의 어떤 것도 그대로 복사해야 하는 리터럴 값이 아닙니다. 모든 값은 배포에서 읽어올 수 있으며, 각 페이지는 값을 명시하는 대신 읽어옵니다:

```bash
cd terraform
terraform output -raw resource_group_name
terraform output -json xc_site_names
```

<Aside type="caution" title="VIP는 모든 VNet CIDR 외부에 있어야 합니다">
`terraform/main.tf`에는 VIP가 허브와 스포크 CIDR 양쪽 모두의 외부에 있음을 단정하는 `check` 블록이 있으며, 그렇지 않으면 플랜을 거부합니다. 그 이유는 VNet CIDR 내부의 VIP는 BGP 경로가 더 구체적이더라도 VNet 자체의 시스템 경로에 밀린다는 것입니다.

이 가드를 계약으로 취급하십시오: 이 데모를 다른 주소 체계로 다시 지정한다면, VIP도 함께 VNet 범위 밖으로 이동해야 합니다.
</Aside>

<Aside type="note" title="2026-07-28 관찰: 실제 객체들은 아직 임시 이름을 유지하고 있습니다">
객체 이름은 `var.component`에서 파생되므로, 고정되지 않은 배포는
`<component>-<region>01`, `<component>-f5se`, `<component>-pool`, `<component>-rs`,
`<component>-bastion`을 생성합니다. 현재 실행 중인 데모는 그 변경 이전의 것으로 원래 이름을 유지하며, 환경이 사용 중인 동안 아무것도 교체되지 않도록 로컬 `terraform.tfvars`에 고정되어 있습니다.

그래서 이 페이지들의 실제 명령 출력에는 위 패턴과 일치하지 않는 이름이 나타납니다. 파생된 이름을 채택하면 모든 CE VM이 교체되는데, 사이트 이름이 cloud-init에 구워진 `ClusterName`이고 cloud-init은 첫 부팅에서만 실행되기 때문입니다 — 즉 이는 이름 변경이 아니라 의도적인 재구축이며,
[issue 700](https://github.com/f5-sales-demo/mcn/issues/700)에서 추적됩니다.
</Aside>
