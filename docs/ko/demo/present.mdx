이 데모가 뒷받침하는 주장은 범위가 좁으며 정확하게 진술할 가치가 있습니다. 더 넓은 주장은
질문을 견디지 못할 것이기 때문입니다:

> 여러 Customer Edge가 각각 eBGP로 동일한 호스트 경로를 광고하고, Azure는 그들 모두를
> 등가 비용 다음 홉으로 설치합니다. 따라서 트래픽 분산과 노드 제거는 라우팅 패브릭의
> 속성입니다 — CE 앞단에 Azure 로드 밸런서는 없습니다.

먼저 [네 가지 상태 점검](../verify/)을 실행하십시오. 아래의 모든 내용은 그 점검이 통과했다고 가정합니다.

## 이를 가시화하는 단 하나의 명령

유효 경로(effective routes)는 가장 강력한 단일 증거물입니다. CE가 주장하는 것이 아니라
Azure가 실제로 프로그래밍한 내용이기 때문입니다.

```bash
cd terraform
az network nic show-effective-route-table \
  -g "$(terraform output -raw resource_group_name)" \
  -n "$(terraform output -raw client_nic_name)" \
  --query "value[?addressPrefix[0]=='$(terraform output -raw vip)/32'].{prefix:addressPrefix[0],nh:nextHopIpAddress,state:state}" \
  -o json
```

2026-07-28 관측 결과:

```json
[
  {
    "nh": ["10.0.1.5", "10.0.1.6", "10.0.1.4"],
    "prefix": "10.250.0.10/32",
    "state": "Active"
  }
]
```

하나의 프리픽스, 세 개의 다음 홉, `Active`. 이것이 단일 출력에 담긴 이 데모의 요점 전부이며,
잠시 짚고 넘어갈 가치가 있습니다: 이 그림 안에 로드 밸런서는 없습니다.

그다음 VNet 내부에서 `Host` 헤더와 함께 서비스가 동작하는 것을 보여주십시오:

```bash
az vm run-command invoke \
  -g "$(terraform output -raw resource_group_name)" \
  -n "$(terraform output -raw client_vm_name)" \
  --command-id RunShellScript --query "value[0].message" -o tsv \
  --scripts "curl -s -o /dev/null -w '%{http_code}\n' \
               -H 'Host: $(terraform output -raw lb_domain)' \
               http://$(terraform output -raw vip)/"
```

<Aside type="caution" title="브라우저에 주소를 입력하는 방식으로 데모하지 마십시오">
로드 밸런서는 `Host`로 매칭하므로, IP만 사용한 요청은 완전히 정상적인 배포에서도 **404**를
반환합니다. 헤더를 함께 보내거나, 먼저 도메인을 VIP로 확인(resolve)하십시오. 아무 문제가
없더라도 청중 앞에서의 404는 되돌리기 어렵습니다.
</Aside>

## 권장 순서

<Steps>

1. **틀을 제시합니다.** 하나의 VIP, 여러 CE, 로드 밸런서 없음. 라우팅 패브릭이 HA
   메커니즘입니다.
2. **광고 측면을 보여줍니다.** 피어링을 순회합니다([점검 2](../verify/)) — 각 CE가 동일한
   프리픽스를 자신의 다음 홉과 함께 광고하며, 모두 동일한 AS 경로를 가지므로 어느 것도
   우선되지 않습니다.
3. **Azure가 그것으로 무엇을 했는지 보여줍니다.** 위의 유효 경로 테이블: 하나의 프리픽스,
   N개의 다음 홉, `Active`.
4. **서비스가 동작함을 보여줍니다.** 헤더를 포함한 위의 `curl`.
5. **구성을 보여줍니다.** [Terraform](../terraform/)이 여기에 게시되어 있으며, 배포를
   수행하는 파일에서 직접 읽어옵니다 — 누군가 이것이 재현 가능한지 물을 때 유용합니다.

</Steps>

## 이 데모가 아직 보여줄 수 없는 것

라이브 중에 발견하는 대신 여기에 명시합니다. 세 가지 모두 알려진 실패가 아니라 증거의
부재입니다.

<Aside type="danger" title="이 페이지들을 근거로 페일오버 시나리오를 리허설하지 마십시오">
**페일오버는 테스트되지 않았습니다.** 등가 비용 다음 홉이 설치되었음은 검증되었지만, CE가
중지되거나 광고를 중단할 때 경로 테이블에 무슨 일이 일어나는지는 이 배포에 대해 실행되지
않았습니다. 의도된 메커니즘은 한 CE의 광고를 철회하고 다음 홉 수가 줄어드는 것을 관찰하는
것이지만, 실제로 실행하고 측정하기 전까지는 결과가 아니라 계획입니다 — 그러므로 약속하지
말고, 청중 앞에서 즉흥적으로 시도하지 마십시오.

[이슈 700](https://github.com/f5-sales-demo/mcn/issues/700)에서 추적됩니다. 라이브 광고
상태를 변경하므로, 아무도 이 환경을 사용하지 않는 시간대가 필요합니다.
</Aside>

- **다음 홉 간 트래픽 분산은 측정되지 않았습니다.** VIP로 향한 1,470건의 요청은
  [검증 페이지](../verify/)에 기록되어 있으며, 이는 경로가 동작함과 시간에 따른 동작 양상을
  입증합니다. 그중 어느 것도 요청이 다음 홉들에 어떻게 분산되었는지는 보여주지 않으며, 이
  토폴로지는 요청을 귀속시킬 노드별 HTTP 리스너를 제공하지 않습니다. "고르게 분산되나요?"라는
  질문에 대한 정직한 답은, 여기서는 측정되지 않았다는 것입니다.
- **신규 빌드의 수렴 과도 현상의 원인은 확인되지 않았습니다.** 특성은 파악되었으나 — 언제
  발생하는지, 얼마나 지속되는지, 그리고 그 기간 내내 오리진은 정상이라는 점 — 설명되지는
  않았습니다.

<Aside type="note" title="새로 빌드한 스택에서 시연하는 경우, 기다리십시오">
CE가 `ONLINE`에 도달한 후 약 첫 45분 동안 VIP는 소수의 요청을 손실합니다. 이는 완전히
해소됩니다. 필요한 시점보다 충분히 앞서 데모를 빌드하고, 바로 직전에 점검 4를 다시
실행하십시오.
</Aside>
