本部署演示的是 **Azure 中的 active/active Customer Edge 高可用性**，
且 CE 前端没有任何 Azure 负载均衡器。三个 CE 各自通过 eBGP 发起相同的主机
路由，Azure Route Server 将这三者全部安装为 VNet 中的等价下一跳。因此，流量
分发与故障节点剔除是由路由结构（而非负载均衡器）来完成的。

以下展示的所有内容都是针对实际部署运行的，输出即为其实际产生的输出。这句话
**未**涵盖的两件事 —— 故障切换与流量分发 —— 会在末尾明确说明，而不是留给读者去假设。

## 部署了什么

```text
                  Azure Route Server  ce-ha-lab-rrs  ASN 65515
                          10.0.4.4  and  10.0.4.5
                                      |
              +-----------------------+-----------------------+
              |                       |                       |
        eastus01-bgp            eastus02-bgp            eastus03-bgp     eBGP
              |                       |                       |      CE ASN 64512
        10.0.1.4                10.0.1.5                10.0.1.6     <- CE eth0 / SLO
     f5-xc-ce-vm-01          f5-xc-ce-vm-02          f5-xc-ce-vm-03
    ar-bgp-eastus01         ar-bgp-eastus02         ar-bgp-eastus03
              |                       |                       |
              +----- each advertises 10.250.0.10/32 -----------+
                          three-way ECMP into the VNet
```

| 组成部分 | 竣工状态 |
| --- | --- |
| Customer Edge | 3 个单节点 Secure Mesh v2 站点 —— `ar-bgp-eastus01`、`ar-bgp-eastus02`、`ar-bgp-eastus03` |
| CE 软件 | 固定为 `9.2024.6`，构建版本 `crt-20250613-3382` |
| Azure 虚拟机 | `f5-xc-ce-vm-01/02/03`，每台三块网卡（管理/SLO、外部、内部/SLI） |
| 路由交换 | Azure Route Server `ce-ha-lab-rrs`，ASN `65515`，实例 `10.0.4.4` 和 `10.0.4.5` |
| 对等体 | 每个 CE 一个 —— `eastus01-bgp`、`eastus02-bgp`、`eastus03-bgp` —— CE ASN `64512` |
| 通告的 VIP | `10.250.0.10/32`，由三个 CE 以完全相同的方式发起 |
| 负载均衡器 | `ar-bgp-ecmp-lb`，服务于域名 `ar-bgp-ecmp.bankexample.com` |
| 测试客户端 | `ar-ecmp-client`，位于同一 VNet 内的一台虚拟机 |
| 资源组 | `rg-mcn-ce-ha-rmordasiewicz` |

<Aside type="caution" title="VIP 必须位于所有 VNet CIDR 之外">
`terraform/main.tf` 中包含一个 `check` 块，用于断言 VIP 位于中心（hub）和分支（spoke）
CIDR 之外，否则拒绝该计划。其给出的理由是：位于 VNet CIDR 内的 VIP 即便 BGP 路由更精确，
仍会输给 VNet 自身的系统路由。

请将这个防护视为契约：如果你将本演示重新指向不同的编址方案，VIP 也必须随之移出 VNet 范围。
</Aside>

## 演示前先验证健康状态

按此顺序执行四项检查。每一项都会缩小故障可能存在的范围，因此某项失败能告诉你具体信息，
而不仅仅是"哪里出问题了"。

<Steps>

1. **三个站点均为 `ONLINE`。** 如果这一条不成立，后续任何内容都无从谈起。

   ```bash
   for s in ar-bgp-eastus01 ar-bgp-eastus02 ar-bgp-eastus03; do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **每个对等体都学到了该 CE 的 VIP 通告。** 分别查询每个对等体 ——
   请参阅下面的陷阱说明，因为这里最常出现演示"看起来坏了"实际却没坏的情况。

   ```bash
   for p in eastus01-bgp eastus02-bgp eastus03-bgp; do
     echo "--- $p"
     az network routeserver peering list-learned-routes \
       --name "$p" --routeserver ce-ha-lab-rrs -g rg-mcn-ce-ha-rmordasiewicz \
       --query "RouteServiceRole_IN_0[].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp

   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp

   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   三个对等体、三个不同的下一跳、一个前缀。这就证明了 ECMP 的通告侧。

3. **客户端的有效路由包含全部三个下一跳。** 这才是 ECMP 本身 ——
   即 VNet 实际编程的结果，不是 CE 声称的内容，而是 Azure 对它做了什么。

   ```bash
   az network nic show-effective-route-table \
     --name ar-ecmp-clientVMNic -g rg-mcn-ce-ha-rmordasiewicz \
     --query "value[?addressPrefix[0]=='10.250.0.10/32']" -o json
   ```

   ```json
   [
     {
       "addressPrefix": ["10.250.0.10/32"],
       "nextHopIpAddress": ["10.0.1.5", "10.0.1.4", "10.0.1.6"],
       "nextHopType": "VirtualNetworkGateway",
       "source": "VirtualNetworkGateway",
       "state": "Active"
     }
   ]
   ```

   检查点是 `state: Active` 且 `nextHopIpAddress` 中有三个条目。本应有三个下一跳
   却只有一个，说明某个 CE 停止了通告，而第 2 步能指出是哪一个。

4. **VIP 能正常提供流量服务。** 从客户端虚拟机发起，并**带上 `Host` 头** ——
   请参阅下面的第二个陷阱。

   ```bash
   az vm run-command invoke -g rg-mcn-ce-ha-rmordasiewicz -n ar-ecmp-client \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts 'for i in $(seq 1 10); do
                  curl -s -o /dev/null -w "%{http_code} " \
                    -H "Host: ar-bgp-ecmp.bankexample.com" http://10.250.0.10/
                done'
   ```

   ```text
   200 200 200 200 200 200 200 200 200 200
   ```

</Steps>

## 陷阱：某个对等体只显示一条路由，而这是正确的

`list-learned-routes` 的作用域限定为你所指定的那个对等体。它报告的是**该**对等体
所通告的内容，而不是 Route Server 的整张表。

因此单独查询 `eastus01-bgp` 只会返回一条经由 `10.0.1.4` 的 `10.250.0.10/32`，很容易
被误读为"只有一个 CE 在通告 —— 另外两个宕了"。其实什么都没宕。另外两条通告在它们
各自的对等体上可见，这正是上面第 2 步循环遍历的内容。

无法通过单次对等体查询来确认 ECMP。要么循环查询全部三个对等体，要么读取客户端的
有效路由表 —— 后者一次调用即可显示合并后的结果。

## 陷阱：使用裸 IP 请求会返回 404

负载均衡器基于 `Host` 进行匹配。VIP 并不是一个会对任何连接到该地址的请求都提供服务的虚拟服务器。

```text
curl -H 'Host: ar-bgp-ecmp.bankexample.com' http://10.250.0.10/   ->  200   (10 of 10)
curl                                        http://10.250.0.10/   ->  404
```

以上两者都是在同一次针对健康部署的运行中产生的。**裸 IP 返回 404 恰恰证明路径是通的** ——
请求到达了 CE，CE 的代理做出了应答，只是因为没有匹配的已配置域名而拒绝了它。把它读成
故障会让你去排查 BGP，而那里根本没有问题。

演示过程中同理：如果你在浏览器中直接输入地址，而不是将域名解析到该地址，你就会得到 404。

## 注册审批已自动化，但 apply 仍是两阶段的

注册审批不再需要人工进入控制台操作。在 provider **v3.81.1** 上，
`xcsh_registration_approval` 资源会执行该操作，站点模块会解析出应批准哪一个注册。

但这仍然不能使部署变成一次性无人值守的 `apply`，理解其原因很有价值 ——
以免你看到首次运行后就断定它失败了：

- CE 的注册对象命名为 **`r-<uuid>`**。它绝不会以站点名称命名，因此在 plan 阶段无法预测其名称。
- 注册只有在虚拟机启动且 `vpm` 完成注册之后才存在。
- 因此**首次 apply 根本不会规划任何审批**。待 CE 完成注册、审批对象创建后，再次执行 apply。

`terraform/main.tf` 在文件顶部记录了这一顺序，那是权威版本 ——
部署顺序与实现它的代码放在一起。

<Aside type="caution" title="全新站点无法立即通过 operate API 访问">
在新站点报告 `ONLINE` 之后的大约 25 到 30 分钟内，`vpm/debug` 端点会返回一个 BIG-IP
`503` 页面，内容为 `The requested URL was rejected`。它看起来像是 Web 应用防火墙拦截
或令牌被吊销，但两者都不是。等待后重试即可。

这只影响刚构建的演示环境，不影响已在运行的环境。
</Aside>

## 访问 Site CLI

常规的机上诊断通过 debug API 进行，此处已有脚本化实现。
确认命令接口仍与文档描述一致：

```bash
bash scripts/capture-sitecli.sh --check --site ar-bgp-eastus01 --node f5-xc-ce-vm-01
```

```text
catalog matches the live CE (build crt-20250613-3382, 34 commands)
```

`--check` 不会写入任何内容，因此对运行中的演示环境是安全的。

对于该 API 不转发的命令，本部署还提供了**通过 SSH 访问设备 `admin` 账户**的方式，
其登录 shell 即为 Site CLI。三个 CE 上均已验证。请从 VNet 内部的主机连接到内部（SLI）
地址，并分配终端：

```bash
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<vm-in-vnet> admin@10.0.3.5
```

```text
WELCOME IN SITE CLI
Registration Status: PROVISIONED
```

<Aside type="caution" title="这种访问方式之所以存在，是因为这些 CE 在构建时就带上了它 —— 事后无法添加">
运维密钥由 cloud-init `write_files` 写入，该步骤仅在首次启动时运行一次。
`custom_data` 只能通过替换来变更，因此在已经运行的 CE 上采用此方案会替换
每一台 CE 虚拟机 —— 而替换其中一台目前会卡住注册流程，同时 `terraform plan`
却报告 "No changes"（[issue 674](https://github.com/f5-sales-demo/mcn/issues/674)）。
恢复过程耗费了两次完整重建。

对于本部署，该变更已经应用且集群健康。在其他环境中采用此方案的人应先阅读
[SSH 页面](../customer-edge/access/ssh/)。
</Aside>

## 另外两个测量陷阱

这两者都在本环境中给出过看似确凿的错误答案，而且都不明显。

- **请从 VNet 内部探测，而不是从你的工作站探测。** Netskope 会在常见端口上自行完成
  TCP 握手，因此工作站的探测会将一个实际关闭的端口报告为**开放**。从工作站探测时，
  CE 公网地址上的 80 和 443 端口显示为开放，而从 VNet 内部探测时它们是关闭的。
  请使用 `ar-ecmp-client`。
- **CE 上的 22 端口仅在内部（SLI）地址上应答。** 从 `ar-ecmp-client` 对三个 CE
  进行探测，`10.0.3.5`、`10.0.3.6` 和 `10.0.3.7` 都返回 `SSH-2.0-OpenSSH_8.7`，
  而管理地址和外部地址均超时 —— 作为对照的未使用地址同样超时。eth0 被重命名为
  `a-i-eth0` 且不承载主机 IP，因为数据面拥有它。因此，探测你惯用来标识节点的那个
  地址并不能告诉你节点的 SSH 状态，应当连接的是 SLI 地址。
