本部署演示了 **Azure 中的 active/active Customer Edge 高可用**，
并且 CE 前面没有 Azure 负载均衡器。三个 CE 各自通过 eBGP 通告同一条主机
路由，Azure Route Server 将这三条都安装为 VNet 内的等价下一跳。因此，流量
分发和故障节点移除应当发生在路由结构中，而不是负载均衡器上。

下面展示的所有内容都是针对实际部署运行的，输出就是它实际产生的输出。而这句话*未*
涵盖的内容 —— 故障切换、流量如何在三个下一跳之间分配、以及为什么全新构建的 VIP 会
短暂丢包 —— 都被明确指出，而不是留给读者去假设。

## 部署了什么

```text
                  Azure Route Server  ce-ha-lab-rrs  ASN 65515
                          10.0.4.4  and  10.0.4.5
                                      |
              +-----------------------+-----------------------+
              |                       |                       |
        eastus01-bgp            eastus02-bgp            eastus03-bgp     eBGP
              |                       |                       |      CE ASN 64512
        10.0.1.4                10.0.1.5                10.0.1.6     <- CE eth0 / SLO
     f5-xc-ce-vm-01          f5-xc-ce-vm-02          f5-xc-ce-vm-03
    ar-bgp-eastus01         ar-bgp-eastus02         ar-bgp-eastus03
              |                       |                       |
              +----- each advertises 10.250.0.10/32 -----------+
                          three-way ECMP into the VNet
```

| 组成部分 | 实际部署 |
| --- | --- |
| F5 Distributed Cloud 租户 | `f5-sales-demo` — `https://f5-sales-demo.console.ves.volterra.io` |
| 命名空间 | 站点位于 `system`；origin pool 和负载均衡器位于 `multi-cloud-networking` |
| Customer Edge | 3 个单节点 Secure Mesh v2 站点 — `ar-bgp-eastus01`、`ar-bgp-eastus02`、`ar-bgp-eastus03` |
| CE 软件 | 固定为 `9.2024.6`，构建 `crt-20250613-3382` |
| Azure 虚拟机 | `f5-xc-ce-vm-01/02/03`，每台三个 NIC（management/SLO、external、internal/SLI） |
| 路由交换 | Azure Route Server `ce-ha-lab-rrs`，ASN `65515`，实例 `10.0.4.4` 和 `10.0.4.5` |
| Peering | 每个 CE 一个 — `eastus01-bgp`、`eastus02-bgp`、`eastus03-bgp` — CE ASN `64512` |
| 通告的 VIP | `10.250.0.10/32`，由三个 CE 以完全相同的方式通告 |
| 负载均衡器 | `ar-bgp-ecmp-lb`，服务域名 `ar-bgp-ecmp.bankexample.com` |
| 测试客户端 | `ar-ecmp-client`，位于同一 VNet 内的一台虚拟机 |
| 资源组 | `rg-mcn-ce-ha-rmordasiewicz` |

<Aside type="caution" title="VIP 必须位于所有 VNet CIDR 之外">
`terraform/main.tf` 包含一个 `check` 块，断言 VIP 位于 hub 和 spoke 两个 CIDR 之外，
否则拒绝该 plan。其给出的理由是：位于 VNet CIDR 内部的 VIP 即使 BGP 路由更具体，
也会输给 VNet 自身的系统路由。

请把这个防护当作契约：如果你把该演示重新指向不同的地址规划，VIP 必须随之移出
VNet 地址范围。
</Aside>

## 租户来自配置，而不是你的 shell 导出的任何内容

`var.expected_xc_tenant` 指定租户，默认值为 `f5-sales-demo`，并且这是唯一
指定它的地方。`providers.tf` 由它派生出 `xcsh` provider 的 `api_url`，这会有意
覆盖环境中的任何 `XCSH_API_URL`，而 `terraform/main.tf` 中的一个 `postcondition`
会在环境指定了不同租户时使 **plan** 失败。

在不运行任何改变状态的操作的情况下读取这两半：

```bash
cd terraform
terraform output -raw xc_tenant       # what the deployment targets
terraform output -raw xc_env_tenant   # what your shell claims — diagnostic only
```

```text
f5-sales-demo
f5-sales-demo
```

<Aside type="danger" title="这个防护措施之所以存在，是因为该演示曾静默地把自己迁移到了错误的租户">
MCN 演示是在 `f5-sales-demo` 中构建的。后来某个凭据文件开始导出一个
`f5-amer-ent` 的 `XCSH_API_URL`；后续的 apply 为该租户签发了 token，CE 虚拟机
在那里重新注册，而它们在 `f5-sales-demo` 的注册被弃置。期间的每一次 plan 都是干净的，
因为配置中没有任何内容对租户有约束
（[issue 696](https://github.com/f5-sales-demo/mcn/issues/696)，已在
[PR 697](https://github.com/f5-sales-demo/mcn/pull/697) 中修复）。恢复它意味着销毁
错误租户中的整个栈，并在正确的租户中重建。

需要识别的症状，因为它并不自我描述：为另一个租户签发的 token 在固定的端点上
只会返回一个裸的 `401`，这看起来完全像是凭据过期。如果你认为有效的凭据返回了 `401`，
请在签发另一个 token 之前先比较上面两个输出。
</Aside>

## 在演示前证明其健康

四项检查，按此顺序。每一项都会缩小故障所在范围，因此一次失败能告诉你一些信息，
而不仅仅是"有问题"。

<Steps>

1. **三个站点都是 `ONLINE`。** 如果这一点不成立，后续的任何内容都不可能为真。

   ```bash
   for s in ar-bgp-eastus01 ar-bgp-eastus02 ar-bgp-eastus03; do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **每个 peering 都学习到了对应 CE 的 VIP 通告。** 分别查询每个 peering ——
   参见下面的陷阱，因为这里最常出现演示看起来坏了但其实没坏的情况。

   ```bash
   for p in eastus01-bgp eastus02-bgp eastus03-bgp; do
     echo "--- $p"
     az network routeserver peering list-learned-routes \
       --name "$p" --routeserver ce-ha-lab-rrs -g rg-mcn-ce-ha-rmordasiewicz \
       --query "RouteServiceRole_IN_0[].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp

   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp

   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   三个 peering，三个不同的下一跳，一个前缀。这就证明了 ECMP 的通告侧。

3. **客户端的有效路由包含全部三个下一跳。** 这就是 ECMP 本身，
   即 VNet 实际编程的结果 —— 不是 CE 声称的内容，而是 Azure 对它做了什么。

   ```bash
   az network nic show-effective-route-table \
     --name ar-ecmp-clientVMNic -g rg-mcn-ce-ha-rmordasiewicz \
     --query "value[?addressPrefix[0]=='10.250.0.10/32']" -o json
   ```

   ```json
   [
     {
       "addressPrefix": ["10.250.0.10/32"],
       "nextHopIpAddress": ["10.0.1.5", "10.0.1.4", "10.0.1.6"],
       "nextHopType": "VirtualNetworkGateway",
       "source": "VirtualNetworkGateway",
       "state": "Active"
     }
   ]
   ```

   `state: Active` 且 `nextHopIpAddress` 中有三个条目，这就是检查点。**这三者的
   顺序没有意义，也不稳定** —— Azure 在不同调用之间返回的顺序不同，因此应当计数，
   而不是把列表与之前的运行结果对比。本应有三个下一跳却只有一个，意味着某个 CE
   已停止通告，而第 2 步能识别出是哪一个。

4. **VIP 能提供流量服务。** 从客户端虚拟机发起，并且**带上 `Host` 头** —— 参见
   下面的第二个陷阱。采样足够多的请求才能发现问题：即使在后文描述的收敛窗口期内，
   几十个请求也会显示为 100 %。

   ```bash
   az vm run-command invoke -g rg-mcn-ce-ha-rmordasiewicz -n ar-ecmp-client \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts 'ok=0; fail=0
                for i in $(seq 1 60); do
                  c=$(curl -s -o /dev/null -m 5 -w "%{http_code}" \
                        -H "Host: ar-bgp-ecmp.bankexample.com" http://10.250.0.10/)
                  [ "$c" = 200 ] && ok=$((ok+1)) || fail=$((fail+1))
                done
                echo "OK=$ok FAIL=$fail"'
   ```

   ```text
   OK=60 FAIL=0
   ```

</Steps>

## 陷阱：某个 peering 只显示一条路由，而这是正确的

`list-learned-routes` 的作用范围仅限于你指定的那个 peering。它报告的是**那个** peer
所通告的内容，而不是 Route Server 的整张表。

因此单独查询 `eastus01-bgp` 只会返回一条经由 `10.0.1.4` 的 `10.250.0.10/32`，
很容易把它读作"只有一个 CE 在通告 —— 另外两个宕了"。什么都没宕。另外两条通告
在它们各自的 peering 上可见，这正是上面第 2 步所循环遍历的内容。

从单个 peering 查询来确认 ECMP 是不可能的。要么循环全部三个 peering，要么读取客户端
的有效路由表，它在一次调用中就显示了合并后的结果。

## 陷阱：裸 IP 请求返回 404

负载均衡器基于 `Host` 匹配。VIP 不是一个会向任何连接到该地址的人提供内容的虚拟服务器。

```text
curl -H 'Host: ar-bgp-ecmp.bankexample.com' http://10.250.0.10/   ->  200   (10 of 10)
curl                                        http://10.250.0.10/   ->  404
```

以上两者都是在同一次针对健康部署的运行中产生的。**裸 IP 返回 404 恰恰证明了路径是通的**
—— 请求到达了 CE，CE 的代理作出了应答，并因为没有匹配任何已配置的域名而拒绝了它。
把它读作故障会让你去查 BGP，而那里什么问题也没有。

演示期间同理：如果你在浏览器中直接输入地址而不是把域名解析到它，你就会得到 404。

## VIP 在最初的三刻钟内丢弃请求，随后停止

在全新构建的栈上，VIP 在 CE 达到 `ONLINE` 后的大约前 45 分钟内会丢失一小部分请求，
之后便干净地提供服务。基于从 `ar-ecmp-client` 发出的 1,470 个请求测量，全部带 `Host` 头：

| 窗口 | 请求数 | 失败数 | 比率 |
| --- | --- | --- | --- |
| ECMP 建立后的前约 45 分钟 | 570 | 12 | **2.11 %** |
| 随后的 23 分钟 | 900 | **0** | **0.00 %** |

每次失败都是 `curl: (28)` —— 超时且收到零字节 —— 而不是 HTTP 错误状态码。最后一次
出现在 ECMP 建立后约 43 分钟。在 900 个干净请求中，有 400 个使用了 30 秒超时，
每一个都在 2 秒内完成，因此没有任何问题被过短的超时掩盖。

**origin 不是原因。** 一批直连 origin 的对照测试
（`http://20.98.232.135/`，绕过 VIP）在与失败的 VIP 批次*并行*运行时 120 个全部干净。
故障出在 VIP、ECMP 或 CE 路径中的某处。

有两件事是刻意不这么说的：

- **它不是稳态缺陷。** 它会完全消失并保持消失。已经运行一小时的演示不存在这个问题
  —— 上面的检查 60 个中 60 个通过，而且在重建后的栈上再次干净地复现了这一点。
- **它无法归因于某个特定的 CE。** 该拓扑中没有任何东西提供逐节点的 HTTP 监听器，
  因此无法把被丢弃的请求绑定到丢弃它的那个节点。CE 的 external 接口（`10.0.2.x`）
  根本没有 HTTP 监听器 —— 只有 VIP `/32` 会应答。

它在另一个租户的全新重建中复现，因此它跟随拓扑而不是环境。

<Aside type="caution" title="不要只采样 40 个请求就断定一切正常">
即使在失败窗口内，40 到 50 个请求的批次大多数时候也会显示为 100 %。这正是它最初
被误判为持续的低速率故障、随后又被误判为完全没有故障的原因。请采样 100 个以上，
并分成时间上彼此分隔的批次。
</Aside>

## 注册审批已自动化，但 apply 仍是两阶段的

注册审批不再需要有人在控制台操作。在 provider **v3.81.1** 上，
`xcsh_registration_approval` 资源会执行它，站点模块会解析出应批准哪个注册。

但这仍然不能让部署变成单次无人干预的 `apply`，在你观察第一次运行并断定它失败之前，
理解其原因是值得的：

- CE 的注册对象命名为 **`r-<uuid>`**。它绝不会以站点命名，因此在 plan 时
  无法预测其名称。
- 注册只在虚拟机启动且 `vpm` 完成注册之后才存在。
- 因此**第一次 apply 根本不会规划任何审批**。等 CE 完成注册且审批被创建后，
  再次 apply。

`terraform/main.tf` 在文件顶部记录了这一顺序，那是权威版本 ——
部署顺序与实现它的代码放在一起。

<Aside type="caution" title="全新站点无法立即通过 operate API 访问">
在新站点报告 `ONLINE` 之后的大约 25 到 30 分钟内，`vpm/debug` 端点会返回一个
BIG-IP `503` 页面，内容为 `The requested URL was rejected`。它看起来像 Web 应用
防火墙拦截或 token 被吊销，但两者都不是。请等待，然后重试。

这影响全新构建的演示，而不是正在运行的演示。
</Aside>

## 访问 Site CLI

常规的机上诊断通过 debug API 进行，这里已经脚本化了。
确认命令面仍与文档描述一致：

```bash
bash scripts/capture-sitecli.sh --check --site ar-bgp-eastus01 --node f5-xc-ce-vm-01
```

```text
catalog matches the live CE (build crt-20250613-3382, 34 commands)
```

`--check` 不写入任何内容，因此对实际运行的演示是安全的。

对于该 API 不转发的命令，本部署还提供**通过 SSH 以运维身份访问设备的 `admin` 账户**，
其登录 shell 就是 Site CLI。这已在全部三个 CE 上验证过。从 VNet 内部的主机连接到
internal（SLI）地址，并分配终端。

<Aside type="danger" title="切勿硬编码 CE 的 internal 地址 —— 它们在每次重建时都会重新分配">
Azure 不会保留哪个 CE 在 internal 子网中获得哪个地址。在最近一次重建后，
`f5-xc-ce-vm-01`、`-02` 和 `-03` 分别持有 `10.0.3.7`、`10.0.3.5` 和 `10.0.3.4`：
既不按节点顺序，也不连续，而且与它们之前持有的不同。测试客户端自己的 NIC 位于同一
子网，并且曾持有过某个 CE 先前持有的地址。

请读取它们，而不是记住它们：

```bash
cd terraform
terraform output -json ce_sli_private_ips
```

```json
{"eastus01":"10.0.3.7","eastus02":"10.0.3.5","eastus03":"10.0.3.4"}
```

如果手边没有 Terraform state，可以按 NIC 名称向 Azure 查询你想要的那个，
NIC 名称*是*稳定的：

```bash
az network nic show -g rg-mcn-ce-ha-rmordasiewicz \
  -n f5-xc-ce-vm-01-internal-nic \
  --query ipConfigurations[0].privateIPAddress -o tsv
```

</Aside>

```bash
SLI=$(terraform output -json ce_sli_private_ips | jq -r '.eastus01')
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<vm-in-vnet> "admin@$SLI"
```

```text
Registration Status: PROVISIONED
SLO IP: 10.0.1.4/26
WELCOME IN SITE CLI
```

<Aside type="caution" title="该访问方式之所以存在，是因为这些 CE 在构建时就带上了它 —— 无法事后添加">
运维密钥由 cloud-init `write_files` 写入，它只在首次启动时运行一次。
`custom_data` 是仅替换的，因此在已经运行的 CE 上采用这一做法会**替换每一台 CE 虚拟机**。
那是一次机队重建，而不是配置变更。

以前情况比这更糟：被替换的 CE 永远无法重新注册，因为被销毁节点的注册仍然占据着控制平面的
唯一 `(tenant, cluster_name, hostname)` 索引 —— 而在整个机队宕机期间，
`terraform plan` 都报告 "No changes"。恢复花了两次完整重建。这已经修复
（[issue 674](https://github.com/f5-sales-demo/mcn/issues/674)，由
[PR 693](https://github.com/f5-sales-demo/mcn/pull/693) 关闭）：站点对象的生命周期现在
与 CE 虚拟机实例耦合，因此替换虚拟机就会替换站点，而删除站点会在替换节点启动之前
一并带走它的注册。

对本部署而言，该变更已经应用，机队是健康的。任何想在别处采用它的人应先阅读
[SSH 页面](../customer-edge/access/ssh/)。
</Aside>

## 另外两个测量陷阱

这两者都在本环境中产生了自信而错误的答案，而且都不显而易见。

- **从 VNet 内部探测，而不是从你的工作站。** Netskope 会在常见端口上自行完成 TCP
  握手，因此工作站上的探测会把实际关闭的端口报告为**开放**。从工作站探测 CE 公网地址时
  端口 80 和 443 显示为开放，而从 VNet 内部探测时它们是关闭的。请使用 `ar-ecmp-client`。
- **CE 上的 22 端口仅在 internal（SLI）地址上应答。** 从 `ar-ecmp-client` 探测时，
  每个 CE 的 internal 地址返回 `SSH-2.0-OpenSSH_8.7`，而其 management 和 external
  地址则超时 —— 用作对照的未使用地址也是如此。eth0 被重命名为 `a-i-eth0` 且不带主机 IP，
  因为数据平面拥有它。因此，探测你所熟知的那个节点地址并不能告诉你该节点的 SSH 状态，
  而 SLI 地址才是应该连接的那一个。请从
  `terraform output -json ce_sli_private_ips` 获取该地址；不要假设 internal 子网
  只有 CE，因为测试客户端的 NIC 也在其中。
