采集时间为 2026-07-28，来自本次部署的某个 CE。`sitecli/capture-manifest.json`
记录了具体是哪个节点，而 `scripts/capture-sitecli.sh --check` 会对照活动 CE
重新验证命令接口。

<Aside type="danger" title="API 无法调试此问题">
调试 API 通过 F5 分布式云控制平面、经由注册过程建立的隧道抵达节点。如果注册失败，隧道便不存在，
因此本站点上的每一条命令在这种特定故障下都不可用。如果节点仍有网络通路，请从
[站点控制台](../../access/site-console/) 着手；如果没有，请从
[串行控制台](../../access/serial-console/) 着手。
</Aside>

<Steps>

1. **确认你查询的租户是正确的。** 这只需一条命令，而且必须放在最前面，因为一旦弄错，
   后续每一步都会给出误导性结果：在你没有查看的那个租户中运行良好的机群，与从未注册过的机群
   看起来毫无区别。

   ```bash
   cd terraform
   terraform output -raw xc_tenant       # the tenant this deployment belongs to
   terraform output -raw xc_env_tenant   # the tenant your shell is exporting
   ```

   ```text
   f5-sales-demo
   f5-sales-demo
   ```

   两者不一致，或者你认为有效的凭据返回了一个裸的 `401`？这正是为其他租户签发的令牌所表现出的
   症状，而它已经让这次部署付出了一次完整重建的代价
   （[issue 696](https://github.com/f5-sales-demo/mcn/issues/696)）。

2. **确认租户方面的认知。** 站点未出现在站点列表中，与站点存在但状态不是 `ONLINE`，
   是两个不同的问题。

   ```bash
   curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
     "$XCSH_API_URL/api/config/namespaces/system/sites" | jq -r '.items[].name'
   ```

   如果站点存在且报告为 `ONLINE`，说明注册已成功，你走错了排查流程。

3. **找到站点的注册记录及其状态。** 节点可能已注册但仍在等待审批，从外部看这与失败完全一样。

   ```bash
   curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
     "$XCSH_API_URL/api/register/namespaces/system/registrations_by_site/<site>" \
     | jq -r '.items[] | "\(.name)  \(.object.status.current_state)  \(.object.spec.gc_spec.infra.hostname)"'
   ```

   ```text
   r-a97e20c8-b7e1-483d-bd76-34a64ff8bc78  ONLINE  f5-xc-ce-vm-01
   ```

   完全没有条目意味着节点尚未注册——请转向串行控制台。存在条目但状态不是 `ONLINE`，
   意味着它已完成注册，但之后某个环节失败了，那是另一项排查工作。

   若要在整个命名空间中扫描所有等待审批的对象，`listregistrationsbystate`
   将状态作为 **`POST` 请求体** 接收：

   ```bash
   curl -sS -X POST -H "Authorization: APIToken $XCSH_API_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"namespace":"system","state":"PENDING"}' \
     "$XCSH_API_URL/api/register/namespaces/system/listregistrationsbystate" | jq -r '.items[].name'
   ```

   在运行正常的机群上该命令不返回任何内容，因为审批是自动完成的。

4. 在假定存在软件故障之前，**先确认虚拟机确实在运行**。

   ```bash
   az vm list -d -g <resource-group> --query "[].{name:name,power:powerState}" -o table
   ```

   ```text
   Name            Power
   --------------  ----------
   ar-ecmp-client  VM running
   f5-xc-ce-vm-01  VM running
   f5-xc-ce-vm-02  VM running
   f5-xc-ce-vm-03  VM running
   ```

5. **连接串行控制台。** 交互式使用需要真实终端；连接动作本身也可以通过 websocket 脚本化——参见
   [串行控制台](../../access/serial-console/)。

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

   如果连接被拒绝，请先检查该虚拟机是否已启用引导诊断，然后再断定节点不可达；
   该前提条件及其失败模式在
   [串行控制台](../../access/serial-console/) 页面中有说明。

6. **按以下顺序阅读控制台输出。** 先看 cloud-init——cloud-init 从未完成的节点没有可用于注册的配置。
   接着看注册尝试本身，然后是 DNS：如果节点无法解析
   `register.ves.volterra.io`，后续任何环节都无法工作。

7. **当节点变为 `ONLINE` 后**，使用 [`health`](../../commands/system/health/) 进行验证，
   并预期看到 `state: PROVISIONED`。

</Steps>

<Aside type="caution" title="注册记录以 UUID 命名，绝不以其站点命名">
注册记录的名称形式为 `r-<uuid>`，并且不存在任何在应当使用注册名称的位置接受站点名称的端点。
`GET .../registrations/<site>` 返回 `404`，这看起来像是"该站点没有注册记录"，
实际含义是"那不是一个注册名称"。站点到注册记录的映射只能通过
`registrations_by_site/<site>`（如步骤 3 所示）获得，或者列出
`registrations` 并按 `gc_spec.passport.cluster_name` 匹配。

正是这个陷阱让一个运行正常的机群看起来像是零注册记录。
</Aside>

## 常见原因

- **你指向了错误的租户**，因此一个状况良好的机群看起来并不存在。见步骤 1。
- cloud-init 未完成，因此 `/etc/vpm/config.yaml` 缺失或有误。
- 注册令牌已过期、已被使用，或来自其他租户。
- 没有通往 `register.ves.volterra.io` 的出站路由。
- 时钟偏差大到足以使证书失效——之后可用
  [`chronyc-sources`](../../commands/network/chronyc-sources/) 快速排除，但在节点上线前
  无法访问。在可以使用 SSH 时，[SSH](../../access/ssh/) 登录横幅会在你运行任何命令之前
  报告 `NTP: Synced` 以及解析器的状态。
