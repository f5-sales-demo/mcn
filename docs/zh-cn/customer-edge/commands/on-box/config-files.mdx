四个命令会在 F5 自有文件上打开编辑器。它们不在
[调试 API](../../../access/debug-api/) 中，其中两个命令的描述本身就已说明：
*"除非 F5 XC 支持团队要求，否则请勿使用"*。

<Aside type="danger" title="本页有意不提供命令输出示例">
以上每个命令都会在实时配置文件上打开交互式编辑器。由于没有只读模式，任何可捕获的输出同时也是写入操作的入口，因此采集工具拒绝了全部四个命令。本文档所验证的是这些命令的存在性，以及每个命令所打开的文件——均来自设备自身的补全菜单。
</Aside>

## `edit-app-env-file`

打开 `/etc/vpm/app_env.yaml`，即节点的本地应用环境配置文件。

```bash
execcli edit-app-env-file
```

设备对此命令的描述结尾为 *"除非 F5 XC 支持团队要求，否则请勿使用"*。
请认真对待：此文件在 `vpm` 启动时读取，任何格式错误的值都会影响节点上的每一个平台容器。

## `edit-certified-hardware`

打开认证硬件配置文件。

```bash
execcli edit-certified-hardware
```

同样被设备标记为仅限支持团队使用。此配置决定了 `vpm` 是否认为自身运行在 F5 认证的硬件上——配置错误的后果并非假设性的。若缺少有效的 `CertifiedHardwareEndpoint`，`vpmd` 将以 *"fail to match certified hardware"* 退出，节点将永远无法注册。这正是本仓库的 cloud-init 配置显式设置该端点而非依赖默认值的原因；详见
`terraform/cloud-init/ce-node.yaml`。

## `edit-azure-client-id-secret`

更新此 CE 所使用的 Azure 客户端 ID 和密钥，适用于凭据过期的情况。

```bash
execcli edit-azure-client-id-secret
```

**适用场景。** 若某个 CE 此前运行正常，但近期开始出现 Azure 操作失败，且没有任何配置变更可以解释，则此命令正是为此场景而设——凭据已过期，而非系统本身出现故障。

## `edit-udev-10-nic-name`

打开 `/etc/udev/rules.d/10-nic-names.rules`，该文件决定 NIC 的命名方式。

```bash
execcli edit-udev-10-nic-name
```

**修改前请先阅读接口相关页面。** CE 上的 NIC 命名本已出人意料：`eth0` 被重命名为 `a-i-eth0` 且不承载主机地址，SLO 地址位于 `vhost0`，而 `eth1`/`eth2` 中哪块网卡承载内部地址，在本部署的三个节点之间并不一致。详见 [`ip`](../../network/ip/)。任何假设有更整齐命名规则的 udev 规则只会使情况更糟。

<Aside type="note" title="另有两个 edit-* 命令为直通命令，与本页无关">
`edit-etc-hosts` 和 `edit-sysctl-conf` 打开的是普通 Linux 文件，已在[节点索引](../)中列为直通命令——操作系统自身的文档已涵盖相关内容，无需补充 CE 特有说明。
</Aside>
