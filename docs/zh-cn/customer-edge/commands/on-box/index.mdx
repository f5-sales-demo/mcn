两套独立的命令集均可访问 Customer Edge，且互不包含。

- **设备本地**：Site CLI 提供 **6 个顶级命令**和 **82 个 `execcli` 子命令**。
- **网络远程**：[调试 API](../../access/debug-api/) 拥有独立的 **34** 条命令目录。

设备本地的大部分接口没有等效的 API：整个 Vega 控制平面、Envoy 封装器、数据包捕获、kubelet 参数集、`edit-*` 文件以及辅助 root 访问对，均只能从设备本地访问。

访问这些命令需要使用 [SSH](../../access/ssh/) 或[串口控制台](../../access/serial-console/)，还有一件在任何文档中都未提及的事项：

<Aside type="tip" title="execcli 是一个隐藏命令">
`execcli` 不会出现在 Site CLI 的交互式菜单中。它以命令名称作为参数，输入 `execcli ` 后按 **Tab** 键可列出全部 82 个子命令，并附带设备自身对每个命令的单行说明。该补全菜单是某个构建版本的权威命令目录，也正是 `sitecli/exec-catalog.json` 所记录的内容。
</Aside>

## 统计方式及命令集重叠情况

以下命令集并非从厂商文档中转录，而是通过 `scripts/sitecli_ssh_harvest.py` 从在线节点读取，并连同出处信息提交至 `sitecli/exec-catalog.json`。共进行了三次采集，涵盖三种注册状态：

| 采集时刻 | 顶级命令数 | `execcli` 子命令数 |
| --- | --- | --- |
| `site_state: PROVISIONING` | 6 | 82 |
| `site_state: PROVISIONED` | 6 | 82 |
| `site_state: ONLINE` | 6 | 82 |

三次采集返回**完全相同的命令集**——名称完全一致，而不仅仅是总数相同。最后一次采集来自不同的部署环境，具有不同的站点和资源名称。因此，命令接口不随注册状态变化，某个命令的缺失是真实意义上的缺失，而非尚未提供。

对比调试 API 的 34 条命令，有两个数字值得区分：

- **51** 个 `execcli` 子命令没有等效的 API。
- **55** 是在整个设备本地接口范围内统计的相同数字，因为它还包括四个 `configure*` 命令——这些命令位于顶级，而非 `execcli` 之下。

两个数字均正确；若读者重新计算其中一个并得到另一个，并非出错。本文所有数字均来源于 `sitecli/catalog.json` 和 `sitecli/exec-catalog.json`。

<Aside type="caution" title="五个不存在的命令">
`factory-reset`、`upgrade`、`reboot`、`show` 和 `clear` **不存在于**本构建版本中。这些命令是 Site CLI 合理可能具备的功能，曾基于此假设被纳入本仓库的分类一段时间，但任何枚举都未发现它们。顶级命令恰好有六个：`configure`、`configure-generic-hardware`、`configure-network`、`configure-http-proxy`、`diagnosis` 和 `health`。
</Aside>

<Aside type="caution" title="三个 API 命令不是 execcli 子命令">
在 `execcli` 下查找以下命令将一无所获，这看起来像"命令缺失"：

- **`health`** 和 **`diagnosis`** 是 Site CLI 的**顶级**命令。直接在 `>>>` 提示符下输入，无需 `execcli` 前缀。
- **`dig`** 可通过调试 API 访问，但在**任何**设备本地菜单中均不存在，因此不在下方的透传列表中。它仅限 API 访问。

</Aside>

## 哪些命令有完整文档，哪些仅作列举

Customer Edge 运行 Linux 及多个第三方守护进程。为这些命令编写文档会与其自身参考资料重复，并暗示 F5 对其拥有所有权，因此原则是：**为 F5 的软件编写文档，对于其他所有内容，仅记录 CE 特有的部分。**

分为三个层级，因为"我们的"与"他们的"并非泾渭分明。该分类记录于 `sitecli/command-classification.json`。

| 层级 | 处理方式 |
| --- | --- |
| **F5 软件** | 完整文档——用途、语法、参数、捕获的输出、关注要点。涵盖 Argo、Vega、`vpm`、`vifdump`、`configure*`、`edit-*` 命令集、kubelet 参数、root 访问。 |
| **CE 特有解读** | 某第三方工具的输出在 CE 上具有特定含义。记录 CE 特有的解读，工具本身的语义留给上游。 |
| **透传** | 纯粹的 Linux 或第三方工具，无 CE 特有内容。仅列出可用性并指引至上游。无说明文字。 |

该区分决定了是否需要为某个命令单独创建页面，同时也避免本文档退化为劣质的手册页副本。

## 透传命令

这些命令在设备上可用，但**不在此处记录文档**——它们属于操作系统和第三方守护进程，而非 F5 的软件，其自身参考资料比本页所能转述的内容更为权威。

| 命令 | 上游 |
| --- | --- |
| `ping`、`netstat`、`lsof`、`ip`、`ip-link-show`、`nmcli`、`tracepath` | iproute2、NetworkManager |
| `top`、`check-mem`、`sysctl`、`load-sysctl-conf`、`journalctl`、`files`、`rpm-ostree`、`chronyc-sources` | coreutils、procps、systemd、rpm-ostree、chrony |
| `edit-etc-hosts`、`edit-sysctl-conf` | 这些文件属于操作系统 |
| `systemctl-status-crio`、`systemctl-status-docker`、`systemctl-status-kubelet`、`systemctl-status-iscsid`、`systemctl-status-multipathd` | systemd |
| `systemctl-restart-crio`、`systemctl-restart-docker`、`systemctl-restart-kubelet`、`systemctl-restart-iscsid`、`systemctl-restart-multipathd` | systemd——每一个此类命令都会中断节点上的工作负载 |

其中有两个值得关注，即便它们没有单独的页面。`files` 执行文件操作，且只会在 `/tmp` 目录下写入。每个 `systemctl-restart-*` 命令从定义上就具有破坏性——重启 `crio` 或 `kubelet` 会中断该节点上的工作负载。

<Aside type="note" title="七个命令存在于较新构建版本而非本版本">
`collect-database-stats`、`iptables-lv`、三个 `marker-exists-*` 命令、`systemctl-restart-NetworkManager` 和 `systemctl-start-crio-prune` 是在构建版本 `crt-20260201-0179` 上通过调试 API 观察到的。它们记录在分类文件的 `not_on_this_build.newer_build_debug_api` 下，以确保此处的任何内容不会被误认为可在 `crt-20250613-3382` 上运行。

`collect-debug-info` 是一个特殊情况：它不出现在任何菜单或目录中。Site CLI 欢迎文本中提到该 CLI"允许……收集用于支持的调试信息"，因此该名称很可能是从这段文字推断而来，而非实际观察到的。它被标记为未经验证，且被刻意不作探测——在在线节点上推测性地运行未知命令，正是导致一台仍在注册中的 CE 上意外启动了 `vifdump` 数据包捕获的原因。
</Aside>
