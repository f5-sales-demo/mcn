Argo 将转发状态与 Linux 内核分开维护。当
[`ip`](../ip/) 与这些命令的输出不一致时，真正决定流量走向的是这些命令。

## `rt`

vRouter 路由表，按 VRF 划分。

```bash
{"command":["rt","--dump","2"]}
```

```text file=../../../../_data/sitecli-rt.txt
```

<Aside type="danger" title="此处的 VRF id 并不是 BGP 报告的那个">
`show-ip-bgp-summary` 输出 `vrf-id 3`。那是 FRR 的编号，与 vRouter 表 id 属于不同的命名空间。在此处传入该值会以一种看起来像节点故障的方式失败：

```
vRouter(Response):  [No such file or directory (2)]
```

`--dump 0` 也会返回同样的结果。在此拓扑中，**VRF 2** 才是已填充的 inet4 表，而 VRF 1 中有两条路由。如果你不知道 id，请从 1 开始向上探测，而不要相信 BGP 的输出。
</Aside>

## `nh`

下一跳表。每条路由都指向一个下一跳 id，此命令用于解析它们。

```bash
{"command":["nh","--list"]}
```

```text file=../../../../_data/sitecli-nh.txt
```

每个条目都带有一个 `Type` 以及所属的 VRF。这些节点上出现了八种类型，比例如下——统计后在三台 CE 上完全一致：

```text
Tunnel 558   Encap 27   NAT 22   Vrf 16   Receive 14   Composite 4   Drop 2   Resolve 2
```

解析到 `Drop` 下一跳的路由就是黑洞，每当某个前缀存在于 `rt` 中但流量仍然消失时，都值得检查这一组合。

<Aside type="caution" title="上面的抓取内容经过截断，因此并不包含所有类型">
它只是 3,849 行中的前 60 行。`Tunnel` 是数量遥遥领先的最常见类型，却完全没有出现在这 60 行中——所以不要把该抓取内容当作完整的类型清单，也不要因为某个类型未出现在截断的抓取中就断定该节点上不存在这种类型。上面的计数来自未截断的响应。
</Aside>

## `vif`

虚拟接口表：数据平面绑定了哪些接口，以及每个接口的计数器。

```bash
{"command":["vif","--list"]}
```

```text file=../../../../_data/sitecli-vif.txt
```

顶部的标志位图例值得读一遍——`Vp` 标记 vhost 物理接口，`Dpdk` 标记由 DPDK 管理的接口。用它来确认数据平面已经接管了你预期的接口，并查看 Linux 不会显示的 RX 与 TX 计数器（因为这些流量从未到达内核）。
