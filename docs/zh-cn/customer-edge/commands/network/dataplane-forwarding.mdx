Argo 将转发状态与 Linux 内核分开维护。当
[`ip`](../ip/) 与这些命令的结果不一致时，以这些命令为准来决定流量的转发。

## `rt`

vRouter 路由表，按 VRF 划分。

```bash
{"command":["rt","--dump","2"]}
```

```text file=../../../../_data/sitecli-rt.txt
```

<Aside type="danger" title="VRF id 与 BGP 报告的并非同一个">
`show-ip-bgp-summary` 输出 `vrf-id 3`，这是 FRR 的编号，与 vRouter 表 id 属于不同的命名空间。将其传入此处会以一种看似节点故障的方式失败：

```
vRouter(Response):  [No such file or directory (2)]
```

`--dump 0` 也会返回相同的错误。在此拓扑中，**VRF 2** 是已填充的 inet4 表，VRF 1 持有两条路由。如果不知道 id，请从 1 开始逐步向上探测，而不要轻信 BGP 的输出。
</Aside>

## `nh`

下一跳表。每条路由都指向一个下一跳 id，此命令用于解析它们。

```bash
{"command":["nh","--list"]}
```

```text file=../../../../_data/sitecli-nh.txt
```

每个条目包含一个 `Type` 以及所属的 VRF。这些节点上共出现八种类型，
经统计在所有三个 CE 上的分布完全相同：

```text
Tunnel 558   Encap 27   NAT 22   Vrf 16   Receive 14   Composite 4   Drop 2   Resolve 2
```

路由解析到 `Drop` 下一跳即为黑洞路由，当某个前缀存在于 `rt` 中但流量仍然消失时，这种组合值得重点排查。

<Aside type="caution" title="上方抓取的内容已被截断，并不包含所有类型">
这是 3,849 行中的前 60 行。`Tunnel` 是迄今为止最常见的类型，但在这 60 行中完全没有出现——因此请勿将此抓取内容视为完整的类型清单，也不要因为某类型未出现在截断的抓取中就断定该节点不存在该类型。上方的计数来自完整的未截断响应。
</Aside>

## `vif`

虚拟接口表：数据平面绑定的内容以及各接口的计数器。

```bash
{"command":["vif","--list"]}
```

```text file=../../../../_data/sitecli-vif.txt
```

顶部的标志说明值得仔细阅读一次——`Vp` 标记 vhost 物理接口，`Dpdk` 标记由 DPDK 管理的接口。可借此确认数据平面是否已接管预期的接口，并查看 Linux 无法显示的 RX 和 TX 计数器（因为该流量从未到达内核）。

## `mpls`

```bash
execcli mpls --help
```

Argo MPLS 表。**仅可从设备本机访问**——`mpls` 不在调试 API 中，因此与上述 `rt`、`nh`、`vif` 不同，需要通过 [SSH](../../../access/ssh/) 或
[串口控制台](../../../access/serial-console/)，并借助
[`execcli`](../../on-box/) 来使用。

此处没有抓取示例输出。在本部署中，CE 使用 BGP 和 ECMP 转发 IPv4，不使用 MPLS 标签，因此抓取内容将显示空表，毫无参考价值。其存在性及 `--help` 参数形式已通过设备自身的补全菜单验证；其填充后的输出不在此处复现。
