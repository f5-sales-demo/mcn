CE 使用 FRR 运行 BGP。在此拓扑中，它与两个 Azure Route Server 实例建立对等，通告 VIP，并学习 VNet 前缀。

## `show-ip-bgp-summary`

从这里开始。一屏即可告知对等是否已建立，以及它保持稳定了多久。

```bash
{"command":["show-ip-bgp-summary"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp-summary.txt
```

首先查看 `State/PfxRcd`。数字表示收到的前缀数量，意味着会话已建立；其他任何内容——`Active`、`Connect`、`Idle`——都表示会话未建立。`Up/Down` 显示当前状态已持续多久，因此不断重置的会话会显示一个可疑的小数值。

<Aside type="caution" title="这里的 vrf id 不是 rt 需要的那个">
此输出报告 `vrf-id 3`。那是 FRR 的编号。Argo 数据平面使用另一套表 id，将 FRR 的编号传给
[`rt --dump`](../dataplane-forwarding/) 会返回 `No such file or directory`，看起来像是节点故障，而实际上只是参数用错了。
</Aside>

## `show-ip-bgp`

完整的路由表，可以看到最佳路径选择。

```bash
{"command":["show-ip-bgp"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp.txt
```

`*` 表示有效路由，`>` 表示选中的最佳路径，`=` 表示多路径成员。在上面的抓取中，学习到的 VNet 前缀 `10.0.0.0/16` 有两条路径——分别经由每个 Route Server 实例——标记为 `*=` 和 `*>`：一条最佳路径加一个多路径成员，因此该节点会在两个实例之间对其回程流量进行负载分担。VIP `10.250.0.10/32` 只有一条 `*>` 路径，因为它是由该节点发起通告的。

<Aside type="caution" title="演示中的三路 ECMP 在此输出中不可见">
`show-ip-bgp` 只是一个节点的路由表。本部署所演示的 ECMP 是三个*不同*的 CE 通告同一个 `/32`，且它是在 Azure 侧编程的——因此任何单个 CE 的 BGP 表都无法显示它，而此处 VIP 上没有多路径标记也并非故障。
应改为从 Route Server 对等或客户端的有效路由表来验证；
两者都在[竣工文档页面](../../../../as-built/)上。
</Aside>

## `show-ip-bgp-neighbors`

逐邻居的详细信息：协商的能力、定时器、消息计数器以及上次重置的原因。

```bash
{"command":["show-ip-bgp-neighbors"]}
```

当摘要显示某个会话在抖动、而你需要知道原因时，就用它。`Last reset` 及其原因是有用的几行。

<Aside type="note" title="此页面尚无抓取的输出">
在 `f5-sales-demo/docs-control#795` 合并之前无法提交此抓取内容。FRR
在其 Graceful Restart 行中拼错了一个单词，而 `codespell` 会拒绝该文件。

修改抓取到的文本会让本文档描述从未真实出现过的输出，因此改为在上游修复。在此期间，请在你自己的节点上运行该命令。
</Aside>

## `show-ip-bgp-neighbors-advertised-route`

该节点正在告知其对等体的内容，与它所知道的内容相对。

```bash
{"command":["show-ip-bgp-neighbors-advertised-route"]}
```

```text file=../../../../_data/sitecli-show-ip-bgp-neighbors-advertised-route.txt
```

这是用于排查“VIP 无法从 VNet 访问”的命令。如果这里没有 VIP，问题就出在该节点上，再怎么查看对等体也无济于事。

该输出会**为每个对等体**重复一个 `bgp neighbor:` 块，因此在此拓扑中你会看到相同的两个前缀出现两次——每个 Route Server 实例各一次。这不是重复渲染：正是它确认了该节点在向两者通告。真正值得关注的情况是：某个对等体有该块，而另一个缺失或内容偏少。
