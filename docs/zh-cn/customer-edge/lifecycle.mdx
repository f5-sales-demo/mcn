两个 Terraform 变量用于设置 Customer Edge 的软件：`ce_os_version` 对应操作系统，`ce_sw_version` 对应 F5 Distributed Cloud 构建版本。两者的实际行为与直觉理解恰好相反，一旦配置错误，代价是整个集群的重建。

## 版本字段的作用：分两个阶段理解

区分阶段是理解这一问题的关键。若将两个阶段混为一谈，其行为看起来便会自相矛盾。

**首次启动时，节点始终会执行升级。** `terraform/modules/ce-node` 使用 `version = "latest"` 部署 Marketplace 镜像，而该镜像所附带的构建版本**早于**租户实际运行的版本。因此，无论是否设置该字段，升级都会发生。`ce_sw_version` 仅决定升级的**目标版本**——留空意味着由服务器决定目标版本，而非不执行任何操作。`ce_os_version` 同理。

**此后，节点不会自动升级。** F5 Distributed Cloud 会通告更新的构建版本并等待用户操作。因此，留空字段并不等同于"跟踪最新版本"：节点将停留在首次落地时的版本。

两个阶段均可在 Site 对象上观察到。`观测于 2026-07-28`，该集群：

```text
volterra_software_status.available_version   crt-20260201-0179
operating_system_status.available_version    9.2026.14
```

而节点运行的版本为 `crt-20250613-3382`，操作系统版本为 `9.2024.6`。更新的构建版本已提供但尚未被采用——这是稳定状态，而非升级卡住的现象。

## 更改版本需要重建，且 Terraform 不会替你完成

`ce_os_version` 和 `ce_sw_version` 均为**仅在创建时生效**的参数，且失败的方式比被拒绝的 apply 更为糟糕。具体过程如下：

1. 修改值并执行 apply。Terraform 提议原地更新。
2. API **拒绝**该请求——`[BAD_REQUEST] Invalid request parameters`。
3. 该被拒绝的请求仍会清除服务器上的字段值，而 Provider 的 read 操作不会将此情况反映出来。Terraform 的状态与实际对象由此产生分歧。
4. 此后每次 plan 都会持续提议**相同的失败变更**，无限循环。

因此，Terraform 不会回退到替换 Site，而是陷入卡死状态，并持续卡死，直到你主动替换 Site 及其 CE 虚拟机为止。将集群迁移到不同版本是一项**需要提前规划的重建操作**，而非可以直接 apply 的编辑。

<Aside type="danger" title="替换 CE 的所有后果均会发生">
新的 SSH 主机密钥、重新分配的内部地址、全新的注册流程，以及仅存在于节点上的所有数据将全部丢失。Cloud-init 会在新虚拟机上重新执行，因此以该方式配置的 SSH 访问可以保留——但 cloud-init *仅在首次启动时运行*，因此所有手动添加到旧节点上的内容都将消失。

在安排此操作之前，请阅读 [SSH](./access/ssh/) 以了解主机密钥和地址变更的影响。
</Aside>

<Aside type="note" title="已记录，未在此处复现">
该拒绝行为与状态分歧已记录在本仓库的 `terraform/modules/xc-site` 注释中——已在三个 Site 上分别对固定版本和取消固定两个方向进行了验证，并对应 Provider Issue `xcsh#1387`。本页面未重新测试此问题，因为测试会导致部署在每次 plan 时持续提议失败的变更。
</Aside>

## 文档所描述的构建版本

本站命令参考描述的是 **`crt-20250613-3382`**，即该集群当前运行的版本。仅在更新版本中观测到的命令已按名称记录在 `sitecli/command-classification.json` 的 `not_on_this_build` 字段下，不会作为可执行命令进行说明。请参阅[节点内命令](./commands/on-box/)。

<Aside type="caution" title="请勿为了使用新命令而规划重建">
目前已有更新的构建版本可用，但其是否能在本拓扑上顺利安装尚无定论——有报告显示其在单节点 Azure Secure Mesh v2 Site 上安装失败，也有观测到 Customer Edge 成功运行该版本的记录。鉴于租户中现有信息有限，两者均无法得到确认。

由于版本变更意味着集群重建，上述不确定性是当前的核心事实：应将使用这些命令视为未经验证的操作，而非已规划的升级。相关证据及可用于验证的实验均记录于 `sitecli/README.md`。
</Aside>
