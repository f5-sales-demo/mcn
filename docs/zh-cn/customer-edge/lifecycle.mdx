两个 Terraform 变量用于设置客户边缘节点的软件：`ce_os_version` 用于操作系统，`ce_sw_version` 用于 F5 Distributed Cloud 构建版本。两者的行为方式与直观理解恰好相反——留空字段会获取最新构建而非不安装任何内容，而在一个节点上能成功安装的版本，可能会因另一个完全相同但磁盘较小的节点而失败。

## 版本字段的作用：两个阶段

区分这两个阶段是理解整个问题的关键。若将两者混淆，行为看起来便会自相矛盾。

**在首次启动时，节点会安装 `ce_sw_version` 所指定的版本。**
`terraform/modules/ce-node` 使用 `version = "latest"` 部署市场镜像，因此节点初始携带的构建版本取决于该镜像当前所附带的内容——而这会随时间变化。`ce_sw_version` 选择的是**目标版本**，而非是否执行安装操作；留空意味着由服务端决定，而非节点保持原状。`ce_os_version` 同理。

不要假设变化方向必然是向上升级。`观测于 2026-07-28`，镜像所附带的构建版本标记为 `20260703-e2c462a`——比本舰队的 `crt-20250613-3382` 更新，也比租户当时发布的 `crt-20260201-0179` 更新。若指定的构建版本旧于镜像所携带的版本，则要求节点向后降级，这属于正常操作：本舰队正是以这种方式创建并运行的。

**留空版本字段是风险最高的选择，而非中立选择。** 在创建时，服务端不会将空字段保持为空——它会以**最新发布**的版本填充，并安装该版本。一个两个字段均未设置的站点，最终被固定为 `crt-20260201-0179` 和操作系统 `9.2026.14`（即租户当时发布的两个版本），随后安装失败。`观测于 2026-07-29`。

这带来两个后果：留空意味着"给我最新版本"，因此未固定版本的部署最可能遇到下文所述的磁盘限制；同时，你无法通过留空其中一个字段来单独隔离另一个字段，因为服务端会自动填充——请明确设置两个字段，或接受各自的最新版本。

**首次启动后，不会发生任何自动升级。** F5 Distributed Cloud 会发布更新的构建版本并等待。"节点保持在初始状态"这一说法在首次创建之后成立，而非创建过程中。

两个阶段均可在站点对象上观察到。`观测于 2026-07-28`，本舰队：

```text
volterra_software_status.available_version   crt-20260201-0179
operating_system_status.available_version    9.2026.14
```

而节点运行的是 `crt-20250613-3382` 和操作系统 `9.2024.6`。更新的构建版本已提供但尚未被采用——这是稳定状态，而非升级停滞。

## Terraform 无法更改版本，但 API 可以

这是两个独立的事实，混淆它们会导致错误的计划。

**Terraform 无法更改。** `ce_os_version` 和 `ce_sw_version` 实际上只在创建时有效。修改其中任意一个并执行 apply，API 会以 `[BAD_REQUEST] Invalid request parameters` 拒绝更新。`观测于 2026-07-29`，在临时站点上，涵盖三个方向——**向前**固定到更新的构建版本、**向后**固定到旧版本，以及通过清空两个字段来**取消固定**。向前升级并非特殊情况。

**API 可以更改。** F5 Distributed Cloud 为每个站点提供专用的升级操作，该操作会就地启动版本变更——无需重建，也无需 Terraform 参与：

```bash
# 软件构建版本
curl -X POST -H "Authorization: APIToken $TOKEN" -H 'Content-Type: application/json' \
  --data '{"version": "<software-version>"}' \
  "$API_URL/api/config/namespaces/system/sites/<site-name>/upgrade_sw"

# 操作系统
curl -X POST -H "Authorization: APIToken $TOKEN" -H 'Content-Type: application/json' \
  --data '{"version": "<os-version>"}' \
  "$API_URL/api/config/namespaces/system/sites/<site-name>/upgrade_os"
```

`观测于 2026-07-29`：软件升级调用返回 `200`，站点进入 `UPGRADING` 状态，`deployment_state.phase` 为 `UPGRADE_IN_PROGRESS`，站点对象中的请求版本变更为所提交的版本。省略该字段会返回 `400`，错误信息为 `version empty in the request`，字段名称由此得到确认。

**请预留数小时而非数分钟，且遇到失败不必慌张。** 在默认磁盘节点上，升级到 `crt-20260201-0179` 大约耗时一小时，中途报告了 `UPGRADE_FAILED`，`result` 为 `Failed`，但随后**成功完成**并运行在新版本上。平台会自动重试。

这对监控升级或编写升级脚本的人员有直接影响：`Failed` 结果是一个需要等待观察的状态，而非最终判定。将第一个失败结果视为最终结论，会将一个最终会成功的升级报告为失败。

注意路径中的分组：这些接口位于 **`config`** 下，而非 `operate`。`operate` 下相同路径会返回 `404 API Group could not be determined`，这是一条路由消息，并非表示不存在升级接口——这一区别曾让本项目得出错误结论。

<Aside type="caution" title="通过 API 升级会导致 Terraform 状态不同步">
固定变量仍保持原有值，因此实际运行的站点版本与配置中记录的版本不符。Terraform 不会对此进行协调——因为更新会被拒绝——请将 API 升级视为主动脱离 Terraform 控制的操作，并在下次重建时更新固定版本以与实际保持一致。
</Aside>

<Aside type="note" title="本页面早前的两处说明，现已撤回">
本页面此前表示，将 CE 迁移到不同版本需要重新创建站点；并且被拒绝的更新"仍会清除服务端的字段"，导致 Terraform 持续提出失败的变更。经测试，两者均不成立：上述 API 升级可以就地启动版本变更，无需重新创建任何内容；而在三次被拒绝的更新之后，站点的 spec 均**未发生变化**，站点保持 `ONLINE` 状态。provider issue `xcsh#1387` 中描述的差异是在站点已自动升级超出其固定版本的情况下观察到的，因此可能需要这种差异的起始状态；在 spec 与固定版本一致的站点上未能复现。
</Aside>

如果选择重建而非升级，则替换 CE 的所有后果均适用。

<Aside type="danger" title="替换 CE 的所有后果均适用">
新的 SSH 主机密钥、重新分配的内部地址、全新的注册，以及仅存在于节点上的所有数据的丢失。Cloud-init 会在新虚拟机上重新运行，因此以该方式配置的 SSH 访问能够保留——但它**仅**在首次启动时运行，因此手动添加到旧节点的任何内容都将丢失。

在安排此操作之前，请阅读 [SSH](./access/ssh/) 以了解主机密钥和地址变更的影响。
</Aside>

## 固定的构建版本可能安装失败，站点随即陷入卡死状态

接受固定版本与成功安装该版本并不等同。在一个新创建的、固定为 `crt-20260201-0179` 的单节点 Azure Secure Mesh v2 客户边缘节点上，站点对象立即反映了固定版本——随后安装失败：

```text
site_state        PROVISIONING
phase             UPGRADE_FAILED
result            Failed
last_installed    (empty)
message           stage: 10, app: voucher obj: voucher objKind: DaemonSet failed ...
                  required replicas: 1, current replicas: 0
```

`观测于 2026-07-28`，并于 2026-07-29 复现两次。**操作系统**固定版本在同一次运行中正常安装（`9.2024.6` 升级至 `9.2026.14`，`UPGRADE_COMPLETED`）；仅软件安装失败。站点始终未达到 `ONLINE` 状态，`last_installed_version` 保持为空，因此未回滚到可用构建版本——此前没有成功安装的记录可供回滚。

**创建时的失败与升级过程中的失败不同。** 两者行为有所差异，在决定是否干预时，这一差异至关重要：

| | 创建时 | 通过 API 升级期间 |
| --- | --- | --- |
| 是否会重试并最终成功？ | 否——两次均在超过 20 分钟后保持 `Failed` 状态 | 是——恢复并完成 |
| 节点最终处于什么状态？ | `PROVISIONING`，未安装任何内容 | `ONLINE`，运行可用构建版本 |
| 是否可以置之不理？ | 否，已陷入卡死 | 是，会自行恢复或保留旧版本 |

因此，创建时的失败需要使用更大磁盘重建，而升级过程中报告 `Failed` 应等待一段时间再做判断。

**失败原因是磁盘，而非版本。** 通过一个软件版本 × 操作系统版本 × 磁盘大小的矩阵，每种组合创建一个临时单节点 Azure Secure Mesh v2 站点，均使用相同的市场镜像，可以将问题隔离。`观测于 2026-07-29`：

| 软件版本 | 操作系统 `9.2024.6`（镜像自带） | 操作系统 `9.2026.14` |
| --- | --- | --- |
| `crt-20250613-3382` | 安装成功 | 安装成功 |
| `crt-20260201-0179` | 安装成功 | **失败**，仅在默认磁盘上 |

单独使用任何一个版本均不会失败。只有组合使用时才会失败，且仅在镜像默认磁盘上——相同的版本组合在 **40 GB**、**48 GB** 和 **64 GB** 磁盘上均可正常安装。因此，更新的构建版本本身并不不受支持，更新的操作系统亦然；两者共同使用时需要比默认节点更多的磁盘空间。

`terraform/modules/ce-node` 未设置 `disk_size_gb`，因此每个客户边缘节点均使用镜像默认磁盘。**若要运行更新的版本组合，请扩大磁盘容量。** 40 GB 是经测试可用的最小尺寸；确切边界位于镜像默认值与 40 GB 之间，未作进一步细化。

无论如何，在将版本变更应用到整个舰队之前，请先在临时站点上进行测试：以这种方式失败的舰队会卡在 `PROVISIONING` 状态，唯一的出路是重新创建。

<Aside type="caution" title="请勿以 F5 的升级前检查数值作为磁盘大小依据">
F5 文档中的升级前检查要求剩余 20 GB 加 15% 的容量空间。该检查适用于**控制台 UI** 升级，并明确不适用于 API 发起的升级，因此无法描述本文所述的失败场景。按该公式计算，48 GB 磁盘应该会失败；但实际上 48 GB 安装正常。请以上述实测结果作为磁盘大小依据，而非该公式。
</Aside>

<Aside type="note" title="本页面早前提供的一种解释，现已撤回">
本页面早期版本曾提出，安装失败是因为请求的构建版本旧于镜像所携带的版本——即节点被要求向后降级。这是错误的。本舰队曾使用**早十三个月**的固定版本从相同镜像创建，安装正常；且当操作系统固定版本保持为镜像自带版本时，`crt-20260201-0179` 同样能够成功安装。升级方向并非决定性因素。
</Aside>

## 文档所描述的构建版本

本站点的命令参考描述的是 **`crt-20250613-3382`**，即本舰队运行的构建版本。仅存在于更新构建版本中的命令已记录在 `sitecli/command-classification.json` 的 `not_on_this_build` 下，并单独归档为[更新构建版本上的命令](./commands/on-box/newer-builds/)，因此其中的内容不应视为在本版本可运行。另请参阅[节点内命令](./commands/on-box/)。

<Aside type="note" title="升级到更新构建版本的方式已明确，且无需重建">
此前本处记录为未解决问题，有报告指出更新构建版本在单节点 Azure Secure Mesh v2 站点上失败，同时存在一例运行正常的反向观察。现两者均已得到解释：更新构建版本可在该拓扑上安装，失败原因是上述磁盘限制，而非构建版本本身。

因此存在两条路径，且两者本身均无需重建——创建具有足够大磁盘的节点，或通过 API 升级现有节点。`观测于 2026-07-29`。
</Aside>
