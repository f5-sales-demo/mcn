`vpm/debug` API 可在已注册的节点上运行 Site CLI 命令并返回其输出。以下内容均基于实际运行节点验证所得，上游均未发布相关文档。

## 命令目录具有自描述性

通过向 `exec-user` 发送 POST 请求（**省略** `command` 键）来查询节点所支持的命令：

```bash
curl -sS -X POST \
  -H "Authorization: APIToken $XCSH_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"namespace":"system","site":"<site>","node":"<node>"}' \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/<node>/exec-user" \
  | jq -r .output | jq .
```

响应为一个以命令名称为键的 JSON 对象：

```json
{
  "crictl-inspect": ["System Troubleshooting", "ExecUser", " container-id"],
  "diagnosis":      ["System Troubleshooting", "ExecUser", "no argument needed", "GLOBAL"],
  "ip-link-set":    ["Network Troubleshooting", "Exec", " (<device>||<group>) (up||down)"]
}
```

每个条目的格式为 `[category, tier, exampleArgument?, scope?]`，这些字段并非仅供参考——它们决定了该命令必须以何种方式调用。

<Aside type="caution" title="省略该键；切勿发送错误的值">
发现功能通过省略 `command` 来实现。若发送未知值，则返回错误，而非命令目录：

```json
{"code":3,"details":[],"message":"exec command failed: command not supported"}
```

该报错信息与*真实*命令发送到错误端点时返回的信息相同，因此很容易被误读为"此命令不存在"。
</Aside>

## 三种传输方式，由目录条目决定

| 条件 | 方法和路径 | 请求体 | 返回值 |
| --- | --- | --- | --- |
| `scope` 为 `GLOBAL` | `GET .../vpm/debug/global/<cmd>` | 无 | JSON |
| `tier` 为 `ExecUser` | `POST .../vpm/debug/<node>/exec-user` | `command` 数组 | 文本 |
| `tier` 为 `Exec` | `POST .../vpm/debug/<node>/exec` | `command` 数组 | 文本 |

### `ExecUser` — 只读层级 <Badge text="31 个命令" variant="note" />

最常见的情况。将命令及其参数以数组形式传递，命令名称在前：

```bash
curl -sS -X POST \
  -H "Authorization: APIToken $XCSH_API_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"namespace":"system","site":"<site>","node":"<node>","command":["crictl-ps"]}' \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/<node>/exec-user"
```

```json
{ "return_code": 0, "output": "CONTAINER    IMAGE    CREATED    STATE ..." }
```

参数应作为独立的数组元素传递，而非单个字符串：

```json
{ "command": ["journalctl", "-u", "vpm", "-n", "200"] }
```

### `GLOBAL` — 站点级别，且使用完全不同的传输方式 <Badge text="2 个命令" variant="tip" />

`health` 和 `diagnosis` 是仅有的两个此类命令。它们使用 `GET` 请求访问 `global` 路径，无需任何参数，并返回结构化 JSON，而非终端文本。

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/global/health" | jq .
```

<Aside type="danger" title="GLOBAL 命令无法通过 exec-user 访问">
这是最容易耗费时间的陷阱。将 `health` 或 `diagnosis` 发送到 `exec-user` 会返回 `command not supported`，看起来像是节点上不存在该命令——而实际上该命令存在，只是使用了错误的传输方式。

```bash
# 错误。返回：exec command failed: command not supported
-d '{"namespace":"system","site":"…","node":"…","command":["health"]}'   # POST exec-user

# 正确。
GET .../vpm/debug/global/health
```

</Aside>

### `Exec` — 特权层级 <Badge text="当前版本中有 1 个命令" variant="danger" />

使用独立的端点，且层级限制是强制执行的，而非建议性的：将 `ExecUser` 命令发送到 `exec` 端点，同样会返回 `command not supported` 错误。该层级中的每个命令要么会更改节点状态，要么会读取状态标记。

在当前租户运行的版本中，该层级仅包含 `ip-link-set`。更新版本还新增了 `systemctl-restart-NetworkManager`、`systemctl-restart-crio`、`systemctl-restart-kubelet`、`systemctl-start-crio-prune` 以及三个 `marker-exists-*` 命令。

<Aside type="danger" title="此处不执行任何 Exec 命令">
采集框架拒绝执行此层级的命令，并从实时目录中读取层级信息，而非使用硬编码列表——因此，若未来版本将某个命令晋升至 `Exec` 层级，系统会自动遵守，无需人工修改代码。如需执行此类命令，请谨慎操作，且仅在您愿意承担中断风险的节点上执行。
</Aside>

## 查找站点名称和节点名称

节点名称即 Azure 虚拟机名称，`list-service` 是一种便捷方式，可同时确认节点名称及其上运行的服务：

```bash
curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
  "$XCSH_API_URL/api/operate/namespaces/system/sites/<site>/vpm/debug/global/list-service" \
  | jq -r '[.service[].node] | unique'
```

## 复现本仓库的采集结果

每个命令页面均包含由 `scripts/capture-sitecli.sh` 采集的输出，该脚本实现了上述全部三条规则。

<Steps>

1. 将其指向某个租户。脚本读取 `XCSH_API_URL` 和 `XCSH_API_TOKEN`，若未设置则回退至当前活跃的 `xcsh` 上下文。

2. 刷新目录并确认节点在文档编写期间未发生变更：

   ```bash
   bash scripts/capture-sitecli.sh --check
   ```

   此步骤仅对比已提交的目录与软件版本。版本变更与命令的新增或删除会分别报告。

3. 如需获取最新数据，重新采集：

   ```bash
   bash scripts/capture-sitecli.sh
   ```

</Steps>

<Aside type="note" title="采集结果是佐证材料，而非可复现的产物">
由于计数器、运行时长和容器存在时间在每次运行之间都会变化，重新采集必然会产生差异。目录是稳定的约定，当节点未发生变更时，其内容在各次运行之间字节完全一致；这正是 `--check` 所比较的内容。较长的输出会被截断，并以明确的标记结尾，因此截断的表格不会被误呈现为完整内容。
</Aside>

<Aside type="danger" title="从客户节点采集数据时：请检查脱敏配置">
命令输出包含基础设施身份信息——内部地址、MAC 地址、AS 号码、主机名——对于客户而言，这些都是可识别其组织的敏感信息。

因此，脱敏过滤器默认使用**严格**配置，会移除所有上述信息。本仓库在 `sitecli/capture-manifest.json` 中声明了 `lab` 配置，该配置会保留这些细节，这仅在本仓库中是合适的，因为这些采集数据来自 F5 自有的演示基础设施。

**请勿将该设置用于客户数据的采集。** 令牌、私钥、租户标识符、对象 UUID、电子邮件地址和主目录路径在两种配置下均会被移除。

有一项限制值得关注：BGP 邻居表以裸列格式打印 AS 号码，没有可供锚定匹配模式的标签，因此 AS 号码通过值与私有范围进行匹配。**公开** AS 号码在严格配置下不会被移除，在发布 `show-ip-bgp*` 的输出之前，需要进行人工审查。
</Aside>
