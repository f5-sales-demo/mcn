Azure 串行控制台通过 Azure 平台连接到节点的仿真串行端口。它不经过 F5 Distributed Cloud 控制平面、节点数据平面，也不经过任何由节点控制的网络路径——这正是它在其他所有方式都失效时仍能正常工作的原因。

当 CE **从未成功启动**时，请使用此方式：注册失败、站点未出现在租户中，或者节点已启动但没有出向路由。在上述所有情况下，[调试 API](../debug-api/) 没有可用的隧道进行中继。[SSH](../ssh/) 可以在注册失败时继续使用，但前提是其密钥已在首次启动时写入，并且您能够从 VNet 内部访问节点的内部地址——而对于您首次接触的节点，这两个条件通常都不满足。

## 先决条件：启动诊断

Azure 要求在 VM 上启用启动诊断，然后才能连接串行控制台。`terraform/modules/ce-node` 中已启用此功能：

```hcl
boot_diagnostics {}
```

空块选择 Azure 托管存储，因此无需自行管理诊断存储账户、生命周期策略或访问密钥。在节点上确认配置：

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="启用操作不具有追溯效力">
启动诊断在**启动时**捕获串行日志。对已在运行中的 VM 开启此功能，不会为已完成的启动过程生成日志，因此 `az vm boot-diagnostics get-boot-log` 将返回：

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

这是预期行为，并非故障。日志将在节点下次重启后生成。而实时控制台连接则会立即生效——它不依赖于日志文件。
</Aside>

## 在无终端环境下检查可用性

连接操作需要交互式会话，但判断*能否*连接只需两次 API 调用，这在健康检查中非常有用。

该服务必须在订阅中启用——管理员可以在租户级别将其禁用：

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

然后请求连接到特定节点的串行端口：

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

以 `wss://` 开头的 `connectionString`——在本部署中为 `eastus.gateway.serialconsole.azure.com`——表示控制台当前可连接。在启用启动诊断之前，此调用没有可连接的目标。

<Aside type="danger" title="该连接字符串是凭据">
它是嵌入在 URL 中的短期有效的持有者令牌。请勿将其记录到日志、粘贴到工单或提交到代码库中。在演示调用成功时，仅打印主机名即可。
</Aside>

## 连接操作

<Steps>

1. 安装扩展（仅需一次）：

   ```bash
   az extension add --name serial-console
   ```

2. 连接：

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. 您将进入节点自身的登录提示符，而非直接获得 Shell。这是站点 CLI，需要在节点上设置的凭据——来自配置时的管理员密码，或通过修改密码端点设置的密码。串行控制台验证的是*通道*是否可用，它不会绕过身份验证。

</Steps>

以下内容捕获自 `f5-xc-ce-vm-01`，中间部分因 systemd 单元输出冗余而已省略：

```text file=../../../_data/serial-console-boot.txt
```

该记录中有四点值得关注，因为它们回答了调试 API 无法回答的问题：

- **cloud-init 已完成** — `Datasource DataSourceAzure`，在 22.37 秒时完成。从未完成注册的节点通常在此处失败，可以在这里看到具体原因。
- **两个容器运行时均已启动。** `Container Runtime Interface for OCI (CRI-O)` 和 `Docker Application Container Engine` 均显示 `[ OK ]`，这是启动时对双运行时行为的验证——该行为在 [crictl](../../commands/system/crictl/) 和 [docker](../../commands/system/docker/) 中常令人感到困惑。
- **`VP Manager image load` 和 `Argo Watch service`** — `vpm` 和 Argo 正在启动。
- **提示符为节点自身的提示符**，位于其审计横幅之后。串行控制台提供的是登录提示符，而非已建立的会话。

<Aside type="caution" title="交互式连接需要真实终端——但可通过脚本实现自动化">
`az serial-console connect` 会将终端切换到原始模式，因此无法在管道或任何缺少 TTY 的环境中运行。它会在客户端侧失败，而非在联系 Azure 之前：

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

该堆栈跟踪属于终端处理问题，并非串行控制台中断。

然而，连接操作本身**是**可以自动化的——直接驱动 WebSocket 而无需使用 CLI。上方的记录正是以这种方式捕获的，无需 TTY。请参阅 `scripts/serial_console_capture.py`，了解如何在无人值守的情况下从注册失败的节点收集启动证据。
</Aside>

<Aside type="caution" title="请做好重试准备：网关大约每隔一次请求会拒绝连接">
网关的第一帧是质询，而非输出，客户端需要用持有者令牌进行响应。即使操作正确，Socket 也经常立即关闭：

```
[close] code=1011 reason=Connection not trusted
```

观察到的现象：连接成功是间歇性的，在持续使用过程中，资源组中的每个节点都会拒绝连接——包括数分钟前还能正常使用的节点。`scripts/serial_console_capture.py` 默认启用重试，因为重试通常有效。

**原因尚未确定。** 以下情况已被排除，因为每种情况都是容易浪费时间的合理猜测：

| 不是此原因 | 确认方法 |
| --- | --- |
| ARM/计算层限流 | 限流会在 ARM 调用上返回 HTTP `429`。此处是单独数据通道上的 WebSocket 关闭。 |
| 代理的 TLS 拦截 | `openssl s_client -connect <region>.gateway.serialconsole.azure.com:443 \| openssl x509 -noout -issuer`。若颁发者确实为 `O=Microsoft Corporation` 可排除此原因；若颁发者为代理厂商则可确认，修复方法是将 `*.serialconsole.azure.com` 加入允许列表。 |
| 启动诊断已禁用 | `az vm show -g <rg> -n <vm> --query diagnosticsProfile` 报告 `enabled: true`。 |
| 授权令牌与质询令牌不匹配 | 对两者使用同一令牌是正确做法，但不能防止连接关闭。 |

**有据可查的 Azure 行为**：**每个 VM 只允许一个串行控制台会话，第二次成功的请求会驱逐第一个会话。** 被驱逐的用户会断开连接，但不会被注销，因此 Shell 会话仍然存在。两个人同时调试同一节点时，会相互反复驱逐对方。

对于批量操作，建议使用 [调试 API](../debug-api/) 或 [SSH](../ssh/)，这两者均无上述限制。特别是 SSH，没有粘贴字符数上限，也没有单会话限制，因此只要节点可从 VNet 内部访问，SSH 是更优的选择。
</Aside>

<Aside type="caution" title="粘贴内容上限为 2,048 个字符">
Azure 将串行控制台的粘贴长度限制为 2,048 个字符，以避免串行端口过载。发送长命令——或在一次写入中发送多条命令——会导致失败，表现为挂起或限流，而非明确的长度超限提示。

请逐条发送命令。这是通过串行控制台进行批量数据收集的实际限制，也是建议优先使用 [调试 API](../debug-api/) 处理此类工作的另一原因。
</Aside>

## 此处可见而 API 无法呈现的信息

- **cloud-init** 的运行、失败或从未启动——这是节点从未完成注册的常见原因。
- **注册尝试**——针对 `register.ves.volterra.io` 的注册请求，包括配置错误或租户拒绝的令牌。
- **内核和启动消息**——来自任何代理运行之前的阶段。
- 节点处于**无可用网络路径**状态时的情况，这会导致所有其他访问方式均失效。

对于处于 `ONLINE` 状态的节点，建议优先使用调试 API：它支持脚本化操作，生成可重复执行的证据，且不会占用唯一的串行端口。
