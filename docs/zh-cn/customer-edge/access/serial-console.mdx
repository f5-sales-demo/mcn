Azure 串行控制台通过 Azure 平台连接到节点的模拟串行端口。它不经过
F5 Distributed Cloud 控制平面、节点的数据平面，也不经过任何由节点掌控的网络路径——
这正是它在其他一切手段都失效时依然可用的原因。

当某个 CE **从未成功启动**时就该用它：注册失败、租户中查不到该站点，
或者节点已启动但没有对外路由。在上述所有情况下，
[调试 API](../debug-api/) 都没有可用于中继的隧道，而
[SSH 在此版本上无法完成身份验证](../ssh/)。

## 前提条件：引导诊断

Azure 要求虚拟机启用引导诊断，之后才会挂载串行控制台。
该功能由 `terraform/modules/ce-node` 启用：

```hcl
boot_diagnostics {}
```

空白块表示选用 Azure 托管存储，因此无需自行管理诊断存储账户、生命周期策略或访问密钥。在节点上确认：

```bash
az vm show -g <resource-group> -n <vm-name> --query diagnosticsProfile
```

```json
{ "bootDiagnostics": { "enabled": true } }
```

<Aside type="caution" title="启用该功能不具有追溯效力">
引导诊断在**引导时**捕获串行日志。为已经运行中的虚拟机启用该功能，
不会为已经发生的那次引导生成日志，因此
`az vm boot-diagnostics get-boot-log` 会返回：

```
<Error><Code>BlobNotFound</Code><Message>The specified blob does not exist.
```

这是预期行为，并非故障。节点下次重启之后才会存在引导日志。不过实时控制台挂载可以立即使用——它并不依赖日志。
</Aside>

## 不使用终端检查可用性

挂载需要交互式会话，但要判断它*是否能*挂载只需两次 API 调用。二者在健康检查中都很有用。

该服务必须为订阅启用——管理员可以在整个租户范围内禁用它：

```bash
az rest --method get --url \
  "https://management.azure.com/subscriptions/<sub>/providers/Microsoft.SerialConsole/consoleServices/default?api-version=2018-05-01"
```

```json
{ "properties": { "disabled": false } }
```

然后请求连接到特定节点的串行端口：

```bash
az rest --method post \
  --headers "Content-Type=application/json" --body '{}' --url \
  "https://management.azure.com/subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Compute/virtualMachines/<vm>/providers/Microsoft.SerialConsole/serialPorts/0/connect?api-version=2018-05-01"
```

返回以 `wss://` 开头的 `connectionString`——在本部署中为
`eastus.gateway.serialconsole.azure.com`——表示控制台此刻可以挂载。
在启用引导诊断之前，该调用没有可挂载的对象。

<Aside type="danger" title="该连接字符串是一项凭据">
它是嵌入在 URL 中的短期 bearer 令牌。不要记录它、不要粘贴到工单中，也不要提交到代码库。
在演示该调用成功时，只打印主机名。
</Aside>

## 挂载

<Steps>

1. 一次性安装扩展：

   ```bash
   az extension add --name serial-console
   ```

2. 挂载：

   ```bash
   az serial-console connect -g <resource-group> -n <vm-name>
   ```

3. 你会进入节点自身的登录提示符，而不是 shell。这是 Site CLI，
   需要在节点上设置好凭据——预配时的管理员密码，
   或通过更改密码端点设置的密码。串行控制台证明*通道*可用；
   它不会绕过身份验证。

</Steps>

以下内容捕获自 `f5-xc-ce-vm-01`，中间省略了 systemd 单元输出中无意义的部分：

```text file=../../../_data/serial-console-boot.txt
```

该记录中有四处值得注意，因为它们回答了调试 API 无法回答的问题：

- **cloud-init 已完成**——`Datasource DataSourceAzure`，在 22.37 秒时结束。
  从未注册成功的节点通常就是在此处失败的，而这里正是你能看到它的地方。
- **两种容器运行时都已启动。** `Container Runtime Interface for OCI (CRI-O)`
  和 `Docker Application Container Engine` 都是 `[ OK ]`，这正是在
  [crictl](../../commands/system/crictl/) 和 [docker](../../commands/system/docker/)
  中令人意外的双运行时行为的引导时证据。
- **`VP Manager image load` 和 `Argo Watch service`**——`vpm` 与 Argo 正在启动。
- **提示符属于节点自身**，位于其审计横幅之后。串行控制台给你的是登录提示符，而不是会话。

<Aside type="caution" title="交互式挂载需要真实终端——但它也可以脚本化">
`az serial-console connect` 会将终端置于原始（raw）模式，因此它无法在流水线或任何没有 TTY 的环境中运行。它在联系 Azure 之前就会在客户端失败：

```
ERROR: (19, 'Operation not supported by device')
  File ".../azext_serialconsole/custom.py", line 633, in connect_serialconsole
    GV.serial_console_instance.launch_console()
```

该回溯是终端处理问题，而非串行控制台故障。

不过挂载本身**是**可自动化的——直接驱动 websocket，而不使用 CLI。上面的记录就是这样在没有 TTY 的情况下捕获的。参见
`scripts/serial_console_capture.py`，你可以用它在无人坐在终端前的情况下，从注册失败的节点收集引导证据。
</Aside>

<Aside type="caution" title="预期需要重试：网关大约每两次尝试就拒绝一次">
网关的第一帧是一个挑战（challenge），而不是输出，客户端需以 bearer 令牌应答。即使正确完成该步骤，套接字往往也会立即关闭：

```
[close] code=1011 reason=Connection not trusted
```

观察到的行为：它时断时续地成功，而在持续使用时资源组中的每个节点都会拒绝连接——包括几分钟前还能正常工作的节点。
`scripts/serial_console_capture.py` 默认进行重试，因为重试往往有效。

**原因尚未确定。** 以下是已被排除的可能，因为每一项都是看似合理却会浪费时间的猜测：

| 并非如此 | 如何确认 |
| --- | --- |
| ARM/计算限流 | 那会在 ARM 调用上返回 HTTP `429`。而这是在独立数据通道上的 websocket 关闭。 |
| 代理进行的 TLS 拦截 | `openssl s_client -connect <region>.gateway.serialconsole.azure.com:443 \| openssl x509 -noout -issuer`。真实的 `O=Microsoft Corporation` 颁发者可排除此项；若颁发者为某代理厂商则可确认此项，解决办法是将 `*.serialconsole.azure.com` 加入允许列表。 |
| 引导诊断被禁用 | `az vm show -g <rg> -n <vm> --query diagnosticsProfile` 报告 `enabled: true`。 |
| 授权与挑战之间的令牌不匹配 | 两处使用同一个令牌是正确做法，但并不能避免连接关闭。 |

而以下**确实**是有文档记录的 Azure 行为：**每个虚拟机只允许一个串行控制台会话，第二次成功请求会挤掉第一个。**
被挤掉的用户会断开连接但不会退出登录，因此 shell 会话得以保留。两个人同时调试同一节点会反复把对方顶下线。

批量作业请优先使用[调试 API](../debug-api/)，它没有这些限制。
[SSH 不是替代方案](../ssh/)——在此版本上无法启用它。
</Aside>

<Aside type="caution" title="粘贴上限为 2,048 个字符">
为避免串行端口过载，Azure 将串行控制台的粘贴长度限制为 2,048 个字符。发送过长的命令——或在一次写入中批量发送多条命令——会以看似挂起或被限流的方式失败，而不像是长度限制。

请逐条发送命令。这对通过串行控制台进行的任何批量收集都是真实的限制，也是该类工作应优先选择[调试 API](../debug-api/) 的另一个原因。
</Aside>

## 在这里能看到而 API 无法呈现的内容

- **cloud-init** 正在运行、失败或从未启动——这是节点从未注册成功的常见原因。
- 针对 `register.ves.volterra.io` 的**注册尝试**，包括配置错误或被租户拒绝的令牌。
- 任何代理运行之前的**内核与引导消息**。
- 节点**没有可用网络路径**时的状态，这种情况会使其他所有访问途径失效。

对于状态*确实*为 `ONLINE` 的节点，请优先使用调试 API：它可脚本化、能产出可重复运行的证据，而且不会占用唯一的串行端口。
