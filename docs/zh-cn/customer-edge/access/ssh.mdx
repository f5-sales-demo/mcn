SSH 连接的是设备的 `admin` 账户，其登录 shell 是 Site CLI
（`/opt/bin/vpmu`）。这是通往**完整的机上命令面**的唯一途径 ——
[debug API](../debug-api/) 只暴露 34 条命令，而设备本身提供的许多命令根本不在该 API 上。

```bash
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<operator-vm> admin@10.0.3.5
```

这条命令行的每一部分都不可或缺，接下来的三个小节将说明每一部分各自避免了哪种故障。

<Aside type="caution" title="仅限引导阶段 —— 现有的 CE 无法在不重建的情况下获得 SSH">
cloud-init 的 `write_files` **仅在首次启动时运行一次**。此后节点上会存在
`/etc/cloud/cloud-init.disabled` 标记文件，cloud-init 不会再次运行。

因此不存在对运行中 CE 的原地改造路径。`custom_data` 在 Azure 中是只可替换的，
这意味着在现有部署上采用此方案会**替换每一台 CE 虚拟机**。为已经运行的节点授予运维 SSH
是一次重建，而不是一次配置变更 —— 下一条警告说明了这次重建目前的代价。
</Aside>

<Aside type="danger" title="替换 CE 虚拟机会卡住注册流程，而在整个集群宕机期间 terraform plan 却报告 'No changes'">
这是本页中最沉重的内容。请在**计划**此变更**之前**阅读
[issue 674](https://github.com/f5-sales-demo/mcn/issues/674)，而不是之后。

陈旧的注册记录占据着唯一的 `(tenant, cluster_name, hostname)` 索引，因此替换节点的注册会被以
`UniqueSecondaryIndexViolationError` 拒绝，并且会永远重试。仅仅删除注册记录还不够：残留的
`StatusObject` 会使工作负载请求返回 `500`，而到那时每个节点都已持久化了一份
`registration-obj.yml`，将自身固定到你刚删除的那条注册记录上，于是它便在 `404` 上循环，无法自行恢复。

恢复过程需要删除注册记录、重新创建站点对象、**第二次替换虚拟机**，
然后再执行审批 —— 为吸收一次 `custom_data` 变更付出了两轮完整重建。

在整个过程中，`terraform plan` 始终报告**"No changes"**，因为从 Terraform 的视角看，
期望状态已经达成。集群宕机了，而 plan 是干净的。不要把吸收此变更当作一次例行的 apply。
</Aside>

## 为什么由 cloud-init 写入密钥，而不是 API

站点对象上的 `admin_user_credentials.ssh_key` 看起来完全就是为此而设的字段。它会被接受、
读回后依然存在，却什么也不配置。`vpm` 管理着节点的本地用户，并拒绝去碰这一个 ——
以下取自节点自身的日志，在一次启动中出现了三遍：

```text
vpm  users.go:165: Won't do any change for user admin (internal skip)
```

其余现象都源于这一行。无论站点是否已达到 `ONLINE`，`/var/home/admin/.ssh` 都从不存在。
`admin` 的 shadow 最后修改日期停留在镜像构建日期，而 `vesbkp` 和 `vesopcon` 显示的是当前日期，
因为 `vpm` 设置了这两个用户，跳过了 `admin`。并且 `vpm` 在任何时候都没有记录关于 `ssh_key`
或 `authorized_keys` 的日志。

所以这个文件必须在 `vpm` 之外写入。`admin` 的 uid 是 2202，已固化在节点镜像中，
因此它在 cloud-init 运行之前就已存在，`owner: admin:admin` 在写入时即可解析 ——
无需 `runcmd`，无需事后修正属主：

```yaml
- path: /var/home/admin/.ssh/authorized_keys
  permissions: "0600"
  owner: admin:admin
  content: |
    ${ssh_public_key}
```

`sshd` 一直是配合的。`sshd -T` 报告 `pubkeyauthentication yes`，并且 `admin`
出现在节点自带的两份 `sshd_config` 文件的 `AllowUsers` 中。从来没有什么需要启用的东西 ——
只是缺了一个文件。

<Aside type="danger" title="不要重新添加 admin_user_credentials，也不要编辑 sshd_config">
`admin_user_credentials` 曾被接入 `terraform/modules/xc-site`，并在收集到上述证据后被回退（#660、PR #663）。
它不是一处等待填补的空缺。

`sshd_config` 会在注册期间被替换，因此对它的编辑会在最不合时宜的时刻被丢弃。
</Aside>

## 为什么它只在一个地址上响应

`sshd` 绑定 `0.0.0.0:22`，但只有**内部（SLI）**地址位于主机网络栈上。eth0 被重命名为
`a-i-eth0` 且不携带主机 IP —— 该接口由 Argo 数据平面接管 —— 而 eth1 和 eth2 留在主机栈上，
`sshd` 正是在那里监听。

从 VNet 内部的一台虚拟机上探测：

```text
10.0.1.4     timed out             CE mgmt/SLO  (eth0)
10.0.2.4     timed out             CE external  (eth1)
10.0.3.5     OPEN                  CE internal/SLI
10.0.3.6     OPEN
10.0.3.7     OPEN
```

因此，针对你所熟知的节点地址做探测，返回的结果与安全组关闭时完全一样。
没有任何东西在阻断它；只是那个地址上没有监听器。

CE 的公网地址在 22 端口上同样没有监听器，这正是上述命令要经过 `-J` 的原因：
一台位于 VNet 内、与 SLI 地址处于同一子网的运维虚拟机。

<Aside type="caution" title="两种会得出自信却错误结论的测量失误">
针对 eth0、外部接口或公网地址探测 22 端口，无论节点的 SSH 状态如何都会报告关闭，
因此它根本无法告诉你任何信息。只有 SLI 地址会响应。

而从公司工作站发起的探测可能会把一个实际关闭的端口报告为**开放**：
Netskope 会在常见端口上自行完成 TCP 握手。从工作站看，CE 公网地址的 80 和 443
端口显示为开放，而从 VNet 内部探测时它们是关闭的。请从 VNet 内的虚拟机进行探测。
</Aside>

## Site CLI 需要一个终端，以及一个回车符

`admin` 的登录 shell 并不是一个 shell。它是一个 `go-prompt` 应用，会将终端置于原始模式，
按键读取而非按行读取。由此产生四个后果，每一个的失败方式看起来都像是另一种问题：

| 机制 | 缺少它会发生什么 |
| --- | --- |
| 分配一个终端（`ssh -tt`） | `go-prompt.NewStandardInputParser` 抛出 `panic: no such device or address`，看起来像设备崩溃 |
| Enter 发送回车符（CR），而不是换行符（LF） | 该行永远不会被提交，会话在输入结束时关闭，且什么也没打印 |
| 保持标准输入打开 | 连接在命令渲染完成之前就结束了，于是一条正常工作的命令看起来毫无输出 |
| 将命令文本与 Enter 字节**分开**写入 | 换行符会作为字面字符落入缓冲区，CLI 回复 `unknown command`，看起来像是该命令不存在 |

因此 `ssh host 'some-command'` 是行不通的：参数会被忽略，交互式提示符照样启动。
要么把它当作终端来驱动，要么就别用。
`scripts/sitecli_ssh_harvest.py` 是参考实现。

<Aside type="caution" title="出现 'no such device or address' 的 panic 意味着认证已成功">
`vpmu` 是在登录**之后**、发现没有可附着的终端时才抛出它的。若把它读作崩溃，
它看起来像是最糟糕的结果，而实际上它是成功前的最后一个错误。加上
`-tt` 再连接一次。
</Aside>

<Aside type="caution" title="替换 CE 会改变它的主机密钥">
替换后的节点在同一地址上呈现不同的主机密钥，因此下一次连接会警告
`REMOTE HOST IDENTIFICATION HAS CHANGED` 并拒绝连接。请清除该地址的旧条目后重新连接。
由于授予 SSH 本身就会替换虚拟机，采用该方案后的第一次连接就应预期会遇到这一情况。
</Aside>

登录横幅会报告节点的注册状态，这是区分仍在启动中的节点与已损坏节点的最快方式：

```text
Registration Status: PROVISIONING
SLO IP: 10.0.1.4/26
```

## 提供密钥对

<Steps>

1. 如果尚未拥有密钥对，先生成一个。使用 Ed25519 而非 RSA：更短，
   并且被设备的 `sshd` 接受。

   ```bash
   ssh-keygen -t ed25519 -C "ce-operator" -f ~/.ssh/id_ed25519
   ```

2. 让部署指向**公钥**部分。根模块读取该文件一次，
   并将字符串向下传递给每个节点：

   ```hcl
   # terraform/terraform.tfvars
   ssh_public_key_path = "~/.ssh/id_ed25519.pub"
   ```

   `ssh_public_key` 则改为内联接收密钥材料，plan 测试使用的正是这种方式。
   私钥部分绝不会离开你的工作站。

3. 执行 apply。请先阅读本页顶部的警告 —— 在现有部署上，这会替换 CE 虚拟机。

</Steps>

<Aside type="note" title="虚拟机自身的 admin_ssh_key 是另一回事">
`modules/ce-node` 中的 `azurerm_linux_virtual_machine.admin_ssh_key` 授权的是 Azure
虚拟机管理员，而不是设备的 `admin` 账户。它不授予任何 Site CLI 访问权限，
设置了它也不能证明 CE SSH 已配置好。
</Aside>

## 这不是什么

以下每一项都在该路径仍被认为不可能时经过了测试并被排除。
每一项都足够貌似合理，足以让你耗掉一天。

| 并非原因 | 如何被排除 |
| --- | --- |
| 该凭据仅在创建时生效 | `sshd` 在首次启动约 90 秒时启动，早于站点对象存在。`admin_user_credentials` 同样出现在 `ReplaceSpecType` 中并可原地生效。 |
| `block_all_services` | 无论服务是否被阻断，管理地址上 22 端口的关闭状态完全一致。 |
| 密钥末尾的换行符 | 两种方式都测试过，没有变化。cloud-init 仍会去掉它，因为字面块否则会渲染出第二行空行。 |
| 固定的较旧 CE 软件版本 | 在三个构建版本上复现，其中一个运行 OpenSSH 9.9。 |
| 缺少 `admin_password` | 在一台全新的 CE 上同时设置 `admin_password` 和 `ssh_key`，没有任何变化。 |

<Aside type="caution" title="两个看似区分因素、实则不是的 API 字段">
`gc_spec.admin_ssh_key` 在**租户内全部 88 个站点上**都是空的，包括那 20 个设置了
`admin_password` 的站点。在一个可用站点和一个不可用站点之间比较它不会告诉你任何信息，
因为它在哪里都是空的。

`registrations_by_site` 完全省略了该字段，并为其返回 `None`，读起来像是
"未配置"，而实际上是"未上报"。
</Aside>

<Aside type="caution" title="新创建的站点需要大约半小时后 operate API 才会响应">
在新站点报告 `ONLINE` 之后的大约 25 到 30 分钟内，`vpm/debug` 端点会返回一个 BIG-IP
`503` 页面，内容为 `The requested URL was rejected`。这看起来像是 Web
应用防火墙拦截，或令牌被吊销，但两者都不是：站点还没准备好中继。请等待并重试，不要去改动任何东西。

SSH 没有这样的预热期。只要 `sshd` 起来了它就会响应，这也正是它能在节点仍在注册时依然可用的原因。
</Aside>
