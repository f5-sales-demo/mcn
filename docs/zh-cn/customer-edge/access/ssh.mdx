SSH 连接至设备的 `admin` 账户，其登录 Shell 为站点 CLI
（`/opt/bin/vpmu`）。这是访问**完整在机命令界面**的唯一途径——
[调试 API](../debug-api/) 仅暴露 34 条命令，而设备本身提供的许多命令并未包含在该 API 中。

```bash
ssh -tt -i ~/.ssh/id_ed25519 -J azureuser@<operator-vm> admin@10.0.3.5
```

该命令行的每个部分都至关重要，接下来三节将分别说明每个部分所防止的故障。

<Aside type="caution" title="在运行中的部署上启用此功能将替换虚拟机">
密钥由 cloud-init 写入，而 cloud-init 的 `write_files` 仅在**首次启动时**运行。
为现有节点启用此功能意味着需要替换这些节点，而这目前会导致注册卡住：
旧的注册记录占用了唯一的 `(tenant, cluster_name, hostname)` 索引，替换节点将永远无法完成注册，
且在此期间 `terraform plan` 始终报告"No changes"。
请在规划变更**之前**查阅 [issue 674](https://github.com/f5-sales-demo/mcn/issues/674)，而非之后。
</Aside>

## 为何由 cloud-init 而非 API 写入密钥

站点对象上的 `admin_user_credentials.ssh_key` 字段看起来正是用于此目的的。
该字段可以被接受，回读时仍然存在，但实际上不配置任何内容。`vpm` 管理节点的本地用户，
并拒绝对该账户进行任何操作——从节点自身日志中，在单次启动过程中出现了三次：

```text
vpm  users.go:165: Won't do any change for user admin (internal skip)
```

后续一切问题均源于这一行日志。无论站点是否达到 `ONLINE` 状态，
`/var/home/admin/.ssh` 均不存在。`admin` 的 shadow 最后修改日期停留在镜像构建日期，
而 `vesbkp` 和 `vesopcon` 则显示当前日期，原因是 `vpm` 设置了这两个账户而跳过了 `admin`。
`vpm` 日志中也没有任何关于 `ssh_key` 或 `authorized_keys` 的记录。

因此，该文件必须在 `vpm` 之外写入。`admin` 的 uid 为 2202，已固化在节点镜像中，
因此在 cloud-init 运行之前该账户已存在，`owner: admin:admin` 在写入时即可解析——
无需 `runcmd`，也无需修正所有权：

```yaml
- path: /var/home/admin/.ssh/authorized_keys
  permissions: "0600"
  owner: admin:admin
  content: |
    ${ssh_public_key}
```

`sshd` 本身始终是允许的。`sshd -T` 报告 `pubkeyauthentication yes`，
且 `admin` 出现在节点上两个 `sshd_config` 文件的 `AllowUsers` 中。
从来不需要启用任何功能——缺少的只是一个文件。

<Aside type="danger" title="请勿重新添加 admin_user_credentials，也请勿编辑 sshd_config">
`admin_user_credentials` 曾被纳入 `terraform/modules/xc-site`，在收集到上述证据后已回滚（#660，PR #663）。
这并非一个有待填补的缺口。

`sshd_config` 在注册过程中会被替换，因此对其所做的任何编辑都会在最不方便的时刻被丢弃。
</Aside>

## 为何仅在一个地址上响应

`sshd` 绑定 `0.0.0.0:22`，但主机网络栈上只有**内部（SLI）**地址。
eth0 被重命名为 `a-i-eth0` 且不携带主机 IP——Argo 数据平面拥有该接口——
而 eth1 和 eth2 保留在主机网络栈上，`sshd` 正在其上监听。

从 VNet 内部的虚拟机探测结果如下：

```text
10.0.1.4     timed out             CE mgmt/SLO  (eth0)
10.0.2.4     timed out             CE external  (eth1)
10.0.3.5     OPEN                  CE internal/SLI
10.0.3.6     OPEN
10.0.3.7     OPEN
```

因此，对已知节点地址的探测返回的结果与安全组关闭时完全相同。
这并非被阻断——该地址上根本没有监听器。

CE 的公共地址上也没有端口 22 的监听器，这就是上述命令使用 `-J` 的原因：
通过 VNet 内部、与 SLI 地址同子网的运营商虚拟机进行跳转。

<Aside type="caution" title="两种会产生错误确信结论的测量误区">
探测 eth0、外部接口或公共地址的 22 端口，无论节点的 SSH 状态如何，报告结果均为关闭，
因此无法提供任何有效信息。只有 SLI 地址才会响应。

此外，从企业工作站探测时，可能将实际关闭的端口报告为**开放**：
Netskope 会在常见端口上自行完成 TCP 握手。从工作站探测 CE 公共地址时，
80 和 443 端口显示为开放，但从 VNet 内部探测时则为关闭。请从 VNet 内的虚拟机进行探测。
</Aside>

## 站点 CLI 需要终端和回车符

`admin` 的登录 Shell 并非真正的 Shell，而是一个 `go-prompt` 应用程序，
它会将终端置于原始模式并逐键读取输入，而非按行读取。这带来四个后果，
每种后果的失败方式看起来都像是不同的问题：

| 机制 | 缺少时的现象 |
| --- | --- |
| 分配终端（`ssh -tt`） | `go-prompt.NewStandardInputParser` 产生 `panic: no such device or address`，看起来像设备崩溃 |
| 按 Enter 时发送回车符而非换行符 | 该行永远不会被提交，会话在输入结束时关闭且不打印任何内容 |
| 保持标准输入打开 | 命令渲染完成前连接已结束，因此正常工作的命令看起来没有任何输出 |
| **分别**写入命令文本和 Enter 字节 | 换行符作为字面字符落入缓冲区，CLI 返回 `unknown command`，看起来像该命令不存在 |

因此 `ssh host 'some-command'` 无法工作：参数被忽略，交互式提示符照常启动。
要么以终端方式驱动，要么根本无法使用。
`scripts/sitecli_ssh_harvest.py` 是参考实现。

登录横幅报告节点的注册状态，这是区分仍在启动中的节点与已损坏节点的最快方式：

```text
Registration Status: PROVISIONING
SLO IP: 10.0.1.4/26
```

## 提供密钥对

<Steps>

1. 如尚未拥有密钥对，请生成一个。使用 Ed25519 而非 RSA：更短，且被设备的 `sshd` 接受。

   ```bash
   ssh-keygen -t ed25519 -C "ce-operator" -f ~/.ssh/id_ed25519
   ```

2. 将**公钥**部分指向部署。根模块读取该文件一次，并将字符串传递给每个节点：

   ```hcl
   # terraform/terraform.tfvars
   ssh_public_key_path = "~/.ssh/id_ed25519.pub"
   ```

   `ssh_public_key` 也可以直接内联接受密钥内容，计划测试使用的即为此方式。
   私钥永远不会离开您的工作站。

3. 应用。请先阅读本页顶部的警告——在现有部署上执行此操作将替换 CE 虚拟机。

</Steps>

<Aside type="note" title="虚拟机自身的 admin_ssh_key 是另一回事">
`modules/ce-node` 中的 `azurerm_linux_virtual_machine.admin_ssh_key` 授权的是 Azure
虚拟机管理员，而非设备的 `admin` 账户。它不授予站点 CLI 访问权限，
且已设置该字段并不能证明 CE SSH 已配置。
</Aside>

## 此方案排除了哪些情况

以下各项均在该路径仍被认为不可能时进行了测试并被排除。每一项都有足够的迷惑性，可能耗费一天时间。

| 非原因 | 排除方式 |
| --- | --- |
| 凭据仅在创建时生效 | `sshd` 在首次启动约 90 秒后启动，此时站点对象尚不存在。`admin_user_credentials` 也存在于 `ReplaceSpecType` 中，可就地应用。 |
| `block_all_services` | 无论服务是否被阻断，管理地址上端口 22 的关闭状态完全相同。 |
| 密钥末尾的换行符 | 两种方式均已测试，无变化。cloud-init 仍会将其去除，因为字面块否则会渲染出第二个空行。 |
| 固定的旧版 CE 软件 | 在三个构建版本上均已复现，其中一个运行的是 OpenSSH 9.9。 |
| 缺少 `admin_password` | 在全新 CE 上同时设置 `admin_password` 和 `ssh_key` 未产生任何变化。 |

<Aside type="caution" title="两个看似可作为判断依据但实际上无效的 API 字段">
`gc_spec.admin_ssh_key` 在**租户中全部 88 个站点**上均为空，包括设置了 `admin_password` 的 20 个站点。
在可用与不可用的站点之间对比该字段毫无意义，因为它在所有地方均为空。

`registrations_by_site` 完全省略该字段，并为其返回 `None`，看起来像"未配置"而非"未上报"。
</Aside>

<Aside type="caution" title="新建站点在 operate API 响应前需要约半小时">
新站点报告 `ONLINE` 后约 25 至 30 分钟内，`vpm/debug` 端点会返回 BIG-IP 的 `503` 页面，
内容为 `The requested URL was rejected`。这看起来像 Web 应用防火墙拦截或令牌被吊销，
但实际上两者都不是：站点尚未准备好进行中继。请等待后重试，而非修改任何配置。

SSH 没有此类预热期。只要 `sshd` 启动，它就会响应，这也是为何在节点仍在注册时 SSH 是可用路径的原因。
</Aside>
