共有三种连接方式，具体适用哪一种取决于节点的状态以及您的连接来源，而非个人偏好。

| 方式 | 需要节点处于 `ONLINE` 状态 | 需要网络可达性 | 限制 | 覆盖范围 |
| --- | --- | --- | --- | --- |
| [调试 API](./debug-api/) | **是** | 是 | 新站点约需 25–30 分钟预热 | 34 条命令 |
| [SSH](./ssh/) | 否 | 仅限从 VNet 内部连接到内部地址 | 密钥必须在首次启动时存在 | 完整的节点 Site CLI |
| [串行控制台](./serial-console/) | 否 | 否 | 每个 VM 仅限一个会话；粘贴上限为 2,048 个字符 | 完整的节点 Site CLI |

串行控制台是最后的手段，也是唯一一种在节点没有可用网络路径时仍然有效的方式。

当调试 API 不够用时，应首选 SSH，因为该设备提供的命令远多于 API 所暴露的 34 条。但 SSH 有两个代价：密钥由 cloud-init 写入，因此必须在**首次启动**时存在，这意味着在运行中的节点上启用它会触发节点替换——而这目前会导致注册卡住（[issue 674](https://github.com/f5-sales-demo/mcn/issues/674)）。此外，`sshd` 仅监听节点的内部地址，因此需要 VNet 内部的主机才能访问；通过您已知的节点地址进行探测，始终会报告连接被拒绝。

## 为什么这种划分不是偏好问题

调试 API 由 F5 分布式云控制平面提供服务，它通过 `vpm` 在注册期间建立的隧道将请求转发到节点。没有注册就没有隧道，也就意味着 API 没有任何转发目标。

其失败方式并不直观，而是表现为 API 问题，因此一个从未启动成功的节点看起来像是 API 出了问题。

串行控制台则完全不同——它通过 Azure 平台连接到节点的模拟串行端口。它不关心节点是否已注册、是否具有网络可达性，或者数据平面是否正常工作。这种独立性正是其核心价值所在，也是为什么 CE VM 上必须始终启用启动诊断的原因。

<Aside type="note" title="应该选择哪种方式">
如果您正在编写自动化脚本，或收集希望日后重新运行的数据，请使用调试 API。如果注册本身出现了问题，串行控制台并非备用方案——它是唯一的选择。
</Aside>

## 凭据

两种方式使用不同的凭据，且均不应出现在命令行中。

- **调试 API** — F5 分布式云 API 令牌，以 `XCSH_API_TOKEN` 形式提供，租户 URL 以 `XCSH_API_URL` 形式提供。`xcsh` 上下文文件位于 `~/.config/xcsh/contexts/<tenant>.json`，其中保存了这两项配置，当环境变量未提供时，`scripts/capture-sitecli.sh` 会从该文件中读取。
- **串行控制台** — 您的交互式 Azure 登录。此处没有服务主体可用：F5 企业 Entra 租户不允许配置服务主体，这也是为什么此流程没有任何部分在 CI 中运行的原因。

<Aside type="danger" title="切勿将令牌作为参数传递">
命令行中的令牌会进入 shell 历史记录和进程列表，机器上的其他所有用户都可以读取。正因如此，`capture-sitecli.sh` 直接拒绝 `--token` 参数，并通过 stdin 将请求头传递给 `curl`。
</Aside>
