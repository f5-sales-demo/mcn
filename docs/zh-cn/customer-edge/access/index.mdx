三种途径都可行，具体适用哪一种取决于节点的状态以及你从何处发起连接，而不是取决于个人偏好。

| 途径 | 需要节点处于 `ONLINE` | 需要网络可达性 | 限制 | 覆盖范围 |
| --- | --- | --- | --- | --- |
| [调试 API](./debug-api/) | **是** | 是 | 新站点需要约 25–30 分钟的预热时间 | 34 条命令 |
| [SSH](./ssh/) | 否 | 需从 VNet 内部连接，且仅限内部地址 | 密钥必须在首次启动时就已存在 | 设备上完整的 Site CLI |
| [串行控制台](./serial-console/) | 否 | 否 | 每台 VM 仅一个会话；粘贴上限 2,048 个字符 | 设备上完整的 Site CLI |

串行控制台是最后的手段，也是唯一在节点完全没有可用网络路径时仍然有效的途径。

当调试 API 不够用时，就该使用 SSH，因为设备提供的命令远多于该 API 暴露的 34 条。它有两项代价。密钥由 cloud-init 写入，因此必须在**首次启动**时就存在，这意味着要在已运行的节点上启用它就得替换节点——而这目前会导致注册卡死（[issue 674](https://github.com/f5-sales-demo/mcn/issues/674)）。此外，`sshd` 仅在节点的内部地址上响应，因此需要一台位于 VNet 内部的主机；探测你平常用来标识该节点的地址永远只会报告端口关闭。

## 为什么这种区分不是偏好问题

调试 API 由 F5 分布式云控制平面提供服务，它通过 `vpm` 在注册期间建立的隧道中继到节点。没有注册就没有隧道，也就意味着 API 无处可中继。

它的失败方式令人费解而非一目了然，因此一个从未成功启动的节点看起来像是 API 出了问题。

串行控制台走的是完全不同的路径——通过 Azure 平台连接到节点的模拟串行端口。它并不关心节点是否已注册、是否具备网络可达性，或数据平面是否正常工作。这种独立性正是它的意义所在，也是必须在 CE 虚拟机上保持启用引导诊断的原因。

<Aside type="note" title="该选用哪一种">
如果你在编写自动化脚本，或在收集希望日后可重复执行的证据，请使用调试 API。如果出问题的正是注册环节，串行控制台就不是备选方案——它是唯一的选择。
</Aside>

## 凭据

每种途径使用不同的凭据，并且它们都不应出现在命令行中。

- **调试 API** —— 一个 F5 分布式云 API 令牌，通过 `XCSH_API_TOKEN` 提供，租户 URL 通过 `XCSH_API_URL` 提供。位于 `~/.config/xcsh/contexts/<tenant>.json` 的 `xcsh` 上下文文件同时保存了这两项，当环境未提供它们时，`scripts/capture-sitecli.sh` 会读取该文件。
- **SSH** —— 密钥对中的私钥部分（其公钥部分由部署过程在首次启动时写入 `/var/home/admin/.ssh/authorized_keys`），以及一台位于 VNet 内部、可用于连通内部地址的主机。以 `admin` 身份连接，而非 `azureuser`。
- **串行控制台** —— 你的交互式 Azure 登录。此处没有服务主体可用：F5 企业 Entra 租户不允许创建服务主体，这也是为什么这部分工作完全不在 CI 中运行。

<Aside type="danger" title="切勿将令牌作为参数传递">
命令行中的令牌会留在 shell 历史记录和进程列表中，机器上的任何其他用户都能读取。正因如此，`capture-sitecli.sh` 直接拒绝 `--token`，改为通过 stdin 将请求头提供给 `curl`。
</Aside>
