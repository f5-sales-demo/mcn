有两条路径可用，具体适用哪一条由节点的状态决定，而非由个人偏好决定。

| 路径 | 需要节点处于 `ONLINE` | 需要网络可达性 | 限制 | 涵盖范围 |
| --- | --- | --- | --- | --- |
| [Debug API](./debug-api/) | **是** | 是 | 新站点需约 25–30 分钟预热 | 34 条命令 |
| [串行控制台](./serial-console/) | 否 | 否 | 每个虚拟机仅限一个会话；粘贴上限 2,048 个字符 | 完整的机上 Site CLI |

串行控制台是最后的手段，也是唯一在节点没有可用网络路径时仍然有效的路径。

[**SSH 不是第三条路径。**](./ssh/) 在该租户运行的构建版本上，`admin` 账户无法完成身份验证，`vpm` 从不应用该密钥，也没有任何站点设置可以改变这一点。该页面的存在是为了记录相关证据，因为那里的每一种故障模式看起来都像是防火墙或凭据问题。

## 为什么这种区分不是偏好问题

Debug API 由 F5 分布式云控制平面提供服务，它通过 `vpm` 在注册期间建立的隧道中继到节点。没有注册就没有隧道，也就意味着 API 没有可中继的目标。

它的失败方式并不明显，反而毫无帮助，因此一个从未启动成功的节点看起来像是 API 问题。

串行控制台走的是完全不同的路径 —— 通过 Azure 平台连接到节点的模拟串行端口。它并不关心节点是否已注册、是否具备网络可达性，或数据平面是否正常工作。这种独立性正是其意义所在，也是为什么必须在 CE 虚拟机上保持启用引导诊断。

<Aside type="note" title="该选择哪一种">
如果你正在编写自动化脚本，或收集希望日后重新运行的证据，请使用 Debug API。如果出问题的正是注册环节，那么串行控制台不是备选方案 —— 它是唯一的选择。
</Aside>

## 凭据

两条路径使用不同的凭据，且两者都不应出现在命令行中。

- **Debug API** —— 一个 F5 分布式云 API 令牌，以 `XCSH_API_TOKEN` 形式提供，同时以 `XCSH_API_URL` 形式提供租户 URL。位于 `~/.config/xcsh/contexts/<tenant>.json` 的 `xcsh` 上下文文件同时保存这两项，当环境未提供它们时，`scripts/capture-sitecli.sh` 会读取该文件。
- **串行控制台** —— 你的交互式 Azure 登录。这里没有服务主体：F5 企业 Entra 租户不允许预配服务主体，这也是为什么这部分内容完全不在 CI 中运行的原因。

<Aside type="danger" title="切勿将令牌作为参数传递">
命令行上的令牌会留在 shell 历史记录和进程列表中，机器上的所有其他用户都能读取到。正因如此，`capture-sitecli.sh` 直接拒绝 `--token`，而是通过标准输入将请求头提供给 `curl`。
</Aside>
