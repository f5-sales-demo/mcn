共有四种可用路由，具体采用哪种由节点状态、连接来源以及目标访问需求决定，而非取决于个人偏好。

| 路由 | 需要节点 `ONLINE` | 需要网络可达性 | 限制 | 覆盖范围 |
| --- | --- | --- | --- | --- |
| [调试 API](./debug-api/) | **是** | 是 | 新站点约需 25–30 分钟预热 | 34 条命令 |
| [站点控制台](./site-console/) | 否 | 通过 Azure Bastion，无需跳板机 | Bastion 必须为支持隧道的 Standard SKU | F5 节点故障排查 UI |
| [SSH](./ssh/) | 否 | 从 VNet 内部，仅限内部地址 | 密钥必须在首次启动时写入 | 完整的节点上站点 CLI |
| [串行控制台](./serial-console/) | 否 | 否 | 每个 VM 一个会话；粘贴内容上限 2,048 个字符 | 完整的节点上站点 CLI |

串行控制台是最后的手段，也是唯一在节点没有任何可用网络路径时仍能使用的路由。

[站点控制台](./site-console/)通常是首选尝试方案。它对您的要求最少——无需分发 SSH 密钥、无需跳板机、节点上不需要公网 IP，也无需替换 VM——因为访问权限变成了 Azure RBAC 决策，而非凭据分发问题。它提供的是 F5 自有的故障排查 UI，而非命令界面，因此当您需要执行特定命令或进行脚本化操作时，需要使用其他路由。

SSH 是在调试 API 不够用时的选择，因为该设备提供的命令数量远超 API 公开的 34 条。它有两个代价。密钥由 cloud-init 写入，因此必须在**首次启动**时就存在，这意味着在运行中的节点上启用 SSH 将导致节点被替换——而这目前会导致注册卡住（[问题 674](https://github.com/f5-sales-demo/mcn/issues/674)）。此外，`sshd` 仅监听节点的内部地址，因此需要 VNet 内部的主机才能访问；直接探测您已知的节点地址将始终报告端口关闭。

## 为何这种区分不是偏好问题

调试 API 由 F5 分布式云控制平面提供服务，该控制平面通过 `vpm` 在注册期间建立的隧道将请求中继到节点。未完成注册意味着没有隧道，也就意味着 API 无法中继任何内容。

其失败方式并不直观，因此从未正常启动的节点看起来像是 API 问题。

串行控制台则完全走另一条路——通过 Azure 平台访问节点的模拟串行端口。它不关心节点是否已注册、是否具有网络可达性，或者数据平面是否正常工作。这种独立性正是其核心价值所在，也是为什么 CE 虚拟机上必须保持启用启动诊断的原因。

<Aside type="note" title="应选择哪种路由">
如果您正在编写自动化脚本，或收集需要在稍后重新执行的证据，请使用调试 API。如果问题出在注册本身，串行控制台不是备选方案——它是唯一的选项。
</Aside>

## 凭据

每种路由使用不同的凭据，且任何凭据都不应出现在命令行中。

- **调试 API** — F5 分布式云 API 令牌，以 `XCSH_API_TOKEN` 形式提供，并以 `XCSH_API_URL` 形式提供租户 URL。`xcsh` 上下文文件位于 `~/.config/xcsh/contexts/<tenant>.json`，其中存储了两者，当环境变量未提供时，`scripts/capture-sitecli.sh` 将从该文件读取。
- **SSH** — 密钥对的私钥部分，对应的公钥已在首次启动时由部署写入 `/var/home/admin/.ssh/authorized_keys`，同时需要 VNet 内部的主机以通过内部地址进行访问。连接用户名为 `admin`，而非 `azureuser`。
- **串行控制台** — 您的交互式 Azure 登录凭据。此处不存在服务主体：F5 企业 Entra 租户不允许创建服务主体，这也是为何本操作不在 CI 中运行的原因。

<Aside type="danger" title="切勿将令牌作为参数传递">
命令行中的令牌会记录在 shell 历史记录和进程列表中，机器上的其他所有用户均可读取。`capture-sitecli.sh` 出于此原因完全拒绝 `--token` 参数，转而通过 stdin 将请求头提供给 `curl`。
</Aside>
