在演示之前先运行这些检查。每项检查都会缩小故障可能存在的范围，因此某项失败能告诉你具体信息，而不仅仅是"出了问题"。

每条命令都会从部署中读取所需内容。设置一次以下变量，其余命令便可直接使用：

```bash
cd terraform
RG=$(terraform output -raw resource_group_name)
RS=$(terraform output -raw route_server_name)
CLIENT=$(terraform output -raw client_vm_name)
DOMAIN=$(terraform output -raw lb_domain)
VIP=$(terraform output -raw vip)
NIC=$(terraform output -raw client_nic_name)
```

## 四项检查，按此顺序

<Steps>

1. **每个站点都是 `ONLINE`。** 如果这一点不成立，下游的任何结论都不可能成立。

   ```bash
   for s in $(terraform output -json xc_site_names | jq -r '.[]'); do
     printf '%s -> ' "$s"
     curl -sS -H "Authorization: APIToken $XCSH_API_TOKEN" \
       "$XCSH_API_URL/api/config/namespaces/system/sites/$s" | jq -r '.spec.site_state'
   done
   ```

   2026-07-28 观测结果，三个 CE：

   ```text
   ar-bgp-eastus01 -> ONLINE
   ar-bgp-eastus02 -> ONLINE
   ar-bgp-eastus03 -> ONLINE
   ```

2. **每个对等会话都在学习到该 CE 的 VIP 通告。** 分别查询每个对等会话——参见下方第一个陷阱，因为演示中最常出现"看起来坏了但实际没坏"的情况就在这里。

   ```bash
   for k in $(terraform output -json xc_site_names | jq -r 'keys[]'); do
     echo "--- ${k}-bgp"
     az network routeserver peering list-learned-routes \
       --name "${k}-bgp" --routeserver "$RS" -g "$RG" \
       --query "RouteServiceRole_IN_0[?network=='${VIP}/32'].{net:network,nextHop:nextHop,asPath:asPath,origin:origin}" \
       -o table
   done
   ```

   2026-07-28 观测结果：

   ```text
   --- eastus01-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.4   64512     EBgp
   --- eastus02-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.5   64512     EBgp
   --- eastus03-bgp
   Net             NextHop    AsPath    Origin
   --------------  ---------  --------  --------
   10.250.0.10/32  10.0.1.6   64512     EBgp
   ```

   三个对等会话，三个不同的下一跳，一个前缀。这就证明了 ECMP 的通告侧。

3. **客户端的有效路由包含每一个下一跳。** 这才是 ECMP 本身，是 VNet 实际编排的结果——不是 CE 声称的内容，而是 Azure 对其所做的处理。

   ```bash
   az network nic show-effective-route-table -g "$RG" -n "$NIC" \
     --query "value[?addressPrefix[0]=='${VIP}/32'].{prefix:addressPrefix[0],nh:nextHopIpAddress,type:nextHopType,state:state}" \
     -o json
   ```

   2026-07-28 观测结果：

   ```json
   [
     {
       "nh": ["10.0.1.5", "10.0.1.6", "10.0.1.4"],
       "prefix": "10.250.0.10/32",
       "state": "Active",
       "type": "VirtualNetworkGateway"
     }
   ]
   ```

   检查点是 `state: Active`，并且 `nh` 中每个 CE 都有一个条目。**顺序没有意义，也不稳定**——Azure 在不同调用之间返回的顺序不同，所以要统计数量，而不是与上一次运行结果作比较。本应有三个下一跳却只有一个，意味着某个 CE 停止了通告，而第 2 步能指出是哪一个。

4. **VIP 能提供流量服务。** 从客户端 VM 发起，并且**带上 `Host` 头**——参见第二个陷阱。采样量要足以发现问题：即使在下文所述的收敛窗口内，几十次请求也会显示为 100 %。

   ```bash
   az vm run-command invoke -g "$RG" -n "$CLIENT" \
     --command-id RunShellScript --query "value[0].message" -o tsv \
     --scripts "ok=0; fail=0
                for i in \$(seq 1 60); do
                  c=\$(curl -s -o /dev/null -m 5 -w '%{http_code}' \
                        -H 'Host: ${DOMAIN}' http://${VIP}/)
                  [ \"\$c\" = 200 ] && ok=\$((ok+1)) || fail=\$((fail+1))
                done
                echo \"OK=\$ok FAIL=\$fail\""
   ```

   2026-07-28 观测结果：

   ```text
   VIP with Host header: OK=60 FAIL=0
   bare IP (no Host): 404
   ```

</Steps>

## 陷阱：某个对等会话只显示一条路由，而这是正确的

`list-learned-routes` 的作用范围限定于你指定的那个对等会话。它报告的是**该**对等体所通告的内容，而不是 Route Server 的整张路由表。

因此单独查询一个对等会话只会返回经由单个下一跳的一条 VIP `/32`，很容易将其解读为"只有一个 CE 在通告——其他都挂了"。其实什么都没挂。其他通告在各自的对等会话上可见，这正是第 2 步循环遍历的内容。

无法通过单个对等会话查询来确认 ECMP。要么遍历每个对等会话，要么读取客户端的有效路由表——后者可在一次调用中显示合并结果。

## 陷阱：裸 IP 请求返回 404

负载均衡器基于 `Host` 进行匹配。VIP 并不是一个会向任何连接到该地址的客户端提供服务的虚拟服务器。

以下两项结果来自针对同一健康部署的同一次运行：

```text
curl -H "Host: $DOMAIN" http://$VIP/   ->  200   (60 of 60)
curl                     http://$VIP/   ->  404
```

**裸 IP 返回 404 恰恰证明路径是通的**——请求到达了 CE，CE 的代理作出了响应，并因没有匹配到已配置的域名而拒绝了它。把它当成故障，会让你去排查 BGP，而那里什么问题也没有。

演示过程中同理：如果你在浏览器中直接输入地址，而不是将域名解析到该地址，就会得到 404。

## VIP 在最初的四十五分钟内丢弃请求，之后恢复正常

在全新构建的环境中，自 CE 达到 `ONLINE` 起，大约最初 45 分钟内 VIP 会丢失一小部分请求，之后便干净地提供服务。从客户端 VM 发起、全部带 `Host` 头的 1,470 次请求测量结果如下：

| 时间窗口 | 请求数 | 失败数 | 比率 |
| --- | --- | --- | --- |
| ECMP 建立后的最初约 45 分钟 | 570 | 12 | **2.11 %** |
| 随后的 23 分钟 | 900 | **0** | **0.00 %** |

每一次失败都是 `curl: (28)`——零字节接收的超时——而不是 HTTP 错误状态码。最后一次失败发生在 ECMP 建立后约 43 分钟。在那 900 次干净请求中，有 400 次使用 30 秒超时运行，每一次都在 2 秒内完成，因此并没有因超时过短而掩盖任何问题。

**源站不是原因。** 一批直连源站的对照请求（`terraform output -raw origin_ip`，绕过 VIP）在与失败的 VIP 批次*并发*运行时，120 次全部成功。故障出在 VIP、ECMP 或 CE 路径中的某处。

有两点特意不这么描述：

- **它不是稳态缺陷。** 它会完全消失并保持消失。已经运行了一小时的演示不存在这个问题——上文检查 4 在已运行数小时的环境上是 60 次全部成功。
- **它无法归因于某个特定 CE。** 该拓扑中没有任何机制提供逐节点的 HTTP 侦听器，因此无法把丢弃的请求绑定到丢弃它的那个节点。CE 的外部接口根本没有 HTTP 侦听器——只有 VIP `/32` 会响应。

它在另一个租户中的全新重建环境上也能复现，因此它伴随拓扑而来，而非环境所致。

<Aside type="caution" title="不要只采样 40 次请求就断定一切正常">
即使在失败窗口内，40 到 50 次的批量测试大多数时候也显示为 100 %。正是因此，这个问题最初被误判为持续存在的低比率故障，后来又被误判为完全没有故障。请采样 100 次以上，并分成时间上彼此间隔的批次。
</Aside>

## 另外两个测量陷阱

两者都在本环境中给出了看似确凿的错误答案，而且都不明显。

- **从 VNet 内部探测，而不是从你的工作站。** 企业代理可能会自行在常用端口上完成 TCP 握手，因此工作站探测会把实际已关闭的端口报告为**开放**。从工作站探测 CE 公网地址时，端口 80 和 443 显示为开放；而从 VNet 内部探测时它们是关闭的。请使用客户端 VM。
- **CE 上的 22 端口只在内部（SLI）地址上响应。** 从客户端 VM 探测时，每个 CE 的内部地址会返回 OpenSSH 横幅，而其管理地址和外部地址则超时——用作对照的未使用地址同样超时。eth0 被重命名为 `a-i-eth0` 且不承载主机 IP，因为数据平面占用了它。因此，探测你所熟知的那个节点地址，无法说明该节点的 SSH 状态。

<Aside type="danger" title="切勿硬编码 CE 内部地址——每次重建都会重新分配">
Azure 不会保留内部子网中哪个 CE 获得哪个地址。2026-07-28 观测结果显示，重建之后三个 CE 分别持有 `10.0.3.7`、`10.0.3.5` 和 `10.0.3.4`：既不按节点顺序，也不连续，并且与之前所持有的地址不同。测试客户端自身的 NIC 位于同一子网，并曾持有某个 CE 之前使用过的地址。

请读取它们，而不是记住它们：

```bash
terraform output -json ce_sli_private_ips
```

如果手头没有 Terraform 状态，就按 NIC 名称向 Azure 查询——NIC 名称*是*稳定的：

```bash
az network nic show -g "$RG" -n "<vm-name>-internal-nic" \
  --query ipConfigurations[0].privateIPAddress -o tsv
```

连接到一个凭记忆得来的地址，会把你送到错误的节点、一台并非 CE 的 VM，或者哪儿也去不了——而最后这种情况看起来和"SSH 未启用"一模一样。
</Aside>
